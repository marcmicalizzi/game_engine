# content/muscle: the muscle line tier's qualification corpus

The trajectories the authoring track qualified the line tier's law and scheme against, with the held-control Radau reference's samples as the oracle. Today that is one source packet: 39 synthetic trajectories (the five original cases, an offset pulse, an active wave, and sixteen parameter corners in a step and a passive variant). `systems/muscle/tests/corpus_tests.cpp` replays every case on every build from its archived static start and holds it to the D20 gates ([muscle](../../docs/subsystems/muscle.md#the-corpus), [ADR-0055](../../docs/adr/0055-the-muscle-line-tier-scheme-schedule-and-failure-semantics.md)). The corpus is also the **only source of qualified domains** the validator accepts: each packet names the domain its rows belong to, and its distinct parameter-set identities, with their nineteen values, are that domain's. Today the one domain is `synthetic-study-only` version 1, 17 identities. A named muscle's calibration qualifies as a new packet in `sources.json` and a run of the script, not as an engine edit (roadmap C55).

## The files

- `sources.json` — **written by hand**: the source packets, each with its `id`, its `domain` (`id` and `version`), its `sources` and its `labels`. A source is a file relative to the authoring track's `06-muscle-activation`, with its `role` and the SHA-256 it must have: `cases` (a CASES.json: per row the inputs, the archived static start, the gate limits, the reference throughput and the per-row hashes), `samples` (the same rows' trajectories with their held-reference samples), and any number of `labels` (a result's `summary.json` with the result `manifest` that must list it, and optionally the `declaration_sha256` and `execution_manifest_sha256` the summary must name, when a review fixed them). `labels` is the decision that sets the cases' classes: its `known_limit_work` and `known_limit_force` lists, and `tolerance_result`, the label result a labelled case's tolerance is measured from. Also `reference_model_sha256`, the reference law's identity, which every label summary that carries one must match. The first packet, `synthetic-r010`, is r010's CASES.json, r007's handoff corpus.json and the r009 S and r010 summaries, under D25's labels.
- `corpus.json` — the index (`format_version` 2): `packets` (each with its domain and case count); `qualified_domains`, a list of `{id, version, identities}`, each identity its `parameter_sha256`, the case and row that first carried it (`source`), and its **full parameter set**, the fourteen `fiber` and five `series` values under the authoring names the identity is taken over; `sources`, every file read with its packet, role and SHA-256; and per case its `domain` and `domain_version`, its parameter identity, the gate limits (`force_N` = max(1% of the reference's peak tendon force, 0.5% of F0), `fiber_m` = 0.5% of the optimal fiber length, `work_J` = 1e-3 of the reference throughput), `reference_throughput_J`, the sample count, `held_samples_sha256`, and its provenance (`source`: the packet, the cases file and row, the samples file and trajectory). The row count is the sources', never a constant.
- `cases/<case>.json` — one case: `inputs` (the control segments, the path, the fiber and series parameters, the initial activation, `end_s`, the identities) and `initial_state` (the archived static start: activation, fiber length and the reference's outputs there), both copied whole from the cases source; then `columns` and `samples`, one row per held-reference sample: `time_s`, `activation`, `fiber_length_m`, `tendon_force_N`, `passive_fiber_energy_J`, `tendon_energy_J`, and the ledger's five channels from t = 0, `external_work_J`, `active_output_work_J`, `dissipation_J`, `active_throughput_J`, `external_throughput_J`. The samples are t = 0 and every 1/480 s parent endpoint of the case's ticks — 289 for the 0.6 s cases, 193 for `shortening` and `lengthening` (0.4 s) — and `offset_pulse` has two more at its off-tick control changes, which the nominal comparison skips.
- `expectations.json` — (`format_version` 2) each case's class, as its packet's labels set it: `qualified` (passes all three gates) or `known_limit_work` / `known_limit_force` (passes the other gates, its failing metric at most 1.5 times its tolerance result's number, which the row names in `tolerance_result`), with every label result's per-row numbers prefixed by the result's name (`r009_force_error_N`, `r010_first_sample_force_error_N`, ...), and `provenance`, per packet, the decision, its description, and each label result's summary, result manifest, declaration and execution manifest. For `synthetic-r010` the labels are D25's (the review of r010's result, 2026-10-14): 35 cases qualified, and `corner_00/02/04/06_step` `known_limit_work` — work-only misses at r009 S and at r010, order-limited at either order, the control step's own transient. `known_limit_force` is still a class the test reads, and no case carries it any more: `corner_04/06_passive` were force-only misses at r009 S's first nominal endpoint, a start-up transient r010's first-tick schedule removed, and D25 made them qualified. A labelled case that passes everything is allowed and printed. A label changes only by the owner's review of a result; D25 is the one that has.

## The validator's table

`tools/muscle-corpus.ps1` also writes `systems/muscle/src/qualified_domains.inc`, which `validator.cpp` includes: every domain's identities, each with its nineteen values as **hexadecimal floating literals** (`0x1.f4p+9`, the source token `1000.0` beside it in a comment). The hexadecimal form was chosen over 17 significant digits because a compiler reads it with no rounding at all, so the literal is the token's binary64 whatever the compiler's decimal conversion does; .NET's parse, which the script converts with, is correctly rounded. The file is generated and committed, never edited by hand, and `tests/validator_tests.cpp` holds it to this directory's `corpus.json` bit for bit: the same domains and identities in the same order, and every one of the 323 values equal to core/json's reading of the corpus's token.

## The tabulated path kind

A case's `inputs.path` is one of the reference's analytic kinds (`constant`, `linear`, `sine`, sampled in absolute time; the synthetic rows) or **`tabulated`**: `{"kind": "tabulated", "tick_hz": 60, "samples": [[length_m, rate_m_s], ...]}`, the musculotendon length and its rate at every tick boundary from t = 0, one more sample than the case has ticks. The corpus test consumes a table through the runtime's own `HermitePath` (a cubic Hermite per tick from the two boundaries' lengths and rates), which is what the engine feeds the tick from a routed path; a tabulated case's tick count is its sample count less one, an analytic case's its `end_s` at 60 Hz, and either must match the oracle's samples.

## What a named packet must contain

A named muscle's calibration and reference trajectories arrive in the same record shape as the synthetic packet, and qualify without an engine edit when they hold:

- the **nineteen values** (fourteen `fiber`, five `series`) under the authoring names, every one a finite number, none negative zero, no other field;
- the **parameter identity** in the canonical form the authoring track's r012 wrote down (`IDENTITY.md`): SHA-256 of the two groups with recursively sorted keys, compact separators and CPython's float text — the script re-derives it from the copied values and stops on a difference;
- the **path** as a `tabulated` table, length and rate at every tick boundary, or an analytic kind;
- the **cases and samples** in the CASES-and-samples shape: per row `case`, `inputs` (with `parameters`, `parameter_sha256`, `path`, `control_segments`, `initial_activation`, `end_s`), `initial_state`, `limits`, `reference_throughput_J`, `held_sample_count` and the three per-row hashes, and per trajectory the same `inputs` and its `held_reference_samples` at t = 0 and every parent endpoint;
- case names that no other packet uses, and a `domain` id and version in `sources.json`: a new domain or a new version, never an identity added silently to `synthetic-study-only` version 1.

The record shape, the D20 gates and the model identity do not change with a packet; a change to any of those is a declaration on the authoring side and an engine change, not data.

The r009 declaration r009 S's numbers belong to is `a204e8cf9c94ff609e44e32534f8b3ebee1bf8fd19f5513e828aff7beaf46232` (its `DECLARATION-MANIFEST.json`, as the summary records it). r010's are the declaration `295c4b55f12d580ec0ee3d5e6e3c3207fb71961c7184a3f5dd8613a911d333c3` and the execution manifest `bcbafc7d7a206cb403e1027f50bdd4846ca8817f034c25fe9fa778749ae92ce4`, which `sources.json` names, so the script stops unless the r010 summary names exactly the two D25 reviewed, since another r010 file would be evidence nobody reviewed.

**Every number is copied as text, never recomputed**: the script writes each source number's own token, so a value here is the reference's binary64 exactly, and the corpus test checks that every number in `corpus.json` and the case files survives a parse-print-parse through `core/json` bit for bit. The script stops on any source whose SHA-256 is not the one `sources.json` names, and re-derives each row's three hashes — `inputs_sha256`, `initial_state_sha256` and `held_samples_sha256` — and its `parameter_sha256` from the data it copies, under the authoring side's canonical form (sorted keys, compact separators, Python's number text), stopping if any differs (156 for the synthetic packet: 117 row hashes and 39 identities): the copy is checked against the hashes the sources carry, not only against the files' hashes. It also stops on an identity that names two parameter sets, a case name two packets use, and a row count that differs between a packet's sources.

To regenerate: `tools/muscle-corpus.ps1 -Authoring <path>` (PowerShell 7, no Python; `-Sources`, `-Out` and `-Table` name other places). A new or changed source is an edit to `sources.json`, and this README's table records the synthetic packet's hashes by hand.
