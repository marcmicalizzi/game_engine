# 10 — Roadmap, Risks, Experiments, and Deferred Decisions

## 10.1 Staging principles

- Every phase ends with a demo that runs headless and windowed, a green test suite, and a batch of ADRs.
- Agent access is built in each phase for that phase's systems, never deferred to a later "tooling phase".
- No phase depends on runtime LLM tiers above 0.
- Linux builds and tests run in CI from Phase 1, so parity gaps are visible as they appear rather than discovered at the end.
- This is a long-running side project; phases are sized so that each leaves something working and documented if work pauses for months.
- Estimates are given in **focused weeks**: wall-clock time with agents working continuously against the full weekly token budget and the project owner reviewing daily. Side-project pacing stretches the same work over roughly 2–3 years. An earlier draft gave figures 2–3× longer; the owner's experience is that agent-driven work lands well under estimates of that kind, so these are deliberately tighter and will be recalibrated against actuals after Phase 0 and Phase 1 ([§10.8](#108-calibrating-the-estimates)). Rendering phases keep wider ranges because each iteration needs GPU time on a single machine plus visual judgment; foundations, tooling, validators, and content compress the most.

## 10.2 Phases

**Phase 0 — Foundations (2–4 focused weeks)**
Core: platform, memory, containers, math, topology-aware jobs, logging and telemetry, schema IDL and code generation (C++, JSON, JSON Schema, docs), serialization, IDs, hashing. Foundation: VFS and async I/O, tunables registry and bench harness, Tracy, protocol skeleton (JSON-RPC, sessions), headless runner, test infrastructure, CI (build, test, sanitizers), repository conventions (`MODULE.toml`, layer check), `AGENTS.md`. Document model v0: objects, layers, transactions, structural diff.
Exit: an agent opens a session, creates objects, commits, diffs, and rolls back through `engine-cli`. **Met 2026-09-15** by the end-to-end suite in `apps/engine_cli/tests`, one process per step; remaining Phase 0 items (Tracy, CI on both platforms, the schemac negative-test harness) follow.

**Phase 1 — Renderer core (6–10 focused weeks)**
Thin RHI over Vulkan 1.3/1.4, render graph, bindless, GPU-resident scene; Windows and Linux CI from the first commit of this phase. Cluster build pipeline (meshoptimizer clusterlod) → pages → streaming. GPU culling and LOD selection; mesh-shader visibility buffer (the software rasterizer exists but stays off the critical path after E1, ADR-0024); material resolve; simple direct lighting. The per-frame deformed-vertex pool for skinned and cage-deformed clusters ([04 §4.3](04-renderer.md#43-geometry)) with the **E25 spike** of the cage-to-cluster transfer path, because the pool's layout and the per-vertex binding slot in the cluster pages cannot be retrofitted once assets are built. Reference GPU path tracer with shared BSDFs; FLIP harness. `ViewSet` multi-view; extreme-resolution CI; capture API with entity-ID buffer. Experiments E1, E2 (month 1), E9, E25 (spike).
Exit: test scenes render through clusters at 4K and 11520×2160; reference comparisons run nightly; agents can capture and benchmark. **"Agents can capture and benchmark" met 2026-09-17**: the renderer left `apps/engine_view/main.cpp` for `systems/renderer`, and engine-host became its second consumer with `render.load`, `render.capture` (color, the entity-ID buffer, depth, normals), `render.benchmark` (GPU milliseconds per pass from the timers, CPU milliseconds per frame, visible pairs), and `render.compare` (FLIP, PSNR, SSIM) — offscreen, with no window in the process, and skipping with a distinct protocol error where there is no GPU, so the same suite runs on the hosted runners and on the GPU machines ([subsystems/renderer](../subsystems/renderer.md), [apps](../subsystems/apps.md)). The remaining two exit clauses need the reference path tracer and the scene corpus of [§4.8](04-renderer.md#48-reference-renderer-and-objective-optimization), and the nightly job that runs them. **"Reference comparisons" met 2026-09-18, "nightly" waits for a runner**: the GPU path tracer, the versioned corpus in `content/test-scenes/`, `render.evaluate` (both pictures, both heat maps, FLIP/PSNR/SSIM and the times in one call), and `tools/ci/reference-compare.ps1` are built and run locally today, with the corpus at 0.0014–0.035 FLIP against a noise floor of 0.0011–0.0027 at 1024 samples ([renderer](../subsystems/renderer.md#reference-renderer)). The nightly step is in `.github/workflows/gpu.yml` and is **queued on a runner label that no machine carries yet** (`rtx`): the reference traces the frame's cluster acceleration structures, and both registered runners are a Maxwell and a Pascal, so pointing it at them would only produce a report of five skips. Registering one RTX machine closes this clause; nothing in the script or the workflow waits on anything else. **"Pages → streaming" met for geometry on 2026-09-18**: the cull pass runs the CPU model's drawing rule against a per-page residency word, writes deduplicated page requests to a bounded feedback buffer, and the CPU reads them back one frame slot later and fills a pool of fixed-size slots under a per-frame upload budget ([04 §4.3](04-renderer.md#43-geometry) step 3 and [§4.9](04-renderer.md#49-streaming-and-residency), [renderer](../subsystems/renderer.md#geometry-streaming-the-gpu-half-of-pages-and-residency)). **The I/O half followed the same day**: `io::FileHandle` reads a file by byte range on the Efficiency pool, `geometry::ClusterFileReader` addresses a `.clusters` container's sections, and a page is three or four ranged reads whose bytes are released from the host once the scene is on the GPU — so this is now a budget on host memory as well as on device memory, measured at 307.5 → 303.5 MB of working set on the FlightHelmet grid at a quarter budget. What the phrase still does not cover, and what carries into Phase 2 with the residency manager it names: the *peak* host footprint is unchanged, because the load still materializes the merged streams before releasing them (the merge takes its bases from the stream lengths rather than from the page table); there is no decompression and no prediction from observer velocity; geometry is one of the three page types [§4.9](04-renderer.md#49-streaming-and-residency) asks one manager to hold; and a budget tight enough to evict every frame currently loses the device when the ray-tracing chain runs beside it ([renderer](../subsystems/renderer.md#geometry-streaming-the-gpu-half-of-pages-and-residency) records the reproducer).

**Phase 2 — RT lighting (6–10 focused weeks, overlaps Phase 3)**
AS management and BLAS budget manager; cluster-AS path (`VK_NV_cluster_acceleration_structure`) plus the first-class fallback; in-house ReSTIR DI; GI cache and ReSTIR GI; RT reflections and shadows; in-house baseline denoiser; plugin interface for vendor upscalers and neural reconstruction; ray budget scheduler; attention-region foveation and per-view VRS.
Exit: hybrid RT at the targets in [04 §4.1](04-renderer.md#41-goals-targets-non-goals) on at least NVIDIA hardware.

**Phase 3 — World and simulation core (4–8 focused weeks, parallel with Phase 2)**
ECS (flecs evaluation → decision), persistent store (SQLite event log, projections, snapshots), sim scheduler, timing wheel, LOD framework and materialization contract, tile streaming, Jolt, Recast, basic animation (standard skeleton, clips, blending), audio, input and replay, save/load with migration corpus, world-mutation guard, dependency substrate v1 for the content build. Experiment E6.
Exit: a tile-streamed world with 10^5 scheduled NPCs, deterministic replay, save and load.
*Status (2026-09-25): two of the three clauses are met for the headless tile-streamed world.* **Save and load**: `session.save_game` and `session.load_game` save a running streamed world and continue it in a new session, byte for byte through a save, a load and a save, with a migration corpus of two format versions loaded on every build ([world](../subsystems/world.md#save-and-load), [ADR-0042](../adr/0042-a-save-is-the-store-the-document-and-the-drivers.md), proposed). **Deterministic replay**: a streamed world run straight through, saved and loaded partway, and replayed from tick 0 with the same input log reaches one pinned persistent-state hash on MSVC, Clang and GCC, in CI ([05 §5.10](05-simulation.md#510-determinism-and-replay)). **Not met: 10^5 scheduled NPCs.** The replay world holds 48 places and 6 carts; the scheduler, the timing wheel and tier assignment have been measured at 10^5–10^6 in isolation (E6, [sim](../subsystems/sim.md#performance-notes)), but no world with 10^5 NPCs scheduled has been streamed, saved or replayed, and nothing yet schedules an NPC's routine through the wheel from a document.
*Status (2026-09-25, evening): the third clause is met, and with it Phase 3's exit.* **10^5 scheduled NPCs**: the npc capability ([npc](../subsystems/npc.md), [ADR-0045](../adr/0045-routines-are-data-with-a-closed-form.md), proposed) schedules `engine.npc.Resident` records' routines through the wheel from the document — a routine is a table of rows with a closed form, one timer per scheduled resident, a summarizer that meets sim.md's five conditions exactly, tiers from the observer set through the existing hooks — and a generator writes 10^5 of them with their places. The clause's test, `apps/engine_cli/tests/npc_replay_tests.cpp`, streams 10^5 residents round declared observers, saves at tick 300, loads, and replays from tick 0 to one persistent-state hash, with the routines' clock five seconds before seven so the seven o'clock transitions — timers fired, records moved, state written back — are inside the run; its hash, **53a8c6295e6d4e78**, was pinned on MSVC on 2026-09-25 and reproduced by Clang 18 and GCC 13 in the Linux container and by GCC 14 at the v2 baseline on the server (the cloud environment that wrote the test could build neither engine-host nor the store, so its first run was here, and it found its own clock wrong: at 07:00 exactly nothing transitions in ten game-seconds). What 10^5 costs is [E38](../experiments/e38-scheduled-npcs.md): 40 µs a tick at LOD2, 0.33–0.76 µs a transition, and two costs outside the capability that keep a streamed 10^5 from its budget — a tile's activation classified the whole document (37 ms a tile) and a resident at LOD3 is 1.5 KB of in-memory document. The first is gone (2026-09-25): the document keeps a tile index and a tile pass takes its records from it, 0.58 ms a tile at 10^5 on the i9 where the same pass was 60 ms ([E38's follow-up](../experiments/e38-scheduled-npcs.md#follow-up-2026-09-25-a-tile-pass-costs-the-tile-and-the-schedule-index)). And the boundary npc.md stated — a resident is materialized by its record's tile, so one that walked to work in a tile nobody simulates stays a record after its routine has it home in a live one — is closed by the capability's schedule index, consulted on every activation and by a watch timer on each resident that is not held ([npc](../subsystems/npc.md#the-schedule-index)): 0.34 ms an activation and 1.1 µs a watch at 10^5, the replay's hash unmoved, and a second replay whose residents cross the simulated edge pinned at `16a407bfad492334`.

**Phase 4 — Agent API v1 and editor (3–5 focused weeks, parallel)**
MCP bridge, the full day-one operation set, validation service, describe and query, semantic and visual mips v0, task ledger, editor client with review queue, first single-agent loop building a small scene end to end. Experiment E5.
Exit: an agent constructs a small level from a text brief using only structured feedback and captures; a human reviews through the editor queue.

**Phase 5 — Content pipeline and generation (4–6 focused weeks)**
glTF import, validators, provenance, procedural generators (terrain, scatter, roads, building kits), generator-service interface with first ML backends, the character standard (skeleton, body, slots), TTS. **The character standard is a design rather than a phrase** ([ADR-0032](../adr/0032-characters-are-parameter-vectors.md), [ADR-0033](../adr/0033-content-classes-and-view-policies.md), [07 §7.11](07-content-pipeline.md#711-characters)): one canonical topology per base family, the three-layer parameter model with a declarative rig, three multilinear macro corner axes over region-masked detail channels with height and proportion carried as skeleton parameters instead, a joint regressor, graft modules over section masks, the layered material compositor, the bake as a `derived` node keyed by the parameter hash, and the numeric validators and content classes that make a character checkable without looking at it — all of it optional per asset and per game. Its two renderer prerequisites, the **morph vertex stream** and the **staged deform chain**, are built in Phase 1 beside the deformed-vertex pool, for the same reason the E25 spike is there: a per-vertex stream slot cannot be retrofitted once assets are built. Experiments E10 and E7 (scripting decision), and E27–E29 for the characters.
Exit: agents produce a validated environment from generator rules and generated props.

**Phase 6 — Destruction, simulation depth, NPC routines (4–6 focused weeks)**
Support graphs, pre-fracture build, collapse simulation, damage-state persistence, nav rebuild and region graph, NPC routines at all tiers, economy and faction event consumers, story-protection policies. Deformable surfaces v1 (snow and sand deformation maps with decay and the coarse CPU grid), gameplay soft bodies via Jolt XPBD, cosmetic GPU cloth ([05 §5.13](05-simulation.md#513-deformable-surfaces-and-soft-bodies)). **Deformable volumes v1** ([05 §5.14](05-simulation.md#514-deformable-volumes), ADR-0026): SDF lattice cages as a content-build `derived` step with authored overrides, the Jolt XPBD backend behind the engine's own abstraction, attachment and layers, soft-against-rigid and soft-against-own-skeleton contact, the simulation LOD tiers with hysteresis and blending, damage as constraint edits on the cage, adhesive contact, and strain-driven surface detail. This phase is where physics and animation depth land, and the deformation work belongs with destruction because they share the constraint-edit representation. Experiments E19–E24 and E26.
Exit: destroy a building; NPCs and quests respond; leave and return; state persists correctly. Walk through snow and it stays trampled until it refills. Walk across a dune crest and it slumps; leave for a game-week and the dune has moved ([13 §13.5](13-reference-consumer-games.md#135-mapping-to-the-roadmap)). Press a creature against a rock and its flesh spreads and recovers; walk a crowd of them past every simulation LOD tier boundary without a visible pop; reach into a cavity in a wall and the tissue resists, clings on the way out, and settles back ([13 §13.7](13-reference-consumer-games.md#137-reference-interactions)).

**Phase 7 — The small game (8–12 focused weeks; bounded by human review bandwidth)**
The desert-survival consumer game ([13 Consumer A](13-reference-consumer-games.md)) ships first as the Phase 6 exit demo made playable: seeded runs, score, leaderboard-ready replays. Then thesis → world → spine → regions with the multi-role agent pipeline; playtest bots at scale; polish; ship a 1–3 hour game with runtime LLM at Tier 0 and telemetry for the long tail.
Exit: playable, reviewed, benchmarked.

Rough total: 30–48 focused weeks with Phases 2–4 overlapping (7–11 months of continuous full-budget effort), or 2–3 years at side-project pacing.

## 10.3 Ordering and dependencies

```
P0 foundations ──┬─► P1 renderer core ──► P2 RT lighting ─────────────┐
                 ├─► P3 world/sim core ───────────────────┬─► P6 destruction/NPC ─► P7 game
                 └─► P4 agent API (doc model from P0; grows with P1/P3) ─┤
                                    P5 content pipeline (P1 clusters, P3 DDC, P4 API) ─┘
```

Critical paths: P0 → P1 → P2 → P7 for fidelity; P0 → P3 → P6 → P7 for the systemic world. P4 must be usable by the end of P1, or agents cannot help build P2 and P3.

## 10.4 Major technical risks

| Risk | Impact | Mitigation |
|---|---|---|
| Cluster geometry ↔ RT integration (LOD mismatch, AS cost, vendor lock) | The core renderer promise | Resolved for NVIDIA by E2 (ADR-0025): cluster acceleration structures from the frame's cut, pixel-identical to raster, 3× less memory than KHR structures; the KHR fallback is built and tested for every other RT GPU; cluster format encodable to future formats |
| Software rasterizer plus mesh-shader pipeline complexity | Phase 1 slip | Resolved by E1 (ADR-0024): hardware-only in Phase 1; the software rasterizer is an experimental path with a test that keeps it pixel-compatible |
| Agent-written C++ defect rate | Everything | Sanitizers, fuzzing, codegen, small modules, strict layering; measure per phase; Rust as the fallback |
| Engine generality without a game | Wasted systems | The two consumer games in [13](13-reference-consumer-games.md) are the concrete consumers (Desert Survival is the recommended first shippable; Island City the density benchmark); Phases 6–7 drive requirements; no system without a consumer in the roadmap |
| ML asset quality and pass rate | Content phase | E10 early; validate-and-repair pipeline; procedural for volume; character standardization |
| Creative coherence | Game quality | Canon graph, validators, review roles, human gates; measure review rejection rates |
| Proprietary vendor SDKs vs. the permissive engine license | Distribution | In-house ReSTIR and denoiser; vendor SDKs as developer-supplied plugins ([08 §8.8](08-toolchain.md#88-engine-license-and-dependency-policy)) |
| Cross-vendor cluster AS may never come to Vulkan | AMD/Intel get fallback-quality RT geometry | Fallback path is first-class; D3D12 backend trigger in [08 §8.3](08-toolchain.md#83-graphics-api) |
| Performance-regression noise on shared GPUs | False alarms, ignored alerts | Dedicated runners, medians, significance tests |
| Persistence and migration debt | Save compatibility | Migration corpus from Phase 3 |
| Runtime LLM cost and latency | Feature creep | Tier 0 mandatory; telemetry-driven compile-to-content |
| Windows/Linux feature drift | Linux parity | Vulkan on both; CI on both from Phase 1; capability tiers make gaps explicit rather than silent |
| Deformable cage authoring cost | Content throughput; the primitive is worthless if every asset needs a simulation expert | Cages are generated from the mesh's signed distance field at content build, with authored overrides only where the default is wrong ([07 §7.10](07-content-pipeline.md#710-deformable-volume-assets)); validators name the failing vertices, attachments, and layers instead of failing vaguely; the character standard ([07 §7.7](07-content-pipeline.md#77-ml-asset-generation-novelty-content)) means one cage per body archetype is retargeted rather than authored per character; E19 and E23 measure how far the defaults get before an override is needed |
| Soft-against-soft contact cost | Crowds of deformable characters; any two-creature interaction | Out of v1 by decision (ADR-0026): v1 is soft-against-rigid and soft-against-own-skeleton, which already covers grabbing, pressing, impact, and contact with the world. Pair cost is quadratic in the interacting set, so it gets its own experiment and its own budget before it is built ([§10.6](#106-decisions-deliberately-deferred)) |

## 10.5 Experiments to run before committing

| ID | Question | Method | Decides |
|---|---|---|---|
| E1 | Where is the hardware-vs-software raster crossover for small clusters on target GPUs? | Prototype both on synthetic cluster sets; measure at 4K and 11520×2160 | Whether software raster is in Phase 1. **Done 2026-09-16** ([results](../experiments/e1-raster-crossover.md), ADR-0024): no crossover down to 0.7 px triangles on the RTX 5090; hardware wins 1.5–3×; Phase 1 is hardware-only, the software rasterizer stays experimental |
| E2 | Cluster AS on D3D12 (NVAPI) vs Vulkan (NV extension): build cost per frame, memory, image match against raster | One-month spike from `vk_lod_clusters` and RTXMG samples at Phase 1 start | Graphics API; AS strategy. **Done 2026-09-17** ([results](../experiments/e2-cluster-acceleration.md), ADR-0025): the Vulkan extension works through ray queries with no API change; cluster structures take 2.9–3.3× less memory and build 1.2–2.6× faster than KHR structures for the same cut on the RTX 5090, trace at the same speed, and match the raster picture to the pixel; per-frame GPU-driven builds are the next step |
| E3 | Do runtime-selected kernel variants beat one good default by more than 10% across two or more machines? | Tunables harness on culling, transform, and animation kernels | Whether calibration Stage 3 is built |
| E4 | Canonical-JSON layered document vs LightUSD as authoring format: agent edit, diff, merge round trips | An agent performs 20 edits and 3 merges; measure errors and diff readability | Document format |
| E5 | Can one agent build a small level using structured feedback and captures only? | Phase 4 exit demo; count tool calls, errors, human interventions | Agent API gaps |
| E6 | flecs at 10^5 entities with relationships plus 10^6 LOD3 records in SQLite | Synthetic sim; measure tick time, memory, query latency | ECS choice; store design. **Done 2026-09-18** ([results](../experiments/e6-ecs-store.md), [ADR-0028](../adr/0028-ecs-and-persistent-store.md), **Accepted**): flecs holds 10^5 entities with relationships and a hierarchy at **2.45 ms a tick single-threaded**, 162 B an entity over 1,346 tables; SQLite holds 10^6 LOD3 records in a 245 MB file, 20–32 µs a point lookup, 293–411 µs a tile, 61.7 k event appends a second, with WAL + `synchronous=NORMAL`, 8 KiB pages, a page cache sized to the indices, one transaction a tick and writes clustered by tile. **The decision: flecs stays unwrapped, and the engine owns five seams** — components come from the schema IDL, systems register through `sim::SystemDesc`, identity is `Id128`, mutation from outside a system goes through `WorldCommands` at a phase boundary, and `flecs.h` is confined by the linter to `domain/ecs`, `systems/` and `game/`. The cost of ever replacing flecs is therefore "rewrite the system bodies and queries", which no wrapper avoids either. The spatial-query answer is a relationship or a structure the system owns, never a per-entity component, and relationship cross-products now have a debug watchdog on the table count. **The worker-scaling half was re-measured on a verified-quiet machine on 2026-09-18, the published table was withdrawn, and the cause was then found and fixed the same day** ([ADR-0030](../adr/0030-flecs-workers-are-long-running-pool-jobs.md)): hosting flecs' workers as *per-tick* jobs cost 1.6–2.2 ms a tick and made every worker count slower than one, because `ecs_set_task_threads` rebuilds the whole worker set inside every `ecs_progress` (5,400–50,000 critical-section round trips a tick against 4–18 with `ecs_set_threads`) and every re-dispatch pays the pool's wake. Not the job system — a bare submit-and-join round trip is 1.2–5.7 µs and `core/jobs` was not changed. flecs' workers are now **long-running jobs on the performance pool**, inside a budget the application sets, and the tick scales: **2.42 ms at one worker to 1.25 ms at four and 1.02 ms at sixteen**, within a few percent of flecs' own OS threads at every count. The budget's cost is that a world holds `workers - 1` pool threads for its lifetime |
| E7 | The same gameplay feature in C++ hot-reload, Luau, and C#: agent error rate, iteration time, performance | Three agent-written implementations | Scripting layer. **Measured in part 2026-09-24** ([Luau half](../experiments/e7-luau-spike.md), [scripting](../subsystems/scripting.md)): the Luau arm is built — sandbox, memory limit, deterministic step budget, bindings generated from the schema, hot reload, a `.d.luau` type file — and measured for cost (call round trip, property reads, `on_tick` over 1,000 and 10,000 instances in one VM against one VM each, compile, reload, GC pauses, binary size, VM floor) and for what the type file catches in three agent-written quest conditions (6 of 7 seeded mistakes statically, against 1 of 7 without it). **Not answered**: the C++ hot-reload and C# arms, so no comparison of error rate or iteration time; the write-up recommends the C++ arm next and deciding C# from it ([08 §8.2](08-toolchain.md#82-gameplay-and-scripting-layer)) |
| E8 | A 1–3B parameter quantized open-weights model on efficiency cores or spare VRAM while rendering: latency, throughput, intent accuracy, effect on frame time | llama.cpp harness inside the engine | Whether Tier 1 is worth building |
| E9 | Three-view surround vs Panini projection at 11520×2160: cost, TAA and denoiser behavior, per-view VRS gains | Phase 1 test scenes | Multi-view design. **Measured 2026-09-18** ([results](../experiments/e9-multi-view.md), [04 §4.6](04-renderer.md#46-extreme-displays) status note) — not Done, because three of the question's clauses cannot be asked yet. **The design is settled**: `renderer::ViewSet` is N views (1..8) over one `GpuScene` with one culling hierarchy, one top-level structure built from the union of the views' cuts and one residency budget, and the per-frame working set is **slices of the scene's shared buffers** rather than a set per renderer — a visibility id is an index into the visible list, so one list is what lets any view's resolve decode any id. A surround is three **off-axis frusta**, not three cameras: flat, they are the three thirds of one wide frustum and the centre one is bit-for-bit a single view of one monitor. Costs on the RTX 5090 at 11520×2160, over a 25-instance FlightHelmet grid and a 2.1 M-triangle heightfield: three views cost **1.10–1.15×** one wide view of the same content, almost all of it the Hi-Z build (three pyramids are 36 dispatches against 14); the cull is the one pass that scales with the view count, 0.032 → 0.09 ms, because every view dispatches one thread per scene pair. **The surprise: turning the side monitors 30° inward made the frame 11% *cheaper* while drawing 18% more pairs** — a flat 140° projection magnifies its edges by 1/cos²θ and the fragments it spends there are waste, so the physically correct picture is also the faster one. **Panini costs about 2× the baseline it replaces** (the same field of view needs a rectilinear source 1.975× as wide at d = 1, and the Hi-Z scales by 2.04×), of which the resample itself is **0.055 ms**; it is a perceptual choice and not a performance one, and it is the only one of the two available on a physically flat ultrawide. The peripheral LOD multiplier takes **18% and 28%** off the frame's visible pairs at 2× and 4× (51% and 82% off the side views themselves) and does not show in the clock, because 80% of both frames is Hi-Z and resolve — the corpus is too light to be geometry-bound, which is the measurement's own biggest caveat. Multi-view ray tracing costs **memory, not time**: the trace and build times are unchanged, but the structures must be sized `views * pair_count`, +688 MiB on the helmet grid. **Open, and needing something that does not exist**: TAA and denoiser behavior across a view seam (there is no TAA, no denoiser and no upscaler to run per view); per-view VRS (`ViewQuality::shading_rate` is carried and consumed by nothing — `VK_KHR_fragment_shading_rate` is not in the RHI); per-view internal resolution and ray budgets; multi-window presentation; and one view-agnostic RT cut instead of the union, since two views at different LOD thresholds put two levels of one surface into the same structure |
| E10 | Pass rate of ML-generated props through validators; repair yield | 200 generated props | Generation pipeline design. **First data point, 2026-09-19 — n = 1, and it already moved the engine.** One Meshy-generated character (539,596 triangles, one material, three embedded textures) imported through `domain/assets` and clustered with **zero warnings**, 12,699 clusters in 14 levels, and drew correctly only at the finest LOD: at the default threshold it was covered in fragments of the wrong texture. The cause was not the asset — it was the engine's LOD simplifier collapsing across the atlas's island edges, fixed the same day ([04 §4.3](04-renderer.md#43-geometry), [geometry](../subsystems/geometry.md#what-the-simplifier-is-given-and-why)). The lesson for this row, before the 200: **"passes the validators" and "renders correctly" are different questions**, and the second one needs a picture compared against a *different* configuration of the engine, not against the engine's own output at the same settings — every picture test the project had compared like with like, which is why a defect this visible survived. The validator the run actually asks for is an **atlas-fragmentation** measure ([07 §7.4](07-content-pipeline.md#74-validation-rules-automatic)), since island size now sets how far a mesh can be simplified at all. **n = 2 since the same day**: the owner supplied the same character remeshed to 224,783 triangles and auto-rigged (28 joints, one clip), which also imported with zero warnings and showed the same defect. So the early reading of this row is: what ML generation costs is not triangles, which the engine already handles, but **atlas quality**, and the pipeline's answer to that has to be in texture space (repack, or per-level bakes), because the geometry builder has now gone as far as it can. **Measured 2026-09-22, first pass: 6 of 20 props pass (30%)** ([results](../experiments/e10-generated-props.md)) — not Done: 20 of the 200, one image model and one service, with Tripo (same images, generated by hand) and the local image-to-3D models still to come, and no repair chain yet to measure a yield. ## 10.6 Decisions deliberately deferred

Scripting language (E7); game UI framework (RmlUi vs in-house); D3D12 backend timing (trigger in [08 §8.3](08-toolchain.md#83-graphics-api)); runtime LLM tiers above 0 (E8, under [12-ai-usage-policy](12-ai-usage-policy.md)); dynamic runtime fracture; soft-against-soft deformable contact (its own experiment and budget when a use case needs it, [05 §5.14](05-simulation.md#514-deformable-volumes)); finite-element deformation and tetrahedral cages (a backend and a cage kind behind the same abstraction; fTetWild if they arrive); motion matching; neural radiance cache; Bazel; tile size and number of sim LOD tiers (per game); multiplayer transport and replication (readiness rules only for now, [05 §5.12](05-simulation.md#512-multiplayer-readiness)); a mobile renderer tier (a later consideration only, not a first-class target; revisited after Phase 7); consoles (out of scope); OpenUSD as the authoring format (rejected pending E4; LightUSD for interop only).

**Direction note, 2026-09-25: what a console path would look like, recorded so the early prerequisites are not missed.** Asked by the owner as a question for after the plan is done, and answered here because two of its prerequisites are cheap now and expensive later. The engineering shape: the core stays platform-agnostic under Apache-2.0 and every console layer lives in a separate tree under the platform holder's NDA, never in this repository, as console licensees do (registration, dev kits and certification are business steps that gate all of it). **PS5** is Zen 2 (x86-64-v3 compliant, so [ADR-0031](../adr/0031-minimum-cpu-x86-64-v3.md)'s baseline holds), RDNA2 with hardware ray tracing but no cluster acceleration structures (the KHR-shaped fallback the renderer keeps pixel-identical is the path that matters there), a proprietary graphics API (a second RHI backend), a fast SSD with hardware decompression that the page-based streaming and the derived-data cache fit, and an object-based audio renderer (Tempest), which is the external object renderer the audio direction note of [05 §5.11](05-simulation.md#511-integration-notes) already names as the decode stage's fourth output. **Switch 2** is an Ampere GPU (mesh shaders and ray tracing cores exist, at a fraction of the desktop budget; a Vulkan driver exists beside the native API, so the Vulkan RHI maps) on **ARM Cortex-A78C** with 12 GB of shared memory, so it needs a second CPU baseline: every kernel that selects x86 intrinsics needs a NEON path behind `platform::cpu_features()`, and the content-build determinism rule has to hold across instruction sets (contraction is already off; libm differences are already a known hole). The two prerequisites worth doing early: **an ARM64 CI target** (a Linux aarch64 container or an ARM runner) so ISA assumptions surface while the code is small, and **RHI hygiene**: on 2026-09-25 Vulkan types appear in 11 of `domain/gfx`'s 17 public headers and in 21 places of the renderer's public headers, which a second backend cannot tolerate; retiring that leak is the first step of the D3D12 decision this section already defers, and it is cheaper before the renderer grows. **Decided 2026-09-25: the owner moved retiring the leak into the near plan, ahead of and independent of any second backend** — the public headers of `domain/gfx` and `systems/renderer` lose their Vulkan types behind engine-owned handles, formats and descriptors, the backend-facing header set is named explicitly and confined to the modules that own a device or a swapchain, and a lint rule keeps it so — **done 2026-09-25**, with no picture or pass timing moved ([gfx](../subsystems/gfx.md#the-rhi-surface-and-the-backend-surface), [08 §8.3](08-toolchain.md#83-graphics-api)'s status note); the ARM64 CI target stays deferred until a Switch-class target is in view. The vendor-upscaler plugin interface of Phase 2 is what DLSS on Switch 2 would use. Nothing here changes the plan's order.

**Direction note, 2026-09-25: macOS, last of the targets, for two reasons that are not gaming.** Asked by the owner and recorded at low priority — after every other target. It is **not a rendering target**: MoltenVK exposes neither mesh shaders nor ray queries, and Metal on Intel Macs has no 64-bit image atomics, so even the baseline vertex tier's visibility buffer would not run there; Apple silicon has the atomics and mesh shaders in Metal, but a real macOS renderer would be a Metal backend behind the RHI, which is the second-backend question this section already defers. What would have value: (1) **portability and CI** — Apple clang with libc++ is a third compiler and C library for the content build's byte-identity claim, and GitHub's hosted macOS runners are Apple silicon, so one macOS job is the ARM64 CI target the console note above asks for early, with no hardware bought and the GPU tests skipping as they do on hosted Linux; (2) **the art workflow** — in the adoption scenario where others use the engine, much graphics design is done on Macs, and the headless half (the content build, engine-host and engine-mcp, the document tooling, the validators, the render methods wherever a device exists) running beside the artist's tools would let assets be built, validated and previewed where they are made. The owner's 2018 Intel Mac mini is available for that headless half and for `package-tests.ps1` runs. Cost when it is done: a preset for AppleClang, whatever libc++ brings out, and a workflow entry — a day or two of agent work. Nothing here moves ahead of any other target.

## 10.7 Decisions to record as ADRs now

1. Headless engine server with a versioned protocol; the editor is a client.
2. Text-serialized, layered, stable-ID document as the source of truth; canonical JSON.
3. Event-sourced persistent state in SQLite with snapshots; non-determinism is logged, not re-executed.
4. One dependency substrate with `derived` and `authored` node classes.
5. The cluster as the universal geometry unit; hybrid renderer; reference path tracer from day one.
6. Vulkan primary behind a thin API-neutral RHI, Windows first and Linux second; D3D12 deferred.
7. C++20 core; schema code generation; no hand-written serialization.
8. Slang for all shaders.
9. Multi-view rendering as a first-class concept; the HUD coordinate model.
10. Fixed-step deterministic sim; LOD as a system property; the materialization contract.
11. Tunables registry now; calibration runner only with evidence.
12. Jolt, Recast, SDL3, Tracy, mimalloc, SQLite, meshoptimizer adopted; flecs pending E6.
13. C++20 as the only core language; no Rust track.
14. Apache-2.0 engine license and the dependency policy that follows: no copyleft, proprietary SDKs as developer-supplied plugins only ([08 §8.8](08-toolchain.md#88-engine-license-and-dependency-policy)).
19. Efficiency as a first-class metric: hot-type size table, the engine container set with banned node-based standard containers, and the "fast path is the easy path" API rule ([11 §11.2](11-performance-principles.md#112-data-layout-and-footprint-first), [11 §11.9](11-performance-principles.md#119-performance-by-default-for-engine-users)).
20. The world reacts physically by default: destruction on unless opted out per object, per material category, or globally; deformable surfaces as a deformation layer over terrain with a deterministic coarse CPU grid for gameplay; soft bodies via Jolt XPBD for gameplay and GPU position-based dynamics for cosmetics ([05 §5.13](05-simulation.md#513-deformable-surfaces-and-soft-bodies)).
21. Deformable volumes as a first-class physics primitive: animation and deformation are separate, the cage is separate from the render mesh, the solver is abstracted with Jolt XPBD first, simulation LOD is mandatory, gameplay-relevant cage state is deterministic CPU state, and damage is constraint edits ([05 §5.14](05-simulation.md#514-deformable-volumes)).
15. AI usage policy: agent outputs are content and code, never training data; runtime models are unmodified third-party open weights ([12-ai-usage-policy](12-ai-usage-policy.md)).
16. Multiplayer-readiness rules enforced from Phase 3 ([05 §5.12](05-simulation.md#512-multiplayer-readiness)).
17. No hidden limits: checked compact types with fallback, tile-relative positions, 64-bit time, every limit a configurable budget ([11 §11.6](11-performance-principles.md#116-no-hidden-limits)).
18. Frame budgets are merge gates from Phase 1 ([11 §11.1](11-performance-principles.md#111-culture-budgets-are-gates)).

## 10.8 Calibrating the estimates

What actually bounds the schedule, in rough order:

1. **Human review bandwidth.** The owner is the creative director and the final reviewer of visual quality, design, and taste. Once agents run ahead of review, the queue, not the agents, sets the pace. The review-queue tooling in [06 §6.10](06-agent-tooling.md#610-multi-agent-roles-review-and-the-human-director) exists to keep this bottleneck as wide as possible.
2. **One GPU for the high end.** Renderer iterations, benchmarks, golden-image runs, and experiments serialize on a single RTX 5090. A second machine (a GTX Titan X at 2560×1440, on a Haswell-class board once the owner's board swap lands; an i7-980 until then) is the minimum-hardware target and the natural self-hosted CI runner for the baseline tier once it is set up; it cannot stand in for the RT and mesh-shader work. That machine and a headless Skylake Xeon server with a GTX Titan Xp are the two baseline-tier self-hosted runners of `.github/workflows/gpu.yml`, which runs the suite on real Vulkan weekly and on demand ([docs/ci/self-hosted-runners.md](../ci/self-hosted-runners.md)). Headless `sim` work does not compete for either. **Both of those machines are below the engine's promised minimum CPU and build the x86-64-v2 presets [ADR-0031](../adr/0031-minimum-cpu-x86-64-v3.md) added** — the desktop until its board swap, and the Xeon E5-2670 (Sandy Bridge: AVX, no AVX2) indefinitely. So v2 is a second build configuration the project maintains for its own test hardware, and since the Xeon is the only Linux machine here with a GPU, letting v2 rot would mean losing Linux GPU coverage entirely rather than losing one old box.
3. **Experiments that need iteration** (E1, E2, E10) and vendor features that arrive on their own schedule.
4. **Visual judgment in renderer debugging.** Captures, the entity-ID buffer, FLIP against the reference path tracer, and golden images shrink this, but do not remove it.

Mechanism: every phase records its estimate and its actual in the task ledger. After Phase 0 and again after Phase 1, the remaining estimates are rescaled by the observed ratio, separately for rendering and non-rendering work, since they are expected to compress differently.
