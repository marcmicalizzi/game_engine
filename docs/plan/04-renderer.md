# 04 — Renderer Architecture

## 4.1 Goals, targets, non-goals

Goal: maximum image quality per millisecond, with runtime cost independent of source-asset complexity.

Provisional targets, to be confirmed once hardware is in hand:

| Configuration | Target |
|---|---|
| 2560×1440, RTX 4070-class | 60 fps hybrid RT, internal resolution ≥ 67% with upscaler |
| 2560×1440, GTX Titan X (Maxwell) on a Haswell-class board: the project's minimum test machine (no mesh shaders, no ray tracing) | Runs the baseline tier: cluster geometry through a vertex-shader path, raster lighting, no RT; 30 fps at reduced settings is the bar |
| 3840×2160, RTX 4080/5080-class | 60 fps hybrid RT with upscaler |
| 11520×2160 surround, RTX 5090-class | 60 fps target, 30 fps floor; attention region at full shading rate, peripheral views at reduced rate |
| Reference mode | Converged path trace; minutes per frame acceptable |

The surround row is the configuration the project owner plays on. Well-optimized non-RT titles reach 70–100 fps there today and poorly optimized ones fail to hold 30; closing that gap with ray tracing enabled is the renderer's defining target.

**The minimum CPU is separate from the minimum GPU, and is x86-64-v3** ([ADR-0031](../adr/0031-minimum-cpu-x86-64-v3.md), 2026-09-19): AVX2, FMA, BMI1/2, F16C, LZCNT and MOVBE, which means Haswell (2013) or Zen and newer, with 4 cores and 8 threads as the floor and 6+ cores recommended. Every CPU Windows 11 supports has it, and most current games list a 2015–2017 part as their minimum. Until 2026-09-19 the floor was the i7-980 (Westmere, 2010, SSE4.2 and no AVX) in the minimum test machine, and the whole tree was compiled to it. The project's **test** hardware is still below v3 — that desktop until its board is swapped, and the Xeon E5-2670 (Sandy Bridge, AVX but no AVX2) in the headless Linux GPU server, which is not being replaced — so the `*-v2` presets are a supported test configuration rather than a one-machine exception ([self-hosted runners](../ci/self-hosted-runners.md)). They are not a second shipping tier: a game built on this engine promises v3. **The minimum GPU does not move:** the GTX Titan X (Maxwell) is still the baseline tier, and a v3 build runs on it unchanged, because the CPU baseline and the GPU capability tier answer different questions.

Non-goals for v1: primary-visibility path tracing in real time; non-RT GPUs as a quality target (they run the baseline tier); mobile; CPUs below x86-64-v3.

## 4.2 Frame architecture

GPU-driven, visibility-buffer, hybrid lighting. Passes, as render-graph nodes:

1. **Scene update.** Upload instance transform deltas; rebuild TLAS; BLAS builds/refits under budget (async compute, starts early).
2. **Culling.** Instance frustum + occlusion (Hi-Z from the previous frame, reprojected); hierarchical cluster culling + LOD selection by projected error; output cluster lists split by size class.
3. **Visibility raster.** All clusters via mesh shaders writing a 64-bit (depth | instance | triangle) visibility buffer with atomics; a compute software rasterizer for small clusters exists but measured slower than the hardware path at every triangle size on the development GPU (E1, ADR-0024) and stays experimental. Two-pass occlusion: pass 1 draws last frame's visible set and builds Hi-Z; pass 2 tests the rest.
4. **Material resolve.** Per pixel: reconstruct barycentrics from triangle ID, fetch attributes, evaluate material into a compact GBuffer. Materials are bindless; per-material-ID tile classification keeps divergence low.
5. **Lighting.** RT direct lighting with ReSTIR DI over all emitters; RT GI via ReSTIR GI fed by a world-space radiance cache; RT reflections (rough surfaces fall back to the cache); RT shadows for key lights; sky/atmosphere; volumetrics.
6. **Denoise and compose.** Per-signal denoisers, then composition.
7. **Forward/transparent.** Particles, glass, water (raster; RT refraction optional).
8. **Post and upscale.** Exposure, bloom, DoF, motion blur, then TAAU/DLSS/FSR/XeSS, optional frame generation.
9. **UI** in HUD coordinate spaces ([§4.7](#47-ui-coordinate-architecture)).

Infrastructure: render graph (automatic barriers, transient aliasing, async-compute scheduling); fully bindless resources; GPU-resident scene (instances, materials, lights, clusters in device buffers); indirect execution everywhere; one **GPU residency manager** spanning geometry pages, texture pages, and acceleration structures.

## 4.3 Geometry

**The cluster is the universal unit** of rasterization, streaming, and acceleration-structure construction. This is the near-irreversible renderer decision.

**Build** (content-build step, a `derived` node):
1. Split the mesh into clusters of ≤128 triangles (meshoptimizer).
2. Group 4–8 adjacent clusters (graph partition; METIS or own), simplify the group with locked boundaries (meshoptimizer simplifier), re-split into clusters. Repeat to a root. The result is a DAG where each cluster stores its own error bound and its parent group's. meshoptimizer 1.2 ships a cluster-LOD DAG builder (`clusterlod.h`) that covers steps 1–2; start from it rather than writing a partitioner. NVIDIA's open `vk_lod_clusters` sample (Apache-2.0) is the closest public reference for continuous cluster LOD with streaming, mesh-shader raster, and cluster-AS ray tracing from one hierarchy.

   **Status (the simplifier is attribute-aware and seam-aware, 2026-09-19).** "Simplify the group" was positions only, and that is not a neutral default: clusterlod's default configuration runs meshoptimizer's **permissive** mode, which is defined as "a collapse may cross an attribute discontinuity unless the vertex is tagged", and nothing was tagged. On the Khronos samples — a handful of large clean atlas islands — it never showed; on the first machine-generated character (539 k triangles, an atlas of thousands of small islands, imported with zero warnings) the default LOD threshold painted the clothing with skin and the skin with clothing, because a simplified triangle interpolated its UVs between two unrelated islands. The builder now tags every UV seam (and every skin-weight split) and passes the UVs as a weighted attribute; the attribute error lands in `ClusterLodDesc`'s own errors for free, because meshoptimizer's reported error already includes the attribute quadric, so nothing in the cut, the GPU pass or the page layout changed. **The measurement that changed the design:** weighting the *normals* as meshoptimizer's own sample does costs between 28% and 4× the triangles at a fixed threshold — a 129×129 heightfield draws all of itself where it drew half — and does **nothing** for the atlas defect, which the seam rule fixes entirely. So the normal weight is off by default, and `--lod 1` still means what it meant. The seam rule's own cost is about one DAG level and a doubling of the coarsest cut. `k_cluster_cache_version` is 7. See [geometry](../subsystems/geometry.md#what-the-simplifier-is-given-and-why) for the mechanism, the alternatives measured, and the CPU metric (`measure_lod_attribute_error`) the fix is judged by, and [07 §7.4](07-content-pipeline.md#74-validation-rules-automatic) for the validator this leaves open — beyond some island size no seam-respecting simplification can be right, and the honest fix is in texture space.
3. Quantize positions per cluster (16-bit relative to cluster bounds), pack normals/tangents/UVs; store clusters in fixed-size **pages** (~128 KB) ordered by DAG locality for streaming. *(Pages built and stored: `geometry::build_cluster_pages`, 2026-09-17. **GPU feedback and residency built 2026-09-18**: the cull pass runs `select_lod_streaming`'s rule against a per-page residency word and writes the pages it could not refine into to a bounded request buffer; the vertex, attribute, triangle and float-position streams are a pool of fixed-size slots with the descriptors' offsets patched on arrival. [renderer](../subsystems/renderer.md#geometry-streaming-the-gpu-half-of-pages-and-residency), [gfx](../subsystems/gfx.md), [apps](../subsystems/apps.md).)*
4. Per cluster: bounds, normal cone, LOD error, material ID, page/offset, and precomputed data for cluster acceleration-structure construction.

**Runtime**
- LOD selection: a cluster is drawn if its own projected error is below threshold and its parent group's is not. Evaluated per cluster in parallel; the hierarchy is only used for culling.
- Per-instance culling BVH over cluster groups, traversed with persistent threads or a multi-dispatch work queue.
- Small-triangle path: experiment **E1** measured a compute software rasterizer against mesh-shader rasterization from 4.5 px down to 0.7 px triangles on the RTX 5090 and found hardware faster throughout (docs/experiments/e1-raster-crossover.md); the software path is kept for other hardware and a smarter revision, not for Phase 1.
- Streaming: the GPU writes requested page IDs to a feedback buffer; the CPU streams pages (DirectStorage with GPU decompression where available); the residency budget evicts by last use.

**Special cases**
- **Deformed clusters (skinning and deformable volumes)**: one path, one per-frame deformed-vertex pool. A compute pass writes deformed positions for the clusters of the current LOD cut only, so deformation costs the cut and not the source mesh — the same rule that makes source-asset complexity irrelevant everywhere else in this section. Skinning reads bone matrices; a deformable volume ([05 §5.14](05-simulation.md#514-deformable-volumes)) reads the tick's cage state through per-vertex cage bindings built with the clusters and streamed in their pages ([07 §7.10](07-content-pipeline.md#710-deformable-volume-assets)); a mesh may use both, skinning first and cage displacement on top. Cluster detail is one level lower than a static mesh at the same screen size. On the ray side the deformed positions feed **cluster acceleration-structure templates**: a template is built once per cluster from the bind-pose topology and instantiated per frame from the deformed vertices (`VK_NV_cluster_acceleration_structure`, [§4.4](#44-ray-tracing), ADR-0025), which is what the extension's templates exist for. The KHR fallback rebuilds or refits the instance's bottom-level structure under the BLAS budget manager, with a bounded count per frame. The transfer pass optionally writes one more channel: for a volume whose asset declares it, each deformed vertex also gets its **local cage strain**, a scalar (compression along the largest principal direction) or a packed symmetric tensor, in a parallel array of the same pool. The channel exists only for volumes that declare it, so the pool's stride and the pass's bandwidth are unchanged for everything else ([05 §5.14](05-simulation.md#514-deformable-volumes), [07 §7.10](07-content-pipeline.md#710-deformable-volume-assets)).

  **Status (E25 spike, 2026-09-17).** The pool, the pass, and both ray-side variants are built and measured ([results](../experiments/e25-deformed-clusters.md), [gfx](../subsystems/gfx.md)). What the spike settles: the pool is unquantized `float3` and per frame; a cluster's vertices are contiguous in it, so a cluster acceleration-structure record can address them directly; the pass is one workgroup per visible cluster dispatched indirectly from the cull pass's own count; and templates beat rebuilding a deformed cut by about 4× at a small memory cost. What it does not settle: the per-vertex cage binding slot in the cluster page format and the strain channel, which need the content-build side of [07 §7.10](07-content-pipeline.md#710-deformable-volume-assets); and the deformers measured are procedural stand-ins, not a solver reading cage state.

  **Status (the pool is budgeted and suballocated per frame, 2026-09-18).** E25's block-per-instance layout made the pool a function of the population — 12.2 MB for 1,024 foxes, 110 MB for 64 FlightHelmets, 1.7 GB had the thousand been helmets — to write the ~1,300 clusters a frame draws. It is now a **budget** suballocated per frame by a prefix sum on the GPU over the cull pass's own visible list, one block per (instance, cluster) pair, which is the smallest unit that keeps a cluster's vertices contiguous; the address moved from `gfx::DeformDesc` to `MeshDesc::deform_slots[visible entry]`, `DeformDesc` fell to 16 bytes, and `MeshDesc` is still 64. A pair the budget cannot fit draws its **rest pose** and is counted, which is the whole of the overflow behaviour. Measured: 64 helmets allocate 8 MiB instead of 110 MB and their cut occupies 0.8 MB of it; the pool pass itself moved by under 5%, and the allocator costs about 5 µs per 1,000 visible entries. See the addendum in [E25](../experiments/e25-deformed-clusters.md) and [renderer](../subsystems/renderer.md#the-deformed-vertex-pool).

  **Status (skinning, 2026-09-17).** "Skinning reads bone matrices" is no longer a stand-in: `deform.slang` has a `k_deform_skin` mode and the data path behind it is closed end to end — glTF skins and influences in `domain/assets`, an optional eight-byte `geometry::SkinBinding` per vertex carried through welding, the LOD DAG, both merges, the streaming pages and the container, `domain/anim` for the pose and the 3×4 skinning matrices, and a gfx test that holds the GPU to `anim::skin_positions` within 1e-5 on a two-bone cylinder (measured 1.2e-7). The binding stream rides on `MeshDesc` (it is per vertex, so it is the mesh's, shared by a whole crowd) and the bone matrices on `DeformDesc` (a pose is per instance), which is the split that makes a hundred characters from one mesh cost one stream plus 48 bytes a joint each. See [anim](../subsystems/anim.md), [gfx](../subsystems/gfx.md), [05 §5.11](05-simulation.md#511-integration-notes).

  **What skinning settles about the crack rule.** E25 found that a deformed position must be a function of quantities every copy of a surface point shares, and that a *normal* is not one. A skinned position is a function of the rest position and the per-vertex binding, and both are: duplicates across clusters hold the same bytes, and a simplified level inherits them from the original source vertex rather than recomputing them. So skinning is position-only and cannot tear — the constraint is on the cage binding of [07 §7.10](07-content-pipeline.md#710-deformable-volume-assets), not on skinning, and the weld keeps two coincident vertices with different weights apart so the pipeline never merges them. ~~**Not yet:** skinning *and* a cage deformer on one instance ("skinning first and cage displacement on top" above) needs a second pass or a wider kind field — `DeformDesc::flags` has exactly two bits of kind.~~ **Closed, 2026-09-20**: see the chain status note below.

  **Status (morph channels and the deform chain, 2026-09-20).** Two consumers wanted per-vertex morph targets — facial and corrective animation, and parametric characters — and, like the skin binding before them, they change the geometry format, so they are in before assets exist. A morph channel is a **sparse, cluster-ordered** per-vertex displacement stream with 16-bit deltas on a per-channel scale; the weld key sees a vertex's deltas and `ClusterLodOptions::morph_seams` stops permissive simplification merging back what the weld kept apart; seven append-only container kinds carry it and `k_cluster_cache_version` is 8 ([geometry](../subsystems/geometry.md#morph-channels-the-second-per-vertex-deformation-stream)). Quantization is free rather than cheap: the worst delta error on the fixture is an eighth of the *position* grid's own, because a channel is stored on a grid over its own extent while the position it modifies is on one over the whole mesh's.

  The deform pass is now a **chain of four optional stages in a fixed order** — static shape, pose morphs, skinning, procedural cage stand-in — which is what closes the paragraph above. The order is the data's: a morph delta is authored in bind space and must precede the skin; a cage acts on the posed surface. The static stage's result is kept in a budgeted per-instance cache so a character's body costs a dispatch when it is authored and nothing after that, and its contract is written as "a rest-space displacement source evaluated per render vertex" rather than "per-vertex deltas on the render mesh", because a **control-mesh binding** is the second source and is the stated follow-up ([gfx](../subsystems/gfx.md#the-deform-chain)). Shading normals go through the chain as deltas and come out in a second pool: a plane normal reconstructed in the resolve is flat by construction, and a morphing surface is exactly where that shows. The pool is null for a scene with no channels, so every existing picture is byte-identical — with one measured exception, the two *procedural* stand-ins, which moved by one level of 255 on a handful of pixels because the same expressions are compiled in a larger module (PSNR 106.5 dB, SSIM 1.000000, FLIP mean 4.3e-7; [E25](../experiments/e25-deformed-clusters.md)'s addendum). **Still open:** a morphed mesh is not streamed and says so; the bound an instance is culled by prices every pose weight at 1; and the per-instance cache is budgeted but not yet evicted under pressure. **2026-09-22:** the chain has been through real files — the four Khronos morph samples — which found three bugs (a single morphed glTF could not load, a skinless file's weight clips were dropped, and an asset's default weights were ignored), all fixed with tests; on them the stream costs 8.3 bytes a cluster vertex where it matters (MorphStressTest, +9.8% on the container), the static stage lands inside the position grid's own step of the file's float answer, and on a 1,024-instance crowd the static cache saves a quarter of the pass while the pool's serial allocator, not the morph stages, is the frame's largest deform cost ([apps](../subsystems/apps.md#the-morph-samples-end-to-end)).

  **Status (an animated character, end to end, 2026-09-18).** The sentence above that said "nothing outside a test animates a skinned instance" is spent: `engine-view --mesh <skinned.gltf> --animate [clip]` draws one, and `--grid-instances n` draws n² of them out of phase ([apps](../subsystems/apps.md), [renderer](../subsystems/renderer.md#skinned-instances)). What the join added, and what it deliberately did not: a `SceneInstance` names a joint count and a bounds padding, a frame hands the renderer `std::span<const anim::JointMatrix>` plus one `{first, count}` per instance, and the renderer uploads the span with **one memcpy** into a per-frame-slot region and rewrites its own copy of the deform table — no per-instance upload, nothing allocated in steady state, and no dependency on `systems/animation`, `domain/ecs` or flecs, because the tick is the app's. The one struct change is `gfx::InstanceDesc::bounds_padding`, a mesh-space slack the cull pass adds to the cluster sphere and both LOD spheres, which is how a swinging limb stays out of the culler's way; it took a pad word, so the record is still 96 bytes and every rigid picture is byte-identical (FlightHelmet through `hw`, `vertex`, `rt --shadows rt`, `--deform wave` and `--views surround3`: same SHA-256, PSNR null, SSIM 1, FLIP 0). Ray tracing needed nothing at all — a skinned instance is a deformed instance, so `--rt-templates` instantiates the cut's templates from the pool and a shadow is cast by the moving character. **Still open:** ~~the pool is allocated per deformed instance's *whole* mesh~~ — **closed 2026-09-18**, see the pool's status note in §4.3 above; and nothing drives `sim::TierAssignment` from the renderer's camera, so a crowd is animated at LOD0 whatever it is worth.
- **Terrain**: heightfield with clipmap/CDLOD tessellation and virtual texturing initially; rocks and cliffs as cluster meshes. Converting terrain itself to clusters is a later optimization. The terrain displacement also reads the per-tile **deformation map** (snow, sand, and mud depth; grass bend direction) described in [05 §5.13](05-simulation.md#513-deformable-surfaces-and-soft-bodies), so walking through snow costs a texture fetch in the terrain path rather than geometry edits.
- **Vegetation**: instanced cluster meshes near, impostors far; alpha-tested foliage in RT via opacity micromaps.
- **Materials**: PBR (GGX metal/rough, clearcoat, sheen, transmission, subsurface approximation), layered via a small material graph compiled to Slang. The same BSDF code is used by the reference path tracer.
- **Strain-driven surface detail**: a material may declare a **strain input** and blend authored wrinkle and fold normal and displacement maps by local compression, reading the per-vertex strain the deformation transfer wrote for that instance. Folds therefore appear at material resolution instead of requiring a cage fine enough to resolve them, which is what keeps a coarse cage affordable on a hero asset ([05 §5.14](05-simulation.md#514-deformable-volumes)). Opt-in on both sides and checked as a pair at content build: a material without a strain input compiles with no fetch and no blend, so the resolve costs exactly what it costs today for every material that does not ask.

## 4.4 Ray tracing

**Acceleration structures**
- TLAS rebuilt every frame (cheap at 10^4–10^5 instances).
- BLAS strategy is backend-dependent behind one interface:
  - **Cluster-AS path**: build cluster-level AS from the *same* clusters the rasterizer selected this frame; assemble BLAS from them. Raster and RT geometry match exactly and share streaming. Availability as of September 2026: NVIDIA only, via NVAPI on D3D12 or `VK_NV_cluster_acceleration_structure` on Vulkan (RTX 20-series and up, driver 570+). Cross-vendor cluster AS is specified in the DXR Tier 2.0 draft (D3D12, preview expected late 2026) and has no Vulkan KHR/EXT equivalent. AMD is pursuing a compressed geometry block format (Dense Geometry Format) for AS builds instead; the cluster format should be encodable to it later. On the primary Vulkan backend this means cluster RT is NVIDIA-only until a cross-vendor extension appears; AMD and Intel take the fallback path, which is first-class rather than an afterthought.
  - **Fallback path** (any RT GPU): per-mesh static BLAS at 2–3 fixed LODs chosen by distance; accept the LOD mismatch and mitigate with ray bias and normal-offset tricks. RT LOD is coarser than raster LOD by design.
- **BLAS budget manager**: per-frame time budget for builds and refits; priority by screen contribution; fast low-quality builds first, background rebuild at high quality when idle. Destruction uses the same manager ([§4.5](#45-destruction-and-acceleration-structures)), and so do deformed instances, whether they instantiate cluster templates or refit ([§4.3](#43-geometry)).

**Lighting techniques: adopt, do not invent**
- Direct: ReSTIR DI. NVIDIA's RTXDI is the reference implementation but is under the proprietary NVIDIA RTX SDKs License, which a permissively licensed engine cannot redistribute ([08 §8.8](08-toolchain.md#88-engine-license-and-dependency-policy)). The algorithms are published; ReSTIR is implemented in-house in Slang with RTXDI as reading material.
- GI: ReSTIR GI plus a world-space radiance cache (hash grid or surfels with multi-frame accumulation). Neural radiance caching later, where tensor hardware exists (NVIDIA's NRC library is experimental and under the same proprietary license).
- Reflections: RT below a roughness threshold, cache lookup above.
- Shadows: RT for the sun and hero lights; ReSTIR-sampled for the rest. **Status (2026-09-17):** the first half is in — the material resolve traces one terminate-on-first-hit ray per light against the same per-frame acceleration structures the raster path selected, so a shadow comes from exactly the geometry and the LOD the picture holds (`engine-view --shadows off|rt`; [gfx](../subsystems/gfx.md), [apps](../subsystems/apps.md)). Hard edges, one ray a light, and no ReSTIR yet. **Direction note, 2026-09-23: shadows without ray queries.** The first GPU run on the project's Pascal box (a TITAN Xp, driver 580) showed what every baseline-tier card will show: acceleration structures and ray-tracing pipelines present through the driver's compute fallback, **no ray queries**, and every ray-tracing consumer in this engine is a ray query. Ray tracing needs an RTX-class card, and a card that has it may still not afford it at a title's target rate, so the baseline tier gets **cascaded shadow maps rendered from the same cull pass and the same rasterizers** the visibility buffer uses: a light-view frustum cull (cones off, LOD from the light's view or the camera's cut re-rasterized), three or four depth cascades, filtered on read. The resolve's shadow query becomes one function with two implementations behind `ResolveParams::shadow_flags`, `--shadows csm` beside `rt`, selected by the tier when ray queries are absent and by setting otherwise. The invariant is the same as for every tier fallback: the shadowed-pixel test compares against the CPU reference with the light removed, with a filter tolerance for the map path, and the ray-traced and mapped shadows of one frame must agree wherever both are defined. The Pascal box is the fixture for it, and the tier rule that called that card `rt` is corrected to key on the ray-query row. Proposed; the CLAS chain and the RT path are untouched. **Status, 2026-09-23:** the tier rule half is done — `rt` is acceleration structures plus ray queries, the TITAN Xp reports `raster` with a verdict sentence naming the missing ray query, and an explicit `--shadows rt` there is refused in that sentence's words rather than drawn without shadows ([gfx](../subsystems/gfx.md#what-a-device-has-to-have), [renderer](../subsystems/renderer.md#the-offscreen-contract)). The same run found the baseline tier could not create a renderer at all (the mesh pipelines were built whatever the path); that is fixed and the card now runs the whole suite ([self-hosted runners](../ci/self-hosted-runners.md#the-first-run-on-the-titan-xp)). Cascaded shadow maps are still proposed.
- Denoising: an in-house SVGF/ReBLUR-class denoiser is the portable baseline. NVIDIA NRD (same license as RTXDI) and vendor neural reconstruction (DLSS Ray Reconstruction on all RTX GPUs via Streamline; AMD FSR Ray Regeneration on RDNA4 only) are optional plugins that the game developer adds under the vendor's license. Intel Open Image Denoise (Apache-2.0) serves the offline reference path.
- Coherence: shader execution reordering where supported; ray sorting by direction and material for GI rays.

**Ray budget scheduling.** Rays per pixel are a function of screen-region importance, temporal stability, surface roughness, and disocclusion. Importance comes from display topology (center view high, periphery low) and from variance estimates. The scheduler is a GPU pass that emits per-tile ray counts consumed by the sampling kernels. This is where "expensive work proportional to perceptual effect" becomes concrete.

## 4.5 Destruction and acceleration structures

- **Pre-fractured** chunk hierarchies (built offline) have prebuilt BLAS per chunk. Destruction changes instance transforms and visibility; no rebuild.
- **Damage-state variants** (intact, damaged, destroyed, rubble cleared) are separate meshes with their own BLAS; distant and persistent destruction swaps variants.
- **Runtime fracture** (if adopted later) produces new meshes → fast low-quality BLAS builds through the budget manager, refit while pieces move, high-quality rebuild once settled.
- Debris bodies are numerous and short-lived: instance them into a shared per-chunk BLAS; drop them from RT after settling and beyond a distance.
- Destruction and deformation meet in one representation: damage to a deformable volume is a constraint edit on its cage ([05 §5.14](05-simulation.md#514-deformable-volumes)), so a weakened or detached region changes the deformed positions the cluster templates are instantiated from, and a chunk that separates becomes an ordinary rigid body the remaining volume collides against.

## 4.6 Extreme displays

- **Multi-view rendering is first-class.** A `ViewSet` is N views sharing one scene, one culling hierarchy, one TLAS, one residency budget. Surround = 3 views with per-monitor frusta; a single ultrawide = 1 view, optionally with a Panini-style projection. Screen-space passes (TAA, SSR, denoise) run per view; RT is view-agnostic.
- **Foveation by attention region**: the user defines an attention region (default: the center monitor for surround, the whole display otherwise). Views or view sections outside it run at reduced internal resolution, coarser VRS rate, smaller ray budget, and cheaper effects (reflection roughness cutoff, volumetric step count, shadow detail). Surround players treat side monitors as peripheral vision, so aggressive cuts there are the expected behavior, not a compromise. The gradient is a user setting; the upscaler runs per view.
- **Presentation**: support both driver surround (one swapchain, views tiled) and multi-window (one swapchain per output). HDR metadata per output.
- **Coordinate hygiene**: no 16-bit screen coordinates anywhere; all screen-space structures are sized from the render config at startup; CI renders at 11520×2160, 7680×4320, 1080×3840 portrait, and 5120×1440 every night.

**Status (E9, 2026-09-18): the `ViewSet` is built and measured; the foveation beyond LOD is not.** [Results](../experiments/e9-multi-view.md), [renderer](../subsystems/renderer.md#multi-view-a-viewset-over-one-scene), [gfx](../subsystems/gfx.md), [apps](../subsystems/apps.md). What exists: `renderer::ViewSet`, N views (1..8) over one `GpuScene` with one culling hierarchy, one top-level structure built from the union of the views' cuts, and one residency budget; `surround3` with per-monitor off-axis frusta, bezel correction and a side yaw; `panini` as one oversampled rectilinear source resampled inside the resolve; `--views`/`--side-yaw`/`--panini-d`/`--peripheral-lod` on engine-view and the same settings over the protocol; per-view statistics in both. The per-frame working set is slices of the scene's shared buffers rather than a set per renderer, because a visibility id is an index into one visible list and the RT union is a contiguous range of it.

What the measurement settles, and what it does not. **The multi-view design is settled** and the cost of the split is small: three views of the same content cost 1.10–1.15× one wide view, and splitting the same total pixels into three Hi-Z pyramids and three resolves adds 0.023 ms and nothing respectively. **Turning the side monitors 30° inward made the frame 11% cheaper while drawing 18% more pairs**, because a flat 140° projection magnifies its edges by 1/cos²θ and spends its fragments there on nothing — the physically correct picture is also the faster one, which is the result this section was written to find. **Peripheral LOD moves the geometry**: 2× and 4× on the side monitors take 18% and 28% off the frame's visible pairs, and on these two corpora that does not show in the clock, because 80% of the frame is Hi-Z and resolve and neither scene is geometry-bound at this resolution. **Panini is a perceptual choice, not a performance one**: matching the same horizontal field of view needs a rectilinear source 1.975× as wide at d = 1, so it costs about twice the raster of the distorted baseline it replaces, of which the resample itself is 0.055 ms. Three things this section asks for are *not* built and are the honest gaps: the shading-rate half of foveation (`ViewQuality::shading_rate` is carried and consumed by nothing; it needs `VK_KHR_fragment_shading_rate` in the RHI), per-view internal resolution and ray budgets, and multi-window presentation with per-output HDR metadata. And "screen-space passes run per view" cannot be tested at all yet, because there is no TAA, no denoiser and no upscaler to run — which is why E9's row stays **Measured** rather than Done. One finding to carry into Phase 2: a union of *per-view LOD cuts* in one structure means two views at different thresholds put two levels of the same surface into it, so "RT is view-agnostic" above has to become one RT cut at a view-agnostic threshold, not the union.

**The extreme-resolution picture changed the same day, and it is the finding that outlives the layout work.** E9's real result was not about views at all: at 11520×2160 **80% of both corpora's frames was Hi-Z and resolve, and most of that was fixed** — the pyramid cost the same 0.59 ms whether the frame was full or empty, and the resolve 45% of its loaded cost with nothing in it. That is a statement that this renderer was paying for *pixels it was not drawing anything on*, which at 48:9 is most of them. Three changes took it back ([E9's sequel section](../experiments/e9-multi-view.md#after-the-fixed-cost-work-2026-09-18-later-the-same-day), [gfx](../subsystems/gfx.md), [renderer](../subsystems/renderer.md)): the Hi-Z folds six mips per workgroup instead of one dispatch per mip, the resolve discards an empty pixel rather than writing a sky the clear already wrote, and the resolve skips a 32×32 tile the Hi-Z build tells it holds nothing — a mask that is free, because the build already reads every word of the visibility buffer and its workgroup *is* a tile. All three keep the picture byte-identical and the visible set exactly equal, which is the bar an optimization under this section has to clear.

Measured on the RTX 5090, `--raster hw --shadows off`, 120 frames, twice: the whole frame at 11520×2160 fell **1.16 → 0.97 ms** on the helmet grid and **1.04 → 0.87** on the heightfield as one wide view, **1.27 → 1.02** and **1.31 → 0.96** as a three-monitor surround, and an **empty** frame fell **0.78 → 0.55**. At 3840×2160 the frame fell by a third and at 1920×1080 by a third again, because a small pyramid's cost is dispatch count rather than bytes. The fixed share of a 11520×2160 frame is now 57% rather than 66%. **What is still fixed is the Hi-Z**, which is unchanged at 0.43 ms whether the frame is full or empty and runs at about 86% of the card's memory bandwidth: it reads the whole visibility buffer twice a frame and writes a full-resolution mip 0 the cull pass reads, and both are the resolution. Every way found so far of moving fewer bytes there — a half-resolution mip 0, skipping the second build — changes the cut rather than the picture, so each needs its own decision and its own measurement rather than being folded into a "no pictures change" pass. §4.6's `--peripheral-lod` lever still does not show in the clock on these two corpora, and for the same reason as before: they are not geometry-bound at this resolution.

## 4.7 UI coordinate architecture

Adopt the brief's model as written:

```
RenderSurface        pixels of the whole output (or per view)
PhysicalDisplays[]   from the OS when available
ViewSet              render frusta
HudSafeRegion        rect in surface pixels; default = center 16:9 (surround) or full (single)
HudScale             user-set
UiSpace              Surface | View | HudSafe | WorldProjected | Reading
```

Every UI element declares its `UiSpace` and anchor. The layout engine resolves to surface pixels each frame. The HUD-safe editor is a small in-editor tool that writes `HudSafeRegion` to user config. Default behavior is correct for surround and ultrawide without per-element work. The game UI framework choice is deferred ([10-roadmap-risks §10.6](10-roadmap-risks.md#106-decisions-deliberately-deferred)); Dear ImGui serves tools now.

## 4.8 Reference renderer and objective optimization

- **GPU path tracer** in Slang sharing material/BSDF, light, and camera code with the real-time path; a compile-time flag selects the integrator. Unbiased, converged to a noise floor. Spectral rendering is not required.
- **Metrics**: FLIP (perceptual) as the primary gate, PSNR/SSIM secondary; per-region metrics so a periphery regression weighs less than a center one; a temporal-stability metric on short sequences.
- **Scene corpus** in `content/test-scenes/`, versioned, including pathological scenes: 10^6 emitters, foliage walls, mirror rooms, 10^5 instances, thin geometry, 48:9 frusta.
- **Optimization loop**: propose → build → run corpus at fixed resolutions → collect frame time, counters, FLIP → compare to baseline → accept if within error tolerance and faster. Exposed to agents as a single tool ([06-agent-tooling §6.9](06-agent-tooling.md#69-day-one-operations)). Noise handled by repeated runs and medians.

**Status (2026-09-18): the integrator, the corpus, and the loop's single call are built; the pathological scenes and the nightly runner are not.** [renderer](../subsystems/renderer.md#reference-renderer), [gfx](../subsystems/gfx.md), [apps](../subsystems/apps.md), [content/test-scenes](../../content/test-scenes/README.md). `path_trace.slang` is the GPU path tracer this section asks for, and it shares more than the BSDF: the material layer moved out of the resolve into `material.slang` (the triangle fetch, the attributes, the tangent frame, the textures, the light falloffs, the sky, the display transform) and the lights into `renderer::frame_lighting`, so a comparison measures transport rather than two material layers — the resolve's pictures are byte-identical across that move. `renderer::ReferenceRenderer` renders **one real-time frame first**, because that is what builds the cluster acceleration structures, and then traces those, so the reference is a reference *for the frame's own LOD cut* unless `finest` asks for threshold 0. `render.evaluate` is this section's loop as one call, and `tools/ci/reference-compare.ps1` runs the corpus through it against per-scene thresholds.

What is measured: the noise floor is 0.0027 FLIP at 1024 samples on the heightfield and 0.0011 on the FlightHelmet against an order-of-magnitude larger signal, at 0.04–0.05 s a scene; today's corpus sits at 0.0014–0.035 FLIP, and PSNR climbs 5.7, 5.1, 4.0 and 2.8 dB per quadrupling of the samples where 1/√n predicts 6. The tables are in [renderer](../subsystems/renderer.md#reference-renderer).

What is **not** built. The pathological scenes this section lists — 10⁶ emitters, foliage walls, mirror rooms, 10⁵ instances — are absent, and their absence shows: on five open-sky scenes the indirect share of the error is near zero, so the corpus cannot yet distinguish "no global illumination" from "a fair ambient approximation". The reference renders **one view**, so a surround comparison is not possible; per-region metrics and the temporal-stability metric this section asks for are still only `render.compare`'s centre weighting; there is no area or environment sampling, so multiple importance sampling weights nothing (every light is a delta light) and a scene lit only by the sky converges through BSDF sampling alone. And the nightly step is wired into `.github/workflows/gpu.yml` but waits for a runner with an RTX card, since the two registered machines are a Maxwell and a Pascal and neither can build the structures the reference traces.

**Status (2026-09-17): the loop's three protocol calls exist; the integrator and the corpus do not.** The renderer became `systems/renderer` and engine-host its second consumer, so the loop's middle three steps are now `render.load` → `render.capture` → `render.benchmark` → `render.compare` over JSON-RPC, with no window in the process and no child process to scrape ([renderer](../subsystems/renderer.md), [apps](../subsystems/apps.md)). `render.compare` is `foundation/image`'s FLIP, PSNR, and SSIM with the center-weighted pooling this section asks for, and `render.benchmark` returns GPU milliseconds per pass from `gfx::GpuTimer` rather than a CPU clock. Still missing, and both Phase 2's: the **GPU path tracer** to compare against (today a comparison is against another rasterized frame or a stored baseline), and the **scene corpus** in `content/test-scenes/` with the pathological scenes, without which "run the corpus" is a script an agent writes per change. The capture side gained the entity-ID buffer §4.2 wanted, resolved per pixel into the scene instance, the cluster, and the triangle.

## 4.9 Streaming and residency

- One residency manager, three page types (geometry, texture, AS), one budget policy with per-type floors.
- Requests come from GPU feedback (geometry pages, virtual-texture pages) and from tile predictions based on observer velocity.
- I/O via platform async I/O (IOCP on Windows, io_uring on Linux) feeding a CPU decompression pool on efficiency cores, with GPU decompression through `VK_EXT_memory_decompression` where the driver supports it (NVIDIA today). meshoptimizer codecs for geometry, zstd or GDeflate for everything else. DirectStorage's GPU decompression requires a D3D12 device and is reserved for a future D3D12 backend. (What arrived first is the simpler shape one step below IOCP: positional reads on the job system's Efficiency pool, which is where a container's pages come from today and what io_uring and DirectStorage slot in behind — see the status note.)
- Priority = f(screen contribution, distance to observer, time since request), with a starvation guard for the current view.

**Status (2026-09-18): geometry is streamed end to end; the other two page types and the I/O are not.** [renderer](../subsystems/renderer.md#geometry-streaming-the-gpu-half-of-pages-and-residency), [gfx](../subsystems/gfx.md), [geometry](../subsystems/geometry.md), [apps](../subsystems/apps.md). What exists: the cull pass implements `geometry::select_lod_streaming`'s rule against a per-page residency word and is held to the CPU reference cluster for cluster on random ancestor-closed residencies; a bounded request buffer with an atomic counter and a per-page mask that deduplicates a page a thousand clusters want down to one entry; a per-page "used this frame" bit that gives the LRU something to order by; a deferred readback one frame slot late, so nothing in the frame path waits on the device; `PageResidencyManager` driven from that feedback with the heap, the starvation guard, the ancestor-closed eviction and the pinned root pages it already had; and a page pool of fixed-size slots filled through a staging ring with a per-frame byte budget, whose descriptors' offsets are **patched on the host** so that no shader that reads geometry changed at all.

What this settles about the priority formula: **the third term stays the manager's and the first two stay the request's**, and the GPU cannot coalesce. The CPU reference keeps the best screen size and the smallest distance of every cluster that asked for a page; the shader's mask lets one lane write its own, because a lock-free best-of is two more atomics on every losing lane and the manager converges on the best over a frame or two anyway.

What it settles about the invariant: "a page is resident only while the pages holding its clusters' parents are" needs **cancellation as well as admission control**, and that is not a detail. A request is made by a cluster that is being drawn, so it arrives with a resident parent — but a queue is not served in the frame it was filled in, and a parent evicted while the request waits makes admitting it a hole. `PageResidencyManager::drop` and a page-parent test are the fix; without them one page in sixty came back resident with nothing above it under a budget tight enough to evict every frame.

**The I/O half is built too** (2026-09-18, the same day): `io::FileHandle` reads a file by byte range — Windows `FILE_FLAG_OVERLAPPED` with an offset and an event per read, POSIX `pread`, so one handle serves any number of concurrent reads with no shared position — `read_ranges_async` puts a group of them on the Efficiency pool against one counter, `geometry::ClusterFileReader` addresses a container's sections by range, and `renderer::FilePageSource` turns a page into **three ranged reads, or four when the frame builds acceleration structures**. `attach_page_source` releases the merged host streams once the scene is uploaded, so the residency budget bounds host memory as well as device memory: measured on the FlightHelmet at `--grid-instances 8`, a quarter budget, the working set falls 307.5 → 303.5 MB and 4.83 MB of streams are freed. What it does not yet bound is the **peak**: the load still materializes those streams and frees them afterwards, because `geometry::merge_paged_cluster_meshes` derives the merged vertex and triangle bases from `mesh.vertices.size()` rather than from the page table that already tiles them. Bounded in flight (eight loads) and cancellation of a load whose page was evicted are both there; what is not is decompression, `VK_EXT_memory_decompression`, and prediction from observer velocity.

What is **not** built. This is still **one** page type: textures are uploaded whole, the acceleration structures are sized for every pair, and "one budget policy with per-type floors" is one budget. Streaming also refuses a deformed or skinned scene — `gfx::DeformDesc::pool_offset` indexes the vertex pool scene-wide while a streamed scene's vertices are slot-relative, which is E25's open suballocation item wearing a different hat — and refuses `--rt-templates`, because a template is built at load from positions a streamed scene does not hold and would have to be built when its page arrives and dropped when it leaves.

## 4.10 Reuse versus build

| Build in-house | Reuse |
|---|---|
| Render graph, cluster pipeline, software rasterizer, residency manager, ray scheduler, view sets, UI layout, ReSTIR, baseline denoiser | Slang, VMA/volk, meshoptimizer (incl. clusterlod), METIS, FLIP, KTX/Basis, OIDN (reference path); Streamline/FSR/XeSS as optional developer-supplied plugins |

Build the thin RHI over Vulkan in-house: the renderer *is* the product and GPU-driven design needs full control. NVRHI is the fallback if velocity is poor (MIT; Vulkan and D3D12; mesh shaders; cluster AS only via NVAPI on D3D12), but note that its companion Donut framework has no RT passes and does not manage acceleration structures. The valuable parts of NVIDIA's samples are shaders and algorithms, which port regardless of RHI.
