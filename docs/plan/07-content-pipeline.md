# 07 — Asset and Content Pipeline

## 7.1 Principles

- Source formats are open interchange formats. Engine-specific data is derived, cached, and content-addressed.
- Every asset carries provenance and license metadata; the build refuses assets without it.
- Validation is automatic and structured; agents receive machine-readable failures with rule IDs.
- Procedural generation handles volume; ML generation handles novelty; agents direct both and evaluate the results.

## 7.2 Source formats and canonical representations

| Type | Source | Notes |
|---|---|---|
| Meshes, skins, animations, PBR materials | glTF 2.0 with KHR extensions | Universal; every generator and DCC tool exports it; agents know it well |
| Textures | PNG/EXR source → KTX2 (BC7/BC5/BC4) derived | |
| Terrain | heightfield EXR + splat masks | Blob-referenced from the document |
| Splines, masks, placements | document objects | |
| Audio | WAV/FLAC source → Vorbis/Opus derived | |
| Structural graphs, fracture chunks | document objects + derived chunk meshes | |
| Interop | USD via LightUSD (read/write); FBX via an import-only converter | |

Canonical engine representations, all derived: cluster pages, AS build inputs, compressed textures, navmesh tiles, support graphs, deformable cages and their surface bindings, compressed animation clips, material shader permutations, semantic summaries, visual mips.

**Status, 2026-09-24 — the texture row exists, and its container is the engine's own, not KTX2** ([texture](../subsystems/texture.md), [ADR-0036](../adr/0036-built-textures-in-the-engines-own-container.md)). PNG, JPEG, TGA and BMP sources build into a `.tex`: the cluster container's sectioned, append-only layout with a level table and the source identity, BC7 (colour, sRGB; and metallic-roughness, linear), BC5 (normals, z rebuilt in the shader), BC4 (a lone occlusion map), and BC1, BC3 and RGBA8 when asked for, with the full mip chain filtered in linear light. KTX2 was the table's word and not a requirement anyone had: it has no place for the identity an incremental build reads and no append-only sections, and nothing here reads it, so an exporter from `.tex` is where it goes when a consumer needs one. EXR sources and BC6H are not built yet.

## 7.3 Content build (the derived-data graph)

- Every transform is a `derived` node ([03-data-model §3.6](03-data-model.md#36-dependencies-and-invalidation)): pure, sandboxed with tracked reads, versioned by function hash so a code change invalidates its outputs automatically.
- Parallel, out-of-process, remote-cache capable through the shared content-addressed store.
- Hot path: an editor edit triggers incremental rebuild of the affected nodes and hot-reload into running sessions per asset. Full rebuilds happen only when a function version changes.
- Build failures are structured diagnostics (asset ID, rule ID, severity, suggested fix) consumed identically by agents and the editor.

**Status, 2026-09-18 — textures are not derived yet, so the mesh container carries them.** §7.2 says textures are a derived node of their own (PNG/EXR source → KTX2 with BC7/BC5/BC4), and that node does not exist: `foundation/image` decodes to 8-bit RGBA and the GPU upload takes it as it comes. Until it does, a `.clusters` container carries the **encoded** bytes of every image its source embedded, because a derived artifact that cannot draw the thing it was derived from is not derived data, it is a broken cache — a GLB's textures have no path, so a container that recorded only paths drew the mesh untextured from the cache and textured from the source ([geometry](../subsystems/geometry.md#embedded-images-the-container-carries-them)). The record identifies each image by the **content hash of its encoded bytes**, which is the key a texture derivative will be addressed by, so the step taken is the one the real node replaces rather than one it has to undo: when that node exists, a container's image records name entries in the shared store and the bytes become a fallback or leave the container altogether. An image the source kept in a file of its own is still named by path and read from disk, which is why a texture can be repainted without rebuilding the mesh.

**Status, 2026-09-24 (later) — textures are a derived node, and the container's image records now name their entries** ([texture](../subsystems/texture.md), [geometry](../subsystems/geometry.md#built-textures-where-each-images-texture-is), [apps](../subsystems/apps.md)). The node the note above waited for: every image a material samples builds into `<ddc>/textures/<key>.tex`, keyed by the content hash of its encoded bytes — the hash the image records already carried — with its options, and `engine-content build`, `build-all` and `texture` run it, in parallel and reported in image order. A container records per image where its texture is (section 32); for an image it carries that is the key itself, and for an image named by path it is the options alone, because the container's own key does not cover the file and a key over its bytes would go stale under it — readers hash the file as it is. The renderer uploads a mesh's built textures as stored, with their mips, when all of them are present, and otherwise draws exactly as before; the carried image bytes stayed, as the fallback for an image nothing has built. And the rule the next status note sets for the next derived node holds for this one: a `.tex` is the same bytes from MSVC, GCC and Clang, at v2 and v3, and for any thread count — with no C library transcendental (the sRGB curve is two committed tables), a polynomial filter, and encoders whose only library calls are correctly rounded — pinned by golden hashes the Linux presets reproduce.

**Status, 2026-09-24 — "pure" includes "whoever compiled it".** A derived node addressed by its inputs is only remote-cache capable if its output is a function of those inputs, and the mesh build's was also a function of the compiler: from the same glTF bytes GCC and Clang at x86-64-v3 built a different LOD DAG from MSVC's (and from every v2 build's), under the same key, because they fuse multiply-adds and MSVC does not. It is settled as determinism rather than as a toolchain term in the key — the tree compiles without floating-point contraction and the builders call no C library function in a decision, at a price of about a tenth of a Linux v3 content build and nothing on MSVC ([ADR-0035](../adr/0035-no-floating-point-contraction.md), [geometry](../subsystems/geometry.md#the-same-bytes-from-every-toolchain), [the measurement](../experiments/content-build-determinism.md)) — and golden section hashes committed with the tests hold every CI toolchain to it. The next derived node inherits the rule: its output may not depend on the machine, and a test with a committed answer says so.

## 7.4 Validation rules (automatic)

- **Geometry**: manifoldness where required, degenerate triangles, scale (bounding box against the declared category's size range), pivot placement, up axis, UV coverage and overlap, texel-density range, **atlas fragmentation** (island count, seam-vertex share, smallest island area — see the status note below), cluster error budget, triangle budget per category, collision presence and fit (convex hull to mesh volume ratio), open edges.
- **Materials**: texture resolution against on-screen size class, missing maps, energy conservation, naming.
- **Rigs and animation**: standard-skeleton conformance, bone count, skin-weight normalization, foot-sliding metric, root-motion consistency.
- **Deformable volumes**: cage covers the render mesh, attachments resolve to existing bones or bodies, layers partition the volume, parameters in range ([§7.10](#710-deformable-volume-assets)).
- **Placement**: floating or interpenetrating objects, below terrain, unreachable by nav, occlusion of required landmarks, style-guide conformance.
- **Performance**: per-asset cost estimate (clusters at typical distance, AS memory, texture memory) against budgets by category.
- **Provenance**: metadata present and license in the allowlist.
- **Visual**: embedding distance to the approved reference board (soft warning), palette conformance.

**Status, 2026-09-19 — the first validator this list needs is one nobody had written down: how fragmented an atlas is.** The first machine-generated character run through the pipeline imported with zero warnings and drew wrongly at any LOD below the finest, because the LOD simplifier collapsed across the atlas's island edges ([geometry](../subsystems/geometry.md#what-the-simplifier-is-given-and-why)). The builder no longer does that, so this is no longer a correctness bug — but it is now a *cost* the asset controls: protecting the seams keeps the triangles a collapse would have removed, so an atlas of a thousand tiny islands simplifies less than an atlas of ten large ones, and at some island size no seam-respecting simplification can help at all, because the island is smaller than a triangle at that level. That is the number the validator has to report and the repair chain (§7.7's "remesh, decimate, UV, bake") has to act on: an atlas repack, or per-level baked textures, is a **texture-space** fix and cannot be done in the geometry builder. Reporting those numbers is the next step, and turning them into a warning belongs with E10's validators.

**Status, 2026-09-22 — E10's first pass reorders this list for generated props** ([results](../experiments/e10-generated-props.md)). Twenty Meshy props imported with **no errors and no warnings** under every rule the build has, and 6 of 20 passed the harness; what failed the other fourteen is three things, in this order of importance. **Triangle budget per category** first: a median of about 800,000 triangles a prop and 1.64 GB of containers for twenty, and the coarse-level picture error follows the triangle count (r = 0.81) because these meshes carry their detail in geometry, so the repair chain's *decimate and bake* is the first repair, not the last. **A UV-degenerate rule** second, which this list did not have: twelve props have an atlas island of zero area, and in eight of them it is one triangle whose three UVs coincide in an otherwise sound atlas — a mechanical fix, which alone would lift the pass rate to 10 of 20. **Atlas fragmentation** third, reported as a distribution (islands below N texels and the surface share they cover) rather than as the smallest island, which cannot tell one bad triangle from ten thousand bad islands: the characters' kind of fragmentation appeared in four props of twenty. The budget rule needs a category per asset, which the E10 subject list now carries.

**Status, 2026-09-23 — E10's second pass: the UV-degenerate rule exists as a repair, the budget is a request to the generator, and the next validator is how far the LOD collapses** ([results](../experiments/e10-generated-props.md#pass-2-the-same-twenty-remeshed-to-a-triangle-budget)). The content build now folds every atlas island under one texel of a 4,096 atlas into the island beside it, before the weld (`geometry.uv_degenerate`, [geometry](../subsystems/geometry.md#uv-degenerate-triangles-the-repair)), and reports it as a **repair** with counts rather than a warning: the fault is mechanical and fixed the same way every time, so an asset that needed it can still be taken unattended. It lifted the first pass's island check from 8 to 20 of 20 and its pass rate from 6 to 11. The rule turned out to be about the **island**, not the triangle: the "zero-area triangles" of the first pass had positive UV area in their files and became points only in the container's half-float UVs. The **triangle budget per category** is carried by the subject list and handed to the generator — Meshy's remesh, Tripo's face limit — and both met it within 9%, which removes the extreme densities the first pass blamed; between 50,000 and 250,000 triangles the whole-frame picture error follows the count only weakly (r = 0.28 and 0.48, against 0.77 across the first pass's 82,000 to 7.5 million). But a budget met by Meshy's *triangle* remesh gives an atlas with 34–96% of its vertices on a seam, and such a mesh **cannot coarsen** (its coarse cut draws a median 70% of the finest) while passing every picture check, because those compare a cut with the finest cut. So the fragmentation validator is best stated as **how far the LOD collapses** at a reference view, with the island distribution as its explanation, and for generated props it comes ahead of decimate-and-bake; its first repair is a generator setting (the quad remesh, TRELLIS.2's segmenter), not a repack.

**Status, 2026-09-23, later — the harness now judges how far the LOD collapses, and the ranking inverts.** A mesh whose 1-pixel cut still draws more than 75% of its finest cut's visible pairs fails (judged only when the finest cut has at least 3 pairs per 1,000 object pixels; both lines from measured known-good and known-stuck sets, [E10](../experiments/e10-generated-props.md)). Re-judged at one build and framing: Meshy pass 1 11 of 20, Meshy pass 2 17 to 11, Tripo 10 to 10, TRELLIS.2 18 to 5. TRELLIS.2's atlases are as fragmented as Meshy's triangle remesh (13 of 20 do not coarsen; its excellent picture error was the coarse cut being the finest cut), and Tripo has the soundest atlases and smallest files but the largest coarse-cut picture error. No generator gives both an LOD that collapses and a clean coarse picture on most props, so the conclusion is downstream of generation: **the pipeline needs its own unwrap, repack and rebake**, so that a generator's atlas stops deciding whether the engine's LOD can work; that is the next content-pipeline item, not a fourth generator.


**Status, 2026-09-23 (later) — the collapse validator exists, calibrated on known-good assets, and it changes the ranking of generators** ([the check](../experiments/e10-generated-props.md#the-collapse-check-how-far-the-lod-collapses), [TRELLIS.2 on the same images](../experiments/e10-generated-props.md#trellis2-from-the-same-twenty-images)). `tools/e10-harness.ps1` now fails a mesh whose coarse cut draws more than **75%** of its finest cut's visible pairs, judged only where the finest cut is at least **3 pairs per 1,000 pixels of the object** — because a low-poly hand-made asset at a close view (the SciFiHelmet, 96%) has nothing to shed and is not at fault, while every generated mesh that did not coarsen was denser than 4. The judged Khronos samples draw at most 46%, the E10 meshes not made by Meshy's triangle remesh at most 68%, the six that do not coarsen at least 86%. Re-judged, the second pass's 17 of 20 is 11 of 20; and TRELLIS.2, given the same twenty images at the same budgets, fragments its atlas as far as Meshy's triangle remesh (median 69% of vertices on a seam) and fails the check on 13 of 20 — **18 of 20 without it**, the best set by the old criteria, because a mesh that cannot coarsen has nothing to lose in a picture check. For the validator list this means the collapse check belongs with the picture check in every automatic acceptance, and the atlas repair — a sounder unwrap from the generator, or a repack and rebake — is the first repair for two of the three generators measured, ahead of decimate-and-bake, which is the first for the third (Tripo: sound atlases, and the largest coarse-cut picture error at the budget).

**Status, 2026-09-24 — the atlas repair exists as a content-build step, and it is not the default** ([atlas](../subsystems/atlas.md), [E10, "Repack"](../experiments/e10-generated-props.md#repack-the-pipelines-own-atlas)). `engine-content build --atlas repack` re-charts every textured material (xatlas on a 2,000-triangle proxy, carried onto the mesh and parameterized by least-squares conformal maps), packs one atlas per material at the source texture's size, and rebakes every texture into it — colour in linear light, tangent-space normal maps converted through object space — between the UV repair and the weld. On E10's three sets it takes Meshy's triangle remesh from 0.69 to 0.46 of the finest cut at the coarse threshold (the no-atlas ceiling is 0.39) and its seams from 70% of vertices to 24%; Tripo, whose atlases were sound, from 0.52 to 0.45; and TRELLIS.2 from 0.88 to 0.81, because a **gate** declines any material whose new charts would fold more than 5% of it, and nine TRELLIS.2 props of twenty — the thin and intricate ones — fold 5–50% and keep their own atlases (seven of those nine do not coarsen even with no atlas at all: that part of the failure is geometry). The repacked picture is 0.004–0.007 FLIP from the source's at the median, from one camera; the step costs about ten seconds a prop. **Should it be the default for generated content? Not yet, and not for every generator**: `keep` stays the default, and a generated prop is repacked when the harness's fragmentation diagnosis says its atlas is the constraint (more than 30% of vertices on a seam or a median island under 1,024 texels) — Meshy's triangle remesh and TRELLIS.2 at these budgets, not Tripo. Making that choice automatic is a validator's job here, reading the numbers `stats` already reports, and belongs with the provenance-aware build of §7.7. For the list above this changes the order once more: the atlas is repaired by the pipeline where the generator fragments it, the collapse check is what says whether it worked, and the failures left are decimate-and-bake's (Tripo's coarse picture, TRELLIS.2's thin geometry, the rope's strands).

## 7.5 Provenance and licensing metadata

```
AssetProvenance {
  generator, model_id, model_version, prompt_hash, seed
  inputs[]           content hashes
  operator           human or agent id
  created_at
  license            SPDX id or project-defined id
  license_terms_url
  commercial_ok, attribution_required
  derived_from[]     asset ids
}
```

Stored beside the asset in the document and carried through derived data. The build fails if `license` is not in the project allowlist. A shipping report lists every attribution requirement.

## 7.6 Procedural generation (volume content)

Engine-provided generators are `derived` nodes whose parameters are document objects, so agents tune parameters and evaluate results rather than writing generators:

- **Terrain**: erosion and hydrology from control heightmaps plus biome rules.
- **Scatter**: density maps × rules (slope, altitude, distance to roads and water, exclusion zones).
- **Roads and rivers**: spline networks from a graph, terrain-conforming, with intersections.
- **Buildings**: shape grammar plus modular kit assembly (kits are generated or authored assets); interiors from room graphs.

  **Direction note, 2026-09-24: ruined desert structures are assembled from the kit, never one asset.** The owner's intent for Desert Survival, recorded with the kit work of [§7.7](#77-ml-asset-generation-novelty-content): a ruined building is the kit's wall sections placed at right angles by a **seeded assembler**, not a single generated model, so the sparse ruins of an endless desert differ from one another and from run to run. The assembler is a small shape grammar over footprints (rectangles, L and U shapes, courtyards) that picks wall variants, joins them with corner pieces the kit provides (quoins, so walls meet cleanly rather than by overlapping end blocks), places openings (doorways and windows with lintels), assigns each wall a collapse state under the ruin rule, drops the debris field the removed blocks make, and adds the sand drift against the walls. It is deterministic from the **world seed and the tile coordinate**, so one seed gives the same ruin on every machine and every run of that seed, and a fresh seed gives a fresh desert, with the same arithmetic discipline the content build has (no toolchain in the result). Where it runs: for the endless desert, at tile materialization, because its output is instances of kit meshes (a thousand ruins are instances of a few dozen meshes, which is what the scene's instance-of-mesh model is for) and no per-building geometry has to be built or stored; for an authored place, as a `derived` node with the footprint and seed as document parameters. Its output is the ruin's *initial* state: the persistent store carries what the simulation does to it afterwards (a doorway buried by a moving dune, a wall brought down), per [13 §13.1](13-reference-consumer-games.md) and the event-sourced state of [03 §3.5](03-data-model.md#35-persistent-world-state). Two representations remain to be measured against each other once E33 has a kit: wall **sections** as kit meshes with their own LOD DAGs (cheap, seams at the joins hidden by corner pieces, debris and sand), or the block-laying generator run **per building** so every block is an instance of one of a dozen block meshes (no two walls alike, no seams, more pairs for the cull pass, and a handover between the two representations that must not pop, like every other LOD transition).
- **Clutter**: rule-based per room or street type.
- **Fracture and support graphs**: automatic from mesh plus material category.

Agents author rules and kits; the generator instantiates; agents review captures.

## 7.7 ML asset generation (novelty content)

A uniform **generator service** interface: `generate(kind, spec, constraints) → candidates[] with provenance`, pluggable backends (local or remote), asynchronous, cached by spec hash.

- **Textures and materials**: diffusion-based PBR material generation; tileable; validated for roughness and energy plausibility.
- **Meshes**: image- or text-to-mesh models produce usable props today with variable quality. Automated validation plus a repair chain (remesh, decimate, UV, bake) is mandatory. Measure the pass rate (experiment **E10**) before depending on it.
- **Concept and reference**: image models for style boards, used for embedding comparison, never shipped.
- **Speech**: TTS with per-character voice profiles, generated at build time for authored lines. Runtime TTS only at LLM Tier ≥ 2.
- **Characters**: **standardize first**. A standard skeleton, a parametric body, modular clothing and hair slots, and a face-rig standard. Generation fills slots (textures, clothing meshes conforming to templates) rather than producing whole rigged characters. Whole-character generation is an experiment, not a dependency.
- **Animation**: motion-capture libraries plus retargeting; generative motion later.

**Status, 2026-09-20 — "standardize first" now has a standard, and it is [§7.11](#711-characters).** The skeleton half was built in 2026-09-17 (`domain/anim`, [anim](../subsystems/anim.md)); "a parametric body" was a phrase with nothing behind it. [ADR-0032](../adr/0032-characters-are-parameter-vectors.md) is the body half — a character is a parameter vector over one canonical topology per base family, baked into a cached vertex stream — and [ADR-0033](../adr/0033-content-classes-and-view-policies.md) is the content classes and view policies that decide what any given output of the engine may contain. The sentence above stands unchanged: generation fills slots against the standard, and whole-character generation is still an experiment rather than a dependency. What changes is that "slots" now names something specific. **What is still a phrase is the face-rig standard**, which neither ADR touches: the standard skeleton has no face and no fingers (`standard_skeleton.h`, [anim](../subsystems/anim.md#the-standard-skeleton-first-cut)), a face is a channel set and a corrective scheme of its own rather than a special case of the body's, and it stays a Phase 5 question.

**Status, 2026-09-22 — the generator service exists as a tool, and provenance has a file format.** `tools/generate.ps1` ([content-generation](../content-generation.md)) is the interface above at tool level: text to image through any ComfyUI workflow on the owner's machine, image to mesh through Meshy's API or through a ComfyUI workflow, and meshes made by hand in Tripo Studio ingested against a manifest the tool wrote, all cached by spec hash. Every output lands **outside the repository** beside a sidecar whose `asset_provenance` block is exactly §7.5's record as `schemas/provenance.schema` defines it — tested against the JSON Schema the build generates — with what the record has no field for yet beside it: the prompt, the workflow's SHA-256 and every override made to it, the model files it loaded, the service's task id, the credits, and the content class, which for everything the tool makes is `general` ([ADR-0033](../adr/0033-content-classes-and-view-policies.md)). Two things are deliberately left for the C++ service this prototypes: the content build does not read sidecars yet, so "the build refuses assets without provenance" (§7.1) is not enforced; and every licence carries the schema's conservative defaults (`commercial_ok: false`, `attribution_required: true`) until the owner has reviewed each service's and model's terms. The paid service's spending rules — balance read before a batch, a floor and a per-run cap enforced before anything is submitted, credits recorded per asset and in a ledger, a task id on disk before its first poll so a crash never pays twice — are the tool's, not its operator's.

**Direction note, 2026-09-24: hard-surface assets are kits, not image-to-3D.** The owner's inspection of the generated props settled a question this section left open: image-to-3D (Tripo, Meshy, TRELLIS) gives good *volume* for a flythrough — the Desert Survival ruins and the Island City buildings and aircraft read at a distance — and poor *assets*: ruined brick walls and structures come out smoothed in both geometry and texture, with no sharp edge anywhere, because the models' latent and implicit representations average, and their textures carry the lighting they were generated under. The owner's working rule, recorded as the hypothesis E33 also tests: the services do well up to about **person scale** and struggle with anything bigger, because a generation spends a fixed detail budget (a bounded latent resolution, a bounded triangle count, one texture set) on the whole object, so detail per metre falls with size, and architecture is exactly the content whose detail is fine, repeated and sharp; a hand-sized prop is their sweet spot, a wall is not, and a building or an aircraft is out of reach. That is the plan's own division of labour ([§7.6](#76-procedural-generation-volume-content) assigns buildings to a shape grammar over modular kits and says "agents author rules and kits; the generator instantiates"; this section assigns ML generation to novelty content) confirmed from the other side, so the path for architecture is **kits authored procedurally by agents in a DCC tool** — kit **profiles** as parameter sets of one generator: Desert Survival's ruins are **weathered sandstone ashlar** (large blocks with irregular coursing, wind-rounded edges, beds eroded differentially, spalled faces, a sand skirt at the ground), the modern clay brick wall belongs to Island City; a few block or brick variants as real geometry with beveled or wind-rounded edges and per-block displacement, courses laid in a declared bond with per-block jitter, ruin as a rule (an erosion mask removes bricks and breaks the top line, the removed bricks become debris settled at the base), every choice under a seed — with surface detail from tileable PBR textures (CC0 sets, or albedos generated by an image model with normal and roughness derived from height), and real geometry wherever the silhouette matters: breaks, missing bricks, debris. None of the generated pieces is photorealistic, and the owner's reading of why is recorded as the target: photorealism at arm's length is mostly **texture fidelity** — scanned or scan-quality PBR sets at a stated texel density (of the order of a thousand texels per metre for a wall a player stands beside, more for a hero piece), with real roughness variation, height for parallax or displacement, and no lighting baked into the albedo — on top of the geometry, and then lighting, which today is direct only and cannot read as real until Phase 2's indirect light exists; so a kit declares its texel density and the texture pipeline ([§7.2](#72-source-formats-and-canonical-representations); its first version landed on 2026-09-24 as [texture](../subsystems/texture.md), with no texel density in it yet) is the prerequisite for carrying it. The engine's cluster LOD is what makes brick-by-brick geometry affordable, so the usual game answer (a flat wall with a normal map, which is right for far and mid distance and for unbroken runs) is the lower tier of the same kit, not a different asset. **Experiment E33** ([10 §10.5](10-roadmap-risks.md#105-experiments-to-run-before-committing)) builds a ruined brick wall both ways and measures sharpness (dihedral-angle histogram), texel density, baked lighting, LOD behaviour through the E10 harness, and authoring cost. Two constraints it works under: the authoring scripts (Blender's Python) live outside the repository under `game_engine_local/`, driven by a PowerShell wrapper, because `tools/` takes no Python, and whether they become a pipeline dependency is an ADR after the experiment; and the agent drives Blender headlessly, never the running session the authoring side uses for character work.

## 7.8 Runtime LLM: interface now, implementation deferred

The runtime-model idea stays in the plan as an optional way to add life to a game (contextual reactions, long-tail dialogue) when the player's hardware has spare capacity, never as something the game depends on. Everything in this section is governed by [12-ai-usage-policy](12-ai-usage-policy.md).

Interface: `Resolve(request) → intent`, where the request carries structured context, a constrained set of candidate options, and an output grammar. Tier 0 implements it with utility scoring and authored tables. Tiers 1–4 replace the resolver. Results are cached by context hash and logged as events with `origin = LLM` ([03-data-model §3.5](03-data-model.md#35-persistent-world-state)).

Constraints: inference runs on whatever the budget system grants. On the GPU when the VRAM budget has headroom after rendering (the residency manager treats model weights as one more page type, at the lowest priority), otherwise on the CPU efficiency-core pool at low priority. Batched; latency of 100 ms or more is acceptable; speculative pre-generation when a player approaches an NPC; grammar-constrained decoding so outputs are always valid; a content filter on generated text; nothing in core state depends on it. Models are third-party open-weights models under licenses that permit redistribution and commercial use, used as published.

**Long-tail authoring.** Playtest telemetry records every runtime resolution. A development-time job clusters recurring contexts, and a development-time agent *authors* deterministic rules and dialogue for them as ordinary game content with provenance. The next build handles those cases at Tier 0, and over time the runtime model handles only the genuine long tail. This is content authoring and caching: no model is trained, fine-tuned, or distilled on any of it, and no dataset of model outputs is assembled for training ([12 §12.2](12-ai-usage-policy.md#122-rules)).

## 7.9 Text and localization

All player-facing strings are document objects with IDs. Generated text is an object with provenance. Localization is a layer. TTS derives from these objects.

## 7.10 Deformable volume assets

What an asset carries for the deformable-volume primitive of [05 §5.14](05-simulation.md#514-deformable-volumes). The source mesh stays a plain glTF mesh; everything here is document properties on the asset plus painted regions, so a deformable asset is an ordinary asset with one more property block.

| Property | Units | Default | Notes |
|---|---|---|---|
| `cage.kind` | `lattice` \| `shell` \| `tet` | `lattice` | `tet` is not in v1 |
| `cage.target_elements` | count | 512 | the generator's budget; adaptive refinement spends it where curvature and thinness need it |
| `cage.min_feature` | m | 0.02 | smallest feature the cage must resolve; sets the finest cell |
| `material.stiffness` | kPa | 200 | per layer; fat ≈ 20, muscle ≈ 200, cartilage ≈ 5,000 as starting points. The solver takes the compliance 1/E |
| `material.damping` | 1/s | 4 | higher settles faster and looks deader |
| `material.density` | kg/m³ | 1,000 | element mass is density × element volume |
| `material.volume_preservation` | 0–1 | 0.8 | weight of the volume constraint; 1 is incompressible |
| `material.anisotropy` | axis + ratio | none (1.0) | fibre direction and the stiffness ratio along it, for muscle |
| `layer.region` | element selection | — | layers partition the volume; every element is in exactly one |
| `layer.bond` | `bonded` \| `sliding` \| `separable(F)` | `bonded` | behavior at a boundary with a neighbouring layer; `separable` takes a force in N |
| `cavity.region` | element selection | — | material-free region; its boundary carries a pressure constraint |
| `cavity.pressure` | kPa, relative | 0 | closed-volume pressure |
| `attachment.target` | bone id \| body id \| placement slot \| `free` | `free` | must resolve in the asset's own skeleton or rigid structure, or, for a volume set into world geometry, to a static collider named by the placement ([13 §13.7](13-reference-consumer-games.md#137-reference-interactions)) |
| `attachment.stiffness` | kPa | 5,000 | a stiff spring, not a weld; 0 is free |
| `limits.max_strain` | ratio | 0.5 | per-element clamp the solver never exceeds |
| `limits.max_velocity` | m/s | 20 | per-element velocity clamp |
| `contact.surface` | mesh ref \| `cage` | `cage` | a coarse authored contact surface when the cage is too coarse. Never the render mesh |
| `contact.model` | `frictional` \| `adhesive` | `frictional` | per layer. `adhesive` turns on the attachment constraints of [05 §5.14](05-simulation.md#514-deformable-volumes); `frictional` creates none |
| `adhesion.tack` | kPa | 0 | adhesion strength: the attachment stress a sustained contact develops. 0 means no adhesion whatever `contact.model` says |
| `adhesion.break_stress` | kPa | 1.5 × tack | break threshold: the normal stress at which an attachment lets go (stick becomes slip) |

| `adhesion.release` | s | 0.08 | release time: a broken attachment's force decays over this instead of vanishing in one tick |

| `gameplay_relevant` | bool | false | true puts the cage in the fixed-step tick and the sim hash ([05 §5.10](05-simulation.md#510-determinism-and-replay)) |

| `binding.strain_output` | `none` \| `scalar` \| `tensor` | `none` | whether the transfer pass writes per-vertex cage strain for materials that blend wrinkle and fold maps by compression ([04 §4.3](04-renderer.md#43-geometry)). `scalar` costs 4 B per deformed vertex of the cut, `tensor` 12 B; `none` costs nothing |

**Cage generation is a `derived` step.** `mesh + deformable properties → signed distance field → adaptive lattice → binding` is one node in the dependency substrate ([03 §3.6](03-data-model.md#36-dependencies-and-invalidation)), keyed by the source mesh hash, the property block, and the function version, cached in the derived-data store like clusters are. Authored overrides (a painted region's element size, a region's material, a cavity, an attachment set) are document objects and therefore inputs to the node, so editing one rebuilds that asset and nothing else. Nothing about the cage is hand-built in a DCC tool; the default path is generation, and an override exists where the default is wrong.

**Surface binding ships with the clusters.** Each render vertex of the affected clusters is bound to its cage element and weights during the cluster build ([04 §4.3](04-renderer.md#43-geometry)) and written into the cluster page's vertex stream as a fixed 12 B per vertex (cell index plus packed local coordinates). Binding therefore streams, evicts, and pages with the geometry that needs it, adds no residency type, and costs the resident cut rather than the source asset. Every level of the cluster DAG binds to the same cage, so a geometry LOD change never changes the deformation. **Strain is output, not binding**: it is written per frame into the deformed-vertex pool by the transfer pass, never into the page, so turning `binding.strain_output` on or off does not rebuild the clusters and does not change a shipped asset's on-disk size.

**Validation** (rule IDs in the structured diagnostics of [§7.3](#73-content-build-the-derived-data-graph)):

- The cage encloses the render mesh at the bind pose with a margin. A render vertex outside every cell fails and the diagnostic names the vertices.
- Every attachment resolves to a bone in the asset's skeleton or a body in its rigid structure, or, for an attachment to a placement slot, to a static collider that the placement supplies — checked when the volume is placed rather than when the asset is built, since the asset cannot know the wall it is set into. An unresolved slot at placement time is a placement error naming the slot. Standard-skeleton conformance is already checked in [§7.4](#74-validation-rules-automatic).
- Layers partition the volume: every element in exactly one layer, none unassigned, none overlapping. Cavities are closed and do not touch the outer boundary.
- Material parameters are in range, and the stiffness ratio across a `bonded` boundary is under the conditioning limit E23 measures — an ill-conditioned XPBD layer stack is a warning with a number, not a mystery at run time.
- Adhesion is consistent: `adhesion.break_stress` is at or above `adhesion.tack` (an attachment that breaks below the stress it develops never holds), tack and break stress are both zero or both non-zero, and a layer with `contact.model = adhesive` and zero tack fails with both property names rather than silently behaving as `frictional`. Adhesive layers must be on the volume's outer boundary or a cavity boundary, since an interior layer never reaches a collider.
- The strain pair resolves: a material that declares a strain input on a mesh whose volume leaves `binding.strain_output` at `none` fails and the diagnostic names the material and the volume, and a `tensor` output with only scalar consumers is a warning with the byte cost attached ([04 §4.3](04-renderer.md#43-geometry)).
- Per-asset cost estimate (cage elements at T0, binding bytes, strain-channel bytes when enabled, adhesion attachment constraints at the declared contact area, solver microseconds from the category's cost model) against the category budget, like every other asset ([§7.4](#74-validation-rules-automatic), Performance).

**Status note, 2026-09-18 ([ADR-0029](../adr/0029-deformable-volume-budgets.md), [E19](../experiments/e19-lattice-cage.md)): three rows of the table above are now decided rather than nominal, and one validation rule is added.**

- **`cage.target_elements` defaults to 256, not 512.** 256 particles is one solve group in the physics backend, and a cage wider than one group does not scale — it is 1.2× to 1.7× *slower* on eight workers than on one, because the solve jobs that find no group spin rather than idle — while eight separate cages are 6.5× faster together. The strain clamp is a second, independent reason: it costs 17 µs a tick on a 216-element cage and 326 µs on a 512-element one. **New rule: the validator warns above 256 elements for a volume that is not flagged `hero`, and refuses above 800 for any volume.** The constants and the verdict function the validator will read are `cage_size_verdict()` in `domain/physics/deformable.h`; the validator itself is a later content-pipeline task and nothing refuses a wide cage today. *(2026-09-24: for imported tetrahedral cages it exists — the tissue definition's `region.cage_size` row, a warning above 256 and an error above 800 ([tissue](../subsystems/tissue.md)); a generated lattice still has no validator, because no generator exists.)*
- **`limits.max_strain` is enforced.** It was "a per-element clamp the solver never exceeds" in this table and nothing clamped it; a per-element clamp now runs in the position pass after every step, symmetric in engineering strain (a limit of 0.5 is a length between half and one and a half times rest), and held stretch across E19's press grid is now exactly 1.5000 against 1.76–2.41 before. **`limits.max_velocity` is still enforced by nothing** and is the remaining half of that row.
- **`material.volume_preservation` is converted with the cell size, and the conversion is `volume_compliance_for()` in `domain/physics/deformable.h`.** A generated cage's volume compliance goes as the **cube** of its cell size at a fixed material, because the backend's constraint is on six times a tetrahedron's volume and equating XPBD's energy with a bulk modulus gives `α = 6h³/K`; the authored 0..1 weight scales the material's own bulk modulus, `K = (E/3)·p/(1−p)`, so 1 is incompressible and 0 is no preservation at all. **Whatever generates cages must call the conversion rather than carrying a compliance in the asset**, because a compliance authored at one cell size is wrong at every other, and getting it wrong does not look like a soft cage — it looks like a cage that takes a permanent set at two thirds of its volume and never comes back.
- **A conditioning limit worth knowing before authoring.** The plan's default preservation of 0.8 is stable through sixteen iterations at one sub-step and eight at two, and unstable at sixteen *and* two — thirty-two XPBD sub-steps a tick — on 512- and 729-element cages. That is outside the default envelope and is what [E23](10-roadmap-risks.md#105-experiments-to-run-before-committing) will pin as the validator's stiffness-ratio rule.

## 7.11 Characters

The authoring and build half of the character standard [§7.7](#77-ml-asset-generation-novelty-content) asks for, decided by [ADR-0032](../adr/0032-characters-are-parameter-vectors.md) and [ADR-0033](../adr/0033-content-classes-and-view-policies.md). The run-time half — the deform chain, the tiers, and what a population costs — is [05 §5.16](05-simulation.md#516-characters-at-run-time).

**None of it is mandatory.** A character may be a plain authored asset: a static mesh, or a skinned glTF with a skeleton and clips, with no parameter vector, no morph channels, no modules and no appearance component. It imports, clusters, streams, animates and renders through exactly the path everything else uses. Every piece below is optional data, and a game that never enables the character capability pays nothing for it ([11 §11.10](11-performance-principles.md#1110-absent-capabilities-are-free), [ADR-0027](../adr/0027-additive-capabilities.md)). Most games built with this engine will never need any of it, and the pipeline must not read as though they should.

**A base family is one mesh.** One canonical topology per base: a neutral pose, one vertex ordering, one UV layout, edge flow built for deformation, one LOD structure, and a single set of sex-characteristic axes rather than two meshes. Everything authored against a base is authored once and fits every character of that base — skin weights, garments, texture layers, hair and accessory attachment, the deformable cage of [§7.10](#710-deformable-volume-assets), the cluster DAG. A generated or scanned body becomes a **preset** by conforming the canonical body to it (wrap, then morph transfer), never a second base; a second base is a second family, with its own garments and its own cage, and is a deliberate act rather than something a creator produces.

**Parameters are three layers.** Semantic parameters (schema-typed, named, versioned, defined by the game) drive a **parameter rig** — a declarative DAG of maps, curves, products, clamps and conditions on module presence, evaluated at bake time, serializable as data and never scripting — which drives the engine's deformation channels. Nothing above the rig knows the channels exist, so a creator UI can change without an asset change.

**Channels do not all combine the same way.** Three macro axes — overall mass, muscularity, and the sex-characteristic axis — interpolate multilinearly across **sculpted corner shapes**, because a heavy muscular body is not the sum of a heavy delta and a muscular delta. That is **eight corner sculpts per base**, and the reason the set stops at three is that every corner axis **doubles** the hand sculpting: an axis earns a corner only when no cheaper carrier represents it. Height and limb, torso and shoulder proportion are **skeleton parameters** carried by bone scales and offsets through the joint regressor, with at most small region-masked correctives where scaling alone looks wrong. Age within the adult range is **region-masked detail channels plus a skin-layer set** in the compositor. Detail channels are additive but region-masked and gain-scheduled by the macro context; **combination correctives** repair known bad pairs; **pose-space correctives** run at run time and are scaled by shape.

**Joints follow shape** through one sparse **joint regressor** per base, evaluated on the baked surface, rather than per-channel joint deltas that go stale the moment a channel is re-sculpted. The skeleton parameters compose here as bone scales and offsets, which is where the retarget's hip-height scale already expects them ([anim](../subsystems/anim.md#the-standard-skeleton-first-cut)). The core is the standard skeleton of `domain/anim`, so one clip library serves every character of every base; a module may add extension bones.

**Modules replace a region of a body.** The base's section is hidden with the same section-visibility mask garments use to hide covered skin, and the module attaches along a **boundary loop** matching the base's (vertex count, order, UVs, skin weights). A module brings its own channels, material layers, optional extension bones, optional soft-tissue regions, and an LOD policy: below a screen-size threshold it is dropped and the base's neutral region shows instead, which is why a base must be complete and presentable alone. The engine does not know what a module depicts — a prosthetic, a creature part, a wound, a piece of equipment that replaces geometry rather than covering it, and anatomical detail are one mechanism. The one thing the engine reads about it is its **content classes** — a level in each category that applies, `nudity` and `violence` being the two the engine defines ([ADR-0033](../adr/0033-content-classes-and-view-policies.md)).

**Materials are a layered compositor** baked per character: a neutral base layer plus tinted, masked, parameter-driven layers, with module-supplied layers stacked in. Two authoring rules fall out of the classes: the base texture is authored **neutral**, and anything classified lives in a **tagged layer**. That is what lets a restricted view drop a layer before the composite runs rather than blurring a finished picture.

**The bake is a `derived` node** ([§7.3](#73-content-build-the-derived-data-graph), [03 §3.6](03-data-model.md#36-dependencies-and-invalidation)). Inputs: the base and its corner set, the module set, the parameter vector, the rig, and the function version. Outputs: the character's position, normal and tangent stream; its composited texture set; its regressed joint positions; and the cage fit where the character carries a deformable volume ([§7.10](#710-deformable-volume-assets)). It is keyed in the derived-data cache by the **hash of the parameter vector** and its inputs, like clusters are, so two characters with the same vector are one bake and a re-bake follows exactly the parameter that changed. What a bake costs in milliseconds and bytes, and therefore how many baked characters a budget holds, is **E28** ([10 §10.5](10-roadmap-risks.md#105-experiments-to-run-before-committing)).

**A character serializes as names, modules and a seed** — semantic parameters by name, the module set, and the generator seed if there was one — schema-versioned with migrations ([03 §3.8](03-data-model.md#38-schema-evolution)), quantized, canonical, and hashed. Generated characters carry provenance like every other generated asset ([§7.5](#75-provenance-and-licensing-metadata)). Random generation is the game's distributions and correlations, sampled from a seed, deterministic, and rejected through the validators.

**Validation is numeric and sweeps the parameter space**, not a look at a character: corners plus low-discrepancy samples, times the module set, times a pose set, through the validators listed in [09 §9.7](09-testing-profiling.md#97-character-validators) and gated on the content build like every other rule in [§7.4](#74-validation-rules-automatic). Two rules are the engine's floor rather than a game's choice. **Characters that can carry nudity- or sexual-classified detail are adults**: a base that admits any module or layer above `none` in the `nudity` or `sexual` category declares an adult age range, the rig clamps to it, the validators reject a vector outside it, the random generator cannot sample outside it, and the bake refuses a character that violates it whatever a game's UI allows. It is **not a view policy and nothing can raise it** — no operator setting, no game override. The rule binds to those two categories and to nothing else: **the engine places no other age restriction on characters**, so a game whose bodies carry nothing above `none` in either may have characters of any age with the whole system, and how violence, injury or damage is handled across ages is the game's decision under its own rating regime ([ADR-0032](../adr/0032-characters-are-parameter-vectors.md) decision 13). And **classified content is verified by those numbers and by human review items**, never by agent inspection ([06 §6.10](06-agent-tooling.md#610-multi-agent-roles-review-and-the-human-director), [12 §12.6](12-ai-usage-policy.md#126-how-this-project-develops-a-character-system)).

**Where the work sits.** The engine owns the mechanisms and the formats (morph stream, deform chain, regressor evaluation, section masks and graft attachment, the rig evaluator, the compositor, content classes and view policies); an optional reference capability owns the appearance component, the bake step and the conform and morph-transfer tools; the game owns the semantic parameter set, the meshes and sculpts, the modules, the distributions, the slots and the creator UI ([ADR-0032](../adr/0032-characters-are-parameter-vectors.md) decision 14). Near term, two engine pieces this section depends on are **in progress** in Phase 1 beside the deformed-vertex pool — a **morph vertex stream** and a **staged deform chain** ([04 §4.3](04-renderer.md#43-geometry)) — and everything else here is Phase 5 ([10 §10.2](10-roadmap-risks.md#102-phases)).

**Direction note, 2026-09-22 (revised the same day after review): tissue regions are authored as definitions; sculpted shapes are inputs to them.** For the tissue-and-attachment model of [05 §5.16](05-simulation.md#516-characters-at-run-time), the authoring source per region is: attachment points on bones (or curves) and their stiffness, rest volume and stiffness, structural dimensions, the fill range and the region's own fill-to-volume/pressure/stiffness mapping (an engine default curve applies when none is authored), the fat-depot mapping, the skin binding, and optionally a rest envelope, skin slack, directional structure and correctives. The build **fits** the definition to the authored geometry and stores the residual as a corrective, then derives both the static bake (the region's equilibrium in the explicit reference state, folded into the character's cached position stream) and the simulation cage, constraints and inverse-statics rest configuration of [§7.10](#710-deformable-volume-assets); the runtime never reads the sculpt, so the two consumers cannot disagree. The validators of §7.11 gain volume-against-fill, attachment-continuity and reference-state rows. A generated or scanned body still becomes a *preset* by conforming the canonical base to it; tissue definitions are authored on the base once. Pending E30.

Element kinds are schema types, the container carries a region's elements in one append-only section per kind, and a reader that lacks a kind skips it and lets the region fall back to its rest shape with a validator warning rather than refusing the file (see the addendum to [05 §5.16](05-simulation.md#516-characters-at-run-time)).

**Direction note, 2026-09-22: garments prevent clipping by construction, simulate only what hangs, and bake fit rather than motion (proposed, E31).** Clipping is the failure players see first, and the split follows what can be precomputed. (1) **Hide what is covered**: the section-visibility mask of [ADR-0032](../adr/0032-characters-are-parameter-vectors.md) removes the skin under a garment, and a garment carries the same mask so an outer layer hides the covered part of an inner one; skin that is not drawn cannot poke through. (2) **Tight garments are surface-bound, not simulated**: a garment authored on the base topology binds each vertex to a body triangle with a positive normal offset, the same primitive the tissue model of [05 §5.16](05-simulation.md#516-characters-at-run-time) uses to bind skin to its cage. The body's deformed positions are already in the per-frame deform pool, so a garment is one gather per vertex and follows morphs, fill, activation and secondary motion with no simulation and no body-to-garment clipping; layers stack offsets, so garment-on-garment clipping is prevented rather than corrected, and waistbands, belts and other friction-held items are held by construction. (3) **Loose parts are simulated** as [05 §5.13](05-simulation.md#513-deformable-surfaces-and-soft-bodies) already decided, cosmetic GPU position-based dynamics one frame late, expressed as shell and body-contact element kinds on the tissue tier policy: full at the hero and near tiers, a spring on the attachment points at mid, rest shape beyond; at the hero tier the body's own tissue cage is the collider, so cloth sliding on soft tissue is a contact element between two regions and not a new system. Only the outermost loose layer simulates. (4) **Bake fit and correctives, never motion**: at character creation or change each garment is relaxed on the morphed body until nothing interpenetrates in the reference pose and stretch is distributed, in the content build's `derived` step for predefined characters and in the asynchronous character bake for players; pose-space correctives (knees, elbows, sitting) are baked from a handful of key poses; secondary motion cannot be baked because pose space is unbounded. A body morphed outside the range a garment was fitted for is a validator failure, never hidden. (5) The hardware and title setting is the existing one: per-asset tier caps and the deformable budgets are tunables, so a low-end title caps loose garments at the spring tier and changes nothing else. Clipping is measured by the garment-penetration row of [09 §9.5](09-testing-profiling.md)'s validator table, which is what makes E31 an experiment with numbers.

**Addendum, 2026-09-22: mods, and bodies nobody baked for.** The owner raised the failure every popular game meets: a body or rig replacer that does not match the shipped body breaks every garment, and a character creator with a wide range of bodies makes design-time baking impossible. Both have one root cause, which this design already removes: a clothing mesh that carries its own copy of the body under it, over a body that is a topology. Here garments never carry body geometry and the body is a canonical topology with morphs, so a body *shape* mod is morph channels and presets on the canonical topology and needs no garment work at all. What the design adds for the remaining cases: (1) **the mod-facing contract is the base's UV layout, not its topology.** A garment vertex binds to a body UV and an offset, resolved to whatever body mesh is present when the character is loaded (one 2D lookup per garment vertex per body change; nearest surface point over a seam), so a replacer that keeps the UV layout keeps every garment, vanilla and modded, exactly as textures already survive body replacers in modded games; a body with a new UV layout is a new base, and the engine says so at load rather than drawing broken clothes. The UV layout is therefore a **versioned public contract** of the base, and a garment names the layout version it binds to. (2) **Fit is a quality level, not a requirement**: clipping-freedom comes from the binding, so an unfitted garment on an unbaked body does not clip; the fit relaxation runs per character instance at creation, asynchronously, and the population skips it or borrows the nearest preset's. (3) **Correctives are baked on the corners and interpolated like the body**, so the rule that bounds body sculpting ([ADR-0032](../adr/0032-characters-are-parameter-vectors.md)) bounds garment bakes too: a garment's design-time work is corners times key poses, independent of how many bodies players make; a modded channel outside the corner space still binds without clipping and only lacks wrinkle correctives, which the mod may ship and a validator names. (4) **Skeleton mods do not touch garments**, which bind to the surface and not to bones; the commonest reason for rig replacers, adding jiggle bones, is what the tissue model provides natively. A mod is a document layer plus a content pack ([02 §2.7](02-architecture.md)), so a body mod is a layer adding channels and presets with a pack holding the meshes, and a garment mod runs the same content build.

The 2026-09-23 torso review ([05 §5.16](05-simulation.md#516-characters-at-run-time), last addendum) adds to the tissue definition's validators a **containment** row and a **transition continuity** row, splits the skin binding into the internal footprint and the outer transition band as separate authored objects, and fixes the binding record's shape: a `u16` triangle index into the *derived smooth surface* (the limit-evaluated refined cage, not the control cage, so the refinement rule is part of the base's contract and identity stays at control level while bindings live at refined level), two `u16` barycentric weights, an `f16` normal offset and a per-vertex blend weight (a proposed packing of 10 bytes, 12 with a region id, not yet a measured quantization acceptance; the `u16` triangle index caps a region at 65,536 refined triangles, which an 800-node cage exceeds at level 3, so the binder refuses rather than wraps and a wider record or a split into regions is still owed, and the `f16` offset rounds by up to 30 µm at the 66 mm residuals the fixture measured), applied as a displacement transfer (base plus weight times the surface's change from its reference observation, so the reference surface is the base bitwise over the whole domain; a normal residual h transports as weight times h times the *change* of the normal from its reference, never as an absolute offset along the current normal, which is nonlinear in the nodes, needs a declared linearization for the runtime, is meant for a dermis-scale h, and whose h(cos θ − 1) projection term is a reported diagnostic and never a volume allowance), the same record a garment binds with ([above](#711-characters), garments note), so one transfer serves skin over cage and cloth over skin. A region ships physical moduli in SI units and never compliances; the build derives the solver's compliances from the cage's cell size ([ADR-0029](../adr/0029-deformable-volume-budgets.md)), which is necessary and not sufficient for an edge network: its compliances are calibrated per cage by an affine patch test against the declared moduli, per shear plane, because an edge network's effective moduli follow the mesh's edge orientation. The validator rows the studies settled on: base bitwise where the weight is zero, seam identity, image orientation (no inverted triangle), normal deviation from the limit surface (p95, with the per-sector maximum kept beside it so a small fold cannot vanish statistically), containment against the base with the rim step per sector, band bite by radius, and the three volume representations with the bias recorded at the reference state; a facet ratio and a curvature-times-offset bound were tried and replaced because the first sat below the evaluator's own floor and the second missed an inverted sliver the orientation test catches. Identity has to survive the weld: a per-vertex identity stream in the weld key, as the skin and morph streams already are, is a prerequisite for any authoring sidecar to name a vertex after the content build. **Status, 2026-09-23: the record and its evaluator exist** in `domain/geometry` ([geometry](../subsystems/geometry.md#limit-surfaces-and-surface-bindings)): `SurfaceBinding` at the proposed 10 bytes (pinned by the size table), `bind_to_surface` and `apply_binding` as the transfer above, and `build_loop_limit_surface`, whose level-3 operator for the neutral fixture's cage matches the authoring side's matrices entry for entry (7,009 × 121, 83,233 nonzeros, rows up to 28 wide) and whose matvec is `apply`. Measured on the record: 0.95 µm of quantization for offsets up to 3 mm, all but a trace of it the half float's. Two limits the implementation made concrete: the `u16` triangle addresses at most 65,536 refined triangles (1,024 control triangles at level 3), and Hoppe's boundary rules are G1 only at control boundary vertices with at most five faces. Not yet a container section, a content-build step or a GPU pass.

**Status, 2026-09-23 (identity): the control-level identity stream exists and survives the weld** ([geometry](../subsystems/geometry.md#canonical-vertex-identity), [assets](../subsystems/assets.md#canonical-vertex-ids)). Every imported vertex carries a `u32` canonical id — the glTF attribute `_CANONICAL_ID` when the base authors one, and otherwise the base's own rule, the index of the vertex's position in a position weld of the source ordered by position, so a UV-seam duplicate carries its twin's id. The weld keys on it (two vertices with different ids never merge; derived ids split nothing, and the samples' geometry is byte-identical with them), the LOD builder protects authored id seams, every cluster copy of a vertex carries its id through both merges and the page layout, the container stores it in append-only sections 30 and 31 (cluster cache version 12), `engine-content info`/`stats` report it, and the renderer's loaded scene exposes it read-only per mesh. What it does **not** do yet: nothing uploads it or reads it on the GPU; there are no refinement-level names for bindings to use, which wait for the limit-surface pass to become a content-build step; there is no sidecar format and no binding step that looks a vertex up by id; derived ids do not survive an edit to the base's own mesh (a base whose sidecars must outlive its edits authors its ids); and the LOD builder's protection of an authored seam is not absolute at the end of a slit (5 of 27 crossings remain on a 129 × 129 test grid).

**Status, 2026-09-24 (tissue definition): the definition, its container and its validators exist** ([tissue](../subsystems/tissue.md)). The skin binding's two authored objects are separate schema objects (`Footprint`, `TransitionBand`) over an explicit `CanonicalIds` domain; the records are the authoring side's own footpoints, imported by `bind_from_records` rather than recomputed as nearest points (whose lack of chart regularization reversed study019's first eight images); the binding names its Loop level, its refinement rule (`loop-hoppe-1994-v1`) and its **normal mode**, which is kept as authored and never substituted; the element kinds are schema types and one append-only container section each, and a reader skips a kind it lacks with a warning, as this section's note above asked.
