# Where a client names a file on the host's disk (survey, 2026-11-18)

Roadmap T174. The question: which protocol methods take a path, a directory or a file name from a **client** — or read a file that names one — and so make the host read, write, create or list on the operator's disk with the host's own rights; what a client learns or changes through each today; whether every role may call it; and what confines it now. It is the evidence for the design in [protocol](../subsystems/protocol.md#the-hosts-file-roots) and for [ADR-0071](../adr/0071-a-host-reads-and-writes-only-under-its-roots.md) (proposed).

**How it was taken.** By reading, not by running anything: `schemas/protocol.schema` for every `string` field and every struct a method takes, then each method's handler and whatever it hands the string to, on `main` at 0073605c and on the unmerged work of A3 (da05c9ac, which holds A10, A11, A12, A13, A14 and T44), of A4 (5a4d7577) and of D13 (fd3dde5e). Line numbers are those trees'; one of that work's is written `<id>:path:line`. Nothing was built and no engine process was run. A row that only *returns* a path is listed once, at the end of the table, since a returned path leaks the operator's layout but makes the host touch nothing.

**Roles.** `content/roles/roles.json` ships five roles: `director` (`*`), `designer` and `environment` (the `doc.*` editors, `lease.*`; on A3 also `doc.begin`/`commit`/`rollback`, on D13 also `doc.put_blob`), `qa` (no writes: the file's `default_role`), `performance` (`content.build`, `tunables.set`). A method registered `read_only` is open to **every** role, the default one included (protocol.md, "Identity, and what a role restricts"); a write is open to the roles that name it. "All" below means all five.

## The table

Access: **R** reads a file, **Rt** reads a file and every file it names (transitively), **W** writes or overwrites a file, **D** creates directories, **L** lists a directory, **X** executes a program. "Learns" is what a client can find out about a path outside any directory it should reach; "changes" what it can do to the disk there.

**A4** adds no method that takes or returns a path: `client.hello` names a client, and the credentials file is the operator's (`engine-host --credentials <file>`, `--issue-credential <file>`). What it changes is who a connection is, which is why this row matters more after it: a credential binds a connection to a role, so a role is no longer only what a call says it is, and a read-only role that can still write the disk through rows 2, 10, 13, 14, 21, 23 and 30 is the gap that is left.

**The served directory is writable through every writer above** (left unread by the security review of A3 and A4; traced here by reading). The shell directory is a directory on disk that the listener reads on every request, and its pages run in the operator's origin with the operator's cookie (on A4, the page *is* the operator). Nothing keeps a writer out of it: `render.capture`, `render.evaluate`, `render.compare` `flip_out` and `profile.report` force their extensions (`.png`, `.exr`, `.trace.json`), so what they can place there is an image or JSON, not a page; but `content.build` `output` (row 17) takes any file name, so a client holding `performance` can replace `shell/index.html` or add `shell/x.html` with a container whose strings (material names, image paths) the glTF it built chooses, and a browser that sniffs it as HTML runs them. That was not run; it is the case for the rule that no write root may hold a served directory. `session.open` with `create` (row 2) can make a document directory inside it, whose `manifest.json` carries the client's `name`.

**No method loads code a client names.** `session.load_game` loads a *save* (a document and a store), not a game module; a game module is hot-loaded only by `engine-view --game`, from its operator's command line (`apps/engine_view/game_runner.cpp`), and nothing in `apps/engine_host`, `apps/engine_editor`, `apps/mcp_bridge` or `domain/protocol`, on main or on the three branches, opens a shared library. The one program a host runs is `git` (row 35), found in the operator's environment.

## The operator's command line, which is not a client

These name paths too, but the person or script that started the process typed them, with that process's rights; they are configuration, and the design leaves them as they are:

- `engine-host`: `--doc`, `--create`, `--mount <scheme>=<dir>[:rw]`, `--roles`, `--tunables`, `--log-json`, `--shell`, `--script` (with `--console`), and on A4 `--credentials` and `--issue-credential`.
- `engine-editor --doc`; `engine-mcp --workspace`, `--connect-from`, `--mount`, `--roles`.
- `engine-view`, `engine-content` and every `tools/*.ps1`: all their paths are their operator's; `engine-view --game` is the one way a module is loaded.
- **`engine-cli --doc` is the operator's, but it reaches the host as a client's `session.open`** (`apps/engine_cli/main.cpp:237, 320-331`): engine-cli spawns `engine-host --stdio` and sends the path over the protocol, so today the host cannot tell it from row 1. The design moves it onto the spawned host's command line.

## The three worst rows

1. **`session.save_game` and `session.load_game` (rows 21-23)**: registered read-only, so the default `qa` role may make a directory anywhere and copy the open document and its store into it, or copy a save's into it, and then open a session there. It is a write to any place on the disk with no role able to refuse it.
2. **`content.build` `output` (row 17)**: a container written over any file the host may write, a document's own `layers/*.json`, `journal.jsonl` or `manifest.json` among them, which goes behind the journal, the roles and the leases at once. The `performance` role holds it.
3. **`session.open` (rows 1-3) and `render.load` (rows 5-9)**: read-only, so every role may learn whether any file exists, open and read any engine document on the machine and rewrite it with `doc.save`, and make the host parse any file as a scene, a mesh or an image; through row 9 a record a designer commits makes every later load read the path it names.

After them, by the same measure: the capture writers (rows 10, 13, 14, 30) write anywhere for every role, and `name` escapes a directory even where one is checked; `render.compare` (row 12) turns any image's pixels into a heat map written where the client says.

## What the three confined methods share, and where they fall short

`doc.place_asset` (A12), `doc.put_blob` (D13) and the listener's static files each carry their own lexical check, three copies of nearly one rule: relative, no drive, no `:`, no `..`, no empty name. Only `doc.put_blob` follows links (`std::filesystem::canonical` of both the directory and the file, then a component-wise compare). None refuses a trailing dot or space, a Windows device name, or a long component that a short (8.3) name stands for, and none compares case-insensitively on Windows (`canonical` returns the on-disk case of both sides, which is why `doc.put_blob`'s compare holds there, but a root spelled in another case before it is made canonical would not). And each answers a refusal with its own code and sentence. That is the case for one function every method calls.
