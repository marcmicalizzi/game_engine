# Every pass declares what its shader touches: an audit by reading (R186)

2026-11-18, batch 69. An audit by reading, a design for the guard, and no measurement: the batch's gate was running, so nothing here was built or run. Every line number is the tree at `cad063f8` (the tip of batch 68's stack, which holds R184's barrier rule). Nothing was mended; the mends and the guard are proposed at the end, unnumbered.

## Why

NVIDIA's 621.24 driver stopped running in order what the engine had not declared ([gfx](../subsystems/gfx.md#the-rhi-surface-and-the-backend-surface), "Render graph v0"; [renderer](../subsystems/renderer.md#mains-three-the-caches-passes-read-what-they-declared-only-to-write)). Batch 68 mended the passes that read a buffer they declared only to write and made every declared storage or transfer write name the read in its barriers (R184). What nobody had read for is an access the graph does not know at all: a shader that loads or stores through a device address in its parameter block, or samples an image, that its pass never declared. This page is that reading.

## What orders an undeclared access today

Three facts decide whether an undeclared access is a fault a person can see or a fault of bookkeeping, and the findings below are ranked by them.

**The graph's buffer barriers are global.** `compute_barriers` (`domain/gfx/src/render_graph.cpp:449-478`) emits a `VkMemoryBarrier2` for a buffer use, never a barrier naming the buffer. The reference page titles that structure "Structure specifying a global memory barrier", describes it as "affecting all device memory", and limits its scopes to "operations and memory accesses specified by the source stage mask and source access mask" and the destination's likewise (Vulkan reference pages, `VkMemoryBarrier2`, read 2026-11-18); `vkCmdPipelineBarrier2`'s page applies the first scopes "to operations that occurred earlier in submission order" and the second to those "later in submission order". So a barrier the graph emits for one buffer orders every earlier access of its source class before every later access of its destination class, whatever buffer they touch and whichever pass or frame they are in.

**The audit's test for "ordered" follows from that**: an undeclared read at (stage, access) of bytes an earlier command wrote at (stage, access) is ordered when some barrier recorded between the two names the write in its source masks and the read in its destination masks; otherwise nothing orders it. The specification's synchronization chapter opens with "The order of execution of commands with respect to the host and other commands on the device has few implicit guarantees, and needs to be explicitly specified", and its section "Execution and Memory Dependencies" says an execution dependency alone is not sufficient for a write's values to be read (the sentence beginning "Execution dependencies alone are not sufficient to guarantee that values resulting from writes in one set of operations…"; the fetch tool cut the quotation there, and the rest of that chapter, 710,000 characters, was not read). The driver holds the engine to the access masks and not only to the stages: the cache's fold stood behind a compute-to-compute barrier whose destination named the write alone, and read stale cells (batch 68's diagnosis log).

**Almost every undeclared read found rides a neighbour's barrier.** The frame is dense in barriers of the two common classes (a transfer write before a compute read; a compute write before a compute or fragment read), and since R184's second mend a later reader in another stage widens the destination of the barrier in front of the first reader (`render_graph.cpp:439-442, 472-475`), retroactively. A pass that reads the scene's instance table without declaring it is ordered behind the frame's table copies because the cull pass in front of it declared the same table. That is why the frame draws rightly, and it is why this is still worth mending: the cover is a property of which passes happen to stand between, a refactor or a configuration that removes the neighbour removes it without a compile error, and R4's aliasing and async compute need the declarations to be the whole truth, since a pass moved to another queue or a transient given another's memory is ordered by its own declarations and nothing else.

Three shapes are **not** covered by a neighbour, and they are where the dangerous findings are:

1. **A barrier whose destination names no read.** R184 made a declared storage write name the storage read and a transfer write the transfer read (`barrier_access`, `render_graph.cpp:111-119`). An `Access::AccelerationBuildWrite` is `ACCELERATION_STRUCTURE_WRITE | SHADER_WRITE` (`render_graph.cpp:87-90`), neither of the two bits the rule looks for, so a build behind a build still gets a write-to-write barrier.
2. **Two commands in one pass body.** The graph puts barriers between passes. A body that records two commands of which the second needs the first is ordered by nothing the graph emits.
3. **A resource the graph never sees whose only users are commands that take it as an argument**, not as an address in a block: no pass's barrier is "for" it, and the neighbours' barriers cover it only by class.

## Findings of class (d): a write the graph does not know

Most dangerous first. "Decides" says what settles whether it can be seen.

**D1. The acceleration structure builds share a scratch buffer nobody declares.** `GpuScene::rt_scratch` (`gpu_scene.h:1636`) is handed to four build commands, in the passes "clas cache" (`scene_renderer.cpp:6072`, used at `:6089`), "clas" once a chunk (`:6110`, `:6141`), "blas" (`:6170`, `:6191`) and "tlas" (`:6217`, `:6227`), and is not among the graph's imports (`:4864-4897`). Every build writes and reads it. Between "clas cache" and the first chunk, between the last chunk and "blas", and between "blas" and "tlas" a neighbour's barrier names an acceleration-structure read (`cache_slots`, `clas_addresses`, `blas_data`), so those pairs are ordered by class. **Between chunk k and chunk k+1 the only barriers are the ones for `clas_addresses` and `clas_sizes`** (`:6124-6125`, `AccelerationBuildWrite` behind `AccelerationBuildWrite`), whose destination names the write alone: shape 1 above, the shape the cache's fold had. The comment at `:6116-6117` says the chunk before "wrote the same arrays and shares it too" and counts on the graph for the order. Every chunk's build starts its scratch at the same address (`domain/gfx/src/cluster_acceleration.cpp:369`). Chunks are R152's default (`rt_step.h:14-24`): more than one whenever the capacity passes a chunk's clusters, which the forest's does.
*Decides*: whether 621.24 lets two cluster builds overlap when the barrier between them names no read. By the specification's letter the barrier's stages still make an execution dependency between the two builds; the diagnosis of the cache's fold did not separate whether the driver honours an execution dependency whose access masks name no read ("which of the three declarations the driver needs was not separated", its log). *Seen as*: cluster structures built from another build's scratch, which is holes or stray triangles in the traced picture and its shadows that differ between two runs of one scene, or a lost device.
*Declaration*: import the scratch and declare it in each of the four passes with an access that names both the acceleration-structure read and write at the build stage; and, for the class, make `barrier_access` give a declared `AccelerationBuildWrite` the acceleration-structure read, as R184 did for storage and transfer.

**D2. The deformed normals are written and read through a buffer the graph never imports.** `GpuScene::deform_normals` (made at `gpu_scene.cpp:2990`, `:3199`, `:3618`) is a buffer of its own beside `deform_pool`. The pool pass writes it (`deform.slang:755`, stores at `:780, :820, :838, :850`; `DeformParams::normal_pool` filled at `scene_renderer.cpp:4217`) in "deform" (`:5450`, declarations `:5452-5460`) and in "shadow deform" (`:5708`, whose block is a copy of the camera's, `:4391-4392`), and the resolve family reads it (`material.slang:258-261` and `:495-496`, through `visibility_resolve.slang:411`; `ResolveParams::normal_pool` filled at `:3992`) in "resolve" (`:6524`) at the fragment stage and in "gi sample" (`:6405`) at the compute stage. `scene_renderer.cpp` names the buffer nowhere else. *Decides*: it rides `rg_pool`: the pool is written by the same dispatch and read by the same passes, each of which declares it at its own stage, and the pool's barrier is global. It is ordered for as long as every writer and reader of the normals also declares the pool at the same stage, and unordered the day a pass shades from the normals without reading positions from the pool. *Seen as* (were it to come apart): a moving terrain's, a morphed mesh's or a swaying tree's shading lagging its shape by a frame, in patches. *Declaration*: import it; `ComputeReadWrite` in "deform" and "shadow deform" beside the pool; the readers' stage read wherever `rg_pool` is read for shading (the resolve, the bounce's sample pass).

**D3. "deform cache" declares the pool and writes the static cache.** The pass (`:5349`) declares `b.write(rg_pool, ComputeWrite)` (`:5352`) and its shader (`deform.slang:864-890`, `deform_cache_main`) stores into the static shape cache, a separate buffer (`DeformDesc::cache`, `gpu_scene.cpp:3028`); "deform" and "shadow deform" read that cache and declare `rg_pool` `ComputeReadWrite` for it (`:5457`, `:5715`, each with the comment "reads the static cache"). Batch 68's leg D recorded this as the pool standing in for the cache. *Decides*: nothing today, since the stand-in is used consistently by the one writer and the two readers. It is a write under another buffer's name, which an aliasing graph or the guard below must not be taught to accept. *Declaration*: import the static cache under its own name; write in "deform cache", read in the two pool passes.

**D4. The texture uploads in "terrain upload" are images the graph never sees, ordered by barriers in the pass body.** `scene_renderer.cpp:5078-5082` calls `gfx::record_image_levels_upload`, which records its own two image barriers round the copy (`domain/gfx/src/device.cpp:1621-1628`), the second to `ALL_COMMANDS` and `SHADER_READ`. *Decides*: the second barrier names every later shader read of that image, so it is ordered by the letter. It is the one hand-written barrier in a pass body the audit met, which the batch's rule says is never the mend. *Declaration*: import each uploaded image and declare the transfer write, with a final layout of shader-read; the body then records the copy alone.

**D5. Two host-read blocks are written by shaders with no declaration, and nothing in the frame reads them.** The cull pass's measurement adds into `hidden_counts`, which is a range of the frame slot's parameter block (`cluster_cull.slang:455, :480`; `scene_renderer.cpp:3933`, only under `occluded_hist`), and the exposure's shader writes its report into `reports_[slot]` (`exposure.slang:195`; `exposure_pass.cpp:213`; the pass's imports at `:236-239` are the bins and the state). The host reads both after the slot's frame has finished. *Decides*: no reader in the frame, so no order to lose; the first is also a shader writing into the block it takes its own parameters from, in the pass's later views' dispatches too. *Declaration*: a graph buffer each (the slot's block imported, or the counts moved to a buffer of their own), declared `ComputeReadWrite`.

### Inside one pass body (shape 2)

These are not undeclared resources; they are orders the graph cannot give, found while reading the bodies.

**P1. "gi stats" copies the cache's header out and then clears it, in one body** (`:6462-6473`: `copy_buffer` then `fill_buffer` over the same `k_gi_header_bytes`). The pass declares the read and then the write, which orders it against its neighbours and puts nothing between its own two commands. *Decides*: whether the driver ever runs a fill ahead of a copy recorded before it over the same bytes; it has not been seen to. *Seen as*: the frame's statistics reading zero cells and rays, and whatever the ray budget does with that. *Mend*: two passes, the copy and the clear.

**P2. "terrain upload" can copy one material record twice** (`:5076-5077`, a `copy_buffer` a `GeometryCopy`): the texture bound pushes one copy of a material's whole record for each of its textures that is promoted (`gpu_scene_texture_bound.cpp:737-750`), each later copy carrying the earlier change, so the last must win. *Decides*: whether two textures of one material are promoted in one frame, and the same question as P1. *Seen as*: a material sampling a retired texture slot until its next promotion. *Mend*: one copy a record, joined on the CPU where the list is made.

Checked and independent: the views' dispatches of "cull", "deform" and its motion pool, "trace", "software", "half sun", "expand", the cascades' of "shadow cull", the two dispatches of "pair expand" (disjoint slots, `:5268`), the two of "texture feedback" (two tables), "medium clouds" (the march does not read the shadow map: only `froxel_fill_main` calls `cloud_sun`, `medium.slang:1017`, and "medium fill" declares it). The views of "gi sample" share the cache through atomics, as the threads of one dispatch do.

## Findings of class (a): a read of what an earlier pass of the frame wrote

None of these was found uncovered: each rides a barrier some neighbour's declaration emits, as the section above explains, and each entry says which. They are ranked by how thin that cover is.

**A1. The visible list, read by the resolve, the half-rate sun pass and the bounce's sample pass.** Writer: "cull" (`:5292`, `b.write(rg_visible, ComputeWrite)` at `:5297`), and under the cascades "shadow cull" (`:5654`, `:5659`). Readers: "resolve" (`:6524`, declarations `:6526-6565`), "half sun" (`:6334`, `:6336-6353`), "gi sample" (`:6405`, `:6407-6428`); none declares `rg_visible`, which "trace" does (`:6240`). **A2. One buffer under two handles: the instance table, and the geometry of a streamed scene.** `scene.instances` is imported as `rg_instances` (`:4665`, on a frame that writes a table set) and again as `tg.instances` (`:4786`, on a frame that moves instance records); `scene.clusters`, `quantized`, `attributes`, `triangles`, `vertices` and `indices8` are imported as the page pool's (`:4808-4820`) and again as the rings' (`:4765-4772`). ## Class (b): written at load, or by the host, outside the frame's graph

Not faults; listed so a guard knows what to let through, with what orders each.

- **Uploaded once and waited for**: `gfx::upload_buffer` and `gfx::submit_immediate` submit and wait before they return (`submit_immediate` waits on its fence, `domain/gfx/src/device.cpp:991-992`; `upload_buffer`'s body was not read; 43 lines of `gpu_scene.cpp` name one or the other; the rings' first chunks at `:995`; the shadow coverage bake `:5239`; the micromap bake; the static bottom-level structures). The scene's mesh, cluster and material tables of a scene read whole, `lod_coverage`, `shadow_coverage`, `sky_facing_`, the crowns' priors, the star tables, the micromap tables, `static_addresses`, the page tables. Ordered by the wait.
- **Per frame slot, written by the host while recording, read by that slot's frame**: the cull and resolve parameter blocks with the eye, the lights, the sky's block, the cascades' block and the ground detail (`params_`, `resolves_`, `ray_params_`); the deform table, joints and morph weights of a slot; the flora poses and the field block; the terrain level table; the stream block and residency; the cache tables' copy and the drop order; the moved-instance table; the overlay's vertices and indices; the volumetrics', the collision draw's and the feedback's blocks. Ordered by the slot's own recycle (its previous frame has finished) and by the submission following the write. Whether each such buffer is on a host-coherent memory type or flushed was not checked.
- **The staging buffers the uploads copy from** (the page stage, the terrain and record stagings): host-written before the frame; "page upload" and "record upload" declare theirs, and "terrain upload" declares the fields' stagings and not the geometry copies' source.
- **The reference path tracer** records no graph pass: each batch is one dispatch in a waited submission (`reference.cpp:328-345`), so the accumulator one batch reads is the last batch's by the wait and by no barrier.

## Class (c): what the previous frame wrote

`import_buffer(name, buffer)` with no state says "never used" (`render_graph.cpp:220-236`): the first read gets no barrier and the first write none either (`:451`, a write needs a barrier only behind a use). Imported so, and read before this frame writes them: the Hi-Z pyramid the first cull pass tests against (`:4648`), last frame's occlusion flags (`:4619`), last frame's visibility and motion buffers under the accumulation and the reconstruction (swapped, not copied: `motion_pass.cpp:172-177, :229-231`; imports `accumulation_pass.cpp:201-202`, `reconstruction_pass.cpp:89-91`), the world-space cache's cells (`:6376`), the cluster structure cache's keys, owners, stamps and slots (`:4866-4878`), the sky's two scene tables, and the static shape cache. **What orders them** is whichever barriers of the right class lie between last frame's write and this frame's read: there usually are some, since submission order spans frames, and nothing declared says so. In the plain configuration (hardware raster, two-pass occlusion, no instance pass, no bounce, no frame pass) the audit found no compute-write to compute-read barrier that must lie between last frame's last Hi-Z build and this frame's first cull. The same holds the other way for every per-frame buffer: this frame's "reset" fills the visibility buffer with no barrier behind last frame's resolve reading it (without the motion pass's swap they are one buffer). The tree already has the right form where someone met the problem: the uploads import "as last read everywhere" (`:4758-4763`), the exposure and the froxels import with a state (`exposure_pass.cpp:236-239`, `volumetrics.cpp:1191-1193`). *Declaration*: the graph remembers a buffer's final stage and access across `reset()` and an import with no state takes them, as an image's layout is carried today.

## The guard

Three checks, the cheapest first. Each is a debug build's (the configuration that carries asserts); a release frame pays nothing.

**1. One import a buffer (S).** `import_buffer` and `import_image` assert that the resource is not already in the graph. A linear look over the imports made so far, about 150 a frame: microseconds. It refuses A2's cause outright and forces the helpers to be joined. It sees nothing about shaders.

**2. Every address in a pass's block resolves to something the pass declared (M).** This is the mechanical form of the rule.
- Each mirrored block lists its address fields once, beside its size-table entry: offset, and whether the shader reads, writes or both, or whether the field is a pointer to another host-written block with a list of its own (`CullPush::params` to `CullParams` to `StreamParams`; `ResolveParams::sky_params` to `SkyParams`; `RecordParams::cache` to `CacheTables`). 64 structs carry addresses today, about thirty of them the frame's. The lint can hold each list to the `.slang` struct's `uint64_t` fields by text, as it holds other mirrors.
- A pass's setup names the blocks its body pushes: `b.block(bytes, fields)`. The bytes are the host's copy, which the recording already has.
- The device keeps a registry of live buffers that have an address: range, and one flag, "constant for a frame" (set by `upload_buffer`, and by the owner of a per-slot host block). Sorted by address.
- At `compile()`, for every non-zero address of every block: inside a buffer this pass declared with an access that covers the field's kind, it passes; inside a graph buffer the pass did not declare, the compile fails naming the pass, the field and the buffer (A1, A2, A3, A5 and the read half of D2); inside a registered buffer marked constant, it passes (class b); inside a live buffer that is neither, it fails (the write half of D2, D3, D5: a buffer a shader writes that the graph was not told about); inside no live buffer, it fails, which also catches an address of a retired buffer.
- The builds take their scratch and their sets through the same call, so D1 is the same check.
- **Cost**: about 60 passes and 600 address fields a frame against a few hundred ranges, a binary search each: tens of microseconds in a debug frame, in vectors kept across frames like the barriers'. To measure when built: `engine-view --scene content/test-scenes/desert-overlook/scene.json --camera-path <path.json> --benchmark out.jsonl` in `msvc-debug` with the check on and off, the frame's `compile` phase.
- **What it cannot see**: a bindless image or a top-level structure, which a block names by slot and not by address (a second list, slot to resource, would take the same check: the atlas and the linear image are declared today and the material textures are class b or D4); an address a shader finds inside a table on the GPU (`MeshDesc::deform_pool`, `deform_slots`, `quantized`; `DeformDesc::cache`; a cluster record's vertex and index buffers; a bottom-level record's references), which the pass that owns the table has to declare by hand; whether the shader reads the field in this frame (it treats a non-zero address as used, so a block has to keep zero in what a pass does not use, which is already the convention: "0: none"); a field's kind being wrong in the list; A4's stage, unless a field's list says which stage reads it; two commands in one body (P1, P2); histories (below).

**3. The frame drawn twice, once with every pass serialized (S).** A tunable (`renderer.graph.serialize`, off) under which the graph records, before every pass, one global barrier from every stage and access to every stage and access. A GPU case draws the path scenes' frames with it on and off and holds the visibility buffer and the colour to the same bytes; a second tunable names the one pass to serialize before, which is how a difference is walked to its pass. It proves nothing where the driver happens to run in order, and it is the only one of the three that sees bindless images, addresses inside GPU tables and whatever a block's list got wrong. It does not see inside a pass body.

**Histories** take a fourth, small piece: the graph keeps each imported buffer's final stage and access across `reset()` (a map of about 150 entries, the "persistent graph cache" the header already names as later work) and uses them for an import that gives none.

**Where the first version goes**: checks 1 and 2 in `domain/gfx/src/render_graph.cpp`'s `compile()` with `PassBuilder::block` in `render_graph.h` and the registry in `domain/gfx`'s device; the lists beside each block's header; a case in `render_graph_tests.cpp` for each refusal (a pass that holds an address it did not declare; a block naming an unregistered buffer; a double import), on no device, since nothing in it records.

## R186-1: what was mended

**C1, a finding added before the mends: the ray-tracing chain's buffers across frames.** A lead from a read-only review on the other coordinator's side (unverified when it came): every buffer of the chain is one set shared by the frames in flight and was imported naming no last stage or access (`scene_renderer.cpp`, the chain's imports), and `FrameContext::end_frame` submits waiting on nothing from the frame before (`domain/gfx/src/frame.cpp`, the submit: a wait only on the swapchain's acquire, at the stage the caller names), so frames two slots apart overlap on the device. Verified by reading: an import with no state gives the first write no barrier at all (`compute_barriers`: a write needs one only behind a recorded use) and the first read none, so the frame before's last use is ordered before this frame's first only through an execution dependency chain of barriers that happen to lie between them (the specification's chaining rule: consecutive dependencies chain when the first's second scope and the second's first scope intersect). The globality of the graph's buffer barriers is what makes such chains common: a build's last read of the records in frame N is followed by the build-to-compute barrier in front of "tlas instances", which chains through frame N+1's compute-to-compute barriers to its first records pass. **What breaks the chain is a last use at the fragment stage**: the resolve's shadow rays read the top-level structure, the bottom-level set, the cluster chunks and the record-to-entry table, and in a traced frame no barrier between frame N's resolve and frame N+1's builds and emit pass names the fragment stage in its source (the only imports that do, the shadow atlas, the frame passes' image and the uploads' "last read everywhere", exist only under the cascades, the frame passes or an upload). So frame N+1's builds can overwrite the structures frame N's resolve is still tracing: real, by the letter, and hidden by nothing but the driver running submissions in order. *Mend*: each buffer of the chain imported naming its last use, every stage the chain is used at and every access (`import_chain`); the scratch with them. *Guard*: check 3's serialized frame records a full barrier before the first pass too, which orders a frame behind the one before, so a difference it finds can be this; no case was made that fails without the mend, since a capture waits for its frame and two frames' overlap on one queue is the driver's to choose. The audit's class (c) above is the same shape for the frame's other buffers and stays open.
