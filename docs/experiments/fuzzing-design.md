# Fuzzing the readers, the protocol and saves (design, 2026-11-18)

Roadmap T13; [plan 09 §9.1](../plan/09-testing-profiling.md#91-test-taxonomy)'s "Fuzzing" row, [plan 08](../plan/08-toolchain.md)'s "fuzz tests on every parser and protocol handler", and the memory-safety burden [ADR-0013](../adr/0013-cpp20-only.md) puts on fuzzing in place of a second language. **Status (2026-11-18): stage 0 is written** — the harness of §2 in `tests/support/fuzz_*.h`, `engine_module_fuzz()` in `cmake/EngineFuzz.cmake`, the `linux-clang-fuzz` preset, and the first target, `parse_json` (`core/json/tests/fuzz_parse_json.cpp`, seeds under `content/fuzz/parse_json/`); how a target is added is [the harness's page](../ci/fuzzing.md), and what the gate pays is [what to run](../ci/what-to-run.md#the-hostile-input-cases). Every oracle of §2 is in the in-tree runner except a sanitizer report, which is the sanitizer builds' own. Built on stage 0: nothing for the nightly on the server, which is the owner's question 2; stages 1 to 5 are open. Reader faults §1 found are mended by their own rows (T187), and a target that meets one lists it as a known failure under that row's id rather than mending it. The rest of this page is the design as written. **Before stage 0 it was a design: nothing was built and nothing was run.** It says every place the engine reads bytes it did not write, what each does today with bytes chosen to hurt it, the harness that finds out, what the gate pays for it, and the order the readers are taken in.

**How it was taken.** By reading the tree at `cad063f8` (batch 68's stack): each reader's entry, its checks and its negative tests, surveyed in three parts and every finding the table below calls *checked* re-read line by line; the client-named paths are T174's survey (`host-file-roots-survey-2026-11-18.md`, on its own branch, 37 rows), which this page does not repeat. The fuzzing tools' behaviour and licences are read from their own documentation on this run, cited where used. Plan 09's other fuzz targets, destruction sequences and the simulation's input, belong to the playtest row (A29) and are not designed here.

## 1. The inventory

"Reach" says who can make the engine read the bytes: **any role** is a protocol method registered `read_only` (open to every role, the default `qa` one included), **writer** a method some roles may call, **operator** a command line or a file the operator places, **repo** a file in the repository. "Today" is what the reader does on hostile bytes by reading, not by running.

### What the reading found

Every row marked *checked* above was re-read at its line on this base; the rest are the survey's reading and are marked "not run" where the outcome needs a run. By class, with the reach that ranks them:

- **Reads past a buffer or unbounded recursion, any role**: cgltf's wrapped accessor bound; the engine's wrapped `inverseBindMatrices` size; `append_node`'s depth; the `.clusters` ranges. Every one is reachable through `render.load` from the default role.
- **An allocation or a loop a file sizes, any role**: `scatter.count`; a camera path's frame count; an image header's dimensions; a batch's length; descending JSON keys.
- **Undefined behaviour on a value**: `f32` from a large double (every schema-typed `f32` field), `doc_scene`'s `i64` product, an input log's `f32`.
- **Assert on external input**: `engine-mcp --connect-from`; the `.clusters` ranges in a debug build.
- **Paths a file names**: a layer's `file`, a save's unlisted files, record and pack paths — T174's design closes these with one admission function; a fuzz target only checks that it is used.

## 2. The harness: both, with different jobs

**A target is one function, run two ways.** Each reader gets a function `fuzz_<reader>(std::span<const u8>)` beside its tests that calls the reader's memory entry (most have one: `parse_json`, `dispatch_text`, `decode_frame`, `parse_http_request`, `load_gltf_memory`, `read_cluster_file_memory`, `read_texture_file_memory`, `decode_image`, `reflect_spirv`, `parse_camera_path`) and checks the oracles below. Under CTest it is a doctest case in the module's own test executable, so `-Affected` selects it with its module and nothing new is scheduled; with Clang and a fuzz preset the same function is wrapped as `LLVMFuzzerTestOneInput`. One function means a finding in either is a case in both.

**In-tree: a deterministic, structure-aware mutator on every preset, every change.** Seeded and bounded by count, never by time: for each seed input and each iteration *i*, the mutation is a function of (target, the seed's hash, *i*) through a SplitMix-style generator of the harness's own, because the standard leaves its distributions' algorithms to the library and the same seed must give the same bytes from MSVC, GCC and Clang. No threads, no clock, no system temp directory: an input that fails is written into the test's `TempDir`, kept, and named with its target, seed file and iteration, which reproduces it anywhere. Mutators by layer, each reused by every reader that shares the layer:

1. **Bytes**: flip, insert, delete, splice two seeds, and write interesting integers (0, 1, −1, 2^15, 2^16−1, 2^31, 2^32−1, 2^53, 2^62, 2^63−1, as 8 to 64 bits) at aligned offsets — the values that turned up every wrap in §1.
2. **JSON**: on a parsed `JsonValue`, not bytes: replace a number with an interesting one, change a value's kind, duplicate, drop or reorder keys, deepen nesting to the cap and one past it, repeat an array element a thousand times, put invalid UTF-8, a NUL, `..`, an absolute path or a device name in a string; written back by the engine's own writer. For the parser itself, the bytes layer as well.
3. **Schema-typed**: walk a type's `TypeInfo` (the tables schemac already emits) and generate a value per field kind — every enum name and one past, every integer width's ends, `Id128`s, positions at the edge of the world. **This is the lever**: one generator covers every method's params (the dispatcher's catalogue names each params type), every record type in a layer, and every schema-typed file (scenes, camera paths, saves' `save.json`, packs, flora recipes), with no grammar written by hand, which is what the structure-aware fuzzing guide reaches with protobuf descriptions ("Structure-Aware Fuzzing with libFuzzer", google/fuzzing, `docs/structure-aware-fuzzing.md`, read on this run).
4. **Containers**: `.clusters` and `.tex` by their section table: a section's kind, offset, size and count, then the known payload fields (a `ClusterDesc`'s offsets and counts, a level's extent), and **the content hash recomputed**, as `cluster_file_tests.cpp`'s `rehash` does. Without the fix-up every mutation dies at the hash and nothing behind it is reached; the guide's zlib and PNG examples make the same point about checksums.
5. **glTF**: the JSON layer on accessors (`count`, `byteOffset`, `byteStride`, `componentType`, sparse), buffer views, nodes (children chains thousands deep, cycles), skins and URIs, with the buffer carried as a `data:` URI so a seed is one text file; GLB by its chunk lengths.

Seeds for binary formats are **made at test time by the engine's own writers** from the fixtures the tests already build (the cluster writer, the texture writer, `encode_png`), so no binary seed is committed.

**What a finding is** (the oracles, every one checked after every input):

- a crash or fault, which `platform` already turns into a line and an exit code;
- **`ENGINE_ASSERT` firing**: a reader never asserts on external input (AGENTS.md, "Asserts"), so in a debug build an assert reached from bytes is a finding, not a test bug;
- a sanitizer report (the nightly, and `linux-clang-asan` and `msvc-asan` whenever they run the in-tree cases);
- **an allocation past the target's cap**: each target declares a cap as a multiple of its input's size plus a floor, checked against the engine allocator's counters (`core/memory`'s `Stats`); third-party `malloc` (cgltf, stb) is the nightly's `-malloc_limit_mb`;
- **a hang**: the nightly's `-timeout`; in-tree, a watchdog of 30 s an input whose only job is to turn a hang into a failure that names the input (count-bounded mutation keeps an honest run far below it);
- **a broken contract**: a refusal leaves the output empty and the message non-empty (the existing tests' "an error instead of a partial mesh"), and an accepted input that has a writer reads back from its own writing to the same value (JSON, layers, `.clusters`, `.tex`, input logs).

**Nightly: libFuzzer with the sanitizers, on the GPU server, not at the gate.** Coverage guidance finds what a count-bounded mutator cannot (a branch twenty mutations deep), and it needs hours, which the gate never has. A preset `linux-clang-fuzz` (Clang, Debug so asserts are live, `-fsanitize=fuzzer-no-link,address,undefined` on engine code and `-fsanitize=fuzzer` on the target links, as libFuzzer's documentation describes the two; x86-64-v2 so it runs on the server) builds one executable a target. The server is the right place: a real Linux machine with clang 22.1.8, 16 threads and 31 GB ([remote Linux](../ci/remote-linux.md)), no GPU needed, and not the machine the gate and the agents share. It has no PowerShell and the repository takes no Python, so the desktop drives it over ssh as `tools/remote-build.ps1` already does (a `-Fuzz` mode, proposed). Flags per target: a `-max_len` the target names (64 KiB for text, 1 MiB for containers), `-timeout=10`, `-rss_limit_mb=2048` (libFuzzer's default), `-malloc_limit_mb=1024`, `-max_total_time`, a committed text `-dict` of the format's keywords, and `-minimize_crash=1` for a finding. Defaults read from the libFuzzer page (llvm.org, `docs/LibFuzzer.html`, read on this run): `-timeout` 1,200 s, `-rss_limit_mb` 2,048, `-malloc_limit_mb` 0 meaning the RSS limit.

- **Licence**: LLVM is Apache-2.0 with the LLVM exceptions, and a runtime the compiler embeds owes no attribution (LLVM Developer Policy, "License", read on this run); libFuzzer comes with the compiler's runtime (`libclang-rt-18-dev`, already in the container image for the sanitizers), nothing is vendored or fetched, and Apache-2.0 is on [ADR-0014](../adr/0014-apache-2-license-and-dependency-policy.md)'s list. `third_party/LICENSES.md` gains a line naming it as the fuzz preset's toolchain runtime so the licence check knows it.
- **libFuzzer is in maintenance**: its authors "have stopped active work on it and switched to working on" Centipede, and it is "still fully supported" for important bugs (same page). That is acceptable here because the target signature is the stable part: whether Centipede or AFL++ run an `LLVMFuzzerTestOneInput` target unchanged was **not read** on this run, and is the check to make before the nightly's second year.
- **MSVC's `/fsanitize=fuzzer`** is "experimental", since Visual Studio 2022 17.0 (Microsoft Learn, "/fsanitize", read on this run). Declined for now: the in-tree cases already run on MSVC, and a second coverage engine on the one shared desktop is the cost T13 must not add.
- **Declined**: FuzzTest and libprotobuf-mutator (a framework or protobuf dependency for structure the `TypeInfo` tables already give; not read beyond the guide), OSS-Fuzz (the repository is public, so it is possible; the owner's call, not read on this run).

**Corpora.** Seeds are **text**, committed under `content/fuzz/<target>/seeds/` (JSON, `.gltf` with `data:` buffers, JSON-RPC lines, HTTP heads, scene and camera-path files), a seed at most 16 KiB, a target's seeds at most 256 KiB, the directory at most 2 MiB (proposed caps). **A finding becomes a regression case** in the commit that fixes it, failing before the fix: a text input under `content/fuzz/<target>/regress/` with a one-line note of what it found, or, for a binary format, a doctest case that builds the input from the writer's fixture and the minimized edit (the field and value), since a binary file is not committed. Every regression replays first, on every build, before any mutation. **The nightly's grown corpus lives on the server, outside the repository**, merged weekly with `-merge=1` (the libFuzzer page's minimization), and is never committed; a new input is promoted to a seed by hand only when it is text and small.

**Drive wear.** A reader that needs a directory (the document store, saves) would write files on every input. The in-tree cases keep to a few hundred inputs in one `TempDir`; the nightly uses the server's `tmpfs`; and an in-memory mount for `io::Vfs` (its header lists the absence) is the better answer, proposed with the documents' stage.

## 3. What the gate pays

- **`msvc-debug`, every change**: the in-tree cases are CPU-only (`NO_DEVICE`) and count-bounded, budgeted at **10 s a target and 60 s for all of them** in a serial debug run. The gate's Windows half is bounded by `msvc-debug`'s chain of GPU-labelled tests (64 minutes of suites at gate b58, [the gate's wall clock](../ci/what-to-run.md#the-gates-wall-clock-t77)) with CPU tests run beside it on three jobs, so a minute of CPU adds about nothing to the gate's wall clock. **To measure** when stage 0 lands: `tools/dev.ps1 test -Preset msvc-debug -Filter '<module>' -NoDriver` before and after, and CTest's per-test times; the iteration counts are set so the slowest target stays under its 10 s, and the counts, not a clock, are what is committed.
- **Linux containers and CI**: the same cases on GCC 13 and Clang 18; under `linux-clang-asan` ([sanitizers](../ci/what-to-run.md#sanitizers)) they become a sanitized fuzz run on every push for no extra job, which is most of the in-tree half's value.
- **Only at night, on the server**: libFuzzer, about two to three hours a night across the targets on at most 12 of the 16 threads, never while a gate's server leg runs (whether `remote-build.ps1` holds a machine lock there is **to confirm**), one JSON line a target (executions, coverage features, corpus size, findings). A finding opens a row at the top of the next batch, as a red server leg does. **To confirm before stage 0**: the server's clang ships the fuzzer runtime (`ls $(clang -print-resource-dir)/lib/*/libclang_rt.fuzzer*`).
