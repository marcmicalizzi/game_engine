# Where on the Earth a scene is: the standards' names (W186)

2026-11-25. The grounding for `engine.scene.Georeference` ([scene_gen](../subsystems/scene_gen.md#where-on-the-earth-a-scene-is)): how the standards that already solve the problem name the same facts, so that the block's fields and their meanings are theirs and not invented here. Every source below was read as text through a fetch tool; nothing was saved, and no number or line was taken from code. Each is marked by how far it was read and under what terms its text stands.

## What the block takes from them

- **Two systems, named separately.** ISO 19111's compound CRS is a pair of independent systems; the block names the pair's two halves (`horizontal_crs`, `vertical_crs`) rather than one compound code, since a compound code exists for some pairs only (CityJSON's EPSG:7415 is one) and a tile tool reading lidar names the two separately anyway.
- **A name is an authority and a code, or well-known text.** EPSG's `EPSG:<code>` is the form most tools print and the OGC URL's last two segments; a system with no code (a local grid) is given by its WKT. The engine reads neither: they are strings a tool compares and hands to a library of its own.
- **The origin is a translation, as everywhere.** CityJSON's `translate`, the world file's C and F, 3D Tiles' root `transform`'s last column: each format carries a local origin as map coordinates beside the system's name. The block's `origin_easting`, `origin_northing` and `origin_height` are the same thing at the world's origin, in f64, with no scale (the engine's unit is the metre; `unit_m` is the map's unit, for the foot grids).
- **The axis-order trap, handled by naming.** The same pair of numbers comes easting first in EPSG:2952 and northing first in EPSG:31467, and every format above leaves the order to the system's definition. A field called `x` or "the first coordinate" is read the wrong way round in one of them, so the block names its fields by meaning (`origin_easting`, `origin_northing`, `east`, `north`), and the one place a tuple's order matters is the tool that reads a tuple in its system's order, once.
- **The engine's axes are stated, not assumed.** glTF and the engine are y up and right-handed; 3D Tiles is z up and turns glTF's frame by a quarter turn. The block says which signed engine axis east and north lie along, with the engine's up the vertical system's up, so that no reader guesses: `PlusX`/`MinusZ` is a rotation of the map, `PlusX`/`PlusZ` its mirror image.

## What the block does not do

No projection, no datum shift, no grid convergence or scale factor, no rotation other than the four quarter turns and their mirrors. A world whose engine axes are not along the map's grid lines, or a tool that needs latitude and longitude, does that arithmetic in a library of its own, outside the engine, from the map coordinate `map_from_world` gives it.
