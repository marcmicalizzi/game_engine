# Where the v35 forest's load goes, and what came out of it (2026-11-08)

Roadmap T73. The owner, 2026-11-07: loading the forest proof of concept's v35 takes about ten
minutes, peaks at 20 GB of RAM and 16–18 GB of VRAM. Not a new asset format and not a smaller
world: the load as it is, measured stage by stage, and its largest costs taken out.

## What was measured, on what

- **The world**: the POC's v35 scene (`scene.json`, 121 MB; 16,351 meshes, 12,470 of them channel
  ribbons, 3,155 flora recipes, 613 deadwood; 5,392 built textures), its derived-data cache as the
  POC had it (every entry present: all meshes `hit`, `textures trusted=5392 built=0`), its material
  pack.
- **The owner's run**: `reports/lab/20261107-161639-528/` — 3840×2160, `--raster rt --shadows rt`,
  the game module with 416 animals and the player, interactive, its load on a load thread. Its
  startup trace is the one in the table below; the trace filled at 251 s (below), so it ends there.
- **The engine-only runs**: `engine-view --offscreen --frames 1` at 1920×1080 with the engine-only
  flags of the batch (`--terrain-tiles --terrain-far 6 --time-rate 0 --world-rate 1 --time-of-day
  15 --no-lights --lod 1 --deform-pool-mib 64 --rt-budget-mib 0 --shadows rt --raster hw`, the three
  flora and micromap tunables), `ENGINE_PIPELINE_CACHE=0`, msvc-release, each under the GPU lock,
  `--startup-trace` with the buffer below. The load runs on the main thread offscreen. A first run
  warmed the OS file cache (669 s); the warm one is the "before".
- **Machine**: i9-10980XE (18 cores, 36 threads), 64 GB, RTX 5090, shared with seven other agents
  building and testing (about half the CPU busy outside the run, 25 GB physical free, at the time of
  the after runs). The before run had the quieter machine; the after runs' stages that did not
  change took 1.3–2.6× as long as in the before run (upload geometry 6.1 → 16.0 s, scene file 38 →
  60 s), so **every after number is an upper bound**, and the time the change took out is larger
  than the difference of the totals.

## The trace could not see the end of the load

`profiling::trace_start`'s default buffer is 32,768 slots; the sampler takes four every 20 ms and a
mesh three. The owner's trace filled at 251 s, 7,003 meshes in, and dropped 173,143 events: every
stage after the meshes, every milestone after `device` (its summary's `scene_loaded`, `gpu_scene`,
`first_frame` are null), and the memory curve's second half — its `peak_working_set_mib` (5.7 GB) is
the peak *of the first 251 s*, not the load's. engine-view now asks for 2^18 slots (about 70 MB,
only under `--startup-trace`), and every run below dropped none.

**Why the meshes ran on one thread.** `JobSystem::schedule(span)` pushes each job onto the caller's
guest deque, then the pool's inbox, and runs a job that fits neither *on the submitter, at once*
(`inline_runs`); it wakes sleeping workers only after the loop. Each queue holds 4,096
(`JobSystemConfig::queue_capacity`). With 16,351 jobs, the first 8,192 queued and the last 8,159
ran inline on the load thread before any worker was woken — one at a time, each a container read
and a generator's inputs (27 ms of mostly waiting), 220–375 s. The workers then took the queued
8,192 in 15 s. The load now gives the pool one runner a thread, each taking the next mesh by an
atomic index; the queues never overflow whatever the count. Every mesh still lands in its own slot,
so the result is the one a single worker gives (`cooked_load_tests.cpp`: 10,000 meshes, zero
inline jobs, the merged clusters hashed equal at one worker and at every one; the old dispatch ran
96 inline at every worker and 1,807 at one). The job system's own behaviour — running an overflow
inline before waking anyone — is reported to its owner rather than changed here: every caller that
schedules more than 8,192 jobs at once has the same cliff (`content_build`'s per-mesh and texture
schedules do).

## Memory

**The working set's peak is the merge** (17.0 GiB at its end, 18.1–18.2 over the run): the 16,351
per-mesh DAGs (about 4.3 GB) and their merged copy (about 5.3 GB) live at once, beside the sources'
records and the scene file's DOM. Releasing the DAGs as soon as the merge has copied them (now
done) takes them out of the instance table's stage, where they used to sit until the load returned,
but not out of the peak: `geometry::merge_cluster_meshes` takes a `span<const ClusterLodMesh>`, so
the copy and the originals overlap inside it. Freeing a mesh's arrays as the merge consumes it would
take ~4 GB off the peak; it is a change to `domain/geometry`'s signature, not this row's.

**What the load hands on stays resident**: 12.9–13.1 GiB of working set at `scene_loaded`, which
the OS trimmed to 6.8 GiB under the after runs' memory pressure without the run slowing — the
merged CPU-side geometry and the sources' records outlive the GPU upload. Whether the session needs
them (collision, picking, the streamed world) is the next question; not answered here.

**The commit (private bytes) climbs 16.5 → 32.3 GiB inside `gpu scene`** with the working set
flat: the driver commits host backing for device allocations. Step by step: `upload geometry`
+7.8 GiB, `upload materials` +3.3 (the textures), `ray tracing` +5.2 (the chain's sets). The
owner's "20 GB" is the report's `host_memory.peak_bytes`, the peak *working set* (20.56 GB, 17.56
at the end of the walk, with the game module's 416 animals).

**VRAM** (the owner's walk: 18,784 MiB used of a 31,617 MiB budget), by category from the engine-only
report, with whether it has a budget:

| category | bytes | budget |
|---|---|---|
| ray tracing chain (per-frame CLAS + BLAS sets) | 5.18 GB peak | `rt_budget_mib` — **0 in the owner's flags, i.e. none** |
| built textures (5,392, with 1,979 normal-variance chains 0.49 GB) | 3.58 GB | none — grows with the world's distinct textures |
| static ray tracing structures (4,057 forms) | 1.04 GB | none |
| deformed-vertex pool | 0.81 GB | `--deform-pool-mib` |
| world tiles' rings | 0.77 GB | by ring count |
| ray tracing cluster cache | 0.57 GB | `renderer.rt.cache_mib` |
| the tail | 2.12 GB budget, 2.3 MB used | device-derived |
| opacity micromaps | ≤ 1 GB | 1 GiB budget (lowered the level cap 6 → 5) |
| geometry (clusters, pages, positions) | the rest (~4 GB) | none |

The textures and the static structures have no budget and grow with the world; the chain has one
and the owner's run turns it off. Not attributed: what the driver keeps beyond VMA's blocks.

## What is not done

- The channels generator's 24–32 s and 11 GB a load (a derived node keyed by its inputs would open
  the network instead of building it; `domain/channels` is W89's tonight).
- `world create`'s 39–42 s (the streamed placements' generators opened over the world).
- The per-texture staging buffer and fence in `gfx::upload_image_2d_levels` (one batched upload
  would take most of what is left of `upload materials`).
- The job system's overflow-runs-inline-before-waking behaviour (`core/jobs`).
- The merge consuming its inputs (the working set's peak).
- The paints decoded as RGBA at the masks' cold build (`read_r`): not on a warm load's path.
