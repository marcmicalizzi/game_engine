# Two tests that failed under load (2026-10-07)

- **Question.** Two GPU tests failed at merge gates — three Windows suites, a Linux container build and a remote build running at once — and passed when run again alone: the rings' culling comparison in `systems/renderer/tests/terrain_motion_tests.cpp` (roadmap F1: 1,419 of 12,799 ids differing between the hardware and the software rasterizer at frame 39 here, 3,338 of 12,797 once on the TITAN Xp) and the live injected session in `apps/engine_view/tests/interactive_tests.cpp` (F2: four markers recorded of five; and once its neighbour, the 420 km frame-record case, three records instead of about 58). "Flaky" is not a cause: each is either a defect that load exposes or a test that assumes something load takes away. Which, and what fixes it?
- **Date:** 2026-10-07. **Machine:** the owner's desktop, i9-10980XE (36 logical CPUs), 64 GB, RTX 5090. **Build:** `msvc-debug` of `main` at `8cb66941` ("before"; the renderer test carrying only the diagnostics below) and this branch ("after"), each copied out of the build tree before the loops so that both could run from one command.
- **Machine state:** loaded on purpose and shared besides. The load was this worktree's `msvc-release` build, cleaned and built again in a loop (about 4.5 minutes a build, every CPU busy), beside other agents' builds and their GPU measurements (one held the machine's GPU lock for a series of frame-budget flights, so some runs below waited minutes for it before they started). Each run's CPU load and free memory at its start are in the logs; under the build they read 85–100%. The C: drive also filled for some minutes, which failed three runs for want of disk and are counted apart.
- **Decision:** no ADR. F1 was an engine defect, fixed in `TerrainMotion::frame` ([renderer](../subsystems/renderer.md#the-dunes-in-time-lapse), "The bound, and a late field"); F2 was engine-view's input injector, fixed in its live loop ([apps](../subsystems/apps.md#--interactive-a-camera-somebody-flies), "Driving a window with nobody at it"), and the 420 km case's assumption of a frame rate was taken out of the test.

## F1: one rig a frame behind

**What the test compares.** `culling_case(true)` builds five rigs one after another — hardware raster with occlusion and cones, without occlusion, without cones, the software rasterizer, the ray path — and drives each through the same 40 frames of a moving terrain with rings at a game week a real second, `TimeLapseConfig::wait` set so that "every rig draws the same sand on the same frame", and compares their captures at frames 9, 24 and 39. A quarter of the ids differing with the depth still agreeing reads like a different frame, not like the tie rule or rounding; so the first step was to record each rig's motion — every level's surface time, pair, blend and padding, and the rings' layout — frame by frame, and compare the rigs before their pictures.

**Reproduced.** The case in a loop of 30 runs, the first ten beside the release build: 4 of those 10 failed, 1 of the 20 that ran after the build had ended (beside another agent's GPU flights). Every failure had the same signature: one rig — the first hardware rig in two runs, the one without cones in one, the ray path's in two — stood at frame 34 at game time 94,956,628.561 s, its inner ring's surface at that ring's b with blend 1, while the other four stood at game time, 94,960,800 s, three of the inner ring's fields further on. Everything before frame 34 was identical in all five. The comparisons the case makes are all against the first rig, so whichever rig fell behind, one of them failed, and the count depends on which. **Both gates' numbers came back to the id** in the before-and-after loop below, each time with the software rasterizer's rig the one a frame behind: 1,419 of 12,799 ids differing from the hardware rig (this machine's gate) in one run, and 3,338 of 12,797 (the TITAN Xp's) in two. The other rigs behind gave 1,412 and 3,333 ids differing under occlusion culling, which the case requires to change none. The gates' failures were therefore this, on both machines, and not the rasterizers disagreeing.

**Why.** A trace of each way the waiting loop in `TerrainMotion::frame` gives up (temporary, not committed), in a second loop of 12 runs under the build, printed one line in every failing run and none in any passing one:

```text
DIAGWAIT frame 35 level 2 gives up (next is neither evaluating nor absent): ahead 1 state0 3 state1 0 recentre 0 frozen 0 busy 0 surface 94956628.561 b 94956628.561 next0 94958567.987
DIAGWAIT frame 36 level 2 gives up (next is neither evaluating nor absent): ahead 1 state0 3 state1 0 recentre 0 frozen 0 busy 0 surface 94958567.987 b 94958567.987 next0 94960507.413
```

6 of the 12 failed, and all 6 printed exactly that (two of them twice, two rigs falling behind in one run). State 3 is `ready`. Offscreen, a frame runs `terrain_surface_frame` and, when a level holds the surface at its b, either asks the worker for that level's next field and waits, or waits for the one it is evaluating — and gave up on anything else. But a pass offers each level one field, and a ring holds two after its b: a ring whose two next fields were both ready took the first, stood on it, and the loop found the second ready — neither missing nor on its way — and gave up, the surface a pair short of game time. Whether a ring had two ready at that frame depends on whether the field worker, which takes a field whenever it is idle at the end of a frame, had got that far ahead of the frames: a matter of how busy the machine is. Under the build some rigs' workers had and some had not.

**What the owner could have seen.** Nothing in a window: a window's frame never runs the waiting loop (its surface follows the clock, which reads every ready field's time). Offscreen — engine-view's `--offscreen`, `--benchmark` and `--capture` runs with `--time-rate` over rings or the world's tiles — a frame could draw the sand up to a pair behind game time, within the per-frame bound and so with no step, and the next frames caught it up; two runs of the same path were therefore not the same pictures on a busy machine, which renderer.md promised they were.

**The fix** (`terrain_time.cpp`): when the level the pass stopped on has its next field ready, the loop goes round again and the next pass takes it. **What holds it:** a case of its own, "terrain rings: an offscreen frame takes every ready field and reaches game time", fills every level's room after b with ready fields by frames of no time (`LevelStats::ready`, new: one for the grid, two for a ring) and then runs a sixtieth of a second at a week a second: every level stands at game time, uncapped, the inner ring having taken four fields. Without the fix it stands on every machine at the inner ring's first field, 2,693 of 10,080 game seconds. And the culling case now checks its premise first — every rig's levels and rings the same, frame by frame — and names the first frame that differs, which is what would have pointed here at once.

## F2: a tick the window never ran, and a frame rate the test assumed

**How the window injects.** `--inject-input` pushes a log's events onto the window's own queue when their tick is the next to run, and a frame then runs every tick that is due by the wall clock, feeding the edge's events at the first of them. A frame slow enough runs many ticks (up to sixty, after which the clock drops the rest), and the events whose ticks fall inside a frame's run are pushed only at the next frame and land late. At the end of the session — the log's own tick count, 480 for the fixture — the last frame's run ends the session, and an event inside it is never pushed at all. The fixture presses its fifth marker at tick 475 and releases it at 477, and its fourth at 450, so a last frame that ran from before tick 450 lost two.

**Not the other suspects.** A press and its release in one tick still count: `InputState` reports the down edge whatever followed it in the tick. The clock dropping wall time past sixty ticks drops time, not events: they are stamped with the tick they will be fed at. And the replay matched the live run bit for bit, because the recording holds what the live run fed — so the loss was at the injection.

**Reproduced.** The two cases in a loop beside the release build, `before` binaries: of 11 runs before the C: drive filled, 3 failed on these assumptions — markers 3 of 5 and 4 of 5 in two of them; and the 420 km case's z moved 0.251, 0.254 and 0.254 m between its first record and its last (it asked for more than 0.3) with 26, 5 and 7 records, where a quiet run draws 51–58. In the last two the window ran the 120 ticks in five and seven frames, the first frame alone sixty ticks. One unloaded run of the live session put its markers at ticks 60, 240, 420, 450 and **476** — the last pressed at 475 and pushed a frame late, as described.

**The two halves.** A game would not lose input this way: somebody at a window has their events polled as they come and fed at the next tick, late by a slow frame and never dropped, and a session they end has no tick count to end at. The losses were the injector's — it assumed frames shorter than the gaps between its events — so **the injector is fixed** (`apps/engine_view/main.cpp`): a frame of an injected run runs no tick past the next event it has not pushed, so every event lands on its own tick at any frame rate and the frames after catch the session up. The live test now also checks each marker's tick against the tick the fixture pressed it at. The 420 km case's assumption was the test's own — that the first frame runs a few ticks — so **the test is fixed**: every record's z is checked against the flight's line at 1 m/s at the record's own simulated time (`pose_time`) to 0.1 mm, and the last record at the session's half second, which holds whatever ticks the frames ran.

## Counts under load, before and after

Each fix's before and after binaries alternated in one command (`compare.ps1`, below), 20 runs each, beside the release-build loop:

| Case | Before: failed / runs | After: failed / runs |
|---|---|---|
| F1, the rings' culling case | 7 / 20 (every one a rig behind at frame 34) | 0 / 20 |
| F2, the live session and the 420 km case | 8 / 20 (three or four markers of five in 6; the 420 km case's z 0.250–0.254 m from 21–29 records in 3; one run both) | 0 / 19 (the loop's time limit came before the twentieth) |

The loop's runs took 26 s to 9 minutes each (some waited for another agent's GPU lock) over 77 minutes, at 80–100% CPU in most of them; the after binaries' runs saw the same load as the before ones they alternated with. The TITAN Xp's `renderer` suite (`tools/remote-build.ps1 -Host titanxp -Preset linux-server -Test -Filter renderer`, GCC 14, this branch with both fixes) passed, unloaded, in 30 minutes; the build compiled every changed file with warnings as errors.

## Reproducing

The scripts are not committed (they are a loop and a load, not a tool); what they do:

- **Load**: `cmake --build --preset msvc-release --target clean`, then `cmake --build --preset msvc-release`, repeated until a time limit, with `TMP` on D:.
- **A loop**: the test executable run `N` times with `-tc=<case>`, one log a run, the CPU load and free memory recorded at each start; `compare.ps1` alternates a before and an after copy of the executables, with `ENGINE_BUNDLE_ROOT` pointing each run at its own copy's `bin/` and the fixture (`tests/support/test_paths.h`), so the same load falls on both.
