| [0024](0024-hardware-rasterization-first.md) | Hardware rasterization for all clusters in Phase 1; software rasterizer experimental (E1 result) | Accepted | (2026-09-24: the sweep its "Revisit when" asks for was rerun on the first GPU without mesh shaders, a TITAN Xp, with the vertex path in the mesh path's place — [E1 on Pascal](../experiments/e1-pascal-rerun.md). The decision stands: the vertex path is the faster rasterizer in 42 of 44 configurations and beats the software rasterizer by 1.9× to 14.5× on E1's heightfield. Two things in the reasoning do not carry over: the software rasterizer is not what a GPU without mesh shaders falls back to — the vertex path is — and "no crossover" is not true there, since 64 FlightHelmets at a fine cut rasterize 30% cheaper in software at 1080p, because the vertex path pays for a cluster's 128-triangle capacity rather than its triangles. The vertex-plus-software split is unmeasured, because `auto` resolves to `vertex` on such a device.) (2026-09-24, later: the vertex path now draws a culled cut's own triangles as one indexed draw where the device has `geometryShader` and `fullDrawIndexUint32`, and on the TITAN Xp that removes the crossover — the helmet grid at LOD 0.25 rasterizes in 0.108 ms against the software rasterizer's 0.136 at 1080p and 0.145 against 0.217 at 1440p — so "no crossover" holds on both GPUs measured and the split has no case left ([After](../experiments/e1-pascal-rerun.md#after-the-vertex-path-draws-the-cuts-own-triangles)). The capacity is 124 triangles, not 128, and what the capacity draw paid for on Pascal was an invocation per triangle corner rather than the lanes past a cluster's count.)
