# ADR-0054: The in-engine tools UI is Dear ImGui, drawn by the renderer's overlay pass

- **Status:** Proposed
- **Date:** 2026-10-10 (narrowed the same day, before acceptance, to the in-engine tools; see "What changed")
- **Status note (2026-10-11): the shell direction is taken, outside this ADR.** A36's spike decided it: the owner judged the web shell's panels clearly better than the ImGui ones, and its capture-based viewport unusable for flying (every frame a render, readback, PNG, fetch and decode). So the authoring shell is the web client **in an OS webview beside the native viewport** — one engine-editor window, the page in Edge WebView2 and the Vulkan viewport in a child window over the page's viewport cell, tiled and never overlapping, both clients of the protocol listener the editor runs in process (roadmap A37; [apps](../subsystems/apps.md#engine-editor-the-engines-window-on-a-document), [06 §6.13](../plan/06-agent-tooling.md#613-human-developer-tooling)). engine-editor's three ImGui panels and its toolbar are retired; this ADR's decision for the in-engine half stands as written — the selection's box, the gizmo and whatever else is drawn in the viewport are ImGui through the overlay pass.

It is a proof-of-concept HUD for a fixture to be played and judged, not the game UI framework: this ADR's own line that a tool's overlay is not a HUD stands, and 04 §4.7 and 10 §10.6 R45 still defer the game UI; when R45 chooses one, the provisional panel is replaced, not grown. ## Context

The editor (06 §6.13) needs two kinds of UI, and they are different things. One lives **inside the engine's window**, over the picture: the viewport's gizmos and overlays, the picking and inspection overlay, a console, profiler and debug panels — developer chrome that reads live engine state every frame. The other is the **authoring editor's shell** — outliner, property panels generated from schemas, the journal, the review queue, asset browsers and graph editors — which is where a person spends the day, and which 06 §6.13 requires never to have a private path into the engine. ADR-0012 adopted Dear ImGui "for tools" without saying how it reaches the screen, what it is not for, or which of the two it meant. Three things constrain the in-engine half:

- **Vulkan is confined** (AGENTS.md, gfx.md "The RHI surface and the backend surface"): only `domain/gfx`, `foundation/window` and an app that presents include the backend set; the renderer records through `gfx::CommandList`. ImGui's own Vulkan backend (`imgui_impl_vulkan`) is a second Vulkan renderer in an app, with its own descriptor pools, pipeline and barriers outside the render graph. Its SDL backend would put SDL outside `foundation/window`.
- **Rendering code lives in `systems/renderer`**, and both hosts get what it does: a pass a UI needs is the renderer's, not the editor's.
- **The game's UI is a different thing again.** 04 §4.7 scopes a UI coordinate model (surface, views, HUD-safe region) and 10 §10.6 defers the game UI framework (R45). A tool's overlay is not a HUD.

**What changed (2026-10-10).** The first draft of this ADR made Dear ImGui the editor's whole UI, and engine-editor's stage 1 built its outliner, property panel and journal that way. The owner looked at it and does not want ImGui as the face of the authoring editor: functional, but not the feel he is after. ImGui stays right for what it is good at — tools inside the engine's window, written in a few lines against live state — and the shell is a separate question. This ADR is still Proposed, so it is narrowed in place rather than superseded.

The alternatives for the in-engine half: ImGui's Vulkan backend in the editor (rejected above); a UI of the engine's own now (that is R45's question, answered for the wrong consumer). For the shell, **Qt** was considered and set aside: utilitarian by construction in Widgets, a style-authoring investment in QML to make it anything else, LGPL or commercial terms, and a second window system and event loop around the viewport. A **web client over the protocol** is the candidate (decision 4).

## Decision

1. **The in-engine tools UI is Dear ImGui** (MIT, so ADR-0014 allows it): the tools that live inside the engine's window — the viewport's gizmos and overlays (engine-editor's translate gizmo and selection box), the picking and inspection overlay, the console, profiler and debug panels, and engine-editor's stage 1 panels for as long as they are the viewport's own stopgap. Fetched by `cmake/EngineImgui.cmake` — the docking branch's release tag, the core only, **none of ImGui's backends** — with its row in `third_party/LICENSES.md`. An immediate-mode UI is the right shape for a tool whose every widget reads live state (the selection, a frame's timings, the document's revision) and whose every edit is a command built at the moment of the gesture; there is no retained widget tree to keep in step. It is also what agents write fluently. It is not the game's UI: R45 stays deferred, 04 §4.7's coordinate model is the game UI's, and when R45 is decided the game UI shares the overlay's place in the frame (decision 3's seam), not ImGui.
2. **It reaches the screen through the renderer's overlay pass**, never through an ImGui backend: `renderer::OverlayPass` (`systems/renderer/overlay.h`) takes 2D triangle lists in the engine's own vocabulary — a vertex is ImGui's `ImDrawVert` byte for byte, a command a scissor, a texture and a run of indices — and records them through `gfx::CommandList` as the frame's last raster pass, onto the colour image the frame was drawn into (the swapchain image, or the renderer's own target offscreen), straight-alpha blended (`gfx::BlendMode::Alpha`, the only blending pipeline). ImGui's textures are overlay textures in the scene's bindless set, made and retired as ImGui asks (`ImGuiBackendFlags_RendererHasTextures`). Nothing below the host includes ImGui. Window events reach ImGui as `window::Event`s, converted in the host.
3. **SDR only, for now.** The overlay blends in the space the output encode wrote, which is what an immediate-mode UI's colours are authored in on an SDR target. On an HDR target (PQ, scRGB) a UI has to be composited at paper white, in the output's primaries, between the curve and the encode — the **seam in `display_output`** that renderer.md ("HDR output") names. That seam is where the game UI and the tools UI will both composite once it is split into a tone pass and an encode pass; it is named here and not built, and a frame asking for an overlay on an HDR target is refused rather than drawn wrongly.
4. **The authoring editor's shell is not decided by this ADR.** Its candidate is a **web client that speaks only the protocol** over the loopback transport (06 §6.2; roadmap A36's spike: a loopback WebSocket on engine-host, `render.load` of a session, a browser shell with outliner, properties and journal). It is the candidate for two reasons: a panel that can only send protocol requests **cannot have a private path into the engine** (06 §6.13's rule becomes a property of the architecture instead of a review item), and **the same HTML runs in a browser, in an OS webview in the editor's own window, or embedded by the engine later**, so choosing it closes none of those doors. The spike informs the decision and a later ADR makes it. Until then engine-editor's outliner, property panel and journal stay as stage 1 built them — read-only, with no text input — and are a stopgap the shell replaces; property editing goes to the shell.
5. **The editor hosts the engine in process and talks to it only through the protocol's own objects** — `protocol::Session` for the document, its checked `apply` with a `Caller` for every edit, its undo, redo and journal — until A2's transport lets it be a client of a separate engine-host. Its viewport is the renderer's, through `doc_scene`. An operation the protocol lacks is added as a method, never as a back door.

## Consequences

- **Easier:** a tool panel is a function of state and a gesture is a command: engine-editor's translate gizmo is a CPU hit test and one `doc.apply` on release through `EditorDocument::apply`, drawn with a few ImGui draw-list calls (stage 2). Any host — engine-view, engine-host for a debug overlay, a game's developer console — composites a UI the same way, because the pass is the renderer's. The shell can be built and restyled without touching the engine, and agents and people reach exactly the same methods.
- **Harder:** the overlay pass has to stay compatible with what ImGui emits (20-byte vertices, 32-bit indices: `ImDrawIdx` is `unsigned int` by compile definition, so a frame's lists concatenate with no rebasing). ImGui's version is a pin, and its 1.92 texture protocol is what `editor_ui.cpp` implements; a bump re-reads it. The editor is two halves until the shell embeds the viewport or the viewport the shell: the engine's window (picture, picking, gizmos) and the shell (everything else), joined by the protocol.
- **Now required:** a pass that composites anything over the picture goes through the overlay or its successor at decision 3's seam, never through a hand-written blend in another pass. `gfx::GraphicsPipelineDesc::blend` exists for it. Direct manipulation in the viewport (gizmos, picking) stays in the engine's window whatever the shell is, and commits through the protocol like any panel.
- **Forbidden:** ImGui's Vulkan, SDL or any other backend in the tree; ImGui types in a public header below `apps/`; an editor feature that reaches past `protocol::Session` into the document or the renderer's privates; growing engine-editor's stopgap panels into the authoring editor (property editing, text input, asset browsers) while decision 4 is open.
- **Lint:** `vulkan-backend-include` allows `apps/engine_editor` beside `apps/engine_view`, because it presents (its swapchain and surface); its viewport and panels include none of the backend.

## Revisit when

- **The shell spike (A36) reports**: whether a web client over the loopback transport carries the authoring editor — then a new ADR decides the shell, engine-editor's three ImGui panels go, and this ADR's decision 4 points at it — or what it lacked.
- R45 chooses a game UI framework: decide whether the in-engine tools move to it or stay on ImGui at the shared seam.
- The `display_output` split is built for HDR: move the overlay to paper white there and lift the SDR-only refusal.
- A2's transport exists: the editor becomes a client of engine-host, and decision 5's in-process shape is retired.
- ImGui's texture or draw-list protocol changes incompatibly at a version the tree wants.
