# ADR-0069: A connection is who its credential says, and a credential is never in a URL

- **Status:** Proposed
- **Date:** 2026-11-18
- **Plan references:** docs/plan/06-agent-tooling.md §6.5; roadmap A4 (on A3)
- **Docs touched:** `docs/subsystems/protocol.md` ([Who a connection is](../subsystems/protocol.md#who-a-connection-is)), `docs/subsystems/apps.md`, `docs/subsystems/engine_shell.md`

## Context

Until now the protocol had no authentication. `engine-host --listen` printed one 128-bit token, and whoever held it was whoever each call's attribution said: the roles file restricted what a *role* may change, but a role was what a call claimed ([protocol](../subsystems/protocol.md#identity-and-what-a-role-restricts)). With several clients on one host (A3) — the owner's shell, an agent's bridge, a command line — that is no longer enough: an agent given the token to edit as `designer` could name `director` in its next call and the host would believe it. The token also travelled in URLs: `?token=` on the WebSocket upgrade, on `GET /capture/<id>`, and in the shell's address the host printed, which is where browser history, proxies and error messages keep things.

Three questions: what is a credential and who issues it; how a connection presents it, browsers included; and what it binds.

## Decision

1. **The operator issues credentials; the host keeps only their digests.** `engine-host --issue-credential <file> --name <n> --actor <a> [--role <r>] [--task <t>]` makes a token of 128 bits from the operating system's secure random source (`platform::secure_random`: `BCryptGenRandom` with the system-preferred generator on Windows, `getrandom(2)` on Linux; never a seeded engine generator), written as 22 characters of unpadded base64url, appends `{name, actor, role, task, token_sha256, issued_unix_ms}` to the credentials file (schema `CredentialsFile`) and prints the token once, then exits. A host started with `--credentials <file>` (engine-host, and engine-editor's in-process listener) accepts those tokens and the one it prints at start. The file holds no secret: it keeps each token's **SHA-256**, a lookup key over a uniformly random 128-bit input. A fast hash is the right kind for that — a slow, salted password hash exists to stretch a guessable human secret, and 2^128 equally likely tokens leave nothing to stretch — and SHA-256 is the strongest member of the kind the tree has: no practical collision or preimage attack is known against it, where SHA-1 has had practical collisions since 2017 and its own header says it decides nothing about trust. No dependency is added: `core/hash/sha256.h` is the one the document's content-addressed blobs brought (roadmap D13, ADR-0067); `domain/tissue` still keeps a copy of its own, which can now forward to it. A presented token's digest is compared with every entry's in constant time, so how long a refusal takes says neither how much of a guess was right nor which entry matched. An agent never issues one: issuing is a flag of the host's command line, not a protocol method, for the same reason view policies are the operator's (ADR-0033).

2. **A connection authenticates once, at the upgrade, before any method runs.** A program sends the token in the `X-Engine-Token` header. A browser cannot set a header on a WebSocket, so the host's printed `shell` address carries a **one-time ticket** instead of the token: the first `GET /?ticket=` spends it, sets an `HttpOnly; SameSite=Strict` cookie holding a fresh per-page secret and redirects to `/` with the rest of the query and no ticket in it, and the page's upgrade and its `<img>` captures carry the cookie without the page ever seeing it. A ticket is the same 128 random bits as a token, good for one spend within ten minutes of its making (`Listener::k_ticket_lifetime_ms`), checked only on a request whose `Host` names the listener's own loopback address, and worth nothing after its redirect: one that was spent, expired or never issued is refused (403). A second tab opened from the same printed address, in a browser that already holds the cookie, is sent on without a new one; a reload of the page is a GET of `/?session=...`, which needs nothing, and its socket carries the cookie, which lives for the browser session and the host's life (no `Max-Age`; the host forgets every cookie when it exits). `?token=` is no longer read anywhere. A connection that presents nothing the host knows is closed with 1008 and a reason before its first message is read, so no method — not even a read — runs for it.

3. **A credential binds the connection's identity.** A connection that presented a credential is its actor, role and task: blank attribution fields are filled from it, and a call or a `client.hello` that names another actor or role is refused with 1008 (`data.reason` "identity") by the dispatcher, before the handler. The host's own printed token (and the shell's cookie made from it) is the operator: it is not bound, keeps A3's `client.hello`, and its calls may name any role the roles file has, as on stdin.

3a. **A role a host cannot enforce is never a label; fail closed** (added before this ADR was accepted, after a security review of this work, 2026-11-18, found that a credential's role held only on a host that had loaded a roles file, and that a credential with no role ran in the host's own). A credential's role binds on every host that accepts the credential, whether or not that host loaded a roles file, and a credential gets nothing it did not name:
   - A bound connection runs in its credential's role **as the host's roles file defines it, and in nothing else**: never the host's own `--role` or `--task`, never the file's `default_role`, never "unrestricted" (`policy.h`, `bound_role`). The dispatcher gates it whether or not a file is loaded (`bound_allows_method`), and `resolve_caller` hands every handler that role, so the session's layer, tile and type checks hold too.
   - A credential that **names no role**, and one whose role the host **cannot enforce** (no roles file loaded, or a role the file does not have), runs in a role that names no method, layer or type: its reads pass, as every read does (plan 06 §6.5), and every write is refused with 1008, `data.reason` "no role" or "unenforced role", the sentence saying which and what to ask the operator for. `client.list` shows the role the credential names, which is now what the host enforces or an empty one that writes nothing.
   - The operator learns at start: `engine-host --listen --credentials` says on stderr how many of the file's credentials may only read there, and `--issue-credential` without `--role` says the credential it printed will only read.
   - Refusing to start was the other choice (a credential naming a role with no roles file, as that review proposed). It was not taken because a read-only credential is a real thing to want (a watcher, a QA agent that reports), and because the rule "a role binds wherever the credential is accepted" then needs no exception for the editor, which loads no roles file.

   **What it costs.** `engine-editor` loads no roles file (its own edits are the editor's, as director, and its page is the operator), so **every credential presented to an engine-editor may read and not write**: an agent given one watches the owner's document, captures, lists and reads the journal, and an agent that writes beside the owner attaches to `engine-host --listen --roles <file> --credentials <file>` on the same document, or is given the operator's token deliberately. The editor says so on stderr when it loads a credentials file. A credential issued with no role, which until now ran in whatever the host was started as — on a director's host, as director — now only reads: the operator issues it again with `--role`.

4. **An agent is never handed the operator's token by the documented attach**. The announcement a host prints first, `{listen, token, session, shell}`, holds the operator's token; `engine-mcp --connect-from` reads that shape, and it remains the operator's own way to attach a bridge as themselves. An agent is issued a credential instead, and the bridge reads it from a file: `--token-file <file>` takes the one line `--issue-credential` printed, saved, and `--connect-from` takes `{"listen": ..., "token": <the credential's token>}` written by the operator. `--token <t>` is gone: a process's command line is readable by every process of its user (adversary 3), a file can be the operator's alone. Nothing is kept for compatibility.

5. **A write is attributed to the caller it was made for**. A protocol method that writes through an app's own document object resolves its caller from the connection (`resolve_caller`), so `editor.import_mesh` from a client is journaled as that client (its credential, or its `client.hello`), with its connection number in the events, and the editor's own identity is the page's, not every client's.

6. **The shell's cookie is named for the listener's port**, `engine_session_<port>`: a browser keeps one cookie per name, host and path and none per port (RFC 6265 §8.5), so two hosts' shells in one browser no longer overwrite each other's cookie and break the first one's captures and reconnects.

7. **A socket that has proved nothing holds no place a client needs** (the bound predates the credentials). `foundation/net`'s server bounds accepted WebSocket connections (32, a 33rd closed with 1013) apart from connections that have not been accepted yet (16, sending their head or a plain GET): a new connection past the second bound shuts the oldest unaccepted one down. Before, one cap of 32 counted every socket, so any local process holding silent sockets kept every client out with a 503 for the 10 s head timeout, renewable forever; now it can only delay a client by an eviction.

8. **Never logged, never in a URL.** No log line names a token, a ticket's secret or a cookie's value; a refusal says which kind of credential was missing or wrong, never what was sent. The announcement on stdout, the operator's own channel, prints the token; it is not a log.

## Consequences

- An agent's bridge given a credential cannot act outside its role, by naming another or by attaching to a host that cannot enforce it; the roles file becomes a boundary for that connection rather than a guardrail, and a host with no roles file gives a credential reads only (decision 3a).
- A credential's write on engine-editor is refused; see decision 3a for what an agent that writes does instead.
- Every client changes how it presents the token: engine-mcp `--connect` already sent the header; the shell reads nothing from its address and relies on the cookie; tests and tools that put `?token=` in a URL send the header.
- The ticket makes the printed shell address single-use and short-lived: a browser that has not spent it within ten minutes, or a second browser, needs a new address, and a running engine-host has no way yet to print one (a row). engine-editor makes one for each page it loads.
- stdio is unchanged: a process that can write to the host's stdin started it, and is its operator.
- What this is not: TLS, a listener another machine can reach, revocation while a host runs (a credential removed from the file takes effect at the next start), or per-user accounts. Nor isolation of the shell's cookie from other servers on this machine: a browser sends a host's cookie to **every** port of 127.0.0.1 (RFC 6265 §8.5: cookies do not provide isolation by port), so a local process that listens on another port and gets the owner to open a page there receives the operator's cookie and can connect as the operator from a program that sends no Origin. The port in the cookie's name stops two hosts' shells colliding, not that leak; over plain http on loopback there is nothing a browser offers that a non-browser cannot replay, so the defence is that a process of the same user can already read the printed token from the host's stdout. A page on another port cannot use the cookie itself: the Origin check, port included, refuses its socket.
- The connection bounds are on threads and places, not on work: a client that has authenticated can still hold the dispatch lock with a long read-only method (`render.benchmark`), and a role does not stop that (reads are never restricted). Not traced; a roadmap entry if it bites.

## When to revisit

When a listener is reachable from another machine (TLS, and a credential with an expiry), or when credentials need revoking without a restart. If SHA-256 is ever weakened for this use, the digest field is replaced the way any field is (a new name, a version) by SHA-3 or BLAKE3, whichever the tree carries by then; the token's length is set by `make_token` alone.
