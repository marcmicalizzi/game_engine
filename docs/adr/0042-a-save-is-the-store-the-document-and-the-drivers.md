## Context

Phase 3's exit asks for a tile-streamed world with deterministic replay and save and load. By 2026-09-25 the world streamed (the tile ring, E35), a `WorldStore` over SQLite held each tile's projections and snapshot, the document materialized per tile and the world wrote back through `@writeback` rows with events in `world.db`. Nothing saved a running world, nothing loaded one to continue it, and nothing asserted a replay. The plan says what a save is in one line — "latest snapshot + events since; load = apply snapshot, replay tail" — written before any of these pieces existed, and it leaves open:

1. **What is in a save.** The plan's line assumes projections are a fold of the event log and snapshots bound the replay. Today they are not: a tile's projections are written directly by the world when the tile goes, and nothing folds the log into them. The document holds everything the world writes back. The tile ring's active set is a function of the observers' *history* (hysteresis, the budget), not of where they are. A player's input is recorded as an `input::InputLog`, not as events.
2. **How a save's bytes are made.** A copy of a SQLite file with a live WAL beside it is not a backup; `VACUUM INTO` and the backup API both are, and neither gives the same bytes for the same content twice.
3. **What "the same state" means.** 05 §5.10 asks for identical persistent-state hashes and nothing defines the hash.
4. **What a load must rebuild exactly.** The runtime world is meant to be "a materialization of (document + persistent state) … for a set of loaded tiles" (03 §3.4), and a load materializes exactly that. The first replay test found the running world was not: the materialization driver filed a record under the tile it was in when it was materialized, and a record a system moved stayed filed there, so which entities existed depended on when each was last materialized.

## Decision

1. **A save is a directory: the document's files, a backup of the whole store, the player's input log so far, and a manifest (`save.json`) naming every file with its size and hash, written last.** The whole store rather than a snapshot and a tail: the projections cannot be rebuilt from the log yet, and the log's history is read by `session.events`. "Latest snapshot + events since" stays the store's own business inside the file.
2. **State and derived are split by one question: can a load rebuild it from the rest?** State: the document (layers and journal), the store's three tables, the clock (tick and game time), the world seed, the tile ring's parameters, observers and active tiles with their rings, and the input log up to the save's tick. Derived: the runtime world's entities and components, tile seeds, reconciliation's work, the input state (a fold of the log), the document's composed index. Random streams a system advances by drawing would be state; none exists (every stream is a hash of seed, tile, id and tick), and the manifest has the list for the first.
3. **A store backup is `VACUUM INTO`, then the copy's schema cookie set to 1** through a connection of its own on a file nothing else has open, so a backup's bytes are a function of the store's content and a save loaded and saved again is the same files byte for byte.
4. **The persistent-state hash is `world::state_hash`**: the clock, the document's live records composed across its layers in id order (id, type, parent, properties as canonical JSON), and every row of the store's three tables in key order, each as little-endian length-prefixed bytes through `core/hash`. It leaves out the journal (wall-clock attribution times), the layer and file layout, the runtime world, and the drivers. One definition serves the protocol (`session.state_hash`), the manifest, the replay test and CI, and the replay test pins its value for every compiler.
5. **Records follow their tile.** The driver reports a held record a write-back put in another tile (`Materializer::take_moved`) and decides nothing; the world files it under the new tile when that tile is live in the consumer's rings and lets it go when it is not, between ticks and inside a deactivation after its flush. What is materialized is then a function of the document and the live tiles.
6. **A load makes the world at the save's clock** (`SimSchedulerConfig::start_tick` and `epoch`), restores the ring's tiles at their rings as activations (the consumers materialize and reconcile them; nothing is written), puts the observers where they were, folds the player's log up to the tick, and must reproduce the saved hash when nothing migrated. A call that declares no observers continues; the player's log is handed over again on the next call.
7. **Versions are checked and migrated on read.** The manifest lists every format its pieces are in — its own types, the store's payload types, `store.tables`, `engine.input.log`, the document's file and record types — with the version written. A newer version, or a format the build lacks, is refused naming it; a file that does not match the manifest is refused naming it; an older one migrates: the manifest by the schema language's `@since` rule, the store's tables by a `user_version` step each, records by their types' defaults. A migration corpus under `content/migration-corpus/saves/` holds one save per version that has existed and a test loads every one.
8. **The player of a headless world is an observer an input log steers** (`world::InputObserver`), between ticks where the ring runs. It is the least a player is and still changes the persistent state, which is what 05 §5.10's "input log + event log ⇒ replay" needs a consumer for.

## Consequences

- Phase 3's "save and load" and "deterministic replay" have a test CI runs on three compilers: run, save at K and continue; load at K in a fresh host and continue; replay from 0 — one hash, pinned.
- A save is as large as the store; there is no incremental save and no trimming of the log. When the log is folded into projections, decision 1 can shrink a save to snapshots and a tail without changing what a load produces.
- A record that walks out of the simulated rings stops there, and resumes when its tile is simulated again; before, it stayed live until the tile it had left went.
- A run split over calls equals the unsplit run only when it splits on the write-back cadence, because every call ends with a flush.
- An agent's edit between calls to a record in a live tile still reaches the world only when the tile next comes in, so a save taken with such an edit pending loads with it applied: recorded as not yet done in world.md.
- Every change to what the world computes moves the replay test's pinned hash, and a change that moves it on one compiler only is a determinism bug, not an expectation to update.
- A migration may not be deleted while a corpus save needs it.

## Revisit when

- The event log is folded into projections (decision 1: a save becomes snapshots and a tail).
- A system keeps a random stream it advances statefully (decision 2: the manifest's `rng` list gets its first entry and a registration point).
- A second consumer of player input exists beside the headless observer — a game's own input systems — at which point input moves into the tick's `Input` phase and the log into the store as `Player`-origin events (03 §3.10).
- Saves grow past what a copy per save can afford, or a game wants autosaves every few minutes.
