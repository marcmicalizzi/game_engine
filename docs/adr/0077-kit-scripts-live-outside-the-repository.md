# ADR-0077: A procedural kit's scripts live outside the repository, and the repository takes what they made with its provenance

- **Status:** Proposed
- **Date:** 2026-11-19
- **Plan references:** docs/plan/10-roadmap-risks.md §10.5 (E33); docs/plan/07-content-pipeline.md §7.5, §7.6, §7.7; ADR-0014; ADR-0047; roadmap G41 (on G40)
- **Docs touched:** `docs/content-generation.md` ("Blender: `tools/blender-run.ps1`"), `docs/plan/10-roadmap-risks.md` §10.5 (the E33 row)

## Context

E33 ([the write-up](../experiments/e33-hard-surface-kits.md)) settled that hard-surface architecture — ruined walls, buildings — is authored as procedural kits in Blender, driven headlessly, rather than generated by image-to-3D. It left one question to an ADR: whether the kits' bpy scripts become a pipeline dependency, "kept, versioned, run by the content build", and so where they live. This records what the tree already does, so the question has an answer a reader can check code against.

What the tree does today:

- **The repository takes no Python.** `tools/` is PowerShell 7 and small C++ ([AGENTS.md](../../AGENTS.md), "Where things are"). A bpy script is Python by necessity: Blender's API has no other language.
- **The scripts live under the local root**, `<local root>\blender-kits\<kit>\scripts\` (`$env:ENGINE_LOCAL_ROOT`, else `game_engine_local` beside the primary checkout), with what they made under `blender-kits\<kit>\out\` ([content generation](../content-generation.md#blender-toolsblender-runps1)). The ruined-wall kit is seven bpy scripts and two PowerShell ones there.
- **The one piece in the repository is the wrapper**, `tools/blender-run.ps1`, which refuses a script or an output inside the repository (exit 2) as `tools/generate.ps1` refuses an output directory there, runs Blender with an empty profile of its own and never the owner's session, and writes a provenance sidecar beside every primary output: the script's SHA-256 with its arguments, seed and parameters, the inputs' hashes and licences, the Blender version.
- **The engine reads what a kit made, never the kit.** The ruin assembler reads a kit's `engine.ruin-kit.v1` description and its members' GLBs ([ruins](../subsystems/ruins.md)); the content build imports a GLB as it imports any other. No build step starts Blender.

The alternatives on the table: commit the scripts (breaks the no-Python rule, and makes Blender a build dependency of every checkout and every CI runner, none of which has it); a repository of their own pinned by hash (the right shape if a build ever has to regenerate a kit, and work nobody needs yet); or keep them where they are and say so.

## Decision

1. **A procedural kit's scripts live outside the repository**, under the local root's `blender-kits\<kit>\scripts\`, for every DCC-tool kit whose scripts are in a language the repository does not take. The repository holds the wrapper that runs them (`tools/blender-run.ps1`), the formats the engine reads from their output (`engine.ruin-kit.v1`, the provenance sidecar's schema), and the pages that say how a kit is run.
2. **A kit is not a pipeline dependency.** The content build and every engine binary read a kit's outputs — meshes, a kit description, textures — with their sidecars; nothing in the repository starts Blender to make an asset, and no CI leg needs Blender.
3. **A kit's output is reproducible from its sidecar, not from the repository**: the script's hash, its arguments, seed and parameters, its inputs' hashes and the Blender version are what name a run, and `tools/generate.ps1 verify` checks those sidecars like any other generated asset's.

Code complies when no committed file is a bpy script, no build or test target runs Blender, and every asset a kit made that the engine reads carries a sidecar written by the wrapper.

## Consequences

- Easier: the repository stays Python-free and Blender-free; a checkout, a CI runner and the GPU server build and test everything without a DCC tool; the owner's Blender session is never touched by a build.
- Harder: a kit cannot be rebuilt from a clone. A second machine, or the local root lost, has the outputs and their sidecars (which say exactly what made them) but not the scripts that made them; keeping those is the local root's backup, not the repository's history.
- The sidecar is the only record tying a committed scene or kit description to the script that made its meshes, so the wrapper's sidecar is load-bearing: a kit run outside the wrapper makes an asset with no claim to its provenance, and the shipping check, once it exists (roadmap G34), refuses an asset whose sidecar lacks its grant.
- Forbidden: a bpy script in the repository, and a content-build step that calls Blender.

## Revisit when

- A build has to regenerate a kit's output — a seed or a parameter chosen by the engine at build time, or CI checking a kit's output against its script. Then the scripts move to a repository of their own, pinned by hash from this one, and the build gets a Blender stage behind a switch that is off where Blender is absent.
- The repository's no-Python rule changes.
- A kit's work moves into the engine's own C++ generators (as the ruin assembler took over laying a building from the wall script's footprints), leaving no script to house.
