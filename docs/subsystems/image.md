# image (foundation)

**Purpose.** Images in and out of the engine on the CPU. Encoding is dependency-free, for captures, test fixtures, and the screenshots agents look at: `encode_png` writes a PNG whose image data is a zlib stream produced by the module's own deflate (RFC 1951, `deflate.h`), so every decoder reads it and nothing has to be linked. The `Compression` level chooses the trade, from a memcpy that grows the data by 1/64 to a dynamic-Huffman encoder that turns a 4K frame into a megabyte at 300 MB/s. `write_png` does the same to a file through `io::write_file`. Decoding goes the other way through stb_image: `decode_image` turns PNG, JPEG, TGA, or BMP bytes into 8-bit-per-channel pixels in an engine `Vector`, `probe_image` reads only the header, and `read_image` reads a file through `io::read_file` and decodes it. `crc32` and `adler32` are exposed for tests and other containers.

**Compression levels.** One LZ77 matcher (32 KiB window, three-byte hash, 32768-entry hash table with chains) behind three levels, measured in `msvc-release` on the dev box (Ryzen-class desktop) over a procedurally generated 3840×2160 RGBA frame — sky gradient, flat ground, solid panels with hard edges, a radial highlight, a band of noise — and over 1 MiB of bytes that cannot be compressed at all:

| Level | 4K RGBA frame (33.2 MB in) | 1 MiB of random bytes |
|---|---|---|
| `Stored` | 1.15 GB/s, 100.01% | 1.19 GB/s, 100.01% |
| `Fast` | 1.04 GB/s, 4.80% (20.9×) | 52.9 MB/s, 100.01% |
| `Default` | 405 MB/s, 3.09% (32.3×) | 48.2 MB/s, 100.01% |

Through the whole encoder, `encode_png` on the same frame runs at 546 MB/s of input at `Fast` (1.60 MB of PNG) and 303 MB/s at `Default` (1.03 MB of PNG); the gap to raw deflate is the scanline buffer, the CRC, and the adler32. `Fast` walks four hash-chain probes, takes matches greedily, and emits fixed Huffman codes; `Default` walks up to 32, holds each match for one position to see whether the next one starts a longer one, and builds a literal/length and distance code from each block's own frequencies. Blocks are at most 256 KiB of input or 65535 symbols, and each one is emitted as whichever of stored, fixed, and dynamic is smallest — which is why a block of noise costs five bytes of framing instead of growing, and why every level stays inside 101% of its input in the worst case. `Stored` is what the encoder produced before there was a compressor, byte for byte, and is still the level to reach for when a capture is written and read once in the same second.

Scanlines carry filter type 0 (None), so what deflate sees is the pixels themselves. The Sub filter would pay for itself on synthetic gradients and not on the flat areas and hard edges that dominate a render, and choosing per row costs a pass over the image; measuring that properly is a job for the capture pipeline rather than a guess here.

**Public API.**

- `foundation/image/deflate.h`: `enum class Compression : u8 {Stored, Fast, Default}`, `deflate(input, level, out)` for a raw RFC 1951 stream ending in a BFINAL block, and `zlib_compress(input, level, out)` for the same stream inside an RFC 1950 container (two-byte header, stream, big-endian adler32). Both replace `out`. `input` must be smaller than 4 GiB, which the `Vector` holding the result requires anyway.
- `foundation/image/png.h`: `encode_png(width, height, channels, pixels, out, level = Compression::Default)` for 1 to 4 channels at 8 bits, `write_png(path, ..., level = Compression::Default)`, `crc32`, `adler32`. `io::Status::InvalidArgument` is returned when the dimensions and byte count disagree.
- `foundation/image/decode.h`: `ImageInfo{width, height, channels}` and `Image{width, height, channels, Vector<u8> pixels}`; `probe_image(bytes, out, error)`, `decode_image(bytes, out, desired_channels = 4, error)`, `read_image(native_path, out, desired_channels = 4, error)`. `desired_channels` of 0 keeps the file's channel count and 1 to 4 converts (gray replicates into RGB, a missing alpha becomes 255). Pixels are always 8 bits per channel, rows top first, tightly packed: a 16-bit PNG is reduced by keeping the high byte, so a sample of 0xABCD decodes to 0xAB. Failures leave `out` empty and fill the error string; `read_image` returns the read's own `io::Status`, `IoError` for bytes that are not a supported image, and `InvalidArgument` for a `desired_channels` above 4 (the file is not touched). stb's buffer is copied into the `Vector` and freed inside the call; nothing of stb's leaks into the API or the include path of other modules.

**Depends on.** `base`, `containers`, `io`; stb_image (pinned by commit in `cmake/EngineImage.cmake`, licensed in `third_party/LICENSES.md`), compiled into `src/decode.cpp` only. The compressor has no third-party code at all.

**Testing.** `tools/dev.ps1 test -Filter image`: reference checksum values, a small RGBA image walked chunk by chunk with every CRC verified and the `Stored` stream inflated by hand, a 300×300 gray image spanning several stored blocks, RGB, argument rejection, and a file round trip. Then the compressor, against a reference inflater written in `tests/deflate_tests.cpp` (RFC 1951, stored, fixed, and dynamic blocks, about 150 lines, and documentation of the format as much as a test): every level round-trips random bytes, zeros, a repeated pattern, and text; empty input and inputs shorter than one match; a megabyte of random bytes staying inside 101% at every level; two megabytes of a short pattern crossing many block boundaries; and the zlib container's header, checksum, and byte-for-byte `Stored` layout. Then PNGs through stb_image at all three levels for RGBA, RGB, and gray at 1×1, 13×7 (a width that is not a multiple of four), 300×300, and 512×512 (whose scanlines outrun a single deflate block), compared byte for byte; and a flat 1024×1024 RGBA image, which comes to 6588 bytes at `Default` (0.16%) and 46420 at `Fast` (1.1%). Then the decoder: images encoded and decoded back byte for byte at `desired_channels` 0 and expanded correctly at 4, luminance reduction to one channel, `probe_image` against an encoded PNG, a baseline JPEG written to memory with stb_image_write (a test-only dependency) and decoded back within tolerance, a hand-built 16-bit PNG reduced to its high bytes, `read_image` over a file from `write_png`, and the failures: an empty span, junk bytes, a truncated PNG, an impossible bit depth, a missing file, and an impossible `desired_channels`, each with a non-empty message and an empty `out`. `domain/gfx`'s capture test encodes a GPU capture and `engine-view --capture` writes real frames.

**Benchmarks.** `tools/dev.ps1 bench -Preset msvc-release -Filter image` runs `bench/image_bench.cpp`: `deflate` at every level over the 4K render-like frame and over a megabyte of random bytes, `encode_png` end to end at `Fast` and `Default`, and `image.flip.render_4k`, one LDR-FLIP over a 3840×2160 pair. The rate column is input bytes per second; the ratio is printed on its own line per benchmark, because a harness result carries rates and not ratios, and the FLIP benchmark prints its own mean and p95 the same way.

The FLIP row exists because this module's whole cost model splits in two and only one half was measured. Deflate is an integer matcher; FLIP is a dozen separable f32 filters over a dozen f32 planes, which is the only float-heavy kernel here and therefore the only one where a wider instruction-set baseline could show up at all. It did: [ADR-0031](../adr/0031-minimum-cpu-x86-64-v3.md) measured **one 4K FLIP at 2.71 s on the old SSE4.2 flags and 2.45 s at x86-64-v3, −9.5%**, reproduced in three sessions, while `deflate` over the same frame moved by −0.6% — this module's two halves answering the instruction set exactly as differently as their shapes predict. Its pair is the same frame twice with the differences a cheaper renderer actually makes — a 3% exposure shift, a hard edge moved one pixel, and ±1 dither noise — so that nothing can later be "optimized" by short-circuiting on an identical pair. The CTest smoke run drops to a sixth of the width and height (`bench::smoke_mode()`), because one 4K FLIP is about two seconds and a 640×360 pair still walks every filter.

**Not yet.** An inflater of our own (decoding goes through stb_image; the reference decoder in the tests is deliberately the slow, readable kind). Per-row filter selection, and with it the Paeth and Up filters, which is where the next large ratio win is for photographic and gradient-heavy captures. A preset above `Default` (optimal parsing, several hash tables, a larger window) — a capture is written once and read once, so the last few percent is not worth the milliseconds. The block-compressed formats the GPU samples, their mip chains and the offline compressor that fills them are **`domain/texture`** now ([texture](texture.md)): it decodes through this module and nothing of it lives here, because a texture pipeline belongs in the content build and not in a decode-on-load path (its container is the engine's own `.tex` rather than KTX2, [ADR-0036](../adr/0036-built-textures-in-the-engines-own-container.md)). EXR and the HDR/float formats for HDR captures. Resizing (the mip filter is `texture::build_mip_chain`'s; stb_image_resize2 is in the same checkout if a general resizer is ever wanted). Animated formats and 16-bit output are out of scope: callers that need more than 8 bits per channel want the texture pipeline, not this module.

**Performance notes.** The matcher is the whole cost. Its hash table is 32768 `u32` heads plus a 32768-entry chain array, 256 KiB that stays in L2, and every candidate is rejected with three byte comparisons before a match is measured eight bytes at a time. `Fast` does not index the interior of a match longer than four bytes, which is what buys it a gigabyte per second on a frame that is mostly flat; `Default` indexes every position, which is what buys it a third off the output. Level parameters are template parameters, not fields, so no knob is read inside the matcher (plan 11 §11.4). Incompressible input is the worst case at about 50 MB/s: every position hashes, inserts, and probes a chain that will not pay, and then the block is stored anyway — `Stored` is the level for data already known to be noise. The bit writer accumulates into a 64-bit word and pushes whole bytes; bulk writes go through one `memcpy` rather than `Vector::append`'s element-by-element copy, which took the stored path from 1.35 ns to 0.88 ns per byte.

## Perceptual and signal metrics

**What they are for.** [04 §4.8](../plan/04-renderer.md#48-reference-renderer-and-objective-optimization) makes a picture comparison the gate of the optimization loop: a change is accepted when it is faster and the picture did not get worse. "Worse" needs a number, and the plan names three — FLIP as the primary one, PSNR and SSIM beside it — with per-region weighting so that a regression in the periphery weighs less than one in the middle of the frame. `foundation/image/metrics.h` is those numbers on the CPU, over the 8-bit RGB(A) `Image` the decoder already produces. `engine-image compare` ([apps](apps.md)) is the command-line face of it. Since 2026-09-18 it has the pictures §4.8 meant it to measure: `render.evaluate` calls `compare_images` on a real-time frame against a converged reference path trace of the same frame, and `tools/ci/reference-compare.ps1` runs the corpus through it against per-scene FLIP thresholds ([renderer](renderer.md#reference-renderer)). Nothing in this module changed for that — the metrics were built ahead of their consumer and fit it unaltered — and the one thing the comparison did need is documented next door rather than here: **the last quantization of a picture has to happen once, in the place with precision to spare**, because a flat one-byte difference across a frame's background moved FLIP by more than every rendering difference in the corpus put together.

**FLIP** is the LDR evaluator of Andersson, Nilsson, Akenine-Möller, Oskarsson, Åström, and Fairchild, *FLIP: A Difference Evaluator for Alternating Images*, HPG 2020, implemented from the paper: sRGB to linear, linear to YCxCz, the spatial contrast-sensitivity filter of the three opponent channels, the Hunt-adjusted HyAB color difference with the paper's exponent (0.7) and its redistribution (0.4 of the gamut's largest difference maps to 0.95 of the range), and a feature difference from first- and second-derivative Gaussians at 0.082 degrees that raises the score where an edge or a point moved. The result is one number per pixel in [0, 1]; about 0.1 is where a person starts to notice. The constants were checked against NVIDIA's reference implementation, which `../../third_party/LICENSES.md` records; no code came from it.

**Why 67 pixels per degree.** The contrast-sensitivity filter is defined in degrees of visual angle, so it has to know how dense the display is. The default, `k_default_pixels_per_degree` = 67.02, is the paper's reference condition — 3840 pixels across a screen 0.7 m wide seen from 0.7 m, which is 3840·π/180 — and it is the default here so that a FLIP number printed by this engine compares with a FLIP number printed by anyone else. When the display is actually known, `pixels_per_degree(width, height, diagonal_inches, distance_m)` computes it: a 4K 27-inch monitor at 0.7 m comes to 78.5, not 67, because 27 inches of 16:9 is 0.598 m wide rather than 0.7 m. Denser means less of the difference is filtered away, so a higher number scores a given difference higher.

**Two departures from the reference implementation**, both deliberate. Each Gaussian of the sensitivity filter gets its own three-sigma support instead of sharing the widest one's: the achromatic and red-green channels are σ ≈ 1.03 and 1.10 pixels at 67 ppd and need a radius of 4, while the blue-yellow channel's two terms need 10 and 8. That is the same filter to within a thousandth — three sigma of a Gaussian leaves 0.3% of the mass outside, and the kernel is renormalized over its own window either way — and about a third less work. And the two-Gaussian channel is evaluated as two separable convolutions blended by the mass each one carries inside its own window, which is algebraically the normalized two-dimensional filter and costs four one-dimensional passes rather than a 21×21 gather.

**PSNR** is over the R, G, and B channels of the stored values with a maximum of 255, alpha ignored; identical images give an infinity, which `engine-image --json` prints as `null` rather than as a large number that would read like "nearly identical". **SSIM** is Wang, Bovik, Sheikh, and Simoncelli (2004) on Rec.601 luma with the paper's 11×11 Gaussian window (σ 1.5) and constants (K1 0.01, K2 0.03), averaged over the windows that fit entirely inside the image, so the border — where a window would have to invent data — is not measured; an image smaller than the window is measured as one window over all of it rather than refused. Both are symmetric, and SSIM of an image against itself is exactly 1, not 1 ± ε, because the covariance and the two variances are then the same computation on the same bytes.

**Pooling, and why there are three of them.** `pool_mean` is the number FLIP is usually quoted as and the one to compare between runs. `pool_percentile` (p95 by default) is the tail: a mean over two million pixels hides a corner of the frame that fell apart, and the p95 does not. `pool_weighted_mean` under a per-pixel weight map is the per-region rule of §4.8, and `center_weight_map` builds the map that rule usually wants — a Gaussian falloff from the middle of the frame in *normalized* coordinates, so the weighting is an ellipse in pixels and a 48:9 surround frame weighs its side monitors down the way [§4.6](../plan/04-renderer.md#46-extreme-displays) says peripheral vision should be treated. The floor (0.05 by default) keeps a catastrophe at the edge of the frame from being weighted to nothing. Measured on a 128×128 checker with the same 24×24 block flattened once in the middle and once in a corner: 0.0186 either way unweighted, 0.0717 against 0.0051 once the attention region is applied.

**Public API.** `foundation/image/metrics.h`: `FloatImage` (one f32 per pixel — an error map, an SSIM map, or a weight map), `k_default_pixels_per_degree`, `pixels_per_degree`, `psnr_rgb`, `ssim_luma`, `FlipOptions` and `flip`, `pool_mean`, `pool_weighted_mean`, `pool_percentile`, `pool_max`, `CenterWeightOptions` and `center_weight_map`, `flip_heat_map` (an error map through a perceptually uniform black-purple-red-yellow ramp, as RGB8 for `write_png`), and `MetricsOptions`/`ImageMetrics`/`compare_images` for all of it in one call.

**Speed and footprint.** Everything is f32, separable, and single-threaded, with the convolutions on raw pointers and nothing allocated inside a loop. A 3840×2160 pair — two real `engine-view` captures of the heightfield at LOD thresholds 1 and 12, so 794 visible clusters against 105 — takes **3.04 to 3.19 s over three runs** in `msvc-release` on the dev box (Ryzen-class desktop), and reports PSNR 23.19 dB, SSIM 0.967, FLIP mean 0.077, p95 0.638, max 0.888. `engine-image compare --json` reports the time as `ms` so the optimization loop can budget for it. The one thing that had to be got right for that number is the direction of the convolution loops: a kernel summed tap by tap at one pixel is a float reduction the compiler may not reorder, so it stays scalar; accumulating one tap at a time across the row is a vector of independent lanes, and writing it that way took the same comparison from 3.9 s to 3.1 s with bit-identical results. The working set is about a dozen float planes — the two images in YCxCz, the feature difference, two convolution accumulators, and the error map — which is roughly 40 bytes a pixel, or 330 MB for a 4K pair. That is the obvious thing to fix first if it ever matters: the filters are separable and the images are read in rows, so a tiled pass over horizontal bands would bound the memory at a few megabytes, and the job system would divide the wall time by the number of performance cores. Neither is worth doing before something needs it.

**Testing the metrics.** `tools/dev.ps1 test -Filter image` runs `tests/metrics_tests.cpp`: identical images give an infinite PSNR, an SSIM of exactly 1, and a FLIP map of zeros whose size matches the inputs; a pair whose every channel differs by exactly four gives the analytic PSNR 10·log₁₀(255²/16); mismatched sizes give a NaN from PSNR and SSIM and a refusal with a message from FLIP; SSIM is symmetric, bounded, falls when structure is destroyed, and its map's mean is the pooled value; a one-pixel shift of a sharp edge pools to 0.096 with a worst pixel of 0.74 while a one-level change of a flat mid-gray field pools to 0.0299 everywhere — which is the number the definitions give by hand for two grays 0.394 of L\* apart, so the color pipeline, the Hunt adjustment, and the redistribution are pinned by it; FLIP is symmetric in its two arguments and blind to a change both images make; the center weighting separates the same damage in the middle from the same damage in a corner by fourteen times while leaving the unweighted means within 0.3% of each other; and the pooling, the viewing-density helper, and the heat map are checked against hand values.

**Not yet, for the metrics.** HDR-FLIP, which needs the exposure sweep and a float image type this module does not have. The temporal-stability metric of §4.8, which is a metric over a sequence rather than over a pair. Tiling and threading, as above. A GPU implementation: the whole thing is a chain of separable filters and a per-pixel combine, so it belongs on the GPU eventually, but a comparison happens once per corpus run and not once per frame.
