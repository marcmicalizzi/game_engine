# gpu_lock (foundation)

**Purpose.** The machine-wide GPU lock in C++: the protocol's file — read, taken, refreshed, broken and released by the rules `D:\workspace\GPU-LOCK.md` writes down for every tool on the machine — the benchmark harness's lease on it (`--gpu-lock`, [bench](bench.md#measuring-on-a-shared-machine)), and the **hold a process keeps while it has a GPU device open**, which `gfx::Device` takes when the test environment asks for it ([ADR-0050](../adr/0050-tests-take-the-gpu-lock-per-device.md)). It is the C++ half of the protocol; `tools/lib/MachineLock.psm1` is the PowerShell half, and there are those two and no more.

**Why a module of its own.** The protocol's C++ implementation was `foundation/bench/gpu_lock.h` until 2026-09-30, because the benchmark harness was its only user. Device creation became the second, and `gfx` (domain) could have linked the benchmark harness — the layering allows a domain module to depend on a foundation one — but a renderer that links a micro-benchmark runner to open a device is a dependency nobody reading `modules.json` would guess the reason for. So the protocol moved here, `bench` depends on it, `gfx` depends on it, and nothing else changed about the harness.

## The problem it solves: the lock is held while a GPU is in use, and no longer

Until this module held the lock per device, whoever ran the tests took the lock around the whole command, `tools/gpu-lock.ps1 run -Exec "tools/dev.ps1 test ..."`, because nothing finer existed. A merge gate ran three suites under one hold — about 63 minutes (1,776, 602 and 1,383 s in the gate of 2026-09-29) — of which perhaps six to ten touched a GPU, and on the evening of 2026-09-29 three holders queued behind each other for most of it. Now:

- a test that never opens a GPU device never touches the lock;
- a suite's holds are many short ones, one per device lifetime, and other holders get the card between them — in practice between two test executables, since a GPU test executable opens its devices back to back ([the measurement](../experiments/gpu-lock-per-device-2026-09-30.md));
- nobody wraps `tools/dev.ps1 test` in the lock, and nobody can forget to, because the test executables take it themselves;
- the owner's own `engine-view` and `engine-host` sessions never take it and never wait for it.

## How a hold works

**Where it is taken: `gfx::Device::create`, just before `vkCreateDevice`, and released by `Device::destroy` as soon as `vkDestroyDevice` returns.** The instance is torn down after the release because its teardown touches no GPU, and because it is where a crash was found: on 2026-09-30 engine-host crashed there on every exit after `gpu.adapters` had run beside a device (fixed; [gfx](gfx.md), "One live device per process"), and until the release moved it left the lock behind for a lease each time, which the next test's engine-host sat out. A test's GPU use comes through several doors — `gfx_test::open_device` (`domain/gfx/tests/raster_path.h`), the renderer's test rigs, and the end-to-end tests, which start `engine-view`, `engine-host`, `engine-cli` (which starts `engine-host`) and `engine-mcp` (which does too) as child processes that open their devices themselves. A lock only the test helper knew about would miss the renderer's rigs and every child. All of them open their device in `Device::create`, so that is the one place, and a process that never gets that far — adapter enumeration (`gpu.adapters`) creates an instance and no device; a test that skips because the device's requirements fail refuses before `vkCreateDevice` — never touches the lock.

**Only when the switch is on: `ENGINE_GPU_LOCK_ON_DEVICE=1`.** The shared test main (`tests/support/test_main.cpp`) sets it for every test executable unless it is already set, and every process a test starts inherits it. Nothing else sets it: the owner's interactive `engine-view` and an agent's `engine-mcp` session open their devices without the lock, as before. `0` in the environment turns it off for a run (the test main does not overwrite a value that is there). The switch is exactly `1`; anything else is off.

**One hold per process, counted by device** (`DeviceHold`). The first device takes the lock — waiting for it if somebody else has it — later devices of the same process join the hold, and the last one out releases it. A GPU test executable opens and closes a device per test case, so its holds are back to back, milliseconds apart; that is also why interleaving happens between executables rather than between cases (a waiter looks every 15 s), which is where the suite's CPU-only tests give it room.

**A short lease, kept alive by a thread that lives exactly as long as the hold.** The file's `expires` is two minutes ahead (`k_device_lease_s`) and a keeper thread refreshes it every 30 s (`k_device_refresh_s`) by writing beside the file and renaming over it, as the protocol requires; three refreshes can be missed before the lease runs out. The keeper starts when the first device takes the lock and is joined inside the release, before `Device::destroy` returns, so no thread outlives the device it holds the lock for. What a crash leaves behind is therefore at most two minutes of a lock nobody refreshes, which any waiter then breaks as expired. Ctrl+C (SIGINT, SIGTERM) deletes the file before the process dies, as the harness's lease always did, and a process that exits normally with a device still open (a leaked one, a static one) lets the lock go from an `atexit` handler.

**Who holds it for whom.** A lock is a process's own when its `pid` is that process, or the process named by `ENGINE_GPU_LOCK_HOLDER`, under the same owner label on the same host ([bench](bench.md#measuring-on-a-shared-machine), "Whose lock is mine"). While a process holds the lock for its devices it sets `ENGINE_GPU_LOCK_HOLDER` to its own pid, and puts the old value back when the hold ends. So:

- **A child finds its parent's hold and neither waits nor releases.** Its mode is `Parents`; its parent, which wrote the file, is the one that deletes it. A child that waited on its parent would deadlock with it, and this is what keeps it from waiting.
- **The parent dies first, or lets go first.** A child in `Parents` mode keeps a keeper too, which watches the lock at the same 30 s. If its parent's hold goes away while the child still has a device — the parent died and its lease ran out, or it released its own last device first — the child takes the lock in its own name if it is free or expired (breaking it by the protocol's verified break), says so on stderr, and from then on refreshes and releases it as its own. If somebody else got there first, it says so once and carries on: its device is open either way, and the lock is not something it can take back.
- **The old way keeps working.** `tools/gpu-lock.ps1 run -Exec "<command>"` sets `ENGINE_GPU_LOCK_HOLDER` to its own pid for the command, as it always has, so a suite somebody still wraps finds the lock its own in every process: nothing waits on itself, nothing takes a second lock, nothing is printed, and the wrapper releases it as before. (It also holds the GPU for the whole run again, which is what this module exists to stop.)
- **The benchmark harness.** `--gpu-lock` takes the lock itself, under its own pid, for the whole measured run ([bench](bench.md#measuring-on-a-shared-machine)); a device the benchmark opens finds that lock in-process (`InProcess`) and leaves it alone. A smoke run under CTest takes no lock, and no bench opens a device today.

**Waiting is not failing.** A process that has to wait prints who holds the lock once per holder, looks again every 15 s (`k_device_poll_s`, the low end of GPU-LOCK.md's 15–30), and waits until an **absolute deadline** that the whole test shares: the test main sets `ENGINE_GPU_LOCK_WAIT_UNTIL` to its start plus **1,800 s** (`ENGINE_TEST_GPU_LOCK_WAIT_S`, GPU-LOCK.md rule 9's half hour for a short job), and every process the test starts inherits it, so fifty engine-host children of one end-to-end test cannot each wait half an hour. A wait that reaches the deadline prints who held the lock and **exits the process with 75** (`k_exit_gave_up`, which is `platform::k_exit_gpu_lock_gave_up`, sysexits' EX_TEMPFAIL) before anything reached the GPU. Exiting rather than returning a failed `Device::create` is deliberate: a failed create reads as "no GPU here", which every test turns into a silent skip that counts as a pass, and `engine-view` into its "unavailable" exit.

**The code reaches the test at the root of the tree.** `platform::Process::wait()` ends a parent that sees a child exit 75 with the same code, when the parent takes part in the lock (the switch is on), so an `engine-host` that gave up under `engine-cli` under `engine_engine_cli_tests` ends all three with 75. CTest reports a test that exits 75 as **skipped, not failed** (`SKIP_RETURN_CODE 75`), and `tools/dev.ps1 test` then exits 75 itself and names the tests that did not run — neither a failure nor, which would be worse, a pass. Only tests that can wait carry that property, with `TIMEOUT` = 600 s of work + 1,800 s of queue = **2,400 s**, and the label `gpu` (`engine_test_waits_for_gpu`, `cmake/EngineModule.cmake`): a module's tests when the module or a test dependency reaches `gfx`, an end-to-end test when its app does, and engine_cli and mcp_bridge because the engine-host they start opens a device. In `msvc-debug` that is `gfx`, `protocol`, `audio`, `renderer`, `audio_system`, `scene_collision`, `world`, `engine_view`, `engine_content`, `engine_cli` and `mcp_bridge` (`ctest -L gpu`). It is a superset on purpose — `protocol` links `gfx` for `gpu.adapters` and `audio` and `engine_content` reach it through that, and none of the three opens a device — because the two ways of being wrong cost different things: a test marked that never waits only reports a hang later, and a test that waits unmarked is killed by CTest's timeout mid-wait, which reads exactly like the hang it is not. Every other test keeps CTest's default of 1,500 s, or 600 s for an end-to-end one, and cannot wait.

**Linux, the hosted runners, and machines that do not take part.** Nothing waits and nothing fails. A machine without a usable Vulkan device never reaches `vkCreateDevice` — the hosted runners, the Linux container — and so never touches a lock. Off Windows the default lock is `/tmp/gpu.lock`, which has no other holder on the GPU server or in the container (whose `/tmp` is its own, not this desktop's), so a hold is taken and released at once. A machine where the lock's directory does not exist — a self-hosted runner, a machine a test bundle was sent to — does not use the protocol (`NoDirectory`) and runs as if the switch were off; create `D:\workspace` (or point `ENGINE_GPU_LOCK` somewhere) on a machine that should take part.

**What it does not do.** Two processes of one test that need a GPU device *at the same time* and share no ancestor that holds the lock — an end-to-end test that started two engine-hosts side by side and rendered in both — would have the second wait for the first until the deadline, and then skip. No test does that today (the full suite shows no skip). A child that took the lock over from its parent does not re-advertise `ENGINE_GPU_LOCK_HOLDER` to children it starts after that, because setting the environment from the keeper thread is not safe while the main thread reads it. And the lock serialises *holders*; it does not order waiters: GPU-LOCK.md has no queue, so a waiter gets the card at its first look after a release.

**The hold log.** `ENGINE_GPU_LOCK_LOG=<file>` appends one JSON line per hold when it ends — `event: "hold"`, the lock's path (`lock`), `pid`, `exe`, `purpose`, `started`, `held_ms`, `waited_ms` and `end_unix_ms` — and one `event: "gave_up"` line per give-up with the holder it gave up on (`holder_owner`, `holder_purpose`). Only holds this process wrote are logged; a child's `Parents` hold is its parent's line. It is how a suite's holds are counted and timed ([the measurement](../experiments/gpu-lock-per-device-2026-09-30.md)); a log that cannot be written never stops a device.

**Owned data.** This process's hold: the device count, its mode, the keeper thread, and the lock file the hold wrote while it lasts. Nothing else on disk.

**Invariants (tested).**
- The file format and the rules are GPU-LOCK.md's: created with create-new, refreshed by rename, an unreadable file is being written until it is a minute old, an expired lock is broken only by the verified move-compare-delete, a person's (`marc`) never, and a release deletes only the file this process wrote (owner, pid and start time).
- With the switch off, a device takes nothing and writes nothing.
- The first device takes the lock, later devices of the same process share it, and the last one releases it; while it is held, `ENGINE_GPU_LOCK_HOLDER` names this process, and afterwards it is what it was.
- The keeper keeps a short lease alive past its first expiry while the hold lasts, and stops before the release returns.
- A lock held for this process by an ancestor (`ENGINE_GPU_LOCK_HOLDER`) or by another path in this process (the harness's lease) is used as it is and never released by the device hold; the same ancestor's lock, expired, is broken and taken.
- A parent's hold that goes away while a child still has a device is taken over by the child; a parent that dies first leaves the lock to its child within one lease.
- A crash leaves the lock for one lease and no longer.
- A wait that runs out exits with 75 and says who held the lock; a parent that takes part in the lock and sees a child do that exits with 75 too; a person's lock is waited on and never broken.
- A command wrapped in `tools/gpu-lock.ps1 run` finds the lock its own in every process it starts.
- A `Lease` (the harness's) that finds a wrapper's lock alive uses it as it is, and breaks it once it has expired.

**Public API.**
- `foundation/gpu_lock/gpu_lock.h`: `State`, `Identity`, `default_path`, `current_identity`, `read`, `k_unreadable_stale_s`, `parse_iso8601_utc`, `format_iso8601_utc`, `Lease` (the harness's hold: `acquire`, `refresh_if_due`, `release`, `Lease::Outcome`), `to_string`.
- `foundation/gpu_lock/device_hold.h`: the environment's names (`k_env_on_device`, `k_env_wait_until`, `k_env_holder`, `k_env_log`), the numbers (`k_device_lease_s`, `k_device_refresh_s`, `k_device_poll_s`, `k_default_wait_s`, `k_exit_gave_up`), `HoldConfig`, `hold_config_from_environment`, `HoldMode`, `DeviceHold` (`acquire`, `release`), `HoldStatus`, `hold_status`.
- `core/platform/process.h`: `k_exit_gpu_lock_gave_up`, and `Process::wait()`'s rule for a child that exits with it ([platform](platform.md)).

**Depends on.** `base`, `containers`, `json`, `platform`, `time`.

**Testing.** `tools/dev.ps1 test -Filter gpu_lock` runs `gpu_lock_tests.cpp` (the file, the reading and the harness's lease, every lock in the case's own `TempDir`) and `device_hold_tests.cpp`: in this process, the switch, the counting, the keeper, a lock held for the process, a parent's hold taken over, waiting, breaking, a person's lock and the log; and through `engine_gpu_lock_probe` — a process that holds the lock as a process with a device does and opens none — a child under its parent, a give-up's 75 and its parent's, a crash (the probe killed with `TerminateProcess`/`SIGKILL`), a parent that dies first, and a command wrapped in `tools/gpu-lock.ps1 run` (skipped where there is no `pwsh`). Each case clears the variables a run around it may have set, so the suite passes wrapped, unwrapped and while being measured. `gfx`'s `device_tests.cpp` checks the one place it is wired in: a device holds a scratch lock while it lives when the switch is on, shares that hold with another holder in the process, and takes nothing when it is off. The PowerShell half is `tools.machine_lock`. The two-process integration in a full suite is measured, not unit-tested: [the measurement](../experiments/gpu-lock-per-device-2026-09-30.md).

**Performance notes.** A hold costs a file create, a thread start, and on release a join and a delete — about a millisecond, next to the tens to hundreds of milliseconds `vkCreateDevice` takes — and nothing at all with the switch off. The keeper wakes every 30 s. Nothing here is on a frame path.
