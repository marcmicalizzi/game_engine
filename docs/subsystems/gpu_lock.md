# gpu_lock (foundation)

**Purpose.** The machine-wide GPU lock in C++: the protocol's file — read, taken, refreshed, broken and released by the rules `D:\workspace\GPU-LOCK.md` writes down for every tool on the machine — the benchmark harness's lease on it (`--gpu-lock`, [bench](bench.md#measuring-on-a-shared-machine)), and the **hold a process keeps while it has a GPU device open**, which `gfx::Device` takes when the test environment asks for it ([ADR-0049](../adr/0049-tests-take-the-gpu-lock-per-device.md)). It is the C++ half of the protocol; `tools/lib/MachineLock.psm1` is the PowerShell half, and there are those two and no more.

**Why a module of its own.** The protocol's C++ implementation was `foundation/bench/gpu_lock.h` until 2026-09-30, because the benchmark harness was its only user. Device creation became the second, and `gfx` (domain) could have linked the benchmark harness — the layering allows a domain module to depend on a foundation one — but a renderer that links a micro-benchmark runner to open a device is a dependency nobody reading `modules.json` would guess the reason for. So the protocol moved here, `bench` depends on it, `gfx` depends on it, and nothing else changed about the harness.

## The problem it solves: the lock is held while a GPU is in use, and no longer

Until this module held the lock per device, whoever ran the tests took the lock around the whole command, `tools/gpu-lock.ps1 run -Exec "tools/dev.ps1 test ..."`, because nothing finer existed. A merge gate ran three suites under one hold — about 63 minutes (1,776, 602 and 1,383 s in the gate of 2026-09-29) — of which perhaps six to ten touched a GPU, and on the evening of 2026-09-29 three holders queued behind each other for most of it. Now:

- a test that never opens a GPU device never touches the lock;
- a suite's holds are many short ones, one per device lifetime, and other holders get the card between them — between test executables, and between the test cases of one executable too ([the measurement](../experiments/gpu-lock-per-device-2026-09-30.md));
- nobody wraps `tools/dev.ps1 test` in the lock, and nobody can forget to, because the test executables take it themselves;
- the owner's own `engine-view` and `engine-host` sessions never take it and never wait for it.

## How a hold works

**Where it is taken: `gfx::Device::create`, just before `vkCreateDevice`, and released by `Device::destroy` as soon as `vkDestroyDevice` returns.** The instance is torn down after the release because its teardown touches no GPU, and because it is where a crash was found: on 2026-09-30 engine-host crashed there on every exit after `gpu.adapters` had run beside a device (fixed; [gfx](gfx.md), "One live device per process"), and until the release moved it left the lock behind for a lease each time, which the next test's engine-host sat out. A test's GPU use comes through several doors — `gfx_test::open_device` (`domain/gfx/tests/raster_path.h`), the renderer's test rigs, and the end-to-end tests, which start `engine-view`, `engine-host`, `engine-cli` (which starts `engine-host`) and `engine-mcp` (which does too) as child processes that open their devices themselves. A lock only the test helper knew about would miss the renderer's rigs and every child. All of them open their device in `Device::create`, so that is the one place for a device — a window for one takes the same hold before it appears ([Windows](#windows)) — and a process that never gets that far — adapter enumeration (`gpu.adapters`) creates an instance and no device; a test that skips because the device's requirements fail refuses before `vkCreateDevice` — never touches the lock.

**Only when the switch is on: `ENGINE_GPU_LOCK_ON_DEVICE=1`.** The shared test main (`tests/support/test_main.cpp`) sets it for every test executable unless it is already set, and every process a test starts inherits it. Nothing else sets it: the owner's interactive `engine-view` and an agent's `engine-mcp` session open their devices without the lock, as before. `0` in the environment turns it off for a run (the test main does not overwrite a value that is there). The switch is exactly `1`; anything else is off.

**One hold per process, counted by device** (`DeviceHold`). The first device takes the lock — waiting for it if somebody else has it — later devices of the same process join the hold, and the last one out releases it. A GPU test executable opens and closes a device per test case, so its holds come close together, with the case's own CPU work between them, and each is an ask of its own: beside other waiters, holders take turns inside an executable as well as between executables, in the order of [the line](#the-line) (before 2026-11-11 nothing ordered the turns, and whoever looked first in a gap had the card). So a test executable can be interrupted mid-run by a long holder and wait for it, inside its deadline.

**A short lease, kept alive by a thread that lives exactly as long as the hold.** The file's `expires` is two minutes ahead (`k_device_lease_s`) and a keeper thread refreshes it every 30 s (`k_device_refresh_s`) by writing beside the file and renaming over it, as the protocol requires; three refreshes can be missed before the lease runs out. The keeper starts when the first device takes the lock and is joined inside the release, before `Device::destroy` returns, so no thread outlives the device it holds the lock for. What a crash leaves behind is therefore at most two minutes of a lock nobody refreshes, which any waiter then breaks as expired. Ctrl+C (SIGINT, SIGTERM) deletes the file before the process dies, as the harness's lease always did, and a process that exits normally with a device still open (a leaked one, a static one) lets the lock go from an `atexit` handler.

**Who holds it for whom.** A lock is a process's own when its `pid` is that process, or the process named by `ENGINE_GPU_LOCK_HOLDER`, under the same owner label on the same host ([bench](bench.md#measuring-on-a-shared-machine), "Whose lock is mine"). While a process holds the lock for its devices it sets `ENGINE_GPU_LOCK_HOLDER` to its own pid, and puts the old value back when the hold ends. So:

- **A child finds its parent's hold and neither waits nor releases.** Its mode is `Parents`; its parent, which wrote the file, is the one that deletes it. A child that waited on its parent would deadlock with it, and this is what keeps it from waiting.
- **The parent dies first, or lets go first.** A child in `Parents` mode keeps a keeper too, which watches the lock at the same 30 s. If its parent's hold goes away while the child still has a device — the parent died and its lease ran out, or it released its own last device first — the child takes the lock in its own name if it is free or expired (breaking it by the protocol's verified break), says so on stderr, and from then on refreshes and releases it as its own. If somebody else got there first, it says so once and carries on: its device is open either way, and the lock is not something it can take back.
- **The old way keeps working.** `tools/gpu-lock.ps1 run -Exec "<command>"` sets `ENGINE_GPU_LOCK_HOLDER` to its own pid for the command, as it always has, so a suite somebody still wraps finds the lock its own in every process: nothing waits on itself, nothing takes a second lock, nothing is printed, and the wrapper releases it as before. (It also holds the GPU for the whole run again, which is what this module exists to stop.) Two things make that hold for the ways gates wrap today. **The owner goes down with the pid**: "held for me" is owner and pid together, so a wrapper started with `-Owner fable-merge-...` also sets `ENGINE_GPU_LOCK_OWNER` for the command — without that, a child whose environment names the default owner took its own parent's lock for a stranger's and waited on it until its deadline (a gate that sets `ENGINE_GPU_LOCK_OWNER` in its environment was never affected). And **a lock session inside a wrapped run holds nothing and waits for nothing** (`Open-MachineLockSession`, so `tools/ci/gpu-smoke.ps1` and `reference-compare.ps1` inside `gpu-lock.ps1 run`): it finds the lock held on its behalf, as the C++ side does, instead of waiting for its own parent. `device_hold_tests.cpp` runs a probe under `gpu-lock.ps1 run` all three ways — the default owner, an owner in the environment, an owner given with `-Owner` — and `tools.machine_lock` checks the owner handed down and the nested session.
- **The benchmark harness.** `--gpu-lock` takes the lock itself, under its own pid, for the whole measured run ([bench](bench.md#measuring-on-a-shared-machine)); a device the benchmark opens finds that lock in-process (`InProcess`) and leaves it alone. A smoke run under CTest takes no lock, and no bench opens a device today.

**Waiting is not failing.** A process that has to wait takes a place in [the line](#the-line), prints who holds the lock and where it stands once per holder and place, looks again every 250 ms (`k_line_look_ms`; it was every 15 s, `k_device_poll_s`, when a waiter had no place and any look could win) — so a holder that died is broken within a look of its lease running out — and waits until an **absolute deadline** that the whole test shares: the test main sets `ENGINE_GPU_LOCK_WAIT_UNTIL` to its start plus **1,800 s** (`ENGINE_TEST_GPU_LOCK_WAIT_S`, GPU-LOCK.md rule 9's half hour for a short job), and every process the test starts inherits it, so fifty engine-host children of one end-to-end test cannot each wait half an hour. A wait that reaches the deadline prints who held the lock and **exits the process with 75** (`k_exit_gave_up`, which is `platform::k_exit_gpu_lock_gave_up`, sysexits' EX_TEMPFAIL) before anything reached the GPU. Exiting rather than returning a failed `Device::create` is deliberate: a failed create reads as "no GPU here", which every test turns into a silent skip that counts as a pass, and `engine-view` into its "unavailable" exit.

**The code reaches the test at the root of the tree.** `platform::Process::wait()` ends a parent that sees a child exit 75 with the same code, when the parent takes part in the lock (the switch is on), so an `engine-host` that gave up under `engine-cli` under `engine_engine_cli_tests` ends all three with 75. CTest reports a test that exits 75 as **skipped, not failed** (`SKIP_RETURN_CODE 75`), and `tools/dev.ps1 test` then exits 75 itself and names the tests that did not run — neither a failure nor, which would be worse, a pass. Only tests that can wait carry that property, with `TIMEOUT` = 600 s of work + 1,800 s of queue = **2,400 s**, and the label `gpu` (`engine_test_waits_for_gpu`, `cmake/EngineModule.cmake`): a module's tests when the module or a test dependency reaches `gfx`, an end-to-end test when its app does, and engine_cli and mcp_bridge because the engine-host they start opens a device. In `msvc-debug` that is `gfx`, `protocol`, `audio`, `renderer`, `audio_system`, `scene_collision`, `world`, `engine_view`, `engine_content`, `engine_cli` and `mcp_bridge` (`ctest -L gpu`). It is a superset on purpose — `protocol` links `gfx` for `gpu.adapters` and `audio` and `engine_content` reach it through that, and none of the three opens a device — because the two ways of being wrong cost different things: a test marked that never waits only reports a hang later, and a test that waits unmarked is killed by CTest's timeout mid-wait, which reads exactly like the hang it is not. Every other test keeps CTest's default of 1,500 s, or 600 s for an end-to-end one, and cannot wait. Since T77 the label also carries `RESOURCE_LOCK gpu_device` (`cmake/EngineTesting.cmake`), so a run with jobs (`tools/dev.ps1 test -Jobs`, the Linux test presets) never starts two of them at once and the second waits in CTest rather than in this lock's budget; `tools.game_sdk`, which starts `engine-view`, has the label too. Two `ctest` invocations at once still meet here, as before ([what to run](../ci/what-to-run.md#jobs)).

## The line

**The lock file says who has the GPU; the line says who is next** (T96, [ADR-0062](../adr/0062-the-machine-locks-have-a-line.md)). Until 2026-11-11 nothing did: a waiter had the lock if its look happened to be the first after a release, and a holder that released and asked again in the same breath always looked first. On the night of 2026-11-10, with twelve agents and a merge gate on the machine, one picture run waited from 22:39 to 01:36 while later arrivals took the lock again and again, one holder re-took it straight after each lease for hours, gate tests sat out their half hour and exited 75, and three rows ended the night without an engine picture. The Linux build lock is the same protocol at another path and had the same night ([local Linux builds](../ci/local-linux.md#one-container-build-at-a-time-whoever-started-it)); the line is one mechanism for both, in this module and in `tools/lib/MachineLock.psm1`.

**A ticket is a file.** An ask that finds somebody waiting, or that could not take the lock at its first try, writes one into the directory `<lock path>.line` (`D:\workspace\gpu.lock.line\`), from then on tries the lock file only while no live ticket stands before its own, and deletes its ticket when it has the lock, gives up or is told the lock is not its to take. (With nobody in the line the first try needs no ticket — there is nobody to pass — so a suite that has the GPU to itself writes no file but the lock's own.) The name is the place, so the line is a sorted directory listing:

```
t-<key ms, 16 digits>-<arrived ms, 16 digits>-<pid, 10 digits>-<counter, 4 digits>.json
```

`arrived` is the wall clock in Unix milliseconds when the process began to ask; `key` is `arrived` plus the lease it asked for, in milliseconds (below). Earliest key first; equal keys by arrival, then by pid, then by the process's own counter. **Two waiters that start in the same millisecond are ordered by what their tickets say — the lower pid first, and one process's two asks by its counter — never by which of them the scheduler ran first**: every process that lists the directory sorts the same names to the same order. The body is a lock's own shape, so the tools that read a lock read a ticket — `owner`, `purpose`, `pid`, `started` (the arrival), `expires`, `host`, and `declared_s` — written beside the file and renamed over it, like a lock's refresh.

**The lock file and its rules are untouched, which is the whole of the compatibility story.** Exclusion is still the create-new of the lock file, an expired lock is still broken by the verified move, a release still deletes only its own file. The line is advice among the processes that take part in it: it decides which of *them* tries the create-new, and nothing else. So:

- **A holder built before the line** (another worktree's older test executable, the Blender agent's Python) is waited for exactly as before; the line cannot tell and does not need to.
- **A waiter built before the line** takes no ticket and tries the lock file at its own interval, 15 to 20 s. It is not in the line, so it is served when its look lands while the file is absent — out of turn if a line is waiting, never if the head of the line (which looks every 250 ms) gets there first, which is most of the time. That is what it did before, when every waiter raced: it can win early, it can wait its half hour and exit 75, and it can neither deadlock nor corrupt anything, because it and the line meet only in a create-new that one of them wins. Against a line that never empties it is at a disadvantage it did not have against other 15-second pollers; the remedy is a rebuild, and until every worktree has one, an old binary's wait is the lottery it always was. `device_hold_tests.cpp` plants exactly that: a second ticketless holder that takes the lock in the instant the first lets go, with two new waiters in the line — they wait for it, keep their order, and lose no file.
- **A new process on a machine where the line's directory cannot be made** asks without a ticket: the protocol as it was.

**A dead waiter never blocks the line.** A ticket carries its own short lease, `expires` 30 s ahead (`k_ticket_lease_s`), refreshed every 10 s by the waiter — from the same loop that tries the lock, so a ticket cannot be alive while its owner has stopped trying. A waiter that is killed stops refreshing; whoever looks next after its `expires` has passed skips the ticket and deletes it. **Worst case: 30 s of lease, counted in whole seconds, and one look of 250 ms — the line moves under 32 s after a waiter dies**, and usually 20 to 30 s after, since the last refresh was up to 10 s before the death. A waiter that gives up, is refused (`-NoWait`) or is interrupted from PowerShell removes its ticket at once. A waiter that only *stalled* past its ticket's lease (a suspended process, a machine out of memory, which was 2026-11-10 too) finds its ticket removed and writes it again under the same name: it stops blocking the line while it is gone and has its place back when it returns. **A dead holder is detected as it always was**: its lock expires one lease after its last refresh (120 s for a device hold, ten minutes for `gpu-lock.ps1 run` unless it says otherwise) and the head of the line breaks it at its next look — within 250 ms of the expiry, where a waiter used to notice up to a poll later. Only the head breaks, because the lock it frees is the head's to take.

**Every waiter looks every 250 ms** (`k_line_look_ms`), not every 15 s. With a line, the head is the only one that takes a released lock, so the head's look is how long the GPU stands idle between two holders; and a waiter learns it has *become* the head only by looking, so the ones behind look as often. A look is a directory listing and a few small reads. `k_device_poll_s`, `Lease::Config::poll_s` and `-PollSeconds` remain as upper bounds a caller may set and no longer set the pace. This is what GPU-LOCK.md's rule 2 ("do not poll hard: every 15–30 s") gives up for the tools that take a ticket; a tool without one keeps its 15–30 s.

### Fairness between kinds of work: arrival plus what you asked for

**A ticket's key is its arrival plus the lease it asked for: the moment it would be done if it were served at once and held for what it declared.** The lease is what every ask already states — a device hold's 120 s, `tools/gpu-lock.ps1 run -Minutes` (ten by default), `acquire` and the bench harness's half hour, a container build's ten minutes — so no caller says anything new. It is capped at half an hour (`k_declared_cap_s`, GPU-LOCK.md's default lease), so a four-hour lease is not four hours at the back. What follows from that one sum:

- **Equal asks are first come, first served.** Every test's device hold asks for 120 s and every container build for ten minutes, so tests among tests, and builds among builds, are a plain queue, and **a holder that releases and asks again takes a new ticket at the back**: the three waiting when it let go are served before its next hold.
- **A short ask passes a long one only while the long one has waited less than the difference between them.** A gate's test (120 s) or a two-minute picture run (`-Minutes 2`) arriving a second after a ten-minute hand lease goes first; arriving eight minutes after it, it does not. So a short job does not sit behind every long lease that happened to be a second earlier.
- **Nobody is passed for longer than the lease it asked for, so nobody starves.** A ticket is passed only by asks whose arrival is before its own key; from the moment the clock reaches its key, everything that arrives stands behind it. A ten-minute ask is first among everything that arrives after its tenth minute in the line, however many short jobs keep coming; with the cap, the longest anyone is passed is half an hour.
- **The order is static.** A key is fixed when the ticket is written, so every process sorts the same line and a place never depends on when it is computed — which a rule on a ratio of wait to length ([highest response ratio next](#published-practice-and-how-far-each-was-read)) would not give a line that each waiter evaluates for itself, at its own moment, with no arbiter.

**Why nothing more.** Strict first come, first served alone would have ended 2026-11-10's three-hour wait, because what starved that run was re-asking, and a re-asker now goes to the back. It would not have kept a gate's test from sitting its half hour out behind three ten-minute hand leases that were merely earlier, which is the other thing that night did; the sum does, with no class of work, no priority and no number chosen by eye — the one constant is the rate, a second of waiting for a second of declared length, which is the only rate with no unit to tune. What was left out, and why: **priorities** (a gate's test is a test; a priority is a thing every agent's brief would claim); **pre-emption** (a GPU job cannot be interrupted, so a hold in progress is always waited out, and the worst wait for the head of the line is still one hold); **enforcing the declaration** (`-Minutes` is the lease a crash leaves behind, and `run` refreshes it for as long as its command runs; a holder that outstays what it asked for has jumped the line by the difference, `status` shows since when and until when, and teeth for it would be a new rule for every tool on the machine, the Blender agent's included — a row if it is abused). What the line does not change: a wait is still the sum of the holds before you, so a holder that keeps the GPU an hour costs everyone behind it an hour.

**What taking turns costs.** A test executable opens and closes a device per test case, and each of those holds is now an ask of its own. Alone, it re-takes the lock at once (its ticket is the only one). Beside N other waiters it is served once per round, so its GPU cases run at about 1/(N+1) of their pace and its queue budget — 1,800 s from the test's start, shared by all its holds — is spent a turn at a time; before the line the incumbent usually kept the lock across its own gaps and everyone else waited whole executables. The total is the same work plus up to 250 ms of idle GPU per hand-off; who finishes first is different, and a long GPU test beside many others can now reach its deadline in slices rather than in one wait (it exits 75 and is skipped, as before). This is the [convoy](#published-practice-and-how-far-each-was-read) the literature warns a first-come hand-off produces; it is accepted here because the holds are device lifetimes, tens of milliseconds to minutes, not the microseconds the warning is about, and because the alternative was the starvation above.

### Seeing the line

`tools/gpu-lock.ps1 status` (and `status -LockFile D:\workspace\linux-build.lock` for the build lock) prints who holds the lock, since when and until when, then who waits, in the order they will be served, with their purpose, how long each has waited, what it asked for and when it arrived:

```
held by 'agent-R143': R143 pair at the overlook (until 2026-11-11T19:02:10Z) (pid 41220, since 2026-11-11T18:52:10Z)
3 waiting, first served first:
  1. 'claude-engine' (pid 7716): gpu device: engine_gfx_tests.exe in D:/workspace/.../bin, waiting 212 s, asks 2 min, since 2026-11-11T18:53:01Z
  2. 'agent-S101' (pid 50008): S101 reel compare, waiting 431 s, asks 10 min, since 2026-11-11T18:49:22Z
  3. 'claude-engine' (pid 9120): bench physics.*, waiting 96 s, asks 30 min, since 2026-11-11T18:54:57Z
```

The first line is what `status` always printed, and its exit code is unchanged (2 held, 0 free or expired). A process that waits says once per holder and per place where it stands — `gpu-lock: waiting for the GPU lock, held by 'agent-R143' (pid 41220): ... (until ...); this process is behind 1 of the 3 in the line, first 'claude-engine' (pid 7716): gpu device: ..., waiting 212 s; gives up at ...` — and **a give-up names its place**: `gave up waiting for the GPU lock after 1800 s; it is held by ..., and this process was behind 2 of the 5 in the line, first ... . Exit 75: ...`, which `tools/dev.ps1 test` prints under the tests that did not run. A place can move back as well as forward, when a shorter ask arrives inside the window in which it may pass.

### Published practice, and how far each was read

The design follows what is published on fair locks; none of it was taken on trust from memory, and where a primary source could not be read on 2026-11-11 the secondary one is named as such.

- **L. Lamport, "A New Solution of Dijkstra's Concurrent Programming Problem", CACM 17(8), 1974** (the bakery algorithm). Read whole, in a full-text transcription with the proofs and the author's later commentary. The line is its shape: take a number, then wait for everyone with a smaller (number, process id), with ties in the number broken by process id — here (key, arrival, pid, counter). Two things it says that the page above depends on: its first-come-first-served is relative to the *doorway* (two processes choosing at once are not ordered by arrival, which is why the tie rule is stated and not hoped for), and its tolerance of a failed process assumes the failed process's number reads as zero afterwards — a file does not do that by itself, which is what the ticket's lease is for. It needs no lower-level mutual exclusion; the line does not either (a ticket write is not atomic with a listing), and leans on the lock file's create-new for the exclusion itself.
- **J. Mellor-Crummey and M. Scott, "Algorithms for Scalable Synchronization on Shared-Memory Multiprocessors", ACM TOCS 9(1), 1991.** The lock sections, from a partly garbled extraction; the conclusions not read. The ticket lock: FIFO, starvation-free, and presented there as the bakery lock made cheap. Also its warning that under FIFO one slow waiter delays everyone behind it — here a stalled waiter, bounded by the ticket's lease.
- **M. Blasgen, J. Gray, M. Mitoma, T. Price, "The Convoy Phenomenon", ACM SIGOPS OSR 13(2), 1979.** *Not read*: the scan has no text layer. Known through A. Colyer's summary ("the morning paper", 2019-07-01), which quotes it: handing a frequently re-requested lock on in arrival order makes every requester queue behind it, and their remedy is to *not* hand off — mark the lock free and let whoever runs take it. That remedy is the protocol as it was, and the starvation it permits is what this row removes; "What taking turns costs", above, is the convoy's price stated for holds of this length.
- **Windows.** J. Duffy, "Anti-convoy locks in Windows Server 2003 SP1 and Windows Vista" (2006; read whole): Windows' locks were made unfair on purpose, for throughput, at an admitted risk of starvation. Microsoft Learn, "Slim Reader/Writer (SRW) Locks" and "Mutex Objects" (read whole): the first says outright that the lock is not fair and not first-in-first-out, the second that a mutex's wait order must not be assumed to be. "LockFileEx" (read whole): documents no order among waiters. So an OS file lock would not have given the order either, and would have dropped the lock's owner, purpose and expiry, which other tools read.
- **Linux.** man7 `fcntl_locking(2)` and `flock(2)` (read whole): neither says anything about the order in which waiters are granted a lock. procmail's `lockfile(1)` (read whole): the retry-and-sleep lock file this protocol is a relative of, with a forced removal by age and no ordering.
- **Batch scheduling.** Highest response ratio next, (wait + service) / service, attributed to P. Brinch Hansen (1971): *secondary only* (the Wikipedia article, which cites Stallings' textbook, and lecture slides); the primary was not found. It is the multiplicative cousin of the sum used here; the sum was chosen because its order is static. Aging as the remedy for starvation under shortest-job-first: *secondary only* (the Wikipedia article citing Silberschatz, Galvin and Gagne). Slurm's multifactor priority plugin (the documentation's relevant sections): a weighted sum with an age factor that is capped (`PriorityMaxAge`), and a job-size factor that by default favours *large* jobs. EASY backfilling (Mu'alem and Feitelson, IEEE TPDS 12(6), 2001; abstract only): a job may jump ahead only if it does not delay the first job in the queue, on user-declared run times — which on one GPU that runs one job at a time never applies, since there is no hole to fill.
- **Ordering by arrival plus declared length** was not found analysed under any name. It is shortest-job-first with linear aging at rate one (rank by declared − waited, and the common "now" cancels), and earliest-deadline-first with each job's deadline at its arrival plus its own length; the no-starvation argument above is this page's, not a citation.

## Windows

**A process never waits for the lock with a window on screen.** A Vulkan window (`window::WindowDesc::vulkan`, the default) is for a GPU device, so `window::Window::create` joins the process's hold *before* `SDL_CreateWindow` — or `show()` before it shows one created hidden, which until then is on nobody's screen and takes nothing, so a test that only needs a window's events does not queue behind somebody else's GPU work — and `destroy()` leaves it after the window is gone ([window](window.md)); the device created afterwards joins the same hold. So a test's `engine-view` that has to wait does it invisibly, and appears when it has the GPU. It was found the hard way: on 2026-09-30 two test `engine-view`s, from two suites run at once while a merge gate held the lock for three suites, had opened their windows and then waited in `Device::create` — whose sleep pumps no messages — and sat "Not responding" on the owner's desktop for six and fifteen minutes. A window that nobody can use while somebody else has the GPU is noise on a person's desktop whatever it does with its messages, so the order was changed rather than the wait taught to pump. `window_tests.cpp` holds it: a window is created against a lock another holder has, while a second thread counts the process's visible windows, and none may appear before the lock is this process's (185 did, with the hold taken after the window).

## Interactive sessions and the owner's scripts

**Only the test harness opts in; no binary does by default.** The switch is `ENGINE_GPU_LOCK_ON_DEVICE=1`, `hold_config_from_environment()` reads it (`enabled = ... == "1"`), and the one place in the tree that sets it is `take_part_in_the_gpu_lock()` in `tests/support/test_main.cpp`, for the test executable and what it starts. An `engine-view` or `engine-host` started any other way takes nothing and waits for nothing, whoever holds the lock. The owner's flights are started that way: `D:\workspace\game_engine_local\bin-interactive\fly-erg.ps1` (line 9) and `walk-erg.ps1` (line 31) run `bin-interactive\engine-view.exe` directly and set no `ENGINE_GPU_LOCK_*` variable, so they never sit behind a test gate however long it holds the lock. (Their header comments suggest `tools/gpu-lock.ps1 run -Exec ...` for a flight whose numbers will be quoted; that takes the lock *for* the flight, and the flight's `engine-view`, with the switch off, still takes nothing of its own.) The other half of the rule holds too: a test's child never draws — and, since the change above, never shows a window — before its process holds the lock, because the hold is taken before the window and before the device, and nothing is drawn without either.

## Tests that start processes

**A holder's children never wait on it.** A process that holds the lock sets `ENGINE_GPU_LOCK_HOLDER` to its own pid for the processes it starts, and a child that finds the lock held by that pid uses it as it is (`Parents`) instead of waiting — so a test, or a script, that holds the lock and starts something that opens a device cannot deadlock with it. That is `device_hold_tests.cpp`'s "a child finds its parent's hold" case, and the same mechanism `tools/gpu-lock.ps1 run` has always used. Every test that starts processes today, and what holds the lock in it:

| Test or script | What it starts | Who holds the lock |
|---|---|---|
| `engine_view` | `engine-view` (window and device), `engine-content` | each `engine-view`, for its own life; the test process opens no device and no window |
| `engine_cli` | `engine-cli`, which starts `engine-host`; `engine-host` directly | each `engine-host`, from its first `render.*` call to its exit; the test and `engine-cli` hold nothing |
| `mcp_bridge` | `engine-mcp`, which starts `engine-host` | the `engine-host`, as above |
| `engine_content`, `engine_input`, `engine_image` | the app | nobody: they open no device (`engine-input`'s window is not a Vulkan one) |
| `gpu_lock` | `engine_gpu_lock_probe` | the probe, or its parent probe with the child in `Parents` mode |
| `tools/ci/gpu-smoke.ps1` | `ctest`; `engine-view` for the captures | the tests their own; the script, around the captures, with `engine-view` finding it through `ENGINE_GPU_LOCK_HOLDER` (and taking nothing itself, since the switch is off) |
| `tools/ci/reference-compare.ps1`, `tools/flythrough.ps1` under `gpu-lock.ps1 run` | `engine-host`, `engine-view` | the script or the wrapper; the children take nothing (switch off) |

No test holds the lock itself while it waits for a child, and none holds a device while it starts one. The one arrangement that could still serialise against itself is two *siblings* that both need a device at the same time under a parent that holds none; see "What it does not do".

## Waiting behind a long holder

**A wait is bounded inside the test's timeout, and ends with a line that says for whom.** Every wait in a test's tree gives up at the test's start plus `ENGINE_TEST_GPU_LOCK_WAIT_S` (1,800 s), and a test that can wait has `TIMEOUT` 1,800 + 600 s, so CTest's timeout — which reads exactly like a hang, the disguise AGENTS.md warns about — is never what ends a wait. What ends it is the process's own line, for example (2026-09-30, behind a merge gate running three suites under one hold):

```
gpu-lock: gave up waiting for the GPU lock after 997 s; it is held by 'fable-merge-sand-detail-3'
(pid 90712): merge gate: sand detail third pass, three suites (until 2026-09-30T15:55:43Z). Exit 75:
nothing ran on the GPU; run this again when the lock is free
gpu-lock: a process this one started gave up waiting for the GPU lock (exit 75); this one ends the same way
```

and CTest's `***Skipped` for the test (`engine_cli`, at 1,801 s), which `tools/dev.ps1 test` turns into exit 75 with that line printed under the names of the tests that did not run. A holder that keeps the GPU for an hour — a gate still wrapping three suites in `gpu-lock.ps1 run`, a diffusion batch — therefore costs a test run its GPU tests, named, rather than a failure; a gate that has to sit behind one can raise the budget for its build (`cmake -DENGINE_TEST_GPU_LOCK_WAIT_S=3600`, and `TIMEOUT` follows). What a suite's wall time is when it has to queue is in [the measurement](../experiments/gpu-lock-per-device-2026-09-30.md).

On Windows, first run `tools/dev.ps1 configure -Preset msvc-debug`, then
`cmake --preset msvc-debug -DENGINE_TEST_GPU_LOCK_WAIT_S=3600` in the **same
PowerShell process**, followed by the usual `tools/dev.ps1 test` command. The
driver establishes the Visual Studio and Ninja environment. Calling CMake from
an uninitialized shell can invalidate the compiler selection in an existing cache;
restore it through `dev.ps1 configure` before applying the override. This changes
the local build's queue allowance and matching CTest timeout, not its assertions.

## Elsewhere, and the limits

**Linux, the hosted runners, and machines that do not take part.** Nothing waits and nothing fails. A machine without a usable Vulkan device never reaches `vkCreateDevice` — the hosted runners, the Linux container — and so never touches a lock. Off Windows the default lock is `/tmp/gpu.lock`, which has no other holder on the GPU server or in the container (whose `/tmp` is its own, not this desktop's), so a hold is taken and released at once. A machine where the lock's directory does not exist — a self-hosted runner, a machine a test bundle was sent to — does not use the protocol (`NoDirectory`) and runs as if the switch were off; create `D:\workspace` (or point `ENGINE_GPU_LOCK` somewhere) on a machine that should take part.

**What it does not do.** Two processes of one test that need a GPU device *at the same time* and share no ancestor that holds the lock — an end-to-end test that started two engine-hosts side by side and rendered in both — would have the second wait for the first until the deadline, and then skip. No test does that today: in every suite measured below, each wait was for another holder — another agent, a sibling suite, or the crashed host described above — never for a sibling process of the same test. A child that took the lock over from its parent does not re-advertise `ENGINE_GPU_LOCK_HOLDER` to children it starts after that, because setting the environment from the keeper thread is not safe while the main thread reads it. And the line orders the waiters that take part in it, not the ones that do not: a tool that takes no ticket (anything built before 2026-11-11, and the Blender agent until GPU-LOCK.md's snippet takes one) still gets the card when its own look lands on a free lock ([the line](#the-line)). A child that takes its parent's lock over does it without a ticket too: its device is already open, and the lock it writes is a statement of that, not a request.

**The hold log.** `ENGINE_GPU_LOCK_LOG=<file>` appends one JSON line per hold when it ends — `event: "hold"`, the lock's path (`lock`), `pid`, `exe`, `purpose`, `started`, `held_ms`, `waited_ms` and `end_unix_ms` — and one `event: "gave_up"` line per give-up with the holder it gave up on (`holder_owner`, `holder_purpose`). Only holds this process wrote are logged; a child's `Parents` hold is its parent's line. It is how a suite's holds are counted and timed ([the measurement](../experiments/gpu-lock-per-device-2026-09-30.md)); a log that cannot be written never stops a device.

## The module

**Owned data.** This process's hold: the device count, its mode, the keeper thread, the lock file the hold wrote while it lasts, and, while it waits, its one ticket in `<lock>.line`. Nothing else on disk; the line's directory is made by the first waiter and left in place, empty when nobody waits.

**Invariants (tested).**
- The file format and the rules are GPU-LOCK.md's: created with create-new, refreshed by rename, an unreadable file is being written until it is a minute old, an expired lock is broken only by the verified move-compare-delete, a person's (`marc`) never, and a release deletes only the file this process wrote (owner, pid and start time).
- With the switch off, a device takes nothing and writes nothing.
- A Vulkan window takes the hold before it appears — in `create()`, or in `show()` for one created hidden, which takes nothing until then: no window of a process is on screen while the lock it waits for is somebody else's (`window_tests.cpp`).
- The first device takes the lock, later devices of the same process share it, and the last one releases it; while it is held, `ENGINE_GPU_LOCK_HOLDER` names this process, and afterwards it is what it was.
- The keeper keeps a short lease alive past its first expiry while the hold lasts, and stops before the release returns.
- A lock held for this process by an ancestor (`ENGINE_GPU_LOCK_HOLDER`) or by another path in this process (the harness's lease) is used as it is and never released by the device hold; the same ancestor's lock, expired, is broken and taken.
- A parent's hold that goes away while a child still has a device is taken over by the child; a parent that dies first leaves the lock to its child within one lease.
- A crash leaves the lock for one lease and no longer.
- A wait that runs out exits with 75 and says who held the lock; a parent that takes part in the lock and sees a child do that exits with 75 too; a person's lock is waited on and never broken.
- A command wrapped in `tools/gpu-lock.ps1 run` finds the lock its own in every process it starts, whether the owner is the default, in the environment, or given with `-Owner`; a lock session opened inside it holds nothing and waits for nothing.
- A `Lease` (the harness's) that finds a wrapper's lock alive uses it as it is, and breaks it once it has expired.
- The line: a free lock is not taken past a live ticket; the order is key, arrival, pid, counter, whatever order the files were written in; waiters are served as they stood and one that asks again goes last; a short ask passes a long one only inside the difference between them, and a declaration counts for at most half an hour; a dead ticket is skipped and removed, and a killed waiter stops counting within its ticket's lease; a killed holder is broken after its lease and the line keeps its order; a holder without a ticket is waited for and takes nothing from the order; a process held for (a child, a wrapped run) takes no ticket; a give-up says where the process stood; the PowerShell half reads the tickets this half writes, and the other way round.

**Public API.**
- `foundation/gpu_lock/gpu_lock.h`: `State`, `Identity`, `default_path`, `current_identity`, `read`, `k_unreadable_stale_s`, `parse_iso8601_utc`, `format_iso8601_utc`, the line (`Waiter`, `line_directory`, `read_line`, `k_ticket_lease_s`, `k_line_look_ms`, `k_declared_cap_s`), `Lease` (the harness's hold: `acquire`, `refresh_if_due`, `release`, `Lease::Outcome`; `Config::look_ms`, `ticket_lease_s`), `to_string`.
- `foundation/gpu_lock/device_hold.h`: the environment's names (`k_env_on_device`, `k_env_wait_until`, `k_env_holder`, `k_env_log`), the numbers (`k_device_lease_s`, `k_device_refresh_s`, `k_device_poll_s`, `k_default_wait_s`, `k_exit_gave_up`), `HoldConfig` (with `look_ms` and `ticket_lease_s`), `hold_config_from_environment`, `HoldMode`, `DeviceHold` (`acquire`, `release`), `HoldStatus`, `hold_status`.
- `core/platform/process.h`: `k_exit_gpu_lock_gave_up`, and `Process::wait()`'s rule for a child that exits with it ([platform](platform.md)).

**Depends on.** `base`, `containers`, `json`, `platform`, `time`.

**What the line asks of GPU-LOCK.md.** That file is outside the repository (`D:\workspace\GPU-LOCK.md`) and is the protocol for tools that are not the engine's; it still says "no queue" by omission and its Python snippet takes no ticket. Until it carries the ticket rules — take a ticket, try the lock only from the head, refresh the ticket, delete it — the Blender agent is a waiter built before the line, with the standing described above. The text to add is the three paragraphs that open this page's "The line"; the owner's to place.

**Testing.** `tools/dev.ps1 test -Filter gpu_lock` runs `gpu_lock_tests.cpp` (the file, the reading and the harness's lease, every lock in the case's own `TempDir`) and `device_hold_tests.cpp`: in this process, the switch, the counting, the keeper, a lock held for the process, a parent's hold taken over, waiting, breaking, a person's lock and the log; and through `engine_gpu_lock_probe` — a process that holds the lock as a process with a device does and opens none — a child under its parent, a give-up's 75 and its parent's, a crash (the probe killed with `TerminateProcess`/`SIGKILL`), a parent that dies first, and a command wrapped in `tools/gpu-lock.ps1 run` under the default owner, an owner in the environment and an owner given with `-Owner` (skipped where there is no `pwsh`). Each case clears the variables a run around it may have set, so the suite passes wrapped, unwrapped and while being measured. Every case reads the lock through one helper that reads again while the file is present and unreadable: the keeper refreshes by renaming over the file, a reader that opens it in that moment is told it is being written, and a case that read once at a fixed time landed in that window once in eight gates (b42, 2026-10-27, the minimal suite beside three others) and failed on an `expires` it never got. `gfx`'s `device_tests.cpp` checks the one place it is wired in: a device holds a scratch lock while it lives when the switch is on, shares that hold with another holder in the process, and takes nothing when it is off. The PowerShell half is `tools.machine_lock`. The two-process integration in a full suite is measured, not unit-tested: [the measurement](../experiments/gpu-lock-per-device-2026-09-30.md).

**Performance notes.** A hold costs a directory check, a read of the lock and a listing of the line (both usually of nothing), a file create, an environment write and a thread start, and on release a join, a read, a delete and the environment put back: measured with `engine_gpu_lock_probe cycles 200` (a take and a release of a free lock, 200 times) at 2.28–2.35 ms a cycle in `msvc-debug`, three runs, with a Linux container build running beside it and the CPU 16% busy — an upper bound — against 1.6 µs with the switch off. That figure is from before the line; with it the same command gave 5.0–7.4 ms, three runs on 2026-11-11 with the CPU 94% busy (a dozen agents building) — an upper bound again, and not a pair with the first: the added work is the read and the listing. A ticket, when there is somebody to wait behind, is three more file operations (a write beside, a rename, a delete): 20–26 ms a cycle with every take made to write one, the CPU 81% busy. A waiter costs a directory listing and one read per ticket every 250 ms. That is next to `vkCreateDevice`, which takes tens to hundreds of milliseconds, once per device. The keeper wakes every 30 s. Nothing here is on a frame path.
