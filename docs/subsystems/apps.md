# apps: engine-host, engine-cli, engine-view, engine-content (apps)

**Purpose.** The first executables (docs/plan/02-architecture.md §2.2, ADR-0001). `engine-host` is the engine as a headless server: in Phase 0 it runs in `sim` mode only and speaks JSON-RPC 2.0 over stdio, one request per line in and one response per line out. `engine-cli` is the thin scriptable client for humans, agents, and CI: it spawns a host, optionally opens a document, sends one method, prints the result, and exits. Because sessions persist their journal and undo position on disk (see [doc](doc.md) and [protocol](protocol.md)), a sequence of separate `engine-cli` invocations behaves like one editing session, which is what the Phase 0 exit criterion asks for and what the end-to-end test checks. `engine-view` is the window on the renderer, and `engine-content` is the content build on the command line: the step that turns a source mesh into the derived form the renderer loads.

**engine-host.**
```
engine-host [--stdio] [--request <json>] [--mount <scheme>=<dir>[:rw]]... [--log <spec>] [--log-json <path>] [--tunables <file>]
```
stdout belongs to the protocol. Log records go to an in-memory ring (`log.tail` reads it), warnings and above to stderr, and optionally every record as JSON lines to a file. Assertion failures are routed through the log before the process aborts. `--request` answers one request and exits, for scripts that do not want a pipe.

**engine-cli.**
```
engine-cli [--host <path>] [--doc <dir>] [--create] [--name <name>] [--mount <spec>]... [--compact] <method> [params-json]
```
With `--doc` the CLI opens the document first (creating it with `--create`) and injects the session id into the params. Results print as pretty JSON (or one line with `--compact`); errors print `error <code>: <message>` and any diagnostics to stderr and exit 1; usage problems exit 2. The host is found beside the CLI unless `--host` says otherwise.

**Example (the exit criterion).**
```bash
engine-cli --doc ./world --create --name World session.info
engine-cli --doc ./world doc.apply '{"commands":[{"kind":"CreateObject","id":"00000000000000100000000000000001","type":"engine.content.AssetProvenance"}],"attribution":{"actor":"me","role":"environment","task":"t1","rationale":"first object"}}'
engine-cli --doc ./world doc.objects
engine-cli --doc ./world doc.undo
engine-cli --doc ./world doc.redo
engine-cli --doc ./world doc.add_layer '{"name":"quest"}'
engine-cli --doc ./world doc.diff '{"from_layer":"base","to_layer":"quest"}'
engine-cli --doc ./world doc.merge '{"base_layer":"base","ours_layer":"quest","theirs_layer":"other","output_layer":"merged"}'
engine-cli gpu.adapters                       # what the machine's GPUs support (see gfx.md)
```

**engine-view.**
```
engine-view [--width <px>] [--height <px>] [--frames <n>] [--capture <file.png>] [--no-vsync] [--adapter <i>] [--validation] [--grid <n>] [--log <spec>] [--shaders <manifest.json>] [--lod <px>] [--no-cull]
            [--raster direct|hw|vertex|sw|auto|rt] [--sw-px <px>] [--view id|tri|depth|shaded|normals|uv] [--orbit <d>] [--no-occlusion] [--no-cone]
            [--mesh <file.gltf|file.glb>]
```
The engine's first window (windowed mode). A procedural heightfield is built into a cluster LOD DAG (`geometry`), uploaded behind device addresses, culled and LOD-selected on the GPU every frame (`cluster_cull.slang`, threshold `--lod` in pixels, default 1), and drawn one mesh-shader workgroup per surviving cluster through an indirect draw into the swapchain with a reversed-Z depth buffer while the camera orbits and zooms between 8 and 36 units so the cut changes visibly; each cluster gets its own color, so the picture is also the cluster-partition debug view. `--no-cull` draws every leaf cluster instead. `--raster` picks the path: `direct` is mesh shaders straight to color with a depth buffer; `hw` (default), `vertex`, `sw`, and `auto` rasterize into the 64-bit visibility buffer through mesh shaders, the vertex-shader baseline tier (chosen automatically on GPUs without mesh shaders), the software rasterizer, or mesh shaders and software split at `--sw-px` pixels of projected cluster diameter, then resolve it; `rt` replaces rasterization with ray queries (NVIDIA RTX only, exit 3 elsewhere): the cull pass's visible list becomes cluster acceleration structure build records on the GPU (`clas_records.slang`), the CLAS, cluster bottom-level, and top-level structures are built in the same frame with no CPU round trip, and `ray_visibility.slang` traces one ray per pixel into the visibility buffer, which the resolve then shades exactly as it shades a rasterized one (`gpu_ms.rt` is the four builds, `gpu_ms.trace` the rays; the FlightHelmet's 253-cluster cut builds in 0.16 ms and traces in 0.02 ms at 800×600 on the RTX 5090) (`--view` shows materials lit by a sun with smooth vertex normals by default, or cluster colors, triangle shading, depth, normals, or UVs; three materials, sand, rock, and snow, are assigned by the height of each cluster's center, and sand and rock sample a procedural ripple texture through the bindless set at different UV scales). `--orbit` fixes the camera distance for measurements; camera distances scale with the scene radius (10 for the heightfield). `--mesh` renders a glTF 2.0 or GLB file instead of the heightfield (`assets::load_gltf`, then `geometry::weld_vertices` so exported duplicate vertices do not starve the clusters; `tools/fetch-samples.ps1` fetches permissively licensed Khronos samples into `content/samples/`): one cluster LOD DAG is built per primitive and the DAGs are merged (`geometry::merge_cluster_lod`) so that every cluster has exactly one material; the file's metallic-roughness materials become the resolve's material table (base color as albedo, roughness and metallic carried along), base-color images are decoded on the CPU (`image::decode_image`, embedded bytes or a file beside the glTF) and uploaded as sRGB textures into the bindless set, an image that fails to decode leaves its material untextured with a warning, and the camera orbits the mesh's bounds. The cull pass backface-culls clusters by their normal cones unless `--no-cone`. In the `hw` and `vertex` modes two-pass occlusion culling is on (`--no-occlusion` turns it off): pass 1 draws last frame's visible clusters, a Hi-Z pyramid is built from the visibility buffer, pass 2 tests the rest against it, and the pyramid is rebuilt for the next frame; the summary reports the clusters each pass drew and the Hi-Z time. The JSON summary reports cluster and level counts, DAG build time, the number of glTF primitives (`mesh_primitives`, 0 for the heightfield), whether cone culling was on, the hardware and software visible-cluster counts (read back one frame late from per-slot copies of the indirect arguments), and GPU milliseconds per pass (cull, hw, sw, resolve) averaged over the run from timestamp queries, which is how experiment E1 was measured. `--frames N --capture out.png` renders N frames and writes the last one as a PNG, and the process prints one JSON line of statistics (frames, seconds, average ms, size, cluster and triangle counts, whether the capture was written) to stdout, so scripts and agents look at the picture and the numbers without a human at the window. Escape or closing the window exits; resizing recreates the swapchain and the depth buffer. Shaders come from the build's manifest when it sits beside the executable (`<exe dir>/../shaders/manifest.json`, or `--shaders`), so editing `cluster_mesh.slang` while the window is open recompiles it through slangc and rebuilds the pipeline within a quarter second; a save that does not compile prints slangc's diagnostics to stderr and keeps the last good shader. `--log` with an explicit spec routes those categories to stderr at the given levels. Exit codes: 0, 1 error, 2 usage, 3 unavailable (no display, no Vulkan device, no mesh shaders, or no presentation), which the end-to-end test treats as a skip. On the RTX 5090 the default 257×257 grid (131,072 triangles, 2,898 clusters in 12 levels, 861 ms to build) draws 98 to 162 clusters per frame at a 1 px threshold and renders in about 0.65 ms per frame at 960×540 without vsync.

**engine-content.**
```
engine-content build <in.gltf|in.glb> <out.clusters> [--max-triangles <n>] [--max-vertices <n>] [--no-weld] [--log <spec>]
engine-content info <file.clusters>
```
The content build on the command line (docs/plan/07-content-pipeline.md §7.3): the step between a source mesh and what the renderer loads. `build` imports the file with `assets::load_gltf`, welds its vertices unless `--no-weld` (exporters duplicate freely, and without welding the 64-vertex cluster limit starves both the clusters and the LOD builder), builds one cluster LOD DAG per glTF primitive with the file's normals and UVs so that every cluster has exactly one material, merges them (`geometry::merge_cluster_lod`), maps each merged cluster to its primitive's material (a primitive that names none gets one appended default), converts the metallic-roughness materials into the file's 64-byte records, carries the image paths over as the glTF gave them (an embedded image keeps its slot with an empty path and is counted separately), and writes the `.clusters` container described in [geometry](geometry.md). `--max-triangles` (4..256) and `--max-vertices` (1..255) are the per-cluster limits, 124 and 64 by default. `info` reads a container back and prints its header, every section record with its kind and name — including a section this build does not know, since it reads the table straight from the bytes — and the counts. Both commands print one JSON line on stdout and nothing else (`build`: `clusters`, `leaf_clusters`, `triangles`, `lod_levels`, `vertices` (cluster-ordered, so duplicated per cluster and per level), `materials`, `images`, `embedded_images`, `bytes`, `build_ms`, `hash`), so a script reads the numbers and an agent checks the hash; everything else is a log record on stderr under the `content` category. Exit codes: 0, 1 (the mesh could not be loaded, clustered, or written), 2 usage. Measured on the samples `tools/fetch-samples.ps1` fetches, `msvc-release` on an i9-10980XE: `Suzanne/Suzanne.gltf` is 3,936 triangles into 88 clusters in 7 levels (42 leaves), 167,168 bytes in 22 ms; `FlightHelmet/FlightHelmet.gltf` is 94,722 triangles into 2,348 clusters in 10 levels (1,102 leaves) with 6 materials and 15 images, 4,435,904 bytes in 288 ms; `Avocado/Avocado.glb` is 682 triangles into 15 clusters, 28,144 bytes in 34 ms, with its 3 images embedded. In `msvc-debug` the same builds take 70 ms and 997 ms. The viewer learns to load a container in a later change; until then `engine-view --mesh` still imports the glTF itself.

**Build.** `engine_app(NAME engine_host OUTPUT engine-host SOURCES ... DEPS ... [E2E_TESTS ...])` in `cmake/EngineModule.cmake` builds an executable into `build/<preset>/bin/`, records it in `modules.json` with layer `apps`, and can build an end-to-end test executable that receives the app's path as `ENGINE_APP_PATH`. The CLI test also receives `ENGINE_HOST_PATH`.

**Depends on.** engine-host: `protocol`, `log`, `io`, `tunables`. engine-cli: `json`, `platform` (`Process`, `executable_directory`). engine-view: `window`, `image`, `io`, `geometry`, `assets`, `gfx`, `math`, `time`, `log`. engine-content: `geometry`, `assets`, `io`, `json`, `log`, `time`, `math`, `containers` (no GPU, no window: it runs on a build machine).

**Testing.** `tools/dev.ps1 test -Filter engine_cli` runs the end-to-end suite: info and methods through a spawned host, error exit codes, and the exit criterion with one process per step (create, apply, objects, undo, redo across processes, add layer, diff, get, validate, journal). `-Filter engine_view` runs engine-view for six frames at 320×200 with a capture and checks the JSON summary and the PNG header, plus the usage exit codes, and writes a two-material cube with an embedded PNG texture as a GLB at test time and renders it through `--mesh` (two primitives, two leaf clusters, both drawn; a missing file exits 1; copies of the fixture and the capture stay in the temp directory as `engine_view_mesh_cube.glb` and `engine_view_mesh_last.png`); it records a skip where the app exits 3. `-Filter engine_content` writes the same cube GLB at test time, runs `build` on it, and checks the JSON summary (12 triangles, two leaf clusters, two materials, one image and that one embedded), then reads the container back with `read_cluster_file`, checks that both materials are used and that the DAG validates against the merged source indices, confirms the hash matches `cluster_file_hash`, runs `info` and checks it names all twelve sections, and pins the exit codes for a missing input, an output directory that does not exist, a file that is not a container, and nine ways to get the arguments wrong; the built container stays in the temp directory as `engine_content_cube.clusters`.

**Not yet.** engine-host `offscreen` and `windowed` modes (engine-view is the standalone window until the host learns to own one), sockets, multiple clients per host, long-running operations, the MCP bridge, a persistent-host mode for the editor. engine-content: the derived-data cache (`ddc/`, content-addressed by the hash it already computes), incremental and parallel builds, textures (decode and compress beside the mesh), a manifest over several meshes, and the validation rules of [07 §7.4](../plan/07-content-pipeline.md#74-validation-rules-automatic).
