# apps: engine-host, engine-cli, engine-view, engine-content, engine-input, engine-image, engine-mcp (apps)

**Purpose.** The first executables (docs/plan/02-architecture.md §2.2, ADR-0001). `engine-host` is the engine as a headless server: in Phase 0 it runs in `sim` mode only and speaks JSON-RPC 2.0 over stdio, one request per line in and one response per line out. `engine-cli` is the thin scriptable client for humans, agents, and CI: it spawns a host, optionally opens a document, sends one method, prints the result, and exits. Because sessions persist their journal and undo position on disk (see [doc](doc.md) and [protocol](protocol.md)), a sequence of separate `engine-cli` invocations behaves like one editing session, which is what the Phase 0 exit criterion asks for and what the end-to-end test checks. `engine-view` is the window on the renderer, and `engine-content` is the content build on the command line: the step that turns a source mesh into the derived form the renderer loads. `engine-mcp` (module `mcp_bridge`) is the MCP bridge: a Model Context Protocol server an agent's client starts, which owns one engine-host and exposes curated tools over it ([its section](#engine-mcp-the-mcp-bridge) below).

**engine-host.**
```
engine-host [--stdio] [--request <json>] [--mount <scheme>=<dir>[:rw]]... [--log <spec>] [--log-json <path>] [--tunables <file>]
            [--roles <file.json>] [--actor <name>] [--role <name>] [--task <id>]
engine-host --debug-hang <method> ...     # a test hook (below)
```

**`--roles` loads role configurations** ([plan 06 §6.5](../plan/06-agent-tooling.md#65-permissions-concurrency-and-leases); `content/roles/roles.json` is the five named roles): what each role may call, which layers, tiles and object types it may change, and whether its work needs review. Every call is then checked against the role it runs in ([protocol](protocol.md#roles-leases-and-proposals)); without the flag nothing is restricted, which is how the host behaved before it existed. **`--actor`, `--role` and `--task` say who a call that names none is**: its attribution's blank fields, and with `--roles` the role it is checked as. A host that serves one agent — engine-mcp starts one per agent — is told that agent's identity this way. A roles file that does not read or does not check, and a `--role` it does not have, exit 2 before the host serves anything: a host told to restrict calls that quietly restricted nothing would be worse than one that refused to start.
stdout belongs to the protocol. Log records go to an in-memory ring (`log.tail` reads it), warnings and above to stderr, and optionally every record as JSON lines to a file. Assertion failures are routed through the log before the process aborts. `--request` answers one request and exits, for scripts that do not want a pipe.

**`--debug-hang <method>` is a test hook, not for use.** A request for that method is recognized before it is dispatched and never answered, and the host reads nothing after it — blocked on a condition variable nobody notifies, not spinning — until something kills it: a host that is alive and never answers, made on purpose, which is what a client's deadline exists for (engine-mcp's deadline test hands it over with `--host-arg`; [Deadlines](#deadlines)). It works for any method name, served or not, because the handler never runs. `--help` lists it under a heading of its own that says so, rather than hiding it: a flag the binary takes but never mentions is behaviour nobody can find, and the heading is what keeps a reader from using it.

Beyond `domain/protocol`'s methods it registers its own: `engine.ping` (in `main.cpp`: the pid and the uptime from a method that touches no state; [protocol](protocol.md#engineping-liveness)), `render.*` over the renderer (`render_methods.cpp`), and the rest of [plan 06 §6.9](../plan/06-agent-tooling.md#69-day-one-operations)'s day-one list — `content.build`, `session.events`, `engine.budgets`, `session.run_headless`, `engine.run_tests` — over the content build, the store, the runtime world and the validators (`ops_methods.cpp`; [protocol](protocol.md#the-day-one-operations) has what each does and returns). Their state is one `host::HostState` behind `protocol::Context::app` (`host_state.h`): the renderer's device and scenes, and each session's runtime world. Every capability those methods reach is optional (ADR-0027) and linked only when the configuration has it — audio, ECS, animation, the audio emitter system, the store, the tissue validators — with `ENGINE_HOST_<NAME>` defined for the code that uses it, as engine-view does for `--animate`; without one, the method that needs it answers 1006 naming the switch, and `session.run_headless` runs the engine's own scheduler alone instead of one driving a flecs world, which materializes nothing and says why. `session.materialize` sits beside the five: the document into the session's runtime world now, and a report of what mapped and what was skipped ([protocol](protocol.md#sessionmaterialize)). It registers `session.state_hash`, `session.save_game` and `session.load_game` too — the persistent-state hash, a save of the running world, and a load that continues it in a new session ([protocol](protocol.md#sessionsave_game-sessionload_game-sessionstate_hash), [world](world.md#save-and-load)) — which are the world capability's and answer 1006 where it is not built. With the ECS, the runtime world is the engine's scheduler driving a flecs world ([ADR-0038](../adr/0038-the-scheduler-owns-the-tick.md), proposed) with the kinematics, animation, audio emitter and npc capabilities installed where they are built, and it materializes the session's document before every run. The npc capability's hooks go after the entity store's, and its tile source — the schedule index — is registered with the driver beside them; its place and schedule indexes are read from the session's document at the start of every call that materializes and before a save's tiles are restored; and in a streamed world its residents take their tiers from the ring's observers ([npc](npc.md)). `msvc-minimal` and the `*-no-ecs` presets build that host.

**engine-cli.**
```
engine-cli [--host <path>] [--doc <dir>] [--create] [--name <name>] [--mount <spec>]... [--compact] [--report <file>] <method> [params-json]
```
With `--doc` the CLI opens the document first (creating it with `--create`) and injects the session id into the params. Results print as pretty JSON (or one line with `--compact`); errors print `error <code>: <message>` and any diagnostics to stderr and exit 1; usage problems exit 2. The host is found beside the CLI unless `--host` says otherwise.

`--report <file>` writes the same result to a file as one JSON document — `{"tool", "method", "generated_utc", "result"}` — **after** printing it, so a file that cannot be written never costs the caller the answer it already has. It is generic across methods and exists for one: `engine-cli gpu.adapters --report adapters.json` is what somebody runs on a machine no one here can log in to, and the file that comes back carries the whole requirements table and the verdict for every device on it (see [gfx](gfx.md#what-a-device-has-to-have)). The timestamp is there because such a file is read weeks later.

**Example (the exit criterion).**
```bash
engine-cli --doc ./world --create --name World session.info
engine-cli --doc ./world doc.apply '{"commands":[{"kind":"CreateObject","id":"00000000000000100000000000000001","type":"engine.content.AssetProvenance"}],"attribution":{"actor":"me","role":"environment","task":"t1","rationale":"first object"}}'
engine-cli --doc ./world doc.objects
engine-cli --doc ./world doc.undo
engine-cli --doc ./world doc.redo
engine-cli --doc ./world doc.add_layer '{"name":"quest"}'
engine-cli --doc ./world doc.diff '{"from_layer":"base","to_layer":"quest"}'
engine-cli --doc ./world doc.merge '{"base_layer":"base","ours_layer":"quest","theirs_layer":"other","output_layer":"merged"}'
engine-cli gpu.adapters                       # what the machine's GPUs support (see gfx.md)
engine-cli gpu.adapters --report adapters.json  # the same, as a file to send back
engine-cli audio.devices                      # what it can play to, each endpoint's layout (see audio.md)

# the day-one operations (protocol.md, "The day-one operations")
engine-cli content.build '{"source":"prop.glb","output":"prop.clusters","jobs":8}'
engine-cli content.build '{"manifest":"content/meshes.json","cache":true}'   # skips what is up to date
engine-cli --doc ./world session.events '{"limit":20}'                       # then '{"cursor":"<next>"}'
engine-cli --doc ./world session.events '{"source":"store","since":600}'     # the document's world.db
engine-cli engine.budgets '{"scope":"process"}'
engine-cli --doc ./world session.run_headless '{"seconds":0.5}'
engine-cli --doc ./world session.run_headless '{"seconds":60,"until":{"object":"0000000000000010000000000000000a","property":"generator","equals":"done"}}'
engine-cli --doc ./world session.run_headless '{"seconds":10,"write_back_every":1,"until":{"object":"<cart>","component":"engine.world.Transform","field":"position[0]","at_least":5}}'
engine-cli --doc ./world session.materialize '{}'                            # what mapped, what was skipped and why
engine-cli --doc ./world engine.run_tests '{"containers":["prop.clusters"]}'
engine-cli engine.run_tests '{"tissue":"torso.tissue"}'

# save and load (protocol.md, "session.save_game, session.load_game, session.state_hash")
engine-cli --doc ./world session.state_hash                                  # 16 hex digits and the parts
engine-cli --doc ./world session.save_game '{"path":"saves/one"}'            # a new or empty directory
engine-cli session.load_game '{"path":"saves/one","dir":"worlds/one-loaded"}'  # a new session on a copy

# roles, leases and proposals (protocol.md, "Roles, leases and proposals"); leases.json and
# proposals.json sit beside the document, so each engine-cli call sees what the last one granted
engine-cli --doc ./world lease.require '{"required":true,"attribution":{"actor":"director"}}'
engine-cli --doc ./world lease.acquire '{"layer":"world","tiles":[{"x0":0,"y0":0,"x1":1,"y1":1}],"attribution":{"actor":"a","task":"t1"}}'
engine-cli --doc ./world doc.propose_layer '{"name":"p.a","target":"world","attribution":{"actor":"a","rationale":"why"}}'
engine-cli --doc ./world doc.apply '{"layer":"p.a","commands":[...],"attribution":{"actor":"a","rationale":"why"}}'
engine-cli --doc ./world doc.promote '{"proposal":"p.a","attribution":{"actor":"director","rationale":"reviewed"}}'
engine-cli --doc ./world lease.list
```

A method that lives in the host rather than on disk — a runtime world's tick, a loaded scene — starts fresh with every engine-cli call, because each call spawns its own host; `session.run_headless` twice through engine-cli runs two fresh worlds, and through one engine-host (or engine-mcp) the second continues the first. A save is how a world crosses that line: `session.save_game` after a run through one host, and `session.load_game` in another, continue it where it stopped ([world](world.md#save-and-load)). Through engine-cli a save takes the world of that call's own host, which has not run, so it saves the document and the store at tick 0; save through the host that ran the world.

`audio.devices` is registered by engine-host only when the build has the audio capability (ADR-0027): the app links `domain/audio` when the target exists and defines `ENGINE_HOST_AUDIO` for the one registration line, as engine-view does for animation, and a minimal build's host answers it "method not found". An empty device list is a normal answer — a CI runner or the headless server has no audio device — exactly as an empty adapter list is.

The engine's first window (windowed mode). A procedural heightfield is built into a cluster LOD DAG (`geometry`), uploaded behind device addresses, culled and LOD-selected on the GPU every frame (`cluster_cull.slang`, threshold `--lod` in pixels, default 1), and drawn one mesh-shader workgroup per surviving cluster through an indirect draw into the swapchain with a reversed-Z depth buffer while the camera orbits and zooms between 8 and 36 units so the cut changes visibly; each cluster gets its own color, so the picture is also the cluster-partition debug view. `--no-cull` draws every leaf cluster instead. `--raster` picks the path: `direct` is mesh shaders straight to color with a depth buffer; `hw` (default), `vertex`, `sw`, and `auto` rasterize into the 64-bit visibility buffer through mesh shaders, the vertex-shader baseline tier (chosen automatically on GPUs without mesh shaders; it draws the cut's own triangles indexed where the device has `geometryShader` and `fullDrawIndexUint32`, and the summary's `triangles_hw_last` is how many and `vertex_fallback_last` how many clusters its index budget sent to the capacity draw instead — [gfx](gfx.md), "Baseline tier"), the software rasterizer, or mesh shaders and software split at `--sw-px` pixels of projected cluster diameter, then resolve it; `rt` replaces rasterization with ray queries (NVIDIA RTX only, exit 3 elsewhere): the cull pass's visible list becomes cluster acceleration structure build records on the GPU (`clas_records.slang`), the CLAS, cluster bottom-level, and top-level structures are built in the same frame with no CPU round trip, and `ray_visibility.slang` traces one ray per pixel into the visibility buffer, which the resolve then shades exactly as it shades a rasterized one (`gpu_ms.rt` is the four builds, `gpu_ms.trace` the rays; the FlightHelmet's 253-cluster cut builds in 0.16 ms and traces in 0.02 ms at 800×600 on the RTX 5090) (`--view` shows materials lit by a sun with smooth vertex normals by default, or cluster colors, triangle shading, depth, normals, or UVs; three materials, sand, rock, and snow, are assigned by the height of each cluster's center, and sand and rock sample a procedural ripple texture through the bindless set at different UV scales). The shaded view lights the surface with the resolve's physically based BSDF (`brdf.slang`, see [gfx](gfx.md)): a directional sun, a sky hemisphere, and two point lights, one warm and one cool (standing where frame 0 puts them; `--orbit-lights` makes them orbit the scene out of phase with the frame number, as they always did before 2026-09-27), whose radius of influence and intensity scale with the scene radius (intensity with its square, because the falloff is inverse square) so a 2 cm mesh and the heightfield are lit alike. They are passed per frame behind the `ResolveParams` block in the same host-visible buffer, and `--no-lights` turns them off, which is how to measure or compare a picture with only the sun in it. On the heightfield they change the picture by up to 110 of 255 and by 9 on average. `--orbit` fixes the camera distance for measurements; camera distances scale with the scene radius (10 for the heightfield). `--mesh` renders a glTF 2.0 or GLB file instead of the heightfield (`assets::load_gltf`, then `assets::weld_vertices` — the weld `engine-content build` runs, over every per-vertex stream including skin bindings, morph channels and canonical vertex ids — so exported duplicate vertices do not starve the clusters; `tools/fetch-samples.ps1` fetches permissively licensed Khronos samples into `content/samples/`): one cluster LOD DAG is built per primitive and the DAGs are merged (`geometry::merge_cluster_lod`) so that every cluster has exactly one material; the file's metallic-roughness materials become the resolve's material table (base color as albedo, roughness and metallic carried along, and the emissive factor as a constant term unless the material modulates it with an emissive texture, which the resolve has no slot for yet), and each material's base-color, metallic-roughness, and normal images are decoded on the CPU (`image::decode_image`, embedded bytes or a file beside the glTF) and uploaded into the bindless set — one slot per image, shared by every material that names it, base color as sRGB and the two data maps as UNORM, since a roughness or a normal is not a color. An image that fails to decode leaves that slot empty with a warning, and the camera orbits the mesh's bounds.

**What the samples look like now that the maps are read.** The three Khronos models the resolve was compared on, before and after, at `--width 800 --height 600 --orbit 22`. FlightHelmet: the leather crown was one flat olive-brown dome with a single broad sheen, and is now visibly creased and quilted, its stitching and panel seams standing out under the orbiting point lights, the brown warmer and more varied; the metal on the mask frame, the buckles, and the ribbed hose pick up small bright glints where before they were the same dull matte as the cloth; the goggle lens has a defined highlight; and the varnished wooden base has gained a glossy band along its top face. BoomBox: the silver body panel, the handle, and the antenna were a uniform mid-grey and now read as metal, bright with a sharp moving highlight, while the speaker grille has gone from a flat printed dot pattern to a recessed, dark, perforated mesh; the black shell's highlight is tighter and the buttons and dials have relief. Corset: the red brocade was plasticky with a wide sheen and is now dull cloth with the damask pattern in relief, the laces are round cords with a highlight each instead of painted-on lines, the eyelets glint, and the cream mannequin is matte with its seams visible; the base disc is glossier than the body it holds. In short: cloth and leather have become dull dielectrics, buckles and the BoomBox's metal have become metal, and the normal maps put surface detail where the geometry has none. `--mesh` also takes a `.clusters` container ([geometry](geometry.md)) and renders it without importing or clustering anything: the DAG, the quantized positions and their grid, the attributes and triangles, the materials from the file's 64-byte records — including the metallic-roughness, normal, and emissive slots that live in the record's second half, which an older container leaves at zero and the reader therefore reads as "none" — the material index of every cluster, and the textures — decoded from the file's image paths, resolved against the directory of the source mesh the container names (against the container's own directory when it names none), or from the **encoded bytes the container carries** for an image the source embedded rather than named ([geometry](geometry.md), "Embedded images"). Everything downstream — cull, LOD selection, the four rasterizers, ray tracing, the resolve — is the same code and draws the same picture, and `--raster hw` and `--raster rt` agree to 59 pixels of 480,000 at 800×600 (silhouettes, where a ray and a rasterized edge disagree). **A mesh drawn from its container is the picture its glTF draws, byte for byte** — from the glTF, from a cache miss, from a cache hit, and from a container `engine-content build` wrote, one PNG. That is asserted rather than assumed: `engine-view`'s end-to-end test renders its cube-GLB-with-an-embedded-PNG fixture all four ways and compares the captures as bytes, and the five Khronos samples were checked the same way by hand at 400×300 (`--orbit 22 --shadows off`), each giving one SHA-256 across all four paths — Lantern `cd40d3dd…`, BoomBox `6cec6390…`, Corset `e35a86d8…`, Avocado `0592f581…`, FlightHelmet `f1669cd6…`. The one thing a container still needs from outside is an image the source kept in a file of its own, which it names by path; such an image missing is a warning and an untextured material, as it is for the glTF. Between the two, `--mesh <file.gltf>` looks in the **derived-data cache** first: `<ddc>/clusters/<hash>.clusters`, where the hash covers the glTF's bytes and those of every external buffer it names, the cluster build options, and a cache version constant (`geometry::cluster_cache_key`, `cluster_cache_path`). A hit loads the container; a miss builds as before and writes the entry, the same mesh `engine-content build --cache` writes to the same path, so either program fills the cache and either finds it. The two entries differ in one section: `engine-content` records the source's identity (`source_hash`, section 15) and `engine-view` leaves it zero, which costs an `engine-content build-all` one rebuild of an entry `engine-view` wrote, and nothing else. `--no-cache` skips both. The cache root is `<repo>/ddc`, found by walking up from the executable to the directory holding `AGENTS.md`, or `--ddc <dir>`; with neither, the cache is off with a warning. The FlightHelmet takes 907 ms to import and cluster in `msvc-debug` on an RTX 5090 machine and 31 ms to load from the cache, reported as `build_ms` either way. **A scene of instances.** `--scene <file.json>` renders several meshes and several instances of them instead of one mesh: `{"meshes":[{"path":"...gltf|.glb|.clusters"}], "instances":[{"mesh":0,"translation":[x,y,z],"rotation":[x,y,z,w],"scale":[x,y,z]}]}`, where a mesh path is resolved against the file's own directory, every instance field but `mesh` is optional, and an empty instance list places one identity instance of every mesh. The file is an `engine.scene.Scene` ([renderer](renderer.md#scenes-camera-paths-and-flythroughs)), so it may also give each mesh a name, the content hash its bytes must have, an overlay hash and a fit, place instances on a terrain with a yaw, scatter them from a seed, and carry the procedural terrain itself; an unknown field is refused with its path. The meshes load exactly as `--mesh` loads one, cache and all, and then go into one set of buffers through `geometry::merge_cluster_meshes`, each keeping its own 16-bit position grid; each mesh's materials follow the last mesh's in one table and each instance's `material_base` points at its mesh's, so the clusters keep mesh-local material indices. `--grid-instances <n>` is the same machinery from one flag: n × n copies of the loaded mesh on a grid three mesh radii apart, with a rotation and a scale that vary per copy and a non-uniform scale on every third, so one run exercises the uniform and the non-uniform path, the cone test's precondition, and the LOD scaling at once. The camera frames the scene's bounding sphere, the union of the instances' transformed mesh bounds, and `--no-cull` is ignored with more than one instance because a scene draws through the cull pass. On the RTX 5090, `--grid-instances 5` on the FlightHelmet (25 instances, 58,700 pairs) at 800×600 culls in 0.023 ms, rasterizes 201 visible pairs in 0.004 ms through mesh shaders, and through `--raster rt` builds the frame's cluster acceleration structures in 0.49 ms — most of it the 25 bottom-level builds, which share one scratch buffer and so are serialized — and traces in 0.012 ms.

**The `textures` block, and `--no-texture-sharing`.** The summary line's `textures` object is the scene's materials' textures on the device: `built` and `decoded` count **distinct** textures, `distinct` is their sum, `shared` is how many of the meshes' sampled images took a texture another mesh had already uploaded, `bytes` is what the allocator gave the textures and `bytes_saved` what the shared images' own copies would have taken, and `sharing` says which way it ran. A flythrough's summary line (`--benchmark`) carries the same block. A scene uploads one texture per distinct image content, keyed by the `.tex` build key or by the encoded bytes and format, never by the path ([renderer](renderer.md#one-upload-per-distinct-image)); `--no-texture-sharing` uploads every mesh's own copy again, which is what every build did before 2026-09-25, to measure against. On E33's ashlar kit the two are 99 textures in 1,440 MiB and 6 in 80 MiB, and the same picture to the byte.

**`--procedural shredded-atlas`, and the four flags that say what the LOD builder is told.** With no `--mesh` and no `--scene`, engine-view draws a procedural scene, and there are now two: the dunes-and-ridges `heightfield` (the default, unchanged) and `shredded-atlas`, the UV-atlas stress fixture of [geometry](geometry.md#the-shredded-atlas) — a torus cut into hundreds of small atlas islands with a probe texture whose colour encodes atlas position. It exists because a LOD collapse that crosses an island edge is invisible on any mesh whose atlas is a few large islands, which is every Khronos sample, and obvious on this one. `--uv-seams`, `--normal-seams`, `--uv-weight` and `--normal-weight` are what the builder is told about seams and attributes; **all four are part of `geometry::cluster_cache_key`**, so `--uv-seams none` builds and addresses its own container and `engine-content build --uv-seams none` writes exactly that one. That is what makes a before-and-after comparison of the seam rule two command lines instead of two builds of the tree, and it is how the numbers in [geometry](geometry.md#what-the-simplifier-is-given-and-why) were taken.

**`--views single|surround3|panini`** and its three knobs are the multi-view layout ([04 §4.6](../plan/04-renderer.md#46-extreme-displays), [renderer](renderer.md#multi-view-a-viewset-over-one-scene), experiment [E9](../experiments/e9-multi-view.md)). `single` is the default and is unchanged in every respect, down to the bytes of the picture. `surround3` divides the target into three monitors with per-monitor off-axis frusta, which is what the project owner's 11520×2160 actually is; `--side-yaw <deg>` is the angle the side monitors are physically turned inward, 0 being a flat arrangement whose three frusta are exactly the three thirds of one wide rectilinear frustum. `panini` renders one wide view rectilinear into an oversampled source and resamples it with a Panini projection of parameter `--panini-d` (0 is the ordinary rectilinear picture, 1 the classic Pannini); the summary reports the `oversample` factor the source needed. `--peripheral-lod <mult>` multiplies the LOD pixel threshold outside the attention region, which for a surround is the two side monitors — a surround player reads them peripherally, so a coarser cut there is the expected behavior and not a compromise. The monitor width, height and bezel gap are parameters of the layout too, but of the module's `Surround3` rather than of a flag: a flag would only be able to say what the target already says, since the rectangles have to tile the swapchain.

The JSON summary gains a `views` block — the layout, the count, the yaw, the Panini `d` and oversample, and a `per_view` array with each view's rectangle, tier and GPU milliseconds by pass beside the totals — and an `rt_bytes` figure for what the acceleration structure chain holds. It used to be the number that grew with the view count; since 2026-09-24 it grows with what the frames build.

**`--rt-budget-mib <n>`** is the most device memory the per-frame cluster acceleration structures may take (default: the `renderer.rt.budget_mib` tunable, 1024). The structures are sized by what the frames build, a step above it, and resized when the demand crosses a threshold ([renderer](renderer.md#the-ray-tracing-chains-memory)); the budget is only the ceiling. A frame that wants more than it holds keeps whole instances' structures in instance order, every instance's drawn clusters before any shadow caster, so the casters are the first to go; it logs that once and counts it. The summary line gains an `rt` block — `capacity` and `peak_capacity` (clusters), `limit` (the budget in clusters), `union_clusters` (what a scene-sized chain would hold, `views * pairs`), `bytes` and `peak_bytes`, `built_last`, `wanted_last` and `peak_wanted`, `grows`, `shrinks`, `overflow_frames`, `dropped_instances` and `dropped_caster_instances` — and `rt_bytes` becomes the run's last figure rather than the load's. A flythrough's `.jsonl` carries `rt_built`, `rt_wanted` and `rt_capacity` on every frame and the summary's `rt` block the same totals with the per-frame percentiles of `built` and `wanted`. **A capture at 11520×2160 belongs to engine-host, not here**: engine-view sizes its swapchain from a real window, so the offscreen path (`render.capture`, `render.benchmark`) is what renders a surround-sized frame on a machine whose display is smaller, and it is what experiment E9's numbers were taken through.

**`--time-rate <r>`** runs a dune terrain's game time at `r` game seconds per real second and moves the sand on screen: [below](#--time-rate-the-dunes-in-time-lapse). **`--terrain-rings`** draws the same terrain's ground near the camera at the terrain rings' finer grids beside the scene's own, rebuilt round the camera as it moves: [below](#--time-rate-the-dunes-in-time-lapse) too.

**`--sun <azimuth,elevation>`** puts the stand-in sun where it is asked, in degrees: the azimuth in the ground plane from +x towards +z, the elevation above the horizon (−90 to 90). Without it the sun stands where the `renderer.sun.azimuth_deg` and `renderer.sun.elevation_deg` tunables put it, whose defaults (48.37, 53.03) are the direction every frame has always had, to the bit. **Nothing in the lighting moves with the frame by default** (2026-09-27): the two point lights used to orbit the scene with the frame index, a warm one a scene's radius away going round in eight seconds, and over a time-lapse of the erg that read as a sun racing across the sky ([renderer](renderer.md#the-dunes-in-time-lapse)). They now stand where frame 0 put them; **`--orbit-lights`** brings the orbit back, for a picture that wants a highlight swept across a surface. Over the protocol they are `RenderSettings`' `sun_azimuth_deg`, `sun_elevation_deg` (both or neither) and `orbit_lights` (version 9).

**`--sun-rate <r>`** runs **the sun's day** at `r` game seconds per real second (0 to 10⁷; without it the `renderer.sun.rate` tunable, 0, a still sun), starting from `--sun`: the sun turns once a game day round the celestial pole on the circle through its start, the pole `renderer.sun.arc_tilt_deg` (40, a mid-latitude) above the northern (−z) horizon, westward — the default start is an April mid-morning that culminates due south at 60° and sets a little north of west 13 hours on — and below the horizon it fades to nothing over 6° of twilight; its colour, the sky and the point lights stay as they are ([renderer](renderer.md#the-suns-day) has the model and why). **A rate of zero draws exactly what the sun drew before it had a day, to the bit.** The day is independent of the sand's `--time-rate`, so the sand can move under a still sun and the sun over still sand. A frame is a sixtieth of a second of the day's clock offscreen and in a plain window, so frame f of `--frames` stands `r · f / 60` game seconds into it and two runs light the same frames alike; an `--interactive` session's day runs on its ticks, and `[` and `]` step its rate ([below](#--interactive-a-camera-somebody-flies)). The summary line gains a **`sun`** block: `rate` (at the end), `start_rate`, `rate_changes` (the keys'), `time_s` (how far into the day the last frame was), `start_azimuth_deg`, `start_elevation_deg`, `tilt_deg`, and where it ended — `azimuth_deg`, `elevation_deg`, `direction` — and its `intensity`; a flythrough's and a session's `--benchmark` summary carries the same block (`FlythroughSummary` version 9). Over the protocol there is no day yet: `render.*` draws every frame at the start.

**`--capture-every <n>`**, offscreen with `--capture`, also writes every n-th frame of a plain run as `<capture stem>-<frame>.png` (and the channels `--capture-channels` names beside it), each drawn *at* that frame — its camera and, under `--time-rate`, the sand as it stood then — where `--capture` alone draws the last frame again after the run. It is how a time-lapse is looked at without a window: `--frames 30 --capture out.png --capture-every 10` writes frames 9, 19 and 29.

**`--view detail`** (2026-09-29) draws a terrain's sand detail — the wind ripples and grain a scene's `terrain.detail` block asks for ([renderer](renderer.md#the-sand-close-up)) — as data rather than colour: R is the ripple height over its amplitude and B the grain's coarse octave, each a function of the point's world (x, z) alone mapped from [−1, 1], and G the share of the ripples the pixel draws (the sand share, times the fade by the ground's slope, times the fade by its footprint); anything that is not the detail's material is black. It is how the seams across the terrain rings were tested, and how to see where the ripples stop being drawn. `render.load`'s `view` takes `detail` too, and `albedo` and `occlusion`, which its schema comment now lists.

**`--reference <spp>`** renders the reference path tracer instead of the real-time frame ([04 §4.8](../plan/04-renderer.md#48-reference-renderer-and-objective-optimization), [renderer](renderer.md#reference-renderer)) — **and opens no window**. A converged picture is minutes of compute with nothing to watch, the machines that will run the nightly comparison have no display, and `systems/renderer` has never needed one, so this path creates the device without the presentation extensions and goes straight to the offscreen contract: load the scene, draw one frame so the frame's acceleration structures exist, then `spp` samples per pixel in batches of `--spp-batch` (default 8) against those structures, then `--capture out.png` and one JSON line. `--bounces <n>` is the number of scattering events after the primary hit (default 3; 1 is direct lighting plus one bounce, which is what the resolve approximates). `--finest` builds the structures from the finest clusters instead of from the frame's LOD cut, so the picture is a reference for the source geometry rather than for the geometry LOD chose. Progress goes to stderr, one line per batch, because stdout is the summary. It needs a device with cluster acceleration structures and ray queries and settings that build them — the default `--shadows auto` does on such a device — and exits 3 with a message where it cannot, exactly as the windowed path does. **`--animate` works under it**, and draws one pose: the offscreen path runs the same `prepare_animation` → `load_scene` → `attach_instances` → one tick the windowed path runs, so the picture is the pose the windowed path's *first* frame would draw and the summary carries `skinned_instances`. It cannot play a clip — one frame is one frame — so `--frames` is ignored and a caller who passed one is told on stderr. Measured on the Fox at 320×240 and 64 samples: the posed reference is 0.0275 FLIP from the posed real-time frame and 0.0675 from a reference of the same scene at rest. The summary line is its own shape, `{"reference":true, "spp", "bounces", "finest", "width", "height", "seconds", "trace_ms", "samples", "visible_pairs", "clusters", "leaf_clusters", "triangles", "instances", "gpu_memory", "machine_state", "captured"}`, where `trace_ms` is the integrator's GPU milliseconds and `seconds` the wall time a caller waited.

engine-view --mesh content/samples/FlightHelmet/FlightHelmet.gltf --orbit 22 --width 640 --height 480 `
            --reference 512 --capture helmet.reference.png
engine-view --mesh content/samples/FlightHelmet/FlightHelmet.gltf --orbit 22 --width 640 --height 480 `
            --frames 1 --capture helmet.realtime.png
engine-image compare --json helmet.realtime.png helmet.reference.png --flip helmet.flip.png

**`--shadows off|rt`.** With `rt` every light of the resolve casts a ray-traced shadow: the sun and both point lights trace one terminate-on-first-hit ray each against the frame's own top-level structure, which holds the clusters the frame drew and, beside them, the ones its normal-cone test kept out of the picture because they face away from the camera — a cluster can face away from the camera and towards a light ([renderer](renderer.md#shadows), [gfx](gfx.md)). `--no-shadow-casters` leaves those out again, which is what every build before 2026-09-24 did, and the summary says which with `shadow_casters` and counts them in `shadow_casters_last` (and per view). `--view shadow` draws the sun's shadow alone: white lit, black blocked, grey facing away. `rt` is the default wherever the device has cluster acceleration structures and ray queries, the cascaded maps (`csm`, below) with a log line where it does not, and off in `--raster direct`, `sw`, and `auto` (the first has no resolve, and the other two split the cut across more than one visible list). **Asked for explicitly on a device that cannot trace, it exits 3**, like `--raster rt`, with the sentence the adapter's verdict carries — on the Pascal server, "NVIDIA TITAN Xp cannot trace rays: no VK_KHR_ray_query and no VK_NV_cluster_acceleration_structure: …" — rather than drawing the frame without the shadows somebody asked for; it used to warn and draw. The same flag on a path that builds no structures stays a warning, since that is a settings conflict on a device that can. **A scene too large for the device's cluster geometry indices is never refused either** (2026-09-25): the chain names a cluster by its visible entry, whose range is the scene's pairs times the views (three times that with casters), and past the device's limit the casters go, with a warning, and past it without them the shadows are the cascaded maps — so the ashlar ruins' 3.7 million pairs on `--views surround3` trace their shadows without casters where they used to exit with "the driver gave no cluster acceleration structure sizes" ([renderer](renderer.md#the-ray-tracing-chains-index-space)). **In `hw` and `vertex` the frame runs the whole acceleration structure chain too** — records, ranges, emit, CLAS, one cluster bottom-level structure per instance, top-level — from the same cull output `--raster rt` builds from, which is why it also turns two-pass occlusion culling off: the structures are built from one visible list and pass 2's survivors are in a second one. `gpu_ms.rt` is that chain; there is no `gpu_ms.shadows`, because the rays are inside the resolve and a timestamp cannot separate them, so the cost is the resolve with shadows against the resolve without them. FlightHelmet 3×3 (9 instances, 94,722 triangles each, `--orbit 22` then the closer `--orbit 9`, 60 frames, `msvc-debug`, RTX 5090):

| | resolve, `off` | resolve, `rt` | `gpu_ms.rt` | frame total, `off` → `rt` |
|---|---|---|---|---|
| 800×600, orbit 22 (124 pairs, 2% of the frame covered) | 0.021 ms | 0.022 ms | 0.363 ms | 0.103 → 0.404 ms |
| 3840×2160, orbit 22 | 0.092 ms | 0.098 ms | 0.544 ms | 0.443 → 0.675 ms |
| 11520×2160, orbit 22 | 0.199 ms | 0.227 ms | 0.529 ms | 0.830 → 0.780 ms |
| 800×600, orbit 9 (356 pairs, the helmets filling the frame) | 0.012 ms | 0.025 ms | 0.352 ms | 0.082 → 0.392 ms |
| 3840×2160, orbit 9 | 0.111 ms | 0.181 ms | 0.772 ms | 0.404 → 1.004 ms |
| 11520×2160, orbit 9 | 0.230 ms | 0.399 ms | 0.921 ms | 0.965 → 1.413 ms |

So the rays cost the resolve **1.6× to 2× when the geometry fills the frame** and almost nothing when it does not — they are traced per covered pixel, and the sky returns before any of them — while the structures that make them possible cost three to nine times as much as the shading. The 11520×2160 row's total falls with shadows on only because two-pass occlusion culling turns off with them, and its Hi-Z pass is 0.58 ms at that width. What the pictures show at `--orbit 9`: 8,760 pixels of 480,000 differ between `off` and `rt` (up to 202 of 255, 13.7 on average), and they are where a helmet's shell shadows its own goggles, mask, and hose, where the hose lays a dark contact band across the wooden base, and where the leather crown darkens the top face of the stand under it. The 3×3 grid spaces the instances three mesh radii apart while the sun sits 53° up, so no helmet's shadow reaches its neighbour there; a `--scene` file with two helmets a quarter of a unit apart gets that too (25,596 pixels of 270,000 differ, and the front helmet's hose and stand darken the one behind).

**`--shadows csm`, `--shadow-cascades <n>`, `--shadow-map <texels>`, `--shadow-distance <d>`** (2026-09-24). With `csm` the sun casts through **cascaded shadow maps**: up to four cascades fit to the camera's depth slices, culled from the light by the same cull pass and drawn depth-only by the picture's own rasterizer into one D32 atlas, and filtered in the resolve by a 3×3 bilinear PCF with a receiver-plane bias ([renderer](renderer.md#cascaded-shadow-maps), [gfx](gfx.md)). The two orbiting point lights are unshadowed under it. It draws on the `hw` and `vertex` paths and **keeps two-pass occlusion culling on**, since the maps are culled from the light into runs of their own; on `direct`, `sw`, `auto` and `rt` it is a warning and no shadows. **It is the default wherever the device cannot trace** — `--shadows` unset (`auto`) is `rt` on the RTX 5090 as before and `csm` on the TITAN Xp, which drew no shadows at all until this change. `--shadow-cascades` takes 1–4 (default 4; a frame whose first cascade already holds the scene's whole bounds draws fewer, which is every orbit engine-view frames a mesh with), `--shadow-map` the texels a side per cascade (64–4096, rounded up to a power of two, default 2048), and `--shadow-distance` how far from the camera they reach (default: the far side of the scene's bounds). The summary says `"shadows":"csm"` with `shadow_cascades`, `shadow_map`, `shadow_pairs_last` (the pairs the cascades drew, summed over them), `shadow_fallback_last` (the cascades' survivors the vertex path's index budget sent to the capacity draw) and `gpu_ms.shadow` and `gpu_ms.shadow_cull` — every pass that draws the maps, and the light-view culls' share; the filtering is inside `gpu_ms.resolve`. `--view shadow` shows the maps' penumbra as grey between the rays' black and white.

The cull pass backface-culls clusters by their normal cones unless `--no-cone`. In the `hw` and `vertex` modes two-pass occlusion culling is on (`--no-occlusion` turns it off): pass 1 draws last frame's visible clusters, a Hi-Z pyramid is built from the visibility buffer, pass 2 tests the rest against it, and the pyramid is rebuilt for the next frame; the summary reports the clusters each pass drew and the Hi-Z time. The JSON summary reports cluster and level counts, DAG build time, the number of glTF primitives (`mesh_primitives`, 0 for the heightfield and 0 for a mesh that came from a container, which does not record how many primitives were merged into it), where the mesh came from (`mesh_cache`: `"miss"` built from the glTF and written to the cache, `"hit"` read from the cache, `"file"` a container named on the command line, `"none"` the heightfield or `--no-cache`), whether cone culling was on, whether shadows were traced (`shadows`: `"rt"` or `"off"`), the scene's `meshes`, `instances`, and `pairs` (the prefix sum the cull pass covers), the hardware and software visible-pair counts and their sum `visible_pairs_last` (read back one frame late from per-slot copies of the indirect arguments), GPU milliseconds per pass (cull, hw, sw, resolve) averaged over the run from timestamp queries, which is how experiment E1 was measured, and the `gpu_memory` and `machine_state` blocks the last section of this page describes. `--frames N --capture out.png` renders N frames and writes the last one as a PNG, and the process prints one JSON line of statistics (frames, seconds, average ms, size, cluster and triangle counts, whether the capture was written) to stdout, so scripts and agents look at the picture and the numbers without a human at the window. Escape or closing the window exits; resizing recreates the swapchain and the depth buffer. Shaders come from the build's manifest when it sits beside the executable (`<exe dir>/../shaders/manifest.json`, or `--shaders`), so editing `cluster_mesh.slang` while the window is open recompiles it through slangc and rebuilds the pipeline within a quarter second; a save that does not compile prints slangc's diagnostics to stderr and keeps the last good shader. `--log` with an explicit spec routes those categories to stderr at the given levels. Exit codes: 0, 1 error, 2 usage, 3 unavailable (no display, no Vulkan device, no mesh shaders, or no presentation), which the end-to-end test treats as a skip. On the RTX 5090 the default 257×257 grid (131,072 triangles, 2,898 clusters in 12 levels, 861 ms to build) draws 98 to 162 clusters per frame at a 1 px threshold and renders in about 0.65 ms per frame at 960×540 without vsync.

**`--deform none|identity|wave|lattice`, `--deform-amplitude <a>`, `--rt-templates`** (experiment [E25](../experiments/e25-deformed-clusters.md)). `--deform` makes **every instance of the scene deformed**: a compute pass (`deform.slang`) fills the frame's deformed-vertex pool for the clusters the cull pass selected, once per run of the visible list, before the draw that reads them, into blocks a second pass (`deform_alloc.slang`) suballocated from a budget for exactly those clusters. Every position reader then takes that instance's positions out of the pool — the rasterizers, the resolve, and the cluster acceleration structure records ([gfx](gfx.md)) — so the raster picture and the ray-traced one deform together. `identity` writes the rest pose, which is the mode to reach for when something looks wrong: it must draw what `--deform none` draws. `wave` displaces along the vertex normal and `lattice` runs a 3×3×3 trilinear cage over the mesh's bounds, both animated by frame number at 60 Hz and both scaled by `--deform-amplitude`, a fraction of the mesh's bounding cube (0.02 by default; 0.4 units on the 20-unit heightfield). `--no-cull` is ignored with `--deform`, because the pass walks the cull pass's visible list — that is the whole point of it. `--rt-templates` changes how `--raster rt` (or `--shadows rt`) turns the cut into ray tracing geometry: instead of rebuilding a cluster acceleration structure per visible cluster every frame, it builds one **template** per cluster of the scene at load, from the rest pose, and instantiates the cut's templates with the pool's positions each frame. **`--deform-pool-mib <n>`** is that budget, in mebibytes (8 by default), clamped down to what a block per instance's whole mesh would have taken so a small scene allocates exactly what it did before the suballocation existed. A frame's cut that does not fit is not an error: the (instance, cluster) pairs that missed out draw their **rest pose**, the renderer says so once in the log, and the summary counts them. The JSON summary gains `deform`, `deform_pool_bytes` (the budget), `deform_whole_mesh_bytes` (what the E25 layout would have allocated), `deform_pool_used_bytes` and `deform_pool_peak_bytes` (what the cut actually took, last frame and at its peak), `deform_entries`, `deform_overflow_entries`, `deform_overflow_bytes`, `rt_templates`, `template_bytes`, and `gpu_ms.deform`, `gpu_ms.deform_alloc` and `gpu_ms.clas` (the cluster structure build or instantiation on its own, inside `gpu_ms.rt`). On the RTX 5090 at 1920×1080, `--orbit 22`, `--shadows off`: the pool pass costs 0.0096 ms for a 266-cluster cut and 0.0132 ms for a 4,363-cluster one on the `--grid 1025` heightfield (2.1M triangles), and 0.0096 / 0.0131 ms for cuts of 396 and 4,831 clusters over 64 FlightHelmets (94,722 triangles) — the same numbers for meshes 22× apart in size, which is the point of the pool. `--rt-templates` turns a 0.066–0.180 ms per-frame cluster structure rebuild into a 0.014–0.061 ms instantiation, for 537 B of template per cluster of the mesh held resident (25 MB for the heightfield's 46,626 clusters, 1.1 MB for the helmet's 2,348). One warning worth reading before using the flags in anger: `--deform wave` displaces along the vertex normal, which **tears** a model at its hard edges and LOD-group boundaries — `--deform lattice`, a function of position alone, does not. The other one used to be the pool's size (110 MB for 64 helmets, 1.7 GB had they been a thousand) and is now a budget: those 64 helmets allocate 8 MiB and their cut uses 0.8 MB of it (2026-09-18; [renderer](renderer.md#the-deformed-vertex-pool) has the table). [E25](../experiments/e25-deformed-clusters.md) has the comparison and the reason, and the command lines that reproduce both.

**`--morph <name|index>=<weight>`, `--morph-animate [clip]`, `--static-shape-kib <n>`: a character that has a shape as well as a pose.** A mesh with morph targets ([geometry](geometry.md), "Morph channels") is deformed whether or not `--deform` is given, and these three say what it plays. **With none of them it plays the asset's own weights**: glTF's `weights` on the mesh or the node are what the file is drawn with when nothing animates it, so the static stage starts from each channel's default and a mesh authored half-morphed (MorphPrimitivesTest, at 0.5) draws half-morphed. `--morph` is repeatable and overrides the **static shape** stage's weight for one channel, named the way the asset names it — glTF's `extras.targetNames`, `<mesh>.<k>` when the file names none, or the channel's index. A weight is any finite number, **zero and negatives included**: zero is how a channel the asset defaults on is turned off, and glTF allows negative weights. An unknown name is a **usage error** rather than a silently ignored weight, because a misspelt expression that quietly does nothing is the kind of thing that gets debugged in the picture instead of on the command line. Its result is cached per instance and costs nothing per frame; `--static-shape-kib` is that cache's budget (4096 by default, 16 bytes a mesh vertex), and an instance the budget had no room for runs its static stage every frame over the cut — the same picture for more work, and the summary says how many instances were cached. `--morph-animate` plays a clip's **weight tracks** through the per-frame **pose** stage on top of whatever `--morph` set; channels the clip does not name keep the asset's own default weights, because a clip writes only what it drives (with it, the defaults move from the static half to the pose half, so they are counted once). The clips come **from the mesh file itself, skin or no skin**: `--animate` is not needed and refuses a mesh with no skin, and a weights-only animation loads as a skeleton-less clip ([animation](animation.md)). The optional value names one — its name, its name after the file-stem prefix, or its index among the clips that have weight tracks — and with none the first such clip plays; a name the file does not have fails. The weights are sampled on the frame counter at 60 Hz times `--anim-speed`, so `--frames N` is the same picture every run. The JSON summary gains `morph_channels`, `morph_static_cache_bytes`, `morph_cached_instances` and `morph_clip` (the library name of the clip the pose stage played, empty when none). In a build without the animation capability `--morph-animate` is refused with the switch to turn on, exactly as `--animate` is; `--morph` needs nothing. Two things are worth knowing before reaching for them: a morphed mesh is **not streamed** — `--stream` is refused with a logged reason, since the delta stream's per-cluster directory would need patching per page the way the cluster offsets are ([renderer](renderer.md)) — and a morphed scene is the only one that carries a deformed **normal** pool, which is what keeps a morphing surface smoothly shaded instead of faceted ([gfx](gfx.md), "What happens to the shading normal").

**`--animate [clip]` and `--anim-speed <x>`: a character that moves.** The first command line that joins the three halves this engine already had — glTF skins and clips through [assets](assets.md), the tick through [animation](animation.md), and the deformed-vertex pool's skinning mode through [gfx](gfx.md). `--animate` reads the mesh file's skins and animations into an `animation::Library`, makes every instance of that mesh skinned, gives each one an entity with an `AnimationPlayer`, and steps a `ecs::SimWorld` once per frame at its fixed 60 Hz. The optional value names the clip by name (`--animate Run`, matched against the library name or its part after the prefix) or by index among that skin's clips; with none, the first one plays. `--anim-speed` multiplies every instance's rate. With `--grid-instances n` every one of the n × n copies is skinned and gets a **phase offset of its own** — `duration * i / count` — so a crowd is not n² clones of one frame; a scene file says the same thing per instance in an optional `"animation"` block, `{"clip":"Run","speed":1.5,"phase":0.4}`, every field optional.

**It needs a glTF, and it needs the capability.** A `.clusters` container carries the per-vertex binding stream but neither a skeleton nor a curve, so `--animate` names the source file; the derived-data cache still serves the geometry, so the second run is as fast as any other. `--animate` on the heightfield, or on a mesh with no skin, is refused with a sentence rather than drawn standing still. And in a build without the animation capability — `ENGINE_WITH_ANIMATION=OFF`, `ENGINE_WITH_ECS=OFF`, or either minimal preset — the whole of the glue compiles away and the flag is refused with a message naming the switch (exit 2, checked in the end-to-end suite and by building `msvc-minimal`). That is [ADR-0027](../adr/0027-additive-capabilities.md)'s removal proof reaching an app: engine-view links the capability when this configuration has it, and is a viewer with no `--animate` when it does not.

**Deterministic by construction.** `ecs::SimWorld::step` reads no clock, so `--frames N` advances the world exactly N steps and two runs of the same command line produce **byte-identical PNGs**; the end-to-end suite checks that, and checks that `--anim-speed 4` produces a different one. The summary gains `skinned_instances`, `joints` (the length of the bone-matrix span the frame uploaded), and `clip`; `gpu_ms.deform` was already there and is now non-zero without `--deform`, because skinning is one of the pool pass's kinds rather than a pass beside it.

**`--anim-lod on|off` and `--anim-lod-scale <x>`: the camera decides what each character is worth.** On by default. Every frame, before the tick, engine-view builds a `sim::ObserverSet` from the renderer's own views — one observer per view, the side monitors of a surround weighted below the centre by `--peripheral-lod` — tests each animated instance's padded bounds against this frame's frusta, runs `sim::TierAssignment` over the result, and hands the accepted changes to the animation capability, which releases a pose slot on demotion and advances the playhead analytically on promotion. `--anim-lod off` is what every build before 2026-09-18 did: every instance at LOD0 for ever, which is the baseline the policy is measured against. `--anim-lod-scale` multiplies the capability's band boundaries (`animation.lod.near/mid/far`, 12/40/120 m of observer score): **the bands are metres and a sample asset's units may not be** — the Khronos Fox has a bounding radius of 82 in its own units, so a crowd of them at `--orbit 22` is thousands of units away and lands entirely at LOD3 with the default scale. The summary gains an `anim` block: `{"on":true,"scale":1,"instances":1024,"tiers":[0,0,0,1024],"promotions":0,"demotions":1024,"deferred":0,"ms":{"tick":0.064,"lod":0.038}}` — the tier histogram at the last frame and the CPU milliseconds a frame of the world's step and of the assignment in front of it. [animation](animation.md#the-app-side-lod-glue-what-the-camera-decides) has the pattern a game copies, the full table by tier mix (1.7× at LOD1, 6.1× at LOD2, 52× frozen, against 3.3 ms with the flag off) and what a tier change costs the picture (0.0011 / 0.0097 / 0.0000 FLIP mean at the three boundaries, against the 0.1 FLIP calls the threshold of noticing).

`gpu_memory.used_mib` was 420–421 MiB in every one of those runs, animated or not; with `--shadows rt` it is 583 at one instance and 783 at 1,024, which is the acceleration structure chain and not the skinning. **Machine state:** the box was shared throughout — other processes at 10–43% of the CPU and the GPU between 1% and 53% busy at the ends of the runs, 3.9–4.3 GB of the card held by other tenants — so every figure here is an **upper bound**, not a cost ([bench](bench.md#measuring-on-a-shared-machine)).

Four things they say.

1. **The pool pass costs the cut**, which is E25's whole claim, and skinning does not change it: 1,325 visible clusters over 1,024 characters deform in 0.139 ms, against E25's prediction of 9.4 µs plus 0.9 µs per 1,000 visible clusters — 10.6 µs predicted against 139 measured. The gap is not the cluster count, it is the *instances*: the pass is one workgroup per visible entry and a skinned workgroup reads a binding and four 48-byte matrices per vertex where a `lattice` one reads nothing but the position, and 1,024 entries spread over 1,024 different matrix arrays is a scattered read where a single deformed mesh's is not. At one instance the same pass is 0.0115 ms for 8 clusters, which is the fixed cost E25 measured.
2. **The frame is not where a crowd gets expensive; the tick is.** At 1,024 characters the GPU frame is 0.46 ms and the CPU frame goes from 0.5 ms to 3.6 ms. That 3.1 ms is the animation tick plus the upload, and it lines up with [animation](animation.md)'s bench to within a tenth: 1,024 instances × 2.53 µs at LOD0 is 2.6 ms, and the rest is the memcpy and the per-instance `joint_run`. ~~**engine-view attaches everything at LOD0 and never demotes**~~ — **closed, 2026-09-18**: `--anim-lod` is on by default and the same crowd's tick is **0.056–0.072 ms** at the default bands, 0.53–0.56 ms at an all-LOD2 mix and 1.92–1.94 ms at an all-LOD1 one, against 3.29–3.37 ms with the flag off. The row above is `--anim-lod off`.
3. **The upload is what the 3×4 matrix was chosen for.** 1.18 MB a frame for a thousand characters, one memcpy, 71 MB/s at 60 Hz. The fourth row would have made it 1.57 MB.
4. ~~**The pool is the memory problem, and it is E25's known one.** 12.2 MB for 1,024 foxes, because a deformed instance gets a block as long as its mesh's *whole* cluster-ordered vertex range whether or not the cut touches it. A fox is 995 vertices; a thousand FlightHelmets would be 1.7 GB.~~ **Closed, 2026-09-18.** The pool is a budget suballocated per frame from the visible list, one block per (instance, cluster) pair (`--deform-pool-mib`, [renderer](renderer.md#the-deformed-vertex-pool)). The `Pool` column above is what the *old* layout allocated; the new one allocates 11,940 B, 1,194,000 B and 8,388,600 B for the three rows, and those 1,024 foxes' cut occupies **597,240 B** of the last. A thousand FlightHelmets would allocate the same 8 MiB the foxes do.

**Ray tracing a moving crowd** (`--grid-instances 3`, 800×600, 41 visible pairs). `--raster rt` traces the deformed geometry: 0.245 ms of structure chain, 0.012 ms of rays, and a picture that differs from the mesh-shader path by PSNR 63.2 / SSIM 0.99995 — silhouettes, the same disagreement a rigid mesh gets. `--rt-templates` instantiates the cut's templates from the pool instead of rebuilding: the chain falls to 0.186 ms and its CLAS build from 0.0567 to 0.0143 ms (4.0×) for 7,712 bytes of template, and the picture is **byte-identical** to the rebuild's (PSNR null, SSIM 1, FLIP 0). `--shadows rt` on the same crowd changes the picture by PSNR 51.8: each fox shadows itself as it walks.

The content build on the command line (docs/plan/07-content-pipeline.md §7.3): the step between a source mesh and what the renderer loads. `build` imports the file with `assets::load_gltf`, welds its vertices unless `--no-weld` (exporters duplicate freely, and without welding the 64-vertex cluster limit starves both the clusters and the LOD builder; **every per-vertex stream is part of the weld key** — a skinned source's bindings, a morphed source's deltas and every vertex's canonical id as well as its normals and UVs — so two coincident vertices that disagree about any of them stay two vertices and the morph channels are renumbered with the vertices, through `assets::weld_vertices`, which `engine-view --mesh` calls too because the two share cache entries — [assets](assets.md#the-weld), and [geometry](geometry.md), "Skinned meshes" and "Morph channels", for the two releases in which a stream was left out), builds one cluster LOD DAG per glTF primitive with the file's normals and UVs so that every cluster has exactly one material — one job per primitive on the job system's performance pool — merges them (`geometry::merge_cluster_lod`) in primitive index order, maps each merged cluster to its primitive's material (a primitive that names none gets one appended default), converts the metallic-roughness materials into the file's 64-byte records — base color, metallic and roughness, the base-color, metallic-roughness, normal, occlusion, and emissive image slots, the emissive factor, the normal scale, and the packed alpha mode, cutoff, and double-sidedness ([geometry](geometry.md)) — carries the image paths over as the glTF gave them (an embedded image keeps its slot with an empty path and its **encoded bytes travel in the container**, deduplicated by content hash, so the container draws what the source draws wherever it ends up — [geometry](geometry.md), "Embedded images") together with the source path the paths are relative to and the source's identity — its content hash and the build key over that hash and the options, which is what lets a later build recognize the container as the answer to the same question — and writes the `.clusters` container described in [geometry](geometry.md). `--max-triangles` (4..256) and `--max-vertices` (1..255) are the per-cluster limits, 124 and 64 by default. `--uv-seams`, `--normal-seams`, `--uv-weight` and `--normal-weight` are what the LOD simplifier is told about attribute discontinuities and attribute error ([geometry](geometry.md#what-the-simplifier-is-given-and-why)); the weights are in thousandths, so `--uv-weight 500` is 0.5. **All four are part of the cache key**, as the per-cluster limits are, so a container built with `--uv-seams none` is a different entry from the default one and `engine-view --uv-seams none` finds exactly it — which is what makes "what does the seam rule cost this model?" a pair of command lines rather than a pair of builds of the engine. `--no-morph` is the same idea for the morph stream: it drops the source's morph targets before anything else sees them, so the container is what the file would build to with no channels — welded without the deltas in the key, simplified without `morph_seams`, the seven morph sections empty — and it moves the recorded build key (`morph_key` in `main.cpp`), so such a container is never taken by `build-all` for the answer to a build that wanted the channels. What it measured on the Khronos morph samples is below, in "The morph samples, end to end". `--cache` replaces the output file with the derived-data cache entry this source and these options address — `<ddc>/clusters/<hash>.clusters`, the path `engine-view --mesh` looks in before it builds anything — and the summary's `path` says where it went; an output file and `--cache` together are a usage error, since one build has one destination. `--ddc <dir>` names the cache root, which is otherwise `<repo>/ddc`, found by walking up from the executable to the directory holding `AGENTS.md`. `info` reads a container back and prints its header, every section record with its kind and name — including a section this build does not know, since it reads the table straight from the bytes — and the counts. Each section record also carries `hash`, `core/hash`'s `hash_bytes` over that section's payload, so two containers built from one source can be compared **section by section** — which is how a divergence is placed (the geometry, or only the source path, which the header's own `hash` covers and which differs between two machines that built from two directories) and how the determinism test reads a build ([geometry](geometry.md#the-same-bytes-from-every-toolchain)). Every command prints JSON lines on stdout and nothing else (`build`: `path`, `cached`, `source_hash`, `build_key`, `clusters`, `leaf_clusters`, `triangles`, `lod_levels`, `vertices` (cluster-ordered, so duplicated per cluster and per level), `materials`, `images`, `embedded_images` (how many of them the container carries the bytes of), `deduplicated_images` (how many of those were served by an earlier image's identical bytes), `image_bytes` (what the distinct ones take), `vertex_id_source` (`authored` when the source carried `_CANONICAL_ID`, `position_weld` when the build derived the ids — [assets](assets.md#canonical-vertex-ids)), `warnings`, `bytes`, `build_ms`, `hash`; `build-all` adds the same three to a built line; `info` adds `source_path`, the three image counts, `morph_channels`/`morph_deltas`, and `vertex_ids` (how many — one per cluster vertex, or 0) with `vertex_id_source`, while its section list shows the ids as kind 30 `vertex_ids` and kind 31 `vertex_id_scalars`; `stats` adds `image_detail`, which is the three counts plus one entry per slot with its path, its carried bytes, and its media type — the per-slot answer to "is this container drawable on its own?" — and, for a mesh with morph targets, `morph`: the channel and delta totals, whether the stream carries normal deltas, the bytes it costs and the bytes per cluster vertex, and one `detail` entry per channel with its name, how many deltas it holds, the **fraction of the mesh's cluster vertices it touches**, its largest displacement, its quantization step and its default weight. Those two are the numbers that say whether the sparse layout earned itself on a given asset: a face rig's channels touch a few percent each, and a channel that touches everything is a whole-body shape that would have been as cheap dense), so a script reads the numbers and an agent checks the hash; everything else is a log record on stderr under the `content` category. Exit codes: 0, 1 (the mesh could not be loaded, validated, clustered, or written), 2 usage.

**Clips** (with the audio capability). `build` of a WAV, FLAC or MP3 (chosen by the extension: a command line has to tell a mesh from a clip before it reads anything) runs the audio capability's **derived step** instead of the mesh build: the source decoded once, by the clip store's own decoders, into the mix format — f32, interleaved, mono or stereo, 48 kHz — and written as a `.clip` ([audio](audio.md#built-clips)), to the named output or, with `--cache`, to `<ddc>/clips/<key>.clip`, the key being `audio::clip_cache_key` over `hash_bytes` of the source's bytes — the entry a clip store with a derived-data root looks for before it decodes anything. The mesh flags do not apply. Its line: `path`, `cached`, `step` (`"audio"`), `source_hash`, `build_key`, `source_bytes`, the step's own `channels`, `frames`, `seconds`, `source_channels`, `source_rate` and `hash` (the file's content hash), then `bytes` and `build_ms`. A source the decoders refuse exits 1 with `derived.build: <source>: the decoders refused it: <status>` and writes nothing. `build-all` reads a manifest's `"clips":[{"source","output"}]` beside (or instead of) its `"meshes"` — resolved against the manifest's directory as meshes are — builds each on the performance pool after the meshes, **skips one whose output already records the same source hash and build key**, prints a line each (`source`, `path`, `step`, `status`, and a built line's counts), and adds `steps: {audio: {built, skipped, failed}}` to the summary, whose `built`/`skipped`/`failed` stay the meshes'. A failed clip fails the command as a failed mesh does. `info` of a `.clip` (told by its magic) prints `kind: "clip"`, the header, each section with its payload's hash, and `channels`, `frames`, `sample_rate`, `seconds`, `source_channels`, `source_rate`, `source_hash`, `build_key`. Without the audio capability none of this exists: a WAV given to `build` is refused as a mesh it cannot import, and a manifest's `"clips"` are not read. The step is handed to the content build through its derived-step table ([content_build](content_build.md#derived-steps)) by `clip_commands.cpp`; `tools/dev.ps1 test -Filter engine_content` runs `tests/clip_tests.cpp` where the capability is built.

**What a build is allowed to be** ([07 §7.4](../plan/07-content-pipeline.md#74-validation-rules-automatic)). `build` checks the mesh as it was imported, before welding, so a diagnostic names the primitive and triangle of the *source* file. Each rule carries a stable id, which is the machine-readable failure [§7.3](../plan/07-content-pipeline.md#73-content-build-the-derived-data-graph) asks for: `geometry.empty_primitive` (a primitive with no indices, or a count that is not a whole number of triangles), `geometry.index_range` (an index past the vertex count), `geometry.nan_position` (a coordinate that is not finite), `geometry.degenerate_triangle` (a repeated corner, or two edges exactly parallel in float arithmetic, so the triangle covers no pixel), and `geometry.cluster_budget` (more than 2^24 clusters, which is what the visibility buffer's `cluster << 8 | triangle` word can name) are errors: the first one exits 1 with `<rule>: <sentence>` on stderr and nothing is written. `geometry.uv_range` (a UV past ±16 — sixteen wraps is already past any texel density the texture pipeline can serve, but a trim sheet legitimately runs to a few, so it is not an error) and `material.missing_image` (a slot naming an image with neither bytes nor a path, or an external path that is not there, which draws untextured) are warnings: a `warn` log record each, counted in the summary's `warnings`, and `--strict` turns the first of them into the same kind of refusal. None of the seven sample models trips any of them.

**And what a build repairs instead of warning about.** One rule is neither: `geometry.uv_degenerate` is a **repair**. After validation and before the weld, every atlas island under one texel of a 4,096 atlas as stored (half-float UVs) is folded into the island beside it — its corners take that island's UV and normal at their positions, a corner the island does not reach is put on the shared edge, and a triangle that is also thinner than a step of the 16-bit position grid is dropped ([geometry](geometry.md#uv-degenerate-triangles-the-repair), which has the rule, why it is about islands rather than triangles, and what it did on E10's sixty generated props). A build that repaired something says so on a `repair:` line on stderr with the counts, and its JSON line carries `repairs`: one row per rule that fired — `rule`, `islands`, `triangles`, `refolded`, `dropped`, `unrepaired`, `corners_from_neighbours`, `corners_on_edge`, `threshold_texels_4096` — and an empty array when nothing did; `build-all` puts the same array on each entry's line. It does not count toward `warnings` and `--strict` does not refuse it, because the fault has been fixed, the same way every time, and an asset that needed it is still one the pipeline can take unattended. `engine-view --mesh <file.gltf>` runs the same repair at the same point (it logs `uv repair` at info), because the two share cache entries; that is why `k_cluster_cache_version` is 10. `stats` counts atlas islands over a position and a stored UV together, so a hard edge inside an island no longer splits it.

**And its own atlas, when asked** ([atlas](atlas.md)). `--atlas repack` puts one more step after the repair and before the weld: every textured material is re-charted, packed into one square atlas as large as its largest texture, and every image it samples is rebaked into that atlas — base colour and emissive in linear light, metallic-roughness and occlusion as data, a tangent-space normal map **converted** through object space into the new triangles' frames (`--atlas-normal-maps resample` skips that, and exists to measure the error it makes). The rebaked images replace the source's in the container as embedded PNGs with no path; nothing of the source's UV layout survives. `--atlas-proxy <n>` is the triangle count of the simplified copy the charts are cut on (2,000; `0` charts the mesh itself), `--atlas-chart-cost <n>` is xatlas's `maxCost` in thousandths, for the proxy's charts or a mesh's own (2,000, xatlas's default; on E10's ribcage 4,000 and 8,000 changed its 168 proxy charts to 177), and `--atlas-supersample <n>` bakes the atlas and every image at 1, 2 or 4 times the source's side ([atlas](atlas.md#what-it-costs-the-picture)). **`keep` is the default** and changes nothing, not even the build key: the step mixes its own options key into the recorded key only when it runs (`atlas_key` in `main.cpp`), so a repacked container is a different cache entry from the kept one, `build-all` never takes one for the other, and every container built before the flag existed is still the answer it was — which is why `k_cluster_cache_version` did not move. A `build-all` entry asks for it with `"atlas":"repack"` in its `options`, with the other atlas settings at their defaults. The build's JSON line (and each `build-all` line) carries `atlas`: `{"mode":"keep"}`, or for a repack the options, `materials_repacked`/`_untextured`/`_unreadable`/`_declined`, `triangles`, `charts`, the vertex and image counts before and after, `image_bytes`, the stage times in `ms` (`decode`, `chart`, `rebake`, `encode`, `total`), a `detail` row per material (`charts`, `resolution`, `utilization`, `pack_attempts`, `proxy_triangles`, `proxy_charts`, `folded_triangles`, `unatlased_triangles`, `crumb_charts` and `crumb_triangles` ([atlas](atlas.md) rules 7 and 8), `chart_ms`, `pack_ms`) and an `images` row per rebaked image with its `space`, `size` and **`rebake_error`** — how far the new image read through the new UVs is from the old read through the old, sampled on the surface, in 8-bit steps for colour and degrees for a normal map — and `notes`, one sentence per material it left alone and why; the same goes to stderr on an `atlas: repack:` line. A material the step could not carry across (an image that does not decode) or whose new charts would fold more than 5% of it keeps its own atlas and is a note, not a failure; `atlas.repack` is the rule id of the step failing outright, which exits 1 like any other.

**Many meshes, once each** ([07 §7.3](../plan/07-content-pipeline.md#73-content-build-the-derived-data-graph): incremental and parallel builds). `build-all <manifest.json>` takes `{"meshes":[{"source":"a.gltf","output":"a.clusters","options":{"max_triangles":124,"max_vertices":64,"weld":true}}]}`; `source` is required, `output` and `options` are not, and both paths are resolved against the manifest file's own directory so a manifest is movable as a unit. An entry with no `output` needs `--cache` and goes to the entry the cache addresses; without `--cache` it is an error before anything is built. Each entry is one job on the performance pool. A job hashes the source (`assets::source_mesh_hash`), computes the build key (`geometry::cluster_cache_key` over that hash, the options, and `k_cluster_cache_version`), and **skips the entry when the container already at the output records that same source hash and that same key** — which is what the `source_hash` section of the container is for, and why a container that records none (an older build, or one `engine-view` wrote) is rebuilt rather than trusted. It prints one JSON line per mesh, in manifest order rather than completion order, with `status` `built`, `skipped`, or `failed` (plus `rule` and `error`), then `{"built","skipped","failed","seconds"}`; a failed entry does not stop the others, and the run exits 1 if any failed.

**The texture step** ([texture](texture.md), [ADR-0036](../adr/0036-built-textures-in-the-engines-own-container.md)). Every image a material samples is a derived node of its own: `build` records, per image, the build options its slots ask for (`texture::options_for_roles`: base colour and emissive BC7 sRGB, normal BC5, metallic-roughness BC7 linear, occlusion alone BC4) and, for an image the container carries, the key — section 32 of the container — and then, **when the build has a derived-data root to put textures in** (`--cache`, or `--ddc` named outright), builds each into `<ddc>/textures/<key>.tex`. A named output with neither writes the container and touches nothing else, which is what every build did before and what every test that builds into its own scratch directory relies on; `--no-textures` skips the step on purpose. The step reads each image (the container's carried bytes, or the file beside the source as it is now), hashes it, takes the key over the hash and the options, and decides from the recorded identity — never from a timestamp — whether the entry is `skipped` (already built from those bytes with those options), `shared` (a key an earlier slot or mesh of this step already had), or to be built; the builds run one job per texture on the performance pool, each spreading its mip and block rows over the same pool, and the results are reported in image order whatever order they finished in. `build`'s JSON line gains `"textures":{"enabled","built","skipped","shared","missing","failed","unreadable","bytes","source_bytes","build_ms","detail":[...]}`, one detail row per texture with its image, status, path, key, format, colour space, size, levels, bytes, PSNR and worst error of level 0 against its source, and the decode, mip, encode and total milliseconds; a missing image file is the validation warning `material.missing_image` again, an image the decoder cannot read or the builder cannot take (a WebP source, a side past 16,384) is the warning `texture.unreadable` — the mesh still builds, and the image draws as it did before — and a texture that cannot be written is `texture.build` on stderr and exit 1. `build-all` runs the same step once every container is settled, in manifest order then image order, **including for a mesh whose container was up to date** — a texture's entry can be missing while its container is current (a cache that lost it, a container engine-view wrote) and a repainted image file changes a texture's key without changing the container's — with a per-mesh `textures` object on each line and the step's rows on the summary line. `texture <in> <out.tex>` builds one image with the options given on the command line: `--format auto` (the default: BC5 for `--normal`, BC4 for a one-channel `--linear` image, BC7 otherwise) or an explicit format, `--srgb` (the default) or `--linear`, `--normal` (implies `--linear`; `--normal --srgb` is a usage error, as are BC4 and BC5 with `--srgb`), `--no-mips`, `--wrap <across>[,<down>]` (`clamp`, the default, `repeat` or `mirror`: what the mip filter reads past the image's edges, which should be what the sampler it will be read through wraps with — `build` takes it from the glTF's samplers, [texture](texture.md#the-mip-chain)); `--cache` writes the entry its bytes and options address instead of a named output. Its JSON line has the source's size, channels and identity, the format, colour space, flags, size, levels, block and file bytes, PSNR and worst error, the milliseconds per stage and the worker count. `info` on a `.tex` (told from a container by its magic, not its name) prints `"kind":"texture"`, the header, every section with its payload hash, the format, colour space, flags, size, the source's channels, each level's size and bytes, and the identity; `info` on a container gains `"textures"`, one row per image with a texture (roles, format, colour space, normal map, mips, `edge_x` and `edge_y`, key, source hash), and lists section 33, `material_sampling` — how each material's slots sample their images ([geometry](geometry.md#how-a-material-samples-its-images)) — among its sections. Measured on the FlightHelmet in [texture](texture.md#what-it-measured). On the other side, `engine-view` and engine-host run the same texture step themselves whenever they read or fill the derived-data cache, so a mesh they cluster on a cold cache has its textures built too ([renderer](renderer.md#built-textures)), and `engine-view`'s JSON summary says what the renderer did with them: `"textures":{"built":n,"decoded":m,"bytes":b}`, the images uploaded from built textures and from decoded sources and what the allocator gave them all ([renderer](renderer.md#built-textures)), and `--view albedo` shows the textured base colour unlit. **`--view occlusion`** (2026-09-24) shows the material's ambient occlusion — `1 + strength · (r − 1)` from its occlusion map, 1 where it has none — as grey and unencoded, so a captured byte is the occlusion times 255: the one factor the resolve puts on its indirect term and nowhere else ([texture](texture.md#occlusion)). The protocol takes the same name in `render.load`'s `"view"`.

**Threads, and why the bytes do not depend on them.** `--jobs <n>` sizes the performance pool ([jobs](jobs.md)); absent, it is one worker per performance CPU. `build` runs the per-primitive `build_cluster_lod` calls as one job each and merges them **in primitive index order, never in completion order**, so a mesh builds the same bytes at any thread count; the tests pin that with `--jobs 1` against `--jobs 8`. `build-all` puts the parallelism one level up, one job per mesh, and builds each mesh's primitives in sequence inside it: the manifest is the coarser level and already fills the pool, and one wait per mesh keeps the helper stack shallow. A single-mesh manifest is therefore no faster than `build` on it, which is what `build` is for.

**The build is a library, and engine-host runs it too.** Everything above but the flags, the usage, the stderr lines and the shape of the JSON lines is `domain/content_build` ([content_build](content_build.md)): the rules, `build_one`, the manifest, the per-mesh tasks with the identity skip, the texture step, and the metrics `stats` prints. It moved there unchanged on 2026-09-24 so that engine-host's `content.build` ([protocol](protocol.md#the-day-one-operations)) runs the same build rather than a copy of it, and this suite — the determinism table's pinned section hashes included — passed across the move without an edit.

**stats** reports what [07 §7.3](../plan/07-content-pipeline.md#73-content-build-the-derived-data-graph) wants watched between builds, as one JSON line: `level_clusters` (clusters per DAG level) and `groups`; `triangles_per_cluster` with `min`, `median` (the upper middle, so it is a count some cluster has), `max`, `total`, and a `histogram` of one `{triangles, clusters}` entry per distinct count, ascending, whose counts add up to the cluster count; `source_vertices` (what the container records, which for a merged mesh is the whole source vertex space once per primitive), `referenced_source_vertices` (the distinct entries of `vertex_source`, which is the only denominator a ratio means anything against), `cluster_vertices`, and `vertex_duplication` between the last two; `bytes` with `total`, `header`, `section_table`, `payloads`, `padding` (what the 16-byte payload alignment costs) and one entry per section, including a section this build does not know; and `quantization` with the grid `step` and `origin`. The FlightHelmet: 2,348 clusters in 10 levels (1,102, 600, 310, 163, 85, 43, 22, 12, 8, 3), 1 to 105 triangles a cluster with a median of 86, 143,515 cluster vertices over 55,392 referenced source vertices for a duplication of 2.59, and of its 5,297,184 bytes 1,722,180 are float positions, 1,148,120 attributes, 861,092 quantized positions, 755,060 triangles, 574,060 vertex sources, 112,704 each of cluster and LOD descriptors, and 76 bytes of alignment padding.

**Two more objects, about the picture rather than the bytes.** `atlas` is how fragmented the UV atlas is — `islands` (connected components of the level-0 triangles over *source* vertex indices, which is exactly the island count because the weld keys on the UV), `source_vertices`, `seam_vertices` and `seam_fraction` (a vertex sharing a position with another that disagrees about the UV), `uv_area`, `smallest_island_texels_4096` with `smallest_island_triangles`, `median_island_texels_4096`, `largest_island_texels_4096`, and `triangles_per_island`. It is here because atlas fragmentation stopped being invisible and became a **cost**: the LOD builder may not collapse across an island edge ([geometry](geometry.md#what-the-simplifier-is-given-and-why)), so island size now sets how far a mesh can be simplified at all, and below some size no seam-respecting simplification can be right at all — the fix there is a texture-space one ([07 §7.4](../plan/07-content-pipeline.md#74-validation-rules-automatic)), and these are the numbers its validator will threshold. `lod_attribute_error` is the other half, and it answers the question a geometric error bound cannot: **how much of the texture a coarse cut moves.** One row per triangle budget (25% and 10% of the leaves), each with the `clusters` and `triangles` of the cut nearest that budget and `geometry::measure_lod_attribute_error`'s numbers — `uv_mean_texels`, `uv_p99_texels`, `uv_max_texels`, `uv_outlier_fraction` (the share over eight texels of a 4,096 atlas) and the normal angles. Both tables go to stderr for a human as well, so stdout stays one JSON line. The maximum is the number to read first: an atlas slot is a few hundred texels, so a worst sample in the thousands means a triangle is interpolating between two unrelated islands and a worst sample in the tens means it is not.

**`identity`: the canonical vertex ids** ([geometry](geometry.md#canonical-vertex-identity)). `source` (`authored`, `position_weld`, or `none` for a container built before cluster cache version 12), `ids` (one per cluster vertex) and the `bytes` they take, and over the **source vertices** — the distinct `vertex_source` entries, as `referenced_source_vertices` counts them, so a vertex two primitives share counts once per primitive: `source_vertices`; `distinct_ids`, how many points of the base the mesh names; `sharing`, the source vertices whose id another one also carries; `duplicates`, source vertices minus distinct ids among those that have one; `largest_share`, the most source vertices on one id; `without_id`, the vertices of a primitive that carried no authored id; and `ids_at_several_positions`, ids whose vertices are not all at one position — always zero for derived ids, and the first number to read on an authored base, since a point of the base is one point. With derived ids **`sharing` is the seam-duplicate count** — every vertex a UV seam, a hard edge or a skin or morph split duplicated — which makes it an atlas number in its own right: on the Fox it is exactly the atlas statistic's 262 `seam_vertices`. A line goes to stderr with the same numbers. On the Khronos skinned and morph samples (distinct ids / source vertices / sharing / duplicates): Fox 290 / 434 / 262 / 144, RiggedFigure 130 / 365 / 364 / 235 (flat-shaded, so nearly every corner is split), AnimatedMorphCube 8 / 24 / 24 / 16, MorphPrimitivesTest 25 / 30 / 10 / 5 (its two primitives share five points), MorphStressTest 1,224 / 1,528 / 568 / 304, SimpleMorph 3 / 3 / 0 / 0; the rest are in [geometry](geometry.md#canonical-vertex-identity).

Measured on the samples `tools/fetch-samples.ps1` fetches, `msvc-release` on an i9-10980XE (28 performance CPUs), `build_ms` being import, validation, clustering, and the write: `FlightHelmet/FlightHelmet.gltf` is 94,722 triangles into 2,348 clusters in 10 levels (1,102 leaves) with 6 materials and 15 images, in **171–185 ms with `--jobs 1` and 109–119 ms at the default** over three runs each — 1.5×, because the file has six primitives and the largest of them is the critical path — and the two outputs are byte-identical (same SHA-256, same content hash). `Suzanne/Suzanne.gltf` is 3,936 triangles into 88 clusters in 7 levels (42 leaves) in 21 ms; `SciFiHelmet/SciFiHelmet.gltf` 23,358 triangles into 587 clusters in 10 levels, 1,320,224 bytes in 87 ms; `Corset/Corset.glb` 18,324 triangles into 437 clusters in 76 ms; `BoomBox/BoomBox.glb` 40 ms; `Lantern/Lantern.glb` 34 ms; `Avocado/Avocado.glb` 682 triangles into 15 clusters in 33 ms, with its 3 images embedded. **The container sizes moved when the embedded images went into it** and are given in [geometry](geometry.md) ("Embedded images") rather than repeated here: a GLB's container grows by its textures (the Lantern from 360,964 to 9,690,467 bytes), and the FlightHelmet's, whose fifteen images are files beside the glTF, grows by 428 bytes to 5,299,104. `build-all --cache` over all seven takes 0.34 s cold at the default and 0.43 s with `--jobs 1` (the FlightHelmet is more than a third of the work, so the manifest-level parallelism has little to spread), and 0.04–0.07 s warm, skipping all seven. In `msvc-debug` the FlightHelmet takes 618–632 ms with `--jobs 1` and 418–470 ms at the default, and Suzanne 55 ms. `engine-view --mesh` reads exactly these containers, and writes the same mesh into the cache itself when it has to build one.

**engine-input.**
```
engine-input devices
engine-input probe [--seconds <n>] [--device <slot>] [--gamepad|--joystick] [--log <file.jsonl>] [--events <file.jsonl>]
engine-input replay <file.jsonl>
engine-input ffb --device <slot> [--spring <s>] [--damper <d>] [--constant <c>] [--seconds <n>]
engine-input rumble --device <slot> [--low <l>] [--high <h>] [--ms <n>]
```
The probe for input devices nobody on the project owns. The engine's input path has to work with wheels, pedal boxes, shifters, flight sticks, and pads on dongles, and none of them can be characterized from a machine they are not plugged into; this tool turns a device into a file that can be read, replayed, and turned into a test here.

`devices` prints one JSON line per attached gamepad and joystick — `{space, slot, name, raw_name, guid, vendor, product, axes, buttons, hats, is_gamepad}`, from `window::input_devices` (docs/subsystems/window.md), where `name` is resolved through the name table and `raw_name` is what the driver said. `probe` streams one JSON line per event to stdout as it happens — `{t_ms, kind, device, index, value}` plus `space` (`"gamepad"` or `"joystick"`, because the two slot spaces are separate) and `name` where the enum has one; a connection or disconnection has no index or value — and ends with one summary line `{events, seconds, per_device, axes_seen, buttons_seen, hats_seen}`, where `per_device` is keyed `"gamepad:0"`, `"joystick:1"`, … , every device is named with its resolved name, and `axes_seen`/`buttons_seen`/`hats_seen` count the *distinct* axes, buttons, and hats that moved. `--log` also records the events as an `input::InputLog` (docs/subsystems/input.md), converting each one into `RawEvent`s at a 60 Hz tick and turning each hat event into four digital signals, one per direction. `--events <file>` sends the event stream to a file the probe opens itself, as UTF-8 bytes with bare newlines, leaving only the summary on stdout (the file gets it too, as its last line): **do not redirect the stream with a shell instead**, because PowerShell's `>` writes UTF-16 with a byte order mark and every text tool downstream then reads the result as binary, which is how the first round of recordings came back. `replay` loads such a log with no device attached, gives every distinct signal in it an action (`joystick_axis_2`, `joystick_button_5`, `joystick_hat_0_8`; `Button` for the digital sources, `Axis` for the analog ones), replays it through an `InputState`, and prints `{file, events, first_tick, last_tick, ticks, actions, button_actions, axis_actions, presses, releases, map, state}`. A log the probe recorded carries no action map, so `replay` stamps it with the hash of the map it just built; a log that does carry one is still refused when the map differs, as `InputLog::replay` requires.

`ffb` and `rumble` are the same tool pointed the other way: output nobody here can feel. `ffb` takes a **raw joystick** slot, opens its haptics device, prints one line of `window::HapticInfo` (`{device, name, constant, spring, damper, friction, sine, axes}`), applies whichever of `--spring`, `--damper`, and `--constant` were named, holds them for `--seconds` (5 by default, 60 at most), stops them, and prints a summary saying what each effect was asked for and whether it ran. With no force named it is a report and nothing else. `rumble` takes a **gamepad** slot and runs its two motors for `--ms`, printing `{device, name, low, high, ms, rumbled}`. Both exit 3 when the slot is empty, and `ffb` also when the device has no haptics and `rumble` when the pad has no motors — which is most pads, so 3 there means "nothing happened", not "something broke". **Opening a wheel stops the driver's own centring spring**, so a wheel goes limp under `ffb` until a force is set and again once it stops; that is the device, not the tool (docs/subsystems/window.md).

SDL needs no window for joystick events, but it does need its own event pump, so the tool creates one hidden, non-Vulkan 64×64 window and drives `poll()` on it; and because SDL drops device events while a process owns windows and none holds keyboard focus, it calls `window::set_background_input(true)` so the terminal it was started from can keep focus while both of the owner's hands are on a wheel. It waits 250 ms at startup for SDL's arrival events, which is what assigns the slots. Exit codes: 0, 1 error, 2 usage, 3 unavailable (no display or no SDL video driver; for `ffb` and `rumble`, also an empty slot or a device with no forces and no motors), which the end-to-end test treats as a skip.

**Reporting a device.** Plug in one device at a time, and for each run exactly these two commands from `build/<preset>/bin/`:
```bash
engine-input devices
engine-input probe --seconds 10 --log <device>.jsonl --events <device>.events.jsonl
```
During the ten seconds, exercise everything the device has, slowly and one thing at a time so the indices are readable in the file: sweep each axis from end to end (a wheel lock to lock, each pedal fully down and back, each stick through both axes), press and release every button once in a predictable order, and push the hat to each of the four directions and back to centre. Send back `<device>.jsonl`, `<device>.events.jsonl`, and the `devices` line. That is enough to name the device's axes and buttons here and to add it to the tests; `engine-input replay <device>.jsonl` reproduces the session with nothing plugged in. With several devices attached at once, `--device <slot>` and `--gamepad`/`--joystick` narrow the stream to one of them. The logs that came back this way are committed under `content/input-logs/` and replayed by `foundation/input`'s corpus test; that directory's README says how to add one.

**Force feedback, next.** Nobody working on the engine has a wheel or a pad to feel these on, so the three force calls are plumbed and tested but unverified on hardware. Two commands answer that, on the rig that recorded `content/input-logs/t300.jsonl` and on the pad that recorded `f710.jsonl`:
```bash
engine-input ffb --device 0 --spring 0.5 --seconds 5
engine-input rumble --device 0 --low 0.5 --high 0.5 --ms 500
```
The first should make the T300's wheel resist being turned away from centre for five seconds and go limp again when it stops; check the printed `HapticInfo` against what the wheel actually did, and whether `spring_ran` was true. The second should buzz the F710 for half a second. Run `engine-input devices` first if anything else is plugged in: `ffb` counts joystick slots and `rumble` counts gamepad slots, and they are different spaces.

**engine-image.**
```
engine-image compare <a.png> <b.png> [--flip <out.png>] [--ppd <n>] [--weights center|none] [--json]
engine-image info <file.png> [--json]
engine-image --version
```
The picture comparison [04 §4.8](../plan/04-renderer.md#48-reference-renderer-and-objective-optimization) makes the gate of the optimization loop: propose, build, render the corpus, compare to the baseline, accept if it is faster and the picture did not get worse. `compare` decodes two images (PNG, JPEG, TGA, or BMP, through `image::read_image`) and prints FLIP — the perceptual metric, which is the primary number — with PSNR and SSIM beside it, all from `foundation/image/metrics.h` ([image](image.md), which says what each one is and why). `--ppd` is the viewing density the contrast-sensitivity filter is evaluated at, 67.02 by default, which is the FLIP paper's reference condition rather than any particular monitor; a denser display scores a given difference higher. `--weights center` pools the per-pixel error under a Gaussian attention region instead of evenly, which is §4.8's per-region rule and [§4.6](../plan/04-renderer.md#46-extreme-displays)'s treatment of peripheral vision: the same damage in a corner of a 48:9 frame then counts for about a fourteenth of the same damage in the middle. `--flip <out.png>` writes the per-pixel error as a heat map, which is how to see *where* two frames disagree rather than by how much.

`--json` prints one object on stdout — `{a, b, width, height, psnr, ssim, flip_mean, flip_p95, flip_max, flip_weighted_mean, ppd, weights, flip_image, ms}` — and without it the same numbers as a short readable report. `psnr` is `null` for two identical images, because the value is infinite and a large number would read like "nearly identical"; `flip_image` is `null` when no heat map was asked for; `ms` is the wall time of the metrics themselves, so a corpus run can budget for it (a 3840×2160 pair is 3.0 to 3.2 s in `msvc-release` on the dev box). `info` prints an image's size and channel count from its header alone, without decoding the pixels.

**Exit codes: 0 and 2, and deliberately no 1.** A difference is a measurement, not a failure: `compare` exits 0 whenever it produced numbers, however large they are, and it is the caller — a CI script, an agent's accept-or-reject rule — that decides which threshold means what. Everything that stopped it from measuring exits 2: a bad argument, a file that is not there or is not an image, two images of different sizes, a heat map that could not be written.

engine-image depends on `base`, `containers`, `time`, `io`, and `image` — no GPU, no window, no scene: it is two file reads and some arithmetic, so it runs on a build machine and on the headless GPU runner alike. `tools/dev.ps1 test -Filter engine_image` runs the end-to-end suite, which writes its own PNGs at test time (a flat field, the same field four levels brighter, and a checker with a 16×16 block flattened once in the middle and once in a corner) and checks: thirteen ways to get the arguments wrong and `--help`; an image against itself giving a `null` PSNR, an SSIM of 1, and a FLIP of 0; the four-level pair giving the analytic PSNR 10·log₁₀(255²/16) and a flat FLIP map whose mean is its maximum; `--ppd` reaching the filters (and a flat difference surviving any density, which is the case where it should not matter); `--flip` writing a three-channel PNG the size of the inputs and exiting 2 when the destination cannot be written; `--weights center` separating the middle of the frame from the corner by more than three times while the plain means stay within a tenth of each other, and the weighted mean equalling the mean when no weights are asked for; mismatched sizes and a file that is not an image exiting 2 with a message; `info` reading the header of a PNG and refusing junk; and `--version` printing the build stamp as one JSON line whose commit is 40 hex characters or `"unknown"`.

**Build.** `engine_app(NAME engine_host OUTPUT engine-host SOURCES ... DEPS ... [E2E_TESTS ...])` in `cmake/EngineModule.cmake` builds an executable into `build/<preset>/bin/`, records it in `modules.json` with layer `apps`, and can build an end-to-end test executable that receives the app's path as `ENGINE_APP_PATH`. **The build stamp.** Every app links `engine_build_stamp` (`cmake/EngineBuildStamp.cmake`), which says which commit it was built from: `engine::build_stamp::commit()` (40 hex characters, or `"unknown"` where there was no git to ask — the Linux container syncs the tree without `.git`) and `dirty()` (tracked files differed from it). `engine-content --version`, `engine-view --version` and `engine-image --version` print it as one JSON line, `{"tool","commit","dirty"}`, and exit 0 without touching a device. It is captured **at build time**, not at configure time, because CMake does not re-run on a commit: a commit captured at configure would name the tree as it was when the build directory was configured — days earlier in a long-lived tree — and anything trusting it would refuse every fresh binary or accept a stale one. So an always-run target asks git on every build (`rev-parse` and a `--no-optional-locks status`, which never takes `index.lock` from under a person's git command) and rewrites the two-line generated source only when the answer changed; after a build with no commit in between, Ninja recompiles and relinks nothing, and after a commit it recompiles that one file and relinks the apps in `bin/` — only apps link it, so the test and bench binaries are untouched. It exists because on 2026-09-22 the E10 harness measured with release binaries hours older than the commit it recorded ([content generation](../content-generation.md#the-e10-harness-toolse10-harnessps1), "Which binaries"); `tools/e10-harness.ps1` now refuses a binary whose stamp is behind the source it reports.

## engine-content terrain: a tile of the dune field

`terrain <scene.json> --tile <x,z>` evaluates one tile of the scene's dune field with the terrain capability's generator ([terrain](terrain.md)) and prints it as one JSON line (`engine.terrain.TileReport`): for tests, for agents deciding where to put things, and for comparing a field between builds without a GPU. The scene's `terrain` is read for the generator's description — seed, dune height and wavelength, ridges, basins, `sand_flux` — **whether or not it names the generator**, so an agent can see what the generator would make of any terrain, and `--time` (game seconds) overrides the terrain's own `time`. `--cells` is the quads a side (128: the overlay's 25 cm grid at the default 32 m `--tile-size`; the tile must be a whole number of cells), `--detail` the LOD term set (`dunes` by default; [terrain](terrain.md#lod-policy)), and `--crests` lists every crest line that crosses the tile. `--storms` lists every storm of the wind record's eight-year period (`storms`, `engine.terrain.StormReport`, report version 3): its `index` in day order — what a terrain's `storm_gains` names — its `day` in the period, `first_hour` and `hours`, `direction_deg` (where it moves the sand), `peak` (its strongest hour's wind over the record's mean), its transport `gain`, and the sand its hours move (`storm_flux_m2`, gained) beside its day's own (`day_flux_m2`); it is how a storm is found to start a scene just before it ([terrain](terrain.md#a-storm-scales-transport)). The terrain's generator fields — time, sand flux, storms, the wind's day and the storms' gains — are checked by the provider's own rule (`terrain::validate_terrain_entry`) and refused with its sentence.

The line: `format` (`engine.terrain.tile`), `tile_x`, `tile_z`, `time_s`, `tile_m`, `cells`, `detail`, `field_hash` and `tile_hash` (16 hex digits: the field's description and the tile's every height, material and normal — the number the golden tests pin for their reference field), `min_m`, `max_m`, `mean_m`, `primitives` (gathered), `sand_share` (of the vertices, the share that is not rock), the wind in the hour holding the time (`WindRecord::wind_at`, a storm's while one blows): `wind_direction`, `wind_speed_mps`, `flux_m2_per_day` (the hour's, as a daily rate) and `saltation_m2_per_day`, and since the report's version 2 `storm`, `displacement_m` (how far each band has moved since time zero: draa, crest, barchan), `crests` (with `--crests`: `band`, `kind`, five `points`, `lee`, `height_m`, `sharpness`, `celerity_m_per_day`) `eval_ms`, and since the report's version 2 two `engine.terrain.StatsReport`s ([terrain](terrain.md#what-the-numbers-say)): `tile_stats`, over the tile's own grid, and with `--stats` `region`, over a square round the tile (`--stats-side`, 4,096 m by default, at `--stats-spacing`, 8 m, on the performance pool, `--jobs`) — the height above the floor by percentile, the slope histogram and the shares over 34° and 36°, the flats, crest length per km² and primitives by band, the tallest dune, its band and that band's spacing, and a `hash` of every count. A band table the generator cannot be built from is refused naming the band. Present with the terrain capability; without it the command is refused with a sentence and exits 1. ## engine-content tissue: the tissue definition

`tissue` reads, checks and reports the engine's tissue definition ([tissue](tissue.md)); it is present when the build has the tissue capability (which needs physics), and without it — `ENGINE_WITH_TISSUE=OFF`, `ENGINE_WITH_PHYSICS=OFF`, a minimal build — the command is refused with a sentence and exit 1, as engine-view refuses `--animate` without animation. Every subcommand prints one JSON line.

- `import <interchange.json> <out.tissue>` reads the authoring side's interchange — the definition's JSON and one binary file per block — checks every block's kind, size and SHA-256, and writes the container. Exit 1 on the first thing that does not add up, with the block named.
- `info <file.tissue>` prints the header, every section (its kind, name, element size, count, offset, and whether this build knows the kind), the definition's outline, and what a read skipped.
- `validate <file>` runs every validator and prints the rows: `{"errors", "warnings", "rows": [{"id", "subject", "severity", "verdict", "threshold", "value", "witness", "note"}]}`. **Exit 1 when an error row fails**, 0 otherwise, warnings included. It reads a container or, for a path ending `.json`, an interchange directly.
- `report <file>` prints the rows and every number they stand on (`"numbers"`: by region, frame, binding and state, in millimetres and millilitres), exit 0 whenever the file reads.
- `--no-modes` skips transferring each binding under the other two normal modes, the one comparison that triples the transfers.
- `validate <file> --expect <expected.json>` is **the fixture mode** ([tissue](tissue.md#the-fixture-mode)): the file declares the rows a regression fixture is known not to pass — the authoring side's `astra.tissue.expected-failures.v1`, read as a packet publishes it: `{"format", "match", "failures": [{"id", "subject", "severity", "witness"}], ...}` — and the exit is **0 exactly when the rows that fail or are skipped are those and only those**, by id, subject and severity, whatever the error count. Otherwise 1, with each difference (a declared row that passes, a failure nobody declared, a declared value the row no longer has) as a sentence on stderr and in the line's `"expect"`. A declaration that cannot be read is exit 1 before anything is validated.
- `validate <file> --write-expect <expected.json>` writes the declaration this run would match, every failing or skipped row with its severity and witness, for review before it becomes a fixture's; exit 0. The two flags belong to `validate` and do not combine; `report` already writes its report as data and takes neither.
- `capabilities` prints what this build reads and evaluates as one JSON line ([tissue](tissue.md#capabilities-and-the-requirements-rule)): `schema_version` (the definition record's), `container_version`, every record with its version, every `Record.field`, every enumeration with its enumerators, every interchange block kind, every validator row as `evaluated`, `info-only` or `not-implemented`, the laws it evaluates by family, the kinds of requirement it reads, and the commit it was built from. It is the capability pin an authoring packet records beside the binary's hash. It takes no argument.
- **Exit 3 is a capability failure.** A file whose `requirements` (its `requires` list) name a record, field, enumerator, block kind, row or law this build does not have is refused by `import`, `info`, `validate` and `report` before anything of it is read, with a sentence naming everything missing on stderr and `{"file", "capability_failure": {"missing", "sentence"}}` as the line — never a validation result and never a row. `validate --expect` exits 3 on it too, whatever the declaration says, and refuses a declaration that names a row this build does not implement the same way before validating anything: a missing capability is never an expected physical failure.
- `example <directory>` writes the synthetic definition as `synthetic.json` with its blocks and as `synthetic.tissue`, its ten-node reference-body variant as `synthetic-quadratic.json` and `.tissue`, and the layered model's three fixtures as `layered-slab.*`, `layered-fusiform.*` and `layered-tied-slab.*`: the worked examples of the interchange an authoring tool can read field by field — the second of the `TetrahedralQuadratic` cage kind and the `Reference` role, the last three of every layered record, the two new block kinds and the requirements, and the tied slab of a `Separated` attachment with its `gap_m` ([tissue](tissue.md#two-interfaces-a-coincident-patch-and-a-separated-tie)). The line carries one entry per stem (`layered_slab`, `layered_fusiform`, `layered_tied_slab`).
- `cage <reference.tissue> <out.tissue>` **derives a runtime cage** ([tissue](tissue.md#cage-derivation)): from a `Reference` region of ten-node cells, a `Runtime` region of four-node cells within ADR-0029's budget — the cells' corner tetrahedra, then half-edge collapses, interior first — carrying the phases by volume, the node sets, the attachments, the frames and their states, and every state, and recording its source's SHA-256 (of the file's bytes), the options and the build key in the region's `derivation`. `--nodes <n>` is the budget (256 by default; past 256 only with `--hero`, which makes the cage a hero volume and lets the budget reach 800; past 800 never); `--region <name>` picks the reference region when the file has more than one; `--omit-state <name>` (repeatable) leaves a state out, which a state the cage's corners invert in needs — without it that state refuses the derivation by name. The line: the method, the source's SHA-256, the build key, the budget, the states left out, the source's nodes, cells and corners, the collapses (interior, boundary, and how far a boundary one moved the boundary), the cage (nodes, cells, boundary nodes, least SICN, ADR-0029's verdict), **the mass ledger** (the reference's mass and volume, exact and on its linear subdivision, the cage's, the difference, and the difference split into curvature, the reference outside the cage and the cage outside the reference), what was carried and what was not, and the output's bytes and SHA-256. Exit 1, with a sentence, on a file with no reference region, a budget outside ADR-0029's, a budget the collapses cannot reach, a state it cannot carry, an essential attachment, a node set with no corner node; 2 on usage. The flags are `cage`'s alone.
- `settle <cage.tissue> --state <name>` **builds a four-node `Runtime` region as the physics module's soft body and settles it** ([tissue](tissue.md#a-soft-body-from-a-runtime-region)): from its rest state, at the fixed step (60 Hz, ADR-0029's 8 iterations at 2 sub-steps; `--iterations` and `--sub-steps` change them), under the named state's load, until the 99th percentile of the nodes' speeds stays under 0.1 mm/s for half a second or `--max-steps` (3,000, 50 s simulated) runs out, and measures the settled nodes against the named state's. The line: the body (nodes, cells, edges, anchors, mass, gravity, its targets and whether each is in contact, what it did not read), the solver's settings, `settled`, `steps`, `simulated_s`, `wall_ms` and `step_us` (single-threaded), the last step's percentile speed, fastest node and its speed, how many nodes were still moving, and the percentile speed at the end of every simulated second, the cells left inverted, the strain clamp's most sweeps, the **distance distribution** (count, min, p50, p95, max, millimetres), the largest's node with its node sets and whether it is on the boundary, and the state's own displacement from the rest beside the settled one. `--repeat` settles a second time from scratch and says whether the two gave the same bytes (exit 1 if not); `--write <out.tissue>` writes the file with the settled nodes as a response state `<name>.settled`, for `validate` to read; `--region` picks the region. Exit 1 when it does not settle (the line is printed first), for a region that is not four-node cells, a state that does not exist, or an attachment the body cannot follow (a bone, another region's sheet); 2 on usage.
- `validate` and `report` take **`--source <reference.tissue>`**: a derived cage's reference file, read, hashed and handed to the `cage.*` rows ([tissue](tissue.md#how-far-the-cage-is-from-its-reference)), which measure the cage against it — the volume and mass at every carried state, the two boundaries' distance, each carried state against the reference's field, the strain-energy share. A source whose SHA-256 is not the recorded one fails `cage.source` (an error row, so exit 1). Without it the rows that need the reference's cells are skipped and say why; a file that carries both regions needs no flag.

```
engine-content tissue example scratch/tissue
engine-content tissue import scratch/tissue/synthetic.json scratch/slab.tissue
engine-content tissue validate scratch/slab.tissue
engine-content tissue report scratch/slab.tissue
engine-content tissue validate scratch/tissue/synthetic-quadratic.tissue --write-expect scratch/expected.json
engine-content tissue validate scratch/tissue/synthetic-quadratic.tissue --expect scratch/expected.json
engine-content tissue validate scratch/tissue/layered-fusiform.tissue
engine-content tissue capabilities
engine-content tissue cage scratch/tissue/synthetic-quadratic.tissue scratch/slab-cage.tissue
engine-content tissue validate scratch/slab-cage.tissue --source scratch/tissue/synthetic-quadratic.tissue
engine-content tissue cage B2a-supine.tissue B2a-cage.tissue --omit-state failed-standing-reference
engine-content tissue settle scratch/tissue/synthetic.tissue --state pressed --repeat
engine-content tissue settle B2a-cage.tissue --state B2a-supine --repeat --write B2a-settled.tissue
```

On study019's neutral data, converted once (tissue.md has the table), `validate` returns 0 errors and 3 warnings in about 10 s in `msvc-debug`. The supine fixtures' ten-node bodies validate in about 21 s, and their packet's published declaration, read by `--expect`, says what tissue.md's table does; the end-to-end test holds them to it where the machine has the packet. The layered fixtures validate clean in under a second each. ## engine-content limit-dump: the conformance exchange

`limit-dump <control.json> --level <n> --out <dump.json> [--mode <m>]` is the limit-surface conformance exchange with the authoring side ([geometry](geometry.md#the-conformance-exchange-engine-content-limit-dump)): a control mesh in — `positions`, `faces`, optionally `states`, `corners` and `footpoints` with `triangle`, `barycentric`, `normal_offset` (or `offset`), `weight` and `base_position`, the authoring side's `astra.normal_conformance.input.v1` as written — and the engine's evaluation out: the L, Tu and Tv operators (`column_count`, `row_offsets`, `column_indices`, f32 `weights`), the refined triangles, and per state the limit positions, the vertex normals under the agreed rule with `invalid_vertices` and `fallback_vertices`, and for footpoints `footpoint_normals`, `invalid_footpoints`, `fallback_footpoints`, `bound_positions` (through the 10-byte records) and `bound_positions_unquantized` (the same transfer from the input's own numbers), plus `input_conversion` (the rounding of every input number to f32) and `records` (the packing's quantization and the offsets' disagreement with the mode's normal). `--level` overrides the input's; `--mode` is `limit-interpolated` (default), `interpolated-vertex-area-weighted` or `triangle`. **`--mode` selects the footpoint normal only**: `vertex_normals`, `invalid_vertices` and `fallback_vertices` are the limit rule's in every mode, because they are what the exchange compares, and only the footpoint and transfer fields (`footpoint_normals`, the footpoint masks, both bound positions, `records`) exercise the selected mode — so the three modes' dumps of one input share their vertex fields byte for byte. Exit 2 on usage (no `--out`, a level past 4, a mode spelled any other way), 1 when the control mesh is not a surface Loop's rules take. The same input writes the same bytes. It builds in every configuration: it needs `domain/geometry` alone.

## engine-content normal-cases: the edge cases one by one

`normal-cases <cases.json> --out <results.json>` evaluates the footpoint-normal rule's edge cases through the engine's own functions and writes, per case, what the engine computed beside what the case expects ([geometry](geometry.md#the-conformance-exchange-engine-content-limit-dump), "The standalone cases"). **Why it exists beside `limit-dump`**: a surface exercises a threshold only if one of its thousands of vertices happens to sit on it, so the authoring side also publishes the rule's edge cases on their own, and the D8 comparison is complete only when both sides have answered them case by case. It reads the authoring side's `astra.normal_conformance.function_cases.v1` as written, and anything with the same fields:

- `tangents`: `u`, `v`, the `reference` normal, `valid`, `expected`. Two engine paths each: the **state path**, which is the case's verdict — a reference frame of orthogonal tangents whose limit normal is `reference`, built at a power of two near the case's own tangents so that reference plus change reproduces them, the case's tangents as the state, and `limit_normal_changes`, the reference normal plus its change exactly as `limit-dump` and the binding frame compute a state (the only path that falls back); and the **rule path**, `limit_reference_normals` on the tangents themselves (invalid is the zero vector, never invented).
- `interpolation_cancellation` (one object or an array): three corner `normals`, `barycentric`, `reference`, `valid`, `expected` — a one-triangle surface whose corners' reference normals are `reference` and whose state normals are `normals`, through `footpoint_normal` plus `footpoint_normal_change` under `limit-interpolated` (the interpolation is the same code in the area-weighted mode); the rule path is `footpoint_normal` with `normals` taken as the reference's.
- `exact_dense_face_collapse` (one object or an array): dense `positions` and `faces`, `foot_triangle`, `barycentric`, `facet_valid`, `area_weighted_normal` — the given triangles as a reference surface, never refined: the facet through `footpoint_normal` in `triangle` mode, the area-weighted vertex normals and their interpolation through `area_weighted_normal_vectors`, `area_weighted_reference_normals` and `footpoint_normal`.
- `facet_states` (the engine's addition; one object or an array): a footpoint triangle's `reference` and `state` corners, optional `barycentric` (default the centroid), `valid`, `expected` — `footpoint_normal` plus `footpoint_normal_change` in `triangle` mode, the transfer's facet code, with diagnostics (`reference_cross`, `state_cross`, `state_length_ratio`); its rule path, `footpoint_normal` on the state's corners, is counted only where a direction is expected, since a facet state's fallback is relative to its reference and a reference evaluation has none.
- `nonfinite_cases` (any value): the runner builds four tangent cases, a NaN and an infinity in u and in v, reference +z, expected the reference — as the authoring side's own harness builds them, since JSON has no number for either.

The output (`engine.normal_cases.v1`): `input` (`path`, `bytes`, `hash_bytes` — `core/hash`'s, as `limit-dump` writes — `schema`, `ignored_keys`), `engine` (the mode, `f32` arithmetic, the three thresholds, the file's `epsilon` and whether it is the engine's sine threshold — the engine's own thresholds are used whatever the file says), `tolerance`, `input_conversion` (every input number is rounded to f32 on the way in, and this is how far), `summary` (`cases`, `matches`, `mismatches`, `by_category`, `mismatched` with each case's angle, `rule_path`, `input_schema`, `input_hash_bytes`), and `cases`: per case the `input` echoed (NaN and the infinities as the strings `"NaN"`, `"Infinity"`, `"-Infinity"`, which the reader accepts back), `expected`, `engine` (`valid`, `normal`, `normal_length`, `fell_back`, the path's own fields, and `rule`), `conditioning`, `tolerance_deg`, `angle_deg` (atan2 of the cross and dot products in double, the authoring side's formula), `valid_matches` and `match`. stdout is one JSON line with the counts and the mismatched ids.

**The tolerance, and why.** A case matches when its validity is exactly the expected one, its normal is within the case's angle of the expected direction and, if valid, of unit length to 2^-18. The angle is 2^-18 rad (2.2e-4°), 64 f32 unit roundoffs: inputs rounded to f32, the rule's normalize, cross product and normalize, and a state's up to four `unit_change`s, all in f32 as the engine does them — tight enough that a disagreement about a definition shows, and 4.6 times under the 0.0010° the first surface exchange agreed footpoint normals to. **Near a threshold it widens by the rule's own conditioning**, to 2^-21 / σ where that is larger, σ being the length of the vector the normal is normalized out of (the sine between two tangents or a facet's edges, the length of an interpolation of unit normals): such a vector carries about two roundoffs a component, divided by σ, in any f32 implementation, and the tolerance allows four times that. At the file's sine of 2e-6 that is 13.7°, still far under the 90° the defect below produced; the unit-length test is what catches a normal that lost its length. **A mismatch is a finding** — about one side's rule or arithmetic, to be settled by agreeing the definition and then fixing whichever side departs, never by adjusting either to the case — so the command exits 0 whenever it read and evaluated the file, 1 only when it could not (a file that is not JSON, a case missing a field, a file that names no cases), and 2 on usage. The same input writes the same bytes.

On the authoring side's `fable-normal-conformance-2026-09-24/data/normal-function-cases.json` (2,440 bytes, SHA-256 `8b5c7774…f9f6fb`) it found one mismatch before the fix of 2026-09-24 (geometry.md, "The expansion measured a short state as no state"): `tangents[1]`, unit tangents at a sine of 2e-6, came back valid with its reference normal 90° from the expected one and no fallback, while the rule path had it right. ## engine-content ruins: a tile's ruined building as a scene fragment

`ruins` runs the ruin assembler ([ruins](ruins.md)) and writes what it made as a **scene fragment**: an `engine.scene.Scene` whose meshes are the kit's member files (by a path relative to the fragment, or absolute when there is none), whose instances are the pieces — translation and `yaw_deg` with the member's own mesh offset folded in, and a `ruin` tag each (`RuinTag`: building, wall, slot, kind, the height fraction the ruin rule asked of it) — with the buildings in `ruin_sites` and their walls' sand in `sand_drifts`. It is the derived-node form for an authored place, whose footprint and seed are the document's parameters, and `engine-view --scene <fragment>` draws it like any scene. It is present when the build has the ruins capability; without it both commands are refused with a sentence and exit 1, as `tissue` is.

- `ruins <kit.json> <world seed> <x,z>` assembles the building the seed puts on tile (x, z) — whether or not the seed's density would give that tile one; choosing tiles is `--region`'s business — on flat ground at `--ground` (the terrain is the renderer's, which the content build does not link; a scene's `ruins` entry stands on its terrain instead). `--tile-size` is the tile's edge (32 m), `--wind` where the prevailing wind blows from (degrees about +y from +x), `--walls` the capability's far tier (the same walls, no debris), `--no-write` reports without writing.
- `--region <x0,z0,x1,z1>` (the tile argument `-`) takes the tiles of that square instead: the `--count` the seed ranks first, or every tile `--density` admits (0.05, the endless desert's rule), assembled on the performance pool (`--jobs`), joined in rank order whatever the thread count.
- One JSON line: `kit`, `profile`, `seed`, `buildings`, `instances`, `drifts`, `kinds` (pieces by kind), `rubble` (`sites`: the rubble field's sites the debris heaps lie on, `pieces`, and `m3`: their volume, [ruins](ruins.md#the-rubble-rule)), `per_building` (`min`, `mean`, `max`), `shapes`, `meshes`, `ms` (the assembly alone), `threads`, `hash` (`ruins::hash_output`, 16 hex digits: the number the determinism test pins) and `output`.
- `--blocks <block-kit.json>` lays the same buildings **block by block** from a block kit (`engine.scene.RuinBlockKit`; [ruins](ruins.md#the-block-layer)) instead of the kit's sections: the kit still decides the footprint, the ruin, the openings and where the rubble lies, and the fragment's meshes are the block kit's, one instance per block, standing or fallen, each `RuinTag` carrying a `block` (role, course, fallen, eroded; a standing block's `kind` is `Section`, a fallen one's `Debris`). Its line has `block_kit`, `instances` (the blocks), `standing`, `fallen`, `eroded`, `roles` (blocks by role), `rubble` (a fallen block a site: `sites` and `pieces` are the fallen blocks, `m3` their volume — the number to set beside the same buildings' sections) and `hash` (`ruins::hash_blocks`, the second number the determinism test pins) in place of `kinds` and `shapes`.
- `ruins-kit <directory>` writes the synthetic kit of boxes ([ruins](ruins.md#the-synthetic-kit)) — `kit.json` and a GLB per member — and prints `{kit, name, members, meshes}`; `--e33-sizes` makes the boxes E33's sizes, `--inside-corner` adds an inside corner.
- `ruins-block-kit <directory>` writes the synthetic block kit ([ruins](ruins.md#the-synthetic-block-kit)) — `block-kit.json` and fourteen block GLBs — at `--fidelity low` (a chamfered box, 44 triangles, one cluster), `mid` (about 5,000 triangles) or `high` (about 50,000), and prints `{kit, name, fidelity, blocks, meshes, triangles, ms}`. `--thickness` should be the section kit's wall (0.6 m, the kit of boxes'; 0.64 m for E33's ashlar), `--course` is 0.3 m and `--stretcher` 0.6 m by default.

Exit codes: 0; 1 a kit that cannot be read or converted (the member named) or a fragment that cannot be written; 2 usage (a tile that is not `x,z`, `--count` without `--region`, no `--out` and no `--no-write`, a fidelity that is not one of the three). `-Filter engine_content` runs `tests/ruins_tests.cpp` — the kit written, one tile's fragment read back as JSON with every piece tagged and inside its tile and the mesh paths relative, the far tier removing exactly the debris, and the refusals — and the two ruins rows of `tests/determinism_tests.cpp`, which assemble 64 buildings (in sections, and laid block by block) on one thread and on three and hold each hash to the one taken on MSVC.

## Streaming pages in the content build

`engine-content build` and `build-all` lay a mesh out in fixed-size streaming pages by default ([geometry](geometry.md), [04 §4.3](../plan/04-renderer.md#43-geometry) step 3): **`--page-bytes <n>`** sets the target, 131072 by default, and **0** writes a container with no page table and leaves the clusters in the builders' order. A manifest entry may set `"page_bytes"` in its `"options"` object; the command line is the default for entries that do not. The flag is part of the derived-data cache key, because laying a mesh out in pages **renumbers its clusters**: two targets are two different containers and "no pages" is a third, so an incremental build never hands back an entry that was paged differently from what was asked for. `engine-view` lays its own cache entries out with the same default, so either program still fills the cache and either finds it.

The renumbering is also why the build pages a mesh *before* it maps clusters to materials: the permutation is applied to the map from cluster to primitive in the same step (`geometry::permute_cluster_array`), and everything downstream sees one numbering. The `build` summary gains `pages`, `page_bytes`, and `page_fill` (mean page bytes over the target); `build-all` prints the same three per entry.

`info` gains a `pages` object — `count`, `bytes_target`, `bytes`, `largest_bytes`, `mean_fill`, `oversized`, `root_pages` (the pages holding a group nothing coarser can replace, which a residency manager never evicts), and `child_page_entries`. `stats` reports all of that plus `valid` (the page table checked against the mesh it came with, with `invalid_reason` when it is not), a `child_pages_histogram` of one `{child_pages, pages}` entry per distinct count — how much of the DAG a page depends on, and so how wide a prefetch is — and a **streaming sweep**: a camera flies from 50 mesh radii to half a radius in 32 steps at 1080p and one pixel of error, and each step reports what the ideal cut needs (`clusters`, `triangles`, `pages_needed`) and what a residency manager under a quarter of the mesh's page bytes actually does (`requested`, `drawn`, `evicted`, `resident`, `resident_bytes`). The table goes to stderr so stdout stays one JSON line; the same numbers are in `pages.streaming.steps_detail`. It is a content metric, not a benchmark — it answers "does the way this mesh is paged make a fly-in cheap?" without a GPU, a window, or a frame loop.

Renumbering a mesh has to be invisible to the renderer, and it is: `engine-view --frames 3 --width 400 --height 300 --orbit 22` on the FlightHelmet gives a **byte-identical PNG** and the same 119 visible pairs from the glTF and from the paged container built from it. The one thing that does change is the *direct* draw, which has no cull pass and draws clusters 0..`leaf_count` on the assumption that the leaves come first; in a paged mesh they come last, so `--no-cull` now turns culling back on with a warning, exactly as it already does for a scene of more than one instance.

The two sample meshes, in `msvc-debug`. The **FlightHelmet** (2,348 clusters, 10 levels) is 25 pages at 91% fill, 2.85 MB of page bytes, one of them pinned, and the whole outer half of the fly-in — 50 radii down to 10, 7 to 38 clusters, 319 to 2,618 triangles — draws out of that one page with nothing requested. Streaming starts at 8.5 radii (2 pages), reaching 5 pages at 5.3, 7 at 3.7, 11 at 2.1 and 17 at half a radius, where the full cut is 960 clusters and 80,422 triangles. Under the 747 KB budget the viewer settles at 6 pages and 687 KB, draws 281 of those 960 clusters and still has 8 pages outstanding, which is what a budget a third of the working set looks like: it lags, it does not crack. **Suzanne** (88 clusters, 7 levels, 113,528 page bytes) is a single page, so its sweep requests nothing at any distance and its cut runs from 3 clusters and 245 triangles at 50 radii to all 42 leaves and 3,936 triangles from 3.7 radii in — and its budget is not honoured, because that one page holds the root and a mesh without its root draws nothing at all.

## Streaming pages at run time: `--stream`

`engine-view --stream` turns the page table the content build wrote into a **GPU residency budget** ([04 §4.9](../plan/04-renderer.md#49-streaming-and-residency), [renderer](renderer.md#geometry-streaming-the-gpu-half-of-pages-and-residency)): the device holds a subset of the scene's cluster pages, the cull pass draws whatever is resident and writes the pages it could not refine into to a feedback buffer, the CPU reads that back one frame slot later and streams them in, and the picture converges. Two more flags size it, and both imply `--stream`:

| Flag | What it sets | Over the protocol |
|---|---|---|
| `--stream` | residency on, with the whole page table as the budget: streaming with nothing to evict | `RenderSettings.stream` |
| `--page-budget <MiB>` | the residency manager's budget over the scene's page bytes | `RenderSettings.page_budget_mib`, the same unit |
| `--upload-budget <KiB>` | page payload one frame may copy into the pool; 256 KiB by default, raised to the largest page when a smaller value is given | `RenderSettings.upload_budget_kib`, the same unit |
| `--page-budget-pct <n>` | the same budget as a **percentage of this scene's page bytes**, applied after the load, because that is the only moment the page table exists to be counted. Overrides `--page-budget` | engine-view's alone: a host that wants a fraction reads `stats.stream.page_bytes` from a first call and asks for the MiB it wants |
| `--page-source auto\|file\|host` | where a page's payload comes from: `auto` reads the meshes' `.clusters` containers when **every** mesh has one and falls back to host memory otherwise, `file` refuses to run when they do not, `host` keeps the in-memory source. `stats.stream.source` says which happened | engine-view's alone today ([protocol](protocol.md) says why the host cannot release the streams a later settings change would need) |

**A budget as a percentage exists because MiB cannot say "a quarter" of a small mesh.** The FlightHelmet's pages come to 2.85 MB, so `--page-budget 1` is 35% and there is no way to ask for 25% at all; and a budget is thought about as a fraction of the working set, not as an absolute, because what makes a budget interesting is its ratio to what the cut wants. The percentage is applied to the sum of `geometry::ClusterPageDesc::bytes`, which is the same number the residency manager counts against, so 25 here and 25 in a report mean the same thing.

**Where a page's bytes come from is the difference between saving device memory and saving memory.** With `--page-source host` the payload is copied out of the loaded mesh, so the whole scene's geometry stays in the process however small the budget is. With `file` it is three ranged reads of the container (four when the frame builds acceleration structures) and the merged host streams are released once the scene is on the GPU — measured on the FlightHelmet at `--grid-instances 8` and a quarter budget, 307.5 → 303.5 MB of working set for 4.83 MB released, with the process's **peak** unchanged ([renderer](renderer.md#geometry-streaming-the-gpu-half-of-pages-and-residency) has the tables and says why the peak does not move). The summary's `streaming` block gains `source`, `file_reads`, `file_bytes`, `host_bytes_freed` and `load_waits`, and the line gains a `host_memory` block with the working set and its peak, so the claim is checkable from one run.

**`--fly <a> <b> <n>`** is the camera path a residency budget is under pressure on: `n` steps from `a` mesh radii to `b`, interpolated **geometrically**, because halving the distance doubles every projected error whether it is 50 radii to 25 or 2 to 1 — linear steps would spend nine tenths of the path on the outer half, where a mesh draws out of one page and asks for nothing. It overrides `--orbit` and sets `--frames` when nothing else did; a longer `--frames` repeats the last step, which is how "and then it sat there" is measured. A two-step fly is therefore also a **camera jump**: `--fly 20 1.5 2 --frames 120` is one frame far away and the rest up close.

The JSON summary gains a **`streaming`** object, present on every run so that a script never has to test for it — `pages_total` is 0 when nothing streamed:

```json
"streaming":{"pages_total":25,"pages_resident":16,"pages_pinned":1,"page_slots":25,"pending":0,
 "requests":58,"uploads":16,"uploads_bytes":1851392,"evictions":0,"stale":0,"overflows":0,
 "frames_to_converge":2,"resident_bytes":1929216,"page_bytes":2989678,"budget_bytes":2989678,
 "source":"file","file_reads":48,"file_bytes":1772544,"host_bytes_freed":5060512,"load_waits":15,
 "pool_pages":16,"steals":0}
```

and a **`host_memory`** block beside `gpu_memory`, which is what a claim about host memory is checked with: `"host_memory":{"bytes":318193664,"peak_bytes":354398208}` — the process's working set as the OS reports it (`platform::process_memory_bytes`) and its high-water mark, read after the last frame and before anything is torn down.

`pool_pages` is what the page pool holds, beside the manager's `pages_resident`: the two differ only while admitted pages are on their way, and a pool that stops short of the manager while `pending` grows is the stall [renderer](renderer.md#admission-never-waits-on-a-read-it-cannot-start) describes. `steals` counts the loads the streamer gave up so that the page at the head of the pool's walk could start its own read — each one a read done twice, and many of them mean too few load slots for the source's latency.

Three of the flags a run might combine with it are **refused rather than half-applied**, each with a line on stderr under the `renderer` category: `--deform` and a skinned scene (the deformed-vertex pool is indexed by the scene-wide vertex index and a streamed scene's vertices are at slot-relative ones), `--rt-templates` (a template is built at load from every cluster's positions, which a streamed scene does not hold), and `--no-cull` (the drawing rule's fallback *is* the LOD cut). A mesh with no page table turns streaming off outright.

**The same thing over the protocol**, in the same units and with the same words ([protocol](protocol.md#methods-an-app-registers-and-render)). The table's right-hand column is the whole of it for the flags; two things are the host's alone, and one is engine-view's alone.

```bash
engine-cli render.load '{"grid":257,"page_bytes":16384,
                         "settings":{"raster":"hw","stream":true,"page_budget_mib":1}}'
engine-cli render.benchmark '{"scene":"scene1","width":1920,"height":1080,"frames":240}'
```

`settings.stream` on **`render.load`** is what keeps the scene's page table — it is `SceneDesc::stream`, a property of what loading produced, and a scene loaded without it cannot be streamed later however a subsequent call spells its settings (streaming turns off with a log line instead). `page_bytes` beside it is the host's own knob and has no flag: it sizes the **procedural heightfield's** pages, which is what makes a test scene with dozens of pages instead of three, and it is refused outside 4096..67108864 because a page too small to hold a cluster is a typo. engine-view never sets it, so its heightfield is always at the 128 KiB default. **`procedural`** beside them says *which* scene an empty `mesh` and `scene` build — `""`/`"heightfield"` or `"shredded-atlas"`, the UV-atlas LOD stress fixture ([geometry](geometry.md#the-shredded-atlas)) the `shredded-atlas` corpus scene draws. An unknown name is refused rather than silently drawing the terrain: a corpus scene that asked for the fixture and quietly got the heightfield would pass its threshold and guard nothing. `RenderLoadParams` went to `@version(3)` for it, with the field `@since(3)` and defaulting to the empty string, so an older client sees exactly what it saw.

**`render.benchmark` is where streaming is measured**, and its optional per-call `settings` may turn it on or off for that run alone; the GPU scene and the pipelines are rebuilt from the `SceneData` already in hand, exactly as any other settings change rebuilds them. **`render.capture` takes its streaming settings from the load** and has no `settings` block at all, which is the rule it has always followed and not a gap: a capture is one frame, a streamed scene's first frame is by definition the unconverged one, and a per-call setting there would be a second place to say something `render.load` already said. A converged capture is a `render.benchmark` to warm the residency followed by a `render.capture`, in that order, in one host process.

`stats.stream` on a benchmark's result is `RenderStreamStats`: **every field of engine-view's `streaming` object above, under the same key names**, so one reader serves both hosts, plus `loads_in_flight`, which engine-view's line leaves out because it is a momentary value rather than a count of the run. `pages_total` is 0 for a scene that was uploaded whole, so a script never has to test for the block.

**What the host cannot do yet: read a page off disk.** `stats.stream.source` is always `"host"` over the protocol, and `file_reads`, `file_bytes` and `host_bytes_freed` are always zero — engine-view's `--page-source file` has no protocol equivalent. Streaming therefore bounds the host's *device* memory and not its host memory. The reason is in [protocol](protocol.md#methods-an-app-registers-and-render): attaching the container-backed source also releases the merged host streams, and those streams are what the host rebuilds a GPU scene from when a later call changes the settings.

## The renderer is a library, and both engine-view and engine-host draw with it

Everything that draws moved out of `apps/engine_view/main.cpp` and into [renderer](renderer.md) (layer `systems`): scene loading through the derived-data cache, the GPU-resident scene, the cull and LOD passes, the four rasterizers, the deformed-vertex pool, the acceleration structure chain, the material resolve, the Hi-Z, the GPU timers, and the capture. The reason was not the file's length. It was that **nothing but engine-view could render**, so the protocol had no `capture` and no `benchmark` and the Phase 1 exit criterion could not be met ([10 §10.2](../plan/10-roadmap-risks.md#102-phases)).

**engine-view is the command line over that library.** It keeps the flags and their validation, the window and its events, the surface and the swapchain with its resize and its present, the screenshot of the *presented* image, the shader-reload timer, and the JSON summary.

**It is the one app that includes the Vulkan backend set**, and the only thing it includes it for is presenting ([gfx](gfx.md#the-rhi-surface-and-the-backend-surface)): `domain/gfx/backend/vulkan/swapchain.h` for the `Swapchain`, `domain/gfx/backend/vulkan/vulkan.h` for the device's instance, and `foundation/window/backend/vulkan/surface.h` for `window::vulkan::instance_extensions()`, `create_surface` and `destroy_surface`. Its target links `engine::gfx_vulkan`, which is what puts the Vulkan headers on its include path at all, and the lint's `vulkan-backend-include` rule names `apps/engine_view` as one of the three places allowed. Everything it hands the renderer is in the engine's vocabulary — the swapchain image as a `gfx::ImageResource`, `gfx::ImageLayout::Present` as the frame's final layout, the acquire and render-finished semaphores as `gfx::SemaphoreHandle`s, the swapchain's `gfx::Format` as the pipelines' colour format — so the renderer draws a presented frame through exactly the path an offscreen one takes. engine-host includes none of it: its renderer is offscreen, and a second graphics backend would change engine-view's presenting code and nothing of engine-host's. Every flag and every JSON field is unchanged, and so is every picture: the FlightHelmet at `--width 400 --height 300 --frames 6 --orbit 22` through `--raster hw`, `--raster vertex`, `--raster rt --shadows rt`, `--deform wave`, and `--grid-instances 3` produces **byte-identical PNGs** before and after the move (`engine-image compare --json` reports `"psnr":null,"ssim":1,"flip_mean":0` on all five, and the files have the same SHA-256). The one visible change is where a log record comes from: the overrides a device or a scene forces — the mesh-shader fallback, culling forced on, shadows off on a path that cannot trace them — are now logged under the `renderer` category rather than `view`, because both hosts make them in the same function.

**engine-host gained `render.*`**, methods over the same library, with no window anywhere in the process:

```
render.load      {mesh | scene | procedural, settings, grid_instances, grid, page_bytes, ddc, cache, adapter, overlay} -> a scene id and its counts
render.capture   {scene, camera | orbit, width, height, channels, out_dir, name} -> file URIs and stats
render.benchmark {scene, width, height, frames, settings, camera | orbit | camera_path, path_frames, repeats, warmup, warmup_seconds} -> gpu_ms per pass, cpu ms per frame, and with a path the flythrough summary
render.compare   {a, b, weights, ppd, flip_out} -> FLIP, PSNR, SSIM
render.evaluate  {scene, camera | orbit, width, height, frame, settings, reference, direct_only, weights, ppd, out_dir, name} -> both pictures, the heat maps, full and direct metrics
render.unload    {scene} -> what was released: counts, GPU state, textures, host heap and device memory before and after
render.scenes    {} -> every scene held: id, source, counts, whether and at what size it is built, its textures and what sharing them saved; the adapter and the process's device memory
```

**A scene naming a generator this build lacks** ([scene_gen](scene_gen.md), [ADR-0046](../adr/0046-scene-generators-register-themselves.md)). What generates part of a scene — its terrain's ground provider, its placement entries' generators (`ruins`, and any `placements` entry by name: `ruins`, `city`) — is found in the scene-generator registry by the name the scene gives, and a generator is in the registry because the host links its capability: engine-view and engine-host link the city, ruins and terrain capabilities where the configuration has them, for their registrars alone, and nothing else in either names them. So a scene may name Island City directly — `{"generator": "city", "params": {"plan": "<dir|plan.json>", "district": 3}}`, or a `tile`, or neither for the whole city, `detail` optional — and draws what `engine-content city fragment` would have written, without the file; with a `world` block the ring streams it tile by tile. A scene naming a generator the executable does not carry — `"generator": "Dunes"` or `"provider": "dunes"` in a build without the terrain capability, a `ruins` entry without the ruins capability, a misspelt name anywhere — is refused as any unreadable scene is (engine-view exits 1, `render.load` answers 1005), with the registry's sentence after where the name is: `scene.json: the terrain names the ground provider "dunes", which this build does not have: its capability is switched off or not linked into this executable (it has waves)`, or `scene.json: ruins 0 names the placement generator "ruins", which this build does not have: its capability is switched off or not linked into this executable (it has none)`. `engine-view --world` streams the same entries through the world's placements consumer, which finds each generator again by the same name.

`render.load` is the expensive call — it imports and clusters a glTF, or reads the container the cache already holds — and the host keeps the result, so a capture and a benchmark of the same scene pay it once. `settings` on `render.benchmark` may differ from the ones the scene was loaded with; the host then rebuilds the GPU scene and the renderer from the loaded `SceneData` rather than re-importing the mesh.

```bash
engine-cli render.load '{"mesh":"content/samples/Suzanne/Suzanne.gltf","settings":{"raster":"hw"}}'
engine-cli render.capture '{"scene":"scene1","orbit":{"distance":22},"width":800,"height":600,
                            "channels":["color","ids","depth","normals"],"out_dir":"out"}'
engine-cli render.benchmark '{"scene":"scene1","width":1920,"height":1080,"frames":120}'
engine-cli render.compare '{"a":"out/capture.png","b":"out/baseline.png","weights":"center"}'
engine-cli render.capture '{"scene":"scene1","width":800,"height":600,"integrator":"reference",
                            "reference":{"spp":512,"bounces":3},"out_dir":"out","name":"ref"}'
engine-cli render.evaluate '{"scene":"scene1","width":800,"height":600,
                             "reference":{"spp":512},"out_dir":"out","name":"eval"}'
```

Because `engine-cli` spawns a host per invocation, a scene id lives only as long as that process: a sequence like the one above is one `engine-host --stdio` session, or one `engine-cli` call per line with a `render.load` in front of each. A scene is released by `render.unload` or when the process exits, whichever comes first — and a long-lived host (one behind engine-mcp, which lives as long as the agent's client) needs the first, because every distinct scene it loads is otherwise held, GPU buffers and all, until the end. `render.scenes` lists what is held. What belongs to a scene rather than to a session, why closing a session unloads nothing, and what the memory figures in unload's answer can and cannot show are in [protocol](protocol.md#methods-an-app-registers-and-render).

`render.capture`'s `channels` are `color` (RGBA8 PNG), `ids` (the entity-ID buffer: three little-endian `u32` per pixel — instance, cluster, triangle — in a `.ids.bin` with a `.ids.json` header describing it), `depth` (an 8-bit gray PNG normalized over the frame's covered range, whose exact bounds are `depth_min`/`depth_max` in the result), and `normals` (an RGB8 PNG of `n * 0.5 + 0.5`, which costs a second frame because only the resolve knows the normal). [renderer](renderer.md) has the encoding in full and says why the id buffer resolves the visibility id into a pair rather than reporting the id. `--raster direct` writes no visibility buffer, so `ids` and `depth` are an error there rather than a buffer of nothing.

**A capture's `gpu_ms` is zero, and that is not a bug.** A timestamp pool is read when its frame slot comes around again, so with two frames in flight the first two frames of any run have no timings yet — and a capture is one frame, or two with `normals`. `stats.gpu_ms.frames` says how many frames the numbers came from, and it is 0 there. `render.benchmark` is the call that measures; `render.capture` reports the visible-pair counts, which do come back, and the picture.

**`render.capture` with `"integrator":"reference"`** draws the same frame with the reference path tracer instead ([04 §4.8](../plan/04-renderer.md#48-reference-renderer-and-objective-optimization), [renderer](renderer.md#reference-renderer)) and writes it to the same `<name>.png`, so a caller comparing the two needs no second code path. The `reference` block is `spp`, `bounces`, `finest`, `seed` and `batch`; the result echoes `integrator` and adds `samples`, `trace_ms` and `seconds`. It has **only** a color channel, because a path tracer writes no visibility buffer — asking for `ids`, `depth` or `normals` is an error with a message. It needs a device with cluster acceleration structures and a scene whose settings build them (`"shadows":"rt"`, or `"auto"` on such a device), and answers 1007 where it cannot.

**`render.evaluate` is the optimization loop in one call.** It renders the real-time picture and the reference of the *same* frame — one camera, one frame number, one set of lights — renders the reference again at a single bounce unless `direct_only` is false, compares both pairs, writes `<name>.realtime.png`, `<name>.reference.png`, `<name>.flip.png`, `<name>.reference_direct.png` and `<name>.flip_direct.png`, and returns `full` and `direct` metrics, the real-time `stats`, `samples`, `reference_trace_ms`, `reference_seconds`, `realtime_seconds`, `metrics_ms` and the `machine_state` span. The `direct` half is what makes a threshold explicable: the gap between it and `full` is the indirect light the real-time path does not have, which is large in a scene with interiors and small in an open one. `tools/ci/reference-compare.ps1` is the corpus runner over this method.

The end-to-end suite for all four is `apps/engine_cli/tests/render_tests.cpp` (`tools/dev.ps1 test -Filter engine_cli`). It drives one `engine-host --stdio` process through the whole round trip — because a scene id lives in the host and the CLI spawns one host per invocation — and renders the **procedural heightfield**, so the case needs no fixture, no sample asset, and no cache entry. It checks the scene counts, all four channels landing on disk with the id file exactly `width * height * 3 * 4` bytes and the header describing that, a benchmark at a different size reusing the loaded mesh and reporting a GPU millisecond field per pass, a capture compared against itself giving a null PSNR and an SSIM of 1, and the four error codes a client has to tell apart. `render.compare` is driven through engine-cli as well, since it is the one method that never opens a device and so runs on a machine without one. A second case covers the reference integrator and `render.evaluate`: a 32-sample reference capture landing on disk with its sample count echoed back, an id channel and an unknown integrator both refused, and one `render.evaluate` producing all five files with both sets of metrics — skipping on 1007, which is what a machine without cluster acceleration structures answers. A third covers geometry streaming, and it is a case about the *schema* as much as about the renderer: the heightfield loaded with `page_bytes` 16384 and a 1 MiB budget gives 179 pages over 3.8 MB, and `stats.stream` comes back with a budget of exactly 1048576 — unclamped, so the MiB on the wire really did become bytes — pages resident, pages pinned, pages uploaded and requests written, and `source` `"host"` with the three file counters at zero, which is all the heightfield can ever report. Then the same scene benchmarked with a per-call `"stream":false` reports `pages_total` 0 while still drawing its pairs, which is the evidence that an additive settings field reached the renderer rather than being decoded into a struct nobody reads; and `page_bytes` 7 and an `upload_budget_kib` of 2³²−1 are both 1004.

Two cases cover **`render.unload` and `render.scenes`**. On every machine: with nothing loaded, `render.scenes` is an empty list with an empty adapter and a null device-memory figure (it opened nothing), an id never handed out is 1003 without the word "unloaded", no id is 1003 too, and a number for an id is -32602. Where there is a GPU: a small scene drawn at 320×240 opens the device and is listed with its kind, source, counts and frame size; then a 256×256-cell heightfield is loaded, drawn once at **7680×4320** by a one-frame benchmark, and unloaded — its host arrays go (the heap drops by more than a MiB, to within 256 KiB of before the load), its id is dead to `render.capture`, `render.benchmark` and a second `render.unload` alike (1003, "it was unloaded"), and the driver's device-memory figure, which had risen by more than 256 MiB, gives back at least three quarters of the rise; a second cycle of the same scene ends at no more than the first did. The 8K frame is there because the driver counts the allocator's blocks, not its allocations: a scene that fits in blocks the small one opened moves the figure by nothing either way ([protocol](protocol.md#methods-an-app-registers-and-render)). On the RTX 5090 the figure goes 137.7 MB → 849.4 MB → 139.5 MB, and 139.5 MB after every later cycle. `engine.ping` has a case of its own in `cli_tests.cpp`: a pid, an uptime of a few seconds at most, and the catalogue entry with no params type.

## Flythroughs

The benchmark corpus of [plan 09 §9.4](../plan/09-testing-profiling.md#94-benchmark-scene-corpus) measures a frame that streams, culls and occludes across a scene rather than one asset from one camera, and engine-view is the command line for it ([renderer](renderer.md#scenes-camera-paths-and-flythroughs) has the formats and the mechanism; [desert-overlook](../../content/test-scenes/desert-overlook/README.md) is the first scene and [its measurements](../experiments/flythrough-desert-overlook.md) the first numbers):

```powershell
engine-view --scene content/test-scenes/desert-overlook/scene.json `
            --camera-path content/test-scenes/desert-overlook/camera-path.json `
            --benchmark run.jsonl --width 3840 --height 2160 --shadows off [--census] [--no-occlusion]
tools/gpu-lock.ps1 run -Purpose "flythrough" -Exec "pwsh tools/flythrough.ps1 -Set substitute"
```

- **`--camera-path <file>`** flies an `engine.scene.CameraPath` in either frame path: in the window, once at the path's own rate (`--frames` resamples it), or offscreen. Its keys are read against the loaded scene, because a key may hold a height above the terrain.
- **`--offscreen`** renders into the renderer's own target with no window, no surface and no swapchain — the device is created without the presentation extensions, as `--reference` does — so 11520×2160 runs on any machine; `--capture` then writes the last frame. **`--benchmark`, `--verify-occlusion` and `--marker-captures` imply it** (for a path and for a replay; a live `--interactive` session measures its window instead, below), because a composited window was E1's named source of noise and a measurement does not need one.
- **`--benchmark <out.jsonl>`** flies the path `--repeat` times (default 3), each after `--warmup` frames (default 240) and at least `--warmup-seconds` (default 2) at the first camera, and writes one `engine.scene.FrameRecord` per path frame and repeat — every pass's GPU milliseconds from `gfx::GpuTimer` (with the bottom-level build, `blas`, beside the cluster build, `clas`, inside `rt`), the CPU's own milliseconds (`cpu_ms`: the submission, not the wait for a free frame slot) and the wall milliseconds since the previous frame (`frame_ms`), the visible pairs by draw, the shadow casters, the pages uploaded and evicted and streaming's state after the frame (`pending`, `loads_in_flight`, `pool_pages` beside the manager's `pages_resident`), and the ray tracing chain's `rt_built`, `rt_wanted` and `rt_capacity` — then an `engine.scene.FlythroughSummary`, which is also the one line on stdout: the median, p95 and p99 per pass over the path of each frame's median across its repeats (and of `cpu_ms` and `frame_ms`), the visible pairs, whether every repeat drew the same pairs frame by frame, every marker's numbers, the hashes of the scene, the path and every mesh, and the machine state around the run. It needs a camera path (a still camera is `render.benchmark`'s) and refuses `--animate`, `--morph-animate` and `--reference`, which have their own paths. An interactive session writes the same file with a `ticks` count on every record ([below](#--interactive-a-camera-somebody-flies)).
- **`--census`** flies the path once more, untimed and one frame at a time, reading each frame's visible list back: visible pairs by DAG level and by mesh go into every record, and a frame whose pairs differ from the timed pass's is counted. **`--census-pixels`** adds the pixels each mesh covers from an id capture, which is how a scene's README states the frame a landmark comes into view.
- **`--verify-occlusion`** draws every frame of the path twice more, with and without occlusion culling, from two uploads of the scene in lockstep, and compares the (instance, cluster) under every pixel and every colour byte; the summary's `occlusion_check` says how many frames differed and, for every differing pixel, whether the frame without occlusion culling had a **nearer** surface there (a visible cluster culled: the invariant is none, `frames_culled_visible` 0) or a surface at **exactly the same depth** (`tied`: coincident geometry, where the visibility buffer keeps the larger visible-entry index and culling renumbers the list), with every differing frame listed. It refuses `--stream`, because a streamed scene releases the geometry the second upload is made from.
- **`--marker-captures <dir>`** writes a PNG of every marker of the path, eight frames after reaching its camera so a streamed scene has its pages.
- **`--capture-channels <list>`** (any of `ids`, `depth`, `normals`; `color` is always written) reads those back too, for an offscreen `--capture` and for every marker capture of a path or a replay, and writes them beside each PNG under its stem in `renderer::write_capture`'s names and formats — `<stem>.ids.bin` + `<stem>.ids.json`, `<stem>.depth.png`, `<stem>.normals.png` — which are also `render.capture`'s, so one reader serves both hosts ([renderer](renderer.md#capture-channels-and-the-id-encoding)). It exists because a picture alone could not say whether a patch that changed between two frames changed its *surface* (the pair under the pixel) or only its colour, and that was the question the first owner session left ([its write-up](../experiments/first-interactive-session-2026-09-24.md)). A window's `--capture` reads the presented swapchain image, which is the picture and nothing else, so the flag is refused there, as it is with nothing to capture; at 11520×2160 an id buffer is 299 MB.
- **`--overlay <manifest>`** replaces a scene file's meshes that name an `overlay` content hash with the manifest's files, which are hashed and refused if their bytes disagree ([renderer](renderer.md#scenes-camera-paths-and-flythroughs)).
- **`--require-quiet`** and **`--wait-quiet <s>`** are the bench harness's flags with the harness's thresholds ([bench](bench.md#measuring-on-a-shared-machine)): measure nothing on a busy machine and exit **4**, or wait up to s seconds for a quiet one and then measure either way.

**`tools/flythrough.ps1`** is the measurement matrix over those flags — every resolution of `-Resolutions` (default 1080p, 1440p, 4K and 11520×2160, the last as `--views surround3`) with occlusion culling on and off, one `-Set` (`substitute`, or `overlay` with the owner's manifest) — writing each run's `.jsonl`, a `summary.json` and a `summary.md` table into `build/<preset>/flythrough/` unless `-Out` says elsewhere; `-Markers` re-reads a scene's marker states at 640×360 with and without occlusion culling, which is where its README's table comes from. Run it under `tools/gpu-lock.ps1 run`, which marks the lock as held for engine-view's own machine-state check.

**Over the protocol** `render.benchmark` takes the same path: `camera_path` (read against the loaded scene's terrain), `path_frames` (0 is its own count), `repeats`, `warmup` and `warmup_seconds`, and returns the same `FlythroughSummary` as `flythrough` beside its usual result — through the same `renderer::fly_camera_path`, so the two hosts' numbers are the same numbers. The per-frame lines are engine-view's alone. `render.load` takes the `overlay` manifest for a `scene` file.

## `--time-rate`: the dunes in time-lapse

`--time-rate <r>` runs a dune terrain's game time at `r` game seconds per real second — a frame is a sixtieth of a second, the frame index's clock; 86,400 is a game day a real second and 604,800 a week — and draws the terrain moving: evaluated off the frame on a job pool of its own and blended between the last two fields every frame in the deformed-vertex pool, so no vertex moves more than `renderer.terrain.move_fraction` (a quarter) of the terrain's spacing in one frame and a dune never changes height in an instant ([renderer](renderer.md#the-dunes-in-time-lapse) has the mechanism and why). The next field is timed for when the field's fastest band will have travelled that same fraction of a sample (the cadence rule), and in a window no sooner than it takes to come at the rate (`renderer.terrain.lead` times the worst recent turnaround, [renderer](renderer.md#a-clock-that-never-stops)). **In a window the sand keeps a steady speed**: the surface clock runs it at game time minus a latency L — how long a field takes to come, at the rate — and when a field is later than L allowed it slows the sand smoothly rather than stopping it and then catching up at a sprint; the picture lags game time by L (about 1.5 s of real time at a day or a week a second on the erg, the summary's `latency_s`). **Offscreen, a late field is waited for** and the fields are timed by the dunes' motion alone, so two runs of `--frames N --time-rate r` draw and capture the same bytes on the same frames however fast the machine is — which makes an offscreen time-lapse as slow as its evaluations at a high rate. A terrain that does not name the dune generator is refused with a sentence (exit 1), and so is a streamed world (`--world`), which has no pool. The stand-in lights stand still unless `--orbit-lights` is given, and the sun unless `--sun-rate` runs its day, so the frames of a time-lapse differ only by the sand; until 2026-09-27 they orbited with the frame index and changed the sand's colour from frame to frame far more than its motion did ([the looks](../experiments/third-interactive-session-2026-09-25.md#the-dunes-in-time-lapse-looked-at-2026-09-26)).

**`--terrain-rings`** puts the terrain rings in the scene ([renderer](renderer.md#the-rings-in-the-scene)): the ground near the camera at 50 cm to 250 m and at a metre to a kilometre (the `terrain.rings.*` tunables), drawn beside the scene's grid, which leaves their square out. They are built at load round the camera's first position — a `--camera-path`'s first frame, else the scene's own path's, else the orbit's — and re-centred as the camera moves: the changed chunks rebuilt on a thread of their own, uploaded `renderer.terrain.ring_upload_mib` a frame, and swapped in whole in one frame; offscreen a re-centre is completed in the frame that asks for it. With `--time-rate` they move with the rest of the sand at one surface time; without it they are the rest pose, and follow the camera. The flag is off by default (the rings cost a few seconds of load and their slots' device memory). With `--stream`, in a streamed world and over a terrain that does not name the dune generator the terrain is drawn without them; a grid whose spacing or half-side is not a whole number of millimetres, which the rings' lattices cannot share, is refused with a sentence (exit 1); `--rt-templates` is turned off with a warning. The summary's `time_lapse` block (present whenever the terrain has levels, so with `--terrain-rings` alone too) then has one level per ring after the scene's grid, and a `rings` block: `rebuilds`, `swaps` and `failed` re-centres, `chunks_built`, `chunks_kept` and `chunks_uploaded`, `upload_bytes` and `upload_frames`, the ring worker's `last_rebuild_ms` and `max_rebuild_ms`, the field worker's `last_pairs_ms` and `max_pairs_ms` for carrying the pairs over, the last re-centre's `last_upload_frames`, `last_upload_bytes`, `last_swap_frames` (asked to drawn) and `last_frozen_frames` (of which the rings held their pairs), and `device_bytes`, what the rings' slots and arenas hold.

**In an `--interactive` window `,` and `.` step the rate** down and up the ladder 0, 60, 600, 3,600, 8,640, 86,400, 604,800 while the sand moves ([below](#--interactive-a-camera-somebody-flies)), through `TerrainMotion::set_rate` and so through every rule above: game time runs on at the new rate, the sand slows down within a second or speeds up over one to three without outrunning the fields already on their way, comes to rest at zero rather than stopping dead, never steps and never moves a vertex past the per-frame bound, and the next field is timed at the new rate ([renderer](renderer.md#changing-the-rate-while-it-runs) has the rules and what the tests hold). So the motion exists to be set going, an interactive window draws a dune terrain as terrain levels even at `--time-rate 0` (`RenderSettings::time_rate_live`) — the pool's 768 MiB floor, the rest pose evaluated once at load and no cone test on the terrain, whether or not the keys are pressed, and the same picture. Offscreen runs ignore the keys, so their pictures stay a function of their frames.

The summary line (the window's and the offscreen one's) gains a `time_lapse` block, `null` without the flag: `rate` (the one it ended at), `start_rate` and `rate_changes` (the keys'), `fraction`, `min_step_s`, `max_step_s`, `lead`, `wait`, `game_time_s`, the surface clock's `latency_s` (L, game seconds; 0 offscreen, where the sand keeps game time and waits for its fields), `max_latency_s`, `latency_frames` (L in frames at the rate), `lag_s` (how far behind game time the sand stood at the end), `stopped_frames` (frames it stood still after it first moved) and `braked_frames` (frames the clock slowed it for a late field), the fields' `upload_bytes` and `upload_ms` (GPU), and `levels`, one object per terrain level with its `spacing_m`, `surface_s` (the game time the sand stands for), `time_a`, `time_b` and `blend` (its pair of fields and where between them it is), `padding_m` (how far its sand is from the rest pose its bounds were fit to), `evaluated` and `installed` (fields), `held`, `capped` and `waited` (frames the sand stood still for a late field, was slowed by the per-frame bound, and waited for one offscreen), `late` (fields timed further out than the displacement rule to keep up), `max_move_m` (the most any vertex moved in a frame), `max_delta_m`, `max_step_s`, `max_lag_s`, `last_eval_ms`, `mean_eval_ms`, `last_turnaround_s` and `max_turnaround_s` (real seconds from the level wanting a field to its being ready to draw: the evaluation and the wait behind the other levels'), and `last_hash` (16 hex digits over the last field's bytes: two offscreen runs of the same `--frames` compare by it).

**With `--benchmark`, every frame's record carries a `terrain` object** (`engine.scene.FrameTerrain`, `FrameRecord` version 7; `null` without a time-lapse): `game_s`, `latency_s`, `lag_s`, `rate` (the rate in force that frame, since `FrameTerrain` version 2: the keys change it), `speed` (the sand's advance that frame over the true one: 1 is the rate) and `levels`, one `TerrainLevelFrame` per level with `surface_s`, `time_a`, `time_b`, `blend`, `move_m` (the most any of its vertices moved that frame), `held` (it stood at its b with no next field), `late` (the clock braked for its newest field) and `ahead` (fields after b it had). It is what a stop, a sprint or a slow-down is found by, a frame at a time — in a window with `--interactive --benchmark`, where the clock runs, and offscreen, where it does not.

## engine-view --world: a streamed scene

A scene whose ruins are too many to read whole — a thousand ashlar buildings are 33 million (instance, cluster) pairs, twice what a visibility id can name — is drawn **a tile at a time** round the camera by the world capability ([world](world.md)): its `ruins` entries are not assembled when the scene is read, but tile by tile as the camera's tile ring takes tiles in, in the representation the ring asks for — laid block by block in the inner ring, the kit's sections with their debris in the middle one, the walls alone beyond — and dropped when the ring lets them go. The renderer takes the tiles' instances between frames as a **tail** behind the scene's own ([renderer](renderer.md#instances-that-come-and-go)), so the terrain and the meshes stay resident and nothing is read again.

```powershell
engine-view --scene scene.json --world --camera-path path.json --offscreen `
            --benchmark run.jsonl --world-log world.jsonl [--world-handover handover.jsonl]
```

- **`--world`** streams a scene file with the capability's rings (1.5 tiles in blocks, 8 in sections, 24 in walls only; 32 m tiles; hysteresis 0.15; 8 activations and 16 deactivations an update). **A scene file's `"world"` block** (`engine.scene.WorldRings`: `tile_size`, `rings` of `{radius, ruins}` innermost first, `hysteresis`, `simulated`) does the same with its own rings, and `"world": {}` is the defaults; without either the scene is read whole, as before. A ruins entry's own `tile_size` must be the world's, or the file is refused ("must be one grid"): a ring tile would otherwise hold parts of four of the entry's.
- **The camera is the observer.** In a flight the ring updates before every frame from that frame's own camera (`FlightOptions::before_frame`), so the frame draws what the ring holds for it; each repeat and each warm-up starts from an empty ring filled without a budget, so every repeat flies the same world. Marker captures and the final `--capture` fill the ring completely first. **In the window** it follows the camera a frame behind — the update runs before a frame is begun, from the previous frame's camera — which is the one frame of latency a game's world has too.
- **`--world-log <out.jsonl>`** writes one `engine.world.TileFrame` per update — the repeat, the path frame, whether the frame was recorded, the tick; the tiles scored and active and the active tiles per ring; the events by kind, the refusals and the changes the budget held over; the ring's microseconds and each consumer's calls, milliseconds, worst call and commit; and the scene's instances and pairs, the buildings and the ruins' instances after it — then one `engine.world.TileWorldSummary` (`format` `engine.world-log.v1`): the rings, the totals, the ring's median, p99 and worst microseconds, and the placements consumer's buildings — the ruins' assembled and laid, by the representation their generator drew — dropped and refused with the milliseconds of each kind of work and of the renderer taking the tail (`insert_ms`, `insert_ms_max`, `handed`). The same summary is the `world` field of the flight's `FlythroughSummary` (version 5), and every `FrameRecord` carries the scene's `instances` and `pairs` at that frame (version 5), since a streamed scene's change from frame to frame — and, since version 6, `table_slots`, `table_pairs` and `hole_pairs`, what the frame wrote into the renderer's table set and how much of its cull dispatch no instance holds, with the writes' GPU time in `gpu_ms.tables` ([renderer](renderer.md#instances-that-come-and-go)).
- **`--world-handover <out.jsonl>`** (offscreen, with a camera path) flies the path once more after the timed flight, one frame at a time and untimed, and for every tile an update moves to a ring that draws it differently draws that frame **twice** — as the update left it, and with only that tile's instances put back as they were, everything else the update did being in both — each drawn once before it is captured so its visible pairs are its own, reading back colour, ids and depth. It writes one `engine.world.TileHandover` per tile: the tile, the two rings and representations, its distance; the pixels the tile's own instances drew before and after (found through the ids); the pixels covered in one picture and not the other (`coverage_changed`), covered in both at depths more than a thousandth apart (`depth_changed`) and, of those, more than a hundredth (`depth_moved`: geometry that moved, not relief), and whose colour changed by more than 8 of 255 (`color_changed`); `depth_changed` again as a **displacement histogram** (`depth_bins`: moved by 0.1–0.3%, 0.3–1%, 1–3%, 3–10% and more than 10% of the distance, which at 47 m is 5 cm, 14 cm, 0.47 m, 1.4 m and 4.7 m); of the changed pixels, those where either picture shows the tile's **rubble** — debris members or fallen blocks, from `PlacementTiles::tail_tags`, the tag the ruins generator gives rubble — rather than its walls (`rubble_changed`); the frame's visible pairs before and after; and the tile's instances and pairs before and after. It is **the pop a handover costs without a cross-fade**, which is the number [E35](../experiments/e35-world-streaming.md) needed, and the histogram and the rubble share say what the pop is made of.
- **Refused**: `--world` with `--raster rt`, `--shadows rt`, `--deform`, `--animate`, `--morph-animate`, `--reference` or `--verify-occlusion` (a tail is rigid and rasterized in v0, and the occlusion check draws a second upload of the scene that no ring fills), `--world-handover` without `--offscreen` and a path, and all three flags in a build without the capability (exit 2). A scene file's `world` block is only known once the file is read, so it meets the last four with a refusal then (exit 1), and the first three the way the renderer resolves any dynamic scene: the ray path to the rasterizer, traced shadows to the cascaded maps, the deformation pass off, a warning each — and `--shadows auto` picks the maps.

`--census` and `--census-pixels` count a tail's meshes through the GPU scene's own table, so a census of a streamed scene names the ruins' meshes like any other. `apps/engine_view/tests/ruins_view_tests.cpp`'s case "a streamed world draws the ruins its ring holds, as a whole read does" draws one ruins entry streamed and read whole and holds the two pictures to each other.
## `--interactive`: a camera somebody flies

`engine-view --interactive` (with `--scene` or `--mesh`, `--views`, `--shadows` and every other rendering flag) puts a fly camera in the window, driven by the keyboard, the mouse and a gamepad, and makes the whole session recordable and replayable bit for bit. It is the first thing in the engine that a person steers, and it is built the way a game will be: window events become `input::RawEvent`s once, at the edge; bindings are an `input::ActionMap` that is data; and the camera integrates at a fixed tick from an `input::InputState`, never from the window and never from a frame's duration ([input](input.md), plan 05 §5.10). The camera is `apps/engine_view/fly_camera.h`, the edge `window_input.h`, the title's numbers `pacing.h`.

```powershell
engine-view --scene content/test-scenes/desert-overlook/scene.json `
            --camera-path content/test-scenes/desert-overlook/camera-path.json `
            --interactive --record-input session.jsonl --benchmark session-frames.jsonl
engine-view --replay-input session.jsonl                                   # the same flight, in the window
engine-view --replay-input session.jsonl --marker-captures markers/        # offscreen, a PNG per marker
engine-view --replay-input session.jsonl --benchmark replay.jsonl          # offscreen, the path as a benchmark
```

**The default bindings** (`content/input-maps/engine-view.json`, which is `view::default_fly_map()` byte for byte — a test holds them together; `--input-map <file>` flies with another):

| Action | Kind | Keyboard and mouse | Gamepad |
|---|---|---|---|
| `move` | Axis2 (x right, y forward) | W / S forward and back, A / D left and right | left stick (deadzone 0.15) |
| `lift` | Axis (world up) | E or Space up, Q or Left Ctrl down | right trigger up, left trigger down |
| `look` | Axis2, read as a **distance** | pointer motion while the window holds the pointer | — |
| `turn` | Axis2, read as a **rate** | — | right stick (radial deadzone 0.15) |
| `fast` | Button (×`view.fly.fast`, 4) | Shift | left stick click |
| `slow` | Button (×`view.fly.slow`, 0.25) | Alt | right stick click |
| `capture` | Button | Escape: give the pointer back; with it already given back, end the session (below) | Back |
| `marker` | Button | M: remember this tick's camera | North (Y on an Xbox pad) |
| `sun_slower`, `sun_faster` | Button | `[` and `]`: the sun's day a rung down or up its ladder (0, 60, 600, 3,600, 8,640, 86,400 game s a real s) | — |
| `dunes_slower`, `dunes_faster` | Button | `,` and `.`: the dunes' time-lapse a rung down or up its ladder (the same and 604,800) | — |
| `walk` | Button | F: walk on the ground under the camera, or fly from where it stands ([Walking](#walking)) | — |
| `jump` | Button | Space, while walking (flying, Space is `lift`) | South (A on an Xbox pad) |

`look` and `turn` are two actions because a mouse says how far and a stick how fast: `look` is read through `InputState::delta2`, the tick's pointer pixels unclamped, and `turn` through `axis2`, a position times `view.fly.turn_rate` per second — one action could not be both without capping how far a mouse can turn in a tick at one pixel's worth.

**The pointer, and the two Escapes** (2026-09-27, the owner's ask after his fly-throughs). **A click in the window, or the window gaining focus, takes the pointer** — relative mode, the cursor hidden and held (`window::Window::set_relative_mouse`) — because switching to the window is switching to fly it; a window opened in front of everything therefore starts with it. **Escape once gives it back**: the cursor shows, the camera stops turning with the mouse, and the keys and a pad still fly it. **Escape again, with the pointer already given back, ends the session** — the frame it was pressed in is drawn and presented and the run ends as a closed window's does, the summary printed and `--record-input`'s log and `--benchmark`'s file written. Losing focus gives the pointer back too, and coming back takes it again. Escape is the `capture` action, read at the tick it was pressed on like any other, so the two presses are ordered by the ticks and a recording holds both; the window's close button still ends the session at any time. **An injected run** (`--inject-input`, below) never takes the real pointer and ignores the desktop's focus: it starts as a window with the focus would — holding the pointer — and then follows its log's clicks and Escapes alone, so what its Escape does is a function of the log. (Until 2026-09-27 the window started without the pointer, Escape took it and gave it back, and nothing but the close button ended a session.)

**The two rates on four keys.** `[` and `]` step the sun's day (`--sun-rate`, above), `,` and `.` the dunes' time-lapse (`--time-rate`), a rung of the ladder each press — the sun's 0, 60, 600, 3,600, 8,640 and 86,400 game seconds a real second, the dunes' the same and a week, 604,800 — from whatever the flags started them at; from a rate between two rungs a key goes to the rung on its side. The two are independent on purpose: the owner watches the sand move under a still sun, and the sun move over still sand. The sun's day runs on the session's ticks at the rate, so a change changes how fast the sun moves and never where it is; the dunes' rate goes through `TerrainMotion::set_rate` ([renderer](renderer.md#changing-the-rate-while-it-runs)), and a scene whose terrain cannot move says so on the console and ignores the key. Each change prints one line on stderr (`engine-view: dunes x604,800 game s a real s (was x86,400)`), the title says both rates at once (below), and the summary's `time_lapse` and `sun` blocks end with the rates the session ended at, the ones it started at and how often the keys changed them. They are actions of the map like the camera's and are recorded with it; **a replay in the window presses them where its recording did**, and an offscreen replay ignores them, so its pictures stay a function of its ticks. Keys only: a player's map can bind a pad's d-pad.

**The map's revisions.** The four keys were appended to engine-view's map as its second revision (`view::k_fly_map_revision`), which moved its hash — and a log names the hash of the map it was recorded against. So a replay given no `--input-map` flies with **the revision its log names** (`view::default_fly_map_for`): every session recorded before 2026-09-27, and the committed synthetic fixture, replays with the first revision, the eight camera actions, exactly as it did, and its keys press nothing new; a log recorded against a player's own map still needs that map. The walk mode's `walk` and `jump` are the **third revision** (2026-09-28, [Walking](#walking)), under the same rule: a session recorded against the first or second replays with it, and its F presses nothing. The sign conventions are the camera paths': yaw about +y counter-clockwise from above, pitch about the camera's right axis, up positive, forward -z at zero — so the orientation is `quat_from_euler(yaw, pitch, 0)`, the same `CameraKey.rotation` a path key holds, and a recorded session's camera at any tick can be written as a path key without a sign flipping. `move` flies along the look direction, pitch included; `lift` is world up.

**Where a session starts**, in order: **`--start <x,y,z> <yaw,pitch>`** — metres, and degrees in the conventions above (`--start 0,4,900 0,-5` is the desert overlook's approach, 4 m up, looking north and a little down), written into the header as exactly those angles in radians; else **`--camera-path`'s first frame**; else **the first frame of the scene file's own camera path** (`Scene.camera_path`, schema version 2, a path relative to the scene file — the desert overlook names `camera-path.json`, so it starts 900 m south of the oasis looking north at the saddle, 2.5 m over the dunes); else the orbit camera with its near plane brought in to at most 5 cm, since a camera that flies in needs one. The orbit frames the whole scene's bounds, which is right for a mesh and was 9.4 km out for the 5 km desert: the first owner session began there, over a minute of flying from anything even with Shift held ([the write-up](../experiments/first-interactive-session-2026-09-24.md)), which is why a scene can now say where it is meant to be seen from. The scene's path is read for its first frame only and never flown. `--start` is refused with `--camera-path` (both say where to start) and with `--replay-input` (a replay starts where its recording started).

**The owner's landmarks in a session.** `--overlay <manifest>` works with `--interactive` exactly as with a flythrough ([Flythroughs](#flythroughs)): the scene's placeholders that name an overlay hash are replaced by the manifest's files, hashed and refused if their bytes disagree. A session recorded without it flew the committed Khronos stand-ins, which is what the first one did:

```powershell
engine-view --scene content/test-scenes/desert-overlook/scene.json --interactive `
            --overlay D:/workspace/game_engine_local/scenes/desert-overlook/landmarks.json `
            --width 11520 --height 2160 --views surround3 --record-input session.jsonl --benchmark frames.jsonl
```

A recording's header names the scene but not the overlay, so its replay takes the same `--overlay` to draw the same meshes (the camera flies the same path either way); the six overlay meshes' first load clusters about ten million triangles into the derived-data cache, and every load after that reads them back.

**Parameters** are tunables, read once as the session starts and written into its header: `view.fly.tick_hz` (240), `view.fly.speed` (metres per second; **0, the default, flies a tenth of the scene's bounding radius a second**, because the same viewer shows a 2 cm mesh and a 5 km desert), `view.fly.fast` (4), `view.fly.slow` (0.25), `view.fly.look` (0.0022 radians per pixel), `view.fly.turn_rate` (2.5 radians per second) and `view.fly.pitch_limit_deg` (89). `--tunable view.fly.speed=20,view.fly.look=0.003` sets them for a run and `--tunables <file.json>` loads a JSON object of them, the file engine-host's `--tunables` takes.

**Why a fixed tick, and not the frame's dt.** A camera integrated over wall-clock frame times is a function of how long each frame happened to take: the same keystrokes flown twice go to two places, a replay can only ever be approximately where the session was, and a benchmark of the replay measures a different path from the one that was flown. At a fixed tick the camera is a function of the tick sequence alone. Every tick is the same `dt`; every event is stamped with the tick it will be fed at; the frames only **read** the state, never write it (a live frame draws it between the last two ticks, below). A frame runs however many ticks a `FixedStepClock` says are due — none when it came sooner than a tick, several after a slow one, and a stall past a quarter of a second is dropped rather than flown through — and the lights and the deformation phase read the tick at a nominal 60 Hz (`FrameDesc::frame_index = tick * 60 / tick_hz`), so they move with simulated time and not with the frame count. The trigonometry is `view::fly_sin_cos`, a polynomial in `f64` that every compiler evaluates to the same bits, because the C library's sine is not the same function on MSVC and glibc; the only libm call turns the start camera into a yaw and a pitch, once, and its answer goes into the header.

**Drawing between ticks.** A live frame draws the camera **between the last two ticks**, at the fraction of a tick the fixed-step clock holds past the last one it ran (`FixedStepClock::interpolation_alpha`): `FlySession::camera_at(alpha)` is `fly_interpolate(previous(), state(), alpha)` — the position on the segment between the two, the pitch between theirs, the yaw the short way round across ±π — so the drawn camera moves by the frame's own time, one tick (4.2 ms) behind the newest state and never ahead of it. Until 2026-09-24 a frame drew the state *at* the last tick boundary, which moves by whole ticks: at 240 Hz against the 82 Hz display of the first owner session that was 3, 3, 3 … 2 — a two-tick frame every 14 — and a near object under a camera turning and strafing at once jumped by a third less on that frame, six times a second, which is the stutter the owner reported and the far scene hides ([the write-up](../experiments/first-interactive-session-2026-09-24.md)). **Only what is drawn moves**: the ticks, the trajectory and its hash, the recording, a replay's frames (four ticks each, tick-aligned by construction), every marker capture and the offscreen `--capture` are exactly what they were, and `tests/fly_tests.cpp` checks every drawn camera of the synthetic session lies on its segment and that asking for them leaves the trajectory's hash alone. What interpolation cannot fix is a frame that samples the clock at the wrong moment: from 3 s into that session the frames came in pairs 1.2 ms apart and 23 ms from the next pair — both presented, a refresh apart, one carrying five or six ticks and the other none or one — and interpolating at the sample time moves the camera by 24 ms per pair however it is drawn. That was present pacing — when a frame samples — and the display pacer below is its fix ([Pacing](#pacing)).

**Why the conversion lives in engine-view.** `foundation/input` must not depend on `foundation/window` (a headless server and a replay have no window), and `foundation/window` stays raw and knows nothing of bindings; the one code that knows both vocabularies is the code that owns both, which is the app — and a game writes this same edge for its own window. Two decisions are made there because that is where the information is: **pointer motion is looking only while the window holds the pointer** (uncaptured, the cursor is pointing, and its motion is dropped at the edge, so it is never fed and never recorded — whether the window held the pointer is already in the log as the events that are there), and **motion and the wheel are summed per tick** (a 1 kHz mouse sends a thousand events a second and the camera reads their sum; summing at the edge gives `InputState` the same total in the same order of additions and keeps a log's size proportional to ticks). Key repeats are dropped for the same reason. **Everything the edge converts is fed at one tick and recorded when it is fed**: a session's recording is exactly what its camera was flown with, and events still waiting for a tick when the window closes are neither.

**`--record-input <log.jsonl>`** writes the session as an `input::InputLog`: the events, the action map's hash, and a **session header** (`engine.view.session`, version `view::k_fly_version`) in the log header's `session` block ([input](input.md)) — what was drawn (`--scene`, `--mesh`, the procedural scene and its grid, `--grid-instances`), the start camera as a position, a yaw and a pitch, the field of view and near plane, every fly parameter above as the session used it, the number of ticks the session ran, and the build stamp of the binary that recorded it. **`--replay-input <log.jsonl>`** flies that log instead of the window: in the window at the recording's own pace (the same fixed-step clock, fed from the file), or offscreen (`--offscreen`, `--benchmark`, `--marker-captures`) at one frame per `tick_hz / 60` ticks, four at 240 Hz, whatever the live frame rate was — a replay benchmark measures the path the player flew at a steady nominal 60 Hz, which is what makes it repeatable, not the frames the player happened to see. It ends when the log's ticks do, or at `--frames`. A replay that names no scene draws the header's; one that names another draws that and says so. `--marker-captures <dir>` writes `tick-NNNNNNN.png` for every tick where `marker` was pressed, each drawn from the marker's own camera and clock after the frames (eight frames at its camera, then the capture), so no grouping of ticks into frames can move one. It is refused together with `--record-input` (a replay is already a recording), `--camera-path` (a replay starts where its recording started), `--animate`, `--morph-animate`, `--reference`, `--fly`, `--census` and `--verify-occlusion` (their own frame loops), and a live session is refused `--offscreen` and `--marker-captures` (nobody can fly a window that is not there, and a live window has no offscreen target to capture from — record, then replay).

### The replay guarantee

**A replay of a recorded session flies the camera the recording flew, bit for bit at every tick, on any machine and any compiler the tree builds for, whatever either run's frame times were — so its marker captures are the recording's to the byte on one machine.** The one thing that can break it is **a change to what the camera computes from the events**: the integration in `fly_camera.cpp` (its arithmetic and its order, the trigonometry, the clamp, the wrap, `frame_index`) or the `InputState` arithmetic it reads, and **the map**. Both are guarded rather than trusted. A log recorded against another action map is refused with both hashes (`input::InputLog::check_map`: the same key would mean another action), and a session header from another integration version is refused rather than misread (`view::k_fly_version`, which a change to the integration bumps). A change that forgot to bump it is caught by the committed trajectory: the synthetic session's hash moves, and `tests/fly_tests.cpp` fails and writes the new trajectory beside its failure. The tunables are not a way to break it — a replay flies with the header's numbers, not today's — and neither is the scene: the camera has no collision, so a replay over another scene flies the same path past different things.

**Driving a window with nobody at it.** `--inject-input <log.jsonl>` pushes a log's keys, mouse buttons, pointer motion and wheel onto the window's own event queue (`window::Window::push_event`) as their ticks come due, so they come back out of `poll()` and go through everything a person's input goes through but the operating system: the edge, the tick, the recording. The session ends at the injected log's tick count, or at an Escape pressed with the pointer given back. It exists for the end-to-end test and for a smoke run on a shared desktop, where synthesizing keystrokes at the OS level would type into whatever window has focus; an injected session never takes the real pointer, and its capture is only the edge's decision about which motion is looking — it starts holding the pointer and then follows the log's clicks and Escapes, never the desktop's focus. Gamepad and joystick events are not injected (their slots belong to real devices).

**The window's numbers.** Presentation is vsync'd unless `--no-vsync`, and each frame is paced by the display unless `--pace off` ([Pacing](#pacing), below). There is no UI module and no on-screen text path yet, so **the window title** carries them: `engine-view — dunes ×86,400 · sun ×3,600 · mouse captured (Esc frees it) — 12.21 ms, p99 13.80 ms (1 s) — tick 4380, recording` — the two rates (the dunes left out where the sand cannot move) and the pointer (`mouse free (click to capture, Esc again exits)` once given back) first, rewritten at once when one of them changes, then the last frame's milliseconds (frame start to frame start) and the 99th percentile over the last second (nearest rank over at most 2,048 frames, `view::FramePacing`, fixed storage), the tick and whether it is recording, four times a second; a replay's says `replay tick N of M` and nothing about a pointer. It is set only when its text changed (`view::format_status`, `time_controls.h`). **`--benchmark <out.jsonl>`** on a live session writes the flythrough's JSONL for the frames the window presented — every record with its GPU passes, `cpu_ms` (everything but the waits for a free frame slot and a swapchain image), `frame_ms`, **`ticks`**, how many camera ticks the frame consumed, and the frame's waits and display times ([Pacing](#pacing)) — and ends with the same `FlythroughSummary` line (`path` is `interactive`, or the replayed log), whose `frame_ms.p99` is the session's pacing number, `ticks` its tick total, and `interactive` the session block below. The last two frames' GPU numbers fold in by bringing their slots around with nothing drawn, so every presented frame has a record.

The summary line on stdout gains `"interactive"` — `null` without the flag, otherwise `{mode ("live" or "replay"), map (the action map's hash), record_input, replay_input, inject_input, session (the header, with the ticks the run flew), trajectory}` — where `trajectory` is `{format, version, tick_hz, ticks, hash, last, markers}`: the hash of every tick's camera, bit for bit, where it ended, and each marker's tick and camera. Two runs with the same `hash` flew the same path to the last bit; that is how the tests and the smoke below compare them.

**The per-frame path allocates nothing in steady state**: the edge's buffer is sized once (a frame converting more than a thousand events grows it), the `InputState` allocates only the first time it sees each bound code, the tick and the camera are arithmetic, and the title is formatted into a stack buffer (SDL copies it). What grows is what a session asked to keep: `--record-input`'s log and `--benchmark`'s records, both amortized and reserved up front.

### Walking

**The owner had only ever flown over the desert** (2026-09-28): to judge a dune's scale from eye height, walk up a slip face and be stopped by a ruin's wall, the camera has to stand on something. **F** switches the session between flying and walking (`walk.h`, `walk.cpp`); **`--walk`** starts a live session walking. F was bound to nothing — W A S D, E and Q, Space and the modifiers, Escape, M and the four rate keys were — and is where a hand on W A S D already is.

- **Walking** puts the camera at eye height on a walker, the look exactly as in flight (the pointer and the right stick, `fly_look`, the first half of `fly_tick` with its arithmetic untouched), **W A S D along the ground in the look's heading** — the camera's forward with its pitch taken out, from `fly_sin_cos` — **Shift to sprint** (the `fast` action), **Space to jump** (and a pad's South). Space is also `lift`'s: a flying camera reads `lift` and never `jump`, a walking one the reverse, so one key means the obvious thing in each. On a pad the left stick walks and its click sprints, which fell out of the actions already bound; the switch itself is the keyboard's.
- **Switching to walking drops the walker onto the ground under the camera**: the highest surface below it — a ruin's wall top, if the camera is over one — or, from under the ground, the surface above; **switching to flying leaves the camera where it is**, and it flies on from the eye. A console line says each switch (`engine-view: walking (physics)`, `engine-view: flying`), and **the window title says which mode it is in**, first: `walking`, `walking (ground only)` or `flying` (`view::TitleMode`, `format_status`).
- **Two walkers, one interface** (`view::Walker`). Where the build carries the physics and scene-collision capabilities, the walker is a **`physics::CharacterBody`** ([physics](physics.md#the-character)) — a 1.8 m capsule of 0.3 m radius with its eye at 1.65 m, a 40° slope limit past which it slides and which it cannot walk up, a 0.35 m step it climbs, gravity and a jump — on the static bodies **`scene_collision::SceneCollision`** keeps round its feet: the ground as a heightfield a tile at 1 m from the scene's ground provider, the ruins' walls and rubble as a compound a tile of each piece's coarse level ([scene_collision](scene_collision.md)). **With physics off** (`ENGINE_WITH_PHYSICS=OFF`, or `msvc-minimal`, where every capability is) the walker **follows the ground**: the feet on the provider's height, a jump an arc of the header's gravity back onto it, and nothing that stands on the ground in the way — the title says `walking (ground only)` and the summary's `walk.collision` is `ground-follow`, with `why` saying so. A scene with no terrain (a `--mesh`, the procedural heightfield) has nothing to walk on: F does nothing there, and `--walk` says so on the console and flies.
- **The collision follows the walker's ticks, not the frames.** The collision ring is the walker's own — one ring of 1.5 tiles round its feet — updated once a **tick**, before the step, from the walker's own position, never once a frame from the camera: a character's contacts are sorted by body id and body ids are handed out in the order bodies are made, so bodies made at frame boundaries — which a live window and its offscreen replay place at different ticks — would make a replay walk somewhere else ([scene_collision](scene_collision.md#why-this-shape)). A streamed scene (`--world`) keeps its drawing ring for the camera beside it; the walker's is separate.
- **A recorded walk replays bit for bit.** The map's third revision (below) is recorded with the session, the session header gains a **`walk` block** — the walk integration's version (`view::k_walk_version`), the walker's numbers and the collision's, and whether it started walking — so a replay walks with the recording's numbers whatever the tunables say now, and a header from another walk version is refused rather than walked somewhere else. The trajectory hash marks every walking tick, and the summary carries the walker's own state chain (`walk.hash`: the character's, or the ground follower's); a replay over the same scene reproduces both, which the end-to-end cases below hold. The camera's own guarantee still holds for flight over any scene; a walk is a function of the scene too, since the ground and the walls decide it. **On moving sand** the collision follows the ground the renderer draws, which a live window's display clock drives, so a walk under a live time-lapse replays against the sand the replay draws; at the game's own rate the sand does not move and the walk replays exactly.
- **The map's third revision** (`view::k_fly_map_revision` 3, 2026-09-28) appends `walk` (F) and `jump` (Space, a pad's South) after the time-lapse's four keys. A log recorded against the first or second revision replays with that revision (`view::default_fly_map_for`), its F pressing nothing, so every session recorded before today flies exactly as it did ([input](input.md)); its header has no `walk` block and reads as a session that starts flying.

### Pacing

**What sets a window's frame time** (2026-09-25, [the second owner session](../experiments/second-interactive-session-2026-09-25.md#present-pacing)). With FIFO the display is the slowest part of the loop, and the frame waits for it in one of three places: for its frame slot (`begin_frame`: the GPU finishing the frame two back, which on this machine's driver cannot start until the display releases its swapchain image), for an image (`acquire`, which on NVIDIA's Windows driver returns at once and leaves the GPU to wait), or in the present call (which blocks while the driver's queue of presents is full). Two throttles make two stable rhythms: **even**, every present blocking about 9–11 ms, and **paired**, one present returning at once and the next iteration waiting 14 ms for its slot and 9 ms in the present — frames starting 0.6 ms and 23.7 ms apart, a pair every two refreshes. The cameras the two draw, read after the slot wait, stand 15 ms and 9 ms apart instead of 12.2, now and then one barely after the other; and the window's input is polled only every 24 ms, so a turn reaches every other frame, out of step with a strafe that reaches every frame — which is the owner's "one frame in between is in a previous position" while strafing with the mouse on an asset ([the strafing stutter](../experiments/second-interactive-session-2026-09-25.md#the-strafing-stutter)). A hitch moves the loop from the first to the second and nothing moves it back: the first owner session was even for 3 s and paired for the remaining 3.5 minutes; the second was paired from its 22nd frame. Behind either rhythm the queue is deep: 55–60 ms, four and a half to five refreshes, from a frame sampling its input to its reaching the display. **The owner's configuration until now — FIFO, three images, two frames in flight, no pacer — is the pairing one**: replayed in the spanned window, 243 of 1,610 frames came more than 20 ms after the one before.

**The display pacer** (`--pace`, default `auto`). Before a frame polls its window and reads the clock, the loop waits until the frame it presented last has been shown (`gfx::Swapchain::wait_for_present`, VK_KHR_present_wait2). Each frame then starts one refresh after the one before, on the display's own clock, with one frame queued, and the three waits above find nothing to wait for: the slot, the image and the present each take under 0.1 ms. Replayed in the spanned window on the final build, 0 and 4 of 1,610 frames came more than 20 ms apart, the frame time was 12.2 ms median and 13.7–14.4 ms p95, every frame reached the display one refresh (12.21 ms) after the one before whenever the compositor flipped the window straight to the display, and each frame reached it within about one refresh of sampling its input instead of nearly five — 46.5 ms sooner, by the display times. The window is polled right after the wait, so input reaches every frame too: in a live session strafing at 30 m/s while turning, each displayed frame strafed 0.32–0.41 m and turned within 0.17° (p95) of what its own time step called for, where the unpaced loop alternated 0.28 m with 0.46 m and turned out of step by up to 0.56°. **How far back it waits is `view::DisplayPacer`'s** (`pacing.h`): depth 1 while the frames make their refresh; two misses within 32 waits — a wait that came a refresh and a half after the last, not made up by an early one after it — mean the work no longer fits, and it waits for the present before the last instead (depth 2: a refresh more latency, a refresh more room), tries depth 1 again after 240 frames, and doubles that hold each time the try fails at once. A frame with 8.3 ms of CPU and GPU work between sampling and presenting still made every refresh at depth 1 at 82 Hz, so depth 2 is for work past about a refresh. `auto` paces the FIFO-family modes (FIFO, FIFO-relaxed, FIFO-latest-ready) and leaves mailbox and immediate unthrottled, since that is what asking for them means; `display` paces any mode; `off` is the loop as it was. A surface that cannot wait on a present is paced by the swapchain's own waits, with a warning. Presents nobody can see (a minimized window's) cost two of the wait's 50 ms timeouts, after which the pacer stops waiting for 120 frames and then looks again.

**In a composed window it trades cadence for latency.** A window that does not cover the display is composed by DWM, which returns a present wait anywhere from about 5 to 20 ms after the last, and whose own display cadence is uneven either way (one frame in six reaches the display a few milliseconds late and the next early, paced or not). There the pacer spends most of its time at depth 2 and cuts the sample-to-display time by about 44 ms (68 ms to 24 ms as the display times report them, which read early), at the cost of the frames sampling on an uneven clock: 12.6 ms median but 18.6 ms p95, where the unpaced loop samples every 12.2 ms. `--pace off` is the even-cadence choice there.

**The knobs, for measuring rather than for flying**: `--present fifo|fifo-relaxed|mailbox|immediate|fifo-latest-ready` (by name, FIFO where the surface lacks one; `--no-vsync` is still mailbox, else immediate), `--swapchain-images <2..8>` (default 3) and `--frames-in-flight <1..3>` (default 2) for the window's loop, `--borderless` (a window with no decorations at the primary display's corner, [window](window.md#borderless-windows-and-presentation)), and **`--windowed`**, which keeps a `--replay-input` with `--benchmark` in the window at the recording's pace instead of offscreen: a replay of the owner's session in the window is the fair before and after of any change here. None of them fixes the pairs without the pacer: at the spanned size mailbox and FIFO-latest-ready pair just the same (the driver paces them like FIFO when the window covers the display), one frame in flight misses refreshes (36 ms frames), and two images behave as three.

**A ceiling on a window its display does not pace** (`view.present.max_hz`, 120 by default; `--present-max-hz <n>` for one run, `0` for none). Mailbox, immediate and `--pace off` leave a frame's cadence to the swapchain's own waits, and a small window has none: a frame of 256×160 draws in microseconds and the window presents thousands of times a second. **Every present of a windowed swapchain goes through the desktop's compositor, and a flood of them stops the compositor composing**: on 2026-09-28, beside one run of this app's own tests, nothing on the owner's desktop repainted — every application, Task Manager included, with only the mouse cursor still moving, which is drawn on the display's own plane — for as long as such a window lived *and for most of a minute after it had closed* (seven stalls in a row, eighty-six seconds in all, measured by timing `DwmFlush()`; the owner could not type and reported it from his phone). It was not the GPU's load (3 to 38% busy), its memory (6.4 GB of 32 GB) or the processor. So the loop starts no frame sooner than a period after the one before it, by yielding until the time comes (the period is a few milliseconds and the system's sleep is coarser).

The stalls grow as a window lives — a quarter second, a half, one, three — which is a backlog building, and the line falls between 240 and 300, about three refreshes' worth of presents a refresh. **The default is 120, half the highest rate measured clean**, because the line was found on one display and will sit lower on a slower one. The ceiling applies only where the display pacer does not pace; a session is its ticks', so a recording replays to the same trajectory under any ceiling, and the test flies the fixture under two of them. The summary's `presentation` block says which ceiling the run had (`max_hz`, 0 where the display paced it) and how many frames it held back (`ceiling_waits`). A flight is vsync'd and paced by its display unless it asks otherwise, and is then untouched by the ceiling; one that asks for `--no-vsync` or `--pace off` is held to it at any size (at 11520×2160 a frame takes about two milliseconds, so such a flight would otherwise present some hundreds of times a second). A measurement that wants the loop's own rate names a higher ceiling or `0`, which warns on stderr, and is run **with nobody working at the desktop**.

**The frame log.** A window's `--benchmark` record carries the frame's waits beside `cpu_ms`: `wait_ms` (the frame slot), `acquire_ms`, `present_ms`, `pace_ms` and `pace_depth`, and `submit_ms`, the part of `cpu_ms` in the renderer's `submit_frame`; and, where the swapchain can say (VK_EXT_present_timing), `shown_ms`, from the previous present reaching the display to this one's, and `latency_ms`, from the frame sampling its input to its reaching the display; and, in an interactive session, the camera the frame drew (`pose_position`, `pose_yaw`, `pose_pitch`) and the simulated time it stands for (`pose_time`), which is what says whether what the viewer saw advanced by a refresh a frame. The summary's `presentation` block says what the swapchain was (mode asked for and got, images asked for and got, frames in flight, the pacer, its misses and changes of depth, borderless, the refresh the driver reports, recreations and suboptimal presents) and gives the percentiles of every wait and display time. Two cautions, both measured: **asking for display times changes how FIFO paces on this driver** — a FIFO chain created with VK_EXT_present_timing never paired in five runs, and every one created without it paired, six runs out of six (present ids and waits alone change nothing) — so a measurement of the unpaced loop as the owner flies it is taken with **`--no-present-timing`**, which asks for none; and **the display times read early**: a frame with 8.3 ms of work between sampling and presenting cannot reach the display 3.6 ms after sampling, which is what they said, so `latency_ms` is low by an offset of at least 5 ms and only its differences between runs are to be trusted. The times are read once, at the end of the run, because on this driver reading them blocks for a refresh ([gfx](gfx.md), "Which present, how deep, and when it was shown").

**Testing.** `tests/fly_tests.cpp` drives `view::DisplayPacer` with made-up waits (steady frames stay at depth 1; a stall is one miss and not two; a compositor's late-then-early waits miss nothing; frames that miss every refresh go to depth 2 on the third, come back after the hold, and a try that fails at once doubles it; a timed-out wait counts for nothing, and two in a row stop the waiting for 120 frames; the refresh estimated from the waits' median when the swapchain gives none), checks `--present`'s names and the display-time bookkeeping by present id, and `tests/interactive_tests.cpp` checks the refusals (unknown modes and depths, the window's flags offscreen, `--windowed` without a replay) and, with a display and a device, that the fixture replayed with `--windowed --benchmark --pace display` flies the committed trajectory, has a record of waits for every presented frame with the ticks adding up to 480, and a `presentation` block naming FIFO, the images and the depth.

## What else the machine was doing, in both hosts' numbers

A frame time from this project's development box is not a frame time from an idle machine: it renders beside GPU jobs that hold most of the card and beside several agent builds. So **engine-view's JSON summary and `render.benchmark`'s result both carry the load they were taken under**, in the same shape and against the same thresholds the CPU benchmark harness uses ([bench](bench.md#measuring-on-a-shared-machine)).

Two blocks, both **added** to the existing fields — nothing was renamed and nothing moved out, because tests and scripts read this line:

```json
"gpu_memory":{"budget_mib":31614,"used_mib":297,"device_local_total_mib":32404},
"machine_state":{"start":{"cpu_total_pct":9.3,"cpu_own_pct":0.0,"cpu_others_pct":9.3,
                          "gpu_util_pct":0.0,"gpu_memory_used_mib":17117,
                          "gpu_memory_total_mib":32607,"session_locked":false,
                          "gpu_lock":null},
                 "end":{...}}
```

`gpu_lock` is the machine-wide GPU lock as the sample found it — `null` when nobody held it, else `{"owner","purpose","expires","mine","expired"}` ([bench](bench.md#measuring-on-a-shared-machine), "The GPU lock") — and a lock somebody else held is a WARNING of its own. It is in engine-view's summary only: the protocol's `MachineState` schema type does not carry it yet, so over `render.benchmark` and `render.evaluate` the lock shows in engine-host's stderr WARNING and not in the result. A host started under a lock-holding wrapper (`gpu-lock.ps1 run`, `gpu-smoke.ps1`, `reference-compare.ps1`) inherits `ENGINE_GPU_LOCK_HOLDER` and reports the lock as `"mine":true` rather than warning about its own parent.

`gpu_memory` is the renderer's ([renderer](renderer.md)), read from the Vulkan device around the run. `machine_state` is sampled **outside** the timed region — before the first frame and after the last — because the sampler sleeps for a quarter of a second to get a CPU percentage and spawns `nvidia-smi` for the GPU reading, and neither belongs between two timed frames. Every field is `null` where the platform could not answer, so "quiet" and "not measured" are different answers; no process names are ever reported.

**Read the two together.** In the line above the Vulkan budget says 31,614 MiB of 32,404 MiB were available to this process while `nvidia-smi` says 17,117 MiB of the card were in use: the budget does not fully see a CUDA tenant, so `device_local_total_mib - budget_mib` is a lower bound on what others hold and `gpu_memory_used_mib` in `machine_state` is the number that answers "is somebody else on this GPU".

When other processes used more than 10% of the CPU or the GPU was more than 20% busy at either end of the run, both hosts write **one WARNING line to stderr** — the same sentence `foundation/bench` prints, for the same reason: stdout is the summary and the protocol, and a caveat that corrupted either would be worse than no caveat. engine-view writes it **before** the summary line and then flushes the summary whole, so the summary is the last line of the two streams merged and never has the caveat spliced into it: stdout into a pipe is fully buffered, and until 2026-09-24 the summary went into the buffer first and out at exit, which only happened to put it last — and split any summary longer than the buffer, which an interactive session's is, around the caveat. It does not mean the numbers are wrong; it means they are upper bounds, and a write-up that quotes them owes its reader the "Machine state" line ([docs/experiments/README.md](../experiments/README.md)).

`render.benchmark`'s result went to `@version(2)` for this, and `RenderStats` with it: `stats.gpu_memory` and `machine_state` are `@since(2)` with defaults, so an older client reading the result sees exactly the fields it saw before.

**Multi-view over the protocol.** `RenderSettings` went to `@version(2)` for this: `views` (`single`, `surround3`, `panini`), `side_yaw_deg`, `panini_d` and `peripheral_lod` are `@since(2)` with the single-view defaults, so both hosts spell the layout the same way and parse it with the same function ([settings.h](renderer.md#public-api)). `RenderStats` went to `@version(3)` and gained `views` — one `RenderViewStats` per view with its rectangle, its source extent, its tier, its visible pairs and its milliseconds by pass — beside `view_layout` and `oversample`. Changing the layout between calls rebuilds the GPU scene and the renderer the way any other settings change does, because the per-frame working set is sized by the view count. This is the path E9 measured through, since it renders offscreen at 11520×2160 on a machine whose window would not be that big.

**Where there is no GPU**, every `render.*` method fails with error code **1007 `RenderUnavailable`** and a message naming the adapter and what it lacks — no Vulkan loader or driver, no 64-bit buffer atomics, or, for `"raster":"rt"`, an explicit `"shadows":"rt"` or the reference integrator, the sentence the adapter's own verdict carries about ray tracing (`renderer::unavailable_reason`), which names the missing extension: on the Pascal server, "NVIDIA TITAN Xp cannot trace rays: no VK_KHR_ray_query and no VK_NV_cluster_acceleration_structure: …". A device without mesh shaders is not unavailable: `"raster":"hw"` resolves to the vertex path there, and the scene info says `"raster":"vertex"`. It is a code of its own so a client can tell "this machine cannot render" from "you asked for something wrong" ([protocol](protocol.md)); the end-to-end test skips on it exactly as engine-view's suite skips on exit 3, which is what lets one suite run on the hosted CI runners and on the GPU machines alike.

## engine-mcp: the MCP bridge

```
engine-mcp [--host <path>] [--host-arg <arg>]... [--mount <scheme>=<dir>[:rw]]... [--workspace <dir>]
           [--actor <name>] [--role <name>] [--task <id>] [--roles <file.json>]
           [--call-timeout <s>] [--long-call-timeout <s>] [--log <spec>]
engine-mcp --help | --version
```

[Plan 06 §6.3](../plan/06-agent-tooling.md#63-mcp-bridge)'s bridge: a Model Context Protocol server on stdin and stdout — newline-delimited JSON-RPC 2.0, MCP's standard stdio transport — that an agent's client (Claude Code, Claude Desktop, any MCP client) starts as a child process. It starts one `engine-host --stdio` of its own and turns curated tools into engine protocol calls. MCP is the cognitive interface and the protocol the mechanical one: the bridge is where the coarse tools, their documentation, attribution rules, pagination, the workspace files and the errors that say what to do next live, and the protocol stays the fine-grained surface the editor, the CLI and the tests use.

**Why a separate process that spawns the host, rather than a second front end on the dispatcher.** The methods an agent needs are not all in one library: `doc.*`, `session.*` and `schema.*` are `domain/protocol`'s, but `render.*` is registered by engine-host over `systems/renderer` ([protocol](protocol.md#methods-an-app-registers-and-render)), and the only thing that has every method is the host. A bridge that linked the dispatcher would have to link the renderer too and would become a second host. As a client it is exactly what engine-cli is — it spawns engine-host through `platform::Process` and writes one request line per call — which is also the plan's shape: the editor, the CLI and this bridge are equal clients of one server ([02](../plan/02-architecture.md)). **One host per bridge** keeps session ownership simple: every session id and scene id an agent sees was made by this bridge's host, nobody else can close them, and they all end together when the client ends the MCP session. Plan 02 describes the bridge as restartable without disturbing the engine; that needs a host that outlives its clients (the persistent-host mode under "Not yet" above), and until one exists the bridge owns its host. Documents do not care: every committed change is on disk before its response, so a new bridge reopens a document exactly where the last one left it.

| Flag | What |
|---|---|
| `--host <path>` | the engine-host to start. Default: beside engine-mcp, as engine-cli finds it. The two are built together: the build makes `engine-mcp` depend on `engine-host`. |
| `--host-arg <arg>` | appended to the host's command line as given; repeatable (`--host-arg --tunables --host-arg t.json`, `--host-arg --log --host-arg info`). Every host the bridge starts gets them, a replacement too. The deadline test passes the host's test hook `--debug-hang` this way. |
| `--mount <scheme>=<dir>[:rw]` | forwarded to the host; repeatable. |
| `--workspace <dir>` | where bulk results go (below). Default `./mcp-workspace` in the directory the client started the bridge in, which `.gitignore` ignores at the repository root. Made absolute at startup and created on the first write. |
| `--actor <name>` | the attribution actor of a mutation that names none. Default `mcp`. |
| `--role <name>`, `--task <id>` | the attribution role and task of a mutation that names none (or names a blank one). No default: without the flag the field is recorded as the call gave it ([below](#attribution-errors-and-the-workspace)). With `--roles`, `--role` is also the role configuration every call runs in ([below](#roles-leases-and-proposals)). The bridge hands `--actor`, `--role` and `--task` to its host as the host's identity. |

**stdout belongs to MCP alone.** Every diagnostic — the bridge's log, engine-host's own warnings (its stderr is inherited), a startup failure — goes to stderr, which an MCP client keeps as the server's log. A bridge that cannot start its host exits 2 without writing a byte to stdout; a usage error exits 2; `--help` and `--version` exit 0. **It never opens a socket**, and no named pipe either: it is an anonymous pipe on both sides, so it raises no firewall prompt and there is nothing any other process could connect to (the reader thread of [Deadlines](#deadlines) exists so that it can stay that way), and `tools/ci/check-no-listeners.ps1` (which probes every built executable with `--help`) and `tools/package-tests.ps1` (which takes every `engine-*` binary) cover it with no change.

**MCP, as far as the bridge speaks it.** `initialize` answers with the client's `protocolVersion` when it is one of `2025-11-25`, `2025-06-18`, `2025-03-26` or `2024-11-05`, and with the newest otherwise (the client then decides, which is MCP's rule); the capabilities are `tools` only, with `listChanged: false`, and the result carries `instructions`, a paragraph telling a model how the tools fit together. `notifications/initialized` and every other notification get no answer; `ping` answers `{}`; `tools/list` returns every tool in one page; `tools/call` runs one. What a result may carry follows the agreed version: `title`, tool `annotations` (read-only, destructive and idempotent hints, and `openWorldHint: false` on everything, because a tool touches nothing but this engine and its files), `structuredContent` and `resource_link` blocks each appear from the version that introduced them. Batches are refused with -32600 (MCP dropped them in 2025-06-18), and resources, prompts, completion and logging are -32601: bulk data reaches an agent as files it reads with its own tools, which is [06 §6.1](../plan/06-agent-tooling.md#61-principles)'s rule and needs no resource protocol. A call is answered before the next line is read, so there is never anything in flight for `notifications/cancelled` to cancel.

### Input schemas are generated, not written

At startup the bridge asks its host for `engine.methods`, and for each tool takes the params type of the method it calls and walks it with `schema.describe`, turning each field's type as the host spells it (`u32`, `engine.doc.Command[]`, `engine.protocol.RenderCamera?`, `map<string, json>`) into JSON Schema: integers with their ranges, `id128` as a 32-hex-digit pattern, `vec3` as three numbers, `json` as the empty schema, an optional as its element (leaving a field out is how "none" is said), an array as `items`, a string-keyed map as `additionalProperties`, an enum as `enum` with each value's documentation folded into the description (so `CommandKind`'s documentation is the command reference an agent reads), and a struct inline, with `additionalProperties: false` because the protocol refuses a field it does not know. The field documentation is the IDL's `///` comments, and the **defaults are the schema's own**: `schema.describe` reports each field's `default` for exactly this ([protocol](protocol.md)), the value a default-constructed object holds, so `open_session.create` says `false`, `capture.width` says `1280` and `load.settings.raster` says `"hw"` without the bridge knowing any of it. An `f32` default is written as its shortest decimal (24.2277, not 24.227699279785156), and the empty string and the null id are left out, because they are what every string and id without a declared default holds and would read as a suggestion.

The bridge then says only what the protocol cannot: which fields it fills or hides (`out_dir`, `offset`, `flip_out`, the attribution timestamp the host stamps), which are required (the protocol has no such notion — an absent field is its default), the fields of its own (`load`, `cursor`, `limit`, `detail`, `name`, `heatmap`, `min_level`, `category`, `method`), and prose appended after the engine's. A field added to a params struct therefore reaches the tool by rebuilding the host, with no edit here, and a tool whose method the host does not serve is not offered at all. The top level of every call is checked against the generated schema before anything is sent, so an unknown or missing argument comes back naming the arguments the tool takes. The measured cost of inlining everything: `tools/list` is 69.2 KB for 28 tools, 43.1 KB of it `capture`, `benchmark` and `evaluate`, whose `load` carries the whole of `RenderLoadParams` and `RenderSettings` with their documentation (2026-09-24; it was 66.7 KB that morning, and the 2.5 KB between is `RenderSettings.rt_budget_mib`, which landed that afternoon and reached the five places the settings appear by rebuilding the host and nothing else). With the five day-one operation tools it is 81.9 KB for 33 (measured on `msvc-debug` the same evening, after the cascaded shadow maps' settings had landed too); the five take 8.6 KB of it, 4.4 KB of that `build_content`, whose `options` carry every build flag with its documentation. With `scenes` and `unload` and the attribution defaults' notes it is **83.6 KB for 35** (measured on `msvc-debug`, 2026-09-24, started without `--role` or `--task`): `scenes` is 0.5 KB, `unload` 0.7 KB, and `capture`, `benchmark` and `evaluate` 12.6, 16.7 and 17.9 KB (that count of 35 left out `materialize`, which was there too). With plan 06 §6.5's six tools and the optional `attribution` that `undo`, `redo` and `merge_layers` took from their params types in the same change, it is **96.1 KB for 42** (measured on `msvc-debug`, 2026-09-25, started without `--role` or `--roles`): `acquire_lease` 2.4 KB, `renew_lease` 1.2, `release_lease` 1.0, `leases` 0.7, `propose_layer` 1.8 and `promote` 2.1. `$defs` and `$ref` would share the settings between `load` and a benchmark's per-call `settings`; they are not used yet because inline schemas are the form every client reads ("Not yet" has what they would save).

### Attribution, errors, and the workspace

**Every change through `doc.apply` carries attribution** — `create_object`, `set_property`, `reparent`, `delete_object` and `apply` — because [06 §6.4](../plan/06-agent-tooling.md#64-transactions-checkpoints-rollback) records actor, role, task and rationale with every commit. `attribution` is required; `actor` defaults to `--actor`, and `role` and `task` to `--role` and `--task` when the bridge was started with them — filled in where the call leaves the field out or blank, overridden by any call that gives one, and stated as the field's `default` in the generated schema exactly when there is one (a schema that promised a default the bridge does not fill would be a lie a model acts on). A **missing or blank `rationale` is refused** before anything reaches the host, with a result that says to add one sentence saying why. Without `--roles` the two flags are the attribution half of [06 §6.5](../plan/06-agent-tooling.md#65-permissions-concurrency-and-leases)'s roles and nothing more. **With `--roles`, `--role` is the name that selects a role configuration** ([below](#roles-leases-and-proposals)): its allowed tools, layers, tiles, types and review rule come with it, and the attribution's `role` stays the name it was selected by, so a journal written before role configurations existed reads the same. `--task` is recorded with every lease the agent takes (06 §6.8's ledger task, when the ledger exists). A transaction the host rejects (`committed: false`) is an error result listing every diagnostic, and says that an atomic batch rolled back whole. `doc.merge`, `doc.undo`, `doc.redo` and `doc.add_layer` take no attribution in the protocol, and `merge_layers` records the host's own.

**Errors come in two kinds.** A message that is not a request the bridge can serve — unparseable (-32700, id null), a batch or not an object (-32600), an unknown method (-32601), an unknown tool or `arguments` that are not an object (-32602, with the tool names in `data`) — is a JSON-RPC error, and the bridge keeps serving. Everything that goes wrong *inside* a tool is a tool result with `isError: true`, which a model reads and can act on: the first line says what failed, then the protocol's code and name (`error 1003 NotFound: no document at …`), then each `{path, message}` diagnostic of an invalid-params error, then `Hint:` and one sentence of what to do, chosen by code and, where it helps, by method (`session.open`'s NotFound says to pass `create: true`; a missing scene says to pass `load`; SessionNotFound says sessions do not survive a host restart). `structuredContent.error` carries the same fields. **Error 1007 reads "No GPU on this machine can do this: …"** with the adapter's own verdict sentence and a hint that says the document tools still work, so an agent on a CI runner or a Pascal box is told the machine's limit rather than a mistake in its request.

**A host that dies is noticed on the next call**, which finds its stdin refusing the write or its stdout ending before the answer: a dead process closes its pipes at once. The bridge reaps it and answers `engine-host exited with code N; …` as an error result whose hint says the next call starts a new host and that open sessions and loaded scenes did not survive (documents are on disk: `open_session` again). The next call does start one, and `host_info` reports its generation. On POSIX the bridge ignores SIGPIPE, so a write to a dead host is a failed write rather than the signal that would end the bridge too. A host that is alive and never answers is the deadline's ([below](#deadlines)).

**The workspace.** Tools that produce files write them under `--workspace` and return `file://` URIs — in the result's text, in `structuredContent`, and as `resource_link` content blocks — with a short summary. Nothing bulk is ever inlined: a capture's answer is under 8 KB whatever the resolution, and the end-to-end suite asserts it.

```
<workspace>/captures/<name>.png, <name>.ids.bin, <name>.ids.json, <name>.depth.png, <name>.normals.png, <name>.json
<workspace>/benchmarks/<name>.json   (and <name>.jsonl: the flythrough summary line engine-view's --benchmark file ends with)
<workspace>/compares/<name>.flip.png, <name>.json
<workspace>/evaluations/<name>.realtime.png, <name>.reference.png, <name>.flip.png, ..., <name>.json
<workspace>/adapters.json
```

`<name>.json` is always the host's whole result, so the summary can stay short without losing anything. A `name` the caller gives is used as given, so a `baseline` can be rewritten on purpose; a generated one is `capture-001`, `capture-002`, … — the first number whose `<name>.json` is free, so two calls, or two bridge runs on one workspace, never overwrite each other.

**Scenes.** A render tool takes `load` — `RenderLoadParams`, generated like every other schema: a mesh, a scene file, or a procedural scene, with `settings` — or the `scene` id an earlier render tool returned. The host keeps every scene it loads until `unload` releases it or the host exits, so the bridge remembers each distinct `load` (by its canonical JSON) per host and reuses the scene when the same `load` comes again; the result says `"reused": true`. **That reuse is why a long session needs `unload`**: an agent comparing twenty assets loads twenty scenes, and each one's GPU state — buffers, textures, acceleration structures, a renderer sized to the last frame it drew — stays until the host goes, which behind engine-mcp is when the agent's client goes. `scenes` shows what is held (and, for each, the `load` that made it), `unload` lets one go, and the bridge forgets its `load` at the same moment, so the next render tool given that `load` loads it again instead of naming a dead id. A scene is the host's and not a session's: closing a document unloads nothing ([protocol](protocol.md#methods-an-app-registers-and-render) says why). A new host, after a death or a deadline, starts with none.

### Roles, leases and proposals

[Plan 06 §6.5](../plan/06-agent-tooling.md#65-permissions-concurrency-and-leases) through the bridge; the mechanism is the host's ([protocol](protocol.md#roles-leases-and-proposals)), and the bridge adds three things.

**The role configuration decides which tools are offered.** At startup the bridge asks its host for `engine.roles`; when a roles file is loaded, the role its calls run in — `--role`, or the file's `default_role` for a bridge started without one — lists the methods it may call (every read-only method, and the writes its patterns name), and a tool is offered only when it may call all of that tool's methods. A QA bridge is not shown `create_object` at all rather than shown it and refused: a tool that always fails only teaches a model to call it. The host checks every call anyway. `host_info` reports the configuration and how many tools were withheld.

**A call cannot name another role.** Under a role configuration, an attribution whose `role` is not the bridge's is refused before it reaches the host, with a hint that the role is chosen when the bridge is started. The protocol has no authentication — a role is what a call says it is — so this is the one place an agent is kept in the role it was given; the bridge is also what hands the host `--actor`, `--role` and `--task`, so a call that names no role (`add_layer`, `undo`) runs in the bridge's.

**Leases and proposals are six tools**: `acquire_lease`, `renew_lease`, `release_lease`, `leases`, `propose_layer`, `promote` (the table above). The protocol's `lease.require`, `doc.reject` and `engine.roles` are left to it: a director's switches, and what the bridge reads for itself. The working protocol an agent follows is **acquire, read, edit, promote, release** — in particular a lease is released after the proposal is promoted, not after the edit, because an edit unmerged in a proposal is exactly what the lease protects ([E12](../experiments/e12-proposal-layers-and-leases.md) found what releasing early costs). Errors 1008 Forbidden, 1009 LeaseConflict and 1010 LeaseRequired come back with hints that say which of those steps is missing.

### Deadlines

Every protocol call the bridge makes waits for its answer with a **deadline**, and a host that stays silent past it is taken for hung: the bridge kills it, answers the tool call with an error that names the method and the seconds waited (`engine-host did not answer session.list within 120 s, so the bridge stopped it`), and starts a new host on the next call — generation + 1, exactly the shape a host that died already had, and with the same hint (sessions and scenes did not survive; documents are on disk), plus which flag to raise if the call was legitimately long. `structuredContent.error` carries `timed_out: true` and `seconds`. Before this a host that was alive and never answered — a driver stuck in a call, a deadlock — blocked the bridge, and with it the agent, forever.

**Two classes, two defaults.** A call's deadline is the one of its class:

| Class | Methods | Default | Flag |
|---|---|---|---|
| long | `render.load`, `render.capture`, `render.benchmark`, `render.evaluate`, `render.compare`, `content.build`, `session.run_headless`, `engine.run_tests`, `session.save_game`, `session.load_game` | **3600 s** | `--long-call-timeout` |
| quick | everything else: `doc.*`, `session.*` but `run_headless`, `save_game` and `load_game`, `schema.*`, `engine.*` but `run_tests`, `log.tail`, `gpu.adapters`, `render.unload`, `render.scenes`, and the startup's own `engine.methods` and `schema.describe` | **120 s** | `--call-timeout` |

The long class is the work whose time grows with the content or with what was asked for; the quick class is bookkeeping over a document or the host's own state, where a host that takes two minutes has stopped. 0 turns a class's deadline off. **A reference render does not come near the hour.** The corpus's heaviest reference (`content/test-scenes/`, 1024 samples at 640×480, three bounces) took 0.28 s of tracing and 3.4 s for the whole `render.evaluate` on the development machine's RTX 5090, and a 4,096-sample reference at 1920×1080 took 2.4 s and 17.5 s — both in `msvc-debug`, whose image metrics are most of that wall time, beside other work (others 21% of the CPU, the GPU 13% busy: upper bounds). That is over two hundred times inside the long deadline for a render sixteen times the corpus's largest, and the baseline-tier GPUs cannot run the reference at all. What *can* pass an hour is a request far outside anything the project runs — `reference.spp` goes to 65,536 and a frame to 16384×16384 — and that caller raises `--long-call-timeout` or sets it to 0; the error's hint says so.

**How the read waits: a reader thread.** The read of the host's stdout needs a timeout, and a blocking pipe read has none. POSIX would give one through `poll` on the descriptor, but Windows gives one only through overlapped I/O, which anonymous pipes (`CreatePipe`, what `platform::Process` makes) do not support; the only pipe that does is a *named* one, an object in the machine's pipe namespace that another local process could open between its creation and the child's — a listener in all but name, which this bridge must not have. So each host gets one reader thread (`host_client.cpp`), started with it and joined when it is reaped: the thread blocks in the kernel's read — no busy loop, no sleep between polls — hands each whole line over under a mutex, and wakes the caller through a condition variable whose `wait_until` is the deadline. One code path on both platforms, and the pipes stay anonymous. On a deadline the host is killed, which closes its end of the pipe and ends the thread's read; on Windows the read is also cancelled (`CancelSynchronousIo`), because a process the host started inherits that end — `CreateProcess` passes every inheritable handle, and the machine-state sampler runs nvidia-smi around every benchmark — and would otherwise hold the join until it exited. The write of a request has no deadline of its own: a host that answered the previous call is back in its read and takes a whole line before dispatching it, so a hang is always after the write, where the read's deadline is. The bridge's own shutdown is bounded the same way — a host still there the short deadline after its input closed is killed rather than waited for.

**The test hook.** A hung host is made on purpose with engine-host's `--debug-hang <method>` (under **engine-host** at the top of this page), handed to it through `--host-arg`, so the end-to-end case needs no fault injection in the bridge: `--call-timeout 1 --host-arg --debug-hang --host-arg session.list` makes `list_sessions` come back after one second (measured 1.004 s) with the error, a new pid and generation 2 on the next call; `--long-call-timeout 3` with `content.build` hung makes `build_content` come back after three (3.013 s) and not after the quick deadline of one.

### Registering it with Claude Code

Build a preset, then register the binary. For yourself, in this project (`--scope local`, kept in your own Claude Code settings rather than in the tree, because the command line names paths on your machine):

```powershell
tools/dev.ps1 build -Preset msvc-release
claude mcp add --transport stdio --scope local engine -- `
  D:/workspace/game_engine/build/msvc-release/bin/engine-mcp.exe `
  --workspace D:/workspace/game_engine_local/mcp-workspace --actor claude
```

or the same as an `.mcp.json` entry (`--scope project` writes one at the repository root; do not commit one with machine paths in it):

```json
{
  "mcpServers": {
    "engine": {
      "type": "stdio",
      "command": "D:/workspace/game_engine/build/msvc-release/bin/engine-mcp.exe",
      "args": ["--workspace", "D:/workspace/game_engine_local/mcp-workspace", "--actor", "claude"]
    }
  }
}
```

`/mcp` in Claude Code then lists the server and its 45 tools. Add `--role` and `--task` to the arguments to have every edit's attribution carry them, `--roles D:/workspace/game_engine/content/roles/roles.json` to make `--role` a role configuration that restricts what the agent may change, and `--long-call-timeout` if the session will ask for renders past the hour. Two things are worth knowing first. **A running server locks its executables on Windows**: while a Claude Code session has engine-mcp open, `engine-mcp.exe` and the `engine-host.exe` it started cannot be replaced, so rebuilding that preset fails at the link until the session ends or `/mcp` reconnects — register a preset you are not rebuilding, or a copy of its `bin/` directory. And a render tool on this shared machine is GPU work like any other: `benchmark` numbers carry the machine state and say when they are upper bounds ([bench](bench.md#measuring-on-a-shared-machine)).

### Not yet

- **Resources and prompts.**
- **Progress notifications** for a long `evaluate` or reference `capture`. The host has no channel for them: its dispatcher answers a request with one line and writes nothing else, and the one place progress exists — the reference renderer's batch loop — has no way out of `render_methods.cpp`. It would take a per-batch callback on `renderer::ReferenceRenderer::render`, the host writing JSON-RPC notifications (no `id`) on stdout while the call runs, and the bridge forwarding each as MCP `notifications/progress` when the `tools/call` carried `_meta.progressToken`. The bridge half is small now: the reader thread of [Deadlines](#deadlines) already sees every line the host writes while a call waits, and skips what is not the answer with a warning; a notification would be forwarded instead. `session.events` is not that channel — it is a cursor a client polls over a document's journal, and a render has no document.
- **A deadline for one call.** Both deadlines are the bridge's flags; a tool argument that raised them for one render would let an agent ask for a render past the hour without restarting its server.
- **Tools for a director's switches** — `lease.require`, `doc.reject` — and for reading `engine.roles` directly. They are protocol methods an agent can reach through engine-cli; a tool is added when an agent's loop needs one ([06 §6.3](../plan/06-agent-tooling.md#63-mcp-bridge)'s rule).
- **Attaching to a host that is already running** instead of starting one.
- **`$defs` to shrink the render tools' schemas.** Each tool's `inputSchema` is a document of its own, so a definition can be shared only inside one tool: `RenderSettings` is 5.3 KB inline and appears twice in `benchmark` and `evaluate` (`load.settings` and the per-call `settings`) and once in `capture`, so `$defs` would save 10.7 KB of the 83.6 KB (13%). That is not worth trading away the one form every client reads, and `$ref` beside a sibling `description` — which the per-call `settings` needs, since its documentation differs from the type's — is read differently by draft-07 and 2020-12 validators. Revisit if a client limits a server's `tools/list`, or a second struct comes to be shared.
