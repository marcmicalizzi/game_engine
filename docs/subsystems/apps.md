# apps: engine-host, engine-cli, engine-view, engine-content, engine-input, engine-image (apps)

**Purpose.** The first executables (docs/plan/02-architecture.md §2.2, ADR-0001). `engine-host` is the engine as a headless server: in Phase 0 it runs in `sim` mode only and speaks JSON-RPC 2.0 over stdio, one request per line in and one response per line out. `engine-cli` is the thin scriptable client for humans, agents, and CI: it spawns a host, optionally opens a document, sends one method, prints the result, and exits. Because sessions persist their journal and undo position on disk (see [doc](doc.md) and [protocol](protocol.md)), a sequence of separate `engine-cli` invocations behaves like one editing session, which is what the Phase 0 exit criterion asks for and what the end-to-end test checks. `engine-view` is the window on the renderer, and `engine-content` is the content build on the command line: the step that turns a source mesh into the derived form the renderer loads.

**engine-host.**
```
engine-host [--stdio] [--request <json>] [--mount <scheme>=<dir>[:rw]]... [--log <spec>] [--log-json <path>] [--tunables <file>]
```
stdout belongs to the protocol. Log records go to an in-memory ring (`log.tail` reads it), warnings and above to stderr, and optionally every record as JSON lines to a file. Assertion failures are routed through the log before the process aborts. `--request` answers one request and exits, for scripts that do not want a pipe.

**engine-cli.**
```
engine-cli [--host <path>] [--doc <dir>] [--create] [--name <name>] [--mount <spec>]... [--compact] [--report <file>] <method> [params-json]
```
With `--doc` the CLI opens the document first (creating it with `--create`) and injects the session id into the params. Results print as pretty JSON (or one line with `--compact`); errors print `error <code>: <message>` and any diagnostics to stderr and exit 1; usage problems exit 2. The host is found beside the CLI unless `--host` says otherwise.

`--report <file>` writes the same result to a file as one JSON document — `{"tool", "method", "generated_utc", "result"}` — **after** printing it, so a file that cannot be written never costs the caller the answer it already has. It is generic across methods and exists for one: `engine-cli gpu.adapters --report adapters.json` is what somebody runs on a machine no one here can log in to, and the file that comes back carries the whole requirements table and the verdict for every device on it (see [gfx](gfx.md#what-a-device-has-to-have)). The timestamp is there because such a file is read weeks later.

**Example (the exit criterion).**
```bash
engine-cli --doc ./world --create --name World session.info
engine-cli --doc ./world doc.apply '{"commands":[{"kind":"CreateObject","id":"00000000000000100000000000000001","type":"engine.content.AssetProvenance"}],"attribution":{"actor":"me","role":"environment","task":"t1","rationale":"first object"}}'
engine-cli --doc ./world doc.objects
engine-cli --doc ./world doc.undo
engine-cli --doc ./world doc.redo
engine-cli --doc ./world doc.add_layer '{"name":"quest"}'
engine-cli --doc ./world doc.diff '{"from_layer":"base","to_layer":"quest"}'
engine-cli --doc ./world doc.merge '{"base_layer":"base","ours_layer":"quest","theirs_layer":"other","output_layer":"merged"}'
engine-cli gpu.adapters                       # what the machine's GPUs support (see gfx.md)
engine-cli gpu.adapters --report adapters.json  # the same, as a file to send back
```

```

            [--raster direct|hw|vertex|sw|auto|rt] [--sw-px <px>] [--view id|tri|depth|shaded|normals|uv] [--orbit <d>] [--no-occlusion] [--no-cone]
            [--mesh <file.gltf|file.glb|file.clusters>] [--procedural heightfield|shredded-atlas] [--scene <file.json>] [--grid-instances <n>] [--no-cache] [--ddc <dir>] [--no-lights] [--shadows off|rt]
            [--uv-seams none|protect|lock] [--normal-seams none|protect|lock] [--uv-weight <n>] [--normal-weight <n>]
            [--deform none|identity|wave|lattice] [--deform-amplitude <a>] [--deform-pool-mib <n>]
            [--rt-templates]
            [--views single|surround3|panini] [--side-yaw <deg>] [--panini-d <d>] [--peripheral-lod <mult>]
            [--animate [clip]] [--anim-speed <x>] [--morph <name|index>=<w>]
            [--morph-animate] [--static-shape-kib <n>]
            [--stream] [--page-budget <MiB>] [--page-budget-pct <n>] [--upload-budget <KiB>] [--page-source auto|file|host] [--fly <a> <b> <n>]
            [--reference <spp>] [--bounces <n>] [--finest] [--spp-batch <n>]
```
The engine's first window (windowed mode). A procedural heightfield is built into a cluster LOD DAG (`geometry`), uploaded behind device addresses, culled and LOD-selected on the GPU every frame (`cluster_cull.slang`, threshold `--lod` in pixels, default 1), and drawn one mesh-shader workgroup per surviving cluster through an indirect draw into the swapchain with a reversed-Z depth buffer while the camera orbits and zooms between 8 and 36 units so the cut changes visibly; each cluster gets its own color, so the picture is also the cluster-partition debug view. `--no-cull` draws every leaf cluster instead. `--raster` picks the path: `direct` is mesh shaders straight to color with a depth buffer; `hw` (default), `vertex`, `sw`, and `auto` rasterize into the 64-bit visibility buffer through mesh shaders, the vertex-shader baseline tier (chosen automatically on GPUs without mesh shaders), the software rasterizer, or mesh shaders and software split at `--sw-px` pixels of projected cluster diameter, then resolve it; `rt` replaces rasterization with ray queries (NVIDIA RTX only, exit 3 elsewhere): the cull pass's visible list becomes cluster acceleration structure build records on the GPU (`clas_records.slang`), the CLAS, cluster bottom-level, and top-level structures are built in the same frame with no CPU round trip, and `ray_visibility.slang` traces one ray per pixel into the visibility buffer, which the resolve then shades exactly as it shades a rasterized one (`gpu_ms.rt` is the four builds, `gpu_ms.trace` the rays; the FlightHelmet's 253-cluster cut builds in 0.16 ms and traces in 0.02 ms at 800×600 on the RTX 5090) (`--view` shows materials lit by a sun with smooth vertex normals by default, or cluster colors, triangle shading, depth, normals, or UVs; three materials, sand, rock, and snow, are assigned by the height of each cluster's center, and sand and rock sample a procedural ripple texture through the bindless set at different UV scales). The shaded view lights the surface with the resolve's physically based BSDF (`brdf.slang`, see [gfx](gfx.md)): a directional sun, a sky hemisphere, and two point lights orbiting the scene out of phase, one warm and one cool, whose radius of influence and intensity scale with the scene radius (intensity with its square, because the falloff is inverse square) so a 2 cm mesh and the heightfield are lit alike. They are passed per frame behind the `ResolveParams` block in the same host-visible buffer, and `--no-lights` turns them off, which is how to measure or compare a picture with only the sun in it. On the heightfield they change the picture by up to 110 of 255 and by 9 on average. `--orbit` fixes the camera distance for measurements; camera distances scale with the scene radius (10 for the heightfield). `--mesh` renders a glTF 2.0 or GLB file instead of the heightfield (`assets::load_gltf`, then `geometry::weld_vertices` so exported duplicate vertices do not starve the clusters; `tools/fetch-samples.ps1` fetches permissively licensed Khronos samples into `content/samples/`): one cluster LOD DAG is built per primitive and the DAGs are merged (`geometry::merge_cluster_lod`) so that every cluster has exactly one material; the file's metallic-roughness materials become the resolve's material table (base color as albedo, roughness and metallic carried along, and the emissive factor as a constant term unless the material modulates it with an emissive texture, which the resolve has no slot for yet), and each material's base-color, metallic-roughness, and normal images are decoded on the CPU (`image::decode_image`, embedded bytes or a file beside the glTF) and uploaded into the bindless set — one slot per image, shared by every material that names it, base color as sRGB and the two data maps as UNORM, since a roughness or a normal is not a color. An image that fails to decode leaves that slot empty with a warning, and the camera orbits the mesh's bounds.

**What the samples look like now that the maps are read.** The three Khronos models the resolve was compared on, before and after, at `--width 800 --height 600 --orbit 22`. FlightHelmet: the leather crown was one flat olive-brown dome with a single broad sheen, and is now visibly creased and quilted, its stitching and panel seams standing out under the orbiting point lights, the brown warmer and more varied; the metal on the mask frame, the buckles, and the ribbed hose pick up small bright glints where before they were the same dull matte as the cloth; the goggle lens has a defined highlight; and the varnished wooden base has gained a glossy band along its top face. BoomBox: the silver body panel, the handle, and the antenna were a uniform mid-grey and now read as metal, bright with a sharp moving highlight, while the speaker grille has gone from a flat printed dot pattern to a recessed, dark, perforated mesh; the black shell's highlight is tighter and the buttons and dials have relief. Corset: the red brocade was plasticky with a wide sheen and is now dull cloth with the damask pattern in relief, the laces are round cords with a highlight each instead of painted-on lines, the eyelets glint, and the cream mannequin is matte with its seams visible; the base disc is glossier than the body it holds. In short: cloth and leather have become dull dielectrics, buckles and the BoomBox's metal have become metal, and the normal maps put surface detail where the geometry has none. `--mesh` also takes a `.clusters` container ([geometry](geometry.md)) and renders it without importing or clustering anything: the DAG, the quantized positions and their grid, the attributes and triangles, the materials from the file's 64-byte records — including the metallic-roughness, normal, and emissive slots that live in the record's second half, which an older container leaves at zero and the reader therefore reads as "none" — the material index of every cluster, and the textures — decoded from the file's image paths, resolved against the directory of the source mesh the container names (against the container's own directory when it names none), or from the **encoded bytes the container carries** for an image the source embedded rather than named ([geometry](geometry.md), "Embedded images"). Everything downstream — cull, LOD selection, the four rasterizers, ray tracing, the resolve — is the same code and draws the same picture, and `--raster hw` and `--raster rt` agree to 59 pixels of 480,000 at 800×600 (silhouettes, where a ray and a rasterized edge disagree). **A mesh drawn from its container is the picture its glTF draws, byte for byte** — from the glTF, from a cache miss, from a cache hit, and from a container `engine-content build` wrote, one PNG. That is asserted rather than assumed: `engine-view`'s end-to-end test renders its cube-GLB-with-an-embedded-PNG fixture all four ways and compares the captures as bytes, and the five Khronos samples were checked the same way by hand at 400×300 (`--orbit 22 --shadows off`), each giving one SHA-256 across all four paths — Lantern `cd40d3dd…`, BoomBox `6cec6390…`, Corset `e35a86d8…`, Avocado `0592f581…`, FlightHelmet `f1669cd6…`. The one thing a container still needs from outside is an image the source kept in a file of its own, which it names by path; such an image missing is a warning and an untextured material, as it is for the glTF. Between the two, `--mesh <file.gltf>` looks in the **derived-data cache** first: `<ddc>/clusters/<hash>.clusters`, where the hash covers the glTF's bytes and those of every external buffer it names, the cluster build options, and a cache version constant (`geometry::cluster_cache_key`, `cluster_cache_path`). A hit loads the container; a miss builds as before and writes the entry, the same mesh `engine-content build --cache` writes to the same path, so either program fills the cache and either finds it. The two entries differ in one section: `engine-content` records the source's identity (`source_hash`, section 15) and `engine-view` leaves it zero, which costs an `engine-content build-all` one rebuild of an entry `engine-view` wrote, and nothing else. `--no-cache` skips both. The cache root is `<repo>/ddc`, found by walking up from the executable to the directory holding `AGENTS.md`, or `--ddc <dir>`; with neither, the cache is off with a warning. The FlightHelmet takes 907 ms to import and cluster in `msvc-debug` on an RTX 5090 machine and 31 ms to load from the cache, reported as `build_ms` either way. **A scene of instances.** `--scene <file.json>` renders several meshes and several instances of them instead of one mesh: `{"meshes":[{"path":"...gltf|.glb|.clusters"}], "instances":[{"mesh":0,"translation":[x,y,z],"rotation":[x,y,z,w],"scale":[x,y,z]}]}`, where a mesh path is resolved against the file's own directory, every instance field but `mesh` is optional, and an empty instance list places one identity instance of every mesh. The meshes load exactly as `--mesh` loads one, cache and all, and then go into one set of buffers through `geometry::merge_cluster_meshes`, each keeping its own 16-bit position grid; each mesh's materials follow the last mesh's in one table and each instance's `material_base` points at its mesh's, so the clusters keep mesh-local material indices. `--grid-instances <n>` is the same machinery from one flag: n × n copies of the loaded mesh on a grid three mesh radii apart, with a rotation and a scale that vary per copy and a non-uniform scale on every third, so one run exercises the uniform and the non-uniform path, the cone test's precondition, and the LOD scaling at once. The camera frames the scene's bounding sphere, the union of the instances' transformed mesh bounds, and `--no-cull` is ignored with more than one instance because a scene draws through the cull pass. On the RTX 5090, `--grid-instances 5` on the FlightHelmet (25 instances, 58,700 pairs) at 800×600 culls in 0.023 ms, rasterizes 201 visible pairs in 0.004 ms through mesh shaders, and through `--raster rt` builds the frame's cluster acceleration structures in 0.49 ms — most of it the 25 bottom-level builds, which share one scratch buffer and so are serialized — and traces in 0.012 ms.

**`--procedural shredded-atlas`, and the four flags that say what the LOD builder is told.** With no `--mesh` and no `--scene`, engine-view draws a procedural scene, and there are now two: the dunes-and-ridges `heightfield` (the default, unchanged) and `shredded-atlas`, the UV-atlas stress fixture of [geometry](geometry.md#the-shredded-atlas) — a torus cut into hundreds of small atlas islands with a probe texture whose colour encodes atlas position. It exists because a LOD collapse that crosses an island edge is invisible on any mesh whose atlas is a few large islands, which is every Khronos sample, and obvious on this one. `--uv-seams`, `--normal-seams`, `--uv-weight` and `--normal-weight` are what the builder is told about seams and attributes; **all four are part of `geometry::cluster_cache_key`**, so `--uv-seams none` builds and addresses its own container and `engine-content build --uv-seams none` writes exactly that one. That is what makes a before-and-after comparison of the seam rule two command lines instead of two builds of the tree, and it is how the numbers in [geometry](geometry.md#what-the-simplifier-is-given-and-why) were taken.

**`--views single|surround3|panini`** and its three knobs are the multi-view layout ([04 §4.6](../plan/04-renderer.md#46-extreme-displays), [renderer](renderer.md#multi-view-a-viewset-over-one-scene), experiment [E9](../experiments/e9-multi-view.md)). `single` is the default and is unchanged in every respect, down to the bytes of the picture. `surround3` divides the target into three monitors with per-monitor off-axis frusta, which is what the project owner's 11520×2160 actually is; `--side-yaw <deg>` is the angle the side monitors are physically turned inward, 0 being a flat arrangement whose three frusta are exactly the three thirds of one wide rectilinear frustum. `panini` renders one wide view rectilinear into an oversampled source and resamples it with a Panini projection of parameter `--panini-d` (0 is the ordinary rectilinear picture, 1 the classic Pannini); the summary reports the `oversample` factor the source needed. `--peripheral-lod <mult>` multiplies the LOD pixel threshold outside the attention region, which for a surround is the two side monitors — a surround player reads them peripherally, so a coarser cut there is the expected behavior and not a compromise. The monitor width, height and bezel gap are parameters of the layout too, but of the module's `Surround3` rather than of a flag: a flag would only be able to say what the target already says, since the rectangles have to tile the swapchain.

The JSON summary gains a `views` block — the layout, the count, the yaw, the Panini `d` and oversample, and a `per_view` array with each view's rectangle, tier and GPU milliseconds by pass beside the totals — and an `rt_bytes` figure for what the acceleration structure chain holds, which is the number that grows with the view count. **A capture at 11520×2160 belongs to engine-host, not here**: engine-view sizes its swapchain from a real window, so the offscreen path (`render.capture`, `render.benchmark`) is what renders a surround-sized frame on a machine whose display is smaller, and it is what experiment E9's numbers were taken through.

**`--reference <spp>`** renders the reference path tracer instead of the real-time frame ([04 §4.8](../plan/04-renderer.md#48-reference-renderer-and-objective-optimization), [renderer](renderer.md#reference-renderer)) — **and opens no window**. A converged picture is minutes of compute with nothing to watch, the machines that will run the nightly comparison have no display, and `systems/renderer` has never needed one, so this path creates the device without the presentation extensions and goes straight to the offscreen contract: load the scene, draw one frame so the frame's acceleration structures exist, then `spp` samples per pixel in batches of `--spp-batch` (default 8) against those structures, then `--capture out.png` and one JSON line. `--bounces <n>` is the number of scattering events after the primary hit (default 3; 1 is direct lighting plus one bounce, which is what the resolve approximates). `--finest` builds the structures from the finest clusters instead of from the frame's LOD cut, so the picture is a reference for the source geometry rather than for the geometry LOD chose. Progress goes to stderr, one line per batch, because stdout is the summary. It needs a device with cluster acceleration structures and ray queries and settings that build them — the default `--shadows auto` does on such a device — and exits 3 with a message where it cannot, exactly as the windowed path does. **`--animate` works under it**, and draws one pose: the offscreen path runs the same `prepare_animation` → `load_scene` → `attach_instances` → one tick the windowed path runs, so the picture is the pose the windowed path's *first* frame would draw and the summary carries `skinned_instances`. It cannot play a clip — one frame is one frame — so `--frames` is ignored and a caller who passed one is told on stderr. Measured on the Fox at 320×240 and 64 samples: the posed reference is 0.0275 FLIP from the posed real-time frame and 0.0675 from a reference of the same scene at rest. The summary line is its own shape, `{"reference":true, "spp", "bounces", "finest", "width", "height", "seconds", "trace_ms", "samples", "visible_pairs", "clusters", "leaf_clusters", "triangles", "instances", "gpu_memory", "machine_state", "captured"}`, where `trace_ms` is the integrator's GPU milliseconds and `seconds` the wall time a caller waited.

```powershell
engine-view --mesh content/samples/FlightHelmet/FlightHelmet.gltf --orbit 22 --width 640 --height 480 `
            --reference 512 --capture helmet.reference.png
engine-view --mesh content/samples/FlightHelmet/FlightHelmet.gltf --orbit 22 --width 640 --height 480 `
            --frames 1 --capture helmet.realtime.png
engine-image compare --json helmet.realtime.png helmet.reference.png --flip helmet.flip.png
```

**`--shadows off|rt`.** With `rt` every light of the resolve casts a ray-traced shadow: the sun and both orbiting point lights trace one terminate-on-first-hit ray each against the frame's own top-level structure, which holds exactly the clusters the frame drew ([gfx](gfx.md)). It is the default wherever the device has cluster acceleration structures and ray queries, and off with a log line where it does not, or in `--raster direct`, `sw`, and `auto` (the first has no resolve, and the other two split the cut across more than one visible list). **In `hw` and `vertex` the frame runs the whole acceleration structure chain too** — records, ranges, emit, CLAS, one cluster bottom-level structure per instance, top-level — from the same cull output `--raster rt` builds from, which is why it also turns two-pass occlusion culling off: the structures are built from one visible list and pass 2's survivors are in a second one. `gpu_ms.rt` is that chain; there is no `gpu_ms.shadows`, because the rays are inside the resolve and a timestamp cannot separate them, so the cost is the resolve with shadows against the resolve without them. FlightHelmet 3×3 (9 instances, 94,722 triangles each, `--orbit 22` then the closer `--orbit 9`, 60 frames, `msvc-debug`, RTX 5090):

| | resolve, `off` | resolve, `rt` | `gpu_ms.rt` | frame total, `off` → `rt` |
|---|---|---|---|---|
| 800×600, orbit 22 (124 pairs, 2% of the frame covered) | 0.021 ms | 0.022 ms | 0.363 ms | 0.103 → 0.404 ms |
| 3840×2160, orbit 22 | 0.092 ms | 0.098 ms | 0.544 ms | 0.443 → 0.675 ms |
| 11520×2160, orbit 22 | 0.199 ms | 0.227 ms | 0.529 ms | 0.830 → 0.780 ms |
| 800×600, orbit 9 (356 pairs, the helmets filling the frame) | 0.012 ms | 0.025 ms | 0.352 ms | 0.082 → 0.392 ms |
| 3840×2160, orbit 9 | 0.111 ms | 0.181 ms | 0.772 ms | 0.404 → 1.004 ms |
| 11520×2160, orbit 9 | 0.230 ms | 0.399 ms | 0.921 ms | 0.965 → 1.413 ms |

So the rays cost the resolve **1.6× to 2× when the geometry fills the frame** and almost nothing when it does not — they are traced per covered pixel, and the sky returns before any of them — while the structures that make them possible cost three to nine times as much as the shading. The 11520×2160 row's total falls with shadows on only because two-pass occlusion culling turns off with them, and its Hi-Z pass is 0.58 ms at that width. What the pictures show at `--orbit 9`: 8,760 pixels of 480,000 differ between `off` and `rt` (up to 202 of 255, 13.7 on average), and they are where a helmet's shell shadows its own goggles, mask, and hose, where the hose lays a dark contact band across the wooden base, and where the leather crown darkens the top face of the stand under it. The 3×3 grid spaces the instances three mesh radii apart while the sun sits 53° up, so no helmet's shadow reaches its neighbour there; a `--scene` file with two helmets a quarter of a unit apart gets that too (25,596 pixels of 270,000 differ, and the front helmet's hose and stand darken the one behind).

The cull pass backface-culls clusters by their normal cones unless `--no-cone`. In the `hw` and `vertex` modes two-pass occlusion culling is on (`--no-occlusion` turns it off): pass 1 draws last frame's visible clusters, a Hi-Z pyramid is built from the visibility buffer, pass 2 tests the rest against it, and the pyramid is rebuilt for the next frame; the summary reports the clusters each pass drew and the Hi-Z time. The JSON summary reports cluster and level counts, DAG build time, the number of glTF primitives (`mesh_primitives`, 0 for the heightfield and 0 for a mesh that came from a container, which does not record how many primitives were merged into it), where the mesh came from (`mesh_cache`: `"miss"` built from the glTF and written to the cache, `"hit"` read from the cache, `"file"` a container named on the command line, `"none"` the heightfield or `--no-cache`), whether cone culling was on, whether shadows were traced (`shadows`: `"rt"` or `"off"`), the scene's `meshes`, `instances`, and `pairs` (the prefix sum the cull pass covers), the hardware and software visible-pair counts and their sum `visible_pairs_last` (read back one frame late from per-slot copies of the indirect arguments), GPU milliseconds per pass (cull, hw, sw, resolve) averaged over the run from timestamp queries, which is how experiment E1 was measured, and the `gpu_memory` and `machine_state` blocks the last section of this page describes. `--frames N --capture out.png` renders N frames and writes the last one as a PNG, and the process prints one JSON line of statistics (frames, seconds, average ms, size, cluster and triangle counts, whether the capture was written) to stdout, so scripts and agents look at the picture and the numbers without a human at the window. Escape or closing the window exits; resizing recreates the swapchain and the depth buffer. Shaders come from the build's manifest when it sits beside the executable (`<exe dir>/../shaders/manifest.json`, or `--shaders`), so editing `cluster_mesh.slang` while the window is open recompiles it through slangc and rebuilds the pipeline within a quarter second; a save that does not compile prints slangc's diagnostics to stderr and keeps the last good shader. `--log` with an explicit spec routes those categories to stderr at the given levels. Exit codes: 0, 1 error, 2 usage, 3 unavailable (no display, no Vulkan device, no mesh shaders, or no presentation), which the end-to-end test treats as a skip. On the RTX 5090 the default 257×257 grid (131,072 triangles, 2,898 clusters in 12 levels, 861 ms to build) draws 98 to 162 clusters per frame at a 1 px threshold and renders in about 0.65 ms per frame at 960×540 without vsync.

**`--deform none|identity|wave|lattice`, `--deform-amplitude <a>`, `--rt-templates`** (experiment [E25](../experiments/e25-deformed-clusters.md)). `--deform` makes **every instance of the scene deformed**: a compute pass (`deform.slang`) fills the frame's deformed-vertex pool for the clusters the cull pass selected, once per run of the visible list, before the draw that reads them, into blocks a second pass (`deform_alloc.slang`) suballocated from a budget for exactly those clusters. Every position reader then takes that instance's positions out of the pool — the rasterizers, the resolve, and the cluster acceleration structure records ([gfx](gfx.md)) — so the raster picture and the ray-traced one deform together. `identity` writes the rest pose, which is the mode to reach for when something looks wrong: it must draw what `--deform none` draws. `wave` displaces along the vertex normal and `lattice` runs a 3×3×3 trilinear cage over the mesh's bounds, both animated by frame number at 60 Hz and both scaled by `--deform-amplitude`, a fraction of the mesh's bounding cube (0.02 by default; 0.4 units on the 20-unit heightfield). `--no-cull` is ignored with `--deform`, because the pass walks the cull pass's visible list — that is the whole point of it. `--rt-templates` changes how `--raster rt` (or `--shadows rt`) turns the cut into ray tracing geometry: instead of rebuilding a cluster acceleration structure per visible cluster every frame, it builds one **template** per cluster of the scene at load, from the rest pose, and instantiates the cut's templates with the pool's positions each frame. **`--deform-pool-mib <n>`** is that budget, in mebibytes (8 by default), clamped down to what a block per instance's whole mesh would have taken so a small scene allocates exactly what it did before the suballocation existed. A frame's cut that does not fit is not an error: the (instance, cluster) pairs that missed out draw their **rest pose**, the renderer says so once in the log, and the summary counts them. The JSON summary gains `deform`, `deform_pool_bytes` (the budget), `deform_whole_mesh_bytes` (what the E25 layout would have allocated), `deform_pool_used_bytes` and `deform_pool_peak_bytes` (what the cut actually took, last frame and at its peak), `deform_entries`, `deform_overflow_entries`, `deform_overflow_bytes`, `rt_templates`, `template_bytes`, and `gpu_ms.deform`, `gpu_ms.deform_alloc` and `gpu_ms.clas` (the cluster structure build or instantiation on its own, inside `gpu_ms.rt`). On the RTX 5090 at 1920×1080, `--orbit 22`, `--shadows off`: the pool pass costs 0.0096 ms for a 266-cluster cut and 0.0132 ms for a 4,363-cluster one on the `--grid 1025` heightfield (2.1M triangles), and 0.0096 / 0.0131 ms for cuts of 396 and 4,831 clusters over 64 FlightHelmets (94,722 triangles) — the same numbers for meshes 22× apart in size, which is the point of the pool. `--rt-templates` turns a 0.066–0.180 ms per-frame cluster structure rebuild into a 0.014–0.061 ms instantiation, for 537 B of template per cluster of the mesh held resident (25 MB for the heightfield's 46,626 clusters, 1.1 MB for the helmet's 2,348). One warning worth reading before using the flags in anger: `--deform wave` displaces along the vertex normal, which **tears** a model at its hard edges and LOD-group boundaries — `--deform lattice`, a function of position alone, does not. The other one used to be the pool's size (110 MB for 64 helmets, 1.7 GB had they been a thousand) and is now a budget: those 64 helmets allocate 8 MiB and their cut uses 0.8 MB of it (2026-09-18; [renderer](renderer.md#the-deformed-vertex-pool) has the table). [E25](../experiments/e25-deformed-clusters.md) has the comparison and the reason, and the command lines that reproduce both.

**`--morph <name|index>=<weight>`, `--morph-animate [clip]`, `--static-shape-kib <n>`: a character that has a shape as well as a pose.** A mesh with morph targets ([geometry](geometry.md), "Morph channels") is deformed whether or not `--deform` is given, and these three say what it plays. **With none of them it plays the asset's own weights**: glTF's `weights` on the mesh or the node are what the file is drawn with when nothing animates it, so the static stage starts from each channel's default and a mesh authored half-morphed (MorphPrimitivesTest, at 0.5) draws half-morphed. `--morph` is repeatable and overrides the **static shape** stage's weight for one channel, named the way the asset names it — glTF's `extras.targetNames`, `<mesh>.<k>` when the file names none, or the channel's index. A weight is any finite number, **zero and negatives included**: zero is how a channel the asset defaults on is turned off, and glTF allows negative weights. An unknown name is a **usage error** rather than a silently ignored weight, because a misspelt expression that quietly does nothing is the kind of thing that gets debugged in the picture instead of on the command line. Its result is cached per instance and costs nothing per frame; `--static-shape-kib` is that cache's budget (4096 by default, 16 bytes a mesh vertex), and an instance the budget had no room for runs its static stage every frame over the cut — the same picture for more work, and the summary says how many instances were cached. `--morph-animate` plays a clip's **weight tracks** through the per-frame **pose** stage on top of whatever `--morph` set; channels the clip does not name keep the asset's own default weights, because a clip writes only what it drives (with it, the defaults move from the static half to the pose half, so they are counted once). The clips come **from the mesh file itself, skin or no skin**: `--animate` is not needed and refuses a mesh with no skin, and a weights-only animation loads as a skeleton-less clip ([animation](animation.md)). The optional value names one — its name, its name after the file-stem prefix, or its index among the clips that have weight tracks — and with none the first such clip plays; a name the file does not have fails. The weights are sampled on the frame counter at 60 Hz times `--anim-speed`, so `--frames N` is the same picture every run. The JSON summary gains `morph_channels`, `morph_static_cache_bytes`, `morph_cached_instances` and `morph_clip` (the library name of the clip the pose stage played, empty when none). In a build without the animation capability `--morph-animate` is refused with the switch to turn on, exactly as `--animate` is; `--morph` needs nothing. Two things are worth knowing before reaching for them: a morphed mesh is **not streamed** — `--stream` is refused with a logged reason, since the delta stream's per-cluster directory would need patching per page the way the cluster offsets are ([renderer](renderer.md)) — and a morphed scene is the only one that carries a deformed **normal** pool, which is what keeps a morphing surface smoothly shaded instead of faceted ([gfx](gfx.md), "What happens to the shading normal").

**`--animate [clip]` and `--anim-speed <x>`: a character that moves.** The first command line that joins the three halves this engine already had — glTF skins and clips through [assets](assets.md), the tick through [animation](animation.md), and the deformed-vertex pool's skinning mode through [gfx](gfx.md). `--animate` reads the mesh file's skins and animations into an `animation::Library`, makes every instance of that mesh skinned, gives each one an entity with an `AnimationPlayer`, and steps a `ecs::SimWorld` once per frame at its fixed 60 Hz. The optional value names the clip by name (`--animate Run`, matched against the library name or its part after the prefix) or by index among that skin's clips; with none, the first one plays. `--anim-speed` multiplies every instance's rate. With `--grid-instances n` every one of the n × n copies is skinned and gets a **phase offset of its own** — `duration * i / count` — so a crowd is not n² clones of one frame; a scene file says the same thing per instance in an optional `"animation"` block, `{"clip":"Run","speed":1.5,"phase":0.4}`, every field optional.

**It needs a glTF, and it needs the capability.** A `.clusters` container carries the per-vertex binding stream but neither a skeleton nor a curve, so `--animate` names the source file; the derived-data cache still serves the geometry, so the second run is as fast as any other. `--animate` on the heightfield, or on a mesh with no skin, is refused with a sentence rather than drawn standing still. And in a build without the animation capability — `ENGINE_WITH_ANIMATION=OFF`, `ENGINE_WITH_ECS=OFF`, or either minimal preset — the whole of the glue compiles away and the flag is refused with a message naming the switch (exit 2, checked in the end-to-end suite and by building `msvc-minimal`). That is [ADR-0027](../adr/0027-additive-capabilities.md)'s removal proof reaching an app: engine-view links the capability when this configuration has it, and is a viewer with no `--animate` when it does not.

**Deterministic by construction.** `ecs::SimWorld::step` reads no clock, so `--frames N` advances the world exactly N steps and two runs of the same command line produce **byte-identical PNGs**; the end-to-end suite checks that, and checks that `--anim-speed 4` produces a different one. The summary gains `skinned_instances`, `joints` (the length of the bone-matrix span the frame uploaded), and `clip`; `gpu_ms.deform` was already there and is now non-zero without `--deform`, because skinning is one of the pool pass's kinds rather than a pass beside it.

**`--anim-lod on|off` and `--anim-lod-scale <x>`: the camera decides what each character is worth.** On by default. Every frame, before the tick, engine-view builds a `sim::ObserverSet` from the renderer's own views — one observer per view, the side monitors of a surround weighted below the centre by `--peripheral-lod` — tests each animated instance's padded bounds against this frame's frusta, runs `sim::TierAssignment` over the result, and hands the accepted changes to the animation capability, which releases a pose slot on demotion and advances the playhead analytically on promotion. `--anim-lod off` is what every build before 2026-09-18 did: every instance at LOD0 for ever, which is the baseline the policy is measured against. `--anim-lod-scale` multiplies the capability's band boundaries (`animation.lod.near/mid/far`, 12/40/120 m of observer score): **the bands are metres and a sample asset's units may not be** — the Khronos Fox has a bounding radius of 82 in its own units, so a crowd of them at `--orbit 22` is thousands of units away and lands entirely at LOD3 with the default scale. The summary gains an `anim` block: `{"on":true,"scale":1,"instances":1024,"tiers":[0,0,0,1024],"promotions":0,"demotions":1024,"deferred":0,"ms":{"tick":0.064,"lod":0.038}}` — the tier histogram at the last frame and the CPU milliseconds a frame of the world's step and of the assignment in front of it. [animation](animation.md#the-app-side-lod-glue-what-the-camera-decides) has the pattern a game copies, the full table by tier mix (1.7× at LOD1, 6.1× at LOD2, 52× frozen, against 3.3 ms with the flag off) and what a tier change costs the picture (0.0011 / 0.0097 / 0.0000 FLIP mean at the three boundaries, against the 0.1 FLIP calls the threshold of noticing).

**engine-content.**
```
engine-content build <in.gltf|in.glb> <out.clusters> [--max-triangles <n>] [--max-vertices <n>] [--no-weld] [--no-morph] [--jobs <n>] [--strict] [--log <spec>]
                     [--uv-seams none|protect|lock] [--normal-seams none|protect|lock] [--uv-weight <n>] [--normal-weight <n>]
engine-content build <in.gltf|in.glb> --cache [--ddc <dir>] [--max-triangles <n>] [--max-vertices <n>] [--no-weld] [--jobs <n>] [--strict] [--log <spec>]
engine-content build-all <manifest.json> [--cache] [--ddc <dir>] [--jobs <n>] [--strict] [--log <spec>]
engine-content info <file.clusters>
engine-content stats <file.clusters>
```
The content build on the command line (docs/plan/07-content-pipeline.md §7.3): the step between a source mesh and what the renderer loads. `build` imports the file with `assets::load_gltf`, welds its vertices unless `--no-weld` (exporters duplicate freely, and without welding the 64-vertex cluster limit starves both the clusters and the LOD builder; **a skinned source's bindings are part of the weld key**, so two coincident vertices with different weights stay two vertices, and `engine-view --mesh` welds identically because the two share cache entries — [geometry](geometry.md), "Skinned meshes"), builds one cluster LOD DAG per glTF primitive with the file's normals and UVs so that every cluster has exactly one material — one job per primitive on the job system's performance pool — merges them (`geometry::merge_cluster_lod`) in primitive index order, maps each merged cluster to its primitive's material (a primitive that names none gets one appended default), converts the metallic-roughness materials into the file's 64-byte records — base color, metallic and roughness, the base-color, metallic-roughness, normal, occlusion, and emissive image slots, the emissive factor, the normal scale, and the packed alpha mode, cutoff, and double-sidedness ([geometry](geometry.md)) — carries the image paths over as the glTF gave them (an embedded image keeps its slot with an empty path and its **encoded bytes travel in the container**, deduplicated by content hash, so the container draws what the source draws wherever it ends up — [geometry](geometry.md), "Embedded images") together with the source path the paths are relative to and the source's identity — its content hash and the build key over that hash and the options, which is what lets a later build recognize the container as the answer to the same question — and writes the `.clusters` container described in [geometry](geometry.md). `--max-triangles` (4..256) and `--max-vertices` (1..255) are the per-cluster limits, 124 and 64 by default. `--uv-seams`, `--normal-seams`, `--uv-weight` and `--normal-weight` are what the LOD simplifier is told about attribute discontinuities and attribute error ([geometry](geometry.md#what-the-simplifier-is-given-and-why)); the weights are in thousandths, so `--uv-weight 500` is 0.5. **All four are part of the cache key**, as the per-cluster limits are, so a container built with `--uv-seams none` is a different entry from the default one and `engine-view --uv-seams none` finds exactly it — which is what makes "what does the seam rule cost this model?" a pair of command lines rather than a pair of builds of the engine. `--no-morph` is the same idea for the morph stream: it drops the source's morph targets before anything else sees them, so the container is what the file would build to with no channels — welded without the deltas in the key, simplified without `morph_seams`, the seven morph sections empty — and it moves the recorded build key (`morph_key` in `main.cpp`), so such a container is never taken by `build-all` for the answer to a build that wanted the channels. What it measured on the Khronos morph samples is below, in "The morph samples, end to end". `--cache` replaces the output file with the derived-data cache entry this source and these options address — `<ddc>/clusters/<hash>.clusters`, the path `engine-view --mesh` looks in before it builds anything — and the summary's `path` says where it went; an output file and `--cache` together are a usage error, since one build has one destination. `--ddc <dir>` names the cache root, which is otherwise `<repo>/ddc`, found by walking up from the executable to the directory holding `AGENTS.md`. `info` reads a container back and prints its header, every section record with its kind and name — including a section this build does not know, since it reads the table straight from the bytes — and the counts. Every command prints JSON lines on stdout and nothing else (`build`: `path`, `cached`, `source_hash`, `build_key`, `clusters`, `leaf_clusters`, `triangles`, `lod_levels`, `vertices` (cluster-ordered, so duplicated per cluster and per level), `materials`, `images`, `embedded_images` (how many of them the container carries the bytes of), `deduplicated_images` (how many of those were served by an earlier image's identical bytes), `image_bytes` (what the distinct ones take), `warnings`, `bytes`, `build_ms`, `hash`; `build-all` adds the same three to a built line; `info` adds `source_path`, the three image counts, and `morph_channels`/`morph_deltas`; `stats` adds `image_detail`, which is the three counts plus one entry per slot with its path, its carried bytes, and its media type — the per-slot answer to "is this container drawable on its own?" — and, for a mesh with morph targets, `morph`: the channel and delta totals, whether the stream carries normal deltas, the bytes it costs and the bytes per cluster vertex, and one `detail` entry per channel with its name, how many deltas it holds, the **fraction of the mesh's cluster vertices it touches**, its largest displacement, its quantization step and its default weight. Those two are the numbers that say whether the sparse layout earned itself on a given asset: a face rig's channels touch a few percent each, and a channel that touches everything is a whole-body shape that would have been as cheap dense), so a script reads the numbers and an agent checks the hash; everything else is a log record on stderr under the `content` category. Exit codes: 0, 1 (the mesh could not be loaded, validated, clustered, or written), 2 usage.

**What a build is allowed to be** ([07 §7.4](../plan/07-content-pipeline.md#74-validation-rules-automatic)). `build` checks the mesh as it was imported, before welding, so a diagnostic names the primitive and triangle of the *source* file. Each rule carries a stable id, which is the machine-readable failure [§7.3](../plan/07-content-pipeline.md#73-content-build-the-derived-data-graph) asks for: `geometry.empty_primitive` (a primitive with no indices, or a count that is not a whole number of triangles), `geometry.index_range` (an index past the vertex count), `geometry.nan_position` (a coordinate that is not finite), `geometry.degenerate_triangle` (a repeated corner, or two edges exactly parallel in float arithmetic, so the triangle covers no pixel), and `geometry.cluster_budget` (more than 2^24 clusters, which is what the visibility buffer's `cluster << 8 | triangle` word can name) are errors: the first one exits 1 with `<rule>: <sentence>` on stderr and nothing is written. `geometry.uv_range` (a UV past ±16 — sixteen wraps is already past any texel density the texture pipeline can serve, but a trim sheet legitimately runs to a few, so it is not an error) and `material.missing_image` (a slot naming an image with neither bytes nor a path, or an external path that is not there, which draws untextured) are warnings: a `warn` log record each, counted in the summary's `warnings`, and `--strict` turns the first of them into the same kind of refusal. None of the seven sample models trips any of them.

**Many meshes, once each** ([07 §7.3](../plan/07-content-pipeline.md#73-content-build-the-derived-data-graph): incremental and parallel builds). `build-all <manifest.json>` takes `{"meshes":[{"source":"a.gltf","output":"a.clusters","options":{"max_triangles":124,"max_vertices":64,"weld":true}}]}`; `source` is required, `output` and `options` are not, and both paths are resolved against the manifest file's own directory so a manifest is movable as a unit. An entry with no `output` needs `--cache` and goes to the entry the cache addresses; without `--cache` it is an error before anything is built. Each entry is one job on the performance pool. A job hashes the source (`assets::source_mesh_hash`), computes the build key (`geometry::cluster_cache_key` over that hash, the options, and `k_cluster_cache_version`), and **skips the entry when the container already at the output records that same source hash and that same key** — which is what the `source_hash` section of the container is for, and why a container that records none (an older build, or one `engine-view` wrote) is rebuilt rather than trusted. It prints one JSON line per mesh, in manifest order rather than completion order, with `status` `built`, `skipped`, or `failed` (plus `rule` and `error`), then `{"built","skipped","failed","seconds"}`; a failed entry does not stop the others, and the run exits 1 if any failed.

**Threads, and why the bytes do not depend on them.** `--jobs <n>` sizes the performance pool ([jobs](jobs.md)); absent, it is one worker per performance CPU. `build` runs the per-primitive `build_cluster_lod` calls as one job each and merges them **in primitive index order, never in completion order**, so a mesh builds the same bytes at any thread count; the tests pin that with `--jobs 1` against `--jobs 8`. `build-all` puts the parallelism one level up, one job per mesh, and builds each mesh's primitives in sequence inside it: the manifest is the coarser level and already fills the pool, and one wait per mesh keeps the helper stack shallow. A single-mesh manifest is therefore no faster than `build` on it, which is what `build` is for.

**stats** reports what [07 §7.3](../plan/07-content-pipeline.md#73-content-build-the-derived-data-graph) wants watched between builds, as one JSON line: `level_clusters` (clusters per DAG level) and `groups`; `triangles_per_cluster` with `min`, `median` (the upper middle, so it is a count some cluster has), `max`, `total`, and a `histogram` of one `{triangles, clusters}` entry per distinct count, ascending, whose counts add up to the cluster count; `source_vertices` (what the container records, which for a merged mesh is the whole source vertex space once per primitive), `referenced_source_vertices` (the distinct entries of `vertex_source`, which is the only denominator a ratio means anything against), `cluster_vertices`, and `vertex_duplication` between the last two; `bytes` with `total`, `header`, `section_table`, `payloads`, `padding` (what the 16-byte payload alignment costs) and one entry per section, including a section this build does not know; and `quantization` with the grid `step` and `origin`. The FlightHelmet: 2,348 clusters in 10 levels (1,102, 600, 310, 163, 85, 43, 22, 12, 8, 3), 1 to 105 triangles a cluster with a median of 86, 143,515 cluster vertices over 55,392 referenced source vertices for a duplication of 2.59, and of its 5,297,184 bytes 1,722,180 are float positions, 1,148,120 attributes, 861,092 quantized positions, 755,060 triangles, 574,060 vertex sources, 112,704 each of cluster and LOD descriptors, and 76 bytes of alignment padding.

**Two more objects, about the picture rather than the bytes.** `atlas` is how fragmented the UV atlas is — `islands` (connected components of the level-0 triangles over *source* vertex indices, which is exactly the island count because the weld keys on the UV), `source_vertices`, `seam_vertices` and `seam_fraction` (a vertex sharing a position with another that disagrees about the UV), `uv_area`, `smallest_island_texels_4096` with `smallest_island_triangles`, `median_island_texels_4096`, `largest_island_texels_4096`, and `triangles_per_island`. It is here because atlas fragmentation stopped being invisible and became a **cost**: the LOD builder may not collapse across an island edge ([geometry](geometry.md#what-the-simplifier-is-given-and-why)), so island size now sets how far a mesh can be simplified at all, and below some size no seam-respecting simplification can be right at all — the fix there is a texture-space one ([07 §7.4](../plan/07-content-pipeline.md#74-validation-rules-automatic)), and these are the numbers its validator will threshold. `lod_attribute_error` is the other half, and it answers the question a geometric error bound cannot: **how much of the texture a coarse cut moves.** One row per triangle budget (25% and 10% of the leaves), each with the `clusters` and `triangles` of the cut nearest that budget and `geometry::measure_lod_attribute_error`'s numbers — `uv_mean_texels`, `uv_p99_texels`, `uv_max_texels`, `uv_outlier_fraction` (the share over eight texels of a 4,096 atlas) and the normal angles. Both tables go to stderr for a human as well, so stdout stays one JSON line. The maximum is the number to read first: an atlas slot is a few hundred texels, so a worst sample in the thousands means a triangle is interpolating between two unrelated islands and a worst sample in the tens means it is not.

Measured on the samples `tools/fetch-samples.ps1` fetches, `msvc-release` on an i9-10980XE (28 performance CPUs), `build_ms` being import, validation, clustering, and the write: `FlightHelmet/FlightHelmet.gltf` is 94,722 triangles into 2,348 clusters in 10 levels (1,102 leaves) with 6 materials and 15 images, in **171–185 ms with `--jobs 1` and 109–119 ms at the default** over three runs each — 1.5×, because the file has six primitives and the largest of them is the critical path — and the two outputs are byte-identical (same SHA-256, same content hash). `Suzanne/Suzanne.gltf` is 3,936 triangles into 88 clusters in 7 levels (42 leaves) in 21 ms; `SciFiHelmet/SciFiHelmet.gltf` 23,358 triangles into 587 clusters in 10 levels, 1,320,224 bytes in 87 ms; `Corset/Corset.glb` 18,324 triangles into 437 clusters in 76 ms; `BoomBox/BoomBox.glb` 40 ms; `Lantern/Lantern.glb` 34 ms; `Avocado/Avocado.glb` 682 triangles into 15 clusters in 33 ms, with its 3 images embedded. **The container sizes moved when the embedded images went into it** and are given in [geometry](geometry.md) ("Embedded images") rather than repeated here: a GLB's container grows by its textures (the Lantern from 360,964 to 9,690,467 bytes), and the FlightHelmet's, whose fifteen images are files beside the glTF, grows by 428 bytes to 5,299,104. `build-all --cache` over all seven takes 0.34 s cold at the default and 0.43 s with `--jobs 1` (the FlightHelmet is more than a third of the work, so the manifest-level parallelism has little to spread), and 0.04–0.07 s warm, skipping all seven. In `msvc-debug` the FlightHelmet takes 618–632 ms with `--jobs 1` and 418–470 ms at the default, and Suzanne 55 ms. `engine-view --mesh` reads exactly these containers, and writes the same mesh into the cache itself when it has to build one.

The probe for input devices nobody on the project owns. The engine's input path has to work with wheels, pedal boxes, shifters, flight sticks, and pads on dongles, and none of them can be characterized from a machine they are not plugged into; this tool turns a device into a file that can be read, replayed, and turned into a test here.

`devices` prints one JSON line per attached gamepad and joystick — `{space, slot, name, raw_name, guid, vendor, product, axes, buttons, hats, is_gamepad}`, from `window::input_devices` (docs/subsystems/window.md), where `name` is resolved through the name table and `raw_name` is what the driver said. `probe` streams one JSON line per event to stdout as it happens — `{t_ms, kind, device, index, value}` plus `space` (`"gamepad"` or `"joystick"`, because the two slot spaces are separate) and `name` where the enum has one; a connection or disconnection has no index or value — and ends with one summary line `{events, seconds, per_device, axes_seen, buttons_seen, hats_seen}`, where `per_device` is keyed `"gamepad:0"`, `"joystick:1"`, … , every device is named with its resolved name, and `axes_seen`/`buttons_seen`/`hats_seen` count the *distinct* axes, buttons, and hats that moved. `--log` also records the events as an `input::InputLog` (docs/subsystems/input.md), converting each one into `RawEvent`s at a 60 Hz tick and turning each hat event into four digital signals, one per direction. `--events <file>` sends the event stream to a file the probe opens itself, as UTF-8 bytes with bare newlines, leaving only the summary on stdout (the file gets it too, as its last line): **do not redirect the stream with a shell instead**, because PowerShell's `>` writes UTF-16 with a byte order mark and every text tool downstream then reads the result as binary, which is how the first round of recordings came back. `replay` loads such a log with no device attached, gives every distinct signal in it an action (`joystick_axis_2`, `joystick_button_5`, `joystick_hat_0_8`; `Button` for the digital sources, `Axis` for the analog ones), replays it through an `InputState`, and prints `{file, events, first_tick, last_tick, ticks, actions, button_actions, axis_actions, presses, releases, map, state}`. A log the probe recorded carries no action map, so `replay` stamps it with the hash of the map it just built; a log that does carry one is still refused when the map differs, as `InputLog::replay` requires.

`ffb` and `rumble` are the same tool pointed the other way: output nobody here can feel. `ffb` takes a **raw joystick** slot, opens its haptics device, prints one line of `window::HapticInfo` (`{device, name, constant, spring, damper, friction, sine, axes}`), applies whichever of `--spring`, `--damper`, and `--constant` were named, holds them for `--seconds` (5 by default, 60 at most), stops them, and prints a summary saying what each effect was asked for and whether it ran. With no force named it is a report and nothing else. `rumble` takes a **gamepad** slot and runs its two motors for `--ms`, printing `{device, name, low, high, ms, rumbled}`. Both exit 3 when the slot is empty, and `ffb` also when the device has no haptics and `rumble` when the pad has no motors — which is most pads, so 3 there means "nothing happened", not "something broke". **Opening a wheel stops the driver's own centring spring**, so a wheel goes limp under `ffb` until a force is set and again once it stops; that is the device, not the tool (docs/subsystems/window.md).

SDL needs no window for joystick events, but it does need its own event pump, so the tool creates one hidden, non-Vulkan 64×64 window and drives `poll()` on it; and because SDL drops device events while a process owns windows and none holds keyboard focus, it calls `window::set_background_input(true)` so the terminal it was started from can keep focus while both of the owner's hands are on a wheel. It waits 250 ms at startup for SDL's arrival events, which is what assigns the slots. Exit codes: 0, 1 error, 2 usage, 3 unavailable (no display or no SDL video driver; for `ffb` and `rumble`, also an empty slot or a device with no forces and no motors), which the end-to-end test treats as a skip.

**Reporting a device.** Plug in one device at a time, and for each run exactly these two commands from `build/<preset>/bin/`:
```bash
engine-input devices
engine-input probe --seconds 10 --log <device>.jsonl --events <device>.events.jsonl
```
During the ten seconds, exercise everything the device has, slowly and one thing at a time so the indices are readable in the file: sweep each axis from end to end (a wheel lock to lock, each pedal fully down and back, each stick through both axes), press and release every button once in a predictable order, and push the hat to each of the four directions and back to centre. Send back `<device>.jsonl`, `<device>.events.jsonl`, and the `devices` line. That is enough to name the device's axes and buttons here and to add it to the tests; `engine-input replay <device>.jsonl` reproduces the session with nothing plugged in. With several devices attached at once, `--device <slot>` and `--gamepad`/`--joystick` narrow the stream to one of them. The logs that came back this way are committed under `content/input-logs/` and replayed by `foundation/input`'s corpus test; that directory's README says how to add one.

**Force feedback, next.** Nobody working on the engine has a wheel or a pad to feel these on, so the three force calls are plumbed and tested but unverified on hardware. Two commands answer that, on the rig that recorded `content/input-logs/t300.jsonl` and on the pad that recorded `f710.jsonl`:
```bash
engine-input ffb --device 0 --spring 0.5 --seconds 5
engine-input rumble --device 0 --low 0.5 --high 0.5 --ms 500
```
The first should make the T300's wheel resist being turned away from centre for five seconds and go limp again when it stops; check the printed `HapticInfo` against what the wheel actually did, and whether `spring_ran` was true. The second should buzz the F710 for half a second. Run `engine-input devices` first if anything else is plugged in: `ffb` counts joystick slots and `rumble` counts gamepad slots, and they are different spaces.

**engine-image.**
```
engine-image compare <a.png> <b.png> [--flip <out.png>] [--ppd <n>] [--weights center|none] [--json]
engine-image info <file.png> [--json]
engine-image --version
```
The picture comparison [04 §4.8](../plan/04-renderer.md#48-reference-renderer-and-objective-optimization) makes the gate of the optimization loop: propose, build, render the corpus, compare to the baseline, accept if it is faster and the picture did not get worse. `compare` decodes two images (PNG, JPEG, TGA, or BMP, through `image::read_image`) and prints FLIP — the perceptual metric, which is the primary number — with PSNR and SSIM beside it, all from `foundation/image/metrics.h` ([image](image.md), which says what each one is and why). `--ppd` is the viewing density the contrast-sensitivity filter is evaluated at, 67.02 by default, which is the FLIP paper's reference condition rather than any particular monitor; a denser display scores a given difference higher. `--weights center` pools the per-pixel error under a Gaussian attention region instead of evenly, which is §4.8's per-region rule and [§4.6](../plan/04-renderer.md#46-extreme-displays)'s treatment of peripheral vision: the same damage in a corner of a 48:9 frame then counts for about a fourteenth of the same damage in the middle. `--flip <out.png>` writes the per-pixel error as a heat map, which is how to see *where* two frames disagree rather than by how much.

`--json` prints one object on stdout — `{a, b, width, height, psnr, ssim, flip_mean, flip_p95, flip_max, flip_weighted_mean, ppd, weights, flip_image, ms}` — and without it the same numbers as a short readable report. `psnr` is `null` for two identical images, because the value is infinite and a large number would read like "nearly identical"; `flip_image` is `null` when no heat map was asked for; `ms` is the wall time of the metrics themselves, so a corpus run can budget for it (a 3840×2160 pair is 3.0 to 3.2 s in `msvc-release` on the dev box). `info` prints an image's size and channel count from its header alone, without decoding the pixels.

**Exit codes: 0 and 2, and deliberately no 1.** A difference is a measurement, not a failure: `compare` exits 0 whenever it produced numbers, however large they are, and it is the caller — a CI script, an agent's accept-or-reject rule — that decides which threshold means what. Everything that stopped it from measuring exits 2: a bad argument, a file that is not there or is not an image, two images of different sizes, a heat map that could not be written.

engine-image depends on `base`, `containers`, `time`, `io`, and `image` — no GPU, no window, no scene: it is two file reads and some arithmetic, so it runs on a build machine and on the headless GPU runner alike. `tools/dev.ps1 test -Filter engine_image` runs the end-to-end suite, which writes its own PNGs at test time (a flat field, the same field four levels brighter, and a checker with a 16×16 block flattened once in the middle and once in a corner) and checks: thirteen ways to get the arguments wrong and `--help`; an image against itself giving a `null` PSNR, an SSIM of 1, and a FLIP of 0; the four-level pair giving the analytic PSNR 10·log₁₀(255²/16) and a flat FLIP map whose mean is its maximum; `--ppd` reaching the filters (and a flat difference surviving any density, which is the case where it should not matter); `--flip` writing a three-channel PNG the size of the inputs and exiting 2 when the destination cannot be written; `--weights center` separating the middle of the frame from the corner by more than three times while the plain means stay within a tenth of each other, and the weighted mean equalling the mean when no weights are asked for; mismatched sizes and a file that is not an image exiting 2 with a message; `info` reading the header of a PNG and refusing junk; and `--version` printing the build stamp as one JSON line whose commit is 40 hex characters or `"unknown"`.

**Build.** `engine_app(NAME engine_host OUTPUT engine-host SOURCES ... DEPS ... [E2E_TESTS ...])` in `cmake/EngineModule.cmake` builds an executable into `build/<preset>/bin/`, records it in `modules.json` with layer `apps`, and can build an end-to-end test executable that receives the app's path as `ENGINE_APP_PATH`. The CLI test also receives `ENGINE_HOST_PATH`.

**The build stamp.** Every app links `engine_build_stamp` (`cmake/EngineBuildStamp.cmake`), which says which commit it was built from: `engine::build_stamp::commit()` (40 hex characters, or `"unknown"` where there was no git to ask — the Linux container syncs the tree without `.git`) and `dirty()` (tracked files differed from it). `engine-content --version`, `engine-view --version` and `engine-image --version` print it as one JSON line, `{"tool","commit","dirty"}`, and exit 0 without touching a device. It is captured **at build time**, not at configure time, because CMake does not re-run on a commit: a commit captured at configure would name the tree as it was when the build directory was configured — days earlier in a long-lived tree — and anything trusting it would refuse every fresh binary or accept a stale one. So an always-run target asks git on every build (`rev-parse` and a `--no-optional-locks status`, which never takes `index.lock` from under a person's git command) and rewrites the two-line generated source only when the answer changed; after a build with no commit in between, Ninja recompiles and relinks nothing, and after a commit it recompiles that one file and relinks the apps in `bin/` — only apps link it, so the test and bench binaries are untouched. It exists because on 2026-09-22 the E10 harness measured with release binaries hours older than the commit it recorded ([content generation](../content-generation.md#the-e10-harness-toolse10-harnessps1), "Which binaries"); `tools/e10-harness.ps1` now refuses a binary whose stamp is behind the source it reports.

**Depends on.** engine-host: `protocol`, `log`, `io`, `tunables`, `renderer` (the `render.*` methods; see the last section of this page). engine-cli: `json`, `platform` (`Process`, `executable_directory`). engine-view: `renderer`, `window`, `image`, `io`, `gfx`, `math`, `time`, `log`, `platform` — the geometry, asset, and scene-file work it used to do itself now comes through [renderer](renderer.md). engine-content: `geometry`, `assets`, `io`, `json`, `log`, `time`, `math`, `containers`, `jobs` (no GPU, no window: it runs on a build machine). engine-input: `window`, `input`, `json`, `io`, `platform`, `log`, `containers`.

**Not yet.** `render.*` cannot animate: `render.load` takes no skin and `render.capture` and `render.benchmark` hand the renderer no matrices, so an animated scene is engine-view's alone and a surround-sized capture of one is not available. The glue is small — the same world, library and per-instance runs engine-view owns, kept beside the host's `SceneData` across calls — and the protocol side is a `joints` block on `RenderLoadParams` plus a tick count on the two that render. It was left out rather than half-built because the host keeps a scene across calls and a world that ticks across calls needs a stated rule for *when*; engine-view's rule (one step per frame) does not transfer to a method that renders one frame on demand. Also not yet: engine-host `offscreen` and `windowed` modes (engine-view is the standalone window until the host learns to own one), sockets, multiple clients per host, long-running operations, the MCP bridge, a persistent-host mode for the editor. engine-content: the cache is one file per built mesh under `ddc/clusters/`, with no index, no eviction, and no sharing between machines — the content-addressed store, remote caching, and the derived-data graph of [07 §7.3](../plan/07-content-pipeline.md#73-content-build-the-derived-data-graph) are still to come, and nothing yet invalidates an entry when the builder changes except bumping `k_cluster_cache_version` by hand. Incrementality is per mesh and per output file, not per derived node: a changed source rebuilds its whole container, and the "up to date" question is answered by reading the container's own identity rather than by a dependency graph. The two levels of parallelism do not nest — a one-mesh manifest builds no faster than `build` — and nothing yet bounds memory when a manifest of large meshes builds at once. Of the validation rules of [07 §7.4](../plan/07-content-pipeline.md#74-validation-rules-automatic) only the geometry ones listed above are implemented: manifoldness, scale against a declared category, pivot and up axis, texel density, UV overlap, collision fit, open edges, the material, rig, deformable, placement, performance, provenance, and visual rules all need data the engine does not carry yet (a category, a budget table, a provenance block), and none of them was found impossible. Also missing: textures (decode and compress beside the mesh) and a manifest form richer than a flat list of meshes. engine-input does not yet write an `ActionMap` from what it saw or name a known device's axes; its `ffb` has never been run against a device that could answer, and its `rumble` has only been seen accepted by an F710, not felt.

## Streaming pages in the content build

`engine-content build` and `build-all` lay a mesh out in fixed-size streaming pages by default ([geometry](geometry.md), [04 §4.3](../plan/04-renderer.md#43-geometry) step 3): **`--page-bytes <n>`** sets the target, 131072 by default, and **0** writes a container with no page table and leaves the clusters in the builders' order. A manifest entry may set `"page_bytes"` in its `"options"` object; the command line is the default for entries that do not. The flag is part of the derived-data cache key, because laying a mesh out in pages **renumbers its clusters**: two targets are two different containers and "no pages" is a third, so an incremental build never hands back an entry that was paged differently from what was asked for. `engine-view` lays its own cache entries out with the same default, so either program still fills the cache and either finds it.

The renumbering is also why the build pages a mesh *before* it maps clusters to materials: the permutation is applied to the map from cluster to primitive in the same step (`geometry::permute_cluster_array`), and everything downstream sees one numbering. The `build` summary gains `pages`, `page_bytes`, and `page_fill` (mean page bytes over the target); `build-all` prints the same three per entry.

`info` gains a `pages` object — `count`, `bytes_target`, `bytes`, `largest_bytes`, `mean_fill`, `oversized`, `root_pages` (the pages holding a group nothing coarser can replace, which a residency manager never evicts), and `child_page_entries`. `stats` reports all of that plus `valid` (the page table checked against the mesh it came with, with `invalid_reason` when it is not), a `child_pages_histogram` of one `{child_pages, pages}` entry per distinct count — how much of the DAG a page depends on, and so how wide a prefetch is — and a **streaming sweep**: a camera flies from 50 mesh radii to half a radius in 32 steps at 1080p and one pixel of error, and each step reports what the ideal cut needs (`clusters`, `triangles`, `pages_needed`) and what a residency manager under a quarter of the mesh's page bytes actually does (`requested`, `drawn`, `evicted`, `resident`, `resident_bytes`). The table goes to stderr so stdout stays one JSON line; the same numbers are in `pages.streaming.steps_detail`. It is a content metric, not a benchmark — it answers "does the way this mesh is paged make a fly-in cheap?" without a GPU, a window, or a frame loop.

Renumbering a mesh has to be invisible to the renderer, and it is: `engine-view --frames 3 --width 400 --height 300 --orbit 22` on the FlightHelmet gives a **byte-identical PNG** and the same 119 visible pairs from the glTF and from the paged container built from it. The one thing that does change is the *direct* draw, which has no cull pass and draws clusters 0..`leaf_count` on the assumption that the leaves come first; in a paged mesh they come last, so `--no-cull` now turns culling back on with a warning, exactly as it already does for a scene of more than one instance.

The two sample meshes, in `msvc-debug`. The **FlightHelmet** (2,348 clusters, 10 levels) is 25 pages at 91% fill, 2.85 MB of page bytes, one of them pinned, and the whole outer half of the fly-in — 50 radii down to 10, 7 to 38 clusters, 319 to 2,618 triangles — draws out of that one page with nothing requested. Streaming starts at 8.5 radii (2 pages), reaching 5 pages at 5.3, 7 at 3.7, 11 at 2.1 and 17 at half a radius, where the full cut is 960 clusters and 80,422 triangles. Under the 747 KB budget the viewer settles at 6 pages and 687 KB, draws 281 of those 960 clusters and still has 8 pages outstanding, which is what a budget a third of the working set looks like: it lags, it does not crack. **Suzanne** (88 clusters, 7 levels, 113,528 page bytes) is a single page, so its sweep requests nothing at any distance and its cut runs from 3 clusters and 245 triangles at 50 radii to all 42 leaves and 3,936 triangles from 3.7 radii in — and its budget is not honoured, because that one page holds the root and a mesh without its root draws nothing at all.

## Streaming pages at run time: `--stream`

`engine-view --stream` turns the page table the content build wrote into a **GPU residency budget** ([04 §4.9](../plan/04-renderer.md#49-streaming-and-residency), [renderer](renderer.md#geometry-streaming-the-gpu-half-of-pages-and-residency)): the device holds a subset of the scene's cluster pages, the cull pass draws whatever is resident and writes the pages it could not refine into to a feedback buffer, the CPU reads that back one frame slot later and streams them in, and the picture converges. Two more flags size it, and both imply `--stream`:

| Flag | What it sets | Over the protocol |
|---|---|---|
| `--stream` | residency on, with the whole page table as the budget: streaming with nothing to evict | `RenderSettings.stream` |
| `--page-budget <MiB>` | the residency manager's budget over the scene's page bytes | `RenderSettings.page_budget_mib`, the same unit |
| `--upload-budget <KiB>` | page payload one frame may copy into the pool; 256 KiB by default, raised to the largest page when a smaller value is given | `RenderSettings.upload_budget_kib`, the same unit |
| `--page-budget-pct <n>` | the same budget as a **percentage of this scene's page bytes**, applied after the load, because that is the only moment the page table exists to be counted. Overrides `--page-budget` | engine-view's alone: a host that wants a fraction reads `stats.stream.page_bytes` from a first call and asks for the MiB it wants |
| `--page-source auto\|file\|host` | where a page's payload comes from: `auto` reads the meshes' `.clusters` containers when **every** mesh has one and falls back to host memory otherwise, `file` refuses to run when they do not, `host` keeps the in-memory source. `stats.stream.source` says which happened | engine-view's alone today ([protocol](protocol.md) says why the host cannot release the streams a later settings change would need) |

**A budget as a percentage exists because MiB cannot say "a quarter" of a small mesh.** The FlightHelmet's pages come to 2.85 MB, so `--page-budget 1` is 35% and there is no way to ask for 25% at all; and a budget is thought about as a fraction of the working set, not as an absolute, because what makes a budget interesting is its ratio to what the cut wants. The percentage is applied to the sum of `geometry::ClusterPageDesc::bytes`, which is the same number the residency manager counts against, so 25 here and 25 in a report mean the same thing.

**Where a page's bytes come from is the difference between saving device memory and saving memory.** With `--page-source host` the payload is copied out of the loaded mesh, so the whole scene's geometry stays in the process however small the budget is. With `file` it is three ranged reads of the container (four when the frame builds acceleration structures) and the merged host streams are released once the scene is on the GPU — measured on the FlightHelmet at `--grid-instances 8` and a quarter budget, 307.5 → 303.5 MB of working set for 4.83 MB released, with the process's **peak** unchanged ([renderer](renderer.md#geometry-streaming-the-gpu-half-of-pages-and-residency) has the tables and says why the peak does not move). The summary's `streaming` block gains `source`, `file_reads`, `file_bytes`, `host_bytes_freed` and `load_waits`, and the line gains a `host_memory` block with the working set and its peak, so the claim is checkable from one run.

**`--fly <a> <b> <n>`** is the camera path a residency budget is under pressure on: `n` steps from `a` mesh radii to `b`, interpolated **geometrically**, because halving the distance doubles every projected error whether it is 50 radii to 25 or 2 to 1 — linear steps would spend nine tenths of the path on the outer half, where a mesh draws out of one page and asks for nothing. It overrides `--orbit` and sets `--frames` when nothing else did; a longer `--frames` repeats the last step, which is how "and then it sat there" is measured. A two-step fly is therefore also a **camera jump**: `--fly 20 1.5 2 --frames 120` is one frame far away and the rest up close.

The JSON summary gains a **`streaming`** object, present on every run so that a script never has to test for it — `pages_total` is 0 when nothing streamed:

```json
"streaming":{"pages_total":25,"pages_resident":16,"pages_pinned":1,"page_slots":25,"pending":0,
 "requests":58,"uploads":16,"uploads_bytes":1851392,"evictions":0,"stale":0,"overflows":0,
 "frames_to_converge":2,"resident_bytes":1929216,"page_bytes":2989678,"budget_bytes":2989678,
 "source":"file","file_reads":48,"file_bytes":1772544,"host_bytes_freed":5060512,"load_waits":15}
```

and a **`host_memory`** block beside `gpu_memory`, which is what a claim about host memory is checked with: `"host_memory":{"bytes":318193664,"peak_bytes":354398208}` — the process's working set as the OS reports it (`platform::process_memory_bytes`) and its high-water mark, read after the last frame and before anything is torn down.

Three of the flags a run might combine with it are **refused rather than half-applied**, each with a line on stderr under the `renderer` category: `--deform` and a skinned scene (the deformed-vertex pool is indexed by the scene-wide vertex index and a streamed scene's vertices are at slot-relative ones), `--rt-templates` (a template is built at load from every cluster's positions, which a streamed scene does not hold), and `--no-cull` (the drawing rule's fallback *is* the LOD cut). A mesh with no page table turns streaming off outright.

**The same thing over the protocol**, in the same units and with the same words ([protocol](protocol.md#methods-an-app-registers-and-render)). The table's right-hand column is the whole of it for the flags; two things are the host's alone, and one is engine-view's alone.

```bash
engine-cli render.load '{"grid":257,"page_bytes":16384,
                         "settings":{"raster":"hw","stream":true,"page_budget_mib":1}}'
engine-cli render.benchmark '{"scene":"scene1","width":1920,"height":1080,"frames":240}'
```

`settings.stream` on **`render.load`** is what keeps the scene's page table — it is `SceneDesc::stream`, a property of what loading produced, and a scene loaded without it cannot be streamed later however a subsequent call spells its settings (streaming turns off with a log line instead). `page_bytes` beside it is the host's own knob and has no flag: it sizes the **procedural heightfield's** pages, which is what makes a test scene with dozens of pages instead of three, and it is refused outside 4096..67108864 because a page too small to hold a cluster is a typo. engine-view never sets it, so its heightfield is always at the 128 KiB default. **`procedural`** beside them says *which* scene an empty `mesh` and `scene` build — `""`/`"heightfield"` or `"shredded-atlas"`, the UV-atlas LOD stress fixture ([geometry](geometry.md#the-shredded-atlas)) the `shredded-atlas` corpus scene draws. An unknown name is refused rather than silently drawing the terrain: a corpus scene that asked for the fixture and quietly got the heightfield would pass its threshold and guard nothing. `RenderLoadParams` went to `@version(3)` for it, with the field `@since(3)` and defaulting to the empty string, so an older client sees exactly what it saw.

**`render.benchmark` is where streaming is measured**, and its optional per-call `settings` may turn it on or off for that run alone; the GPU scene and the pipelines are rebuilt from the `SceneData` already in hand, exactly as any other settings change rebuilds them. **`render.capture` takes its streaming settings from the load** and has no `settings` block at all, which is the rule it has always followed and not a gap: a capture is one frame, a streamed scene's first frame is by definition the unconverged one, and a per-call setting there would be a second place to say something `render.load` already said. A converged capture is a `render.benchmark` to warm the residency followed by a `render.capture`, in that order, in one host process.

`stats.stream` on a benchmark's result is `RenderStreamStats`: **every field of engine-view's `streaming` object above, under the same key names**, so one reader serves both hosts, plus `loads_in_flight`, which engine-view's line leaves out because it is a momentary value rather than a count of the run. `pages_total` is 0 for a scene that was uploaded whole, so a script never has to test for the block.

**What the host cannot do yet: read a page off disk.** `stats.stream.source` is always `"host"` over the protocol, and `file_reads`, `file_bytes` and `host_bytes_freed` are always zero — engine-view's `--page-source file` has no protocol equivalent. Streaming therefore bounds the host's *device* memory and not its host memory. The reason is in [protocol](protocol.md#methods-an-app-registers-and-render): attaching the container-backed source also releases the merged host streams, and those streams are what the host rebuilds a GPU scene from when a later call changes the settings.

## The renderer is a library, and both engine-view and engine-host draw with it

Everything that draws moved out of `apps/engine_view/main.cpp` and into [renderer](renderer.md) (layer `systems`): scene loading through the derived-data cache, the GPU-resident scene, the cull and LOD passes, the four rasterizers, the deformed-vertex pool, the acceleration structure chain, the material resolve, the Hi-Z, the GPU timers, and the capture. The reason was not the file's length. It was that **nothing but engine-view could render**, so the protocol had no `capture` and no `benchmark` and the Phase 1 exit criterion could not be met ([10 §10.2](../plan/10-roadmap-risks.md#102-phases)).

**engine-view is the command line over that library.** It keeps the flags and their validation, the window and its events, the surface and the swapchain with its resize and its present, the screenshot of the *presented* image, the shader-reload timer, and the JSON summary. Every flag and every JSON field is unchanged, and so is every picture: the FlightHelmet at `--width 400 --height 300 --frames 6 --orbit 22` through `--raster hw`, `--raster vertex`, `--raster rt --shadows rt`, `--deform wave`, and `--grid-instances 3` produces **byte-identical PNGs** before and after the move (`engine-image compare --json` reports `"psnr":null,"ssim":1,"flip_mean":0` on all five, and the files have the same SHA-256). The one visible change is where a log record comes from: the overrides a device or a scene forces — the mesh-shader fallback, culling forced on, shadows off on a path that cannot trace them — are now logged under the `renderer` category rather than `view`, because both hosts make them in the same function.

**engine-host gained `render.*`**, four methods over the same library, with no window anywhere in the process:

```
render.load      {mesh | scene | procedural, settings, grid_instances, grid, page_bytes, ddc, cache, adapter} -> a scene id and its counts
render.capture   {scene, camera | orbit, width, height, channels, out_dir, name} -> file URIs and stats
render.benchmark {scene, width, height, frames, settings, camera | orbit} -> gpu_ms per pass, cpu ms per frame
render.compare   {a, b, weights, ppd, flip_out} -> FLIP, PSNR, SSIM
```

`render.load` is the expensive call — it imports and clusters a glTF, or reads the container the cache already holds — and the host keeps the result, so a capture and a benchmark of the same scene pay it once. `settings` on `render.benchmark` may differ from the ones the scene was loaded with; the host then rebuilds the GPU scene and the renderer from the loaded `SceneData` rather than re-importing the mesh.

```bash
engine-cli render.load '{"mesh":"content/samples/Suzanne/Suzanne.gltf","settings":{"raster":"hw"}}'
engine-cli render.capture '{"scene":"scene1","orbit":{"distance":22},"width":800,"height":600,
                            "channels":["color","ids","depth","normals"],"out_dir":"out"}'
engine-cli render.benchmark '{"scene":"scene1","width":1920,"height":1080,"frames":120}'
engine-cli render.compare '{"a":"out/capture.png","b":"out/baseline.png","weights":"center"}'
engine-cli render.capture '{"scene":"scene1","width":800,"height":600,"integrator":"reference",
                            "reference":{"spp":512,"bounces":3},"out_dir":"out","name":"ref"}'
engine-cli render.evaluate '{"scene":"scene1","width":800,"height":600,
                             "reference":{"spp":512},"out_dir":"out","name":"eval"}'
```

Because `engine-cli` spawns a host per invocation, a scene id lives only as long as that process: a sequence like the one above is one `engine-host --stdio` session, or one `engine-cli` call per line with a `render.load` in front of each. The scenes are released when the process exits.

`render.capture`'s `channels` are `color` (RGBA8 PNG), `ids` (the entity-ID buffer: three little-endian `u32` per pixel — instance, cluster, triangle — in a `.ids.bin` with a `.ids.json` header describing it), `depth` (an 8-bit gray PNG normalized over the frame's covered range, whose exact bounds are `depth_min`/`depth_max` in the result), and `normals` (an RGB8 PNG of `n * 0.5 + 0.5`, which costs a second frame because only the resolve knows the normal). [renderer](renderer.md) has the encoding in full and says why the id buffer resolves the visibility id into a pair rather than reporting the id. `--raster direct` writes no visibility buffer, so `ids` and `depth` are an error there rather than a buffer of nothing.

**A capture's `gpu_ms` is zero, and that is not a bug.** A timestamp pool is read when its frame slot comes around again, so with two frames in flight the first two frames of any run have no timings yet — and a capture is one frame, or two with `normals`. `stats.gpu_ms.frames` says how many frames the numbers came from, and it is 0 there. `render.benchmark` is the call that measures; `render.capture` reports the visible-pair counts, which do come back, and the picture.

**`render.capture` with `"integrator":"reference"`** draws the same frame with the reference path tracer instead ([04 §4.8](../plan/04-renderer.md#48-reference-renderer-and-objective-optimization), [renderer](renderer.md#reference-renderer)) and writes it to the same `<name>.png`, so a caller comparing the two needs no second code path. The `reference` block is `spp`, `bounces`, `finest`, `seed` and `batch`; the result echoes `integrator` and adds `samples`, `trace_ms` and `seconds`. It has **only** a color channel, because a path tracer writes no visibility buffer — asking for `ids`, `depth` or `normals` is an error with a message. It needs a device with cluster acceleration structures and a scene whose settings build them (`"shadows":"rt"`, or `"auto"` on such a device), and answers 1007 where it cannot.

**`render.evaluate` is the optimization loop in one call.** It renders the real-time picture and the reference of the *same* frame — one camera, one frame number, one set of lights — renders the reference again at a single bounce unless `direct_only` is false, compares both pairs, writes `<name>.realtime.png`, `<name>.reference.png`, `<name>.flip.png`, `<name>.reference_direct.png` and `<name>.flip_direct.png`, and returns `full` and `direct` metrics, the real-time `stats`, `samples`, `reference_trace_ms`, `reference_seconds`, `realtime_seconds`, `metrics_ms` and the `machine_state` span. The `direct` half is what makes a threshold explicable: the gap between it and `full` is the indirect light the real-time path does not have, which is large in a scene with interiors and small in an open one. `tools/ci/reference-compare.ps1` is the corpus runner over this method.

The end-to-end suite for all four is `apps/engine_cli/tests/render_tests.cpp` (`tools/dev.ps1 test -Filter engine_cli`). It drives one `engine-host --stdio` process through the whole round trip — because a scene id lives in the host and the CLI spawns one host per invocation — and renders the **procedural heightfield**, so the case needs no fixture, no sample asset, and no cache entry. It checks the scene counts, all four channels landing on disk with the id file exactly `width * height * 3 * 4` bytes and the header describing that, a benchmark at a different size reusing the loaded mesh and reporting a GPU millisecond field per pass, a capture compared against itself giving a null PSNR and an SSIM of 1, and the four error codes a client has to tell apart. `render.compare` is driven through engine-cli as well, since it is the one method that never opens a device and so runs on a machine without one. A second case covers the reference integrator and `render.evaluate`: a 32-sample reference capture landing on disk with its sample count echoed back, an id channel and an unknown integrator both refused, and one `render.evaluate` producing all five files with both sets of metrics — skipping on 1007, which is what a machine without cluster acceleration structures answers. A third covers geometry streaming, and it is a case about the *schema* as much as about the renderer: the heightfield loaded with `page_bytes` 16384 and a 1 MiB budget gives 179 pages over 3.8 MB, and `stats.stream` comes back with a budget of exactly 1048576 — unclamped, so the MiB on the wire really did become bytes — pages resident, pages pinned, pages uploaded and requests written, and `source` `"host"` with the three file counters at zero, which is all the heightfield can ever report. Then the same scene benchmarked with a per-call `"stream":false` reports `pages_total` 0 while still drawing its pairs, which is the evidence that an additive settings field reached the renderer rather than being decoded into a struct nobody reads; and `page_bytes` 7 and an `upload_budget_kib` of 2³²−1 are both 1004.

## What else the machine was doing, in both hosts' numbers

A frame time from this project's development box is not a frame time from an idle machine: it renders beside GPU jobs that hold most of the card and beside several agent builds. So **engine-view's JSON summary and `render.benchmark`'s result both carry the load they were taken under**, in the same shape and against the same thresholds the CPU benchmark harness uses ([bench](bench.md#measuring-on-a-shared-machine)).

Two blocks, both **added** to the existing fields — nothing was renamed and nothing moved out, because tests and scripts read this line:

```json
"gpu_memory":{"budget_mib":31614,"used_mib":297,"device_local_total_mib":32404},
"machine_state":{"start":{"cpu_total_pct":9.3,"cpu_own_pct":0.0,"cpu_others_pct":9.3,
                          "gpu_util_pct":0.0,"gpu_memory_used_mib":17117,
                          "gpu_memory_total_mib":32607,"session_locked":false,
                          "gpu_lock":null},
                 "end":{...}}
```

`gpu_lock` is the machine-wide GPU lock as the sample found it — `null` when nobody held it, else `{"owner","purpose","expires","mine","expired"}` ([bench](bench.md#measuring-on-a-shared-machine), "The GPU lock") — and a lock somebody else held is a WARNING of its own. It is in engine-view's summary only: the protocol's `MachineState` schema type does not carry it yet, so over `render.benchmark` and `render.evaluate` the lock shows in engine-host's stderr WARNING and not in the result. A host started under a lock-holding wrapper (`gpu-lock.ps1 run`, `gpu-smoke.ps1`, `reference-compare.ps1`) inherits `ENGINE_GPU_LOCK_HOLDER` and reports the lock as `"mine":true` rather than warning about its own parent.

`gpu_memory` is the renderer's ([renderer](renderer.md)), read from the Vulkan device around the run. `machine_state` is sampled **outside** the timed region — before the first frame and after the last — because the sampler sleeps for a quarter of a second to get a CPU percentage and spawns `nvidia-smi` for the GPU reading, and neither belongs between two timed frames. Every field is `null` where the platform could not answer, so "quiet" and "not measured" are different answers; no process names are ever reported.

**Read the two together.** In the line above the Vulkan budget says 31,614 MiB of 32,404 MiB were available to this process while `nvidia-smi` says 17,117 MiB of the card were in use: the budget does not fully see a CUDA tenant, so `device_local_total_mib - budget_mib` is a lower bound on what others hold and `gpu_memory_used_mib` in `machine_state` is the number that answers "is somebody else on this GPU".

When other processes used more than 10% of the CPU or the GPU was more than 20% busy at either end of the run, both hosts write **one WARNING line to stderr** — the same sentence `foundation/bench` prints, for the same reason: stdout is the summary and the protocol, and a caveat that corrupted either would be worse than no caveat. It does not mean the numbers are wrong; it means they are upper bounds, and a write-up that quotes them owes its reader the "Machine state" line ([docs/experiments/README.md](../experiments/README.md)).

`render.benchmark`'s result went to `@version(2)` for this, and `RenderStats` with it: `stats.gpu_memory` and `machine_state` are `@since(2)` with defaults, so an older client reading the result sees exactly the fields it saw before.

**Multi-view over the protocol.** `RenderSettings` went to `@version(2)` for this: `views` (`single`, `surround3`, `panini`), `side_yaw_deg`, `panini_d` and `peripheral_lod` are `@since(2)` with the single-view defaults, so both hosts spell the layout the same way and parse it with the same function ([settings.h](renderer.md#public-api)). `RenderStats` went to `@version(3)` and gained `views` — one `RenderViewStats` per view with its rectangle, its source extent, its tier, its visible pairs and its milliseconds by pass — beside `view_layout` and `oversample`. Changing the layout between calls rebuilds the GPU scene and the renderer the way any other settings change does, because the per-frame working set is sized by the view count. This is the path E9 measured through, since it renders offscreen at 11520×2160 on a machine whose window would not be that big.

**Where there is no GPU**, every `render.*` method fails with error code **1007 `RenderUnavailable`** and a message naming the adapter and what it lacks — no Vulkan loader or driver, no 64-bit buffer atomics, or no cluster acceleration structures for `"raster":"rt"`. It is a code of its own so a client can tell "this machine cannot render" from "you asked for something wrong" ([protocol](protocol.md)); the end-to-end test skips on it exactly as engine-view's suite skips on exit 3, which is what lets one suite run on the hosted CI runners and on the GPU machines alike.
