# apps: engine-host, engine-cli, engine-view, engine-content, engine-input, engine-image (apps)

**Purpose.** The first executables (docs/plan/02-architecture.md §2.2, ADR-0001). `engine-host` is the engine as a headless server: in Phase 0 it runs in `sim` mode only and speaks JSON-RPC 2.0 over stdio, one request per line in and one response per line out. `engine-cli` is the thin scriptable client for humans, agents, and CI: it spawns a host, optionally opens a document, sends one method, prints the result, and exits. Because sessions persist their journal and undo position on disk (see [doc](doc.md) and [protocol](protocol.md)), a sequence of separate `engine-cli` invocations behaves like one editing session, which is what the Phase 0 exit criterion asks for and what the end-to-end test checks. `engine-view` is the window on the renderer, and `engine-content` is the content build on the command line: the step that turns a source mesh into the derived form the renderer loads.

**engine-host.**
```
engine-host [--stdio] [--request <json>] [--mount <scheme>=<dir>[:rw]]... [--log <spec>] [--log-json <path>] [--tunables <file>]
```
stdout belongs to the protocol. Log records go to an in-memory ring (`log.tail` reads it), warnings and above to stderr, and optionally every record as JSON lines to a file. Assertion failures are routed through the log before the process aborts. `--request` answers one request and exits, for scripts that do not want a pipe.

**engine-cli.**
```
engine-cli [--host <path>] [--doc <dir>] [--create] [--name <name>] [--mount <spec>]... [--compact] <method> [params-json]
```
With `--doc` the CLI opens the document first (creating it with `--create`) and injects the session id into the params. Results print as pretty JSON (or one line with `--compact`); errors print `error <code>: <message>` and any diagnostics to stderr and exit 1; usage problems exit 2. The host is found beside the CLI unless `--host` says otherwise.

**Example (the exit criterion).**
```bash
engine-cli --doc ./world --create --name World session.info
engine-cli --doc ./world doc.apply '{"commands":[{"kind":"CreateObject","id":"00000000000000100000000000000001","type":"engine.content.AssetProvenance"}],"attribution":{"actor":"me","role":"environment","task":"t1","rationale":"first object"}}'
engine-cli --doc ./world doc.objects
engine-cli --doc ./world doc.undo
engine-cli --doc ./world doc.redo
engine-cli --doc ./world doc.add_layer '{"name":"quest"}'
engine-cli --doc ./world doc.diff '{"from_layer":"base","to_layer":"quest"}'
engine-cli --doc ./world doc.merge '{"base_layer":"base","ours_layer":"quest","theirs_layer":"other","output_layer":"merged"}'
engine-cli gpu.adapters                       # what the machine's GPUs support (see gfx.md)
```

**engine-view.**
```
engine-view [--width <px>] [--height <px>] [--frames <n>] [--capture <file.png>] [--no-vsync] [--adapter <i>] [--validation] [--grid <n>] [--log <spec>] [--shaders <manifest.json>] [--lod <px>] [--no-cull]
            [--raster direct|hw|vertex|sw|auto|rt] [--sw-px <px>] [--view id|tri|depth|shaded|normals|uv] [--orbit <d>] [--no-occlusion] [--no-cone]
            [--mesh <file.gltf|file.glb|file.clusters>] [--scene <file.json>] [--grid-instances <n>] [--no-cache] [--ddc <dir>] [--no-lights] [--shadows off|rt]
            [--deform none|identity|wave|lattice] [--deform-amplitude <a>] [--rt-templates]
            [--views single|surround3|panini] [--side-yaw <deg>] [--panini-d <d>] [--peripheral-lod <mult>]
```
The engine's first window (windowed mode). A procedural heightfield is built into a cluster LOD DAG (`geometry`), uploaded behind device addresses, culled and LOD-selected on the GPU every frame (`cluster_cull.slang`, threshold `--lod` in pixels, default 1), and drawn one mesh-shader workgroup per surviving cluster through an indirect draw into the swapchain with a reversed-Z depth buffer while the camera orbits and zooms between 8 and 36 units so the cut changes visibly; each cluster gets its own color, so the picture is also the cluster-partition debug view. `--no-cull` draws every leaf cluster instead. `--raster` picks the path: `direct` is mesh shaders straight to color with a depth buffer; `hw` (default), `vertex`, `sw`, and `auto` rasterize into the 64-bit visibility buffer through mesh shaders, the vertex-shader baseline tier (chosen automatically on GPUs without mesh shaders), the software rasterizer, or mesh shaders and software split at `--sw-px` pixels of projected cluster diameter, then resolve it; `rt` replaces rasterization with ray queries (NVIDIA RTX only, exit 3 elsewhere): the cull pass's visible list becomes cluster acceleration structure build records on the GPU (`clas_records.slang`), the CLAS, cluster bottom-level, and top-level structures are built in the same frame with no CPU round trip, and `ray_visibility.slang` traces one ray per pixel into the visibility buffer, which the resolve then shades exactly as it shades a rasterized one (`gpu_ms.rt` is the four builds, `gpu_ms.trace` the rays; the FlightHelmet's 253-cluster cut builds in 0.16 ms and traces in 0.02 ms at 800×600 on the RTX 5090) (`--view` shows materials lit by a sun with smooth vertex normals by default, or cluster colors, triangle shading, depth, normals, or UVs; three materials, sand, rock, and snow, are assigned by the height of each cluster's center, and sand and rock sample a procedural ripple texture through the bindless set at different UV scales). The shaded view lights the surface with the resolve's physically based BSDF (`brdf.slang`, see [gfx](gfx.md)): a directional sun, a sky hemisphere, and two point lights orbiting the scene out of phase, one warm and one cool, whose radius of influence and intensity scale with the scene radius (intensity with its square, because the falloff is inverse square) so a 2 cm mesh and the heightfield are lit alike. They are passed per frame behind the `ResolveParams` block in the same host-visible buffer, and `--no-lights` turns them off, which is how to measure or compare a picture with only the sun in it. On the heightfield they change the picture by up to 110 of 255 and by 9 on average. `--orbit` fixes the camera distance for measurements; camera distances scale with the scene radius (10 for the heightfield). `--mesh` renders a glTF 2.0 or GLB file instead of the heightfield (`assets::load_gltf`, then `geometry::weld_vertices` so exported duplicate vertices do not starve the clusters; `tools/fetch-samples.ps1` fetches permissively licensed Khronos samples into `content/samples/`): one cluster LOD DAG is built per primitive and the DAGs are merged (`geometry::merge_cluster_lod`) so that every cluster has exactly one material; the file's metallic-roughness materials become the resolve's material table (base color as albedo, roughness and metallic carried along, and the emissive factor as a constant term unless the material modulates it with an emissive texture, which the resolve has no slot for yet), and each material's base-color, metallic-roughness, and normal images are decoded on the CPU (`image::decode_image`, embedded bytes or a file beside the glTF) and uploaded into the bindless set — one slot per image, shared by every material that names it, base color as sRGB and the two data maps as UNORM, since a roughness or a normal is not a color. An image that fails to decode leaves that slot empty with a warning, and the camera orbits the mesh's bounds.

**What the samples look like now that the maps are read.** The three Khronos models the resolve was compared on, before and after, at `--width 800 --height 600 --orbit 22`. FlightHelmet: the leather crown was one flat olive-brown dome with a single broad sheen, and is now visibly creased and quilted, its stitching and panel seams standing out under the orbiting point lights, the brown warmer and more varied; the metal on the mask frame, the buckles, and the ribbed hose pick up small bright glints where before they were the same dull matte as the cloth; the goggle lens has a defined highlight; and the varnished wooden base has gained a glossy band along its top face. BoomBox: the silver body panel, the handle, and the antenna were a uniform mid-grey and now read as metal, bright with a sharp moving highlight, while the speaker grille has gone from a flat printed dot pattern to a recessed, dark, perforated mesh; the black shell's highlight is tighter and the buttons and dials have relief. Corset: the red brocade was plasticky with a wide sheen and is now dull cloth with the damask pattern in relief, the laces are round cords with a highlight each instead of painted-on lines, the eyelets glint, and the cream mannequin is matte with its seams visible; the base disc is glossier than the body it holds. In short: cloth and leather have become dull dielectrics, buckles and the BoomBox's metal have become metal, and the normal maps put surface detail where the geometry has none. `--mesh` also takes a `.clusters` container ([geometry](geometry.md)) and renders it without importing or clustering anything: the DAG, the quantized positions and their grid, the attributes and triangles, the materials from the file's 64-byte records — including the metallic-roughness, normal, and emissive slots that live in the record's second half, which an older container leaves at zero and the reader therefore reads as "none" — the material index of every cluster, and the textures decoded from the file's image paths resolved against the directory of the source mesh the container names (against the container's own directory when it names none). Everything downstream — cull, LOD selection, the four rasterizers, ray tracing, the resolve — is the same code and draws the same picture: the FlightHelmet gives the same cut and a byte-identical capture whether it came from the glTF or from a container built from it, and `--raster hw` and `--raster rt` agree to 59 pixels of 480,000 at 800×600 (silhouettes, where a ray and a rasterized edge disagree). An image the source embedded has no path and no bytes in a container, so such a material draws untextured with a warning until the texture pipeline gives images a derived form of their own. Between the two, `--mesh <file.gltf>` looks in the **derived-data cache** first: `<ddc>/clusters/<hash>.clusters`, where the hash covers the glTF's bytes and those of every external buffer it names, the cluster build options, and a cache version constant (`geometry::cluster_cache_key`, `cluster_cache_path`). A hit loads the container; a miss builds as before and writes the entry, the same mesh `engine-content build --cache` writes to the same path, so either program fills the cache and either finds it. The two entries differ in one section: `engine-content` records the source's identity (`source_hash`, section 15) and `engine-view` leaves it zero, which costs an `engine-content build-all` one rebuild of an entry `engine-view` wrote, and nothing else. `--no-cache` skips both. The cache root is `<repo>/ddc`, found by walking up from the executable to the directory holding `AGENTS.md`, or `--ddc <dir>`; with neither, the cache is off with a warning. The FlightHelmet takes 907 ms to import and cluster in `msvc-debug` on an RTX 5090 machine and 31 ms to load from the cache, reported as `build_ms` either way. **A scene of instances.** `--scene <file.json>` renders several meshes and several instances of them instead of one mesh: `{"meshes":[{"path":"...gltf|.glb|.clusters"}], "instances":[{"mesh":0,"translation":[x,y,z],"rotation":[x,y,z,w],"scale":[x,y,z]}]}`, where a mesh path is resolved against the file's own directory, every instance field but `mesh` is optional, and an empty instance list places one identity instance of every mesh. The meshes load exactly as `--mesh` loads one, cache and all, and then go into one set of buffers through `geometry::merge_cluster_meshes`, each keeping its own 16-bit position grid; each mesh's materials follow the last mesh's in one table and each instance's `material_base` points at its mesh's, so the clusters keep mesh-local material indices. `--grid-instances <n>` is the same machinery from one flag: n × n copies of the loaded mesh on a grid three mesh radii apart, with a rotation and a scale that vary per copy and a non-uniform scale on every third, so one run exercises the uniform and the non-uniform path, the cone test's precondition, and the LOD scaling at once. The camera frames the scene's bounding sphere, the union of the instances' transformed mesh bounds, and `--no-cull` is ignored with more than one instance because a scene draws through the cull pass. On the RTX 5090, `--grid-instances 5` on the FlightHelmet (25 instances, 58,700 pairs) at 800×600 culls in 0.023 ms, rasterizes 201 visible pairs in 0.004 ms through mesh shaders, and through `--raster rt` builds the frame's cluster acceleration structures in 0.49 ms — most of it the 25 bottom-level builds, which share one scratch buffer and so are serialized — and traces in 0.012 ms.

**`--views single|surround3|panini`** and its three knobs are the multi-view layout ([04 §4.6](../plan/04-renderer.md#46-extreme-displays), [renderer](renderer.md#multi-view-a-viewset-over-one-scene), experiment [E9](../experiments/e9-multi-view.md)). `single` is the default and is unchanged in every respect, down to the bytes of the picture. `surround3` divides the target into three monitors with per-monitor off-axis frusta, which is what the project owner's 11520×2160 actually is; `--side-yaw <deg>` is the angle the side monitors are physically turned inward, 0 being a flat arrangement whose three frusta are exactly the three thirds of one wide rectilinear frustum. `panini` renders one wide view rectilinear into an oversampled source and resamples it with a Panini projection of parameter `--panini-d` (0 is the ordinary rectilinear picture, 1 the classic Pannini); the summary reports the `oversample` factor the source needed. `--peripheral-lod <mult>` multiplies the LOD pixel threshold outside the attention region, which for a surround is the two side monitors — a surround player reads them peripherally, so a coarser cut there is the expected behavior and not a compromise. The monitor width, height and bezel gap are parameters of the layout too, but of the module's `Surround3` rather than of a flag: a flag would only be able to say what the target already says, since the rectangles have to tile the swapchain.

The JSON summary gains a `views` block — the layout, the count, the yaw, the Panini `d` and oversample, and a `per_view` array with each view's rectangle, tier and GPU milliseconds by pass beside the totals — and an `rt_bytes` figure for what the acceleration structure chain holds, which is the number that grows with the view count. **A capture at 11520×2160 belongs to engine-host, not here**: engine-view sizes its swapchain from a real window, so the offscreen path (`render.capture`, `render.benchmark`) is what renders a surround-sized frame on a machine whose display is smaller, and it is what experiment E9's numbers were taken through.

**`--shadows off|rt`.** With `rt` every light of the resolve casts a ray-traced shadow: the sun and both orbiting point lights trace one terminate-on-first-hit ray each against the frame's own top-level structure, which holds exactly the clusters the frame drew ([gfx](gfx.md)). It is the default wherever the device has cluster acceleration structures and ray queries, and off with a log line where it does not, or in `--raster direct`, `sw`, and `auto` (the first has no resolve, and the other two split the cut across more than one visible list). **In `hw` and `vertex` the frame runs the whole acceleration structure chain too** — records, ranges, emit, CLAS, one cluster bottom-level structure per instance, top-level — from the same cull output `--raster rt` builds from, which is why it also turns two-pass occlusion culling off: the structures are built from one visible list and pass 2's survivors are in a second one. `gpu_ms.rt` is that chain; there is no `gpu_ms.shadows`, because the rays are inside the resolve and a timestamp cannot separate them, so the cost is the resolve with shadows against the resolve without them. FlightHelmet 3×3 (9 instances, 94,722 triangles each, `--orbit 22` then the closer `--orbit 9`, 60 frames, `msvc-debug`, RTX 5090):

| | resolve, `off` | resolve, `rt` | `gpu_ms.rt` | frame total, `off` → `rt` |
|---|---|---|---|---|
| 800×600, orbit 22 (124 pairs, 2% of the frame covered) | 0.021 ms | 0.022 ms | 0.363 ms | 0.103 → 0.404 ms |
| 3840×2160, orbit 22 | 0.092 ms | 0.098 ms | 0.544 ms | 0.443 → 0.675 ms |
| 11520×2160, orbit 22 | 0.199 ms | 0.227 ms | 0.529 ms | 0.830 → 0.780 ms |
| 800×600, orbit 9 (356 pairs, the helmets filling the frame) | 0.012 ms | 0.025 ms | 0.352 ms | 0.082 → 0.392 ms |
| 3840×2160, orbit 9 | 0.111 ms | 0.181 ms | 0.772 ms | 0.404 → 1.004 ms |
| 11520×2160, orbit 9 | 0.230 ms | 0.399 ms | 0.921 ms | 0.965 → 1.413 ms |

So the rays cost the resolve **1.6× to 2× when the geometry fills the frame** and almost nothing when it does not — they are traced per covered pixel, and the sky returns before any of them — while the structures that make them possible cost three to nine times as much as the shading. The 11520×2160 row's total falls with shadows on only because two-pass occlusion culling turns off with them, and its Hi-Z pass is 0.58 ms at that width. What the pictures show at `--orbit 9`: 8,760 pixels of 480,000 differ between `off` and `rt` (up to 202 of 255, 13.7 on average), and they are where a helmet's shell shadows its own goggles, mask, and hose, where the hose lays a dark contact band across the wooden base, and where the leather crown darkens the top face of the stand under it. The 3×3 grid spaces the instances three mesh radii apart while the sun sits 53° up, so no helmet's shadow reaches its neighbour there; a `--scene` file with two helmets a quarter of a unit apart gets that too (25,596 pixels of 270,000 differ, and the front helmet's hose and stand darken the one behind).

The cull pass backface-culls clusters by their normal cones unless `--no-cone`. In the `hw` and `vertex` modes two-pass occlusion culling is on (`--no-occlusion` turns it off): pass 1 draws last frame's visible clusters, a Hi-Z pyramid is built from the visibility buffer, pass 2 tests the rest against it, and the pyramid is rebuilt for the next frame; the summary reports the clusters each pass drew and the Hi-Z time. The JSON summary reports cluster and level counts, DAG build time, the number of glTF primitives (`mesh_primitives`, 0 for the heightfield and 0 for a mesh that came from a container, which does not record how many primitives were merged into it), where the mesh came from (`mesh_cache`: `"miss"` built from the glTF and written to the cache, `"hit"` read from the cache, `"file"` a container named on the command line, `"none"` the heightfield or `--no-cache`), whether cone culling was on, whether shadows were traced (`shadows`: `"rt"` or `"off"`), the scene's `meshes`, `instances`, and `pairs` (the prefix sum the cull pass covers), the hardware and software visible-pair counts and their sum `visible_pairs_last` (read back one frame late from per-slot copies of the indirect arguments), GPU milliseconds per pass (cull, hw, sw, resolve) averaged over the run from timestamp queries, which is how experiment E1 was measured, and the `gpu_memory` and `machine_state` blocks the last section of this page describes. `--frames N --capture out.png` renders N frames and writes the last one as a PNG, and the process prints one JSON line of statistics (frames, seconds, average ms, size, cluster and triangle counts, whether the capture was written) to stdout, so scripts and agents look at the picture and the numbers without a human at the window. Escape or closing the window exits; resizing recreates the swapchain and the depth buffer. Shaders come from the build's manifest when it sits beside the executable (`<exe dir>/../shaders/manifest.json`, or `--shaders`), so editing `cluster_mesh.slang` while the window is open recompiles it through slangc and rebuilds the pipeline within a quarter second; a save that does not compile prints slangc's diagnostics to stderr and keeps the last good shader. `--log` with an explicit spec routes those categories to stderr at the given levels. Exit codes: 0, 1 error, 2 usage, 3 unavailable (no display, no Vulkan device, no mesh shaders, or no presentation), which the end-to-end test treats as a skip. On the RTX 5090 the default 257×257 grid (131,072 triangles, 2,898 clusters in 12 levels, 861 ms to build) draws 98 to 162 clusters per frame at a 1 px threshold and renders in about 0.65 ms per frame at 960×540 without vsync.

**`--deform none|identity|wave|lattice`, `--deform-amplitude <a>`, `--rt-templates`** (experiment [E25](../experiments/e25-deformed-clusters.md)). `--deform` makes **every instance of the scene deformed**: it gets a block of the frame's deformed-vertex pool as long as its mesh's cluster-ordered vertex range, and a compute pass (`deform.slang`) fills the blocks of the clusters the cull pass selected, once per run of the visible list, before the draw that reads them. Every position reader then takes that instance's positions out of the pool — the rasterizers, the resolve, and the cluster acceleration structure records ([gfx](gfx.md)) — so the raster picture and the ray-traced one deform together. `identity` writes the rest pose, which is the mode to reach for when something looks wrong: it must draw what `--deform none` draws. `wave` displaces along the vertex normal and `lattice` runs a 3×3×3 trilinear cage over the mesh's bounds, both animated by frame number at 60 Hz and both scaled by `--deform-amplitude`, a fraction of the mesh's bounding cube (0.02 by default; 0.4 units on the 20-unit heightfield). `--no-cull` is ignored with `--deform`, because the pass walks the cull pass's visible list — that is the whole point of it. `--rt-templates` changes how `--raster rt` (or `--shadows rt`) turns the cut into ray tracing geometry: instead of rebuilding a cluster acceleration structure per visible cluster every frame, it builds one **template** per cluster of the scene at load, from the rest pose, and instantiates the cut's templates with the pool's positions each frame. The JSON summary gains `deform`, `deform_pool_bytes`, `rt_templates`, `template_bytes`, and `gpu_ms.deform` and `gpu_ms.clas` (the cluster structure build or instantiation on its own, inside `gpu_ms.rt`). On the RTX 5090 at 1920×1080, `--orbit 22`, `--shadows off`: the pool pass costs 0.0096 ms for a 266-cluster cut and 0.0132 ms for a 4,363-cluster one on the `--grid 1025` heightfield (2.1M triangles), and 0.0096 / 0.0131 ms for cuts of 396 and 4,831 clusters over 64 FlightHelmets (94,722 triangles) — the same numbers for meshes 22× apart in size, which is the point of the pool. `--rt-templates` turns a 0.066–0.180 ms per-frame cluster structure rebuild into a 0.014–0.061 ms instantiation, for 537 B of template per cluster of the mesh held resident (25 MB for the heightfield's 46,626 clusters, 1.1 MB for the helmet's 2,348). Two warnings worth reading before using the flags in anger: the pool is allocated for each deformed instance's **whole** mesh (33 MB for one heightfield instance, 110 MB for 64 helmets), and `--deform wave` displaces along the vertex normal, which **tears** a model at its hard edges and LOD-group boundaries — `--deform lattice`, a function of position alone, does not. [E25](../experiments/e25-deformed-clusters.md) has the comparison and the reason, and the command lines that reproduce both.

**engine-content.**
```
engine-content build <in.gltf|in.glb> <out.clusters> [--max-triangles <n>] [--max-vertices <n>] [--no-weld] [--jobs <n>] [--strict] [--log <spec>]
engine-content build <in.gltf|in.glb> --cache [--ddc <dir>] [--max-triangles <n>] [--max-vertices <n>] [--no-weld] [--jobs <n>] [--strict] [--log <spec>]
engine-content build-all <manifest.json> [--cache] [--ddc <dir>] [--jobs <n>] [--strict] [--log <spec>]
engine-content info <file.clusters>
engine-content stats <file.clusters>
```
The content build on the command line (docs/plan/07-content-pipeline.md §7.3): the step between a source mesh and what the renderer loads. `build` imports the file with `assets::load_gltf`, welds its vertices unless `--no-weld` (exporters duplicate freely, and without welding the 64-vertex cluster limit starves both the clusters and the LOD builder), builds one cluster LOD DAG per glTF primitive with the file's normals and UVs so that every cluster has exactly one material — one job per primitive on the job system's performance pool — merges them (`geometry::merge_cluster_lod`) in primitive index order, maps each merged cluster to its primitive's material (a primitive that names none gets one appended default), converts the metallic-roughness materials into the file's 64-byte records — base color, metallic and roughness, the base-color, metallic-roughness, normal, occlusion, and emissive image slots, the emissive factor, the normal scale, and the packed alpha mode, cutoff, and double-sidedness ([geometry](geometry.md)) — carries the image paths over as the glTF gave them (an embedded image keeps its slot with an empty path and is counted separately) together with the source path they are relative to and the source's identity — its content hash and the build key over that hash and the options, which is what lets a later build recognize the container as the answer to the same question — and writes the `.clusters` container described in [geometry](geometry.md). `--max-triangles` (4..256) and `--max-vertices` (1..255) are the per-cluster limits, 124 and 64 by default. `--cache` replaces the output file with the derived-data cache entry this source and these options address — `<ddc>/clusters/<hash>.clusters`, the path `engine-view --mesh` looks in before it builds anything — and the summary's `path` says where it went; an output file and `--cache` together are a usage error, since one build has one destination. `--ddc <dir>` names the cache root, which is otherwise `<repo>/ddc`, found by walking up from the executable to the directory holding `AGENTS.md`. `info` reads a container back and prints its header, every section record with its kind and name — including a section this build does not know, since it reads the table straight from the bytes — and the counts. Every command prints JSON lines on stdout and nothing else (`build`: `path`, `cached`, `source_hash`, `build_key`, `clusters`, `leaf_clusters`, `triangles`, `lod_levels`, `vertices` (cluster-ordered, so duplicated per cluster and per level), `materials`, `images`, `embedded_images`, `warnings`, `bytes`, `build_ms`, `hash`; `info` adds `source_path`), so a script reads the numbers and an agent checks the hash; everything else is a log record on stderr under the `content` category. Exit codes: 0, 1 (the mesh could not be loaded, validated, clustered, or written), 2 usage.

**What a build is allowed to be** ([07 §7.4](../plan/07-content-pipeline.md#74-validation-rules-automatic)). `build` checks the mesh as it was imported, before welding, so a diagnostic names the primitive and triangle of the *source* file. Each rule carries a stable id, which is the machine-readable failure [§7.3](../plan/07-content-pipeline.md#73-content-build-the-derived-data-graph) asks for: `geometry.empty_primitive` (a primitive with no indices, or a count that is not a whole number of triangles), `geometry.index_range` (an index past the vertex count), `geometry.nan_position` (a coordinate that is not finite), `geometry.degenerate_triangle` (a repeated corner, or two edges exactly parallel in float arithmetic, so the triangle covers no pixel), and `geometry.cluster_budget` (more than 2^24 clusters, which is what the visibility buffer's `cluster << 8 | triangle` word can name) are errors: the first one exits 1 with `<rule>: <sentence>` on stderr and nothing is written. `geometry.uv_range` (a UV past ±16 — sixteen wraps is already past any texel density the texture pipeline can serve, but a trim sheet legitimately runs to a few, so it is not an error) and `material.missing_image` (a slot naming an image with neither bytes nor a path, or an external path that is not there, which draws untextured) are warnings: a `warn` log record each, counted in the summary's `warnings`, and `--strict` turns the first of them into the same kind of refusal. None of the seven sample models trips any of them.

**Many meshes, once each** ([07 §7.3](../plan/07-content-pipeline.md#73-content-build-the-derived-data-graph): incremental and parallel builds). `build-all <manifest.json>` takes `{"meshes":[{"source":"a.gltf","output":"a.clusters","options":{"max_triangles":124,"max_vertices":64,"weld":true}}]}`; `source` is required, `output` and `options` are not, and both paths are resolved against the manifest file's own directory so a manifest is movable as a unit. An entry with no `output` needs `--cache` and goes to the entry the cache addresses; without `--cache` it is an error before anything is built. Each entry is one job on the performance pool. A job hashes the source (`assets::source_mesh_hash`), computes the build key (`geometry::cluster_cache_key` over that hash, the options, and `k_cluster_cache_version`), and **skips the entry when the container already at the output records that same source hash and that same key** — which is what the `source_hash` section of the container is for, and why a container that records none (an older build, or one `engine-view` wrote) is rebuilt rather than trusted. It prints one JSON line per mesh, in manifest order rather than completion order, with `status` `built`, `skipped`, or `failed` (plus `rule` and `error`), then `{"built","skipped","failed","seconds"}`; a failed entry does not stop the others, and the run exits 1 if any failed.

**Threads, and why the bytes do not depend on them.** `--jobs <n>` sizes the performance pool ([jobs](jobs.md)); absent, it is one worker per performance CPU. `build` runs the per-primitive `build_cluster_lod` calls as one job each and merges them **in primitive index order, never in completion order**, so a mesh builds the same bytes at any thread count; the tests pin that with `--jobs 1` against `--jobs 8`. `build-all` puts the parallelism one level up, one job per mesh, and builds each mesh's primitives in sequence inside it: the manifest is the coarser level and already fills the pool, and one wait per mesh keeps the helper stack shallow. A single-mesh manifest is therefore no faster than `build` on it, which is what `build` is for.

**stats** reports what [07 §7.3](../plan/07-content-pipeline.md#73-content-build-the-derived-data-graph) wants watched between builds, as one JSON line: `level_clusters` (clusters per DAG level) and `groups`; `triangles_per_cluster` with `min`, `median` (the upper middle, so it is a count some cluster has), `max`, `total`, and a `histogram` of one `{triangles, clusters}` entry per distinct count, ascending, whose counts add up to the cluster count; `source_vertices` (what the container records, which for a merged mesh is the whole source vertex space once per primitive), `referenced_source_vertices` (the distinct entries of `vertex_source`, which is the only denominator a ratio means anything against), `cluster_vertices`, and `vertex_duplication` between the last two; `bytes` with `total`, `header`, `section_table`, `payloads`, `padding` (what the 16-byte payload alignment costs) and one entry per section, including a section this build does not know; and `quantization` with the grid `step` and `origin`. The FlightHelmet: 2,348 clusters in 10 levels (1,102, 600, 310, 163, 85, 43, 22, 12, 8, 3), 1 to 105 triangles a cluster with a median of 86, 143,515 cluster vertices over 55,392 referenced source vertices for a duplication of 2.59, and of its 5,297,184 bytes 1,722,180 are float positions, 1,148,120 attributes, 861,092 quantized positions, 755,060 triangles, 574,060 vertex sources, 112,704 each of cluster and LOD descriptors, and 76 bytes of alignment padding.

Measured on the samples `tools/fetch-samples.ps1` fetches, `msvc-release` on an i9-10980XE (28 performance CPUs), `build_ms` being import, validation, clustering, and the write: `FlightHelmet/FlightHelmet.gltf` is 94,722 triangles into 2,348 clusters in 10 levels (1,102 leaves) with 6 materials and 15 images, 5,297,184 bytes, in **171–185 ms with `--jobs 1` and 109–119 ms at the default** over three runs each — 1.5×, because the file has six primitives and the largest of them is the critical path — and the two outputs are byte-identical (same SHA-256, same content hash). `Suzanne/Suzanne.gltf` is 3,936 triangles into 88 clusters in 7 levels (42 leaves), 198,992 bytes in 21 ms; `SciFiHelmet/SciFiHelmet.gltf` 23,358 triangles into 587 clusters in 10 levels, 1,320,224 bytes in 87 ms; `Corset/Corset.glb` 18,324 triangles into 437 clusters, 989,936 bytes in 76 ms; `BoomBox/BoomBox.glb` 40 ms; `Lantern/Lantern.glb` 34 ms; `Avocado/Avocado.glb` 682 triangles into 15 clusters, 33,568 bytes in 33 ms, with its 3 images embedded. `build-all --cache` over all seven takes 0.34 s cold at the default and 0.43 s with `--jobs 1` (the FlightHelmet is more than a third of the work, so the manifest-level parallelism has little to spread), and 0.04–0.07 s warm, skipping all seven. In `msvc-debug` the FlightHelmet takes 618–632 ms with `--jobs 1` and 418–470 ms at the default, and Suzanne 55 ms. `engine-view --mesh` reads exactly these containers, and writes the same mesh into the cache itself when it has to build one.

**engine-input.**
```
engine-input devices
engine-input probe [--seconds <n>] [--device <slot>] [--gamepad|--joystick] [--log <file.jsonl>] [--events <file.jsonl>]
engine-input replay <file.jsonl>
engine-input ffb --device <slot> [--spring <s>] [--damper <d>] [--constant <c>] [--seconds <n>]
engine-input rumble --device <slot> [--low <l>] [--high <h>] [--ms <n>]
```
The probe for input devices nobody on the project owns. The engine's input path has to work with wheels, pedal boxes, shifters, flight sticks, and pads on dongles, and none of them can be characterized from a machine they are not plugged into; this tool turns a device into a file that can be read, replayed, and turned into a test here.

`devices` prints one JSON line per attached gamepad and joystick — `{space, slot, name, raw_name, guid, vendor, product, axes, buttons, hats, is_gamepad}`, from `window::input_devices` (docs/subsystems/window.md), where `name` is resolved through the name table and `raw_name` is what the driver said. `probe` streams one JSON line per event to stdout as it happens — `{t_ms, kind, device, index, value}` plus `space` (`"gamepad"` or `"joystick"`, because the two slot spaces are separate) and `name` where the enum has one; a connection or disconnection has no index or value — and ends with one summary line `{events, seconds, per_device, axes_seen, buttons_seen, hats_seen}`, where `per_device` is keyed `"gamepad:0"`, `"joystick:1"`, … , every device is named with its resolved name, and `axes_seen`/`buttons_seen`/`hats_seen` count the *distinct* axes, buttons, and hats that moved. `--log` also records the events as an `input::InputLog` (docs/subsystems/input.md), converting each one into `RawEvent`s at a 60 Hz tick and turning each hat event into four digital signals, one per direction. `--events <file>` sends the event stream to a file the probe opens itself, as UTF-8 bytes with bare newlines, leaving only the summary on stdout (the file gets it too, as its last line): **do not redirect the stream with a shell instead**, because PowerShell's `>` writes UTF-16 with a byte order mark and every text tool downstream then reads the result as binary, which is how the first round of recordings came back. `replay` loads such a log with no device attached, gives every distinct signal in it an action (`joystick_axis_2`, `joystick_button_5`, `joystick_hat_0_8`; `Button` for the digital sources, `Axis` for the analog ones), replays it through an `InputState`, and prints `{file, events, first_tick, last_tick, ticks, actions, button_actions, axis_actions, presses, releases, map, state}`. A log the probe recorded carries no action map, so `replay` stamps it with the hash of the map it just built; a log that does carry one is still refused when the map differs, as `InputLog::replay` requires.

`ffb` and `rumble` are the same tool pointed the other way: output nobody here can feel. `ffb` takes a **raw joystick** slot, opens its haptics device, prints one line of `window::HapticInfo` (`{device, name, constant, spring, damper, friction, sine, axes}`), applies whichever of `--spring`, `--damper`, and `--constant` were named, holds them for `--seconds` (5 by default, 60 at most), stops them, and prints a summary saying what each effect was asked for and whether it ran. With no force named it is a report and nothing else. `rumble` takes a **gamepad** slot and runs its two motors for `--ms`, printing `{device, name, low, high, ms, rumbled}`. Both exit 3 when the slot is empty, and `ffb` also when the device has no haptics and `rumble` when the pad has no motors — which is most pads, so 3 there means "nothing happened", not "something broke". **Opening a wheel stops the driver's own centring spring**, so a wheel goes limp under `ffb` until a force is set and again once it stops; that is the device, not the tool (docs/subsystems/window.md).

SDL needs no window for joystick events, but it does need its own event pump, so the tool creates one hidden, non-Vulkan 64×64 window and drives `poll()` on it; and because SDL drops device events while a process owns windows and none holds keyboard focus, it calls `window::set_background_input(true)` so the terminal it was started from can keep focus while both of the owner's hands are on a wheel. It waits 250 ms at startup for SDL's arrival events, which is what assigns the slots. Exit codes: 0, 1 error, 2 usage, 3 unavailable (no display or no SDL video driver; for `ffb` and `rumble`, also an empty slot or a device with no forces and no motors), which the end-to-end test treats as a skip.

**Reporting a device.** Plug in one device at a time, and for each run exactly these two commands from `build/<preset>/bin/`:
```bash
engine-input devices
engine-input probe --seconds 10 --log <device>.jsonl --events <device>.events.jsonl
```
During the ten seconds, exercise everything the device has, slowly and one thing at a time so the indices are readable in the file: sweep each axis from end to end (a wheel lock to lock, each pedal fully down and back, each stick through both axes), press and release every button once in a predictable order, and push the hat to each of the four directions and back to centre. Send back `<device>.jsonl`, `<device>.events.jsonl`, and the `devices` line. That is enough to name the device's axes and buttons here and to add it to the tests; `engine-input replay <device>.jsonl` reproduces the session with nothing plugged in. With several devices attached at once, `--device <slot>` and `--gamepad`/`--joystick` narrow the stream to one of them. The logs that came back this way are committed under `content/input-logs/` and replayed by `foundation/input`'s corpus test; that directory's README says how to add one.

**Force feedback, next.** Nobody working on the engine has a wheel or a pad to feel these on, so the three force calls are plumbed and tested but unverified on hardware. Two commands answer that, on the rig that recorded `content/input-logs/t300.jsonl` and on the pad that recorded `f710.jsonl`:
```bash
engine-input ffb --device 0 --spring 0.5 --seconds 5
engine-input rumble --device 0 --low 0.5 --high 0.5 --ms 500
```
The first should make the T300's wheel resist being turned away from centre for five seconds and go limp again when it stops; check the printed `HapticInfo` against what the wheel actually did, and whether `spring_ran` was true. The second should buzz the F710 for half a second. Run `engine-input devices` first if anything else is plugged in: `ffb` counts joystick slots and `rumble` counts gamepad slots, and they are different spaces.

**engine-image.**
```
engine-image compare <a.png> <b.png> [--flip <out.png>] [--ppd <n>] [--weights center|none] [--json]
engine-image info <file.png> [--json]
```
The picture comparison [04 §4.8](../plan/04-renderer.md#48-reference-renderer-and-objective-optimization) makes the gate of the optimization loop: propose, build, render the corpus, compare to the baseline, accept if it is faster and the picture did not get worse. `compare` decodes two images (PNG, JPEG, TGA, or BMP, through `image::read_image`) and prints FLIP — the perceptual metric, which is the primary number — with PSNR and SSIM beside it, all from `foundation/image/metrics.h` ([image](image.md), which says what each one is and why). `--ppd` is the viewing density the contrast-sensitivity filter is evaluated at, 67.02 by default, which is the FLIP paper's reference condition rather than any particular monitor; a denser display scores a given difference higher. `--weights center` pools the per-pixel error under a Gaussian attention region instead of evenly, which is §4.8's per-region rule and [§4.6](../plan/04-renderer.md#46-extreme-displays)'s treatment of peripheral vision: the same damage in a corner of a 48:9 frame then counts for about a fourteenth of the same damage in the middle. `--flip <out.png>` writes the per-pixel error as a heat map, which is how to see *where* two frames disagree rather than by how much.

`--json` prints one object on stdout — `{a, b, width, height, psnr, ssim, flip_mean, flip_p95, flip_max, flip_weighted_mean, ppd, weights, flip_image, ms}` — and without it the same numbers as a short readable report. `psnr` is `null` for two identical images, because the value is infinite and a large number would read like "nearly identical"; `flip_image` is `null` when no heat map was asked for; `ms` is the wall time of the metrics themselves, so a corpus run can budget for it (a 3840×2160 pair is 3.0 to 3.2 s in `msvc-release` on the dev box). `info` prints an image's size and channel count from its header alone, without decoding the pixels.

**Exit codes: 0 and 2, and deliberately no 1.** A difference is a measurement, not a failure: `compare` exits 0 whenever it produced numbers, however large they are, and it is the caller — a CI script, an agent's accept-or-reject rule — that decides which threshold means what. Everything that stopped it from measuring exits 2: a bad argument, a file that is not there or is not an image, two images of different sizes, a heat map that could not be written.

engine-image depends on `base`, `containers`, `time`, `io`, and `image` — no GPU, no window, no scene: it is two file reads and some arithmetic, so it runs on a build machine and on the headless GPU runner alike. `tools/dev.ps1 test -Filter engine_image` runs the end-to-end suite, which writes its own PNGs at test time (a flat field, the same field four levels brighter, and a checker with a 16×16 block flattened once in the middle and once in a corner) and checks: thirteen ways to get the arguments wrong and `--help`; an image against itself giving a `null` PSNR, an SSIM of 1, and a FLIP of 0; the four-level pair giving the analytic PSNR 10·log₁₀(255²/16) and a flat FLIP map whose mean is its maximum; `--ppd` reaching the filters (and a flat difference surviving any density, which is the case where it should not matter); `--flip` writing a three-channel PNG the size of the inputs and exiting 2 when the destination cannot be written; `--weights center` separating the middle of the frame from the corner by more than three times while the plain means stay within a tenth of each other, and the weighted mean equalling the mean when no weights are asked for; mismatched sizes and a file that is not an image exiting 2 with a message; and `info` reading the header of a PNG and refusing junk.

**Build.** `engine_app(NAME engine_host OUTPUT engine-host SOURCES ... DEPS ... [E2E_TESTS ...])` in `cmake/EngineModule.cmake` builds an executable into `build/<preset>/bin/`, records it in `modules.json` with layer `apps`, and can build an end-to-end test executable that receives the app's path as `ENGINE_APP_PATH`. The CLI test also receives `ENGINE_HOST_PATH`.

**Depends on.** engine-host: `protocol`, `log`, `io`, `tunables`, `renderer` (the `render.*` methods; see the last section of this page). engine-cli: `json`, `platform` (`Process`, `executable_directory`). engine-view: `renderer`, `window`, `image`, `io`, `gfx`, `math`, `time`, `log`, `platform` — the geometry, asset, and scene-file work it used to do itself now comes through [renderer](renderer.md). engine-content: `geometry`, `assets`, `io`, `json`, `log`, `time`, `math`, `containers`, `jobs` (no GPU, no window: it runs on a build machine). engine-input: `window`, `input`, `json`, `io`, `platform`, `log`, `containers`.

**Testing.** `tools/dev.ps1 test -Filter engine_cli` runs the end-to-end suite: info and methods through a spawned host, error exit codes, and the exit criterion with one process per step (create, apply, objects, undo, redo across processes, add layer, diff, get, validate, journal). `-Filter engine_view` runs engine-view for six frames at 320×200 with a capture and checks the JSON summary and the PNG header, plus the usage exit codes, and writes a two-material cube with an embedded PNG texture as a GLB at test time and renders it through `--mesh` (two primitives, two leaf clusters, both drawn; a missing file and a `.clusters` file that is not one both exit 1; copies of the fixture and the capture stay in the temp directory as `engine_view_mesh_cube.glb` and `engine_view_mesh_last.png`); it records a skip where the app exits 3. Incrementality is per mesh and per output file, not per derived node: a changed source rebuilds its whole container, and the "up to date" question is answered by reading the container's own identity rather than by a dependency graph. ## Streaming pages in the content build

`engine-content build` and `build-all` lay a mesh out in fixed-size streaming pages by default ([geometry](geometry.md), [04 §4.3](../plan/04-renderer.md#43-geometry) step 3): **`--page-bytes <n>`** sets the target, 131072 by default, and **0** writes a container with no page table and leaves the clusters in the builders' order. A manifest entry may set `"page_bytes"` in its `"options"` object; the command line is the default for entries that do not. The flag is part of the derived-data cache key, because laying a mesh out in pages **renumbers its clusters**: two targets are two different containers and "no pages" is a third, so an incremental build never hands back an entry that was paged differently from what was asked for. `engine-view` lays its own cache entries out with the same default, so either program still fills the cache and either finds it.

The renumbering is also why the build pages a mesh *before* it maps clusters to materials: the permutation is applied to the map from cluster to primitive in the same step (`geometry::permute_cluster_array`), and everything downstream sees one numbering. The `build` summary gains `pages`, `page_bytes`, and `page_fill` (mean page bytes over the target); `build-all` prints the same three per entry.

`info` gains a `pages` object — `count`, `bytes_target`, `bytes`, `largest_bytes`, `mean_fill`, `oversized`, `root_pages` (the pages holding a group nothing coarser can replace, which a residency manager never evicts), and `child_page_entries`. `stats` reports all of that plus `valid` (the page table checked against the mesh it came with, with `invalid_reason` when it is not), a `child_pages_histogram` of one `{child_pages, pages}` entry per distinct count — how much of the DAG a page depends on, and so how wide a prefetch is — and a **streaming sweep**: a camera flies from 50 mesh radii to half a radius in 32 steps at 1080p and one pixel of error, and each step reports what the ideal cut needs (`clusters`, `triangles`, `pages_needed`) and what a residency manager under a quarter of the mesh's page bytes actually does (`requested`, `drawn`, `evicted`, `resident`, `resident_bytes`). The table goes to stderr so stdout stays one JSON line; the same numbers are in `pages.streaming.steps_detail`. It is a content metric, not a benchmark — it answers "does the way this mesh is paged make a fly-in cheap?" without a GPU, a window, or a frame loop.

Renumbering a mesh has to be invisible to the renderer, and it is: `engine-view --frames 3 --width 400 --height 300 --orbit 22` on the FlightHelmet gives a **byte-identical PNG** and the same 119 visible pairs from the glTF and from the paged container built from it. The one thing that does change is the *direct* draw, which has no cull pass and draws clusters 0..`leaf_count` on the assumption that the leaves come first; in a paged mesh they come last, so `--no-cull` now turns culling back on with a warning, exactly as it already does for a scene of more than one instance.

The two sample meshes, in `msvc-debug`. The **FlightHelmet** (2,348 clusters, 10 levels) is 25 pages at 91% fill, 2.85 MB of page bytes, one of them pinned, and the whole outer half of the fly-in — 50 radii down to 10, 7 to 38 clusters, 319 to 2,618 triangles — draws out of that one page with nothing requested. Streaming starts at 8.5 radii (2 pages), reaching 5 pages at 5.3, 7 at 3.7, 11 at 2.1 and 17 at half a radius, where the full cut is 960 clusters and 80,422 triangles. Under the 747 KB budget the viewer settles at 6 pages and 687 KB, draws 281 of those 960 clusters and still has 8 pages outstanding, which is what a budget a third of the working set looks like: it lags, it does not crack. **Suzanne** (88 clusters, 7 levels, 113,528 page bytes) is a single page, so its sweep requests nothing at any distance and its cut runs from 3 clusters and 245 triangles at 50 radii to all 42 leaves and 3,936 triangles from 3.7 radii in — and its budget is not honoured, because that one page holds the root and a mesh without its root draws nothing at all.

## The renderer is a library, and both engine-view and engine-host draw with it

Everything that draws moved out of `apps/engine_view/main.cpp` and into [renderer](renderer.md) (layer `systems`): scene loading through the derived-data cache, the GPU-resident scene, the cull and LOD passes, the four rasterizers, the deformed-vertex pool, the acceleration structure chain, the material resolve, the Hi-Z, the GPU timers, and the capture. The reason was not the file's length. It was that **nothing but engine-view could render**, so the protocol had no `capture` and no `benchmark` and the Phase 1 exit criterion could not be met ([10 §10.2](../plan/10-roadmap-risks.md#102-phases)).

**engine-view is the command line over that library.** It keeps the flags and their validation, the window and its events, the surface and the swapchain with its resize and its present, the screenshot of the *presented* image, the shader-reload timer, and the JSON summary. Every flag and every JSON field is unchanged, and so is every picture: the FlightHelmet at `--width 400 --height 300 --frames 6 --orbit 22` through `--raster hw`, `--raster vertex`, `--raster rt --shadows rt`, `--deform wave`, and `--grid-instances 3` produces **byte-identical PNGs** before and after the move (`engine-image compare --json` reports `"psnr":null,"ssim":1,"flip_mean":0` on all five, and the files have the same SHA-256). The one visible change is where a log record comes from: the overrides a device or a scene forces — the mesh-shader fallback, culling forced on, shadows off on a path that cannot trace them — are now logged under the `renderer` category rather than `view`, because both hosts make them in the same function.

**engine-host gained `render.*`**, four methods over the same library, with no window anywhere in the process:

```
render.load      {mesh | scene, settings, grid_instances, ddc, cache, adapter} -> a scene id and its counts
render.capture   {scene, camera | orbit, width, height, channels, out_dir, name} -> file URIs and stats
render.benchmark {scene, width, height, frames, settings, camera | orbit} -> gpu_ms per pass, cpu ms per frame
render.compare   {a, b, weights, ppd, flip_out} -> FLIP, PSNR, SSIM
```

`render.load` is the expensive call — it imports and clusters a glTF, or reads the container the cache already holds — and the host keeps the result, so a capture and a benchmark of the same scene pay it once. `settings` on `render.benchmark` may differ from the ones the scene was loaded with; the host then rebuilds the GPU scene and the renderer from the loaded `SceneData` rather than re-importing the mesh.

```bash
engine-cli render.load '{"mesh":"content/samples/Suzanne/Suzanne.gltf","settings":{"raster":"hw"}}'
engine-cli render.capture '{"scene":"scene1","orbit":{"distance":22},"width":800,"height":600,
                            "channels":["color","ids","depth","normals"],"out_dir":"out"}'
engine-cli render.benchmark '{"scene":"scene1","width":1920,"height":1080,"frames":120}'
engine-cli render.compare '{"a":"out/capture.png","b":"out/baseline.png","weights":"center"}'
```

Because `engine-cli` spawns a host per invocation, a scene id lives only as long as that process: a sequence like the one above is one `engine-host --stdio` session, or one `engine-cli` call per line with a `render.load` in front of each. The scenes are released when the process exits.

`render.capture`'s `channels` are `color` (RGBA8 PNG), `ids` (the entity-ID buffer: three little-endian `u32` per pixel — instance, cluster, triangle — in a `.ids.bin` with a `.ids.json` header describing it), `depth` (an 8-bit gray PNG normalized over the frame's covered range, whose exact bounds are `depth_min`/`depth_max` in the result), and `normals` (an RGB8 PNG of `n * 0.5 + 0.5`, which costs a second frame because only the resolve knows the normal). [renderer](renderer.md) has the encoding in full and says why the id buffer resolves the visibility id into a pair rather than reporting the id. `--raster direct` writes no visibility buffer, so `ids` and `depth` are an error there rather than a buffer of nothing.

**A capture's `gpu_ms` is zero, and that is not a bug.** A timestamp pool is read when its frame slot comes around again, so with two frames in flight the first two frames of any run have no timings yet — and a capture is one frame, or two with `normals`. `stats.gpu_ms.frames` says how many frames the numbers came from, and it is 0 there. `render.benchmark` is the call that measures; `render.capture` reports the visible-pair counts, which do come back, and the picture.

The end-to-end suite for all four is `apps/engine_cli/tests/render_tests.cpp` (`tools/dev.ps1 test -Filter engine_cli`). It drives one `engine-host --stdio` process through the whole round trip — because a scene id lives in the host and the CLI spawns one host per invocation — and renders the **procedural heightfield**, so the case needs no fixture, no sample asset, and no cache entry. It checks the scene counts, all four channels landing on disk with the id file exactly `width * height * 3 * 4` bytes and the header describing that, a benchmark at a different size reusing the loaded mesh and reporting a GPU millisecond field per pass, a capture compared against itself giving a null PSNR and an SSIM of 1, and the four error codes a client has to tell apart. `render.compare` is driven through engine-cli as well, since it is the one method that never opens a device and so runs on a machine without one.

## What else the machine was doing, in both hosts' numbers

A frame time from this project's development box is not a frame time from an idle machine: it renders beside GPU jobs that hold most of the card and beside several agent builds. So **engine-view's JSON summary and `render.benchmark`'s result both carry the load they were taken under**, in the same shape and against the same thresholds the CPU benchmark harness uses ([bench](bench.md#measuring-on-a-shared-machine)).

Two blocks, both **added** to the existing fields — nothing was renamed and nothing moved out, because tests and scripts read this line:

```json
"gpu_memory":{"budget_mib":31614,"used_mib":297,"device_local_total_mib":32404},
"machine_state":{"start":{"cpu_total_pct":9.3,"cpu_own_pct":0.0,"cpu_others_pct":9.3,
                          "gpu_util_pct":0.0,"gpu_memory_used_mib":17117,
                          "gpu_memory_total_mib":32607,"session_locked":false},
                 "end":{...}}
```

`gpu_memory` is the renderer's ([renderer](renderer.md)), read from the Vulkan device around the run. `machine_state` is sampled **outside** the timed region — before the first frame and after the last — because the sampler sleeps for a quarter of a second to get a CPU percentage and spawns `nvidia-smi` for the GPU reading, and neither belongs between two timed frames. Every field is `null` where the platform could not answer, so "quiet" and "not measured" are different answers; no process names are ever reported.

**Read the two together.** In the line above the Vulkan budget says 31,614 MiB of 32,404 MiB were available to this process while `nvidia-smi` says 17,117 MiB of the card were in use: the budget does not fully see a CUDA tenant, so `device_local_total_mib - budget_mib` is a lower bound on what others hold and `gpu_memory_used_mib` in `machine_state` is the number that answers "is somebody else on this GPU".

When other processes used more than 10% of the CPU or the GPU was more than 20% busy at either end of the run, both hosts write **one WARNING line to stderr** — the same sentence `foundation/bench` prints, for the same reason: stdout is the summary and the protocol, and a caveat that corrupted either would be worse than no caveat. It does not mean the numbers are wrong; it means they are upper bounds, and a write-up that quotes them owes its reader the "Machine state" line ([docs/experiments/README.md](../experiments/README.md)).

`render.benchmark`'s result and `RenderStats` are at `@version(2)` for this: `stats.gpu_memory` and `machine_state` are `@since(2)` with defaults, so an older client reading the result sees exactly the fields it saw before.

**Multi-view over the protocol.** `RenderSettings` is at `@version(2)`: `views` (`single`, `surround3`, `panini`), `side_yaw_deg`, `panini_d` and `peripheral_lod` are `@since(2)` with the single-view defaults, so both hosts spell the layout the same way and parse it with the same function ([settings.h](renderer.md#public-api)). `RenderStats` is at `@version(3)` and gains `views` — one `RenderViewStats` per view with its rectangle, its source extent, its tier, its visible pairs and its milliseconds by pass — beside `view_layout` and `oversample`. Changing the layout between calls rebuilds the GPU scene and the renderer the way any other settings change does, because the per-frame working set is sized by the view count. This is the path E9 measured through, since it renders offscreen at 11520×2160 on a machine whose window would not be that big.

**Where there is no GPU**, every `render.*` method fails with error code **1007 `RenderUnavailable`** and a message naming the adapter and what it lacks — no Vulkan loader or driver, no 64-bit buffer atomics, or no cluster acceleration structures for `"raster":"rt"`. It is a code of its own so a client can tell "this machine cannot render" from "you asked for something wrong" ([protocol](protocol.md)); the end-to-end test skips on it exactly as engine-view's suite skips on exit 3, which is what lets one suite run on the hosted CI runners and on the GPU machines alike.
