# assets (domain)

**Purpose.** Source-asset import (docs/plan/07-content-pipeline.md §7.2). glTF 2.0 is the interchange format the plan names for meshes and PBR materials, because every DCC tool, generator, and agent already speaks it. This module turns one glTF file into one plain `MeshData` — positions, normals, UVs, indices, primitive ranges, materials, and undecoded image references — which is exactly the input `geometry::build_clusters` and `geometry::build_cluster_lod` take. It is the front door of the content build; nothing in it touches the GPU.

**What one file becomes.** The default scene (`scene`, or scene 0 when there is none) is traversed recursively. Every primitive of every node's mesh is appended to a single vertex and index space with the node's world transform baked into the positions and the inverse transpose baked into the normals, which are renormalized per vertex because that matrix is not orthonormal under non-uniform scale. Primitives keep their identity as a `Primitive` range into `indices` plus a material index, so a merged mesh can still be drawn or clustered per material. Two primitives that share one POSITION accessor get one vertex block each: the merge is by range, not by deduplication, and the cluster builder's own vertex reuse makes that cheap. `u8`, `u16`, and `u32` index accessors are all widened to `u32`; a primitive with no index accessor gets `0..count-1`. Only triangle topology is accepted — strips, fans, lines, and points fail with an error rather than being converted, because the whole renderer is a triangle cluster pipeline.

**Attributes.** `normals` and `uvs` are either empty or the same length as `positions`, which is what `geometry::AttributeSource` requires; `attribute_source(mesh)` builds one. Empty means no primitive in the file carried that attribute, and the cluster builders then compute smooth normals and leave UVs at zero. A primitive that lacks an attribute other primitives have contributes zeros rather than shortening the stream. `TEXCOORD_1`, `TANGENT` and `COLOR_0` follow the same rule into `uvs1`, `tangents` and `colors` ("What G2 reads" below). **Every** mesh also carries `vertex_ids`, one canonical id per vertex, authored or derived ("Canonical vertex ids" below) — the one stream that is never empty, because a mesh with no authored ids is named by a rule rather than left nameless.

**Materials and images.** `Material` is the whole metallic-roughness core of glTF 2.0: the base color factor, metallic and roughness, the emissive factor, `normal_scale` from `normalTexture.scale`, `alpha_mode` (`k_alpha_opaque`, `k_alpha_mask`, `k_alpha_blend`) with `alpha_cutoff`, `double_sided`, and five image slots — base color, metallic-roughness (glTF packs roughness in G and metallic in B of one texture), normal, occlusion, and emissive — each an index into `MeshData::images` or −1. **A slot's image here reads `TEXCOORD_0`**: a texture bound to the second set arrives as −1 here and in `uv1_images` instead ("What G2 reads" below), one bound to any other set nowhere, and a material with no normal texture keeps `normal_scale` at 1 instead of the zero cgltf leaves in an unparsed texture view. Images are *not* decoded here. `ImageRef` carries the encoded bytes for GLB buffer views and base64 data URIs and the (percent-decoded) URI for external files, with the media type when the file states one; `foundation/image` and the texture pipeline own decoding. This keeps the import step free of codecs and lets the content build decide what to decode and when.

**Samplers and texture transforms.** Every slot also records *how* it reads its image, in `Material::sampling[slot]` (indexed by `geometry::k_slot_*`, types in `geometry/material_sampling.h`): the glTF sampler of the texture it names — `wrapS` and `wrapT` as repeat, mirrored repeat or clamp to edge, and the filters — and the reference's `KHR_texture_transform` (offset, rotation in radians, scale). glTF puts the sampler on the texture and the transform on the reference, so one image can tile three times as a base colour and be clamped as an occlusion map in one material, and the record keeps both per slot rather than per image. A texture with no sampler, and a filter the file leaves undefined, get the glTF defaults: repeat, linear. `minFilter` names two decisions — `NEAREST` and `NEAREST_MIPMAP_*` filter within a level by nearest, `*_MIPMAP_NEAREST` pick one level rather than blending two — and `NEAREST` or `LINEAR` alone, which ask for no mip chain, read as a linear blend, because the content build always makes the chain ([geometry](geometry.md#how-a-material-samples-its-images)). A transform that names its own `texCoord` overrides the reference's, so one that moves a texture to `TEXCOORD_1` is refused (−1) exactly as a reference's own `texCoord` of 1 is. `occlusion_strength` is `occlusionTexture.strength` (1 where there is no map). The container carries all of it (section 33) and the renderer turns it into bindless samplers and the material table's UV transform ([texture](texture.md#samplers-and-texture-transforms)). Why it is read now: tileable textures are how the ruined-wall kits get their surface detail ([07 §7.7](../plan/07-content-pipeline.md#77-ml-asset-generation-novelty-content)), and until it was, a brick texture authored to repeat eight times drew once.

**`KHR_materials_diffuse_transmission`** on a double-sided material is read since R164 as `Material::transmission`, `t / (1 - t)` at most 1, with the base colour factor multiplied by `1 - t` since R164-3 so the two split the base colour as the extension does instead of adding to it, its colour and textures not read ([renderer](renderer.md#foliage-lit-from-both-sides)); `source_mesh_hash` mixes a tag into the key of a file that states it, as it does for a BLEND read as MASK, so an entry built before the reading is never read again and every other file keeps its key. What the rest of the format adds — tangents, a second UV set, vertex colours, more than four influences, the other material extensions, lights and cameras — is read since G2 ("What G2 reads" below).

**Not yet.** Draco and meshopt-compressed buffer views: the tree vendors no decoder for either, so a Draco-compressed primitive is refused by name before the buffers are read (its accessors have no buffer view, which the unpacker would otherwise have read as zeros: a heap of vertices at the origin, not an error), and so is a meshopt-compressed view whose own buffer is the extension's empty fallback (one with a real fallback buffer reads from it). Splitting the merged mesh back into per-node or per-material meshes. A file with no scene is an error, not an implicit "use every mesh". Skins and animations *are* read — see "Skins and animations" below — but never evaluated here.

## What G2 reads

Roadmap G2, 2026-11-17: the part of glTF 2.0 an imported scene lost before, ordered by what it lost. **The engine stays general purpose**: a consumer that uses none of the solvers and only imported assets gets all of it, every piece is a property any asset may declare, and **a file that declares none of it imports, welds and builds exactly the bytes it did** — the new streams are empty, the new container sections are not written, and the determinism tests' pinned hashes do not move (`gltf G2: a file without the new attributes builds the container it built before` holds the same at the module's level). A file that declares any of it gets a tag in `source_mesh_hash` ("G2IMPOR1"), so an entry built before the reading is rebuilt and `k_cluster_cache_version` does not move. **The tag is the cache key's and never a scene's pin**: a scene's `hash` names the file's bytes (`source_bytes_hash`, "Source hash" below), and when the scene loader compared it with the tagged key the desert overlook refused its Lantern, whose bytes had not moved (mended on G2's stack, 2026-11-18; `gltf: the bytes' hash is the bytes and buffers, whatever the key folds in`).

**Tangents, a second UV set and vertex colours.** `TANGENT`, `TEXCOORD_1` and `COLOR_0` arrive as `MeshData::tangents` (`Vec4`), `uvs1` and `colors` (linear `Vec4`; a VEC3 colour gets alpha 1; float and normalized forms both), each empty unless some primitive carried it and then parallel to the positions, a primitive without it contributing the "none" value (no tangent: w = 0; UV1 zero; white). A tangent is a direction in the surface, so a rigid primitive's goes through the node transform's **linear part** — not the inverse transpose the normal takes — and is renormalized; its `w` says which way the bitangent runs (`cross(N, T) * w`), and a node with a negative determinant turns the normal's side of that product over, so **`w` flips under a mirroring node**. A tangent of no length imports as none. The weld keys on all three (`geometry::WeldExtraStreams`), so the two sides of a mirrored UV seam — one position, one UV, opposite handedness — stay two vertices. The cluster builders carry them through `vertex_source` into `ClusterMesh::extra`, one 12-byte `geometry::VertexExtra` a cluster vertex (the tangent octahedral in two snorm16 with the handedness in the lowest bit of the first, the second UV in two halves, the colour in four unorm8), and the container writes them as section 49 ([geometry](geometry.md#what-an-imported-gltf-says-beyond-the-core)). **Why the asset's tangent matters**: the resolve derives a frame per triangle from its positions and UVs (`tangent_frame`, `material.slang`), which keeps a mirrored island's handedness but is flat across each triangle; a normal map baked in MikkTSpace expects the frame interpolated across the vertices, and on a low-polygon asset with a baked map the two differ by the shear between neighbouring triangles' parameterizations — a faceted, seamy lighting where the bake meant a smooth one.

**Measured on the Khronos samples** (`gltf G2: the Khronos samples' tangents against the per-triangle frame`, 2026-11-17, a test that reads `content/samples` when the checkout has them and skips each one it lacks; a corner is one triangle's view of a vertex with a tangent; "apart" is more than 10° between the two tangents projected into the surface; "opposite" is the asset's bitangent, `cross(N, T) * w` as glTF defines it, pointing against the resolve's, which is `dP/dv`):

| Sample | Corners | Tangents apart | Bitangent opposite |
|---|---|---|---|
| Lantern | 16,182 | 1,894 (11.7 %) | 16,173 (99.9 %) |
| BoomBox | 18,108 | 929 (5.1 %) | 18,103 (99.97 %) |
| Corset | 54,972 | 17,500 (31.8 %) | 54,792 (99.7 %) |
| Avocado | 2,046 | 54 (2.6 %) | 2,046 (100 %) |
| SciFiHelmet | 70,074 | 0 | 54,062 (77 %) |
| FlightHelmet | 284,166 | 23,453 (8.3 %) | 283,469 (99.8 %) |
| Suzanne | 11,808 | 0 | 0 |

Two findings. **The direction differs on 3 to 32 % of corners** of the baked assets, which is the faceting above, largest on the Corset's dense parameterization. **The handedness disagrees on nearly every corner of five files**: glTF's UV origin is the image's top-left and its normal maps are +Y up, so for an unmirrored island the glTF bitangent is `−dP/dv`, while the resolve's derived frame takes `+dP/dv` — which reads such a map's green channel the other way up. Suzanne (whose tangents agree everywhere) and SciFiHelmet (77 %) show that files differ in what they wrote, which is the case for carrying the asset's own frame rather than guessing one convention. Whether the resolve's sign is a defect for every glTF map, or matches the convention the engine's own material sets were made in, is the first thing the renderer's leg checks, with a picture of a sample under a low light before and after.

**The renderer does not read section 49 yet**: the GPU half (a scene-wide stream beside the attributes, the resolve interpolating the asset's frame where a vertex has one and deriving it where none does, the second UV set for a slot that names it, the colour into the base colour) is the next leg of the row, and until it lands an imported scene draws exactly what it drew.

**Slots on the second UV set.** A texture reference whose `texCoord` (or whose `KHR_texture_transform`'s `texCoord`, which overrides it) is 1 — an occlusion or light map is the common case — is no longer refused: its image goes to `Material::uv1_images[slot]` and its sampling to `sampling[slot]` as for the first set, while the slot's own image stays −1. The container writes the five as section 50 (`geometry::ClusterFileUv1Slots`, one-based like the material record's optional slots), so **a reader that knows one UV set draws the material without the map rather than with the map on the wrong UVs**. A third set is still refused. `--atlas repack` repacks the first set only: it keeps a second-set slot's image (renumbered with the rest), copies the second UV and the colour into every vertex copy it makes, and drops the imported tangents, which described the first set it replaced.

**Material extensions.** Each is either mapped to what the BSDF has or read, recorded and not drawn, and `Material::extensions` says which a material stated (`k_ext_*`). `KHR_materials_emissive_strength` **is drawn**: it multiplies the emissive factor, which the container stores as floats and the resolve draws unclamped, so an HDR emitter draws at its strength. `KHR_materials_ior`, `_specular`, `_clearcoat`, `_transmission`, `_volume` and `_sheen` are read into `Material` (`ior`, `specular`, `clearcoat`, `clearcoat_roughness`, `transmission_factor`, `thickness`) and **not drawn**, because the BSDF (`brdf.slang`) has nothing to map them onto: one dielectric F0 of 0.04, which is an IOR of 1.5 — the extension's own default, so the common case is already right — no coat lobe, no sheen lobe, and a visibility buffer with no sorted transmission or volume. Folding one into what is there (a clearcoat into roughness, a transmission into alpha) would change the picture in a way the source did not ask for. The import logs one line a file naming those it read and left out ("glTF material extensions read and not drawn"). The record is import-time data; nothing of it reaches the container beyond the emissive factor.

**Lights and cameras.** A node of the default scene that carries a `KHR_lights_punctual` light or a glTF camera puts it in `MeshData::lights` or `cameras` at the node's world placement, in the flattened mesh's space like the perches: a light's position, its direction (the node's −z, normalized: a node's scale says nothing about where a light points), its type, linear colour, intensity in the extension's own units (candela for a point or spot light, lux for a directional one), range and cone angles; a camera's position, its rotation as a unit quaternion (the scale-free part of the node's matrix, a mirror on x as `node_trs` puts it), and its projection (y field of view and aspect, or x and y magnification; a far plane of 0 is infinite). The container writes them as sections 51 and 52 (`geometry::ClusterFileLight`, `ClusterFileCamera`, 80 bytes each, a light's name cut at 23 bytes and a camera's at 31). **Nothing places them in a scene yet**: the scene reader turning a mesh's lights into the frame's lights and its cameras into named viewpoints is a renderer row of its own.

**The influences.** A vertex with `JOINTS_1` and `WEIGHTS_1` beside the first set has up to eight influences; the format's binding holds four ("Skins and animations" below). The importer adds a joint named twice, keeps the four heaviest (a tie to the lower joint, so the choice is a function of the vertex alone), and `geometry::make_skin_binding` renormalizes them to 255. **What that costs is measured, not hidden**: `MeshData::influences_over_four` counts the vertices that had more than four non-zero weights and `influence_dropped_max` and `_sum` the share of weight dropped, which the import logs; skinning with the four kept moves a vertex from where all eight would put it by at most that share times the spread of the dropped joints' displacements. On the test's vertex (eight weights, a quarter dropped, a pose that moves joint k by k along x) the four kept put it 0.97 from where eight would, inside the bound of 1.75. Carrying eight would double the binding and every deform pass's reads for the vertices that rarely need it; a file whose drop the log shows to matter is the case for doing it.

**Testing.** `import_extras_tests.cpp` (`tools/dev.ps1 test -Filter assets`), every file written in the test as a data URI: a quad under a node that mirrors x carries tangents (one of no length), a second UV set and colours on one primitive and none on a second, and comes back with the tangents through the linear part and their handedness turned over, the "none" values on the second primitive, one `VertexExtra` per cluster vertex equal to its source vertex's, and the same through a written and read container; the same file without the three attributes imports with empty streams, and the first with its streams taken away builds byte-identical container bytes; a mirrored seam's two sides stay two vertices in the weld (8 weld to 5); the tangent and colour packing; a spot light on a node turned a quarter about x points up, a camera on a scaled node keeps the identity rotation, and both round-trip through sections 51 and 52; a material stating every extension folds the emissive strength (4) into the factor and records the rest; eight influences keep the heaviest four with the tie to the lower joint, a dropped share of 0.25, and the error against eight inside its bound; and a Draco-compressed primitive is refused with a sentence that names Draco. `sampler_tests.cpp`'s emissive map on `TEXCOORD_1`, refused before, now arrives in `uv1_images` with its sampler and round-trips through section 50.

**Source hash.** `source_mesh_hash(path, out, error)` is the identity of a source mesh for a content-addressed cache of what is built from it (docs/plan/07-content-pipeline.md §7.3): the file's own bytes through `core/hash`'s `hash_bytes`, mixed with the bytes of every external buffer a `.gltf` names in `buffers[].uri`. A `.glb` carries its buffer inside and a data URI is already part of the text, so neither adds anything; an external buffer that cannot be read contributes an empty one rather than failing, since the load that follows reports it properly and the hash has changed with the glTF that names it anyway. **External** images are deliberately not hashed: a container stores their paths and the renderer reads those files every time, so a repainted texture shows up without a rebuild and would only cost one if the key covered it. An image the file **embeds** needs no special case and gets none — it is part of the file's own bytes, so the hash already covers it, which is what makes the cache key sound now that the container carries those bytes ([geometry](geometry.md), "Embedded images"): change the texture inside a GLB and the entry misses, as it must. It parses but does not load buffers, so it costs one read of the text and one of each `.bin`. `geometry::cluster_cache_key` is what turns it into a cache entry's name. **Two values come out of that one read, and they answer different questions.** The key folds a tag in for every importer change that reads some files differently (BLEND read as MASK, a two-sided transmission, G2's streams), so an entry built before is rebuilt while every other file keeps its key; the derived data's name and a container's recorded source identity use it, and so `engine-content build-all` rebuilds such an entry. **The bytes' hash** is the same value before any tag (`source_bytes_hash(path, out, error)`, or both at once from `source_mesh_hash(path, key, bytes, error)`), and it is what a scene pins: a pin says which file, and a file whose bytes did not move must still match it after an importer change.

**Public API.** `domain/assets/gltf.h`: `k_canonical_id_attribute`, `Material` (with `occlusion_strength` and `sampling`), `k_alpha_opaque`, `k_alpha_mask`, `k_alpha_blend`, `ImageRef`, `Primitive`, `Node`, `Skin`, `AnimationSampler`, `AnimationChannel`, `Animation`, `k_interp_linear`, `k_interp_step`, `k_interp_cubic`, `k_path_translation`, `k_path_rotation`, `k_path_scale`, `MeshData` (with `vertex_ids` and `vertex_id_source`; since G2 `tangents`, `uvs1`, `colors`, `lights`, `cameras` and the influence counts), `k_ext_*` and `k_ext_not_drawn`, `load_gltf(path, out, error)`, `load_gltf_memory(bytes, base_dir, out, error)`, `source_mesh_hash(path, out, error)` (and `(path, key, bytes, error)`), `source_bytes_hash(path, out, error)`, `attribute_source(mesh)`, `repair_zero_area_triangles(mesh, report, error)`, `repair_uv_degenerate_triangles(mesh, report, error)`, `weld_vertices(mesh)`, `cluster_file_material(material)` and `write_import_sections(mesh, data)` (the one conversion both builders of a container call, G2). `domain/assets/mesh_generator.h` ([Generated meshes](#generated-meshes)): `MeshGeneratorInputs` (with `hosts`), `GeneratorHostMesh`, `MeshGeneratorHosts`, `host_mesh_of`, `generated_source_hash`, `generated_mesh_build_key`, `MeshGeneratorDesc` (whose `build` takes the inputs, and whose optional `source_hash_with` takes them too), `mesh_generator_of`, `MeshGeneratorRegistry` (`global`, `add`, `find`, `names`, `unknown`), `MeshGeneratorRegistrar`. Failures return false and fill `error` with a sentence naming the cause; `out` is left empty. There are no exceptions and no logging: a loader reports to its caller.

**Depends on.** `base`, `containers`, `math`, `hash`, `io`, `geometry`, `materials` (the pack a generator's inputs carry, and its key); cgltf v1.15 (MIT, third_party/LICENSES.md), whose implementation is compiled once in `src/gltf.cpp` and whose file reads are routed through `io::read_file` so the module has one way to touch the disk.

**Testing.** `tools/dev.ps1 test -Filter assets`: the fixtures are generated at test time in a temporary directory rather than committed, because a binary in the tree is something no one can review. A unit cube (24 vertices, 36 `u16` indices, per-face normals and UVs, two primitives with two materials, under a child node with a translation and a quarter turn) is written as a `.gltf` plus a `.bin`, as a `.gltf` with a base64 buffer, and as a `.glb` built byte by byte (12-byte header, JSON chunk, BIN chunk), and all three must produce the same mesh: 48 vertices in two blocks, the expected rotated and translated positions, unit-length normals that rotated with the node, UVs inside [0, 1], the materials' factors and all five image slots (one image in two roles keeping one slot, as the usual ORM packing does), the emissive factor, the normal scale, the alpha mode and cutoff, double-sidedness, a texture bound to `TEXCOORD_1` refused as −1, an embedded data-URI image arriving as bytes with its media type, and external images arriving as percent-decoded URIs. The loaded mesh is then fed to `geometry::build_clusters` with its `AttributeSource`. Negative tests: a missing file, corrupt JSON, a missing external buffer, a triangle-strip primitive, and empty input all fail with a non-empty error and an empty mesh. `source_mesh_hash` is pinned against the same fixtures: it is stable across calls, moves when the `.bin` changes although the glTF text does not, moves when the text changes although the buffer does not, differs between the `.gltf` and the `.glb` forms, survives a buffer that is not there, and fails with an untouched output on a missing file and on one that is not a glTF. `sampler_tests.cpp` writes a quad whose three materials use a repeating, a mirrored and a clamped sampler with nearest and linear filters, a transform with every field set, an occlusion strength, and a transform that moves its texture to `TEXCOORD_1`; every slot comes back with the right wrap, filters and transform, the refused one at −1 and the defaults, and the same materials go through a `.clusters` container and back unchanged — and through one written without section 33, which reads every slot at the glTF defaults. The size table pins `Primitive` exactly and `Material` around its `std::string`.

**A BLEND material whose alpha is a picture is read as MASK, and the import says what it did** (T139, [the bought foliage](../experiments/static-asset-world.md#bought-foliage)). The engine draws into a visibility buffer and has no sorted transparency, so `k_alpha_blend` reached the renderer as opaque, and a bought plant whose leaves say `BLEND` (five of the twelve Poly Haven plants fetched) stood as solid cards without a word. A `BLEND` material with a base colour image now imports as `k_alpha_mask` at glTF's default cutoff, 0.5 (a `BLEND` material's own `alphaCutoff` means nothing in glTF): its alpha is a shape — leaves, a fence, a decal — and the test draws the shape, its opacity micromaps, shadow proxy and crown included. One whose alpha is the factor alone (a pane of glass) stays `k_alpha_blend` and is drawn opaque as before, because a mask of one uniform alpha would draw all of it or none. `load_gltf` logs one line a file for each (category `assets`, "glTF BLEND materials: …", with `read_as_mask` and `drawn_opaque`), and one for **a default scene of several roots carrying meshes** ("… several mesh roots imported as one mesh", with `roots`): a bought plant file's three or four variants side by side flatten into one mesh, which a scene `Mesh` places whole. **The cache follows the reading without a version bump**: `source_mesh_hash` combines a fixed salt into the key of a file that has such a material, so a container cooked from the old reading is rebuilt and every other file keeps its key and its derived data, which moving `k_cluster_cache_version` would have thrown away. The test: `gltf: a BLEND material with a base colour image is read as MASK`; the cube fixture's factor-only `BLEND` material still imports as `k_alpha_blend`.

**Performance notes.** Import is a content-build step, not a frame-loop one, so it favors clarity: one scratch buffer per accessor reused across primitives, `reserve` before every append, and no attempt to stream. The one number worth watching is that the merged vertex space is capped at `u32`, which the loader checks rather than wrapping.

**The same mesh from every toolchain.** The import's arithmetic — cgltf's TRS-to-matrix composition, the node transforms, the inverse transpose and renormalization of the normals, the transformed morph deltas — ends up in every container, and a container has to be the same bytes whichever compiler built the tool ([geometry](geometry.md#the-same-bytes-from-every-toolchain)). It is, because the tree is compiled without floating-point contraction ([ADR-0035](../adr/0035-no-floating-point-contraction.md)), and this module is where turning it off only for the content build's own sources was seen to fail: the transforms go through `core/math`'s header-only functions, and in a debug Clang build `engine-content` called `main.cpp`'s fused copy of `dot(Vec3, Vec3)` rather than this module's, which put one normal of the Lantern and five of the FlightHelmet a snorm16 step away from MSVC's. The end-to-end determinism test puts a rotated, non-uniformly scaled and translated node over normals that are not axis-aligned for exactly this path ([apps](apps.md)). The one C library call on that path is cgltf's `atof` for the JSON's numbers (a node's TRS, a material's factors), parsed to the nearest double and narrowed to a float; the UCRT and glibc both round decimal input correctly, and the test's `0.6` and `0.8` come out the same on both.

## Generated meshes

`MeshGeneratorHosts` also provides an optional `read_image(context, path, bytes, error)` callback
for generators that bake material images into derived geometry textures (flora G87). It returns
encoded image bytes; the generator decodes them and includes the bytes it consumes in
`source_hash_with`. The content-build host resolves relative paths against the generator recipe.
Missing requested images are errors, not silently cached colour fallbacks. Beside it,
`hash_image(context, path, hash, error)` answers `hash_bytes` over those same bytes without them where
the host already knows it — a load's table of its images, a material pack's index (roadmap W75;
[content_build](content_build.md#one-hash-per-image-and-a-packs-from-its-manifest)) — and a generator
that only hashes an image (flora's `source_hash_with`) asks it first; the two must agree, so a source
hash is the same number whichever answered.

`domain/assets/mesh_generator.h` is the registry a scene reader finds a **generated mesh's** builder in: a file named `<anything>.<generator>.json` — `content/flora/date-palm.flora.json` — is parameters that generator's capability turns into a mesh, and a scene's mesh table names one as it names a glTF ([renderer](renderer.md), "The scene file"). The renderer may not link a capability (ADR-0027), so a capability registers a constant-initialized `MeshGeneratorDesc` — its name, the source hash of a file's bytes (over what the file says, canonicalized, and the generator's version), and the build of the whole container under given LOD options and page target — with a `MeshGeneratorRegistrar` from its own whole-archive source, and a host links the capability; the reader finds the descriptor by `mesh_generator_of(path)`, the second extension before `.json`. It is the scene-generator registry's pattern ([scene_gen](scene_gen.md), ADR-0046) one level down — `scene_gen` makes instances of meshes, this makes a mesh — and it lives here because this module is every other source of a mesh. **One build, two hosts**: `build` makes the whole container, so engine-content (which links the capability and calls it) and the renderer (which finds it here) write the same bytes under the same key. A build without the generator refuses such a path with `unknown(path, name)`, a sentence naming the generator, its capability switch (`ENGINE_WITH_<NAME>`) and the generators it has — never by reading the file as a glTF. The flora capability's "flora" is the first ([flora](flora.md#in-a-scene)) and the rocks capability's "rock" the second ([rocks](rocks.md#the-build)). Its switch is `ENGINE_WITH_ROCKS`, and the sentence takes `ENGINE_WITH_<NAME>` from the generator's name, so it says `ENGINE_WITH_ROCK` for a `.rock.json` in a build without the capability: a wart, to fix by letting the sentence name the switch from a table rather than derive it. `content_build` reaches this registry too, so `engine-content build` and `build-all` take a generated mesh ([content_build](content_build.md)).

**The host seam** (2026-10-21, roadmap G76, G78; [cover](cover.md#why-this-shape)): a generator whose file names **another mesh** — a vine's or a cover's host — reaches it through `MeshGeneratorInputs::hosts`, an `assets::MeshGeneratorHosts` of a context and two hooks the host app provides: `identify` (the host's source hash, cheaply) and `load` (its triangles as an `assets::GeneratorHostMesh`: positions, three indices a triangle, each triangle's roughness and whether a climber may hold it, the identity). `assets::host_mesh_of` makes one from a container's finest level. Such a generator sets `MeshGeneratorDesc::source_hash_with`, whose hash covers the host's identity, and every host app calls `assets::generated_source_hash`, which takes it where it is set; the plain `source_hash` refuses, since a key that cannot see the host would serve a stale companion. The hooks are implemented once, in content_build (`GeneratorHosts`, `generator_hosts.h`), which engine-content and the renderer's scene reader both use.

**What a host hands a generator besides the bytes** is `MeshGeneratorInputs`: today the **material pack** a recipe that names no set for a part falls back to ([materials](materials.md)), which the host finds and reads, so a generator stays a function of what it is given. The pack changes what the container holds (its images), so it is in the key, and every host keys a generated mesh by one function, `generated_mesh_build_key(source_hash, inputs, lod, page_bytes)`: `cluster_cache_key` with no weld, combined with `materials::pack_key` when the pack has roles — so a build with no pack keys exactly as before the inputs existed, and the source hash stays the file's alone (a scene's `expected_hash` is over what the file says).

## Perches

**An imported asset says where a small animal may stand** (roadmap A43; [apps](apps.md#what-a-module-can-ask-the-world), "Supports"). The import reads a **perch** from every node of the default scene whose name begins with `perch` (`perch`, `perch.001`, `perch_branch`), or whose `extras` has a `perch` member — an empty in Blender with a custom property `perch` exports as `"extras": {"perch": {...}}` — into `MeshData::perches` (`geometry::ClusterFilePerch`): the node's world translation, its world +y normalized for `up`, and `extras.perch.size_m` for the foot it holds (`k_default_perch_size_m`, 5 cm, without one: a songbird's to a crow's branch). In the flattened mesh's space, like the positions, so a fit or an instance scale moves it with the mesh. A node with a mesh may be a perch too; the perch is its origin. **Why a node and not a material or a vertex attribute**: every DCC tool exports an empty with a name and custom properties, the convention costs an author nothing to learn, and a perch is a point and a direction, which is what a node is. Both builders of a cluster container — `engine-content build` and the renderer's glTF path — write them into section 43 ([geometry](geometry.md#perches)); a file with none imports and builds the bytes it always did.

## Skins and animations

A character is a mesh, a skeleton, and a set of clips, and glTF carries all three. The importer reads them without evaluating anything: `domain/anim` turns what comes out into a `Skeleton`, a `Pose`, and a `Clip`, and the deform pass turns the result into vertices ([04 §4.3](../plan/04-renderer.md#43-geometry), [05 §5.11](../plan/05-simulation.md#511-integration-notes)).

**A skinned primitive stays in bind space.** This is the one place a skinned import is not the rigid one plus extra arrays, and it has to be: glTF places a skinned mesh entirely through its joints, and the spec says the mesh node's own transform is *not* applied. Baking it into the positions — which is what the flattening does for every rigid primitive — would place the mesh twice, once here and once through the joints' model matrices, and the error would be invisible on a rig whose mesh node happens to sit at the origin and obvious on one that does not. So a primitive whose node has a skin keeps its positions and normals exactly as the accessor holds them, and `Primitive::skin` says which primitives those are. The transform that was *not* applied is recorded on `Skin::node_transform` by the first node that instances the skin, because it is otherwise the only thing about a skinned mesh this import would lose, and a tool that wants to plant a character where its author put it needs it.

**The hierarchy.** `MeshData::nodes` is the file's node list with each node's own transform as a `Transform3` and its parent's index — **reordered so a parent always comes before its child**. glTF puts no order on `nodes`, and everything downstream (composing model transforms, retargeting, blending) wants one forward pass rather than a recursive walk, so the topological sort is paid once at import. It is a stable sort by depth, so the result is a function of the file alone. The TRS form is kept rather than a matrix because a joint's node transform *is* its bind pose and every consumer of a bind pose wants rotations and translations; a node written as a matrix is decomposed here (column lengths are the scales, normalized columns the rotation, a negative determinant putting the mirror on x), once, instead of at every pose. **Every** node is kept, joint or not, with its transform: a skin's joints usually sit under a non-joint `Armature` node that carries one, and a joint's rest includes it — the [animation](animation.md#non-joint-ancestors) library folds those ancestors, and any animation channel on them, into the joints (S92); nothing here changed for it.

`nodes`, `skins`, and `animations` are populated **only for a file that has a skin or an animation**. A static mesh therefore imports exactly as it did before any of this existed, down to the allocations, which is what the unskinned tests assert.

**The skin.** `Skin::joints` is the palette a vertex's indices name, as node indices; `inverse_bind` is parallel to it and is filled with the identity when the file omits `inverseBindMatrices`, so a consumer never has to ask which form it got; `skeleton_root` is the file's `skeleton` node or −1. A skin is refused when it binds more joints than `geometry::k_max_skin_joints` (256), because that is what a `u8` per-vertex index can name: clamping would attach a limb to the wrong bone and the mesh would look right until it moved.

**The influences.** `JOINTS_0` and `WEIGHTS_0` become one `geometry::SkinBinding` per vertex in `MeshData::skin_bindings`, parallel to `positions`. Joint indices come through `cgltf_accessor_read_uint`, which widens both the `u8` and the `u16` forms exporters write; weights come through the float unpacker, which handles the float and the normalized-integer forms; and `geometry::make_skin_binding` renormalizes the four of them to sum to exactly 255. Four influences is the format's whole budget; a second set (`JOINTS_1`/`WEIGHTS_1`) is read since G2 and the heaviest four of the eight are kept, with what was dropped counted ("What G2 reads", "The influences"). A joint index outside the skin's palette, in either set, fails the load.

A file with several skins keeps each vertex's indices **in its own primitive's skin's palette**: the merge gives every primitive its own vertex block, so a vertex belongs to exactly one primitive and therefore to exactly one skin, and `Primitive::skin` says which. `attribute_source` reports the widest skin as the joint count, which is the bound `geometry::validate_clusters` needs; the content build's per-primitive cluster DAGs keep the palettes apart in practice. A rigid primitive in a file that also has skinned ones contributes the default binding (all weight on joint 0), which is what keeps the stream parallel to the positions.

**The clips.** One `Animation` per glTF animation, holding its samplers and its channels as the file wrote them: `times` in seconds, `values` with three or four floats per key (and three times that for `CUBICSPLINE`, which stores in-tangent, value, and out-tangent), `interpolation` as `k_interp_linear`/`step`/`cubic`, and a `duration` that is the largest keyframe time of any sampler. A channel names a node, a sampler, and one of translation, rotation, scale, or **weights**. Nothing is resampled, retimed, or converted: a curve that was authored at 24 Hz arrives at 24 Hz, and the decision about what to do with it belongs to `domain/anim`.

## Morph targets

One `geometry::MorphChannelSource` per **(mesh, target index)** pair in `MeshData::morph`, holding the POSITION and NORMAL deltas of every primitive of that mesh in the flattened vertex space. Per mesh and not per primitive, because that is what glTF means: within one mesh, target *k* of every primitive is driven by the same entry of the mesh's `weights` array. Per mesh and not globally, because two *different* meshes' targets are unrelated even where they share a name — a head's "smile" and a jacket's are different channels — and the flatten must not merge them; a mesh instanced by two nodes does share one set of channels, and both instances then play the same weights, which is what the format can express today (per-instance `node.weights` overriding the mesh's is a follow-up). Names come from `extras.targetNames` when the file says and are `<mesh>.<k>` when it does not; default weights come from the node's own `weights` if it has them and the mesh's otherwise, which is the order the specification gives. TANGENT deltas are ignored: since G2 a vertex may carry its asset's own tangent, but the deform pass moves no tangent, so a morphed vertex keeps its rest one (and the resolve, which does not read imported tangents yet, solves its frame per pixel from the deformed triangle).

**The deltas are transformed, and a normal delta is not a direction.** A rigid primitive's positions are baked into world space, so its position deltas go through the node transform's **linear part** alone. A normal delta, though, is the difference of two unit vectors, and transforming that difference gives the wrong answer under any non-uniform scale: it is recomputed as `normalize(N·(n + dn)) − normalize(N·n)`, which is why the importer keeps the primitive's own untransformed normals beside it while it reads the targets. A skinned primitive's vertices stay in bind space, and so do its deltas.

**Sparsity is lossless.** A delta is kept only when some component survives the stream's own 16-bit quantization — at least half the channel's step, which is its peak over 32767 — so what is dropped is exactly what would have been stored as zero anyway. That is deliberately not a second, invisible tolerance on top of the one [geometry](geometry.md) documents: the sparsity a build reports is then a property of the asset.

**What the Khronos morph samples confirmed** (the four `tools/fetch-samples.ps1` fetches; [apps](apps.md), "The morph samples, end to end"). Default weights come from the **mesh's** `weights` when the node has none — MorphPrimitivesTest's 0.5 and SimpleMorph's two 0.5s arrive as `default_weight` — and a name-less target set is named `<mesh>.<k>` (`mesh.0` for a mesh with no name, `Cube.0` for AnimatedMorphCube). AnimatedMorphCube's targets carry TANGENT deltas, which are ignored as they should be, under a node scaled by 100, which reaches the deltas through the linear part; MorphPrimitivesTest's carry **no NORMAL**, so its channel has no normal array; SimpleMorph has no NORMAL attribute at all and packs its targets as accessors into one buffer view at byte offsets; MorphStressTest names its eight targets in `extras.targetNames` and has three clips. Every one of the three animated files drives `weights` through a channel whose target is the **node**, which is the only place glTF puts it, and `collect_animations` resolved each to the right channel run. None of the four uses a **sparse** accessor, so that path — `cgltf_accessor_unpack_floats` applies the sparse substitution — is still exercised by no real file here. Reading the importer while they went through it found one latent bug no sample has the shape for: a channel's normal deltas are **one array parallel to its vertices or none, across every primitive of the mesh**, and the drop that enforced it only ran for a primitive *lacking* target normals, so a mesh whose first primitive's target had no NORMAL and whose second one's did came out with the array shorter than `vertices`. A primitive's normal deltas now join the channel only when every entry already in it has one; `gltf morph targets: normal deltas stay parallel whichever primitive lacks them` writes both orders. What they did **not** show at the time was the builders' weld, which left every channel in the pre-weld numbering: every container built before cluster cache version 11 carried MorphStressTest's deltas on the wrong vertices at 1,124 of its 1,528 ("The weld" below).
**An animation's `weights` channels** arrive as `k_path_weights` with a **SCALAR** sampler whose output holds one float per morph target per key. The target count is not in the accessor, so it is recovered as `output.count / (input.count × per_key)` and stored in `AnimationSampler::components` — which is why a scalar sampler is now accepted where only three and four components were before. `AnimationChannel::morph_channel` says which entry of the flattened `morph` array the curve's first value per key drives, and that is the one reason `collect_animations` runs **after** the scene walk rather than before it: only the walk knows where each mesh's channels landed. A weights channel whose mesh the default scene never instanced is dropped rather than left pointing at another mesh's rig.

**Testing (skins).** `tools/dev.ps1 test -Filter assets`, `skin_tests.cpp` over the fixture in `skinned_glb.h`: a two-bone bar of six vertices in three rows, its mesh node at x = +5 and its joints at the origin, written as a GLB at test time. The positions come back where the accessor put them rather than five units along x — the bind-space rule as an assertion — with the +5 on `Skin::node_transform`; the node array comes back parent-before-child although the file deliberately writes the mesh node before the deepest joint; the joint palette, the two inverse bind matrices, and the middle row's 127/128 split are checked exactly; the `u16`-joint and normalized-`u8`-weight forms give byte-identical bindings to the float form; the one animation's three samplers come back as LINEAR rotation, STEP translation, and CUBICSPLINE scale with the right value counts and the right target nodes; and the loaded mesh feeds `geometry::build_clusters`, which validates with its binding stream. Two failures are pinned: a `JOINTS_0` index outside the skin's palette, and a skin of 302 joints.

**The UV repair over an imported mesh.** `repair_uv_degenerate_triangles(mesh, report, error)` runs `geometry::repair_uv_degenerate_triangles` ([geometry](geometry.md#uv-degenerate-triangles-the-repair)) over a `MeshData`: one run per primitive, in index order whatever order the file listed them in, a run counted as sampled when its material names any of the five image slots (an untextured primitive is left exactly as the file had it), the normals passed so a folded corner can take its neighbour's, and every primitive's `first_index` and `index_count` rewritten when a triangle is dropped. It lives here rather than in either caller because it has **two** callers that must agree byte for byte — `engine-content build` and the renderer's glTF path behind `engine-view --mesh`, which share derived-data cache entries — and both call it after the load and before the weld. It returns false only for primitives out of order or overlapping, which the importer never produces. **Testing:** `uv_repair_tests.cpp` builds two primitives by hand, one textured and one not, each a quad beside a sliver of no UV area thinner than the grid: only the textured one's sliver is dropped and the second primitive's range moves down by three; and a mesh whose primitives are listed out of index order gets each primitive's own range back.

**The zero-area repair over an imported mesh.** `repair_zero_area_triangles(mesh, report, error)` runs `geometry::repair_zero_area_triangles` ([geometry](geometry.md#zero-area-triangles-the-repair)) over a `MeshData` the same way: one run per primitive in index order (the two adapters share the ordering), **every** primitive whatever its material — a triangle with no area is nobody's geometry — and every primitive's range rewritten as triangles are dropped; no per-vertex stream is touched. Both builders call it after the load and **before** the UV repair, for the same two-callers reason. It returns false only for input the importer never produces. **Testing:** `zero_area_repair_tests.cpp` builds a textured and an untextured primitive, a collinear triangle in one and a coincident one in the other: both are dropped, each primitive keeps its material and gets its own range back (also when listed out of index order), every stream keeps its length and values, and the weld then drops the four orphaned vertices.

## Canonical vertex ids

`MeshData::vertex_ids` is one `u32` per vertex naming **the point of the canonical base the vertex stands for**, and `vertex_id_source` says where the names came from. They are what a file written beside the mesh — a binding, a region's membership, a corrective residual — names vertices by, because the index a vertex has after the content build is the weld's and changes whenever the weld's input does ([geometry](geometry.md#canonical-vertex-identity) has the why, the weld and LOD rules, the container sections, and what it costs; [07 §7.11](../plan/07-content-pipeline.md#711-characters) the intent).

**The attribute: `_CANONICAL_ID`** (`k_canonical_id_attribute`). The name is **reserved** by this engine; glTF requires an application's own vertex attributes to start with an underscore, which is why it does. The accessor is SCALAR, one id per vertex of the primitive, and one of UNSIGNED_BYTE, UNSIGNED_SHORT or UNSIGNED_INT, not normalized — the glTF 2.0 core reserves UNSIGNED_INT for indices, and the importer takes it anyway, because an id space past 65,536 needs it and cgltf reads it — or FLOAT holding whole numbers from 0 to 2^24, which is what a DCC tool that exports integer attributes as floats writes, exact over that range. An id is a **name**, so every form that could round, wrap or scale it is refused with a sentence rather than converted: a signed or normalized component, another shape, a sparse accessor, a fraction or a negative number, and a float past 2^24. **One value is not refused: the one that means "no id"** (G130). A FLOAT exactly `-1` and an UNSIGNED_INT `0xFFFFFFFF` read as `geometry::k_no_vertex_id` for that vertex, and every other negative number (−2), fraction and out-of-range value still fails with the same sentence. This reverses the first version of the rule, which refused `0xFFFFFFFF` as reserved, and the reason is that the reserved value *is* the no-id value: accepting it confuses nothing, and it is what the authoring tracks write (the male anatomy module holds −1 on 8,816 of its 8,901 vertices and the nipple-areola caps on 6,804 of 6,929 — every vertex that is not a body vertex), so the engine takes what the tools produce rather than asking each export to be post-processed. The vertex is then exactly a vertex of a primitive with no attribute (next paragraph): the weld and the simplifier's id lock treat it as "no identity", so it merges with no named vertex and with other no-id vertices only on their other attributes, and `engine-content stats` counts it as `without_id`. The mesh's source stays `authored`. `engine-content morphs` reads the attribute by its own path and still refuses −1, since it needs every vertex of a canonical-topology body to be a canonical id; that is right for its input and unchanged. A material that names `texCoord 1`, which the caps carry, is still refused: that is the second UV set of roadmap G2. Two vertices the author gave one id at two positions are allowed (an author may mean a point that moves between two copies of a mesh a node instances twice); `engine-content stats` counts them as `ids_at_several_positions`, which is the first thing to read on an authored base.

**Ids from a file that has them** (`VertexIdSource::authored`): the values, as written. In a file where some primitives carry the attribute and some do not, the vertices of those that do not get `k_no_vertex_id`: to the weld that is "no identity", so they merge among themselves on their other attributes exactly as before ids existed, and never into a named vertex.

**Ids for a file that has none** (`VertexIdSource::position_weld`): the base's own rule, `geometry::position_weld_ids` — **the id is the index of the vertex's position in a position weld of the source**, the distinct positions ordered by x, then y, then z, numerically, with −0 and +0 one position. The two sides of a UV seam, a hard edge and any exporter's duplicates therefore share an id, which is the control-level meaning; the ids are dense; and they depend on the **set** of positions and not on the file's vertex order. Deterministic by construction: a sort, never a hash table's iteration order.

**Computed once, at import, over the mesh exactly as imported**: over every vertex the flatten produced (world space for a rigid primitive, bind space for a skinned one, both instances of a mesh a node instances twice), before the UV repair and before the weld. The UV repair moves no position and the weld carries the stream (`weld_vertices` below), so no later step can name a vertex differently from the source. It costs four bytes a vertex on every import and a sort of one 16-byte key per vertex ([geometry](geometry.md), performance notes); this is the one stream a static mesh now allocates that it did not before, deliberately, since a mesh that nobody named still needs names for anything written beside it.

**Testing.** `vertex_id_tests.cpp` (`tools/dev.ps1 test -Filter assets`), over three quads in a row written as a `.gltf` at test time, each with its own four vertices: a shared edge whose two vertices agree on everything and carry one id welds into one; a UV seam whose two sides carry one id stays two vertices, both with the point's id; two coincident vertices that agree on everything but their ids stay two — and the geometry weld not handed the ids merges them, which is the defect as an assertion — so 12 vertices weld to 10 (9 without the stream); every cluster copy carries its source vertex's id, checked against the mesh **before** the weld through the map the weld's own index rewrite gives. The UNSIGNED_INT, UNSIGNED_SHORT, UNSIGNED_BYTE and FLOAT forms read the same ids; a VEC2, a signed short, a normalized byte, a fraction, a number below −1 and a float past 2^24 each fail the load with the attribute's name and their own reason and leave the mesh empty; a float `-1` or a uint `0xFFFFFFFF` on two vertices (b0, which would otherwise merge into a1, and b1) reads as `k_no_vertex_id` there and the named ids elsewhere, welds 12 to 11 (b0 is not merged into a1), and every cluster copy carries its source's value (G130); a second primitive without the attribute gets `k_no_vertex_id` and welds 12 to 9 on its own; and the same file without the attribute is named by ranks computed independently in the test, with the two sides of the seam sharing one. The last case runs the Khronos skinned and morph samples through the load, the UV repair, the weld and one DAG per primitive when `tools/fetch-samples.ps1` has fetched them (it says so and passes when it has not): the weld with derived ids gives the same vertices and indices as the weld without them, and every cluster copy carries its source's id — 3,812 of them on the Fox, 727 on RiggedFigure, 24, 40, 3,716 and 3 on AnimatedMorphCube, MorphPrimitivesTest, MorphStressTest and SimpleMorph, 0 wrong. **With the ids withheld from `weld_vertices`** the same case fails on five of the six: every copy is wrong on the Fox, RiggedFigure and MorphPrimitivesTest (their weld merges or drops vertices, so the stream no longer fits and the builders drop it), 3,571 of 3,716 on MorphStressTest and 12 of 24 on AnimatedMorphCube (renumbered, not resized, so the ids land on whichever vertex took the old number); SimpleMorph's weld renumbers nothing and cannot see it.

## The weld

`weld_vertices(mesh)` is `geometry::weld_vertices` over **every per-vertex stream a `MeshData` owns** — positions, normals, UVs, skin bindings, morph channels and canonical vertex ids — and it is the weld both builders of a cluster container run, after the UV repair and before clustering: `engine-content build` and the renderer's glTF path behind `engine-view --mesh`, which share derived-data cache entries and so must build the same bytes. Two vertices merge only when they agree on every stream, so two coincident vertices whose skin weights or morph deltas differ stay two vertices (a morph seam stays a seam, [geometry](geometry.md#morph-channels-the-second-per-vertex-deformation-stream)), and so do two the author gave different ids; unreferenced vertices are dropped; the indices are rewritten in place, so the primitive ranges do not move; and each morph channel's vertex list is renumbered to match. It returns the new vertex count.

**Why it is one function over the struct, and not each builder spelling out the streams.** The weld numbers vertices by first use in the index buffer, so it renumbers nearly every indexed file even when it merges nothing, and a stream it is not handed is left **in the old numbering** while the others move. That has now happened twice. The skin bindings were a parameter neither builder passed for one release (cache version 5 fixed it); the morph channels were one neither builder passed for three (versions 8 to 10), and every container built in that time put a morphed source's deltas on whichever vertices took the old numbers and silently dropped those whose old number was past the welded count — MorphStressTest's on 1,124 of its 1,528 vertices, AnimatedMorphCube's on 10 of 24 ([geometry](geometry.md#morph-channels-the-second-per-vertex-deformation-stream), "The builders' half, which was missing", has the table and why no test saw it). Both times the call site was one line from right and looked right. The builders now hold a `MeshData` and call this, so neither chooses which streams take part, and a stream `MeshData` gains is added here once — which is exactly how the canonical ids arrived: one argument in this function, and both builders had them. Passing an absent stream costs nothing: the weld keys on the skin bindings and the ids only when they are parallel to the positions and on the morph channels only when there are some.

**Testing.** `weld_tests.cpp`. A strip of four quads written as a triangle soup in two primitives, after one vertex nothing references, with skin bindings and two channels — one its coincident copies agree on, one they disagree on across the primitive boundary — welds to 12 vertices (the agreeing copies merged, the seam kept, the unreferenced vertex gone), renumbers both channels onto vertices at the right places, and, built into one DAG per primitive exactly as the builders build it, every one of the 24 corners' cluster copies carries its own source vertex's deltas (18 of them non-zero) and its own binding. The comparison is against the mesh **before** the weld, through the map the weld's own index rewrite gives, so nothing of the weld's bookkeeping sits between the two sides. With the builders' old call this case failed 24 assertions — 10 vertices instead of 12, and 33 wrong comparisons on 18 of the 25 source vertices. The second case runs the same check, after the load and the UV repair as both builders run them, over the four Khronos morph samples when `tools/fetch-samples.ps1` has fetched them (it says so and passes when it has not, as CI does; a bundle made with `-WithSamples` carries them): zero wrong on all four, where the old call gave geometry.md's table. `engine-content: a morph delta lands on its own vertex when the weld renumbers` ([apps](apps.md)) holds the engine-content call site itself to the same property, end to end through the container.

## Editing a glTF document

`gltf_document.h` is the module's one writer, beside an importer that only reads. `read_gltf_document` takes a `.gltf` and the file its one buffer names, or a `.glb`'s JSON and BIN chunks, into a `GltfDocument`: the file's own JSON as a `DocValue` tree and buffer 0 as bytes. `read_accessor` reads an accessor through its view's offset and stride, `append_float_accessor` pads the buffer to four bytes and appends a float buffer view and accessor with their `min` and `max`, and `write_gltf_document` sets `buffers` to the one `<stem>.bin` and writes the pair. A document with more than one buffer, a data-URI buffer, a sparse or normalized accessor is refused: nothing that edits one has needed them.

**Why a JSON model of its own, and not `core/json`.** `JsonValue`'s objects are sorted maps, which is what makes the engine's canonical writer canonical; a glTF document's key order is its exporter's. An edit has to leave every object it does not touch as it was, so `DocValue` keeps each object's keys in file order, appends a new key last (what a Python dict does), keeps an integer as the digits it was written with, and a float as the double it parses to.

**Why the writer is Python's.** `write_document_json` is `json.dumps(value, indent=2)` byte for byte: two-space indentation, one item a line, `": "` after a key, `[]` and `{}` for empty containers, everything outside printable ASCII escaped as a lowercase `\uXXXX` (a surrogate pair past the BMP), and a float as `repr` prints it — the shortest digits that round-trip (`std::to_chars`, which picks the same digits Python does), positional for a decimal exponent from −4 to 15 and `1e-05`/`1.5e+16` outside it, `.0` on a whole number (`python_float_repr`). The documents it edits come out of Python (Blender's exporter, the authoring scripts, the forest proof of concept's recipe), so a Python-shaped writer turns an edit into a diff of what changed, and its first job's acceptance was byte identity with a Python-written file. The line break is the caller's: `engine-content morphs` writes `"\r\n"`, what Python's text-mode write produced on the owner's machine, on every platform.

**Testing.** `gltf_document_tests.cpp`: `repr` against CPython's output for twenty values (the boundaries, negative zero, float32 values widened, the owner's own numbers); a document whose keys are out of order, with escapes, an empty object and array, a 64-bit integer and `1E2`, written to the exact expected text and back; the parser's refusals; and an appended accessor's padding, offsets, `min`/`max` and the written `buffers` entry.

## Morph channels from MakeHuman targets

`engine-content morphs` ([apps](apps.md#engine-content-morphs-makehuman-targets-as-morph-channels), roadmap C59) appends MakeHuman's CC0 shape targets to an authored canonical-topology body as morph channels, `shape.<key>.less` and `shape.<key>.more` a control of the catalogue, with `POSITION` and recomputed `NORMAL` deltas, through `gltf_document.h`. It is the engine's form of the forest proof of concept's recipe step (its `scripts/build-player-asset.py`, P59), and reproduces that script's `body.gltf` and `body.bin` byte for byte on the two v1 creator bodies.

**A canonical id is not a MakeHuman vertex index.** The roadmap row first assumed it was; the POC's v27 one-shot found otherwise. Three maps stand between a target and an export vertex: the target names a vertex of MakeHuman's `base.obj`; the authoring release's `exports/control-data.json` holds `source_template_vertex_ids`, canonical id → `base.obj` vertex, which must equal the sorted set of vertices the `body` group's faces use (the command refuses a release whose list is not, since it was authored on another base); and the glTF's `_CANONICAL_ID` attribute names each export vertex's canonical id, which the identity file beside a `.gltf` (`*.identity.json`, `mappings[0].export_vertex_to_canonical_id`) must agree with. So a delta reaches export vertex `v` as `target[mapping[id[v]]] · scale`. The end-to-end test puts ten helper vertices before the body's in its synthetic base, so a tool that read an id as an index fails every delta.

**The scale.** MakeHuman's raw units are decimetres only roughly, so the scale is derived rather than assumed: `scale = 1.75 / h`, where `h` is the `body` vertices' y extent on the baseline body — `base.obj` plus a third of each of the three young-male ancestry targets (`adult-body-baseline-targets/{african,asian,caucasian}-male-young.target`), the average young adult male MakeHuman shows, taken to stand 1.75 m. On MakeHuman a8bc2d54 that is 0.10113268608414239 m per raw unit.

**The normals.** A morphed body's normals are recomputed, not read from the target (MakeHuman's targets carry none): area-weighted face normals summed per canonical id — so the two sides of a UV seam, two export vertices of one id, agree — normalized, spread back to the export vertices, minus the same for the unmorphed body. The arithmetic follows the Python operation for operation, because the acceptance is byte identity: float face vectors for the body as stored (numpy's float32 positions), double for the morphed one (`pos + delta` is float64), sums in double corner by corner and triangle by triangle, the length as `(x² + y²) + z²`, deltas cast to float last. Contraction is off tree-wide ([ADR-0035](../adr/0035-no-floating-point-contraction.md)), so the products round where numpy's do.

**What else moves.** Every animation's `weights` track that drives a morphed mesh is padded with zero channels so a clip keeps one value a channel (a new accessor; the old one stays, unreferenced); the mesh's `weights` and its nodes' `weights` get zeros; the source's buffer is the output's prefix, unchanged. A file with several meshes gets the channels on every mesh whose vertices carry `_CANONICAL_ID` (ids missing from a mesh, a removed face's, are allowed); a mesh without the attribute is left exactly as it was and named in the summary, because making a module follow the body's morphs is the authoring side's design, not a guess for the tool. A mesh with the attribute and more than one primitive is refused. Before reading a target the command checks what the durable script checks: each file the targets' `target-downloads.json` names has its pinned git blob hash, and the licence texts and breast targets beside them are the reference tree's, byte for byte.

**Not committed.** The MakeHuman targets and `base.obj` stay in the owner's reference tree; the tests use synthetic ones. A later job that wanted the 30 targets in the tree would commit them with `LICENSE.md`/`LICENSE.ASSETS.md` (CC0) under `content/`, with a row in `third_party/LICENSES.md`, and a test that runs the real scale.

**Testing.** `apps/engine_content/tests/morphs_tests.cpp`: a synthetic base of 266 vertices, three baseline targets, five shape targets and a two-control catalogue, and a 272-vertex canonical-topology glTF with a seam, a skin, one existing morph, a `weights` animation and a second mesh without ids. The deltas are held to a double reference cast to float (exact), the normal deltas to within 1e-5 of an all-double reference, the buffer prefix to the source's bytes, the track to its padding, the second mesh to its JSON, the output to `load_gltf` reading the channels by name, and two runs and a GLB of the same document to the same bytes; a mapping that reads an id as an index is refused.
