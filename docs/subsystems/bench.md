# bench (foundation)

**Purpose.** The micro-benchmark harness (ADR-0011; docs/plan/11-performance-principles.md §11.8): registration, calibrated timing, statistics, tunable sweeps, and reports as a table and as JSON lines, so "is this faster?" is a command. Every module keeps its benchmarks in `bench/` and `engine_module_bench()` builds one executable per module with `run_main` as its entry point.

**Model.**
- `ENGINE_BENCH(ident, "module.topic.case")` and `ENGINE_BENCH_ARGS(ident, name, 16, 256, ...)` define and register a body. The body sets up outside the loop, runs `while (state.keep_running()) { ... bench::keep(result); }`, and reports `state.set_items()` / `set_bytes()` per iteration for rate columns. `pause_timing`/`resume_timing` exclude setup inside the loop. `bench::keep` forces a value to be materialized so the optimizer keeps the work that produced it.
- The runner calibrates an iteration count that fills `min_time_ns` (default 100 ms), runs `warmup_repeats`, then `repeats` (default 7) timed repeats of that count, and reports the per-iteration median, minimum, maximum, mean, and standard deviation. `--smoke` runs one iteration once, for CTest. A fixture built once for a whole bench file (a corpus, a world) sizes itself from `bench::smoke_mode()`, so the smoke run stays seconds long in release builds too.
- `--sweep=<tunable>=<v1;v2;...>` runs every matching benchmark once per value and prints a relative column against the first value, then restores the original; `--set=<tunable=value,...>` applies overrides for the run. This is how a tunable's effect is measured (experiment E3's input).
- Output: a table on stdout and, with `--json=<path>`, one JSON object per result appended after a header line carrying the CPU brand, logical CPU and cache-domain counts, build configuration, and time. `tools/dev.ps1 bench` runs every bench executable and writes `build/<preset>/bench/<module>.jsonl`.
- The runner pins itself to the first performance CPU and raises its priority unless `--no-pin`. **A thread started after that inherits the pin**, so a bench's own `jobs::JobSystem` must pin its workers (`JobSystemConfig::pin_threads`, the default) or they all share the runner's one CPU: `terrain_bench.cpp`'s pool was made with `pin_threads = false` and its `terrain.field.reevaluate` and `terrain.ring.*` numbers were one core's until 2026-09-27 — user time equal to wall time is the sign ([the experiment](../experiments/time-lapse-smoothness-2026-09-27.md#c-evaluation)).

- A filter may name **one variant** of an `ENGINE_BENCH_ARGS` registration the way `--list` prints it: `--filter=physics.e19.tick/216010081`, `--filter=test.bench.args/*`, or `--filter=*/4` for every registration's four-worker variant. Everything before the first `/` selects the registration and the whole pattern selects the variant; a filter with no `/` behaves as it always did and runs every variant of what it matched. This exists for the shared machine below: the length of a run is the length of the window that has to stay quiet, and reaching one row of a fifty-row registration used to mean running all fifty.

**Invariants (tested).** Smoke mode touches every matching benchmark exactly once; measured mode calls the body at least once for calibration, once per warmup, and once per repeat; sweeps set each value in order and restore the original even when a value is rejected; the JSON file holds one header and one object per result; filters accept `*` globs and plain substrings, and a filter carrying a `/` selects variants rather than registrations; a measured run samples the machine once before and once after itself and a smoke run samples it not at all; a GPU lock that is absent, this process's own, or expired is quiet, and one somebody else holds (another tool, another engine agent under the same owner label, a person's even when expired, a file still being written) is not; `--gpu-lock` holds the lock while the benchmarks run and releases it after, gives up with exit 4 on somebody else's lock, breaks an expired one, never breaks a person's, and a release never deletes a lock it did not write.

## Measuring on a shared machine

The development machine is not an idle benchmark rig. It runs GPU diffusion jobs that hold the whole card and most of its memory for minutes at a time, and several agents compile and test on it at once. A number taken beside those is an **upper bound** on the cost, not the cost — and the numbers that decided the first budgets were taken with no record of what else was running, so nobody can tell which of them were. The harness therefore records the machine's state around every measured run, says when it was busy, and can refuse to measure or wait.

**What is recorded**, at the start and at the end of a run (`foundation/bench/machine_state.h`):

| Field | Where it comes from | Absent when |
|---|---|---|
| `cpu_total_pct`, `cpu_own_pct`, `cpu_others_pct` | `GetSystemTimes` + `GetProcessTimes` on Windows, `/proc/stat` + `/proc/self/stat` on Linux, over a 250 ms window; "others" is total minus own, clamped at zero | the counters could not be read |
| `gpu_util_pct`, `gpu_memory_used_mib`, `gpu_memory_total_mib` | `nvidia-smi --query-gpu=...` when it is on PATH | no such tool: an AMD or Intel box, or a CI runner |
| `gpu_sm_clock_mhz`, `gpu_sm_clock_max_mhz` | the same `nvidia-smi` line, `clocks.sm` and `clocks.max.sm` (roadmap T69): the SM clock at the instant of the reading and the most it may run at, so a number taken on a throttled or a boosted card says so. An instant, not an average: an idle card at the start sample reads its idle clock, and the end sample keeps the first reading, taken as the run's own work ends, which is the run's clock; `worst_of` keeps the slower | no GPU reading, or a card that answers `[N/A]` for its clock (the busy share and memory still stand) |
| `session_locked` | a `LogonUI.exe` process exists (Windows) | anywhere else — reported as `null`, never as "unlocked" |
| `gpu_lock` | the machine-wide GPU lock file (see "The GPU lock" below): `owner`, `purpose`, `expires` as its holder wrote them, plus `mine` and `expired` | there is no lock file — reported as `null`, which is also what a machine that does not use the lock reports |

**No process names, no command lines, no user names leave the sampler**, on purpose: the question is how loaded the box is, and the answer does not need to say by whom. The session check walks the process list for one name and keeps a boolean. The one exception is the GPU lock's `owner` and `purpose`, and it is not really one: the holder wrote them into a file every tool on the machine reads, precisely so that whoever is waiting can see who has the GPU and why, and a report that says "the GPU was spoken for" without saying by what leaves its reader to guess which numbers to distrust.

`nvidia-smi` rather than NVML because the engine takes no new dependency for a measurement convenience ([08 §8.6](../plan/08-toolchain.md)) and the utility is already installed wherever the driver is; a machine without it reports nulls and everything else still works. The first GPU's line is the one read.

**The thresholds, and why those.** A run is *quiet* when other processes used no more than **10%** of the CPU and the GPU was no more than **20%** busy. Both are deliberately loose. An otherwise idle Windows desktop with a browser, a shell, an editor and the usual services sits at a few percent of 36 logical CPUs, and a desktop compositor driving three monitors keeps the GPU in the low teens, so a tighter bound would fire on a machine nobody is using and the flags would be ignored within a week. They are also loose enough to be *meaningful* in the other direction: one parallel `cmake --build` on this box is 40–90% of the CPU and a diffusion job is 100% of the GPU, so the things that actually move a benchmark are far above the line rather than near it. `--quiet-cpu=<pct>` and `--quiet-gpu=<pct>` move them when a particular measurement needs a stricter or looser rule; say in the write-up when you moved them.

**A GPU lock held by somebody else is not quiet**, whatever the utilization sample says. A sample is a quarter of a second; a render between frames, a bake loading its scene, or an image job about to start all read as an idle GPU for that long, and the lock is the holder saying in advance that the card is spoken for. A lock that is this run's own — taken with `--gpu-lock`, or by a wrapper on its behalf — does not count against it, and neither does an expired one, except a person's (`owner` `"marc"`), which the protocol says no tool may treat as gone.

**The end sample is read after the run's own work** (roadmap T178, 2026-11-17). `nvidia-smi`'s `utilization.gpu` is "percent of time over the past sample period during which one or more kernels was executing", the period "between 1 second and 1/6 second depending on the product" (`nvidia-smi --help-query-gpu`), so a reading taken as a GPU run ends counts the run's own last frames. The frame budgets' unpaced erg walk read **busy** at every gate of batches 66 and 67 for exactly that: other processes at 1% of the CPU and the card at 97 to 99% in the end sample, idle in the start one. So the end sample of a measured `engine-view` run (the flythrough's timed pass, the frame loop's benchmark and the reference render, each after the device is idle) is `bench::sample_machine_state_after_own_gpu_work`: when its first GPU reading is over the threshold it waits `k_gpu_utilization_period_ms` (1 s, the counter's longest period) and reads the GPU again, and that second reading is the end's — what the card is still doing a second after this process stopped is somebody else's. The first is kept as `gpu_own_tail_pct` in the end object (present only when it was set aside), and `tools/frame-budget.ps1` prints it, `GPU 2% (own tail 97%)`, so the discount stays visible. A quiet first reading costs nothing more; the CPU, the session and the lock are never discounted; a second reading that fails keeps the first. The start sample needs none of this: nothing of the run's has been drawn yet. The windowed run's end (a player's session, not a gate's measurement) and `engine-host`'s `render.benchmark` still take a plain sample. `machine_state_tests.cpp` holds it with the readings injected.

An **unknown** field can never make a machine noisy. A box with no GPU reading is quiet as far as its GPU is concerned, because a rule that refused to measure on missing information would make `--require-quiet` useless on Linux CI and on every non-NVIDIA machine.

**What the flags do.**

```powershell
build/msvc-release/domain/sim/engine_sim_bench.exe --filter=sim.wheel.* --require-quiet
build/msvc-release/domain/sim/engine_sim_bench.exe --filter=sim.wheel.* --wait-quiet=7200
build/msvc-release/domain/sim/engine_sim_bench.exe --filter=sim.wheel.* --gpu-lock --require-quiet
tools/dev.ps1 bench -Preset msvc-release -Filter "sim.wheel.*" -GpuLock
```

- `--require-quiet` measures nothing on a busy machine: it prints the state and exits **4**, which is a code of its own so a script can tell "come back later" from "this run failed" (2) and from a real failure.
- `--gpu-lock[=<max wait s>]` takes the machine-wide GPU lock for the run: it waits for it (default up to four hours, the PowerShell tool's bound, saying whom it waits for), holds it from before the first sample to after the last, and releases it however the run ends. Giving up is exit **4** as well. It comes *first*: the lock is the queue, so a run waits its turn and then asks whether the machine is quiet, holding the GPU while it asks. `tools/dev.ps1 bench -GpuLock` passes it to every bench executable. Details under "The GPU lock" below.
- `--wait-quiet=<seconds>` looks every 5 seconds until the machine is quiet or the deadline passes, then runs either way and says on stderr which of the two happened and how long it waited. It never sleeps past the deadline. This is the flag to reach for before a session of measurements: start it, let the diffusion job finish, and the numbers come from the other side of it.
- `--smoke` does none of these, and does not sample or take the lock at all. A smoke run answers "does this benchmark run", CTest runs one per module, and a quarter of a second plus a process spawn per module would buy nothing there. Its JSON header says `"machine_state": null` rather than reporting a state it did not take.

**What a WARNING means for a write-up.** When either threshold was crossed at either end of a run, or somebody else held the GPU lock, the table gets one line under it (on stderr when `--quiet` suppressed the table):

```
WARNING: other processes used 20.5% of the CPU and the GPU was 100% busy; these numbers are
upper bounds (cpu 20.6% (others 20.5%, own 0.2%), gpu 100% util 24864/32607 MiB, session unlocked,
gpu lock free)
WARNING: the GPU lock was held by 'astra-blender' (bake: desert), other processes used 1.2% of the
CPU and the GPU was 4% busy; these numbers are upper bounds (...)
```

It does not mean the numbers are wrong; it means they are **upper bounds** and that a quiet run would be the same or faster. A write-up may use them — sometimes the loaded case is the interesting one — but it has to say so: an experiment page that quotes a number from a warned run and does not carry a "Machine state" line is the failure this whole feature exists to prevent (see [docs/experiments/README.md](../experiments/README.md), and AGENTS.md's "Rules that are reviewed"). A *ratio* between two benchmarks measured in the same warned run survives far better than either absolute number, because both paid the same tax; a comparison against a number from another day does not survive at all.

**A load time states the driver cache's state.** A cold pipeline is the driver's compile, and the driver keeps a disk cache of its own that `ENGINE_PIPELINE_CACHE=0` does not touch, so a "cold" load time says whether that cache was warm too: cold means `__GL_SHADER_DISK_CACHE=0` with `__GL_SHADER_DISK_CACHE_PATH` an empty directory of the run's own on NVIDIA, beside the engine's switch ([gfx](gfx.md#pipelines-created-in-parallel)). **Two binaries copied out of two checkouts compile their pipelines cold** (roadmap T183): the engine's file is `<ddc>/pipeline-cache/`, a copied-out binary finds no ddc above it and two checkouts have two, and the driver's own cache misses the side whose SPIR-V is new, so the first flight of each side pays its compile and the sides pay it differently. A pair passes both sides the same `--ddc` (a root of the pair's own, not the staging's) and flies each side once, unmeasured, before the measured flights — or, for a load time, runs both sides cold as above; a warm side's load against a cold side's is the cache, not the change ([apps](apps.md), "engine-view's pipeline cache").

**In the JSON.** The header line gains `machine_state` with a `start` and an `end` object of the fields above, each field `null` where it is unknown (`gpu_lock` is `null` or `{"owner", "purpose", "expires", "mine", "expired"}`), and every result line gains `worst_others_cpu_pct` — the worst "others" CPU either sample saw — so that one line out of a `.jsonl` carries its own caveat without the reader having to find the header. The end sample only exists once the last benchmark has finished, which is why the whole file is written when the run ends rather than streamed: a run killed part way leaves no JSON, and its numbers were taken under whatever killed it anyway.

**What two samples cannot see, and what to do about it.** Load that starts *and* ends inside a run is invisible to a check at its two ends. Measured on 2026-09-18 while re-taking the numbers below, that is not hypothetical: one `store.projections.range_by_tile` run began at 3.2% others and ended at 86.3%, and its medians came back 2.1× and 1.8× the documented ones — the WARNING caught it because the load was still there at the end, and a build that had finished a second earlier would have been missed. So the rule for a run whose numbers will be quoted is **`--require-quiet` plus a repeat**: two runs that agree to a percent were almost certainly both quiet, and two that disagree tell you to look. Per-benchmark sampling would close the gap and is not free — a 250 ms window per benchmark is a third of the cost of the seven repeats it qualifies — so it is a deliberate gap, not an oversight. Running one bench executable at a time, rather than `tools/dev.ps1 bench` over all of them, also keeps the window a run covers short enough to mean something — and so does naming the one variant you want (`--filter=physics.e19.tick/216010081`) rather than the registration it belongs to. Measured while taking [ADR-0031](../adr/0031-minimum-cpu-x86-64-v3.md)'s numbers on this box: a two-minute `physics.step.*` run was warned-on three times in a row because somebody else's build started inside it, and the same rows taken as three runs of fifteen seconds each came back clean on the first or second try. **Make the run shorter before making the machine quieter.**

**The GPU lock.** Quiet is not only a property of the machine but of who else is using it, and this GPU is shared with other agents that never see this harness (as of 2026-09-22, a ChatGPT agent working in Blender on the same card). So anything heavy on the GPU takes the machine-wide lock first: `tools/gpu-lock.ps1 run -Purpose "<what>" -Exec "<command line>"` waits for the GPU, runs the command, and releases in a `finally`; `acquire`/`release`/`refresh`/`status` are the pieces. **`run` exits with the code of the program its command ran**, not with PowerShell's 1-for-anything-that-failed: until 2026-10-04 it reported 1 for every failure, which turned an access violation's `0xC0000005` into an anonymous "exit 1" and sent an agent bisecting for an hour (`machine-lock.Tests.ps1` holds it). The lock is one JSON file created atomically with an owner, a purpose, and an expiry, at `$env:ENGINE_GPU_LOCK` or by default `<workspace>\gpu.lock` on Windows and `/tmp/gpu.lock` elsewhere; its format and rules are written once, for every tool on the machine in whatever language, in `<workspace>\GPU-LOCK.md`: an expired lock may be broken, an unexpired one never, a lock owned by a person never by a tool. *Heavy* means more than about 4 GB of VRAM or more than a minute of GPU time: image generation, image-to-3D, Blender bakes and renders, GPU benchmarks and measurements whose numbers get recorded. A single short capture does not take it; a measurement taken while someone else holds it is an upper bound, and `--require-quiet` refuses it.

**Tests take it themselves, per device** ([gpu_lock](gpu_lock.md), [ADR-0049](../adr/0049-tests-take-the-gpu-lock-per-device.md)). A test executable, and every process it starts, takes the lock in `gfx::Device::create` for exactly as long as a GPU device is open, so a suite holds the GPU while it uses it and not while it checks documents, builds content or steps physics; nobody wraps `tools/dev.ps1 test` in `gpu-lock.ps1 run` any more (it still works, and holds the GPU for the whole run again). The owner's own sessions never take it: only the test main turns the switch on.

There are two implementations of the protocol and no more: `tools/lib/MachineLock.psm1` for every PowerShell tool (`gpu-lock.ps1`, `tools/ci/gpu-smoke.ps1`, `tools/ci/reference-compare.ps1`, and the Linux container build's own lock in `tools/linux-build.ps1`), and `foundation/gpu_lock` for C++ — this harness's `--gpu-lock` and device creation's hold — which cannot import a PowerShell module. (It was this module's `gpu_lock.h` until device creation needed it too; a renderer should not link a benchmark runner to open a device, so it moved.) Both refresh by writing beside the file and renaming over it, never by rewriting in place (a reader that caught a half-written file used to judge it expired and delete a live lock); both treat an unreadable file as mid-write until it is a minute old; both break an expired lock by moving it aside and deleting it only if it is still the file they judged, so two waiters cannot both break it and then share the GPU; and both release only the file they wrote — owner, pid and start time — because every engine agent is `claude-engine`.

**Whose lock is "mine".** Not the owner label's: every engine agent writes `claude-engine`, so an owner match would let one agent's measurement run straight through another agent's render. A lock is this process's when its owner is this process's (`$env:ENGINE_GPU_LOCK_OWNER`, default `claude-engine`) and its `pid` is this process — the harness took it with `--gpu-lock`, or a device of this process did — or the process named by `ENGINE_GPU_LOCK_HOLDER`, which `gpu-lock.ps1 run`, `gpu-smoke.ps1`, `reference-compare.ps1` and a process holding the lock for its GPU device set to their own pid for everything they start while they hold it — the PowerShell ones with `ENGINE_GPU_LOCK_OWNER` set to the owner they hold under beside it, so a wrapper given `-Owner` is still its children's ([gpu_lock](gpu_lock.md)). So `tools/gpu-lock.ps1 run -Purpose "bench" -Exec "..."` and `--gpu-lock` both work with `--require-quiet`; a lock taken by a separate `gpu-lock.ps1 acquire` does not, because the process that took it has exited and nothing distinguishes it from another agent's, and `--require-quiet` says so when it refuses. A wrapper's lock that has **expired** is a wrapper that died, and `--gpu-lock` breaks it like anybody else's (since 2026-09-30; it used to be taken as this process's for as long as the file stayed).

**How `--gpu-lock` holds it.** The lease is sized from the run — the options' prediction of it (calibration, warmups and repeats at `min_time_ns`, for every variant and sweep value), doubled, at least ten minutes and at most an hour — so the `expires` a waiting agent reads of a long run is roughly when it will be done, and a crashed run blocks the machine for one lease and not for as long as it might have run. It is refreshed between benchmarks, never inside one, whenever less than half is left, so only a single benchmark (setup included) longer than the ten-minute floor could outlive its lease. SIGINT and SIGTERM delete the file before the process dies, so Ctrl+C on a session does not leave the GPU spoken for; a crash does, until the lease runs out. A lock that is already this process's (a wrapper took it, and is still refreshing it) is used as it is and left for the wrapper to release. A GPU device the benchmark opens finds the harness's own lock and leaves it alone ([gpu_lock](gpu_lock.md)). A machine whose lock directory does not exist (a CI runner, a laptop) runs without it and says so. `tools/dev.ps1 bench -GpuLock` takes it **per executable** rather than once around all of them: each module's run holds it for exactly what it measures, and another agent waiting for the card gets it between two modules instead of after all of them.

**Reading results.** Trust one machine's numbers for layout and traversal decisions; do not use them to choose cross-machine defaults (11 §11.8). Compare medians; treat a spread above a few percent as noise to investigate (background load, frequency scaling) before believing a difference — and read the run's `machine_state` first, because on a shared machine background load is the common answer. Benchmarks run in release builds; debug numbers are for smoke only.

## The frame's GPU metrics, by pass

**What the frame records cannot say is why a pass is slow** (roadmap R219, 2026-11-24; [where the frame waits on the card](../experiments/frame-waits-on-the-card.md)). A pass's `gpu_ms` is its two timestamps; whether its warps waited on memory, on ray traversal or on nothing in flight is the device's performance counters', which on this machine only an elevated process may read. `nvidia-smi dmon -s pucvmt` needs no rights and gives the card's power, its SM-busy figure (the time any kernel runs, not how full the SMs are), the memory controller and PCIe once a second, so it is logged beside an agent's flights and read against them; the split by pass needs Nsight Systems' GPU metrics and the render graph's pass labels (`renderer.graph.labels`, [gfx](gfx.md), "Render graph v0") in one capture.

**The pass labels** (`domain/gfx`, `render_graph.h`). `RenderGraph::set_labels` makes `execute` open a `VK_EXT_debug_utils` command-buffer label named as the pass before its barriers and close it after its body, so a Vulkan capture splits the frame by the graph's own passes (Nsight Systems shows the labels on the CPU and the GPU rows); `stats().labels` counts the labels the last `execute` recorded. It needs the instance extension, which the device enables wherever the loader has it under `DeviceOptions::debug_messenger` (the default) and reports as `DeviceFeatures::debug_labels`; the renderer sets it each frame from `renderer.graph.labels` (false) and that feature, so off it is one test of a bool a pass and records nothing. `render_graph_tests.cpp` ("pass labels, one a pass, and none when off") holds the count to the passes with it on (none on a device without the extension), none with it off, and the words read back the same either way. Vulkan stays confined: the labels are recorded inside `domain/gfx` and named by the passes' own strings.

**`tools/gpu-pass-metrics.ps1` is that capture, and only the owner runs it, once, elevated.** Its first lines say it and so does this page: **never open the driver's counters to all users** to avoid the elevation (the control panel's switch, or its registry key) — on 2026-11-24 it reset the owner's display driver about fifty times and did not stay set. `record` checks that it runs as administrator and stops otherwise, takes the GPU lock, and flies engine-view offscreen along a named camera path under `nsys profile --trace=vulkan --vulkan-gpu-workload=individual --gpu-metrics-devices=0` (the device's default metric set, or `-MetricSet`; 2 kHz, the rate of the owner's first metrics run, so a minute is about two million rows to join) after `-Delay` seconds of load for `-Duration` seconds, with the labels on and the engine's own frame records beside (`frames.jsonl`). `read` needs no rights and no device: it exports the report with Nsight's own `nsys export --type jsonlines` and `nsys stats --report vulkan_gpu_marker_sum`, finds the metric samples, their names, the string table and the labels' GPU rows by their columns, joins every sample to the pass ranges that hold it by time, and prints per pass its share of the labelled GPU time and the median and 90th percentile of SM issue, warps in flight, unallocated warps, SMs active and DRAM read and write. PowerShell and Nsight's own commands only: the repository takes no Python.

**What the join rests on.** GPU metrics are samples of the whole device that know no process or pass, so a pass's figure is the average of the samples inside its GPU range, and a pass shorter than the sample period gets few: the sample count is printed beside it. Passes the graph lets overlap give a sample to each; `-Serialize` records the serialized frame (`renderer.graph.serialize`) so none overlap, at the cost of the overlap. NVIDIA's own forum has reports, as late as Nsight Systems 2026.3.1, of GPU label ranges that overlap or end early around ray-tracing work, so `read` prints the engine's own `gpu_ms` from the same flight beside the labels' times; a pass whose two disagree is not read for its metrics. The jsonlines export's table and column names were not seen when the script was written (no agent can make a capture with metrics): where `read` does not find what the join needs it lists every table with its columns and names what is missing, which is the one thing to fix in the script. The join itself is held on a synthetic export (`-JsonlOnly` reads a `profile.jsonl` and runs no Nsight command): two labels and twenty sample times give each pass exactly its own samples, a range is start-inclusive and end-exclusive, a label row with no GPU is left out, and an export with none of the tables lists what it holds and exits 3.
## Frame budgets

ADR-0018 makes frame budgets merge gates "from Phase 1", and until 2026-10-07 nothing held one (roadmap T46). The smallest form that holds is three pieces, and the harness above is not one of them: a frame is measured along a camera path by `engine-view --benchmark`, whose summary already carries per-pass GPU milliseconds at the median and p99 and the machine's state in this page's shape.

- **The budget file**, `content/budgets/frame-budgets.json` (`engine.frame-budgets.v2`; v1, which held one budget a run, was retired by T161): one machine — `machine.device`, the adapter's name as the driver gives it and the summary's `device` repeats ("NVIDIA GeForce RTX 5090", the desktop) — the tolerance, and a list of runs. A run is a path scene, its camera path, a resolution and views, its repeats, warm-up and flags, optionally a `prepare` command (a program of the preset's `bin/` and its arguments, run from the repository root before the lock is taken, for a scene that names files the tree does not commit: the static world's kit, `["engine-content", "static-kit", "content/test-scenes/static-world/kit"]`, roadmap T130; a prepare that fails fails the run), and **a budget per Windows session state**, `budgets.locked` and `budgets.unlocked`, side by side (either may be absent; see "Which session a budget holds" below). Each holds, for each GPU pass it budgets (`gpu_ms.<pass>`, the summary's names: `total`, `cull`, `hw`, `resolve`, `rt`, `shadow`, ...) and for the frame thread's `cpu_ms`, a `median` and a `p99` in milliseconds; and a `baseline` — the date, who, why, the commit, the device, the `session` it was flown in and the machine's state of the numbers — with `sources` saying, line by line, where each number came from.
- **A budget is a native measurement** ([ADR-0064](../adr/0064-every-measurement-is-native.md)): the gate refuses a summary whose `reconstruction` block names a provider or an internal size below the output's, whose times are under `reconstructed`, or whose `gpu_ms` is null, before it reads a number of it, with **exit 5** (which wins over every other code: nothing of such a gate is a verdict), and `-Rebaseline` never takes one. A summary written before the block existed is native. `Get-ReconstructionRefusal` in `tools/lib/FrameBudget.psm1` is the one rule, `tools/flythrough.ps1` asks it too, and `tools/frame-budget.Tests.ps1` holds both scripts to it over summaries written there.
- **The gate**, `tools/frame-budget.ps1`: per run it takes the GPU lock (one hold per run, as `dev.ps1 bench -GpuLock` holds one per executable), runs `engine-view --offscreen --benchmark` with `--wait-quiet` (600 s by default) inside the hold, releases it, and compares. A number is **over** when it passes `budget × (1 + pct/100) + ms`. **The tolerance**: GPU medians +10% and +0.05 ms, GPU p99s +20% and +0.4 ms (0.1 ms until 2026-10-12: a desktop that is also someone's workstation spikes a sub-millisecond pass's tail by half again on one quiet flight in three, measured on main's own binary while gating batch 16, so a tail gate tighter than that fails merges for nothing the engine did; the medians keep gating what the renderer draws), the frame thread's `cpu_ms` +25% +0.1 ms at the median and +50% +0.5 ms at the p99. The percentages are what one binary moves between two runs on this machine (the endless desert's `csm` total read 4.045 and 4.108 ms in two runs of the same build, the erg's p99 1.516 and 1.614: [world positions](../experiments/world-positions-renderer-2026-10-05.md)); the absolute parts are for the passes that cost hundredths of a millisecond, where a timer's jitter is the whole difference; the CPU's are wider because a build beside the run moves the frame thread's time and not the GPU's. **The verdicts**: within budget passes, whatever the machine was doing — an upper bound under the limit is under it; over on a quiet machine **fails** (exit 1) naming the pass, the statistic, the number and the limit; over on a busy machine is **inconclusive** (exit 4, run it again); another adapter's run is skipped (exit 3), and so is a machine whose `nvidia-smi` names another adapter, before anything is flown; a run flown in a session state it holds no budget for is **compared with nothing** (verdict `nobaseline`, exit **6**, inconclusive), and the line says which states the run does hold and how to take the missing one, and so is a flight whose summary records no session state or records it locked at one end and unlocked at the other (verdict `session`: it measured two cards). Exit 6 ranks below a failure (1) and a refusal (5) and above a busy over (4). A summary missing a budgeted pass fails: a pass that stopped being timed is not a pass that got cheaper. The `.jsonl` per run, `report.md` and `report.json` go in `build/<preset>/frame-budget/<time>/` for a flight by hand (and a `-Rebaseline`), or in the directory `-Out <dir>` names: a gate's flights since T220 go in its `-Logs`, as `<Logs>/<batch>-budgets-1` and, for the busy runs flown again, `-budgets-2` ([the gate](../ci/gate.md)), so a gate's records from 2026-11-24 on are there and no longer under the gate worktree's `build/`; `-FromSummaries <dir>` compares a directory of them again without flying anything. **A flight draws with no material pack** (T103): the gate sets `ENGINE_DEFAULT_MATERIALS=0` for its engine-view, so a budget is a function of the tree and never of whether the checkout has fetched or generated a pack, and a summary whose `load.materials` names one fails ([materials](materials.md), "Where the hosts find it"). Until T103 the flights passed no `--ddc`, so they looked the repository's pack up; none of the budget scenes has a generated mesh that falls back to one (the overlook's meshes are glTF samples with their own maps, the erg's and the endless desert's the dune terrain), so nothing drawn and no budget moved.
- **The re-baseline**, `tools/frame-budget.ps1 -Rebaseline -Reason "<why>" [-By <who>] [-Run <id>]`: the run's numbers replace its budget **for the session state it was flown in**, every pass it timed, and that set's `baseline` records who (`-By`, default the git user), when, why, the commit (marked when the tree had uncommitted changes), the device, the session and the machine's state; the other state's set is left as it was, so the two are taken on different days by whoever is at the machine in each state. It refuses no reason, refuses a run measured on a busy machine unless `-AllowBusy`, because a busy number is an upper bound and would loosen the budget, and refuses a flight whose session state is unknown or changed during it. The old numbers stay in the file's git history; the commit that moves them says why, as a size-table change does. `tools/frame-budget.Tests.ps1` holds every rule here with the session's state injected into the summaries it writes, since the harness reads the real one from the machine.

**The frame thread's two modes** (T221, 2026-11-24). Every run's `cpu_ms` on this machine is two-moded: most frames in a fast mode and a share of them in a slow mode 2.3 to 3 times dearer, **every section of the frame by the same factor** (`begin`, `passes`, `compile`, `record` and `submit` each 2.0 to 2.8 times their fast-mode median), in stretches of one to a few dozen frames, a median 4 to 36 frames apart. So the slow mode is not a path in the frame and not the sound, and keeping the frame thread on one CPU removes it, which points at the thread's moves between cores; what in a core does it (its clock, its idle state, its caches) is not shown, the second pinned flight flew beside a busier machine, which by the correlation lowers the share by itself, and one clean pair a side carries the removal. **The frame thread pinned** (T221, 2026-11-24). `tools/frame-budget.ps1` takes the slow mode out of what it measures, not out of the judge: every flight's frame thread is pinned to one logical CPU from outside the process (`-FrameCpu`, default `auto`), and the whole median is judged as before. **Which thread, and when**: engine-view's offscreen flight runs its frames on the process's main thread (`main` calls `run_offscreen`, and the only threads it starts are a load's and the device-loss watchdog's), which is the process's first thread; the tool starts engine-view as a process it holds, finds that thread by its start time, and pins it with `SetThreadAffinityMask` at once, before the scene loads and so before the warm-up and the first measured frame. The loader's, the drivers' and every other thread stay free. Every two seconds of the flight it sets the same mask again, which returns the mask the thread had, so a look that finds another says the pin did not hold. **A pin that cannot be applied, or does not hold, makes the run inconclusive** (`busy`, exit 4, flown again by the gate as a busy run is), unless the run is already over on a quiet machine, which a free flight is too: it never flies free silently. The run's line and `report.json`'s `Pin` record the CPU, the thread and the looks (`frame thread pinned to CPU 4, held (29 looks)`). **Which CPU**: the first logical CPU of the third physical core, from the machine's own counts (`Win32_Processor`), Windows numbering a core's hyperthreads side by side, or the last core of a machine with fewer than three: core 0 takes the system's interrupts and deferred calls by default and core 1 is its neighbour, and the third core is where the experiment above pinned (logical CPU 4 of 36 here). `-FrameCpu <n>` names another and `-FrameCpu free` flies the thread free, for a person measuring; off Windows `auto` is free. **What a busy sibling does**: a loop on the pinned core's other hyperthread made every frame 1.4 times slower (above). One busy logical CPU is 2.8 % of this machine's 36, under the quiet check's 10 % of others' CPU, so the flight reads **quiet**, not `busy`, and is judged. On the smallest `cpu_ms` budget in `content/budgets/` (the overlook locked, 0.07 ms, limit 0.07 × 1.25 + 0.1 = 0.1875) 1.4 times is 0.098 ms, far inside; on the largest (the endless walk at three screens unlocked, 0.547 ms, limit 0.784) it is 0.766 ms, inside by 0.018 ms, so a sibling kept busy for a whole flight spends nearly all of that run's tolerance and a regression of 2.4 % more would be red for it. A row that meets a pinned red on a quiet machine flies that run once with `-FrameCpu free` before reading it as the code. **The baselines were flown free and do not move here**: they carry that flight's slow share in their median (the overlook's unlocked 0.091 ms against that flight's fast mode of 0.089, so its limit is about 1.2 % looser than a pinned flight's would be) and in their p99 (the overlook's 0.341 ms, in the slow mode). A rebaseline flown pinned on a quiet machine would take both out; it is the owner's decision and is proposed as a row, not taken.

**Other programs' share of the GPU through a flight** (T230, 2026-11-25; **sampled on request, reported, decides nothing**). The summary's `machine_state` is two looks, one at each end, and batch 75's follow-up gate flew `endless-surround3-rt` over three p99 lines (the cluster build 1.021, the top-level build 0.807, the trace 1.538 ms against 0.839, 0.653 and 1.274) with its medians on the baseline, on a machine those looks called quiet, while 4 to 5 % of the GPU was in the desktop's other programs' hands; batch 74's binary flown beside it showed the same tail, and batch 74's own gate flight, the desktop idle, none. **A locked session is a slower card (batch 66 gate, 2026-11-16).** `endless-1080p-csm` flown with the Windows session locked reads every GPU zone 2 to 9 times what the same source reads with it unlocked, on a quiet machine both times: the total 2.84 against 1.13 ms, the cull 0.376 against 0.042, the resolve 0.545 against 0.213, the deform 0.124 against 0.022. The summary's `machine_state.session_locked` says which state a flight had; `quiet` does not look at it. The engine is not the cause; the card's clocks are: unlocked, the owner's displays hold it in P0 with its memory clock at 14,001 MHz however little it draws (`nvidia-smi` during a flight at 10% load), and with them asleep a light frame — about a millisecond of GPU work in each paced 16 ms — lets it idle down between frames, which costs a pass by the bytes it reads from memory far more than by its arithmetic (inferred from which zones moved most: no clock sample was taken locked). The gate flies with the session locked (every gate run of `endless-1080p-csm` from 2026-11-14 on), and a cull budget of 0.296 ms is a locked number, so the budgets hold a change to that state: a change that trades a chain of cached loads for bytes from memory can win unlocked and lose there (W6: [renderer](renderer.md), "Where the table costs more than the search: a card at idle clocks"). **Read `session_locked` beside `quiet` before comparing two flights, and never pair a locked run with an unlocked one.** Since T161 `tools/frame-budget.ps1` holds a flight only to the budget of its own state (below). The heavy runs barely move: replayed through the gate's rules, the same day's locked and unlocked gate flights read `erg-walk-surround3-rt` at 3.80 and 3.99 ms and `endless-surround3-rt` at 4.34 and 4.48, because a frame of several milliseconds keeps the card at its clocks either way; it is the light runs, a millisecond or less in a paced frame, that a locked session slows.

**Which session a budget holds, and which one a player is in (T161, 2026-11-16).** A player's machine is **unlocked**: somebody is in front of it with the displays on, the game is the foreground program, and the card holds the clocks a game's load keeps it at. No player plays with the lock screen up, so a locked flight measures a card nobody has — its light passes paying for memory clocks that idle between frames — and only the unlocked budgets say what a player's frame costs. The locked budgets are kept beside them for one reason: the gate often runs unattended, overnight, with the session locked, and a locked flight compared with nothing would leave a night's merges ungated, while a locked flight compared with unlocked numbers would fail every light run for the card's clocks rather than for anything the engine did. So each state is held to its own numbers: a change that costs the locked card (bytes from memory where cached loads were, as W6 did) still fails a locked gate, and an unlocked gate measures the player's card. **When the two disagree, the unlocked verdict is the one that speaks for a player**; a locked over with an unlocked pass is a cost to a card at idle clocks, worth a row but not a reason to hold a merge on its own. The numbers in the file on 2026-11-16 recorded no state; T161 filed every one of them as `locked` without a new flight, with a `session_note` saying why (every gate from 2026-11-14 flew them locked and passed, and the light runs' unlocked readings are a half to a ninth of them; `endless-1080p-csm` was seeded at a 1.625 ms total on 2026-10-07 and re-seeded at 3.161 on 2026-10-12 as "measured drift", which is the ratio a locked session gives, so that drift was most likely the session, though neither flight recorded it), and took no unlocked set: those are taken by a gate flown with the session unlocked, `tools/frame-budget.ps1 -Rebaseline -Reason "..."`, which writes `budgets.unlocked` and leaves `budgets.locked` alone. Until then an unlocked gate exits 6 on every run, saying so.

**Performance notes.** The harness's own overhead per iteration is one branch and one counter increment; timing is read only at the start and end of a repeat. Benchmarks with sub-nanosecond bodies measure the loop; give them real work per iteration.
