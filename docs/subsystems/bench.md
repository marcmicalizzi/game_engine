# bench (foundation)

**Purpose.** The micro-benchmark harness (ADR-0011; docs/plan/11-performance-principles.md §11.8): registration, calibrated timing, statistics, tunable sweeps, and reports as a table and as JSON lines, so "is this faster?" is a command. Every module keeps its benchmarks in `bench/` and `engine_module_bench()` builds one executable per module with `run_main` as its entry point.

**Model.**
- `ENGINE_BENCH(ident, "module.topic.case")` and `ENGINE_BENCH_ARGS(ident, name, 16, 256, ...)` define and register a body. The body sets up outside the loop, runs `while (state.keep_running()) { ... bench::keep(result); }`, and reports `state.set_items()` / `set_bytes()` per iteration for rate columns. `pause_timing`/`resume_timing` exclude setup inside the loop. `bench::keep` forces a value to be materialized so the optimizer keeps the work that produced it.
- The runner calibrates an iteration count that fills `min_time_ns` (default 100 ms), runs `warmup_repeats`, then `repeats` (default 7) timed repeats of that count, and reports the per-iteration median, minimum, maximum, mean, and standard deviation. `--smoke` runs one iteration once, for CTest. A fixture built once for a whole bench file (a corpus, a world) sizes itself from `bench::smoke_mode()`, so the smoke run stays seconds long in release builds too.
- `--sweep=<tunable>=<v1;v2;...>` runs every matching benchmark once per value and prints a relative column against the first value, then restores the original; `--set=<tunable=value,...>` applies overrides for the run. This is how a tunable's effect is measured (experiment E3's input).
- Output: a table on stdout and, with `--json=<path>`, one JSON object per result appended after a header line carrying the CPU brand, logical CPU and cache-domain counts, build configuration, and time. `tools/dev.ps1 bench` runs every bench executable and writes `build/<preset>/bench/<module>.jsonl`.
- The runner pins itself to the first performance CPU and raises its priority unless `--no-pin`. **A thread started after that inherits the pin**, so a bench's own `jobs::JobSystem` must pin its workers (`JobSystemConfig::pin_threads`, the default) or they all share the runner's one CPU: `terrain_bench.cpp`'s pool was made with `pin_threads = false` and its `terrain.field.reevaluate` and `terrain.ring.*` numbers were one core's until 2026-09-27 — user time equal to wall time is the sign ([the experiment](../experiments/time-lapse-smoothness-2026-09-27.md#c-evaluation)).

- A filter may name **one variant** of an `ENGINE_BENCH_ARGS` registration the way `--list` prints it: `--filter=physics.e19.tick/216010081`, `--filter=test.bench.args/*`, or `--filter=*/4` for every registration's four-worker variant. Everything before the first `/` selects the registration and the whole pattern selects the variant; a filter with no `/` behaves as it always did and runs every variant of what it matched. This exists for the shared machine below: the length of a run is the length of the window that has to stay quiet, and reaching one row of a fifty-row registration used to mean running all fifty.

**Invariants (tested).** Smoke mode touches every matching benchmark exactly once; measured mode calls the body at least once for calibration, once per warmup, and once per repeat; sweeps set each value in order and restore the original even when a value is rejected; the JSON file holds one header and one object per result; filters accept `*` globs and plain substrings, and a filter carrying a `/` selects variants rather than registrations; a measured run samples the machine once before and once after itself and a smoke run samples it not at all; a GPU lock that is absent, this process's own, or expired is quiet, and one somebody else holds (another tool, another engine agent under the same owner label, a person's even when expired, a file still being written) is not; `--gpu-lock` holds the lock while the benchmarks run and releases it after, gives up with exit 4 on somebody else's lock, breaks an expired one, never breaks a person's, and a release never deletes a lock it did not write.

## Measuring on a shared machine

The development machine is not an idle benchmark rig. It runs GPU diffusion jobs that hold the whole card and most of its memory for minutes at a time, and several agents compile and test on it at once. A number taken beside those is an **upper bound** on the cost, not the cost — and the numbers that decided the first budgets were taken with no record of what else was running, so nobody can tell which of them were. The harness therefore records the machine's state around every measured run, says when it was busy, and can refuse to measure or wait.

**What is recorded**, at the start and at the end of a run (`foundation/bench/machine_state.h`):

| Field | Where it comes from | Absent when |
|---|---|---|
| `cpu_total_pct`, `cpu_own_pct`, `cpu_others_pct` | `GetSystemTimes` + `GetProcessTimes` on Windows, `/proc/stat` + `/proc/self/stat` on Linux, over a 250 ms window; "others" is total minus own, clamped at zero | the counters could not be read |
| `gpu_util_pct`, `gpu_memory_used_mib`, `gpu_memory_total_mib` | `nvidia-smi --query-gpu=...` when it is on PATH | no such tool: an AMD or Intel box, or a CI runner |
| `session_locked` | a `LogonUI.exe` process exists (Windows) | anywhere else — reported as `null`, never as "unlocked" |
| `gpu_lock` | the machine-wide GPU lock file (see "The GPU lock" below): `owner`, `purpose`, `expires` as its holder wrote them, plus `mine` and `expired` | there is no lock file — reported as `null`, which is also what a machine that does not use the lock reports |

**No process names, no command lines, no user names leave the sampler**, on purpose: the question is how loaded the box is, and the answer does not need to say by whom. The session check walks the process list for one name and keeps a boolean. The one exception is the GPU lock's `owner` and `purpose`, and it is not really one: the holder wrote them into a file every tool on the machine reads, precisely so that whoever is waiting can see who has the GPU and why, and a report that says "the GPU was spoken for" without saying by what leaves its reader to guess which numbers to distrust.

`nvidia-smi` rather than NVML because the engine takes no new dependency for a measurement convenience ([08 §8.6](../plan/08-toolchain.md)) and the utility is already installed wherever the driver is; a machine without it reports nulls and everything else still works. The first GPU's line is the one read.

**The thresholds, and why those.** A run is *quiet* when other processes used no more than **10%** of the CPU and the GPU was no more than **20%** busy. Both are deliberately loose. An otherwise idle Windows desktop with a browser, a shell, an editor and the usual services sits at a few percent of 36 logical CPUs, and a desktop compositor driving three monitors keeps the GPU in the low teens, so a tighter bound would fire on a machine nobody is using and the flags would be ignored within a week. They are also loose enough to be *meaningful* in the other direction: one parallel `cmake --build` on this box is 40–90% of the CPU and a diffusion job is 100% of the GPU, so the things that actually move a benchmark are far above the line rather than near it. `--quiet-cpu=<pct>` and `--quiet-gpu=<pct>` move them when a particular measurement needs a stricter or looser rule; say in the write-up when you moved them.

**A GPU lock held by somebody else is not quiet**, whatever the utilization sample says. A sample is a quarter of a second; a render between frames, a bake loading its scene, or an image job about to start all read as an idle GPU for that long, and the lock is the holder saying in advance that the card is spoken for. A lock that is this run's own — taken with `--gpu-lock`, or by a wrapper on its behalf — does not count against it, and neither does an expired one, except a person's (`owner` `"marc"`), which the protocol says no tool may treat as gone.

An **unknown** field can never make a machine noisy. A box with no GPU reading is quiet as far as its GPU is concerned, because a rule that refused to measure on missing information would make `--require-quiet` useless on Linux CI and on every non-NVIDIA machine.

**What the flags do.**

```powershell
build/msvc-release/domain/sim/engine_sim_bench.exe --filter=sim.wheel.* --require-quiet
build/msvc-release/domain/sim/engine_sim_bench.exe --filter=sim.wheel.* --wait-quiet=7200
build/msvc-release/domain/sim/engine_sim_bench.exe --filter=sim.wheel.* --gpu-lock --require-quiet
tools/dev.ps1 bench -Preset msvc-release -Filter "sim.wheel.*" -GpuLock
```

- `--require-quiet` measures nothing on a busy machine: it prints the state and exits **4**, which is a code of its own so a script can tell "come back later" from "this run failed" (2) and from a real failure.
- `--gpu-lock[=<max wait s>]` takes the machine-wide GPU lock for the run: it waits for it (default up to four hours, the PowerShell tool's bound, saying whom it waits for), holds it from before the first sample to after the last, and releases it however the run ends. Giving up is exit **4** as well. It comes *first*: the lock is the queue, so a run waits its turn and then asks whether the machine is quiet, holding the GPU while it asks. `tools/dev.ps1 bench -GpuLock` passes it to every bench executable. Details under "The GPU lock" below.
- `--wait-quiet=<seconds>` looks every 5 seconds until the machine is quiet or the deadline passes, then runs either way and says on stderr which of the two happened and how long it waited. It never sleeps past the deadline. This is the flag to reach for before a session of measurements: start it, let the diffusion job finish, and the numbers come from the other side of it.
- `--smoke` does none of these, and does not sample or take the lock at all. A smoke run answers "does this benchmark run", CTest runs one per module, and a quarter of a second plus a process spawn per module would buy nothing there. Its JSON header says `"machine_state": null` rather than reporting a state it did not take.

**What a WARNING means for a write-up.** When either threshold was crossed at either end of a run, or somebody else held the GPU lock, the table gets one line under it (on stderr when `--quiet` suppressed the table):

```
WARNING: other processes used 20.5% of the CPU and the GPU was 100% busy; these numbers are
upper bounds (cpu 20.6% (others 20.5%, own 0.2%), gpu 100% util 24864/32607 MiB, session unlocked,
gpu lock free)
WARNING: the GPU lock was held by 'astra-blender' (bake: desert), other processes used 1.2% of the
CPU and the GPU was 4% busy; these numbers are upper bounds (...)
```

It does not mean the numbers are wrong; it means they are **upper bounds** and that a quiet run would be the same or faster. A write-up may use them — sometimes the loaded case is the interesting one — but it has to say so: an experiment page that quotes a number from a warned run and does not carry a "Machine state" line is the failure this whole feature exists to prevent (see [docs/experiments/README.md](../experiments/README.md), and AGENTS.md's "Rules that are reviewed"). A *ratio* between two benchmarks measured in the same warned run survives far better than either absolute number, because both paid the same tax; a comparison against a number from another day does not survive at all.

**In the JSON.** The header line gains `machine_state` with a `start` and an `end` object of the fields above, each field `null` where it is unknown (`gpu_lock` is `null` or `{"owner", "purpose", "expires", "mine", "expired"}`), and every result line gains `worst_others_cpu_pct` — the worst "others" CPU either sample saw — so that one line out of a `.jsonl` carries its own caveat without the reader having to find the header. The end sample only exists once the last benchmark has finished, which is why the whole file is written when the run ends rather than streamed: a run killed part way leaves no JSON, and its numbers were taken under whatever killed it anyway.

**What two samples cannot see, and what to do about it.** Load that starts *and* ends inside a run is invisible to a check at its two ends. Measured on 2026-09-18 while re-taking the numbers below, that is not hypothetical: one `store.projections.range_by_tile` run began at 3.2% others and ended at 86.3%, and its medians came back 2.1× and 1.8× the documented ones — the WARNING caught it because the load was still there at the end, and a build that had finished a second earlier would have been missed. So the rule for a run whose numbers will be quoted is **`--require-quiet` plus a repeat**: two runs that agree to a percent were almost certainly both quiet, and two that disagree tell you to look. Per-benchmark sampling would close the gap and is not free — a 250 ms window per benchmark is a third of the cost of the seven repeats it qualifies — so it is a deliberate gap, not an oversight. Running one bench executable at a time, rather than `tools/dev.ps1 bench` over all of them, also keeps the window a run covers short enough to mean something — and so does naming the one variant you want (`--filter=physics.e19.tick/216010081`) rather than the registration it belongs to. Measured while taking [ADR-0031](../adr/0031-minimum-cpu-x86-64-v3.md)'s numbers on this box: a two-minute `physics.step.*` run was warned-on three times in a row because somebody else's build started inside it, and the same rows taken as three runs of fifteen seconds each came back clean on the first or second try. **Make the run shorter before making the machine quieter.**

**The GPU lock.** Quiet is not only a property of the machine but of who else is using it, and this GPU is shared with other agents that never see this harness (as of 2026-09-22, a ChatGPT agent working in Blender on the same card). So anything heavy on the GPU takes the machine-wide lock first: `tools/gpu-lock.ps1 run -Purpose "<what>" -Exec "<command line>"` waits for the GPU, runs the command, and releases in a `finally`; `acquire`/`release`/`refresh`/`status` are the pieces. The lock is one JSON file created atomically with an owner, a purpose, and an expiry, at `$env:ENGINE_GPU_LOCK` or by default `D:\workspace\gpu.lock` on Windows and `/tmp/gpu.lock` elsewhere; its format and rules are written once, for every tool on the machine in whatever language, in `D:\workspace\GPU-LOCK.md`: an expired lock may be broken, an unexpired one never, a lock owned by a person never by a tool. *Heavy* means more than about 4 GB of VRAM or more than a minute of GPU time: image generation, image-to-3D, Blender bakes and renders, GPU benchmarks and measurements whose numbers get recorded. A single short capture does not take it; a measurement taken while someone else holds it is an upper bound, and `--require-quiet` refuses it.

**Tests take it themselves, per device** ([gpu_lock](gpu_lock.md), [ADR-0049](../adr/0049-tests-take-the-gpu-lock-per-device.md)). A test executable, and every process it starts, takes the lock in `gfx::Device::create` for exactly as long as a GPU device is open, so a suite holds the GPU while it uses it and not while it checks documents, builds content or steps physics; nobody wraps `tools/dev.ps1 test` in `gpu-lock.ps1 run` any more (it still works, and holds the GPU for the whole run again). The owner's own sessions never take it: only the test main turns the switch on.

There are two implementations of the protocol and no more: `tools/lib/MachineLock.psm1` for every PowerShell tool (`gpu-lock.ps1`, `tools/ci/gpu-smoke.ps1`, `tools/ci/reference-compare.ps1`, and the Linux container build's own lock in `tools/linux-build.ps1`), and `foundation/gpu_lock` for C++ — this harness's `--gpu-lock` and device creation's hold — which cannot import a PowerShell module. (It was this module's `gpu_lock.h` until device creation needed it too; a renderer should not link a benchmark runner to open a device, so it moved.) Both refresh by writing beside the file and renaming over it, never by rewriting in place (a reader that caught a half-written file used to judge it expired and delete a live lock); both treat an unreadable file as mid-write until it is a minute old; both break an expired lock by moving it aside and deleting it only if it is still the file they judged, so two waiters cannot both break it and then share the GPU; and both release only the file they wrote — owner, pid and start time — because every engine agent is `claude-engine`.

**Whose lock is "mine".** Not the owner label's: every engine agent writes `claude-engine`, so an owner match would let one agent's measurement run straight through another agent's render. A lock is this process's when its owner is this process's (`$env:ENGINE_GPU_LOCK_OWNER`, default `claude-engine`) and its `pid` is this process — the harness took it with `--gpu-lock`, or a device of this process did — or the process named by `ENGINE_GPU_LOCK_HOLDER`, which `gpu-lock.ps1 run`, `gpu-smoke.ps1`, `reference-compare.ps1` and a process holding the lock for its GPU device set to their own pid for everything they start while they hold it — the PowerShell ones with `ENGINE_GPU_LOCK_OWNER` set to the owner they hold under beside it, so a wrapper given `-Owner` is still its children's ([gpu_lock](gpu_lock.md)). So `tools/gpu-lock.ps1 run -Purpose "bench" -Exec "..."` and `--gpu-lock` both work with `--require-quiet`; a lock taken by a separate `gpu-lock.ps1 acquire` does not, because the process that took it has exited and nothing distinguishes it from another agent's, and `--require-quiet` says so when it refuses. A wrapper's lock that has **expired** is a wrapper that died, and `--gpu-lock` breaks it like anybody else's (since 2026-09-30; it used to be taken as this process's for as long as the file stayed).

**How `--gpu-lock` holds it.** The lease is sized from the run — the options' prediction of it (calibration, warmups and repeats at `min_time_ns`, for every variant and sweep value), doubled, at least ten minutes and at most an hour — so the `expires` a waiting agent reads of a long run is roughly when it will be done, and a crashed run blocks the machine for one lease and not for as long as it might have run. It is refreshed between benchmarks, never inside one, whenever less than half is left, so only a single benchmark (setup included) longer than the ten-minute floor could outlive its lease. SIGINT and SIGTERM delete the file before the process dies, so Ctrl+C on a session does not leave the GPU spoken for; a crash does, until the lease runs out. A lock that is already this process's (a wrapper took it, and is still refreshing it) is used as it is and left for the wrapper to release. A GPU device the benchmark opens finds the harness's own lock and leaves it alone ([gpu_lock](gpu_lock.md)). A machine whose lock directory does not exist (a CI runner, a laptop) runs without it and says so. `tools/dev.ps1 bench -GpuLock` takes it **per executable** rather than once around all of them: each module's run holds it for exactly what it measures, and another agent waiting for the card gets it between two modules instead of after all of them.

**Reading results.** Trust one machine's numbers for layout and traversal decisions; do not use them to choose cross-machine defaults (11 §11.8). Compare medians; treat a spread above a few percent as noise to investigate (background load, frequency scaling) before believing a difference — and read the run's `machine_state` first, because on a shared machine background load is the common answer. Benchmarks run in release builds; debug numbers are for smoke only.

**Public API.** `foundation/bench/bench.h`: `State`, `keep`, `clobber_memory`, `Registration`, `first_registration`, `glob_match`, `Stats`, `compute_stats`, `Options`, `Result`, `run`, `run_main`, `k_exit_not_quiet`; macros `ENGINE_BENCH`, `ENGINE_BENCH_ARGS`. `foundation/bench/machine_state.h`: `Tristate`, `MachineState`, `QuietThresholds`, `k_sample_window_ms`, `is_quiet`, `worst_of`, `describe`, `machine_state_json`, `warn_if_busy`, `MachineSampler`, `system_sampler`, `sample_machine_state` — the last three are the injection point, so a test drives the quiet and not-quiet paths with a fake instead of hoping the machine cooperates. The lock itself — `gpu_lock::State`, `Identity`, `read`, `Lease` and the rest — is `foundation/gpu_lock/gpu_lock.h` ([gpu_lock](gpu_lock.md)), and `MachineState::gpu_lock` is a `gpu_lock::State`; `Options::gpu_lock_path` is the other injection point, and a test that sets it has the run take and read its lock there instead of the machine's. CMake: `engine_module_bench(NAME <module> SOURCES <files> [DEPS ...])` in `cmake/EngineBench.cmake`; option `ENGINE_BUILD_BENCH`.

**Depends on.** `base`, `containers`, `json`, `platform`, `time`, `tunables`, `gpu_lock`.

**Testing.** `tools/dev.ps1 test -Filter bench` runs the harness tests and every module's smoke run (`bench.<module>`, label `bench`). The GPU-lock cases here (`tests/gpu_lock_tests.cpp`) are the harness's side — what a reading makes of the machine state, and what `--gpu-lock` does to a run — and write their lock files into their own `engine::test::TempDir`, so the machine's real lock, and whoever holds it while the suite runs, never reaches a result. The lock's own rules are tested in `foundation/gpu_lock` ([gpu_lock](gpu_lock.md)), and the PowerShell side of the protocol is `tools.machine_lock` (`tools/machine-lock.Tests.ps1`).

**Performance notes.** The harness's own overhead per iteration is one branch and one counter increment; timing is read only at the start and end of a repeat. Benchmarks with sub-nanosecond bodies measure the loop; give them real work per iteration.
