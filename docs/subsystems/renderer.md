# renderer (systems)

**Purpose.** The engine's renderer ([04](../plan/04-renderer.md), [02 §2.3](../plan/02-architecture.md#23-subsystem-boundaries-and-layering) L3): it turns a set of meshes and instances of them into a picture and into the numbers that describe how it was made. It owns the whole frame — source-mesh loading through the derived-data cache, the GPU-resident scene, two-pass GPU culling and LOD selection, the four rasterizers, the deformed-vertex pool, the per-frame cluster acceleration structures, the material resolve, the Hi-Z pyramid, the GPU timers, and the capture — and it does all of it **without a window**. `engine-view` is the command line over it and `engine-host`'s `render.*` methods are the protocol over it; neither is privileged, and a third consumer (the editor, a test, a benchmark harness) needs nothing new.

**Why it is a module and not an app.** Until this split every one of those passes lived in `apps/engine_view/main.cpp`, 2,654 lines of it, and the consequence was not that the file was long: it was that **nothing but engine-view could render**. The protocol had no `capture` and no `benchmark`, so the Phase 1 exit criterion ("agents can capture and benchmark", [10 §10.2](../plan/10-roadmap-risks.md#102-phases)) could not be met without either duplicating the frame in the host or driving a child process and reading its stdout. The renderer is the engine's own, in the same sense `gfx` is — not a capability a game adds ([ADR-0027](../adr/0027-additive-capabilities.md)) — so it is `engine_module(... LAYER systems)` with no `OPTIONAL`: a build without it could not draw at all, and every consumer of it would have to be switched off with it.

**The window is the app's.** `foundation/window` is not a dependency of this module, and nothing here touches a surface, a swapchain, or a present queue. A frame is recorded into a color image the caller names: engine-view acquires a swapchain image and hands it in with its two semaphores; engine-host renders into an offscreen target the renderer owns. That is the *only* difference between the two, which is why a picture captured through the protocol is the picture engine-view shows. `systems/renderer/tests/renderer_tests.cpp` opens with `#if __has_include(<foundation/window/window.h>) #error`, so the day the dependency comes back the build says so rather than a hosted CI run failing to open a display.

## Owned data

| Owner | What it is sized by | What it holds |
|---|---|---|
| `SceneDesc` | — | what to load: mesh paths, instances, the instance grid, the heightfield resolution, the derived-data root |
| `SceneData` | the content | one merged cluster LOD DAG, one `geometry::ClusterMeshPart` per mesh, each mesh's materials and images, the instance table, the bounding sphere, and the counts a summary reports |
| `GpuScene` | the **scene** | every device buffer whose size is a function of the scene: geometry behind device addresses, the material table and the bindless textures, the instance table, the deformed-vertex pool, the visible list and the indirect argument blocks, and the ray tracing chain |
| `ViewSet` | the **layout** | N views over one scene: each one's rectangle of the target, its orientation and frustum shape, its source extent, and its quality tier |
| `SceneRenderer` | the **screen** | the shader library and its pipelines, the visibility buffer and the Hi-Z pyramids, the frame context, the GPU timers, the render graph, the per-slot parameter blocks, and `Stats` |

That line — scene-sized against screen-sized — is also the order the two build in, and it is not arbitrary: the `gfx::MeshDesc` array names the deformed-vertex pool, the deform table, and this scene's cluster templates, so it is uploaded last, after every address it carries exists. A `GpuScene` therefore finishes itself; a `SceneRenderer` is created against a finished one.

## Invariants

- **A picture does not depend on which host drew it.** Every device- and scene-driven override lives in one function, `resolve_settings`, and nothing below it probes `gfx::DeviceFeatures` again. The order of the overrides is load-bearing and the function says so: the mesh-shader fallback decides which path runs, the path decides whether shadows can be traced, and shadows decide whether two-pass occlusion culling may run (the acceleration structures are built from one visible list, and pass 2's survivors are in a second one). Everything after that only ever forces a switch *on*.
- **What a summary reports is what ran**, not what was asked for: `ResolvedSettings::settings` carries the overrides, so a run whose `--raster hw` fell back to the vertex path says `"raster":"vertex"`.
- **The renderer never reads a buffer back inside a frame.** The visible-pair counts come from a per-slot copy of the indirect argument blocks, read one frame late; the GPU milliseconds come from `gfx::GpuTimer`, never from a CPU clock. The only blocking readbacks in the module are in `capture()`, which is not a frame path.
- Pass bodies are stored in the render graph's arena and capture by reference, so declaring, compiling, and executing a frame are **one function** (`record_frame`): every parameter block a body pushes has to still be alive when `execute()` records it.
- A capture's id buffer names the (instance, cluster, triangle) a pixel's visibility id led to, never the id itself — see below.
- **A view's cut does not depend on how many views there are beside it.** Every view culls, rasterizes and resolves against its own slices, and the only thing they share is the scene. The test that holds this is the one that renders a flat three-monitor surround at 3w × h and a single view at w × h from the same camera and requires the centre monitor to be *the same picture and the same ids, pixel for pixel* (see [Multi-view](#multi-view-a-viewset-over-one-scene)).

## The offscreen contract

```cpp
SceneData data;   load_scene(desc, data, error);
ResolvedSettings resolved;  resolve_settings(settings, device.features(), &data, resolved);
if (check_availability(resolved, device.features()) != RenderAvailability::Ok) { ... }
GpuScene scene;   scene.create(device, data, resolved, &error);
SceneRenderer r;  r.create(device, scene, resolved, {.width = w, .height = h}, &error);
```

`check_availability` is deliberately separate from `create`: a device that cannot render is not a caller's mistake, and the two hosts report it differently — engine-view exits 3 (which its tests treat as a skip) and engine-host answers protocol error 1007 (`RenderUnavailable`). It checks two things and not a third: 64-bit buffer atomics, without which nothing can write the visibility buffer, and cluster acceleration structures plus ray queries when the ray path was asked for. **Presentation is not checked**, because presenting is the window's requirement and not the renderer's.

One frame is `begin_frame()` (wait for the slot, fold in the completed frame's statistics and timings), then `submit_frame(FrameDesc)`, then — for a presented frame — the caller's present. `FrameDesc` names the color image, the layout to leave it in, and the two semaphores; a null image draws into the renderer's own offscreen target. `render_offscreen()` is the three calls plus the wait, and `capture()` is `render_offscreen` plus the readbacks. The pipelines are built for one color format (`Desc::color_format`), which engine-view sets to the swapchain's so the picture is produced exactly as it is presented; the offscreen default, `R8G8B8A8_UNORM`, differs from a typical swapchain's `B8G8R8A8_UNORM` only in channel order and so reads back byte for byte the same.

The camera is a plain struct, and `orbit_camera(center, radius, distance, frame)` is the orbit engine-view has always used — distances scale with the scene's radius, and a `distance` of zero breathes between 8 and 36 radius-tenths. `orbit_camera_at(center, radius, distance, yaw, pitch)` is the same orbit at explicit angles, where `pitch` is the elevation above the orbit circle; its default, `k_orbit_pitch` = atan(0.45), is engine-view's fixed height factor, so `--orbit 22` and `orbit {distance: 22}` are the same camera and the two hosts' captures of a scene compare directly.

## Multi-view: a `ViewSet` over one scene

[04 §4.6](../plan/04-renderer.md#46-extreme-displays) asks for multi-view rendering as a first-class concept: *N views sharing one scene, one culling hierarchy, one TLAS, one residency budget.* `systems/renderer/view_set.h` is that concept. `ViewSet::build` lays a `ViewLayout` — `single`, `surround3`, or `panini` — out over the color target and fixes everything the screen sizes; `ViewSet::update` turns one frame camera into N view-projection matrices. A `View` carries its rectangle of the target, its **source** extent (what the rasterizers run at, which is wider than the rectangle only for a Panini view), the yaw its camera is turned by, its frustum as tangents at unit distance, and its `ViewQuality` tier.

**What is shared and what is per view.**

| Shared by the set | Per view |
|---|---|
| the `GpuScene`: geometry, materials, textures, instances, the deformed-vertex pool | the cull params (frustum, Hi-Z, flags and prev_flags, LOD threshold) |
| one top-level acceleration structure, built from the **union** of the views' cuts | its run of the visible list, its indirect argument blocks |
| one CLAS set and one cluster bottom-level structure per instance | its region of the visibility buffer and its own Hi-Z pyramid |
| the eye position, the near plane, the lights, the residency budget | its viewport, its resolve, its ray dispatch, its statistics |

**Why the per-frame working set is slices of shared buffers and not a set per renderer.** The [Not yet](#not-yet) note this replaces said a second `SceneRenderer` on one `GpuScene` would need its own visible list, argument blocks and flags. Duplicating them per renderer was the wrong half of the choice. A visibility id is an *index into the visible list*, so if two views had two lists an id would be ambiguous and the resolve could not decode one without knowing which view wrote it; the ray tracing chain builds one set of structures from the union of the cuts, and a union is a contiguous range of one array rather than a gather over N; and §4.6 asks a `ViewSet` to share *one residency budget*, which one allocation that scales with the view count is and N allocations are not. So `GpuScene` takes the view count from `ResolvedSettings` and every per-frame buffer carries a slice per view.

**The id space.** The visible list is **run-major**: run *r* of view *v* starts at entry `(r * views + v) * pair_count` (`GpuScene::visible_base`). There are `k_visible_runs` = 3 runs — occlusion pass 1, pass 2, the software rasterizer — so the list is `3 * views * pair_count` entries, and a visibility id is unique across the whole frame. Run-major rather than view-major for one reason: it puts the **first** run of every view in one contiguous range at the front of the list, and that range is exactly what the ray tracing chain consumes, so `records_main` covers every view's cut in one dispatch reading each view's own count word out of its indirect block (`gfx::k_draw_args_bytes` apart). With one view the layout is the same three runs it has always been, at the same offsets.

The records chain widens by the same factor: an instance's slice of the bucketing scratch is `views` times its mesh's cluster count, because in the worst case every view draws every cluster of it, and `gfx::ClusterRecordParams::views` is what says so. The CLAS set is sized `views * pair_count` and its largest geometry index is `views * pair_count - 1`. **That is capacity, not traffic**: on a surround the views see nearly disjoint thirds of the world, so a frame builds about as many records as one view would while the allocation is three times it ([E9](../experiments/e9-multi-view.md) has the numbers).

**What each shader had to learn, and what it did not.** The rasterizers and `hiz_build.slang` learned *nothing*: a view's raster pass sets a viewport at the **origin** of its own source rectangle, so `SV_Position` is already view-local, its `visibility` address is its own region of the buffer, and its Hi-Z pyramid is built from that region and indexed from element zero. Only the resolve had to learn where it is — `ResolveParams::view_x`/`view_y` are the rectangle's origin, which it subtracts from `SV_Position` — because the resolve is the one pass that writes the shared color target. Every one of those fields is zero for a single view and the arithmetic reduces to what it was, which is why the single-view pictures are byte-identical before and after (verified on the FlightHelmet through `--raster hw`, `--raster vertex`, `--raster rt --shadows rt` and `--deform wave`: PSNR null, SSIM 1, FLIP 0 on all four).

**Surround3.** Three views over a target divided in three, with per-monitor off-axis frusta. The eye distance is the one that makes a monitor subtend the field of view; `Surround3::bezel` is bezel *correction* (the rectangles always tile the target, because a driver-surround surface has no pixels behind a bezel, so the gap widens the angle between the monitors instead); `side_yaw` turns the side monitors inward, which turns their cameras and reshapes their frusta. The centre monitor is centred whatever the arrangement, so it takes the symmetric projection rather than the off-axis one — deliberately, because that makes the centre view of a flat surround **bit-for-bit** the single view of one monitor, which is the identity the multi-view cull is tested against. At `side_yaw` 0 the three off-axis frusta are exactly the three thirds of one wide rectilinear frustum, so a flat surround and a single wide view are the same picture.

**Panini.** One view, rendered rectilinear into an oversampled source and resampled in the resolve. The source is the *same frustum* the single rectilinear view would have used, at a wider resolution: `(d + cos t) / ((d + 1) cos t)` times as wide at the half horizontal field of view, which is what it takes for the resample never to magnify (about 2× at d = 1 and 48:9). The resample happens **inside the resolve**, in the visibility domain: an output pixel maps back through the Panini inverse to a fractional source position, reads the visibility buffer there, and reconstructs its barycentrics at that same fractional point, so it stays sub-pixel accurate. That is the cheapest form — no intermediate color image, no second full-screen pass, no bindless slot for it — and it is the honest one, because a visibility id cannot be filtered anyway. Its cost is that the periphery, where the source is several times denser than the picture, is point-sampled and aliases; a filtered color-domain resample plus TAA is the fix and both are open ([E9](../experiments/e9-multi-view.md)). At d = 0 the Panini projection *is* the rectilinear one, and the picture comes back identical to the single view's (measured: not one pixel of 49,152 differs at 384 × 128).

**Foveation, as far as it goes.** `ViewQuality::lod_scale` multiplies the view's LOD pixel threshold, so `--peripheral-lod 4` lets a cluster be four times as wrong in screen space on the side monitors before its parent group is drawn instead. That is the whole of §4.6's foveation that is built. `ViewQuality::shading_rate` is **stubbed**: it is set, carried into the statistics and reported, and nothing consumes it — a real rate needs `VK_KHR_fragment_shading_rate` in the RHI and either a per-view rate attachment or `vkCmdSetFragmentShadingRateKHR` per draw, neither of which `domain/gfx` has. Per-view internal resolution, ray budget and effect cutoffs are not built either; the `View` carries a source extent per view, which is the seam a resolution scale would use.

**Per-view statistics, and what the milliseconds mean.** `Stats::views[v]` carries the view's rectangle, its tier, its visible pairs by draw, and its GPU milliseconds by pass; `Stats::view_ms(v)` divides. The acceleration structure chain is deliberately *not* attributed to a view: it is built once from the union and belongs to the frame. Each stage is one render-graph pass with a loop over the views inside it rather than a pass per view, because the views write disjoint slices of the same buffers and the graph tracks whole buffers — a pass per view would make it insert a barrier between views that have no hazard. The Hi-Z build is the exception: one dispatch of it folds six mips and the next one reads the last of those, so its dispatches must be barriered anyway, and the views' pyramids are therefore built one after another and a view's pyramid is one timer zone. **A zone's timestamps are written at ALL_COMMANDS on both ends, so timing the views separately orders them on the queue**: the per-view numbers are what each view costs alone, and the frame total measured this way is an upper bound on what the views would cost if the driver were free to overlap them.

**What multi-view does to ray tracing, which is the finding worth carrying.** One TLAS over the union of per-view *cuts* means two views that take different LOD levels of the same surface put both levels in one structure. With the peripheral LOD multiplier at 1 the views agree and nothing overlaps; at 2 and 4 they do not, and a ray from any view may hit the other's level. §4.6's "RT is view-agnostic" is the fix — one RT cut at a view-agnostic threshold rather than a union of the views' — and it is not built. A consequence of the same union: with more than one view a ray may name a pair through *another* view's entry, which resolves to the same (instance, cluster, triangle) and so is invisible to a capture, but means E2's word-for-word "ray-traced visibility matches the rasterized cut" invariant is a single-view statement.

## Skinned instances

E25 built the deformed-vertex pool and `deform.slang` grew a skinning kind; [animation](animation.md) produced the matrices as one contiguous span; nothing joined the two. This is the join, and it is deliberately small: **the renderer knows about bone matrices and knows nothing about clips.**

**What a caller says.** A `SceneInstance` names a joint count — `joints > 0` is what makes an instance skinned — and a bound on how far skinning moves its vertices (`bounds_padding`, below). `SceneDesc::max_joints` is the longest matrix span a frame will hand over, which is what the joint buffer is sized by; a longer one is clamped with one warning rather than overrunning it. Everything else is per frame: `FrameDesc::joints` is `std::span<const anim::JointMatrix>`, every animated instance's matrices in one run, and `FrameDesc::instance_joints` is one `{first, count}` per scene instance saying where each one's run is.

That is the whole interface, and it is spans rather than a system because **the renderer must not depend on `systems/animation`, on `domain/ecs`, or on flecs**. What it does depend on is `domain/anim`, for `anim::JointMatrix` alone — a domain module, not a capability, so the dependency cannot be switched off, and copying the 48-byte record here instead would be exactly the drift `domain/anim` took its own `geometry` dependency to avoid. The tick is the app's: `engine-view --animate` owns a world, steps it at the fixed rate, and hands over the span ([apps](apps.md), [animation](animation.md) has the pattern a game copies).

**An instance with no matrices this frame draws its rest pose.** A `count` of zero, or an instance the array does not reach, leaves `DeformDesc::joints` at zero, and `deform_skin` then writes the rest position into the pool. That is what an instance at animation LOD3 — no pool slot — looks like from here. The alternative, marking it `k_invalid_deform` for the frame, would mean rewriting the instance table mid-frame, which is a per-instance upload to save a pool write the cut had already paid for.

**The upload: one memcpy, and two deform tables.** `GpuScene` allocates a host-visible, persistently mapped joint buffer with `k_joint_slots` regions, one per frame in flight, so the host write never races a device read and needs no staging copy and no barrier; `SceneRenderer::create` refuses more frames in flight than there are regions rather than letting a character twitch one frame in ten. A frame copies the whole span into its slot's region with **one memcpy** and then walks the deform table once, rewriting the two words that change.

The two words are the problem that shapes the rest. `MeshDesc::deform` is baked into an array uploaded at create, and `scene.slang`'s `load_position` reads it on every position read of every rasterizer — for `pool_offset` alone, which never changes. Only `joints` and `joint_count` change per frame, and only `deform.slang` reads them, through a push constant. So the static table stays exactly what it was (device-local, written once, what a `--deform` run without skinning still uses) and the per-frame one is a **separate** host-visible buffer with a region per slot, whose address goes into `DeformParams::deform`. A skinned scene therefore has no host write racing a device read; a rigid one has no second table at all, and no allocation, and no changed instruction.

**Which instances get a pool block.** Every instance under `--deform`, and the skinned ones otherwise — so a scene of one character and a hundred props allocates blocks for the character and leaves every prop on the rigid path. `ResolvedSettings::deform_pass` is the one flag that says the pool pass runs, and `resolve_settings` is the one place it is decided, because skinning is a *kind* of `deform.slang` and not a second pass.

### Bounds: the cluster spheres are the rest pose's, and a skinned vertex is not in them

The cull pass tests an instance by its mesh's rest-pose cluster spheres. A skinned vertex is `sum_k w_k M_k p`, which is not in that sphere, so something has to give or a character's swinging limb is culled while it is on screen.

**The decision: one number per instance, computed at load, added to every sphere the cull pass tests.** `gfx::InstanceDesc::bounds_padding` took one of the record's two spare words — so the struct is still 96 bytes and is zero for every instance that existed before, which is why the pictures are byte-identical (a float plus zero is exact). `cluster_cull.slang` adds `bounds_padding * scale_max` to the cluster sphere's radius *and* to both LOD spheres.

Why that and not the alternative, per-frame bounds recomputed from the joint matrices: per-frame bounds are tighter and cost a pass over every cluster of every animated instance every frame, plus an upload of the result, to buy back a fraction of a frustum test that is already one sphere compare. The whole point of the cull pass's flat pair enumeration is that a pair costs a handful of compares; making each one depend on data recomputed that frame is the wrong trade at 1,000 instances, and at 10 it does not matter. A static bound is one `f32` in a record that already existed and nothing per frame at all.

**Why all three spheres and not only the culling one.** Adding it to the LOD spheres as well is what keeps the DAG cut crack-free: a cluster's `parent` sphere *is* its children's `own` sphere, so one constant added to every sphere of one instance leaves the projected errors in the same order and exactly one cluster per DAG path still passes. Add it to the culling sphere alone and the two would disagree at a group boundary. It also errs the right way for quality — a larger radius means a smaller distance, a larger projected error, and therefore a *finer* cut, which is what a limb swinging towards the camera wants.

**Where the number comes from.** `animation::clip_displacement_bound` ([animation](animation.md)) summarizes a clip once, at load: for each joint, and for a sphere of the vertices that joint actually influences, `|M p - p| <= |(A - I) c + t| + ||A - I|| r`, maximized over every keyframe time of every track plus a uniform grid. It is conservative for every vertex and any weights. Two things about it were measured rather than assumed. Bounding each joint by the *mesh's* sphere instead of by the vertices it influences asks how far the tail joint would move a vertex at the nose: on the Khronos Fox that is a padding of 249 units on a mesh of radius 82, and the framing camera pulls back far enough to make the animal a smudge. Splitting the inequality further, into `||A - I|| |p| + |t|`, is looser again, because a rotation about a joint a hundred units up the rig has a hundred-unit translation the centre term is there to cancel. The per-joint form gives the Fox **49.3** on a radius of 82 for its Survey clip and RiggedFigure **0.48** on 0.83.

The bound is a *sample* over the timeline — exact for STEP and LINEAR tracks, because slerp runs along the geodesic between two keys and the displacement it induces is largest at an end of the interval, and dense-but-not-proven for CUBICSPLINE, the one interpolation that can overshoot its keys. What being wrong costs is a cluster culled while a limb is on screen, at one phase of one clip: a hole, not a crash.

The padding is also in the scene's bounding sphere (`update_scene_bounds`), so `--orbit` frames the character wherever the clip puts it rather than only where it rests. That is a real cost and worth knowing: the Fox's framing radius goes from 82 to 131, so the animal is about 60% of the size it would be at rest.

### Ray tracing a moving character

Nothing had to change. A skinned instance is a deformed instance, so `clas_records.slang`'s emit pass already points its records' vertex address into the pool, `--rt-templates` already instantiates the cut's templates from the pool instead of rebuilding, and the resolve's shadow rays already trace against the structures this frame built from this frame's visible list. Verified with a capture: a posed bar through `--raster rt` differs from the mesh-shader path on 0 of 1,278 covered pixels in coverage and 1 in triangle, which is what a silhouette costs on a rigid mesh too.

## Capture channels, and the id encoding

`CaptureChannels` asks for any of four, and `CapturedFrame` carries what came back.

| Channel | Form | Notes |
|---|---|---|
| `color` | RGBA8 | the picture, as `engine-view --capture` writes it |
| `ids` | three `u32` per pixel | instance, cluster, triangle; `0xFFFFFFFF` in all three where the scene did not cover the pixel |
| `depth` | `f32` per pixel | reversed-Z clip depth, 0 where nothing covered it, plus the covered range as `depth_min`/`depth_max` |
| `normals` | RGB8 | the world normal encoded `n * 0.5 + 0.5` |

A capture is always in the **target's** pixels, whatever the layout: the walk is per view, a pixel inside a view's rectangle reads that view's region of the visibility buffer, a pixel no view covers is empty, and a Panini view's pixels go through the same map the resolve used (`panini_source_pixel`, the CPU mirror of the shader's), so an id names what is under that pixel of the picture rather than of the source.

**The id channel is the plan's entity-ID buffer** ([04 §4.2](../plan/04-renderer.md#42-frame-architecture), [10 §10.2](../plan/10-roadmap-risks.md#102-phases) Phase 1), and it is resolved rather than raw on purpose. The visibility buffer holds `depth << 32 | (visible_index << 8 | triangle)`, and `visible_index` names an entry of **this frame's** visible list — a cut entry, not a cluster (AGENTS.md). Two cuts of the same scene put the same triangle under different ids, and the list is overwritten by the next frame, so a raw id is meaningless the moment the frame is over. A capture therefore reads the visible list back with the visibility buffer and writes the pair the id led to. That is the number an agent can act on ("which instance is under this pixel"), and it is stable across rasterizers and LOD cuts. The decode is the same one `visible_entry` does in `visibility_resolve.slang`, including the no-cull case where the list is null and entry *i* is `{0, i}`.

`--raster direct` writes no visibility buffer — it draws mesh shaders straight to color with a depth buffer — so asking it for `ids` or `depth` is an **error with a message**, not a buffer of nothing.

`normals` costs a second frame: the normal is what the resolve reconstructs, and only the resolve knows it, so the renderer renders again in the normals view mode and reads the color back. `ids` and `depth` come out of the visibility buffer of the first frame and cost one blocking readback each.

**On disk** (`write_capture`, which engine-host calls and the module's tests check) the channels are `<base>.png`, `<base>.ids.bin` + `<base>.ids.json`, `<base>.depth.png`, and `<base>.normals.png`. The id buffer is a raw little-endian `u32` array with a JSON header beside it rather than an image, because it is data to be indexed (`(y * width + x) * 3`) and any lossy or reordered image form would make a pixel's instance number unreadable:

```json
{"format":"engine.renderer.ids.v1","file":"shot.ids.bin","width":400,"height":300,
 "type":"u32","byte_order":"little","words_per_pixel":3,
 "channels":["instance","cluster","triangle"],"order":"row_major_top_first",
 "empty":4294967295,"covered":47213}
```

Depth is an 8-bit gray PNG normalized over the frame's own covered range (black is both "not covered" and the far end), because the engine's own encoder writes 8 bits per channel and a depth channel is looked at far more often than it is measured — a measurement takes the ids beside it or the `f32` array in `CapturedFrame`. Adding a 16-bit path to `foundation/image` is the obvious next step if that stops being true.

## Statistics

`Stats` carries exactly the fields engine-view's JSON summary prints and engine-host's `render.benchmark` returns: frames, timed frames, the three visible-pair counts and their running minimum and maximum, the GPU milliseconds of each pass (cull, hw, sw, hiz, resolve, rt, clas, deform, trace, total) as sums with `*_ms()` accessors that divide by the timed frames, the CPU nanoseconds spent inside `submit_frame`, and one `ViewStats` per view (above). The per-view rectangles and tiers are filled when the layout is laid out rather than when a frame completes, because a capture is one or two frames and would otherwise report a run of zeros. The visible counts are read one frame late from a per-slot copy of the indirect argument blocks; `collect_visible()` is how a caller that waited for a specific frame (engine-view's last, before it captures) folds that frame's counts in without waiting for the slot to come around. The GPU timings of that frame are *not* in it, because a timestamp pool is read when its slot is reused.

**`Stats::gpu_memory` says who else was using the card.** `budget_mib`, `used_mib` and `device_local_total_mib` come from `gfx::MemoryBudget` ([gfx](gfx.md)) through `sample_gpu_memory()`, which `create()` and `reset_stats()` call so a summary always has a figure and which a host that measures calls again at the end of a run. It is a driver query and so is **not** in the frame path, which is the same rule as the one that keeps buffer readbacks out of it. The reason it is here at all: this project's development machine renders beside GPU jobs that hold most of its memory, and a frame time measured against a contended card is a measurement of the contention. Read it together with the `machine_state` block both hosts print — the Vulkan budget under-reports a CUDA tenant, and `nvidia-smi`'s number does not ([bench](bench.md#measuring-on-a-shared-machine) says how far apart the two were, measured).

## Testing

`tools/dev.ps1 test -Preset msvc-debug -Filter renderer` runs the module's tests, all headless. They write a unit-cube GLB at test time (one primitive, one material — the fixture `apps/engine_view/tests` writes, minus the textures) into a `test::TempDir` of their own, with the derived-data root inside it, so nothing in the tree, nothing in the repository's cache, and nothing another copy of the suite is using is touched (AGENTS.md, test hygiene). They skip with a message on a machine with no Vulkan device or no 64-bit buffer atomics, exactly as engine-view exits 3. They check: a cube rendered offscreen into all four channels at once, with the center pixel's id naming instance 0, a cluster of that scene, and a triangle under 128, and an uncovered corner naming nothing; every `Stats` field present and consistent; the four channels landing on disk in the documented shapes, with the id file exactly `width * height * 3 * 4` bytes; two instances of the cube producing exactly the ids 0 and 1 and no others; `resolve_settings` making the same five decisions on a synthetic baseline device, an RT device, and a path that cannot shadow; and the direct path refusing an id capture with a message while still capturing color.

**Occlusion culling changes no pixel**, which is the case that guards both of the fixed-cost changes above: the same wall of cubes at two depths is rendered with `occlusion` on and off at 302×154 — a multiple of neither the 32-pixel coverage tile nor a surround's thirds — and every colour channel and the (instance, cluster) under every pixel must agree, at both `single` and `surround3`. Shadows are set off for it, because they turn occlusion off with them and this GPU would otherwise have taken them, which is also why the module's other cases never exercise the Hi-Z at all.

The multi-view cases add four. **The layouts**, on the CPU with no device: a single view over the whole target; a flat surround whose three off-axis rectangles meet and whose union is the single view's, with the centre one centred; a turned surround whose side cameras carry the yaw and whose side views alone carry the peripheral LOD multiplier; and a Panini view whose oversampling factor is the arithmetic's, is 1 at d = 0, and is refused past `k_max_oversample`. **The off-axis projection** against `perspective_reversed_z` through a centred rectangle, and a shifted rectangle putting its own centre line at normalized x of zero. **The Panini inverse map** against the projection it inverts, azimuth by azimuth, and its centre against the source's centre. **The frame itself**, on a GPU: a flat surround's centre monitor against a single view of one monitor from the same camera — equal visible-pair counts and *the same ids and the same colors, all 16,384 pixels of them* — and a 35-degree surround with one cube in front of each view's own centre, where each view's centre pixel names its own instance through the rasterizers **and** through the ray path, which proves the union structure serves every view. The d = 0 Panini case renders the same scene both ways and reports how many pixels differ. `Stats::gpu_memory` is checked with the rest of the statistics: a device-local total above zero always, and a budget within that total on a device with `VK_EXT_memory_budget`.

The pictures are pinned end to end by engine-view's own suite and by the comparison in that page: the FlightHelmet at a fixed orbit through `--raster hw`, `--raster vertex`, `--raster rt --shadows rt`, `--deform wave`, and `--grid-instances 3` is **byte-identical** before and after the move out of `main.cpp` (PSNR null, SSIM 1, FLIP 0 on all five).

**Skinning adds four cases**, over a two-bone bar built in the test rather than imported — a skinned glTF written at test time would be testing the importer too, and what these are about is the renderer's half of the contract. The bar is a square column sliced into 32 rings, bound root-to-tip by height, so every vertex of the top half moves when the tip joint turns. At the **bind pose** the skinned instance draws exactly what a rigid instance of the same mesh draws: 4,776 covered pixels, 0 id words differing, worst depth difference 4.7e-10 against the documented 2e-7 (they cannot be bit-identical — the rigid path dequantizes inside the rasterizer while the skinned one reads the float the pool stored). A **60° bend** moves the picture where `anim::skin_positions` says: the drawn rectangle's bend axis is [63, 109] against a projected [62.6, 110.0], 1,099 of 1,330 pixels change coverage, and the bent bar is visibly wider than the straight one. **Culling stays conservative** over the whole 0–90° sweep: twelve phases, each rendered with the exact displacement bound and again with eight times it, 0 id words differing at any of them, with the bar filling the frame where a frustum test can actually bite. And the three paths **agree on a posed frame**: the vertex path writes the same words as the mesh shader (0 of 1,278 covered pixels differ) and the ray path differs on 0 coverage and 1 triangle, which is what a silhouette costs on a rigid mesh.

## Performance notes

Nothing about the frame changed in the move, and the numbers in [apps](apps.md) and [gfx](gfx.md) still hold. Two allocations were added and both are outside the frame: the render graph is heap-allocated once (it is not default-constructible), and `capture()` allocates its staging buffers per call. The visibility buffer and the visible list gained `VK_BUFFER_USAGE_TRANSFER_SRC_BIT` so a capture can read them; nothing in a frame copies from either.

**The fixed cost of a frame** — what it costs with nothing in view — is what [E9](../experiments/e9-multi-view.md) found dominates the owner's 11520×2160, and where the renderer's own passes were rebuilt.

- **The Hi-Z pyramid is folded, not built a mip at a time.** `Targets::hiz_dispatches` is `gfx::hiz_dispatch_count(mips)` and `add_hiz` records that many passes per view per build, each pushing one `gfx::HizParams` that names the source mip and how many folds to write; the shader does the rest in shared memory ([gfx](gfx.md)). The pyramid is bit-identical and the visible set is unchanged, which is the requirement: the Hi-Z is the input to a test that must not change the picture.
- **The resolve leaves the sky to the clear.** The resolve pass clears the colour target to the sky before it draws, so a pixel the scene does not cover is a fragment that would write the value already under it; `gfx::ResolveParams::sky_is_clear` says so and the shader discards instead ([gfx](gfx.md)). The renderer is entitled to set it because it owns both ends: `k_sky` in `scene_renderer.cpp` is the clear value **and** `ResolveParams::sky`, in one place, because two spellings of the same colour would make an uncovered pixel take whichever the clear said without anything saying so.
- **The resolve does not read a 32×32 tile with nothing in it.** The last Hi-Z build of a frame leaves a coverage word per tile behind its pyramids in `Targets::hiz` — one per workgroup of its first dispatch, so it is free — and `ViewTarget::coverage_offset`/`coverage_pitch` are where each view's is. The resolve pass declares a `FragmentRead` of the Hi-Z buffer and `ResolveParams::coverage` points at it, **but only when `resolved_.occlusion` is set**, because that is the only arrangement in which nothing writes the visibility buffer between the last Hi-Z build and the resolve. The build after pass 1 writes no mask at all: it would be a truthful mask of a moment nothing reads.

**The rule that keeps the mask honest.** A pass added to `record_frame` that writes the visibility buffer *after* `add_hiz(1)` makes the mask a lie, and the failure is a 32×32 block of sky where a surface should be. Today the pass order makes that impossible — occlusion culling only runs in the two modes that have no software-raster pass and no ray trace — and `resolve.coverage` is gated on exactly that flag. Whoever changes the order changes the gate.

## Not yet

Multi-view got the per-frame working set split ([above](#multi-view-a-viewset-over-one-scene)), so a second `SceneRenderer` on one `GpuScene` is no longer what §4.6 wants — one renderer draws the whole set. What is still open there: a per-view **internal resolution** and the shading-rate half of foveation (the `ViewQuality::shading_rate` stub), which need `VK_KHR_fragment_shading_rate` in the RHI; one RT cut at a view-agnostic threshold instead of the union of the views' cuts; a filtered color-domain Panini resample; multi-window presentation and per-output HDR metadata (engine-view has one swapchain); and the screen-space passes §4.6 says run per view, none of which exist yet — there is no TAA, no denoiser and no upscaler to run per view. Changing `RenderSettings` without rebuilding the `GpuScene` and the `SceneRenderer`: the deformed-vertex pool and the ray tracing chain are sized by the settings, so engine-host rebuilds both and keeps only the `SceneData`, which is where the import and the clustering cost is. Streaming and residency ([04 §4.9](../plan/04-renderer.md#49-streaming-and-residency)): a scene is uploaded whole. The reference path tracer and the accept-or-reject loop's automation ([04 §4.8](../plan/04-renderer.md#48-reference-renderer-and-objective-optimization)) — `render.compare` is the metric half of it, and the integrator is Phase 2's.
