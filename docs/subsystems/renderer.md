# renderer (systems)

**Purpose.** The engine's renderer ([04](../plan/04-renderer.md), [02 §2.3](../plan/02-architecture.md#23-subsystem-boundaries-and-layering) L3): it turns a set of meshes and instances of them into a picture and into the numbers that describe how it was made. It owns the whole frame — source-mesh loading through the derived-data cache, the GPU-resident scene, two-pass GPU culling and LOD selection, the four rasterizers, the deformed-vertex pool, the per-frame cluster acceleration structures, the material resolve, the Hi-Z pyramid, the GPU timers, and the capture — and it does all of it **without a window**. `engine-view` is the command line over it and `engine-host`'s `render.*` methods are the protocol over it; neither is privileged, and a third consumer (the editor, a test, a benchmark harness) needs nothing new.

**Why it is a module and not an app.** Until this split every one of those passes lived in `apps/engine_view/main.cpp`, 2,654 lines of it, and the consequence was not that the file was long: it was that **nothing but engine-view could render**. The protocol had no `capture` and no `benchmark`, so the Phase 1 exit criterion ("agents can capture and benchmark", [10 §10.2](../plan/10-roadmap-risks.md#102-phases)) could not be met without either duplicating the frame in the host or driving a child process and reading its stdout. The renderer is the engine's own, in the same sense `gfx` is — not a capability a game adds ([ADR-0027](../adr/0027-additive-capabilities.md)) — so it is `engine_module(... LAYER systems)` with no `OPTIONAL`: a build without it could not draw at all, and every consumer of it would have to be switched off with it.

**The window is the app's.** `foundation/window` is not a dependency of this module, and nothing here touches a surface, a swapchain, or a present queue. A frame is recorded into a color image the caller names: engine-view acquires a swapchain image and hands it in with its two semaphores; engine-host renders into an offscreen target the renderer owns. That is the *only* difference between the two, which is why a picture captured through the protocol is the picture engine-view shows. `systems/renderer/tests/renderer_tests.cpp` opens with `#if __has_include(<foundation/window/window.h>) #error`, so the day the dependency comes back the build says so rather than a hosted CI run failing to open a display.

## Owned data

| Owner | What it is sized by | What it holds |
|---|---|---|
| `SceneDesc` | — | what to load: mesh paths, instances, the instance grid, which **procedural** scene an empty path builds (`Procedural::heightfield` or `shredded_atlas`, the UV-atlas LOD fixture of [geometry](geometry.md#the-shredded-atlas)) and its resolution, what the LOD builder is told (`lod`, which is part of the derived-data cache key), the derived-data root; and what a scene file adds — per mesh a name, the content hash its bytes must have and a fit, and the terrain an empty path then builds ([Scenes, camera paths and flythroughs](#scenes-camera-paths-and-flythroughs)) |
| `SceneData` | the content | one merged cluster LOD DAG, one `geometry::ClusterMeshPart` per mesh, each mesh's materials and images, the instance table, the bounding sphere, and the counts a summary reports; and, host side only, every cluster vertex's canonical id (`mesh_vertex_ids`, below); every mesh's source hash, and the terrain, names and file hash carried from the description, so a host holding only the loaded scene can fly a path over it and say what it measured |
| `GpuScene` | the **scene** | every device buffer whose size is a function of the scene: geometry behind device addresses, the material table and the bindless textures, the instance table, the deformed-vertex pool, the visible list (with a run per shadow cascade behind the views') and the indirect argument blocks, the pair table and the per-view pair-to-entry tables, the vertex path's indexed-draw regions, and the ray tracing chain — whose per-frame structures are the one thing here sized by the *frames* rather than the scene, and which `SceneRenderer` resizes ([The ray tracing chain's memory](#the-ray-tracing-chains-memory)); and, for a streamed world, the tail of instances that comes and goes between frames — each tile in a block of the instance table with a reserved run of pairs, the instance and pair tables in one set per frame in flight — with the per-pair buffers at a stride that grows with it ([Instances that come and go](#instances-that-come-and-go)) |
| `ViewSet` | the **layout** | N views over one scene: each one's rectangle of the target, its orientation and frustum shape, its source extent, and its quality tier |
| `SceneRenderer` | the **screen** | the shader library and its pipelines, the visibility buffer and the Hi-Z pyramids, the frame context, the GPU timers, the render graph, the per-slot parameter blocks, and `Stats` — and the sun's shadow atlas, which is sized by the settings rather than the screen and so survives a resize |

That line — scene-sized against screen-sized — is also the order the two build in, and it is not arbitrary: the `gfx::MeshDesc` array names the deformed-vertex pool, the deform table, and this scene's cluster templates, so it is uploaded last, after every address it carries exists. A `GpuScene` therefore finishes itself; a `SceneRenderer` is created against a finished one.

## Invariants

- **A picture does not depend on where the mesh came from.** `load_source_mesh` takes a glTF, a derived-data cache entry, or a `.clusters` container named outright, and all three have to reach the GPU upload with the same materials *and the same image bytes* — the loader hands on a container's carried bytes for an image the source embedded and its path for an image the source named, so that one `assets::MeshData` shape serves every route ([geometry](geometry.md#embedded-images-the-container-carries-them)). It is asserted in `engine-view`'s end-to-end test as four byte-identical captures, because the failure mode is a texture that quietly does not arrive and a cut that looks right. **The textures are the one input that a load may take from the cache instead**: a mesh whose images the content build has built draws them from `<ddc>/textures/` whether it arrived as a glTF, a cache entry or a container ([Built textures](#built-textures)), so those three routes still agree, and only `--no-cache` — which reads no derived data at all — draws the decoded source images; the two pictures differ by what BC7 and mips do, which `texture_tests.cpp` bounds.
- **A picture does not depend on which host drew it.** Every device- and scene-driven override lives in one function, `resolve_settings`, and nothing below it probes `gfx::DeviceFeatures` again. The order of the overrides is load-bearing and the function says so: the mesh-shader fallback decides which path runs, the path decides whether shadows can be traced or mapped, and traced shadows decide whether two-pass occlusion culling may run (the acceleration structures are built from one visible list, and pass 2's survivors are in a second one); the cascaded maps do not, because they are culled from the light into runs of their own. Everything after that only ever forces a switch *on*.
- **The material map follows the merge.** A cluster draws with its own material whatever the scene's merge did to its index. `geometry::merge_cluster_meshes` puts each mesh's leaves first, and every mesh that came through the cache arrived in page order, leaves last, so the merge moves nearly all of its clusters; `load_scene` takes the merge's `source_of_cluster` and permutes each `SourceMesh::part_of_cluster` with it, which is the array `GpuScene::upload_materials` indexes by the merged position. Until 2026-09-24 it did not, and from 2026-09-17 every non-streamed scene of more than one mesh drew each cluster of a multi-material mesh with whichever material belonged to the cluster that used to sit at its index: rock on the dunes and sand on the ridges of the desert overlook's terrain, the FlightHelmet's leather in metal and glass, and — because every LOD cut draws different clusters — patches that changed as the camera moved, which is exactly what the first owner session reported ([the write-up](../experiments/first-interactive-session-2026-09-24.md)). The streamed path merges with `ClusterOrder::keep` and a single mesh is not merged, which is why neither the renderer's tests nor any single-asset capture showed it. `flythrough_tests.cpp` holds it on a glTF of two primitives side by side, whose every cluster's material is known from where its vertices are (the terrain was the fixture until it stopped having more than one material, below).
- **A cut change never changes a surface's colour beyond the cut's own geometric error.** A material is per cluster, so anything whose colour varies across a mesh must vary through the vertices' attributes — a texture over UVs, which every LOD level interpolates from the same source vertices — and never through which material a cluster was given. The terrain broke this until 2026-09-25: it chose one of four materials per cluster by a vote of the cluster's vertices, a coarser cluster votes over a larger patch, and the sand, rock and basin borders jumped by whole clusters as the camera moved (the second owner session, [its write-up](../experiments/second-interactive-session-2026-09-25.md)). It is one material over baked maps now ([Scenes, camera paths and flythroughs](#scenes-camera-paths-and-flythroughs), "The terrain"), and `flythrough_tests.cpp` draws it at the owner's six marker cameras from two cuts and holds the colour to within 8 of 255 on all but a sliver of the pixels.
- **What a summary reports is what ran**, not what was asked for: `ResolvedSettings::settings` carries the overrides, so a run whose `--raster hw` fell back to the vertex path says `"raster":"vertex"`.
- **The renderer never reads a buffer back inside a frame.** The visible-pair counts come from a per-slot copy of the indirect argument blocks, read one frame late; the GPU milliseconds come from `gfx::GpuTimer`, never from a CPU clock. The only blocking readbacks in the module are in `capture()`, which is not a frame path.
- Pass bodies are stored in the render graph's arena and capture by reference, so declaring, compiling, and executing a frame are **one function** (`record_frame`): every parameter block a body pushes has to still be alive when `execute()` records it.
- A capture's id buffer names the (instance, cluster, triangle) a pixel's visibility id led to, never the id itself — see below.
- **A picture does not depend on the order the GPU did anything in.** The visibility id is the scene's pair, so two surfaces at exactly one depth resolve to the larger (pair, triangle) whichever run, pass, rasterizer or thread drew them, and occlusion culling on or off gives the same id channel and the same colour, word for word ([gfx](gfx.md), "The tie rule"; the desert-overlook path checks it over 2,401 frames, [below](#scenes-camera-paths-and-flythroughs)). The visible list itself is still in append order, and the one place that order reaches a picture is a deformed-vertex pool past its budget ([What overflow costs](#the-deformed-vertex-pool)).
- **A view's cut does not depend on how many views there are beside it.** Every view culls, rasterizes and resolves against its own slices, and the only thing they share is the scene. The test that holds this is the one that renders a flat three-monitor surround at 3w × h and a single view at w × h from the same camera and requires the centre monitor to be *the same picture and the same ids, pixel for pixel* (see [Multi-view](#multi-view-a-viewset-over-one-scene)).

## The offscreen contract

```cpp
SceneData data;   load_scene(desc, data, error);
ResolvedSettings resolved;  resolve_settings(settings, device.features(), &data, resolved);
if (check_availability(resolved, device.features()) != RenderAvailability::Ok) { ... }
GpuScene scene;   scene.create(device, data, resolved, &error);
SceneRenderer r;  r.create(device, scene, resolved, {.width = w, .height = h}, &error);
```

`check_availability` is deliberately separate from `create`: a device that cannot render is not a caller's mistake, and the two hosts report it differently — engine-view exits 3 (which its tests treat as a skip) and engine-host answers protocol error 1007 (`RenderUnavailable`). It checks two things and not a third: 64-bit buffer atomics, without which nothing can write the visibility buffer, and cluster acceleration structures plus ray queries when a ray was **explicitly** asked for — the ray path, or `ShadowMode::RayTraced`. The second half used to cover only the ray path, and an explicit `--shadows rt` on a device that cannot trace drew the frame without shadows and a warning; it is refused now, like `--raster rt`, because a picture without the shadows somebody asked for reads as a shadowing bug. `ShadowMode::Auto` is the request that degrades quietly, and `--shadows rt` on a *path* that builds no structures (direct, sw, auto) is a settings conflict rather than a device one and stays a warning. **Presentation is not checked**, because presenting is the window's requirement and not the renderer's.

**A refusal says what the device lacks in the words of its own verdict.** `unavailable_reason(availability, device)` is what both hosts print — the adapter's name and, for a ray-tracing refusal, `gfx::ray_tracing_degradation(device.caps())`, the sentence `engine-cli gpu.adapters` carries in `verdict.degraded` ([gfx](gfx.md#what-a-device-has-to-have)). On the project's TITAN Xp that reads "NVIDIA TITAN Xp cannot trace rays: no VK_KHR_ray_query and no VK_NV_cluster_acceleration_structure: every ray the renderer traces is a ray query …". `reference_available` takes the device for the same reason and says the same. `availability_message` is the short phrase, for a caller with no device in hand.

**A path the device lacks is never compiled.** `SceneRenderer::create_pipelines` builds the two mesh-shader pipelines — the direct one and the visibility one — only when the resolved path draws with them, and does not even load `cluster_mesh` otherwise. It built both unconditionally until 2026-09-23, which nothing noticed while every GPU the suite ran on had mesh shaders: on the first device without them — the Pascal server — `resolve_settings` correctly chose the vertex path and `SceneRenderer::create` still failed in `create_mesh_pipeline`, so no renderer could be created there at all. The vertex path's indexed pipelines and its expansion pass follow the same rule — built, and `cluster_vertex_indexed` loaded, only when `ResolvedSettings::vertex_indexed` says they draw, since that module declares the `Geometry` capability a device without `geometryShader` cannot create. Everything else it builds runs on any device `check_availability` accepted, and is built as before.

**The vertex path draws its cut indexed where the device lets it.** `resolve_settings` sets `ResolvedSettings::vertex_indexed` for the vertex path with culling on, `DeviceFeatures::geometry_shader` and `DeviceFeatures::full_draw_index_uint32` (after every other override, since it changes how the path draws and not what), and that flag is the only thing that chooses between the baseline tier's two draws ([gfx](gfx.md), "Baseline tier"). With it, the cull pass runs `cull_vertex_main` instead of `cull_main`, an expansion pass runs before each hardware draw and is timed in its zone (`gpu_ms.hw` is the expansion plus the draw), and each view's draw is one `vkCmdDrawIndexedIndirect` of the cut's own triangles followed by one `vkCmdDrawIndirect` of whatever overflowed the index budget — an instance count of zero on every frame measured. `GpuScene::create_working_set` makes the three buffers it needs, one region of each per view and hardware run like the visible list: a 64-byte `gfx::VertexDrawHeader`, a 16-byte `gfx::VertexDrawRecord` per pair, and an index array of `k_vertex_index_budget` triangles (2^20, 12 MiB) **or the scene's own bound — every triangle of every pair — when that is smaller**, so a small scene can never overflow and pays only for what it could draw; the frame's reset writes each header with `vkCmdUpdateBuffer`. The largest cut measured, 64 FlightHelmets at LOD 0.25 and 3840×2160, is 0.85 M triangles of the 1.05 M. Everything downstream reads what it read before: the visible list the resolve, the Hi-Z build and the ray chain use is written exactly as it was, and the records are a second output of the cull pass beside it, not a change to it. The shadow casters' run (`gfx::k_caster_run`) does not meet it: a caster leaves the cull pass before the hardware survivor tail where the allocation is, and the draw reads only runs 0 and 1. The two draws are the same picture to the byte (the case below), and what the indexed one costs and saves is in [E1 on Pascal](../experiments/e1-pascal-rerun.md#after-the-vertex-path-draws-the-cuts-own-triangles): 42–48% of the raster pass on the TITAN Xp's helmet grid (6–19% of its frame), 6–24% *more* on its heightfield (at most 2.5% of that frame), and 7–22% more on the RTX 5090's helmet grid, which does not matter there because the 5090 draws the mesh path unless asked.

One frame is `begin_frame()` (wait for the slot, fold in the completed frame's statistics and timings), then `submit_frame(FrameDesc)`, then — for a presented frame — the caller's present. `FrameDesc` names the color image (a `gfx::ImageResource`), the layout to leave it in (a `gfx::ImageLayout`: `TransferSrc` offscreen, `Present` for a swapchain image), and the two semaphores (`gfx::SemaphoreHandle`s, the acquire and the render-finished); a null image draws into the renderer's own offscreen target. `render_offscreen()` is the three calls plus the wait, and `capture()` is `render_offscreen` plus the readbacks. The pipelines are built for one color format (`Desc::color_format`, a `gfx::Format`), which engine-view sets to the swapchain's so the picture is produced exactly as it is presented; the offscreen default, `R8G8B8A8Unorm`, differs from a typical swapchain's `B8G8R8A8Unorm` only in channel order and so reads back byte for byte the same.

**This module's public headers name no Vulkan type, and its sources include no Vulkan header** ([gfx](gfx.md#the-rhi-surface-and-the-backend-surface)). Since 2026-09-25 the renderer records every pass through `gfx::CommandList` (`bind_pipeline`, `push_constants`, `dispatch`, the indirect draws, `fill_buffer`, `update_buffer`, `copy_buffer`, …), creates its buffers with `gfx::BufferUsage`, its images with `gfx::Format` and `gfx::ImageUsage`, its samplers with `gfx::SamplerDesc`, and holds pipelines, views, samplers and semaphores as `gfx::` handles — `FrameDesc`, `SceneRenderer::Desc`, `GpuScene`'s buffers and `GeometryStreamer::record_uploads(gfx::CommandList)` included. Before that the public headers named Vulkan in 21 places and three of them included the RHI's Vulkan header, so every consumer of the renderer — both hosts, their tests — compiled against `vulkan_core.h`. The rule that it records into an image the caller names is what makes this possible: the renderer owns no device, no surface and no swapchain, so it needs nothing from the backend set, and `tools/lint.ps1`'s `vulkan-backend-include` rule and the build (only `engine::gfx_vulkan`'s linkers see `volk.h`) both keep it that way. The change moved no picture and no pass timing (the numbers are in gfx.md), which it could not by construction: every `CommandList` method is one Vulkan command, and every engine enumerator carries the Vulkan value it replaced.

The camera is a plain struct, and `orbit_camera(center, radius, distance, frame)` is the orbit engine-view has always used — distances scale with the scene's radius, and a `distance` of zero breathes between 8 and 36 radius-tenths. `orbit_camera_at(center, radius, distance, yaw, pitch)` is the same orbit at explicit angles, where `pitch` is the elevation above the orbit circle; its default, `k_orbit_pitch` = atan(0.45), is engine-view's fixed height factor, so `--orbit 22` and `orbit {distance: 22}` are the same camera and the two hosts' captures of a scene compare directly.

## Multi-view: a `ViewSet` over one scene

[04 §4.6](../plan/04-renderer.md#46-extreme-displays) asks for multi-view rendering as a first-class concept: *N views sharing one scene, one culling hierarchy, one TLAS, one residency budget.* `systems/renderer/view_set.h` is that concept. `ViewSet::build` lays a `ViewLayout` — `single`, `surround3`, or `panini` — out over the color target and fixes everything the screen sizes; `ViewSet::update` turns one frame camera into N view-projection matrices. A `View` carries its rectangle of the target, its **source** extent (what the rasterizers run at, which is wider than the rectangle only for a Panini view), the yaw its camera is turned by, its frustum as tangents at unit distance, and its `ViewQuality` tier.

**What is shared and what is per view.**

| Shared by the set | Per view |
|---|---|
| the `GpuScene`: geometry, materials, textures, instances, the deformed-vertex pool | the cull params (frustum, Hi-Z, flags and prev_flags, LOD threshold) |
| one top-level acceleration structure, built from the **union** of the views' cuts | its run of the visible list, its indirect argument blocks |
| one CLAS set and one set of cluster bottom-level structures, sized by the frame's union | its region of the visibility buffer and its own Hi-Z pyramid |
| the eye position, the near plane, the lights, the residency budget | its viewport, its resolve, its ray dispatch, its statistics |

**Why the per-frame working set is slices of shared buffers and not a set per renderer.** The [Not yet](#not-yet) note this replaces said a second `SceneRenderer` on one `GpuScene` would need its own visible list, argument blocks and flags. Duplicating them per renderer was the wrong half of the choice. A visibility id is an *index into the visible list*, so if two views had two lists an id would be ambiguous and the resolve could not decode one without knowing which view wrote it; the ray tracing chain builds one set of structures from the union of the cuts, and a union is a contiguous range of one array rather than a gather over N; and §4.6 asks a `ViewSet` to share *one residency budget*, which one allocation that scales with the view count is and N allocations are not. So `GpuScene` takes the view count from `ResolvedSettings` and every per-frame buffer carries a slice per view.

**The entry space, and the id beside it.** The visible list is **run-major**: run *r* of view *v* starts at entry `(r * views + v) * pair_count` (`GpuScene::visible_base`). There are `k_visible_runs` = 3 runs — occlusion pass 1, pass 2, the software rasterizer (which a frame that traces shadows uses for its shadow casters instead, `gfx::k_caster_run`) — so the list is `3 * views * pair_count` entries, and an entry index is unique across the whole frame: it is what the deformed-vertex pool's slot table, the indexed draw's records and a CLAS record's base geometry index are indexed by. Within a run the entries are in the order the cull pass's append handed out slots, which is not the same twice ([gfx](gfx.md), "The visible list's order", has why it stays that way). The **visibility id is not an entry**: it is the scene's pair ([gfx](gfx.md), "The tie rule"), the same in every run and every view, and the cull pass also writes each view's **pair-to-entry table** (`GpuScene::pair_entries`, `pair_count` words a view) for every pair it draws — a pair is drawn at most once per view per frame — which is how the resolve gets from a pixel of a deformed instance back to the entry its pool block belongs to. Every other pixel decodes through the scene's **pair table** (`GpuScene::pair_table`, the {instance, cluster} of every pair, written once at upload), one load as `visible[entry]` was; reading the per-view table for every pixel cost the TITAN Xp's resolve 2–3% ([visible order](../experiments/visible-order.md)). Run-major rather than view-major for one reason: it puts the **first** run of every view in one contiguous range at the front of the list, and that range is exactly what the ray tracing chain consumes, so `records_main` covers every view's cut in one dispatch reading each view's own count word out of its indirect block (`gfx::k_draw_args_bytes` apart). With one view the layout is the same three runs it has always been, at the same offsets.

The records chain widens by the same factor: an instance's slice of the bucketing scratch is `views` times its mesh's cluster count, because in the worst case every view draws every cluster of it, and the view count in `gfx::ClusterRecordParams::mode` is what says so. The largest geometry index is `views * pair_count - 1`. The CLAS set **was** sized `views * pair_count` too, which is capacity and not traffic: on a surround the views see nearly disjoint thirds of the world, so a frame builds about as many records as one view would while the allocation was three times it ([E9](../experiments/e9-multi-view.md) has the numbers). Since 2026-09-24 it is sized by what the frames build instead ([The ray tracing chain's memory](#the-ray-tracing-chains-memory)), and a surround costs what its union of cuts costs.

**What each shader had to learn, and what it did not.** The rasterizers and `hiz_build.slang` learned *nothing*: a view's raster pass sets a viewport at the **origin** of its own source rectangle, so `SV_Position` is already view-local, its `visibility` address is its own region of the buffer, and its Hi-Z pyramid is built from that region and indexed from element zero. Only the resolve had to learn where it is — `ResolveParams::view_x`/`view_y` are the rectangle's origin, which it subtracts from `SV_Position` — because the resolve is the one pass that writes the shared color target. Every one of those fields is zero for a single view and the arithmetic reduces to what it was, which is why the single-view pictures are byte-identical before and after (verified on the FlightHelmet through `--raster hw`, `--raster vertex`, `--raster rt --shadows rt` and `--deform wave`: PSNR null, SSIM 1, FLIP 0 on all four).

**Surround3.** Three views over a target divided in three, with per-monitor off-axis frusta. The eye distance is the one that makes a monitor subtend the field of view; `Surround3::bezel` is bezel *correction* (the rectangles always tile the target, because a driver-surround surface has no pixels behind a bezel, so the gap widens the angle between the monitors instead); `side_yaw` turns the side monitors inward, which turns their cameras and reshapes their frusta. The centre monitor is centred whatever the arrangement, so it takes the symmetric projection rather than the off-axis one — deliberately, because that makes the centre view of a flat surround **bit-for-bit** the single view of one monitor, which is the identity the multi-view cull is tested against. At `side_yaw` 0 the three off-axis frusta are exactly the three thirds of one wide rectilinear frustum, so a flat surround and a single wide view are the same picture.

**Panini.** One view, rendered rectilinear into an oversampled source and resampled in the resolve. The source is the *same frustum* the single rectilinear view would have used, at a wider resolution: `(d + cos t) / ((d + 1) cos t)` times as wide at the half horizontal field of view, which is what it takes for the resample never to magnify (about 2× at d = 1 and 48:9). The resample happens **inside the resolve**, in the visibility domain: an output pixel maps back through the Panini inverse to a fractional source position, reads the visibility buffer there, and reconstructs its barycentrics at that same fractional point, so it stays sub-pixel accurate. That is the cheapest form — no intermediate color image, no second full-screen pass, no bindless slot for it — and it is the honest one, because a visibility id cannot be filtered anyway. Its cost is that the periphery, where the source is several times denser than the picture, is point-sampled and aliases; a filtered color-domain resample plus TAA is the fix and both are open ([E9](../experiments/e9-multi-view.md)). At d = 0 the Panini projection *is* the rectilinear one, and the picture comes back identical to the single view's (measured: not one pixel of 49,152 differs at 384 × 128).

**Foveation, as far as it goes.** `ViewQuality::lod_scale` multiplies the view's LOD pixel threshold, so `--peripheral-lod 4` lets a cluster be four times as wrong in screen space on the side monitors before its parent group is drawn instead. That is the whole of §4.6's foveation that is built. `ViewQuality::shading_rate` is **stubbed**: it is set, carried into the statistics and reported, and nothing consumes it — a real rate needs `VK_KHR_fragment_shading_rate` in the RHI and either a per-view rate attachment or `vkCmdSetFragmentShadingRateKHR` per draw, neither of which `domain/gfx` has. Per-view internal resolution, ray budget and effect cutoffs are not built either; the `View` carries a source extent per view, which is the seam a resolution scale would use.

**Per-view statistics, and what the milliseconds mean.** `Stats::views[v]` carries the view's rectangle, its tier, its visible pairs by draw, and its GPU milliseconds by pass; `Stats::view_ms(v)` divides. The acceleration structure chain is deliberately *not* attributed to a view: it is built once from the union and belongs to the frame. Each stage is one render-graph pass with a loop over the views inside it rather than a pass per view, because the views write disjoint slices of the same buffers and the graph tracks whole buffers — a pass per view would make it insert a barrier between views that have no hazard. The Hi-Z build is the exception: one dispatch of it folds six mips and the next one reads the last of those, so its dispatches must be barriered anyway, and the views' pyramids are therefore built one after another and a view's pyramid is one timer zone. **A zone's timestamps are written at ALL_COMMANDS on both ends, so timing the views separately orders them on the queue**: the per-view numbers are what each view costs alone, and the frame total measured this way is an upper bound on what the views would cost if the driver were free to overlap them.

**What multi-view does to ray tracing, which is the finding worth carrying.** One TLAS over the union of per-view *cuts* means two views that take different LOD levels of the same surface put both levels in one structure. With the peripheral LOD multiplier at 1 the views agree and nothing overlaps; at 2 and 4 they do not, and a ray from any view may hit the other's level. §4.6's "RT is view-agnostic" is the fix — one RT cut at a view-agnostic threshold rather than a union of the views' — and it is not built. A consequence of the same union: with more than one view a ray may name a pair through *another* view's entry, which resolves to the same (instance, cluster, triangle) and so is invisible to a capture, but means E2's word-for-word "ray-traced visibility matches the rasterized cut" invariant is a single-view statement.

## Morphed instances

A mesh with morph channels ([geometry](geometry.md)) is **deformed whatever the flags say**, exactly as a skinned one is: `SceneData::morphed()` joins `skinned()` in what makes `resolve_settings` turn the deform pass on, and every instance of such a mesh gets a `gfx::DeformDesc` with the two morph stages in its mask ([gfx](gfx.md), "The deform chain"). What this module adds is the three things the chain needs and only a renderer can supply.

**The stream, once per scene.** `GpuScene::create_morph` uploads the six arrays `merge_cluster_meshes` concatenated — the channel records, the per-cluster slice directory, the slices, the delta indices, and the two delta streams — and one `gfx::MorphParams` block naming them. They are the *scene's*: the slices are keyed by the global cluster index and the channels by the global channel index, so one block serves every mesh and every view of a frame, the way `StreamParams` serves the page table.

**The weights, on the same contract the joint matrices travel on.** Each deformed instance has `2 x channel_count` floats: the **static** half and the **pose** half. The static half is the scene's — `RenderSettings::morph_static_weights`, written at create and again through `GpuScene::set_static_weights`, which marks the caches dirty — and the pose half is the frame's, `FrameDesc::morph_weights`, one plain span the caller samples from a clip's weight tracks (`anim::Clip::sample(time, pose, weights)`) and the renderer copies into this slot's region. A morphed scene therefore always has the **per-frame** copy of the deform table that skinning already forced, because each record has to point at this slot's weights.

**The caches, budgeted.** `RenderSettings::static_shape_kib` (4 MiB by default, 16 bytes a mesh vertex) is handed out in instance order; an instance that gets none runs its static stage every frame over the cut, which is the same picture for more work. When the weights change, the frame dispatches `deform_cache_main` once per cached instance — over the whole mesh, not the cut — and the next frames read the cache. The summary reports `morph_channels`, `morph_static_cache_bytes` and `morph_cached_instances`, so "did this character get a cache?" is a number rather than a guess.

**Bounds.** A morphing instance's vertices leave their rest positions, so its `bounds_padding` gains `geometry::morph_bounds_padding`'s bound — the sum over the mesh's channels of |weight| × the channel's largest displacement — computed with the **static** weights as they are and every **pose** weight priced at 1, which is the range a glTF weights track lives in. It is conservative in the honest direction: a sphere too big draws a cluster that might have been culled, a sphere too small drops a limb off the screen. The three spheres it inflates are the cluster's and both LOD spheres, for the reason skinning's does — one constant on all three is what leaves exactly one cluster per DAG path passing.

**A single morphed mesh carries its own channel run, and until the Khronos samples nothing checked it.** A part's `first_morph_channel`/`morph_channel_count` is what gives an instance its morph stages and its deform record, and `merge_cluster_meshes` fills it for every part it concatenates — but a one-mesh scene never goes through the merge, and `load_scene`'s single-mesh branch left the run at zero while the stream (which `resolve_settings` reads) said otherwise. The deform pass was turned on for a scene with no deform record, the pool was sized for no vertices, and **every single morphed glTF failed to load** with `vmaCreateBuffer: VK_ERROR_INITIALIZATION_FAILED`. The morph case in this module's tests had never seen it because it builds its `SceneData` by hand and fills the part itself; `renderer: a single morphed glTF loads, draws, and moves through load_scene` goes through the loader, the way both hosts do.
**Streaming refuses a morphed mesh, and says so.** `resolve_settings` turns `--stream` off with a logged reason when the scene has channels. A page's payload is the cluster's positions, attributes, triangles and bindings; the morph stream is keyed by cluster too, but its slice directory indexes a scene-wide delta array whose offsets a page copy would have to patch the way it patches `ClusterDesc::vertex_offset`. That is the same work and belongs with it, so until then the whole stream is resident — `ClusterFileReader`'s resident list says so — and a caller that asks for both gets the one that draws the right picture.

## Skinned instances

E25 built the deformed-vertex pool and `deform.slang` grew a skinning kind; [animation](animation.md) produced the matrices as one contiguous span; nothing joined the two. This is the join, and it is deliberately small: **the renderer knows about bone matrices and knows nothing about clips.**

**What a caller says.** A `SceneInstance` names a joint count — `joints > 0` is what makes an instance skinned — and a bound on how far skinning moves its vertices (`bounds_padding`, below). Every member after `transform` carries a default, so `SceneInstance{mesh, transform}` is the whole of a rigid, unanimated instance and is the spelling the loader and the tests use; `animation`'s default is written `SceneAnimation animation{}` rather than left implicit, because a member of class type with no initializer of its own makes that spelling a `-Wmissing-field-initializers` error on Clang and the Windows build never said so. `SceneDesc::max_joints` is the longest matrix span a frame will hand over, which is what the joint buffer is sized by; a longer one is clamped with one warning rather than overrunning it. Two fields are the caller's to fill in **after** the load rather than before, and both for the same reason — they are lengths in a space the load is what reveals. `SceneData::max_joints` is final only once the population is attached, because it is the pose pool's capacity; `InstanceDesc::bounds_padding` needs the mesh's own bounds. A host that skins therefore loads, attaches, writes both, and calls `update_scene_bounds` before creating the `GpuScene`, which is what `engine-view --animate` does. Everything else is per frame: `FrameDesc::joints` is `std::span<const anim::JointMatrix>`, every animated instance's matrices in one run, and `FrameDesc::instance_joints` is one `{first, count}` per scene instance saying where each one's run is.

That is the whole interface, and it is spans rather than a system because **the renderer must not depend on `systems/animation`, on `domain/ecs`, or on flecs**. What it does depend on is `domain/anim`, for `anim::JointMatrix` alone — a domain module, not a capability, so the dependency cannot be switched off, and copying the 48-byte record here instead would be exactly the drift `domain/anim` took its own `geometry` dependency to avoid. The tick is the app's: `engine-view --animate` owns a world, steps it at the fixed rate, and hands over the span ([apps](apps.md), [animation](animation.md) has the pattern a game copies).

**An instance with no matrices this frame draws its rest pose.** A `count` of zero, or an instance the array does not reach, leaves `DeformDesc::joints` at zero, and `deform_skin` then writes the rest position into the pool. That is what an instance at animation LOD3 — no pool slot — looks like from here. The alternative, marking it `k_invalid_deform` for the frame, would mean rewriting the instance table mid-frame, which is a per-instance upload to save a pool write the cut had already paid for.

**The upload: one memcpy, and two deform tables.** `GpuScene` allocates a host-visible, persistently mapped joint buffer with `k_joint_slots` regions, one per frame in flight, so the host write never races a device read and needs no staging copy and no barrier; `SceneRenderer::create` refuses more frames in flight than there are regions rather than letting a character twitch one frame in ten. A frame copies the whole span into its slot's region with **one memcpy** and then walks the deform table once, rewriting the two words that change.

The two words are the problem that shapes the rest. `MeshDesc::deform` is baked into an array uploaded at create, and `scene.slang`'s `load_position` reads it on every position read of every rasterizer — for `pool_offset` alone, which never changes. Only `joints` and `joint_count` change per frame, and only `deform.slang` reads them, through a push constant. So the static table stays exactly what it was (device-local, written once, what a `--deform` run without skinning still uses) and the per-frame one is a **separate** host-visible buffer with a region per slot, whose address goes into `DeformParams::deform`. A skinned scene therefore has no host write racing a device read; a rigid one has no second table at all, and no allocation, and no changed instruction.

**Which instances read the pool.** Every instance under `--deform`, and the skinned ones otherwise — so a scene of one character and a hundred props deforms the character and leaves every prop on the rigid path. `ResolvedSettings::deform_pass` is the one flag that says the pool pass runs, and `resolve_settings` is the one place it is decided, because skinning is a *kind* of `deform.slang` and not a second pass.

## The deformed-vertex pool

**The pool holds what the frame deforms, not every instance's whole mesh.** E25 built it the other way: a deformed instance owned a block as long as its mesh's cluster-ordered vertex range, whether the cut touched it or not. That is what kept a cluster's vertices contiguous — a cluster acceleration-structure record points straight at them — and it is what made the pool the binding memory constraint the moment there was a crowd: **12.2 MB for 1,024 foxes, 110 MB for 64 FlightHelmets, 1.7 GB if the 1,024 had been helmets**, to write the 1,325 clusters the frame actually draws. The pool is now a **budget** (`RenderSettings::deform_pool_mib`, 8 MiB by default, `--deform-pool-mib`), suballocated per frame from the visible list.

**The block is the (instance, cluster) pair, because that is the smallest unit that stays contiguous.** A cluster's vertices have to be one run in the pool or the ray side needs a gather it cannot do (E25 decision 2). One instance's cut is a scattered set of clusters in its mesh's vertex stream, so an instance-sized block would have to be the whole mesh again — which is what it was. A per-**visible-entry** block is exactly one cluster's vertices, and the entry is the one name every reader already has in hand: the mesh shader's workgroup, the vertex path's `SV_InstanceID`, the software rasterizer's group, the resolve (through the pair-to-entry table, since the visibility id became the pair), and the CLAS emit pass's `visible_index`. So the address moved from the instance to the entry: `MeshDesc::deform_slots[entry]` is that block's first pool vertex, `gfx::k_no_pool_slot` if it has none. That word replaced the `DeformDesc[]` address in `MeshDesc`, so the struct is still 64 bytes, `DeformDesc` fell from 24 bytes to 16 (`pool_offset` and `vertex_count` were the per-instance block), and a position read is **one indirection shorter**: the base is resolved once per cluster by `deform_base` rather than a `DeformDesc` being read per vertex.

**Why the allocation is on the GPU.** The cut is the cull pass's output and the renderer never reads a buffer back inside a frame (see [Invariants](#invariants)); an allocation computed on the CPU would be a round trip, or a frame late, or an allocation for a cut nobody drew. `deform_alloc.slang` is a prefix sum over the visible entries' vertex counts, dispatched once per run of the list before the pool pass that consumes it — one workgroup, looping the views inside the dispatch, so the three runs and every view share one budget through a groupshared cursor and no global atomic. The cursor advances by what was *placed*, not by what was asked for, which is what keeps a refused large cluster from charging the budget and starving every small one behind it. `gfx::DeformAlloc` (the cursor and three counters) is copied into the per-slot statistics block beside the visible counts and read one frame late, the same way and for the same reason.

**The overflow rule: the rest pose, counted.** An entry the budget cannot fit gets `k_no_pool_slot`, and every position reader turns that into the cluster's **rest pose** — off the 16-bit grid in the rasterizers and the resolve, off the float positions in a CLAS record, which is the same fallback a rigid instance takes and the same code path. So overflow is a character momentarily drawn at rest: never garbage, never a wild address, never a crash. It is also never silent: the renderer logs it once and `Stats::deform_overflow_entries`/`deform_overflow_vertices` reach both hosts' summaries. Measured at the pathological end — 64 FlightHelmets at `--lod 0.05`, a 24,619-pair cut, 8 MiB of budget — 11,508 entries got blocks and 13,111 fell back, and the picture is 0.0040 FLIP (35.2 dB) from the same frame with a 256 MiB pool: a picture, not a failure.

**What overflow costs in reproducibility, stated rather than hidden.** While the cut fits the budget, *which* order the blocks were handed out in never reaches the picture — every entry reads its own block — so a capture is byte-identical run to run, which is what the five FlightHelmet comparisons and the animated `--frames 37` capture check. Past the budget it does reach the picture, because the order is the order the cull pass's atomics appended entries in and that is not the same twice: two runs of the overflowing case above differ by 0.0003 FLIP. Making it reproducible needs the visible list in pair order, which was built and measured on 2026-09-24 and not adopted, at 6–58 µs a frame on the RTX 5090 ([gfx](gfx.md), "The visible list's order"); sizing the budget so overflow does not happen is what the default does instead.

**The numbers** (RTX 5090, `msvc-debug`, 3840×2160, `--orbit 22`, 240 frames; `whole mesh` is what the E25 layout would have allocated and what main's build does allocate). The pool budget is clamped **down** to the whole-mesh figure, so a scene small enough for the old layout allocates exactly what it did and can never overflow:

| Scene | visible pairs | whole-mesh pool | budgeted pool | the cut actually used |
|---|---|---|---|---|
| 1 fox, `--animate` | 8 | 11,940 B | 11,940 B | 5,664 B |
| 100 foxes | 480 | 1,194,000 B | 1,194,000 B | 320,256 B |
| 1,024 foxes | 1,325 | 12,226,560 B | **8,388,600 B** | **597,240 B** |
| 64 FlightHelmets, `--deform wave` | 1,117 | 110,219,520 B | **8,388,600 B** | 804,924 B |

The last row is the point: **13.1× less allocated, and the frame used 0.77 MB of it.** The pool has stopped scaling with the population at all — 1,024 FlightHelmets would allocate the same 8 MiB the 64 do, where E25's layout would have asked for 1.7 GB. What scales with the population now is the slot table, one `u32` per entry of the visible list (`3 × views × pair_count`), which is 360 KB for 1,024 foxes.

### Bounds: the cluster spheres are the rest pose's, and a skinned vertex is not in them

The cull pass tests an instance by its mesh's rest-pose cluster spheres. A skinned vertex is `sum_k w_k M_k p`, which is not in that sphere, so something has to give or a character's swinging limb is culled while it is on screen.

**The decision: one number per instance, computed at load, added to every sphere the cull pass tests.** `gfx::InstanceDesc::bounds_padding` took one of the record's two spare words — so the struct is still 96 bytes and is zero for every instance that existed before, which is why the pictures are byte-identical (a float plus zero is exact). `cluster_cull.slang` adds `bounds_padding * scale_max` to the cluster sphere's radius *and* to both LOD spheres.

Why that and not the alternative, per-frame bounds recomputed from the joint matrices: per-frame bounds are tighter and cost a pass over every cluster of every animated instance every frame, plus an upload of the result, to buy back a fraction of a frustum test that is already one sphere compare. The whole point of the cull pass's flat pair enumeration is that a pair costs a handful of compares; making each one depend on data recomputed that frame is the wrong trade at 1,000 instances, and at 10 it does not matter. A static bound is one `f32` in a record that already existed and nothing per frame at all.

**Why all three spheres and not only the culling one.** Adding it to the LOD spheres as well is what keeps the DAG cut crack-free: a cluster's `parent` sphere *is* its children's `own` sphere, so one constant added to every sphere of one instance leaves the projected errors in the same order and exactly one cluster per DAG path still passes. Add it to the culling sphere alone and the two would disagree at a group boundary. It also errs the right way for quality — a larger radius means a smaller distance, a larger projected error, and therefore a *finer* cut, which is what a limb swinging towards the camera wants.

**Where the number comes from.** `animation::clip_displacement_bound` ([animation](animation.md)) summarizes a clip once, at load: for each joint, and for a sphere of the vertices that joint actually influences, `|M p - p| <= |(A - I) c + t| + ||A - I|| r`, maximized over every keyframe time of every track plus a uniform grid. It is conservative for every vertex and any weights. Two things about it were measured rather than assumed. Bounding each joint by the *mesh's* sphere instead of by the vertices it influences asks how far the tail joint would move a vertex at the nose: on the Khronos Fox that is a padding of 249 units on a mesh of radius 82, and the framing camera pulls back far enough to make the animal a smudge. Splitting the inequality further, into `||A - I|| |p| + |t|`, is looser again, because a rotation about a joint a hundred units up the rig has a hundred-unit translation the centre term is there to cancel. The per-joint form gives the Fox **49.3** on a radius of 82 for its Survey clip and RiggedFigure **0.48** on 0.83.

The bound is a *sample* over the timeline — exact for STEP and LINEAR tracks, because slerp runs along the geodesic between two keys and the displacement it induces is largest at an end of the interval, and dense-but-not-proven for CUBICSPLINE, the one interpolation that can overshoot its keys. What being wrong costs is a cluster culled while a limb is on screen, at one phase of one clip: a hole, not a crash.

The padding is also in the scene's bounding sphere (`update_scene_bounds`), so `--orbit` frames the character wherever the clip puts it rather than only where it rests. That is a real cost and worth knowing: the Fox's framing radius goes from 82 to 131, so the animal is about 60% of the size it would be at rest.

### Normal cones are the rest pose's too, and a padding cannot fix a cone

A padded sphere still bounds a deformed cluster. A **normal cone** does not bound anything once the triangles have turned. Until 2026-09-23 the cull pass applied a cluster's rest-pose cone to every instance of uniform scale, skinned or not. A joint that turned far enough therefore brought round a cluster whose cone still said it faced away, and that cluster was culled in front of the camera. The pass now cone-tests **rigid** instances only (`InstanceDesc::deform == k_invalid_deform`), so a skinned, morphed or `--deform` instance keeps every cluster the frustum, the cut and the Hi-Z keep. Because the pass serves all of them, the mesh shaders, the vertex path, the software rasterizer, the ray path and the shadow structures all see the same change.

It cost nothing measurable where it was measured. On the Fox and RiggedFigure under `--animate`, one instance or a grid of 100, the visible pairs are identical with cones on and off, before the change and after it. Neither mesh has a single cluster with a usable cone for the test to act on. [geometry](geometry.md), "Normal cones", has the numbers, and the two alternatives that were rejected with them: a per-bone cone, which is exact only for clusters bound wholly to one joint (neither sample has one), and a per-frame refit, which would cost at least twenty times the raster work it could remove.

### Ray tracing a moving character

Nothing had to change. A skinned instance is a deformed instance, so `clas_records.slang`'s emit pass already points its records' vertex address into the pool — at the block this frame gave that visible entry, since the pool was suballocated per entry — `--rt-templates` already instantiates the cut's templates from the pool instead of rebuilding, and the resolve's shadow rays already trace against the structures this frame built from this frame's visible list. An entry the pool budget refused points at the mesh's rest-pose float positions instead, which is the same address a rigid instance's record carries, so the ray geometry and the picture stay the same surface. Verified with a capture: a posed bar through `--raster rt` differs from the mesh-shader path on 0 of 1,278 covered pixels in coverage and 1 in triangle, which is what a silhouette costs on a rigid mesh too.

The **reference renderer** inherits that for free, for the same reason: it traces the structures the frame built, so a posed character is path traced in the pose the tick put it in. See [Reference renderer](#reference-renderer), "An animated instance".

## Shadows

**Two implementations behind one query** ([04 §4.4](../plan/04-renderer.md#44-ray-tracing), the 2026-09-23 direction note "shadows without ray queries"). The resolve asks one question per light — how much of it reaches this surface — through one function, `shadow_visibility` ([gfx](gfx.md)), and `ResolveParams::shadow_flags` says how it is answered: by a **ray query** against the frame's own acceleration structures, or, for the sun, by the **cascaded shadow maps** below. `resolve_settings` decides which, once, like every other override:

| `--shadows` | a device with cluster acceleration structures and ray queries (the RTX 5090) | a device without them (the TITAN Xp, every baseline-tier card) |
|---|---|---|
| `auto` (the default) | `rt` on the hw, vertex and rt paths | `csm` on the hw and vertex paths |
| `rt` | `rt`; a warning and none on direct, sw and auto | refused, exit 3 / error 1007, in the verdict's words |
| `csm` | `csm` on the hw and vertex paths; a warning and none elsewhere | the same |
| `off` | none | none |

`auto` therefore keeps the RTX 5090's picture and cost exactly as they were; whether that card should default to maps is **a later decision the flythrough informs** ([the write-up's csm section](../experiments/flythrough-desert-overlook.md)), not one this change made. The maps need a path that rasterizes the picture into the visibility buffer one list per pass and resolves it — `hw` (the mesh path, or the vertex path it falls back to) and `vertex` — and the ray path, which traces its picture, keeps its own shadows. Summaries say what ran: `"shadows": "rt" | "csm" | "off"` (`resolved_shadow_name`).

### Ray-traced

With `ShadowMode::RayTraced` (or `Auto` on a device that can trace), the resolve traces one terminate-on-first-hit ray per light, from the surface offset along its geometric normal by `FrameLighting::shadow_bias`. The rays go against the top-level structure the frame built from its own cull output, which is why a raster mode with shadows on runs the whole records-to-TLAS chain and why shadows turn two-pass occlusion culling off: the structures are built from the visible list, and pass 2's survivors would be in a second one. **A shadow is cast by the frame's own cut, at the picture's LOD.** It is not a finer level and not a second selection, so the shadow of a distant object coarsens exactly as its picture does.

**What the frame builds is the picture's clusters plus its shadow casters** (since 2026-09-24). The cull pass's cone test drops a cluster whose triangles all face away from the *camera*, and a cluster can face away from the camera while facing the light. Until that date such a cluster stopped casting as well. A card seen from behind threw no shadow, and a prop on a floor seen from the side lost part of the shadow it throws on the floor: the SciFiHelmet up to 4,627 pixels of a 1280×720 frame, the BoomBox 60,689 pixels of a point light's shadow. [geometry](geometry.md#facing-away-from-the-camera-is-not-facing-away-from-a-light-shadow-casters) has the fixture, the samples and the three remedies that were weighed. The one chosen keeps the picture exactly as it was:

- `ResolvedSettings::casters` is true when shadows are traced, the cone test is on, `RenderSettings::shadow_casters` is set (the default), and the chain builds records rather than instantiating templates. It is decided in `resolve_settings` like every other override.
- The cull pass keeps a pair that passed the frustum test and that the cone test alone rejected. It runs that pair through the cut and the page residency like a drawn pair and appends it to the visible list's **third run** (`gfx::k_caster_run`) under the software argument block's counter. A frame that traces shadows has no software pass and no occlusion pass 2, so that run and that counter are free, and the renderer asserts they are. No rasterizer reads the run, and the deformed-vertex pool never sees it: a caster is always rigid, since a deformed instance is never cone-tested.
- The records pass builds the caster run of every view beside run 0, into the same per-instance structures, **non-opaque**. The shadow rays (`RAY_FLAG_FORCE_OPAQUE`) stop on a caster. The ray path's primary rays and the reference path tracer's camera rays (`RAY_FLAG_CULL_NON_OPAQUE`) pass through it, so `--raster rt` still draws the raster picture word for word, and the reference still sees what the frame sees. The reference's bounces and shadow rays hit casters like any surface, which is what they should do.
- `Stats::shadow_casters` (and `ViewStats::shadow_casters`) counts them, one frame late like the visible counts. The software block's count goes there instead of `visible_sw` in such a frame, so `visible_pairs()` still counts only what is drawn. engine-view's summary prints `shadow_casters` (the setting) and `shadow_casters_last`, and `render.benchmark` returns `shadow_casters`. `--no-shadow-casters` and the protocol's `shadow_casters: false` restore the old behaviour, to measure against.

At the default cut the casters are 0 to 19% of the cut on the Khronos samples, and building them costs nothing measurable. At the FlightHelmet's finest cut, 74 casters beside 1,028 drawn pairs cost the chain 0.011 ms, about 0.14 µs a caster. Two things are **not** covered. `--rt-templates` keeps no casters, because an instantiated cluster is opaque whatever its record says. A caster **outside the camera frustum** still casts nothing: a tree behind the camera throws no shadow into the view. That is the larger half of the same trade. The cascaded maps below close it for their own shadows — their cull is from the light — and the test that says so draws the ray-traced shadow of the same off-frustum card as 0 pixels; the ray-traced path needs the same light-space cull for its structures, which belongs with their sizing and is not in this change.

**`--view shadow`** (`gfx::ResolveMode::Shadow`) draws the sun's shadow query alone. White is lit, black is blocked, and mid grey is a surface facing away from the sun, where nothing is asked. It asks the shaded view's exact question, which makes it the picture to count a shadow difference on, and the shadow tests do. A ray answers black or white; the cascaded maps answer the filtered fraction, so their penumbra is grey between the two.

### Cascaded shadow maps

`ShadowMode::Cascaded`, or `Auto` without ray queries: the sun's shadow from depth maps drawn **from the light by the same cull pass and the same rasterizers the visibility buffer uses**, filtered by the resolve. `ResolvedSettings::csm` and `shadow_cascades` say a frame draws them; `RenderSettings::shadow_cascades` (1–4, default 4), `shadow_map` (texels a side per cascade, a power of two, default 2048) and `shadow_distance` (how far from the camera they reach; 0 is the far side of the scene's bounds) size them — `--shadow-cascades`, `--shadow-map`, `--shadow-distance` and the protocol's fields of the same names.

**The fit** (`fit_shadow_cascades`, `shadow_cascades.h`, on the CPU once a frame). The camera's depth is cut into slices **logarithmically from where geometry can begin** — the near side of the scene's bounds, or the near plane when the camera is inside them — to the shadow distance, with the logarithm's base never under a thousandth of that distance, so a camera standing in a 5 km terrain does not spend its first cascade on its own feet (on the desert overlook's scale the splits are about 11, 63, 356 and 2,000 m for 2 km of shadow). Each slice's cascade is the **smallest sphere centred on the camera's forward axis** that holds the slice's corners in every view of the layout — a sphere because it is the same size whichever way the camera turns, so a turning camera keeps its texels and a static shadow does not swim; its radius is rounded up to a 64th of its power of two so float noise cannot change a texel's size between frames; and its centre is **snapped to a whole texel across the light** (`gfx::shadow_snap`), so a moving camera moves the grid by whole texels. A cascade whose sphere would hold the scene's whole bounds is replaced by them and is the last: every receiver is inside it. That is the common case for a camera framing an object — engine-view's orbit frames a mesh with a frustum wider than the mesh, so its first slice already holds it and the frame draws **one** cascade with every texel on the scene (about a 1,024th of the scene's diameter a texel at 2048). A cascade's depth runs from the sphere's far side, away from the light, **to the far side of the scene's bounds towards the light**, so it holds every caster between the light and its receivers — including one outside the camera's frustum.

**The light-view cull.** Each cascade is one more **run of the visible list, behind every view's three** (`GpuScene::cascade_base`), with its own indirect block (`shadow_args`) and, on the vertex path's indexed draw, its own header, records and index array behind the views' two runs; the camera's runs, and everything indexed by them — the ray chain's union, the census, the pool's allocation of the camera's runs — are exactly where they were. The cull pass runs once per cascade (`cull_main` or `cull_vertex_main`, whichever the picture uses) with the cascade's six planes, **no normal cones** (a caster's facing to the camera says nothing about the light), **no occlusion** (there is no Hi-Z from the light), no pair-to-entry table (the resolve decodes the picture's pairs, never a cascade's), everything to the hardware run, and **the camera's own LOD**: its eye, its projection scale and its threshold (the finest view's under a multi-view layout). The cull pass needed no change for it: its LOD test never looks at the frustum, so for every pair in both a view and a cascade it makes the same decision it made for the picture. **A shadow's LOD is therefore the picture's LOD** — a receiver's own triangle is in the map at exactly the depth the resolve reconstructs it at, which is what lets the bias be the receiver's plane rather than a guess — and a caster outside the frustum is drawn at the LOD the camera would draw it at from where it stands. The alternative, a cut chosen from the light's own view, would put a different triangle of the receiver in the map; `RenderSettings::shadow_lod_scale` (measurement only) coarsens the cascades' cut against the picture's, and the Khronos measurement below says what that does. A streamed scene's cascades read the frame's residency and ask for the pages they miss, like the picture's cull. A deformed or skinned instance's cascade entries get **pool blocks of their own**, allocated behind the camera's runs by one more dispatch of the same allocator (`DeformAllocParams::first_entry`) and deformed by the same pass, so a moving character casts its pose; the pool's small-scene clamp allows the whole meshes once per cascade as well.

**Drawing.** One raster pass draws every cascade into its tile of a single **D32 atlas** (`shadow_map × cascades` by `shadow_map`, 64 MiB at the defaults; reversed depth, cleared to 0, greater-or-equal) through **the picture's own rasterizer with no fragment stage**: the mesh path's mesh stage, or the vertex path's indexed draw and its fallback (or the capacity draw), with each cascade's viewport flipped like every raster pass. The triangles come off the same 16-bit grid or the same pool block through the same arithmetic as the picture's, and the mesh and vertex paths write the same map — the tests hold their shadows equal to the byte.

**Reading** is gfx's ([gfx](gfx.md), "The sun's cascaded shadow maps"): the first cascade whose tile holds the filter's footprint, a **3×3 bilinear PCF** (a 4×4-texel footprint, weights (1 − f, 1, 1, f)/3 per axis) evaluated as four gathers, and a **receiver-plane bias** — each texel compared against the receiver's own plane at that texel's centre, plus `k_shadow_bias_texels` (half a texel) for what is not flat, with the slope clamped at `k_shadow_max_slope` (tan 83°); and a **normal offset** — the point looked up leaves the surface along its geometric normal by `k_shadow_normal_offset_texels` (three texels of the cascade read) times (1 − N·L), for the concave creases and the terminator of a low-poly curved surface, which a plane cannot describe. `RenderSettings::shadow_normal_offset` overrides it for measurement. The maps shadow **the sun alone**: the two orbiting point lights are unshadowed under them.

**Measured on the Khronos samples** (the skipped case `renderer: cascaded shadow maps on the Khronos samples`; the tables are in [the experiment](../experiments/cascaded-shadow-maps.md)). Seven samples, each on a ground six radii wide, from sixteen cameras at 1280×720, in the shadow view, mapped against ray-traced on the RTX 5090: a pixel is interior when the rays give it and every pixel within three of it the same answer, and there the maps must give that answer too. **At the picture's cut, with the normal offset, the two never give opposite answers: 0 of 6.35–7.40 million interior pixels on every sample**, which the case asserts; the maps answer grey (partly shadowed) on 0.03–0.3% of them, where the 4×4 footprint of the last cascade reaches past the three-pixel band. Without the normal offset the maps shadowed 162–21,627 interior pixels that the rays lit, every one on a sample's own surface — at the terminator of its low-poly curves and in its concave creases — and an offset of two texels left 0–3, three 0, four 0 with less grey; three is the default, the smallest that gave 0 everywhere. **A cascade cut coarser than the picture's brings the self-shadowing back**: with the cascades' LOD threshold doubled, 16–8,436 interior pixels are shadowed that the rays light, quadrupled 113–38,888, and the first leaks appear (34–104 lit where the rays shadow). The receiver's own triangle in the map is then not the one the resolve reconstructs, and no plane predicts that difference. That is the measurement behind "a shadow's LOD is the picture's LOD". What they cost at engine-view's own camera: the maps' passes 0.013–0.021 ms, 0.010–0.011 ms of it the culls, and 0.009–0.010 ms more in the resolve for the filter. The frame is 0.088–0.107 ms, against 0.068–0.077 ms without shadows and 0.18–0.25 ms with rays (the chain before it was sized by the frame). A coarser cut saves at most 0.002 ms, because at these sizes a cascade costs its dispatches, not its pairs.

**Statistics.** `Stats::shadow_pairs` (the pairs drawn into the maps, summed over the cascades), `Stats::shadow_fallback` (the cascades' survivors the indexed draw's budget sent to the fallback, logged once), `gpu_shadow` (every pass that draws the maps: the culls, the cascades' pool and index passes, the depth raster) and `gpu_shadow_cull` (the culls' share); the filtering is in `gpu_resolve`. They reach engine-view's summary (`shadow_pairs_last`, `shadow_fallback_last`, `gpu_ms.shadow`, `gpu_ms.shadow_cull`), `render.benchmark` and the flythrough's per-frame records. `SceneRenderer::shadow_cascades()` is the fit the last frame used.

**What it does not do.** Point and spot lights cast no mapped shadow (a cube map or a perspective map each, and the ReSTIR-sampled lights of §4.4 are the plan's answer for them); the RTX 5090's rays still shadow them under `rt`. There is **no blending between cascades**, so the penumbra's width steps where one cascade hands over to the next. Nothing is cached between frames: every cascade is culled and drawn every frame, even where the light, the geometry and the cascade have not moved. And the far cascade of a large scene covers its whole far side at the camera's LOD, and every cascade holds whatever lies beside and behind the view inside its sphere. Along the desert overlook's path that is seven to fourteen times the picture's pairs with occlusion culling on. It costs the RTX 5090 0.10–0.26 ms of median frame; the ray-traced chain, sized by the frame, is 0.40–0.61 ms at 1080p ([The ray tracing chain's memory](#the-ray-tracing-chains-memory)). It costs the TITAN Xp 0.60–1.22 ms, and its maps' passes reach 1.9 ms at 4K p95 ([the flythrough's rows](../experiments/flythrough-desert-overlook.md#cascaded-shadow-maps-rtx-5090-and-titan-xp)). `--shadow-distance` bounds it today; a tighter caster volume and cached far cascades are the follow-ups.

## The ray tracing chain's memory

**The per-frame structures are sized by what the frames build, not by what the scene could build** (2026-09-24). Until then `GpuScene::create_ray_tracing` created the cluster acceleration structure set for `views * pair_count` clusters — every (instance, cluster) pair in every view, because any of them *could* be in some frame's cut — and the driver reserves every one of those at its worst case: **6,144 bytes** a cluster of 124 triangles and 64 vertices on the RTX 5090 at driver 610. The desert overlook with the owner's landmarks as a three-monitor surround is 2,629,611 such clusters, so the set alone was 16.2 GB and the process 20.6 GB, for a path whose frames build at most 43,291 (the [flythrough](../experiments/flythrough-desert-overlook.md#the-ray-tracing-chain-sized-by-the-frame)). The chain's per-frame half is now held a step above what recent frames built, and the scene-sized half is what is left:

| Part | Sized by | Cost |
|---|---|---|
| CLAS build (or instantiate) records | the capacity | 64 bytes a cluster (32 instantiating) |
| the CLAS set: storage, addresses, sizes | the capacity | the driver's worst case (6,144 bytes) + 12 bytes a cluster |
| every instance's bottom-level structure, one set | the capacity | about 43 bytes a cluster reference, one buffer |
| the scratch the three builds share | the capacity | the largest of the three builds' |
| the records pass's bucketing scratch (`slots`) | the scene | 4 bytes a pair a view — 10.5 MB for the overlay surround |
| per-instance counts, bottom-level records, top-level structure and its instance records | the instances | a few hundred bytes an instance |
| the 8-bit indices and the float positions the builds read | the geometry | 3 bytes a triangle, 12 a vertex (paged when streamed) |
| cluster templates (`--rt-templates`) | the clusters | what each one occupies, packed (below) |

`GpuScene::rt_bytes()` is all of it, at the current capacity; `rt_capacity()` is the capacity in clusters, `rt_capacity_limit()` the budget as one, `rt_union_clusters()` the old size, and `resize_ray_tracing(n)` replaces the per-frame half — with the device idle, which the caller guarantees — and nothing else: the top-level structure, its bindless slot and every scene-sized buffer stay, so the next frame simply imports the new buffers.

**The policy is `RtCapacity` (`rt_capacity.h`), and it is arithmetic only**, so its hysteresis is tested on the CPU. `SceneRenderer::begin_frame` feeds it each folded frame's demand — the records pass writes what it built and what it wanted into `record_count`, and the frame's statistics copy both out, one frame late like the visible counts — and resizes the scene when it answers with a different capacity. **It grows ahead**: as soon as a frame's demand has eaten half the headroom (`renderer.rt.headroom_pct`, 25), to the demand plus the whole headroom rounded up to a step (`renderer.rt.step_clusters`, 4,096 — 24 MiB of structures). **It shrinks late**: only when a whole window of `renderer.rt.shrink_frames` frames (240) has peaked at under half of what it holds, to that peak plus the headroom. Between those events nothing is allocated, and an event is a wait for the device and a new set of buffers — a hitch, on a trend rather than on a frame. Along the desert path the demand moves by at most 1.7% a frame (p99 0.6–0.9%), so the headroom is many frames of warning; on it the chain resized 2 to 27 times in a run of three flights and their warm-ups, and no frame of any run dropped a structure. **The first capacity** is the whole union when that fits under both the budget and `k_initial_rt_clusters` (65,536 clusters, 400 MB), which is every scene the tests draw and so every picture they pin, and 65,536 otherwise — above every first frame the desert path draws at any resolution.

**The budget is a ceiling, and what happens past it is a stated rule.** `RenderSettings::rt_budget_mib` (`--rt-budget-mib`, the protocol's `rt_budget_mib`; 0 takes the `renderer.rt.budget_mib` tunable, 1,024 MiB) becomes a cluster count through what the driver says one costs (`rt_bytes_per_cluster()`, from `gfx::cluster_set_build_sizes` and `cluster_blas_set_build_sizes` at a probe count: 6,397 bytes on the RTX 5090, so 1 GiB is 167,850 clusters). A frame that wants more than the capacity holds — past the budget, or in the frames before a growth lands — keeps what fits by `clas_records.slang`'s rule ([gfx](gfx.md)): every instance's drawn clusters in instance order while they fit, an instance that does not fit skipped whole (its casters with it), then the other instances' casters the same way. **What that costs is the picture's shadows, and under the ray path its surfaces**: an instance that lost its structures casts no shadow and is missing from a traced picture; one that lost only its casters loses the shadows of the surfaces facing away from the camera; a rasterized surface is the rasterizer's and never changes. Whole instances, because a partial one would keep whichever clusters the atomics bucketed first and so differ run to run; casters first, because they are the part of the shadows a viewer is least likely to miss. `Stats::rt` (`RtStats`) counts every frame that did it and the instances it dropped, and the renderer logs it once. It is not the cut that degrades — the picture's LOD is the raster path's, and a coarser ray cut would break the word-for-word match between the two that the ray path is tested against.

**A frame somebody waits for is drawn complete.** The policy learns a frame's demand after the frame, so the first frame of a large scene, a camera cut or a finer LOD can want more than the chain holds, and a frame drawn in flight lives with that for the one or two frames a growth takes to land. `render_offscreen` — which every capture, the reference renderer and the tests go through — does not: when the frame it waited for dropped anything and the budget has room, it grows the chain to fit and draws the frame again, with the policy held still for the redraw. `FrameDesc::rt_complete` goes further, past the budget up to the whole union, and only the reference renderer sets it: its one real-time frame is the geometry a converged picture traces, and `--finest` makes that every leaf in view. The next ordinary frame brings the chain back under the budget.

**One bottom-level build, not one per instance.** Each instance used to have its own cluster bottom-level structure, created for its mesh's clusters in every view and built to an explicit destination, so the host could write the top-level records once — which summed over the instances is `views * pairs` again, and was 90 builds a frame on the desert overlook, each waiting for the last because they shared the scratch. They are now one `gfx::ClusterBlasSet`: every instance's structure in one command with implicit destinations, into one buffer sized for the capacity's worth of references. The structures' addresses are then known only on the device, so the top-level instance records — transforms and custom indices written once, at load, device-local — take them by one copy of eight bytes an instance (`GpuScene::rt_instance_copies`) between the bottom-level and top-level builds, declared to the render graph like every other pass. An instance the frame built nothing for gets a null reference, which the top-level build treats as inactive. The chain's GPU time fell six- to sevenfold along the desert path — from 2.54 to 0.40 ms at 1080p on the substitute set, from 7.08 to 0.97 ms on the landmarks' surround — with the cluster build itself unchanged to within 2%; the one bottom-level build is 0.14–0.19 ms.

**Templates are packed to what they occupy** (`--rt-templates`). They are built once per cluster at load, so they stay scene-sized, but they were reserved at the driver's worst case — about 2.2 KB a template, against the 504–532 bytes the desert overlook's occupy. `gfx::create_packed_cluster_templates` sizes them first (the template build in `COMPUTE_SIZES` mode), packs them on the host and builds them into exactly that (`EXPLICIT_DESTINATIONS`), with its scratch freed afterwards. On the desert overlook the templates made the process 434 MiB larger with the substitutes and 947 MiB with the landmarks — the reservation and a record buffer kept after the build — for 104 and 222 MB of templates; packed they are 111 and 238 MB, and the record buffer is freed once they are built.

**The KHR fallback has nothing per frame to size.** [ADR-0025](../adr/0025-cluster-acceleration-structures.md)'s KHR bottom-level path is built and traced in `domain/gfx`'s own tests, where `create_blas` is sized from the geometry list it is handed — the cut — and it is not wired into this module ([gfx](gfx.md#what-a-device-has-to-have)); the one KHR structure here is the top-level one, sized by the instances.

**The numbers** (RTX 5090, `msvc-release`, the desert overlook's path with `--shadows rt`, three repeats after 240 frames of warm-up, [the write-up](../experiments/flythrough-desert-overlook.md#the-ray-tracing-chain-sized-by-the-frame) has the machine state of every run):

## Built textures

The texture upload (`GpuScene::upload_materials`, the only place in the module that knows) takes
a mesh's images one of two ways. **Built**, when the load reads the derived-data cache and every
image the resolve samples — base colour, metallic-roughness, normal, occlusion, emissive — has a
`.tex` in `<ddc>/textures/` whose recorded identity matches: the container's records say where
(`SourceMesh::textures`, section 32 of the `.clusters` file; [geometry](geometry.md#built-textures-where-each-images-texture-is)),
an image the container carries by its recorded key and an image named by path by the file's bytes
as they are now, so a repainted file finds its new texture or none. Those upload as stored, every
level (`gfx::upload_image_2d_levels`), sample through mipmapping, anisotropic samplers ("Materials"
below), and carry `k_material_mipped` — plus `k_material_normal_rg` for a BC5 normal map — so the
resolve samples them with the UV derivatives it computes from the triangle
([texture](texture.md#mip-selection-without-quads)). **Decoded** otherwise, as before: the image
decoded on the CPU, uploaded RGBA8 at one level, level-0 reads, flags zero, through samplers that
read level 0 alone — with the file's wrap and filters since 2026-09-24, where the decoded path used
to clamp, so a decoded texture's picture moved within half a texel of its edges and wherever its
UVs leave [0, 1]. It is **all or nothing per mesh**, so no material mixes the two, and the log says which and why
(`mesh textures`, `from: built|decoded`, `reason`). A device without `textureCompressionBC` gets the
decoded path and a warning naming the feature. `GpuScene::texture_bytes()`, `textures_built()` and
`textures_decoded()` report what happened — distinct textures, since one upload serves every mesh
that samples the same image ([below](#one-upload-per-distinct-image)) — and engine-view prints them
as `"textures":{"built","decoded","distinct","shared","bytes","bytes_saved","sharing"}`.

**The renderer builds them itself on a cold cache.** A load through the derived-data cache
(`SceneDesc::cache`) runs the content build's texture step (`content_build::run_texture_step`,
the function `engine-content build --cache` runs) for every mesh it reads: beside the container it
writes when it clusters a glTF itself, and on a cache hit for whatever of the container's textures
is missing. An entry whose recorded identity already matches is found, not rebuilt, so a warm load
pays a read and a hash per image. Until 2026-09-24 only engine-content built textures, so a scene
flown without running it first — every `engine-view --mesh <file.gltf>` on a fresh cache, and every
scene file whose meshes the renderer clustered itself — drew its textures decoded at one level,
with no mips, and shimmered at a distance; the session-diagnosis run on the desert overlook is
where that was seen. The `.tex` it leaves is byte for byte engine-content's (`texture_tests.cpp`,
"a glTF on a cold cache"), because the step, the records and the keys are the same code. A texture
that cannot be built is a warning (`texture not built`) and its mesh draws through the decode.

The reference path tracer samples the same textures at level 0, as it always sampled everything: it
is a compute pass with no derivatives, and a converged reference is not the place for a filter
footprint. Its BC5 normal maps go through the same z reconstruction as the resolve's.

## One upload per distinct image

**A scene uploads each distinct texture once, however many of its meshes sample it** (since
2026-09-25). `upload_materials` keys every (mesh, image) a material samples by what the texture is
made from, and a key the scene already holds hands back the bindless slot of the texture already
uploaded instead of uploading again:

- **built**, by the `.tex` build key, `texture::texture_cache_key(source hash, options)`: the
  image's encoded bytes and everything the build was told about them — format, colour space, the
  edges its samplers wrap with ([texture](texture.md#the-derived-data-cache-and-the-containers-records)).
  Two images with one key are one file in the derived-data root, so they are one texture.
- **decoded**, by `hash_bytes` over the encoded bytes — embedded, or the file as it is now — and
  the format the image goes up as (sRGB for colour, UNORM for data): the decode is a function of the
  bytes, and the format is the rest of what the device holds.

Each mesh still chooses between the two on its own, all or nothing, so a built texture and a
decoded one never share (they are different images on the device). A key the scene already holds is
not read from the derived-data root again — `find_built_textures` skips the read, since the mesh
that uploaded it checked its identity — and not decoded again: a repeat costs a hash on the decoded
path and nothing on the built one. The entry keeps both halves of its key and is compared whole, so a
64-bit collision between two different images uploads the second again rather than drawing the
wrong one.

**Why the key is the content and not the path.** The duplication this removes is a kit's. E33's
ashlar kit is nineteen GLBs exported one by one, and each embeds the same six images — the block's
and the mortar's base colour, normal and ORM, 16.2 MB of JPEG — so each member uploaded its own
copy of them: 99 textures for 6 images, and one building could hold the atlas nineteen times
([E34](../experiments/e34-ruin-blocks.md), [ruins](ruins.md#the-kit)). An embedded image has no path
at all. Where images are files, a path is both too strict and too loose: two paths name the same
bytes whenever each member's folder carries its own copy, and one name holds different bytes in
every kit that calls its atlas `atlas.png`. The content is the identity the derived-data cache
already addresses a texture by ([ADR-0036](../adr/0036-built-textures-in-the-engines-own-container.md)),
so on the built path the key costs nothing new — the container's record carries it for an embedded
image, and a file is hashed as it is now anyway, which is also why a repainted file finds its new
texture — and on the decoded path it costs a hash over bytes that were about to be decoded.

**What it keeps.** The picture: every material reads the same texels through the same sampler,
from a slot another mesh made. `texture_tests.cpp` holds a kit's picture — ids, depth and colour —
to the byte against every member's own upload, from the decoded images and from the built textures,
and so do the captures below. The bindless set spends one sampled-image slot per distinct image
rather than per member. **Samplers were already shared this way**: one per distinct description
(wrap s, wrap t, filters, mipmapped), scene-wide ([Materials](#materials)).

**Lifetime: the scene's.** The textures are made with the `GpuScene`, owned by it and destroyed
with it, and nothing counts them per instance. A streamed world's tail of instances
([Instances that come and go](#instances-that-come-and-go)) takes its mesh's material base and
nothing else, so a tile's buildings arriving and leaving uploads no texture; the test gives a scene
of one instance the rest as a tail between frames and requires the same two textures, the same bytes
and the same picture, and the E35 world below uploads the kit's six once and none in the 62 tails of
its flight. **Nothing is shared across scenes**: two scenes engine-host holds at once
each upload their own, because a texture's lifetime is its scene's and a host-wide table would
need an owner that outlives every scene and a rule for when an entry dies, neither of which exists.

**What it reports.** `GpuScene::textures_built()` and `textures_decoded()` count distinct textures;
`texture_references()` the (mesh, image) pairs that reached one, `textures_shared()` those that took
one the scene already held, and `texture_bytes_saved()` what their own copies would have cost on the
device. The load logs it once (`scene textures`: `distinct`, `references`, `shared`, `bytes`,
`bytes_saved`, `sharing`). engine-view's summary has `"textures":{"built","decoded","distinct",
"shared","bytes","bytes_saved","sharing"}` and a flythrough's summary line the same block
(`engine.scene.FlythroughTextures`, through `summarize_textures`); `render.scenes` and
`render.unload` add `textures_shared` and `texture_bytes_saved` beside `textures` and
`texture_bytes`. `RenderSettings::share_textures` false — `engine-view --no-texture-sharing`, the
protocol's `"share_textures": false` — uploads every mesh's own copy again, which is the build
before this one, kept to measure against and to hold the picture to.

**What it measured** (RTX 5090, driver 610.88, `msvc-debug`, E33's ashlar kit from a derived-data

## Materials

**What a material table entry carries** (`gfx::ResolveMaterial`, 112 bytes; [gfx](gfx.md), "The
material table"): the factors, five texture slots — base colour, metallic-roughness, normal,
occlusion, emissive — a bindless sampler per slot, the occlusion strength, and one UV transform.
`upload_materials` fills it from `assets::Material`, which the glTF import or a container's
section 33 filled ([texture](texture.md#samplers-and-texture-transforms)).

**Samplers, one per combination.** A slot with a texture asks for the sampler its glTF texture
names — wrap s and t, the three filters — built (the whole chain, 16x anisotropic where the
minification is linear) or decoded (level 0 alone), and `upload_materials` makes one bindless
sampler per distinct combination the scene asks for, shared by every material after the first that
asked (`GpuScene::material_samplers()`, logged as `material samplers`) — keyed by that description,
as the textures are keyed by their content ([One upload per distinct image](#one-upload-per-distinct-image)),
so a kit whose members all ask for the glTF default draws through one. A slot with no texture asks
for none and borrows the base colour's slot word, which it never reads. The classic heightfield keeps
its own clamped tooling sampler, uncounted. Every sample in `content/samples` names the glTF default
sampler or none, so each of them draws through **one** material sampler.

**The UV transform is one per material** — the base colour's, or the first textured slot's — and a
material whose other textured slots ask for a different one is counted
(`GpuScene::transform_conflicts()`) and logged with a warning; it draws every slot with the one kept.
The container keeps them per slot, so carrying more is a table change and not a rebuild.

**Emission** is the factor times the emissive texture, added after the lighting in the resolve and
wherever a ray lands in the reference. Before 2026-09-24 a material with an emissive texture drew
with no emission, because the resolve had no slot for the texture — which is what the Lantern's
glass did in both pictures, and what `thin-geometry`'s FLIP band was set against. **v1 treats
emission as radiance only** in the reference: seen directly and by bounce rays, never sampled as a
light ([texture](texture.md#emissive)).

**What it cost and what it changed** ([texture](texture.md#what-the-samplers-emission-and-occlusion-cost)):
the resolve 2–5% slower on the FlightHelmet at 1080p and 4K, about half of it the occlusion;
against the reference, `flighthelmet` from 0.0190 to 0.0172 FLIP and `thin-geometry` from 0.0051 to
0.0048 — both towards it — and every other scene of the corpus where it was.

**Occlusion** multiplies the resolve's indirect term — the sky hemisphere today — and nothing else,
and is never applied in the reference, which traces that visibility. `--view occlusion`
(`ResolveMode::Occlusion`, `render.load`'s `"view":"occlusion"`) shows the value unencoded beside
`--view albedo`: a captured byte is the occlusion times 255 ([texture](texture.md#occlusion)).

**What it measured** on the FlightHelmet (RTX 5090, `msvc-release`, 600 frames windowed at three
orbit distances and two resolutions; the table and the machine's state are in
[texture](texture.md#what-it-measured)): the fifteen images take **71.3 MB** of device memory built,
every level included, against **213.9 MB** decoded at one level; the resolve moved by no more than
3% against the parent commit either way (2–3% slower up close for the derivative pass, 3% faster
far away at 4K); and the decoded path's capture is byte-identical to the parent commit's.

## Geometry streaming: the GPU half of pages and residency

[04 §4.3](../plan/04-renderer.md#43-geometry) step 3 and [§4.9](../plan/04-renderer.md#49-streaming-and-residency) ask for clusters in fixed-size pages, GPU feedback that requests them, a CPU that streams them, and a residency budget that evicts by last use. [geometry](geometry.md) built the CPU half — the layout, `select_lod_streaming`'s drawing rule, and `PageResidencyManager`'s priority heap and ancestor-closed eviction. `systems/renderer/streaming.h` is the half that runs beside a frame, and `--stream` on either host turns it on.

**What is paged and what is not.** The descriptors stay resident whatever the budget: `geometry::ClusterDesc`, `geometry::ClusterLodDesc`, the material index, the page table, `page_of_cluster` and the per-cluster child ranges — 112 bytes a cluster plus 48 a page. Everything a cluster costs *in bytes* is paged: six bytes of quantized position and eight of attributes a vertex, four bytes a triangle, and — when the frame builds acceleration structures — twelve more bytes of float position and three more of 8-bit index. That is about 7% held to stream the other 93%, and the split is not a compromise: the cull pass tests **every pair of every frame** and has to be able to say "not that one" about a cluster whose payload is not here, so its inputs cannot themselves be streamed without a second level of the same problem.

**The drawing rule, on the GPU.** `cluster_cull.slang` implements `select_lod_streaming` exactly: draw a cluster when its page is resident **and** its projected parent error is over the threshold **and** (its own error is at or under it **or** the pages holding its children are not all resident). The last clause is the fallback that makes a starved budget coarse rather than holey. Both residency tests are over a whole *group* in the CPU model, and the GPU tests one cluster's page instead — which is the same thing, because `build_cluster_pages` never splits a group across pages (it closes the open page before a group that would not fit and gives a group that fits in no page one of its own). `GpuScene::create_streaming` checks that before it uploads a page table, because the rule is crack-free only while it holds.

**Feedback.** A cluster that wanted to refine and could not appends a `geometry::PageRequest` — the page, the projected diameter in pixels of the requesting cluster's sphere, and the distance to it — to a bounded buffer under an atomic, **deduplicated behind a per-page mask word** that the first lane exchanges, so a page a thousand clusters want costs one twelve-byte entry and not a thousand. A cluster that is drawn sets a "used this frame" word for its page, which is what gives the manager's LRU something to order by. All three arrays are cleared by the frame's reset pass and copied into a per-frame-slot host-visible buffer at the end of it; the CPU reads them when the slot comes around, which is `frames_in_flight` frames later and is the same deferred pattern the visible-pair counts already use. **The frame never waits on the device**, and the price of that is that a page a camera jump asks for arrives two or three frames after it was wanted — which is exactly what the fallback clause is for.

One thing the GPU does not reproduce: the CPU reference keeps the *best* priority of every cluster that asked for a page, and the GPU keeps the **winning lane's**. A lock-free best-of would be two more atomics on every losing lane and it buys nothing over a frame or two, because `PageResidencyManager::request` keeps the best of every request it sees and a queued page's key can only improve.

**The page pool, and why the offsets are patched.** The paged streams are a pool of fixed-size slots, each sized for the largest page's vertex and triangle counts. When a page lands in slot *s* the host rewrites that page's `ClusterDesc::vertex_offset` and `triangle_offset` to point into slot *s* and uploads the 48-byte records with the payload. **Nothing in any shader changes.** The alternative — leaving the offsets page-relative and having the shader add `slot_base[page_of_cluster[c]]` — would need two more addresses in every pass that reads geometry, and `gfx::ClusterDrawParams` is full at its 128-byte push limit while `gfx::MeshDesc` is full at 64: the indirection has nowhere to put them without restructuring the rasterizers', the resolve's and the CLAS records' blocks. It would also cost two dependent loads on every position read, where patching costs one memcpy of 48 bytes a cluster on a page that is being copied anyway. See [gfx](gfx.md) for the measurement.

**How many slots, and what an eviction is.** The budget is in page bytes and the pool is in slots, and the two have to agree on the worst case or a frame would admit a page with nowhere to put it. The bound is exact and cheap: sort the pages by size and take them smallest first until the budget is spent — no set of pages within the budget can be larger than that count. Real pages are 85–95% full, so the pool is about a tenth larger than the budget it serves, which is the price of a fixed-size slot and is what makes an eviction *a slot handed back* rather than a compaction. Two consequences are worth knowing. The pool can run out of slots while the byte budget still has room, and then the slot is the budget: one eviction is forced by lowering the manager's own budget for the length of the call, which takes the least recently used page with nothing under it exactly as a byte-driven eviction would. And **a freed slot retires for `frames_in_flight` frames** before it is filled again, because the frames still on the queue carry residency words that say the page is resident and their draws read that slot.

**Uploads.** A staging ring with one region per frame slot and a per-frame byte budget (`--upload-budget`, 256 KiB by default; a value under the largest page's payload is raised to it, because a budget no page fits in never converges). A frame copies what it staged in one transfer pass before the cull pass, so a page that arrives is drawn in the frame it arrives in. Nothing is allocated in steady state: the ring, the scratch for a page's patched descriptors, and the heap the manager queues in are all sized once.

**Two invariants, and the one that cost an afternoon.** The manager keeps residency ancestor-closed: requests only ever come from a resident parent, and eviction only ever takes a page with no resident child. The renderer has to keep a *second* copy of that on the pool, because the pool lags the manager by an upload budget — a page the manager holds but whose bytes are still in the queue is invisible to the cull pass. Two rules do it: pages are staged in **page order**, which is coarse first and therefore parent before child, and **nothing new is admitted while the pool is behind the manager**.

That was not enough, and the case that broke it is the one [04 §4.9](../plan/04-renderer.md#49-streaming-and-residency) calls "cancellation of requests that became stale". A request arrives with a resident parent, by construction. But a queue is not served in the frame it was filled in, and by the time a page reaches the front of the heap the parent that asked for it may have been evicted — and admitting it then puts the fine geometry back under a hole, which is precisely the grandparent case the invariant exists to prevent. It showed up as one page in sixty, resident with nothing above it, and only under a budget tight enough to evict every frame. `PageResidencyManager::drop` is the removal the fix needed and `GeometryStreamer::may_admit` is the test: a page is still loadable if it is pinned, if it spans two DAG levels (such a page holds its own parents, and the child list leaves it out of its own run — which is a second thing worth knowing before it looks like a bug), or if any page holding its clusters' parents is still resident. A dropped request costs nothing: a view that still wants the page is still drawing its parent and asks again next frame.

**What streaming refuses, and why each refusal is a refusal.** `resolve_settings` turns `--stream` off, with the reason logged, for a scene with no page table. It forces culling on, because the drawing rule's fallback clause *is* the LOD cut. It drops `--rt-templates`, because a template is built once at load from every cluster's float positions, which a streamed scene does not hold — a template has to be built when its page arrives and dropped when it leaves, which is a second residency problem with its own budget. And it refuses **a deformed or skinned scene** outright, because `gfx::DeformDesc::pool_offset` indexes the deformed-vertex pool by the *scene-wide* vertex index while a streamed scene's vertices live at slot-relative ones; joining the two is a change to the pool's allocation, which is E25's open suballocation item.

### Admission never waits on a read it cannot start

**The stall the desert flythrough found, and the rule that ends it** (2026-09-24). One streamed run of the flythrough — the first, at 1080p with occlusion culling off and a 5% budget — made 60,034 page requests over the path and uploaded nothing; three reruns of the same command were normal ([the write-up](../experiments/flythrough-desert-overlook.md#the-streaming-run-that-uploaded-nothing)). It was not bad luck and not the disk. It was a **circular wait** between three rules above, each right on its own:

- a page's load slot is given back when the page is **staged**, and a pool slot is held from the moment its read starts;
- pages are staged strictly in **page order** — coarse first, which is parent before child — and the walk goes on past a page still waiting for its read only to *start* the reads behind it;
- admission, and the reads it starts, go in **priority order**, the manager's heap by projected size.

So when reads take longer than frames, the eight load slots (`k_page_loads`) fill with pages behind the walk's head. If a page is then admitted with a lower index than every one of them — a coarser page some cluster asked for a little later — while no slot is free, admission makes it resident in the manager with no read, and on the next frame it *is* the head of the walk. It cannot start its read: every slot is held. None of those can be staged: they are behind it. So none is ever given back, the pool stops at what it had, `blocked` keeps admission shut, and the requests pile up for the rest of the run. Nothing in the loop ever leaves that state. What it needs is reads slower than a frame — the first run after a build reads the containers off a cold file cache, and the reruns found them in memory — and a priority order that puts a low page after the slots have filled, which a fly-in toward a terrain does almost at once.

**The rule: the head of the walk always gets a load** (`GeometryStreamer::steal_load_for`). When the page at the head of the page-order walk has no read and no free load or pool slot, the streamer gives up the load of another page — one the manager no longer holds if there is one, otherwise the one furthest behind the head, which the walk would reach last — and starts the head's. Every load belongs to a page at or behind the head, since the pages before it are in the pool and a pool page has no load, so when the head has none there is always one to take. The page it was taken from reads again when the walk reaches it; `StreamStats::steals` counts every read that is done twice, and a run that counts many has too few load slots for its read latency. With the rule the head waits for its own read and nothing else, so the pool gains a page at least every few read latencies whatever order the requests came in.

**A read that fails is read again.** A short or failed read already dropped the page rather than staging it; the case below makes sure dropping it does not strand it — the walk reaches it again, starts it again, and the pages behind it follow once it lands. A page whose read fails *every* time still holds the pages behind it in page order, since staging past it would break the ancestor-closure the order exists for; a container that cannot be read is a load-time failure the source should refuse, not a frame-time one, and it is a follow-up.

**How often, before and after.** The stuck run's own command — the landmarks overlay at 1080p, occlusion off, shadows off, a 5% budget, pages from the containers — each run over a cold file cache: on the RTX 5090 the old streamer stalled in **7 of 10** runs, six from the warm-up and one 33 s into the path, and the new one in **0 of 10**; with the substitute set, **4 of 10** against **0 of 10**. The TITAN Xp's runs, and every stalled run's state, are in [the write-up](../experiments/flythrough-desert-overlook.md#the-streaming-run-that-uploaded-nothing).

**What holds it.** `streaming_tests.cpp` serves the pages from `SlowPageSource`, a `PageSource` whose loads land a fixed number of frames after they begin, over the scene's own host streams — which is what a cold cache does to a real run, and what a container the test just wrote never does, because it is in the file cache. `PageSource` is the interface `GeometryStreamer` reads pages through, and `FilePageSource` is the one the hosts use. **`admission never waits on a read it cannot start`** flies the 129-grid heightfield in 16 KB pages toward the camera under a 32 KiB upload budget with a six-frame source. Against the streamer before the rule it stalls on every run — the pool frozen at 12 of the 21 pages the manager admitted from the 48th frame to the 1,200th, all eight loads out — and with the rule it converges in 89 frames, 27 pages of 27, having given up one load, with no stretch longer than 12 frames without a page landing (the test allows four latencies and eight frames of feedback, 32). That is the RTX 5090. Whether the slots fill behind the head depends on the order the cut asks for pages in, which differs by device, and on the TITAN Xp the same fly-in never filled them — no load given up, converged in 83 frames — so there the case holds convergence and nothing more; its message says which. A case that builds the wait on every device would drive admission directly rather than through a cut, and is a follow-up. **`a read that fails is read again, and the rest of the queue goes on`** fails the first page past the roots four times with a three-frame source: the page is read five times and the run converges in 82 frames, 26 of 26, longest stall 19 frames. That one passes against the old streamer too — dropping a failed read was already right — and is there so the rule cannot break it. `FrameStats` and the flythrough's `.jsonl` carry `pending`, `loads_in_flight` and `pool_pages` beside the manager's `pages_resident` on every frame, which is the trace that says a run is in this state — the pool flat, the queue full, eight loads out — rather than leaving it to be inferred from a summary with no uploads in it.

### A page's 8-bit indices are its own

**The defect this section used to record — a starved budget and the ray chain together losing the device — was a host-side buffer overrun in the staging path, and it is fixed.** It is written up rather than deleted because the shape of it is worth keeping: nothing about it was on the GPU, nothing about it was a barrier, and every suspect the symptom suggested was innocent.

**What it was.** `GeometryStreamer::pack_indices` turns a staged page's packed triangles into the tightly packed 8-bit indices a cluster acceleration structure build reads, into the reused scratch vector `indices8_`. `gfx::pack_cluster_indices` **appends** — which is what `GpuScene::create_ray_tracing`'s one-shot pack of a whole mesh wants — and the per-page caller never cleared the vector between pages. So the *k*-th page staged in a run wrote the concatenation of all *k* pages' indices, starting at this page's 8-bit index block. Two things followed from one missing line:

- **The pool got the wrong page's triangles.** Page 0 was correct; every page after it was staged with page 0's indices at the front of its block, so a CLAS build record for one of its clusters described triangles that are not in that cluster — local indices past the cluster's `vertexCount`, addressing vertices outside the cluster's run of the pool.
- **The write ran off the end of the page's region of the staging ring**, by one page's indices for every page staged before it. The ring is `k_stream_slots` regions of one upload budget, so the spill first landed on the *other frame slot's* staged page — whose copy into the pool may not have executed yet, since a frame's staging is written on the host after `begin_frame()` and its transfer is recorded into that frame's command buffer — and, once long enough, off the end of the mapped ring entirely, into whatever host-visible allocation VMA had placed behind it. `GpuScene::rt_instances` and `ClusterSet::addresses` are both host-visible and both hold device addresses that a build or a traversal dereferences; a spill onto either is a wild address in an acceleration structure, which is exactly the `vkQueueSubmit2` device loss that was recorded.

**Why only that configuration.** The 8-bit index block is staged **only when the frame builds acceleration structures** — `GpuScene::page_stage_layout` sets `ray_tracing` from `ResolvedSettings::rt_chain` — so `--shadows off` never called the packer and never overran anything. And the overrun grows with the number of pages staged in a run, so it takes a budget tight enough to keep re-uploading: a budget that holds the working set stages a dozen pages once and stops. Reproduced on the RTX 5090 with `--mesh FlightHelmet.gltf --grid-instances 8 --stream --page-budget-pct 25 --page-source host --orbit 4 --frames 150` at 1920×1080 in `msvc-release` — three runs of three lost the device, and the same command with the fix runs 300 frames and 125 uploads clean.

**The invariant, as a rule a future change must keep.** *A page's staged bytes are a function of that page alone, and every one of them lands inside that page's own region of the staging ring.* Concretely: a block written into a staged page is sized from the page's `geometry::ClusterPageDesc` and placed at its offset in `GpuScene::page_stage_layout`, never sized from a buffer that outlives the page. `pack_indices` now clears the scratch, copies exactly `triangle_count * 3` bytes, and asserts both halves of the rule in debug; `patch_clusters` already obeyed it. The wider statement for anyone adding a stream to a page: **a scratch buffer shared across pages is a hazard unless the copy out of it is sized by the page**, because the staging ring has no guard band and the frame slot next to it is live.

**What holds it.** `systems/renderer/tests/streaming_tests.cpp`, "a page's 8-bit indices are its own, under a budget that evicts every frame": the heightfield with 16 KB pages, `ShadowMode::RayTraced`, a tenth-of-the-page-bytes budget and a camera that moves, so the pool recycles its slots (28 uploads, 23 evictions in 48 frames). It then reads both pool streams back — `GeometryStreamer::slot_of_page` is the accessor that says where a page's payload actually is, so the check walks the pool rather than re-deriving the mapping and getting it wrong the same way twice — and requires `indices8[3t .. 3t+3)` to be `pack_cluster_indices` of `triangles[t]` for every triangle of every page the pool holds. The two are written by the same upload from the same staged bytes, so nothing but the right bytes can make them agree. Before the fix, 4,121 of 5,078 pool triangles disagreed, the first on page 1; after it, none. **Every other case in that file runs with shadows off**, which is why the defect lived: the stream it corrupts does not exist without the ray chain.

**What a validation layer would still have to say.** None of this needed one — it is a host-side overrun of a mapped buffer, which `VK_EXT_debug_utils` and the standard layers would not have flagged either. What a layer *would* settle, and what is still owed, is the cross-frame question this investigation raised and did not resolve: the render graph is reset per frame and an imported buffer starts each frame with no recorded producer, so the first use of a buffer in frame N is barriered against nothing in frame N−1. The pool's slot-retirement rule (`frames_in_flight` frames before a freed slot is refilled) makes that safe for the payload streams, and the scene-wide `ClusterDesc` array is rewritten in place with identical bytes for every field the cull pass reads — but "identical bytes" is an argument, not a check, and `VK_LAYER_KHRONOS_synchronization2`'s hazard tracking is what would turn it into one. The SDK is not installed on this machine.

**Where a page's bytes come from, and why that decides whether streaming saves host memory.** There are two sources and `GeometryStreamer::copy_page` is the seam between them (`systems/renderer/page_source.h`).

*In memory* is what the first streaming change had: a page's payload is copied out of the `SceneData` the load produced. It is what the procedural heightfield and a glTF loaded with `--no-cache` have to use, because there is no file behind them — and it means the whole scene's geometry stays in the process whatever the budget is, so streaming saved **device** memory and not host memory.

*From the container* is `FilePageSource`, one implementation of `PageSource` — the interface `GeometryStreamer` reads every page through: begin a load into one of `capacity()` slots, ask whether it is `done` and `complete`, read its `bytes`, `release` it (the tests' `SlowPageSource` is the other, and lands its loads a set number of frames late). Every mesh of a scene came out of a `.clusters` container — one named outright, a derived-data cache hit, or the entry the load just wrote (`SourceMesh::container`) — and `geometry::ClusterFileReader` addresses that container's sections by byte range ([geometry](geometry.md), "The container read by range"). A page's payload is then **three ranged reads, or four when the frame builds acceleration structures**: the quantized positions, the attributes, the packed triangles, and the float positions. The other two blocks of a staged page are the host's either way — the cluster descriptors, which have to carry *this* slot's offsets, and the 8-bit indices, which are packed from the triangles that just landed rather than read a second time, so the two can never disagree about a triangle. That a page's slice of each stream is one contiguous run is not luck: `build_cluster_pages` reordered the streams so that it would be.

`attach_page_source` opens the containers **and releases the merged host streams** — quantized, attributes, triangles, float positions, vertex sources, bindings — which is the point of the whole thing and is why the two are one call rather than two. What it does *not* release is the cluster and LOD descriptor arrays: they are 96 bytes a cluster against the ~1.5 KB a cluster a page carries, the streamer patches a page's descriptors out of them on the way past, and the cull pass needs them for every pair of every frame anyway.

**All or nothing, per scene.** A scene whose meshes are not *all* backed by a container is refused with the reason and keeps the in-memory source. A partial source would be worse than none: the caller's next act is to release the streams, and the pages the source could not answer for would then have nowhere to read from.

**What is bounded is the steady state, not the peak.** `load_scene` still materializes the merged streams and `attach_page_source` releases them afterwards, so the working set falls after the load and the *peak* does not. Making the load never read them needs `geometry::merge_paged_cluster_meshes` to stop deriving the merged bases from `mesh.vertices.size()` — the counts are in the page table, which tiles the vertices and the triangles — and that is a change to the merge's signature rather than to this seam. Both numbers are in engine-view's summary (`host_memory.bytes` and `peak_bytes`) so the distinction is measurable rather than assumed.

**Nothing blocks, and the pipeline is what makes that affordable.** `begin` issues a page's reads on the Efficiency pool and returns; `prepare` polls one counter per load. Three rules keep it correct and fast:

- **Staging is in page order**, which is coarse first and therefore parent before child, which is what keeps the pool ancestor-closed. Unchanged from the in-memory path, and it is what makes an out-of-order completion harmless.
- **Past a gap, the walk goes on but only starts reads.** Without that the disk would work on one page at a time and a scene would converge at one page per read latency; with it the queue is being read while the frame waits for the page at its head. Nothing behind the gap is staged, so the order holds.
- **Pending is not blocked.** A page whose reads are on their way stops *that* page being staged and nothing else, because what keeps the pool ancestor-closed is the staging order and not what the manager holds. No upload budget, no pool slot and no load capacity do still stop admission. A frame's upload budget bounds both what it copies and what it newly asks for, so it can neither move nor request more than one budget's worth.

A page evicted while its reads are in flight is cancelled in a pass of its own, because `apply_evictions` walks what the *pool* holds and a load is not that yet; without it a load slot and a pool slot would leak one per eviction. A read that fails or comes back short drops the page rather than staging it, since the pool would otherwise hold that page's descriptors over whatever was in the buffer.

Eight loads may be outstanding (`k_page_loads`), which is more than the default 256 KiB upload budget can stage in a frame, so the reads are never what holds a convergence up; their buffers are one largest page each and are sized once, like everything else in the frame path.

**The fly-in, and the guarantee it holds.** `renderer::fly_camera` and engine-view's `--fly <from> <to> <steps>` are a scripted path in mesh radii, interpolated **geometrically** — halving the distance doubles every projected error whether it is 50 radii to 25 or 2 to 1, so equal steps in log distance are equal steps in refinement, and a linearly sampled path would spend nine tenths of its steps on the outer half where a mesh draws out of one page and asks for nothing. The streaming test walks 24 steps of the heightfield from 8 to 0.9 radii under a **quarter budget and a 32 KiB upload budget** and compares every step against the fully resident picture *of that step*.

What it asserts is on the reference coverage **eroded by two pixels**: every surviving pixel must be covered, which says "no region of the surface is missing" with no tolerance to calibrate. Counting silhouette pixels against an area-scaled tolerance measures the shape of the object instead — at 8 radii the terrain covers 2,494 pixels of 76,800 and its jagged horizon is a sizeable fraction of that, while at 0.9 radii it covers most of the frame and the same edge is a rounding error. **Zero interior misses at all 24 steps.** The single-frame starved case (`a starved budget is coarser and never has a hole`) asks its question the same way since 2026-09-23. It used to count holes against a tenth of a percent of the covered pixels plus eight, and that was a calibration of one GPU: at a quarter budget the manager never settles (one of eight pages resident, 86 uploads and 85 evictions to the 256-frame cap), and the RTX 5090 left 65 edge pixels against an allowance of 66 on the mesh and the vertex path alike, while the TITAN Xp's cut of the same frame left 70 and failed. **The cull pass's streaming cost is not measurable here.** The extra work is one residency-word load per pair and, for a cluster that wants to refine and cannot, a masked atomic append — and against 150,272 pairs a frame it is inside the run-to-run spread of the same scene with streaming off (0.029–0.031 ms either way, on a card another process was using). That is the honest statement: not "free", but smaller than this machine can resolve.

**A 100% budget costs more device memory than not streaming at all** — 3.73 MB of pool, ring and tables against 2.85 MB uploaded whole. That is not a defect, it is the price of a fixed-size slot: the pool is 25 slots each sized for the *largest* page, plus two 256 KiB staging regions, plus the always-resident descriptors. Streaming is a way to hold *less than the scene*, and a budget that holds all of it is the configuration where it has nothing to trade. The benefit starts at 50% (2.32 MB) and the quarter budget holds half of what the whole scene costs.

**A camera jump converges in the same two frames a cold start does**, at every budget: the interval is bounded by the feedback latency (`frames_in_flight` = 2) and not by the bytes, because two 128 KB pages a frame is more than this cut asks for. `frames_to_converge` is the *last* interval, so under a tight budget — where eviction restarts an interval every few frames — it reports a few frames and not the whole run; the uploads and eviction counts are what say how much churn there was.

**A tight budget churns, and the stale-request rule is what makes that safe rather than wrong.** At 25% the run evicts 110 pages, drops 91–97 requests as stale, and uploads 4.3–5.1 MB — nearly twice the whole scene — to hold 0.5 MB at a time. The picture degrades as designed (1,080–1,298 visible pairs against 1,545) and never holes, which is what the fly-in case asserts.

**And the row the table could not hold before: the quarter budget with the ray chain on.** The table above is `--shadows off` because the shadowed run used to lose the device; it does not any more, so here is the same scene with shadows on. Same machine, `msvc-release`, 1920×1080, 120 frames, container-backed source, `--orbit 4` — which is the camera that reproduces the table's own 1,545 visible pairs, so the two sets of rows are the same cut. **Run twice, and every figure below was identical to the digit across the pair unless a range is given.** The card was shared throughout: `nvidia-smi` read 6,049–6,750 MiB used and 5–9% utilization around the batch, and the per-run `machine_state` recorded 4–20% GPU utilization and 9.5–34.4% CPU from other processes, so **every millisecond here is an upper bound**.

That is the paged half of what [gfx](gfx.md) calls "a mesh that is ray traced uploads both streams", and it is the ratio a budget has to be set against: **a page costs about 1.4× as much resident with shadows on**. **The same six slots hold the same pages**, so the budget buys the same cut either way; what the ray chain adds is bytes per page, not pages. **`gpu_ms.cull` halves with shadows on**, which is not the cull pass getting faster: shadows turn two-pass occlusion culling off (`resolve_settings`), so the frame runs one cull dispatch instead of two and the zone is summed over one. And **device memory is dominated by the CLAS set, not by streaming**: 1,712 MiB against 662 MiB, because `create_cluster_set` is sized for `views * pair_count` = 150,272 clusters while the frame builds about 1,550 of them. Streaming bounds the *geometry* and does nothing about that; a CLAS set sized for the cut rather than for the scene was the open item beside it, and is closed ([The ray tracing chain's memory](#the-ray-tracing-chains-memory): this scene's chain now holds a few thousand clusters).

## Reference renderer

[04 §4.8](../plan/04-renderer.md#48-reference-renderer-and-objective-optimization) asks for *a GPU path tracer in Slang sharing material/BSDF, light, and camera code with the real-time path*, converged to a noise floor, against which the real-time path is measured. `systems/renderer/reference.h` is that: `ReferenceRenderer::render(camera, settings)` gives back a linear HDR buffer and an RGBA8 picture through **the same display transform the resolve ends on**, so a reference image and a real-time image are in one space and FLIP compares pictures rather than transfer curves.

**It uses a `SceneRenderer`; it is not one.** A reference render is one ordinary frame followed by N compute dispatches. The frame is what matters: it runs the cull pass, fills the visible list, and builds the cluster acceleration structures and the top-level structure over them — and *those* are what the path tracer traces. There is no second scene, no second geometry path and no second material table, so a reference ray shades the material the resolve would have shaded on that pixel, and a disagreement between the two pictures is a disagreement about **transport** rather than about two different scenes. The one thing the reference changes about the frame is `FrameDesc::lod_px`.

**What the reference is a reference *for*.** On this engine the geometry under the acceleration structures is the frame's **LOD cut**, so a converged path trace of it is the right answer *for the geometry the renderer chose*, not for the source mesh. Both questions are worth asking and a capture says which it answered:

| `finest` | The structures hold | The comparison measures |
|---|---|---|
| false (default) | the frame's own LOD cut | shading, lighting and transport — everything but the cut |
| true | the finest clusters (`FrameDesc::lod_px` = 0) | those **plus** what the LOD cut costs |

Measured on the FlightHelmet at 640×480, `--orbit 22`, 1024 samples, three bounces, `msvc-release` on the RTX 5090, twice with identical numbers: the frame's cut is **189 pairs** and the finest **1031**, 5.5× as much geometry for 45.4 ms of tracing against 40.5. The real-time picture is 0.0190 FLIP from the reference of its own cut and **0.0214** from the reference of the source geometry, and the two references are **0.0106** apart from each other. So at a 1-pixel threshold the LOD selection costs about a tenth of a FLIP percent of the real-time path's total error against the truth — small, but the only way to see it at all is to render both, which is why the flag exists and why a capture records which one it used.

**What is shared, and why each piece had to be.** `brdf.slang` was already shared. That was not enough: two integrators that agree on `brdf_eval` and disagree about how a triangle's UVs are interpolated, what a metallic-roughness texture multiplies, where a light's falloff reaches zero, or what the display transform is would produce a comparison of their material layers. So everything between the geometry and the BSDF moved into `material.slang` ([gfx](gfx.md)) and the resolve now calls it — the move is behaviour-preserving and was checked as such, byte for byte, on five FlightHelmet configurations. The lights moved too, into `renderer::frame_lighting` (`systems/renderer/lighting.h`): the sun, the sky, the two orbiting point lights and the ray bias are one function that both `record_frame` and `ReferenceRenderer::render` call with the same frame index, because "the same scene at the same moment" has to include the lights.

| Shared | Separate, and why |
|---|---|
| the scene, its materials and textures, the acceleration structures the frame built | the integrator: rasterize-and-resolve against trace-and-accumulate |
| `brdf.slang`: the BSDF, the falloffs, the roughness clamp | `sampling.slang`: densities and a random stream, which the resolve has no use for |
| `material.slang`: the triangle fetch, the attributes, the tangent frame, the textures, `light_sample`, `sky_radiance`, `display_encode` | the resolve's screen-space reconstruction, which exists because a rasterized pixel carries no barycentrics and a ray-traced one does |
| `frame_lighting`: sun, sky, the two point lights, the ray bias | the shadow ray's *shape* is the same; the reference traces one per light per **path vertex**, the resolve one per light per pixel |

**The sky has two roles and the reference mirrors both, deliberately.** In the real-time path `ResolveParams::sky` is written straight out for an uncovered pixel *and* used, scaled by normal elevation, as the entire indirect term. Those are two different functions of one number, which is a property of a renderer that has no sky model yet. The reference copies it rather than fixing it: a **primary** miss returns `sky^2.2` in linear, so the display transform gives back exactly the bytes the resolve writes, and a **secondary** miss returns `sky_radiance(sky, direction)`, the same hemisphere ramp the resolve adds. Copying it is what makes the two comparable at all; fixing it belongs with the atmosphere of §4.2 step 5, and until then the residual in the table below is partly this.

**Where the two still disagree, in order of size.** No indirect light in the real-time path at all — the resolve has one ambient term where the reference integrates a hemisphere, and at more than one bounce the reference carries light that bounced off the rest of the scene, which is most of the FLIP on any scene with interiors or close-standing geometry. The ambient model itself: `albedo * sky_radiance(n)` plus the specular lobe's share of the sky (`brdf_env_specular`, an analytic fit of the lobe integrated against a uniform environment) against an integral of `sky_radiance(d)` over the hemisphere, which differ by about 10% even with nothing else in the scene. Antialiasing: the reference box-filters a pixel and the rasterizer point-samples one, which shows at every silhouette — `ReferenceSettings::pixel_center` turns the jitter off when a comparison is about shading rather than about edges. And one honest divergence: the reference turns a shading normal that has ended up behind the surface into the geometric hemisphere, where the resolve lets the BSDF return nothing and keeps only its ambient. It is the reference that is right, and it matters on thin two-sided geometry.

**Accumulation, batches, and what "deterministic" means.** `accum` is one `float4` per pixel — radiance sum in rgb, sample count in w — and a dispatch adds `batch` samples starting at `sample_base`. A pixel's Nth sample is a function of (pixel, N, seed) and nothing else, so the *samples* do not depend on how the render was split; batching exists so progress can be reported, a render can be stopped and still produce a valid (noisier) picture, and no single submission runs long enough to meet the display driver's watchdog. The guarantee is therefore precise: **the same seed and the same batch size is the same bytes**, which the tests check. Across batch sizes the samples are identical and only the order the partial sums are added in differs, and float addition is not associative — measured at 64 spp that is under `4.5e-7` of linear radiance, which after the display transform moves **no byte at all**.

**The finding that cost the most, and the reason a background pixel is not tonemapped.** The first corpus run came back with FLIP means of 0.04 to 0.07 on every scene and a p95 *below* the mean, which is the signature of a flat difference rather than a rendering one. It was: the real-time path writes `sky` for an uncovered pixel as a **display-space** colour straight into a UNORM target, while the reference carried linear radiance and had to round-trip it through `pow(sky, 2.2)` and back. Two things then went wrong at once. The round trip is exact to about a part in ten million, but `sky.g` = 0.70 lands at 178.4999969 of 255 — three millionths under a byte boundary — so the trip moved it to 179. And the shader's own quantization could not have saved it either: `0.699999988 * 255` is 178.4999969 in exact arithmetic, and **rounding that product to float32 gives exactly 178.5**, because the spacing of float32 there is 1.5e-5 and the error is 3e-6. The fixed-function UNORM conversion the resolve's colour target performs does not have that problem; it converts the float exactly and writes 178. So the reference does two things: it keeps a one-bit **coverage** buffer saying whether any sample's primary ray hit geometry, and it writes the background for an uncovered pixel from a value **quantized on the CPU in double precision** (`gfx::pack_unorm_rgba8`). A pixel something did cover is tonemapped as before, including a silhouette pixel whose box filter mixed sky and surface, which is what that pixel should be. Removing the flat one-byte offset took the corpus from 0.019–0.063 FLIP to **0.0014–0.035**: between 45% and 96% of what the gate was measuring was a rounding artefact. The lesson is general enough to write down: *whenever two paths have to agree to the byte, the last quantization must happen once, in the place with precision to spare.*

**The integrator.** Unidirectional paths; next-event estimation to the sun and to the analytic lights, one terminate-on-first-hit ray each, offset along the geometric normal by the same bias the resolve uses; the two-lobe BSDF importance-sampled with a Fresnel-weighted lobe pick, GGX by visible normals and Lambert by cosine, the estimator dividing by the *mixture* density; Russian roulette after three scattering events; emissive — the factor times the emissive texture, through the same `sample_material` the resolve calls — added where a ray lands on it, with weight 1, and never sampled as a light, which is v1's stance on emitters ([texture](texture.md#emissive)); no occlusion map, ever. Every light the engine has today is a **delta** light, so nothing a BSDF ray can hit is also sampled directly and every multiple-importance-sampling weight is 1 — the power heuristic is written and tested in `sampling.slang` for the area and environment sampling that will change that, and is not called here. `max_bounces` counts **scattering events after the primary hit**, so 1 is direct lighting plus one bounce, which is exactly what the resolve approximates with its ambient term.

**What the tests hold it to** (`systems/renderer/tests/reference_tests.cpp`, all headless, all skipping with a message on a device without cluster acceleration structures, since there are then no structures to trace). A **furnace**: a white cube in a closed environment of one radiance with the sun and the lights off — a furnace with a sun in it is not a furnace — where an uncovered pixel returns the environment to 1e-5 and a covered one returns the surface's directional albedo. Measured over ~3,300 covered pixels at 512 spp: a white dielectric at roughness 1 returns **0.9746** of the environment (the CPU quadrature in `domain/gfx/tests/sampling_tests.cpp` says 0.9726 at `n·v` = 0.95) and a white metal at roughness 1 returns **0.3870** (the CPU says 0.3168 head-on; a cube shows grazing angles too, where Fresnel is higher). The metal row is the energy single-scatter GGX loses, and it is a property of the model the two integrators *share*, so it cancels in a comparison. **Determinism**: same seed, byte-identical; different seed, different picture. **Convergence**: the root-mean-square linear error of a 32×32 block against a 4096-spp picture at 16, 64, 256 and 1024 spp falls by 2.08×, 2.06× and 1.64× per quadrupling, against the 2× that 1/√n predicts — the last step is short because the picture it is measured against is itself only 4096 samples converged, which is the honest reading and the reason the bound is a range rather than a number. **Agreement with the resolve** at one bounce, jitter off, 512 spp, 128×128, on four scenes the engine can build with no content at all:

Two things about how that was caught are worth keeping. The gate found a bug it was not looking for — it is a *picture* comparison, so a picture that changed for a reason nobody had modelled still moved a number — and it only became legible because the report records `mesh_cache` per scene, which is why that field is in the report and why anything else whose provenance could vary belongs there too. **Where a paged mesh's leaves are, and the measurement that found out they were not there.** `ClusterMeshPart::first_leaf_cluster` exists because a `.clusters` container is in **page order** — coarse first, leaves last ([geometry](geometry.md#pages-and-streaming)) — and every container is, whether or not anyone will stream from it, because the page layout is part of the derived-data cache key. The single-mesh load path built its part by hand and left that field at zero, so everything that asked a part where its leaves are got the **coarsest** clusters instead. The visible consequence was the camera: it frames the leaves' bounds, a coarse cluster's sphere is looser than the surface it stands for, and how loose depends on how far the simplifier got — so two builds of one mesh that differed only in their *coarse* levels were drawn at two different sizes. It surfaced while measuring the atlas-seam fix: the two builds' pictures disagreed by **0.23 FLIP at the finest threshold**, where they draw exactly the same triangles. With the field right they are **byte-identical** (FLIP 0, SSIM 1) on all four test models, which is what made the rest of that measurement trustworthy. The lesson is the one the field's own comment already gave and nobody applied: a convention that is true for half the meshes is worse than no convention, and the test that pins it now (`atlas_lod_tests.cpp`) writes a paged container and asserts the leaves are a contiguous run at `first_leaf_cluster` and that nothing before it is one.

‡ **This row is the odd one out and is meant to be.** Its number is not the shading gap the other five measure but **what LOD costs the picture**, because its reference is traced from the finest geometry while the real-time path draws a 16-pixel-threshold cut of it — the only comparison in the corpus that renders two different cuts. Its thresholds are therefore set from both ends rather than from one: the measured 0.0575 / 0.1870 below (0.0424 / 0.1339 since the sky term changed on 2026-09-25), and **0.1231 / 0.6481** above, which is what the same scene gives with the LOD builder's seam rule turned off (`engine-view --procedural shredded-atlas --uv-seams none --uv-weight 0`, the same camera, the same reference). 0.09 and 0.30 sit between the two, so the regression this scene exists for fails the gate instead of passing it — which is the rule the thin-geometry row learned the hard way, applied at the time rather than afterwards.

**A sixth scene, and the blind spot it closes.** Every row above compares the real-time path and the reference at the **same** LOD threshold — the reference traces the structures the frame built, which is what makes the comparison about shading rather than about geometry. That is also a blind spot the size of the whole LOD system: a defect in simplification puts the same wrong triangles into both pictures and the gate reports that they agree. It hid one for months ([geometry](geometry.md#what-the-simplifier-is-given-and-why)): the LOD builder was collapsing across UV atlas islands, and no picture test in the tree could see it because none of them ever rendered two different cuts. `shredded-atlas` is the row that does — the procedural atlas fixture at a coarse threshold against `"reference": {"finest": true}`, which traces the source geometry — so the number it carries is *what LOD costs the picture* rather than what shading does. Measured through the renderer's own test at 384×384, coarse (63 pairs) against finest (140 pairs) on the same camera: **FLIP 0.0092, PSNR 39.0 dB** with the seam rule, and **FLIP 0.140, PSNR 18.8 dB** without it, from cuts of the same size — 63 pairs against 64. The whole of that difference is texture, not geometry, which is the clearest statement of the defect there is.

Two things are worth reading out of that. **The indirect share is near zero on all five**, which is not a claim that the real-time path has global illumination — it is that these are isolated objects under an open sky, where a second bounce almost always escapes and the resolve's hemisphere ambient is a fair approximation of it. A scene with interiors, a mirror room or a foliage wall would separate the two columns, and none of those is in the corpus yet; that is the gap the pathological scenes of §4.8 fill. **The p95 is below the mean on three scenes** because most of those frames is background the two agree on exactly, so the error is concentrated in the few percent of pixels the object covers — which is why the thresholds carry both numbers.

**An animated instance.** A reference render is one frame, so what it draws is **one pose**, and getting that right needed a pass-through and nothing else: `ReferenceSettings::joints` and `instance_joints` are the same two spans `FrameDesc` takes, the preliminary frame writes the deformed-vertex pool from them, the cluster acceleration structures are built from the pool, and the reference traces those. The reference therefore path traces a character where the tick put it without this module learning what a clip is — which is the same "nothing had to change" that [Skinned instances](#skinned-instances) reports for the ray path, for the same reason. Measured on the Khronos Fox at 320×240, 64 samples: the posed reference is **0.0275** FLIP from the posed real-time frame and **0.0675** from a reference of the same scene at rest, so the pose is demonstrably in the picture rather than assumed to be. What the reference cannot do is *play* the clip: `engine-view --reference --animate` ticks the world once and draws the pose the windowed path's first frame would draw, `--frames` means nothing to it, and it says so on stderr when a caller passes one anyway. A sequence — which is what §4.8's temporal-stability metric will need — is a loop over frame indices that does not exist yet.

**The fixed-cost work the resolve gained, and the gate it sits behind.** The resolve skips a 32×32 tile the Hi-Z build called empty (`ResolveParams::coverage`) and discards an empty pixel rather than writing the sky the clear already wrote (`sky_is_clear`). The tile mask is exact **only** while nothing writes the visibility buffer after the last Hi-Z build, which is exactly when two-pass occlusion culling is on — and a reference render is never in that case, because `reference_available` demands `rt_chain` and `resolve_settings` turns occlusion off whenever the chain runs. So the preliminary frame carries no mask and reads every word, which is correct and costs a fraction of a millisecond on a render measured in seconds. `FrameDesc::lod_px` cannot disturb it either: it changes the cull pass's threshold, which runs before every raster and every Hi-Z build in the frame, so it moves *which* clusters are drawn and not *when* anything is written.

The `sky_is_clear` path is also why the reference's background is now written from a CPU-quantized constant rather than tonemapped (above): the bytes an empty pixel carries come from the **clear**, one fixed-function conversion of `renderer::k_sky`, and the reference's `gfx::pack_unorm_rgba8(k_sky)` is the CPU's answer to the same conversion. There is one spelling of that colour in the tree (`lighting.h`), and three things read it — the clear, `ResolveParams::sky`, and the reference's background. A second spelling would be a one-byte difference on every empty pixel of every comparison, which is exactly the bug this section already records.

**Availability.** `reference_available(resolved, device, &why)` refuses three things before anything is created, the way `check_availability` does for the renderer: a device without cluster acceleration structures or ray queries — said in the device's verdict's own sentence, which names the one it lacks (on the TITAN Xp, both) —, settings that build no structures at all (`--shadows rt` or `--raster rt` is what turns the chain on), and more than one view — the reference renders one view, and a surround reference is open work.

**Cost.** The reference is not a frame path and the rules that keep readbacks and driver queries out of one do not reach it: `render()` blocks per batch, reads two buffers back, and is measured in wall seconds. `ReferenceFrame::trace_ms` is the integrator's own GPU milliseconds from a `gfx::GpuTimer`, summed over the batches; `seconds` is what a caller waits, including the real-time frame and the readbacks.

## Capture channels, and the id encoding

`CaptureChannels` asks for any of four, and `CapturedFrame` carries what came back.

| Channel | Form | Notes |
|---|---|---|
| `color` | RGBA8 | the picture, as `engine-view --capture` writes it |
| `ids` | three `u32` per pixel | instance, cluster, triangle; `0xFFFFFFFF` in all three where the scene did not cover the pixel |
| `depth` | `f32` per pixel | reversed-Z clip depth, 0 where nothing covered it, plus the covered range as `depth_min`/`depth_max` |
| `normals` | RGB8 | the world normal encoded `n * 0.5 + 0.5` |

A capture is always in the **target's** pixels, whatever the layout: the walk is per view, a pixel inside a view's rectangle reads that view's region of the visibility buffer, a pixel no view covers is empty, and a Panini view's pixels go through the same map the resolve used (`panini_source_pixel`, the CPU mirror of the shader's), so an id names what is under that pixel of the picture rather than of the source.

**The id channel is the plan's entity-ID buffer** ([04 §4.2](../plan/04-renderer.md#42-frame-architecture), [10 §10.2](../plan/10-roadmap-risks.md#102-phases) Phase 1), and it is resolved rather than raw on purpose. The visibility buffer holds `depth << 32 | (pair << 8 | triangle)`, where `pair` is the scene's (instance, cluster) pair index ([gfx](gfx.md), "The tie rule"; it was the frame's visible-list entry until 2026-09-24, which a capture had to read the list back to decode). A capture decodes it with the scene alone — `GpuScene::pair_cluster`, a binary search over the instances' `first_pair` and the mesh's `first_cluster`, the inverse of the cull pass's arithmetic — and writes the (instance, cluster, triangle). That is the number an agent can act on ("which instance is under this pixel"), and it is stable across rasterizers, runs, frames and LOD cuts. The no-cull case, where the list is null and the rasterizers draw instance 0's clusters in index order, names cluster *i* as pair *i* and decodes it that way.

`--raster direct` writes no visibility buffer — it draws mesh shaders straight to color with a depth buffer — so asking it for `ids` or `depth` is an **error with a message**, not a buffer of nothing.

`normals` costs a second frame: the normal is what the resolve reconstructs, and only the resolve knows it, so the renderer renders again in the normals view mode and reads the color back. `ids` and `depth` come out of the visibility buffer of the first frame and cost one blocking readback each.

**On disk** (`write_capture`, which engine-host calls and the module's tests check) the channels are `<base>.png`, `<base>.ids.bin` + `<base>.ids.json`, `<base>.depth.png`, and `<base>.normals.png`. The id buffer is a raw little-endian `u32` array with a JSON header beside it rather than an image, because it is data to be indexed (`(y * width + x) * 3`) and any lossy or reordered image form would make a pixel's instance number unreadable:

```json
{"format":"engine.renderer.ids.v1","file":"shot.ids.bin","width":400,"height":300,
 "type":"u32","byte_order":"little","words_per_pixel":3,
 "channels":["instance","cluster","triangle"],"order":"row_major_top_first",
 "empty":4294967295,"covered":47213}
```

Depth is an 8-bit gray PNG normalized over the frame's own covered range (black is both "not covered" and the far end), because the engine's own encoder writes 8 bits per channel and a depth channel is looked at far more often than it is measured — a measurement takes the ids beside it or the `f32` array in `CapturedFrame`. Adding a 16-bit path to `foundation/image` is the obvious next step if that stops being true.

## Statistics

`Stats` carries exactly the fields engine-view's JSON summary prints and engine-host's `render.benchmark` returns: frames, timed frames, the three visible-pair counts and their running minimum and maximum, the shadow casters the frame built beside them ([Shadows](#shadows)), the pairs the cascaded shadow maps drew and their fallback count, with `gpu_shadow` and `gpu_shadow_cull` beside the passes' milliseconds ([Cascaded shadow maps](#cascaded-shadow-maps)), the vertex path's indexed-draw counts — `triangles_hw`, the triangles the cull pass allocated in both hardware runs, which is 0 on every other draw, and `vertex_fallback`, the survivors the index budget sent to the capacity draw, which logs one warning per renderer the first time it is not 0 because it is a frame that got slower with nothing else saying so — the GPU milliseconds of each pass (cull, hw, sw, hiz, resolve, rt, clas, deform, deform_alloc, trace, total) as sums with `*_ms()` accessors that divide by the timed frames, the deformed-vertex pool's suballocation for the frame (vertices used, the run's peak, the entries given a block and the entries refused), the CPU nanoseconds spent inside `submit_frame`, and one `ViewStats` per view (above). The per-view rectangles and tiers are filled when the layout is laid out rather than when a frame completes, because a capture is one or two frames and would otherwise report a run of zeros. The visible counts are read one frame late from a per-slot copy of the indirect argument blocks; `collect_visible()` is how a caller that waited for a specific frame (engine-view's last, before it captures) folds that frame's counts in without waiting for the slot to come around. The GPU timings of that frame are *not* in it, because a timestamp pool is read when its slot is reused.

**`Stats::gpu_memory` says who else was using the card.** `budget_mib`, `used_mib` and `device_local_total_mib` come from `gfx::MemoryBudget` ([gfx](gfx.md)) through `sample_gpu_memory()`, which `create()` and `reset_stats()` call so a summary always has a figure and which a host that measures calls again at the end of a run. It is a driver query and so is **not** in the frame path, which is the same rule as the one that keeps buffer readbacks out of it. The reason it is here at all: this project's development machine renders beside GPU jobs that hold most of its memory, and a frame time measured against a contended card is a measurement of the contention. Read it together with the `machine_state` block both hosts print — the Vulkan budget under-reports a CUDA tenant, and `nvidia-smi`'s number does not ([bench](bench.md#measuring-on-a-shared-machine) says how far apart the two were, measured).

**`Stats::last` is one frame on its own**, beside the sums (`FrameStats`): which frame it was — its own `FrameDesc::frame_index` and its `submission` since the last `reset_stats()`, both **carried** from the submit rather than inferred, because the fold lags the submission by the frames in flight and a caller counting that lag would be wrong the day it changed — its visible pairs by draw, its shadow casters, every pass's GPU milliseconds from that frame's own timer zones (the bottom-level build, `gpu_blas`, beside `gpu_clas` inside `gpu_rt`), what streaming did while it was the latest frame folded (pages uploaded and their bytes, evictions, requests, pages resident) and the state it left (`pending`, `loads_in_flight`, and `pool_pages`, what the pool holds as against what the manager has admitted), and what the ray tracing chain built, wanted and had room for (`rt_built`, `rt_wanted`, `rt_capacity`). **`Stats::rt`** (`RtStats`) is the chain's run: its capacity and bytes now and at their peak, the budget as a capacity, the scene's union, the resizes, and every frame that dropped instances' structures ([The ray tracing chain's memory](#the-ray-tracing-chains-memory)). `Stats::folded` counts the folds, so a caller reads `last` after each `begin_frame()` that moved it. It is the only per-frame number the renderer exposes and it costs a struct copy per frame; the flythrough below is built on it.

**`Stats::tiles`** (`TileStats`) is a streamed world's run ([Instances that come and go](#instances-that-come-and-go)): the changes the scene took and the CPU nanoseconds they cost in `set_dynamic_instances` (summed, and the worst), the blocks kept, rewritten in place, reused, appended and freed, the compactions and the changes that grew the per-pair buffers, and the frames that brought a table set up to date with the slots, pairs and GPU milliseconds they wrote (`gpu_tables`, the copy and the expansion; `gpu_pair_expand`, the expansion alone). `Stats::last` carries the same frame by frame, with the frame's `hole_pairs`. The renderer logs the run's totals once when it is destroyed (`tile changes`), since no per-frame record says them whole.

**`Stats::tiles`** (`TileStats`) is a streamed world's run ([Instances that come and go](#instances-that-come-and-go)): the changes the scene took and the CPU nanoseconds they cost in `set_dynamic_instances` (summed and the worst), the blocks kept, rewritten in place, reused, appended and freed, the compactions and the changes that grew the per-pair buffers, and the frames that brought a table set up to date with the slots, pairs and GPU milliseconds they wrote (`gpu_tables`, the copy and the expansion; `gpu_pair_expand`, the expansion alone). `Stats::last` carries the same frame by frame, with the frame's `hole_pairs`. The renderer logs the run's once when it is destroyed (`tile changes`), since no per-frame record says it whole.

## Scenes, camera paths and flythroughs

The benchmark corpus of [plan 09 §9.4](../plan/09-testing-profiling.md#94-benchmark-scene-corpus) starts with a **flythrough**: a scene, a scripted camera path over it, and per-frame numbers along the path, so the same scene and path give a comparable number across builds and machines. Everything the two hosts need for it is in this module — the scene file, the terrain, the path, the timed flight, the census and the summary — so `engine-view --benchmark` and `render.benchmark` with a `camera_path` fly the same frames through the same function and report the same shape. The first scene is [desert-overlook](../../content/test-scenes/desert-overlook/README.md); its measurements are in [flythrough-desert-overlook](../experiments/flythrough-desert-overlook.md).

**The formats are schema types** (`schemas/scene.schema`, namespace `engine.scene`), so `schemac` generates them and `engine-cli schema.describe '{"type":"engine.scene.Scene"}'` explains any of them: `Scene` (meshes with a name, a content `hash`, an `overlay` hash and a `Fit`; instances with a translation, rotation, `yaw_deg`, scale and `ground`; seeded `Scatter`s; `ruins`, the `RuinScatter`s below; an optional `Terrain` with `Ridge`s and `Basin`s; since version 2, an optional `camera_path` naming the path the scene is flown along, which `read_scene_file` resolves against the scene file into `SceneDesc::camera_path` and which a host with no path of its own starts a camera at — engine-view's `--interactive` ([apps](apps.md#--interactive-a-camera-somebody-flies)); and, since version 3, in a fragment the ruin assembler wrote, a `RuinTag` on each instance with `ruin_sites` and `sand_drifts` beside them, which the reader accepts and does not interpret), `Overlay` (a local manifest from content hash to file), `CameraPath` (`CameraKey`s and `CameraMarker`s), and what a run writes — `FrameRecord` per frame and `FlythroughSummary` at the end. **Why a JSON file keyed to schema types and not a `doc::Document` layer**, which is how the plan stores a world ([03 §3.2](../plan/03-data-model.md#32-the-authoring-document-world-document)): the renderer reads scenes and must not depend on the document model's journal and ids to do it; a corpus scene is a fixture whose identity is its bytes, so one committed file that diffs as text and hashes as a unit is the honest unit; and the types are chosen to map one-to-one onto a layer's placement objects, so the move is an export and not a redesign. `read_scene_file` reads the **oldest spelling too** — `{"meshes":[{"path"}],"instances":[{"mesh","translation","rotation","scale","animation"}]}` is a valid `Scene` — and is stricter than it was: an unknown field is refused with its path, because a misspelt `ground` that quietly did nothing would float a building.

**Content addressing.** A mesh's `hash` is `assets::source_mesh_hash` of the file; the load computes it (the cache path already does) and refuses other bytes, naming both hashes. The terrain's is `terrain_hash`, over every field and `k_terrain_version`. A run's summary carries the scene file's hash, the path file's hash, every mesh's hash and where it came from (`scene`, `overlay` or `terrain`), and one `identity` over all of them: the number that names what was measured.

**The overlay.** A mesh may name, in `overlay`, the content hash of a file that should stand in its place; `SceneFileOptions::overlay` (`engine-view --overlay`, `render.load`'s `overlay`) is a local `engine.scene.Overlay` manifest from hashes to paths. A mesh the manifest names is loaded from there and checked against the hash; one it does not name keeps the scene's file, with a warning. That is how the owner's paid-plan landmarks — never committed — replace a committed scene's Khronos placeholders by their bytes alone.

**Fit.** `MeshFit` scales a mesh uniformly to a height or a longest extent and puts its bounding box's bottom centre (or its centre) at its origin, before any instance transform: a fitted slot occupies the same volume whichever file fills it, which is what lets a 2 cm sample and a 2-million-triangle landmark share one set of placements and one camera path's occlusion. The box is read from the mesh's float positions during `load_scene`, while they exist.

**The terrain** (`terrain.h`) is the classic heightfield's generalization, built **beside** it rather than into it, because the classic one is a fixed 20-unit fixture whose ids and cuts the tests pin: seeded dunes — a handful of transverse waves around one prevailing wind, normalized so their peak-to-trough is about `dune_height` (the first normalization made a 5 m field 2 m high, and the LOD builder rightly turned the ground in front of the camera into clusters a few hundred metres across) — plus hand-placed ridges (a cosine profile around a segment, roughened by a seeded value noise) and basins. `terrain_height` is analytic, so an instance can stand on the ground (`ground`) and a camera key can hold a height above it before the mesh exists. **A caller that asks more than a handful of times holds a `TerrainSampler`**: `terrain_height` draws the dune field from the seed on every call (six waves' worth of trigonometry and a `pow` each, more than the height itself costs), and the scene read asks for every grounded instance and scatter and a ruins entry's dozens of heights per building — reading 1,000 ruins over the desert overlook spent 43–59 ms in the scene read with the field drawn per call and 23–28 ms with one sampler for the read (2026-09-24, seven runs each, [ruins](ruins.md#performance-notes)). The sampler **is** the object `terrain_height` and `build_terrain_mesh` build, not a cache of it, so its heights are the direct function's and the mesh's to the bit; the flythrough test compares all three on a grid across a ridge, a basin and plain dunes. `read_scene_file` builds one per read and `parse_camera_path` one per path. The mesh gets **the grid's own normals** as an attribute rather than normals recomputed per LOD level — recomputed ones made every LOD boundary a visible change of shade — and **one material whose colour and roughness are two maps over the terrain's UVs** (`bake_terrain_maps`: one texel per grid cell, `terrain_surface` at the texel's centre — sand, ridge rock, basin sand and the basin's green floor, blended across a band of 0.1 of the feature's weight around each threshold of `terrain_material`, ten to twenty metres on the desert). The maps travel as PNG bytes in the mesh's images, so the cache entry carries them and the texture step builds them into mipmapped BC7 beside it like a GLB's embedded textures (two 2048² maps for the 2049 grid: the bake and the PNG encode 646 ms of a 42 s cold load, the texture build 410 ms, `msvc-release` on the i9-10980XE beside other agents' builds, so upper bounds). **Why not per cluster, as it was until 2026-09-25**: the terrain carried the four materials and drew each cluster with the one most of its vertices were. A coarser cluster votes over a larger patch and comes out differently near every border, so as the camera moved and the cut changed, patches of rock and of the green floor grew, shrank and jumped by whole clusters — the "green and grey ground textures that shift at position thresholds" of the second owner session ([its write-up](../experiments/second-interactive-session-2026-09-25.md): at the owner's six markers a cut change alone moved the ground's colour on 2.6–4.3% of its pixels, and moves it on 0.009–0.027% now, all of that the cut's own geometric error across a blend). The UVs every level interpolates come from the same source vertices, so a point of the ground is one colour whichever cluster draws it; `flythrough_tests.cpp`'s "the ground's colour does not move when the LOD cut does" draws the owner's terrain at his six marker cameras from two cuts and holds it to that. It is laid out in pages exactly as a glTF's cache entry is and cached in the derived-data root under `cluster_cache_key(terrain_hash, …)`, so a 2049 × 2049 terrain costs its clustering once per machine (`k_terrain_version` 5 is the maps; an entry of 4 is simply not found).

**The dune generator** (`"generator": "Dunes"`, `engine.scene.Terrain` version 2; the terrain capability, [terrain](terrain.md), [ADR-0043](../adr/0043-dunes-as-a-function-of-time.md), proposed). A terrain may hand its dunes to the terrain capability's generator instead of drawing the waves: parametric dune primitives the seeded wind has carried to the terrain's game `time` (seconds since the world's epoch) at its mean `sand_flux` (m² a year), integer and the same bits on every toolchain. **Only the dunes change.** The ridges and basins are this module's in both fields and added the same way — the generator knows where they are, thins its sand over rock, flattens it in a basin and bows its crests round a ridge, but the rock and the bowls are `TerrainSampler::features`, the waves' own arithmetic. The waves stay the default and their arithmetic is untouched, statement for statement, so every existing terrain keeps its heights, its `terrain_hash` (the generator's fields enter the hash only when the generator is named) and its cache entry; the owner's fly-through decides when the generator becomes the default. With the generator the sampler holds the generator's field and a point query gathers the primitives near the point — a few microseconds, and thread-safe, since the scene reader grounds a large ruins entry on a job pool through one sampler — while `build_terrain_mesh` gathers once per 64 × 64 block of vertices: the same heights to the bit (a test compares every vertex of a mesh with the sampler and the direct function), and 1.34 s for the desert overlook's 2049 × 2049 grid where the waves take 0.72 (GCC release, once per machine, since the mesh is cached by its hash). **`TerrainSampler::ground` is what buildings stand on**: with the waves the surface, as before; with the generator the interdune floor plus the ridges and basins, which never moves, so a ruin is the same building at any `time` and the dunes migrate over it and bury what stands there (the scene reader's `terrain_ground` asks it; the world's ruins consumer too). [`content/test-scenes/desert-dunes/`](../../content/test-scenes/desert-dunes/README.md) is the overlook's terrain with the generator three years in, for the owner's fly-through. A build without the terrain capability builds the renderer, draws every waves terrain, and refuses a terrain that names the generator with a sentence (`terrain_generator_available`); a generator time outside [0, 3·10¹¹) s or a flux outside [0, 100,000] is refused too. `terrain_generator_tests.cpp` holds all of it with no device, including a ruins scene read a year apart to the same instances.

**Ruins** (`ruins`, `engine.scene.RuinScatter`; the ruins capability, [ruins](ruins.md)). A scene may ask for ruined buildings over the terrain's tiles instead of placing them: a kit file (relative to the scene), a world seed, a tile size, a square of tiles, and either a `count` — the tiles of the square the seed ranks first — or a `density`, the endless desert's share of tiles with a building, and the wind's direction. `read_scene_file` reads each kit once, appends its meshes **after the file's own** (so every index the file used still names what it named) and **before the terrain** (which stays the last mesh, its index now the count of meshes before it rather than the file's mesh count — the first draft kept the old index and gave the terrain's instance a kit mesh, which the scene test caught), assembles every building standing on the terrain (through the read's one `TerrainSampler`), and hands the renderer plain instances of kit meshes: nothing downstream knows a ruin from a scatter. `SceneDesc::ruin_buildings` and `ruin_instances` say what the entries made. An entry with `"representation": "Blocks"` and a `block_kit` (`engine.scene.RuinBlockKit`, relative to the scene) draws the same buildings **laid block by block** ([ruins](ruins.md#the-block-layer)): the kit is read for the footprint, and only the block kit's meshes are appended, since nothing would instance the kit's members and E33's are hundreds of megabytes on the GPU; every block is a plain instance, standing or fallen. An entry of more than 32 tiles is assembled on a job system's performance pool made for the read — `build_cache_textures` already makes one for textures — because a thousand buildings laid block by block are hundreds of milliseconds on one thread; the buildings are joined in tile order, so the instances are the single thread's (the renderer's ruins test reads forty buildings pooled and compares them with the layer's own single-threaded output), and the `ruins assembled` line says how many threads it used. `load_scene` ends with a `scene loaded` line (`ms`, `meshes`, `instances`, `pairs`, `clusters`): an offscreen run had no other record of what the load cost, and a scene of hundreds of thousands of instances spends its time there. The renderer links the capability only where the configuration has it (`ENGINE_RENDERER_RUINS`), the way engine-view links `animation`: without it a scene that names ruins is refused with a sentence, and every other scene reads as before. A scene fragment `engine-content ruins` wrote is an ordinary scene of instances and reads the same with or without the capability.

**The camera path** (`camera_path.h`) is keys of time, position, a look-at point or an orientation, and a vertical field of view, flown `Linear` or `Smooth` — a cubic Hermite through every key with tangents averaged from its neighbours, except that a key beside a segment that does not move gets none, so a hold is a stop and not a wobble; the field of view eases rather than following the cubic, because an overshooting zoom would be the one wobble nobody could explain. A key may hold its height above the terrain, and an orientation becomes a point 100 m ahead so both forms interpolate alike; both are resolved once, when the file is read against the loaded scene, so sampling is arithmetic. `camera_path_frame(path, f, frames)` spreads `frames` over the path, both ends included: at the path's own `frame_count()` it is time `f / fps`, and any other count resamples it. Markers name frames at the path's own rate; `marker_frame` maps them onto a resampled run.

**The timed flight** (`fly_camera_path`, `flythrough.h`) is the loop both hosts ran already, with the path in it: frames kept in flight, never waited on, `Stats::last` read after every `begin_frame()`, each path frame's record (`frame_record`) kept against the submission that drew it, and `frames_in_flight` extra frames at the end so the last path frames fold in. Each of `repeats` flights starts with `warmup` frames **and** `warmup_seconds` of them at the first camera: the frames give every repeat the same occlusion history, the seconds bring a fast card's clocks up (240 frames of a 0.1 ms scene is 24 ms of work). `summarize_frames` takes each frame's **median over its repeats**, then the median, p95 and p99 over the path, per pass and for the frame's sum of passes; it also says whether every repeat drew the same visible pairs at every frame (`deterministic`), which holds for an unstreamed scene and does not for a streamed one, whose pages land when their reads do.

**The CPU's side of a frame, and an interactive session's ticks** (2026-09-24, `FrameRecord` version 4, `FlythroughSummary` version 4). A record now carries `cpu_ms` — the CPU's own milliseconds for the frame, which in the timed flight is `submit_frame` and the camera sample, never the wait in `begin_frame` for a free slot — and `frame_ms`, the wall time since the previous submission began, which is the frame time a player sees. `frame_record` leaves both at zero and the loop that runs the frames fills them, because the renderer does not see the loop around it. The summary gains their percentiles beside the passes' (`cpu_ms`, `frame_ms`), `ticks`, and `interactive`: engine-view's `--interactive` and `--replay-input` write this same JSONL with a **`ticks`** count on every record — the fixed camera ticks the frame consumed — and the session's header and trajectory in `interactive` (null for a path). The additions are `@since(4)` with defaults, so an older reader of either line sees what it saw, and `render.benchmark`'s `flythrough` result carries the two new percentiles through the same `summarize_frames` ([apps](apps.md#--interactive-a-camera-somebody-flies)).

**The census is a second, untimed pass** (`VisibleCensus`): the same warm-up, then one frame at a time, the frame's visible list read back and counted by DAG level and by scene mesh (and, with pixels, the id channel counted by mesh). It cannot be inline, because the renderer never reads a buffer back inside a frame and a wait between timed frames would let the clocks fall and measure that; it compares its visible pairs with the timed pass's frame by frame, which is a second determinism check. `engine-view --verify-occlusion` goes further: every frame of the path drawn with and without occlusion culling, from two uploads of the scene in lockstep, and the (instance, cluster) under every pixel and every colour byte compared — [the occlusion invariant](#invariants) held over a real path instead of one frame. **What it first found on desert-overlook was a tie-break, not a culling bug**: over 2,401 frames at 1080p no pixel ever lost a nearer surface to occlusion culling, and yet 64 frames (Khronos set) and 1,118 frames (the owner's landmarks) differed, every differing pixel a pair of surfaces at **exactly the same depth** — overwhelmingly the palms, whose fronds are coincident back-to-back faces — because the visibility word's id was then the visible-list entry and the list's order is the cull pass's append order, which culling changes and nothing made repeatable (two identical checks of one build disagreed by 9 and 13 tied pixels). The id has been the scene's pair since 2026-09-24 ([gfx](gfx.md), "The tie rule"), and the same check now finds **nothing**: 0 frames, 0 pixels and 0 colour bytes differ over the whole path, on both sets and on both the mesh and the vertex path ([flythrough](../experiments/flythrough-desert-overlook.md)). So the invariant is the strict one again — occlusion culling does not change the picture — and the check keeps classifying a differing pixel by depth (`lost_nearer`, `gained_nearer`, `tied`, and `frames_culled_visible` for a frame with a nearer surface lost or gained), so that if a difference ever comes back it says at once whether it is a culling bug or a tie.

**What the flythrough found in the renderer, and fixed.** The occlusion history's ping-pong buffers were indexed by the **caller's frame number** (`FrameDesc::frame_index % 2`). That number drives the lights, and a caller may repeat it — a benchmark's warm-up holds frame 0, `render.capture` may ask for one frame twice — and a repeated parity made pass 1 read the flags written two frames earlier, or never: the first frame after a warm-up drew with no history at all (pass 1 empty, every pair through pass 2). The picture was right either way, because pass 2 catches what pass 1 missed, but the visible pairs and the timings were not the frame's, and repeats of one path disagreed at their first frame. The parity is now the renderer's own count of frames recorded (`recorded_`), which alternates whatever the caller passes; every picture is unchanged, and the flythrough's repeats agree frame for frame.

**Shadows are `auto` in both hosts**: traced wherever the device has cluster acceleration structures and ray queries (the RTX 5090), cascaded maps where it has not (the TITAN Xp; off there until 2026-09-24). A flythrough that measures occlusion culling passes `--shadows off`, because a frame that traces shadows runs one visible list and turns occlusion culling off ([Invariants](#invariants)); the maps leave it on. `FrameRecord::shadow_casters` counts the casters the ray chain adds when it is on, `FrameRecord::shadow_pairs` the pairs the maps draw, and `PassMs::shadow` what the maps cost.

**A flight's host may change the scene between frames** (2026-09-25, `FrameRecord` version 5, `FlythroughSummary` version 5). `FlightOptions::before_frame` is a function pointer and a context called before every submission — warm-ups and the drain included — with the repeat, the path frame, its place in the warm-up and the camera the frame will be drawn from (`FlightStep`): where a streamed world updates its ring and hands the renderer its instances ([Instances that come and go](#instances-that-come-and-go)). It runs before `begin_frame`, so it is in the frame's `frame_ms` and not in its `cpu_ms`, which stay the renderer's own. A record now carries the scene the frame culled, `instances` and `pairs` (`FrameStats::instances`/`pairs`, captured per slot at the submission like the frame index), which are constant for a scene read whole and are the number E34 said a streamed world's ring bounds; the summary carries a streamed world's own block, `world` (`engine.world.TileWorldSummary`, [world](world.md#the-world-log)), null otherwise. Since `FrameRecord` version 6 a record also carries what a streamed world's tables cost that frame — `table_slots` and `table_pairs`, the instance slots it copied into the table set it flipped to and the pairs it expanded for them (zero on a frame with no change behind it), and `hole_pairs`, the pairs of its dispatch no instance holds — and `PassMs` (version 4) and `PassPercentiles` (version 4) carry `tables`, the copy and the expansion's GPU milliseconds ([Instances that come and go](#instances-that-come-and-go)); all of them default to zero, so an older reader sees what it saw.

**A windowed frame's waits, and when it was shown** (2026-09-25, `FrameRecord` version 6, `FlythroughSummary` version 7). A record gains `wait_ms`, `acquire_ms`, `present_ms` and `pace_ms` — the CPU milliseconds a window's frame spent waiting for its frame slot, a swapchain image, the present call and the pacer, which `cpu_ms` leaves out — `pace_depth`, how far back the pacer waited, `submit_ms`, the part of `cpu_ms` inside `submit_frame` (where a driver can hide a presentation wait), and `shown_ms` and `latency_ms`, from the previous present reaching the display to this one's and from the frame sampling its input to its reaching the display, where the swapchain can say, and `pose_position`, `pose_yaw`, `pose_pitch` and `pose_time`, the camera an interactive frame drew and the simulated time it stands for. The summary gains `presentation` (`FlythroughPresentation`): the present mode asked for and got, the images, the frames in flight, the pacer with its misses and changes of depth, whether the window was borderless, the refresh the driver reports, the recreations and suboptimal presents, and the percentiles of every wait and display time. engine-view's window fills them ([apps](apps.md#pacing)); a flight fills none of them, since nothing in it presents, and `render.benchmark`'s `flythrough` carries `presentation` as null. Everything is `@since` with a default, so an older reader of either line sees what it saw.

**A streamed world's scene file** (`"world": {...}`, `engine.scene.WorldRings`, or `SceneFileOptions::world` — engine-view's `--world` — on a file with none). The block is carried and never interpreted, like an instance's `animation` (`WorldDesc` on `SceneDesc` and `SceneData`): the tile ring is the world capability's ([world](world.md)). What the reader does differently is the ruins: each entry is read — so a bad kit is refused with the scene, not when the first tile asks for it — and **both** of its kits' meshes are appended, the section kit's always and the block kit's when the entry is drawn in blocks, because the rings draw both; **no building is assembled**, and the entry becomes a `StreamedRuins` with everything the world's ruins consumer needs to assemble a tile's building exactly as a whole read would (seed, tiles, count or density, wind, both kits and where their meshes start). An entry whose `tile_size` is not the world's is refused: a ring tile has to be the entry's tile. `SceneData::dynamic` is set, which is what tells the GPU scene and `resolve_settings` that instances will come and go.

## Instances that come and go

A streamed world's buildings arrive and leave with their tiles ([world](world.md)), so the resident scene has to take instances **between frames** without loading the scene again. The meshes stay — a kit is a few dozen, loaded with the scene — and only the instances change: `SceneRenderer::set_dynamic_instances(tail, blocks)`, which hands the tail to `GpuScene::set_dynamic_instances` and **does not wait for the device**. The meshes' textures stay with them, one per distinct image for the whole kit, and a tail uploads none ([One upload per distinct image](#one-upload-per-distinct-image)).

**A fixed prefix and a tail of blocks.** A scene whose `SceneData::dynamic` is set is its load's instances — the terrain, whatever the file placed — followed by a tail the caller hands over whole, **named block by block**: a `DynamicBlock` is a key and a run of the tail, and the world's ruins consumer names one per tile, by the tile's key, from the ranges it builds the tail out of (`RuinsTiles::tile_ranges`, engine-view's `ViewWorld::hand_over`). A caller that names none hands the whole tail over as one block. The prefix never moves: its instances, their `first_pair`s and so their pairs keep their numbers through every change, so the terrain's occlusion history survives every tile and its ids mean what they meant. **Neither does a tile.** Each block gets a run of instance slots and a **reserved** run of pairs, laid out in the same order in both spaces (`TileLayout`, `tile_layout.h`), so the instances' `first_pair`s stay sorted and a tile that arrives, leaves or changes writes its own slots and nothing else; every other tile keeps its instances, its pairs, its ids and its occlusion history, the way the prefix always did. The instances are placed as the load places its own (`make_instance`: the mesh's fit, then the instance's transform, at the pair its block gives it; `SceneData::mesh_fit` keeps the fits, because the float positions they were measured from may be gone by then) and given their mesh's material base (kept by the GPU scene from the material table's layout). Until 2026-09-25 the tail was one prefix sum after the load's instances, so every change rewrote every tile's instances and pair entries behind the first one that moved and waited for the device to do it: [E35](../experiments/e35-world-streaming.md) measured 3.2 ms a change for a kit of boxes and 15–17 ms for E33's ashlar kit, whose tail is eight million pairs — the largest cost of a frame by two orders of magnitude, on six frames of seven along the desert flythrough.

**The block rules** (`TileLayout::apply`, each counted in `Stats::tiles`):

- **Size.** A block reserves its instances' pairs rounded up to `k_block_pair_granularity` (16) and its slots rounded up to `k_block_instance_granularity` (4), and past eight granules to eight steps an octave (9, 10, …, 16, 18, 20, … granules; `block_capacity`), so at most an eighth of a large block is slack and blocks come in few enough sizes that a freed one fits the next tile of its kind. A slack pair costs the cull what a hole does (below), which is why it is an eighth and not the quarter the first version allowed: [E37](../experiments/e37-tile-instance-blocks.md) measured the ashlar world's holes at a median 16% of the dispatch with four steps an octave. Sixteen pairs is small beside an ashlar tile (tens of thousands) and not much beside a tile of one-cluster boxes (a few dozen).
- **Kept** when the key comes back with the same instances — mesh, transform and padding, compared field by field against what the slots were made from: nothing is written. **Rewritten in place** when the key comes back with other instances that still fit its block (an ashlar tile moving from sections to walls, 25,726 pairs to 24,377, stays where it was). Otherwise the old block is freed and the tile placed.
- **Placed** in the smallest free block both of whose runs hold it, split when what is left is at least a granule of each; when none does, at the end. A freed block merges with a free neighbour, and a free block at the end is given back before anything is placed, so the dispatch ends where the last tile does.
- **Compacted** — every tile laid out again in the caller's order, as a first fill lays it, and every slot written once — when the holes pass `k_default_compact_pct` (25%, the `renderer.tiles.compact_pct` tunable, read when the scene is created) of the pairs the cull dispatches and `k_compact_min_holes` (4,096), or when the caller asks (`set_dynamic_instances(…, compact = true)`) — engine-view asks when its world starts over, at a flythrough's repeat, so every repeat lays its tiles out as the first fill did and inherits nothing of where the last one's ended up. A layout whose classes' slack would take it past the 2^24 pairs is packed **tight** instead — each block exactly its tile — which is the layout a scene loaded with the same tail has and which the pair check below already proved fits.

**A hole is a pair nobody owns, and the cull rejects it after its search.** The slack a block keeps past its instances and a freed block are holes: the cull dispatches one thread per pair of the whole space, holes included. A block's slots past its instances, and a freed block's, hold **null instances** of a **null mesh** — one `gfx::MeshDesc` past the scene's, with no clusters — whose `first_pair` is where the live pairs end, so the slots stay sorted and the binary search over `first_pair` is exactly the one `scene.slang` has always had; `cluster_cull.slang` then rejects the pair because it is past the found instance's clusters (`pair - first_pair >= mesh.cluster_count`), before it reads anything about a cluster. A scene read whole has no holes and never takes the branch; `pair_of` and the pair table's inverse are unchanged, and `GpuScene::pair_cluster`, the CPU's decode, answers "nothing" for a hole the same way. A hole therefore costs the cull about what a pair it culls does, since the search is most of a thread: [E37](../experiments/e37-tile-instance-blocks.md) measured the ashlar world's cull 18% slower with a median 17.5% of its dispatch in holes, which is why the compaction share bounds it. Rejecting a hole before the search needs a per-pair mark the cull could read first — the pair table, as the resolve reads it — and a field in `gfx::CullParams` to name it, which is not built.

**The pair table is expanded on the GPU.** The pair table — the {instance, cluster} of every pair, which the resolve decodes a pixel's id through — used to be built on the CPU for the whole tail and uploaded with every change: 66 MB for the ashlar tail, most of its 15 ms. Everything its entries hold is already in the instance table, so a change now uploads its own slots and a list of the live instances among them, and `pair_expand.slang` writes their entries: one 64-lane workgroup per listed instance, its lanes striding over the mesh's clusters. A hole's entries are never listed and keep whatever they held, because nothing reads the pair table but the resolve and only for a pair the frame drew.

**Table sets, flipped at the frame boundary.** The instance table and the pair table a frame reads are one of `GpuScene::table_sets()` **sets**, at least two and one per frame in flight (`reserve_table_sets`, which `SceneRenderer::create` calls). A change is written into the CPU's table (`instance_table_`) and marked, as runs of slots, pending for every set; the next frame to be recorded flips `GpuScene::instances` and `pair_table` to the next set and brings it up to date before anything reads it (`GpuScene::prepare_tables`): it copies that set's pending runs out of the frame slot's own staging buffer (host-visible, kept, one per slot, written after `begin_frame` has waited for the slot's previous frame) in a `table copy` transfer pass and expands their pairs in a `pair expand` compute pass, both in the render graph, and every pass that reads either table declares it. A set is written only by the frame that flips to it, and the sets are used in turn, so a set comes round again only after every other one has been current — at least as many frames as there are frames in flight — and the frames still in flight read the others. **So nothing waits for the device:** a change is CPU work on the tile's own instances and a flip, and when a change outgrows the per-pair buffers or the table sets (below) the old buffers go to `gfx::FrameContext::defer_destroy` rather than to a wait, and are freed when the frames that may read them are done. A frame with no change behind it flips nothing and declares nothing; a scene read whole has one pair table written at upload and one instance table, as before.

**The picture does not depend on where a tile's block is — with one stated exception.** A tile's instances sit wherever its block is, so a streamed scene's instance numbers and pair numbers are not a loaded scene's; its surfaces are. The ids a capture decodes name the same (cluster, triangle) of the same instance, which `GpuScene::tail_index`/`tail_indices` turn back into its place in the tail — the loaded scene's numbering — and every depth and colour is the loaded scene's word for word ([What holds it](#instances-that-come-and-go), below). **The exception is a depth tie between two tiles' surfaces.** The tie rule gives it to the larger pair ([gfx](gfx.md), "The tie rule"), and which of two tiles has the larger pairs now depends on the order the blocks were placed in, where the one prefix sum made it tile order — a function of the set. Within a tile, and between a tile and the prefix, a tie goes where it always did, and a compaction lays the tiles out in the caller's order again. Two tiles of a streamed world are buildings on different ground and do not share coincident surfaces; a world whose tiles do would see the winner of such a tie depend on when each arrived.

**Every per-pair buffer is laid out by a stride, not by the count.** The visible list's runs, the per-view pair-to-entry tables, the occlusion flags, the vertex path's indexed-draw records and the table sets' pair tables are `GpuScene::pair_stride()` apart or long — `visible_base`, `cascade_base`, `pair_entries_address`, `vertex_records_offset` and the shaders' own run strides (`DeformAllocParams::pair_count`, `ClusterRecordParams::pair_count`, `DeformParams::max_entries`) all take it — and only the cull's dispatch and its bounds check take `pair_count()`, the end of the layout's pair space, holes included. For a scene read whole the two are one number, so its layout, its buffers and its pictures are the bytes they were; the renderer's whole suite passing unchanged is the check. A dynamic scene's stride starts at its prefix's pairs and **grows** when the layout passes it — half as much again, in whole pages of 4,096 pairs, so a world that fills its rings reallocates a handful of times and not on every tile — and the per-pair buffers and the table sets are then made again (the old ones deferred), after which the occlusion flags hold whatever the allocator left and the next frame fills both, as a first frame does, and every set is written whole by the frame that next flips to it. The instance tables keep a capacity the same way, in pages of 1,024 slots. A change that grows nothing leaves the flags alone: a tile's stale flag only decides which occlusion pass tests its pairs, and pass 2 tests everything pass 1 did not draw, so it may cost a frame of culling and never a pixel. The vertex path's index budget is the full `k_vertex_index_budget` for a dynamic scene, since no load can bound a tail; a cut past it goes to the capacity draw, as any cut does.

**The 2^24-pair limit stays a stated refusal.** `k_max_pairs` is the visibility id's 2^24 (`pair << 8 | triangle` in 32 bits). `pairs_after` checks a run of instances against it — or against a caller's own budget — and `set_dynamic_instances` checks the tail's pairs before the layout is touched, and the layout's own end after it, packing the tiles tight when the classes' slack is what passes it: a tail past it is refused with a sentence and the scene is exactly as it was. So are blocks that do not cover the tail in order or repeat a key, a mesh the scene has not and a skinned instance. The world's ruins consumer runs the same check before it asks — over every tile it holds, drawing the innermost rings and the nearest tiles first ([world](world.md#the-consumers)) — so a streamed world withholds its farthest tiles rather than a frame.

**Still rigid and rasterized.** The ray tracing chain's top-level records, its bottom-level set and its bucketing scratch are laid out once per instance, and so is the deformed-vertex pool's table; nothing rewrites them for a tail, so `GpuScene::create` refuses a dynamic scene with the chain or the pool, and `resolve_settings` resolves them away first: the ray path draws with the rasterizer, traced shadows become the cascaded maps (whose runs follow the views' at the stride like everything else), and `--deform` is off, each with a warning; a skinned or morphed dynamic scene is refused. The chain's `slots_main` searches `first_pair` too and would need the cull's hole check the day a dynamic scene is traced. [E37](../experiments/e37-tile-instance-blocks.md) measures the blocks along E35's flythrough: a change costs 0.17–0.18 ms of CPU with the ashlar kit and 0.36 ms with the kit of boxes, against 15.6–15.9 and 3.3 ms before, and no frame waits for the device (the worst frame is 2.4 ms of wall time, against 23); a frame that brings a table set up to date spends 16–17 µs of GPU on it at the median, and 0.27–0.51 ms on a whole rewrite after a compaction or a growth; and the holes, at a median 14–18% of the dispatch under the 25% share, cost the ashlar kit's cull 18% (0.037 ms) — a hole costs what a culled pair does, which is the search — and the boxes' nothing measurable. At a 12% share they cost half that for four times the compactions. What a change still reads whole is the tail itself: the world hands every tile over on every change, and the renderer compares each against what it holds to find the ones that changed.

**What holds it.** `dynamic_instances_tests.cpp` builds one scene with a prefix (a box and the ground) and, in its first case, gives it tails as one block between frames — a tile of six boxes; that tile and 768 small boxes, which grows the stride twice (to 4,096 and to 12,288 pairs); another tile alone, rewritten in place and compacted; both tiles in the other order; nothing — rendering a few frames from elsewhere after each change so the capture's occlusion history is a moving one, and captures each against a scene **loaded** with the prefix and the tail from the start: **0 id, 0 depth and 0 colour differences** at every step, through the mesh path with occlusion culling, with cascaded shadow maps, and through the vertex path's indexed draw, with the tail holding 832–7,550 of the pixels (RTX 5090, 2026-09-25). Its second case hands the tail over **tile by tile**: a tile, then a second behind it, the first leaving a hole, a third taking the hole (a block reused, split), a fourth going to the end, the first coming back differently and then moved (rewritten in place), a compaction asked for, the large tile leaving so that the holes bring one on, and nothing — every step against the loaded scene, with the ids compared through `tail_indices`, and `validate_tables` (every slot's `first_pair` at or above the last, every live slot its block's, every other slot null) after every change; and then the same ten changes on **consecutive frames none of which is waited for**, captured at the end — through the mesh path with two and with three frames in flight (two and three table sets), with cascaded maps and through the vertex path: **0 id, 0 depth and 0 colour differences** at every step of every run, with 2 compactions, the hole reused, and 10–320 hole pairs at the steps that have them (RTX 5090, 2026-09-25). The same file checks that a scene read whole refuses a tail, that the ray path and traced shadows resolve away for a dynamic scene, that `PairExpandParams` is the push-constant block `pair_expand.slang` reflects, and, with no device, the pair cap and the placement: a tail's prefix sum, a caller's own budget, the 2^24 limit before anything is allocated, a mesh the scene has not, a skinned tail instance, and the fit and the transform composed as the load composes them. `tile_layout_tests.cpp` holds the layout's arithmetic with no device: the classes and their quarter bound; first fill, keep, rewrite in place, free, reuse with a split, merge and trim, step by step; compaction by share and on request, tight packing at the cap and the refusals past it; and 400 random changes of forty tiles of four kinds, after each of which a simulated table written from the layout's own writes is sorted by `first_pair`, holds every tile where the layout says, and answers every sampled pair of the dispatch — found by the cull's own search — with its tile's instance or with nothing.

**Canonical vertex ids, read-only.** `mesh_vertex_ids(scene, mesh)` is a span over the loaded mesh's cluster vertices' canonical ids ([geometry](geometry.md#canonical-vertex-identity)): entry *i* names `lod.mesh.vertices[parts[mesh].first_vertex + i]`, and `parts[mesh].vertex_id_source` says which id space it is in — each mesh of a scene has its own. ## Testing

`tools/dev.ps1 test -Preset msvc-debug -Filter renderer` runs the module's tests, all headless. They write a unit-cube GLB at test time (one primitive, one material — the fixture `apps/engine_view/tests` writes, minus the textures) into a `test::TempDir` of their own, with the derived-data root inside it, so nothing in the tree, nothing in the repository's cache, and nothing another copy of the suite is using is touched (AGENTS.md, test hygiene). They skip with a message on a machine with no Vulkan device or no 64-bit buffer atomics, exactly as engine-view exits 3. `vertex_id_tests.cpp` needs no device: a two-quad `.gltf` whose shared edge carries two authored ids loads with all eight vertices, `authored` on its part, and every id at the position the file gave it — from the glTF on a cache miss and again from the container on the hit; a scene of it beside the same file without the attribute keeps one id space per mesh (`authored`, then `position_weld` ranks under 6) with the two spans adding up to the merged vertices; and the procedural terrain exposes no ids. The others check: a cube rendered offscreen into all four channels at once, with the center pixel's id naming instance 0, a cluster of that scene, and a triangle under 128, and an uncovered corner naming nothing; every `Stats` field present and consistent; the four channels landing on disk in the documented shapes, with the id file exactly `width * height * 3 * 4` bytes; two instances of the cube producing exactly the ids 0 and 1 and no others; `resolve_settings` making the same five decisions on a synthetic baseline device, an RT device, and a path that cannot shadow; and the direct path refusing an id capture with a message while still capturing color.

**The glTF sampler's wraps and the texture transform** are a fourth case of `texture_tests.cpp`: a quad with UVs from 0 to 3 and a 2×2 texture of four colours through a nearest sampler shows nine whole tiles under repeat, every other tile reflected under mirror, and one tile then the edge texel under clamp — all 36 cells, matched to the nearest of the four colours at their centres — and UVs from 0 to 1 with a `KHR_texture_transform` scale of 3 show the same nine tiles; each from the decoded image and from the built texture, with one material sampler in the scene. The reference's agreement case gained a **dark plane lit by its own emissive texture**, held to the same kind of FLIP bound as the other three: 0.014 on the RTX 5090, under a bound of 0.05 ([Materials](#materials)). The emissive and occlusion slots, the ORM packing and the transform's rotation are held to the CPU reference at the gfx level, 1 of 255 at worst on the RTX 5090 ([gfx](gfx.md)).

**Built textures have three cases** (`texture_tests.cpp`, [Built textures](#built-textures)), each over a textured quad written at test time and loaded through a derived-data root in the test's scratch directory, drawn through the albedo view (`ResolveMode::Albedo`, the textured base colour unlit, so the lights are not in the comparison), once decoded and once after the test builds the `.tex` the container names. **Up close**, where level 0 is what both paths sample, the built picture is within BC7's bound of the decoded one (PSNR above 38 dB, no channel more than 16 codes off). **Far away**, a one-texel checkerboard resolves to its mean through the mips — display value 186, half the light, since the chain was filtered in linear light — with a spread under 3 codes, where the decoded path aliases to black and white. **The level the hardware picks** is read back from a probe texture written by hand whose level L is red 28 L: at four distances the red, taken back to linear, gives the level of detail the resolve's analytic derivatives selected, and it is log₂ of the texels per pixel that the projection's finite difference across a pixel gives, within 0.2 of a level. The distances put the level just past a whole one on purpose: NVIDIA's driver shortens the blend between two levels (a fraction f of the way reads as min(1, 2f)), which is the driver's filtering and not the derivatives' choice ([texture](texture.md#what-it-measured)).

**One upload per distinct image has a case of its own** (`kit members that sample one image upload it once and draw the same picture`, [One upload per distinct image](#one-upload-per-distinct-image)): four kit members written at test time, each a glTF quad in a directory of its own — two naming their own copy of one PNG beside them, one embedding the same bytes as a data URI, one naming an `image.png` that is another picture — three instances each, from the decoded images and from the built textures a cold cache fills. Each member's own upload (`share_textures` off) is four textures; shared, it is two — the three members whose bytes match, whatever they called the image, and the one that only shares its name — with half the bytes, the other half counted as saved, and **0 differing pixels** in ids, depth and colour at 256×256 (14,840 covered, RTX 5090). The same scene loaded with one instance and given the other eleven as a tail between frames keeps the same two textures and bytes and draws the same picture again.

**On a device without mesh shaders or ray queries — the baseline tier — the suite runs, it does not skip.** `RenderSettings{}` asks for `hw`, which `resolve_settings` turns into the vertex path there, so every case about the *picture* (the cube and its channels, two instances, the surround's centre view, occlusion culling, Panini, the skinned bar and its bend and sweep, the morph cases, the pool's budget, the cones, the shredded atlas, and all seven streaming cases) draws through `cluster_vertex.slang`. Only a case about a *path* skips, naming what is missing in the device's own words: the direct path (`no mesh shaders`), the mesh-path half of "the mesh, vertex and ray paths agree" and of the cone case (`no VK_EXT_mesh_shader`), and every ray half — the ray path, the turned surround's TLAS half, the four reference cases, the 8-bit-index streaming case, which only exists when the frame builds the ray chain — with `unavailable_reason`'s sentence. "The mesh, vertex and ray paths agree" holds the other two to the **vertex** path now, because it is the one every device that renders has; asking a device without mesh shaders for `hw` would compare the vertex path with itself. The harnesses of the atlas and streaming files skip **only** on no device or `check_availability`; a scene, GPU scene, page source or renderer that fails to build is a `REQUIRE` failure. Until 2026-09-23 they reported any build failure as a skip, which is how nine cases — all eight streaming cases and the shredded atlas — "passed" on the first run on the TITAN Xp without drawing a frame, while the renderer could not be created there at all; eight of them draw there now, and the ninth, the 8-bit-index case, skips because the card builds no ray chain ([self-hosted runners](../ci/self-hosted-runners.md#the-first-run-on-the-titan-xp)).

**A TITAN-Xp-like device is a case of its own** (`a TITAN-Xp-like device draws the default request through the vertex path`), so the baseline tier is tested on every GPU and not only on the server: `DeviceOptions::overrides` removes `VK_EXT_mesh_shader`, `VK_KHR_ray_query`, `VK_NV_cluster_acceleration_structure` and the two extensions the card lacks besides, which creates a device that really lacks them. The default request builds and draws there through the vertex path's indexed draw (the card has `geometryShader` and `fullDrawIndexUint32`, so the profile keeps them, and the case checks `vertex_indexed`, a nonzero `triangles_hw` and no fallback) with occlusion culling and no shadows, and the picture — a two-row wall of cubes at 200×120 — is compared with the same scene drawn by the device as it is with shadows off: on the RTX 5090 that is the mesh path, and **7,931 covered pixels, 0 id words, 0 colour bytes and 0 depths differ**. `--shadows rt`, `--raster rt` and the reference are refused on the profile with the verdict's own sentence, which has to name `VK_KHR_ray_query` and appear verbatim in `verdict.degraded`. The two devices are built one after the other and never live at once (see [gfx](gfx.md), "One live device per process"): the first draft held both, and the full device's next mesh draw called a null `vkCmdDrawMeshTasksIndirectEXT`.

**The baseline tier's two draws are one picture** (`without geometryShader the vertex path capacity-draws the same picture`). The same wall with the default request, drawn on a device without mesh shaders twice — with `geometryShader`, which is the indexed draw, and with it removed as well, which is the capacity draw — must agree to the byte: the ids, the colour and the depth, **7,931 covered pixels and 0 differences** on the RTX 5090 and on the TITAN Xp itself, with 72 triangles drawn indexed on one side and `triangles_hw` 0 on the other, over the same visible pairs. Both hardware runs draw in it, since occlusion is on. That equality is what lets `resolve_settings` choose between the draws by a device feature alone; the case skips where the adapter has no indexed draw to take away (no `geometryShader` or no `fullDrawIndexUint32`); removing `geometryShader` alone is enough to force the capacity draw.

**A scene's ruins** (`ruins_scene_tests.cpp`, compiled with the ruins capability, no device): the kit of boxes written into the test's scratch directory and a scene with a terrain, a mesh of its own and four buildings read — the file's mesh, then the kit's, then the terrain, the instances exactly the assembler's for those fields in that order with the file's first and the terrain's last, every debris block on the terrain under it and every wall at or under the ground where it stands, a second read identical to the bit, and the scene loaded into a derived-data root in scratch — and a scene naming a kit that is not there refused with the entry named. engine-view's `ruins_view_tests.cpp` draws the same kind of scene offscreen ([ruins](ruins.md#testing)).

**The streaming cases wait for the reads, not only the queue.** `streaming_tests.cpp`'s `converge()` counts a frame as quiet — four in a row end the loop — only when nothing is pending, nothing is staged **and `StreamStats::loads_in_flight` is zero**. Until 2026-09-25 it left the last out, and on the TITAN Xp under load "pages read from the container draw what pages read from memory draw" declared convergence with five reads still in flight and captured a picture missing the pages they carried (463 s instead of 200 s, and a failure that passed on a rerun). A file-backed source's read has no bound in frames; the only honest end of a convergence is a streamer with nothing outstanding anywhere, which is the same three-way condition `GeometryStreamer` itself uses for `frames_to_converge`.

**The flythrough's cases** (`flythrough_tests.cpp`) are in two halves. With no device: the camera path — keys hit exactly under both interpolations, the cubic leaving the straight line between them, the frame count and the resampling, and each refusal with its sentence (no keys, times that do not increase, a height above a terrain the scene has not, a marker past the end, an unknown field); the terrain — deterministic, its ridge and basin where the fields put them, dunes with real relief, materials by feature, a hash that moves with every field, and a counter-clockwise grid; the scene file — the oldest spelling read as it always was, a typo refused with its path, grounded and yawed placements, a scatter inside its annulus and identical on a second read, a fit to 4 m on its point and to 2 m about its centre, a hash the bytes do not have refused naming both, and the overlay substituting by hash and then insisting on it; the summary's percentiles and per-frame medians over synthetic records; a terrain's cache entry giving back byte-identical positions and materials; and **every one of the fixture terrain's 182 clusters drawing with its own material after the scene's merge** — the vote of the merged cluster's own vertices against the map the GPU upload reads, on a cache miss and on a hit, with rock and sand both present so the check can fail (it found 18 wrong before the fix); and the scene file's `camera_path` resolved against the file's own directory like a mesh path, and absent from the oldest spelling. On a GPU, over a 64 m terrain with an 8 m ridge and three fitted cubes behind it: **two rigs built from scratch fly the path to the same visible pairs at all 25 frames**, `Stats::last` returns every frame once and in order with its own frame index, and the same rig flown again agrees from the fourth frame on; and **occlusion culling changes no pixel anywhere on the path** — all 25 frames drawn with and without it in lockstep, 0 surface and 0 colour differences — while the census shows it culled the hidden cubes (0 pairs against 12 at frames 3–6) and they are drawn once in view.
**Occlusion culling changes no pixel**, which is the case that guards both of the fixed-cost changes above: the same wall of cubes at two depths is rendered with `occlusion` on and off at 302×154 — a multiple of neither the 32-pixel coverage tile nor a surround's thirds — and every colour channel and the (instance, cluster) under every pixel must agree, at both `single` and `surround3`. Shadows are set off for it, because they turn occlusion off with them and this GPU would otherwise have taken them, which is also why the module's other cases never exercise the Hi-Z at all.

The multi-view cases add four. **The layouts**, on the CPU with no device: a single view over the whole target; a flat surround whose three off-axis rectangles meet and whose union is the single view's, with the centre one centred; a turned surround whose side cameras carry the yaw and whose side views alone carry the peripheral LOD multiplier; and a Panini view whose oversampling factor is the arithmetic's, is 1 at d = 0, and is refused past `k_max_oversample`. **The off-axis projection** against `perspective_reversed_z` through a centred rectangle, and a shifted rectangle putting its own centre line at normalized x of zero. **The Panini inverse map** against the projection it inverts, azimuth by azimuth, and its centre against the source's centre. **The frame itself**, on a GPU: a flat surround's centre monitor against a single view of one monitor from the same camera — equal visible-pair counts and *the same ids and the same colors, all 16,384 pixels of them* — and a 35-degree surround with one cube in front of each view's own centre, where each view's centre pixel names its own instance through the rasterizers **and** through the ray path, which proves the union structure serves every view. The d = 0 Panini case renders the same scene both ways and reports how many pixels differ. `Stats::gpu_memory` is checked with the rest of the statistics: a device-local total above zero always, and a budget within that total on a device with `VK_EXT_memory_budget`.

The pictures are pinned end to end by engine-view's own suite and by the comparison in that page: the FlightHelmet at a fixed orbit through `--raster hw`, `--raster vertex`, `--raster rt --shadows rt`, `--deform wave`, and `--grid-instances 3` is **byte-identical** before and after the move out of `main.cpp` (PSNR null, SSIM 1, FLIP 0 on all five).

**Skinning adds four cases**, over a two-bone bar built in the test rather than imported — a skinned glTF written at test time would be testing the importer too, and what these are about is the renderer's half of the contract. The bar is a square column sliced into 32 rings, bound root-to-tip by height, so every vertex of the top half moves when the tip joint turns. At the **bind pose** the skinned instance draws exactly what a rigid instance of the same mesh draws: 4,776 covered pixels, 0 id words differing, worst depth difference 4.7e-10 against the documented 2e-7 (they cannot be bit-identical — the rigid path dequantizes inside the rasterizer while the skinned one reads the float the pool stored). A **60° bend** moves the picture where `anim::skin_positions` says: the drawn rectangle's bend axis is [63, 109] against a projected [62.6, 110.0], 1,099 of 1,330 pixels change coverage, and the bent bar is visibly wider than the straight one. **Culling stays conservative** over the whole 0–90° sweep: twelve phases, each rendered with the exact displacement bound and again with eight times it, 0 id words differing at any of them, with the bar filling the frame where a frustum test can actually bite. And the three paths **agree on a posed frame**: the vertex path writes the same words as the mesh shader (0 of 1,278 covered pixels differ when this was written; 0 of 1,450 on 2026-09-23) and the ray path differs on 0 coverage and 1 triangle (0 and 0 on 2026-09-23), which is what a silhouette costs on a rigid mesh. The vertex path is the reference both are compared against, so on a device without one of the other two the case still runs and says which it skipped.

**The pool's suballocation adds a fifth case**, and it is the two halves of the budget. With the default budget over eight skinned bars, nothing overflows, `deform_entries` equals the visible pair count — plus `shadow_pairs` where the default request draws cascaded shadow maps, since a cascade's entries of a deformed instance get blocks of their own — and the pool's occupancy is the cut's 272 vertices rather than the instances' meshes. With `deform_pool_kib` set to **1** — 85 vertices, a third of what that cut needs — the pairs that did not fit draw their rest pose: the picture is still covered, every pixel still names an instance of the scene, `deform_overflow_entries` is nonzero, and placed plus refused equals the visible pairs (and the maps' pairs) exactly. That the budget is in kibibytes is what makes the second half writable at all; a mebibyte is more than a bar's whole mesh.

**A sixth case covers normal cones on a posed instance** (`a turned joint's clusters are not culled by their rest-pose cones`). The bar cannot carry it, because its clusters wrap all four sides and have no cone. The fixture is a closed sphere of 2,208 triangles bound wholly to a head joint and turned 150° about the vertical, with a rigid copy beside it. The frame's cut is set to the leaves (`FrameDesc::lod_px = 0`). A CPU witness, which runs with or without a GPU so the container's v3 builds check it as well, first establishes that the case is real: 8 of the skinned ball's 24 leaf clusters are culled by their rest-pose cones from this camera, and 6 of those face it once turned. The frame is then rendered with cones on and off through all four paths — `hw`, `vertex`, `sw` and `rt`, the first and last skipped by name on a device without them — and every id word and every depth must agree. The rigid ball must also lose clusters to the cone test, since a test that passed because the cones were off everywhere would be worth nothing. **On the unfixed shader the case failed** with 1,676 id words and 751 depths different of 2,639 covered pixels, identically in all four paths. It now passes with 0 and 0 in each, and cones on still take the frame from 48 visible pairs to 41.

**Shadow casters have three cases of their own** (`shadow_caster_tests.cpp`, [Shadows](#shadows)). In **`a cluster the cone test drops from the picture still casts its shadow`**, four casters (a single-sided card, a thin slab, a floating cube and an L) each stand between the sun and a ground plane with the camera on the dark side. Each is drawn in the shadow view three ways, through the mesh shaders and again through the vertex path: cones off, cones on with the casters dropped, and cones on with them kept. The two paths count drawn pairs in different words of their argument blocks and the casters in neither, so a change to how either counts cannot quietly take the casters with it. A CPU witness first shows that the cone test drops clusters of every caster from that camera, and all of the card's. The GPU half then requires the kept frame's shadowed ground to equal the cones-off frame's pixel for pixel. It requires the dropped frame to lose the card's whole shadow (521 pixels at 320×240) and part of the cube's (113 of 1,246). The two cones-on frames must draw the same pairs with the same ids, and drawn pairs plus casters must equal the cones-off cut. **`the ray path traces the casters' shadows and not the casters`** draws the card through `--raster rt`. Its ids are the same words with and without the casters in the structures, and its shadow comes back. **`the casters are on only where they mean something`** checks `resolve_settings` on a synthetic device: on by default with traced shadows, off with cones off, with the switch off, on the ray path without shadows, under templates, and without shadows at all. The two GPU cases skip by name where ray queries are absent (`unavailable_reason`'s sentence), which is every case on the TITAN Xp. The measurement on the Khronos samples is a fourth case, skipped by default (`-tc='renderer: shadow casters on the Khronos samples' -ns -s` in a release build, under the GPU lock).

**The ray tracing chain's capacity has three cases** (`rt_capacity_tests.cpp`, [The ray tracing chain's memory](#the-ray-tracing-chains-memory)). **`grows ahead, shrinks late, steps, and stops at the limit`** is the policy on the CPU: nothing moves inside a window, a whole window of small frames shrinks it, half the headroom eaten grows it to the demand plus the headroom in steps, a demand that swings between two cuts settles on the larger, and past the limit it stays at the limit. **`a chain sized by the frame draws what a chain sized by the scene draws`** flies a 3×3 grid of heightfields far, near, far, nearer and mid-way through the mesh path with traced shadows and through the ray path, beside a renderer whose chain keeps the whole union, with a four-frame window, no headroom and a 64-cluster step so it shrinks onto every cut and must grow for every larger one: every capture must be the same colour and the same ids, and the chain must have shrunk under the union and grown back (on the RTX 5090: 0 of 307,200 colour bytes and 0 of 230,400 id words differ at any of the ten captures, with 2 grows, 3 shrinks and a smallest capacity of 64 against a union of 6,453). **`past the budget a frame drops whole instances and costs only shadows`** gives the same grid a 1 MiB budget (163 clusters) under a cut that wants 400: the frames count their overflow and the instances they dropped, the capacity stays at the limit, the id channel is the full chain's word for word, and no pixel of the shadow view is in shadow that the full chain left lit. The records half of the rule is `domain/gfx`'s records test ([gfx](gfx.md)).

**The cascaded shadow maps have six cases** (`shadow_map_tests.cpp`, over the casters' fixture, which `shadow_fixture.h` now shares with `shadow_caster_tests.cpp`; [Cascaded shadow maps](#cascaded-shadow-maps)). On the CPU: **the fit** covers every corner of every slice in every view (checked through each view's own inverse matrix, a second route to the corners), collapses an orbiting camera's framing to one cascade over the scene's bounds, starts the first slice at the scene's near side from outside and at a thousandth of the distance from inside, keeps every radius bit-identical while the camera turns on the spot, keeps every centre on its whole-texel grid while it moves, and holds a turned surround's corners too; and **the settings** resolve `csm` for `auto` without ray queries and `rt` with them, for an explicit `csm` on hw and vertex, never on direct, sw, auto or rt, with occlusion culling left on and the knobs clamped. On a GPU: **the maps cast what a CPU ray finds** — every caster, through the mesh path and the vertex path, each ground pixel whose ray to the sun (Möller-Trumbore in double precision against the caster's triangles) has the same answer for every pixel within two of it must be black or white accordingly: 0 of 33,456–34,740 interior pixels differ for any caster on either path on the RTX 5090, 304–921 of them shadowed, and the two paths' pictures are the same bytes. **A caster outside the camera's frustum casts**: the card above and beside a camera looking straight down at its shadow (a CPU witness first requires both of its clusters outside the frustum) shadows 61,997 interior pixels in the maps with 0 against the CPU ray, where the ray-traced shadows draw 0 shadowed pixels. **The light-view cull never changes the shadow**: the cube and the L with the cascades' frustum test on and off, in the shadow view and the shaded one, and the 129 × 129 heightfield close in, plain and under `--deform wave` (which exercises the cascades' own pool blocks), give 0 differing colour bytes and 0 id words while the test culls 143 of 198, 145 of 201 and 336 of 792 pairs out of the maps (334 of 780 on the TITAN Xp, whose GCC build makes a slightly different heightfield). And **mapped and traced shadows agree** where both are defined: against the ray-traced shadow view of the same frame, 0 interior pixels differ on each caster, with 2,333–2,652 pixels in the band and 31–41 of them grey. On the TITAN Xp, through the vertex path, every count above that does not need rays is the same to the pixel. The TITAN-Xp-like profile's case in `renderer_tests.cpp` checks that the default request draws maps there through the indexed draw with occlusion culling on, with the picture's ids unchanged. The measurement on the Khronos samples is a seventh case, skipped by default (`-tc='renderer: cascaded shadow maps on the Khronos samples' -ns -s` in a release build, under the GPU lock; `ENGINE_SHADOW_SAMPLES`, `ENGINE_SHADOW_CASCADES`, `ENGINE_SHADOW_NORMAL_OFFSET`, `ENGINE_SHADOW_PICTURE_LOD_ONLY` and `ENGINE_SHADOW_NO_TIMING` narrow it). It asserts that at the picture's cut no interior pixel gets opposite answers from the maps and the rays, and it keeps the view that disagrees most as three PNGs in its kept scratch directory: the rays, the maps, and where they differ.

**Depth ties have three cases** (`visibility_tie_tests.cpp`; the rule is [gfx](gfx.md)'s "The tie rule"). **`coincident copies resolve to the last one, every run, every rasterizer`** draws 24 copies of one box at one transform, so every covered pixel is a 24-way tie, six times through each of the mesh shaders, the indexed vertex draw, the capacity vertex draw (on a device opened without `VK_EXT_mesh_shader` and `geometryShader`, which is what selects it), the software rasterizer and the ray path. Every pixel must name the last copy, every repeat must equal the first, and the three hardware rasterizers must write the same words. **`a tie between the two occlusion passes resolves as one pass does`** gives the second of two coincident copies a large `bounds_padding`, which moves no vertex, and frames away and then toward them, so the padded copy is in the previous frame's cut and occlusion pass 1 draws it while pass 2 draws the other: the picture must equal the single-pass one, with the padded copy winning everywhere. **`back-to-back faces resolve the same way every run and with occlusion`** is the palms' case, a curved sheet and its reverse in one mesh with cones off. On the atomic-append id the first two failed — the last copy held none of the 2,857 covered pixels on any rasterizer or the ray path, and occlusion on and off differed at 2,356 — and the third passed. Every repeat matched its first there too: a fixture this small fills a handful of workgroups, whose appends land in the same order each time, so what the cases catch is the rule and the two passes, not run-to-run noise, which needs the flythrough's scale to show.

## Performance notes

Nothing about the frame changed in the move, and the numbers in [apps](apps.md) and [gfx](gfx.md) still hold. Two allocations were added and both are outside the frame: the render graph is heap-allocated once (it is not default-constructible), and `capture()` allocates its staging buffers per call. The visibility buffer and the visible list gained `gfx::BufferUsage::TransferSrc` so a capture can read them; nothing in a frame copies from either.

**The fixed cost of a frame** — what it costs with nothing in view — is what [E9](../experiments/e9-multi-view.md) found dominates the owner's 11520×2160, and where the renderer's own passes were rebuilt.

- **The Hi-Z pyramid is folded, not built a mip at a time.** `Targets::hiz_dispatches` is `gfx::hiz_dispatch_count(mips)` and `add_hiz` records that many passes per view per build, each pushing one `gfx::HizParams` that names the source mip and how many folds to write; the shader does the rest in shared memory ([gfx](gfx.md)). The pyramid is bit-identical and the visible set is unchanged, which is the requirement: the Hi-Z is the input to a test that must not change the picture.
- **The resolve leaves the sky to the clear.** The resolve pass clears the colour target to the sky before it draws, so a pixel the scene does not cover is a fragment that would write the value already under it; `gfx::ResolveParams::sky_is_clear` says so and the shader discards instead ([gfx](gfx.md)). The renderer is entitled to set it because it owns both ends: `k_sky` in `scene_renderer.cpp` is the clear value **and** `ResolveParams::sky`, in one place, because two spellings of the same colour would make an uncovered pixel take whichever the clear said without anything saying so.
- **The resolve does not read a 32×32 tile with nothing in it.** The last Hi-Z build of a frame leaves a coverage word per tile behind its pyramids in `Targets::hiz` — one per workgroup of its first dispatch, so it is free — and `ViewTarget::coverage_offset`/`coverage_pitch` are where each view's is. The resolve pass declares a `FragmentRead` of the Hi-Z buffer and `ResolveParams::coverage` points at it, **but only when `resolved_.occlusion` is set**, because that is the only arrangement in which nothing writes the visibility buffer between the last Hi-Z build and the resolve. The build after pass 1 writes no mask at all: it would be a truthful mask of a moment nothing reads.

**The rule that keeps the mask honest.** A pass added to `record_frame` that writes the visibility buffer *after* `add_hiz(1)` makes the mask a lie, and the failure is a 32×32 block of sky where a surface should be. Today the pass order makes that impossible — occlusion culling only runs in the two modes that have no software-raster pass and no ray trace — and `resolve.coverage` is gated on exactly that flag. Whoever changes the order changes the gate.

**Skinning adds nothing to the frame's allocations and one memcpy to its CPU cost.** [apps](apps.md) has the crowd numbers; two of them belong here. A thousand characters' matrices are **1.18 MB a frame**, one copy into a mapped buffer, which is what the 3×4 form was chosen for — the fourth row would make it 1.57 MB. And the pool pass costs the cut, not the scene: 1,325 visible clusters over 1,024 skinned instances deform in **0.132 ms** at 3840×2160, against 0.011 ms for a single instance's 8 clusters.

**What the pool pass costs, before and against E25's line** (RTX 5090, `msvc-debug`, 1920×1080, `--orbit 22`, `--deform wave --shadows off`, 240 frames; `before` is main's build with the per-instance pool, `after` is the per-frame suballocation, both measured back to back on the same machine). `alloc` is the suballocator, which did not exist before:

| Scene | cut (pairs) | `deform` before | `deform` after | `alloc` after |
|---|---|---|---|---|
| heightfield `--grid 1025 --lod 1` | 373 | 0.0080 ms | 0.0084 ms | 0.0061 ms |
| heightfield `--lod 0.25` | 1,228 | 0.0090 ms | 0.0092 ms | 0.0113 ms |
| heightfield `--lod 0.06` | 4,352 | 0.0121 ms | 0.0116 ms | 0.0275 ms |
| 64 FlightHelmets `--lod 1` | 562 | 0.0093 ms | 0.0085 ms | 0.0085 ms |
| 64 FlightHelmets `--lod 0.05` | 24,131 | 0.0223 ms | 0.0206 ms | 0.1234 ms |
| 1,024 foxes, skinned, 3840×2160 † | 1,325 | 0.1341 ms | 0.1323 ms | 0.0103 ms |

† with `--anim-lod off`, because the default coarsens that crowd to LOD3 and a frozen instance hands the pool pass no bone matrices at all — which takes the same row to **0.024 ms**. That is the animation LOD doing its job rather than the pool's layout doing anything, and it is why the comparison above pins the flag.

Three things it says. **The pool pass itself did not move** — within ±5% at every cut size, which is what a layout change that touches only where a workgroup writes should look like, and E25's 9.4 µs fixed cost plus 0.9 µs per 1,000 visible clusters still describes it (here: 7.8 µs fixed, 0.53 µs per 1,000). **The skinned crowd's 0.13 ms is not the layout's fault and the new layout does not fix it**: at 1,024 instances a workgroup reads a different instance's bone-matrix array and a different `DeformDesc`, and the pass is latency-bound on those scattered reads rather than on the 1.6 MB it writes. Packing the blocks does not change which arrays a workgroup reads; what would is sorting the visible list by instance so that consecutive workgroups share a matrix array, and that is a change to the cull pass, not to the pool. **The allocator is the new cost, and it is serial**: one workgroup means about 5 µs per 1,000 entries, fine at an ordinary cut and 0.12 ms at a 24,000-pair one. A two-level scan — block sums in parallel, one serial pass over the block sums — keeps the exact cursor and removes it; it is the first thing to do here if a frame ever has that many deformed pairs in it.

## Not yet

Multi-view got the per-frame working set split ([above](#multi-view-a-viewset-over-one-scene)), so a second `SceneRenderer` on one `GpuScene` is no longer what §4.6 wants — one renderer draws the whole set. What is still open there: a per-view **internal resolution** and the shading-rate half of foveation (the `ViewQuality::shading_rate` stub), which need `VK_KHR_fragment_shading_rate` in the RHI; one RT cut at a view-agnostic threshold instead of the union of the views' cuts; a filtered color-domain Panini resample; multi-window presentation and per-output HDR metadata (engine-view has one swapchain); and the screen-space passes §4.6 says run per view, none of which exist yet — there is no TAA, no denoiser and no upscaler to run per view. Changing `RenderSettings` without rebuilding the `GpuScene` and the `SceneRenderer`: the deformed-vertex pool and the ray tracing chain are sized by the settings, so engine-host rebuilds both and keeps only the `SceneData`, which is where the import and the clustering cost is. Streaming ([above](#geometry-streaming-the-gpu-half-of-pages-and-residency)) is built for geometry and **only** for geometry: the textures are still uploaded whole, the acceleration structures are sized by the frames rather than by a budget streaming shares ([The ray tracing chain's memory](#the-ray-tracing-chains-memory)) and their bucketing scratch is still four bytes for every pair in every view, and `04 §4.9`'s "one residency manager, three page types, one budget with per-type floors" is one page type with one budget. A page's bytes now come out of the `.clusters` container by range, so the budget bounds host memory as well as device memory — but only in the **steady state**: the load still materializes the merged streams and `attach_page_source` releases them afterwards, so the peak working set is what it always was. Making the load never read them needs `geometry::merge_paged_cluster_meshes` to take the merged vertex and triangle bases from the page table instead of from `mesh.vertices.size()`. Streaming also refuses a deformed or skinned scene and `--rt-templates`, for the reasons in that section, and a scene without a container behind every mesh keeps the in-memory source. The reference path tracer and the accept-or-reject loop's automation ([04 §4.8](../plan/04-renderer.md#48-reference-renderer-and-objective-optimization)) — `render.compare` is the metric half of it, and the integrator is Phase 2's.
