# schema (core) and schemac (tools)

**Purpose.** Every serialized or transmitted type is declared once in a `.schema` file (ADR-0007). `schemac` compiles it to C++ types with constant-initialized reflection tables, a JSON Schema, and Markdown; the `schema` runtime reads and writes any such type as JSON through those tables and applies version migrations. Agents never write serialization code. The IDL is documented in `schemas/README.md`.

**Owned data.** The global type `Registry` (qualified name → `TypeInfo`), the global `MigrationRegistry`, and the global `MaterializeRegistry` (record type → `MaterializeInfo`).

**Descriptors.** `TypeInfo` (struct or enum: names, version, flags, tag, doc, fields or enumerators, type-erased `StructOps`); `FieldInfo` (name, `TypeRef`, offset, `@since`, flags, doc); `TypeRef` (a `Kind` plus, for containers and optionals, element/key refs and type-erased `OptionalOps`/`ArrayOps`/`MapOps`). Generated code references the op tables from `core/schema/ops.h` so the walker never instantiates templates.

**Markings: `tag` against `flags`.** `@kind(x)` reaches C++ as the free-form string `TypeInfo::tag` ("component", "record", "event"), because it says what a type *is* and nothing generic branches on it. `TypeFlag::transient` is a bit in `TypeInfo::flags`, because generic code does: the persistence layer has to skip a transient type and the protocol has to know it will not be in a save. That is the rule for anything added later — a marking becomes a flag when generic code branches on it, and stays in `tag` when it does not. Field-level `@transient` is the narrower thing and stays where it was, in `FieldInfo::flags`; a struct may be `@transient` only when it is also `@kind(component)`, since a component is the only thing the store writes whole.

**The ECS backend.** `schemac` emits a fifth output, `<schemas/<stem>_ecs.h>`, registering the file's `@kind(component)` structs with the entity store ([ADR-0028](../adr/0028-ecs-and-persistent-store.md) seam 1). It is a header rather than a source file because the generated module is in the core layer and must not link flecs, while the registration must, and a header is compiled only where it is included — which ADR-0028 seam 5 confines to `domain/ecs`, `systems/`, `game/` and their tests and benches. The mapping from schema kinds to flecs' meta types is deliberately *not* in the emitter: generated code says which types to register and `ecs::register_schema_component<T>()` decides what a `vec3` or an `id128` looks like to flecs, so the judgement lives in one reviewable place instead of in generated text. What it can and cannot describe is on [ecs](ecs.md).

**JSON conventions.** Structs are objects keyed by field name, transient fields omitted; enums are names (integers accepted on read, unknown enumerators written as integers); optionals are null when empty; `Id128` and `bytes` are hex strings; maps with string keys are objects, other maps are arrays of `[key, value]`; fixed arrays must match their declared length. Missing fields keep defaults; unknown fields are errors unless `ReadOptions::ignore_unknown_fields`. Diagnostics carry a path such as `inners[1].x`.

**Migrations.** A `Migration{type, from_version, apply}` rewrites the JSON of one version step. `from_json_versioned` applies every step from the stored version to the current one, then maps; a missing step or a stored version newer than the build is an error.

**Invariants.**
- Every generated `TypeInfo` is constant-initialized, so descriptors are valid at any point during static initialization; registration happens in a `Registrar` during dynamic initialization and the registry is safe to query from `main()` onward.
- `from_json(to_json(x)) == x` for every schema type, modulo transient fields.
- Two types never share a qualified name (verified at registration).

**Build integration.** `engine_schema_library(NAME m SCHEMAS a.schema b.schema)` runs schemac once over the set (imports also resolve against `schemas/`) and declares module `m` from the generated sources; include as `<schemas/<stem>.h>`, and `<schemas/<stem>_ecs.h>` where an ECS is in scope. Generated modules link whole-archive (`engine_module(... WHOLE_ARCHIVE)`) because their only job at link time is static registration, which a normal static library would drop for any object file nothing references. Outputs go to `build/<preset>/<dir>/generated/<m>/{include,src,json,docs}`. schemac writes files only when content changes, so unchanged schemas do not trigger rebuilds. schemac itself is a standalone tool (standard library only) under `tools/schemac`, built before any module, and it is a **host tool** ([ADR-0034](../adr/0034-host-tools-build-for-the-build-machine.md)): the build runs it on the build machine and it never ships, so `engine_host_tool(engine_schemac)` compiles it for the compiler's default rather than for `ENGINE_CPU_BASELINE`. Compiled for x86-64-v3 it died with SIGILL, printing nothing, six minutes into a v3 build on the Sandy Bridge GPU server — it links no engine module and so has no `require_cpu_baseline()` of its own. `build.cpu_baseline` fails a build in which it carries an arch flag.

**Public API.** `core/schema/type_info.h`, `core/schema/ops.h`, `core/schema/json_reflect.h`, `core/schema/materialize.h` (`MaterializeFlag`, `MaterializeParent`, `MaterializeField`, `MaterializeInfo`, `MaterializeRegistry`, `MaterializeRegistrar`, `read_mapped`, `write_mapped`, `is_byte_comparable`, `stable_type_id`).

**Depends on.** `base`, `hash`, `memory`, `containers`, `ids`, `json`.

**Testing.** `tools/dev.ps1 test -Filter schema`. A feature-complete schema (`core/schema/tests/features.schema`) is generated into a test-only module; tests pin the generated defaults, descriptors, a canonical JSON rendering, error paths, enum handling, and migrations. `tools/dev.ps1 test -Filter schemac` drives the compiler as a child process: a valid schema produces every output including the ECS header, syntax and resolution errors name the file and line and write nothing, a struct-level `@transient` without `@kind(component)` is refused, and a schema with no components still produces a registration function that registers none. What the ECS header then does is tested in `domain/ecs` against components declared in `domain/ecs/tests/ecs_demo.schema`. For `materialize`: a declaration compiles to a table with the conversions, the write-back flag, the parent, the tiers and the registrar in the generated source and a section in the generated Markdown; **a mapping to an undeclared component is refused**, and so is one to a struct that is not a component, a bare component that does not resolve, a record type that is missing or not a record, a component field or record property that does not exist, types that do not join, two dimensions, a unit on one side only, a write-back on a string, a field mapped twice, an unknown parent rule, a second declaration for one record type, an unknown unit and a unit on a string. `-Filter schema` reads the table schemac emitted for `core/schema/tests/materialize_test.schema` — the record type, the components in order, the rows grouped by component, cm→m, deg→rad, g→kg into an f64, °C→K with its offset, a direct string copy, a bare component, `ChildOf` and `@tiers(0, 1, 2)` — converts values both ways through `read_mapped`/`write_mapped`, checks that a value that does not fit leaves the field alone, and pins `stable_type_id`.

**Performance notes.** Reflection-driven JSON is the tooling and document path. Hot-path binary serialization, when needed, will be generated directly from the same descriptors rather than walked at runtime.

## Materialization: type mapping as data

Which components a document record type becomes in the runtime world, and which record property fills which component field, is declared in the IDL beside the types it joins ([03 §3.4](../plan/03-data-model.md#34-the-runtime-world); the language is in [schemas/README.md](../../schemas/README.md#materialize-what-a-record-becomes)):

```
materialize Mover @tiers(0, 1, 2) {
  Transform.position = position @writeback   // a field row; @writeback lets the world write it back
  Velocity.angular = spin                    // deg/s on the record, rad/s on the component: converted
  Marker                                     // a component with its schema defaults
  parent = ChildOf                           // the document's parent becomes the entity's ChildOf
}
```

schemac compiles each declaration into a constant-initialized `schema::MaterializeInfo` (`core/schema/materialize.h`) in the generated `.cpp` of the file that declares it — the record type, the components in the order first named, one `MaterializeField` per field row grouped by component (component, field, property, scale, offset, flags), the parent rule, the tiers and the documentation — and a `MaterializeRegistrar` adds it to `MaterializeRegistry::global()` at start-up, keyed by the record type's qualified name. **The runtime reads the table and runs no per-type code**: the driver (`domain/sim/materialize.h`) finds a record's row by its type and the entity store's hook (`domain/ecs/materialize.h`) writes the fields ([sim](sim.md#the-driver-a-document-through-the-hooks), [ecs](ecs.md#materialization-the-entity-stores-hook)). A record type with no declaration has no row and stays document-only, by design; the driver counts it and says so.

**Why in core and not in the entity store.** The protocol (`session.materialize` lists every mapping), the driver and a document's own tools have to see which types materialize, and none of them links an ECS; a row names `TypeInfo`s and fields by string, and nothing in it is flecs'.

**What schemac checks**, each an error naming the file and line: the record type resolves and is `@kind(record)`; every component resolves and is `@kind(component)` — **a mapping to an undeclared component is refused**, as is one to a struct that is not a component; the component field and the record property exist, and the property is not `@transient` (no record ever carries it); the two types join (the same type, or two float widths); units (below); a `@writeback` row is on a field that is its own bytes — a number, an enum, an id, a vector, a quaternion or a fixed array of them, because write-back decides "changed" by comparing bytes — on a component and a field that are not transient, and no property has two write-back rows; no component field is mapped twice; the parent is `ChildOf` or `none`, at most once; `@tiers` are 0..7; and a record type has one declaration in the whole schema set (a second across two libraries is caught by the registry at start-up, as two types under one name are).

**Units.** A field may declare `@unit(<symbol>)` from a small closed table in `tools/schemac/src/resolve.cpp` — length (`m`, `cm`, `mm`, `km`), angle (`rad`, `deg`), time (`s`, `ms`, `us`, `min`, `h`), mass (`kg`, `g`, `t`), velocity (`"m/s"`, `"cm/s"`, `"km/h"`), angular velocity (`"rad/s"`, `"deg/s"`, `rpm`), temperature (`K`, `degC`), ratio (`ratio`, `percent`); a symbol with a `/` is quoted. A row whose two sides declare different units of one dimension converts: schemac computes the affine map `component = record × scale + offset` from the table (temperature is why there is an offset) and emits it as exact doubles, and `read_mapped`/`write_mapped` apply it and its inverse in f64 and store the field's own width. Different dimensions are refused, a conversion into anything but a float or float vector is refused (it would round), and **a unit on one side only is refused**: it cannot say whether the other side means the same unit or forgot to say. Units change nothing else: the C++ types are the same, and the generated Markdown lists each field's unit.

**`stable_type_id(name)`** is the 32-bit FNV-1a of a qualified name: what a store event or projection names its type by (`store::EventRecord::type`), the same on every build and machine without a registry of numbers. The write-back event `engine.world.WriteBack` is the first user ([store](store.md#write-back-events)).
