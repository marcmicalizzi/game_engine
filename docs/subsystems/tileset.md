# tileset (domain, capability)

**Purpose.** An authored terrain ([world](world.md#an-authored-world), roadmap W23, W24): a heightfield somebody made — a DEM, an editor's sculpt, Island City's mountain ([13 §13.2](../plan/13-reference-consumer-games.md)), a flat test range — turned into a **tile set** the renderer and the collision read through the tile source they already ask ([scene_gen](scene_gen.md#the-tile-source), [ADR-0050](../adr/0050-the-ground-is-drawn-from-the-worlds-tiles.md)), with the **far mip chain** the renderer's far levels ask for ([renderer](renderer.md#ground-to-the-horizon), [ADR-0051](../adr/0051-the-far-ground-is-the-renderers.md)), and the **`tiles` ground provider** that opens a set from a scene's terrain entry, registered through the scene-generator registry as the dunes are ([ADR-0046](../adr/0046-scene-generators-register-themselves.md)).

**Why a capability of its own.** Until it, every ground the engine drew was a generator's: a function of seed, tile and time. The renderer's tests already drew a world from a set built ahead and read back (`terrain_tiles_gpu_tests.cpp`, "a tile set built ahead"), so the drawing half of an authored world worked; what nothing did was read an authored heightfield, write the set, answer a filter from a chain, or let a scene name one. That is data and arithmetic with no GPU and no generator behind it, so it lives in `domain/`, below every reader, and is removable ([ADR-0027](../adr/0027-additive-capabilities.md)): `ENGINE_WITH_TILESET=OFF` and the minimal build take it out, and a scene naming the provider `tiles` is then refused with the registry's sentence (`unknown_ground`).

## The source: `engine.terrain.heightfield/1`

A JSON header (`engine.tileset.HeightfieldHeader`, `schemas/tileset.schema`) beside a raw grid:

```json
{"format": "engine.terrain.heightfield", "version": 1, "width": 4001, "height": 4001,
 "spacing_mm": 1000, "origin_mm": [-2000000, -2000000], "vertical_mm_per_unit": 1000,
 "data": "mountain.f32", "data_hash": "0123456789abcdef"}
```

The grid is little-endian float32, row-major, z then x (`width` points a row, `height` rows), each value `vertical_mm_per_unit` millimetres (1000: metres). `origin_mm` is point (0, 0) in millimetres from the world's origin and must be a whole number of spacings, so the grid **is** a window of the world's lattice at its spacing (`ring_lattice`), which is what lets a set answer a window by index without resampling. `data_hash` is `hash_bytes` over the grid's bytes (16 hex digits); a grid that does not hash to it is refused, so the header's own bytes — the build's key starts from them — cover the grid.

**Why raw, not EXR or a 16-bit PNG.** The engine's image decoder reads 8 bits a channel ([image](image.md)), and EXR sources are roadmap G9's ([texture](texture.md#not-yet)); a raw grid with a hash is readable today, the same bytes on every machine, and what a DEM converter or an editor writes without a codec. EXR and 16-bit PNG heightfields arrive with G9, as another reader of the same header's fields. **Why not SHA-256** in the header: the tree's one SHA-256 is the tissue capability's, which nothing here may depend on; `hash_bytes` is the hash every derived node starts from (`content_build`).

`synth_heightfield` (and `engine-content terrain-synth`) writes five analytic shapes for tests and for a person without a DEM — `ridge` (a 40 m ridge along a diagonal on ground rising 6 m), `basin` (a bowl 20 m deep inside a rim), `steps` (eight 2 m terraces: cliffs a filter must smear), `flat`, `mountain` (a 180 m mountain whose slopes cross the mask priors' soil, scree and bedrock bands on a 1 km grid, on a plain with two pond bowls at nearly one height: `content/test-scenes/ground-by-place`) — with an optional seed adding a quarter-metre of roughness. Polynomials and integer hashes only, never libm, so a seed is the same grid on every toolchain.

## The set

`build_tileset` / `ensure_tileset` write, into one directory:

- **`manifest.json`** (`engine.tileset.TileSetManifest`), written last, so a set whose manifest is there is whole: the build key, the source's hash, the finest lattice (spacing, origin, size), the vertical scale and offset, the far parameters it was built for (`ring_spacing_mm`, `far_ratio`, `far_levels`), the chain's spacings, and per level its spacing and filter, the lattice indices and tiles it stores, a hash over its tile records, and its archive's name and size (`archive`, `archive_bytes`); and the set's hash over the levels'.
- **An archive a level** (`<spacing_mm>.tiles` the finest's, `far-<spacing_mm>.tiles` a far level's, below): every tile's **record** — a 32-byte header (`ETIL`, the record's version, the cells, the level's spacing, the tile) and `(cells + 3)²` little-endian i32 millimetres, rows of x in order of z, the tile's own `cells + 1` points a side and **a point of apron** round them, the layout the renderer's test set has (`BuiltTileSet`), so a consumer reading one tile alone has its neighbours' edge — and a table of contents that finds each.

### The archive

**A level is one file, not a directory of them** (2026-10-24, roadmap W76; `src/archive.h`, internal to the capability). `k_tileset_version` 2. Its layout, little-endian:

| bytes | what |
|---|---|
| 0–63 | the header: `ETAR`, the archive's version (1), the records' kind (`ETIL`; `EMSK` for the mask level), the count at byte 12, the level's spacing at 16, the table's offset at 24, the records' hash (each record's `hash_bytes`, combined in order from `k_hash_seed`) at 32, every record's size at 40 |
| 64 … | the records, back to back, in the table's order |
| table offset … end | one 24-byte entry a tile — `tx`, `tz` (i32), the record's offset (u64), its size (u32), four reserved bytes — **sorted by `tile_key`**: z, then x, both signed, which is the order the build writes in and the renderer asks the masks in, so a row of tiles lies contiguous |

The reader opens a level's archive once, at `TileSet::open`, reads its header and table (176 KB for the forest's 7,345 finest tiles), checks them (the kind, spacing and record size the manifest says, at most the tiles it lists, records inside the file, keys strictly ascending), and holds the file open; a tile is then found by a binary search of the table and read at its offset, with no open and no directory lookup. A tile the table lacks is refused when it is asked, as a missing tile file was (the request false, `failures()` up, the point NaN), not the whole level at open.

**Every record is the bytes its tile file held**, header and all: the record's own version stays 1 and moves only when a record's layout does, so **every level's hash is unchanged** by the archive (the manifest's `hash` is over the records, as it was over the files) and the set's moves only through its key, which names `k_tileset_version`. The archive is written whole and atomically (`io::write_file_atomic`) after the level's tiles, before the manifest. **One caution on Windows**: a reader holding a level's archive open keeps a rebuild from replacing that file (a rename over an open file is refused even with `FILE_SHARE_DELETE`), so `--force` into the directory of a set a viewer has open fails until the viewer lets it go. Builds into the cache never meet this — another build is another key, another directory.

**Why one file, when the reasoning for files was right about which bytes are read.** A camera still reads few of a 64 km world's tiles; what the directory got wrong was *how*: a file open per tile costs milliseconds on a cold cache (the directory lookup, the file's own metadata, an on-access scan), where a positional read of an open file costs its transfer, and nothing issued more than one at a time. The forest's load read 7,428 small files serially for 46 of its 72 cold seconds ([the startup trace](../experiments/startup-trace-forest-2026-10-24.md)): measured, 11.2 ms a freshly written 18 KB tile file cold (an open, a read, a close, and an on-access scan of a file Defender has not seen) against 0.2 ms a positional read of the open archive, and 0.14 s for the whole 132 MB level as one batch against 82 s for its files ([tile archives](../experiments/tile-archives-2026-10-24.md)). The set's identity is still one thing — the manifest's key and hash — so an incremental build never decides from a timestamp.

**Where it goes.** `ensure_tileset` builds into a directory it is given, or into the derived-data cache at `<ddc>/tilesets/<key>/` (`tileset_cache_dir`), and skips the build when the manifest there records this build's key (a hit). The key is `tileset_key`: the source header's bytes' hash, every option, and `k_tileset_version`, bumped whenever a build's output for the same source and options changes.

**Two levels at one spacing** (2026-11-11, roadmap T90; `k_tileset_version` 3). A heightfield whose spacing is one of the chain's — 8 or 16 m under the renderer's default chain, which a landform's ground is — has two levels at that spacing: the finest (filter 0) and a far level (filter = spacing, the finest's own points, since a level no coarser than the source is its bilinear surface). Until version 3 both were named `<spacing_mm>.tiles`, so the far level, written second, replaced the finest's file, and the set built and then refused to open ("its records are not the … its manifest lists"); and the reader's cache keyed a tile by its spacing alone, so one level's tile could answer for the other's, the two differing only in the apron where an edit reaches the data's edge. A level is now named by what it is (`level_archive(spacing_mm, filter_mm)`: the finest `<spacing_mm>.tiles`, a far level `far-<spacing_mm>.tiles`), and the cache keys a tile by its level. The records' bytes did not move, so every level's hash is what it was; the version moves the key, so a set built before (the colliding ones among them, whose manifest recorded the key) is rebuilt rather than opened. `tileset_tests.cpp` holds a 16 m ridge under the default chain: seven levels, seven archives, every point of every level against the source or the box filter, and one read a tile.

### Integer millimetres, from the build on

Following the terrain's rule ([terrain](terrain.md#integer-in-every-decision)), the float32 source becomes **whole millimetres once, when the set is built** (`quantize_heights`): the unit times `vertical_mm_per_unit` times the vertical scale, plus the offset, in f64, rounded half up (`floor(x + 0.5)`), refused when it is not finite or does not fit an i32 (±2,147 km). Everything after is integers: the tiles hold i32 millimetres, the box filter sums them in i64 and rounds once, and the reader turns a millimetre into a float32 metre by one correctly rounded division (`f32(mm / 1000.0)`). A point between lattice points is the bilinear surface in f64 over the integer corners (`TileSet::point_mm`), whose weights are exact at a lattice point, so a lattice point asked as a point is the lattice's own height to the bit. Why there and not at read: the build is where a toolchain could disagree only once, and from then on two readers on two machines turn the same integers into the same floats.

### The far mip chain and its filter

The renderer's far levels ask the source for a lattice **filtered to** each far spacing (`TileSourceOps::heights`' `filter_mm`): the first far level's spacing is `far_ratio` times the outermost ring's, and each one after doubles it ([renderer](renderer.md#ground-to-the-horizon), `terrain_far_level`). The build takes those parameters as options (`BuildOptions::ring_spacing_mm`, `far_ratio`, `far_levels`; the renderer's defaults are 2 m rings — 32 m tiles at 16 cells — a ratio of 4 and six levels: 8, 16, 32, 64, 128 and 256 m), records them, and writes a level for every spacing. **The outermost ring is the world's, not the set's**: a world of four rings at the default cells ends at 4 m and asks 16 to 512 m, so its set is built with `ring_spacing_mm` 4000; one built for 2 m is refused by the renderer before it builds anything, by a sentence naming the far level and the spacing to build for (2026-10-24, W77, [renderer](renderer.md#ground-to-the-horizon)).

**A level's point is the surface box-filtered over its own cell**: the mean of the finest's bilinear surface over the square one level spacing wide centred on the point. On the finest's points that mean is exactly the trapezoid rule — weights 1, 2, …, 2, 1 along each side of the `r + 1` points the square spans, `r` the level's spacing over the finest's — so the build sums the integers with those weights, separably (each row's sum, then the rows'), in i64, and rounds once, half up. It is exact: `tileset_tests.cpp` holds every level against the same sum done in one loop, and a tilted plane's chain against the plane itself. A level's spacing must be a whole number of twice the finest's, so the square's edges land on the finest's points; one no coarser than the finest is its bilinear surface's points (it carries everything the source has); any other is refused at the build with a sentence naming the spacing. Each level is a quarter of the one before it, so the chain is about a third more than the finest — of the data's extent, not the far windows' (below).

**Past the data the edge is held**: a point outside the heightfield is the nearest edge point's height, flat beyond it, at every level. Each level stores the points whose cell touches the data and one more a side whose cell lies wholly past it; past those a point's cell sees only the edge held, which is that outermost point's value, so the reader clamps the index to what is stored and answers the filtered field of the held surface exactly. This is the choice over refusing outside the extent: a far level's window is kilometres to tens of kilometres, so a renderer's far square reaches past any authored map, and refusing would leave it unable to draw at all, where holding the edge draws a plain to the horizon.

## The reader

`TileSet::open(manifest)` checks the format, version and levels and reads no tile. Its cache is bounded by a tile payload budget (`TileSet(cache_bytes)`, 64 MiB by default; `tileset.cache_mib` for the registered provider), with a sparse index bounded by the same number of tiles, independent of the source's extent. Tiles enter on first use and the oldest entry is replaced when the cache fills; return travel may reread them. A request **pins** the tiles it reads and evaluates from them with no lock held, so another job cannot evict its data and nobody waits for its arithmetic ([The reader's lock](#the-readers-lock)); its last tile is looked up before the rest, so adjacent points take no hash lookup. No pointer escapes the request. `cache_stats()` reports budget, held payload bytes, tile count and evictions; `reads()` counts successful reads, including rereads. A budget smaller than one tile is refused at open. `TileSet::source()` is the set as a `scene_gen::TileSource`:

- at `filter_mm` 0, **the ground at each point of any spacing**: the finest's own points where the spacing is a multiple of its own (every r-th, as the renderer's test set answers), and its bilinear surface at a spacing finer than or between them — so a renderer's 50 cm finest ring over a 1 m heightfield draws the surface between its points rather than being refused;
- at a filter, **the chain level of that spacing**, point for point; a filter it was not built with, or one that is not its spacing, is **refused** (false), not answered with the wrong lattice;
- no time: every time is the one surface, and `travel_m` is null, so a time-lapse never re-evaluates it.

A missing or invalid tile refuses the lattice request and increments `failures()`; callers discard the output. The scalar point API returns NaN on missing data. Neither substitutes zero-height ground. Finite-source edges retain their documented edge holding; missing data inside the set is a different case.

The cache index admits at most 2²⁶ entries even if a larger payload budget could hold more; this
bounds metadata for oversized budgets and does not restrict the source's extent. Admission also
temporarily holds the incoming payload and its file-read buffer, each one tile in size. The index and the entries grow as tiles come in, reserved up to 1,024 at open rather than to the whole capacity, since a budget of small tiles is millions of entries whose metadata would outweigh the payload it bounds.

`point_mm`/`height_mm(x_mm, z_mm)` are the bilinear surface at whole millimetres, the edge held: what placement and a camera key stand on.

### The reader's lock

**What it costs, and who waits** (2026-10-24, roadmap W70). `reader_stats()` counts, over every thread, the lock taken, the nanoseconds callers waited for it and held it (and the most of each once), tiles found resident and read from disk with their bytes and read time, and waits for another caller's read of the same tile; `TileSet::thread_reader_stats()` is the calling thread's share over every set, so a host's frame thread can tell its own waits from the terrain workers' (engine-view's records carry both, [apps](apps.md#walking)). `tile_set_of(source)` finds the set behind a `TileSet::source()`, for a host that holds only the renderer's source. Counters only: nothing a request answers reads them.

**What they found.** Until 2026-10-24 one lock was held over a whole window's evaluation, tile reads from disk included (since 4b31ac77, W67, which replaced the lock-free resident tiles of the first reader with the bounded cache): a walker's tick then queued behind every terrain worker of a rebuild, and after a flight to the forest POC's summit the frame thread waited 636 ms for it in one frame while holding it 0.4 ms, the workers 26 s among themselves ([the measurement](../experiments/walk-stalls-2026-10-24.md)).

**The reader never holds its lock across work.** The lock guards the cache's index and its entries' pin counts, and nothing else:

- **A request pins what it reads.** Under the lock, for the lookup alone, a resident tile's pin count goes up and its payload pointer is taken; the heights are then read with no lock, and the request's pins (at most eight at once; more are let go and taken again) are let go together when it returns. An entry is evicted only at a pin count of zero, so a pinned payload cannot move or go, and the oldest unpinned entry is the one replaced — the FIFO it was.
- **A miss is read outside the lock, once.** The caller claims a slot under the lock — an entry in the index marked `loading`, pinned by it — reads and checks the file with the lock released, and publishes it under the lock again (or, on a failed read, frees the slot so the next asker tries afresh). A second caller asking for a tile being read waits on a condition for that read alone, never reads it twice, and never waits for the lock across another tile's IO.
- **The budget holds unless every entry is pinned.** A claim with no unpinned entry first lets go the claimant's own pins (every height it read through them is already read); only with every entry pinned by other requests — more requests at once than the budget has tiles — does the cache grow past its budget by those pins, and the next evictions bring it back.
- **The cache's numbers take no lock**: `cache_stats` reads atomics.

So a point asked beside a long window costs its own lookup: `tileset: a point is not held behind another thread's long window` holds a 1,400 × 1,400 window on one thread (0.8 s in a debug build) against points asked on another, the slowest 0.75 ms — 748 ms, the whole window, with the old lock — and `tileset: concurrent callers missing the same tiles read each once` has eight callers ask one window of twenty tiles at once and the set read twenty. After the fix the POC's flight-and-walk frame thread waited 3 µs at most for the lock.

### Reading a level

**A request for many tiles reads its misses as one batch** (2026-10-24, W76). Three shapes reach the reader, and each is served as what it is:

- **A window** (`heights`, every tile source request): before a point is evaluated, the tiles its points read are found per axis (each point's lattice index clamped as `value` clamps it, and both corners for the bilinear surface between the finest's points), and every one neither resident nor being read is **claimed under one lock** — the same claim a point's miss makes, `loading` and pinned by the claimant — up to half the cache's tiles. The claimed tiles are read with **one queue of range reads** of the level's archive (`archive::Reader::fetch` over `io::read_queued`): records adjacent in the file are coalesced into runs of up to `ReadOptions::run_bytes` (256 KiB), up to `ReadOptions::depth` runs in flight at once (32), from the calling thread. Each run is published under the lock **as it lands**, and anyone waiting for one of its tiles is woken then, so a point asked beside a window waits for that tile's run, never for the window. A tile that did not arrive whole frees its slot, and its asker reads it alone and counts the failure, as before. The window's evaluation then pins resident tiles exactly as it did.
- **A point that misses** issues its one read: one record at its offset, straight into the entry's storage (a buffered read needs no staging).
- **The whole level, in order** (`prefetch_level`; a rectangle, `prefetch`): every tile of the level not resident, in file order, as one batch — so in runs of `run_bytes`, a level in a few hundred large reads — as many as the cache has room for without evicting what the batch itself read. This is the shape of standing a region's placements on the ground at load, which touches most of the finest level.

**What the load uses after this change.** The scene load (`systems/renderer/src/scene.cpp`, `scene expand`) still stands its 12,330 instances one `height_mm` at a time, so it takes the **point** path: one positional read a missed tile, from the archive held open, at queue depth one. Every miss is now a read of an open file rather than an open, a read and a close of a small file; the window and whole-level shapes are what the load gets when it moves the standing to tile activation or asks `prefetch_level` first (the load agent's, W69's list). The terrain's first fields and every tile rebuild after it are windows, so they are batches now.

`ReaderStats` counts the batches, the tiles they read, the runs they read them in and the deepest a batch's queue was (`batches`, `batch_tiles`, `runs`, `most_in_flight`). The provider's options are tunables: `tileset.read_depth` (32), `tileset.read_run_kib` (256; 0 reads every record alone) and `tileset.unbuffered` (off: the archives read past the OS's file cache, through sector-aligned runs and a staging ring — what a cold measurement does without the rights to drop the cache). `engine-content terrain-read` reads a level in each shape and says what it cost ([apps](apps.md#engine-content-terrain-synth-and-terrain-tiles-an-authored-terrain)); the measurement is [tile archives](../experiments/tile-archives-2026-10-24.md).

## The provider: `tiles`

Registered from `src/ground.cpp` through the registry (`k_ground_provider`, flags `k_ground_millimetres` only). A scene's terrain names it with `"provider": "tiles"` and a `tiles` block (`engine.scene.TerrainTileSet`, `Terrain` version 7): `manifest`, a built set's manifest; or `heightfield`, a source the provider builds into the derived-data cache on a miss through `ensure_tileset` — **the content step as a library call**, as a scene mesh's clusters are built on a miss — with the block's `origin` (x, z added to the source's origin in whole spacings; y added to every height), `vertical_scale`, `ddc` (empty: the repository's, found from the heightfield's directory) and build options. Paths resolve against the scene's directory (`Context::dir`). **The host's derived-data root wins over the block's** (2026-11-11, roadmap T90): `--ddc` and `render.load`'s `ddc` reach the provider twice over — the scene reader writes `SceneDesc::ddc` into the block's `ddc` when it reads the file, which is how every `TerrainSampler` a host makes from the description gets it, and the provider reads `Context::ddc` before the block, as `resolve_tile_set` always took a root it was handed first ([scene_gen](scene_gen.md#the-derived-data-root)). Until then the root stopped at the reader, so a scene outside a checkout had to name `tiles.ddc` or was refused with "no derived-data root to build … into". `tiles_view_tests.cpp` reads such a scene with a root and no device and finds the set built under it.
- **Every point entry is the set's surface**: `height`, `height_mm` (at any time), `surface_mm`, and `floor` and `floor_mm` (an authored ground does not move, so what a building stands on is its surface).
- **`grid`** is the set's window on the world's lattice — a chain level at a filter it holds — and the bilinear surface on the scene's grid. **A grid cannot refuse** (`GroundOps::grid` returns nothing), so a filter the chain lacks is answered there with the points' heights; the set's own source refuses it, and the provider returns that native source to the renderer and collision through `GroundOps::tile_source` (below, "What the seam lacks").
- **No time function**: no `evaluate`, `travel_m`, `wind` or `transport`. A set that does not move is a level whose fields never change, so the time-lapse keys do nothing to it and its surface time is constant. With no wind the renderer lays no ripples across it (`wind` absent); its sand share is the renderer's own maps' (no map says otherwise: maps are W25, below). No rings (`make_rings`, which builds cluster DAGs, is the terrain capability's) and no world tiles of its own (`open_tiles`): the world's tile ring draws it through the tile source.
- **Refused**, each with a sentence: a terrain with no `tiles` block, one naming neither a manifest nor a heightfield, one with ridges or basins (an authored terrain carries its own), a set that will not open, a heightfield that will not build (an origin between its points, a far spacing its points cannot filter onto).

### What the seam lacks

**A scene file naming `tiles` draws in the stock hosts** (2026-10-18). Three seams stood between a scene file and this provider, each outside this module, and all three are closed:

- **The renderer carries the `tiles` block** (`3b92cd06`): `read_scene_file` copies `Terrain.tiles` into `renderer::TerrainDesc::tiles` with its paths resolved against the scene's directory and refuses a tile set beside another provider; `terrain_entry` copies it back into the entry the provider is made from, and `doc_scene` carries a Heightfield record's.
- **engine-view, engine-host and engine-editor link this capability** where the configuration has it, for its registrar alone, as they link the dunes' ([apps](apps.md#engine-content-terrain-synth-and-terrain-tiles-an-authored-terrain)); before, only engine-content did, and a scene naming `tiles` was refused by the viewer with the registry's sentence ("… which this build does not have … (it has dunes, waves)"). `apps/engine_view/tests/tiles_view_tests.cpp` builds a set with `engine-content terrain-synth` and `terrain-tiles` into its scratch directory and draws a scene naming it offscreen.
- **The terrain's render mesh is keyed by the set's content**: `terrain_hash` reads the manifest's build key, set hash and lattice (or a heightfield header's grid hash and lattice and the block's transform and options), never the paths, so a heightfield rewritten behind the same path builds a new scene grid instead of drawing the cached one under the new heights ([renderer](renderer.md#scenes-camera-paths-and-flythroughs), "Content addressing"). A game that derived the terrain's `seed` from its heightfield's hash to force the rebuild no longer needs to.

The remaining integration is closed by W67:

1. **Static authored terrain uses the stock terrain levels** (2026-10-23, W67, [ADR-0057](../adr/0057-ground-providers-expose-their-native-tile-source.md)). `resolve_settings` accepts a still millimetre-capable provider when terrain tiles are requested (`--terrain-tiles`, protocol `settings.terrain_tiles`, or a scene's `world.ground`). `GroundOps::tile_source` returns the set's native source through the registry; no host or renderer needs the typed accessor. Unsupported filters and missing tiles remain refusals. `MovingGround` owns the sampler until all its workers finish; its static source keeps rate zero even when a time control requests motion. Tile layouts, fields and drawing still use the existing rings mechanism. The hidden scene grid is a 17-point material/UV carrier, independent of source resolution. The editor viewport uses the same setup and follows its camera for a Heightfield record.

## The record

**How a terrain is defined in the scene graph and stored** (roadmap W66): a document holds an authored ground as one `engine.terrain.Heightfield` record (`schemas/heightfield.schema`, `@kind(record)`) — `name`, `source` (the heightfield header's path, relative to the document's directory), `origin` (`worldpos`: x and z moved by whole spacings, y added to every height) and `vertical_scale`. The grid itself is not in the document: it is the file the record names, as [07 §7.6](../plan/07-content-pipeline.md#76-procedural-generation-volume-content)'s table has it ("blob-referenced from the document"), and the set built from it is derived data, rebuildable and never committed. No yaw: a heightfield is a window of the world's lattice, axis-aligned on its grid, so a turn would be a resample, not a placement.

`systems/doc_scene` maps one live record to the scene's terrain with the provider `tiles` and a `tiles` block naming the heightfield ([doc_scene](doc_scene.md#the-mapping)), and makes the provider through the registry when it reads the document, so **the set is built into the derived-data cache on the first read** and a hit after. A change of `source`, `origin` or `vertical_scale` is a rebuild, a change of `name` nothing; the brief this was built from listed only the first two, and the scale is here too because it changes every height drawn. Two live records are refused naming both (one ground per document, today). `doc_scene` names no capability: in a build without this one the record is refused with the registry's sentence. **What the editor does with it**: its viewport reads the document scene, so the editor draws an authored ground: the renderer carries the `tiles` block into the provider it makes, and the editor links this capability's registrar as engine-view does ("What the seam lacks", 2026-10-18). A document holding the record is refused with the registry's sentence only by an editor built without the capability.

### The editor's brush, next

Sculpting in the editor is W66's second half, not built. What it needs: (1) **the grid in memory** — the editor loads the heightfield (`read_heightfield`) beside the record and edits its floats, never the set; (2) **a brush as a command** — a stroke is a document command whose payload is the rectangle of grid points it changed, before and after (a blob the journal keeps, since the grid is not a property bag), so undo and redo go through the document and its journal like every other edit; (3) **write-back** — saving writes the grid and a new `data_hash` (`write_heightfield`), which changes the header's bytes and so the set's key: the next read builds the set again, which for a stroke should be **an incremental build** (the finest tiles the rectangle touches and the chain tiles whose cells reach it; today a build is whole, 7 s at 4 km × 1 m in debug); (4) **live drawing while the brush moves** — a tile source over the edited grid in memory that the viewport's tiles ask, so a stroke is seen before it is saved, the time-lapse's machinery redrawing the tiles it changed. None of that changes the format: a stroke is an edit of the source the set is built from.

## The mask level

**Ground materials by place** (roadmap W72, [renderer](renderer.md#ground-materials-by-place); the grounding is [ground materials](../experiments/ground-materials-grounding.md)): a terrain's `masks` block (`engine.scene.TerrainMasks`, `Terrain` version 9) is built into a **mask level** beside the set — per tile, the palette layers it uses and their weights — which the renderer reads through `scene_gen::GroundOps::masks` (`domain/scene_gen/ground_masks.h`) without naming this capability, as it reads heights through `tile_source` (ADR-0057). `src/masks.cpp`, `include/domain/tileset/masks.h`.

**The inputs, composited in order, each over the last** (`mask_inputs`, `build_mask_level`): the **generated priors** — soil, scree, bedrock and snow by slope, elevation and aspect, from the set's own bilinear surface (`TileSet::point_mm`, a central difference one mask spacing either side) — with a region's `base` standing in for the soil inside it; the **painted weight maps** (`paint`: an image's R is a layer's weight over the map frame, bilinear, the edge clamped); the **index map** (`index`: R names a layer outright, nearest); and the **regions** (`regions`: a polygon or circle, or a scene water body's outline by name, resolved by the host with `scene_gen::resolve_mask_water` so the build and its key see a shape, never a name), each giving a `material` outright, or a water body's `bed` inside and `margin` within `margin_m` outside, with `feather_m` softening the edge inward and `wet_m` wetting the ground out from it. "Over" is the alpha rule — every weight below scaled by one less the share laid — so a stack of inputs never exceeds one, and what an input leaves uncovered is the ground palette the terrain drew before. Every decision is f64 arithmetic, a square root, or a series sine and cosine (the prior's angles become slope gradients without libm), so the level is the same bytes on every toolchain.

**A tile's record** (in the level's archive `<spacing_mm>.masks` under `<ddc>/tilemasks/<key>/`, `manifest.json` written last; [the archive](#the-archive), records `EMSK`, `k_mask_version` 3 since T74, 2 since W76): a 32-byte header (`EMSK`, the record's version 1) and the words the GPU reads as they are — the table (four palette indices, `0xFF` for none), an RGBA8 word of four weights a point for every mip (mip 0's `cells + 1` points a side, down to two), and a byte of wetness a point. A tile with nothing authored is not written and the manifest's `present` list does not name it; the renderer draws it as the ground palette. Each record is the bytes the tile's own `.mask` file held before the archive.

**Read in windows.** `MaskLevel` opens the archive once and copies a tile out of a **read-ahead window**: records from the one asked onwards in file order, up to 2 MiB, read as runs of 256 KiB eight at a time. The renderer counts manifest presence through `GroundMaskOps::present` without reading payloads, checks the resident budget, then reads each present tile once to copy it (W76, 2026-10-26); the fixture's 289 tiles fit one window and the forest's 7,346 take a few dozen. The before/after is in [the archive measurement](../experiments/tile-archives-2026-10-24.md#one-mask-payload-pass-at-load).

**Why points, not texels, and why there is no separate apron ring.** The level is a window of the world's lattice at `spacing_mm`, like the heights: point *i* is at *i* times the spacing from the origin, and a tile holds its own points edge to edge, so **its last row is its neighbour's first**, stored in both. A pixel's cell lies in one tile and its four corners are that tile's points, so the shader reads one table; on a seam both tiles hold the same edge points, so the weights are continuous across it and identical at it from either side. The brief that asked for this named a one-texel apron for that property; the shared edge row is the apron, and a ring beyond it would be bytes no reader uses. **It holds only if no edge point loses a layer**, so **a tile whose points name more layers than `materials.layer_budget` is refused** with a sentence naming the tile, its place in metres and the layers that meet there, never trimmed to its largest four: a trimmed layer would show on one side of a seam and not the other.

**Mips that keep the seam exact.** Mip *m* of a tile holds `cells / 2^m + 1` points; each is mip 0's points filtered over its cell (weights 1, 2, …, 2, 1 along each axis, the height chain's box), **except along an axis where the point lies on the tile's edge**, where it is mip 0's edge point alone — so a mip's edge points are computed from points both tiles hold, by the same integer arithmetic, a layer at a time (rounded half up), and the seam stays exact at every mip. Interior mip points never reach past the edge (a cell's half-width is at most its distance from it), so no filter is clamped.

**The refusal names every tile, and a check names them before the cook** (roadmap T72). The build scans the whole level and refuses once, with a sentence that lists each tile over budget (its place, its layers with their mean weight over the tile, the weakest) up to 32 and then "and N more", so a composer fixes a scene in one pass rather than one tile a cook; `tileset::check_mask_budget` runs the same composition without writing the archive and `engine-content masks check <scene.json>` ([apps](apps.md)) prints a JSON line a tile over and a summary (exit 0 none, 1 some). The weakest layer is the smallest mean weight, what a blend-out would drop; no blend-out exists yet, and the budget stays 4 layers a tile.

**The check composes what the load composes** (roadmap T74, 2026-11-08). The forest proof of concept's v36 was refused at its load for 13 tiles naming a fifth layer while `masks check` on the same scene found none: the check opened the heightfield's set *without the scene's `tiles.cuts`*, so it read the uncut ground, whose slopes are not the cut banks' (the banks are where the slope priors add scree and bedrock). Both now call `tileset::resolve_tile_set` (`masks.h`; defined in `ground.cpp` beside the provider), the one function that finds the set a terrain names or builds it from its heightfield with the block's options **and cuts**, so the two cannot differ again. The terrain's `holes` are not in the set (they are the renderer's, cut at draw) and the masks never read them, so there is nothing of them to compose. **A layer under one quantization step does not count.** A texel stores a layer's weight as a u8, `round(w * 255)`; the step is `k_mask_step` = 1/255. A layer takes a channel in a tile, and counts against `layer_budget`, only when its peak weight over the tile's points is at least one step; a lighter layer is dropped from that tile (its weight, under one step, is lost, which the eye cannot see — it is under half a percent of a texel) and, when its peak is over half a step, which the old rounding stored as 1/255, named: `check_mask_budget` lists it in `MaskBudgetReport::dropped` (`masks check` prints a `{"dropped":true,...}` line each), and the build returns it in `MaskBuildResult::dropped`, which the `tiles` provider logs as `mask layer dropped: under one quantization step` (tile, layer, peak) when it builds the level (a cache hit builds nothing and so warns nothing — the warning belongs to the build that decided). A layer weighing less than half a step was never stored and is not named. **The budget does not widen:** a tile whose layers are all at a step or more and number more than `layer_budget` is refused exactly as before, with the same sentence. `k_mask_version` is 3 for it: a tile that stored a layer at 1/255 by rounding up now stores none, so an older cached level is rebuilt rather than reused. Tests: `tests/mask_tests.cpp` (a fifth layer at a peak weight of 0.0026 loads with one dropped line, at 0.0047 it is refused, check and build agreeing; a cut whose banks add bedrock is reported by the check and refused by the provider's masks, and accepted by both without the cut).

A refusal suggests increasing `materials.layer_budget` only when it is below four,
and only up to four. At four, it names the format limit and asks for less overlap.
An explicit region's `material` can keep steep excavated soil from becoming the
slope prior's bedrock; `base` cannot, because it changes only the soil channel.
The override and its feather still share the same four-layer per-tile budget.

**The texel density: 1 m by default** (`spacing_mm`, 250 to 4000). A trail or a shore margin is one to a few metres wide and is the narrowest thing the masks must place; a metre resolves it with the bilinear blend, and the layers' own textures carry the centimetre detail at their `tile_m`. Half a metre quadruples the level's bytes for edges the priors' slope transitions (several metres wide) do not need; two metres blurs a trail to a smear. Unreal's landscape weightmaps are of the same order (a component's weightmap at its vertex density, typically a metre).

**Cost**: a tile of 32 cells is 1,873 words (7.5 KB) holding 1,024 m² at 1 m, 7.3 bytes a square metre with its mips; the fixture's 256 m square at 16-cell tiles is 289 tiles and 600 KB. A 4 km square at 1 m is about 117 MB, a 10 km square 730 MB — at 2 m, 183 MB. **The renderer holds every tile of the level resident** (below the block's `resident_mib`, refused above it): streaming them with the terrain's tiles is W25's remainder.

**Keyed as the heights are** (`mask_key`): the set's hash, the inputs as canonical JSON with every image path cleared and every image's bytes hashed instead, the palette's names, the budget, the map frame and `k_mask_version`; `resident_mib` is the renderer's and changes no byte, so it is left out. `ensure_mask_level` is a hit when the manifest records the key. The `tiles` provider builds the level on a miss when the terrain names `masks`, into the same derived-data root as its set; `engine-content terrain-masks` is the step on its own ([content build](content_build.md#terrain-masks-ground-materials-by-place)). `write_mask_priors` writes the priors alone as one greyscale PNG per role over the map frame, which an author edits and gives back as a `paint` entry.

Tests (`tests/mask_tests.cpp`): every edge point of every seam of the fixture (544 seams, 19,584 points at every mip) holds the same weight per layer and the same wetness in both tiles, and the CPU reading just before a seam equals the reading on it; the priors put snow, scree, bedrock and soil where the paraboloid's slopes and heights say, the two ponds at one height get sand and mud, the margin gravel, the trail its material, the painted corner its litter; five layers meeting in one tile are refused with the sentence; the level reads back as its field within half a code at 700 points, is a hit the second time, and a changed image is another key; **the level hashes to a pinned value** (`558a6a74fd7c454a` since W76's archive moved the key; it was `8127dd57bf0cee9c`, over the same records) and **its archive to another** (`75eef7ec443e0e7e`), taken on MSVC and reproduced in the Linux containers; the archive holds every present tile in the manifest's order, each record hashing into the level's hash, and a level asked in the renderer's order twice is read in one window.
## Channels cut into the ground

**A channel lies below its floodplain** (2026-11-07, roadmap W89; the POC's v35 engine-needs, item 1: W86's bed slab and berms read as "a raised canal between levees"). A `tiles` block built from a heightfield may carry `cuts` (`engine.scene.TerrainCut`, `TerrainTileSet` version 2; since W98 the `edits` of mode `Cut`, [below](#ground-edits-that-raise-as-well-as-lower)): polylines downstream, each point with the top of the bank (its y: the floodplain's height at the line), the bankfull width and the bed's depth below that top, and one bank slope. `engine-content channels --cut` writes one per link of a channel network ([channels](channels.md#the-cut)); a scene may author one by hand. `TerrainCuts` (`include/domain/tileset/cuts.h`, `src/cuts.cpp`) compiles them, and **the build writes them into the heights** (`BuildOptions::cuts`):

- **The section** is a trapezoid: a flat bed `depth` under the top, banks rising from it at the bank slope `m` to the top at half the width either side of the line, and above the top the bank's face going on up at the same slope for at most `depth` more, where it meets higher ground (a channel cut into a trough's side); past that reach, nothing. A bed narrower than the banks allow (`m w < 2 depth`) is a V, its banks steepened to `2 depth / w`. Along the line each segment's top, width and depth are its two points' interpolated by the projection's parameter, and the surface is the lowest of every segment of every cut, so a joint, a junction and an overlap are each the union of their sections, whichever order they come in. The heights become `min(ground, round(surface))`: the ground is lowered where it stands above the section and nowhere else, so the floodplain past the top of the bank, and ground already lower than the section, are untouched. The source of the profile and its numbers is [channels' grounding](../experiments/channels.md#the-cut).
- **The cell rule.** A level is cut only where its spacing is **finer than the width** there; a level whose spacing is not keeps its heights, so the cut closes on a level that cannot draw it, as a hole does ([terrain](terrain.md#holes)). Each level is cut **after** its own heights are made, so a chain level is the box filter of the ground as it was: the far levels (16 m and coarser for the forest) hold no channel and keep every byte. The finest level holds every cut wider than its spacing.
- **What reads it.** Everything that reads the set: every ring and world tile the renderer draws (they are the finest's points), and so the pool's terrain stage, every rasterizer, the ray path and the cascades with no change of their own; the collision's heightfields and its ground query ([scene_collision](scene_collision.md)); and every point a placement stands on (`point_mm`). **Why at the source** and not in the rest mesh or the pool's stage: all of those must agree on one ground, and only the heights are read by every one of them, which is the same reason W87 put holes in the lattice rather than in a shader. **A ring coarser than a channel** reads the finest's points, so it point-samples the cut as it point-samples the trough the erosion carved; the cell rule closes the cut on the set's own levels only.
- **Keys.** The set's key adds the cuts' hash only when there are some (`tileset_key`), so a set without cuts keys, builds and hashes exactly as before. With cuts, **a tile's record is the bytes it was without them unless a cut lowered one of its points**: the level's hash moves, the records of the tiles no cut reaches do not. `terrain_hash` adds the block's cuts too (renderer, the scene grid's cache key). `BuildResult::cut_points` counts the lowerings.
- **Refused**, with a sentence naming the cut: fewer than two points, arrays whose length is not the points', a width or depth not positive and finite, a bank slope outside [0.25, 8]; and `cuts` beside a `manifest` (a set built ahead is not built here).
- **Integer in every decision.** Millimetres in f64; products, sums, one division and one square root (both correctly rounded), never libm; rounded half up once. A cut is the same millimetres on every toolchain.

**A cut is a ground edit along a line** (2026-11-10, roadmap W93; `TerrainCut` version 2; the header of `cuts.h` has the formulas). The trapezoid above is one case of a **profile across the line** (`CutProfile`, `cut_profile`): the lower envelope of a bed and a bank each side, `delta(s) = min(depth, m_l (w / 2 + offset - s), m_r (w / 2 - offset + s))` at the signed distance `s` from the line, left positive (the side of (-dz, dx) for a segment running (dx, dz)), each face going on `rise` past its top. What a cut may now say, each absent by default, **and a cut that says none of it is the millimetres and the hash it was** (the symmetric case is computed by W89's operations, in their order):

- **A slope per bank and per point** (`bank_slope_left`, `bank_slope_right`, 0.02 to 16): a cut bank on a bend's outside, a point bar's slope on its inside, so the bed's deepest point lies toward the outer bank. Banks too gentle to reach the bed inside the width are steepened together until they meet at it. [Channels](channels.md#the-section) writes them from the line's bends.
- **A rounded top** (`bank_round`, 0.1 to 1, 0.75 where a cut names none; **every cut rounds**: W93's continuation refuses 0, the crease W89 left, which no cut can ask for any more): the cut's surface and the ground are joined by the polynomial smooth minimum over the band where they stand within `bank_round` times the depth of each other, `min(g, s) - (max(k - |g - s|, 0) / k)^2 k / 4`, so a bank's top is a curve and not a crease, lowered by a quarter of the band at the most. It needs the ground, so **each segment is rounded against the ground as it was and the lowest kept** (`TerrainCuts::lowered_mm`), which is the same in any order and continuous wherever the surfaces are; a rounding that read the lowest *surface* first would step where two cuts of different depths tie, by a quarter of the difference of their bands (found by the continuity test below, and why the function has this shape). The band is at most the depth, so a face's reach, which ends a depth over its top, ends where the rounding has: no step at the reach's edge over ground at the top or under it.
- **A flood bed** (`flood_left_m`, `flood_right_m`, `flood_depth_m`, `scarp_m`, `scarp_slope`): a second profile on the same line, a flat bed `flood_depth_m` under the top reaching its two distances from the line, bounded each side by a scarp whose top stands `scarp_m` over the bed. A segment's surface is its channel's and its flood bed's joined by the same rounded minimum. **The cell rule reads each by its own width**: a level too coarse for a stream may still hold its flood bed (a 4 m level holds a 7 m bed and not the 2 m channel in it).
- **A face that runs out.** W89's face ended a depth over its top, and where the ground beside the channel stood higher than that the cut ended in a wall, which the lattice draws as a row of teeth along the lip (the proof of concept's item 7; reproduced on W93's scratch scene in a valley with sides of 17 to 19 degrees). Every cut's faces, and a flood bed's scarps, go on past that end over one more run of their own, the height over the top `rise / (1 - v)` at the share `v` of that run: the same height and slope where it begins, steepening without bound, so the face meets the ground wherever the ground is, the cut's reach is two runs past the top and no further, and nothing ends in a wall. `TerrainCut` is version 3 for this: a cut written by hand with no `bank_round` was W89's trapezoid with a crease and is now rounded over 0.75 of its depth, so a set built from one is another set (its key carries the rounding) and the heights beside its banks move by up to a quarter of that band; the collision's cut test, which stands on such a cut, reads 1.496 m and 1.85 m where it read 1.5 m and 2 m.
- **Beyond a line's end** the profile is read at the radial distance from the end point with its two sides blended by the direction, so an end is a round cap whichever its banks are and the outside of a joint is the union of two caps, an offset curve with no tooth.

**The build walks the window in blocks** of 64 points a side: the segments of each block are found by a counting sort, the lowest reading over them is kept per point, and the heights are written once per block, after its segments have all read them. So a point's height is a function of the cuts and its own height before them: **the same from any window that holds it** (the tile-stability test), where W89 lowered in place a segment at a time, which was order-free only because a plain minimum is. `BuildResult::cut_points` now counts each lowered point once (W89 counted a point once per segment that lowered it; nothing read the number but the tests' "more than none").

**A second client** (a trail's tread, a terrace, a pad): W98 built what it lacked, the fill rule and a block of its own, by replacing the cut with the edit below; the `cuts` named on this section are `edits` of mode `Cut` since then.

**What it costs.** The build walks each segment's reach over each level it applies to (one comparison a segment for a level it does not), so a cut costs its own area, not the set's. The reader is unchanged. **Measured** (W93, 2026-11-10, `msvc-release`, `engine-content terrain-masks` over an empty tile-set cache, best of two, the machine at 34 % CPU with other agents building, so upper bounds): W93's scratch scene, 1,537 by 1,025 points at 25 cm in 384 tiles of 64 cells with 475 m of channel in 7 cuts — the set uncut 0.78 s; with W89's cuts 0.75 s on the base (76d96ced) and 0.77 s on this row; with W93's cuts (shaped sections, rounded, 266 m of flood bed) 0.79 s. The cut's whole cost is inside the run-to-run spread, under 0.03 s for the set, under 0.1 ms a tile. In `msvc-debug` the case "a cut lowers the finest level" fell from 0.77 s to 0.22 s with the block walk (three builds of a 161-point set).

Tests (`tests/cut_tests.cpp`): the section against its formula (bed, banks, the face past the top, the reach, the V); on a flat 40 m square at 25 cm every finest point equals the rounded minimum of the ground and the section (`cut_round` over 0.75 of the depth, to the millimetre) by a distance computed in the test, every point past the reach and every tile no cut reaches holds what it held without the cut, the bed under the line is the depth below the top; the chain's 1 and 2 m levels are cut and its 4 and 8 m levels hash as the plain set's; a 20 cm cut on 25 cm points lowers nothing on any level; no cuts keys as before, two crossing cuts in either order give the same levels, a second build the same hash; the refusals; the provider stands on the cut ground and refuses cuts beside a manifest. **W93's**: the profile against its formula, left and right, the V, an offset, and W89's section as the symmetric profile bit for bit; a segment whose width, depth and both slopes change along it, with a rounded top, across a ground with a slope and a swell, every point of a 161-point lattice within a millimetre of a reading written apart in the test (the projection, the side, the caps' blend, the rounded minimum), the rounding lowering points the plain minimum does not; **continuity**: a trunk of five points turning 25 degrees at each with a bar on alternating sides and a tributary joining it, what the cuts leave of a flat ground walked on a 20 mm lattice (3.9 million neighbour pairs), no step past **121 mm** (the steepest slope over the step, plus one: a face is 4 at the most here, and the blend of the two sides round a line's end reaches 5; a step would be a share of a depth, 300 mm and more), and the same surface and the same lowered ground in either order of the two cuts; **tile stability**: two crossing rounded cuts over the swell, the whole lattice at once, the same in the other order, and two windows of it that start off its blocks (one a single tile with its apron) the same millimetres wherever they overlap, **and the lattice after the two cuts hashes to a pinned value** (`13997414741782788461`, with the ground's own beside it, `3593206589486382013`, since the test's swell is the C library's sine), taken on MSVC and reproduced by Clang and GCC at v3 and GCC at v2 in the containers; a flood bed against its numbers (the channel's bed, the bed either side, the scarps, the reach, the cell rule at 4 and 8 m, and a built set); the refusals of W93's fields, and a cut that names none hashing as it did. **On a GPU** (`systems/doc_scene/tests/channel_cut_gpu_tests.cpp`, offscreen, the device the GPU lock gives): a 3 m channel 0.6 m deep cut into a flat ground 2 m up, built through the provider on load and drawn by the world's tiles over four rings and a far level, beside the same ground uncut. A pixel whose ray meets the bed in one frame and the floodplain in the other sees them at view depths in the ratio of their heights under the eye, whatever its direction, so the depth channel gives the height the cut frame met: the image's centre at 1.4 m, the bed, and 3,584 pixels on it, none nearer than the uncut ground. The cascades change no id; the ray path's bed is the same 1.4 m and 3,584 pixels, and its ids are reported beside the hardware's, not held, as the holes' test reports them (11 words differ with the cut, 27 on the same ground uncut; RTX 5090, 2026-11-08).

## Ground edits that raise as well as lower

**An edit brings the ground down to a surface, up to it, or both** (2026-11-10, roadmap W98; four of the day's rows asked for it and none could take it: a scree deposit lay on the ground as a mesh the heights and the collision knew nothing of, a wall's footing and a ledge's tread wanted ground put where there was none, and a cut across a slope left a bench with no downhill bank, the solver-needs report's 2.1 item 2). `engine.scene.TerrainEdit` **replaced** `TerrainCut` (the `tiles` block's `edits`, `TerrainTileSet` version 3; a scene naming `cuts` is refused naming the field, and `engine-content channels --cut` writes `edits`), and `TerrainEdits` (`cuts.h`, `cuts.cpp`) compiles it. The formulas are the header of `cuts.h`; the grounding of the numbers is [ground edits](../experiments/ground-edits.md).

- **A mode** (`TerrainEditMode`): `Cut` lowers only, `Fill` raises only, `Bench` both — cut where the ground stands above the surface and filled where it lies below, so the surface *is* the ground across the edit: a tread benched into a cross-slope, cut on the uphill side and filled on the downhill, a pad, a causeway level across a hollow.
- **A line** (`points`, two or more): a `Cut` is the channel above, to the bit. A `Fill` or a `Bench` is flat across `width_m` at the point's y (no depth: one named is refused), its **cut faces** rising at the bank slope for `face_m` (2 m where it names none) and its **fill faces** falling at `fill_slope` (0.5, one on two, the usual embankment batter; per side and per point as the banks, `fill_slope_left`/`_right`) for `fill_m` (2 m), each face then running out as a cut's does, so it meets the ground wherever the ground is and the reach is two runs past the top. Along the line, the caps, the joints and the cell rule are the cut's.
- **A patch** (`outline`, a simple polygon of three or more points): a surface over the polygon — flat at its points' y, which must agree, or the bilinear surface of a small grid of whole-millimetre heights (`grid_origin`, `grid_spacing_mm`, `grid_nx` by `grid_nz`, 2 to 1024 a side, `grid_mm`), held at the grid's edge past it — with the same faces leaving its edge at the distance from the polygon, so its edge is feathered into the ground. A deposit's surface is a `Fill` patch with a grid; a pad on a slope a `Bench` patch, flat.
- **How edits compose, whatever their order and whichever tile applies them**: every fill against the ground as it was, the highest kept; then every cut against that, the lowest kept — `R = max(g, max fill_round(g, D_i))`, `L = min(R, min cut_round(R, U_j))`. A plain maximum and minimum are each order-free and every term reads `g` or `R`, never another edit's work, so the result is a function of the edits and the point's own height: the same from any window. **A cut wins where the two disagree**: a channel through a causeway is a gap in it, a stream across a tread a ford. With no fill `R` is the ground, and every cut is W93's to the millimetre; every W93 pin holds.
- **Why a cut lowered only, and what W98 keeps of it.** `min(ground, round(surface))` was what made the union order-free and tile-free, and a chain level is the box filter of the ground as it was, edited after, so a level that cannot draw an edit keeps its bytes. Both stand: the fills are a plain maximum taken first, the cuts a plain minimum after, and each level is edited after its own heights by the same **cell rule** — a level holds an edit only where its spacing is finer than the edit's width (a line's at the point; **a patch's, four times its area over its perimeter**: a square's side, a disc's diameter). The far levels and the collision read the same edit, the collision with no change of its own: it reads the set's heights.
- **Rounding stops at a top.** A fill's crest stands at an unknown height over the ground (a berm 0.8 m high has a 2 m `fill_m`), so a band of `bank_round` times the face's height over its crest would lift it by up to a quarter of the band; and a bench's two envelopes meet at its tread, where a smooth minimum and maximum would leave a dip where the old ground crosses the tread's height. So a fill's rounding, and a bench's and a patch's cut, is the least of the band and the face's own height there: **0 on a crest, a tread and a patch's surface, which are exact to the millimetre**, and the full band where a face meets the ground. A `Cut` line keeps W93's band over its whole section.
- **Refused**, with a sentence naming the edit: neither or both shapes; too few points; arrays whose length is not the points'; a width not positive; a `Cut` line's depth not positive, or a `Fill`'s or `Bench`'s named; a bank slope outside [0.25, 8], a fill slope outside [0.1, 8], a per-point slope outside [0.02, 16], a rounding outside [0.1, 1], a face height outside [0, 100] m, a fill height outside (0, 100] m; a flood bed on a line that is not a `Cut`; a patch with no area, points at different heights and no grid, a grid whose numbers do not make one, or a line's arrays named on it.
- **Keys.** The set's key adds the edits' hash only when there are some, and that hash is **every edit's canonical bytes** (`schema::to_json` written by `write_json`), so every field enters by construction; the renderer's `terrain_hash` reads the same bytes. Until W98 both named a cut's fields one by one, and the renderer's named only the points, widths, depths and bank slope, so a cut that changed only its side slopes, rounding or flood bed reused a cached render mesh (W93 found it; `scene_gen_scene_tests.cpp`, "every field of a ground edit enters the terrain hash", fails on the base). `BuildResult::edited_points` counts the points an edit changed, each once.
- **Integer in every decision**, as the cut: millimetres in f64, products, sums, the projection's division, the run-out's and the grid's divisions and one square root a segment or a polygon edge, each correctly rounded, never libm; rounded half up once.

**What reads it.** Everything that reads the set, as for a cut: the renderer's rings and world tiles, the ray path, the cascades, the collision's heightfields and ground query, every point a placement stands on. **What does not, yet**: no generator writes an edit (a deposit, a wall's footing, a ledge's tread and a route's tread are their rows'), and an edit reaches a scene the way channels' cuts do, written into the `tiles` block by a subcommand; a generator handing one over at a tile's activation is R142's contract (the roadmap's W98 row says what it should carry).

**What it costs.** As a cut: the build walks each edit's reach over each level it applies to (one comparison an edit for a level it does not), in two passes over a block's edits when any edit fills, so an edit costs its own area and a set with no fill pays nothing for the rule. Measured (W98, 2026-11-10, `msvc-release`, the case "what edits cost a tile", best of two, **the CPU at 100 % with other agents building**, so upper bounds): 32 edits — 16 benched treads 246 m long and 16 gridded 6 m deposits — over a 1,025-point lattice at 25 cm (256 tiles of 64 cells, 400,000 points changed) in 259 ms, **1.0 ms a tile**; the same 16 lines as cuts alone 43 ms (0.17 ms a tile); no edit 1 µs. A fill costs more than a cut by its reach (a batter at one on two reaches twice as far as a backslope at one) and by the second pass; a bench pays both. In `msvc-debug` the case takes 1.9 s.

Tests (`tests/cut_tests.cpp`, W98's): a fill's line against its formula (the crest, a face at its slope, the run-out at twice its drop half way, nothing past its end, no upper envelope), what it leaves of a ground below, above and on its crest (exact), and the rounding where a face meets the ground; `fill_round` and `face_height` against theirs; **a bench across a one-in-four cross-slope is flat to the millimetre over its whole tread** (1,243 points, the old ground crossing the tread's height through it), cut and never raised uphill, filled and never cut downhill, and the slope its own past both faces; a flat pad and a gridded deposit against their surfaces inside, their faces outside, the grid held past its edge, a bench pad flat over five grounds from 1.5 m under to 1.5 m over it, and the patch's width read by the cell rule (a 6 m pad on a 4 m level and not an 8 m one); **a causeway benched across a hollow, a channel cut through it, a gridded deposit and a bench pad, in either order, the same millimetres**, the causeway's crest at the rim's height where the hollow was 0.84 m deep, the channel's bed under it, three windows off the blocks (one a tile with its apron) the same millimetres wherever they overlap, no step between neighbours past the steepest face over the step (376 mm at 25 cm; 250 measured), **and the lattice pinned** (`16557965784987386551`, the hollow `17149333333107072769`) with its ground beside it (the hollow is integer arithmetic and one division, so the ground pin is a function of the build's arithmetic alone); a berm and a pad built into a set, their 1, 2 and 4 m levels moved as the cell rule says and the 8 m level the plain set's to the byte; and every refusal. Re-taken from W93's: the hash of a cut that changed only a field the heights do not read is now another key (it was the same, which is what let the renderer's defect pass). `systems/scene_collision/tests/channel_cut_tests.cpp`: the collision's ground on a causeway's crest, down its face and rounded into the ground, the set's to the bit, and a character set down over the crest standing on it.

## What an authored world still lacks after this

Items 1, 2 and 4 of [world](world.md#an-authored-world)'s list are this module; 3, 5 and 6 are not:

- **Maps** (W25): the material weights are now a level beside the heights ("The mask level", W72); what remains is streaming them with the terrain's tiles rather than holding the whole level resident, and a colour or sand-share map per tile.
- **Holes and overhangs**: a placement generator reading its own authored set of placements per tile.
- **The world's persistent layers**: the overlay's mechanism taken unchanged; an authored set has no lag.
- **Erosion, hydrology and biomes** (G36) would write this format: a generator's heightfield is an authored one to the set.

## The pixel test

**An authored set draws its heightfield, pixel for pixel** (`systems/doc_scene/tests/authored_ground_gpu_tests.cpp`, where the renderer, this capability and the terrain capability meet; offscreen, on the device the GPU lock gives). It is the renderer's own "a tile set built ahead and read back" case with an authored heightfield in place of the dunes' procedural answer: a seeded ridge 481 points a side at 50 cm (240 m, scaled to a tenth) is built by `ensure_tileset` into a derived-data cache with the chain the renderer's test layout asks (8 m tiles, rings at 50 cm, 1 m and 2 m, far levels at 4, 8 and 16 m), read back through `TileSet::source()`, and drawn beside a reference source computed in memory from the same quantized millimetres — the finest's points, each far level's trapezoid sum in one loop, the edge held — that shares nothing with the set's tiles, reader or separable sums. Three views (down at the rings, grazing across the ridge, high over the far levels and past the data's edge 120 m out) compare 125,337 pixels, colour and depth, and **0 differ**; every level's rest-height hash agrees; 175 of the set's 268 tiles are read. The original comparison retains its dune-scene material fixture; under tiles its grid carries only the material and UV frame, so every height drawn is the source's. W67 adds a stock authored-provider case through `MovingGround`, with travel, rate changes, finite edges, a teleport and identical return captures.

## Invariants

Each is a test in `tests/tileset_tests.cpp` unless it says otherwise.

- A heightfield round-trips through its header and grid, bit for bit; a grid that does not hash to its header, an unknown field and an origin off its lattice are refused with a sentence.
- Every stored point of every level reads back as the build computed it — the finest the quantized source, a chain level the box filter summed directly in one loop — and so do three points past each level's stored window a side, where the edge is held; every level is one archive of the size its tiles make, and every tile is read.
- **The archive** (W76): its table lists every tile of the level in order of z then x, each record names its own tile, and the records hashed in the table's order are the manifest's level hash — the bytes the tile files held; a record whose header is overwritten and a table entry removed are each refused at read as a missing tile file was (false, `failures()`, NaN), and the repaired archive answers a reader opened after it.
- **Batches** (W76): eight callers asking one window at once read its twenty tiles once, in one batch of five runs (a row each), the rest waiting for it; a whole level is read in one batch and one run when it fits a run, and a window over it afterwards reads nothing; a cache of ten tiles prefetching a level of 49 reads ten and evicts nothing it read, and a rectangle over it reads only what is not resident; a record a read at depth one, small runs at depth eight, runs of a megabyte at depth 128 and the archive read unbuffered all answer every level bit for bit as the default reader does, each tile once. A point asked beside a long window is still answered in its own time (0.1 ms against a 0.7 s window, debug).
- The box filter of a tilted plane is the plane at each point; a cliff is smeared over the cell.
- A filter the set was not built with, and a filter that is not its spacing, are refused; a spacing finer than the set's is its bilinear surface, a multiple its every r-th point; a point is the corner at a corner, the four's mean at a cell's centre, and the edge's past the data.
- A second build is a hit with the same key and hash; a forced build writes the same hash; another option or another grid is another key; a far spacing the source's points cannot filter onto is refused.
- The provider through the registry: its point entries are the set's surface at any time; its native tile source is the set's chain and refuses any filter it lacks; its refusals are sentences. A terrain naming a heightfield builds the set the content step builds, keyed the same, with its origin, scale and lift; an origin between the source's points is refused.
- A walker stands on it (`systems/scene_collision/tests/tileset_ground_tests.cpp`, where the collision is): the collision handed the set's source holds its heights to the bit on its lattice, and a character walks across a bowl and a tile's edge with its feet on the set's surface.
- The record (`systems/doc_scene/tests/heightfield_record_tests.cpp`, where the mapping is): read into the scene's terrain with its set built into the document's cache on the first read and a hit after; its name a change of nothing, its source, origin and scale each a rebuild, its deletion and creation a rebuild; two refused naming both; a missing source and an origin between its points refused with a sentence.
- **The same bytes everywhere** (`tests/determinism_tests.cpp`): a seeded synthetic ridge's set, built with an offset, a scale and a lift, hashes level by level, archive by archive and as a whole to the pinned values, taken on MSVC and reproduced by GCC and Clang at v3. The levels' hashes are the ones pinned on 2026-10-17 (the records did not change); the set's moved with W76's key (`d3d1ae3493a1a152` to `9d8c5f04c967e143`), and the archives' are new pins (`60560ee72a1596b4`, `49b1a32cfb0a8baa`, `279816856e9d9afe`).

## Testing

`tools/dev.ps1 test -Filter tileset`: the module's own tests above, with no device. `apps/engine_content/tests/tileset_tests.cpp` runs the two commands end to end: each synthetic shape written by `terrain-synth` is the library's grid to the bit, and refused with a bad kind, size, missing spacing or an origin off the lattice; `terrain-tiles` builds a set into a directory and into a cache at `tilesets/<key>/`, the same key either way, a hit the second time and not with `--force` or another offset, and the library opens what it wrote; its usage errors exit 2 and a source or a build the source cannot have exits 1; `terrain-read` reads a built set's finest level whole, as windows and point by point, every tile once in each, and refuses a bad pattern or depth (exit 2) and a set that does not open (exit 1) ([apps](apps.md#engine-content-terrain-synth-and-terrain-tiles-an-authored-terrain)). **The capability contract**: `ENGINE_WITH_TILESET=OFF` and `msvc-minimal`/`linux-clang-minimal` build without it.

## Performance notes

A 4 km × 4 km heightfield at 1 m is 16 million points; its build quantizes them, writes the finest's tiles and filters each chain level from the finest separably (a level costs about one pass over the finest), then writes the far levels' few tiles. The reader reads a tile on first ask and again after eviction when its budget is exceeded; cache payload and indices remain bounded. Measured (2026-10-17, `msvc-debug`, the shared desktop with its CPU 35% busy beside the run, so an upper bound): a 4 km × 4 km ridge at 1 m, 4001 points a side and 64 MB of float32, builds with the renderer's default chain in 7.2 s into seven levels, 4,197 tiles and 75.5 MB — the finest's 3,969 tiles of 67² points are 71 MB of it, the six far levels' 228 tiles the rest. A hit reads one manifest. Since the archive the forest's set (7,427 tiles, 133.8 MB) builds in 1.5 s in `msvc-release`, seven files instead of 7,428.

**Reading** (2026-10-24, W76, [tile archives](../experiments/tile-archives-2026-10-24.md); `msvc-release`, the shared desktop, every number an upper bound): the forest's finest level, 7,345 tiles and 132 MB, read cold as files one at a time took 82 s; as its archive point by point, 1.5 s; whole as one batch at depth 32 in 256 KiB runs, 0.14 s (965 MB/s), where the reader's own work a tile (about 17 µs) is the cost and more depth buys nothing. The forest's cold launch to nearby-stable went from 72.8–79.5 s to 13.9 s, `scene expand` from 40.4 s to 1.2 s and `ground start` from 14–16 s to 0.26 s; the mask level's 7,345 tiles from 99 s as files to 0.06 s.
