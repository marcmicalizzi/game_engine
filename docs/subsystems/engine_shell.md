# engine_shell: the browser shell over the protocol (apps)

**Purpose.** The authoring editor's shell (roadmap A36's spike, then A37, [06 §6.13](../plan/06-agent-tooling.md#613-human-developer-tooling)): a page that **speaks nothing but the engine protocol over a socket**. It began as the candidate beside engine-editor's Dear ImGui panels ([ADR-0054](../adr/0054-the-tools-ui-is-dear-imgui-drawn-by-the-renderer.md), proposed), which worked but did not have the feel the owner wanted (Qt he knows and finds utilitarian); the owner judged its panels clearly better, and since 2026-10-11 it *is* the editor's panels, in a web view beside the native viewport ([below](#embedded-in-the-editor)), while still opening in a browser against engine-host. This is the third option made concrete enough to judge by using it: static HTML, one stylesheet and a handful of ES modules in `apps/engine_shell/`, served by `engine-host --listen` itself ([apps](apps.md#engine-host---listen-the-protocol-over-a-loopback-websocket)) and opened in a browser tab. The same files can later run in an OS webview inside our own window, or in an embedded Chromium if the game UI ever wants one; in every form, no panel has a private path into the engine.

**The rule: it holds no engine knowledge beyond the protocol.** Every string it shows about the world came out of a method — the outliner from `doc.objects`, the fields, their kinds, their documentation and defaults from `schema.describe`, the journal from `doc.journal`, the identity from `engine.roles`, the completions from `engine.methods`, the picture from `render.capture`. It never reads a document file, never names a record type (the only types it knows are the protocol's own field kinds, `f32` or `worldpos`), and every change it makes is a request a script could make. A feature it needs that the protocol lacks is a protocol change, made in the host where every client gets it — which is how `render.load {session}`, `render.capture`'s `keep`, `records` and A32's `camera` came to exist ([apps](apps.md#engine-host---listen-the-protocol-over-a-loopback-websocket)).

**Open it.** One host command; the browser is the user's:

```
build/msvc-debug/bin/engine-host --listen 127.0.0.1:0 --doc <dir> [--create] --actor <name>
```

The first line it prints is `{"listen":"ws://127.0.0.1:<port>/","session":"s1","shell":"http://127.0.0.1:<port>/?ticket=...&session=s1","token":"..."}`; open the `shell` URL. Its one-time ticket buys the page a cookie and the host sends it on to an address with no ticket; the cookie is what the listener checks on the socket and on capture fetches, so the page never holds a credential and its address keeps none ([protocol](protocol.md#who-a-connection-is), ADR-0069). A page the host refuses (its address spent in another browser, or older than ten minutes) says so and does not retry: a running engine-host cannot print a new address yet, so restart it; a second tab in the same browser, and a reload, need nothing new. The host ends when its standard input closes (Ctrl+C in its terminal).

## What it is

- **Viewport.** `render.load {session}` once, then `render.capture` at the panel's size with `channels: ["color", "ids"]` and `keep: true`, the PNG fetched from `GET /capture/<id>`. It is a **slideshow, and says so on screen**: every gesture ends in one full-size capture, and while a gesture lasts the page asks for half-size captures back to back (never more than one in flight) so motion can be followed. engine-view's fly controls on the keyboard (W A S D, Q E down and up, Shift to hurry), a drag to look, the wheel to dolly, F to have the host frame the scene again, R to capture again. The camera is the host's: every capture reports the one it drew with (A32), the page flies from that report in engine-view's convention and sends the camera back, and the corner shows it with the capture's size, time and id. A click reads the kept id buffer at that pixel (`GET /capture/<id>/ids`, three `u32` a pixel) and selects `records[instance]`. After every transaction the page loads the session again — the host moves or rebuilds in place — and captures again. **The live viewport comes when the native window is a client of this same host** ([06 §6.13](../plan/06-agent-tooling.md#613-human-developer-tooling)), not from this page.
- **Outliner.** Type, name and id tail of every live object, parents before children, collapsible, filtered as you type; the arrow keys walk it.
- **Properties.** Every field of the selected record from its type's `schema.describe`, with an editor by kind: number boxes (integers checked), text, a checkbox, x/y/z(/w) axis boxes for `vec2`, `vec3`, `quat` and `worldpos`, a list for an enum the host describes, JSON for anything else, and an Unset (`ClearProperty`) for an optional field that is set. **A changed field is one `doc.apply` with one `SetProperty`** and the rationale typed in the field under the panel, which defaults to "Set <field> of <name>"; the input flashes when the host committed it and turns red when it did not, with the reason in the status strip. Properties a record holds that its type does not declare are shown too, as JSON.
- **Journal.** The session's transactions newest first, each with its rationale, actor, role, task, command count, layer and time; entries past the undo position faded. Undo and Redo in the title bar (Ctrl+Z, Ctrl+Shift+Z) are `doc.undo` and `doc.redo`, which the host checks against the role like any write.
- **Command line.** One JSON-RPC request typed by hand — `method {params}`, or a whole request object — and the answer, coloured, with its round-trip time. Completion is the engine's own catalogue from `engine.methods`, each with its documentation and a `write` badge on methods that are not read-only; taking one fills in the session. History survives a reload. A `session.open` typed here becomes the page's session; any other write refreshes the panels.
- **Status strip.** The host, the session, the actor and role the host attributes edits to, how the page is known to the host (its cookie), and the last error a method returned.

**When another client edits: events** (2026-10-11, roadmap A2; [protocol](protocol.md#events)). On every connect — the first and each reconnect, since a subscription is the connection's — the page sends `session.subscribe` for its session's `journal`, `selection`, `scene` and `session` events, and from then on the host pushes them as they happen and the page reacts: a **journal** event whose journal length or undo position differs from what the page shows refreshes the outliner, the properties, the journal and the viewport (the page's own edits included — its `doc.apply` no longer refreshes by itself, so a change refreshes once whoever made it); a **selection** event moves the outliner's highlight and the properties (embedded, a click in the native viewport); a **scene** event for the scene the slideshow shows, newer than the revision it last drew, takes the picture again (another client loaded it after a change); a **session** event names a lease taken or released in a toast, and a close as an error; an event that carries `dropped` (the page stopped reading and its queue overflowed) refreshes everything. An agent's edit through an attached engine-mcp reaches the outliner in about 25 ms on loopback in a debug build and 13 ms in release — the event, then the `doc.objects` the outliner sends — plus the page's layout ([apps](apps.md#attached-to-a-running-host---connect) has the measurement); the poll it replaced took up to two seconds. **The fallback** is the old look at `session.info`, every **ten** seconds now, and it runs only while no subscription stands (a host without `session.subscribe`, or none yet). The status strip's **updates** badge says which is in use: "events" with a green dot, or "poll 10 s" with an amber one and, in its tooltip, why the subscription failed.

**It reconnects, and says so.** A dropped socket turns the title bar's pill amber ("reconnecting"), the page retries with a growing pause up to five seconds, and when it is back it loads the session again; a request in flight when the socket dropped fails rather than being sent twice, since the host may have run it.

## Embedded in the editor

The A36 spike's verdict (2026-10-11) was that the panels were right and the slideshow viewport could not be flown, so the shell's main form is now **inside engine-editor's own window** (roadmap A37, [apps](apps.md#engine-editor-the-engines-window-on-a-document)): the editor runs the protocol's listener in process, opens this page from it in the platform's web view ([webview](webview.md)) with `&embedded=1` on the URL, and lays its **native, live Vulkan viewport** in a child window over the page's viewport cell. The two tile and never overlap; nothing is composited and nothing crosses per frame.

- **The viewport panel becomes an empty cell** (`embedded.js`, `EmbeddedViewport`, standing where the slideshow's `Viewport` stands, so nothing else in the page knows which mode it is in): the same panel with the same drag-to-resize splits, its slideshow image, notes, Frame and Capture buttons gone, and a dark backing — which is what shows for the frame a resize takes the native window to follow. The panel's corner names the native picture's size.
- **`editor.layout`, a notification**: the cell's rectangle in CSS pixels from the page's corner (`getBoundingClientRect`) and `devicePixelRatio`, sent on load, whenever the socket (re)opens, on a split drag, on a window resize and when the ratio changes (a `ResizeObserver` on the cell, `resize`, and a `matchMedia` on the current resolution), coalesced to one a frame and not sent again when nothing moved. A notification has no id, so the editor sends nothing back; the page sends it only while the socket is open (`Rpc.notify`) and again when it opens, since what it carries is the page's current state, not an event to queue. The editor moves its child window there ([protocol](protocol.md#the-editors-methods)).
- **The selection goes both ways.** A click in the outliner sends `editor.select {id}` (read-only: UI state, never the document), so the native viewport outlines the record and its gizmo attaches. A click in the native viewport reaches the page as an **`event.selection`** pushed by the editor's listener ([above](#what-it-is)), so the outliner and the properties follow a pick as it happens; the half-second poll of `editor.state` that did this before events is gone. The page's own `editor.select` comes back as an event too and is recognised as the selection it already has.
- **Nothing else changes.** The outliner, the properties and their edits, the journal and its Undo and Redo, the command line and the status strip are the same code over the same protocol; a transaction from the page is a transaction on the editor's own session, and the viewport follows it the next frame. The page has no bridge to the process — no `window.chrome.webview`, no binding — so the same files still run in a plain browser against engine-host, and against the editor too (its listener prints the same `shell` URL).
- **Popups stay in their panels, and a test says so.** The native window covers the cell, so anything the page drew over it would be hidden. The command line's completions and an enum's list are placed by `fitPopup` (`dom.js`): against their anchor, below it or above it where there is more room, with their height capped to the room left in their own panel; an enum's list is the page's own (`enumList`, `properties.js`), not a native `<select>`, whose list is the platform's popup and can be neither kept anywhere nor measured, and it is fixed-positioned so the scrolling properties do not clip it. The toasts sit at the bottom middle of the page, over the command line. The test hook proves the two lists and the "Reconnected" toast stay off the cell ([below](#the-test-hook)); `shell.css` says so beside the embedded rules for whoever adds the next popup.
- **The gizmo's tool and adding a mesh** (2026-10-12, A39). Embedded, the title bar has a two-button toggle, **Move** and **Rotate**, that calls `editor.tool` and shows the editor's answer; the status strip shows the tool too; and the page follows the editor's `editor.tool` notification, which it sends when T or R is pressed in the viewport, and reads `editor.state`'s `tool` on every (re)connection. The outliner's header has **Add…**, which asks the editor for a file (`editor.pick_file`, the platform's own dialog, on the editor's thread) and imports it by the grant the editor answers in place of its path (`editor.import_mesh {grant}`, so a file the person chose may lie outside the editor's roots and the page never handles an absolute path; [protocol](protocol.md#where-each-method-is-carried)): copied under the document's `assets/`, placed in one transaction, selected — the outliner and the journal follow by their events), with a toast naming what was imported or the method's reason in the status strip. A file dropped on the page is not navigated to (the page cancels the drop and says to drop it on the viewport, which imports it). **In a browser tab none of this is shown** (`.embedded-only`): those methods are the editor's, and engine-host answers "method not found". The properties panel reads a quaternion field (`rotation`) in degrees beside its four numbers — yaw, pitch and roll in `quat_from_euler`'s order, derived, never written.
- **`editor.relayout`.** The editor speaks first once: when the display's scale under its window changes it sends this notification, and the page answers with a layout whether or not its rectangle moved. The transport answers requests and drops what has no id, so `EmbeddedViewport` listens on the socket itself for that one method (`listen`), on every (re)connection.
- **The page never scrolls.** The app's one grid column is `minmax(0, 1fr)`, so no panel's content can make the page wider than its window; before that, a page wider than its window scrolled sideways when an input took focus, and the native viewport stayed where the cell had been. The cell also re-sends its layout on a scroll, should anything scroll it.

The editor's default window is 1600 × 900 because the three columns want about 950 CSS pixels (left 280, the viewport at least 320, right 340) — at a display scale of 150 % that is about 1430 window pixels. Narrower, the page takes its narrow layout.

## The narrow layout

Below **960 CSS pixels** of width (`NARROW_BELOW`, `layout.js`) the three columns do not fit, and before A38 the page simply overflowed — in a browser the right column went under the window's edge, and in engine-editor's 1280 × 720 window at 150 % (853 CSS pixels) the properties, the title bar's Undo, Redo and pill, and the right part of the viewport cell were cut off, the native viewport with them. So below the line the page is **two columns**: the outliner over the **properties** on the left, the **journal a drawer** under them (its head only, with a ▸, until a click opens it to a third of the column), and the viewport over the command line on the right; the brand's name gives up its room in the title bar. A `ResizeObserver` on the page decides and sets `.narrow` on the root; the stylesheet does the rest, except moving the properties panel between the columns, which no stylesheet can do. The two layouts' widths do not overlap, so a resize across the line flips once. The viewport cell is one rectangle in both, its rectangle goes to the editor through `editor.layout` as before, and the layout's `narrow` flag tells the editor which it is. The splits keep working: the left one sizes the column (at most 42 % of the page), the row split the properties.

## The test hook

`testhook.js` is loaded only when the page's address carries **both** `embedded=1` and `test=1` — which only `engine-editor --test-page` puts there — so a browser, and the editor without the flag, never load it, and the page exposes nothing else for tests (a `window.__test` holding its report function, nothing that changes the page). It checks from inside the page what only the page can see, by DOM events the page dispatches to itself — the layout of its own popups is the page's; the platform's input is the editor's own test (`--test-keys`) — and reports each check as an `editor.test_report` notification, a method the editor registers only with the flag, into the run's summary: **"completions"** (typing `doc.` into the command line opens the completions, which stay inside the command line's panel and off the cell), **"enum"** (a click on the AssetProvenance record in the outliner, then on its `license_class` button, opens the enum's list, which stays inside the properties panel and off the cell), **"hostile"** (A50: a record and a transaction's actor that the page test's fixture names `<img src=x onerror=alert(1)>` are drawn as those characters, in the outliner and in the journal, and no element of the page carries an `onerror`), **"policy"** (A50: the listener's content security policy is in force in the web view — `trustedTypes.createPolicy` is refused under `trusted-types 'none'`, which the browser reports as a violation of its own that the check sets aside — and the page has met no other violation, an image from the listener included; the reconnect's check then holds the new socket to none either, so `connect-src 'self'` covers the page's own `ws:` socket in WebView2), **"done"**, and on every reconnect **"reconnect"** (the pill said "reconnecting" while the socket was down and "connected" after, and the "Reconnected" toast is off the cell). Because the hook clicks the page, `--test-page` runs only on a document under the tests' scratch root (`<system temp>/engine-tests/`), and **`engine-editor --embedded --test-page --no-viewport`** (A51) runs the page and its hook with no viewport at all: the web view and the listener, no GPU device, no GPU lock, the browser's own GPU off, the cell its dark backing ([apps](apps.md#engine-editor-the-engines-window-on-a-document)).

## Feel: what the page spends effort on

The point of the spike is feel, so the page is designed rather than defaulted: the system's UI face at 13 px with tabular figures, monospace only where the text is data; an 8 px spacing scale with a 4 px half step; one accent on a near-black ground, borders a step lighter than the panels; a visible focus ring on everything focusable; a hover and an active state on every control; splits between the panels that highlight under the pointer, drag smoothly, move with the arrow keys and are remembered; axis labels coloured x red, y green, z blue in the vector editors; a pulse on the connection pill while it waits; and `prefers-reduced-motion` honoured. No component library, no framework, nothing generated: about 2,700 lines with the stylesheet, which a reader can follow.

**No bundler, no package manager, no CDN, nothing fetched at run time** but what the host it came from answers. The page opens offline from the host's listener, and the build only copies the files (`apps/engine_host/CMakeLists.txt`, into `build/<preset>/shell/`); an edited file is served on the next reload because every response says `Cache-Control: no-store`.

**The page runs only its own files, and puts other clients' text on it as text** (A50, 2026-11-18). Every HTTP answer of the listener — the page, its scripts and stylesheet, a 404's body, the ticket's redirect, a capture — carries the content security policy given [below](#what-another-clients-content-cannot-do) as a `Content-Security-Policy` header (`protocol::k_shell_content_policy`, `listener.h`), never as a `<meta>` tag, which a page reads only for itself and only once the parser reaches it. So the page runs no inline script, style or handler, loads images only from its listener (the slideshow's captures) and connects only to it (the socket, the capture fetches), and with Trusted Types and no policy a string handed to an HTML sink throws in the browser. Today's page needed no change for it: it has no inline script or style, `h()` sets a style through the CSSOM (`style.setProperty`, which the policy does not govern), its images are `/capture/` on the same origin, and its one `import()` is a literal. `tools/lint.ps1`'s `shell-html-sink` holds every `.js` and `.html` file here to the same at the commit: no `innerHTML`, `outerHTML`, `insertAdjacentHTML`, `document.write`, `createContextualFragment`, `parseFromString` or `srcdoc`, no `eval` or `Function`, no timer given a string, no `import()` of anything but a literal, and in the HTML no inline script, style, handler or `javascript:` URL; its marker (`// engine-lint: allow-html-sink <reason>`) has no use. In WebView2 it holds: the test hook's "policy" check finds Trusted Types enforced and no violation, and the page's own `ws:` socket, reconnected under the hook's eye, passes `connect-src 'self'` ([below](#the-test-hook)).

## Testing

The shell is tested through its clients, not in a browser. The windows that load it are engine-editor's embedded tests, small and throttled: the page, served by the editor's listener, must send an `editor.layout` that places the native viewport; resized from 1280 × 720 to 800 × 600 its layouts must keep the viewport inside the window, narrow exactly when the page is under 960 CSS pixels; and with the test hook, under `--no-viewport` since A51 (no device, no GPU lock: the lock's own log holds no hold), its popups must stay in their panels, it must answer `editor.relayout`, and after the editor shuts its socket it must show the pill and reconnect (each skipped with the reason where the WebView2 runtime is absent); the methods themselves are tested through the editor's dispatcher with no web view ([apps](apps.md#engine-editor-the-engines-window-on-a-document)). `domain/protocol/tests/listener_tests.cpp` reads the content security policy back, once and as a header, from the page, a script, the stylesheet, two 404s, the ticket's redirect, a capture and two refusals, and `tools/lint.Tests.ps1` holds `shell-html-sink` to each sink it names, in a scratch module, and to the text, the literal `import()` and the function timer it allows. `apps/engine_host/tests/transport_tests.cpp` checks that the listener serves `index.html` and the stylesheet and nothing outside the directory, and every protocol path the page uses: `render.load {session}`, the kept capture and its ids over HTTP, `records`, the reported camera given back, the move in place and the rebuild. `tools/host-ws.Tests.ps1` fetches the page with .NET's HTTP client. The events the page relies on are tested at the host ([protocol](protocol.md#events)): the journal's for another connection's commit, undo and redo, the scene's after a move and a rebuild, the editor's selection for `editor.select` and a pick; `tools/mcp-check.ps1 -Connect` times one from an agent's edit to a second client. The modules are checked to parse (`node --check`) by whoever changes them; a person opens the page to judge it.

## The review queue (designed, not built)

**Designed 2026-11-18 and taken through a second pass the same day, after a review of the first; nothing in this section exists yet but A50, the page's floor ([above](#feel-what-the-page-spends-effort-on)), and A51, the page tested with no device ([above](#the-test-hook)), both built and run on 2026-11-18, and A52, the agents' rule and its lint ([below](#how-it-is-tested-without-a-person-and-without-a-browser)).** It is roadmap A24's remainder and plan 06 §6.10's human director surface: the place where a person meets the work agents leave for one — review items, proposal layers waiting for promotion, and tasks — and decides. It reads the task ledger (A23, [protocol](protocol.md#the-task-ledger-and-review-items)), its decisions are [ADR-0076](../adr/0076-the-person-at-the-editor-is-its-own-page.md), and it stands on three others taken the same day, not all in this tree yet:

- **A role marked `human` is conferred by two things only: a credential the operator issued for that role, presented on a connection, and the editor's seat (below). No start line confers one.** `engine-host` refuses `--role <a human role>` in every mode (exit 2), `engine-cli` refuses it before any host starts, and `engine-mcp` refuses to start in one or to forward one — because `engine-cli` passes its `--role` on to the host it starts, a start line that conferred the role would let the cheapest command an agent has close a person's item. How a caller is known to be a person is **one field, `Caller::human_via`** (none, the seat, or a credential's name), set only in `resolve_caller`, and `Role::human` is read nowhere else; **every ledger write records how its caller was known** (`via`: a credential's name, the operator's token, stdio, the seat, or the host itself); review and task ids are random, not a counter; and **an item carries a revision** that moves on every change to it. All of that is the protocol's follow-up to A4 and A23, built beside this design: the design refers to it as there and builds its seat on it.
- **A connection over a listener is who its credential says**, and the shell's own connection is the operator's, by a cookie a one-time ticket bought (roadmap A4; its decision record is not in this tree yet).
- **A client names a file only inside roots the operator named** (roadmap T174, not in this roadmap yet), and **the shell never names a path at all** — *recommended, not decided*; the queue below is designed so that it never needs one.

The classified item is where a person meets the refusals of content classes and view policies (roadmap C3 and A26, their build rows C61 to C66: designed, with a decision record of their own, not in this tree yet). The build is thirteen rows: the first seven are roadmap A50 to A56, and the other six are numbered "row 8" to "row 13" until they have ids ([below](#the-build-in-rows)).

### Who the person at the editor is

engine-editor loads no roles file, so today nobody at its shell can close a person's item, and nothing about the shell's connection says a person is behind it: the printed `shell` address and the operator's token are on the host's stdout, which whoever started the editor reads — sometimes an agent. **So the person is the editor's own page, and only that page: a *seat*, a connection the editor gives its own web view.** The operator types:

```
engine-editor --doc ./world --roles content/roles/roles.json --person ada
```

- **`--person <name>`** says who sits at this window. It needs **`--roles`**: the editor loads that roles file (beside A4's credentials, which then bind to the roles it defines), and the seat is given the file's one role marked `human` — `reviewer` in the shipped file — or the one `--person-role <role>` names where a file marks several. The start is refused, exit 2 with the reason, with no roles file; when the file marks no role human; when `--person-role` names a role not marked human; when `--actor` names somebody else; **when the file has no role of the editor's own working role's name** (`director`, the editor's identity: without it every edit the person made would be refused, which a start can say once instead); with `--shell` (below); and with a runtime variable set (below). Without `--person` nothing changes: there is no seat, and the queue says nobody at this editor may close a person's item.
- **A name is a claim unless the connection is bound.** `--person ada` reserves the actor name `ada` against every other connection: a `client.hello` or an attribution naming it from any connection but the seat is refused (1008, `reserved actor`), compared exactly and after case folding. An unbound connection's actor name is otherwise whatever it says, and the queue draws it as that: "says it is `bot-7` (the operator's connection)". A bound connection's actor — a credential's, the seat's — is drawn plainly.
- **How the seat is made.** The editor asks its in-process listener for a **seat ticket** (`Listener::seat_url()`, beside A4's `shell_url()`) and puts it in its own web view's navigation: never printed, never written, never in the announcement. Spending it buys a cookie as A4's tickets do, of a second kind; the socket that carries it is the seat. The printed `shell` address stays the operator's.
- **One seat, and the newest wins.** Every navigation of the editor's view, a reload included, is intercepted (`NavigationStarting`) and sent through a fresh seat ticket, and **spending a ticket closes every socket that presented an older seat cookie** — logged by connection number, never by the cookie, and shown on the page. A second socket presenting the current cookie while the seat's is open is refused (1008, `seat in use`). A page refused the seat shows one banner with one button, which navigates the view; the editor turns that navigation into a fresh ticket, so the person's own window always takes the seat back, and whoever held a copied cookie loses it the moment the person presses it.
- **Only the view's own browser holds it, where the platform can say who a socket's peer is.** The listener accepts a seat socket only when its TCP peer's owning process (`GetExtendedTcpTable`) is the web view's browser process (`ICoreWebView2::get_BrowserProcessId`) or a child of it; a replay from any other process is refused and logged. The row that builds it (A54) checks first what process WebView2's network service presents as the peer. If it is neither the browser nor its child, or the platform cannot say, the seat is the cookie alone — a secret held in the browser process's memory — and the limit below is the whole of it.
- **The profile and the runtime are the seat's too.** The seat's web view uses a profile kept in memory (InPrivate, through the controller's options) and outside the document, so neither the seat's cookie nor the page's storage reaches the disk; developer tools are off on the seat; and there is no seat while an environment variable that changes the web view's runtime or its arguments is set (`WEBVIEW2_BROWSER_EXECUTABLE_FOLDER`, `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS`, `WEBVIEW2_USER_DATA_FOLDER`, `WEBVIEW2_RELEASE_CHANNEL_PREFERENCE`, and any per-user policy the loader reads in their place, which A54 lists from the loader's documentation first): the start with `--person` is refused, exit 2, naming the variable, because the second of them alone gives a debugging port that drives the page with no cookie at all.
- **The shell's files are part of the seat.** With `--person`, `--shell <dir>` is refused, and the shell's files are read and hashed at start; before a file is served to the seat it is hashed again, and a file whose bytes have changed is not served and **ends the seat until the editor restarts**, logged and said in the window. Hashes at start rather than bytes embedded at build time: a process that can write the shell directory beside the executable can write the executable too, so embedding buys nothing against it, and it would give the shell two serving paths, one for a person and one for everyone else, where hashing keeps one. What hashing does catch is the honest route — a rebuilt or merged shell landing under a running seat — and it catches it loudly, where `script-src 'self'` would have run the new file as the person on the next reload.
- **The seat holds two roles, for two kinds of call.** Its *working role* is the editor's own (`director`, as A37 has it), so the properties, the journal's undo and the queue's promotions behave as the page's edits do today, attributed to the person. Its **conferred human role** is read only by the checks that ask for a person — `review.close` of a `Human` item, the human half of `task.update` (row 8), lowering a record's content class (C63), and `editor.look` (row 13) — and those read `human_via`, which is `seat` on the seat and nowhere else. No call reaches it by naming a role: `reviewer` named in an attribution off the seat or a human credential is refused (1008), not run.
- **With a seat, every other connection is an agent's as far as classified content goes.** On an editor started with `--person`, every connection but the seat — the operator's printed token, every page opened from the printed `shell` address, any credential naming no policy — runs under `agent-default` narrowed by the editor's own policy, the rest the viewport takes; the editor's own policy is reached only by the person's look, in the native window ([below](#a-classified-item)). The content classes' design carries the same sentence from its own leg (C65). Until row 12 builds it, an editor started with `--person` refuses a view policy wider than `agent-default`, so the gap never opens in between.
- **`editor.layout` is the seat's, when there is one**: from any other connection it is refused (1008, `seat`), so nobody else can shrink the viewport to nothing during a look while the history says `looked`. `editor.select` and `editor.pick_file` stay open to every connection: one moves a highlight that no action reads, the other opens a dialog the person answers.
- **Who does not get it**: every start line (above); the operator's printed token and every page opened from the printed address; a connection that presented a credential, unless the operator issued that credential a human role, which an agent is never issued; engine-mcp attached with `--connect-from` or `--token-file`, which is one of those two; and the editor's native viewport, whose gestures are the editor's own calls (the one native act a decision needs, the look, is the seat's call).
- **Why not engine-host.** A browser tab is opened from an address that whoever read the host's stdout holds too, so a browser against engine-host is never a seat. The queue there reads everything and offers every action on agents' items, proposals and tasks that the connection's role allows; a person's item says it is closed at an editor started with `--person`.
- **What the ledger records**: the closer's attribution and `via` as every write has them, plus `closed_via` — `seat`, `seat (test page)` or `credential <name>` — with how the editor was started (`started`: whether its stdout is a console or a pipe, and its parent process's image name), and the subject digest the person decided at ([below](#what-a-close-is-tied-to)).
- **What this is not.** In the content classes' words: against a protocol client the seat is a wall; **against a process of the same user it is a rule and an audit trail, and nothing here claims more.** The routes such a process has, which the guard rails above narrow and none closes: the seat's cookie in the browser process's memory and in its crash dumps (bound to that process where the platform allows); the user's environment and per-user policies that change the runtime or add a debugging port (refused at start, not watched after); the shell's files on disk (hashed); and the desktop itself. **Whatever can drive the desktop can click the seat**: UI Automation's Invoke on a button in the web view's accessibility tree, synthetic input, the desktop-control tools agents run — and the audit cannot tell that click from a person's. So the seat certifies a click in this window, not a person. That an agent never starts engine-editor with `--person` on a document outside a test's scratch directory and never operates its queue is the repository's rule, as editing a view policy is: `AGENTS.md` says so (A52), and the lint `person-flag` holds every committed script, CMake file, CI workflow and launch configuration that starts engine-editor to it.
- **A sign-in on closing, described and declined** (the owner, 2026-11-18: no prompt; [below](#open-questions)). The editor could ask for the person's own sign-in through the system (Windows Hello, `UserConsentVerifier`) on each close of a person's item, recorded as `closed_via: seat+hello`. It buys the one thing nothing above does: a synthetic click cannot pass it. It costs a prompt per decision (thirty items are thirty prompts, unless one sign-in covers a minute of closes, which reopens the window it was meant to shut); a Windows API with no counterpart this tree uses on Linux; an editor that cannot close a person's item on a machine without Hello set up; and one more system dialog, which no test may ever meet, so the test page could never exercise the path a person takes.

### What the queue lists, and how it stays current

**A tab beside the journal**, "Queue", in the same place in both layouts (the narrow layout's drawer holds both tabs), with a count of open items for a person on the tab and in the title bar. Four sections, each one bounded read (`limit` and `order` on both list methods, A55, so "the newest fifty" reads fifty):

| Section | Read | Shown first |
|---|---|---|
| For a person | `review.list {state: Open, audience: Human, brief: true, order: Oldest, limit: 50}` | oldest first: a person's items wait |
| For agents | `review.list {state: Open, audience: Agent, brief: true, order: Newest, limit: 50}` | newest first |
| Proposals waiting | `doc.layers`, the layers whose `proposal.state` is Open with `touched` above zero | oldest first |
| Tasks | `task.list {statuses: [Open, Claimed, Blocked], brief: true, limit: 50}` | Blocked, then Open, then Claimed |

A toggle shows the closed ones (`state: Closed`, and Done and Dropped tasks, `order: Newest, limit: 50`). A section that holds more than its limit says how many it did not show.

**No poll where an event exists.** The page already subscribes to `session` events; the ledger's changes (`task_created`, `task_claimed`, `task_updated`, `review_raised`, `review_closed`) name an id, and the page **coalesces the ids its events name over a quarter of a second into one read** — `review.list {reviews: [ids]}` and `task.list {tasks: [ids]}` (A55) — never one read per event and never the list: every read parses the ledger under its lock, and a burst of an agent's writes answered with a read each would starve the person's close. Two kinds of change publish no event today and get one (`SessionChangeEvent` version 4, A55): a proposal opened, promoted, rejected or reopened (`proposal_*`, with the layer, from the proposals' methods after `proposals.json` is written), which re-reads `doc.layers`; and **`ledger_changed`**, for a ledger another process wrote (engine-cli's host per call, a second host on the document). The host watches the ledger's directory with the system's directory-change notice (`ReadDirectoryChangesW`; inotify on Linux) as its hint to look; on a notice, or a notice the system reports it dropped, it reads the file's revision, size and content hash, and publishes when **any of the three differs** from what it last saw — inequality, never "greater", because a ledger restored from a copy has a revision that went back. The ledger is written through the one side-file helper, which writes nothing when the bytes are unchanged, so the revision moves only when the content does (the ledger's move onto that helper is the protocol's follow-up to A11 and A23). Where the file system gives no notice, the host falls back to looking once a second, and says so in its summary. An `event.journal` moves the journal counts of the items whose subject it names, from its ids, with no call. An event with `dropped` reads everything again. Only with no subscription does the page fall back to today's ten-second look, which then reads the four lists too.

**One row** shows numbers, names and identities, and never a picture, a capture, a thumbnail, a property value of the subject or a URL:

- *An item*: its kind and audience, its id, its summary on one line, who raised it — actor, role, and how it was known (`via`: a credential, the operator's connection, stdio, the seat, or the host itself) — and when, the subject as counts (records, blobs, assets, the layer), the task it is for as its key, and **the journal's counts, as colour and never as the decider**: "7 transactions since, 2 touch it" when the item was stamped by this host's own session, and "raised elsewhere" when it was not, since two processes' journal numbers are not one history. A list never computes a digest; only the item's opened detail says whether its subject is what it was.
- *A proposal*: the layer and its target, its owner and the owner's role, the task, how many target records it touched, when it was opened, and its rationale.
- *A task*: its key, title, status, the role it is for, its claimant and when the claim lapses, and how many review items and links it has.

The summary, a rationale, a title, a goal, a note and a client's name are **other clients' words**: shown as text, clipped, and always beside whose words they are ([below](#what-another-clients-content-cannot-do)).

**Opening a row.** An item's detail has its whole summary, its report as JSON text, its history and its subject. The subject is **selected**: `editor.select` of its first live record embedded, so the native viewport outlines it and the properties show it, or the slideshow's selection in a browser; the subject's other records are listed, each a button that selects it, and records no longer live are named as gone. Then **the subject, plainly**, from the digest the host computes now against the one it stamped at the raise (`review.list {review, digest: true}`, A56; [below](#what-a-close-is-tied-to)):

- the same: "What this item is about is as it was when it was raised: its records, their parents, the layer order, and every asset and blob they name."
- not the same: "What this item is about has changed since it was raised", then what the host can name — the records whose content differs, the assets whose bytes differ, the records gone, the layer order moved — and, as colour where the stamp shares this session's history, "7 transactions since, 3 of those it was raised after undone". With a checkpoint on the item: "Checkpoint `<id>` holds the version it was raised at."
- **An item about a proposal layer** (`ReviewSubject.layer`) says which document the viewport draws: "The viewport draws the document with its proposals unpromoted; this item is about proposal layer `<id>`."

The viewport shows the document as it stands, never an older version. A proposal's row selects nothing until a record of its list is chosen (row 11); a task's links select what they name — a proposal its row, a record the record, a review item its row — and name the rest (leases, transactions, checkpoints) by id.

### What a close is tied to

A person who accepts an item accepts what the window showed them. Between the drawing and the click another connection can change the subject's records, a parent's transform, the layer order or an asset file (which makes no journal entry at all), or undo below the stamp and redo after the close; and journal numbers stamped by two processes are not one history. So **the close carries a digest of what it is about, and the host refuses it when the digest is not the one the page showed.**

- **The subject digest** is a SHA-256 the host computes over one canonical stream: a version; the document's layer stack in composition order; then, sorted by id and each once, every record the subject names and every `ChildOf` ancestor of one — its id, type, parent and composed properties in the document's canonical form, or a mark that it is gone; then every blob those records and the subject name, by its SHA-256 name (a blob's name is its content, so this costs nothing); then every asset they name, by its root's name and portable path (T174) and the SHA-256 of its bytes read now, or a mark that it is missing.
- **It hashes content and never trusts a file's time.** An asset's bytes are read at every computation that decides anything; a time or a size is never taken for "unchanged". So an asset rewritten under a running editor changes the digest whether or not the viewport has reloaded it, and the close is refused rather than decided on bytes the window may not be drawing.
- **When**: stamped at the raise into the item (`ReviewInfo.raised_digest`), by the raising host from its own document — content, so a digest stamped by engine-cli's host compares with one the editor computes, where journal numbers do not; computed again when an item's detail is opened (`review.list {review, digest: true}`, one item, never a list) and at the close; never for a list's rows.
- **The close carries what the page showed**: `review.close {review, resolution, note, seen: {revision, digest}}`, the item's revision and the digest its detail was drawn with. Either differing from the host's now is refused with 1004, and the record of the decision holds the digest it was made at (`ReviewInfo.decided_at`).
- **Promotion the same**: `doc.promote {proposal, dry_run: true}` returns a digest of the proposal layer's records and of the target's values at each conflict it reports, and `doc.promote {proposal, prefer, seen: {digest}}` is refused with 1004 when the proposal or those target values changed since, so "take the proposal's" applies to the values the person saw.
- **What it does not cover**: a record the subject names only by reference in a property (a material record by id), unless the item lists it — the raiser lists what the decision rests on; the scene's sky and its hour; and anything after the close.
- **What it costs, estimated and not measured** (A56 measures it, on a quiet machine, and writes the numbers here): for a subject of a thousand records of about a kilobyte of composed properties each, plus their few dozen ancestors, an index lookup a record, about a megabyte of canonical form, and a hash of it in `core/hash`'s portable SHA-256 (no SHA extensions; a few hundred megabytes a second a core in release) — tens of milliseconds in all in release, the serialization rather than the hash most of it. **Assets are the cost that scales**: their bytes are read and hashed at every deciding computation, so a subject naming 200 MB of source files costs about a second when the detail opens and again at the close. Blobs cost nothing.
- **Where it is cached**: in the host's memory only, never on disk, since a cache file is one more thing another process can write. A record's part is kept by its id and dropped by the document's change feed (`changed_since`), the host's own record of every mutation of its document, not a time. An asset's hash may be reused when a detail opens while the directory-change notice on its root has reported nothing for it since (a notice the system reports dropped clears them all); at the close it is always read again, so the computation that decides trusts nothing kept.

### The actions, and what a refusal shows

Every action is one button that sends one method, and **the host decides**: the page shows a button it expects to be refused as disabled with the reason beside it, and shows a refusal it did not expect in the row, in words, with the method's message under them. **Accept and Reject live only in one item's opened detail**, never in a list's row, and rest disabled for half a second after anything in that detail changes, so a redraw on an event cannot put another item's button, or a changed item's, under the pointer.

| Action | Method | Refused when, and what the row says |
|---|---|---|
| Accept, Reject | `review.close {review, resolution, note, seen: {revision, digest}}` | a person's item from a connection with no `human_via` (1008 `human review`): "Only a person closes this, at an editor started with --person; this connection is not one." The item or its subject changed since the detail was drawn (1004): "This item, or what it is about, changed since you opened it", and the detail is drawn again with the new statement |
| A note | `review.note {review, note}` (row 8) for an item; `task.update {note}` for a task | a role that does not name the method (1008 `method`): "This connection's role, <role>, may not write to the ledger" |
| Withdraw | `review.close {resolution: Withdrawn}` | shown only on an agent's item raised by this connection's bound actor; a person's item has no Withdraw |
| Promote | `doc.promote {proposal, dry_run: true}`, then `doc.promote {proposal, prefer, seen: {digest}}` | `promoted: false`: the sentence, the conflicts by record and property, and the validation problems the promotion would introduce, with a "keep the target's" and a "take the proposal's" choice for the conflicts (`prefer`), never for validation. 1004: "The proposal changed since its dry run", and the dry run is shown again. 1008 `review required`: "This connection's role may propose and not promote" |
| Reject a proposal | `doc.reject {proposal}` | 1008: "Only its owner or a role that may change <target> rejects it" |
| Claim | `task.claim {task}` | 1009: "<actor> holds it until <time>"; 1008 `task role`: "It is for <role>; reassign it first" (a task for a human role is claimed by `human_via`, not by the working role's name) |
| Reassign | `task.update {owner_role, release}` (version 2, row 8) | anyone but the task's creator or a person (1008 `task owner`): "Only its creator or a person reassigns it" |
| Look (a classified item) | `editor.look {review}` (row 13) | below |

### What another client's content cannot do

- **Rendered as text, never as markup.** Every string another client wrote — a summary, a note, a rationale, a title, a goal, an acceptance criterion, a report's strings, an actor's or a hello's name, a record's name — goes on the page through `dom.js`'s `h()`, which makes text nodes. No module of the shell assigns `innerHTML`, `outerHTML` or `insertAdjacentHTML`, or calls `document.write`, `eval`, `Function`, a timer with a string, or `import()` with anything but a literal: a lint rule (`shell-html-sink`, A50) holds every file of `apps/engine_shell/` to it, as `tools/lint.ps1` holds engine code to its rules. A report is shown by `prettyJson`, as text.
- **Bidirectional controls and look-alike letters are drawn, not obeyed.** Every span of another client's text is isolated (a `<bdi>`, or `unicode-bidi: isolate` from the stylesheet), so a right-to-left override cannot reorder the words around it; control and format characters (the bidirectional overrides and isolates, zero-width spaces and joiners) are drawn visibly as their code points; and a name or word that mixes scripts — a Cyrillic `а` in a Latin name — is marked as mixed, so a look-alike of the person's name reads as what it is.
- **Never an attribute.** No `href`, `src`, `style`, `class`, `id` or `data-` is set from another client's string; a link inside the queue is a button whose target is an id the page parsed itself (a number, an id128), never a URL. So a summary that is a `javascript:` URL, an `<img onerror>` or a stylesheet is a line of text. This one is a review rule: a lint cannot tell an attribute set from another client's string from one set from a constant.
- **Nothing is evaluated, and nothing is fetched**, beyond what the page already does: the listener serves every file of the shell, a 404's body included, with a content security policy as a header (`default-src 'self'; script-src 'self'; style-src 'self'; img-src 'self' blob:; connect-src 'self'; object-src 'none'; base-uri 'none'; form-action 'none'; frame-ancestors 'none'; require-trusted-types-for 'script'; trusted-types 'none'`, A50), so a mistake in the page could not run a script or load an image from elsewhere, and a string that reached an HTML sink anyway throws in the browser, whatever the lint missed.
- **Only a click on a button the page drew writes.** No event, notification, row, report field or note triggers a call that changes anything, and nothing confirms itself after a delay. The id a button acts on is the one its detail was drawn for; the selection is not it, so an agent's `editor.select` moves the outliner's highlight and never what Accept accepts. The close carries the item's revision and the subject's digest the detail showed, so a note slipped in, or a subject changed, while the person read is refused by the host and drawn, not decided past.
- **Whose words they are is the host's, not the text's.** The raiser, its role and how it was known come from the ledger's attribution and `via`, which the host fills from the connection, and are drawn beside the words in another style; an unbound connection's actor name is its own claim and drawn as one; a summary that says "approved by Ada" reads as the agent's sentence it is.
- **The command line stays the person's**: the queue never fills it, and nothing in a row is a request to run.

### A classified item

A `classified content review` item (C66) is raised **by the host and only by the host**, when a capture, a load, a compare or a blob read was refused above the caller's view policy, and carries numbers, never a picture. `review.raise` refuses that kind from every client (1008), and the look is offered only on an item whose `via` is the host's own, so nobody can make the queue offer a look at a subject of their choosing with a report in the item's shape. **Designed, not built** (C66, A66): today `review.raise` takes that kind from any client, and the ledger bounds an item's report only at 64 KiB of JSON.

**Before the person chooses to look**, the row and its detail show exactly what the item carries: the kind and the Person badge; the category, the level found, the cap and the policy that refused it (from the report's schema type, which C66 defines, so the page reads it as it reads any protocol type); the subject's identity — records by name, type and id, assets by their root's name and their path under it (T174's portable names, never a path of the machine), each asset's source hash, build key and content hash; the digest it was stamped with and whether it still holds; who was refused, by which method, over which kind of connection; and the validator numbers. Nothing else: there is no image anywhere in the queue, and the page never asks for one.

**Looking happens on the person's own editor, in its native window, and nowhere else.**

- **The editor's viewport rests held.** It draws under `agent-default` narrowed by the editor's own `--view-policy` (C65), so a person who started an editor wide enough to review sees nothing classified until they choose to: the subject is the proxy box or nothing, as an agent's capture would be. (This is the held state, the default of an option the owner chose ([below](#open-questions)); an editor started not held has no look, and draws and serves at its own policy from the start.)
- **The look is a scene of its own.** Look (embedded, on the seat only) sends `editor.look {review}`. The editor reads the subject's classes from **the main scene's own decisions** (C64's table), never from the item's report; instantiates a second scene holding the subject's records alone, under its own `--view-policy`; and draws it in the native window **in place of** the main viewport while the look lasts, framed, with "Looking" in the corner. **The main scene is never widened**, so the content classes' rule that a scene is instantiated under one policy stands, and no decision per placement is needed.
- **The look is pinned.** It records the subject's record, mesh and class at its start, and ends when any of the three changes — a `SetProperty` of the placement's mesh from any connection, a sidecar that moves the class — as well as at **Hold** (`editor.look {review, end: true}`), when the item is closed, when the editor's window stops being the foreground window or the session locks (`window::desktop_state()`), and at exit.
- Refused with 1008 (`seat`) to every connection but the seat, with -32601 on engine-host (it is the editor's method), and with 1011 when the editor's own policy does not cover the subject: "This editor may draw <category> up to <cap>; the subject is <level>. A person looks at it in an editor started with a view policy that covers it; nothing in this window widens one."
- **Never through an agent's session**: the picture exists only in the native child window — the editor registers no `render.capture`, so no frame of its viewport reaches any connection, the page's included; every other connection runs under the rest (above) and sees what the page showed before the look, the numbers.

**What is lost by looking at the subject alone**, an open question of this design ([below](#open-questions)), built into no row: the subject's scale and place among its neighbours, the light and shadow the scene gives it, and how it reads beside the content around it. The look's scene could carry the main scene's sky and lights, which are not classified content, without any other mesh — that keeps the light, and not the neighbours or their shadows. Widening the subject's placements inside the main scene instead would cost the content classes' design its invariant: `instantiated_under` per instance rather than per scene (a `decided_under` on each), every output that names its policy naming a set of them, the one admission function taking a policy per placement, the live re-decision on a mesh change reading the instance's own policy — which is the route by which a widened placement draws what nobody chose — and "under one policy a class always decides the same way" given up.

**What the item records**: a history line `looked` — the person, the human role, when, the policy name, the subject's digest and the record, mesh and class it pinned — and `held` with how long the look lasted and why it ended; then the close with `closed_via` and the digest decided at. Accept on an item the person has not looked at asks once ("Accept without looking?") and its note says so. The ledger never holds the picture; closing changes no class and no policy (C66).

### How it is tested, without a person and without a browser

The guarantees are the host's, so they are tested where the shell's protocol paths are tested today, through clients that are not a browser; the page's own behaviour is tested by the editor's test hook in its web view, made to run with no GPU.

- **The page's floor, no browser** (A50). `listener_tests.cpp`: the policy above, as a header, on every response that serves a file of the shell — the page, a script, a stylesheet, a 404 — and read back per kind of file. `tools/lint.Tests.ps1`: `shell-html-sink` refuses each sink in a scratch module and allows `h()` and `textContent`.
- **The page with no device** (A51): `engine-editor --embedded --test-page --no-viewport` runs the page with no device and no GPU lock, and the browser's own GPU off; a case asserts from what the process reports that it opened neither.
- **The agents' rule** (A52, built). `AGENTS.md` says it beside the view-policy rule, and `tools/lint.ps1`'s `person-flag` reads what is committed and an agent may run: PowerShell scripts and modules, batch and shell files, CI workflows and CMake files under `tools/`, `.github/`, `templates/`, `cmake/`, the six layers and the root, and the `launch.json` and `tasks.json` of `.claude/` and `.vscode/`. A file of that set that names engine-editor outside a comment passes `--person` or `--person-role` on no line outside a comment — the file and not the line, because a script builds its arguments a line or more away from the program it starts; the marker `engine-lint: allow-person-flag <reason>` exists and has no use. A test's C++ is not in the set: its document is under its own scratch root, and the editor itself refuses `--person` with the test page anywhere else (A53). `tools/lint.Tests.ps1`: a scratch script starting engine-editor with the flag is refused, and so are a batch file with `--person-role`, a CI workflow, a CMake test definition, a launch configuration and a game repository's template; the flag in a comment of each kind, another program's `--person` and engine-content's `--persons` are not; the marker without a reason is refused; and the rule finds nothing in the tree, where nothing uses the marker.
- **The seat, CPU only** (A53). `domain/protocol/tests/listener_tests.cpp` over a loopback listener in process: a seat ticket made in process and spent once, its cookie's socket reported by `client.hello` with `human_via` `seat`; a second ticket spent closes the first seat's socket; a second socket with the current cookie refused while the seat's is open; a hello naming the reserved actor refused from the operator's socket; a shell file changed after start not served to the seat, and the seat ended. ### Open questions

None of the design's four questions for the owner is open. Decided on 2026-11-18:

- **The viewport at rest: an option of the editor** (the owner). Holding classified content until a look is not a fixed behaviour but something an editor is started with or without: an agent that may have trouble with classified content runs the editor with it, and an agent or a person that has none runs it without. What follows is the design's reading of that decision, taken in its review and not by the owner, and reversible:
  - **Held**, the default (the default is a decision of the design, taken in its review and not in the owner's words; reversible), is what this section describes: the viewport rests at `agent-default` narrowed by the editor's policy, every connection but the seat runs at that rest, and the editor's own policy is reached only by a look.
  - **Not held**: there is no look. The viewport draws at the editor's policy from the start, and the editor's connections run under the policy the content classes' design gives any host (the host's own, or a connection's credential's), every output naming its policy as that design already requires.
  - **The option is not a view policy and widens none.** It chooses only whether an editor rests below the policy it was started under; which policy an editor has is still the operator's, by the content classes' rules, and an editor at `agent-default` draws the same in either state.
  - How the option is given (a start flag and its name, whether it is also a stored preference) is decided by the row that builds it. Rows 12 and 13 (the rest under a seat, and the classified item's look) build the held state; the not-held state needs nothing from them.
- **A sign-in on closing: no prompt** (the owner). The question was whether closing a person's item at the editor should also ask for the person's own system sign-in (Windows Hello) on each close, which a synthetic click could not pass. The owner chose no prompt. So the protection against a program that drives the desktop stays what this page says it is: the agents' rule (A52) and the record of how each item was closed (`closed_via`, with how the editor was started).
- **The seat's roles: two** (a decision of the design, taken in its review as it recommended and not by the owner; reversible): the editor's working role and the conferred human role, rather than one human role that may also edit.
- **engine-host and a person: a browser against engine-host never closes a person's item** (a decision of the design, taken in its review as it recommended and not by the owner; reversible), rather than an `engine-host --person` whose printed shell address is the seat.

Of the design itself, held for a decision before row 13: **whether a person can judge a subject without its surroundings** ([above](#a-classified-item)), and if not, whether the look's scene carries the main scene's sky and lights or the content classes take a decision per instance. Also open, from the first pass: "the shell never names a path" is a recommendation, not the owner's decision.

## Not yet

- **A live viewport in a browser.** In a browser tab each picture is a `render.capture` — a frame drawn offscreen, read back, encoded as a PNG and fetched over HTTP — which is a slideshow, not a view, however fast the GPU; the time each one took is in the viewport's corner. The live one is engine-editor's native viewport beside the embedded page ([above](#embedded-in-the-editor)).
- **Selection in the picture.** A selected record is not outlined in the viewport (engine-editor draws its box); the shell would need the host to draw it, which is a capture option nobody has asked for yet.
- **A gizmo, multi-select, create and delete**, a layer picker, and leases in the UI. Each is a protocol call away; none is built. The review queue and the proposals' view are designed and not built ([below](#the-review-queue-designed-not-built)).
- **The bulk channel** instead of HTTP GETs of kept captures (roadmap A2's remaining half).
- **A layout narrower still.** Under about 400 CSS pixels the two columns' minimums (180 and 160) no longer fit either; nothing here opens a window that small. (The spike's two blemishes in the browser form are fixed: the "Connecting…" placeholder stayed drawn over every capture because its `display: grid` beat the `hidden` attribute, which a global `[hidden]` rule now settles; and the slideshow notice fades for good a few seconds after the first picture instead of sitting over every one.)
