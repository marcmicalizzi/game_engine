# engine_shell: the browser shell over the protocol (apps)

**Purpose.** The authoring editor's shell (roadmap A36's spike, then A37, [06 §6.13](../plan/06-agent-tooling.md#613-human-developer-tooling)): a page that **speaks nothing but the engine protocol over a socket**. It began as the candidate beside engine-editor's Dear ImGui panels ([ADR-0054](../adr/0054-the-tools-ui-is-dear-imgui-drawn-by-the-renderer.md), proposed), which worked but did not have the feel the owner wanted (Qt he knows and finds utilitarian); the owner judged its panels clearly better, and since 2026-10-11 it *is* the editor's panels, in a web view beside the native viewport ([below](#embedded-in-the-editor)), while still opening in a browser against engine-host. This is the third option made concrete enough to judge by using it: static HTML, one stylesheet and a handful of ES modules in `apps/engine_shell/`, served by `engine-host --listen` itself ([apps](apps.md#engine-host---listen-the-protocol-over-a-loopback-websocket)) and opened in a browser tab. The same files can later run in an OS webview inside our own window, or in an embedded Chromium if the game UI ever wants one; in every form, no panel has a private path into the engine.

**The rule: it holds no engine knowledge beyond the protocol.** Every string it shows about the world came out of a method — the outliner from `doc.objects`, the fields, their kinds, their documentation and defaults from `schema.describe`, the journal from `doc.journal`, the identity from `engine.roles`, the completions from `engine.methods`, the picture from `render.capture`. It never reads a document file, never names a record type (the only types it knows are the protocol's own field kinds, `f32` or `worldpos`), and every change it makes is a request a script could make. A feature it needs that the protocol lacks is a protocol change, made in the host where every client gets it — which is how `render.load {session}`, `render.capture`'s `keep`, `records` and A32's `camera` came to exist ([apps](apps.md#engine-host---listen-the-protocol-over-a-loopback-websocket)).

**Open it.** One host command; the browser is the user's:

```
build/msvc-debug/bin/engine-host --listen 127.0.0.1:0 --doc <dir> [--create] --actor <name>
```

The first line it prints is `{"listen":"ws://127.0.0.1:<port>/","session":"s1","shell":"http://127.0.0.1:<port>/?ticket=...&session=s1","token":"..."}`; open the `shell` URL. Its one-time ticket buys the page a cookie and the host sends it on to an address with no ticket; the cookie is what the listener checks on the socket and on capture fetches, so the page never holds a credential and its address keeps none ([protocol](protocol.md#who-a-connection-is), ADR-0069). A page the host refuses (its address spent in another browser, or older than ten minutes) says so and does not retry: a running engine-host cannot print a new address yet, so restart it; a second tab in the same browser, and a reload, need nothing new. The host ends when its standard input closes (Ctrl+C in its terminal).

## What it is

- **Viewport.** `render.load {session}` once, then `render.capture` at the panel's size with `channels: ["color", "ids"]` and `keep: true`, the PNG fetched from `GET /capture/<id>`. It is a **slideshow, and says so on screen**: every gesture ends in one full-size capture, and while a gesture lasts the page asks for half-size captures back to back (never more than one in flight) so motion can be followed. engine-view's fly controls on the keyboard (W A S D, Q E down and up, Shift to hurry), a drag to look, the wheel to dolly, F to have the host frame the scene again, R to capture again. The camera is the host's: every capture reports the one it drew with (A32), the page flies from that report in engine-view's convention and sends the camera back, and the corner shows it with the capture's size, time and id. A click reads the kept id buffer at that pixel (`GET /capture/<id>/ids`, three `u32` a pixel) and selects `records[instance]`. After every transaction the page loads the session again — the host moves or rebuilds in place — and captures again. **The live viewport comes when the native window is a client of this same host** ([06 §6.13](../plan/06-agent-tooling.md#613-human-developer-tooling)), not from this page.
- **Outliner.** Type, name and id tail of every live object, parents before children, collapsible, filtered as you type; the arrow keys walk it.
- **Properties.** Every field of the selected record from its type's `schema.describe`, with an editor by kind: number boxes (integers checked), text, a checkbox, x/y/z(/w) axis boxes for `vec2`, `vec3`, `quat` and `worldpos`, a list for an enum the host describes, JSON for anything else, and an Unset (`ClearProperty`) for an optional field that is set. **A changed field is one `doc.apply` with one `SetProperty`** and the rationale typed in the field under the panel, which defaults to "Set <field> of <name>"; the input flashes when the host committed it and turns red when it did not, with the reason in the status strip. Properties a record holds that its type does not declare are shown too, as JSON.
- **Journal.** The session's transactions newest first, each with its rationale, actor, role, task, command count, layer and time; entries past the undo position faded. Undo and Redo in the title bar (Ctrl+Z, Ctrl+Shift+Z) are `doc.undo` and `doc.redo`, which the host checks against the role like any write.
- **Command line.** One JSON-RPC request typed by hand — `method {params}`, or a whole request object — and the answer, coloured, with its round-trip time. Completion is the engine's own catalogue from `engine.methods`, each with its documentation and a `write` badge on methods that are not read-only; taking one fills in the session. History survives a reload. A `session.open` typed here becomes the page's session; any other write refreshes the panels.
- **Status strip.** The host, the session, the actor and role the host attributes edits to, how the page is known to the host (its cookie), and the last error a method returned.

**When another client edits: events** (2026-10-11, roadmap A2; [protocol](protocol.md#events)). On every connect — the first and each reconnect, since a subscription is the connection's — the page sends `session.subscribe` for its session's `journal`, `selection`, `scene` and `session` events, and from then on the host pushes them as they happen and the page reacts: a **journal** event whose journal length or undo position differs from what the page shows refreshes the outliner, the properties, the journal and the viewport (the page's own edits included — its `doc.apply` no longer refreshes by itself, so a change refreshes once whoever made it); a **selection** event moves the outliner's highlight and the properties (embedded, a click in the native viewport); a **scene** event for the scene the slideshow shows, newer than the revision it last drew, takes the picture again (another client loaded it after a change); a **session** event names a lease taken or released in a toast, and a close as an error; an event that carries `dropped` (the page stopped reading and its queue overflowed) refreshes everything. An agent's edit through an attached engine-mcp reaches the outliner in about 25 ms on loopback in a debug build and 13 ms in release — the event, then the `doc.objects` the outliner sends — plus the page's layout ([apps](apps.md#attached-to-a-running-host---connect) has the measurement); the poll it replaced took up to two seconds. **The fallback** is the old look at `session.info`, every **ten** seconds now, and it runs only while no subscription stands (a host without `session.subscribe`, or none yet). The status strip's **updates** badge says which is in use: "events" with a green dot, or "poll 10 s" with an amber one and, in its tooltip, why the subscription failed.

**It reconnects, and says so.** A dropped socket turns the title bar's pill amber ("reconnecting"), the page retries with a growing pause up to five seconds, and when it is back it loads the session again; a request in flight when the socket dropped fails rather than being sent twice, since the host may have run it.

## Embedded in the editor

The A36 spike's verdict (2026-10-11) was that the panels were right and the slideshow viewport could not be flown, so the shell's main form is now **inside engine-editor's own window** (roadmap A37, [apps](apps.md#engine-editor-the-engines-window-on-a-document)): the editor runs the protocol's listener in process, opens this page from it in the platform's web view ([webview](webview.md)) with `&embedded=1` on the URL, and lays its **native, live Vulkan viewport** in a child window over the page's viewport cell. The two tile and never overlap; nothing is composited and nothing crosses per frame.

- **The viewport panel becomes an empty cell** (`embedded.js`, `EmbeddedViewport`, standing where the slideshow's `Viewport` stands, so nothing else in the page knows which mode it is in): the same panel with the same drag-to-resize splits, its slideshow image, notes, Frame and Capture buttons gone, and a dark backing — which is what shows for the frame a resize takes the native window to follow. The panel's corner names the native picture's size.
- **`editor.layout`, a notification**: the cell's rectangle in CSS pixels from the page's corner (`getBoundingClientRect`) and `devicePixelRatio`, sent on load, whenever the socket (re)opens, on a split drag, on a window resize and when the ratio changes (a `ResizeObserver` on the cell, `resize`, and a `matchMedia` on the current resolution), coalesced to one a frame and not sent again when nothing moved. A notification has no id, so the editor sends nothing back; the page sends it only while the socket is open (`Rpc.notify`) and again when it opens, since what it carries is the page's current state, not an event to queue. The editor moves its child window there ([protocol](protocol.md#the-editors-methods)).
- **The selection goes both ways.** A click in the outliner sends `editor.select {id}` (read-only: UI state, never the document), so the native viewport outlines the record and its gizmo attaches. A click in the native viewport reaches the page as an **`event.selection`** pushed by the editor's listener ([above](#what-it-is)), so the outliner and the properties follow a pick as it happens; the half-second poll of `editor.state` that did this before events is gone. The page's own `editor.select` comes back as an event too and is recognised as the selection it already has.
- **Nothing else changes.** The outliner, the properties and their edits, the journal and its Undo and Redo, the command line and the status strip are the same code over the same protocol; a transaction from the page is a transaction on the editor's own session, and the viewport follows it the next frame. The page has no bridge to the process — no `window.chrome.webview`, no binding — so the same files still run in a plain browser against engine-host, and against the editor too (its listener prints the same `shell` URL).
- **Popups stay in their panels, and a test says so.** The native window covers the cell, so anything the page drew over it would be hidden. The command line's completions and an enum's list are placed by `fitPopup` (`dom.js`): against their anchor, below it or above it where there is more room, with their height capped to the room left in their own panel; an enum's list is the page's own (`enumList`, `properties.js`), not a native `<select>`, whose list is the platform's popup and can be neither kept anywhere nor measured, and it is fixed-positioned so the scrolling properties do not clip it. The toasts sit at the bottom middle of the page, over the command line. The test hook proves the two lists and the "Reconnected" toast stay off the cell ([below](#the-test-hook)); `shell.css` says so beside the embedded rules for whoever adds the next popup.
- **The gizmo's tool and adding a mesh** (2026-10-12, A39). Embedded, the title bar has a two-button toggle, **Move** and **Rotate**, that calls `editor.tool` and shows the editor's answer; the status strip shows the tool too; and the page follows the editor's `editor.tool` notification, which it sends when T or R is pressed in the viewport, and reads `editor.state`'s `tool` on every (re)connection. The outliner's header has **Add…**, which asks the editor for a file (`editor.pick_file`, the platform's own dialog, on the editor's thread) and imports it (`editor.import_mesh`: copied under the document's `assets/`, placed in one transaction, selected — the outliner and the journal follow by their events), with a toast naming what was imported or the method's reason in the status strip. A file dropped on the page is not navigated to (the page cancels the drop and says to drop it on the viewport, which imports it). **In a browser tab none of this is shown** (`.embedded-only`): those methods are the editor's, and engine-host answers "method not found". The properties panel reads a quaternion field (`rotation`) in degrees beside its four numbers — yaw, pitch and roll in `quat_from_euler`'s order, derived, never written.
- **`editor.relayout`.** The editor speaks first once: when the display's scale under its window changes it sends this notification, and the page answers with a layout whether or not its rectangle moved. The transport answers requests and drops what has no id, so `EmbeddedViewport` listens on the socket itself for that one method (`listen`), on every (re)connection.
- **The page never scrolls.** The app's one grid column is `minmax(0, 1fr)`, so no panel's content can make the page wider than its window; before that, a page wider than its window scrolled sideways when an input took focus, and the native viewport stayed where the cell had been. The cell also re-sends its layout on a scroll, should anything scroll it.

The editor's default window is 1600 × 900 because the three columns want about 950 CSS pixels (left 280, the viewport at least 320, right 340) — at a display scale of 150 % that is about 1430 window pixels. Narrower, the page takes its narrow layout.

## The narrow layout

Below **960 CSS pixels** of width (`NARROW_BELOW`, `layout.js`) the three columns do not fit, and before A38 the page simply overflowed — in a browser the right column went under the window's edge, and in engine-editor's 1280 × 720 window at 150 % (853 CSS pixels) the properties, the title bar's Undo, Redo and pill, and the right part of the viewport cell were cut off, the native viewport with them. So below the line the page is **two columns**: the outliner over the **properties** on the left, the **journal a drawer** under them (its head only, with a ▸, until a click opens it to a third of the column), and the viewport over the command line on the right; the brand's name gives up its room in the title bar. A `ResizeObserver` on the page decides and sets `.narrow` on the root; the stylesheet does the rest, except moving the properties panel between the columns, which no stylesheet can do. The two layouts' widths do not overlap, so a resize across the line flips once. The viewport cell is one rectangle in both, its rectangle goes to the editor through `editor.layout` as before, and the layout's `narrow` flag tells the editor which it is. The splits keep working: the left one sizes the column (at most 42 % of the page), the row split the properties.

## The test hook

`testhook.js` is loaded only when the page's address carries **both** `embedded=1` and `test=1` — which only `engine-editor --test-page` puts there — so a browser, and the editor without the flag, never load it, and the page exposes nothing else for tests (a `window.__test` holding its report function, nothing that changes the page). It checks from inside the page what only the page can see, by DOM events the page dispatches to itself — the layout of its own popups is the page's; the platform's input is the editor's own test (`--test-keys`) — and reports each check as an `editor.test_report` notification, a method the editor registers only with the flag, into the run's summary: **"completions"** (typing `doc.` into the command line opens the completions, which stay inside the command line's panel and off the cell), **"enum"** (a click on the AssetProvenance record in the outliner, then on its `license_class` button, opens the enum's list, which stays inside the properties panel and off the cell), **"done"**, and on every reconnect **"reconnect"** (the pill said "reconnecting" while the socket was down and "connected" after, and the "Reconnected" toast is off the cell).

## Feel: what the page spends effort on

The point of the spike is feel, so the page is designed rather than defaulted: the system's UI face at 13 px with tabular figures, monospace only where the text is data; an 8 px spacing scale with a 4 px half step; one accent on a near-black ground, borders a step lighter than the panels; a visible focus ring on everything focusable; a hover and an active state on every control; splits between the panels that highlight under the pointer, drag smoothly, move with the arrow keys and are remembered; axis labels coloured x red, y green, z blue in the vector editors; a pulse on the connection pill while it waits; and `prefers-reduced-motion` honoured. No component library, no framework, nothing generated: about 2,700 lines with the stylesheet, which a reader can follow.

**No bundler, no package manager, no CDN, nothing fetched at run time** but what the host it came from answers. The page opens offline from the host's listener, and the build only copies the files (`apps/engine_host/CMakeLists.txt`, into `build/<preset>/shell/`); an edited file is served on the next reload because every response says `Cache-Control: no-store`.

## Files

`index.html` (the layout), `shell.css` (the one stylesheet), `main.js` (the connection, the session, the selection, and "after a change, ask again"), `rpc.js` (JSON-RPC over the WebSocket, reconnecting, and notifications), `dom.js` (element and storage helpers, the JSON colouring), `splits.js`, `viewport.js` (the slideshow), `embedded.js` (the empty cell, `editor.layout` and `editor.relayout`), `layout.js` (the narrow layout), `testhook.js` (the test hook, loaded only with `?embedded=1&test=1`), `outliner.js`, `properties.js`, `journal.js`, `console.js`. engine-editor depends on the same copy step (`engine_shell_files`) and serves the files from `<bin>/../shell`.

## Testing

The shell is tested through its clients, not in a browser. The windows that load it are engine-editor's embedded tests, small and throttled: the page, served by the editor's listener, must send an `editor.layout` that places the native viewport; resized from 1280 × 720 to 800 × 600 its layouts must keep the viewport inside the window, narrow exactly when the page is under 960 CSS pixels; and with the test hook its popups must stay in their panels, it must answer `editor.relayout`, and after the editor shuts its socket it must show the pill and reconnect while the viewport goes on drawing (each skipped with the reason where the WebView2 runtime is absent); the methods themselves are tested through the editor's dispatcher with no web view ([apps](apps.md#engine-editor-the-engines-window-on-a-document)). `apps/engine_host/tests/transport_tests.cpp` checks that the listener serves `index.html` and the stylesheet and nothing outside the directory, and every protocol path the page uses: `render.load {session}`, the kept capture and its ids over HTTP, `records`, the reported camera given back, the move in place and the rebuild. `tools/host-ws.Tests.ps1` fetches the page with .NET's HTTP client. The events the page relies on are tested at the host ([protocol](protocol.md#events)): the journal's for another connection's commit, undo and redo, the scene's after a move and a rebuild, the editor's selection for `editor.select` and a pick; `tools/mcp-check.ps1 -Connect` times one from an agent's edit to a second client. The modules are checked to parse (`node --check`) by whoever changes them; a person opens the page to judge it.

## The review queue (designed, not built)

**Designed 2026-11-18; nothing in this section exists yet.** It is roadmap A24's remainder and plan 06 §6.10's human director surface: the place where a person meets the work agents leave for one — review items, proposal layers waiting for promotion, and tasks — and decides. It reads the task ledger (A23, [protocol](protocol.md#the-task-ledger-and-review-items)) and stands on three decisions taken the same day, not all in this tree yet:

- **A role marked `human` is conferred only by a connection's credential or by the host's own start line, never by a call naming the role in its attribution.** Not built: the ledger's check today reads the role a call runs in (`caller.role->human`), which a call may name.
- **A connection over a listener is who its credential says**, and the shell's own connection is the operator's, by a cookie a one-time ticket bought (roadmap A4; its decision record is not in this tree yet).
- **A client names a file only inside roots the operator named** (roadmap T174, not in this roadmap yet), and **the shell never names a path at all** — *recommended, not decided*; the queue below is designed so that it never needs one.

The classified item is where a person meets the refusals of content classes and view policies (roadmap C3 and A26, their build rows C61 to C66: designed, with a decision record of their own, not in this tree yet). The build is seven rows, numbered "new row 1" to "new row 7" until they have roadmap ids ([below](#the-build-in-rows)).

### Who the person at the editor is

engine-editor loads no roles file, so today nobody at its shell can close a person's item, and nothing about the shell's connection says a person is behind it: the printed `shell` address and the operator's token are on the host's stdout, which whoever started the editor reads — sometimes an agent. **So the person is the editor's own page, and only that page: a *seat*, a connection the editor gives its own web view.** The operator types:

```
engine-editor --doc ./world --roles content/roles/roles.json --person marc
```

- **`--person <name>`** says who sits at this window. It needs **`--roles`**: the editor loads that roles file (beside A4's credentials, which then bind to the roles it defines), and the seat is given the file's one role marked `human` — `reviewer` in the shipped file — or the one `--person-role <role>` names where a file marks several. The start is refused, exit 2 with the reason, with no roles file, when the file marks no role human, when `--person-role` names a role not marked human, and when `--actor` names somebody else. Without `--person` nothing changes: there is no seat, and the queue says nobody at this editor may close a person's item.
- **How the seat is made.** The editor asks its in-process listener for a **seat ticket** (`Listener::seat_url()`, beside A4's `shell_url()`) and puts it in its own web view's navigation: never printed, never written, never in the announcement. Spending it buys a cookie as A4's tickets do, of a second kind; the socket that carries it is the seat. The printed `shell` address stays the operator's. **One seat connection at a time**: a second socket presenting the seat's cookie while the first is open is refused (1008, reason `seat in use`) and logged by connection number, never by the cookie. Each page the editor loads gets a new seat ticket, and spending it retires the previous seat cookie; a reconnect carries the cookie the page has.
- **The seat holds two roles, for two kinds of call.** Its *working role* is the editor's own (`director`, as A37 has it), so the properties, the journal's undo and the queue's promotions behave as the page's edits do today, attributed to the person. Its **conferred human role** is read only by the checks that ask for a person: `review.close` of a `Human` item, the human half of `task.update` (new row 3), lowering a record's content class (C63), and `editor.look` (new row 7). No call reaches it by naming a role: `reviewer` named in an attribution, on the seat or on any other connection, only makes that call run as `reviewer`, which may change no document, and confers nothing. In code this is the human-role change's own shape: the caller carries the conferred role apart from the role it runs in, set by the dispatcher from the connection — a credential whose role is marked human, or, for stdio, the host's start line — and the seat is one more source of it.
- **Who does not get it**: the operator's printed token and every page opened from the printed address; a connection that presented a credential, unless the operator issued that credential a human role, which an agent is never issued; engine-mcp attached with `--connect-from` or `--token-file`, which is one of those two; and the editor's native viewport, whose gestures are the editor's own calls (the one native act a decision needs, the look, is the seat's call).
- **Why not engine-host.** A browser tab is opened from an address that whoever read the host's stdout holds too, so a browser against engine-host is never a seat. The queue there reads everything and offers every action on agents' items, proposals and tasks that the connection's role allows; a person's item says it is closed at an editor started with `--person`.
- **What the ledger records**: the closer's attribution as now, plus how the human role was conferred (`ReviewInfo.closed_via`: `seat`, `credential <name>` or `start line`) and the document's version the person decided at.
- **What this is not**: a wall against a process of the same user that reads the web view's profile while the editor runs — the limit A4 states of the printed token and ADR-0033 decision 4 of view policies. Against that, a guard rail and an audit trail: the web view is pinned to its listener's origin (a navigation elsewhere and a new window are refused, so the page that holds the cookie sends it nowhere else), the refused second seat is logged, and an agent that starts an editor with `--person` on anything but a test's scratch document breaks AGENTS.md's rule as one that edits a view policy does.

### What the queue lists, and how it stays current

**A tab beside the journal**, "Queue", in the same place in both layouts (the narrow layout's drawer holds both tabs), with a count of open items for a person on the tab and in the title bar. Four sections, each from one read:

| Section | Read | Shown first |
|---|---|---|
| For a person | `review.list {state: Open, audience: Human, brief: true, drift: true}` | oldest first: a person's items wait |
| For agents | `review.list {state: Open, audience: Agent, brief: true, drift: true}` | newest first |
| Proposals waiting | `doc.layers`, the layers whose `proposal.state` is Open with `touched` above zero | oldest first |
| Tasks | `task.list {statuses: [Open, Claimed, Blocked], brief: true}` | Blocked, then Open, then Claimed |

A toggle shows the closed ones (`state: Closed`, and Done and Dropped tasks), the newest fifty.

**No poll where an event exists.** The page already subscribes to `session` events; the ledger's changes (`task_created`, `task_claimed`, `task_updated`, `review_raised`, `review_closed`) name an id, and the page reads that one task or item again (`task.list {task}`, `review.list {review, drift: true}`), never the list. Two kinds of change publish no event today and get one (`SessionChangeEvent` version 4, new row 3): a proposal opened, promoted, rejected or reopened (`proposal_*`, with the layer, from the proposals' methods after `proposals.json` is written), which re-reads `doc.layers`; and **`ledger_changed`**, for a ledger another process wrote (engine-cli's host per call, a second host on the document): the ledger gains a revision that every write raises, the host looks at the file a second after the last change it saw (its time as a hint to look, the revision as the decision) and publishes the change when the revision moved, and the page reads its three lists again. An `event.journal` moves the drift of the items whose subject it names, from its ids, with no call; an open item reads its drift again. An event with `dropped` reads everything again. Only with no subscription does the page fall back to today's ten-second look, which then reads the four lists too.

**One row** shows numbers, names and identities, and never a picture, a capture, a thumbnail, a property value of the subject or a URL:

- *An item*: its kind and audience, its id, its summary on one line, who raised it — actor, role, and whether by a credential, the operator's connection or the host itself (C66) — and when, the subject as counts (records, blobs, assets, the layer), the task it is for as its key, and its drift: "at the current version", or "7 transactions since, 2 touch it".
- *A proposal*: the layer and its target, its owner and the owner's role, the task, how many target records it touched, when it was opened, and its rationale.
- *A task*: its key, title, status, the role it is for, its claimant and when the claim lapses, and how many review items and links it has.

The summary, a rationale, a title, a goal, a note and a client's name are **other clients' words**: shown as text, clipped, and always beside whose words they are ([below](#what-another-clients-content-cannot-do)).

**Opening a row.** An item's detail has its whole summary, its report as JSON text, its history and its subject. The subject is **selected**: `editor.select` of its first live record embedded, so the native viewport outlines it and the properties show it, or the slideshow's selection in a browser; the subject's other records are listed, each a button that selects it, and records no longer live are named as gone. Then **the version, plainly**, from `review.list`'s drift (new row 3), which the host computes from the session's journal against the version it stamped:

- the same version: "This is the document as it was when the item was raised."
- moved on: "Raised at journal 412. The document is now at 419: 7 transactions since, 2 of them touch these records. What you see is the document now." With an undo below the stamp: "3 of the transactions it was raised after have been undone." With records gone: "2 of its 5 records have been deleted since." With a checkpoint on the item: "Checkpoint `<id>` holds the version it was raised at."

The viewport shows the document as it stands, never an older version. A proposal's row selects nothing until a record of its list is chosen (new row 6); a task's links select what they name — a proposal its row, a record the record, a review item its row — and name the rest (leases, transactions, checkpoints) by id.

### The actions, and what a refusal shows

Every action is one button that sends one method, and **the host decides**: the page shows a button it expects to be refused as disabled with the reason beside it, and shows a refusal it did not expect in the row, in words, with the method's message under them.

| Action | Method | Refused when, and what the row says |
|---|---|---|
| Accept, Reject | `review.close {review, resolution, note, seen_history}` | a person's item from a connection with no human role (1008 `human review`): "Only a person closes this, at an editor started with --person; this connection is not one." The item changed since it was drawn (new row 3's `seen_history`, 1004): "This item changed since you read it", and the row is drawn again with what changed marked |

**No action is anybody else's to start.** What another client can make the page do is limited to what it is shown:

### What another client's content cannot do

- **Rendered as text, never as markup.** Every string another client wrote — a summary, a note, a rationale, a title, a goal, an acceptance criterion, a report's strings, an actor's or a hello's name, a record's name — goes on the page through `dom.js`'s `h()`, which makes text nodes. No module of the shell assigns `innerHTML`, `outerHTML` or `insertAdjacentHTML`, or calls `document.write`, `eval`, `Function`, a timer with a string, or `import()` with anything but a literal: a lint rule (`shell-html-sink`, new row 1) holds every file of `apps/engine_shell/` to it, as `tools/lint.ps1` holds engine code to its rules. A report is shown by `prettyJson`, as text.
- **Never an attribute.** No `href`, `src`, `style`, `class`, `id` or `data-` is set from another client's string; a link inside the queue is a button whose target is an id the page parsed itself (a number, an id128), never a URL. So a summary that is a `javascript:` URL, an `<img onerror>` or a stylesheet is a line of text.
- **Nothing is evaluated, and nothing is fetched**, beyond what the page already does: the listener serves the shell with a content security policy (`default-src 'self'; script-src 'self'; style-src 'self'; img-src 'self' blob:; connect-src 'self'; object-src 'none'; base-uri 'none'; form-action 'none'; frame-ancestors 'none'`, new row 1), so even a mistake in the page could not run a script or load an image from elsewhere.
- **Only a click on a button the page drew writes.** No event, notification, row, report field or note triggers a call that changes anything, and nothing confirms itself after a delay. The id a button acts on is the one its row was drawn for; the selection is not it, so an agent's `editor.select` moves the outliner's highlight and never what Accept accepts. Before a close the page reads the item again and sends the length of the history it showed (`seen_history`), so a note slipped in while the person read is refused by the host and drawn, not decided past.
- **Whose words they are is the host's, not the text's.** The raiser, its role and how it connected come from the ledger's attribution, which the host fills from the connection, and are drawn beside the words in another style; a summary that says "approved by Marc" reads as the agent's sentence it is.
- **The command line stays the person's**: the queue never fills it, and nothing in a row is a request to run.

### A classified item

A `classified content review` item (C66) is raised by the host when a capture, a load, a compare or a blob read was refused above the caller's view policy, and carries numbers, never a picture.

**Before the person chooses to look**, the row and its detail show exactly what the item carries: the kind and the Person badge; the category, the level found, the cap and the policy that refused it (from the report's schema type, which C66 defines, so the page reads it as it reads any protocol type); the subject's identity — records by name, type and id, assets by their root's name and their path under it (T174's portable names, never a path of the machine), each asset's source hash, build key and content hash; the version it was stamped with and the drift since; who was refused, by which method, over which kind of connection; and the validator numbers. Nothing else: there is no image anywhere in the queue, and the page never asks for one.

**Looking happens on the person's own editor, in its native window, and nowhere else.**

- *Recommended, not decided*: **the editor's viewport rests held.** It draws under the narrower of `agent-default` and the editor's own `--view-policy` (C65), so a person who started an editor wide enough to review sees nothing classified until they choose to: the subject is the proxy box or nothing, as an agent's capture would be. The alternative is a viewport drawing at the editor's policy from the start, with Look only selecting.
- **Look** (embedded, on the seat only) sends `editor.look {review}`: the editor re-instantiates **the subject's placements alone** under its own `--view-policy` (C64's per-placement policy), selects and frames them, and says "Looking" in the viewport's corner; everything else stays at rest. It ends at **Hold** (`editor.look {review, end: true}`), when the item is closed, when the editor's window stops being the foreground window or the session locks (`window::desktop_state()`), and at exit.
- Refused with 1008 (`seat`) to every connection but the seat, with -32601 on engine-host (it is the editor's method), and with 1011 when the editor's own policy does not cover the subject: "This editor may draw <category> up to <cap>; the subject is <level>. A person looks at it in an editor started with a view policy that covers it; nothing in this window widens one."
- **Never through an agent's session**: the picture exists only in the native child window — the editor registers no `render.capture`, so no frame of its viewport reaches any connection, the page's included; an agent attached to the same editor runs under its credential's policy (C65) and sees what the page showed before the look, the numbers.

**What the item records**: a history line `looked` — the person, the human role, when, the policy name, the version and how many placements were widened — and `held` with how long the look lasted; then the close with `closed_via` and the version decided at. Accept on an item the person has not looked at asks once ("Accept without looking?") and its note says so. The ledger never holds the picture; closing changes no class and no policy (C66).

### How it is tested, without a person and without a browser

The guarantees are the host's, so they are tested where the shell's protocol paths are tested today, through clients that are not a browser; the page's own behaviour is tested by the editor's test hook in its web view, made to run with no GPU.

- **The seat and the human role, CPU only** (new row 2). `domain/protocol/tests/listener_tests.cpp` over a loopback listener in process: a seat ticket made in process and spent once, its cookie's socket reported by `client.hello` as the seat with the human role; the operator's printed ticket's socket, a credential's socket in a role not marked human, and a call on either naming `reviewer`, each refused closing a person's item (1008 `human review`) over a ledger fixture the test raises through the dispatcher; the seat closing it, `closed_via` `seat`; a second socket with the seat's cookie refused while the first is open and accepted after it closes. `apps/engine_editor/tests/editor_tests.cpp`, no window: `--person` refused without `--roles`, with a file marking no role human, with a `--person-role` not marked human and beside a different `--actor`; through the editor's dispatcher, the seat's edit attributed to the person in the editor's role.
- **The ledger's additions, CPU only** (new row 3). `domain/protocol/tests/ledger_tests.cpp`: `review.note` on both audiences; `task.update` version 2 reassigning by the creator and by a person, refused to a third actor; `review.list`'s drift after commits, an undo below the stamp and a deleted record; `seen_history` refusing a close after a note; `ledger_changed` published to a subscriber when a second session manager on the same directory writes; the proposals' events. `apps/engine_cli/tests/policy_tests.cpp`: an item raised by an engine-cli process reaches a subscriber of `engine-host --listen` as `ledger_changed`.
- **The page's floor, no browser** (new row 1). `listener_tests.cpp`: the shell's files are served with the content security policy, and nothing else is. `tools/lint.Tests.ps1`: `shell-html-sink` refuses each sink in a scratch module and allows `h()` and `textContent`.
- **The page itself** (new rows 4 to 7), in engine-editor's web view through the test hook ([above](#the-test-hook)), against a document the test makes in its `TempDir` and fills through a second in-process connection — a task, an agent's item, a person's item whose summary is `<img src=x onerror=alert(1)>` and whose note is a `javascript:` URL, a proposal with a conflict, and (new row 7) a classified item — so nothing is committed as a fixture. New row 4 makes `engine-editor --embedded --test-page --no-viewport` run the page with no device and no GPU lock, so these run wherever WebView2 is, without a GPU. The hook's new checks: **"queue"** (each section's row count is the reads' count; the hostile summary's text is the fixture's string and the queue holds no `img`, `a`, `script`, `iframe` or `object` element), **"queue-event"** (an item raised mid-run is drawn within a second, after exactly one `review.list` for its id), **"queue-close"** (Accept on the person's item closes it, `closed_via` `seat`), **"queue-refused"** (a page with no seat shows Accept disabled with its reason, and the call forced through the hook is refused and drawn in the row), **"proposals"** (a dry run's numbers, a refused promotion's conflicts drawn, then promoted with `prefer`), **"classified"** (numbers only, no image element in the page, Look refused 1011 under a policy that does not cover it). What the page sent is asserted from the editor's side: the summary gains `seat_requests`, each method the seat called and how often, so a check also proves the page wrote nothing it was not asked to.
- **The picture of a look** (new row 7): the subject drawn as the proxy at rest and as itself after `editor.look`, a capture of the editor's offscreen viewport — the one case that needs a device.

**What needs a person, once** (the owner, after new row 5, and again after new row 7):

1. Start an editor with `--person` on a scratch copy of a document; raise from engine-cli an agent's item, a person's item and a task; see each row appear without touching the page.
2. Accept, reject and note them; reload the page (F5) and accept another: the seat survives a reload.
3. From engine-cli, and from an engine-mcp attached to the editor, try to close the person's item naming `reviewer`: both refused. Open the printed `shell` address in a browser: the queue is there, and the person's item cannot be closed from it.
4. Start the editor without `--person`: the queue reads, and says why nothing for a person can be decided.
5. Promote a proposal with a conflict from the queue; reassign a task and claim another.
6. With content classes built: raise a classified item by a refused capture, read its numbers, Look, Hold, then accept; check what the item's history says.
7. Judge the feel: whether the rows say enough to decide without opening them, and whether the version statement reads plainly.

## Not yet

- **A live viewport in a browser.** In a browser tab each picture is a `render.capture` — a frame drawn offscreen, read back, encoded as a PNG and fetched over HTTP — which is a slideshow, not a view, however fast the GPU; the time each one took is in the viewport's corner. The live one is engine-editor's native viewport beside the embedded page ([above](#embedded-in-the-editor)).
- **Selection in the picture.** A selected record is not outlined in the viewport (engine-editor draws its box); the shell would need the host to draw it, which is a capture option nobody has asked for yet.
- **A gizmo, multi-select, create and delete**, a layer picker, and leases in the UI. Each is a protocol call away; none is built. The review queue and the proposals' view are designed and not built ([below](#the-review-queue-designed-not-built)).
- **The bulk channel** instead of HTTP GETs of kept captures (roadmap A2's remaining half).
- **A layout narrower still.** Under about 400 CSS pixels the two columns' minimums (180 and 160) no longer fit either; nothing here opens a window that small. (The spike's two blemishes in the browser form are fixed: the "Connecting…" placeholder stayed drawn over every capture because its `display: grid` beat the `hidden` attribute, which a global `[hidden]` rule now settles; and the slideshow notice fades for good a few seconds after the first picture instead of sitting over every one.)
