# content_build (domain)

G87 extends the shared GeneratorHosts image callback used by flora: recipe-relative base-colour images are read as encoded bytes for both source hashing and CPU LOD baking. The command-line flora build and renderer-generated trees therefore share material colour, alpha and cache invalidation behavior. Image decode failures are build errors; see [flora](flora.md#the-impostor-chain).


**Purpose.** The content build as a library ([07 §7.3](../plan/07-content-pipeline.md#73-content-build-the-derived-data-graph)): import a glTF or GLB file, validate it against [§7.4](../plan/07-content-pipeline.md#74-validation-rules-automatic)'s rules, drop its zero-area triangles and repair its UV-degenerate islands, optionally repack its atlas, weld it, build one cluster LOD DAG per primitive on the job system's performance pool, merge them in primitive order, lay them out in streaming pages, and write the `.clusters` container with its materials, its images, their texture records and the source's identity; the same over a manifest of meshes, one job per mesh, skipping an entry whose output already records this source and these options; the texture step that builds every image a mesh samples into a `.tex` under the derived-data root ([texture](texture.md)); the orchestration of the derived steps capabilities supply — the audio capability's `.clip` is the first ("Derived steps" below); and the content-build metrics of a built container. It has two hosts: `engine-content` (`build`, `build-all`, `stats`) and engine-host's `content.build` ([protocol](protocol.md#the-day-one-operations)); the one other module that links it is `systems/renderer`, for the texture step, the generator hosts and the load's table of its source images: a load through the derived-data cache runs `run_texture_step` once, over whatever of its meshes' textures is missing, so the renderer's cache fill builds the same `.tex` files engine-content does ([renderer](renderer.md#what-the-load-reads)).

**Why it is a module and not a file in an app.** Until 2026-09-24 all of this was `apps/engine_content/main.cpp` (the texture step included, which landed there the same day and moved with the rest), which was right while one program ran the build. When engine-host needed to run it too ([06 §6.9](../plan/06-agent-tooling.md#69-day-one-operations)'s `build_content`), the choice was a second copy or one library, and a second copy of a build is not the same build for long: the bytes a container holds, its cache key and the rule that skips it are exactly what two hosts must agree on byte for byte, which is the reason `geometry::cluster_cache_key` already lives in a module that engine-content and engine-view share. **It cannot live in `domain/geometry` or `domain/assets`**, which is where the minimal piece would otherwise go: the build calls the atlas step (`domain/atlas`), which depends on both, and the texture step (`domain/texture`), so the orchestration has to sit one step above them all. The code moved **unchanged** — the same function bodies, the same log category (`content`, so `--log content=debug` reaches it from either host), the same order of work — and engine-content kept everything that is the command line's: the flags, the usage, the stderr lines, and the shape and key order of its JSON lines. The proof is engine-content's own suite, which passed without an edit, including `determinism_tests.cpp`'s section hashes pinned on MSVC.

**Owned data.** Nothing persistent. A build's inputs are a source file and a `MeshOptions`; its output is a container on disk and a `BuildResult` in memory. The cache's rules (`geometry::cluster_cache_key`/`cluster_cache_path`/`find_ddc_root`) stay in `domain/geometry`, where engine-view reads them too.

**What moved, and what is new.**
- `MeshOptions` and `build_key_of` — the cache key of `geometry::cluster_cache_key` moved by the two steps outside the geometry (`--no-morph` and `--atlas repack`), each only when asked for; `lod_options_of`, `options_in_range`, and the spellings `read_seam_rule`, `read_atlas_mode`, `read_normal_map_mode`.
- The rule ids (`geometry.empty_primitive` … `atlas.repack`) as constants, `Diagnostic`, and `k_max_clusters`.
- `build_one`: one mesh, always built. `BuildResult` is what engine-content's build line reports, with the `TextureSource`s the texture step builds for it (`collect_texture_sources`, after `texture::fill_cluster_texture_records`).
- `repairs_json` and `atlas_json`: the `repairs` array and the `atlas` object of a build's line, so both hosts report a build in the same words. **New (G57):** the array's first row is the zero-area repair's (`geometry.zero_area`, `BuildResult::zero_area_repair`), which runs after validation and before the UV repair ([geometry](geometry.md#zero-area-triangles-the-repair)); `geometry.degenerate_triangle` now refuses only what it does not cover — a repeated index, reported after the repair so its sentence can say what the repair removed, and a primitive with no area left at all.
- `ManifestEntry` and `read_manifest`: paths resolved against the manifest's own directory.
- `MeshTask`, `run_mesh_task` and `run_mesh_tasks`: the identity skip — a container that records this source's hash and this build key is the answer already; one that records none is rebuilt rather than trusted — and one job per mesh. **New:** `MeshTask::force`, which rebuilds regardless (engine-content's `build-all` never sets it; the protocol's `content.build` does when asked), and `MeshTask::pool`, which lets a single mesh run on its own hand its primitives to the pool, as `engine-content build` does, where a manifest leaves it null.
- The texture step: `run_texture_step` (keys taken in order on the calling thread, a key met earlier `shared`, an entry that records its identity `skipped`, the rest one job each), `textures_json`, `texture_sources_of_container` for a mesh a manifest skipped, `TextureResult`/`TextureState` and the `texture.*` rule ids. engine-content prints its failures on stderr; engine-host logs them.
- **New (W75):** `TextureSource::view` (bytes the caller holds, built without a copy) and `TextureSource::source_hash` (the caller hashed exactly these bytes, so the step does not again); `ImageIdentities` and `pack_index_path` (image_identities.h, below); `GeneratorHosts::set_identities` and the hosts' `hash_image` hook.
- `container_stats`, `load_container`, `page_summary` (container_stats.h): the object `engine-content stats` prints, and the tables it prints for a person returned as a string in the order it prints them, so a host with no person to show them to drops them.

## One hash per image, and a pack's from its manifest

**A load knows each of its source images once** (`ImageIdentities`, image_identities.h; since 2026-10-24, roadmap W75). A built texture is addressed by the hash of its image's encoded bytes, so finding one for an image a container names by path takes that hash, and until W75 every reader took it by reading the file: the renderer's texture step once per mesh that named the image (and a job pool made and joined per mesh to do it), the GPU upload again, a baked tree's source hash a third time — 2.7 GB of the forest's 4.4 GB read before ready ([startup trace](../experiments/startup-trace-forest-2026-10-24.md)). The table is one per load, shared by the per-mesh loads on the job system, the generator hosts (`GeneratorHosts::set_identities`, whose `hash_image` hook a generator that only hashes an image asks first — flora's baked base colours) and the texture pass:

- **A file is read and hashed at most once a load.** The first reader hashes it; a second asking meanwhile waits for that answer rather than reading the file again.
- **A material pack's file is not read at all once it has been hashed under that pack.** A pack is fetched and verified as a unit against its `pack.json`, which pins every map by its SHA-256 ([materials](materials.md#a-pack)), and `materials::Pack::hash` is over that text, so a file the pack names has the same bytes for as long as the pack has the same hash. The hash those bytes give is therefore derived data: `<ddc>/textures/packs/<pack hash>.json` (`engine.texture.pack_identities` version 1: the pack's hash and, sorted by path, each file's `hash_bytes` and size), written when a load hashed a pack file the index did not hold. Only a file the pack names now is answered from it. A pack edited in place without its manifest is not a pack: the one reader that reads such a file anyway — a build of its missing texture — compares the bytes with the index, says so (`a pack file changed without its manifest`), and builds under the key the bytes give.
- **Every other file is hashed as it is now**, once a load: a glTF's sibling PNG and a recipe's own set are covered by nothing the load reads, so a repainted one still finds its new texture ([texture](texture.md#trusted-not-read)).

Why an index beside the derived data and not a key in the container: a container's identity is its source's (`assets::source_mesh_hash`, a recipe's canonical parameters), and an image named by path is outside it on purpose (geometry.md, section 32), so a key recorded at build would go stale under an unchanged container key; the pack's own hash is what covers a pack file, so the index is keyed by it, needs no container to be rebuilt (no `k_cluster_cache_version` move, the owner's cooked caches kept), and is shared by every mesh built with the pack. Nothing decides from a timestamp.
## Derived steps

**A capability's precomputed content attaches here as a table, not a link.** [ADR-0027](../adr/0027-additive-capabilities.md) names "a `derived` content-build step" as one of the points a capability plugs into; the audio capability's `.clip` — a clip decoded once into the mix format ([audio](audio.md#built-clips)) — is the first. It cannot be linked into this module: the module is not a capability and must build, and build the same containers, with every capability off (`msvc-minimal`), and a capability is declared after it (`audio` needs `protocol`, which comes after this module). Linking it anyway would also have pulled the audio module, whole-archive, and miniaudio into every binary that links this one — engine-view among them — for a step engine-view never runs. So the module holds the **orchestration** and the capability supplies the **work**, as a `DerivedStep`: its name, the manifest array its entries live in, which command-line sources it takes, its build key over a source's hash, its cache path, how to read what an output records, and the build itself. A host that has the capability hands the table over: engine-content does (`apps/engine_content/clip_commands.cpp`, compiled with `ENGINE_CONTENT_AUDIO` where the configuration has audio); engine-host's `content.build` does not yet.

**A tile set is not a derived step** (2026-10-17, [tileset](tileset.md)): `engine-content terrain-tiles` builds an authored heightfield's set into the cache under the same rules — a key over the source header's bytes (which record its grid's hash), the options and `k_tileset_version`, an output that records its key skipped, never a timestamp — but on its own, because `DerivedStep::build` is handed the source's bytes and no path, and a heightfield's header names the grid beside it, and because its output is a directory of files (a manifest and an archive a level, since W76) rather than one file. `build-all` would list one once a step can be handed its source's path and write a directory.

### terrain-masks: ground materials by place

**A mask level is not a derived step either, for the same reasons** (2026-10-24, W72; [tileset](tileset.md#the-mask-level)): `engine-content terrain-masks <scene.json> [<out dir>] [--ddc <root>] [--force] [--write-priors <dir>]` reads a scene file, resolves its terrain's `masks` block (images against the scene's directory, water bodies by name against its `water`), opens or builds the set its `tiles` block names, and builds the level into `<out dir>` or `<ddc>/tilemasks/<key>/`. The key is the set's hash, the inputs as canonical JSON with every image named by its bytes' hash rather than its path, the palette's names, the per-tile budget, the map frame and `k_mask_version` — an output that records its key is skipped, never a timestamp — and the `tiles` provider builds the same level under the same key on a miss, so the step and a viewer's first load agree. Its output is the same bytes on every toolchain (integers, f64 polynomials and square roots only; `tests/mask_tests.cpp` pins a hash). It prints one JSON line (`engine.tileset.MaskLevelReport`); `--write-priors` also writes the generated priors as one greyscale PNG per role for an author to edit and give back as a `paint` entry. A tile whose points name more palette layers than the budget fails the step (exit 1) with the sentence that names it. Measured on the 1 km test scene (`content/test-scenes/ground-by-place`, `msvc-debug`, the shared desktop): 1,089 tiles, 8.2 MB, 26 s — the region distances and the priors' four height reads a point dominate, linear in points.

**A generated mesh is not a derived step.** The flora capability's palms ([flora](flora.md#the-build)) are built by `engine-content flora` and, inside a scene, by the renderer through the mesh-generator registry ([assets](assets.md#generated-meshes)), not through this table: a derived step's output is something other than a container (a `.clip`), while a palm's is a `.clusters` container that must be the same bytes whichever host built it, so the capability builds the whole container itself and both hosts call that one function. **It is a mesh to `build_one`, though** (since G62): a source named `<name>.<generator>.json` — a palm, a rock ([rocks](rocks.md#the-build)) — is built by its generator from the registry instead of imported, keyed as the scene reader keys it (`source_hash_of` is the generator's hash of the canonical parameters, `mesh_build_key` is `assets::generated_mesh_build_key(hash, inputs, LOD options, page target)` — `cluster_cache_key` with no weld, and the material pack's key when `MeshOptions::materials` names a pack with roles ([materials](materials.md)), without the morph and atlas steps a glTF's key carries; `engine-content build` and `build-all` set that pack to the repository's `content/materials` for a generated mesh, as `engine-content flora` and the renderer do), so `engine-content build` and a `build-all` manifest's `meshes` take recipes beside glTF files and write the entry the renderer reads. The import, the validation, the repairs, the weld and the atlas are the glTF path's and do not apply; the texture step does: a generated container's texture records name the images its parts' material sets sample, and `build_generated` hands them to the host's texture step as a glTF build's sources are. The generator's own identity must match the one hashed, or the build fails rather than writing a container under a key it was not built for. Why here rather than a derived step: a derived step keys its source by `hash_bytes` of the file as read, and a recipe's key is its canonical parameters, so two spellings of one rock would have been two entries and neither the renderer's.

**A tree's impostor bake is the generator's, not a step** (R89, 2026-10-21; [flora](flora.md#the-impostor-chain)). The branch-group cards' and the whole-tree star's atlases are drawn on the CPU by the flora capability inside its own container build and embedded in the container as PNG (sections 21 and 22), with the chain's levels recorded in **section 38** (`ClusterFileImpostor`, append-only and written only for a tree that has a chain), so they are keyed by the recipe's canonical parameters with the rest of the container, are the same bytes from every host and toolchain, and reach the texture step as any embedded image does. A separate derived step would have needed the solver's finest geometry as its source, which is not a file, and would have keyed one tree's atlases apart from the container that samples them.

**The rules are the meshes' rules.** `run_derived_task` reads the source, takes its identity as `hash_bytes` over the bytes as read — the convention every derived node starts from, so the clip store computes the same key from the same bytes — asks the step for the key and the path (the cache's for an entry with no output, whose directory it makes), and **skips the entry when the output already records that same source hash and that same key**; a zero key is never a match, and nothing is decided from a timestamp. Otherwise it builds, timing it, and reads the output's size back. `run_derived_tasks` runs one job per entry on the performance pool; results are read in manifest order. `read_derived_entries` reads the step's array — `{"source","output"}` objects, paths resolved against the manifest's own directory — where an absent array is no entries; `read_manifest` takes the names of the steps' arrays so that a manifest of nothing but clips (no `"meshes"`) is not refused. The two failures have rule ids: `source.unreadable` and `derived.build`.

**Invariants.**
- The bytes a build writes depend neither on the thread count nor on the toolchain ([geometry](geometry.md#the-same-bytes-from-every-toolchain)): the per-primitive DAGs merge in primitive order, never completion order, and a manifest's tasks are read back in manifest order.
- An incremental build never decides from a timestamp. A skip needs the container's recorded source hash and build key to equal the ones this source and these options give, and a zero key is never a match.
- A derived step's output is skipped only when it records the source hash and the build key this source gives, and its key is a function of the source's bytes and the step's options and version, never of a path or the machine.
- The module links no capability; a derived step is a table a host hands it.
- `protocol::ContentBuildOptions` states the defaults `MeshOptions` has. The protocol could not use `MeshOptions` itself (it is a C++ struct, not a schema type), so the IDL repeats the numbers, and this module's test is what holds the two together.

**Public API.** `domain/content_build/content_build.h` (the build, the manifest, the tasks, and the derived steps: `DerivedStep`, `DerivedEntry`, `read_derived_entries`, `DerivedTask`, `run_derived_task`, `run_derived_tasks`, `k_rule_derived_build`, `k_rule_source_unreadable`), `domain/content_build/container_stats.h` (the metrics and the container reader), `domain/content_build/generator_hosts.h` (`GeneratorHosts`: the host seam of `assets::MeshGeneratorInputs` — a vine's or a cover's host read by the path its recipe gives, a generated mesh built in memory under the dependant's options, a `.clusters` read, a glTF imported, at most `k_host_depth` levels of hosts deep — which `build_generated`, `source_hash_of`, engine-content's `vine` and `cover` and the renderer's scene reader all use, so every host app reads a host the same way; [cover](cover.md#the-host)).

**Depends on.** `base`, `containers`, `math`, `hash`, `time`, `jobs`, `log`, `io`, `json`, `geometry`, `materials`, `assets`, `atlas`, `texture`.

**Testing.** `tools/dev.ps1 test -Filter content_build` runs `tests/image_identities_tests.cpp` — a file read and hashed once however often it is asked for and a missing one said once; a pack's file answered from its index by the next table with no read, a file the pack does not name read, another pack's index its own, and a pack file edited without its manifest answered from the index until a read catches it and the bytes' hash taken from then on; the hosts' `hash_image` the same number from the table as from the bytes — and `tests/content_build_tests.cpp`: the build key moving with `--no-morph` and `--atlas repack` and with a repack's own options, and not with a kept atlas's; the spellings, with a refusal leaving the output untouched; a manifest resolved against its own directory, an entry's options overriding the defaults and the rest keeping them, and six malformed manifests refused with a sentence naming the manifest; a 16×16 grid written as a `.gltf` and `.bin` at test time, built on a two-worker pool, skipped on a second run with the same key and bytes, rebuilt by `force` to the same content hash, its metrics read back by `container_stats` (the cluster count, the triangles-per-cluster object, the bytes, and the streaming sweep's table in the text for a person), and a missing source failing with `source.unreadable`; and `protocol::ContentBuildOptions`' every default equal to `MeshOptions`'; and a stand-in derived step (it writes a source's bytes behind the identity it is given) over a manifest of nothing but its array — the entries resolved, the output cached or named, a second run skipping both, `force` rebuilding, a changed source a new key and a new entry, a source the step refuses failing `derived.build` and a missing one `source.unreadable`, and an array that is not one refused with a sentence naming the manifest. The audio step itself is held to the same rules end to end by engine-content's `tests/clip_tests.cpp`. The command line's end-to-end suite is `-Filter engine_content` ([apps](apps.md)), and the protocol's is `apps/engine_cli/tests/ops_tests.cpp` (`-Filter engine_cli`).

**Performance notes.** The build's own numbers are engine-content's and are in [apps](apps.md) ("engine-content"); moving the code into a library changed none of them. A second host adds one cost of its own: `content.build` makes a job system per call, which is a few milliseconds of thread start-up against builds that take tens to hundreds.
