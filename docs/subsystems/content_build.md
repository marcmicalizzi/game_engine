# content_build (domain)

**Purpose.** The content build as a library ([07 §7.3](../plan/07-content-pipeline.md#73-content-build-the-derived-data-graph)): import a glTF or GLB file, validate it against [§7.4](../plan/07-content-pipeline.md#74-validation-rules-automatic)'s rules, repair its UV-degenerate islands, optionally repack its atlas, weld it, build one cluster LOD DAG per primitive on the job system's performance pool, merge them in primitive order, lay them out in streaming pages, and write the `.clusters` container with its materials, its images, their texture records and the source's identity; the same over a manifest of meshes, one job per mesh, skipping an entry whose output already records this source and these options; the texture step that builds every image a mesh samples into a `.tex` under the derived-data root ([texture](texture.md)); the orchestration of the derived steps capabilities supply — the audio capability's `.clip` is the first ("Derived steps" below); and the content-build metrics of a built container. It has two hosts: `engine-content` (`build`, `build-all`, `stats`) and engine-host's `content.build` ([protocol](protocol.md#the-day-one-operations)); the one other module that links it is `systems/renderer`, for the texture step alone: a load through the derived-data cache that clusters a glTF itself runs `run_texture_step` beside the container it writes, so the renderer's cache fill builds the same `.tex` files engine-content does ([renderer](renderer.md#built-textures)).

**Why it is a module and not a file in an app.** Until 2026-09-24 all of this was `apps/engine_content/main.cpp` (the texture step included, which landed there the same day and moved with the rest), which was right while one program ran the build. When engine-host needed to run it too ([06 §6.9](../plan/06-agent-tooling.md#69-day-one-operations)'s `build_content`), the choice was a second copy or one library, and a second copy of a build is not the same build for long: the bytes a container holds, its cache key and the rule that skips it are exactly what two hosts must agree on byte for byte, which is the reason `geometry::cluster_cache_key` already lives in a module that engine-content and engine-view share. **It cannot live in `domain/geometry` or `domain/assets`**, which is where the minimal piece would otherwise go: the build calls the atlas step (`domain/atlas`), which depends on both, and the texture step (`domain/texture`), so the orchestration has to sit one step above them all. The code moved **unchanged** — the same function bodies, the same log category (`content`, so `--log content=debug` reaches it from either host), the same order of work — and engine-content kept everything that is the command line's: the flags, the usage, the stderr lines, and the shape and key order of its JSON lines. The proof is engine-content's own suite, which passed without an edit, including `determinism_tests.cpp`'s section hashes pinned on MSVC.

**Owned data.** Nothing persistent. A build's inputs are a source file and a `MeshOptions`; its output is a container on disk and a `BuildResult` in memory. The cache's rules (`geometry::cluster_cache_key`/`cluster_cache_path`/`find_ddc_root`) stay in `domain/geometry`, where engine-view reads them too.

**What moved, and what is new.**
- `MeshOptions` and `build_key_of` — the cache key of `geometry::cluster_cache_key` moved by the two steps outside the geometry (`--no-morph` and `--atlas repack`), each only when asked for; `lod_options_of`, `options_in_range`, and the spellings `read_seam_rule`, `read_atlas_mode`, `read_normal_map_mode`.
- The rule ids (`geometry.empty_primitive` … `atlas.repack`) as constants, `Diagnostic`, and `k_max_clusters`.
- `build_one`: one mesh, always built. `BuildResult` is what engine-content's build line reports, with the `TextureSource`s the texture step builds for it (`collect_texture_sources`, after `texture::fill_cluster_texture_records`).
- `repairs_json` and `atlas_json`: the `repairs` array and the `atlas` object of a build's line, so both hosts report a build in the same words.
- `ManifestEntry` and `read_manifest`: paths resolved against the manifest's own directory.
- `MeshTask`, `run_mesh_task` and `run_mesh_tasks`: the identity skip — a container that records this source's hash and this build key is the answer already; one that records none is rebuilt rather than trusted — and one job per mesh. **New:** `MeshTask::force`, which rebuilds regardless (engine-content's `build-all` never sets it; the protocol's `content.build` does when asked), and `MeshTask::pool`, which lets a single mesh run on its own hand its primitives to the pool, as `engine-content build` does, where a manifest leaves it null.
- The texture step: `run_texture_step` (keys taken in order on the calling thread, a key met earlier `shared`, an entry that records its identity `skipped`, the rest one job each), `textures_json`, `texture_sources_of_container` for a mesh a manifest skipped, `TextureResult`/`TextureState` and the `texture.*` rule ids. engine-content prints its failures on stderr; engine-host logs them.
- `container_stats`, `load_container`, `page_summary` (container_stats.h): the object `engine-content stats` prints, and the tables it prints for a person returned as a string in the order it prints them, so a host with no person to show them to drops them.

## Derived steps

**A capability's precomputed content attaches here as a table, not a link.** [ADR-0027](../adr/0027-additive-capabilities.md) names "a `derived` content-build step" as one of the points a capability plugs into; the audio capability's `.clip` — a clip decoded once into the mix format ([audio](audio.md#built-clips)) — is the first. It cannot be linked into this module: the module is not a capability and must build, and build the same containers, with every capability off (`msvc-minimal`), and a capability is declared after it (`audio` needs `protocol`, which comes after this module). Linking it anyway would also have pulled the audio module, whole-archive, and miniaudio into every binary that links this one — engine-view among them — for a step engine-view never runs. So the module holds the **orchestration** and the capability supplies the **work**, as a `DerivedStep`: its name, the manifest array its entries live in, which command-line sources it takes, its build key over a source's hash, its cache path, how to read what an output records, and the build itself. A host that has the capability hands the table over: engine-content does (`apps/engine_content/clip_commands.cpp`, compiled with `ENGINE_CONTENT_AUDIO` where the configuration has audio); engine-host's `content.build` does not yet.

**The rules are the meshes' rules.** `run_derived_task` reads the source, takes its identity as `hash_bytes` over the bytes as read — the convention every derived node starts from, so the clip store computes the same key from the same bytes — asks the step for the key and the path (the cache's for an entry with no output, whose directory it makes), and **skips the entry when the output already records that same source hash and that same key**; a zero key is never a match, and nothing is decided from a timestamp. Otherwise it builds, timing it, and reads the output's size back. `run_derived_tasks` runs one job per entry on the performance pool; results are read in manifest order. `read_derived_entries` reads the step's array — `{"source","output"}` objects, paths resolved against the manifest's own directory — where an absent array is no entries; `read_manifest` takes the names of the steps' arrays so that a manifest of nothing but clips (no `"meshes"`) is not refused. The two failures have rule ids: `source.unreadable` and `derived.build`.

**Invariants.**
- The bytes a build writes depend neither on the thread count nor on the toolchain ([geometry](geometry.md#the-same-bytes-from-every-toolchain)): the per-primitive DAGs merge in primitive order, never completion order, and a manifest's tasks are read back in manifest order.
- An incremental build never decides from a timestamp. A skip needs the container's recorded source hash and build key to equal the ones this source and these options give, and a zero key is never a match.
- A derived step's output is skipped only when it records the source hash and the build key this source gives, and its key is a function of the source's bytes and the step's options and version, never of a path or the machine.
- The module links no capability; a derived step is a table a host hands it.
- `protocol::ContentBuildOptions` states the defaults `MeshOptions` has. The protocol could not use `MeshOptions` itself (it is a C++ struct, not a schema type), so the IDL repeats the numbers, and this module's test is what holds the two together.

**Public API.** `domain/content_build/content_build.h` (the build, the manifest, the tasks, and the derived steps: `DerivedStep`, `DerivedEntry`, `read_derived_entries`, `DerivedTask`, `run_derived_task`, `run_derived_tasks`, `k_rule_derived_build`, `k_rule_source_unreadable`), `domain/content_build/container_stats.h` (the metrics and the container reader).

**Depends on.** `base`, `containers`, `math`, `hash`, `time`, `jobs`, `log`, `io`, `json`, `geometry`, `assets`, `atlas`, `texture`.

**Testing.** `tools/dev.ps1 test -Filter content_build` runs `tests/content_build_tests.cpp`: the build key moving with `--no-morph` and `--atlas repack` and with a repack's own options, and not with a kept atlas's; the spellings, with a refusal leaving the output untouched; a manifest resolved against its own directory, an entry's options overriding the defaults and the rest keeping them, and six malformed manifests refused with a sentence naming the manifest; a 16×16 grid written as a `.gltf` and `.bin` at test time, built on a two-worker pool, skipped on a second run with the same key and bytes, rebuilt by `force` to the same content hash, its metrics read back by `container_stats` (the cluster count, the triangles-per-cluster object, the bytes, and the streaming sweep's table in the text for a person), and a missing source failing with `source.unreadable`; and `protocol::ContentBuildOptions`' every default equal to `MeshOptions`'; and a stand-in derived step (it writes a source's bytes behind the identity it is given) over a manifest of nothing but its array — the entries resolved, the output cached or named, a second run skipping both, `force` rebuilding, a changed source a new key and a new entry, a source the step refuses failing `derived.build` and a missing one `source.unreadable`, and an array that is not one refused with a sentence naming the manifest. The audio step itself is held to the same rules end to end by engine-content's `tests/clip_tests.cpp`. The command line's end-to-end suite is `-Filter engine_content` ([apps](apps.md)), and the protocol's is `apps/engine_cli/tests/ops_tests.cpp` (`-Filter engine_cli`).

**Performance notes.** The build's own numbers are engine-content's and are in [apps](apps.md) ("engine-content"); moving the code into a library changed none of them. A second host adds one cost of its own: `content.build` makes a job system per call, which is a few milliseconds of thread start-up against builds that take tens to hundreds.
