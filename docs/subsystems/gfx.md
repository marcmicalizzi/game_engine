# gfx (domain)

**Purpose.** The RHI (docs/plan/04-renderer.md, ADR-0006): a thin, API-neutral layer over Vulkan 1.3/1.4 that the render graph and every renderer system build on. Phase 1 starts here with device discovery: enumerate the physical devices the loader exposes with the properties needed to choose a device and a capability tier, so experiment E2 (cluster acceleration structures on the development GPU) has data before any rendering code exists.

**Today.** Device discovery and creation, resources, one-shot submission, frames in flight, render graph v0 with raster passes, bindless resources, the first mesh-shader pipeline drawing the cluster geometry format, a swapchain, and image capture.

`enumerate_adapters()` creates a throwaway Vulkan 1.3 instance, fills one `AdapterInfo` per physical device (name, vendor, ids, type, API version, driver name and info, device-local memory, queue families, presence of each extension in `extensions_of_interest()`, **every row of the requirements table checked against that device, and a verdict**), assigns a hardware tier (`raster`, `rt` with acceleration structures **and ray queries**, `rt-cluster` when `VK_NV_cluster_acceleration_structure` is present as well), sorts discrete devices first and by memory, and destroys the instance. `gpu.adapters` exposes the same through the protocol, so `engine-cli gpu.adapters` reports a machine's capabilities in the schema-typed form, and `engine-cli gpu.adapters --report <file>` writes the whole thing as one JSON document with a UTC timestamp — the file to send back from a machine nobody here can log in to.

**Device.** `Device::create()` builds the instance (validation layer when installed and requested, debug messenger routed into the log under `gfx.validation`), matches the chosen adapter, picks queue families (graphics+compute; a compute-only family for async compute and a transfer-only family when the device has them, otherwise aliases), checks the requirements table below, and creates the logical device with exactly the feature chain that table's answer allows. A VMA allocator with buffer-device-address support and a transient command pool complete the device. On the RTX 5090 every optional feature enables and every row passes.

**The GPU lock.** Just before `vkCreateDevice`, `Device::create` joins this process's hold on the machine-wide GPU lock, and `Device::destroy` leaves it as soon as `vkDestroyDevice` has returned — before the instance is torn down, which touches no GPU and once crashed (below, "One live device per process"), so a crash there cannot leave the GPU spoken for — when `ENGINE_GPU_LOCK_ON_DEVICE=1`, which the shared test main sets for every test executable and the processes it starts, and not otherwise ([gpu_lock](gpu_lock.md), [ADR-0049](../adr/0049-tests-take-the-gpu-lock-per-device.md)). Every process opens its device here — a test through `gfx_test::open_device` or the renderer's rigs, `engine-view`, `engine-host` — so this is the one place a test's use of the GPU is gated, and a run that never reaches `vkCreateDevice` (adapter enumeration, a device the requirements refuse) never touches the lock. It may wait for another holder, and a wait that runs past the test's deadline ends the process with exit code 75 before anything reached the GPU, rather than returning a failure every caller would read as "no GPU here". With the switch off — the owner's sessions, an agent's `engine-mcp` — it costs nothing.

## The RHI surface and the backend surface

**Why this section exists.** Until 2026-09-25 the RHI was "thin and API-neutral" in intent only: Vulkan types or Vulkan includes appeared in 11 of this module's 17 public headers (`VkCommandBuffer` in every pass body, `VkBufferUsageFlags` in every buffer, `VkFormat`, `VkImageLayout`, `VkPipeline`, `VkSemaphore` in the renderer's frame description), in 21 places of `systems/renderer`'s public headers, and in `foundation/window`'s. A public header is what every module that includes it compiles against, so each of those was a Vulkan dependency of the whole renderer and of both hosts, and every week the renderer grew it leaked further. A second backend — D3D12 behind [08 §8.3](../plan/08-toolchain.md#83-graphics-api)'s trigger, or a console's API ([10 §10.6](../plan/10-roadmap-risks.md#106-decisions-deliberately-deferred)) — cannot live beside a renderer whose headers say `VkBuffer`, and retiring the leak costs in proportion to how much code names it. The owner moved it into the near plan on 2026-09-25, ahead of and independent of any second backend, and this is the result: **the public headers of `domain/gfx` and `systems/renderer` name no Vulkan type, constant or header; the backend-facing headers are a named set confined to the modules that own a device, a swapchain or a surface; and a lint rule keeps it so.**

**What a public header may say: the engine's vocabulary.** Four headers carry it, and none of them includes a Vulkan header.

- `rhi.h` — **handles**: `BufferHandle`, `ImageHandle`, `ImageViewHandle`, `SamplerHandle`, `AccelerationStructureHandle`, `AllocationHandle`, `ShaderModuleHandle`, `PipelineHandle`, `PipelineLayoutHandle`, `DescriptorSetLayoutHandle`, `DescriptorSetHandle`, `DescriptorPoolHandle`, `CommandListHandle`, `CommandPoolHandle`, `SemaphoreHandle`, `QueryPoolHandle`, all one `Handle<Tag>` template: 64 bits, trivially copyable, strongly typed (a buffer cannot be passed where an image view is wanted), null by default (`valid()`, `explicit operator bool`), and opaque — only the backend makes one from bits or reads them. `DeviceAddress` (a `u64`) and `k_whole_size`. **Flag sets** with `|`, `&`, `~` and `any()`: `BufferUsage`, `ImageUsage`, `PipelineStage` and `MemoryAccess` (synchronization2's stage and access bits, named `MemoryAccess` so it is never confused with the render graph's `Access`), `ShaderStage`, `AccelerationBuildFlags`, `GeometryInstanceFlags`. **Enumerations**: `Format`, `ImageLayout` (with `Present`), `BindPoint`, `IndexType`, `LoadOp`, `CullMode`, `CompareOp`, `Filter`, `SamplerMipmapMode`, `SamplerAddressMode`, `DescriptorType`. **Small descriptions**: `Extent2D`, `Offset2D`, `Rect2D`, `Viewport`, `BufferCopy`, `ClearColor`, and the indirect argument records the GPU reads, `DrawIndirectArgs`, `DrawIndexedIndirectArgs`, `DispatchIndirectArgs`.
- `commands.h` — **`CommandList`**, what a render graph pass body, `submit_immediate`, the timers and the acceleration builds are handed: a `CommandListHandle` in an 8-byte value, copied into a pass body exactly as the `VkCommandBuffer` was, owning nothing, with the commands the renderer records as methods — `bind_pipeline`, `push_constants`, `dispatch`, `dispatch_indirect`, `set_viewport`, `set_scissor`, `draw`, `draw_indirect`, `bind_index_buffer`, `draw_indexed_indirect`, `draw_mesh_tasks`, `draw_mesh_tasks_indirect`, `fill_buffer`, `update_buffer`, `copy_buffer`. **No barriers**: a pass declares its accesses and the graph derives them, and the two recorded by hand have functions of their own (`acceleration_build_barrier`, and the backend's `image_barrier` for the RHI's own code). A command is added when something above the RHI needs it; the RHI's tests reach the rest through the backend set.
- `resources.h` — `BufferResource` and `ImageResource` (engine handles, the same 40 bytes the Vulkan-typed structs were), `ImageLevelData`, `create_buffer`, `upload_buffer`, `upload_image_2d`, `upload_image_2d_levels`, `create_image_2d`, the destroys, and `submit_immediate` over a `CommandList`.
- `pipeline.h` — `create_shader_module`, `ComputePipeline`, `create_compute_pipeline` (over `DescriptorSetLayoutHandle`s), `GraphicsPipelineDesc`, `MeshPipelineDesc`, `create_graphics_pipeline`, `create_mesh_pipeline`, the destroys.

Everything else public is written in those terms: the render graph (`RgBufferDesc`/`RgImageDesc` take `BufferUsage`, `Format`, `ImageUsage`; an import's history is a `PipelineStage` and a `MemoryAccess`, its layout an `ImageLayout`; an attachment's load is a `LoadOp` and its clear a `ClearColor`; `image_layout`, `image_view`, `render_area` and `final_layout` answer in engine types), the frame context (`begin_frame()` returns a `CommandList`; `PresentSync` and `acquire_semaphore()` are `SemaphoreHandle`s), bindless (views, samplers, structures and layouts by handle; `bind(CommandList, BindPoint)`), capture (`Format`, `ImageLayout`), the shader library's reflection (`ShaderStage`, `DescriptorType` — SPIR-V's execution models are the engine's stages whatever the backend, so `shader_library.cpp` needs no backend at all), the timers, and both acceleration structure headers. The render graph's own `Access` vocabulary was already engine terms; what changed is that it now ends in engine terms too.

**Why the numbers are Vulkan's.** Every enumerator carries the value of the Vulkan constant it stands for, and every handle the bits of the Vulkan handle. That is a convenience for the first backend and not part of the contract — nothing above the RHI may do arithmetic on the numbers — and it buys two things. Moving the renderer onto this vocabulary could not change one flag it passes, because the mapping is a cast; and the cast is *proved*: `src/rhi_vulkan.cpp` is a page of `static_assert`s, one per enumerator, plus the layouts of the records handed to Vulkan as they are (`BufferCopy` against `VkBufferCopy` member for member, the indirect argument records against Vulkan's), so a wrong value is a compile error, not a wrong barrier. A second backend has a file like it with a switch where this one has a cast. A handle is 8 bytes because the handle it replaced was, which is why no struct that holds one changed size (the size table pins the handles, `CommandList`, both resources and the argument records).

**What the backend set holds, and who includes it.** Two directories, named in the lint:

- `domain/gfx/include/domain/gfx/backend/vulkan/vulkan.h` — volk and VMA (configured for dynamic entry points), `Handles` (the instance, physical device, device, queues, allocator, messenger and immediate pool behind a `Device`), `result_name`, `read_device_caps`, `image_barrier`, and `gfx::vk::native(x)` / `gfx::vk::wrap(x)`: the Vulkan object or value behind an engine one and the way back, for every handle, enumeration and small description (flags convert one way, with a named function where the way back is wanted, because Vulkan spells every 32-bit set `VkFlags`).
- `domain/gfx/include/domain/gfx/backend/vulkan/swapchain.h` — `SwapchainDesc` (a `VkSurfaceKHR`), `PresentStatus`, `Swapchain`. Presenting is backend-specific in this engine today — a D3D12 swapchain is made from a window and a queue, not a surface — so the class lives here and a second backend brings its own. What it hands the engine is engine-typed: its images are `ImageResource`s, its semaphores `SemaphoreHandle`s, its format a `Format`, so the renderer draws into a swapchain image without knowing it is one.
- `foundation/window/include/foundation/window/backend/vulkan/surface.h` — `window::vulkan::instance_extensions()`, `create_surface(window, instance, out)`, `destroy_surface` ([window](window.md#the-vulkan-surface)).

**Included by** `domain/gfx`'s sources and tests (the RHI's tests test the RHI, and parts of them — descriptor sets built by hand, raw barriers, image copies — are about Vulkan things the RHI does not wrap), `foundation/window`'s sources and tests, and `apps/engine_view`, which presents ([apps](apps.md#the-renderer-is-a-library-and-both-engine-view-and-engine-host-draw-with-it)). **Not by** `systems/renderer` — its sources, headers or tests: it records into an image the caller names, so it needs no device of its own, no surface and no swapchain, and that is what lets a second backend run it unchanged — and not by `engine-host`, whose renderer is offscreen.

**How it is kept.** Twice over. `tools/lint.ps1` has two rules with the marker `// engine-lint: allow-vulkan <reason>`: **`vulkan-in-public-header`** refuses `Vk…`, `VK_…`, `#include <vulkan/...>`, `<volk.h>` and `<vk_mem_alloc.h>` in any file under an `include/` directory of the engine tree outside the two backend directories — reading code, not comments, because a comment naming the extension a capability comes from (`VK_EXT_memory_budget` beside `MemoryBudget`) documents the backend and is not a type anyone compiles against — and **`vulkan-backend-include`** refuses an include of either backend directory, volk, VMA or `vulkan/*` anywhere outside `domain/gfx`, `foundation/window` and `apps/engine_view`, tests and benches included. The exemptions are meant to be zero, and are: nothing in the tree carries the marker. And the build: the Vulkan headers, volk and VMA are not on `engine_gfx`'s public include path; the INTERFACE target `engine::gfx_vulkan` carries them, and only gfx itself, its tests and engine-view link it, so anything else that includes the backend set fails to find `volk.h` before the lint runs. (engine_gfx links it `PRIVATE`, which for a static library still hands volk's library to every executable as `LINK_ONLY`.)

**What it cost, and what it did not.** Every `CommandList` method is one Vulkan command and nothing else — no cached state, no checks beyond the driver's — so a pass body records exactly what it recorded when it named `vkCmd*`; it costs one call more per command, a few hundred a frame. Measured on 2026-09-25 in `msvc-release` on the RTX 5090, before and after, interleaved (baseline, after, baseline, after) along the desert overlook's 2,401-frame path at 1920×1080 with three repeats each: `--shadows off` total GPU median 0.1252/0.1251/0.1252/0.1255 ms, `--shadows rt` 0.5360/0.5351/0.5355/0.5357 ms, `--raster vertex --shadows csm` 0.2418/0.2423/0.2424/0.2424 ms, the totals within 0.0009 ms (0.2%) of the old build's in the same round, in both directions, and a single pass's median within 0.001 ms except the cluster structure build's 0.002 ms, which is also its own run-to-run spread in the old build (0.1083/0.1062 before, 0.1062/0.1062 after); cull's 0.0281 → 0.0262 moved identically in both builds' second round. The CPU's per-frame recording time is the one number that moved at all: 0.0597/0.0597 → 0.0601/0.0601 ms on the `--shadows off` path, 0.4 µs a frame, which is what one extra call per command costs, and inside the old build's own spread on the other two (0.1067/0.1097 → 0.1081/0.1092, 0.1350/0.1363 → 0.1381/0.1322); other processes held 8–22% of the CPU and the GPU was otherwise idle, with 7.5 GB of its memory held by another process. The pictures did not move at all: every capture of the desert overlook's twelve markers under four configurations (hw with ray-traced shadows, hw with cascaded maps, the vertex path with maps, `--raster rt`), the FlightHelmet through all seven raster modes, the deformed heightfield and a 32-sample reference path trace — 222 files of colour, depth, normals and ids — is byte-identical to the build before the change, as are the 30 pictures `tools/ci/reference-compare.ps1` writes for the corpus; and the baseline was byte-identical to itself run to run, so the comparison can see a one-byte difference. The render graph's barriers stay Vulkan's own records, built once by `compile()` and handed over as they are, behind a pointer the header names only as `struct Barriers`, allocated with the graph and reused every frame, so no allocation was added to the frame.

**What a second backend would implement.** The engine side is now closed: the renderer, both hosts and everything above them compile against `rhi.h`, `commands.h`, `resources.h`, `pipeline.h` and the typed headers built on them. A second backend implements the functions those headers declare — `CommandList`'s methods (`src/commands.cpp`), buffers, images, uploads and `submit_immediate` (`src/device.cpp`), shader modules and the three pipeline kinds, `Device::create` and the adapter report behind the same requirements table, `FrameContext`, the render graph's barrier derivation and `execute`, the bindless set, capture, `GpuTimer`, and the acceleration structure builds (`src/acceleration.cpp`, `src/cluster_acceleration.cpp`, whose cluster forms have no D3D12 equivalent until DXR Tier 2.0 ships) — plus a `rhi_*.cpp` of its own mapping the enumerations, and a backend set beside `backend/vulkan/`: its swapchain, and the window system's glue for its surface. The D3D12 decision itself stays deferred; this is the step before it that was cheap now and expensive later.

## What a device has to have

**The requirements are one table** (`domain/gfx/requirements.h`), and device creation and the adapter report both walk it. Before it they were different code: `create()` checked a hand-written boolean of twelve feature bits and `gpu.adapters` printed an extension list, so a **limit** the renderer depended on — the 256-thread workgroup, the 128-byte push block, the update-after-bind budgets the bindless set is sized from — appeared in neither, and a machine that could not run the renderer would have found out at the first pipeline with a message naming none of it. Every GPU this engine has run on is one RTX 5090 with one driver; the three machines waiting for it are a Maxwell card, an Intel Gen9 part and a 2014 Kepler laptop, and the first run on each has to cost one copy and one command and come back saying *why*.

Each row is a name, a kind (`api`, `feature`, `extension`, `limit`, `queue`), a level, what is needed, what the device reports, whether it passes, and **one sentence saying what in the engine needs it**. That sentence is the point of the row: `"maxComputeWorkGroupInvocations": 128` tells nobody anything, and "deform_alloc.slang is 256 x 1 x 1 and hiz_build.slang is 16 x 16 x 1; Vulkan guarantees only 128" tells them what to do about it.

The three levels:

- **Required** — `Device::create()` fails, `verdict.tier` is `"none"`, and the error names every unmet row. Vulkan 1.3; a graphics+compute queue family; dynamic rendering, synchronization2 and maintenance4; buffer device address, descriptor indexing with runtime arrays, partial binding and update-after-bind for sampled and storage images, non-uniform indexing of sampled images, timeline semaphores, scalar block layout, host query reset, draw-indirect-count and multi-draw-indirect; `shaderInt64`; and the limits `maxPushConstantsSize` ≥ 128, `maxComputeWorkGroupInvocations` ≥ 256, `maxComputeWorkGroupSize[0]` ≥ 256 and `[1]` ≥ 16, `maxComputeSharedMemorySize` ≥ 4096, `maxMemoryAllocationCount` ≥ 256, and the update-after-bind budgets the bindless set is sized from — 256 sampled images, 8 storage images and 4 samplers, each per stage and per set, plus 264 for `maxPerStageUpdateAfterBindResources`, which sampled and storage images share.
- **Optional** — the row names the capability it `unlocks`. Presentation (`VK_KHR_swapchain`), the visibility buffer (`shaderBufferInt64Atomics`, `fragmentStoresAndAtomics`), mesh shaders, the vertex path's indexed draw (`geometryShader`, for `SV_PrimitiveID` in its fragment stage and nothing else, and `fullDrawIndexUint32`, for index values past 2^24 − 1 — see the baseline tier below), ray tracing (deferred host operations, acceleration structures, ray query, ray-tracing pipeline, and the acceleration-structure descriptor budget), cluster acceleration structures, the memory budget, memory decompression, descriptor buffers, anisotropy, fragment shading rate.
- **Note** — reported because a reader comes looking, enforced by nothing. `maxStorageBufferRange`, because every scene buffer is read through a device address (ADR-0023) and that limit does not bound it — the biggest buffer in the frame is the visibility buffer at 190 MiB for 11520×2160 and nothing checks it against a descriptor limit it never meets. `VK_EXT_index_type_uint8`, because the cluster format's 8-bit indices are widened on the host for the KHR builders and consumed natively by the NV one, and the one index buffer bound — the vertex path's indexed draw — is 32-bit, because an index carries the visible slot beside the local vertex. `subgroupSize`, because **no shader in the tree uses a subgroup operation** — which is worth writing down, since the pool allocator's serial prefix sum is the first thing a wave-level scan would replace. `storageBuffer8BitAccess` and `storageBuffer16BitAccess`, because the quantized grid and the packed indices are read out of the 32-bit words containing them, which is also fewer loads.

Two rows are Required for a reason that is worth knowing: `drawIndirectCount` and `multiDrawIndirect` have been required since the first indirect draw, and **today's call sites need neither** — `vkCmdDrawIndirect`, `vkCmdDrawIndexedIndirect` and `vkCmdDrawMeshTasksIndirectEXT`, each with a draw count of one. A draw per visible cluster through `vkCmdDrawIndirectCount` was tried for the vertex path on 2026-09-24 and rejected on the TITAN Xp's numbers: the count-driven draw cost a fixed 0.48 ms there plus 17 ns a draw, more than the whole raster pass it was meant to shorten ([E1 on Pascal](../experiments/e1-pascal-rerun.md#after-the-vertex-path-draws-the-cuts-own-triangles)). They stay Required because that is what creation does today; their rows say so, and they are the first thing to relax if a device is ever refused for them. `shaderInt64`, by contrast, moved *into* Required with this table: every push-constant block carries buffer device addresses as `uint64_t`, a SPIR-V module that declares a 64-bit integer needs the `Int64` capability, and a device without it can create no shader of the renderer at all — so refusing at `vkCreateDevice` with that sentence beats failing at the first pipeline with a driver's.

**The verdict is what somebody setting up a machine reads.** `DeviceVerdict` carries the tier (or `"none"`), `usable`, `blocking` — one plain sentence per unmet Required row — `degraded`, and `clamps`. `degraded` is the part a boolean list cannot give: "no `VK_EXT_mesh_shader`" becomes "`--raster hw`, `direct` and `auto` fall back to the vertex-shader baseline tier, which draws the same visibility buffer from the same clusters and the same cull pass" — followed, on a device without `geometryShader` or `fullDrawIndexUint32` as well, by the line naming which and saying that the baseline tier then draws every cluster's capacity rather than its cut indexed, and what that cost on the TITAN Xp — and no 64-bit buffer atomics becomes the sentence that matters most on Maxwell — every rasterizer writes the visibility buffer with a 64-bit atomic max, so **without it and without mesh shaders a device cannot draw a frame at all**, and the follow-up that would change that is a 32-bit visibility buffer (depth and id in one word), which is not built. `AdapterInfo::tier` stays the *hardware* tier, because that is the fixed vocabulary the adapter invariants are written in; `verdict.tier` is what the renderer would actually give the device.

**The `rt` tier is ray queries, not ray-tracing pipelines.** Every ray this engine traces is a ray query — the shadowed resolve from the fragment stage, the ray-traced visibility and the reference path tracer from compute — and nothing builds a ray-tracing pipeline, so `hardware_tier` keys on `VK_KHR_acceleration_structure` plus `VK_KHR_ray_query`, and the pipeline row is reported and decides nothing. It keyed on the pipeline until 2026-09-23, when the first GPU run on the project's Pascal server showed the cost: its TITAN Xp advertises acceleration structures and ray-tracing pipelines through the driver's compute fallback and **no ray query**, and it reported `"tier": "rt"` while it could not trace one ray the renderer asks for. It is `raster` now, the baseline tier, and its verdict says why. **The ray-tracing sentence of the verdict is one function**, `ray_tracing_degradation(caps)`: empty where every ray path of the renderer runs, otherwise one sentence naming exactly what is missing — no acceleration structures; no ray query (with or without the cluster structures, and saying that the pipeline is present when it is); or ray queries without `VK_NV_cluster_acceleration_structure`, which today is also a refusal, because the renderer builds only cluster structures and ADR-0025's KHR fallback, which this module builds and traces in its own tests, is not wired into the renderer yet. `device_verdict` puts that sentence in `degraded`, and a host refusing `--raster rt`, `--shadows rt` or the reference prints the same sentence after the adapter's name (`renderer::unavailable_reason`), so the report a machine's owner reads before running anything and the refusal they get when they run it cannot drift apart. The TITAN Xp's, verbatim: "no VK_KHR_ray_query and no VK_NV_cluster_acceleration_structure: every ray the renderer traces is a ray query (…), so --raster rt, ray-traced shadows (--shadows rt) and the reference path tracer are unavailable and the tier is "raster", although VK_KHR_acceleration_structure and VK_KHR_ray_tracing_pipeline are present (…)". A KHR-only device (ray queries without the NV extension) is `rt` by the rule and cannot trace in the renderer until the fallback is wired; its sentence says exactly that rather than the old promise of a pixel-identical KHR picture.

**Where the bindless set's sizes exceed a device, it clamps rather than fails.** `clamp_bindless` (same header) is the one implementation, used by `BindlessSet::create` and by the report, so the numbers in a report from an unseen machine are the numbers that machine would really get. A device with room for 2,048 textures runs the renderer perfectly well — it just cannot hold a scene of 16,384 of them — and refusing it would turn a smaller scene into no picture at all. Below a floor there is nothing left to run, and the floor is a Required row rather than a clamp: 256 sampled images (one slot per *image*, shared by every material that names it; the Khronos samples use 3 to 12, so 256 is about 85 textured materials with three maps each), 8 storage images (nothing in the renderer writes a bindless storage image today), 4 samplers (the renderer creates a nearest and a linear one), 1 acceleration structure (a `ViewSet` shares one top-level structure), and 128 push-constant bytes, which is `ClusterDrawParams` exactly and cannot be clamped at all. Sampled and storage images share `maxPerStageUpdateAfterBindResources`, so when the two do not fit together the storage array keeps its floor and the texture array takes what is left — a texture is what a scene actually runs out of.

**`DeviceOptions::overrides` is how a machine that has everything tests a machine that does not.** It names rows by the same `name` the table and the report use — `absent: ["VK_EXT_mesh_shader"]`, `limits: [{"maxDescriptorSetUpdateAfterBindSampledImages", 2048}]`, `api_version: 1002` — a name that matches no row is an error rather than a test that silently checks nothing, and the overridden caps are what the check, the clamping **and the enabled feature chain** are built from. So a profile that removes mesh shaders creates a device that really has none: `DeviceFeatures::mesh_shader` is false, `create_mesh_pipeline` fails, and every suite that guards on it skips exactly as it would on Maxwell. Nothing in the engine sets overrides; they exist for the tests and for diagnosis.

**One live device per process.** `Device::create` calls `volkLoadDevice`, which fills volk's *process-wide* dispatch table with that device's entry points, so a second live `Device` replaces the first one's — and when the two enabled different extensions, the first is left calling the second's. Found writing the renderer's TITAN-Xp-like case: with an override device alive that had no `VK_EXT_mesh_shader`, the full device's `vkCmdDrawMeshTasksIndirectEXT` was null and its next mesh draw crashed. Every host has one device (engine-view, engine-host's `RenderHost`), and every test that compares two devices builds and destroys them one after the other, which is the rule until the RHI moves to per-device tables (`volkLoadDeviceTable`), a change to every call site in this module. **The instance table is process-wide too**, and adapter enumeration fills it from an instance of its own: until 2026-09-30 `enumerate_adapters` left it pointing at that instance after destroying it, so a device open beside it tore its own instance down through stale entry points and crashed — engine-host did, on every exit after `gpu.adapters` had run beside a render, unnoticed because the end-to-end test does not read the host's exit code, and found only because the crash left the GPU lock behind ([gpu_lock](gpu_lock.md)). The live device's instance is recorded (`src/volk_instance.h`), enumeration loads it back when it is done, and `destroy()` reloads its own before tearing it down; `device_tests.cpp` holds enumeration beside an open device to it.

**Device-local memory, and what it can and cannot see.** `Device::memory_budget(MemoryBudget&)` sums the device-local heaps: their size always, and with `VK_EXT_memory_budget` this process's budget and usage as the driver estimates them (`vkGetPhysicalDeviceMemoryProperties2` with `VkPhysicalDeviceMemoryBudgetPropertiesEXT`). It exists so a measurement can say whether it was taken against a card another process was using — the development machine shares its GPU with other work — and `systems/renderer`'s `Stats::gpu_memory` is this in mebibytes. It is a driver query and deliberately not in the frame path; the renderer samples it in `create()` and when a host asks.

**The budget does not see everything, and the honest reading matters.** `heapBudget` is what the *Vulkan* driver will let this process allocate given what it knows about, and on NVIDIA a CUDA process's allocations are not fully reflected in it: measured on this machine with 17.1 GB of the 32 GB card held by a CUDA workload, the Vulkan budget still reported 31,614 MiB of 32,404 MiB available. So `device_local_total_mib - budget_mib` is a *lower* bound on what other processes hold, useful when it is large and meaningless when it is small. The number that does see a CUDA tenant is `nvidia-smi`'s, which is what the `machine_state` block beside it reports ([bench](bench.md#measuring-on-a-shared-machine)); read the two together, and trust the second one for "is somebody else using this GPU".

**Resources.** `resources.h` holds `BufferResource` and `ImageResource` through VMA (`create_buffer` with persistent mapping for host-visible buffers and a device address on request, `create_image_2d`) and `submit_immediate` (record into a `CommandList`, submit on the graphics queue, wait). The Vulkan handles behind them, `image_barrier` (synchronization2) and the conversions to and from the engine's types are in the backend set, `backend/vulkan/vulkan.h` ([above](#the-rhi-surface-and-the-backend-surface)); nothing above the RHI but a presenting app includes it.

**Shaders.** `engine_shaders(NAME <name> SOURCES <file.slang>...)` (`cmake/EngineShaders.cmake`) fetches the pinned Slang release (`ENGINE_SLANG_VERSION`, prebuilt Windows and Linux binaries, Apache-2.0 with LLVM exception) and compiles every `.slang` to SPIR-V 1.6 at build time with entry point names preserved, then embeds the bytes as a 4-byte-aligned `engine::shaders::k_<stem>_spirv` array in `<shaders/<stem>.spv.h>` on the INTERFACE target `engine_shaders_<name>`. Shader sources live beside the code that owns them (`domain/gfx/shaders/` for the RHI). `create_shader_module` and `create_compute_pipeline` turn embedded SPIR-V into pipelines. Runtime loading through the VFS, a hash-keyed cache, and Slang modules with link-time specialization arrive with the renderer's shader library (ADR-0008).

**Frames.** `FrameContext` (`frame.h`) runs N frames in flight: one transient command pool per slot, GPU progress on a timeline semaphore (frame k signals value k+1), `begin_frame()` blocking only when the GPU is N frames behind, and `defer_destroy()` for buffers and images the GPU may still read, freed when the slot is recycled. Presentation and multi-queue submission arrive with the swapchain and async compute.

**Render graph v0.** `RenderGraph` (`render_graph.h`): passes declare the resources they read and write with an `Access` (compute read/write, sampled read, transfer read/write, color or depth attachment); the graph validates that every read has a producer, allocates one physical resource per transient (no aliasing yet), derives every synchronization2 barrier and image layout transition from the transitions between declared accesses (read-after-read only widens the recorded stage mask), and records barriers plus pass bodies in declaration order. Pass bodies are stored in an arena and must be trivially destructible, so they capture by reference or pointer. Imported resources carry their last state in and report their final layout out, so consecutive graphs chain exactly. `stats()` counts passes, transients, barriers, and layout transitions, and the tests pin those counts. **A pass that uses one buffer two ways declares the write last.** The graph tracks a resource's state per pass, and the state a pass leaves behind is its *last* declared access: a pass that declares a write and then a read of the same buffer leaves it "read", and the next pass's read of it is read-after-read, which widens a stage mask and inserts no barrier — so the next reader sees the buffer as it was before the write. That is exactly what the vertex path's index expansion did on its first run (it reads its dispatch arguments out of the header it finishes; declared write-then-`IndirectRead`, the draw read an index count of zero and drew nothing), and the order is load-bearing in `record_frame` and the vertex path test, each with a comment. Later: aliasing, async-compute scheduling, raster passes through dynamic rendering, and a persistent graph cache.

**Raster passes.** A `PassKind::Raster` pass declares `color_attachment`/`depth_attachment` (load operation and clear value) instead of plain writes; the graph creates whole-image views for attachment images at compile, begins dynamic rendering with those attachments, sets a full-extent viewport and scissor, runs the body, and ends rendering. `create_graphics_pipeline` builds a dynamic-rendering pipeline with no vertex input (geometry is pulled through device addresses or generated), dynamic viewport and scissor, one color attachment, optional depth with reversed-Z greater-or-equal by default. `triangle.slang` draws the first pixels from the vertex index alone.

**Mesh shaders.** `create_mesh_pipeline` (`MeshPipelineDesc` in `pipeline.h`) builds a dynamic-rendering pipeline from an optional task stage, a mesh stage, and a fragment stage; it fails cleanly when `DeviceFeatures::mesh_shader` is false. `cluster_mesh.slang` is the cluster path from docs/plan/04-renderer.md §4.3 in its first form: one 128-thread workgroup per `geometry::ClusterDesc`, positions and packed local-index triangles pulled through push-constant device addresses, a `view_proj` transform, and a visibility ID per pixel (cluster index in the high 24 bits, triangle index in the low 8) written to an `R32_UINT` attachment. The mesh stage writes `SV_PrimitiveID` per primitive because the fragment stage reads an undefined value otherwise; the cluster index rides a flat per-vertex attribute until per-primitive attributes are wired. Task shaders, cluster culling, LOD selection, and the software-raster path for small clusters (experiment E1) build on this.

**Presentation.** `Swapchain` (`backend/vulkan/swapchain.h`, a backend header: [above](#the-rhi-surface-and-the-backend-surface)) sits on a surface the window system created (`window::vulkan::create_surface`; the device must have been created with `DeviceOptions::instance_extensions` from `window::vulkan::instance_extensions()`, and `DeviceFeatures::presentation` reports VK_KHR_swapchain). It picks B8G8R8A8_UNORM when offered, FIFO for vsync and MAILBOX then IMMEDIATE otherwise, three images, and TRANSFER_SRC usage when the surface allows it so captures can read presented frames. Binary semaphores are paired the safe way: one acquire semaphore per frame slot (`FrameContext::acquire_semaphore()`, reusable because `begin_frame()` waited for the frame that last waited on it) and one render-finished semaphore per swapchain image (`Swapchain::render_finished(index)`). `FrameContext::end_frame(PresentSync)` waits on the acquire at color output and signals render-finished alongside the timeline; `Swapchain::present` waits on it. `acquire()` and `present()` return `PresentStatus::OutOfDate` on resize or minimize and `resize()` recreates the chain through `oldSwapchain`. `RenderGraph::set_final_layout(image, ImageLayout::Present)` makes the graph append the transition after the last pass, so a presented frame is one imported image and one call.

**Which present, how deep, and when it was shown** (2026-09-25, [the second owner session](../experiments/second-interactive-session-2026-09-25.md#present-pacing)). `SwapchainDesc::present_mode` asks for a mode by name — FIFO, FIFO-relaxed, mailbox, immediate or FIFO-latest-ready, FIFO where the surface lacks it, `present_mode()` saying which — overriding `vsync`; `min_image_count` is clamped to the surface's range and `image_count()` is what the driver made. `suboptimal_presents()` counts presents that came back `VK_SUBOPTIMAL_KHR` (still reported as `OutOfDate`, so the caller recreates) and `chains_created()` the chains, so a run can say whether it was recreating its swapchain rather than guess. A chain asked for them carries **present ids** (`VK_KHR_present_id2`: `last_present_id()`, one per present over the object's life), with `SwapchainDesc::present_wait` **present waits** (`VK_KHR_present_wait2`: `wait_for_present(id, timeout)`, which blocks until that present has been shown and refuses an id from before a recreation, since the new chain never saw it — what engine-view's display pacer waits on) and with `SwapchainDesc::timing` **display times** (`VK_EXT_present_timing`: each present asks for its first-pixel-out time; `refresh_ns()` is the refresh the driver reports and `poll_timings()` hands back `{id, shown_ns}` on `time::monotonic_ns()`'s clock, mapped from the swapchain's time domain by a two-point calibration through `vkGetCalibratedTimestampsKHR`, since neither QueryPerformanceCounter's rate nor a present-stage domain's is anything the module is told). The device enables the three, with the calibrated timestamps present timing needs and the instance's `VK_KHR_get_surface_capabilities2`, **only when presentation is enabled and the device and surface offer them**, and reports them in the backend's `Handles` rather than `DeviceFeatures`, because nothing but a presenting app reads them and a device without them presents exactly as before; they are not rows of the requirements table for the same reason. **`poll_timings` is not a frame-loop call**: on the RTX 5090's driver (610.88, whose Vulkan presentation is layered on DXGI) `vkGetPastPresentationTimingEXT` blocks for about a refresh whatever its flags ask — 10.4–11.2 ms a call at 82 Hz, measured — and polling it every frame paced the loop by the poll (it looked like a steady 12.2 ms frame with 11.9 ms of "CPU" in it). So the driver's queue is set as deep as it will go (16,384 presents, 200 s at 82 Hz), a run reads it once at its end, and past that depth `present()` stops asking and `timing_dropped()` counts the frames that went unmeasured. `vkWaitForPresent2KHR` and `vkGetPastPresentationTimingEXT` both take the swapchain externally synchronized, so neither can move to another thread while the frame loop presents. Two more things the same driver does, measured on the owner's 11520×2160 window and written down because each would mislead a measurement: **a chain created with present timing paces FIFO differently** — its images come back one per refresh and the loop never fell into the paired rhythm apps.md describes (five runs), where every chain without it did (six runs), with or without present ids and waits — so `timing` stays off unless a run measures, and a measurement of the loop as it runs without it says `--no-present-timing`; and **its first-pixel-out times read early** on `time::monotonic_ns()`'s clock by at least 5 ms (the only domain it offers is `VK_TIME_DOMAIN_PRESENT_STAGE_LOCAL_EXT`, in nanoseconds, and a frame with 8.3 ms of work between sampling and presenting was reported shown 3.6 ms after sampling), so intervals between them are exact and their offset from anything else is not.

**Viewport convention.** Raster passes set a negative-height viewport, flipping Vulkan's y-down framebuffer to the y-up clip space `core/math` produces; counter-clockwise triangles in y-up space are the front faces, and the raster test's triangle covers the bottom-left half.

**Capture.** `capture_image` (`capture.h`) copies any 8-bit RGBA/BGRA, R32, D32, or float RGBA image into host memory with an immediate submission and puts it back in the layout it was found in; `capture_to_rgba8` swizzles BGRA to RGBA for `image::write_png`. It is the same readback the tests use, so what a test checks is what a screenshot shows; `engine-view --capture` writes one.

**Shader library.** `ShaderLibrary` (`shader_library.h`) hands out shaders by name. Embedded SPIR-V (`add_embedded`, the shipping path) and the build's `shaders/manifest.json` (`load_manifest`, written by `engine_write_shader_manifest()` with each shader's source, SPIR-V path, and slangc arguments) feed the same table; a manifest entry shadows an embedded one, and a manifest shader whose SPIR-V is missing or older than its source is compiled through the pinned slangc on first use. `poll_changes()` recompiles and reloads the shaders whose sources changed since they were loaded and names them, so callers rebuild the affected pipelines; a save that fails to compile keeps the previous version and reports slangc's diagnostics once. Reflection (`reflect_spirv`) comes from a small SPIR-V walk rather than the compiler: entry points with stages and workgroup sizes, descriptor bindings with set, binding, type, and count (0 for unbounded arrays), and the push-constant block size (unpadded, so 92 for `cluster_mesh` where the C++ mirror is 96). The library works without a device for tools and tests, which is how CI covers the slangc round trip on machines without a GPU. `engine-view` uses it and recompiles `cluster_mesh.slang` while running.

**Hot reload follows `#include`.** A shader's source is not one file. `visibility_resolve.slang` includes `brdf.slang` and `scene.slang`, the four rasterizers include `scene.slang`, and an edit to either of those changes every shader that reaches it — so watching each shader's own timestamp, as `poll_changes` first did, meant that editing the BSDF in a running `engine-view` did nothing until the including file happened to be saved too. The library now walks each tracked source's `#include "..."` graph and remembers every file it reaches with its timestamp; `poll_changes` checks those alongside the source itself and recompiles and names every shader that transitively includes a changed file. `include_count(name)` reports how many files a shader reaches, and `describe()` prints it.

Resolution follows slangc, because a set of files the compiler and the watcher disagree about is worse than no watcher: a quoted path is resolved against the **including file's own directory** first, which is what slangc does, and against the top-level source's directory second, which is what a shared header in the module's `shaders/` directory looks like from a source in a subdirectory. `<...>` includes are the compiler's own and are not tracked, a path that resolves to no file is left for slangc to complain about, and a file is visited once, so a cycle terminates; the walk stops at 64 files. The graph is rescanned after every successful compile, so an edit that adds or removes an `#include` is watched correctly from the next poll — an include that stops being included stops being watched. A save that does not compile keeps the last good shader and reports slangc's diagnostics once, whether it was the source or an include that changed.

The build-time side is the same rule, in `cmake/EngineShaders.cmake`: `engine_shaders()` walks each source's include graph at configure time and adds what it finds to that source's dependencies, so `hiz_build.slang` depends on nothing, `cluster_cull.slang` on `scene.slang`, and `visibility_resolve.slang` on `scene.slang` and `brdf.slang`. That replaces the hand-written `DEPENDS shaders/brdf.slang shaders/scene.slang`, which named the union of the group's includes and so rebuilt all eight shaders whenever the BSDF changed. The scan is deliberately *not* registered as a configure dependency: re-running CMake on every shader save would cost far more than it saves, and the loop that matters while iterating on a shader is the library's hot reload, not the build. The consequence, and the only thing to remember: adding or removing an `#include` line needs a reconfigure before the build sees it. `DEPENDS` stays supported for a file the scan cannot resolve.

**The scene: instances of meshes.** A frame draws a GPU-resident scene (docs/plan/04-renderer.md §4.2): every mesh of it lives in one set of global buffers — clusters, LOD descriptors, triangles, attributes, quantized positions, and the float positions the acceleration structure builders read — with the offsets baked into each `geometry::ClusterDesc` by `geometry::merge_cluster_meshes`. `MeshDesc` (`cluster_cull.h`, 64 bytes today; it started at 32 and grew with the deformation fields below) says which range of the cluster array a mesh owns (`first_cluster`, `cluster_count`) and which 16-bit position grid its vertices are on, because each mesh keeps its own through the merge. `InstanceDesc` (96 bytes) places one mesh: a world matrix, a `material_base` added to the cluster's material index, the prefix sum `first_pair`, the largest axis scale `scale_max`, and a flag saying whether the scale is uniform.

The unit of work is the **pair** (instance, cluster). Instance *i* owns its mesh's clusters starting at `first_pair`, so the whole scene is `pair_count` pairs and the cull dispatch covers exactly that many threads; thread *t* finds its instance by binary search over `first_pair` (the instances are in order, and a per-instance culling BVH is a later optimization — this flat enumeration is one load and a handful of compares). Every test then runs in the instance's frame: the bounding sphere's centre goes through the world matrix and its radius times `scale_max`, the LOD spheres and both errors likewise, the occlusion test uses the transformed sphere, and the normal cone is tested only where the scale is uniform, since a non-uniform scale shears a cone open, and only on a rigid instance (`InstanceDesc::deform == k_invalid_deform`), since a deformed one's triangles are not the ones its cone was fit to ([geometry](geometry.md), "Normal cones"). Survivors append a `uint2 {instance, cluster}` to the visible list.

**The visibility id is the scene's pair** (since 2026-09-24; it was the visible entry until then). The 64-bit word is `depth << 32 | (pair << 8 | triangle)`, where `pair` is the (instance, cluster) pair's index in the scene, `instance.first_pair + (cluster − mesh.first_cluster)` (`pair_of` in `shaders/scene.slang`) — 24 bits, so 16 million pairs a scene. The rasterizers read their entry `visible[i]` for the instance's world matrix and the mesh's grid, transform positions to world before the view projection, and write the entry's pair; the resolve reads the scene's **pair table** (`ResolveParams::pairs`: the {instance, cluster} of every pair, written once at upload by `renderer::GpuScene`, or for a streamed world expanded on the GPU as its tiles change, below) to get from `id >> 8` to the {instance, cluster} in one load — the one `visible[entry]` was when the id was the entry — and, for a deformed instance only, this view's **pair-to-entry table** (`ResolveParams::pair_entries`, which the cull pass fills for every pair it draws) for the entry whose block of the deformed-vertex pool holds the positions. Going through the pair-to-entry table for every pixel was the first version: a second dependent load that cost the TITAN Xp's resolve 2–3% on a full-screen heightfield ([visible order](../experiments/visible-order.md)). It decodes the positions through that mesh's grid (or the entry's pool block), transforms them by the world matrix and the normal by the cofactor matrix of its upper-left 3×3 (the adjugate transpose, which is the inverse transpose up to a positive factor, so normalizing afterwards makes the division unnecessary and a uniform scale needs no special case), and looks up `cluster_material[cluster] + instance.material_base`. A null visible list means entry *i* is `{0, i}` and pair *i*, which is what a direct draw of one mesh's leaves wants, and the resolve then takes the pair as the entry. Every draw of a frame appends to its own run of one list — occlusion pass 1, occlusion pass 2, the software rasterizer — and carries the run's base index in `ClusterDrawParams::visible_offset`, so everything that is per *entry* (the deformed-vertex pool's blocks, the indexed draw's records, a CLAS record's base geometry index) is one array and one index space however many draws filled it. The *id* is not in that space, which is the point: it names the same triangle in every cut, every run, every rasterizer and every frame, so two captures of the same surface are the same words, and a capture decodes an id from the scene alone (`GpuScene::pair_cluster`), with no readback of a list that is overwritten a frame later.

**The tie rule.** Two surfaces at exactly the same depth are one 64-bit word apart only in the id's bits, so the atomic max keeps **the larger (pair, triangle)** — the later instance, then the later cluster of its mesh, then the later triangle of the cluster — and that is the rule, stated here because it is what every rasterizer and the ray path have to agree on. It is a function of the scene alone. Until the id was the pair it was not: the word carried the visible entry, the cull pass filled the list by atomic append, and a tie went to whichever pair's thread reached the counter last — a different surface from one run to the next, from occlusion on to off (pass 2's run sits above pass 1's, so a coincident surface drawn by pass 2 won every tie), and between the hardware and software runs. The desert-overlook flythrough found every one of its differing pixels to be such a tie, overwhelmingly the palm fronds' coincident back-to-back faces ([flythrough](../experiments/flythrough-desert-overlook.md)); two identical checks of one build disagreed by 9 and 13 pixels. **What holds it:** the mesh path, the indexed vertex draw, the capacity vertex draw and the software rasterizer all write `pair_of(instance, mesh, cluster) << 8 | triangle`, and the renderer's `visibility_tie_tests.cpp` draws 24 copies of one box at one transform — every covered pixel a 24-way tie — through all four and the ray path, six times each, and requires the last copy to hold every pixel, every repeat to be identical, and the three hardware rasterizers' pictures to be identical word for word; it adds a tie that lands in different occlusion passes (a copy whose `bounds_padding` got it drawn in the previous frame, so pass 1 draws it and pass 2 the other) and requires the two-pass picture to equal the single-pass one. On the atomic append the rule and the two-pass checks failed — the last copy held none of the 2,857 covered pixels on any rasterizer or the ray path, and occlusion on against off differed at 2,356 of them — while the repeats still matched, since so small a fixture appends in the same order every time; run-to-run disagreement needs the flythrough's scale. **The ray path** is held to the same rule by a second look: a ray query commits the first of two hits at the same distance the traversal happens to meet, which is the structure's order and nothing the rasterizers know, so `ray_visibility.slang`, once it has the closest hit, traces again over exactly that distance with every candidate forced non-opaque (reported rather than committed), keeps the larger key among the candidates at exactly the committed distance, and leaves the shadow casters' entries out by their range (`RayVisibilityParams::caster_base`), since forcing non-opacity undoes the cull flag that kept them out of the first look. It is a second descent per hit pixel: on the RTX 5090 it costs the trace pass 71–74% on the heightfield (127 to 217 µs at 1080p, every pixel a hit) and 7–10% on the helmet grid. Two cheaper-looking ways were measured and rejected ([visible order](../experiments/visible-order.md)): **one traversal whose loop commits the nearest candidate itself** cost 16% and was wrong, because on the RTX 5090's driver a commit shrinks the ray to *exclude* its own distance, so a coincident candidate met after the first is never reported and the traversal's order decides again (the tie case lost every pixel); the **same loop without committing** is right, but reports everything behind the surface as well, 52–56% on the heightfield and 26–51% on the helmet grid, and grows with the depth complexity a ray crosses — where the second look is bounded by one descent to one point. The ray path is the parity and E2 path, not the shipping primary visibility ([04 §4.1](../plan/04-renderer.md#41-goals-targets-non-goals)); the resolve's shadow rays terminate on the first hit and have no tie to settle. **What the rule does not decide** is whether that is the *right* surface. For two copies of one surface it does not matter, and the resolve reconstructs exactly the same point either way — the same three vertices, the same grid, the same matrix. For back-to-back faces it does: the two sheets carry opposite normals, and the rule picks by index, not by which one faces the camera, so a two-sided leaf can resolve to the sheet facing away and shade dark. Preferring the front face at a tie would need a facing bit above the pair in the id, which costs a bit of the 24; it is a follow-up, not built. Nor is the software rasterizer's depth bit-identical to the hardware's (its edge functions and its interpolation are its own), so a surface split between the two paths by size ties only within each.

The shaders mirror `ClusterDesc`, `VertexAttributes`, `MeshDesc`, and `InstanceDesc` once, in `shaders/scene.slang`, together with `load_position`, the visible-list lookup, the binary search, and the normal transform; a shader that includes it names it in the `DEPENDS` of its `engine_shaders()`, as they do for `brdf.slang`.

**Cluster culling and LOD selection.** `cluster_cull.slang` runs one thread per pair: a sphere test against the frustum planes, a backface test on the cluster's normal cone when `CullParams::cone_cull` is set and the instance is rigid and uniformly scaled (meshoptimizer's apex form on the snorm8 packing in `geometry::ClusterDesc::cone`, the same arithmetic as `geometry::cluster_backfacing`), then the DAG cut test on the two error bounds of `geometry::ClusterLodDesc` (projected own error at or under the threshold, projected parent error over it, the same formula as `geometry::lod_selects`). Survivors append their `{instance, cluster}` pair to a visible list through an atomic that is also the x component of the indirect draw arguments, so `vkCmdDrawMeshTasksIndirectEXT` follows the cull with no CPU round trip; the mesh shader reads its pair through that list when `MeshParams::visible` is set, and each survivor also writes the entry it got into this view's pair-to-entry table (`CullParams::pair_entries`), which is how the resolve gets from a deformed instance's pair back to the entry its pool block belongs to. `CullParams` (`cluster_cull.h`, 464 bytes, read through a device address so the frustum fits) carries the planes from `frustum_from_view_proj`, the camera, the projection scale and threshold, enable flags, the scene (the instance and mesh arrays, the instance count, and the pair count), and the buffer addresses; the RHI never includes the geometry module. The render graph gained `Access::IndirectRead` and `Access::MeshRead` so the fill, cull, indirect draw, and readback chain is barriered from declared accesses like everything else. Measured on the Khronos samples at a 1 px threshold (SciFiHelmet, Suzanne, Corset), the cones remove 0 to 5% of the clusters the LOD cut selects: simplified clusters spread their normals wide and thin parts face both ways, so the cone is a cheap always-on test rather than a win; the cone test's sphere, at 37%, is the upper bound for compact closed geometry, and occlusion culling is where the clusters go.

**A pair nobody owns is rejected after the search** (2026-09-25, [renderer](renderer.md#instances-that-come-and-go)). A streamed world's scene keeps each tile's instances in a block of the instance table with a reserved run of pairs, so its pair space has **holes**: the slack a block keeps past its instances' pairs, and freed blocks. Their instance slots hold null instances of a mesh with no clusters (one `MeshDesc` past the scene's) whose `first_pair` is where the live pairs end, so the table stays sorted and `instance_of_pair` is the search it always was; `cull_pair` then rejects a pair past the found instance's `cluster_count` before it reads anything about a cluster. It is one compare on a word the pass already loaded, and a scene read whole never takes it. `clas_records.slang`'s `slots_main` searches `first_pair` too and has no such check, because a scene with holes has no ray tracing chain. **The pair table of such a scene is written here as well**: `pair_expand.slang` (`renderer::PairExpandParams`, 40 bytes; the C++ mirror lives with the renderer, which is its one user) writes the entries `first_pair + c` → `{instance, first_cluster + c}` for a list of instances, one 64-lane workgroup each with its lanes striding over the mesh's clusters, so a change uploads the instances it touched and a list of them rather than a table built on the CPU. It includes `scene.slang` for `InstanceDesc` and `MeshDesc`, and the renderer's test holds its push-constant block to the reflection.

**The visible list's order.** Within a run the entries are in the order the cull pass's atomic append handed out slots, which is not the same from one run to the next, and since the id became the pair nothing *drawn* depends on it: every rasterizer writes the same word for a pair whatever entry it was drawn as, and the resolve decodes it through the scene's pair table. What still follows the order is what the list *feeds* past a budget or into a readback: which deformed entries the pool's budget refuses (they draw their rest pose), which survivors the indexed draw's index budget sends to the capacity fallback (the same words at a different cost), the order a frame's acceleration structures are built in, and a readback of the list itself — so a test that compares two lists compares them as sets. A list filled **in pair order** was built and measured on 2026-09-24 ([visible order](../experiments/visible-order.md)): each cull workgroup scanned its block's survivors in shared memory, the workgroup that finished last (a device-scope counter after a device memory barrier, the pattern of CUDA's `threadFenceReduction` sample, so no workgroup ever waits for another) scanned every block's counts into offsets and added the totals to the count words, and a second dispatch scattered each survivor to its slot. It kept every picture test green and made the pool's overflow reproducible, and it cost the RTX 5090 6–12 µs a frame with occlusion off and 8–19 µs with it on (two cull passes) on scenes of 47,000 and 151,000 pairs, against a cull pass of 10–14 µs — and 29 and 58 µs at the overlay desert's 876,537 pairs, because the last block's scan is over every block of the *scene*, not of the cut; the TITAN Xp's numbers are on the experiment page. That buys reproducibility for two budgets the defaults are sized never to reach, so it is **not adopted**. A single-pass decoupled look-back would save the second dispatch, but it chains every block behind its predecessor when all the blocks are resident at once, as they are at these pair counts, and it rests on forward progress between workgroups, which is not a guarantee to lean on for a GPU the owner is also using. If something does come to need the order, the experiment page says where the cost went and where a cheaper version would start.

**Visibility buffer, two rasterizers (experiment E1).** The cull pass also splits survivors by projected cluster diameter (`CullParams::raster`: everything hardware, everything software, or split at a pixel size) into two lists with their own indirect arguments. The hardware path is the mesh shader with `fs_visibility`, an attachment-less raster pass (`PassBuilder::render_area`) whose fragments fold reversed-Z depth and the visibility id into one 64-bit word and take the nearest with a 64-bit atomic max on a storage buffer (`DeviceFeatures::buffer_int64_atomics`). The software path is `cluster_sw_raster.slang`: one 128-thread workgroup per cluster from the software list (`vkCmdDispatchIndirect`), vertices transformed to pixel space in shared memory, one thread per triangle walking its bounding box with edge functions and writing the same words the same way; triangles with a vertex behind the camera or a bounding box over 64×64 pixels are skipped, since such clusters belong to the hardware path. `ClusterDrawParams` (128 bytes, the largest push block the renderer allows) is the shared push-constant block of all three rasterizers. `Access::FragmentRead` and `Access::FragmentReadWrite` cover fragment-shader storage traffic in the graph.

**Quantized positions.** Both rasterizers and the resolve read positions off one 16-bit grid per mesh instead of float triples: **6 bytes per vertex instead of 12**. `MeshDesc` (`cluster_cull.h`, GPU-mirrored, read through a device address) carries the grid (`geometry::ClusterMeshPart::quant_origin` and `quant_scale` in a `float4`), the address of the scene-wide `quantized` stream, and the mesh's range of the cluster array; `ClusterDrawParams::mesh` and `ResolveParams::mesh` are arrays of it, indexed by an instance's mesh id. `shaders/scene.slang` holds `MeshDesc` and a `load_position` helper that reads the three `u16` at `3 * vertex` out of the 32-bit words containing them, the way it holds `ClusterDesc` and `InstanceDesc`; the CPU pads the stream to an even `u16` count so the last word read is in bounds. Error is bounded by half a grid step, which on engine-view's 20-unit terrain moves a vertex by under 0.002 px at 320×240 (the CPU check in the vertex path test), and the existing pixel comparisons pass with their tolerances untouched. `clas_records.slang` and the acceleration structure builders still read the float positions, so a mesh that is ray traced uploads both streams.

**GPU timers.** `GpuTimer` (`gpu_timer.h`): one timestamp query pool per frame slot, `begin_frame` reads the slot's completed results and resets from the host, `begin`/`end` bracket zones at ALL_COMMANDS, `results()`/`ms(name)` report the last completed frame. engine-view reports per-pass milliseconds through it.

**Two-pass occlusion culling.** `hiz_build.slang` builds a Hi-Z pyramid of the farthest depth from the visibility buffer (mip 0 copies the depth word, empty pixels are 0, every further mip is the minimum of its 2×2 sources, sizes round up so nothing is skipped), laid out back to back in one buffer by `hiz_layout()`. The cull pass gains `CullParams::pass`, `hiz`, `prev_flags`, and `flags`: pass 1 considers the clusters drawn last frame and tests them against last frame's Hi-Z, pass 2 considers everything pass 1 did not draw and tests it against the Hi-Z rebuilt from pass 1's depth, both mark what they draw, and the Hi-Z is rebuilt once more after pass 2 for the next frame. The test projects the eight corners of the sphere's box to a screen rectangle, picks the mip whose texels are at least a quarter of it (a footprint of at most 5×5 texels, which culls far more than a 2×2 footprint at coarser mips), and rejects the cluster when its nearest point is farther than every Hi-Z texel it touches; anything touching the near plane stays visible. Occlusion culling never changes the picture: the test draws a terrain behind a wall with and without it and gets the same visibility buffer while drawing 53 clusters instead of 100.

**One workgroup folds six mips, not one dispatch per mip.** The pyramid is the frame's largest fixed cost at high resolution — at 11520×2160 it measured 0.57–0.60 ms whether the frame was full or empty, and it is built twice a frame — and the reason is bandwidth: a dispatch per mip re-reads the whole of each mip out of memory to produce the next one, so one build moved about 460 MB of which 160 MB was re-read, and the two builds a frame ran at 87% of the card's peak. `hiz_build.slang` is now one entry point whose 16×16 workgroup folds a **32×32 tile**: each thread reduces a 2×2 quad, writing mip 0's copy of the depth word and mip 1's minimum, and the four further halvings (16 → 8 → 4 → 2 → 1) run through shared memory. What is left in memory is the visibility read, which cannot be avoided, and one write per texel of every mip, which is what the cull pass reads. A pyramid deeper than six mips is a second dispatch reading the sixth, so 11520×2160's fifteen mips are **three dispatches and two barriers instead of fifteen and fourteen**, and `HizParams` says which mip the source is and how many folds to write rather than naming one source and one destination — same 40 bytes, because the destination mips are contiguous behind the source and the shader walks their offsets the way `hiz_layout()` does. `hiz_group_count()` now counts workgroups over a dispatch's **source** extent, and `hiz_dispatch_count`/`_src_mip`/`_levels` say what the chain is.

**Why that is safe, which is the whole question for a pass occlusion culling reads.** The values are bit-identical, not merely close: `min` is exact in floating point, and a 32×32 tile aligned at a multiple of 32 covers, at every level, exactly the 2×2 subtrees the mip-at-a-time pass reduced — the same partition, so the same numbers. The odd-extent rule is reproduced rather than approximated: a mip of odd width rounds up and its last texel had a clamped, duplicated source, and `min(a, a) = a`, so a shared-memory slot outside the mip holds a stand-in for infinity (every reversed-Z depth is in [0, 1]) and folds away to the same answer. Nothing about the pyramid's size, layout, mip count or contents changed, so `occluded()` reads the same texels through the same footprint rule and the visible set is unchanged — which matters because it is the *input* to a test that must not change the picture, and a coarser mip 0 (the obvious way to make the copy cheaper) would have changed it. Two tests hold it: the occlusion test recomputes the whole pyramid on the CPU from the visibility buffer and requires equality at every mip, and a second case builds a **2053×1027** pyramid — thirteen mips, three dispatches, odd at six levels and a partial tile on both axes at every level — from a pseudo-random visibility buffer and compares every one of its 2,812,873 texels against the mip-at-a-time recomputation. Measured on the RTX 5090, `--raster hw --shadows off`, two builds a frame: 11520×2160 **0.580 → 0.451 ms** empty and 0.563 → 0.427 loaded, 3840×2160 **0.200 → 0.095**, 1920×1080 **0.070 → 0.021**, and a three-view surround at 1920×1080 **0.129 → 0.039**. The win grows as the resolution falls because what dominates a small pyramid is the dispatch and barrier count, not the bytes.

**Material resolve.** `visibility_resolve.slang` is the first material pass (`visibility_resolve.h`: `ResolveParams`, 336 bytes read through a device address; `ResolveMaterial`, 64 bytes; `ResolveLight`, 64 bytes; `ResolveMode`; `k_no_texture`). For every covered pixel the id's pair leads through the scene's pair table (`ResolveParams::pairs`; without one, through this view's pair-to-entry table and the visible list, `pair_entries` and `visible`) to the (instance, cluster) pair and so to the triangle's three vertices, off the 16-bit grid of that instance's mesh (`ResolveParams::mesh`) and through that instance's world matrix, exactly as the rasterizer moved them; screen-space barycentrics against the pixel center, made perspective-correct through the vertices' clip-space w, reconstruct the surface position and interpolate the per-vertex normal and UV from `geometry::VertexAttributes` (the triangle plane gives a flat, two-sided normal when a mesh has no attributes). A material table indexed by the cluster's material index plus the instance's `material_base` (`ResolveMaterial`, 112 bytes) supplies albedo and roughness, emissive and metallic, and five optional textures sampled through the bindless set: `albedo_texture` multiplies the albedo, `metallic_roughness_texture` multiplies the roughness and metallic factors by the texture's G and B (glTF's packing), `normal_texture` perturbs the shading normal, `emissive_texture` multiplies the emissive factor (sRGB colour; the product is radiance the pass adds after the lighting), and `occlusion_texture` (R, with `occlusion_strength`: `1 + strength · (r − 1)`) multiplies the indirect term — the hemisphere of sky and lit ground, today the resolve's whole ambient — and nothing else.

**The material table: samplers and the UV transform.** Every slot names its own bindless sampler: `sampler` for the base colour, and the 16-bit halves of `samplers_mr_normal` and `samplers_occlusion_emissive` for the other four, a half of `k_same_sampler` (0xFFFF, the default) borrowing `sampler` — so a material written before the slots had samplers of their own, which sets only `sampler`, reads as it always did. A sampler is an index, so a slot's own costs the table two bytes and the shader a select. The **UV transform** (`KHR_texture_transform`) is one per material: `uv_transform` holds the 2×2 part and `uv_offset.xy` the offset, read when `k_material_uv_transform` is set, and `set_uv_transform(material, offset, rotation, scale)` is the one place the extension's `T · R · S` becomes those numbers (`u' = c·sx·u + s·sy·v + ox`, `v' = −s·sx·u + c·sy·v + oy`) and the one place the identity leaves the flag clear. The resolve applies it after `uv_scale` (`material_uv` in `material.slang`) and puts the derivatives through its linear part (`material_duv`), so a texture tiled eight times picks its mip for eight tiles; the path tracer applies it to its hit's UV. One transform rather than five is the table's size: 24 bytes a slot would have taken it from 112 bytes to 208 for a case no exporter in the corpus writes, and the container keeps the per-slot transforms for a renderer that wants them ([texture](texture.md#samplers-and-texture-transforms)). The table is not reflected — it is read through an address, and `reflect_spirv` sees push constants — so the mirror is held by the size table and by the attributes test, whose blocks read every new field back out of the picture.

**An empty pixel costs a read it cannot avoid and a write it can.** E9 found the resolve about 45% fixed at 11520×2160 — 0.19 ms of sky against 0.39 ms of covered frame — and the reason is bandwidth, not shading: one 64-bit visibility word read and one colour word written per pixel is 299 MB at that size, and the pass measured 90% of the card's peak. The read is how a pixel is *known* to be empty and so cannot go; the write can, because the pass clears the whole target to the sky before it draws and an empty pixel's colour is therefore already in the target. `ResolveParams::sky_is_clear` is the caller saying it cleared to exactly `ResolveParams::sky`, and the shader then **discards** the fragment instead of writing it. The picture is identical because the bytes under it are, and the flag defaults to zero — writing the sky, as before — because `domain/gfx`'s own resolve tests clear to black and read the sky back out of the picture. Measured on the RTX 5090 at 11520×2160, `--raster hw --shadows off`: an empty frame's resolve 0.192 → 0.178 ms single and 0.186 → 0.166 surround3, a loaded one 0.383 → 0.380 and 0.375 → 0.363. Less than the bandwidth arithmetic predicts, and that is the finding: a full-screen write of one constant colour is already nearly free on a compressed colour target, so what the discard removes is the ROP traffic and not the DRAM traffic. The visibility read is the number that matters, and skipping *that* needs to know a whole region is empty before reading it.

**Which the Hi-Z build already knows, for free.** Its first dispatch reads every word of the visibility buffer, and its workgroup is exactly a 32×32 tile of it, so one OR across the workgroup says whether that tile holds any surface — `HizParams::coverage` is where it puts the answer, one `u32` per tile (97 KB for a 11520×2160 view, small enough to sit in cache while the resolve runs, and a plain store rather than a bit and an atomic so nothing has to be cleared between frames). `ResolveParams::coverage` and `coverage_pitch` hand the mask to the resolve, which reads the tile word before the visibility word and takes the sky if it is zero. A pixel is "empty" by the **whole** 64-bit word, not by its depth half, because a surface exactly at the far plane has a zero depth and a non-zero id and the resolve shades it. Measured at 11520×2160, `--raster hw --shadows off`, against the discard above: an empty frame's resolve **0.178 → 0.084 ms** single and 0.166 → 0.084 surround3, and a *loaded* frame's **0.380 → 0.320** (helmets) and 0.348 → 0.285 (heightfield), because most of a frame is sky at 48:9 whatever is in it. The Hi-Z build pays 0.00–0.02 ms for the mask, which is inside its own run-to-run spread.

**When the mask is valid, which is a property of the pass order and not of the mask.** It describes the visibility buffer as the last Hi-Z build saw it, so it is the truth for the resolve only when nothing writes the buffer in between. That is exactly when two-pass occlusion culling is on: `renderer::resolve_settings` allows occlusion only under `--raster hw` and `--raster vertex`, which are the two modes with no software-raster pass and no ray trace after the Hi-Z, and the last build of the frame follows the pass-2 draw. Off, `ResolveParams::coverage` is zero and every pixel reads its word as it always did. **Anything added to a frame that writes the visibility buffer after the last Hi-Z build has to turn the mask off with it**, and that is the one way this can go wrong: an over-eager mask does not shade a pixel that should be shaded, which is a 32×32 hole and not a subtle error. `systems/renderer`'s test renders the same scene with occlusion on and off at both layouts and requires the colour and the (instance, cluster) under every pixel to be identical.

**The tangent frame** is solved per pixel from the hit triangle's own data, because nothing upstream carries tangents: its three positions go through the instance's world matrix like the ones the reconstruction interpolated, so the frame is in the same space as the normal it perturbs, and the two edge vectors and the two UV deltas give `dp1 = T du1 + B dv1` and `dp2 = T du2 + B dv2`, which invert to a tangent and a bitangent, and those are Gram-Schmidt orthonormalized against the interpolated shading normal, so the frame is orthonormal and keeps the UV parameterization's handedness (a mirrored island gets a mirrored bitangent, which is what a map authored on it expects). A triangle with no attributes or a degenerate UV area has no frame, and the normal is then left alone rather than perturbed by a frame the shader invented. The map's bytes are UNORM, remapped to −1..1; `normal_scale` multiplies the tangential xy before the vector is renormalized, so a scale of 0 gives the interpolated normal back exactly. The perturbed normal goes into the BSDF and into the sky hemisphere's elevation term; nothing else in the lighting changes, and the `normals` debug view still shows the interpolated normal, before any map. Normal and metallic-roughness textures are **data, not color**, so they are uploaded `R8G8B8A8_UNORM` while base color goes up `R8G8B8A8_SRGB` — on the decoded path. A mesh whose images the content build has built ([texture](texture.md)) uploads them as stored instead: BC7 sRGB for base colour, BC7 UNORM for metallic-roughness, **BC5 for the normal map**, which holds x and y only and samples blue as zero, so `normal_map_vector` rebuilds z as `sqrt(1 - x² - y²)` before `normal_scale` when the material carries `k_material_normal_rg`.

**The lighting model** is physically based and lives in `shaders/brdf.slang`, a file with no bindings and no entry points that the reference path tracer will include unchanged (docs/plan/04-renderer.md §4.3, "Materials"): Cook-Torrance with a GGX/Trowbridge-Reitz normal distribution, Smith height-correlated visibility (Heitz 2014), Schlick's Fresnel with F0 = lerp(0.04, albedo, metallic), and a Lambert diffuse lobe scaled by (1 − metallic) and (1 − F). Perceptual roughness is clamped to 0.045 so a mirror's highlight stays finite, and alpha is its square. **n·v is clamped to 10⁻⁴, not rejected** (`k_min_n_dot_v`, Filament's `clampNoV`; since 2026-09-25): a shading normal leaning away from the eye on the camera's side of its triangle — a grazing view across smooth vertex normals, a normal map's texel turned away — still takes a light it faces, where the rejection left the pixel with the ambient alone; that was the whole of the dunes' "grey seams" ([renderer](renderer.md#a-shading-normal-is-not-the-surface)). A light exactly opposite the eye, where l + v is zero, takes the normal as its half vector rather than a NaN. For the clamp not to shine a light through thin two-sided geometry, the resolve turns a shading normal that is behind its triangle (against the geometric normal, which faces the camera) to the camera's side before it shades, as the path tracer turns it to the side its ray came from. The resolve evaluates it for the directional sun (`ResolveParams::sun`, direction and intensity) and for `light_count` analytic lights at `ResolveParams::lights` (`ResolveLight`, 64 bytes: position and radius of influence, linear color and intensity, spot direction and type, cosines of the inner and outer cone). A light's falloff is inverse square windowed to zero at its radius with Karis' `(1 − (d/r)⁴)²`, so a light contributes exactly nothing beyond its radius and culling by radius cannot change the picture; a spot multiplies that by a smoothed cone. A hemisphere of two uniform halves is the whole indirect term until the lighting passes of §4.2 step 5 exist (2026-09-25): the sky above the horizon at 0.35 of `ResolveParams::sky`, and below it the ground — `ResolveParams::ground`, the ground's albedo, lit by the sun's irradiance on a horizontal surface and by the sky, `ρ (E_sun / π + L_sky)` (`brdf_ground_radiance`), unshadowed because it stands for the ground *around* the point. A surface takes the two blended by the share of its cosine lobe above the horizon, `lerp(ground, sky, (1 + n.y) / 2)` (`brdf_hemisphere_ambient`), which is exact for two uniform halves and is why the path tracer's escaped rays see exactly those halves; before, it was one ramp, 15% to 35% of the sky color by normal elevation, with no ground at all ([renderer](renderer.md#the-sky-above-the-ground-below) has why and what it measured). The diffuse albedo takes that, and the specular lobe takes the share of it `brdf_env_specular` gives — the GGX lobe's reflectance of a uniform environment, the split-sum's second factor in Karis' analytic fit, F0 · a(roughness, n·v) + b(roughness, n·v) — which keeps metals, which have no diffuse lobe, from going black and keeps a rough dielectric matte at grazing. **Until 2026-09-25 that share was bare Schlick at n·v**, which is a mirror's curve at every roughness: it climbs to 1 at grazing and at every texel of a normal map turned away from the camera (n·v clamped to 0), so a rough stone wall seen edge-on reflected the whole sky as a white-blue sheen — the ruins that looked "reflective instead of matte" in the second owner session ([its write-up](../experiments/second-interactive-session-2026-09-25.md)). With roughness forced to 1 and metallic to 0 the sheen was unchanged, which is what ruled the kit's metallic-roughness map and its sampling out; with the fit, the resolve also agrees better with the reference path tracer, whose escaped rays see the same sky: the four agreement scenes went from 0.0206, 0.0218, 0.0281 and 0.0144 FLIP to 0.0131, 0.0140, 0.0215 and 0.0034, and the FlightHelmet at `--orbit 22` from 0.0168 to 0.0128 against 1024 samples at three bounces ([renderer](renderer.md#reference-renderer)). The CPU reference (`tests/brdf_reference.h`, `env_specular`) carries the same fit, and the shading and attributes tests still hold the GPU to it within 1 of 255 — the ground term included, which the reference mirrors as `ground_radiance` and `hemisphere_ambient`, and which the shading test pins at its far end: the quad seen from below, facing straight down with the sun and the light behind it, is the reference to 0 of 255 on every one of its 12,100 covered pixels under a neutral ground and a sand-coloured one, and black under no ground at all. Emissive adds, and the result goes through a 1/2.2 display gamma onto the UNORM swapchain (tone mapping is a later pass). `engine_shaders(... DEPENDS shaders/brdf.slang)` puts the included file in the dependencies of every slangc command of that group, so editing it rebuilds the shaders that include it; `ShaderLibrary`'s hot reload, though, watches only each shader's own source, so a running `engine-view` picks a `brdf.slang` edit up when the including file is saved too. Debug modes show cluster colors, triangle shading, depth, normals, or UVs. `upload_image_2d` (`resources.h`) creates a sampled texture from host pixels, at one level. **`upload_image_2d_levels`** creates one with a whole mip chain — any format, block-compressed included (the BC formats need `DeviceFeatures::texture_compression_bc`, the optional `textureCompressionBC` row) — from one staging buffer in one submission, each level at a 16-byte aligned offset and copied with its own region, one barrier over every level each way; `ImageResource` now says how many levels it has (`levels`, which `create_image_view` covers) and what the allocator gave it (`bytes`). **`create_mip_sampler`** (`bindless.h`) is the material sampler of built textures: linear within and between levels, the whole chain, 16x anisotropic where `samplerAnisotropy` is on and trilinear where it is not, and clamp-to-edge like `create_sampler`, so a built texture and its decoded fallback read the same texels at the edges. **Mip selection** in the resolve: a fullscreen pass has no quad derivatives it can trust across a triangle edge, so a material flagged `k_material_mipped` (`visibility_resolve.h`) samples with `SampleGrad` and UV derivatives computed from the hit triangle (`screen_uv_gradients` in `material.slang`, derived in [texture](texture.md#mip-selection-without-quads)); every other material reads level 0 exactly as before (`sample_material_grad` falls through to `sample_material`). `ResolveMode::Albedo` (7) shows the textured base colour unlit, which is how the texture tests measure filtering without the lights.

**The material layer is a file, not a copy** (`shaders/material.slang`, docs/plan/04-renderer.md §4.8). §4.8 asks the reference path tracer to *share* material, BSDF, light, and camera code with the real-time path, and sharing a BSDF is not enough: two integrators that agree on `brdf_eval` and disagree about how a triangle's UVs are interpolated, what a metallic-roughness texture multiplies, where a light's falloff reaches zero, or what the display transform is would produce a comparison of their material layers rather than of their transport. So everything between the geometry and the BSDF moved out of `visibility_resolve.slang` into `material.slang`, which `path_trace.slang` includes too: the `ResolveMaterial` and `ResolveLight` mirrors, `SceneGeometry` (the eight addresses a hit is read through), `fetch_triangle` and `surface_at` (positions through `load_position` and the world matrix, then the octahedral normals and half UVs interpolated at given barycentrics), `reconstruct_screen` (the resolve's perspective-correct screen barycentrics, which a rasterized pixel needs and a ray-traced one does not), `tangent_frame`, `material_of`/`sample_material`/`apply_normal_map`, `light_sample` (the windowed inverse square and the spot cone, returning the direction, the arriving radiance, and the distance a shadow ray stops at), `sky_radiance`, and `display_encode`. Unlike `brdf.slang` it *does* declare the two bindless arrays it reads (sampled images at binding 0, samplers at binding 2), because a shader that samples a material is one that binds the scene's set; the acceleration structures at binding 3 stay out of it, so the plain resolve still compiles on a device that has no such binding. The move is behaviour-preserving by construction and was checked as one: the FlightHelmet through `--raster hw`, `--raster vertex`, `--raster rt --shadows rt`, `--deform wave`, and `--views surround3` is **byte-identical** before and after (PSNR null, SSIM 1, FLIP 0 on all five).

**What `reconstruct_screen` cannot rebuild** (found 2026-09-30). The resolve's point is the pixel centre's barycentrics in the triangle's corners *divided by w*, projected to the screen, which is meaningless for a triangle with a corner behind the camera's plane. The rasterizer clips such a triangle and the visibility buffer names it rightly; the point the resolve rebuilds for its pixels is not the one the pixel sees, and neither are the UVs, the footprint or anything read at the point. Looking down at a walker's feet the camera's plane meets the ground metres behind him — `h tan(pitch)`, about 3 m for a 1.65 m eye looking 60° down — and a triangle long enough to reach it from the bottom of the picture is drawn at the wrong point: on the waves' 4 m grid the sand's 2 m grainflow tongues ran on as stripes to the bottom of the resolved picture where the reference path tracer, whose hit is a ray against the triangle, drew them ending ([renderer](renderer.md#the-sand-close-up)). Nothing that varies slowly across a triangle shows it, which is why it went unseen; a triangle shorter than that distance is exact. The fix, not made, is barycentrics that need no divide: the pixel's ray against the triangle's plane, as the path tracer's hit is, or 2D homogeneous rasterization (Olano and Greer, 1997). The ground's detail tests draw their sand in metre cells to stay clear of it.

**The reference path tracer** is `shaders/path_trace.slang` with `shaders/sampling.slang` beside it (`path_trace.h`: `PathTraceParams`, 288 bytes via address; `k_pt_uniform_sky`, `k_pt_pixel_center`, `path_trace_group_count`). It is a compute pass with two entry points — `path_trace_main`, which adds `spp` samples to a `float4` accumulator (radiance sum in rgb, sample count in w), and `tonemap_main`, which divides and writes packed RGBA8 through `display_encode`, the transform the resolve ends on, so a reference image and a real-time image are in the same space. It traces **the frame's own acceleration structures**: `renderer::ReferenceRenderer` runs a `SceneRenderer` frame so the cluster chain builds, then dispatches this against the top-level structure in the bindless set, decoding a hit exactly as `ray_visibility.slang` does (GeometryIndex is the visible entry, PrimitiveIndex the triangle). Unidirectional paths, next-event estimation to the sun and the analytic lights with one shadow ray each, the two-lobe BSDF importance-sampled, Russian roulette after three scattering events, and progressive accumulation. Everything below the transport is the shared code: `material.slang` for the surface and the material, `brdf.slang` for the BSDF, `sampling.slang` for the densities. `renderer::ReferenceRenderer` and [renderer](renderer.md#reference-renderer) are the rest of the story, including what the sky does and what the two integrators still disagree about.

`sampling.slang` holds a PCG hash seeded by (pixel, sample index, seed) rather than a counter carried between dispatches — so a capture split into ten dispatches of ten samples is the same image as one of a hundred, and the same seed is the same bytes — cosine-hemisphere sampling, Heitz 2018 visible-normal sampling of GGX with its density, the Fresnel-weighted lobe pick and the mixture density the estimator divides by, Smith's one-directional masking term `ggx_g1` (which the visible-normal density is written in and which nothing in the resolve wants, so it is here rather than in `brdf.slang`), and Veach's power heuristic. **Every light the engine has today is a delta light**, so nothing a BSDF ray can hit is also sampled directly and every MIS weight is 1; the heuristic and its CPU twin are there, tested, for the area and environment sampling that will change that.

`brdf_reference.h` carries all of it in double precision and `tests/sampling_tests.cpp` holds the pair to five properties, none of which needs a GPU: the densities integrate to one by quadrature; a twelve-band histogram of 200,000 half vectors matches that quadrature band by band; a specular sample's weight `f cos / pdf` equals `F G2 / G1` **exactly** (to 1e-6), which is the one check that reaches the narrow lobes a grid cannot resolve; the generator is uniform, in range, and a function of (pixel, sample, seed) alone; and the power heuristic splits one unit of weight between two strategies. The white furnace is measured rather than assumed, at `n·v` = 0.95 — **white dielectric at roughness 1: 0.9726**; white metal at roughness 0.30, 0.50, 0.75, 1.00: **0.9901, 0.9118, 0.6269, 0.3168**. The metal row is the energy single-scatter GGX loses to the microsurface bounces this model does not simulate (what a Kulla-Conty compensation term would give back), and it is a property of the lighting model the real-time path and the reference *share*, so it cancels in a comparison between them rather than showing up as a difference. Half the visible-normal samples at roughness 1 reflect below the horizon and are dropped, which is measured in the same file and is why a very rough metal is the noisiest thing the reference renders.

**Shadows are ray-traced, or for the sun mapped** (docs/plan/04-renderer.md §4.4, "Shadows: RT for the sun and hero lights", and its 2026-09-23 note "shadows without ray queries"). The resolve's shadow query is **one function with two implementations**, `shadow_visibility`, which answers how much of a light reaches the surface (0 to 1): the ray query described here, and the cascaded shadow maps described below it, chosen by `k_shadow_cascades` in `shadow_flags`. `ResolveParams` carries `scene` (the bindless slot of a top-level structure, or `k_no_scene`), `shadow_flags` (`k_shadow_sun`, `k_shadow_lights`), `shadow_bias` in world units and `shadow_bias_steps` in steps of the receiver's own grid. After the surface and the shading normal are known, each light whose bit is set traces one ray query from the surface point **offset along the geometric normal** — the triangle's own plane normal, turned towards the camera, kept beside the interpolated one for exactly this — with the terminate-on-first-hit flag, so any hit ends the traversal and zeroes that light: the sun to infinity, a point or spot light to the distance minus the offset. Ambient and emissive never see a ray.

**The offset is the receiver's, not the scene's** (`ray_offset` in `material.slang`, since 2026-09-26): `shadow_bias + shadow_bias_steps × MeshDesc::quant.w × InstanceDesc::scale_max`, the second term being that many steps of the 16-bit grid of the mesh the pixel is on, through its instance's largest scale. It exists because the resolve reconstructs positions off that grid while the structures are built from the float positions it was rounded from, half a step away on each axis at most — √3/2 of a step along any normal — so a ray from an unmoved surface point can start behind its own triangle and hit it. That gap belongs to the mesh: 0.06 mm on a 4 m wall of the ashlar kit, 7.8 cm on the 5 km terrain it stands on. Until that date the offset was one number for the frame, and `engine-view` passed a thousandth of the scene's radius — which is a couple of centimetres on a sample and **4.1 m on the ashlar ruins' desert**, where every ray from the sand started above every wall and the ruins cast nothing ([renderer](renderer.md#ray-traced) has the diagnosis and the rule's two numbers). The reference path tracer offsets its shadow and bounce rays by the same function (`PathTraceParams::ray_bias`, `ray_bias_steps`), because its hits are rebuilt off the same grid by `fetch_triangle` and the two integrators must start their rays alike. `shadow_bias_steps` defaults to zero, so a caller that sets only `shadow_bias` gets exactly what it always got: the shading test's hundredth of a unit still removes every self-shadowed pixel on its flat quad. **The structure a frame traces is the one it built from its own visible list**, so a shadow can only be cast by geometry the picture holds, at the LOD the picture holds it at, whether the picture was rasterized or traced.

**The resolve runs once per view** ([04 §4.6](../plan/04-renderer.md#46-extreme-displays), `renderer::ViewSet`). It is the only pass of the frame that writes the shared color target, so it is the only one that had to learn where in it a view lives: `ResolveParams` grew from 224 to 256 bytes for `view_x`/`view_y`, which the shader subtracts from `SV_Position` to get a view-local pixel of that view's own region of the visibility buffer, for `out_width`/`out_height`, and for three Panini parameters. The rasterizers and `hiz_build.slang` needed nothing at all, because a view's raster pass sets a viewport at the **origin** of its own source rectangle and its Hi-Z is built from its own region — every shader below the resolve is already view-local. All seven fields are zero for a single view and the arithmetic reduces to exactly what it was, which is why the single-view pictures are byte-identical across the change.

**Panini resampling** is in the resolve too, in the visibility domain. A Panini view rasterizes a *wider rectilinear source* — `panini_oversample(d, half_fov_x)` = `(d + cos t) / ((d + 1) cos t)` times as wide as the picture, which is what it takes never to magnify — and each output pixel maps back through the Panini inverse (`panini_source_ndc`, with `panini_abscissa`'s forward map on the CPU side) to a fractional source position, reads the visibility word there, and takes its barycentrics at that same fractional point. No intermediate color image and no second pass; a visibility id cannot be filtered anyway, which is both why this form is cheap and why the periphery, where the source is several times denser than the picture, point-samples and aliases. At d = 0 the map is the identity and the picture comes back the rectilinear one.

The rays are a **second module of the same source**: `visibility_resolve_rt.slang` is `#define RESOLVE_RAY_SHADOWS` plus `#include "visibility_resolve.slang"`, because `g_scenes[]` is binding 3 of the bindless set and a device without acceleration structures has no binding 3 — a pipeline whose shader declares a descriptor its layout lacks is invalid, so the module every device draws with cannot declare it. Both modules have the same entry points and the same `ResolveParams`; an app picks one at pipeline creation. The render graph gained `Access::FragmentRayQueryRead` (fragment stage, acceleration-structure read) for the resolve pass, since `Access::RayQueryRead` names the compute stage and the resolve is a raster pass. `gpu_ms.shadows` does not exist and cannot: the rays are inside the resolve, so the cost is the resolve's time with shadows on against its time with them off (see [apps](apps.md) for the numbers).

The tests pin the model against a second implementation rather than against numbers written by hand: `tests/brdf_reference.h` evaluates the same BSDF, the same falloff, the same hemisphere of sky and lit ground, the same tangent frame and normal-map perturbation (`tangent_frame`, `map_normal`), and the same gamma on the CPU in double precision, and reconstructs the shaded point as the camera ray through the pixel center. The shading test renders one quad through eight materials (roughness 0.05, 0.3, 0.7, 1.0 at metallic 0 and 1) under a 24° sun and a point light and finds every center pixel and an off-center pixel exactly equal to the reference on the RTX 5090 through the mesh path and on the TITAN Xp through the vertex path (0 of 255 on both, tolerance 2; the quad is drawn through whichever raster path the device has, see Testing); it also checks the normals mode against the plane normal, that a point light 30 units away with a radius of 5 leaves the picture byte-identical to no light at all, and that a white dielectric at roughness 1 under a head-on unit sun reflects 0.3087606 — (1 − 0.04)/π of diffuse plus (1/π)(1/4)(0.04) of GGX — which is 149 of 255 after the gamma. The attributes test tilts the quad's vertex normals 45°, checks the shading and the normals view follow them rather than the plane — and over a sand-coloured ground instead of the neutral one, whose share of the tilted normal's cosine lobe (a seventh) lands on the pixel as the reference says (132 → 139 in red) — and samples a 2×2 checker texture by UV, comparing each quadrant against the reference shaded with that texel as its albedo. A second case puts the two data maps on a flat quad: a 2×2 metallic-roughness map whose quadrants are a rough dielectric, a smooth dielectric, a rough metal, and a smooth metal, each quadrant equal to the reference shaded with that texel's roughness and metallic (0 of 255 on the RTX 5090 and on the TITAN Xp), and a constant normal map tilted 45° about the tangent axis, whose center pixel equals the reference shaded with the normal the frame and the map produce (0 of 255) and differs from the unmapped render by 24 of 255; the same map at `normal_scale` 0 leaves the picture byte-identical to no normal map at all. A map tilted 80° faces away from the camera over 3,850 of the quad's 12,100 pixels while it faces the sun, and every one of them is the reference within 1 of 255 and brighter than the same surface without the sun; and the quad seen from below, whose vertex normals point up through it at the sun, is the reference for a normal of (0, −1, 0), lit by the ground alone, to 0 of 255. A third case holds the emissive and occlusion slots and the UV transform to the reference, which gained the two terms the resolve gained (`emissive_of`: the factor times the sRGB-decoded texel; `occlusion_of`: `1 + strength · (r − 1)`, and `shade(..., occlusion)`, which multiplies the sky hemisphere term by it and nothing else): a 2×2 sRGB emissive texture under a factor, unlit — no sun, no sky — writes the emissive colour through the display transform and nothing else, quadrant by quadrant; the same material lit is the reference with the emission added last; a 2×2 occlusion map at strength 0.75 under the sun and the sky is the reference with that quadrant's occlusion on the hemisphere term; `ResolveMode::Occlusion` returns the same number as an unencoded byte; with the sky at zero — no indirect term — the occluded material and the same material without its map are byte-identical; a quarter turn of `set_uv_transform` on a checker through a repeating sampler moves each quadrant's texel where the CPU's matrix says; and an ORM texture — occlusion in R, roughness in G — named by both the metallic-roughness and the occlusion slot is the occlusion block's reference again. The tolerance is the file's 2 of 255, and 1 on the unencoded occlusion; the RTX 5090 through the mesh path is 1 of 255 at worst.

The shadow case builds the acceleration structures with the KHR helpers — one bottom-level structure with two geometries, the lit quad exactly as the rasterizer draws it and an occluder quad above it that no rasterizer ever draws — so it runs on any GPU with a ray query rather than only on the cluster path, which `engine-view --raster rt` covers. Every covered pixel is compared against the reference told what a CPU ray-rectangle intersection found, with the pixels within a quarter unit of the shadow's edge left out because a fraction of a pixel decides them: the sun's shadow agrees on 1,444 shadowed and 9,600 lit pixels and the point light's on 3,364 and 6,772, **worst 1 of 255 either way**, and every lit pixel is byte-identical to the unshadowed render. A third render traces the same two rays against a scene holding only the lit quad: 0 differing pixels of 16,384 against the render with no rays at all, which is the statement that the bias prevents acne.

**The ground's detail** (2026-09-29; `shaders/ground_detail.slang`, `ground_detail.h`; the scene's side is [renderer](renderer.md#the-sand-close-up)). Wind ripples and grain on a terrain's sand, drawn as **a function of the shaded point's world (x, z)**, the scene's seed and the wind — no texture coordinates, no tiles, nothing to meet at an edge — so it has no seam anywhere a function of position has none and never repeats. The file is shared the way `brdf.slang` is: no binding, no push constant, no entry point, included by the resolve (`visibility_resolve.slang`, so the rasterized picture, the ray-traced path's picture — the same resolve over a visibility buffer the rays wrote — and the traced-shadow module alike) and by the reference path tracer. A material draws it when it carries **`k_material_ground_detail`** and the frame hands over a block (`ResolveParams::ground_detail`, `PathTraceParams::ground_detail`, both blocks 16 bytes larger, 336 and 288); its **sand share** is the metallic-roughness map's **alpha** (`MaterialSample::detail_mask`, 1 without a map), which glTF gives no meaning and every other material ignores. With the flag clear or the address zero the resolve reads nothing it did not read before, which is why no picture moved.

- **The ripples are phasor noise** (Tricard et al., "Procedural Phasor Noise", SIGGRAPH 2019). Complex Gabor kernels — a sinusoid along the wind, turned within a spread of it, under the bell `(1 − r²/R²)³`, which reaches zero *with its slope* at its radius so a kernel leaves no edge where it ends — two to a cell of a jittered lattice of side R, the 3 × 3 cells round the point summed, every centre, phase and turn drawn from a PCG hash of the cell, the seed and the kernel's index. The sum's **argument** is the pattern's phase, and the profile is laid on the phase: a warped cosine that rises over the windward share of a wavelength and falls over the rest, whose slope is continuous because the warp's kink falls where the cosine is flat. **Why phasor noise and not a sum of real Gabor kernels**: a sum of real kernels has a contrast that wanders wherever they cancel and can only ever be a sinusoid, so it can neither hold a ripple's height nor give it a steep lee; the phase has constant contrast and takes any periodic profile — and its **singularities**, where the kernels cancel, are exactly a ripple field's defects, a crest that ends and two that join. How many there are is the kernels' size in wavelengths — a narrower spectrum is longer, straighter crests — so the scene's `ripple_defects` sets R (6 wavelengths at 0, 1.5 at 1) and the spread (2° to 20°). The height is tapered by `|S|² / (|S|² + c²)`, c a third of the sum's rms magnitude, so a defect's core is a crest fading out rather than a point every phase meets at. The gradient is analytic, `taper ∇phase` written as `(S.re ∇S.im − S.im ∇S.re) / (|S|² + c²)`, which stays finite where |S| vanishes. The shading normal becomes `normalize(n − n.y · w · (∂h/∂x, 0, ∂h/∂z))`, the exact normal of the heightfield `H + w h`.
- **The grain** is two octaves of value noise, `grain_size` and a quarter of it, smoothstep-interpolated, one hash a lattice point giving an albedo and a roughness channel; the lattice is counted in tiles of 4,096 cells, since a 5 mm cell 3 km out is 600,000 cells, where a float has four bits left under the point.
- **The filter.** The footprint is the reconstruction's own: `screen_position_gradients` in `material.slang`, `screen_uv_gradients`' arithmetic with the triangle's corners (as edges from the first, since a terrain's corners are kilometres from the origin) in place of its UVs. The ripples fade by the larger, over the two screen axes, of the pixel's step **along the wind** (plus the step across it times the kernels' spread) in wavelengths — a grazing footprint is long and thin, and only its extent across the crests aliases — in **two stages**: the profile's harmonics first, the asymmetry easing to a plain sinusoid between eight pixels a wavelength and four, because the lee is a quarter of a wavelength wide and aliases an octave before the ripple does; then the sinusoid, between four pixels and two (`ground_fade`, `1 − smoothstep(0.25, 0.5, cycles per pixel)`). **The slope variance the two stages take moves into the GGX roughness**, `α² += w² (σ²(a) − fade² σ²(a_drawn))` with `σ²(a) = slope_scale (1/a + 1/(1 − a))`, so distant sand is rougher and not a mirror. `slope_scale` is the profile's `(π A/λ)²/2` times `k_ground_slope_share` (0.65), which is the share of it the pattern actually has — measured over the CPU function, 160,000 points: 1.00 of the block at the defaults, 1.00 at the sinusoid, 1.05 with no defects and 1.08 with the most. The grain fades by its cells against the footprint's longest side. The ripples also fade by the ground's slope (the shading normal's y, which is continuous where the triangle's is not) between `ripple_slope_start_deg` and `_end_deg`, and everything by the sand share.
- **The reference path tracer draws it unfiltered**: a ray has no footprint, and the jittered samples a reference pixel averages are the filter, so a converged reference is what the resolve's fades and roughness transfer stand for.
- **`ResolveMode::GroundDetail`** (9; `--view detail`) draws it as data: R the ripple height over its amplitude at the scene's own profile, B the grain's coarse octave — each a function of (x, z), mapped from [−1, 1] — and G the share of the ripples the pixel draws. With the second pass's spacing R is a function of the normal too, through the wavelength it scales, and G carries the exposure; B, the gradient grain's coarse octave over three of its root-mean-squares (`1 / (3 k_ground_noise_rms)`), stays a function of (x, z) alone. It is what the renderer's seam tests hold to the CPU function at each pixel's own world position, and what they read the normal's step at a ring's border from ([renderer](renderer.md#the-sand-close-up)).

**The CPU mirror and the tolerance.** `tests/ground_detail_reference.h` is the same function in double precision — the same hashes and draws, which are integer arithmetic and so the same kernels, the same kernel, profile, taper, gradient, fades and transfer — beside `brdf_reference.h`, and `tests/ground_detail_tests.cpp` renders sixty metres of sand in one-metre cells (not one quad: the resolve rebuilds a pixel from its triangle's corners projected to the screen, which is meaningless for a triangle reaching behind the camera, and a quad under a walker's feet does) from a walker's eyes looking along it and looking down at the feet, by the origin and 3.7 km out, shaded and in the detail view, and holds every covered pixel to the CPU at the point the pixel sees on **its own triangle** — the visibility buffer names it, its corners are read off the mesh's 16-bit grid as the shader reads them, and the point is clamped into it as `reconstruct_screen` clamps its barycentrics — and the footprint by central differences there. **By the origin, 2 of 255 on both** (1 measured, RTX 5090 through the mesh path, 2026-09-29); **3.7 km out, 4 on the shaded picture and 16 on the detail view** (3 and 14 measured): a float there has a quarter of a millimetre under the point, the reconstruction interpolates corners that far out and is off by about a millimetre, and that is a thirtieth of a ripple's lee, which the raw height channel shows at full contrast. Without a device the same file checks the block the scene's numbers make, the transfer's share (above), and that the function has no seam of its own: along 72,000 half-millimetre steps across lattice cells, kernel edges and phase wraps the height never jumps by more than its slope allows, and the analytic gradient is the numeric one everywhere but at a defect's core.

**The second pass on the GPU** (2026-09-30; its terms are below). The second pass was written where no GPU ran, so until this case the shader's exposure, gradient grain, streaks and spacing were held to nothing but the mirror they were written beside. The same case, a helper taking the block, the ground and the tolerances, draws the ergs' numbers (`ground_ref::erg_numbers`, the desert-erg scene's `detail` block, which the renderer's rings test holds the copy to) with every term on, on five planes tilted along the test's wind so that the shading normal the resolve hands the function is not straight up: **level** (the grain and its normal), **climbing into the wind at 12°** (the spacing, 1.53), **falling away at 14°** (inside the exposure's band, 10° to 18°), and **at 26° and 32°** (the streaks' band, 22° to 30°, and a whole slip face, no ripples) — and adds a third look at each site, **the feet at a millimetre a pixel** (6° over 160 pixels from 1.6 m, the owner's pixel at 11520×2160), since at the other two looks a pixel is a centimetre or more and the grain's coarsest octave, 2 cm, has faded there into the roughness. On a sloped plane the reference needed two things the level one did not. **The pixel's own triangle**: the grid moves a corner off the plane by up to half a step (0.46 mm on 60 m), which turns a triangle by half a milliradian, and through the spacing that slides a ripple's lee by several levels of the detail view, so the reference shades the triangle the visibility buffer names, with its normal. **The resolve's clamp**: a pixel centre within the rasterizer's sub-pixel snap of an edge can be drawn by the triangle across it, and `reconstruct_screen` then clamps the barycentrics and shades the point on the edge — a millimetre from where the ray meets the surface under a grazing footprint a metre long, which read as 10 of 255 on the grain's channel by the origin on the windward slope until the reference clamped too. **No term of the shader differs from the mirror.** By the origin every plane and every look is within **1 of 255**, shaded and on every channel of the detail view (tolerance 2). 3.7 km out the shaded picture is within **4** (tolerance 5; the millimetre look, where a pixel resolves the reconstruction's millimetre in the grain's 5 and 2.5 mm octaves and its normal, 898 pixels of 25,600 over 1 at worst, climbing into the wind; at the feet 3, as the first pass), the share within 1, and the ripple height and the grain within **24 and 25** (tolerance 28), looking down the 32° lee, where the picture runs down the slope to grazing pixels 20 cm long — against the first pass's 14 and 12 on level sand; the gradient grain's coarse octave changes faster with position than the first pass's value noise, and the view shows it raw. The first pass's case is the same helper with the defaults on level sand and its tolerances unchanged, and measures what it always measured: it is the proof the defaults did not move. The numbers per plane, site and look are in [the experiment](../experiments/sand-detail-second-pass-2026-09-29.md#on-the-gpu).

**The third pass on the GPU** (2026-09-30). The third pass was written where no GPU ran too, and the second pass's case stopped at its first line when the ergs' numbers changed under it, so that case now draws the ergs' numbers **as the second pass had them** (its streaks on, nothing of the third pass), and "the resolve draws the third pass's function on sloped sand" draws the ergs' numbers as their scene has them, with a frame's motion (`ground_detail_motion`: 3.7 cm of travel, 2 mm a frame, the avalanche clock a third of the way round): level (the patches and the travel), 12° on a line 50° off the wind (the steering, which has nothing to turn on ground that climbs or falls along the wind: `GroundCase::turn_deg`), the same in a storm half way between the two flattening numbers, and falling with the wind at 27° and 32° (the lanes and their episodes). The shaded picture holds the second pass's tolerance on every plane, lanes included: 1 of 255 by the origin, 4 at most 3.7 km out. One number is wider, the raw ripple height 3.7 km out, 40 for 28: the patches shorten the wavelength to 0.7 of the scene's at the least and spread the kernels further, so the reconstruction's millimetre is more phase than it was (35 measured on the 32° lee, where no ripple is drawn, and 22 with the patches alone switched off; [the measurements](../experiments/sand-third-pass-2026-09-30.md#on-the-gpu-measured-at-the-merge)).

**Exposure** (version 2 of the scene's block, 2026-09-29; `k_ground_exposure`, `ground_exposure`). The ripples' weight is multiplied by how much the ground faces the wind: `1 - smoothstep(tan start, tan end, dot(n.xz, w) / n.y)`, the ground's fall along the wind against the scene's band of lee slope (`GroundDetailParams::lee_tan_start`/`lee_tan_end`, two of the block's three spare words, so it stays 80 bytes). The roughness transfer is weighted by the same weight, so sheltered sand is smooth rather than rough. Without the flag the arithmetic is the first pass's to the bit: `ground_detail_tests.cpp` holds the live mirror with the defaults to the frozen one (`ground_detail_reference_v1.h`) at 4,000 probes, exactly.

**Gradient grain** (version 2, `k_ground_gradient_grain`, `ground_gradient_noise3`, `ground_grain_octaves`). With `GroundDetailParams::grain_octaves` above 0 the grain is three channels of gradient noise (albedo, roughness, height) in that many octaves from `grain_size` halving, each corner's three gradients from one hash (five bits a component), the quintic fade, and the height's analytic gradient leaning the normal by `grain_normal`; the channels are scaled by `k_ground_noise_rms` and `k_ground_noise_slope_rms`, the noise's own root-mean-square value and slope, measured over the mirror and checked there to 3%. An octave fades by `max(footprint, 4 × the float's step at the point)` over its cell, the step read from the position's exponent bits (`asuint(m) & 0x7f800000`, `float_step` in the mirror) so both sides agree exactly. The block grew to 96 bytes for it (`grain_octaves`, `grain_normal`), then to 128 for the streaks and the spacing; `ResolveParams` and `PathTraceParams` hold its address and did not change. Without the flag the first pass's value noise runs, unchanged.

**Grainflow** (version 3, `k_ground_grainflow`, `ground_grainflow`, `k_ground_flow_rms`, `k_ground_flow_slope_rms`). Since the fourth pass (2026-10-03, `ground_lane_set`, `k_ground_flow_directions`): sixteen fixed directions 22.5° apart, each a one-dimensional gradient noise of the position's own coordinate across it, `dot(p, across) / flow_width`, so a lane is a function of position alone and runs without end; the fall line picks the nearest direction and blends the two nearest only over the middle fifth of a sector, normalised by `sqrt((1-w)² + w²)`. The normal moves only that weight. Since the soft cutoff (version 4, `flow_length`, `ground_smooth_d`) each lane is a chain of tongues, one per segment of `flow_length`: a chute with levees easing into a widening lobe with a rounded toe, its height and gradient analytic; three lanes a direction, six lattice hashes a pixel. Each tongue's shape (`GroundTongue`, `ground_tongue`, `ground_lobe`) meanders by two harmonics, pinches, and for three in ten splits into two lobes; its gradient is a forward difference of 2 mm in the tongue's local coordinates, mirrored by `ground_ref::tongue`. The block word that held `flow_cell` now holds `flow_length`, and `flow_widening`'s is `flow_retired`. The third pass's four cells of `flow_cell`, each a fan of lanes widening from its centre line, crossed and beat into ovals ([the experiment](../experiments/sand-fourth-pass-2026-10-03.md)); `flow_cell` and `flow_widening` are retired. The block scales by the lanes' own root-mean-square value and derivative per lane width (0.119 and 0.429), measured over the mirror and held there to 10%. The block grew to **224 bytes** for the third pass (grainflow's eight words and its episodes' three — `flow_share`, `flow_clock`, `flow_clock_step`, `ground_episode` — the patches' four, steering's three and motion's three, three spare). `GroundShading::flow` carries its weight.

**Streaks** (version 2, `k_ground_streaks`, `ground_streaks`, `k_ground_streak_impulses`). Three kernels a cell of a lattice of `streak_length`, each an ellipse down the fall line under `(1 - r^2)^3` with a draw in [-1, 1]; the block scales the sum to unit root-mean-square and its gradient to `streak_normal` by the closed forms in `ground_detail_block` (`E S^2 = k π a b / (21 L^2)`, `E |∇S|^2 = k 0.6 π a b (1/a^2 + 1/b^2) / (3 L^2)`), which the mirror measures to 2% and 5%. The block grew to **128 bytes** for them (eight words, three spare). `GroundShading::streak` carries their weight; the detail view does not show it, since its three channels are the first pass's and the renderer's seam tests read them, and the GPU case above tells the streaks apart by the planes it draws them on (none below 22°, whole on the 32° slip face) rather than by a channel.

**Spacing** (version 2, `k_ground_spacing`). `ground_ripple` takes a `scale` that multiplies the wavelength and the height, `clamp(1 + spacing_gain × climb, spacing_min, spacing_max)` from the pixel's own normal, and the footprint's fade divides by the scaled wavelength; the three words are the block's last three spare ones, so it stays 128 bytes with none left.

**Looking at it without a GPU.** `tests/ground_detail_preview_tests.cpp` evaluates the mirror over patches of sand and shades them with `brdf_reference.h` under a sun 20° up, along the wind and across it, into PNGs in its own scratch directory, which it keeps and names: 2 m from above at 2 mm a pixel on the flat, a 15° windward slope, a 15° lee slope and a 32° slip face; 25 cm at a quarter of a millimetre on the flat, where the grain is judged; and a walker's view from 1.65 m, on the flat and on the lee slope, with the footprint by central differences. Each is drawn twice: `before_*` by `tests/ground_detail_reference_v1.h`, the first pass's mirror frozen as it merged, and `after_*` by the live one, with the masks beside them. It is skipped unless asked for (`engine_gfx_tests -tc="ground detail preview*" --no-skip`, about half a minute in a debug build), so the suite's time does not move.

**The sun's cascaded shadow maps** (2026-09-24) are the other implementation, for a device without ray queries — every baseline-tier card — and for `--shadows csm` anywhere a raster path resolves the picture ([renderer](renderer.md#shadows) has the frame side: the fit, the light-view cull, the atlas). What this module owns of them:

- **The interface.** `k_shadow_cascades` in `shadow_flags` says the sun's shadow is read from the block behind `ResolveParams::shadow_maps`, a `ShadowMapParams` (400 bytes, read through its address): up to `k_max_shadow_cascades` (4) `ShadowCascade`s of 80 bytes — a world-to-tile matrix whose depth runs 1 at the light's side to 0 away from it (reversed, like every depth here), the world size of a texel across the light, the world depth range, and the constant bias in depth units — then the light's frame (`light_right`, `light_up`, `light_dir`), the cascade count, the texels a side, the atlas's bindless image slot, a bindless sampler slot (nearest, clamped), `max_slope`, the atlas's width in tiles (`tiles`, the cascades it was allocated for, which a frame may not all use) and `normal_offset` (below). `shadow_maps` took `ResolveParams`' last pad word, so the block is still 304 bytes and every caller that does not draw maps sends zero. The maps shadow **the sun alone**: with the bit set, `k_shadow_lights` is ignored and the point and spot lights are unshadowed.
- **The arithmetic the CPU and the shader share**: `shadow_light` (the light's frame: world up across it unless the sun is overhead), `shadow_snap` (a centre moved across the light to whole texels, so a moving camera moves the grid by whole texels and a static shadow does not shimmer), and `make_shadow_cascade` (a sphere of receivers plus how far towards the light the casters reach, as the matrix and the three numbers above).
- **The filter: 3×3 bilinear PCF**, nine bilinear taps a texel apart, which is a 4×4-texel footprint with separable weights (1 − f, 1, 1, f)/3 per axis. It is evaluated as **four gathers** of the depth atlas rather than nine hardware comparison samples, because a comparison sampler compares every texel of a tap against one reference and the bias below needs a reference per texel. The cascade is the first whose tile holds the whole footprint and whose depth range holds the point; a point beyond the last is lit. A penumbra is therefore about three texels wide, which is sub-pixel wherever the cascade fit matches texels to pixels, and the shadow view shows it as grey between black and white. **What it costs** is the resolve's growth: 0.020–0.061 ms on a frame-filling terrain from 1080p to 4K on the RTX 5090, and 0.19–0.71 ms (about 85 ps a pixel) on the TITAN Xp. On Pascal that is more than every pass that draws the maps ([the measurement](../experiments/cascaded-shadow-maps.md#what-the-maps-cost-two-scenes-three-resolutions-the-e1-reruns-method)); a one-gather filter for the baseline tier is a follow-up there.
- **The bias is the receiver's own plane.** Every texel of the footprint is compared against the depth the receiver's plane has *at that texel's centre*, read off the geometric normal in the light's frame — which is exactly the depth the rasterizer wrote there for the receiver's own triangle, since the maps are drawn from the same 16-bit grid (or the same pool block) through the same arithmetic. A flat receiver therefore never shadows itself at any angle, and the kernel's width costs no extra bias. On top of it `ShadowCascade::bias` is a constant half-texel (`renderer::k_shadow_bias_texels`) for what is not planar across the footprint — curvature, a neighbouring triangle — and for the float distance between the resolve's reconstruction and the rasterizer; the slope is clamped at `max_slope` (tan 83°), which only a grazing receiver reaches.
- **The normal offset is for what the plane cannot see.** The point looked up leaves the surface along its geometric normal by `normal_offset` texels of the cascade read (`renderer::k_shadow_normal_offset_texels`, 3) times (1 − N·L): nothing on a surface that faces the sun, where the receiver's plane is exact; the whole offset at grazing and on a surface that faces away. The receiver's plane is exact for a flat receiver only, and a low-poly curved one shadows itself in two places without the offset: in every **concave crease**, where the neighbouring triangle rises above the receiver's plane inside the footprint, and along the **terminator**, where a triangle whose geometric normal just faces away from the sun still has a shading normal that faces it (so the shading asks) — the first version answered 0 there by rule, and a ray lifted off such a triangle skims the convex surface and reaches the sun, so the two implementations disagreed in a band a triangle wide. A lookup lifted clear of the footprint escapes the same way. On the Khronos samples it took the maps' interior disagreement with the rays from tens of thousands of pixels to none ([renderer](renderer.md#cascaded-shadow-maps) has the counts, and the offsets that were tried), and on the flat fixtures it moves nothing: the lift at the fixtures' 24° sun is a quarter of a texel.
- **Depth-only pipelines.** `GraphicsPipelineDesc` and `MeshPipelineDesc` take a null `fragment` for a pipeline with no fragment stage, which is how a cascade is drawn: the picture's own mesh or vertex stage, depth tested and written, nothing shaded. `create_image_view` names the depth aspect for a depth format, which the render graph's depth attachments (the direct path's, the shadow atlas) and a sampled depth image both need; it named the colour aspect for every format before, which is invalid usage however quietly it drew.
- **`DeformAllocParams::first_entry`** replaced `run`: the pool allocator took a run index and computed the run-major entry `(run × views + view) × pairs`, and a shadow cascade's run is behind every view's three, where that formula cannot reach. The caller now says where view 0's run starts, which for the camera's runs is the same number as before.

The maps' shadowed-pixel case (`material resolve: cascaded shadow maps against the geometry the rasterizer drew`, beside the ray-traced one in `shading_tests.cpp`) is the same comparison with the occluder drawn into a 512-texel depth map by the cluster rasterizer — through the mesh path and the vertex path, each where the device has it — and not into the picture. **Its tolerance is the filter's footprint, stated where it is computed**: a pixel whose sun ray passes within 0.345 world units of the occluder's edge is left out, which is the ray-traced case's quarter unit plus three texels (2.8 cm each here) over the cosine of the sun's 24°, because the farthest footprint centre is two and a half texels from the point along an axis and a distance across the light is at most 1/cos 24° longer on the horizontal occluder, plus the normal offset's lift (a quarter of a texel at 24°) times tan 24°, a third of a centimetre. The case sets the renderer's offset of three texels. Everywhere else a shadowed pixel is the reference with the sun removed and a lit pixel the unshadowed picture byte for byte. On the RTX 5090, both paths: **1,296 shadowed and 9,396 lit pixels within 2 of the reference, worst 1 of 255**; 1,408 pixels in the band, 180 of them penumbra grey; 0 self-shadowed pixels on the flat quad at the 24° sun **and at a grazing 75° one**, which is what the receiver-plane bias is for; the point light's bit changes nothing; and the mesh path's map and the vertex path's give the same shadow to the byte. The TITAN Xp, through the vertex path alone (it has no mesh shaders), gives the same counts to the pixel.

**Baseline tier: the vertex-shader cluster path.** GPUs without mesh shaders (Maxwell, Pascal, integrated parts) draw the same clusters into the same visibility buffer from the same cull pass through the vertex pipeline, pulling positions through device addresses as the mesh shader does. Occlusion culling, LOD selection, and the resolve are unchanged. The path has two draws, and the renderer picks between them by one device feature.

- **The indexed draw** (`cluster_vertex_indexed.slang` and `vertex_expand.slang`; the renderer's culled draw on every device with `geometryShader` and `fullDrawIndexUint32`) draws one hardware run of the visible list as **one `vkCmdDrawIndexedIndirect` of exactly the triangles its clusters hold**. The cull pass's `cull_vertex_main` entry point allocates each hardware survivor's triangles under an atomic cursor in the run's `VertexDrawHeader` and writes its `VertexDrawRecord` — instance, cluster, first triangle, overflowed — at its slot; `expand_main`, dispatched indirectly with one 64-lane workgroup per survivor, writes three `u32` indices a triangle, each `slot << 8 | local vertex`, and finishes the draw's index count. An index therefore names one vertex of one visible entry's cluster, so the post-transform cache shades a cluster's shared vertices once instead of once per triangle corner, and the vertex shader gets from the index to the record, the cluster and the position with nothing else. The fragment stage writes the word every rasterizer writes: `SV_PrimitiveID` counts the draw's triangles, the vertex stage hands down `(pair << 8) − first triangle` as a flat value, and the sum is the visibility id. `SV_PrimitiveID` in the fragment stage of a vertex pipeline is SPIR-V's `Geometry` capability, which Vulkan grants with the `geometryShader` feature although no geometry shader exists here — hence the Optional row, and a module of its own so that `cluster_vertex.slang` still loads on a device without it. The index's slot in the upper 24 bits is also why the draw wants `fullDrawIndexUint32`: from the 65,537th cluster of a run its index values pass 2^24 − 1, the most a device without the feature has to honour. The slot itself cannot outgrow 24 bits, because a run holds at most the scene's pairs, which the visibility id's 24 bits already bound. `Access::IndexRead` covers the index fetch and `Access::IndirectRead` the header, and the expansion is a pass of its own rather than a loop in the cull pass's survivor tail because one thread striding over its own cluster's triangles cost the TITAN Xp's cull pass 0.08 ms at 6,000 survivors; the survivor-tail step it does keep is compiled into its own entry point (`cull_pair(pair, vertex_draw)`, `[ForceInline]`), because on the RTX 5090 any code in that tail cost every path 2 µs a frame even behind a uniform branch that skipped it.
- **The capacity draw** (`cluster_vertex.slang`'s `vs_cluster`) is what the path drew until 2026-09-24, and what it still draws without either feature and with culling off: one instance per visible cluster and a fixed vertex count of three times the cluster build's triangle capacity (`ClusterDrawParams::triangles_per_cluster`, 124 — 372 vertex invocations a cluster), the vertex shader mapping `SV_VertexID` to a local triangle and corner and collapsing the vertices of triangles past the cluster's count so they never rasterize. The cull pass counts survivors into the instance count of a `vkCmdDrawIndirect` block instead of the mesh-task group count (`CullParams::count_index` = 1, arguments prefilled `{vertex_count, 0, 0, 0}`), and `Access::VertexRead` covers the vertex stage's read of the visible list. It is also the indexed draw's **fallback**: a run's index array is a budget (the renderer's is 2^20 triangles, 12 MiB, or the scene's own bound when that is smaller — [renderer](renderer.md#statistics)), and a survivor whose triangles do not fit is flagged in its record and drawn by `vs_cluster_fallback`, the capacity draw instanced over the slots up to the highest one that overflowed with every entry that did fit collapsed. Allocation is in atomic order, so the survivors that fit are exactly those allocated before the first that did not (`fit_end`) — not the same ones every frame, which cannot change the picture (a fallback draw writes the same words) but does change the frame's cost — and nothing is ever missing from the picture; the frame is slower and says so.

**Why indexed — measured, on the TITAN Xp** ([E1 on Pascal](../experiments/e1-pascal-rerun.md#after-the-vertex-path-draws-the-cuts-own-triangles)). The rerun found the capacity draw losing to the software rasterizer on 64 FlightHelmets at a fine cut and blamed its 372 invocations a cluster. That was half right. On Pascal the raster pass of that scene is the vertex stage and nothing else — culling every triangle after the vertex shader, or dropping the fragment atomics, moves it by 1% — at about 5 ns per 32-lane warp of real vertices, and warps wholly past a cluster's count turned out nearly free: what the capacity draw wasted was three invocations per triangle *corner*, not the invocations past the count. Three ways of drawing only the real triangles were built and measured before this one and rejected: a draw per cluster through `vkCmdDrawIndirectCount` (a fixed 0.48 ms plus 17 ns a draw, more than the pass it replaces), a per-triangle table drawn three vertices a triangle (−23% to +7%, because it still runs three invocations a corner), and chunks of 8 to 32 triangles (worse than both). Indexing is the one that shares the vertices, and it took the helmet grid's raster pass down by 42–48% on the TITAN Xp, the expansion included, which puts it under the software rasterizer's at every resolution measured and removes the crossover the rerun found. What it costs: the expansion (9–28 µs on the helmet grid), `SV_PrimitiveID` (11–13% of the draw — a per-primitive cost on Pascal), and on the heightfield, whose raster pass is mostly fragment atomics and had little vertex work to save, a net 6–24% (0.001–0.05 ms) that is the expansion plus a few percent on the fragment side nothing measured explains. **On the RTX 5090 the same draw is 7–22% slower than the capacity draw on the helmet grid** (0.0448 against 0.0379 ms at LOD 0.25 and 1080p, cull and expansion included), because there the vertex front end is not the bottleneck and the extra pass and the index fetch are. The 5090 draws the mesh path and never takes the vertex path unless asked, so the renderer chooses by the feature alone; a baseline-tier GPU that behaves like the 5090 rather than like Pascal would want the choice made per device, and none has been measured.

The vertex path test draws a terrain's leaf clusters through the capacity draw and the mesh path and finds the visibility buffers identical to the pixel, and the indirect draw equal to the direct one. Its indexed case draws the terrain's LOD cut — 24 clusters holding 2,045 triangles against 2,976 of capacity — through `cull_vertex_main`, the expansion and the indexed draw twice, once with the whole budget and once with a third of it, and checks the bookkeeping exactly (the survivors' records partition the cursor's range in allocation order, every index is its slot and the cluster's own local vertex, and the small budget sends 17 of the 24 clusters to the fallback with their records flagged) and the picture against three others: the capacity draw over the same list (0 pixels of coverage and 0 of surface apart), the software rasterizer over it (1 pixel of coverage, 12,292 of 12,305 the same id), and — where the device has mesh shaders — the mesh path (0 and 0); the small budget changes no pixel. It needs `geometryShader` and `fullDrawIndexUint32` and is the one case that skips without them; on a device without mesh shaders the software rasterizer is its independent reference.

**Acceleration structures and ray queries.** `acceleration.h` is the ray tracing side of docs/plan/04-renderer.md §4.4 on the first-class path (VK_KHR_acceleration_structure, the fallback the plan keeps whatever experiment E2 decides). A bottom-level structure takes one geometry per visible cluster (`ClusterGeometry`: float3 positions and 16-bit local indices, which `expand_packed_triangles` widens from the cluster format's packed bytes) and a scene builds one per instance, so a hit's GeometryIndex plus `RayVisibilityParams::instance_base` names the visible entry and PrimitiveIndex the triangle, and the ray pass turns the entry into the scene's pair through the visible list, the instance and the mesh (`RayVisibilityParams::visible`, `instances`, `meshes`) so that it writes the word the rasterizer writes; `create_blas`/`build_blas`, `create_tlas`/`write_instances`/`build_tlas`, `create_scratch` (aligned to the device's minimum), `acceleration_build_barrier`, and `destroy_acceleration_structure` split object creation and size queries from the recorded builds so builds batch and scratch is reused. Top-level structures live in the bindless set (binding 3, see below) because a shader cannot trace against a device address. `ray_visibility.slang` (`ray_visibility.h`: `RayVisibilityParams`, 208 bytes via address) shoots one ray per pixel center through the same view-projection as the rasterizer with a `RayQuery` and writes the visibility buffer's 64-bit word (the cluster path needs no remap at all, since a CLAS record carries its own base geometry index), so the RT and raster pictures compare word for word. The ray query test builds a terrain's LOD cut both ways and finds identical coverage on 12,306 pixels, 17 shared-edge pixels naming the other triangle, and depth agreeing to 1.4e-6; tracing the 24-cluster cut costs 9 µs at 320×240 on the RTX 5090 against 5 µs of rasterization.

**Cluster acceleration structures (experiment E2, ADR-0025).** `cluster_acceleration.h` is the NVIDIA path (`VK_NV_cluster_acceleration_structure`, `DeviceFeatures::cluster_acceleration_structure`): `create_cluster_set` sizes storage for up to N cluster acceleration structures and `build_cluster_set` builds them in one indirect command from a device array of per-cluster records (`ClusterBuildInput` written by `write_cluster_build_records`: float3 positions, tightly packed 8-bit indices from `pack_cluster_indices`, the cluster id as `ClusterID` and as the base geometry index) whose count may itself be a device address, so the frame's GPU-selected cut can build without a round trip; the driver packs the structures into one buffer and writes each one's address and size to host-visible arrays. `create_cluster_blas`/`build_cluster_blas` make a cluster bottom-level structure over those addresses, and its address goes into a standard `TlasInstance`, so the top-level structure and `ray_visibility.slang` are shared with the KHR path. Ray queries traverse cluster structures from a compute pipeline with no opt-in.

**`pack_cluster_indices` appends to its output and does not clear it**, which is what a whole mesh packed in one call wants and is a trap for anything that packs a *piece* at a time into a scratch buffer it reuses. A caller that packs per page or per cluster clears the vector itself and, more importantly, **sizes the copy out of it from the piece rather than from the vector** — three bytes a triangle of *that* piece. Geometry streaming got this wrong once and it cost a device: a page staged the concatenation of every page before it, which put another page's triangles in the pool and ran the write off the end of the staging ring onto a live host-visible buffer ([renderer](renderer.md#a-pages-8-bit-indices-are-its-own) has the whole story and the rule it left behind). The signature stays append-only because `GpuScene::create_ray_tracing` and the cluster acceleration structure tests build one array out of many calls; what changed is that the per-page caller now states the byte count it means.

Per frame, from the GPU's own cut, over a scene: `clas_records.slang` (`ClusterRecordParams`) turns the cull pass's visible list and count into the build records in three small passes, because a scene builds **one cluster bottom-level structure per instance** and an instance's records therefore have to be contiguous while the cull's atomics leave the list in whatever order they produced. `records_main` buckets each visible entry into its instance's slice of a pair-indexed scratch array — a drawn entry from the bottom of the slice up (`first_pair * views` plus a per-instance atomic), a shadow caster from the top down (below) — and counts both; `ranges_main` decides what the set's **capacity** keeps (below), prefix-sums it into the dense bases, writes the total the CLAS build reads from the device, and writes one 16-byte bottom-level record per instance over that instance's run of CLAS addresses; `emit_main`, one thread per pair slot, moves the kept entries down into the dense records array — an instance's drawn clusters, then its casters — and writes the 64-byte build record there, with the **visible entry as the record's cluster id and base geometry index** so a hit's GeometryIndex is the same word the rasterizer would have written. Then one `build_cluster_set` over the dense array, **one `build_cluster_blas_set` for every instance's structure**, a copy of each structure's address into its top-level record, and one top-level build with an instance per scene instance whose transform is the world matrix and whose custom index is the instance. The render graph orders it all through `Access::AccelerationBuildRead`/`AccelerationBuildWrite` (the build stage), `TransferRead`/`TransferWrite` (the address copy) and `Access::RayQueryRead` (the traversal), so the builds, the trace, and the resolve are barriered from declared accesses like every other pass. **With more than one view the geometry is the union of the views' cuts**, under one top-level structure, which is what §4.6 asks a `ViewSet` to share. The view count (the low half of `ClusterRecordParams::mode`) is what makes the bucketing fit: an instance's slice is `views` times its mesh's cluster count, because in the worst case every view draws every cluster of it, and the renderer lays the visible list out run-major so that every view's first run is one contiguous range at the front and one `records_main` dispatch covers them all, reading each view's own count word `k_draw_args_bytes` further into the indirect buffer. The per-run clamp is `pair_count`, which is the right bound, since a run is filled by one atomic over a dispatch of `pair_count` threads. Two views at different LOD thresholds put two levels of the same surface into one structure — see [renderer](renderer.md#multi-view-a-viewset-over-one-scene) and [E9](../experiments/e9-multi-view.md).

**The set is sized by the frame, and what it cannot hold is dropped by a stated rule (2026-09-24).** Until this date the renderer created the CLAS set for `views * pair_count` clusters — any pair could be in some frame's cut — and the driver reserves every one at its worst case, 6,144 bytes for 124 triangles and 64 vertices on the RTX 5090 at driver 610. That was 16.2 GB of cluster structures for the desert overlook's landmarks on a surround, whose frames build at most 43,291. Three things in this header make a frame-sized chain possible, and the renderer's half is [renderer](renderer.md#the-ray-tracing-chains-memory):

- **`ClusterRecordParams::capacity`** is how many structures the set was created for, and `ranges_main` never keeps more. Past it the frame drops **whole instances**: every instance's drawn clusters in instance order while they fit, an instance that does not fit skipped entirely (its casters with it), then the other instances' casters the same way from what is left. Whole instances because a partial one would keep whichever clusters the atomics bucketed first, which is not the same twice; casters last because they add only the shadows of surfaces facing away from the camera. **`ranges_main` is one workgroup of 256 threads** (2026-09-30): each sums a run of the instances and the group scans the runs, which is the whole pass when everything the frame wants fits — nothing dropped, the bases the prefix sum — and only a frame over its capacity takes the rule above on one thread, which is the one place that sees every count in instance order. It was one thread throughout, sized for the scenes of its day ("at 90 instances it is nothing"); the world's tiles made a scene of 40,000 instances, one a tile slot, and at 1080p on the RTX 5090 the chain took 7.50 ms a frame at the median over `desert-endless`'s first minute with that thread, and 0.67 ms over its whole flight with the group (the whole frame 8.11 and 1.36; [the flight](../experiments/world-tiles-flight-2026-09-30.md)). `clas_records_tests.cpp` holds both paths to the rule over 1,337 instances at four capacities, word for word. `record_count` is four words (`k_cluster_record_count_words`): built, wanted, instances that lost their drawn clusters, instances that lost only their casters, so a host can size the next frame and say what this one dropped. The word came from packing the view count and the instantiate flag into `mode` (`cluster_records_mode`); the block is still 128 bytes, and `instance_counts` is three words an instance (drawn, casters, base).
- **`ClusterBlasSet`** builds every instance's bottom-level structure in **one** command, with implicit destinations, into one buffer sized for the set's total cluster references (`max_clusters`) rather than for each instance's worst case. A structure built to an explicit destination has to be reserved for everything it could hold, which summed over a scene's instances is `views * pairs` again; and the one command replaces a build per instance, each waiting for the last because they shared the scratch. The price is that each structure's address is known only on the device after the build, so the top-level records — transforms and custom indices written once, at load — take it by a `vkCmdCopyBuffer` of eight bytes an instance from `ClusterBlasSet::addresses`; an instance the frame built nothing for gets a null reference, which the top-level build treats as inactive. `ClusterBlas`, the explicit per-structure form, stays for the tests and the experiments that build one structure.
- **`cluster_set_build_sizes`** and **`cluster_blas_set_build_sizes`** return what a set of given limits costs before anything is allocated, so a byte budget becomes a cluster count; the storage is linear in the count. Both return false for limits the device refuses (`limits_fit`: the triangles and vertices a cluster, and the geometry index) and for a driver answer of zero bytes, which is how a driver refuses a size query — it has no error code to give — and `create_cluster_set` says which row failed and by how much.

**What a set can name is not what it can hold (2026-09-25).** The capacity bounds how many structures a set holds; the limits' `max_geometry_index` bounds the largest base geometry index any of them may carry, and the device bounds that: `VkPhysicalDeviceClusterAccelerationStructurePropertiesNV::maxClusterGeometryIndex`, **16,777,215 on the RTX 5090 at driver 610** — the record's 24 bits, which `write_cluster_build_records` and `clas_records.slang` mask to as well. It is the one cluster limit the extension reports that a *scene* can exceed (the rest are per cluster, or alignments; nothing bounds the cluster count of a set or of a bottom-level structure), so it is also `DeviceFeatures::cluster_max_geometry_index`, where the renderer can read it before creating anything. Because a record's base geometry index is its **visible entry**, the renderer's range is the scene's pairs times its views, three times that with the shadow casters' run — a function of the scene and the view layout, never of the frame's size or the capacity. The ashlar ruins (3,699,274 pairs) on a three-view surround asked for 33,293,465 and every size query refused them, which surfaced as the renderer's "the driver gave no cluster acceleration structure sizes" at 640×360 as at 11520×2160; with one view the same scene asks for 11,097,821 and builds. What the renderer does about it is `renderer::resolve_settings`'s ([renderer](renderer.md#the-ray-tracing-chains-index-space)). Naming a hit by a dense record index and a record-to-entry table would bound the range by the capacity instead, at the cost of one dependent load in every consumer of a hit (`ray_visibility.slang`, `path_trace.slang`) and of the records staying byte-identical to `write_cluster_build_records`; it is not built.

**Templates are packed to their size.** `create_cluster_templates` reserves the driver's worst case for every template — about 2.2 KB on the RTX 5090, where the desert overlook's templates occupy 504–532 bytes once built. `create_packed_cluster_templates` does the job at load in three blocking steps: the template build in `COMPUTE_SIZES` mode writes each template's size, the host packs them back to back at the template alignment, and the build runs again in `EXPLICIT_DESTINATIONS` mode into one buffer of exactly that sum, with its scratch allocated and freed inside. The addresses array then holds each template's explicit destination, which is what an instantiate record names, so nothing downstream changes.

**Shadow casters (2026-09-24).** The cull pass's normal-cone test answers a question about the *camera*, and the structures above are built from the cull pass's output, so until this date a cluster that faced away from the camera stopped casting shadows as well. A card seen from behind cast none, and a closed box lit from one side and seen from the other lost every shadow ray that enters its bottom and leaves by its lit side. [geometry](geometry.md#normal-cones-fit-to-what-is-drawn) has the fixture, the samples and the options that were weighed. What the RHI now does about it:

- **`CullParams::casters` and `caster_count`** (432 bytes, from 416). When they are set, a pair that the cone test alone rejected is not dropped. It takes the rest of the pass's tests exactly as a drawn pair does: the cut, the page residency, and the Hi-Z (which never runs beside casters, because the ray tracing chain turns occlusion culling off). A survivor goes into a run of its own, `k_caster_run`, which is the software rasterizer's run, because a frame that builds ray tracing geometry never splits clusters off to software. Its counter is the first word of that view's software argument block. A caster is not flagged as drawn. Both fields null is what every caller but the renderer with traced shadows passes, and the pass then drops the pair as it always did.
- **`clas_records.slang`** buckets that run of every view beside run 0. `ClusterRecordParams::caster_count` is view 0's count word, and the per-instance slices still fit, because in one view a pair is drawn or a caster, never both. `emit_main` writes a caster's record **without** `VK_CLUSTER_ACCELERATION_STRUCTURE_GEOMETRY_OPAQUE_BIT_NV`. `ClusterBuildInput::opaque` is the CPU half, so the records test holds the flag to `write_cluster_build_records` like every other byte, over a run of casters of its own.
- **The flag is how a traced consumer tells a caster from the picture.** `ray_visibility.slang`'s primary ray and the path tracer's camera ray trace with `RAY_FLAG_CULL_NON_OPAQUE`, so they never see a caster, and the ray path stays the raster picture word for word. Every shadow ray and every bounce traces with `RAY_FLAG_FORCE_OPAQUE` and stops on one. KHR geometry is built opaque and every CLAS record was opaque before, so neither flag changes a picture that has no casters.
- **`ClusterRecordParams` is still 128 bytes**, the largest push block the renderer allows. The dense record bases moved into `instance_counts` (the last third of it since the capacity rule above, which counts drawn clusters and casters apart), and the word that `instance_first` used to hold is `caster_count`. The caster run's position is `k_caster_run`, mirrored in the shader, rather than another field.
- **A template cannot carry the distinction.** An instantiated cluster takes its geometry flags from its template, which is opaque, so the renderer asks for no casters under `--rt-templates`. Templates are for deforming meshes, which are never cone-tested, so what that gives up is a rigid instance's casters.
- **`ResolveMode::Shadow`** (6) is the resolve's shadow view: the sun's shadow query alone, white where the ray escapes, black where it is blocked, and mid grey where the surface faces away and no ray is traced. It asks the shaded view's exact question, with the same normal and the same origin. That makes it the picture a shadow comparison counts, and it is `--view shadow` on engine-view.

The records test asserts the shader's bytes equal `write_cluster_build_records`' for the same clusters, and its second case holds the capacity rule: a set one caster short keeps every drawn cluster and drops the casting instance's casters whole; a set that holds one instance's drawn clusters keeps that instance and drops the other; and a large instance that does not fit does not starve a smaller one behind it, losing its casters with its drawn clusters. `engine-view --raster rt` runs the whole chain every frame. The comparison test builds a terrain cut both ways: pixel-identical pictures, 2.9× to 3.3× less memory (about 14 bytes per triangle against 62), 1.2× to 2.6× faster builds, the same trace time (docs/experiments/e2-cluster-acceleration.md).

**Deformed clusters: the per-frame vertex pool (experiment E25, ADR-0026 decision 7).** Skinning and cage deformation are one path in this renderer ([04 §4.3](../plan/04-renderer.md#43-geometry)): a compute pass fills **one per-frame pool of deformed positions**, and every position reader takes an instance's positions from there instead of from the mesh's 16-bit grid. The pool is plain `float3` — 12 bytes a vertex, three times the quantized stride — and that is deliberate: it lives for one frame, it is sized by the LOD cut and not by the scene, and a second quantization grid per frame would have to be computed from data nobody has read back. A `DeformDesc` (`cluster_cull.h`, 16 bytes) per deformed instance says which deformer it plays and, for a skinned one, where its bone matrices are; `InstanceDesc::deform` is the index into that table and `k_invalid_deform` means rigid, which is what an instance is by default, so the rigid path is untouched down to the instruction.

**Where in the pool is per frame and per visible entry, not per instance.** E25 gave each deformed instance a block as long as its mesh's whole cluster-ordered vertex range and `DeformDesc::pool_offset` was the bias into it. That kept a cluster's vertices contiguous — which is what a CLAS record needs — but it sized the pool by the *population*: 12.2 MB for 1,024 foxes, 1.7 GB if they had been FlightHelmets, to write the ~1,300 clusters a frame draws. The pool is now a **budget**, suballocated every frame by `deform_alloc.slang` from the cull pass's own visible list: one block per entry, exactly that cluster's vertex count, packed from the front. `MeshDesc::deform_slots` is the result — one `u32` per entry of the whole visible list, its block's first pool vertex or `k_no_pool_slot` — and it took over the word that held the `DeformDesc[]` address, so `MeshDesc` is still 64 bytes and a position read is one indirection shorter than it was. A cluster's vertices are still contiguous, because a block *is* a cluster.

The pool's address and the slot table's ride in `MeshDesc`, which grew from 32 to 56 bytes for them and for `templates`, and to 64 when skinning added the binding stream ("Skinning", below). They are the *scene's*, not the mesh's, and repeating them per mesh is redundant — but `ClusterDrawParams` is exactly 128 bytes, which is the largest push block the renderer allows and the Vulkan guaranteed minimum, and every position read already holds the `MeshDesc`. The choice was that redundancy against packing `width`/`height` and `visible_offset`/`triangles_per_cluster` into bitfields to free eight bytes, and the redundancy is the one that does not make three rasterizers and a dozen tests harder to read. `scene.slang` therefore has two functions that decide: `deform_base(mesh, instance, entry)`, which every reader calls **once per cluster** to turn a visible entry into a pool block base, and `load_position(mesh, base, cluster_vertex_offset, local)`, which reads the pool when there is a block and the mesh's grid when there is not. `load_quantized_position` is the rest-pose read the pool pass itself uses. **Anything that reads a position calls `load_position`** — the mesh, vertex, and software rasterizers, the resolve's `reconstruct` and `tangent_frame`, and, as an address rather than a value, `clas_records.slang`'s `emit_main`. Resolving the base per cluster instead of per vertex is why the extra table costs nothing: the old form read a `DeformDesc` on every position read.

`deform.slang` (`DeformParams`, 88 bytes of push constants) is the pass: one 128-thread workgroup per entry of **one run of the cull pass's visible list**, dispatched by `vkCmdDispatchIndirect` from a copy of that run's own count word, so the cut's size never reaches the CPU. A workgroup reads its entry, drops it if the instance is rigid or if the allocator refused it, dequantizes the cluster's vertices, applies the instance's deformer, and writes its own block. Every other slot of the pool keeps whatever it held, which is the cost rule stated as behaviour and asserted with a sentinel fill in the test.

`deform_alloc.slang` (`DeformAllocParams`, 72 bytes) is the allocator that runs before it, once per run of the list: **one workgroup**, a prefix sum over the entries' vertex counts, looping the views inside the dispatch so that the three runs and every view share one budget through a groupshared cursor rather than a global atomic. That matters because the cursor has to advance by what was *placed*, not by what was asked for — a block that refuses one large cluster must not charge the budget for it and refuse every small one behind it. It costs about 5 µs per 1,000 visible entries, which is the same order as the pool pass at ordinary cut sizes and the one thing here worth making parallel (see [renderer](renderer.md#the-deformed-vertex-pool)). **Overflow is a stated behaviour, not an error**: an entry the budget cannot fit gets `k_no_pool_slot`, every reader — the three rasterizers, the resolve, and the CLAS records — falls back to that cluster's **rest pose**, and `gfx::DeformAlloc` counts the entries and the vertices refused. Never a crash, never a garbage address, and never a silent one: the renderer warns once and the summary carries the counters. Two deformers stand in until the solver exists: `wave`, a sinusoid along the vertex normal, and `lattice`, a 3×3×3 trilinear free-form-deformation cage whose box is **the mesh's own quantization grid** — `geometry::quantize_positions` anchors that grid at the bounding box's low corner and gives it the largest axis extent, so it is a bounding cube already on the GPU and the cage needs no authored bounds. Occlusion culling splits the cut across two runs, so engine-view runs the pass once per run, each before the draw that consumes it.

**The one rule a deformer has to obey, and what breaks when it does not.** A deformed position must be a function of quantities the cluster build guarantees *every copy of a surface point* shares. Position is such a quantity: duplicates across clusters hold the same quantized bytes, and the LOD DAG locks group-boundary positions across levels. A **vertex normal is not**: welded duplicates at a hard edge are separate vertices with different normals, and a simplified level recomputes them even where the positions are locked. `lattice`, a function of the rest position alone, is crack-free; `wave`, which displaces along the normal, tears the FlightHelmet's surface open along its hard edges and its LOD-group boundaries at 5% amplitude while the lattice at the same amplitude is whole ([E25](../experiments/e25-deformed-clusters.md) has the comparison). This is not a bug in the pass and not something the pass can fix — it is the constraint the real cage-to-surface transfer inherits, and it says the per-vertex cage binding of [07 §7.10](../plan/07-content-pipeline.md#710-deformable-volume-assets) must be derived from position and stored per vertex rather than recomputed per level.

**Cluster templates.** On the ray side a deforming mesh has two options, and both are measured. The **rebuild** is the existing chain with the records' vertex address pointing into the pool. The **templates** variant builds one `VK_CLUSTER_ACCELERATION_STRUCTURE_OP_TYPE_BUILD_TRIANGLE_CLUSTER_TEMPLATE_NV` per cluster at load, from the rest pose and with cluster id and base geometry index **zero**, and per frame instantiates the cut's templates (`OP_TYPE_INSTANTIATE_TRIANGLE_CLUSTER`) with the pool positions; the instantiate record's `clusterIdOffset` and `geometryIndexOffset` are added to the template's own, so zero at build time makes them the visible entry outright and `ray_visibility.slang` needs no remap. `cluster_acceleration.h` gains `create_cluster_templates`/`build_cluster_templates` (a 72-byte record: the 64-byte cluster build record plus an instantiation bounding-box limit, left 0) and `instantiate_cluster_templates`, which is `build_cluster_set` over a `ClusterSet` whose `limits.instantiate` picked the instantiate op and its 32-byte record stride — everything downstream, the addresses array, the cluster bottom-level build and the top-level structure, is the same either way. `clas_records.slang` writes whichever record the `instantiate` flag asks for, which is why `ClusterRecordParams` grew to 128 bytes: the emit pass needs the `MeshDesc` array to find a deformed instance's pool and a cluster's template. On the RTX 5090 instantiating a 27-cluster cut costs **0.015 ms against 0.063 ms to rebuild it**, for 22% more CLAS bytes, after a one-off 0.068 ms and 219 KB to build 407 templates; the numbers at frame scale are in [docs/experiments/e25-deformed-clusters.md](../experiments/e25-deformed-clusters.md).

**What the deform tests assert** (`domain/gfx/tests/deform_tests.cpp`, one mesh, two instances at the same transform, one deformed and one rigid). With the **identity** deformer the three rasterizers put the deformed instance on exactly the same pixels with exactly the same ids as the rigid one, and the pool's slots past the cut's blocks still hold their sentinel — 1,622 vertices written for a cut of 27 of 407 clusters, packed from the front of a pool with 1,024 vertices of slack behind them, where the per-instance layout this replaced would have allocated all 25,135 of the mesh's. The depths are *not* bit-identical — 1,391 of 12,313 covered pixels differ, by at most 1.3e-8 of a reversed-Z depth around 0.005 — and cannot be: the rigid path dequantizes inside the rasterizer while the deformed path reads the float the pool pass stored, and the two compilations of the same expression round the multiply and the add differently in the last bit. Slang's `precise` on that expression changed nothing, so the test asserts identical coverage and ids and a depth within 2e-7 rather than pretending to bit-equality. With the **wave** deformer the rasterized picture and a KHR ray-traced picture built from the same pool agree as two rasterizers do (coverage identical, 16 of 12,475 pixels naming the other triangle of a shared edge, depth to 2.8e-6) while both differ from the rigid instance on most covered pixels, so the deformation reaches every reader and not just one. And the templates variant traces a picture **identical to the rebuild's**, 0 coverage and 0 id differences with depth agreeing exactly. The records test covers the other half: two instances, one deformed, and the shader's 64-byte records byte-identical to `write_cluster_build_records` including the deformed one's pool address.

**Skinning: the pool's first real deformer.** E25 left the pool with two procedural stand-ins and named skinning as what it was built for ([04 §4.3](../plan/04-renderer.md#43-geometry), [05 §5.11](../plan/05-simulation.md#511-integration-notes)). `deform.slang` now has a third kind, `k_deform_skin`, and it is linear blend skinning: for each vertex of the cut, read the mesh's `geometry::SkinBinding` (four `u8` joint indices, four `u8` weights summing to 255), read the instance's bone matrices, and write `sum over k of (w_k / 255) * (M_k * rest)`. The CPU reference is `anim::skin_positions` ([anim](anim.md)), and the gfx skinning test holds the two to **1e-5** on a two-bone cylinder — measured worst component difference 1.2e-7 on the RTX 5090.

**Where the two addresses live, and why they are not in the same place.** `MeshDesc` grew from 56 to 64 bytes for `skin`, the per-vertex binding stream, because a binding is *per vertex* and the vertex streams are the mesh's: a crowd of a hundred characters built from one mesh shares one binding stream. `DeformDesc` grew from 16 to 24 bytes for `joints` and `joint_count`, because a **pose** is per instance: those hundred characters have a hundred bone-matrix arrays and one mesh. That split is the whole reason the two fields are not neighbours, and it is what makes a crowd cost one binding stream plus 48 bytes a joint a character rather than a copy of the mesh each. The word that was `DeformDesc::pad` became `joint_count`, so the growth is one appended address; both sizes are pinned by the size table with those reasons.

A bone matrix is `anim::JointMatrix`: the affine 3×4 of `model * inverse_bind` as three `float4` rows, 48 bytes. Skinning a position is three dot products with `float4(p, 1)` whichever form the matrix is in, and the fourth row of a skinning matrix is `(0, 0, 0, 1)` for every joint of every pose, so storing it would be a quarter of an array uploaded **per instance per frame** for nothing ([anim](anim.md) has the arithmetic). `scene.slang` mirrors `SkinBinding` as two `uint`s rather than a byte array, because eight `u8` loads through a device address is four times the work of two word loads and the unpacking is two shifts and a mask.

**Skinning is position-only, so it cannot tear.** The crack rule above says a deformed position has to be a function of quantities the cluster build guarantees every copy of a surface point shares. A skinned position is a function of the **rest position** and the **binding**, and both qualify: duplicates across clusters hold the same quantized bytes and the same eight binding bytes, and a simplified level inherits both from the original source vertex, because clusterlod keeps original vertices and `fill_cluster_attributes` maps the binding through `vertex_source` ([geometry](geometry.md), "Skinned meshes"). The shader never reads a normal, which is exactly what `wave` does wrong. The remaining way to crack a skinned mesh is to *author* two coincident vertices with different weights, and the weld keeps those apart rather than merging them, so the pipeline has no step at which the two could silently become one.

Two guards, matched on both sides so the reference stays a reference: an influence whose weight is zero is skipped outright (which also makes a stale joint index on a dead influence harmless), and a non-zero influence naming a joint at or past `DeformDesc::joint_count` is skipped, so bad data deforms a vertex short rather than reading past the end of the array. `anim::skin_positions` does exactly the same, and the test runs the pass with a joint count shorter than the bindings to check that the two agree about it.

**What the skinning test asserts** (`domain/gfx/tests/skin_tests.cpp`, a 180-vertex two-bone cylinder bound root-to-tip by height). The pass is dispatched over the whole mesh and the pool is read back; nothing is drawn, because the rasterizers' side of the pool is `deform_tests.cpp`'s job and this case needs no raster pipeline and no 64-bit atomics, so it runs on any device. At the **bind pose** every skinning matrix is the identity and the pool holds the rest pose to 1e-6 whatever the weights are — the property that makes a skinned instance and a rigid one draw the same picture, and the first thing a transposed matrix breaks. Under a **bent pose** (the tip turned 50°, scaled, and the root translated) every one of the 180 vertices moves and every component matches the CPU reference to 1.2e-7, which is the case a wrong weight normalization, a missing divide by 255, or a column-major matrix read all fail. With a **joint count shorter than the bindings** the GPU skips the same influences the reference does. The wave, lattice, identity, and template cases of `deform_tests.cpp` are unchanged and still pass.

**What a moving character needs from the cull pass.** `InstanceDesc` stayed 96 bytes and gained `bounds_padding`, the second of its three former pad words: a length in the instance's own mesh space that `cluster_cull.slang` adds to the cluster sphere's radius **and** to both LOD spheres. A deformed instance's vertices leave their rest positions and the spheres are the rest pose's, so without it a swinging limb is culled while it is on screen. All three spheres rather than just the culling one, because a cluster's `parent` sphere is its children's `own` sphere and one constant added to every sphere of one instance is what leaves exactly one cluster per DAG path passing — add it to the culling sphere alone and the two would disagree at a group boundary. It is zero for a rigid instance and a float plus zero is exact, so nothing about the rigid path changed, down to the picture's bytes. Where the number comes from, and what it costs to be wrong, is [renderer](renderer.md#skinned-instances)'s.

## The sky

**One file of functions, three readers, one mirror** (2026-09-30; `shaders/sky.slang`, `shaders/sky_luts.slang`, `include/domain/gfx/sky.h`; the scene's side is [renderer](renderer.md#the-sky), the model's [sky](sky.md), the decision [ADR-0048](../adr/0048-the-sky-is-a-providers-model-drawn-by-the-renderer.md)). `sky.slang` has no bindings and no entry points, like `brdf.slang`: everything reads a `gfx::SkyParams` block (1,008 bytes: the air, the sun and the moon, the eye, the celestial frame, the exposure's rule, the tables' device addresses, up to eight views' inverse view-projections) through a device address, and every table through its buffer's address with a bilinear lookup written out by hand, so the file needs nothing from a pipeline layout and any shader can include it. The resolve (`visibility_resolve.slang`: an uncovered pixel, the sun's light at a surface, a directional light's transmittance, the ambient term, the air to the surface), the ray path (its uncovered pixels are the resolve's) and the reference path tracer (`path_trace.slang`: primary misses, next-event estimation of the sun through the air, escaped rays, the air to the first hit) all call it; `ResolveParams::sky_params` and `PathTraceParams::sky_params` took over former pad words, so neither block changed size, and **zero is the stand-in** — every line of the old sky, sun and ambient runs as it did.

**The method is Hillaire's** ("A Scalable and Production Ready Sky and Atmosphere Rendering Technique", 2020), in sun units (the sun's illuminance outside the air is 1, 128,000 lux; a radiance is per steradian of that) and kilometres, the planet's surface at the world's y = 0:

| Table | Size | Parameterization | Built |
|---|---|---|---|
| transmittance | 256 × 64 | Bruneton's (distance to the top, spread between its least and greatest for the height; the height as the horizon's distance) | once a scene, **256** midpoint steps a ray |
| multiple scattering Ψ_ms | 32 × 32 | the sun's zenith cosine × height | once a scene, 64 directions × 20 steps a texel (Hillaire's isotropic second order and the geometric series) |
| sky-view | 192 × 108 | absolute world azimuth × elevation, quadratic about the horizon so the band round it gets the rows | every frame, 32 steps a texel, sun **and moon** single-scattered, Ψ_ms for the rest, the regional ground's bounce for a ray that meets the planet |
| aerial perspective | 64 × 32 × 32 | the sky-view table's own azimuth and elevation × 32 distance slices, quadratic out to 32 km | every frame, two sub-steps a slice: in-scattered light and mean transmittance |
| the frame | 208 bytes | nine L2 harmonics of the environment (the upper hemisphere read out of the sky-view table on a 32 × 64 grid, the uniform ground below), the ground's radiance, the sun's and the moon's light at the eye, the exposure | every frame, one workgroup |

**Why these shapes.** The sky-view and aerial tables are indexed by **world** direction, not by a camera's frustum: the renderer draws up to eight views of one frame (surround, Panini), and a froxel volume per view would be eight volumes where one direction table serves them all at the cost of a direction-to-texel mapping per lookup. The aerial table is also the sky-view table's own parameterization with depth, so its horizon band has the rows the sky's has. Both tables integrate from the **eye's height**, clamped to 10 m (`k_sky_min_altitude_km`) because at the planet's surface a ray at the horizon's elevation grazes forever and the table's quadratic spacing has nothing to resolve. The moon scatters too: a full moon's aureole and a moonlit sky's blue are the same integral as the sun's, 10⁻⁶ of it, and the exposure rule lifts them into view. The ambient is **L2 spherical harmonics** convolved with the cosine lobe (Ramamoorthi and Hanrahan), because a sky has one bright side and two uniform halves no longer said so; its lower hemisphere is uniform ground, `local_albedo × (sun + moon + sky on a level surface) / π`, as the stand-in's was.

**The discs and the stars** are drawn through the air along the pixel's direction and hidden below the planet's horizon: the sun's disc with limb darkening (the linear law `1 − u (1 − μ)` per channel, u = 0.48, 0.60, 0.72 for about 680, 550 and 450 nm, normalized so the disc's mean is the sun's illuminance over its solid angle: dimmer and redder at the edge), the moon's as a **Lambertian sphere shaded by the sun's direction**, so its phase is the two directions and needs no number of its own, and each star a Gaussian spot as wide as the pixel (its angle, `SkyView::pixel`, times 0.7, capped at 0.1°), found through a cube map of 6 × 32 × 32 cells, each with the list of stars whose spot can reach it (3 σ), so a pixel reads one cell's list — a handful on a clear night.

**The mirror** (`tests/sky_reference.h`, namespace `sky_ref`) is every function and every table in double precision, beside `brdf_reference.h`, built from the same `SkyParams`. `tests/sky_tests.cpp` builds four skies on the GPU and in the mirror — noon, the sun two degrees up, five degrees under the horizon, and a moonlit night with the sun forty degrees down — and holds them: every texel of every table (transmittance within 10⁻³, the others within 2 × 10⁻³ of the table's own scale; measured worst 2.3 × 10⁻⁴), the frame's sums (2 × 10⁻³ relative, the exposure's EV100 within 0.002), and, through a test-only probe shader (`sky_probe.slang`, in `gfx_tests`' shaders only), the functions the resolve and the path tracer call at 82 directions of every kind — zenith, round the horizon, under it, the sun's disc and limb, the moon's, each star and a pixel beside it — **in display bytes**: the uncovered pixel, the ambient radiance and the air's in-scattering each within 0.05 of a byte at the frame's exposure (measured 0.002), the air's transmittance within 10⁻⁴ and a surface's light within 10⁻³. The mirror's own model is held with no device: the transmittance round trips, a ray up against one at the horizon, and **256 steps against 4,000** (under 0.1%) where Hillaire's 40 are over 2% short.

**What the mirror found, which is worth knowing before touching the file.** The GPU was first 3% off in the sky-view table and 57 bytes off in a pixel at the planet's horizon, for four reasons, each a numerical lesson: (1) **`1 − exp(−x)` in float is zero for small x**, so a thin layer's scattering vanished — `sky_absorbed` switches to its series under 0.01; (2) **the ray-sphere distance by the textbook quadratic cancels** for a ray from the ground at the horizon, 5% of its length wrong — the distance to the ground is `c / far` and to the top `(room) / (r mu + root)`, the stable forms; (3) **Slang's `%` of a negative int is negative**, so the bilinear lookup's wrap in azimuth read the column before the first as column 63 of another table's row — the wrap is written as two compares; (4) **40 midpoint steps are 3% short in blue through the Mie layer** at a grazing angle, because the aerosol's 1.2 km scale height lives in the ray's first steps — 256, which cost nothing once a scene.

## The deform chain

E25 left one question open in as many words: "skinning plus a cage deformer on one instance needs a second pass or a wider kind field". This is the wider field, and with it the two **morph** stages the geometry format now feeds ([geometry](geometry.md), "Morph channels").

`gfx::DeformDesc::stages` is a **mask**, not a mode, and `deform.slang` runs what it names in a fixed order:

| | stage | what it reads | when it costs |
|---|---|---|---|
| 1 | **static shape** | a set of morph channel weights that changes rarely — a character's body, baked once from a parametric rig | once per weights change, over the **whole mesh** |
| 2 | **pose morphs** | per-frame morph weights: expressions, correctives | every frame, over the **cut** |
| 3 | **skinning** | the mesh's `geometry::SkinBinding` stream and the instance's `anim::JointMatrix` array | every frame, over the cut |
| 4 | **procedural** | `wave` or `lattice`, the E25 stand-ins for a cage solver | every frame, over the cut |
| — | **terrain** (`k_deform_stage_terrain`, alone) | a terrain level's two evaluated height fields and their blend, from the frame's `TerrainLevelDesc` table | every frame, over the cut |

**The terrain stage** runs instead of the chain, never beside it: a terrain level is a heightfield whose every vertex sits on one lattice, and the dune field moves only its heights, so a vertex's position is a function of its lattice point alone — found from its rest position, which every copy of the vertex shares bit for bit, so the crack rule holds — and its height is `a (1 − t) + b t` of the level's two fields (exactly a at t = 0 and b at t = 1), its normal the blended field's central difference, into the pool and the deformed normal pool. A vertex strictly inside the level's `hole` is moved to the hole's nearest edge, on the lattice, at the field's height there **less the distance it was moved**: no map of a square's inside onto its edge is without a fold, so a triangle whose corners went to two different edges spans the square's corner, and unsunk it stood up to 1.3 m proud of the finer level's ground there (the rings test); sunk, it lies under that ground unless the sand across it rises faster than its corners were pulled in, and a triangle stretched from the last vertex outside to the edge dips by at most the stretch, into the finer level's skirt. A vertex whose rest normal points straight down is a ring's **skirt** (no heightfield vertex has such a normal, and the pool writes the normals the resolve reads, so the rest one is free to say it): it takes its border vertex's lattice point and hangs `skirt` metres under the blended field, so a skirt follows the sand down however far it moves. **A vertex drawn from another level** (2026-09-30, [renderer](renderer.md#the-ground-from-the-worlds-tiles)): in a level whose `flags` carry `k_terrain_level_named` — the world's tiles' — a vertex whose rest normal is horizontal names a level, at that many eighths of a turn from +x (`gfx::terrain_level_normal`), and the stage places, raises and lights it from that level's description instead of its own: a tile's border along a coarser tile, which the coarser tile's own copy of the vertex is drawn from too, so the two are one computation whatever pair and blend each level is at. No other level sets the flag, and no heightfield normal or skirt's is horizontal, so the rings and the grid draw what they drew. `gfx::TerrainField` (24 bytes: the heights' address and the lattice window they cover) and `gfx::TerrainLevelDesc` (96: two fields, the lattice's origin and spacing, the blend, the padding its spheres take in the cull pass in place of `InstanceDesc::bounds_padding`, the skirt's depth, the flags, the hole) are written per frame into a host-visible table that `DeformParams::terrain` (112 bytes now) and `CullParams::terrain` (480) point at, and `InstanceDesc::terrain` (its last pad word) names an instance's level; the cull pass drops a level's cluster whose sphere lies wholly inside its hole before any other test. A level whose table names no field yet writes its rest pose. The renderer's use of it is [renderer](renderer.md#the-dunes-in-time-lapse)'s.

That order is [ADR-0032](../adr/0032-characters-are-parameter-vectors.md)'s decision 7 word for word — "static shape → pose correctives → skinning → cage or soft-tissue displacement" — arrived at from the other end: the ADR reasons from what a parametric character *is*, this page from what the data means. One difference in vocabulary is worth stating so the two are not read as disagreeing. The ADR calls the static stage a **bake**, keyed in the derived-data cache by the parameter vector's hash; what is built here is the **runtime half** of that, a per-instance cache recomputed when the weights change. They compose rather than compete: when the content-build bake exists it fills the same buffer this stage fills, which is exactly why the stage's contract is written as a displacement *source* below.

**The order is what the data means, not a preference.** A morph delta is authored **in bind space**, against the rest mesh, so it has to be applied before the skin moves that mesh: applying a bind-space delta to an already-posed vertex would displace it along an axis that has already rotated. A cage acts on the **posed** surface, because that is what a soft-tissue solver sees. The test asserts the difference rather than only asserting the right answer: on the morph fixture with a two-bone skin, skin-then-morph and morph-then-skin put a vertex up to **0.064 mesh units** apart, 500 times the tolerance the chain is held to. Static before pose is not forced by the data but by the cache: the static stage's result *is* the rest mesh every later frame starts from, and a stage that ran after it could not be kept with it.

**The crack rule, stage by stage.** E25's rule is that a deformed position must be a function of quantities the cluster build guarantees *every copy of a surface point* shares.

- **Static and pose morphs** are a function of the rest position, the vertex's morph deltas, and a per-instance weight. The deltas reach a built cluster through `vertex_source` exactly as a skin binding does, so every copy of a source vertex on every LOD level carries bitwise the same ones; the weights are per instance and therefore shared by every copy trivially. The one way to break it is to *author* two coincident vertices with different deltas, and the weld keeps those apart and `ClusterLodOptions::morph_seams` stops the simplifier merging them back — the same two defences the skin binding has, for a worse failure: a merged skin wedge deforms wrongly, a merged morph wedge opens a **hole** the moment the channel plays.
- **Skinning** is unchanged and the argument is the one below ("Skinning is position-only").
- **The procedural stand-ins** are unchanged: `lattice` is a function of the position alone and is safe, `wave` reads a normal and is not, which is exactly why it is a counter-example and not a feature.

**The static shape cache.** `DeformDesc::cache` is a persistent per-instance array of `gfx::DeformCacheVertex` (16 bytes: the displaced position and its octahedral normal), one per vertex of the instance's **mesh**, filled by a second entry point — `deform_cache_main`, one workgroup per cluster of that mesh — and read by the per-frame chain instead of the mesh's 16-bit grid. Over the whole mesh and not over the cut, because a cache the *next* frame's cut can start from has to cover every cluster the cut might name. The normal is in the record because a cache of positions alone would leave the stage's directory walk running every frame for the normals, which is the cost the cache exists to remove. `GpuScene` hands the blocks out in instance order from `RenderSettings::static_shape_kib`; **an instance that gets none keeps `cache` at zero and runs its static stage every frame over the cut** — the same answer for more work, which is the same graceful degradation `k_no_pool_slot` gives the pool.

**The stage's contract is a displacement source, not a delta stream.** It is written as "a rest-space displacement source evaluated per render vertex, whose result is cached per instance", and that wording is load-bearing: the characters this is for are two-level, a low-resolution control mesh carrying the shape channels and a dense detail surface bound to it, and under that scheme a dense character's morph data is a function of the **control mesh's** size and not the render mesh's. Nothing in this section has to change for it — the stage mask, the cache, the bound below and the crack argument all care about *what a vertex is displaced by*, not about where the displacement came from. What a control-mesh binding adds is a per-vertex stream of a few indices and weights, the same record shape as `geometry::SkinBinding` and the same shape a cage binding needs, travelling through `vertex_source` the same way. It is the stated follow-up, and the per-cluster slice directory is specific to the current source rather than in its way: a binding stream is per vertex and needs no directory at all.

**What happens to the shading normal.** Until now the resolve took every shading normal from the rest attribute stream and turned it only by the instance's world matrix — **skinning did not rotate it**, which is worth writing down because nothing said so before. With morphs that stops being tolerable: a channel changes the surface's *curvature*, so the rest normal is not an approximation of the deformed one, it is the wrong vector.

Two answers were on the table and the choice is measured. *Reconstruct from the deformed positions in the resolve* is free — the resolve already computes the triangle's plane normal for the shadow bias — but a plane normal is a **flat** normal by construction: there is no smooth vertex normal to recover from one triangle, so a morphing sphere would come out faceted. *Carry a delta normal through the chain* costs a second pool: one octahedral `u32` per pool vertex against the position's twelve bytes, a third of what the positions cost, written by the same pass in the same loop. That is the choice. The morph stages add `sum of weight x delta normal` and renormalize; the skinning stage turns the normal by the same blend it turns the position by, which also closes the gap above; the procedural stages leave it alone.

**It is off unless the scene has morph channels**, and that is deliberate rather than shy. `DeformParams::normal_pool` and `ResolveParams::normal_pool` are null for a scene with none, and the resolve then reads the attribute stream through exactly the instructions it always did — which is what keeps every existing picture byte-identical. Turning the skinning half on everywhere would change every skinned picture in the corpus, and that is a change with its own measurement to take rather than a side effect of this one.

**What the chain's tests assert** (`domain/gfx/tests/morph_deform_tests.cpp` against `deform_reference.h`, the same four stages in the same order on the CPU, the way `brdf_reference.h` is the BSDF's twin). On the morph sphere fixture, 1,592 vertices, RTX 5090: static only **6.0e-8** mesh units, pose only 6.7e-8, static+pose 1.2e-7, morph+skin 1.3e-7, and the whole chain — static, pose, skin and `lattice` on one instance — **3.6e-7**, with every normal within **0.028°** of the reference (the pool's own snorm16 floor). The cache case fills the cache once and then runs five frames with the weights untouched, checking that the cache pass dispatches exactly **zero** more times and that every frame still matches the reference. And the order case asserts the *difference*: skin-then-morph moves a vertex up to 0.064 units away from morph-then-skin.

**The chain on the Khronos samples.** The cases above run on the procedural sphere, which was all the stream had when it landed. `deform chain: the Khronos morph samples, against the CPU reference and their own targets` runs the static stage over the four models `tools/fetch-samples.ps1` now fetches, every channel at weight 1, when they are present (it says so and passes when they are not — CI does not fetch them; a test bundle made with `-WithSamples` carries them). Two comparisons each: against `deform_reference.h` over the **stored** stream, which is the directory walk, the slices and the 16-bit deltas of a real file's layout rather than the fixture's; and against the **asset itself** — rest position plus the glTF's own float deltas through `vertex_source` — which is what the two quantizations cost on content nobody here authored. **One thing did not stay byte-identical, and it is worth the paragraph.** `--deform wave` and `--deform lattice` on the FlightHelmet differ from the exclusive-mode pass on a handful of pixels by one level of 255: PSNR **106.5 dB** / SSIM **1.000000** / FLIP mean 4.3e-7 with a worst pixel of 0.0088 for `wave`, and 109.5 dB / 1.000000 / 1.6e-7 / 0.0063 for `lattice`. Nothing about their arithmetic changed — `--deform identity`, which writes the rest position, is byte-identical, and so is every picture with no deform pass and the skinned Fox through `--animate`. What changed is that the same expressions are now compiled in a module that also holds the morph stages, and the driver contracts their multiply-adds differently. Moving the stage back into the caller's loop body was tried and changed nothing, which is what says the cause is the module rather than the call; it is the same effect E25 recorded for the pool's depths. The two paths it touches are the spike's procedural stand-ins, not a production path.

**Sizes.** `DeformDesc` 16 → 48 bytes, `DeformParams` 88 → 104, `ResolveParams` 272 → 288, plus `MorphParams` (48) and `DeformCacheVertex` (16); the size table carries the reason for each. The morph stream's six scene-wide addresses ride behind **one** `DeformParams::morph` pointer, the way the page table rides behind `CullParams::streaming`: the push block is 128 bytes and they are read once per workgroup rather than once per vertex. `k_deform_skin` is **retired rather than reused** — a container or a saved scene still holding the value 3 would name a procedural deformer that no longer exists, and naming nothing is better than naming the wrong one.

**Not yet on the GPU side.** The pool's allocator is one workgroup, so it is serial in the size of the cut (about 5 µs per 1,000 entries, 0.12 ms at a pathological 24,000-entry cut); a two-level scan — block sums in parallel, one serial pass over the block sums — would keep the exact cursor and remove that. And *which* entries overflow is not reproducible, because the order they are allocated in is the order the cull pass's atomics appended them; making it so needs a sorted visible list, which was built and measured on 2026-09-24 and not adopted ("The visible list's order").

**Bindless (ADR-0023).** `BindlessSet` (`bindless.h`) owns one global descriptor set with unbounded, partially bound, update-after-bind arrays (sampled images at binding 0, storage images at 1, samplers at 2, and on devices with `DeviceFeatures::acceleration_structure` acceleration structures at 3; `has_acceleration_structures()` says whether the binding exists), capacities clamped to the device's update-after-bind limits by `clamp_bindless` ("What a device has to have", above — the same function the adapter report clamps with, so a report says what the set would really be), a free list per array, and deferred slot release keyed on the frame timeline (`release_*` with the value of the last frame that could read the slot, `recycle(completed)` once per frame). `pipeline_layout()` is set 0 plus a push-constant block for all stages, so every pipeline shares one layout shape. Buffers never enter the set: shaders receive device addresses and use Slang pointers (`uint* data = (uint*)params.address`). Helpers create views and samplers: `create_sampler(device, filter)` is the tooling sampler (clamped, level 0), `create_mip_sampler` the clamped trilinear-anisotropic one, and `create_sampler(device, SamplerDesc)` a material sampler as a glTF sampler describes one — wrap in u and v (repeat, mirrored repeat, clamp), magnification and minification filters, the blend between levels, and `mipmapped`, which samples the whole chain with 16x anisotropy where the device has `samplerAnisotropy` and the minification is linear (a nearest one asks for none), or level 0 alone without it. The renderer makes one per distinct combination a scene's materials ask for ([texture](texture.md#samplers-and-texture-transforms)); the set's 256 sampler slots hold all 144 there can be (72 sampler words, each mipmapped or not).

**No SDK required.** The Vulkan headers and volk come through FetchContent (`cmake/EngineGraphics.cmake`, tag `vulkan-sdk-1.4.357.0`); volk loads the driver's loader library at run time. Without a loader, or with a loader but no driver behind it (GitHub-hosted runners have exactly that), `enumerate_adapters` returns false with a message saying which, and everything else keeps working. `vulkan_available()` answers only the loader question. The SDK arrives with validation layers and shader tooling.

**Invariants (tested).** Every adapter has a name, a `1.x.y` API version, every extension of interest reported present or absent, at least one queue family (a graphics one unless the device is a CPU implementation), a hardware tier from the fixed set, one requirement row per table entry, and a verdict whose tier is either that hardware tier or `"none"`; the list is sorted discrete-first. On a machine without a usable Vulkan driver the function fails cleanly with a message naming the missing piece.

**Geometry streaming in the cull pass.** `gfx::StreamParams` (64 bytes, size table) is the block `gfx::CullParams::streaming` points at, and it is null for a scene that is uploaded whole — the pass then runs exactly the instructions it ran before pages existed, which is why every non-streamed picture is byte-identical. It carries the page table, `page_of_cluster` and the per-cluster child ranges the drawing rule reads, the residency word array, and the three feedback arrays it writes: the bounded `geometry::PageRequest` buffer and its atomic counter, and the per-page "requested this frame" and "used this frame" words. `scene.slang` mirrors `geometry::ClusterPageDesc`, `ClusterChildren` and `PageRequest` beside the structs they index. `CullParams` went from 400 to 416 bytes to hold the address and the two counts that bound every index the shader writes; the drawing rule itself is [renderer](renderer.md)'s to explain.

**The indirection decision, and what it would have cost.** A page's clusters read their vertices and triangles out of a fixed-size pool slot, and there are two ways to make an offset slot-relative: patch `ClusterDesc::vertex_offset`/`triangle_offset` on the host when the page is copied in, or leave them page-relative and have every shader add the slot base of `page_of_cluster[c]`. **Patching won, and the reason is a push-constant budget rather than a clock.** The indirection needs two addresses — the page table's and `page_of_cluster`'s — in every pass that touches geometry: `cluster_mesh.slang`, `cluster_vertex.slang`, `cluster_sw_raster.slang`, `visibility_resolve.slang` through `material.slang`, `clas_records.slang` and `deform.slang`. `ClusterDrawParams` is **full at 128 bytes**, which is the largest push block the renderer allows, and `MeshDesc` — which every position read already holds and which is where the deform pool's and the templates' addresses ride for exactly this reason — is **full at 64**. So the indirection is not a line in `load_position`; it is a restructuring of two GPU-mirrored records that every rasterizer, the resolve and the acceleration-structure chain read, in a change whose stated requirement is that the pictures do not move. Against that, patching is one memcpy of 48 bytes a cluster onto a page that is being copied anyway, and it leaves the shader side of streaming at exactly one extra load (the page's residency word) per pair. The cost the indirection *would* add is two dependent loads on every position read — one for `page_of_cluster[c]`, one for the slot base — on a path that today reads a `ClusterDesc` and a `MeshDesc` and then the position.

**What has been measured, and what is still owed.** The half that *shipped* has a number: the extra load the cull pass does per pair costs nothing this machine can resolve. Measured in `msvc-release` on the RTX 5090 at 1920×1080 over a FlightHelmet grid of 64 instances — **150,272 pairs a frame**, the largest pair count in the corpus — the cull pass takes 0.029–0.031 ms with streaming off and 0.029–0.032 ms with it on, at every budget from a quarter to the whole page table, over two runs of 120 frames each ([renderer](renderer.md#geometry-streaming-the-gpu-half-of-pages-and-residency) has the table and the machine state; the card was 5–25% busy with other work, so both figures are upper bounds). One residency-word load and a masked atomic append per pair are inside the run-to-run spread.

The indirection's own number is **still owed**, and the shape of the experiment that would take it is worth writing down so the next attempt does not have to rediscover it. It cannot be measured by adding the indirection to the shipping path, because that path has nowhere to put the two addresses — which is the decision itself, not an obstacle to measuring it. It has to be a **test-only compute shader with two entry points over the same data**: one workgroup per cluster, each thread walking the cluster's vertices and accumulating into a sink so nothing folds away, reading a position either at `cluster.vertex_offset + v` or at `slot_base[page_of_cluster[c]] + (cluster.vertex_offset + v - page_first_vertex[page])`, timed against each other with a `GpuTimer` on the paged heightfield. Two details decide whether such a measurement means anything. The two extra loads must **not be hoisted out of the vertex loop** — a mesh shader would hoist them per workgroup and a resolve could not, and those are different numbers, so the probe has to state which of the two it is measuring and ideally measure both. And the pages must be **scattered across pool slots** rather than laid out in order, because a `page_of_cluster` that reads like an identity map is a cache hit the real thing would not get.

Until then the decision rests on the structural argument above, which is the stronger of the two anyway: the indirection is not a line in `load_position`, it is a restructuring of two GPU-mirrored records that every rasterizer, the resolve and the acceleration-structure chain read, in a change whose stated requirement is that the pictures do not move.

The cluster acceleration structure test does the same for the cluster path at two scales (an 85-cluster frame cut and all 1,357 leaves of the default terrain), requires the two ray-traced pictures to be identical to 0.1% and both to match the rasterizer, and reports build times, trace times, and memory per path. The shadow case of the shading test is described under the material resolve above. The scene test puts two meshes (a terrain and a sphere, each on its own grid) and five instances (one three times bigger, one scaled unevenly, one turned a quarter turn, one hidden behind the big sphere) through the whole frame: the GPU's 76 surviving pairs of 506 equal a CPU reference that repeats every test in the instance's frame, the mesh and vertex paths write identical words, every instance puts pixels on the screen, a KHR bottom-level structure per instance traces a picture that differs from the rasterized one on 2 pixels of 13,154 with 17 naming the neighbouring triangle, and two-pass occlusion culling drops the hidden instance's 3 pairs while every covered pixel keeps the same surface. The deform tests put one mesh and two instances at the same transform, one deformed and one rigid, through the pool: the identity deformer draws the same coverage and the same ids in all three rasterizers, the pool's slots past the cut's blocks keep their sentinel, the wave deformer's rasterized picture matches a ray-traced one built from the same pool, and instantiated templates trace exactly what rebuilt cluster structures trace (details and numbers above). They fill the per-entry slot table on the CPU rather than running the allocator, which is what lets them check the shaders' half of the contract — that a reader goes where the table says — on its own; `systems/renderer` covers the allocator itself end to end. All of them skip with the reason on machines without a usable driver.

**On a device without mesh shaders or ray queries — the baseline tier — the suite runs, it does not skip.** [ADR-0024](../adr/0024-hardware-rasterization-first.md) makes the vertex path draw the same visibility buffer from the same clusters and the same cull pass, so a case about the *picture* has no reason to need mesh shaders, and until 2026-09-24 six of them did anyway — the shading case, both attributes cases, the cull test, the occlusion test and the visibility test all built `cluster_mesh.slang`'s pipeline and skipped without it, so the lighting model's check against `brdf_reference.h`, "culling never changes the picture" and the software rasterizer's only coverage had never run on the tier both legacy GPU machines are. `tests/raster_path.h` holds the rule once, the one `renderer::resolve_settings` applies to `--raster hw`: `gfx_test::ClusterRaster` builds the mesh pipeline where `DeviceFeatures::mesh_shader` is set and `cluster_vertex.slang`'s (`vs_cluster`, three vertices per triangle of the cluster build's capacity) where it is not, both with `fs_visibility`, and gives a case the direct draw, the indirect draw, the `CullParams::count_index` the cull pass must count into (0 for mesh tasks, 1 for `vkCmdDrawIndirect`), the reset of the argument block (`{0, 1, 1}` or `{3 × capacity, 0, 0, 0}`, one `k_draw_args_bytes` block either way), the survivor count read back from it, and the stage its geometry reads are declared in. It is the capacity draw on purpose, not the renderer's indexed one: it is the draw every device without mesh shaders has, and the one case about the indexed draw (above) holds the two to one picture. Those six cases draw through it and assert exactly what they assert on the mesh path, and the scene test's occlusion half, which had been inside its mesh-path branch, runs through the device's own path too. What still skips is what is about a path the device does not have, and it names the requirements-table row that is missing: the mesh-shader test (`VK_EXT_mesh_shader` — it is about the mesh stage itself, its workgroup per cluster and the `SV_PrimitiveID` it must write), the vertex path's indexed case (`geometryShader` or `fullDrawIndexUint32`), the ray cases (`VK_KHR_ray_query`: ray-query visibility, the shadowed resolve, the wave deformer; with `VK_NV_cluster_acceleration_structure` for the cluster structures and the templates), and the halves of cases that compare paths (the mesh path in the vertex-path, scene and identity-deformer cases, the scene's ray-traced picture). A skip is one line — `skipped: <adapter> has no <rows>` for a case, `part skipped: <what>: <adapter> has no <rows>` for a half — because doctest has no skip at run time and counts a case that returns early as passed, so `grep -c "MESSAGE: skipped:"` over a run's output is the number of cases that checked nothing, and the doctest summary is not.

**`ENGINE_GFX_TEST_DEVICE` runs the whole suite as a weaker device on any GPU**, the way the renderer's TITAN-Xp-like case does for one picture: `baseline` removes `VK_EXT_mesh_shader`; `titanxp` removes what the TITAN Xp's driver reports absent (mesh shaders, ray queries, the cluster structures, and two rows nothing here draws with — the renderer case's profile); anything else is a comma-separated list of requirement rows. It goes through `DeviceOptions::overrides`, so the device really lacks what the profile removes and a mesh pipeline on it fails as it would on Pascal, and a forced profile that yields no device — a misspelled row, say — fails the case rather than skipping it, since a run that asked for the baseline tier and drew nothing must not come back green. `device_tests.cpp` and the profiles of `requirements_tests.cpp` ignore it: they compare a device with its adapter's own report, which a profile makes disagree on purpose. On the RTX 5090 (2026-09-24, `msvc-debug`) the suite is 53 cases either way: natively 0 skipped; under `baseline` 1 (the mesh-shader test) and four mesh halves; under `titanxp` 6 (the mesh-shader test and five ray cases) and five halves; under `VK_EXT_mesh_shader,geometryShader` — a baseline-tier device without the feature the indexed draw needs — 2 (the mesh-shader test and the indexed case) and three mesh halves. (The morph-sample halves, which skip wherever `tools/fetch-samples.ps1` has not run, are not counted.) Every number the picture cases report is the same through the vertex path as through the mesh path — the shading and both attributes cases 0 of 255 from the reference, the cull cut 24 of 13,957 pixels from the leaves along silhouettes, occlusion changing 0 pixels, the hardware and software visibility buffers 1 pixel of coverage and 29 of 21,195 ids apart — which is ADR-0024's promise held by the suite rather than by one comparison. On the TITAN Xp itself (`linux-server`, GCC 14, driver 580.178.04, 2026-09-24) the suite went from 39 of its 52 cases checking something to 45: the six that had skipped for want of mesh shaders without being about the mesh stage draw through the vertex path there and pass, and what still skips is the mesh-shader test, the five ray cases and the swapchain test, which has no display ([self-hosted runners](../ci/self-hosted-runners.md#the-first-run-on-the-titan-xp)). With the vertex path's indexed case it is 46 of 53: the card reports `geometryShader` and `fullDrawIndexUint32`, and the case draws its 23-cluster cut (2,042 triangles against 2,852 of capacity) the same as the capacity draw to the pixel and the same as the software rasterizer on 12,296 of 12,306 ids. The lighting model holds on Pascal to the same 0 of 255 as on the RTX 5090 — every pixel the shading and attributes cases compare with the double-precision reference is exact on both — so the tolerance of 2 is headroom for a device whose `pow` and `sqrt` are within Vulkan's precision bounds without being correctly rounded, not a calibration of either card. Counts that come from the CPU side of a case are not portable, and a reader comparing two logs should not expect them to be: the terrain the cases make with `std::sin` and `std::cos` builds a 184-cluster LOD DAG in the desktop's MSVC build and a 181-cluster one in the server's GCC 14 build, so the cull test's cut is 24 clusters on one machine and 23 on the other, each checked against the CPU reference built beside it. It is not the builder: the two C libraries differ in the last bit of some of those floats, so it is not the same terrain, and from the same bytes both builds make the same DAG ([geometry](geometry.md#the-same-bytes-from-every-toolchain)).

**Next.** Soft shadows (one ray gives a hard edge; an area light wants several rays and a denoiser), a shadow ray that does not stop at the first hit for alpha-tested geometry, shadows in the modes that build more than one visible list (the software split's second list and occlusion culling's second pass, which is why `--shadows rt` turns two-pass occlusion off today), a per-instance culling BVH over cluster groups (the pair enumeration is flat, which is one thread per (instance, cluster) and fine until scenes reach millions of pairs), transform updates instead of a static instance buffer, lighting through the ray-traced visibility. On the ray path, two instances of one mesh build their own copies of the same cluster acceleration structures, because a record's base geometry index has to be the visible entry; cluster templates (now built, see above) are the answer, and pointing a rigid instance's instantiation at the rest-pose positions is the step that has not been taken. The per-instance bottom-level builds are recorded one after another with a barrier between them because they share one scratch buffer; a scratch per instance, or the extension's multi-structure form, would overlap them. **A 32-bit visibility buffer** is the follow-up the requirements table makes concrete: a device with neither `shaderBufferInt64Atomics` nor mesh shaders cannot draw a frame at all, because every rasterizer writes depth and id as one 64-bit atomic max. Packing a reversed-Z depth and a visible-entry id into 32 bits (say 22 bits of depth and 10 of triangle, with the entry in a second buffer, or 24/8 at a lower depth precision) would give such a device the vertex path back at the cost of a coarser depth test; it is not built, and the verdict says so rather than leaving a reader to work it out. Running the vertex path on the Maxwell machine once it is reachable (the Pascal server runs this whole suite through it since 2026-09-24), quantized positions for the acceleration structure builders too (they take a vertex format; the rasterizers already read the 16-bit grid), cheaper Hi-Z and resolve passes at surround resolutions, and the experiment E2 spike on cluster acceleration structures. Validation layers need the Vulkan SDK installed. Experiment E2 follows.
