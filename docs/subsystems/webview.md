# webview (foundation, capability)

**Purpose.** The platform's own web view, embedded as a child of a native window — on Windows the **Edge WebView2 runtime** that Windows ships — so a host can show a web page beside what it draws itself. engine-editor shows the web shell ([engine_shell](engine_shell.md#embedded-in-the-editor)) in one, beside its Vulkan viewport in a child window ([window](window.md#child-windows); [apps](apps.md#engine-editor-the-engines-window-on-a-document); roadmap A37). Capability `ENGINE_WITH_WEBVIEW` (ADR-0027).

**API** (`foundation/webview/webview.h`). `webview::runtime_available(&why)` says whether this machine can show one — the build has a backend and the runtime is installed — and why not. `Webview::create(parent, options, &error)` embeds one in `parent`, the platform's window handle (`window::Window::os_handle()`, an HWND), blocking while it pumps the thread's messages until the runtime has made it (a few hundred milliseconds; the first start on a machine makes the runtime's profile and takes longer); `navigate(url)`; `set_rect(x, y, width, height)` places it in the parent's coordinates and shows it; `widget()` is the view's own window, a sibling of the parent's other children; `destroy()`. `WebviewOptions::devtools` turns on the inspector (F12) for a person working on the page, never in a test. Main-thread only, and the thread must pump its window messages, which an SDL event loop does: WebView2 delivers its callbacks as messages.

**It installs no bridge.** The library can bind JavaScript functions to the process (`window.chrome.webview`, `webview_bind`); this module calls none of that, so a page in it has no path into the process but the network — for the editor's shell, the protocol over the editor's own loopback listener. That is what keeps the same page running unchanged in a plain browser against engine-host, and what keeps every panel a client of the protocol rather than of the editor (06 §6.13).

**The dependency, and its licences** (`cmake/EngineWebview.cmake`, [`third_party/LICENSES.md`](../../third_party/LICENSES.md)). [webview/webview](https://github.com/webview/webview) 0.12.0, MIT: a small header-only library over WebView2, WebKitGTK and WKWebView. Its implementation is compiled once into the static library `engine_webview_core` from the library's own `core/src/webview.cc`, as third-party code with its own policy — it uses exceptions internally and catches them at its C API, which is all this module calls (`webview_create`, `webview_navigate`, `webview_get_native_handle`, `webview_destroy`). On Windows it needs the COM interface declarations of WebView2, which come from Microsoft's WebView2 SDK NuGet package; the package's `LICENSE.txt` is a BSD-3-Clause text (Copyright Microsoft Corporation, read before adoption on 2026-10-11), so its headers are allowed by ADR-0014, and they are **fetched at configure time by URL and SHA-256, never vendored**. **No Microsoft binary is used**: the package's `WebView2Loader.dll` and import libraries are neither linked nor copied, because the library's *built-in* loader (`WEBVIEW_MSWEBVIEW2_BUILTIN_IMPL`, with `WEBVIEW_MSWEBVIEW2_EXPLICIT_LINK`) finds the installed runtime and calls it itself. The runtime is Windows' own, installed with Edge on Windows 10 and 11 and updated by it; nothing ships it.

**Detecting the runtime.** `runtime_available` reads the runtime's registered version the way Microsoft documents (the `pv` value of the Evergreen runtime's EdgeUpdate client key, machine-wide in the 32-bit view, machine-wide, or for the user; present and not `0.0.0.0`). That is asked before anything appears, so engine-editor's `--embedded` on a machine without it (a hosted CI runner, Windows Server, an N edition) exits 3 with the sentence and shows nothing.

**Only Windows has a backend here.** The library's Linux backend is WebKitGTK and its macOS one WKWebView; neither is installed or built on this project's machines (the Linux containers have no WebKitGTK), so on any platform but Windows the capability **switches itself off at configure with one line** (`webview: no backend on this platform ...`), and the Linux builds and tests run with it off. ENGINE_MINIMAL switches it off like every capability. Nothing below an app depends on it: engine-editor links it when the configuration has it (`ENGINE_EDITOR_WEBVIEW`) and otherwise shows the viewport alone and says where the shell is.

**The profile.** The library puts WebView2's user data folder (its cache, cookies and the page's local storage — the shell's remembered splits) at `%APPDATA%\<executable name>`, chosen in its embedding code with no parameter to change it, so every engine-editor on the machine, tests included, shares `%APPDATA%\engine-editor.exe`. The runtime supports several processes on one profile; nothing a test asserts reads it.

**LOD policy and determinism.** None applies: it is a view for a person, it draws nothing the engine renders, and nothing it does is replayed.

**Testing.** `foundation/webview/tests/webview_tests.cpp`: the runtime check gives a reason when it says no; a web view is not made without a parent, and nothing opens. The view itself, in a window beside the editor's viewport, is engine-editor's `--embedded` test ([apps](apps.md#engine-editor-the-engines-window-on-a-document)), which skips with the reason where the runtime is absent.

**Not yet.** WebKitGTK on Linux (it would need the GTK main loop pumped beside SDL's), a user data folder of the host's choosing (it needs the library's embedding code to take one), and DPI changes across displays followed by anything but the page's own `devicePixelRatio`.
