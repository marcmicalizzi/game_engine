# window (foundation)

**Purpose.** OS windows, input events (keyboard, mouse, gamepads, raw joysticks), and the two pieces of Vulkan glue a window system owns: the instance extensions a surface needs and surface creation. SDL3 (ADR-0012, zlib) sits underneath, statically linked with video, events, and gamepads only; nothing outside this module includes SDL. Headless machines keep working: `init()` reports failure and callers run without a window, which is how the CI runners and `engine-host` behave. This module stays raw — the binding table and the per-tick state a game reads are `foundation/input`'s, and it deliberately does not depend on this one.

**API.** `window::init()` starts the video subsystem (false with the reason on a machine without a display) and then the gamepad and joystick subsystems, whose failure is logged rather than returned: a machine with no joystick driver still gets a window. `Window::create(WindowDesc)` opens a resizable, high-DPI-aware window; `pixel_width()/pixel_height()` are the framebuffer size, refreshed on every `Resized` event. `poll(Event&)` pulls one event at a time: `Quit`, `CloseRequested`, `Resized`, focus, `KeyDown/KeyUp` (a small `Key` enum for the common keys plus the raw scancode), mouse move, buttons, and wheel. `Window::vulkan_instance_extensions()` feeds `gfx::DeviceOptions::instance_extensions`; `create_vulkan_surface(instance)` and `destroy_vulkan_surface` bracket a `gfx::Swapchain`. Vulkan handle types are forward-declared the way SDL does it, so the header depends on neither SDL nor the Vulkan headers.

**Gamepads.** `poll()` also reports `GamepadConnected`, `GamepadDisconnected`, `GamepadButtonDown`, `GamepadButtonUp`, and `GamepadAxis`. `Event::gamepad` is this module's own slot id, `0..k_max_gamepads-1` (8), handed out lowest free first and released on disconnect — not SDL's instance id, which grows for the life of the process and would make a replay depend on the order pads were plugged in. `GamepadButton` is the standard layout named by position rather than by label (`South` is Xbox A, PlayStation cross, Nintendo B), plus the dpad, shoulders, sticks, `Back`/`Guide`/`Start`, and `LeftTrigger`/`RightTrigger` for the pads whose triggers click digitally (SDL routes the GameCube's there); anything else maps to `Unknown` and is dropped. `GamepadAxis` is the two sticks and the two triggers, normalized to -1..1 and 0..1 in `Event::value`, keeping SDL's sign convention (+x right, +y **down**, so a stick pushed forward reads negative). `gamepad_button_name`, `gamepad_axis_name`, `gamepad_name(slot)`, and `gamepad_connected(slot)` are for logs and tools. Gamepad events carry no window, so they go to whichever window is polling; the slot table is process-wide and `shutdown()` closes every pad. **The enumerator values of `GamepadButton` and `GamepadAxis` are part of the input log format** (docs/subsystems/input.md): append to them, never reorder or renumber.

**Raw joysticks.** SDL announces every device as a joystick, and the subset it has a mapping for a second time as a gamepad. This module opens a joystick only when SDL does *not* consider it a gamepad, so the two tables never hold the same device: everything with a known layout is reported by name through the gamepad events above, and everything else — wheels, pedal boxes, sequential and H-pattern shifters, flight sticks, button panels — arrives as `JoystickConnected`, `JoystickDisconnected`, `JoystickAxis`, `JoystickButtonDown`, `JoystickButtonUp`, and `JoystickHat`. There is nothing to name them by, so they carry bare indices: `Event::index` is the axis, button, or hat number the device itself uses, `Event::value` is the axis position normalized to -1..1 (no trigger convention — a pedal that rests at one end of its travel reads -1 at rest, which is the binding's `scale` to deal with, not the module's), and `Event::hat` is a `HatDirection`.

**The two slot spaces are separate.** `Event::gamepad` indexes the gamepad table, `Event::joystick` the joystick table; both start at 0, both are handed out lowest free first, both are released on disconnect, and **gamepad 0 and joystick 0 are two different devices**. Whoever converts these events into `input::RawEvent`s keeps them apart by *source*, never by the slot number: a `RawEvent` whose source is `GamepadButton` has a gamepad slot in `device`, one whose source is `JoystickButton` has a joystick slot. `k_max_joysticks` is 8, like `k_max_gamepads`.

**Hats.** A hat (a "POV hat", the d-pad on a wheel rim or a flight stick) reports a *position*, not a press: `HatDirection` is a bitmask of `Up` 1, `Right` 2, `Down` 4, `Left` 8, with the four diagonals as two bits or-ed and `Centered` as none — SDL's own numbering, and part of the log format (`input::k_hat_up` and friends mirror it). `hat_direction_name` names the nine positions and answers "Unknown" for anything else. Because a binding names a direction rather than a hat, the conversion to `input::RawEvent` turns one hat event into four digital signals, one per cardinal direction, coded `input::hat_code(hat_index, direction)`.

**Describing a device without waiting for an event.** `input_devices(Vector<InputDeviceInfo>&)` lists every attached gamepad and joystick with its `name`, SDL's 32-character `guid` (bus, vendor, product, version — stable across sessions and machines), `vendor`, `product`, the number of `axes`, `buttons`, and `hats`, whether SDL calls it a gamepad, and the slot it holds. Reading the counts needs the device open, which SDL reference-counts, so listing does not disturb the event stream or the slot tables. `slot` is `k_invalid_slot` (0xFF) for a device whose arrival event has not been polled yet — SDL announces what is already plugged in as an arrival, so a caller polls for a moment first — or one that refused to open or found every slot of its kind taken.

**Rumble and background events.** `rumble(gamepad, low, high, ms)` runs the two motors of a gamepad slot at 0..1 for a duration; it returns false for an empty slot or a pad with no motors, which is most of them, so false means "nothing happened" rather than "something went wrong". Joysticks have none: a force-feedback wheel is a haptics device, not two motors. `set_background_input(true)` clears SDL's rule that device events are dropped while a process owns windows and none of them holds keyboard focus — right for a game, wrong for a tool started from a terminal whose user then has both hands on a wheel, which is why `engine-input` turns it on and `engine-view` does not.

**Build.** `cmake/EngineGraphics.cmake` fetches SDL `release-3.4.16` (`ENGINE_SDL_TAG`) and builds it static with audio, render, GPU, camera, and sensor subsystems off; joystick and haptics stay on, and `init()` calls `SDL_InitSubSystem(SDL_INIT_GAMEPAD)` and then `SDL_InitSubSystem(SDL_INIT_JOYSTICK)` after the video subsystem (the first implies the second; the second is asked for separately so a machine whose gamepad mappings fail to load still reports its wheels and sticks). On Linux SDL needs the X11 or Wayland development headers at build time (the libraries themselves are loaded at run time), and refuses to configure without them; the CI workflow installs them. A headless server build can set `SDL_UNIX_CONSOLE_BUILD=ON` to skip that check, and `init()` then fails cleanly at run time.

**Depends on.** `base`, `containers`, `log`; SDL3 (third_party/LICENSES.md).

**Testing.** `tools/dev.ps1 test -Filter window`: creates a hidden window, checks the pixel size, the surface extension list, event draining, rename, destroy, and shutdown; records a skip on machines without a display. The drain also covers the gamepad and joystick paths, since SDL reports every device already plugged in as an arrival during `init()`: each one must come through with a slot below its table's size and an open handle behind it, every gamepad button must map to something other than `Unknown`, every axis value must be in range, every hat must be one of the nine named positions, untouched slots of both kinds must read as empty, and `shutdown()` must close them all. The test then lists the devices, prints each one's name, GUID, vendor, product, and counts as a doctest message — which is how a machine reports what it has — checks that every listed device holds the slot its arrival claimed, and calls `rumble` on an empty slot and on each pad. A machine with no device simply records that and checks the empty slots. A second case needs neither a display nor a device: it pins the numbering of `GamepadButton`, `GamepadAxis`, and `HatDirection` and checks that every enumerator has a name of its own. `apps/engine_input` is the end-to-end probe for devices nobody here owns (docs/subsystems/apps.md); `domain/gfx`'s swapchain test and `engine-view`'s end-to-end test open real windows.

**Not yet.** Haptics beyond the two rumble motors — force feedback on a wheel, trigger rumble, LED and touchpad state — devices beyond `k_max_gamepads`/`k_max_joysticks`, joystick trackballs (`SDL_EVENT_JOYSTICK_BALL_MOTION`), battery level, and the non-standard gamepad buttons — paddles, the touchpad, `Misc1` — which are dropped rather than reported. Text input and IME, clipboard, multiple windows and per-output presentation for surround (docs/plan/04-renderer.md §4.8), and cursor capture for first-person controls.

**Performance notes.** Event polling is a few microseconds per frame. SDL's static library adds about a minute to a cold CI build.
