# window (foundation)

**Purpose.** OS windows, input events (keyboard, mouse, gamepads, raw joysticks), force feedback and rumble, and the two pieces of Vulkan glue a window system owns — the instance extensions a surface needs and surface creation — in a backend header of their own ([below](#the-vulkan-surface)). SDL3 (ADR-0012, zlib) sits underneath, statically linked with video, events, and gamepads only; nothing outside this module includes SDL. Headless machines keep working: `init()` reports failure and callers run without a window, which is how the CI runners and `engine-host` behave. This module stays raw — the binding table and the per-tick state a game reads are `foundation/input`'s, and it deliberately does not depend on this one.

**API.** `window::init()` starts the video subsystem (false with the reason on a machine without a display) and then the gamepad and joystick subsystems, whose failure is logged rather than returned: a machine with no joystick driver still gets a window. `Window::create(WindowDesc)` opens a resizable, high-DPI-aware window; `pixel_width()/pixel_height()` are the framebuffer size, refreshed on every `Resized` event. `poll(Event&)` pulls one event at a time: `Quit`, `CloseRequested`, `Resized`, focus, `KeyDown/KeyUp` (a small `Key` enum for the common keys plus the raw scancode), mouse move, buttons, and wheel. `window.h` names no graphics API; the surface glue is in [the Vulkan surface](#the-vulkan-surface) below.

## Borderless windows and presentation

`WindowDesc::borderless` (engine-view's `--borderless`) opens a window with no title bar or border at the primary display's top-left corner (`SDL_WINDOW_BORDERLESS`, then `SDL_GetDisplayBounds` of `SDL_GetPrimaryDisplay`), so a window of the display's size covers it exactly — the "borderless fullscreen" a game offers. It is **not** an exclusive fullscreen: the display mode never changes and other windows can come over it. Sizes are in pixels on Windows here (a `--width 1280` window has a 1280-pixel swapchain on the 150 %-scaled desktop), so `--width` and `--height` of the display are what cover it.

**What covering the display changes, and what it does not** (2026-09-25, [the second owner session](../experiments/second-interactive-session-2026-09-25.md#present-pacing)). The owner's three 4K monitors are **one display to Windows**: NVIDIA Surround presents them as a single 11520×2160 display at 82 Hz (`\\.\DISPLAY1`, 12.2063 ms a refresh by the driver's own report), with one refresh clock, so a window spanning them is not a window spanning three displays and there is no clock disagreement between monitors to pace against; a 1920×1080 60 Hz monitor above them is `\\.\DISPLAY2`. What decides how a window paces is whether it **covers that display**: a window that does is flipped straight to it by the compositor (its present-to-display interval is exactly the refresh, frame after frame), and one that does not is composed by DWM (its frames reach the display at the refresh on average, but one in six or so a few milliseconds late and the next early, and 50–60 ms after they were sampled with the default queue). **Decorated or borderless made no difference**: the owner's decorated 11520×2160 window covers the display with its title bar pushed off the top, and it and a borderless one paced identically in every configuration measured (the pairs of frames 0.6 ms and 23.7 ms apart included), so `--borderless` is a convenience, not a fix; the fix is the display pacer ([apps](apps.md#pacing)). A window that spans several displays with separate clocks — two monitors without Surround — was not measured; it is composed by DWM on the primary display's clock, and the pacer's miss detection is what would notice it.

## The Vulkan surface

`foundation/window/backend/vulkan/surface.h` is a **backend header**, under the convention gfx's are ([gfx](gfx.md#the-rhi-surface-and-the-backend-surface)): `window::vulkan::instance_extensions()` feeds `gfx::DeviceOptions::instance_extensions`, and `window::vulkan::create_surface(window, instance, out)` and `destroy_surface(instance, surface)` bracket a `gfx::Swapchain`. Until 2026-09-25 these were members of `Window` in `window.h`, which put `VkInstance` and `VkSurfaceKHR` in the public header everything that opens a window compiles against — `engine-input`, which only reads devices, and engine-view's input conversion among them — for the benefit of the one caller that presents. Now `window.h` names no graphics API, and only what presents includes the backend header: `apps/engine_view` and gfx's swapchain test. `tools/lint.ps1` keeps both halves (`vulkan-in-public-header` allows Vulkan names only under `backend/vulkan/`; `vulkan-backend-include` allows including this directory only from `domain/gfx`, `foundation/window` and `apps/engine_view`). A second graphics backend brings its own glue beside it; a D3D12 swapchain wants the window's HWND, which `Window::native()` already hands out.

The two handle types are still forward-declared the way SDL does it (`typedef struct VkInstance_T* VkInstance`), so the header pulls in neither SDL nor the Vulkan headers and `foundation/window` (layer 1) stays below `domain/gfx` (layer 2); on 64-bit targets the typedefs are exactly vulkan_core.h's, and a translation unit that includes both sees the same typedef twice, which C++ allows. The three functions are implemented in `window.cpp` beside the rest, where SDL is. SDL's Vulkan entry points exist whatever display backends SDL was built with, so the header compiles and links under `ENGINE_WINDOW_BACKENDS=none` as well, where `init()` fails first and nothing calls it.

**Gamepads.** `poll()` also reports `GamepadConnected`, `GamepadDisconnected`, `GamepadButtonDown`, `GamepadButtonUp`, and `GamepadAxis`. `Event::gamepad` is this module's own slot id, `0..k_max_gamepads-1` (8), handed out lowest free first and released on disconnect — not SDL's instance id, which grows for the life of the process and would make a replay depend on the order pads were plugged in. `GamepadButton` is the standard layout named by position rather than by label (`South` is Xbox A, PlayStation cross, Nintendo B), plus the dpad, shoulders, sticks, `Back`/`Guide`/`Start`, and `LeftTrigger`/`RightTrigger` for the pads whose triggers click digitally (SDL routes the GameCube's there); anything else maps to `Unknown` and is dropped. `GamepadAxis` is the two sticks and the two triggers, normalized to -1..1 and 0..1 in `Event::value`, keeping SDL's sign convention (+x right, +y **down**, so a stick pushed forward reads negative). `gamepad_button_name`, `gamepad_axis_name`, `gamepad_name(slot)`, and `gamepad_connected(slot)` are for logs and tools. Gamepad events carry no window, so they go to whichever window is polling; the slot table is process-wide and `shutdown()` closes every pad. **The enumerator values of `GamepadButton` and `GamepadAxis` are part of the input log format** (docs/subsystems/input.md): append to them, never reorder or renumber.

**Raw joysticks.** SDL announces every device as a joystick, and the subset it has a mapping for a second time as a gamepad. This module opens a joystick only when SDL does *not* consider it a gamepad, so the two tables never hold the same device: everything with a known layout is reported by name through the gamepad events above, and everything else — wheels, pedal boxes, sequential and H-pattern shifters, flight sticks, button panels — arrives as `JoystickConnected`, `JoystickDisconnected`, `JoystickAxis`, `JoystickButtonDown`, `JoystickButtonUp`, and `JoystickHat`. There is nothing to name them by, so they carry bare indices: `Event::index` is the axis, button, or hat number the device itself uses, `Event::value` is the axis position normalized to -1..1 (no trigger convention — a pedal that rests at one end of its travel reads -1 at rest, which is the binding's `scale` to deal with, not the module's), and `Event::hat` is a `HatDirection`.

**The two slot spaces are separate.** `Event::gamepad` indexes the gamepad table, `Event::joystick` the joystick table; both start at 0, both are handed out lowest free first, both are released on disconnect, and **gamepad 0 and joystick 0 are two different devices**. Whoever converts these events into `input::RawEvent`s keeps them apart by *source*, never by the slot number: a `RawEvent` whose source is `GamepadButton` has a gamepad slot in `device`, one whose source is `JoystickButton` has a joystick slot. `k_max_joysticks` is 8, like `k_max_gamepads`.

**Hats.** A hat (a "POV hat", the d-pad on a wheel rim or a flight stick) reports a *position*, not a press: `HatDirection` is a bitmask of `Up` 1, `Right` 2, `Down` 4, `Left` 8, with the four diagonals as two bits or-ed and `Centered` as none — SDL's own numbering, and part of the log format (`input::k_hat_up` and friends mirror it). `hat_direction_name` names the nine positions and answers "Unknown" for anything else. Because a binding names a direction rather than a hat, the conversion to `input::RawEvent` turns one hat event into four digital signals, one per cardinal direction, coded `input::hat_code(hat_index, direction)`.

**Names.** Drivers name a device badly or not at all, so this module keeps a small table and prefers it over what the driver said. A Thrustmaster T300 RS arrives from the Windows driver as `44F B66E` — its USB ids in hex, because nothing wrote an OEM name into the registry. A Logitech F710 with its switch on XInput arrives as `XInput Controller #1`, because that is all XInput knows. A T500 RS gear shift reports `Thustmaster T500 RS Gear Shift`, a typo in the hardware's own product string. `resolve_device_name(vendor, product, raw_name)` answers the table's entry where it has one, the driver's name where it does not, the ids in hex (`"044F B66E"`) where nothing named it, and `"Unknown device"` where there is not even that; `known_device_name` is the table lookup alone, `nullptr` for a miss. The table's rows are keyed on vendor and product — every id in it read out of SDL's own database in the vendored source, so **0x044F 0xB65D is SDL's generic "Thrustmaster Wheel FFB" and not the T.16000M, which is 0x044F 0xB10A** — except the gear shift's, which is keyed on its exact misspelled name under its vendor, because the probe that found it recorded events and not ids. `gamepad_name(slot)`, `joystick_name(slot)`, the names in the connected events' log records, and `InputDeviceInfo::name` are all the resolved name; `InputDeviceInfo::raw_name` is what the driver said, unedited. Adding a device is a row in `k_device_names` in `src/window.cpp` and a line here.

**Describing a device without waiting for an event.** `input_devices(Vector<InputDeviceInfo>&)` lists every attached gamepad and joystick with its resolved `name` and the driver's `raw_name`, SDL's 32-character `guid` (bus, vendor, product, version — stable across sessions and machines), `vendor`, `product`, the number of `axes`, `buttons`, and `hats`, whether SDL calls it a gamepad, and the slot it holds. Reading the counts needs the device open, which SDL reference-counts, so listing does not disturb the event stream or the slot tables. `slot` is `k_invalid_slot` (0xFF) for a device whose arrival event has not been polled yet — SDL announces what is already plugged in as an arrival, so a caller polls for a moment first — or one that refused to open or found every slot of its kind taken.

**Rumble.** `rumble(gamepad, low, high, ms)` runs the two motors of a gamepad slot at 0..1 for a duration; it returns false for an empty slot or a pad with no motors, which is most of them, so false means "nothing happened" rather than "something went wrong". Joysticks have none: a force-feedback wheel is a haptics device, not two motors.

**Force feedback.** A wheel is driven with *forces*, over the raw joystick slot space, through SDL's haptics API. `haptics_open(joystick)` takes the device (false for an empty slot, a device with no haptics, or a machine with no haptics subsystem — `init()` asks for `SDL_INIT_HAPTIC` as optionally as it asks for the others), `haptics_info(joystick, HapticInfo&)` reports which of `constant`, `spring`, `damper`, `friction`, and `sine` the device supports and how many `axes` it can be pushed along, and `haptics_close` stops everything and hands it back. `set_constant_force(joystick, level)` is a fixed push along the first axis, -1..1; `set_spring(joystick, strength, center)` pulls towards a point, strength 0..1 and centre -1..1; `set_damper(joystick, strength)` resists velocity; `stop_forces(joystick)` stops and destroys all three. Each effect is created on first use, run with an infinite length, and *updated in place* afterwards, so a game that writes a new spring strength every frame is not rebuilding an effect every frame. Everything returns false where it is unsupported: false means "no force was applied", never "something went wrong". `shutdown()` and a disconnect close a slot's haptics before its joystick.

**Opening a wheel stops its own centring**, and a game has to take that over. The driver applies an autocentre spring until an application takes the device; SDL's open *is* that takeover, so a wheel that felt sprung goes limp the moment `haptics_open` succeeds — which is exactly what happened to the T300 RS during the probe that produced `content/input-logs/t300.jsonl`. So: a game that opens a wheel sets a spring or a damper itself and keeps it running for as long as it holds the device. `set_spring(slot, 0.5f, 0.0f)` is a reasonable resting force. `engine-input ffb` (docs/subsystems/apps.md) is how to feel one without writing a game.

**Relative mouse.** `Window::set_relative_mouse(true)` hides the cursor, holds it inside the window, and keeps `MouseMove`'s `dx`/`dy` reporting motion where an absolute pointer would have stopped at the screen's edge — SDL's `SDL_SetWindowRelativeMouseMode`, which is what a first-person camera needs; `relative_mouse()` reads back what SDL says is in effect. False for no window or a platform that refused (with the reason logged once as a warning), so a caller that tracks what it asked for does not ask again every frame. SDL keeps the mode per window and suspends it while the window has no focus, so switching away gives the cursor back without the caller doing anything; engine-view also drops its own capture on `FocusLost`, so coming back to the window does not start turning the camera until Escape is pressed again ([apps](apps.md#--interactive-a-camera-somebody-flies)). It is a mode of the window and not an input binding on purpose: *whether* the pointer is looking is a window's decision, and the conversion to `input::RawEvent` reads it — motion while the window does not hold the pointer is pointing, and engine-view's edge drops it before it becomes input.

**Synthetic events.** `Window::push_event(const Event&)` puts a key (by `scancode`), a mouse button, pointer motion or a wheel event on the window's own queue, and the next `poll()` returns it through the same switch a platform event takes — `SDL_PushEvent` with the window's id. Gamepad and joystick events are refused, because their slots are this module's names for real devices. It exists so a window can be driven with nobody at it: `engine-view --inject-input` feeds a recorded session through it for the end-to-end test and for smoke runs on a shared desktop, where synthesizing keystrokes at the operating system would type into whatever window has focus instead.

**Background events.** `set_background_input(true)` clears SDL's rule that device events are dropped while a process owns windows and none of them holds keyboard focus — right for a game, wrong for a tool started from a terminal whose user then has both hands on a wheel, which is why `engine-input` turns it on and `engine-view` does not.

**Build.** `cmake/EngineGraphics.cmake` fetches SDL `release-3.4.16` (`ENGINE_SDL_TAG`) and builds it static with audio, render, GPU, camera, and sensor subsystems off; joystick and haptics stay on, and `init()` calls `SDL_InitSubSystem(SDL_INIT_GAMEPAD)`, then `SDL_INIT_JOYSTICK`, then `SDL_INIT_HAPTIC` after the video subsystem (the first implies the second; each is asked for separately so a machine whose gamepad mappings fail to load still reports its wheels and sticks, and one with no force-feedback driver still reads them). On Linux SDL needs the X11 or Wayland development headers at build time (the libraries themselves are loaded at run time), and refuses to configure without them; the CI workflow installs them. A headless server build can set `SDL_UNIX_CONSOLE_BUILD=ON` to skip that check, and `init()` then fails cleanly at run time.

**Depends on.** `base`, `containers`, `log`; SDL3 (third_party/LICENSES.md).

**Testing.** `tools/dev.ps1 test -Filter window`: creates a hidden window, checks the pixel size, the surface extension list, event draining, rename, destroy, and shutdown; records a skip on machines without a display. The drain also covers the gamepad and joystick paths, since SDL reports every device already plugged in as an arrival during `init()`: each one must come through with a slot below its table's size and an open handle behind it, every gamepad button must map to something other than `Unknown`, every axis value must be in range, every hat must be one of the nine named positions, untouched slots of both kinds must read as empty, and `shutdown()` must close them all. The test then lists the devices, prints each one's resolved name, the driver's raw name, GUID, vendor, product, and counts as a doctest message — which is how a machine reports what it has — checks that every listed device holds the slot its arrival claimed and that its `name` is what `resolve_device_name` makes of its ids, and calls `rumble` on an empty slot and on each pad. On the same hidden window it turns relative mouse mode on and off and reads back what SDL says each time (a hidden window has no focus, so SDL records the mode without taking the pointer from whoever is at the machine), pushes a synthetic `W` and a synthetic motion and finds both coming back out of `poll()` with their scancode, `Key`, `dx` and `dy`, and checks that a gamepad event is refused and that all three calls answer false once the window is destroyed. Force feedback is the same shape: no test can feel one, so every empty joystick slot must answer false to `haptics_open`, `haptics_info`, the three `set_*` calls and `stop_forces`, and `haptics_close` on a slot that was never opened must do nothing; a slot that *does* have a device is opened, its `HapticInfo` printed as a message, stopped, and closed again without ever setting a force, since opening alone already takes a wheel's centring away. A machine with no device simply records that and checks the empty slots. A borderless window is created hidden at the size asked, so the flag is exercised without covering anybody's desktop. A second case needs neither a display nor a device: it pins the numbering of `GamepadButton`, `GamepadAxis`, and `HatDirection` and checks that every enumerator has a name of its own. A third pins the name table against the exact strings the drivers of this project's own devices produced — `"44F B66E"`, `"XInput Controller #1"`, `"Thustmaster T500 RS Gear Shift"` — including that the typo row matches under its vendor and nobody else's, and that an unknown device keeps the driver's name or, failing that, gets its ids. `apps/engine_input` is the end-to-end probe for devices nobody here owns (docs/subsystems/apps.md); `domain/gfx`'s swapchain test and `engine-view`'s end-to-end test open real windows.

**Not yet.** Haptics beyond a constant force, a spring, and a damper: no periodic effect (the rumble strip and the engine vibration a wheel's `sine` would give), no ramp, no envelope, no per-axis direction, no gain or autocentre control, no trigger rumble, and no LED or touchpad state. The three forces are also unverified on hardware — nobody here has a wheel to feel one, so what is tested is the plumbing and `content/input-logs/README.md` records what the T300 rig did. Devices beyond `k_max_gamepads`/`k_max_joysticks`, joystick trackballs (`SDL_EVENT_JOYSTICK_BALL_MOTION`), battery level, and the non-standard gamepad buttons — paddles, the touchpad, `Misc1` — which are dropped rather than reported. Text input and IME, clipboard, and multiple windows and per-output presentation for surround (docs/plan/04-renderer.md §4.8). Relative mouse mode has no raw-input or acceleration setting of its own (SDL's defaults: the platform's relative motion, unscaled), and synthetic gamepad events do not exist.

**Performance notes.** Event polling is a few microseconds per frame. SDL's static library adds about a minute to a cold CI build.
