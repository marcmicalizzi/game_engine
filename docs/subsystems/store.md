# store (foundation)

**Purpose.** The persistent world state of [03 §3.5](../plan/03-data-model.md#35-persistent-world-state) and [ADR-0003](../adr/0003-event-sourced-persistent-state.md), on SQLite: an append-only event log, the projections it folds down to, and one snapshot per tile that bounds how far a load has to replay. Underneath it is a thin, honest SQLite wrapper — `Status`-returning errors in `foundation/io`'s shape, a prepared-statement cache, RAII transactions, typed binds, `user_version` migrations. Measured by experiment **E6** ([results](../experiments/e6-ecs-store.md)); the settings below are its output, and the decision is drafted as [ADR-0028](../adr/0028-ecs-and-persistent-store.md), status Proposed.

**Why a wrapper at all, and why a thin one.** The reason [03 §3.5](../plan/03-data-model.md#35-persistent-world-state) chose SQLite is that agents and tests can run **SQL** against world state, which is the most powerful introspection surface available for almost no engineering cost. An abstraction over storage would throw that away. So `Database::handle()` hands out the `sqlite3*`, `exec` takes SQL as written, and nothing here pretends the store could be something else. What the wrapper exists for is the four things raw SQLite makes easy to get wrong:

- **Errors as `Status`.** Exceptions are off in engine targets and a bare `int` return tells a caller nothing.
- **A prepared-statement cache.** Preparing a statement parses and plans it. A save file written every tick runs the same dozen statements forever; preparing them once is the difference between a store you can call per tick and one you cannot. A `Statement` *borrows* from the cache and gives it back on destruction, so it is a scope rather than an owner; asking for the same SQL twice at once prepares a second, uncached copy so two live cursors never share one statement.
- **Transactions that roll back on scope exit.** An early return on an error path cannot leave half a tick in the file.
- **`user_version` migrations.** SQLite's own answer to [03 §3.8](../plan/03-data-model.md#38-schema-evolution). Each migration and its version bump commit together, so a file is never at a half-applied version, and a file written by a newer build is `SchemaTooNew` rather than silently misread.

**Owned data.** One `sqlite3` connection per `Database`, its statement cache, and the three tables `EventLog` creates. The `EventLog` also caches a per-tile sequence high-water mark so an append is one insert and not a `max()` first; a rolled-back batch drops the cache rather than leaving it ahead of the file.

**Why WAL and `synchronous=NORMAL`.** WAL lets readers run while a writer commits and turns a commit into an append; a rollback journal blocks readers for the length of every write, which is wrong for a file a simulation tick writes to while a streaming thread reads from it. `NORMAL` fsyncs at checkpoints rather than at every commit: a crash may lose the last transactions and can never corrupt the database, which is the right trade when the event log is what replays them. E6 measured the pair at **2×** a rollback journal at `FULL` on the same 1,000-row transaction. It is a durability trade and it is deliberate, not a default nobody looked at.

**Why 8 KiB pages.** A projection blob is 64–256 bytes and `projections` is `WITHOUT ROWID`; SQLite spills such a row to an overflow page once it passes about 1/20 of a page, which at the 4 KiB default is ~204 bytes — a threshold a 256-byte blob crosses. 8 KiB keeps the whole record inline and halves the depth of a million-row B-tree. It only takes effect on a database being created.

**Why the page cache is a setting you must set.** The by-entity index is keyed on random 128-bit ids, so a bulk load dirties a random page of a ~30 MB index per row. With SQLite's default 2 MiB cache E6 built a million records at 16,600 rows/s; with 64 MiB, at 67,900 — **4.1× for one pragma**. `OpenOptions::cache_kib` exists because leaving it at the default is a decision, and the wrong one.

**Why the tables have these keys.** The keys *are* the design:

| Table | Key | Why |
|---|---|---|
| `events` | `(tile, sequence)`, `WITHOUT ROWID` | every read of the log is "this tile, from this sequence" ([05 §5.5](../plan/05-simulation.md#55-reconciliation-when-a-tile-activates)), so storing rows in exactly that order makes a replay one contiguous B-tree walk instead of an index probe per event, and an append an insert at the right edge. The sequence is per tile, so two tiles written by two threads never contend for one counter |
| `projections` | `(tile, entity, kind)`, `WITHOUT ROWID`, plus an index on `(entity, kind)` | the dominant access is "materialize this tile", which wants a tile's projections contiguous; point lookup by entity is rarer and pays the secondary index |
| `snapshots` | `tile INTEGER PRIMARY KEY` (a rowid table) | the rowid *is* the tile, so a lookup is one descent. A snapshot blob is megabytes and lives in overflow pages whatever the key, so `WITHOUT ROWID` would buy nothing |

The consequence of a tile-leading key is that **an entity moving between tiles is a delete and an insert**, not an update. `upsert_projection` does that correctly and pays one extra seek of the by-entity index for it — E6 measured the correctness at about **2%**. `insert_projection` skips that seek for a bulk load where the caller knows the row is not filed elsewhere.

The consequence for *writers* is that **a persistence flush should sort by tile before it writes**. E6 measured tile-clustered inserts at 4.5× the throughput of the same rows round-robined over 1,024 tiles. That is a sort of a few thousand elements against a 4.5× write cost.

**Invariants (tested).**
- A new file opens in WAL mode with `synchronous=NORMAL`, 8 KiB pages, and foreign keys on; a second connection to the same file finds WAL already set. `wal = false` gives a rollback journal and `synchronous=FULL`.
- A `Transaction` that goes out of scope without `commit()` rolls back, and a `BEGIN` while one is open is refused rather than silently nesting.
- Every operation returns a `Status`; nothing throws. `SQLITE_DQS=0`, so `"typo"` is an identifier and a typo'd column is an error, not a constant string.
- The cache hands out the same `sqlite3_stmt*` for repeated preparations of one SQL text, and two *live* borrows of the same text get different cursors.
- Migrations run once, in ascending order; a failure leaves `user_version` at the last version that committed; a file beyond the last known version is `SchemaTooNew`; versions that do not ascend are `InvalidArgument` and nothing is applied.
- Appended events get ascending per-tile sequences, replay in sequence order, and survive a reopen (the counter is read back from the file, not reset). A failed batch append leaves the log exactly as it was.
- A projection is replaced in place, follows its entity between tiles as one row, and keeps a different `kind` as a separate row; `load_projection`'s blob points into a buffer the log owns, so it outlives the statement it was read through.
- A snapshot round-trips a tile's projections, records the sequence it covers so a replay resumes after it, and replaces the previous snapshot rather than accumulating.
- `scan` walks the whole log, across tiles, in (tick, tile, sequence) order, and resumes strictly after a `LogPosition`: paged two at a time it visits the same events in the same order as one scan and none twice, and an event appended later at a later tick is found after the place a reader stopped, whatever tile it lands in.
- A snapshot covers every event the file holds for its tile, including ones another connection appended after this one last looked, and this connection's next append follows them.
- `visit_events`, `visit_projections` and `visit_snapshots` walk every row in key order, and two stores holding the same rows written in different orders read the same.
- A file at table version 1 opens at version 2 with every event it held reading payload version 1, and an event appended at another payload version reads back with it through `replay`, `scan` and `visit_events`.
- A backup (`backup_to`) of a WAL database holds what the WAL held, has no free pages and no sidecar, and a backup of that backup, taken through a connection that opened it in WAL mode, is the same bytes. A destination that exists, or a call inside a transaction, is refused.

**Reading the whole log: `scan`.** `replay` answers the simulation's question — this tile, from this sequence — and is one B-tree walk because the key leads with the tile. A tool's question is different: what happened, in order, since I last looked ([06 §6.6](../plan/06-agent-tooling.md#66-introspection)'s `events(since, filter)`). The per-tile sequence cannot answer "after this" for the log as a whole, so `scan` orders by the simulation tick first, then tile, then sequence, and a `LogPosition` of those three is the cursor: a log is appended in tick order, so a reader that stops at a position finds everything appended since after it. The table has no index on the tick, so a page is a sort of the matching rows (a top-N sort, with the `LIMIT`) rather than a walk: right for an introspection page, wrong for anything that runs per tick, which should keep using `replay`. The comparison is SQLite's own row value, so "after" is exactly the `ORDER BY`'s "after"; the tile and the tick compare as the table stores them, signed, which is consistent and is all a cursor needs.

**Migrations: the tables' versions.** `EventLog::open` runs the log's migrations through `Database::migrate`, a step per `user_version`, each in a transaction with its bump. There are two:

| Version | What it did | Why |
|---|---|---|
| 1 | created `events`, `projections` (with `projections_by_entity`) and `snapshots` | the tables above |
| 2 | `ALTER TABLE events ADD COLUMN payload_version INTEGER NOT NULL DEFAULT 1` | [03 §3.8](../plan/03-data-model.md#38-schema-evolution): events carry their schema version, so a reader can upcast an old one. `EventRecord::payload_version` is the `@version` of the payload's type when it was written; engine-host's write-back events carry `engine.world.WriteBack`'s. Since 2026-11-17 (roadmap D26) a reader upcasts on read: `world::read_event_payload` (`systems/world/tile_store.h`) finds the type by its id (`schema::find_by_stable_id`), parses the payload and takes it through the type's steps, registered or generated (`schema::upcast`), and refuses a type the build lacks, a newer version or a missing step with a sentence. The store itself still never interprets a payload |

Version 2 is the worked example of a migration that adds a column, and three things about it are the pattern for the next one. **The default is a statement about every existing row**, so it must be true: every event a version 1 file holds was written with a payload at its type's first version, because no event type had a second one before the column existed — so 1, not 0 or null. **Adding a column with a constant default is a change to the schema, not a rewrite of the table** in SQLite, so migrating a store of a million events costs nothing measurable. **A migration is never edited once a file can carry it**, and never deleted while a save in the migration corpus needs it ([world](world.md#save-and-load)): `content/migration-corpus/saves/v1` is a save whose `world.db` is at version 1, loaded and migrated on every build. The test builds a version 1 file as that build created it, with two events, opens it, finds it at version 2 with both events reading payload version 1, and appends one at version 3 that reads back as 3 through `replay`, `scan` and `visit_events`. `EventRecord` grew from 80 to 88 bytes for the field — the four small fields no longer fit the eight bytes before `subject` — and is built per event appended or read, never stored in bulk.

**Reading the whole store: `visit_*`.** The persistent-state hash ([world](world.md#the-persistent-state-hash)) needs every row, and needs them in an order that is a function of the rows alone — never of when they were written or through which connection — so that two runs of a world that left the same rows behind read the same bytes. `visit_events`, `visit_projections` and `visit_snapshots` walk each table in its key order, (tile, sequence), (tile, entity, kind) and tile, comparing a tile and the halves of an id as the tables store them, signed. That is the B-tree's own order, so each is one walk of a table and not a sort. They are for a hash or a tool, not for anything per tick.

**Backups.** `Database::backup_to(path)` is `VACUUM INTO`: one read transaction's snapshot of the database, whatever other connections are writing — so a copy taken while the world's connection has the file open is consistent, and never a copy of a file with a live WAL beside it — with the WAL's committed frames folded in and no free pages, written in rollback-journal mode at the page size the connection was opened with. A save game is one ([world](world.md#save-and-load)), and a save has to go through a load and come out the same bytes, so **a backup's bytes are a function of the database's content**. `VACUUM INTO` gets most of the way by laying every table out afresh in key order; what it leaves is the schema cookie, which it sets to the source's plus one — so a backup of a backup would differ from the backup in four bytes of its header. `backup_to` therefore sets the copy's `schema_version` to 1 afterwards, through a connection of its own on a file nothing else has open. That is the one case the pragma is safe in: the cookie tells *other* connections their cached schema is stale, and there are none. The file change counter and the "version valid for" number are then the same on every copy (2), and the SQLite version number is the pinned amalgamation's. The test backs up a WAL database with history the content does not show (a table made and dropped, rows deleted, rows still in the WAL), backs the backup up again through a connection that opened it in WAL mode as a live store would, and compares the two files byte for byte.

**Two connections, one file.** `EventLog` caches each tile's next sequence so an append is one insert and not a `max()` first. engine-host used to hold two connections to a document's `world.db` — one the write-back's events went through, one the world's tiles did — and `snapshot` took the sequence it covers from *its* connection's cache. Events the other connection had appended to the tile since were then claimed by no snapshot, and a world loaded from a save, whose cache starts empty, recorded a different sequence than the run that never stopped: the first determinism fault the replay test found ([world](world.md#save-and-load)). **`snapshot` now reads the high-water mark from the file** — an index seek on the table's own key — and raises the cache to it, so this connection's next append does not collide with what another wrote. engine-host also routes the write-back's events through the tile store's connection when a streamed world has one open. Two writers appending to one tile through two connections is still wrong — the second's cached sequence collides with the first's rows as a `Constraint` — and nothing does it.

**Public API.**

- `foundation/store/database.h`: `Status` and `status_name`; `OpenOptions` (`read_only`, `create`, `wal`, `synchronous_normal`, `busy_timeout_ms`, `page_size`, `cache_kib`, `statement_cache_capacity`); `Migration`; `Statement` (1-based `bind`/`bind_ref`/`bind_null`, `step`, `run`, `reset`, 0-based `column_*`); `Transaction` (`commit`, `rollback`, `active`); `Database` (`open`, `open_memory`, `close`, `exec`, `prepare`, `begin`, `migrate`, `user_version`, `set_user_version`, `backup_to`, `journal_mode`, `file_size_bytes`, `last_insert_rowid`, `changes`, `last_error`, `handle`).
- `foundation/store/event_log.h`: `TileId`, `EventOrigin` and `origin_name`, `EventRecord`, `ProjectionRecord`, `SnapshotInfo`, `EventVisitor`/`ProjectionVisitor`/`SnapshotVisitor` (function pointers, not `std::function`: a replay of a million rows must not pay an indirect call through a type-erased object per row); `LogPosition`; `EventLog` (`open`, `schema_version`, `append` for one and for a batch, `next_sequence`, `replay`, `scan`, `count_events`, `upsert_projection`/`upsert_projections`, `insert_projection`, `erase_projection`, `load_projection`, `projections_by_tile`, `count_projections`, `snapshot`, `load_snapshot`, `restore_snapshot`, `visit_events`, `visit_projections`, `visit_snapshots`).
- `foundation/store/sql_query.h`: `SqlType`, `SqlValue`, the connection's limits (`k_sql_max_*`), `k_sql_functions`, `SqlQueryLimits`, `SqlQueryResult`, `run_sql_query`, `SqlConnectionReport` and `describe_sql_connection` ("SQL a client wrote", below).

**Threading.** SQLite is compiled `SQLITE_THREADSAFE=2` (multi-thread), so one `Database` belongs to one thread at a time. Two threads that both want the store open two connections to the same file; WAL is what makes the concurrent-reader case work. Serialized mode would take a mutex on every API call for a guarantee the engine does not need.

**Depends on.** `base`, `containers`, `ids`, `log`, and SQLite (`engine::sqlite3`, the amalgamation pinned by URL and SHA-256 in `cmake/EngineStore.cmake`, compiled as a SYSTEM static library).

**Zero-cost-when-unused ([11 §11.10](../plan/11-performance-principles.md#1110-absent-capabilities-are-free)):** no linked code. `ENGINE_WITH_STORE=OFF` and the minimal presets skip the module, its tests, its bench, *and* the SQLite download.

**Testing.** `tools/dev.ps1 test -Filter store` runs the invariants above in a temporary directory and in memory: WAL and pragma state on a fresh file and on a second connection, the rollback-journal variant, `NotFound` for a missing file with `create` off, transaction rollback on scope exit and refusal to nest, a round trip of every bind and column type, the statement cache's identity and its two-live-borrows behaviour, migrations forward and failing and too-new and out of order, `Status` for every error path including the `DQS` one, `file_size_bytes`, then the event log: per-tile sequences, replay in order and from the middle and of an empty tile, the whole-log `scan` by tick and tile, paged by position, from a tick, and after an event appended later into an earlier tile, an atomic batch, survival across a reopen, projections by tile and by entity, a tile change, and a snapshot written, read, restored, and replaced with only the events after it replayed; a version 1 file migrated to version 2 with its events at payload version 1; a snapshot taken after a second connection appended to its tile, covering those events; the whole store visited in key order from two stores written in opposite orders, row for row the same; and a backup of a WAL database, read back, and backed up again to the same bytes, with an existing destination and a call inside a transaction refused; and `sql_query_tests.cpp`, each rule of "SQL a client wrote" with the case that fails without it. The size table pins `EventRecord` at 88 bytes (80 before table version 2), `ProjectionRecord` at 56, `SnapshotInfo` at 40, `Statement` at 24.

`tools/dev.ps1 bench -Preset msvc-release -Filter store.*` runs experiment E6's half: insert throughput against batch size and against insert order, upsert against insert, WAL against a rollback journal, point lookup and range-by-tile at two page-cache sizes, the hourly summarization's read and write halves, snapshot write and read, event append at three batch sizes, a 10,000-event replay, and `store.sql_query`, a client's query by entity, by tile and as a scan ("SQL a client wrote").

**Performance notes.** Measured on an i9-10980XE with NVMe ([E6](../experiments/e6-ecs-store.md)): a million records is a **245 MB** file, 245 bytes a row for 64–256 byte blobs, built in **14.0 s**. Point lookup 20–32 µs, a tile's ~977 projections 293–411 µs, a 10,000-record snapshot 12.5 ms to write and 0.88 ms to read at 1.91 MB. The event log sustains **61,700 appends a second** at one transaction a tick and **285,000** at 1,024 events a transaction, against the hundreds-to-low-thousands [03 §3.5](../plan/03-data-model.md#35-persistent-world-state) expects, and replays **2.5 M events a second**. The rules those numbers imply: one transaction per tick (16× over one per row), sort by tile before writing (4.5×), size the page cache to the indices (4.1× on bulk load), and keep per-frame reads in memory — the store is the durability and query layer, not the hot read path.

**Machine state.** The read figures above were re-taken on 2026-09-18 ([bench](bench.md#measuring-on-a-shared-machine)). Point lookup ran twice on a machine below 10% others' CPU at both ends of both runs, agreeing within 3% (31.85/20.13 and 31.68/19.62 µs); range-by-tile took four attempts to get one such run (410.55/292.66 µs), and the attempt before it — which began at 3.2% others and ended at 86.3% because a parallel build started inside it — reported **948/584 µs, more than double**, and was thrown away on the WARNING. That pair of runs is the clearest demonstration available of why this section exists. The accepted figures are **7–11% faster** than the ones E6 first recorded (34.9/22.0 µs and 442/317 µs) and the corpus build 5% faster (14.7 s → 14.0 s); nothing in this module changed in between. The write, snapshot and event-log figures are still the original run's and have no record beside them.

**Not yet.** Schema-typed payloads in general: `EventRecord::payload` and `ProjectionRecord::blob` are opaque bytes to the store, and the `schemas/` types that [03 §3.5](../plan/03-data-model.md#35-persistent-world-state) wants in them, with migration on read, are wired up for one event and one projection so far (the write-back's, below, and the world's tile projection, below that); nothing reads an event's payload back into a type yet. Also absent: the projection cache for loaded tiles that systems actually read during play (the world reads a tile's projections once, when it activates, and nothing reads them while it is live); a host calling the flush's projections at `TickPhase::Persist` (`world::project_writeback` is built and engine-host's sink does not call it yet, below); projections of components beyond a record's place (a projection is the record, its type, its position and its importance, never its other state); writing on an efficiency-pool thread so a tick never waits on the file; `PRAGMA wal_checkpoint` policy and WAL size control (the WAL reached 30 MB during the million-row build); the content-addressed derived-data index of [03 §3.6](../plan/03-data-model.md#36-dependencies-and-invalidation), which is a second database with a different shape; and compacting the live file in place (`VACUUM`) — a save's copy of it is compact (`backup_to`, above), the file a world keeps writing is not.

## Write-back events

The first events the engine itself writes. When the runtime world writes back what systems changed in a document's `@writeback` fields ([sim](sim.md#write-back)) and the document keeps a store — `world.db` in its directory, `session.events`' convention — engine-host appends **one event per record the flush changed**, in one transaction, beside the journal commit:

| Field | Value |
|---|---|
| `type` | `schema::stable_type_id("engine.world.WriteBack")`: the 32-bit FNV-1a of the event type's qualified name ([schema](schema.md#materialization-type-mapping-as-data)), so every build agrees on it without a registry of numbers; `session.events` shows it in decimal as the event's `kind` |
| `origin` | `Deterministic` — the simulation wrote it — which `session.events` shows as the `actor` |
| `subject` | the record's `Id128` |
| `sim_tick`, `game_time_us` | the tick and game time of the flush |
| `tile` | the record's tile under its defining layer's partition, packed as x in the high 32 bits and y in the low (each two's complement), or 0 for a record in no tile. The store only compares and orders tile ids, so the packing is the host's; this one keeps a tile's events contiguous |
| `payload` | the canonical JSON of an `engine.world.WriteBack` (`schemas/world.schema`): the record, its type, the properties written (in the record's units) and the journal patch the write-back committed as |

Why both the journal and the log: the journal is the *document's* history — what the authoring state is and how to undo it — and the log is the *world's* ([ADR-0003](../adr/0003-event-sourced-persistent-state.md)): what happened, in tick order, replayable. A write-back is both a change to the document and a thing that happened in the world, and a reader of either should find it without consulting the other. The connection is opened for writing on the first flush that has something to log and kept for the session's world; `session.events` reads the same file through its own read-only connection, which WAL is what allows.

## Tiles: projections and snapshots (the world)

The first reader and writer of `projections` and `snapshots` that is not a test is the world capability's `WorldStore` ([world](world.md#the-consumers)), the `sim::TileStore` reconciliation reads a tile through when the tile ring activates it ([05 §5.5](../plan/05-simulation.md#55-reconciliation-when-a-tile-activates), [sim](sim.md#tile-reconciliation)). When a tile goes inactive it writes **one projection per record the tile held** — `kind` `schema::stable_type_id("engine.world.TileProjection")`, the entity the record's `Id128`, the blob the canonical JSON of an `engine.world.TileProjection` (`systems/world/schemas/world_tiles.schema`: the record, its type, its position from the document, its importance) — with `upsert_projections` (one transaction), then takes **the tile's snapshot** at the tick and game time it went — `snapshot`, which packs the tile's projections into one blob, as it always has. When the tile comes back, `tile_state` reads the snapshot (the tile is *known* when there is one; its last-active time is the snapshot's game time) and `load_records` the tile's projections of that kind, one `EntityRecord` each. The tile id is the write-back events' packing above, so a tile's events and its snapshot share one id. What a tile's simulation state is beyond its records' projections has no type yet, so the snapshot holds those and nothing else. The store itself learned nothing for this: the world keeps its own vocabulary in its own schema file, and the store stays the SQLite layer this page describes.

**Kept current by the flush** (roadmap S11, 2026-11-18). Written only at a tile's going, a live tile's projections said where its records were when the tile last went, or nothing — while [03 §3.5](../plan/03-data-model.md#35-persistent-world-state) has the store hold projections "for all tiles". `world::project_writeback(store, document, batch)` is the flush's half: handed a write-back's batch after the document took it, it replaces the projection of every record the flush wrote, as the document now has it, under the tile the document now puts it in (`WorldStore::write_projections`, one `upsert_projections` transaction, sorted by tile and then record as this page asks of a flush), so a record moved by the world leaves its old tile's rows as it moves; a record in no tile, or one the document no longer has, is counted and skipped; no snapshot is taken, which stays a tile's going. It reads the document, never the world, so it costs the records a flush wrote and nothing for the rest. **Not wired yet**: engine-host's write-back sink is where it belongs (after the session's commit, beside the events it appends, through the tile store's connection when a streamed world has one open), and the host is not this row's to edit. Calling it changes what `session.state_hash`'s projection part reads at a save taken while tiles are live — the rows are current rather than as of the tile's last going — so the hashes pinned over a streamed world (`apps/engine_cli`'s `npc_replay_tests.cpp`) move with it, once, by design. `session.run_headless` with `stream` opens the document's `world.db` for it ([protocol](protocol.md#sessionrun_headless-the-materialized-world)).

## SQL a client wrote

`store::run_sql_query` (`foundation/store/sql_query.h`, roadmap A14) runs one statement a client wrote against a store file, and is what engine-host's `store.query` is ([protocol](protocol.md#querying-the-document)). It is the reason [03 §3.5](../plan/03-data-model.md#35-persistent-world-state) chose SQLite — agents and tests running SQL against world state — and it is a client's text run inside the host, so the shape is that **nothing the text says can reach past its own statement, and nothing it does can run without a bound**. Each rule below fails a test against the plainest implementation (open, prepare, step, return), named in brackets.

**A connection of its own.** The function opens the file with `SQLITE_OPEN_READONLY` (and no `SQLITE_OPEN_URI`, so a path is never a URI with options in it), never through the world's connection, and closes it before it returns: the statement is finalized, no cursor is kept, and the read transaction that pins the WAL ends with the call. A next page is the client's own `LIMIT`/`OFFSET` or keyset.

**Hardened before the text is seen**, from SQLite's own page on running SQL that is not yours ([sqlite.org/security.html](https://www.sqlite.org/security.html), "Untrusted SQL Inputs" and "Untrusted SQLite Database Files", read whole): `SQLITE_DBCONFIG_DEFENSIVE` on (no statement may corrupt the file), `SQLITE_DBCONFIG_TRUSTED_SCHEMA` off (and `PRAGMA trusted_schema=0`), triggers and views off (`SQLITE_DBCONFIG_ENABLE_TRIGGER`, `ENABLE_VIEW`: the store has neither, so a file that grew one cannot run code through it), the double-quoted-string misfeature off for DML and DDL, extension loading off, the 3.49 attach-create and attach-write switches off where the amalgamation has them, `PRAGMA query_only=1` (a second wall behind the read-only open), `PRAGMA mmap_size=0` (the page's advice for a file read on someone else's behalf), and the page cache at 8 MiB. Each is read back by `describe_sql_connection` and the settings test holds every one. The page's "extra layers" for a file from another security domain (`integrity_check` first, `cell_size_check`) are not taken: the file is the world's own, written by this engine, and an integrity check of a million-row store would cost the query its whole budget. **The limits** (`sqlite3_limit`, set and read back): the statement 64 KiB, a value 1 MiB, 64 columns, expression depth 100, parser depth 100, 8 compound terms, 25,000 program instructions, 32 function arguments, no attached database, a `LIKE` pattern of 256 bytes, 64 parameters, trigger depth 1, no worker threads — the protocol page's design where it named a number, the security page's high-security column where a query over three tables can live with it, and the next value up where it cannot (`json_object` over a row wants more than 8 arguments; a `LIKE` pattern of 50 bytes refuses a reasonable prefix).

**The expression-depth limit needed a build change.** The amalgamation was compiled `SQLITE_MAX_EXPR_DEPTH=0`, from the "smaller, faster" set of SQLite's compile-options page, and that setting compiles the depth check away, so `sqlite3_limit(SQLITE_LIMIT_EXPR_DEPTH)` did nothing and an expression nested a few thousand deep would be walked recursively on the host's stack. `cmake/EngineStore.cmake` now leaves the define out (SQLite's compiled maximum, 1,000), and this connection lowers it to 100 [nested 5,000 deep; a chain of 200 and 5,000 calls].

**One statement that writes nothing.** The text is refused when it is longer than the limit, holds a NUL (the prepare would stop there and the rest would go unread) [`SELECT 1\0; DROP TABLE events`], holds no statement [empty; a comment], or holds a second one — the tail is prepared only to learn whether a statement is there, with the authorizer denying everything, since a prepare is not always free of effects (a flag pragma such as `query_only` or `writable_schema` takes effect as it is compiled, after its authorizer check), so whatever compiles or fails to compile there is the refusal [`SELECT 1; SELECT 2`, `SELECT 1; DROP TABLE events`, `SELECT 1; PRAGMA writable_schema = 1`, `SELECT 1; VACUUM`] — or when `sqlite3_stmt_readonly` says it writes. It is prepared with `SQLITE_PREPARE_NO_VTAB`, so **no virtual table is reachable**: the pragma table-valued functions, `json_each` and `json_tree`, `dbstat`, `generate_series` [each refused]. That is a change from the protocol page's design, which named the authorizer alone: a statement that reads no column of a virtual table never meets `SQLITE_READ`, and the flag closes the whole class at once.

**An authorizer** (`sqlite3_set_authorizer`, installed before the prepare) admits `SQLITE_SELECT`, `SQLITE_RECURSIVE` (common table expressions), `SQLITE_READ` of a table named `events`, `projections` or `snapshots` in the main database, and `SQLITE_FUNCTION` of a name on `k_sql_functions` — SQLite's scalars, aggregates, window, date and JSON functions that read only their arguments and whose work is about the sum of their lengths (seven that are not are off it; "`max_ms` is kept between opcodes", below) — and denies everything else with a sentence naming it: every write [INSERT, REPLACE, UPDATE, DELETE, a CTE's DELETE, CREATE and DROP of a table, index, view and trigger, ALTER, VACUUM and VACUUM INTO, REINDEX, ANALYZE, BEGIN, COMMIT, SAVEPOINT, RELEASE, DETACH, each with the file's counts and schema unchanged], `ATTACH` [a file, `:memory:`; no file made], `PRAGMA` reading and writing [`user_version`, `table_info`, `writable_schema` both ways, `query_only=0`, `journal_mode`, `cache_size`, `trusted_schema`], the schema table under every name [`sqlite_master`, `sqlite_schema`, `count(*)` of it, `main.` and `temp.` of it], a temp table or view, `load_extension` [one and two arguments], and every function off the list [`sqlite_compileoption_get`, `sqlite_version`, `changes`, `last_insert_rowid`; one this build lacks fails to compile]. Reads of a common table expression or a subquery are not reported to the authorizer, since they read no table; what they read underneath is.

**Values are bound**, `?1` to `?64`, never spliced: text by its length, so a NUL inside it survives the round trip; a blob as bytes; the parameter count must be the statement's [`'; DROP TABLE events; --` comes back as the text it is and the table stands; `a\0b` comes back three bytes long; a blob bound compares equal to the blob column it was read from; every storage class round-trips, a real's bits included]. **Bytes come back as bytes**: a blob column is an `SqlValue` of type `Blob` (`store.query` writes it `{"blob": "<base64>"}`), text its bytes with their length — which need not be UTF-8, since `CAST(x'ff' AS TEXT)` makes a text value of one byte 0xFF, so `store.query` writes text that is not well-formed UTF-8 in the blob form rather than as a JSON string it would make invalid.

**The bounds.** `max_ms` is a progress handler, called every 1,000 virtual-machine instructions, that interrupts the statement once the clock passes it; the rows returned before it are kept and the result names `max_ms` [a recursive CTE that never ends, stopped at 200 ms]. `max_rows` stops the stepping one row past the bound, so `complete` is false only when a row was left [a product of three 1,000-row tables, a billion rows, cut at 100]. `max_bytes` counts the values returned, text and blobs at their length and a number at 8, and drops the row that would pass it [two 500,000-byte blobs under 1 MiB]; the row is counted as its columns are read and refused at the column that passes the bound, before that column is copied, so one wide row is never built whole first and the bytes copied out of the statement (`copied_bytes`) are never more than `max_bytes` [sixty values of a million bytes in one row under 4 MiB: four copied, not sixty]. A value's size is read from its own storage class before its bytes, which converts nothing and does not even expand a `zeroblob`. A value grown inside the statement past the 1 MiB value limit fails the statement with the limit named, whatever grew it [`zeroblob`, `randomblob`, `printf` with a huge precision and a huge width, `hex` of a large blob, `replace` doubling a string in a recursive CTE, `group_concat` over a product]; a bound value past it is refused at the bind. **What the temporary store costs** was the one part the protocol page's design got wrong: it said the page cache and temp store would be bounded by `OpenOptions`, but SQLite has no per-connection cap on temporary storage — a sort or a `DISTINCT` past the page cache spills to temporary files of its own, ephemeral tables are separate b-trees `temp.max_page_count` does not reach, and the one heap cap (`sqlite3_hard_heap_limit64`) is process-wide and would starve the world's connection. So the page cache is capped (8 MiB), `temp_store=FILE` keeps a spill off the heap, and the temporary files a query makes are bounded by `max_ms` (at most 10 s) and deleted when the connection closes.

**`max_ms` is kept between opcodes, not inside one.** The progress handler runs every 1,000 virtual-machine instructions, so a statement runs past its bound by those instructions and at most one opcode more, and one call of a function is one opcode. So **a function is on the list only if its work is about the sum of its arguments' lengths**, which over operands capped at a value (1 MiB) and a pattern (256 bytes) is milliseconds: a `LIKE` or `GLOB` over the longest value gives up a star as soon as what follows it cannot match anywhere later [a 242-byte star pattern over a million characters, held within a second of `max_ms` 50], and a sort is not one opcode, since SQLite's sorter sorts each batch of about the page cache's size as it fills and merges the batches a row at a time. **Seven functions that read only their arguments are off it, because their work is a product of two lengths**: `instr` and `replace` compare a needle at every position of a haystack, `trim`, `ltrim`, `rtrim` and `unhex` look each character of one argument up in the whole of another, and `json_patch` looks each key of one object up among all of the other's. Measured on 2026-11-18 at the value limit with `max_ms` 1,000 (`msvc-debug` `engine-host --stdio`, the machine 80–96% busy with other rows' builds, so upper bounds; the scaling is the point): `instr` and `replace` of 1,048,000 characters for 524,001 each **19.5 s** in one opcode, `json_patch` of two objects of 40,000 keys **67 s**, and `unhex` of 600,000 characters skipping a set of 300,001 **889 s**. `ltrim` of the same shape was refused by the value limit, which its table of the set's characters passes at about 116,000 of them; with a set under that, `trim`, `ltrim` and `rtrim` do the same lookup as `unhex` (not measured). Outside the dispatch lock that would have been the caller's own answer and the host's exit, which waits for the statement ([protocol](protocol.md#work-outside-the-dispatch-lock)) — a host that cannot exit for a minute — so they are refused by name [each of the seven]. **What to use instead**: a `LIKE` or `GLOB` with a pattern of at most 256 bytes for a substring (`instr`), and the client for the rest — a query returns the values and the client replaces, trims, decodes or merges them; `json_set`, `json_insert` and `json_replace` with explicit paths change a JSON value in place, one path a lookup.

**Beside a world.** A query never takes a write lock, so in WAL mode the world's appends go on while it runs; what a long reader does hold is the WAL's read mark, so a checkpoint cannot pass the frames its snapshot needs and the WAL grows for as long as the query runs, at most `max_ms`. The test appends 64-event batches on the world's connection alone and then for as long as a 600 ms query runs beside it, and after the call a `wal_checkpoint(TRUNCATE)`, which must wait for every reader, finds no reader and empties the WAL — the query's connection is gone. In engine-host this is no longer two connections in a test: `store.query`'s statement runs with the dispatch lock let go ([protocol](protocol.md#work-outside-the-dispatch-lock)), so a world's write-back appends to `world.db` while it reads, and the WAL grows past its automatic checkpoint for at most the statement's `max_ms` (10 s) before the next commit's checkpoint catches it up.

**What it costs** (2026-11-18, `msvc-release`, `engine_store_bench --filter=store.sql_query* --repeats=3`, the E6 corpus of a million projections over 1,024 tiles; **upper bounds**: the harness recorded 45.8% of the CPU used by others, the GPU 96% busy under another row's lock): one entity through the by-entity index **2.05 ms** a call, one tile's ~977 rows through the primary key **2.89 ms**, a scan of the whole table (`count(*)`, `sum(length(blob))`) **284 ms**. The entity lookup is 20–32 µs through `EventLog` (above), so about 2 ms of every call is the call's own connection — the open, the hardening, the schema read for the authorizer, the close — which is the price of nothing outliving the call and is paid once a query, not once a row. The test beside a world (`msvc-debug`, the same shared machine) measured an append of 64 events at a median of 0.66–0.83 ms alone and 0.85–1.10 ms beside a 600 ms query over three runs, with a worst append of 69–85 ms beside it: the appends are not blocked, and the worst one is the writer's automatic checkpoint, which cannot pass the reader's snapshot while it stands.

**Without these rules** the tests fail: the same cases run against the plainest implementation (open read-write, `sqlite3_prepare_v2`, step, return) fail 10 of the 11 they could run, 160 assertions among them, and the never-ending query and the world beside it were not run against it, since the first never returns.

**General purpose.** Nothing here names an event type or a projection kind; a game's events and projections are queried as the engine's are, as opaque blobs beside typed key columns.
