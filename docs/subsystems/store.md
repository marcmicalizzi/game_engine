# store (foundation)

**Purpose.** The persistent world state of [03 §3.5](../plan/03-data-model.md#35-persistent-world-state) and [ADR-0003](../adr/0003-event-sourced-persistent-state.md), on SQLite: an append-only event log, the projections it folds down to, and one snapshot per tile that bounds how far a load has to replay. Underneath it is a thin, honest SQLite wrapper — `Status`-returning errors in `foundation/io`'s shape, a prepared-statement cache, RAII transactions, typed binds, `user_version` migrations. Measured by experiment **E6** ([results](../experiments/e6-ecs-store.md)); the settings below are its output, and the decision is drafted as [ADR-0028](../adr/0028-ecs-and-persistent-store.md), status Proposed.

**Why a wrapper at all, and why a thin one.** The reason [03 §3.5](../plan/03-data-model.md#35-persistent-world-state) chose SQLite is that agents and tests can run **SQL** against world state, which is the most powerful introspection surface available for almost no engineering cost. An abstraction over storage would throw that away. So `Database::handle()` hands out the `sqlite3*`, `exec` takes SQL as written, and nothing here pretends the store could be something else. What the wrapper exists for is the four things raw SQLite makes easy to get wrong:

- **Errors as `Status`.** Exceptions are off in engine targets and a bare `int` return tells a caller nothing.
- **A prepared-statement cache.** Preparing a statement parses and plans it. A save file written every tick runs the same dozen statements forever; preparing them once is the difference between a store you can call per tick and one you cannot. A `Statement` *borrows* from the cache and gives it back on destruction, so it is a scope rather than an owner; asking for the same SQL twice at once prepares a second, uncached copy so two live cursors never share one statement.
- **Transactions that roll back on scope exit.** An early return on an error path cannot leave half a tick in the file.
- **`user_version` migrations.** SQLite's own answer to [03 §3.8](../plan/03-data-model.md#38-schema-evolution). Each migration and its version bump commit together, so a file is never at a half-applied version, and a file written by a newer build is `SchemaTooNew` rather than silently misread.

**Owned data.** One `sqlite3` connection per `Database`, its statement cache, and the three tables `EventLog` creates. The `EventLog` also caches a per-tile sequence high-water mark so an append is one insert and not a `max()` first; a rolled-back batch drops the cache rather than leaving it ahead of the file.

**Why WAL and `synchronous=NORMAL`.** WAL lets readers run while a writer commits and turns a commit into an append; a rollback journal blocks readers for the length of every write, which is wrong for a file a simulation tick writes to while a streaming thread reads from it. `NORMAL` fsyncs at checkpoints rather than at every commit: a crash may lose the last transactions and can never corrupt the database, which is the right trade when the event log is what replays them. E6 measured the pair at **2×** a rollback journal at `FULL` on the same 1,000-row transaction. It is a durability trade and it is deliberate, not a default nobody looked at.

**Why 8 KiB pages.** A projection blob is 64–256 bytes and `projections` is `WITHOUT ROWID`; SQLite spills such a row to an overflow page once it passes about 1/20 of a page, which at the 4 KiB default is ~204 bytes — a threshold a 256-byte blob crosses. 8 KiB keeps the whole record inline and halves the depth of a million-row B-tree. It only takes effect on a database being created.

**Why the page cache is a setting you must set.** The by-entity index is keyed on random 128-bit ids, so a bulk load dirties a random page of a ~30 MB index per row. With SQLite's default 2 MiB cache E6 built a million records at 16,600 rows/s; with 64 MiB, at 67,900 — **4.1× for one pragma**. `OpenOptions::cache_kib` exists because leaving it at the default is a decision, and the wrong one.

**Why the tables have these keys.** The keys *are* the design:

| Table | Key | Why |
|---|---|---|
| `events` | `(tile, sequence)`, `WITHOUT ROWID` | every read of the log is "this tile, from this sequence" ([05 §5.5](../plan/05-simulation.md#55-reconciliation-when-a-tile-activates)), so storing rows in exactly that order makes a replay one contiguous B-tree walk instead of an index probe per event, and an append an insert at the right edge. The sequence is per tile, so two tiles written by two threads never contend for one counter |
| `projections` | `(tile, entity, kind)`, `WITHOUT ROWID`, plus an index on `(entity, kind)` | the dominant access is "materialize this tile", which wants a tile's projections contiguous; point lookup by entity is rarer and pays the secondary index |
| `snapshots` | `tile INTEGER PRIMARY KEY` (a rowid table) | the rowid *is* the tile, so a lookup is one descent. A snapshot blob is megabytes and lives in overflow pages whatever the key, so `WITHOUT ROWID` would buy nothing |

The consequence of a tile-leading key is that **an entity moving between tiles is a delete and an insert**, not an update. `upsert_projection` does that correctly and pays one extra seek of the by-entity index for it — E6 measured the correctness at about **2%**. `insert_projection` skips that seek for a bulk load where the caller knows the row is not filed elsewhere.

The consequence for *writers* is that **a persistence flush should sort by tile before it writes**. E6 measured tile-clustered inserts at 4.5× the throughput of the same rows round-robined over 1,024 tiles. That is a sort of a few thousand elements against a 4.5× write cost.

**Invariants (tested).**
- A new file opens in WAL mode with `synchronous=NORMAL`, 8 KiB pages, and foreign keys on; a second connection to the same file finds WAL already set. `wal = false` gives a rollback journal and `synchronous=FULL`.
- A `Transaction` that goes out of scope without `commit()` rolls back, and a `BEGIN` while one is open is refused rather than silently nesting.
- Every operation returns a `Status`; nothing throws. `SQLITE_DQS=0`, so `"typo"` is an identifier and a typo'd column is an error, not a constant string.
- The cache hands out the same `sqlite3_stmt*` for repeated preparations of one SQL text, and two *live* borrows of the same text get different cursors.
- Migrations run once, in ascending order; a failure leaves `user_version` at the last version that committed; a file beyond the last known version is `SchemaTooNew`; versions that do not ascend are `InvalidArgument` and nothing is applied.
- Appended events get ascending per-tile sequences, replay in sequence order, and survive a reopen (the counter is read back from the file, not reset). A failed batch append leaves the log exactly as it was.
- A projection is replaced in place, follows its entity between tiles as one row, and keeps a different `kind` as a separate row; `load_projection`'s blob points into a buffer the log owns, so it outlives the statement it was read through.
- A snapshot round-trips a tile's projections, records the sequence it covers so a replay resumes after it, and replaces the previous snapshot rather than accumulating.

**Public API.**

- `foundation/store/database.h`: `Status` and `status_name`; `OpenOptions` (`read_only`, `create`, `wal`, `synchronous_normal`, `busy_timeout_ms`, `page_size`, `cache_kib`, `statement_cache_capacity`); `Migration`; `Statement` (1-based `bind`/`bind_ref`/`bind_null`, `step`, `run`, `reset`, 0-based `column_*`); `Transaction` (`commit`, `rollback`, `active`); `Database` (`open`, `open_memory`, `close`, `exec`, `prepare`, `begin`, `migrate`, `user_version`, `set_user_version`, `journal_mode`, `file_size_bytes`, `last_insert_rowid`, `changes`, `last_error`, `handle`).
- `foundation/store/event_log.h`: `TileId`, `EventOrigin` and `origin_name`, `EventRecord`, `ProjectionRecord`, `SnapshotInfo`, `EventVisitor`/`ProjectionVisitor` (function pointers, not `std::function`: a replay of a million rows must not pay an indirect call through a type-erased object per row); `EventLog` (`open`, `schema_version`, `append` for one and for a batch, `next_sequence`, `replay`, `upsert_projection`/`upsert_projections`, `insert_projection`, `erase_projection`, `load_projection`, `projections_by_tile`, `count_projections`, `snapshot`, `load_snapshot`, `restore_snapshot`).

**Threading.** SQLite is compiled `SQLITE_THREADSAFE=2` (multi-thread), so one `Database` belongs to one thread at a time. Two threads that both want the store open two connections to the same file; WAL is what makes the concurrent-reader case work. Serialized mode would take a mutex on every API call for a guarantee the engine does not need.

**Depends on.** `base`, `containers`, `ids`, `log`, and SQLite (`engine::sqlite3`, the amalgamation pinned by URL and SHA-256 in `cmake/EngineStore.cmake`, compiled as a SYSTEM static library).

**Zero-cost-when-unused ([11 §11.10](../plan/11-performance-principles.md#1110-absent-capabilities-are-free)):** no linked code. `ENGINE_WITH_STORE=OFF` and the minimal presets skip the module, its tests, its bench, *and* the SQLite download.

**Testing.** `tools/dev.ps1 test -Filter store` runs the invariants above in a temporary directory and in memory: WAL and pragma state on a fresh file and on a second connection, the rollback-journal variant, `NotFound` for a missing file with `create` off, transaction rollback on scope exit and refusal to nest, a round trip of every bind and column type, the statement cache's identity and its two-live-borrows behaviour, migrations forward and failing and too-new and out of order, `Status` for every error path including the `DQS` one, `file_size_bytes`, then the event log: per-tile sequences, replay in order and from the middle and of an empty tile, an atomic batch, survival across a reopen, projections by tile and by entity, a tile change, and a snapshot written, read, restored, and replaced with only the events after it replayed. The size table pins `EventRecord` at 80 bytes, `ProjectionRecord` at 56, `SnapshotInfo` at 40, `Statement` at 24.

`tools/dev.ps1 bench -Preset msvc-release -Filter store.*` runs experiment E6's half: insert throughput against batch size and against insert order, upsert against insert, WAL against a rollback journal, point lookup and range-by-tile at two page-cache sizes, the hourly summarization's read and write halves, snapshot write and read, event append at three batch sizes, and a 10,000-event replay.

**Performance notes.** Measured on an i9-10980XE with NVMe ([E6](../experiments/e6-ecs-store.md)): a million records is a **245 MB** file, 245 bytes a row for 64–256 byte blobs, built in **14.0 s**. Point lookup 20–32 µs, a tile's ~977 projections 293–411 µs, a 10,000-record snapshot 12.5 ms to write and 0.88 ms to read at 1.91 MB. The event log sustains **61,700 appends a second** at one transaction a tick and **285,000** at 1,024 events a transaction, against the hundreds-to-low-thousands [03 §3.5](../plan/03-data-model.md#35-persistent-world-state) expects, and replays **2.5 M events a second**. The rules those numbers imply: one transaction per tick (16× over one per row), sort by tile before writing (4.5×), size the page cache to the indices (4.1× on bulk load), and keep per-frame reads in memory — the store is the durability and query layer, not the hot read path.

**Machine state.** The read figures above were re-taken on 2026-09-18 ([bench](bench.md#measuring-on-a-shared-machine)). Point lookup ran twice on a machine below 10% others' CPU at both ends of both runs, agreeing within 3% (31.85/20.13 and 31.68/19.62 µs); range-by-tile took four attempts to get one such run (410.55/292.66 µs), and the attempt before it — which began at 3.2% others and ended at 86.3% because a parallel build started inside it — reported **948/584 µs, more than double**, and was thrown away on the WARNING. That pair of runs is the clearest demonstration available of why this section exists. The accepted figures are **7–11% faster** than the ones E6 first recorded (34.9/22.0 µs and 442/317 µs) and the corpus build 5% faster (14.7 s → 14.0 s); nothing in this module changed in between. The write, snapshot and event-log figures are still the original run's and have no record beside them.

**Not yet.** Schema-typed payloads: `EventRecord::payload` and `ProjectionRecord::blob` are opaque bytes, and the `schemas/` types that [03 §3.5](../plan/03-data-model.md#35-persistent-world-state) wants in them (with `type`/`kind` as schema type ids and migration on read) are not wired up. Also absent: the projection cache for loaded tiles that systems actually read during play; the persistence flush that would attach this to `domain/ecs`' `TickPhase::Persist`; writing on an efficiency-pool thread so a tick never waits on the file; `PRAGMA wal_checkpoint` policy and WAL size control (the WAL reached 30 MB during the million-row build); the content-addressed derived-data index of [03 §3.6](../plan/03-data-model.md#36-dependencies-and-invalidation), which is a second database with a different shape; and `VACUUM`/save-file compaction.
