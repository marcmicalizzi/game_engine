# store (foundation)

**Purpose.** The persistent world state of [03 §3.5](../plan/03-data-model.md#35-persistent-world-state) and [ADR-0003](../adr/0003-event-sourced-persistent-state.md), on SQLite: an append-only event log, the projections it folds down to, and one snapshot per tile that bounds how far a load has to replay. Underneath it is a thin, honest SQLite wrapper — `Status`-returning errors in `foundation/io`'s shape, a prepared-statement cache, RAII transactions, typed binds, `user_version` migrations. Measured by experiment **E6** ([results](../experiments/e6-ecs-store.md)); the settings below are its output, and the decision is drafted as [ADR-0028](../adr/0028-ecs-and-persistent-store.md), status Proposed.

**Why a wrapper at all, and why a thin one.** The reason [03 §3.5](../plan/03-data-model.md#35-persistent-world-state) chose SQLite is that agents and tests can run **SQL** against world state, which is the most powerful introspection surface available for almost no engineering cost. An abstraction over storage would throw that away. So `Database::handle()` hands out the `sqlite3*`, `exec` takes SQL as written, and nothing here pretends the store could be something else. What the wrapper exists for is the four things raw SQLite makes easy to get wrong:

- **Errors as `Status`.** Exceptions are off in engine targets and a bare `int` return tells a caller nothing.
- **A prepared-statement cache.** Preparing a statement parses and plans it. A save file written every tick runs the same dozen statements forever; preparing them once is the difference between a store you can call per tick and one you cannot. A `Statement` *borrows* from the cache and gives it back on destruction, so it is a scope rather than an owner; asking for the same SQL twice at once prepares a second, uncached copy so two live cursors never share one statement.
- **Transactions that roll back on scope exit.** An early return on an error path cannot leave half a tick in the file.
- **`user_version` migrations.** SQLite's own answer to [03 §3.8](../plan/03-data-model.md#38-schema-evolution). Each migration and its version bump commit together, so a file is never at a half-applied version, and a file written by a newer build is `SchemaTooNew` rather than silently misread.

**Owned data.** One `sqlite3` connection per `Database`, its statement cache, and the three tables `EventLog` creates. The `EventLog` also caches a per-tile sequence high-water mark so an append is one insert and not a `max()` first; a rolled-back batch drops the cache rather than leaving it ahead of the file.

**Why WAL and `synchronous=NORMAL`.** WAL lets readers run while a writer commits and turns a commit into an append; a rollback journal blocks readers for the length of every write, which is wrong for a file a simulation tick writes to while a streaming thread reads from it. `NORMAL` fsyncs at checkpoints rather than at every commit: a crash may lose the last transactions and can never corrupt the database, which is the right trade when the event log is what replays them. E6 measured the pair at **2×** a rollback journal at `FULL` on the same 1,000-row transaction. It is a durability trade and it is deliberate, not a default nobody looked at.

**Why 8 KiB pages.** A projection blob is 64–256 bytes and `projections` is `WITHOUT ROWID`; SQLite spills such a row to an overflow page once it passes about 1/20 of a page, which at the 4 KiB default is ~204 bytes — a threshold a 256-byte blob crosses. 8 KiB keeps the whole record inline and halves the depth of a million-row B-tree. It only takes effect on a database being created.

**Why the page cache is a setting you must set.** The by-entity index is keyed on random 128-bit ids, so a bulk load dirties a random page of a ~30 MB index per row. With SQLite's default 2 MiB cache E6 built a million records at 16,600 rows/s; with 64 MiB, at 67,900 — **4.1× for one pragma**. `OpenOptions::cache_kib` exists because leaving it at the default is a decision, and the wrong one.

**Why the tables have these keys.** The keys *are* the design:

| Table | Key | Why |
|---|---|---|
| `events` | `(tile, sequence)`, `WITHOUT ROWID` | every read of the log is "this tile, from this sequence" ([05 §5.5](../plan/05-simulation.md#55-reconciliation-when-a-tile-activates)), so storing rows in exactly that order makes a replay one contiguous B-tree walk instead of an index probe per event, and an append an insert at the right edge. The sequence is per tile, so two tiles written by two threads never contend for one counter |
| `projections` | `(tile, entity, kind)`, `WITHOUT ROWID`, plus an index on `(entity, kind)` | the dominant access is "materialize this tile", which wants a tile's projections contiguous; point lookup by entity is rarer and pays the secondary index |
| `snapshots` | `tile INTEGER PRIMARY KEY` (a rowid table) | the rowid *is* the tile, so a lookup is one descent. A snapshot blob is megabytes and lives in overflow pages whatever the key, so `WITHOUT ROWID` would buy nothing |

The consequence of a tile-leading key is that **an entity moving between tiles is a delete and an insert**, not an update. `upsert_projection` does that correctly and pays one extra seek of the by-entity index for it — E6 measured the correctness at about **2%**. `insert_projection` skips that seek for a bulk load where the caller knows the row is not filed elsewhere.

The consequence for *writers* is that **a persistence flush should sort by tile before it writes**. E6 measured tile-clustered inserts at 4.5× the throughput of the same rows round-robined over 1,024 tiles. That is a sort of a few thousand elements against a 4.5× write cost.

**Invariants (tested).**
- A new file opens in WAL mode with `synchronous=NORMAL`, 8 KiB pages, and foreign keys on; a second connection to the same file finds WAL already set. `wal = false` gives a rollback journal and `synchronous=FULL`.
- A `Transaction` that goes out of scope without `commit()` rolls back, and a `BEGIN` while one is open is refused rather than silently nesting.
- Every operation returns a `Status`; nothing throws. `SQLITE_DQS=0`, so `"typo"` is an identifier and a typo'd column is an error, not a constant string.
- The cache hands out the same `sqlite3_stmt*` for repeated preparations of one SQL text, and two *live* borrows of the same text get different cursors.
- Migrations run once, in ascending order; a failure leaves `user_version` at the last version that committed; a file beyond the last known version is `SchemaTooNew`; versions that do not ascend are `InvalidArgument` and nothing is applied.
- Appended events get ascending per-tile sequences, replay in sequence order, and survive a reopen (the counter is read back from the file, not reset). A failed batch append leaves the log exactly as it was.
- A projection is replaced in place, follows its entity between tiles as one row, and keeps a different `kind` as a separate row; `load_projection`'s blob points into a buffer the log owns, so it outlives the statement it was read through.
- A snapshot round-trips a tile's projections, records the sequence it covers so a replay resumes after it, and replaces the previous snapshot rather than accumulating.
- `scan` walks the whole log, across tiles, in (tick, tile, sequence) order, and resumes strictly after a `LogPosition`: paged two at a time it visits the same events in the same order as one scan and none twice, and an event appended later at a later tick is found after the place a reader stopped, whatever tile it lands in.
- A snapshot covers every event the file holds for its tile, including ones another connection appended after this one last looked, and this connection's next append follows them.
- `visit_events`, `visit_projections` and `visit_snapshots` walk every row in key order, and two stores holding the same rows written in different orders read the same.
- A backup (`backup_to`) of a WAL database holds what the WAL held, has no free pages and no sidecar, and a backup of that backup, taken through a connection that opened it in WAL mode, is the same bytes. A destination that exists, or a call inside a transaction, is refused.

**Reading the whole log: `scan`.** `replay` answers the simulation's question — this tile, from this sequence — and is one B-tree walk because the key leads with the tile. A tool's question is different: what happened, in order, since I last looked ([06 §6.6](../plan/06-agent-tooling.md#66-introspection)'s `events(since, filter)`). The per-tile sequence cannot answer "after this" for the log as a whole, so `scan` orders by the simulation tick first, then tile, then sequence, and a `LogPosition` of those three is the cursor: a log is appended in tick order, so a reader that stops at a position finds everything appended since after it. The table has no index on the tick, so a page is a sort of the matching rows (a top-N sort, with the `LIMIT`) rather than a walk: right for an introspection page, wrong for anything that runs per tick, which should keep using `replay`. The comparison is SQLite's own row value, so "after" is exactly the `ORDER BY`'s "after"; the tile and the tick compare as the table stores them, signed, which is consistent and is all a cursor needs.

**Reading the whole store: `visit_*`.** The persistent-state hash ([world](world.md#the-persistent-state-hash)) needs every row, and needs them in an order that is a function of the rows alone — never of when they were written or through which connection — so that two runs of a world that left the same rows behind read the same bytes. `visit_events`, `visit_projections` and `visit_snapshots` walk each table in its key order, (tile, sequence), (tile, entity, kind) and tile, comparing a tile and the halves of an id as the tables store them, signed. That is the B-tree's own order, so each is one walk of a table and not a sort. They are for a hash or a tool, not for anything per tick.

**Backups.** `Database::backup_to(path)` is `VACUUM INTO`: one read transaction's snapshot of the database, whatever other connections are writing — so a copy taken while the world's connection has the file open is consistent, and never a copy of a file with a live WAL beside it — with the WAL's committed frames folded in and no free pages, written in rollback-journal mode at the page size the connection was opened with. A save game is one ([world](world.md#save-and-load)), and a save has to go through a load and come out the same bytes, so **a backup's bytes are a function of the database's content**. `VACUUM INTO` gets most of the way by laying every table out afresh in key order; what it leaves is the schema cookie, which it sets to the source's plus one — so a backup of a backup would differ from the backup in four bytes of its header. `backup_to` therefore sets the copy's `schema_version` to 1 afterwards, through a connection of its own on a file nothing else has open. That is the one case the pragma is safe in: the cookie tells *other* connections their cached schema is stale, and there are none. The file change counter and the "version valid for" number are then the same on every copy (2), and the SQLite version number is the pinned amalgamation's. The test backs up a WAL database with history the content does not show (a table made and dropped, rows deleted, rows still in the WAL), backs the backup up again through a connection that opened it in WAL mode as a live store would, and compares the two files byte for byte.

**Two connections, one file.** `EventLog` caches each tile's next sequence so an append is one insert and not a `max()` first. engine-host used to hold two connections to a document's `world.db` — one the write-back's events went through, one the world's tiles did — and `snapshot` took the sequence it covers from *its* connection's cache. Events the other connection had appended to the tile since were then claimed by no snapshot, and a world loaded from a save, whose cache starts empty, recorded a different sequence than the run that never stopped: the first determinism fault the replay test found ([world](world.md#save-and-load)). **`snapshot` now reads the high-water mark from the file** — an index seek on the table's own key — and raises the cache to it, so this connection's next append does not collide with what another wrote. engine-host also routes the write-back's events through the tile store's connection when a streamed world has one open. Two writers appending to one tile through two connections is still wrong — the second's cached sequence collides with the first's rows as a `Constraint` — and nothing does it.

**Public API.**

- `foundation/store/database.h`: `Status` and `status_name`; `OpenOptions` (`read_only`, `create`, `wal`, `synchronous_normal`, `busy_timeout_ms`, `page_size`, `cache_kib`, `statement_cache_capacity`); `Migration`; `Statement` (1-based `bind`/`bind_ref`/`bind_null`, `step`, `run`, `reset`, 0-based `column_*`); `Transaction` (`commit`, `rollback`, `active`); `Database` (`open`, `open_memory`, `close`, `exec`, `prepare`, `begin`, `migrate`, `user_version`, `set_user_version`, `backup_to`, `journal_mode`, `file_size_bytes`, `last_insert_rowid`, `changes`, `last_error`, `handle`).
- `foundation/store/event_log.h`: `TileId`, `EventOrigin` and `origin_name`, `EventRecord`, `ProjectionRecord`, `SnapshotInfo`, `EventVisitor`/`ProjectionVisitor`/`SnapshotVisitor` (function pointers, not `std::function`: a replay of a million rows must not pay an indirect call through a type-erased object per row); `LogPosition`; `EventLog` (`open`, `schema_version`, `append` for one and for a batch, `next_sequence`, `replay`, `scan`, `count_events`, `upsert_projection`/`upsert_projections`, `insert_projection`, `erase_projection`, `load_projection`, `projections_by_tile`, `count_projections`, `snapshot`, `load_snapshot`, `restore_snapshot`, `visit_events`, `visit_projections`, `visit_snapshots`).

**Threading.** SQLite is compiled `SQLITE_THREADSAFE=2` (multi-thread), so one `Database` belongs to one thread at a time. Two threads that both want the store open two connections to the same file; WAL is what makes the concurrent-reader case work. Serialized mode would take a mutex on every API call for a guarantee the engine does not need.

**Depends on.** `base`, `containers`, `ids`, `log`, and SQLite (`engine::sqlite3`, the amalgamation pinned by URL and SHA-256 in `cmake/EngineStore.cmake`, compiled as a SYSTEM static library).

**Zero-cost-when-unused ([11 §11.10](../plan/11-performance-principles.md#1110-absent-capabilities-are-free)):** no linked code. `ENGINE_WITH_STORE=OFF` and the minimal presets skip the module, its tests, its bench, *and* the SQLite download.

**Testing.** `tools/dev.ps1 test -Filter store` runs the invariants above in a temporary directory and in memory: WAL and pragma state on a fresh file and on a second connection, the rollback-journal variant, `NotFound` for a missing file with `create` off, transaction rollback on scope exit and refusal to nest, a round trip of every bind and column type, the statement cache's identity and its two-live-borrows behaviour, migrations forward and failing and too-new and out of order, `Status` for every error path including the `DQS` one, `file_size_bytes`, then the event log: per-tile sequences, replay in order and from the middle and of an empty tile, the whole-log `scan` by tick and tile, paged by position, from a tick, and after an event appended later into an earlier tile, an atomic batch, survival across a reopen, projections by tile and by entity, a tile change, and a snapshot written, read, restored, and replaced with only the events after it replayed; a snapshot taken after a second connection appended to its tile, covering those events; the whole store visited in key order from two stores written in opposite orders, row for row the same; and a backup of a WAL database, read back, and backed up again to the same bytes, with an existing destination and a call inside a transaction refused. The size table pins `EventRecord` at 80 bytes, `ProjectionRecord` at 56, `SnapshotInfo` at 40, `Statement` at 24.

`tools/dev.ps1 bench -Preset msvc-release -Filter store.*` runs experiment E6's half: insert throughput against batch size and against insert order, upsert against insert, WAL against a rollback journal, point lookup and range-by-tile at two page-cache sizes, the hourly summarization's read and write halves, snapshot write and read, event append at three batch sizes, and a 10,000-event replay.

**Performance notes.** Measured on an i9-10980XE with NVMe ([E6](../experiments/e6-ecs-store.md)): a million records is a **245 MB** file, 245 bytes a row for 64–256 byte blobs, built in **14.0 s**. Point lookup 20–32 µs, a tile's ~977 projections 293–411 µs, a 10,000-record snapshot 12.5 ms to write and 0.88 ms to read at 1.91 MB. The event log sustains **61,700 appends a second** at one transaction a tick and **285,000** at 1,024 events a transaction, against the hundreds-to-low-thousands [03 §3.5](../plan/03-data-model.md#35-persistent-world-state) expects, and replays **2.5 M events a second**. The rules those numbers imply: one transaction per tick (16× over one per row), sort by tile before writing (4.5×), size the page cache to the indices (4.1× on bulk load), and keep per-frame reads in memory — the store is the durability and query layer, not the hot read path.

**Machine state.** The read figures above were re-taken on 2026-09-18 ([bench](bench.md#measuring-on-a-shared-machine)). Point lookup ran twice on a machine below 10% others' CPU at both ends of both runs, agreeing within 3% (31.85/20.13 and 31.68/19.62 µs); range-by-tile took four attempts to get one such run (410.55/292.66 µs), and the attempt before it — which began at 3.2% others and ended at 86.3% because a parallel build started inside it — reported **948/584 µs, more than double**, and was thrown away on the WARNING. That pair of runs is the clearest demonstration available of why this section exists. The accepted figures are **7–11% faster** than the ones E6 first recorded (34.9/22.0 µs and 442/317 µs) and the corpus build 5% faster (14.7 s → 14.0 s); nothing in this module changed in between. The write, snapshot and event-log figures are still the original run's and have no record beside them.

**Not yet.** Schema-typed payloads in general: `EventRecord::payload` and `ProjectionRecord::blob` are opaque bytes to the store, and the `schemas/` types that [03 §3.5](../plan/03-data-model.md#35-persistent-world-state) wants in them, with migration on read, are wired up for one event and one projection so far (the write-back's, below, and the world's tile projection, below that); nothing reads an event's payload back into a type yet. Also absent: the projection cache for loaded tiles that systems actually read during play (the world reads a tile's projections once, when it activates, and nothing reads them while it is live); the persistence flush that would attach this to `domain/ecs`' `TickPhase::Persist`; writing on an efficiency-pool thread so a tick never waits on the file; `PRAGMA wal_checkpoint` policy and WAL size control (the WAL reached 30 MB during the million-row build); the content-addressed derived-data index of [03 §3.6](../plan/03-data-model.md#36-dependencies-and-invalidation), which is a second database with a different shape; and compacting the live file in place (`VACUUM`) — a save's copy of it is compact (`backup_to`, above), the file a world keeps writing is not.

## Write-back events

The first events the engine itself writes. When the runtime world writes back what systems changed in a document's `@writeback` fields ([sim](sim.md#write-back)) and the document keeps a store — `world.db` in its directory, `session.events`' convention — engine-host appends **one event per record the flush changed**, in one transaction, beside the journal commit:

| Field | Value |
|---|---|
| `type` | `schema::stable_type_id("engine.world.WriteBack")`: the 32-bit FNV-1a of the event type's qualified name ([schema](schema.md#materialization-type-mapping-as-data)), so every build agrees on it without a registry of numbers; `session.events` shows it in decimal as the event's `kind` |
| `origin` | `Deterministic` — the simulation wrote it — which `session.events` shows as the `actor` |
| `subject` | the record's `Id128` |
| `sim_tick`, `game_time_us` | the tick and game time of the flush |
| `tile` | the record's tile under its defining layer's partition, packed as x in the high 32 bits and y in the low (each two's complement), or 0 for a record in no tile. The store only compares and orders tile ids, so the packing is the host's; this one keeps a tile's events contiguous |
| `payload` | the canonical JSON of an `engine.world.WriteBack` (`schemas/world.schema`): the record, its type, the properties written (in the record's units) and the journal patch the write-back committed as |

Why both the journal and the log: the journal is the *document's* history — what the authoring state is and how to undo it — and the log is the *world's* ([ADR-0003](../adr/0003-event-sourced-persistent-state.md)): what happened, in tick order, replayable. A write-back is both a change to the document and a thing that happened in the world, and a reader of either should find it without consulting the other. The connection is opened for writing on the first flush that has something to log and kept for the session's world; `session.events` reads the same file through its own read-only connection, which WAL is what allows.

## Tiles: projections and snapshots (the world)

The first reader and writer of `projections` and `snapshots` that is not a test is the world capability's `WorldStore` ([world](world.md#the-consumers)), the `sim::TileStore` reconciliation reads a tile through when the tile ring activates it ([05 §5.5](../plan/05-simulation.md#55-reconciliation-when-a-tile-activates), [sim](sim.md#tile-reconciliation)). When a tile goes inactive it writes **one projection per record the tile held** — `kind` `schema::stable_type_id("engine.world.TileProjection")`, the entity the record's `Id128`, the blob the canonical JSON of an `engine.world.TileProjection` (`systems/world/schemas/world_tiles.schema`: the record, its type, its position from the document, its importance) — with `upsert_projections` (one transaction), then takes **the tile's snapshot** at the tick and game time it went — `snapshot`, which packs the tile's projections into one blob, as it always has. When the tile comes back, `tile_state` reads the snapshot (the tile is *known* when there is one; its last-active time is the snapshot's game time) and `load_records` the tile's projections of that kind, one `EntityRecord` each. The tile id is the write-back events' packing above, so a tile's events and its snapshot share one id. What a tile's simulation state is beyond its records' projections has no type yet, so the snapshot holds those and nothing else. The store itself learned nothing for this: the world keeps its own vocabulary in its own schema file, and the store stays the SQLite layer this page describes. `session.run_headless` with `stream` opens the document's `world.db` for it ([protocol](protocol.md#sessionrun_headless-the-materialized-world)).
