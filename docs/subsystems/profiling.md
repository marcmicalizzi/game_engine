# profiling (core)

**Purpose.** The profiler hooks every module instruments itself with (docs/plan/09-testing-profiling.md §9.3, ADR-0012). With the CMake option `ENGINE_TRACY` the macros are Tracy client zones, frame marks, plots, messages, and allocation events; without it they expand to nothing, so instrumentation stays in the code at zero cost. Tracy runs in on-demand mode: until a profiler connects, a zone costs a predictable few nanoseconds.

**Placement.** The plan lists profiling under the foundation layer; the hooks live in core so that the job system, I/O, and every other core module can carry zones. The startup trace lives here too, for the same reason: a loader in any layer records its stages. The profiling *service* — the frame report and the trace export over the frame capture below, for the `profile` protocol tool — is the foundation-layer module that builds on this, [profiler](profiler.md); budget checks will join it.

**Public API.** `core/profiling/profile.h`: `ENGINE_PROFILE_ZONE()`, `ENGINE_PROFILE_ZONE_NAMED(name)`, `ENGINE_PROFILE_ZONE_TEXT(text, size)`, `ENGINE_PROFILE_FRAME()`, `ENGINE_PROFILE_FRAME_NAMED(name)`, `ENGINE_PROFILE_THREAD(name)`, `ENGINE_PROFILE_PLOT(name, value)`, `ENGINE_PROFILE_MESSAGE(text, size)`, `ENGINE_PROFILE_ALLOC(ptr, size)`, `ENGINE_PROFILE_FREE(ptr)`; `profiling::enabled()`, `profiling::connected()`. `core/profiling/frame_capture.h`: the frame capture (below).

**Rules.** One `ENGINE_PROFILE_ZONE` per scope (it declares a local). A zone per system and per pass, not per element; per-job zones exist in the job system because a job is the unit of scheduling. Plots for the counts a frame budget tracks. Worker threads name themselves.

**A thread that names itself keeps 4 MiB of commit until the process ends** (T129, 2026-11-14; [the measurement](../experiments/memory-commit-accounting.md#who-made-the-unnamed-commit)). In a Tracy build `ENGINE_PROFILE_THREAD` stores the name in Tracy's own allocator, rpmalloc, whose first allocation on a thread maps that thread a heap of 64 spans of 64 KiB at once, committed and untouched; the name lives in the first span for the rest of the process (Tracy keeps every thread's name), so the mapping is never returned when the thread ends, on-demand mode or not. Every job pool's worker names itself, so **a pool made and joined per call cost 4 MiB a worker each time**: the tile meshes' texture pass did that per mesh and held 6.2 GB of the forest staging's commit after its tiles arrived twice. Two answers, both in: the pass no longer makes a pool, and `cmake/EngineProfiling.cmake` builds Tracy's client with `DEFAULT_SPAN_MAP_COUNT=4`, so a thread's first mapping is 256 KiB, not 4 MiB (rpmalloc maps more as it needs them, which only a connected profiler's queues do). A thread that names itself still keeps its 256 KiB: make pools long-lived, or do short work on the calling thread. A build without `ENGINE_TRACY` has none of it.

**Instrumented today.** Job workers (thread names, a zone per executed job), protocol dispatch, document store load and save, and the startup stages below (each is a Tracy zone of the same name in a Tracy build).

**A frame's time, attributed whole, without Tracy** (roadmap T71 part 3, landed 2026-11-03 with R130; parts 1 and 2, the profile shader variant and a timestamp pair a dispatch, are open). Every frame record a benchmark writes carries `sections` (`engine.scene.FrameSections`): the frame loop's spans in its order — the host's turn, the slot's wait, the rest of `begin_frame` with the chain's resize inside it, the fold, the acquire, the ticks, the submission, what follows it, the present and the tail — which partition the frame's own interval and sum to it, so a hitch is never "unattributed" again; and `gpu_ms.unbucketed`, the timer's total less every bucket, which names GPU time folded into no bucket. They are measured with the clock reads the loop already made, in every build, at no cost a frame worth stating ([apps](apps.md#flythroughs) has the fields; the test is `flythrough: a frame's sections sum to its wall time, and a slow host turn is named`). Tracy's GPU zones for the live view are still part 3's to do.

## The frame capture

`core/profiling/frame_capture.h` (roadmap T44): what a running process did over a stretch of frames, **in every build, Tracy or not**, recorded only while a host has turned it on (`capture_start` .. `capture_stop`), and read by [profiler](profiler.md) into a frame report and a trace. Tracy needs a profiler connected to the process and a release build; a `profile` request over the protocol needs neither, which is why the capture exists beside it rather than through it.

- **Zones.** Every `ENGINE_PROFILE_ZONE()` (named `__func__`) and `ENGINE_PROFILE_ZONE_NAMED(name)` scope is also a `CaptureZone`: when the capture was on at both its ends it records one event with its thread and its two times. In a Tracy build the macro is both, Tracy's zone and the capture's.
- **Frame marks.** `capture_frame(index)` at a frame's start and, optionally, `capture_frame_end(index)` at its end. The index is the frame loop's own, so `ENGINE_PROFILE_FRAME()` (which has none) stays Tracy's alone.
- **Values.** `capture_value(CaptureTrack::gpu | cpu, name, index, ms)`: a time measured elsewhere for frame `index` — a GPU pass from its timestamp queries, a CPU span of the frame loop.
- **Threads.** `ENGINE_PROFILE_THREAD(name)` also calls `capture_name_thread`, which copies the name onto the thread (31 bytes; the job system names its workers from a stack buffer) and into the capture's table at the thread's first event. A thread's index is the order of its first event in the capture.
- **Thread names** (2026-11-18, from a concurrency review). A report of a running capture (`profile.report` while it runs) copies the table while threads make their first events and rename themselves, and the table was plain chars the reader copied as a writer wrote them — a data race, and a torn name in the report — because the thread count is bumped before the name is written. Each name is now 32 bytes of atomic 8-byte words under a sequence word that is odd while it is written; `capture_thread_name(thread, out)` copies a name only when the sequence was even and unchanged across its copy, looks again a few times while one is being written, and otherwise answers no name. A slot never named in this capture (sequence 0) answers no name too, which is the one answer for a thread counted before its name lands. One writer a slot (its thread; the shared last slot is written once), so the sequence needs no lock. `frame_capture_tests.cpp`, "a name read while threads name themselves is whole or empty", reads the table 2,000 times while eight threads rename themselves, and on past them until every thread has named itself and made its first event, a minute at most (T199: on a busy machine the 2,000 looks once ended before any worker had run, and found no name to check).

**Off it costs one relaxed atomic load per zone and allocates nothing** (before T44 it was nothing at all; the zones are per system and per pass, so the load is not in an inner loop). On, each event enters as a writer and pays for it:
- a sequentially consistent add on **its thread's writer word**, two sequentially consistent loads (the switch, then the generation), a relaxed add on the one counter every thread shares that claims its slot, 48 bytes written (`CaptureEvent`, in the size table), a release store that publishes them, and a release subtract on the writer word;
- that is three read-modify-writes, of which only the claim is on a line other threads write. The writer words are 64 cache lines, one a thread in the order threads first record (a 65th thread shares the first's, as a count), and `capture_stop` turns the switch off and then waits for every word to read zero: the same Dekker pair as before, per word, so the stop is as exact as it was (below).

**Why the words** (found by batch 68's review of the capture, mended in batch 69). Until then the writer count was one counter every thread shared, entered and left with two read-modify-writes an event, and threads recording at once queued on its line. `engine_profiler_bench` (`profiler.capture.zone/<threads>`: one zone timed on one thread while the others record as fast as they can; `msvc-release`, 2026-11-18, others at 58 to 88 % of the CPU, so upper bounds), before and after, two runs each: alone 86 ns a zone both ways; with eight threads 1.47 to 1.50 µs before and 0.80 to 0.82 µs after; with sixteen 2.51 µs before and 1.55 to 1.63 µs after. What is left with threads is the claim, which stays one shared counter because the order of claims is what lets a filled buffer say that nothing after its `full_ns` was recorded ([profiler](profiler.md#the-frame-report)); claiming slots in blocks a thread would end that and was not done. A number taken under a capture still states that it was. A full buffer drops and counts (`CaptureInfo::dropped`) and stamps when it filled (`CaptureInfo::full_ns`, which the report ends at; [profiler](profiler.md#the-frame-report)), so **a frame loop with the capture on still allocates nothing**.

The default is 2^18 events, 14 MiB with each slot's publication word. **A start holds exactly the capacity asked** (found by batch 68's review of the capture): `capture_start` reuses the last buffer only when it is that size, and otherwise gives it back and makes one that is, so a capture drops at the event its caller was told, and `capture_capacity()` says what the buffer holds. Before, a start kept any buffer at least as large, so a small capture after a large one dropped later than it said and the largest buffer anyone asked for — 4,194,304 events, about 200 MiB, which every role may ask a host for — stayed for the life of the process. **A stopped capture's buffer stays** until the next start or `capture_reset`, because a stopped capture is still read (`profile.report` after `profile.stop`); freeing a large buffer at the stop would have made that read fail, so it was not done, and a host that wants the memory back starts a small capture and stops it.

**Generations.** Each start bumps a generation, and a zone that began under one capture and ends under another is dropped. A writer reads the switch and then the generation, the reverse of the order in which `capture_start` stores them (generation, then switch). So a writer that sees a capture on is in that capture or a later one. Read the other way round, an event racing a start could pass with the old generation: a frame mark the new capture never sees, and a phantom thread (review C2, 2026-11-18).

**Stopping is exact.** A writer enters by raising a count before it reads the switch a second time, and `capture_stop` turns the switch off and then waits for that count to fall to zero (sequentially consistent on both sides, the order a store-then-load handshake needs), so once it returns no thread is still inside the buffer: a zone that began while the capture was on and ends after the stop is dropped whole, never half written, and `capture_snapshot` after the stop reads the same events every time (the threaded test takes two snapshots while three threads keep running zones). Each capture has a generation, and a zone that began in one capture and ends in the next is dropped too. `capture_snapshot` while recording copies only the slots already published.

**Names are pointers**: a string literal, `__func__`, or a table that outlives the capture — the report keeps them as they are.

## The startup trace

`core/profiling/startup_trace.h` (roadmap W69): what a process did between its launch and the moment it was ready, recorded only while a host has turned it on (`engine-view --startup-trace`, `render.load` with `startup_trace`; [apps](apps.md#--startup-trace-from-launch-to-ready)). Flat memory over a load cannot tell a wait from CPU work, IO, a cache check or the driver; this can, because every stage carries what tells them apart.

- **A stage** (`ENGINE_STARTUP_STAGE(name)`, `ENGINE_STARTUP_STAGE_DETAIL(name, detail)`, `TraceStage`) is a named interval on the thread that ran it: wall time from the trace's origin, the thread's own CPU time over it (`GetThreadTimes`, `CLOCK_THREAD_CPUTIME_ID`), the bytes the process read through the OS while it ran (`GetProcessIoCounters`, `/proc/self/io` `rchar` — process-wide, so exact for a serial stage and an upper bound beside other threads' reads; mapped files arrive as page faults instead), the time it reported blocked (`trace_wait`, `TraceWait`), a count (`trace_items`), and a copied detail (96 bytes: a path, a reason). Stages nest per thread: a stage's parent is the one open on its thread when it began.
- **A dependency edge** (`trace_depends`, or a `TraceWait` scope naming the stage it waits for) points at a stage that **began earlier** — anything else is refused and counted — so the graph is acyclic by construction (`trace_acyclic` checks a set read from anywhere), and a summary never adds two overlapping stages as if one followed the other.
- **A milestone** (`trace_milestone`, `trace_milestone_at` for one dated after the fact) is an instant with the process's counters at it.
- **The sampler** (a thread, every 20 ms) records the process: CPU time, bytes and read calls, working set, private commit, page faults. The Chrome trace draws them as counter tracks (cores busy, read MiB/s, faults/s, memory), which is what shows a stretch of no memory growth to be CPU-bound, reading, or neither.
- **The origin** is the process's launch as the OS records it (`process_start_ns`: `GetProcessTimes`, `/proc/self/stat`), so the time before `main` — the loader, static initialization, an antivirus scan of a freshly built executable — is in the numbers and not lost.

**Off it costs one relaxed atomic load per stage and allocates nothing**; every entry point returns while `trace_enabled()` is false. On, the events go into a buffer `trace_start` allocates once (32,768 events by default; a full buffer drops and counts), so recording never allocates, and a frame loop with the trace on allocates nothing (engine-view's `startup_trace_view_tests.cpp` checks the frame records). **engine-view asks for 2^18** (`apps/engine_view/startup.cpp`, T73; about 70 MB, only under `--startup-trace`): the sampler takes four slots every 20 ms and a mesh three, so the v35 forest's ten-minute load filled the default at 251 s, 7,003 meshes in, and dropped 173,143 events — every stage after the meshes, every milestone after `device` and the second half of the memory curve ([the measurements](../experiments/load-v35-2026-11-08.md)). A summary whose `dropped_events` is not zero has lost its tail; `tools/startup-trace-summary.ps1 -Trace <startup.json>` prints a trace as tables (stages by name, the longest stages with the working set and commit at their ends, one stage's spread over the threads, the milestones). Names are string literals; the trace keeps the pointer.

**The trace records past ready, to its buffer's end, and no further.** Nothing stops it at the host's ready milestone: a walk's frames (`frame`, the tile changes, the collision builds, the samples) go on filling the buffer after `nearby_stable`, which is how a walk's long frames have been attributed (T167, T172), until the buffer is full; then every later event is refused and counted (`trace_dropped`, the summary's `dropped_events`, the Chrome trace's `otherData.dropped`), the memory never grows past what `trace_start` allocated, and the live progress, which has its own switch, keeps working. engine-view's block says what had been refused when `nearby_stable` was reached as `dropped_before_ready` (null when it never was), so a lost tail of the walk is not read as a lost tail of the load. A host's frame loop feeds its readiness to the last milestone, past its own ready rung (engine-view's `StartupTrace::feed`, roadmap T211: a window stopped at `player_controllable`, and no windowed session had reached `nearby_stable` before it).

**The readers are linear in the events** (T210). On 2026-11-20 the owner's five-minute walk of the forest at 4K ended with engine-view on one core for over twenty minutes inside `startup_summary_json`, its report never written (43 s on 2026-11-17): for every top-level stage of the main thread before ready the summary walked every event and climbed its parents with a lookup by id, and a walk never ready makes every `frame` such a stage — quadratic in the events, and the trace full at 2^18. `trace_acyclic` scanned every event per edge, the same shape. Now one pass orders the events by id (a snapshot is in order already; a set from elsewhere is sorted once), a lookup by id is a binary search and never a scan, the stages beneath each top-level stage are found by one climb per event and kept with it in event order, and the other threads' totals are one pass for all threads: the summary, `chrome_trace_json` and `trace_acyclic` are linear in the events but for those lookups (n log n), and **their bytes are what they were** — `tests/startup_summary_reference.h` keeps the readers as they were, and the tests compare the two on a recorded trace, on a streamed session's shape ready and never ready (`tests/synthetic_session.h`), and on a set out of id order. Each reader counts what it does (`TraceWalkCost`: an event read, a step of a lookup), and a case holds the count under the bound its passes give at 10^5 and 10^6 events, where a clock would say nothing on a busy machine. The bench `profiling.startup_summary.*` times both: [the measurements](../experiments/startup-trace-readers-2026-11-20.md).

**Output.** `chrome_trace_json` writes the JSON Object Format: complete events (`"ph":"X"`) with every field in `args` (`id`, `parent`, `depends`, `cpu_ns`, `wait_ns`, `read_bytes`, `items`, `detail`), global instants for milestones, counter tracks for the samples, and flow arrows for the edges — loadable in `chrome://tracing` and [Perfetto](https://ui.perfetto.dev). `startup_summary_json` is the block both hosts report: the milestones in the order given, **held monotone** (one reached before a milestone listed ahead of it is reported at that one's time, with `reached_ms` and a count in `milestones_reordered`); the top-level stages of the thread that recorded the first milestone, its serial critical path, each with its three longest children and every wait beneath it; `unstaged_ms`, the time before the last milestone no top-level stage covers; the other threads' busy time; and `before_ready`, the process from the samples — CPU, bytes read, page faults, the peak working set and commit, and the intervals spent on a CPU (half a core or more), reading (4 MiB/s or more), or neither.

### The trace is live

**The same stages feed a progress record while they run** (`ProgressPlan`, `LoadProgress`, `progress_*` in `startup_trace.h`; roadmap W79), which is what a loading screen draws, what a game's `game_loading` hook is handed ([hotload](hotload.md#the-module-abi), ABI 7) and what `render.progress` answers ([protocol](protocol.md)). It has its own switch (`progress_start` .. `progress_stop`), so a window that shows its load pays for no trace buffer and a trace can record with nothing shown; every `TraceStage` checks both, and off it is still one relaxed load each.

- **A plan** names the load's top-level stages, each with a weight, and its milestone ladder. The host builds it — engine-view from the previous run's measured stage times (`progress_measured`, stored at `<ddc>/startup/<scene hash>.json`; [apps](apps.md#the-loading-presentation)), or the same weight for every stage when there is none. Nothing about it is decided by a timestamp: the file is a previous run's numbers, read or not there.
- **A plan's stage** becomes the current stage when it begins and is done when it ends; **any other stage** that begins meanwhile, on any thread, becomes the current stage's `detail` (`cluster read: tree.clusters`), so the detail says what the load is doing without the plan having to know every stage. `trace_items` counts into `items` and every milestone sets its rung's bit, both whether the trace records or not.
- **The fraction** is the done stages' weight over the plan's, plus — only when the weights are a previous run's — the current stage's weight times its elapsed time over its previous duration, capped at 0.9 of it, so the bar moves inside a long stage and never claims it finished. It **never falls**: a read returns at least the largest fraction any read returned. `progress_finish` (the host's ready milestone) makes it 1.
- **Readable from any thread, allocating nothing.** A writer (a stage's begin or end; a few hundred a load) takes a spin flag and bumps a sequence on both sides of its change; `progress_read` copies the record between two equal, even reads of the sequence and retries otherwise, so a reader never sees a stage with another's detail half-written (the threaded test reads 20,000 times beside three writers).
- **The pump** (`progress_set_pump`, `progress_pump`): the thread that owns a window registers a callback, and every stage that begins or ends **on that thread** while progress is on calls it, as does `progress_pump()` from inside a long stage between its slices (the GPU scene's texture uploads, the ground's first fields). That is how a stage that has to run on the device's thread keeps the window's messages flowing without knowing there is a window. A stage the callback itself begins does not pump again.

**Instrumented stages** (zones only; none changes what it times): engine-view's own sequence (`device`, `scene file`, `animation clips`, `load scene`, `attach`, `ground prepare`, `gpu scene`, `renderer`, `ground start`, `world create`, `session`, one `frame` a frame); in the renderer the scene file's `schema read` (its text read straight into the schema's structs since D40, where it was a `json parse` into a tree and then a `schema read` out of it), `scene expand`, `ground sampler`, `mask level` (the masks cooked and held to their budget before the placements, T122, with the provider's `ground masks` inside it: the cook or its hit, a stage wherever it is first asked), `placements`, `water`, `content classes` (the class read before any mesh is read, items the distinct paths; [renderer](renderer.md#content-classes-at-load), C72), `meshes` (the load's wait for its per-mesh jobs; since W75 each `mesh` stage is on the job system's thread that ran it) and per mesh `mesh` with `source hash`, `cluster read`, `generator inputs`, `generate`, `mesh build`, `cache entry ignored` (an **accidental rebuild**: an entry under the key that the build would not use, its reason as the detail), then the load's one `cache textures` with `texture identities` (items: the distinct files), `texture probe` (items: the distinct keys), `texture build` (items: the textures built) and `textures trusted` (an instant whose detail is `trusted=… built=… hashed=… from_index=…`; until W75 `cache textures` was one stage per mesh), the instance table's `instances`; the GPU scene's `upload geometry`, `upload materials`, `working set`, `flora motion`, `terrain levels`, `ray tracing`; the renderer's `shader manifest`, `sky`, `pipelines`; the ground's `tile rebuild`, the terrain workers' `terrain field`, `terrain pairs`, `terrain rebuild` and the frame thread's waits for them; `tileset open`; the world's `world update`; the collision's `collision tile`.

**Testing.** `tests/startup_trace_tests.cpp`: the live progress following a plan's stages with monotone fractions (equal weights and a previous run's), a nested stage as the detail, items, every milestone's bit, the measured plan; a token from an earlier plan finishing nothing; reads never torn beside three writing threads; the pump called on its own thread's boundaries and slices only, not nested, not off; off by default and recording nothing while off; nesting and a wait's edge across threads; a forward edge refused and a hand-made cycle caught; a full buffer counting what it dropped; the summary's milestones monotone with one reordered and one never reached; the Chrome trace round-tripping a recorded set (every stage's and milestone's fields read back equal, through `core/json`, with the sampler thread's first sample waited for, a minute at most, since a fixed spin found none on a saturated machine); the three readers' text byte for byte what the copies of them from before T210 write (`tests/startup_summary_reference.h`), on a recorded session of 160 frames with a worker thread each, on a synthetic streamed session ready and never ready, and on one out of id order, for four `until`s; and their cost by count (`TraceWalkCost`) under the bound their passes give at 10^5 and 10^6 events (the Chrome trace at 10^5 only: at 10^6 it is a quarter of a gigabyte of text). `bench/startup_trace_bench.cpp` times the readers and the old summary on the same shapes.

**Build.** `cmake/EngineProfiling.cmake` fetches Tracy v0.14.1 (BSD-3, `third_party/LICENSES.md`) when `ENGINE_TRACY` is on; the `msvc-release` and `linux-gcc-release` presets turn it on, debug presets leave it off, so both modes compile in CI. The client is configured loopback-only (below). Tracy's headers are included as system headers so the engine's warning policy applies only to engine code.

**The client listens on loopback only.** A Tracy client opens a listening TCP socket when the process starts and announces itself by UDP broadcast, and Tracy's default is every interface. On Windows a listener on a non-loopback address makes the firewall raise a prompt once per executable *path*, and this tree makes paths cheaply: every preset and every agent worktree has its own copy of every test, bench, and app. `ENGINE_TRACY` therefore sets `TRACY_ONLY_LOCALHOST` and `TRACY_NO_BROADCAST`; a profiler on the same machine connects as before, and `-DENGINE_TRACY_REMOTE=ON` restores Tracy's default for profiling another machine (a baseline-tier box from the desktop), where one prompt for one binary is the expected price.

**The client installs no crash handler** (`TRACY_NO_CRASH_HANDLER`, since 2026-10-04). Tracy's own replaces the engine's fault handlers when its profiler object is constructed, after them: on Windows a top-level exception filter that reports to a connected profiler and otherwise lets the process die with nothing printed, on Linux `sigaction` handlers that end every fault — a SIGSEGV as much as an abort — in `abort()`. The engine prints one line for every fatal fault instead ([platform](platform.md#every-fatal-fault-prints-one-line)), and a release build, the one Tracy is in, is where that line matters most. A crash no longer appears in a connected profiler's timeline; the line on stderr names it.

Why this is written down at length: it cost most of a night. On 2026-09-18 every process on the development machine that created a Vulkan device crashed with an access violation inside the NVIDIA driver (`nvoglv64.dll` or `nvcuda64.dll` under `vkCreateDevice`, driver 610.88), twice, for hours, with binaries that had passed minutes earlier. It was not a wedged driver, not the locked screen, not memory pressure (device creation worked with 31 GB of 32 in use), and not an implicit Vulkan layer. Each pending firewall prompt is a `PickerHost.exe FirewallNotificationDialogServer` process holding a GPU context; thirty-five of them took the machine from 49 GPU client processes to 77, and somewhere between those two numbers the driver stops surviving `vkCreateDevice`. Dismissing the prompts fixed it on the spot. The diagnosis, for the next time device creation crashes machine-wide: `nvidia-smi --query-compute-apps=pid --format=csv,noheader` for the client count, `Get-CimInstance Win32_Process -Filter "Name='PickerHost.exe'"` for the prompts, and the Application event log (Id 1000, faulting module `nv*`) for when it began. The block rules Windows added for the old paths are harmless and the owner's to remove.

**Depends on.** `base`, `containers`, `json` (the summary is a `JsonValue`, which is why the module is declared after `json` in `core/CMakeLists.txt`); Tracy when enabled.

**Testing.** `tools/dev.ps1 test -Filter profiling` compiles every macro in whichever mode the preset selects, checks `enabled()` and `connected()`, and runs the startup trace's tests (above) and the frame capture's (`tests/frame_capture_tests.cpp`: off records nothing; on records zones by name and by `__func__`, marks, values on both tracks and a thread's name; a full buffer counts its drops and a restart clears it; zones on three threads with a stop that leaves nothing written after it returns).

**Performance notes.** Off: nothing for Tracy's macros, one relaxed atomic load per zone for the frame capture. On, not connected: an atomic load per zone. Connected: Tracy's own overhead, about 20 ns per zone. Memory allocation events are not wired into `core/memory` yet; that hook arrives with the mimalloc backend so both change once.
