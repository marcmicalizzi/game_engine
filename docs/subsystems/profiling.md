# profiling (core)

**Purpose.** The profiler hooks every module instruments itself with (docs/plan/09-testing-profiling.md §9.3, ADR-0012). With the CMake option `ENGINE_TRACY` the macros are Tracy client zones, frame marks, plots, messages, and allocation events; without it they expand to nothing, so instrumentation stays in the code at zero cost. Tracy runs in on-demand mode: until a profiler connects, a zone costs a predictable few nanoseconds.

**Placement.** The plan lists profiling under the foundation layer; the hooks live in core so that the job system, I/O, and every other core module can carry zones. The startup trace lives here too, for the same reason: a loader in any layer records its stages. The profiling *service* (capture export for the `profile` protocol tool, frame reports, budget checks) is the foundation-layer module that will build on this.

**Public API.** `core/profiling/profile.h`: `ENGINE_PROFILE_ZONE()`, `ENGINE_PROFILE_ZONE_NAMED(name)`, `ENGINE_PROFILE_ZONE_TEXT(text, size)`, `ENGINE_PROFILE_FRAME()`, `ENGINE_PROFILE_FRAME_NAMED(name)`, `ENGINE_PROFILE_THREAD(name)`, `ENGINE_PROFILE_PLOT(name, value)`, `ENGINE_PROFILE_MESSAGE(text, size)`, `ENGINE_PROFILE_ALLOC(ptr, size)`, `ENGINE_PROFILE_FREE(ptr)`; `profiling::enabled()`, `profiling::connected()`.

**Rules.** One `ENGINE_PROFILE_ZONE` per scope (it declares a local). A zone per system and per pass, not per element; per-job zones exist in the job system because a job is the unit of scheduling. Plots for the counts a frame budget tracks. Worker threads name themselves.

**Instrumented today.** Job workers (thread names, a zone per executed job), protocol dispatch, document store load and save, and the startup stages below (each is a Tracy zone of the same name in a Tracy build).

## The startup trace

`core/profiling/startup_trace.h` (roadmap W69): what a process did between its launch and the moment it was ready, recorded only while a host has turned it on (`engine-view --startup-trace`, `render.load` with `startup_trace`; [apps](apps.md#--startup-trace-from-launch-to-ready)). Flat memory over a load cannot tell a wait from CPU work, IO, a cache check or the driver; this can, because every stage carries what tells them apart.

- **A stage** (`ENGINE_STARTUP_STAGE(name)`, `ENGINE_STARTUP_STAGE_DETAIL(name, detail)`, `TraceStage`) is a named interval on the thread that ran it: wall time from the trace's origin, the thread's own CPU time over it (`GetThreadTimes`, `CLOCK_THREAD_CPUTIME_ID`), the bytes the process read through the OS while it ran (`GetProcessIoCounters`, `/proc/self/io` `rchar` — process-wide, so exact for a serial stage and an upper bound beside other threads' reads; mapped files arrive as page faults instead), the time it reported blocked (`trace_wait`, `TraceWait`), a count (`trace_items`), and a copied detail (96 bytes: a path, a reason). Stages nest per thread: a stage's parent is the one open on its thread when it began.
- **A dependency edge** (`trace_depends`, or a `TraceWait` scope naming the stage it waits for) points at a stage that **began earlier** — anything else is refused and counted — so the graph is acyclic by construction (`trace_acyclic` checks a set read from anywhere), and a summary never adds two overlapping stages as if one followed the other.
- **A milestone** (`trace_milestone`, `trace_milestone_at` for one dated after the fact) is an instant with the process's counters at it.
- **The sampler** (a thread, every 20 ms) records the process: CPU time, bytes and read calls, working set, private commit, page faults. The Chrome trace draws them as counter tracks (cores busy, read MiB/s, faults/s, memory), which is what shows a stretch of no memory growth to be CPU-bound, reading, or neither.
- **The origin** is the process's launch as the OS records it (`process_start_ns`: `GetProcessTimes`, `/proc/self/stat`), so the time before `main` — the loader, static initialization, an antivirus scan of a freshly built executable — is in the numbers and not lost.

**Off it costs one relaxed atomic load per stage and allocates nothing**; every entry point returns while `trace_enabled()` is false. On, the events go into a buffer `trace_start` allocates once (32,768 events by default; a full buffer drops and counts), so recording never allocates and a frame loop with the trace on allocates nothing (engine-view's `startup_trace_view_tests.cpp` checks the frame records). Names are string literals; the trace keeps the pointer.

**Output.** `chrome_trace_json` writes the JSON Object Format: complete events (`"ph":"X"`) with every field in `args` (`id`, `parent`, `depends`, `cpu_ns`, `wait_ns`, `read_bytes`, `items`, `detail`), global instants for milestones, counter tracks for the samples, and flow arrows for the edges — loadable in `chrome://tracing` and [Perfetto](https://ui.perfetto.dev). `startup_summary_json` is the block both hosts report: the milestones in the order given, **held monotone** (one reached before a milestone listed ahead of it is reported at that one's time, with `reached_ms` and a count in `milestones_reordered`); the top-level stages of the thread that recorded the first milestone, its serial critical path, each with its three longest children and every wait beneath it; `unstaged_ms`, the time before the last milestone no top-level stage covers; the other threads' busy time; and `before_ready`, the process from the samples — CPU, bytes read, page faults, the peak working set and commit, and the intervals spent on a CPU (half a core or more), reading (4 MiB/s or more), or neither.

### The trace is live

**The same stages feed a progress record while they run** (`ProgressPlan`, `LoadProgress`, `progress_*` in `startup_trace.h`; roadmap W79), which is what a loading screen draws, what a game's `game_loading` hook is handed ([hotload](hotload.md#the-module-abi), ABI 7) and what `render.progress` answers ([protocol](protocol.md)). It has its own switch (`progress_start` .. `progress_stop`), so a window that shows its load pays for no trace buffer and a trace can record with nothing shown; every `TraceStage` checks both, and off it is still one relaxed load each.

- **A plan** names the load's top-level stages, each with a weight, and its milestone ladder. The host builds it — engine-view from the previous run's measured stage times (`progress_measured`, stored at `<ddc>/startup/<scene hash>.json`; [apps](apps.md#the-loading-presentation)), or the same weight for every stage when there is none. Nothing about it is decided by a timestamp: the file is a previous run's numbers, read or not there.
- **A plan's stage** becomes the current stage when it begins and is done when it ends; **any other stage** that begins meanwhile, on any thread, becomes the current stage's `detail` (`cluster read: tree.clusters`), so the detail says what the load is doing without the plan having to know every stage. `trace_items` counts into `items` and every milestone sets its rung's bit, both whether the trace records or not.
- **The fraction** is the done stages' weight over the plan's, plus — only when the weights are a previous run's — the current stage's weight times its elapsed time over its previous duration, capped at 0.9 of it, so the bar moves inside a long stage and never claims it finished. It **never falls**: a read returns at least the largest fraction any read returned. `progress_finish` (the host's ready milestone) makes it 1.
- **Readable from any thread, allocating nothing.** A writer (a stage's begin or end; a few hundred a load) takes a spin flag and bumps a sequence on both sides of its change; `progress_read` copies the record between two equal, even reads of the sequence and retries otherwise, so a reader never sees a stage with another's detail half-written (the threaded test reads 20,000 times beside three writers).
- **The pump** (`progress_set_pump`, `progress_pump`): the thread that owns a window registers a callback, and every stage that begins or ends **on that thread** while progress is on calls it, as does `progress_pump()` from inside a long stage between its slices (the GPU scene's texture uploads, the ground's first fields). That is how a stage that has to run on the device's thread keeps the window's messages flowing without knowing there is a window. A stage the callback itself begins does not pump again.

**Instrumented stages** (zones only; none changes what it times): engine-view's own sequence (`device`, `scene file`, `animation clips`, `load scene`, `attach`, `ground prepare`, `gpu scene`, `renderer`, `ground start`, `world create`, `session`, one `frame` a frame); in the renderer the scene file's `json parse`, `schema read`, `scene expand`, `ground sampler`, `placements`, `water`, `meshes` (the load's wait for its per-mesh jobs; since W75 each `mesh` stage is on the job system's thread that ran it) and per mesh `mesh` with `source hash`, `cluster read`, `generator inputs`, `generate`, `mesh build`, `cache entry ignored` (an **accidental rebuild**: an entry under the key that the build would not use, its reason as the detail), then the load's one `cache textures` with `texture identities` (items: the distinct files), `texture probe` (items: the distinct keys), `texture build` (items: the textures built) and `textures trusted` (an instant whose detail is `trusted=… built=… hashed=… from_index=…`; until W75 `cache textures` was one stage per mesh), the instance table's `instances`; the GPU scene's `upload geometry`, `upload materials`, `working set`, `flora motion`, `terrain levels`, `ray tracing`; the renderer's `shader manifest`, `sky`, `pipelines`; the ground's `tile rebuild`, the terrain workers' `terrain field`, `terrain pairs`, `terrain rebuild` and the frame thread's waits for them; `tileset open`; the world's `world update`; the collision's `collision tile`.

**Testing.** `tests/startup_trace_tests.cpp`: the live progress following a plan's stages with monotone fractions (equal weights and a previous run's), a nested stage as the detail, items, every milestone's bit, the measured plan; a token from an earlier plan finishing nothing; reads never torn beside three writing threads; the pump called on its own thread's boundaries and slices only, not nested, not off; off by default and recording nothing while off; nesting and a wait's edge across threads; a forward edge refused and a hand-made cycle caught; a full buffer counting what it dropped; the summary's milestones monotone with one reordered and one never reached; the Chrome trace round-tripping a recorded set (every stage's and milestone's fields read back equal, through `core/json`).

**Build.** `cmake/EngineProfiling.cmake` fetches Tracy v0.14.1 (BSD-3, `third_party/LICENSES.md`) when `ENGINE_TRACY` is on; the `msvc-release` and `linux-gcc-release` presets turn it on, debug presets leave it off, so both modes compile in CI. The client is configured loopback-only (below). Tracy's headers are included as system headers so the engine's warning policy applies only to engine code.

**The client listens on loopback only.** A Tracy client opens a listening TCP socket when the process starts and announces itself by UDP broadcast, and Tracy's default is every interface. On Windows a listener on a non-loopback address makes the firewall raise a prompt once per executable *path*, and this tree makes paths cheaply: every preset and every agent worktree has its own copy of every test, bench, and app. `ENGINE_TRACY` therefore sets `TRACY_ONLY_LOCALHOST` and `TRACY_NO_BROADCAST`; a profiler on the same machine connects as before, and `-DENGINE_TRACY_REMOTE=ON` restores Tracy's default for profiling another machine (a baseline-tier box from the desktop), where one prompt for one binary is the expected price.

**The client installs no crash handler** (`TRACY_NO_CRASH_HANDLER`, since 2026-10-04). Tracy's own replaces the engine's fault handlers when its profiler object is constructed, after them: on Windows a top-level exception filter that reports to a connected profiler and otherwise lets the process die with nothing printed, on Linux `sigaction` handlers that end every fault — a SIGSEGV as much as an abort — in `abort()`. The engine prints one line for every fatal fault instead ([platform](platform.md#every-fatal-fault-prints-one-line)), and a release build, the one Tracy is in, is where that line matters most. A crash no longer appears in a connected profiler's timeline; the line on stderr names it.

Why this is written down at length: it cost most of a night. On 2026-09-18 every process on the development machine that created a Vulkan device crashed with an access violation inside the NVIDIA driver (`nvoglv64.dll` or `nvcuda64.dll` under `vkCreateDevice`, driver 610.88), twice, for hours, with binaries that had passed minutes earlier. It was not a wedged driver, not the locked screen, not memory pressure (device creation worked with 31 GB of 32 in use), and not an implicit Vulkan layer. Each pending firewall prompt is a `PickerHost.exe FirewallNotificationDialogServer` process holding a GPU context; thirty-five of them took the machine from 49 GPU client processes to 77, and somewhere between those two numbers the driver stops surviving `vkCreateDevice`. Dismissing the prompts fixed it on the spot. The diagnosis, for the next time device creation crashes machine-wide: `nvidia-smi --query-compute-apps=pid --format=csv,noheader` for the client count, `Get-CimInstance Win32_Process -Filter "Name='PickerHost.exe'"` for the prompts, and the Application event log (Id 1000, faulting module `nv*`) for when it began. The block rules Windows added for the old paths are harmless and the owner's to remove.

**Depends on.** `base`, `containers`, `json` (the summary is a `JsonValue`, which is why the module is declared after `json` in `core/CMakeLists.txt`); Tracy when enabled.

**Testing.** `tools/dev.ps1 test -Filter profiling` compiles every macro in whichever mode the preset selects, checks `enabled()` and `connected()`, and runs the startup trace's tests (above).

**Performance notes.** Off: nothing. On, not connected: an atomic load per zone. Connected: Tracy's own overhead, about 20 ns per zone. Memory allocation events are not wired into `core/memory` yet; that hook arrives with the mimalloc backend so both change once.
