# io (foundation)

**Purpose.** File access for the engine and its tools (docs/plan/02-architecture.md §2.3): status-returning native file operations in UTF-8, a mount table so engine code addresses files as `content://levels/a.json` or `cache://ddc/...` without knowing where a project keeps them, asynchronous reads on the job system's Efficiency pool, and files held open and read **by byte range**. The content-addressed derived-data store (domain/ddc) and streaming build on this.

**Owned data.** The `Vfs` mount table. Nothing else; files belong to the OS.

**Invariants (tested).**
- Every operation returns a `Status`; nothing throws. `std::filesystem` is used through its `error_code` overloads only.
- `write_file_atomic` writes a sibling temporary and renames over the target, so a reader sees the old or the new file, never a mix, and no temporary is left behind on failure.
- `overwrite_file` is **not** atomic: it writes over the file in place and leaves nothing beside it; a caller that needs all or nothing across its writes makes it so itself ([Writing a file](#writing-a-file)).
- `make_directories` is `Ok` for a directory that is already there and makes every missing level otherwise; a file in the way is refused and left alone.
- `Vfs::resolve` never yields a path outside the mount root: absolute paths, `..` that escapes, and drive prefixes are `InvalidPath`; unknown schemes are `UnknownMount`; writes through read-only mounts are `ReadOnly`. Paths without `scheme://` pass through as native paths, normalized.
- `normalize_path` uses forward slashes on every platform and is a pure string operation.
- `list_directory` returns entries sorted by name, so tools and agents see stable order.

## Writing a file

**On the Windows development machine the file system charges by the operation and its kind, not by the byte** — measured one operation at a time by `doc.fs.*` in `domain/doc/bench`, because the document store is where it showed (E12's edits cost 87–158 ms; [doc](doc.md#writing-a-file) has the whole table). Two consequences live here.

**`make_directories` asks first.** `Vfs::write` and `Vfs::append` call it for the parent of every file they write, and MSVC's `std::filesystem::create_directories` walks the path from its root and creates every prefix in turn, each failing because it is there: 4.3 ms a call on a directory that exists. So it asks `is_directory` first — one stat — and only a path that is not a directory goes to `create_directories`, exactly as before, so what it makes and what it refuses are unchanged. `msvc-release`, the two builds back to back (other processes 6–15% of the CPU, the GPU lock free):

| | before | after |
|---|---|---|
| `make_directories` on a directory that exists (`doc.fs.make_directories`) | 4.24 ms | 0.074 ms |
| on a missing leaf under one that exists (`make_directories_new`) | 4.35 ms | 4.38 ms |
| `Vfs::append` of 256 bytes (`vfs_append`) | 4.32 ms | 0.64 ms |
| `Vfs::write` of 256 bytes, an atomic replace (`vfs_write`) | 6.56 ms | 3.31 ms |

A missing directory still costs what `create_directories` costs, 4.4 ms for one new level, because it still creates every prefix; walking up to the deepest level that exists and creating downward would fix that too, and was left alone because a directory is made once and the semantics of the missing case are `create_directories`'s. In the Linux container the call was 1.4 µs before and after.

**`overwrite_file` is the cheap write.** Opened for writing alone (`_wsopen_s` with `_O_WRONLY | _O_CREAT`, `_SH_DENYNO` so a scanner holding the file does not make it fail; `open` with `O_WRONLY | O_CREAT` elsewhere), not truncated, written from the start and cut to the new length (`_chsize_s`, `ftruncate`), it costs 0.50 ms from 64 B to 64 KiB and 0.61 ms at 1 MiB, where `write_file_atomic`'s new file and rename cost 2.9–3.4 ms, stdio's truncating `"wb"` 5.8 ms at 64 KiB, and stdio's `"r+b"` (which opens to read as well) 9.6 ms. Changing a file's length in place is the one expensive thing left — 4.8 ms from 16 KiB, 0.7 ms at 4 KiB — so a caller that knows the file's current length passes it, and a file of 8 KiB or more whose length changes is removed and made again, 1.2 ms. The file's missing directories are made when the write finds them missing rather than asked for first, and a write that finds the file held by something else is retried briefly, as `write_file_atomic`'s rename is. It is not atomic: `domain/doc`'s store makes a save all or nothing with a log written before any file ([doc](doc.md#a-save-is-all-or-nothing)), which is what it is for. It was the store's own until it proved to be a fact about the file system rather than about documents; moving it here changed no byte a save writes (the store's byte-identity and crash tests are unchanged and pass).

## Ranged reads: a file open, addressed by offset

`read_file` answers "give me this file". Streaming asks a different question — "give me these four ranges of this ten-megabyte container, and tell me when they have landed" — and answering it with `read_file` means holding the whole container in host memory, which is exactly the cost geometry streaming exists to remove ([renderer](renderer.md#geometry-streaming-the-gpu-half-of-pages-and-residency)). `FileHandle` is that second question: open once, read by `(offset, length)`, close when the scene goes.

**Every read names its own offset, and that is the whole design.** `read_at` is `const` and safe to call concurrently on one handle from any number of threads, because no read depends on where another left a file position. On POSIX that is `pread`, which has the contract by definition. On Windows the handle is opened `FILE_FLAG_OVERLAPPED` and each read carries its offset in an `OVERLAPPED` **with its own event**, and both halves of that matter: a *synchronous* handle serializes concurrent reads on the file object even when each names an offset (and updates the shared position while it is at it), and an overlapped read with a null event signals completion on the file handle itself, which two reads in flight would then share. One event per call costs a couple of microseconds against a read of tens of kilobytes; the test that would catch getting it wrong is the 128-scattered-range case, which reads a pattern whose every byte is a function of its offset, so a range that lands in the wrong place fails on its contents and not only on its length.

**Past the end is a short read, not a failure.** `read_at` clamps against the size the file had when it was opened and reports what arrived in `read_out`; a caller that wanted the whole range compares the two (`AsyncRangeRead::complete()`), and one reading "the rest of the file" does not have to stat it first. A zero-length read is `Ok` and touches neither the destination nor the disk, so a caller with an empty section — an unskinned mesh's binding stream, say — needs no special case. Only a real I/O error is an error. The handle is opened `FILE_SHARE_DELETE` as well as read/write, so holding a container open never stops a build replacing it: `write_cluster_file` renames over the target and a reader keeps reading the bytes it opened.

`read_ranges_async` puts a group of reads on the Efficiency pool against **one** counter, because the caller of a group wants to know when all of it has landed and polling one word is cheaper than polling N. It schedules one job at a time rather than building a span of them, so it allocates nothing and may be called every frame.

## Queued reads: a deep queue from one thread (roadmap W54)

`read_ranges_async` puts each range on an Efficiency worker, and each worker issues its read and **blocks in it**, so the device never sees more reads at once than there are Efficiency workers. That is the wrong shape for a caller with hundreds of small ranges of one file — a tile set's window, a level read whole ([tileset](tileset.md#reading-a-level)) — where the time is the device's latency and what pays for it is the queue's depth. `read_queued(requests, depth, on_completed, context, stats)` is that shape: **up to `depth` reads in flight at once, issued from the calling thread**, and it returns when every one has landed (true when all are `complete()`).

- **On Windows** each read is an overlapped `ReadFile` on the handle `FileHandle` already opens `FILE_FLAG_OVERLAPPED`, with **an event of its own** from a pool kept per thread (made on first use, as deep as the deepest queue the thread asked, closed when the thread ends), so `depth` reads are queued at the device together and two reads in flight never share the handle's signal. It is a completion *path*, not a completion *port*: a port is bound to a handle for the handle's life, and two threads queueing reads of one handle through one port would take each other's completions, where an event per read keeps every batch its caller's own; at the rates measured (52,000 reads a second at depth 128, [tile archives](../experiments/tile-archives-2026-10-24.md)) the event is not where the time goes, so nothing says a port would buy more.
- **On POSIX** the reads are `pread` in order, one at a time — today's behaviour behind the same request shape. io_uring is W54's remainder: the Linux containers run under Docker's default seccomp profile, which refuses `io_uring_setup`, (since Docker 25), so the path could not be tested where this tree's Linux tests run, and nothing here measured a Linux disk.
- **Requests complete in order**: `on_completed(context, i)` runs on the calling thread after request i has landed and **before request `i + depth` is issued**, so a caller can read every request into a ring of `depth` buffers and copy each out as it lands — which is how the tile set's archive reader reads runs of adjacent records through a bounded staging ring. A request with no handle, or misaligned on an unbuffered handle, fails alone (`InvalidArgument`); a read past the end is short, as `read_at`'s is. `depth` is clamped to 1 … `k_max_queue_depth` (256). Allocates nothing once the thread's events are as deep as asked.

**Unbuffered handles.** `FileHandle::open(path, ReadMode::unbuffered)` opens with `FILE_FLAG_NO_BUFFERING` on Windows and `O_DIRECT` on Linux: reads bypass the OS's file cache, and every offset, length and destination must be a multiple of `k_unbuffered_alignment` (4 KiB, which covers 512-byte-emulating and 4K-native drives) or the read is refused, not read wrong. A read running past the end comes back short to the byte, as a buffered one does. It is how a measurement reads a file cold without the administrator's right to drop the cache, and whether it belongs in production for large sequential reads is the measurement's question. A file system that cannot read unbuffered refuses at open (`InvalidArgument`).

**Public API.** `foundation/io/vfs.h`: `Status`, `status_name`, `FileInfo`, `DirEntry`; path helpers `normalize_path`, `join_path`, `parent_path`, `file_name`, `extension`, `is_absolute_path`; native operations `read_file`, `write_file`, `write_file_atomic`, `append_file`, `overwrite_file` (with `k_unknown_file_size`), `stat_file`, `exists`, `list_directory`, `make_directories`, `remove_file`, `remove_directory_recursive`, `rename_path`; `Mount`, `Vfs` (`mount`, `unmount`, `resolve`, `read`, `write`, `append`, `stat`, `exists`, `list`, `make_directories`, `remove`); `AsyncRead`, `read_async`, `wait_all`; `FileHandle` (`open` with a `ReadMode`, `close`, `valid`, `unbuffered`, `size`, `path`, `read_at`; `native` on Windows), `ReadMode`, `k_unbuffered_alignment`, `AsyncRangeRead` (with `complete()`), `read_range_async`, `read_ranges_async`, `read_queued` (with `ReadCompleted`, `QueuedReadStats`, `k_max_queue_depth`), `read_file_range`.

**Depends on.** `base`, `containers`, `jobs`, `time`.

**Testing.** `tools/dev.ps1 test -Filter io`. Works in a temporary directory: path normalization, the native operation set including atomic replacement and cleanup, `make_directories` on a directory that is there, a missing nested one, and a file in the way at the leaf and on the way (refused, the file untouched), `overwrite_file` making a file and its directories, cutting, growing and emptying it, remaking it when told its old length in both directions and when told a wrong one, refusing a directory, and leaving nothing beside it; mount resolution and escape refusal, and asynchronous reads with a two-worker job system. For ranges: a range out of the middle of a 100 KB pattern with the byte past it untouched, the first and the last byte, a read that runs off the end coming back short, an offset at and past the end coming back empty, a zero-length read, a moved handle that still reads while its source is closed, a closed handle refusing, the one-shot `read_file_range` and its `NotFound`; and 128 scattered 3 KB ranges of one megabyte file through one handle, one counter and two Efficiency workers, each checked byte for byte against the offset that produced it. Queued reads: the same 128 ranges at depths 1, 8, 32, 128 and 1000 (clamped), every one byte for byte and completed in order, a request with no file failing alone, a read past the end short and a zero-length one complete; 64 requests through a ring of four buffers copied out in their completions, the whole file in order; and an unbuffered handle reading aligned ranges (one running past the end, short to the byte) while a misaligned offset, length or destination is refused.

**Performance notes.** Whole-file reads go through a 64 KB stdio buffer with the whole size reserved up front. Asynchronous whole-file reads are synchronous reads on Efficiency workers. Ranged reads are unbuffered and one system call each, which is what a caller reading 128 KB at a time wants and what a caller reading four bytes at a time must not do — the container reader therefore reads its header and section table once, at open, and addresses everything after that in page-sized runs. io_uring and DirectStorage-style GPU decompression slot in behind the same `AsyncRangeRead` request when streaming bandwidth asks for them.

**Queued against the pool** (2026-10-24, W54, [tile archives](../experiments/tile-archives-2026-10-24.md), `msvc-release`, a striped volume of three 990 Pros, others' CPU 14–30%): the 7,345 18 KB records of a cold 132 MB file read each its own range, into one buffer — the Efficiency pool with 4 workers 0.262 s and with 16 0.205 s; `read_queued` from one thread at depth 4 0.261 s, 32 0.205 s and **128 0.140 s** (941 MB/s, about 52,000 reads a second). At one depth the two are the same; the queue reaches the depth without the threads. Warm, the pool's sixteen cores copy out of the cache faster (0.031 s) than the queue's one (0.076 s), which is why a caller with adjacent ranges coalesces them. Unbuffered, the tile set's level read whole in 256 KiB runs is 0.12 s against 0.14 s from a cold copy through the cache: 12%, and an unbuffered read leaves nothing in the cache for the next launch, so nothing in production reads unbuffered.
