# io (foundation)

**Purpose.** File access for the engine and its tools (docs/plan/02-architecture.md §2.3): status-returning native file operations in UTF-8, a mount table so engine code addresses files as `content://levels/a.json` or `cache://ddc/...` without knowing where a project keeps them, asynchronous reads on the job system's Efficiency pool, and files held open and read **by byte range**. The content-addressed derived-data store (domain/ddc) and streaming build on this.

**Owned data.** The `Vfs` mount table. Nothing else; files belong to the OS.

**Invariants (tested).**
- Every operation returns a `Status`; nothing throws. `std::filesystem` is used through its `error_code` overloads only.
- `write_file_atomic` writes a sibling temporary and renames over the target, so a reader sees the old or the new file, never a mix, and no temporary is left behind on failure.
- `overwrite_file` is **not** atomic: it writes over the file in place and leaves nothing beside it; a caller that needs all or nothing across its writes makes it so itself ([Writing a file](#writing-a-file)).
- `make_directories` is `Ok` for a directory that is already there and makes every missing level otherwise; a file in the way is refused and left alone.
- `Vfs::resolve` never yields a path outside the mount root: absolute paths, `..` that escapes, and drive prefixes are `InvalidPath`; unknown schemes are `UnknownMount`; writes through read-only mounts are `ReadOnly`. Paths without `scheme://` pass through as native paths, normalized.
- `normalize_path` uses forward slashes on every platform and is a pure string operation. A UNC path's `//server/share` is its root and is kept whole, and `..` never climbs above it; `join_path` keeps it too. Until 2026-11-18 both folded the two leading slashes into one, so `//server/share/x` became `/server/share/x`, a directory on whichever drive is current, for every caller (the scene and save readers, the mounts, the document store's session directory) — nothing relied on the fold, and a share named on a command line was opened in the wrong place.
- `list_directory` returns entries sorted by name, so tools and agents see stable order.
- `Roots::admit` admits nothing when no root is set, and answers a canonical path that lies under a root ([Roots](#roots)).

## Roots

`io::Roots` (`include/foundation/io/roots.h`, roadmap T174, [ADR-0071](../adr/0071-a-host-reads-and-writes-only-under-its-roots.md)) is the one check a protocol host runs on every path a client names before it reads, writes or makes a directory there. Each root is a **name** and a directory, read or read and write, which the operator named at start. A path crosses the protocol, and is stored, as the root's name and a path under it, `out://captures/a.png`. It is never stored as an absolute path, because an absolute path of the operator's machine should not end up in a committed document, and it may name a worktree that is gone by the time anyone reads it (the owner, 2026-11-18). `admit` also takes a path relative to the caller's base, or an absolute one, and checks all three alike. It answers an `Admitted`: `native`, the canonical path the caller opens (never sent, never stored), and `root` and `relative`, which `portable()` joins into the form a client is told. `<name>://` that names a root this host does not have, or one whose directory has gone, is `Refusal::unknown_root` and is never resolved some other way.

The rules, in order, the same on Windows and Linux wherever the systems allow it:

- **Lexical** (`check_path_text`): valid UTF-8, no control byte, not past the system's length; none of `< > " | ? *`; a `:` only as a drive's (`C:/`), so `a.png:x`, `a::$DATA`, `dir::$INDEX_ALLOCATION` and `C:x` are refused; no `\\.\` (and `\\?\`, `\??\` fall to the reserved `?`); on Windows no `/x` that means the current drive's root; no device name in any component, whatever its case, suffix or trailing dots and spaces (`CON`, `nul.txt`, `COM1`, `COM¹`, `CONIN$`, `CLOCK$`...); no component but `.` and `..` that ends in a dot or a space, because Win32 strips them and `.. ` would be `..` in one order of its steps and a name in another. `\` is a separator on both systems.
- **No network share.** `add` refuses a root on one (`InvalidPath`, `Refusal::unc`): a UNC spelling, a drive the system calls remote (`GetDriveTypeW`, which answers from the drive table without opening the share), or a directory whose canonical form is UNC; the spelling is checked before anything is made or opened. So no root is UNC, and `admit` refuses a UNC path and one on a remote drive after joining it to the base and before step 8 opens anything: with a root on a share, a client's `//server/share` would have to be resolved to be compared, and resolving it makes the host connect to the server the client named with the operator's credentials, once per prefix, each attempt able to hold the dispatch for the redirector's time-out. On Linux a share is a mount the operator made and no spelling reaches another, so only the UNC spelling is refused there.
- **Canonical**: joined to the base, `..` collapsed lexically (and refused above the volume's root), then the longest prefix that exists made canonical by the system: `CreateFileW` with backup semantics and `GetFinalPathNameByHandleW` on Windows, which follow links, junctions and mount points and give long names for 8.3 ones and the case on disk; `realpath` on Linux. A prefix with no DOS name is refused. The rest is appended as written, and its first component must not exist unfollowed: a dangling link is refused, because a write through it would make its target wherever it points.
- **Under a root**, by whole components (`work` does not hold `workshop`), case-insensitively on Windows and by bytes on Linux. The most specific root that holds the path answers, and a write or a directory needs it to be writable: so `out/` under a read-only document is the writable `out` root, and a read-only root the operator named inside a writable one stays read-only (until 2026-11-18 the most specific root that *allowed* the access answered, so `--root work=<w>:rw --root refs=<w>/refs` wrote `refs://x` under `work`). A `<name>://` path must also stay under the root it names: `out://../layers` is refused.
- **For a write or a directory**: never inside a directory the host serves to a browser (`serve`), and never inside an open document's directory but under its `out/` (`protect` when a session is made, `release` when it closes, by any path: protocol's `SessionManager` does both, [protocol](protocol.md#the-hosts-file-roots)). A directory is held once, compared canonically, with a count of its holders, so a second spelling of it is the same entry, opening a document again and again does not grow the list every write's admission walks, and the directory is free when its last holder lets go (`roots_tests`, "a document protected again and again is held once"). `may_make_document` answers whether a client may make a new document at an admitted directory: not one that is or holds a root's own directory, a served directory or an open document's, nor an open document's `out/`, since the new document's protection would close that place to every client write (`roots_tests`, "a document is not made where the host keeps a root, a served or an open one"). A writable root that holds or lies under a served directory is refused at `add`, and the other way round at `serve`. An existing last component must be a regular file for a write (a directory for `make_directory`) and never a link or junction. A hard link is admitted, because it *is* a file of the root. The caller writes by rename (`write_file_atomic`), which replaces the link rather than writing through it.

A root that is itself a link is resolved once, at `add`, and `Root::linked` says so; retargeting the link later moves nothing. That is the rule for a directory the operator spelled. **A root the host derives is held to its parent instead**: `add_inside(name, parent, child)` adds the writable, made-on-write root at `<parent>/<child>` only when nothing is there or a plain directory is — not a link, live or dangling, not a junction or another reparse point, not a file — and its canonical form is that path itself, else answers `NotDirectory` and adds nothing. It is how a host adds a document's `out/`: the operator named the document, and where a link its author put at `out` leads is not the operator's choice.

**A path a document's record stores** goes through `admit_stored_path`: the stored form first (`check_stored_path_form`: the lexical rules, then `<root>://<relative>` or relative, never absolute — `Refusal::absolute_stored`, whether or not a root holds it, because a committed document carrying the machine's own path names nothing on another machine — and never `<root>://` with nothing after it, which is the root's directory and not a file, `Refusal::empty`), then `admit` for reading from the document's directory. It does not ask whether the file is there. The protocol calls it as a record lands and `doc_scene` as it reads one ([protocol](protocol.md#paths-a-documents-records-hold)).

**A URI one file names another by** (a glTF's buffers and images) goes through `uri_relative_path` first and then through `admit_stored_path` from the naming file's directory, so it gets every rule a stored path gets after its own: decoded once (`%255C` is a percent sign in a name), and refused when the decoded text holds a backslash — a URI has none, and none is turned into a separator, since every path function here takes `\` for one and `\\host` for a share — a control byte, a colon in its first segment (a scheme or a drive), a leading `/` or a `..` segment ("uri_relative_path takes a relative URI and refuses every way out of its directory"). The subject digest admits a glTF's names with the host's lock let go, so it admits them against `Roots::read_copy`, the roots alone copied under the lock: everything `admit` reads for `Access::read`, while a session opening adds a document's `out/` to the live set ([protocol](protocol.md#what-a-close-is-tied-to)).

**Between the admission and the open** a component of the admitted path can be replaced by a link, which a plain open follows. A reader that opens long after it admitted (the subject digest, whose reads come with the host let go) opens through `FileHandle::open_regular_unmoved`: `open_regular`, then what the system says the opened handle is — `GetFinalPathNameByHandleW` on Windows, the link under `/proc/self/fd` on Linux — held to the admitted path as `path_is_under` compares, both ways; a handle that leads anywhere else is closed and `InvalidPath` answered before a byte is read ("open_regular_unmoved refuses a file the admitted path no longer leads to"). A link swapped in after the open is the open's own file, as for any reader.

**A limit on Linux: a case-blind file system under a root.** On Linux `realpath` follows links but keeps the case it was given, and `path_is_under` compares bytes, so where a root lies on a file system that ignores case (WSL's `/mnt/<drive>`, a casefolded ext4 directory, an exFAT or NTFS mount) a write spelled `<root>/WORLD/layers/base.json` is not under the protected `<root>/world` and reaches the open document's own files, and a served directory likewise. Reads fail closed. Until the comparison asks the file system what a directory is (its device and inode, walked up the existing prefix) rather than how it is spelled, **an operator on Linux names no writable root on a case-blind file system that holds an open document or the shell's directory** (roadmap T188, which also covers a Windows directory made case-sensitive per directory, the converse). Windows is not affected: its comparison ignores case, and its canonical form is the on-disk spelling.

**What is left to the operator**: between the check and the open the tree can change. No protocol method makes a link, so only a process with the operator's own rights can race it, and such a process could write the file itself.

**Tests**: `tests/roots_tests.cpp`, a case for each way round the check, each a path that lands under the root (or reaches out of it) if the rule it names is taken out: spellings outside, `..`, a root's name as a prefix, the lexical classes, devices, trailing dots and spaces, a read-only root, the protected document and its `out/`, a served directory, a link and a junction that lead out, a file link, a dangling link, a write onto a link, a hard link, a root that is a link and is retargeted, a derived `out` that is a file, a link or a dangling link, a root on a network share (spelled with a server under `.invalid`, so even a regression that probed it would reach nobody), and on Windows case, backslashes and an 8.3 name. A case that needs a link the process may not make says so and skips that half. A mapped network drive has no case: a test cannot make one without a share of its own. 23 cases, about 0.5 s in `msvc-debug`.

## Writing a file

**On the Windows development machine the file system charges by the operation and its kind, not by the byte** — measured one operation at a time by `doc.fs.*` in `domain/doc/bench`, because the document store is where it showed (E12's edits cost 87–158 ms; [doc](doc.md#writing-a-file) has the whole table). Two consequences live here.

**`make_directories` asks first.** `Vfs::write` and `Vfs::append` call it for the parent of every file they write, and MSVC's `std::filesystem::create_directories` walks the path from its root and creates every prefix in turn, each failing because it is there: 4.3 ms a call on a directory that exists. So it asks `is_directory` first — one stat — and only a path that is not a directory goes to `create_directories`, exactly as before, so what it makes and what it refuses are unchanged. `msvc-release`, the two builds back to back (other processes 6–15% of the CPU, the GPU lock free):

| | before | after |
|---|---|---|
| `make_directories` on a directory that exists (`doc.fs.make_directories`) | 4.24 ms | 0.074 ms |
| on a missing leaf under one that exists (`make_directories_new`) | 4.35 ms | 4.38 ms |
| `Vfs::append` of 256 bytes (`vfs_append`) | 4.32 ms | 0.64 ms |
| `Vfs::write` of 256 bytes, an atomic replace (`vfs_write`) | 6.56 ms | 3.31 ms |

A missing directory still costs what `create_directories` costs, 4.4 ms for one new level, because it still creates every prefix; walking up to the deepest level that exists and creating downward would fix that too, and was left alone because a directory is made once and the semantics of the missing case are `create_directories`'s. In the Linux container the call was 1.4 µs before and after.

**`overwrite_file` is the cheap write.** Opened for writing alone (`_wsopen_s` with `_O_WRONLY | _O_CREAT`, `_SH_DENYNO` so a scanner holding the file does not make it fail; `open` with `O_WRONLY | O_CREAT` elsewhere), not truncated, written from the start and cut to the new length (`_chsize_s`, `ftruncate`), it costs 0.50 ms from 64 B to 64 KiB and 0.61 ms at 1 MiB, where `write_file_atomic`'s new file and rename cost 2.9–3.4 ms, stdio's truncating `"wb"` 5.8 ms at 64 KiB, and stdio's `"r+b"` (which opens to read as well) 9.6 ms. Changing a file's length in place is the one expensive thing left — 4.8 ms from 16 KiB, 0.7 ms at 4 KiB — so a caller that knows the file's current length passes it, and a file of 8 KiB or more whose length changes is removed and made again, 1.2 ms. The file's missing directories are made when the write finds them missing rather than asked for first, and a write that finds the file held by something else is retried briefly, as `write_file_atomic`'s rename is. It is not atomic: `domain/doc`'s store makes a save all or nothing with a log written before any file ([doc](doc.md#a-save-is-all-or-nothing)), which is what it is for. It was the store's own until it proved to be a fact about the file system rather than about documents; moving it here changed no byte a save writes (the store's byte-identity and crash tests are unchanged and pass).

## Ranged reads: a file open, addressed by offset

`read_file` answers "give me this file". Streaming asks a different question — "give me these four ranges of this ten-megabyte container, and tell me when they have landed" — and answering it with `read_file` means holding the whole container in host memory, which is exactly the cost geometry streaming exists to remove ([renderer](renderer.md#geometry-streaming-the-gpu-half-of-pages-and-residency)). `FileHandle` is that second question: open once, read by `(offset, length)`, close when the scene goes.

**Every read names its own offset, and that is the whole design.** `read_at` is `const` and safe to call concurrently on one handle from any number of threads, because no read depends on where another left a file position. On POSIX that is `pread`, which has the contract by definition. On Windows the handle is opened `FILE_FLAG_OVERLAPPED` and each read carries its offset in an `OVERLAPPED` **with its own event**, and both halves of that matter: a *synchronous* handle serializes concurrent reads on the file object even when each names an offset (and updates the shared position while it is at it), and an overlapped read with a null event signals completion on the file handle itself, which two reads in flight would then share. One event per call costs a couple of microseconds against a read of tens of kilobytes; the test that would catch getting it wrong is the 128-scattered-range case, which reads a pattern whose every byte is a function of its offset, so a range that lands in the wrong place fails on its contents and not only on its length.

**Past the end is a short read, not a failure.** `read_at` clamps against the size the file had when it was opened and reports what arrived in `read_out`; a caller that wanted the whole range compares the two (`AsyncRangeRead::complete()`), and one reading "the rest of the file" does not have to stat it first. A zero-length read is `Ok` and touches neither the destination nor the disk, so a caller with an empty section — an unskinned mesh's binding stream, say — needs no special case. Only a real I/O error is an error. The handle is opened `FILE_SHARE_DELETE` as well as read/write, so holding a container open never stops a build replacing it: `write_cluster_file` renames over the target and a reader keeps reading the bytes it opened.

`read_ranges_async` puts a group of reads on the Efficiency pool against **one** counter, because the caller of a group wants to know when all of it has landed and polling one word is cheaper than polling N. It schedules one job at a time rather than building a span of them, so it allocates nothing and may be called every frame.

## Queued reads: a deep queue from one thread (roadmap W54)

`read_ranges_async` puts each range on an Efficiency worker, and each worker issues its read and **blocks in it**, so the device never sees more reads at once than there are Efficiency workers. That is the wrong shape for a caller with hundreds of small ranges of one file — a tile set's window, a level read whole ([tileset](tileset.md#reading-a-level)) — where the time is the device's latency and what pays for it is the queue's depth. `read_queued(requests, depth, on_completed, context, stats)` is that shape: **up to `depth` reads in flight at once, issued from the calling thread**, and it returns when every one has landed (true when all are `complete()`).

- **On Windows** each read is an overlapped `ReadFile` on the handle `FileHandle` already opens `FILE_FLAG_OVERLAPPED`, with **an event of its own** from a pool kept per thread (made on first use, as deep as the deepest queue the thread asked, closed when the thread ends), so `depth` reads are queued at the device together and two reads in flight never share the handle's signal. It is a completion *path*, not a completion *port*: a port is bound to a handle for the handle's life, and two threads queueing reads of one handle through one port would take each other's completions, where an event per read keeps every batch its caller's own; at the rates measured (52,000 reads a second at depth 128, [tile archives](../experiments/tile-archives-2026-10-24.md)) the event is not where the time goes, so nothing says a port would buy more.
- **On POSIX** the reads are `pread` in order, one at a time — today's behaviour behind the same request shape. io_uring is W54's remainder: the Linux containers run under Docker's default seccomp profile, which refuses `io_uring_setup`, (since Docker 25), so the path could not be tested where this tree's Linux tests run, and nothing here measured a Linux disk.
- **Requests complete in order**: `on_completed(context, i)` runs on the calling thread after request i has landed and **before request `i + depth` is issued**, so a caller can read every request into a ring of `depth` buffers and copy each out as it lands — which is how the tile set's archive reader reads runs of adjacent records through a bounded staging ring. A request with no handle, or misaligned on an unbuffered handle, fails alone (`InvalidArgument`); a read past the end is short, as `read_at`'s is. `depth` is clamped to 1 … `k_max_queue_depth` (256). Allocates nothing once the thread's events are as deep as asked.

**Unbuffered handles.** `FileHandle::open(path, ReadMode::unbuffered)` opens with `FILE_FLAG_NO_BUFFERING` on Windows and `O_DIRECT` on Linux: reads bypass the OS's file cache, and every offset, length and destination must be a multiple of `k_unbuffered_alignment` (4 KiB, which covers 512-byte-emulating and 4K-native drives) or the read is refused, not read wrong. A read running past the end comes back short to the byte, as a buffered one does. It is how a measurement reads a file cold without the administrator's right to drop the cache, and whether it belongs in production for large sequential reads is the measurement's question. A file system that cannot read unbuffered refuses at open (`InvalidArgument`).

**Regular files only.** `FileHandle::open_regular(path)` opens for reading only a regular file and never in a way that can wait: a directory is `IsDirectory`, and a FIFO, a socket, a character or block device or a pipe is `NotRegular` (`Status`'s last value), closed again before a byte is read. On Linux the open is `O_NONBLOCK` — a plain `open` of a FIFO with no writer waits for one — and the type is `fstat`'s; on Windows it is the handle's (`GetFileType` is `FILE_TYPE_DISK`, then the directory attribute). It is for a reader of a path someone else named, which must answer whatever is there: a review item's subject digest reads its files through it ([protocol](protocol.md#what-a-close-is-tied-to)). `vfs_tests.cpp` ("open_regular opens a regular file and refuses anything else without waiting") opens a file, refuses a directory and a missing file, and refuses the null device on Windows and a FIFO nobody writes to on Linux.

## Mapped files

**A file mapped read-only is a buffer every thread can read with no lock** (2026-11-18, roadmap T182; `foundation/io/mapped_file.h`). `MappedFile::open(path)` maps the whole file (`CreateFileMappingW` and `MapViewOfFile` with `PAGE_READONLY`; `mmap` with `PROT_READ`, `MAP_SHARED`), closes the handles the view no longer needs, and hands out `bytes()`, a span over the file as it was mapped. It is for a reader that serves small records out of a large file to several threads: a copy a record (`read_at`) is a system call each, and a shared read-ahead buffer is a lock each reader waits behind, which is what the tile set's mask level had until T182 ([tileset](tileset.md#the-mask-level)). Through a view the OS's file cache *is* the buffer.

**What it costs, by the OS's accounting.** Address space the size of the file, and **no commit**: a read-only view of a file is backed by the file, so it charges nothing against the commit limit and the page file never holds it. In the working set it costs the pages read, and those are clean and shared with the file cache: under pressure the OS drops them without writing anything, and the next touch reads them back (a soft fault while the cache still holds them, the disk's latency once it does not). So on a machine with less memory the view stays the size it is and its resident part shrinks to what is in use; a private buffer of the same bytes would have to be paged out instead.

**A replacement.** Every writer here replaces a file by renaming a new one over it (`write_file_atomic`). The case "a mapped file and a replacement" holds that a view does not stop it and keeps reading the bytes it mapped, while a new view reads the new file. A file truncated in place under a view faults its reader on POSIX (`SIGBUS`); Windows refuses the truncation while the view exists. An empty file opens as an empty span, since the OS maps no zero-length file, so **"mapped" is "the view has bytes", never `is_open()`** (T194: the mask level asked `is_open()` and could take an empty view for a mapped one); a directory is `IsDirectory`.

**The size read is the size mapped** (2026-11-19, T194, from the review of batch 69's tree). `open` reads the file's size, then maps exactly that many bytes, not "the file as it is now": a writer sharing the file could cut it between the two, and the view would have been shorter than `size()`. On Windows a read-only section asked for more than the file holds is refused, so that open fails (`IoError`), and once the section exists the file cannot be cut below it. On POSIX `mmap` maps past a file's end without complaint, so the size is read again once mapped and a file that shrank fails the open; one cut after that is the `SIGBUS` above, the documented limit of a shared view. The case "a mapped view is exactly the size read, and a writer cannot cut it" holds the view's size against a file grown under it and, on Windows, a cut refused; the race itself is not opened by a test.

**What a writer in place can and cannot do to a reader.** A view is `MAP_SHARED` (and a Windows view of a file shares its cache), so a tool that writes a mapped file in place, rather than by rename, changes the bytes the reader sees while it reads them. It cannot make a view shorter than its `size()` (above), so a reader that holds every offset and length it reads from the view to `bytes().size()` **at the moment it reads them** never reads outside the view, whatever the writer does; what the writer *can* do is change any value between two reads, so a check made once at open over bytes read later protects nothing. The mask level reads its archive's table where it lies, and holds each entry's offset to the view at every `tile()` for that reason ([tileset](tileset.md#the-mask-level)); every writer in this tree replaces by rename, which a view never sees.

**Public API.** `foundation/io/vfs.h`: `Status`, `status_name`, `FileInfo`, `DirEntry`; path helpers `normalize_path`, `join_path`, `parent_path`, `file_name`, `extension`, `is_absolute_path`; native operations `read_file`, `write_file`, `write_file_atomic`, `append_file`, `overwrite_file` (with `k_unknown_file_size`), `stat_file`, `exists`, `list_directory`, `make_directories`, `remove_file`, `remove_directory_recursive`, `rename_path`; `Mount`, `Vfs` (`mount`, `unmount`, `resolve`, `read`, `write`, `append`, `stat`, `exists`, `list`, `make_directories`, `remove`); `AsyncRead`, `read_async`, `wait_all`; `FileHandle` (`open` with a `ReadMode`, `close`, `valid`, `unbuffered`, `size`, `path`, `read_at`; `native` on Windows), `ReadMode`, `k_unbuffered_alignment`, `AsyncRangeRead` (with `complete()`), `read_range_async`, `read_ranges_async`, `read_queued` (with `ReadCompleted`, `QueuedReadStats`, `k_max_queue_depth`), `read_file_range`. `foundation/io/mapped_file.h`: `MappedFile` (`open`, `close`, `is_open`, `bytes`, `size`).

**Depends on.** `base`, `containers`, `jobs`, `time`.

**Testing.** `tools/dev.ps1 test -Filter io`. Works in a temporary directory: path normalization, the native operation set including atomic replacement and cleanup, `make_directories` on a directory that is there, a missing nested one, and a file in the way at the leaf and on the way (refused, the file untouched), `overwrite_file` making a file and its directories, cutting, growing and emptying it, remaking it when told its old length in both directions and when told a wrong one, refusing a directory, and leaving nothing beside it; mount resolution and escape refusal, and asynchronous reads with a two-worker job system. For ranges: a range out of the middle of a 100 KB pattern with the byte past it untouched, the first and the last byte, a read that runs off the end coming back short, an offset at and past the end coming back empty, a zero-length read, a moved handle that still reads while its source is closed, a closed handle refusing, the one-shot `read_file_range` and its `NotFound`; and 128 scattered 3 KB ranges of one megabyte file through one handle, one counter and two Efficiency workers, each checked byte for byte against the offset that produced it. Queued reads: the same 128 ranges at depths 1, 8, 32, 128 and 1000 (clamped), every one byte for byte and completed in order, a request with no file failing alone, a read past the end short and a zero-length one complete; 64 requests through a ring of four buffers copied out in their completions, the whole file in order; and an unbuffered handle reading aligned ranges (one running past the end, short to the byte) while a misaligned offset, length or destination is refused. Mapped files (`mapped_file_tests.cpp`): a 70,000-byte pattern read through the view byte for byte, a moved view still reading and a closed one empty, an empty file an empty span, a missing file and a directory refused, and a replacement renamed over a mapped file while the old view keeps its bytes and a new one reads the new.

**Performance notes.** Whole-file reads go through a 64 KB stdio buffer with the whole size reserved up front. Asynchronous whole-file reads are synchronous reads on Efficiency workers. Ranged reads are unbuffered and one system call each, which is what a caller reading 128 KB at a time wants and what a caller reading four bytes at a time must not do — the container reader therefore reads its header and section table once, at open, and addresses everything after that in page-sized runs. io_uring and DirectStorage-style GPU decompression slot in behind the same `AsyncRangeRead` request when streaming bandwidth asks for them.

**Queued against the pool** (2026-10-24, W54, [tile archives](../experiments/tile-archives-2026-10-24.md), `msvc-release`, a striped volume of three 990 Pros, others' CPU 14–30%): the 7,345 18 KB records of a cold 132 MB file read each its own range, into one buffer — the Efficiency pool with 4 workers 0.262 s and with 16 0.205 s; `read_queued` from one thread at depth 4 0.261 s, 32 0.205 s and **128 0.140 s** (941 MB/s, about 52,000 reads a second). At one depth the two are the same; the queue reaches the depth without the threads. Warm, the pool's sixteen cores copy out of the cache faster (0.031 s) than the queue's one (0.076 s), which is why a caller with adjacent ranges coalesces them. Unbuffered, the tile set's level read whole in 256 KiB runs is 0.12 s against 0.14 s from a cold copy through the cache: 12%, and an unbuffered read leaves nothing in the cache for the next launch, so nothing in production reads unbuffered.
