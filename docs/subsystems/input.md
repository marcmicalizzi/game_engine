# input (foundation)

**Purpose.** What a player does, in the shape the simulation reads it: named actions with bindings a game ships and a player edits, one `InputState` per simulation tick built from tick-stamped events, and a log of those events that replays bit for bit (docs/plan/05-simulation.md §5.2 "input" phase, §5.10 determinism and replay). The module does not depend on `window` and never will: it consumes `RawEvent`, a plain record with no platform in it, so the same code path serves a live session, a headless server with no display, and a replay read from a file. Nothing inside reads a clock — a hold time is the caller's tick arithmetic — so the same event sequence produces the same states on every machine, which is what makes the log worth recording.

**Why a separate event type.** A window event is about a device; an action is about the game. Between them sits a table the player owns, and a replay has to survive both: the log must still mean what it meant after the renderer, the window backend, and the machine have all changed. `RawEvent` is that boundary — `{tick, source, code, value, device}`, 24 bytes, nothing that needs a display to construct. Whoever owns the window does the conversion once (`apps/engine_input` does it today, `apps/engine_view` will), and the numbering it converts into is a file format: key codes are SDL scancodes, mouse buttons are 1 left / 2 middle / 3 right, mouse axes are `MouseAxisCode`, gamepad codes are `window::GamepadButton` and `window::GamepadAxis`, raw joystick codes are the device's own axis and button indices, a hat code is `hat_code(hat_index, direction)`, and the slot id is the `device` (docs/subsystems/window.md). Those enumerators are appended, never reordered; the header of `foundation/input/input.h` spells the whole conversion out as code.

**Devices.** `RawEvent::device` is the gamepad slot for the gamepad sources and the joystick slot for the joystick ones. The two slot spaces are separate and overlap numerically — a `RawEvent` with `device = 0` means the first gamepad or the first raw joystick depending on its `source`, never both — so `set_device_filter` and any per-player assignment read the source too.

**Raw joysticks.** A device SDL has no gamepad mapping for (a wheel, a pedal box, a shifter, a flight stick) has no layout to name, so its bindings are by index: `Source::JoystickAxis` with the axis number, `Source::JoystickButton` with the button number, and `Source::JoystickHat`. A hat reports a position rather than a press, and a binding needs a direction, so a hat binding packs both into the code:

```
code = hat_index << 8 | direction        // hat_code(hat, direction); hat_code(0, k_hat_up) == 1
```

with `hat_index_of()` and `hat_direction_of()` to take it apart and `k_hat_up/right/down/left` (1, 2, 4, 8) mirroring `window::HatDirection`. The conversion at the window edge emits all four directions of a hat on every hat event, so `InputState` sees one digital signal per direction and counts an edge only where the value changed; that keeps the converter stateless. Deadzones apply to `JoystickAxis` exactly as they do to `GamepadAxis` (`is_analog_axis` is the predicate), including the radial deadzone an `Axis2` gets when both of its components are analog axes *of the same source* with the same non-zero deadzone — a flight stick's two axes are a stick by the same rule a gamepad's are, and a pair mixing a joystick axis with a gamepad axis is not.

**Public API.**

- `foundation/input/input.h`: `Source{Key, MouseButton, MouseAxis, GamepadButton, GamepadAxis, JoystickAxis, JoystickButton, JoystickHat}` with `source_name`/`source_from_name`/`is_digital`/`is_analog_axis`, `MouseAxisCode{X, Y, WheelX, WheelY}`, `hat_code`/`hat_index_of`/`hat_direction_of`, and `Binding{source, code, scale, deadzone}`. **The enumerator values of `Source` are log format**: they are appended, never reordered or renumbered, and the JSON names (`"key"`, … , `"joystick_axis"`, `"joystick_button"`, `"joystick_hat"`) are file format too. `scale` turns a key into an axis end (+1 or -1) and inverts or attenuates an analog axis; `deadzone` is the fraction of an analog axis's travel that reads as zero, with the rest rescaled so full travel still reaches 1 (`apply_deadzone` is the curve).
- `ActionMap`: `add_action(name, ActionKind::Button|Axis|Axis2)` returns an `ActionId` (a dense index; `k_invalid_action` for an empty or conflicting name), `bind(action, Binding, component = 0)` adds one of any number of bindings — `component` picks x or y of an `Axis2` — and `find_action`, `action_name`, `action_kind`, `bindings`, `clear_bindings`, `is_bound` read it back. `to_json()`/`from_json()` are the shipped default map and the player's rebind, through the canonical writer, so a rebind is a diff; `describe()` is that text with a header line for tools; `hash()` digests every name, kind, and binding into a 64-bit value that identifies the map's contents on every platform.
- `InputState`: `begin_tick(SimTick)`, `feed(const RawEvent&)`, `end_tick()`, then `pressed(action)` (went down during this tick), `released(action)`, `held(action)`, `axis(action)` (the bindings' values times their scales, summed and clamped to -1..1), `axis2(action)` (`Vec2`), and `mouse_delta()`. A press and a release inside one tick both report, so a slow tick never swallows a click; a key repeat is not a second press; an analog binding on a `Button` action counts as down past `k_analog_button_threshold`, which is how a trigger fires. An `Axis2` bound to two analog axes of the same source, one per component with the same non-zero deadzone, is recognized as a stick and gets a *radial* deadzone, so a diagonal is not harder to reach than a cardinal direction. `set_device_filter(slot)` splits one event stream between two players; `state_hash()` digests every query result at this tick and is what a replay compares.
- `foundation/input/input_log.h`: `InputLog::record` appends (ticks may not go backwards), `set_map` stores the `ActionMap::hash()` the session was recorded against, `save`/`load` are JSON lines through `foundation/io` — a header line, then one event per line as `[tick, source, code, value, device]`, tick first and canonical — and `replay(state, from, to, {on_tick, user}, error)` feeds the events tick by tick, including the ticks with no events, calling `on_tick` (a function pointer, so no `std::function`) after each. A replay into a state whose map hashes differently is **refused with a message** rather than silently reinterpreted: the same scancode would mean a different action and the replay would diverge from the session it came from.

**Depends on.** `base`, `containers`, `math`, `time`, `json`, `io`. Not `window`, by design, and not a higher layer; the module is pure computation over events plus one file read and one file write.

**Testing.** `tools/dev.ps1 test -Filter input`: a key driving a button action across four ticks (pressed only on the tick it went down, held after, released once and only once), a press and a release inside one tick, a key repeat that is not a second press, two keys on one axis at +1 and -1 cancelling when both are down, a gamepad axis through its deadzone and its scale (including the curve's own values and an inverted binding), a trigger crossing the button threshold, `axis2` from four keys and from a stick — inside the disc, straight out to 1, a diagonal that keeps its direction and does not leave the unit disc, and a nudge whose components are each under the deadzone but whose radius is not — mouse motion accumulating over a tick and starting at rest on the next, events for unbound codes leaving no trace, the device filter, the clamp on a sum, and a JSON round trip that compares `describe()`, the hash, and the canonical bytes, with ten malformed maps each refused with a message. Then a racing rig as the window module hands it over: a wheel axis with a deadzone driving an `Axis` action, two pedals on one axis action at +1 and -1 scale, a hat direction as a `Button` (pressed on the tick it reaches Up, no second press when it moves to a diagonal, released when it centres), a shifter's gates as two `Button` actions on a second device, a joystick axis and a gamepad axis on slot 0 that stay separate, and a flight stick's two axes taking the radial deadzone while a joystick/gamepad pair does not. The source names and numbering are pinned, including that the joystick sources are appended at 5, 6, and 7. Then the log: a nine-tick scripted session recorded while it is fed live, replayed into a fresh `InputState`, and compared digest by digest; the same file saved, read back event for event, saved again byte for byte, and replayed to the same digests; a replay against a rebound map refused with both hashes in the message, and against a state with no map at all; an empty range and an empty log; replaying from the middle of a log; and nine broken files — empty, not JSON, the wrong type, no map, a future version, a short row, an unknown source, a field of the wrong type, and events out of tick order; and a wheel session over the joystick sources saved, checked for the three source names in the text, loaded back event for event, and replayed to the same digests. The size table pins `RawEvent` at 24 bytes, `Binding` at 16, and `ActionBinding` at 20.

**Not yet.** The `window::Event` → `RawEvent` conversion inside the engine's own window owner: `apps/engine_input` does it for the probe (docs/subsystems/apps.md) and `apps/engine_view` is next. Named layouts for the raw devices — nothing turns "axis 2 of a Logitech G29" into "brake" yet, which is what the probe's output is being collected for. Chords and modifiers (`Ctrl+S` as one action), a "consumed" flag and input contexts so a menu can take the keyboard from the game, and text input and IME, which are a different kind of input than a binding table. Haptics and rumble, which are output. Per-player device assignment beyond the slot filter, and hot-swapping a pad mid-session without the game noticing. Chording an event log with the world event log into one replay file, which is where plan §5.10's "input log + event log" ends up. Recording to the log incrementally while a session runs, rather than in memory until `save()`.

**Performance notes.** An `InputState` holds one signal per *bound* code — an unbound event costs a binary search in the map's reverse index and nothing else — so a game with fifty bindings has a state of a few hundred bytes and queries that touch one cache line. Queries walk an action's bindings and look each up; they are not cached, on the assumption that a system reads an action once per tick. The signal map allocates only when a bound code is seen for the first time, so a session reaches steady state within a few ticks and allocates nothing after that. `state_hash()` walks every action and is a debug and CI tool, not something to call per system.
