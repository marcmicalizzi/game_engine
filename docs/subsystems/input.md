# input (foundation)

**Purpose.** What a player does, in the shape the simulation reads it: named actions with bindings a game ships and a player edits, one `InputState` per simulation tick built from tick-stamped events, and a log of those events that replays bit for bit (docs/plan/05-simulation.md §5.2 "input" phase, §5.10 determinism and replay). The module does not depend on `window` and never will: it consumes `RawEvent`, a plain record with no platform in it, so the same code path serves a live session, a headless server with no display, and a replay read from a file. Nothing inside reads a clock — a hold time is the caller's tick arithmetic — so the same event sequence produces the same states on every machine, which is what makes the log worth recording.

**Why a separate event type.** A window event is about a device; an action is about the game. Between them sits a table the player owns, and a replay has to survive both: the log must still mean what it meant after the renderer, the window backend, and the machine have all changed. `RawEvent` is that boundary — `{tick, source, code, value, device}`, 24 bytes, nothing that needs a display to construct. Whoever owns the window does the conversion once (`apps/engine_input` for the device probe, and `apps/engine_view` for `--interactive`, below), and the numbering it converts into is a file format: key codes are SDL scancodes, mouse buttons are 1 left / 2 middle / 3 right, mouse axes are `MouseAxisCode`, gamepad codes are `window::GamepadButton` and `window::GamepadAxis`, raw joystick codes are the device's own axis and button indices, a hat code is `hat_code(hat_index, direction)`, and the slot id is the `device` (docs/subsystems/window.md). Those enumerators are appended, never reordered; the header of `foundation/input/input.h` spells the whole conversion out as code.

**Devices.** `RawEvent::device` is the gamepad slot for the gamepad sources and the joystick slot for the joystick ones. The two slot spaces are separate and overlap numerically — a `RawEvent` with `device = 0` means the first gamepad or the first raw joystick depending on its `source`, never both — so `set_device_filter` and any per-player assignment read the source too.

**Raw joysticks.** A device SDL has no gamepad mapping for (a wheel, a pedal box, a shifter, a flight stick) has no layout to name, so its bindings are by index: `Source::JoystickAxis` with the axis number, `Source::JoystickButton` with the button number, and `Source::JoystickHat`. A hat reports a position rather than a press, and a binding needs a direction, so a hat binding packs both into the code:

```
code = hat_index << 8 | direction        // hat_code(hat, direction); hat_code(0, k_hat_up) == 1
```

with `hat_index_of()` and `hat_direction_of()` to take it apart and `k_hat_up/right/down/left` (1, 2, 4, 8) mirroring `window::HatDirection`. The conversion at the window edge emits all four directions of a hat on every hat event, so `InputState` sees one digital signal per direction and counts an edge only where the value changed; that keeps the converter stateless. Deadzones apply to `JoystickAxis` exactly as they do to `GamepadAxis` (`is_analog_axis` is the predicate), including the radial deadzone an `Axis2` gets when both of its components are analog axes *of the same source* with the same non-zero deadzone — a flight stick's two axes are a stick by the same rule a gamepad's are, and a pair mixing a joystick axis with a gamepad axis is not.

**The device log corpus.** `content/input-logs/` holds real recordings of real hardware, committed and replayed on every build. They are the answer to a problem this module cannot solve by reasoning: a wheel, a pedal box, a shifter, and a flight stick each number their axes and buttons however their firmware felt like it, nobody working on the engine owns one, and a device that is not plugged in cannot be asked. So its owner runs `engine-input probe` (docs/subsystems/apps.md), and what comes back is a file — which means it is a fixture, not a note. There are three so far, all taken 2026-09-17: a Logitech F710 pad (the named gamepad sources, d-pad as buttons, no hat), a Thrustmaster T.16000M flight stick (raw joystick, four axes, eleven buttons, the corpus's only hat), and a T300 RS wheel recorded together with its gear shift, which is two raw joysticks at once — the wheel with steering on axis 0 and three pedals on 1..3, the shifter with six buttons and nothing else. `content/input-logs/README.md` says what each file is, what every axis physically is, and how to add a device; the logs themselves carry slots and codes and no names, so that README is the only place a slot is tied to a device, and the test checks that the tie is still there.

**The first owner of a window that feeds a consumer: engine-view's fly camera.** `engine-view --interactive` ([apps](apps.md#--interactive-a-camera-somebody-flies)) is where this module stopped being exercised only by tests and a probe. Its edge (`apps/engine_view/window_input.h`) turns every `window::Event` into `RawEvent`s stamped with **the tick they will be fed at** — the next tick of a `FixedStepClock` — and its camera (`fly_camera.h`) reads an `InputState` once per tick at 240 Hz and never sees the window. Three things here exist because of it, and each is the general shape of something a game will need:

- **`InputState::delta2(action)`** is the tick's pointer motion through an action's `MouseAxis` bindings and their scales, **not clamped**. `axis2` clamps to -1..1, which is right for a stick and caps a mouse's turn per tick at one pixel's worth. A mouse says how far and a stick how fast, so a camera reads one through `delta2` and the other through `axis2`; `state_hash()` includes it.
- **`feed_ticks(state, events, cursor, from, to, options)`** is `InputLog::replay`'s own tick loop — begin, feed the events stamped with the tick, end, `on_tick` — over any sorted span, from a cursor, returning the next cursor. `replay` is now this function over the log's events, and engine-view calls it for a frame's worth of ticks both on the live session's pending batch and on a replayed log's events. **That is the replay guarantee's foundation**: a session and its replay do not run two loops meant to agree; they run one loop.
- **`InputLog::check_map(state)`** is the refusal `replay` makes (no map, or another map's hash, with both hashes in the message), on its own, for a caller that feeds a log a frame at a time and checks once before the first. **`set_session(JsonValue)` / `session()`** carry one object in the log's header that the *recording application* owns and this module never reads: engine-view's is `engine.view.session` — what was drawn, the start camera, the tick rate, the camera's parameters, the ticks the session ran, the build — so a log names what it needs to be replayed without this module learning what a camera is. A log without one writes no `session` key, which is why every log in the device corpus is still the bytes it was.

The first recorded *session*, as opposed to a device recording, is `content/input-logs/sessions/fly-synthetic.jsonl`: synthetic, because nobody can move a mouse in CI, generated by a test helper and checked against it byte for byte, with the camera trajectory it flies committed beside it (content/input-logs/README.md).

**A map that grows, and the logs that name the old one.** `check_map` refuses a log whose map hash is not the state's, and appending an action moves the hash. engine-view appended four (the time-lapse's rate keys, 2026-09-27), so it keeps its map in **revisions** — each one the last plus what it appended — and replays a log with the revision whose hash the log names (`view::default_fly_map_for`, [apps](apps.md#--interactive-a-camera-somebody-flies)). That is the refusal's own rule kept, not relaxed: the log is replayed with exactly the map it was recorded against, so a key an older session pressed that a later revision binds — a `.` somebody pressed before it meant anything — does nothing on replay, as it did live. A rebound key is still a map no revision has, and still refused. The module itself is unchanged; the rule belongs to whoever ships the map, which a game will also be.

**Public API.**

- `foundation/input/input.h`: `Source{Key, MouseButton, MouseAxis, GamepadButton, GamepadAxis, JoystickAxis, JoystickButton, JoystickHat}` with `source_name`/`source_from_name`/`is_digital`/`is_analog_axis`, `MouseAxisCode{X, Y, WheelX, WheelY}`, `hat_code`/`hat_index_of`/`hat_direction_of`, and `Binding{source, code, scale, deadzone}`. **The enumerator values of `Source` are log format**: they are appended, never reordered or renumbered, and the JSON names (`"key"`, … , `"joystick_axis"`, `"joystick_button"`, `"joystick_hat"`) are file format too. `scale` turns a key into an axis end (+1 or -1) and inverts or attenuates an analog axis; `deadzone` is the fraction of an analog axis's travel that reads as zero, with the rest rescaled so full travel still reaches 1 (`apply_deadzone` is the curve).
- `ActionMap`: `add_action(name, ActionKind::Button|Axis|Axis2)` returns an `ActionId` (a dense index; `k_invalid_action` for an empty or conflicting name), `bind(action, Binding, component = 0)` adds one of any number of bindings — `component` picks x or y of an `Axis2` — and `find_action`, `action_name`, `action_kind`, `bindings`, `clear_bindings`, `is_bound` read it back. `to_json()`/`from_json()` are the shipped default map and the player's rebind, through the canonical writer, so a rebind is a diff; `describe()` is that text with a header line for tools; `hash()` digests every name, kind, and binding into a 64-bit value that identifies the map's contents on every platform.
- `InputState`: `begin_tick(SimTick)`, `feed(const RawEvent&)`, `end_tick()`, then `pressed(action)` (went down during this tick), `released(action)`, `held(action)`, `axis(action)` (the bindings' values times their scales, summed and clamped to -1..1), `axis2(action)` (`Vec2`), `delta2(action)` (the `MouseAxis` bindings only, summed over the tick and unclamped: a distance, not a position), and `mouse_delta()`. A press and a release inside one tick both report, so a slow tick never swallows a click; a key repeat is not a second press; an analog binding on a `Button` action counts as down past `k_analog_button_threshold`, which is how a trigger fires. An `Axis2` bound to two analog axes of the same source, one per component with the same non-zero deadzone, is recognized as a stick and gets a *radial* deadzone, so a diagonal is not harder to reach than a cardinal direction. `set_device_filter(slot)` splits one event stream between two players; `state_hash()` digests every query result at this tick and is what a replay compares.
- `foundation/input/input_log.h`: `InputLog::record` appends (ticks may not go backwards), `set_map` stores the `ActionMap::hash()` the session was recorded against, `save`/`load` are JSON lines through `foundation/io` — a header line, then one event per line as `[tick, source, code, value, device]`, tick first and canonical — and `replay(state, from, to, {on_tick, user}, error)` feeds the events tick by tick, including the ticks with no events, calling `on_tick` (a function pointer, so no `std::function`) after each. A replay into a state whose map hashes differently is **refused with a message** rather than silently reinterpreted: the same scancode would mean a different action and the replay would diverge from the session it came from. `check_map(state, error)` is that refusal alone; `feed_ticks(state, events, cursor, from, to, options)` is the tick loop alone, over any span, a piece at a time; `set_session`/`session` are the application's header block, saved under `session` only when there is one and refused on load when it is not an object.

**Depends on.** `base`, `containers`, `math`, `time`, `json`, `io`. Not `window`, by design, and not a higher layer; the module is pure computation over events plus one file read and one file write.

**Testing.** `tools/dev.ps1 test -Filter input`: a key driving a button action across four ticks (pressed only on the tick it went down, held after, released once and only once), a press and a release inside one tick, a key repeat that is not a second press, two keys on one axis at +1 and -1 cancelling when both are down, a gamepad axis through its deadzone and its scale (including the curve's own values and an inverted binding), a trigger crossing the button threshold, `axis2` from four keys and from a stick — inside the disc, straight out to 1, a diagonal that keeps its direction and does not leave the unit disc, and a nudge whose components are each under the deadzone but whose radius is not — mouse motion accumulating over a tick and starting at rest on the next, `delta2` reading 400 pixels as 400 where `axis2` reads 1, leaving a stick bound to the same action out and reading zero on a tick with no motion, events for unbound codes leaving no trace, the device filter, the clamp on a sum, and a JSON round trip that compares `describe()`, the hash, and the canonical bytes, with ten malformed maps each refused with a message. Then a racing rig as the window module hands it over: a wheel axis with a deadzone driving an `Axis` action, two pedals on one axis action at +1 and -1 scale, a hat direction as a `Button` (pressed on the tick it reaches Up, no second press when it moves to a diagonal, released when it centres), a shifter's gates as two `Button` actions on a second device, a joystick axis and a gamepad axis on slot 0 that stay separate, and a flight stick's two axes taking the radial deadzone while a joystick/gamepad pair does not. The source names and numbering are pinned, including that the joystick sources are appended at 5, 6, and 7. Then the log: a nine-tick scripted session recorded while it is fed live, replayed into a fresh `InputState`, and compared digest by digest; the same file saved, read back event for event, saved again byte for byte, and replayed to the same digests; a replay against a rebound map refused with both hashes in the message, and against a state with no map at all; an empty range and an empty log; replaying from the middle of a log; the same session fed through `feed_ticks` in pieces of one, two, three, five and twelve ticks giving `replay`'s digests at every tick, an empty range moving the cursor past what came before it, and `check_map` refusing a rebound map and a state with none; a session block saved, loaded back as the same JSON with a float as the same float, saved again byte for byte, absent from a log that has none, and gone after loading such a log; and ten broken files — empty, not JSON, the wrong type, no map, a future version, a short row, an unknown source, a field of the wrong type, events out of tick order, and a session that is not an object; and a wheel session over the joystick sources saved, checked for the three source names in the text, loaded back event for event, and replayed to the same digests. The size table pins `RawEvent` at 24 bytes, `Binding` at 16, and `ActionBinding` at 20.

Then the corpus (`tests/corpus_tests.cpp`), which is the only test here whose numbers were measured rather than written: each committed log is loaded, every distinct signal in it is given an action the way `engine-input replay` does, and a row of expectations is checked against it — the event count, the first and last tick, how many actions of each kind, and for every device in the log its slot, which of the two source families it used, and how many distinct axes, buttons, and hats it moved. Then the whole session replays through an `InputState` and the ticks, presses, and releases are pinned: f710 796 events over ticks 9..583, one gamepad on slot 0 with 4 axes, 8 buttons, **no hat**, and 67 presses; t16000m 907 events over 15..596, one joystick with 4 axes, 11 buttons, **one hat**, 49 presses; t300 2,073 events over 5..591, joystick 0 with 4 axes and 10 buttons and joystick 1 — the shifter — with **6 buttons and nothing else**, 34 presses between them. Each file is also written back out and compared line for line with the committed bytes, so a recording in the repository is canonical. The logs are located through `ENGINE_SOURCE_DIR`, a compile definition `foundation/input/CMakeLists.txt` sets on the test target, since a test binary sits wherever the preset put it.

**Not yet.** A shared converter: `apps/engine_input` and `apps/engine_view` each convert window events themselves, because the only module that could hold one would depend on both `window` and `input`, and there is no such module below the apps yet — a game will be the third copy, and the moment to lift it. Named layouts for the raw devices — the corpus now says that axis 1 of the T300 rig is a pedal, but nothing turns that into a binding called "brake", and a device is still named rather than described (`window::resolve_device_name`). Chords and modifiers (`Ctrl+S` as one action), a "consumed" flag and input contexts so a menu can take the keyboard from the game, and text input and IME, which are a different kind of input than a binding table. Haptics and rumble are output and live in `window` (docs/subsystems/window.md); nothing in a binding table describes them yet, so a game drives them through the window layer directly. Per-player device assignment beyond the slot filter, and hot-swapping a pad mid-session without the game noticing. A replay of plan §5.10's "input log + event log" now exists without one file: a headless world's player is an observer steered by an `InputLog` (`world::InputObserver`), a save carries the log up to its tick beside the world's store, and the replay test runs both ([world](world.md#the-player)). Input recorded into the store's event log as `Player`-origin events (03 §3.10), and a game's own systems reading `InputState` in the tick's `Input` phase, are not built. Recording to the log incrementally while a session runs, rather than in memory until `save()`.

**Performance notes.** An `InputState` holds one signal per *bound* code — an unbound event costs a binary search in the map's reverse index and nothing else — so a game with fifty bindings has a state of a few hundred bytes and queries that touch one cache line. Queries walk an action's bindings and look each up; they are not cached, on the assumption that a system reads an action once per tick. The signal map allocates only when a bound code is seen for the first time, so a session reaches steady state within a few ticks and allocates nothing after that. `state_hash()` walks every action and is a debug and CI tool, not something to call per system.
