# animation (systems)

**Purpose.** The capability that plays clips. [anim](anim.md) is the data half — skeletons, poses, clips, the blends over a pose, 3×4 skinning matrices — and nothing ticks it; this module is the tick. It owns a playhead per entity, an SoA **pose pool**, and the bone-matrix buffer a skinned instance uploads, and it is the first capability in this engine built end to end through [ADR-0027](../adr/0027-additive-capabilities.md)'s contract: a schema file, three `sim::SystemDesc`s registered with `ecs::register_system`, an LOD policy over `sim`'s tiers, a docs page, tests, a size table and a bench, in one directory, behind one switch.

What it deliberately does not do: **draw**. The renderer contract is a span and two offsets ("The renderer contract" below), and filling `gfx::DeformDesc` from it is the renderer's change — which has now been made, so a character imported through [assets](assets.md), ticked here, and skinned in `deform.slang` is one command line ([apps](apps.md), `engine-view --animate`). Also absent and named rather than implied: blend trees and state machines as data, IK, motion matching ([05 §5.11](../plan/05-simulation.md#511-integration-notes)).

**Why this shape.**

*The pose is not a component, and that is the whole design.* [03 §3.4](../plan/03-data-model.md#34-the-runtime-world)'s hedge — "hot systems own their own data; the ECS holds identity, relationships and gameplay components" — is usually quoted about physics. Animation is the cleaner case, because a pose fails every test for being a component at once. It is *variable length*, so as a component it is either a fixed-width worst case (a 23-joint character paying for a 100-joint one) or three `Vector`s per entity — three heap allocations and three pointer chases per instance per tick, which is the layout [anim](anim.md) spends its first page arguing against. It is *private*: nothing outside this capability reads a pose, and putting it in the world would show it to the protocol, to a persistence walk and to every query that touches the archetype for nobody's benefit. And it is *recomputable* from `(skeleton, clip, time)`, so putting it in the world would make the world carry a cache. So the ECS holds a `u32` slot and the capability holds the arena.

*The arena is one set of channel arrays with every instance's joints laid end to end*, plus one array of `anim::JointMatrix` with the same slot geometry. Sampling an instance walks four contiguous runs; the matrices of *every* instance are one span the renderer can upload whole. There is no per-slot stride, so there is no waste: the arena is exactly the sum of the live skeletons' joint counts. Free lists are per skeleton, so a released slot is reused by an instance of the same skeleton and its run stays the right length, and reuse is LIFO — which is what makes slot assignment a deterministic function of the acquire/release sequence, and what the bit-identical tests rest on.

*The playhead is `Id128`-addressed but index-resolved.* `AnimationPlayer::clip` is an `Id128` because that is what a save holds ([ADR-0028](../adr/0028-ecs-and-persistent-store.md) seam 3), and a hash lookup is the wrong thing to do per instance per tick. `advance_players` resolves the handle into `SkeletonInstance::clip_index` and checks it with a 16-byte compare against the library's own record, so only a clip that actually changed pays for a lookup — including one set from JSON through `WorldCommands`, which arrives with no cached index and is resolved on the tick it changed.

**Owned data.** The pose pool (`PosePool`: three channel arrays, the matrix array, the slot table and the per-skeleton free lists), the clip library (`Library`: `anim::Skeleton`s and `anim::Clip`s loaded from glTF, their `Id128`s and their standard-skeleton mappings), and the three components' *meaning*. Nothing else may hold a pose; nothing else may hand out a pool slot.

## The components, and what a save contains

Declared once, in `systems/animation/schemas/animation.schema`, as `@kind(component)` structs ([ADR-0028](../adr/0028-ecs-and-persistent-store.md) seam 1). The split between them *is* this capability's answer to "what does a save need to resume the same pose".

| Component | Persisted? | Holds |
|---|---|---|
| `AnimationPlayer` | **yes** | `clip`, `time`, `speed`, `weight`, `looping`, and the cross-fade: `fade_clip`, `fade_time`, `fade_elapsed`, `fade_seconds`, `fade_looping` |
| `SkeletonInstance` | no (`@transient`) | `skeleton`, `pose_slot`, `joints`, and the resolved `skeleton_index`/`clip_index`/`fade_index` |
| `AnimationLod` | no (`@transient`) | `tier`, `divisor`, `phase`, `interpolate`, `skin`, `frozen_at_us` |

**Why exactly those fields are the persistent ones.** A pose is a pure function of `(skeleton, clip, time)`, and of `(fade_clip, fade_time, fade_elapsed/fade_seconds)` as well while a cross-fade is in flight. Save those and the pose comes back; save the pose instead and you have saved a cache that the clip library can regenerate and that a re-authored clip would make wrong. `speed`, `looping` and `weight` are there because they are inputs to the *next* tick's time, not because they are pose state.

**Why the skeleton reference is not persistent** even though it is an asset id. Which skeleton an entity rides is a property of the model it materializes from, exactly like its mesh: the entity's asset brings it back. Saving it here would give one fact two owners, and the two would disagree the first time a character's model changed. The pool slot is a run-time allocation that means nothing in the next process, and `AnimationLod` is derived from the tier, which is derived from where the cameras are this session.

**What this does to the archetype set** ([ADR-0028](../adr/0028-ecs-and-persistent-store.md)'s guard rail): three components and **no relationship**, so an animated entity adds at most one archetype per distinct combination it appears in, and nothing here multiplies tables as a cross product. The tier is a *field*, not a relationship — see "What the contract could not express" for what that costs and when it should change.

## The pose pool

`PosePool::acquire(skeleton, joints)` hands out a slot; `release` gives it back. `pose(slot)` is an `anim::PoseView` over the slot's run and `matrices(slot)` its bone matrices; `upload_buffer()` is all of them.

**When the arrays may move.** `acquire` may reallocate, so no view or span from the pool survives one. The capability acquires and releases only from tier transitions, which happen outside the parallel systems phase, so within a tick the arena is stable and every instance writes only its own run — which is also what makes the sampling systems' writes safe at any worker count.

**Growth is geometric, and it is the container's job now.** A pool that appends one skeleton's worth of joints and resizes to the new total used to reallocate and copy on every acquire, because `Vector::resize` took the size exactly: O(n²) in the population, and not "slow" so much as "never finishes" — filling 65,536 slots that way spun for ten CPU-minutes in a debug build. `PosePool::grow` worked around it by reserving a doubled capacity by hand; [containers](containers.md) now grows geometrically on `resize`, so the workaround is gone and this is four `resize` calls. `AnimationConfig::reserve_joints` is still how a world that knows its population never reallocates at all.

**Cost.** 40 bytes of pose (`Vec3` + `Quat` + `Vec3`) and 48 bytes of matrix per joint of every slot ever used. A 23-joint character is 2,024 bytes; 10,000 of them are 20 MB, of which 11 MB is the upload buffer. `PosePool::bytes()` reports the arena **in use**; while the population is still growing the allocator holds up to half again as much, which is what geometric growth costs and what `reserve_joints` avoids.

## The systems

Five, registered through `ecs::register_system` with a `sim::SystemDesc` each ([ADR-0028](../adr/0028-ecs-and-persistent-store.md) seam 2), in this order. `AnimationSystem::install(sim)` is the one call that does it, plus the components. The two `graph_*` rows are S35 stage 2's ("Graphs: the pose program", below) and match only entities with **no** `AnimationPlayer`, so their queries and the player's are disjoint; the scheduler puts them in four waves (the two controls together, then the player's sample, the graph's, the matrices).

| System | Phase | Reads | Writes | Determinism |
|---|---|---|---|---|
| `animation.advance_players` | `Systems` | `AnimationLod` | `AnimationPlayer`, `SkeletonInstance` | `Hashed` |
| `animation.graph_control` | `Systems` | `AnimationLod` | `AnimationGraphInput`, `AnimationGraphState` | `Hashed` |
| `animation.sample_poses` | `Systems` | the player's three | resource `animation.pose_pool` | `Hashed` |
| `animation.graph_sample` | `Systems` | the graph's two, `SkeletonInstance`, `AnimationLod` | resource `animation.pose_pool` | `Hashed` |
| `animation.build_skinning_matrices` | `Systems` | `SkeletonInstance`, `AnimationLod`, resource `animation.pose_pool` | resource `animation.joint_matrices` | **`Derived`** |

`advance_players` moves the playhead, resolves the clip handles, and collapses a finished cross-fade so the sampler never changes state. `sample_poses` fills the slot with the rest pose, samples the clip into it, blends the incoming clip when a fade is in flight, and blends toward the bind pose when `weight < 1`. `build_skinning_matrices` composes the pose into model space and writes `model * inverse_bind` as 3×4.

The player's three match on all of `AnimationPlayer`, `SkeletonInstance` and `AnimationLod`, so **an entity that has a player but no instance is not ticked**: a playhead with no skeleton animates nothing, and `AnimationSystem::attach` is what gives it one. That is the shape an external edit arrives in — `WorldCommands` can set an `AnimationPlayer` from JSON before anything has attached a skeleton — and it costs a tick of nothing rather than a branch per instance forever. `AnimationStats` is written once per system per tick by stage 0 only, which makes it free and makes it stage 0's share rather than the world's total when there is more than one worker; `promotions` and `demotions` are exact, because a tier transition never happens on a worker.

**Every ordering the three need is declared, and one of the two declarations did not exist when this capability was built.** `advance_players` before `sample_poses` is a component conflict and always was: one writes `AnimationPlayer`, the other reads it. `sample_poses` before `build_skinning_matrices` is a conflict on **the pose pool**, which is not a component and must not be (see "The pose pool" above). That used to be inexpressible, so the third system sat in `PostPhysics` and borrowed its ordering from the phase — honest, and arguable on its own merits, but it moved a system for a reason that had nothing to do with which phase it belongs in. `sim::SystemDesc::reads_resources`/`writes_resources` ([sim](sim.md), "Named resources") say it directly: `sample_poses` writes `animation.pose_pool`, `build_skinning_matrices` reads it and writes `animation.joint_matrices`, and all three run in `Systems`, one wave apart, for exactly the reason the code requires. Their determinism stances are unchanged and are now visibly the *system's* rather than the phase's: the matrices are `Derived` because nothing reads them back into gameplay and a load rebuilds them from the playhead.

**What actually orders them today, which is not the declaration.** flecs' pipeline inserts a sync point for a staged write, not for an in-place write to a `$this` term (`flecs_pipeline_check_term` returns false for owned terms), so there is no barrier between these three systems at any worker count — there was none across the `Systems`/`PostPhysics` boundary either, because a phase boundary is not a sync point in flecs. What makes the tick correct at eight workers is that flecs hands each worker the *same* slice of the same table in consecutive systems, so one entity's three systems run in order on one thread; the bit-identical worker test is what holds that down. The declaration is what [ADR-0028](../adr/0028-ecs-and-persistent-store.md) decision 7's scheduler will read, and writing it is what turns "correct because of how flecs partitions" into a stated property that survives the executor changing.

**Determinism ([ADR-0010](../adr/0010-deterministic-sim-and-lod-contract.md)): `hashed`** for the capability as a whole. Everything inside a tick is arithmetic over per-entity state with no wall-clock read, no shared accumulator and no worker-count-dependent ordering; slots come off a LIFO free list outside the parallel phase. One worker and eight produce identical bytes, and so do two runs — asserted, not assumed.

## The LOD policy

The tier itself is `sim::TierAssignment`'s — the minimum over observers of f(distance, importance, weight), with the hysteresis band and the rate limits the engine's reference implementation already gets right. What belongs to this capability is the *bands* and what each tier *costs*:

| Tier | Divisor | Cross-fade | Skinning matrices | Pool slot |
|---|---|---|---|---|
| LOD0 | every tick | blended | yes | held |
| LOD1 | every 2nd tick | **off** (a cut at the fade's midpoint) | yes | held |
| LOD2 | every 4th tick | off | **no** | held |
| LOD3 | never | — | no | **released** |

The bands are tunables (`animation.lod.near/mid/far/hysteresis`, 250 / 1000 / 3000 **reference metres**), and since A44 they are not plain distances: a host's importance carries how many pixels the actor's limbs travel through the view's lens, so a band of `D` metres is a threshold of `1000 / D` pixels of limb travel — 4, 1 and 1/3 of a pixel by default. "The LOD policy: what the eye can see", below, derives each and says what they come to at the owner's target. Until A44 they were 12 / 40 / 120 m of plain distance, which froze a deer at 40 m on a 2160-row screen where its legs still swung twenty pixels. `animation::lod_tier()` is the single-entity form of the same rule, and the test pins it against `sim::TierAssignment::tier_of` band by band so the two cannot drift.

**Interpolation is the first thing to go, not the sampling rate.** At LOD1 a character is a few pixels across; the cross-fade is invisible long before the halved update rate is, and sampling a second clip is the larger of the two costs. At LOD2 the pose still exists — gameplay reads it for a foot plant, a grab point, a footstep query — and nothing on screen deforms from it, so the matrices are what stop.

**The divisor is staggered by the slot** (`(tick + phase) % divisor == 0`, with `phase` derived from the pool slot), so a crowd at LOD2 spreads over four ticks instead of costing four ticks' work on one of them. Deriving the stagger from the slot rather than from the iteration order is what keeps it identical at one worker and at eight.

**LOD3 freezes the playhead and gives the slot back, and the promotion advances the playhead analytically.** `AnimationLod::frozen_at_us` records the game time at the demotion; the promotion computes where the clip would have got to over the gap in closed form — the same `advance_time` the tick uses, with the whole gap as its delta — and then re-acquires a slot and fills it with the rest pose. A clip's playhead is affine in elapsed time and its wrap is a modulo, so this meets [sim](sim.md)'s summarizer contract *exactly* rather than approximately: equivalence, determinism from stated inputs, idempotence over a partition. That is why LOD3 can be "not animated" rather than "animated cheaply" — nothing pops in time on the way back.

**How tiers reach the capability.** `AnimationSystem::hooks()` is a `sim::MaterializationHooks` row for `sim::SimScheduler::add_hooks`: `materialize`, `promote`, `demote` and `dematerialize` all go to one function, so the scheduler-driven path and a game calling `set_tier` directly cannot behave differently. Promote/demote are idempotent and the tests drive both paths.

**What a coarsened instance draws is the *renderer's* question, and the answer is the rest pose at LOD2 as well as at LOD3.** At LOD3 there is no choice: the pool slot is released, `joint_run` answers false, and the renderer reads that absence as "this instance draws its rest pose" ([renderer](renderer.md#skinned-instances)). At LOD2 the slot is still held and its matrices simply stop being rebuilt, so a consumer that handed them over would draw the character frozen at whatever pose the last LOD1 tick left. `engine-view` hands a zero-length run instead, and a game should. Three reasons, in the order that decided it: it is what LOD2 already *means* here — the pose exists for gameplay and nothing on screen deforms from it, and a stale pose is deforming from it; keeping the last pose makes what is on screen depend on *when* an instance was demoted, so the same character at the same distance differs between two runs and between two cameras, and this project compares captures byte for byte; and at LOD3 keeping one would mean the renderer holding a private copy of every frozen instance's matrices, which is the pose pool rebuilt on the far side of the boundary that exists to keep poses off it. What it costs is measured — see the boundary table below, where the LOD2/LOD3 switch costs **nothing at all** precisely because both sides draw the same pose.

**And which name each hook carries is the contract's, not this capability's choice.** `materialize` is handed the record's persistent `Id128`, resolves it through `ecs::entity_for`, and answers with the `sim::EntityHandle` for the entity it found — this capability attaches a pose to an entity that already exists rather than bringing one into being, so a record naming nothing this world holds gets a null handle and `reconcile_tile` skips it rather than promoting into nothing. `promote`, `demote` and `dematerialize` read their handle with `ecs::entity_of` and keep nothing ([sim](sim.md), "Which name each hook carries"; [ADR-0028](../adr/0028-ecs-and-persistent-store.md) seam 3).

## The LOD policy: what the eye can see

**An actor keeps animating as far as it can be seen to move** (roadmap A44, 2026-11-14; `include/systems/animation/visibility.h`). The owner, walking the forest's animals at 3840 × 2160: "i can see them run away without animating clearly and when i get close enough they do start animating". The bands were 12 / 40 / 120 m of plain distance, and past the middle one an actor draws its rest pose; the forest measured a flying raven's pose hash constant from 45 to 100 m. A distance cannot be right for a bird against the sky and for a crowd of characters, nor for 1080p and a surround, so the tier is now chosen by **how many pixels the actor's limbs travel on the screen**.

**The measure.** A tier past the middle band draws the rest pose ("What a coarsened instance draws", above), so the error it makes at a vertex is that vertex's displacement from rest, and the largest such displacement over the clip is a number this module already computes for the cull pass: `clip_displacement_bound`, the instance's `bounds_padding`. Times the instance's scale it is the **travel** `b`, in world metres. Through a view whose lens is `p` pixels a radian (`renderer::View::proj_scale`, cot(fov_y / 2) × rows / 2 — what the cull pass bounds a cluster's screen error in), it subtends `b × p / d` pixels at distance `d`. The rule is a threshold on that, and it folds exactly into the tier code's importance:

```
importance = (b / 1 m) × (p / 1000 px) × bias            (animation::motion_importance)
score = d / importance < D   ⇔   b × p × bias / d > 1000 / D pixels
```

So **the bands stay metres and mean one thing**: the distance at which a reference actor — limbs that travel one metre, seen through a lens of 1,000 pixels a radian (a 1080-row view at 56.7°) — crosses the band. The hysteresis, the rate limits and the observer set are `sim::TierAssignment`'s as before; only the importance changed. The host computes it (`view_importance` in engine-view's `anim_lod.h`, below): per view that contains the instance's padded sphere, its weight times its lens, the best of them, times the travel and the bias. Off screen it is a constant, `k_offscreen_importance` = 1/400, whatever the travel or the bias, since nothing off screen crosses a pixel: sampled for its pose within 7.5 m, frozen beyond — where the old 1/16 against 12 / 40 / 120 m put it.

**Why these thresholds.**

| Band | Boundary | Pixels of travel | What is lost past it, and why that many pixels |
|---|---|---|---|
| `near` | 250 m | **4** | LOD1: the pose is held two ticks (30 Hz) and a cross-fade cuts at its midpoint. A limb swinging through `A` pixels at a cycle of `f` Hz moves at most 2π f A / 60 pixels in the extra tick; at 4 px that is 0.41 px at a walk's 0.97 Hz stride and 0.59 px at a run's 1.40 Hz ([gait grounding](../experiments/gait-grounding-2026-11-04.md): Perry's free walk, 1.41 m at 1.37 m/s; Cavanagh & Kram's run), and 1 px only at 2.4 Hz. 8 px would put a run's held step over a pixel. The fade's cut is at most the travel, once per fade. |
| `mid` | 1000 m | **1** | LOD2: the rest pose is drawn. Every vertex is within the travel of where the true pose has it, so under a pixel of travel nothing on the screen moves by a pixel between the two; over it, a limb crosses pixels and its stillness reads. This is the band the owner saw. |
| `far` | 3000 m | **1/3** | LOD3: the playhead freezes and the slot is released. Both sides draw the rest pose, so the picture cannot tell; the band decides how far a gameplay query still finds a pose, and keeps the old ratio of three to the middle band. |

**What they come to.** At the owner's target, 3840 × 2160 per view at the renderer's 55° (2,074.6 px a radian), an actor whose limbs travel half a metre — a deer's legs, a person's — is animated every tick to **259 m**, skinned to **1,037 m** and keeps its playhead to **3,112 m**; at 1920 × 1080 each halves, and on a surround each monitor is its own lens (the side monitors' weight divides it as `--peripheral-lod` says). A bird whose wings travel 0.3 m is skinned to 622 m at 2160 rows; one that a game biases by 4 to 2.5 km. The rule moves with the projection: the same actor at the same distance is twice the pixels at twice the rows, which `visibility_tests.cpp` and engine-view's `anim_visibility_view_tests.cpp` hold (the bar at 100 m: LOD2 at 540 rows, skinned at 1080).

**A per-actor bias** multiplies the importance: above 1 for an actor conspicuous beyond its travel (a bird against the sky, a flag), below 1 for one not worth its pixels (a prop's idle), 0 for the coarsest tier always; at most 64 (`k_lod_bias_max`). A scene authors it on an instance's block, `"animation": {"clip": "fly", "lod_bias": 4}` (`engine.scene.Animation` version 2); a game module sets it at run time with `actor_lod_bias` (hotload ABI 11, [apps](apps.md#actors-the-characters-a-game-moves)). A value outside [0, 64] is refused, not clamped.

**What any asset gets, and what nothing costs.** The travel is measured from the asset's own skin and clip — the per-joint influence spheres of its mesh and the clip's keys — so an imported glTF gets the same rule as a generated one, with no list of species, sizes or names anywhere in the engine: what was run is the end-to-end case above, a skinned glTF written at test time with its own clip (`bend`), measured at 2.12 m of travel at scale 1 by the same bound the cull pads it with (a two-metre bar whose tip turns a quarter turn), and at 7 % of its size 100 m away it is 0.77 px of travel at 540 rows (LOD2, its rest pose) and 1.54 px at 1080 (skinned). Every other clip an actor's skeleton has is measured at the load, when engine-view binds a game's actors (`clip_travel` in engine-view's `animation.cpp`, from `GameActors::bind`), against the same spheres, so a game's `actor_play` reads a number and never measures one ("What a clip's first play costs", below). A skin with no clip has no travel and sits at the coarsest tier, which draws what it draws anyway: its bind pose. A scene with no animated instance has no rows and pays nothing; one that has them pays one multiply a row a step over what the tier code already did, and the budget's pass below when a ceiling is set.

## What a clip's first play costs

**Nothing on the frame's thread** (roadmap A47, 2026-11-15). Before, it cost the forest's walk frames of 8.1 and 5.3 s at the start, 2.4 to 2.6 s twice near half a minute and 0.3 to 0.8 s between, to about 70 s (the owner's run, 416 animals; the forest's `engine-needs` 101 and 124). The game module's meter put the time in `actor_play`; the renderer's record of those frames was a few milliseconds, and a clip's second play was free.

**The cause.** `GameActors::play` sets the actor's tier row's travel (`set_travel`, A44), and `clip_travel` measured a clip the first time any actor played it — `clip_displacement_bound`, on the frame's thread, once per library clip (the result is cached in `AnimatedScene::clip_travel`, so 416 animals do not multiply it; the number of distinct clips does, every species' every clip, and each one's size). The bound is the largest displacement over a set of evaluation times, and the set was **every track's key times back to back** (`anim::Clip::times`, not deduplicated) plus a 64-point grid. An exporter keys every track at the same times — Blender's glTF exporter bakes every channel at every frame — so a clip with a translation, a rotation and a scale track per joint evaluated each distinct time three times per joint: 6,836 evaluations for a 37-joint two-second clip at 30 keys a second where 126 are distinct. And each evaluation samples every track, whose key is found by a walk from the front (`locate` in `domain/anim/src/clip.cpp`), so the measurement was quadratic in the tracks and in the keys at once: `animation.travel.joints` doubles the rig and quadruples the time, and the keys are between linear and quadratic.

| `animation.travel.*` (`msvc-release`, one clip) | Before | After | |
|---|---|---|---|
| `joints/23` (two seconds) | 25.7 ms | 0.95 ms | ×27 |
| `joints/37` (a bird of the forest's roster) | 66.3 ms | 1.42 ms | ×47 |
| `joints/74` | 268 ms | 2.89 ms | ×93 |
| `keys/31` (37 joints, one second) | 26.5 ms | 0.91 ms | ×29 |
| `keys/61` (two seconds) | 66.1 ms | 1.58 ms | ×42 |
| `keys/121` (four seconds) | 188 ms | 2.17 ms | ×87 |
| `keys/241` (eight seconds) | 580 ms | 6.99 ms | ×83 |

Medians of three repeats, 2026-11-15, i9-10980XE, the same tree before and after the change. **Upper bounds**: the harness found other processes at 100 % of the CPU at both runs (`--wait-quiet=60` timed out; about ten agents were building), and the GPU lock held by another agent on the second. So the forest's seconds are what a few dozen to a hundred clips first played in one tick cost — at the start every species' first clips, then a species at a time as its animals come near — at 66 ms for a bird's two-second clip and more for a longer one or a bigger rig. (Its rigs' exact sizes were not read here; the forest's notes give its birds 37 joints and seven clips each.)

**What changed, and why the answer did not.**
- **Each distinct time is evaluated once** (`clip_displacement_bound`, `library.cpp`): the times are sorted and the repeats dropped before the walk. The bound is a maximum over the poses at those times, and a maximum over the same set is the same float whatever its order and however often a member repeats (no NaN enters it: `std::max(out, NaN)` keeps `out`), so this moves the cost and not one bit of the answer. `travel_tests.cpp` keeps the old walk as a reference and holds the new one to it **to the bit** on clips of every shape a file carries — baked, sparse (every track its own times, where nothing repeats), step, cubic, keys that start late, a single key — at grids of 0, 7 and 64 points, and on the Khronos Fox's three clips where the samples are fetched; an `--animate` pair of 400 Foxes on main's build and this one gave all 400 instances the same `travel_m` and the same pose hash.
- **And every clip an actor can play is measured at the load** (`GameActors::bind`): for each actor in declaration order, every clip of its skeleton not yet measured, against the actor's own mesh — the same call `play` made, so the same number. It logs `actor clips measured at load` with the count and the milliseconds, **at info on the category `view.anim`**, which engine-view's stderr shows only under `--log view.anim=info` (or `--log info`): by default stderr carries warnings and up, which is why the forest session's log never held the line (2026-11-16). The same two numbers are in every run's summary, the animation block's `clips_measured` and `clips_measured_ms` (`engine.scene.FlythroughAnimation` version 3). A play is now a read of the cache. Where two meshes share a skeleton the first actor in declaration order's mesh measures a clip, where before it was the mesh of the first actor to *play* it — the same where each skeleton has one mesh, as every file this engine has loaded does, and now a function of the scene rather than of the game's first moves.

**Why at the load and not at the content build**, which would be first choice: a `.clusters` container carries a skin's bindings but neither its skeleton nor its clips (engine-view refuses to animate one and asks for the glTF), and the travel is a property of the (mesh, clip) pair — the mesh's per-joint spheres and the clip's keys — read from the glTF at load anyway. After the change the load pays about 1.5 ms a two-second clip of a 37-joint rig: a roster of twenty species with seven clips each is about 0.2 s of a load the forest measures in minutes. Not on a worker either: nothing then has to stand in for a measurement that has not landed.

**What any asset gets, and what nothing costs.** Any skinned glTF with clips, imported or generated, gets the same: no list of species or sizes. A scene with no game actors binds none and measures nothing more than it did (its instances' own clips, at the attach, as before, and those 27 to 93 times faster). A clip whose tracks each have their own times has nothing to drop and still costs its tracks times its keys in evaluations, but at the load, not in a frame. A game with a thousand species of long clips pays their measurement once, at the load, single-threaded; the job pool is where it goes when that matters.

**Not done, and not measured.** The tick's own sampler walks a track's keys from the front too (`locate`, "a handful of keys"): for an eight-second baked clip that is up to 240 compares a track at the end of the clip, every sample of every LOD0 actor — a cost per tick this row did not measure and left alone (`domain/anim` is not this capability's). The forest's frames were not flown on this branch (the machine had about 14 to 27 GB of free commit against the 40 a load needs).

## The budget

**When more actors want the finest tiers than the frame pays for, the ones the rule ranks first keep them** (`animation::cap_tiers`, `TierBudget`). Two ceilings: `animation.lod.full_max` (default 256) actors at LOD0, and `animation.lod.skinned_max` (default 1,024) at LOD0 and LOD1 together; 0 is no ceiling. A row wants LOD0 when its score is under the near band — or, already there, under it widened by the hysteresis, the band the tier code itself keeps it in — and a skinned tier likewise against the middle band. The wanting rows are ranked by score, which is distance over pixels of travel, so **the nearest and the largest on screen rank first**; an incumbent's score is divided by the same widening, so two actors at the margin hand the tier over once, not every step. The first `skinned_max` keep a skinned tier and of those the first `full_max` LOD0; each one held back has its importance lowered so its score lands just past the widened boundary (×1.0625), and the tier code's own hysteresis and rate limits move it like an actor that walked away. Deterministic (a sort by score, ties by row), allocation-free once the host has sized its scratch at attach, and O(n log n) in the rows that want a skinned tier.

**What fell back is reported**: the most actors any step held at LOD1 that wanted LOD0 (`fell_back_full`) and at LOD2 that wanted a skinned tier (`fell_back_skinned`), with the ceilings in force, in the summary's `animation` block (`engine.scene.FlythroughAnimation` version 2), and per instance the travel and the bias the rule read (`AnimatedInstance.travel_m`, `.lod_bias`).

**Why those ceilings.** What each tier costs an instance is this module's bench ("Performance notes", below). Taken again for A44 (2026-11-14, `msvc-release` at v3, one worker, 10⁴ instances of a 23-joint skeleton, three repeats; the box was loaded — other processes at 95 % of the CPU — so these are **upper bounds**): **2.83 µs** an instance a tick at LOD0, **1.39** at LOD1, **0.49** at LOD2 and **0.012** at LOD3. So 256 actors at LOD0 and 768 more at LOD1 are at most 0.72 + 1.07 = **1.8 ms** of a 60 Hz step, about a tenth of a frame, and the rest of a crowd costs tenths of a microsecond each. A game whose rigs are heavier, or whose frame is lighter, moves them.

**What the rule costs, measured as a pair** (2026-11-14; main's release engine-view at 0aa8e44a against this branch's, both copied out of their trees, back to back in one lease of the GPU lock). The machine was shared — other processes at 81–97 % of the CPU and the GPU busy at both ends of every run (`machine_state`) — so every figure is an upper bound and the pair's differences are what it is for.

## The renderer contract

`AnimationSystem::joint_matrices()` is every animated instance's bone matrices as **one contiguous span**, in slot order, of `anim::JointMatrix` — three `Vec4` rows, 48 bytes, the record `deform.slang` mirrors. An instance's own run is `[first_joint(slot), first_joint(slot) + joint_count(slot))`.

What a renderer does with it:

```cpp
gfx::DeformDesc desc;
desc.flags       = gfx::k_deform_skin;
desc.joint_count = animation.joint_count(instance.pose_slot);
desc.joints      = upload_address + animation.first_joint(instance.pose_slot) * sizeof(anim::JointMatrix);
```

One upload per frame for the whole population rather than one per instance — which is why the pool's slots are a shared arena — while `DeformDesc::joints` is per instance, because two characters share one mesh, one `geometry::SkinBinding` stream and one skeleton and have entirely different poses ([gfx](gfx.md) says the same thing from the other side).

**It is wired up now.** `systems/renderer` takes the span and a `renderer::InstanceJoints` — a `{first, count}` per scene instance — and does the rest: one memcpy into the frame slot's region of a joint buffer, and one pass over its own copy of the deform table pointing each skinned instance's `joints` at its run ([renderer](renderer.md#skinned-instances)). An instance the array does not reach, or whose `count` is zero, **draws its rest pose**, which is what an instance at LOD3 or LOD2 looks like from the other side: the renderer read the absence rather than this module reaching across the boundary to say it.

## The app-side glue

The tick is not the renderer's. A game that animates characters writes the code below, and `engine-view --animate` ([apps](apps.md)) is it, so this is what to copy:

**A host may hand the renderer other matrices than the pool's** (2026-11-01, roadmap P52): engine-view's first-person player collapses its head joint's subtree to the head's position in a copy of `joint_matrices()` made after each step (`AnimatedScene::JointCollapse`, [apps](apps.md#the-players-body)), and hands the frame the copy. Nothing in this capability changed for it: the pool, the pose and every hash a host takes over them stay the capability's, and the renderer's contract — one contiguous span and a run per instance — is the same span length.

```cpp
ecs::SimWorld sim;                          // the fixed step; 60 Hz by default
animation::Library library;                 // the skins and clips of the model files
animation::AnimationSystem animation(library);
library.load_gltf(mesh_path);               // skins become skeletons, curves become clips
animation.install(sim);                     // three systems, three components, once

ecs::WorldCommands commands(sim.world());
for (u32 i = 0; i < instances; ++i) commands.create(entity_id(i));
commands.apply();
for (u32 i = 0; i < instances; ++i) {
  animation.attach(entity_id(i), skeleton_id, clip_id);
  animation.set_playhead(entity_id(i), phase_of(i), speed);   // a crowd, out of lockstep
}

// per frame
sim.step();
for (u32 i = 0; i < instances; ++i) {
  runs[i] = {};
  if (lod_plan(tier[i]).skin) animation.joint_run(entity_id(i), runs[i].first, runs[i].count);
}
frame.joints = animation.joint_matrices();
frame.instance_joints = {runs.data(), runs.size()};
```

**The step is the simulation clock's, not the frame's** (roadmap S87): engine-view steps the world from its session's tick observer, step *k* at tick `k * tick_hz / 60` with the tiers decided from that tick's camera, and a frame only reads the runs — so a window and an offscreen replay of one recording end on the same poses, and `AnimationSystem::player(Id128, AnimationPlayer&)` gives a host the player as it stands for the per-instance clip and playhead hashes its summary carries ([apps](apps.md#animation-in-a-session)). The `// per frame` above is the frame clock of a run with no session, one step a frame. **A game's actors (roadmap S88) are driven through this surface and nothing new**: `play(Id128, clip, seconds, looping)` and `set_playhead` at the tick the module asks, and a stop — which the surface has no call for — as the player's own `weight` faded to 0 and its clip cleared, written back with `ecs::WorldCommands::set_bytes` between steps, since `weight` is what `sample_poses` already blends toward the bind pose by ([apps](apps.md#actors-the-characters-a-game-moves)).

## The app-side LOD glue: what the camera decides

The tier policy above sat unused until 2026-09-18, because nothing told it where the cameras were: `engine-view --animate` attached every instance at LOD0 and left it there, so 1,024 foxes cost **3.3 ms** of CPU a frame for a crowd of which most is a smudge. `engine-view --anim-lod` (on by default) closes that, and the code is `apps/engine_view/anim_lod.h` plus forty lines of `main.cpp` — **this is the pattern a game copies**, so it is spelled out rather than folded in.

**Why it is in the app and not in either module.** The tier is `sim::TierAssignment`'s, the pose is this capability's, and where the cameras are is `systems/renderer`'s — and the renderer must not depend on this capability, on `domain/ecs` or on flecs, while `domain/sim` must not depend on the renderer. The one place the three meet is the host that owns all three. What crosses each boundary is data, and nothing else.

```cpp
// once, when the population is attached: the rows the tier code scores
for (u32 i = 0; i < instances; ++i) {
  row_instance.push_back(i);
  positions.push_back(world_centre_of(i));                 // the instance's bounding sphere
  radii.push_back((mesh_radius(i) + bounds_padding(i)) * scale_max(i));   // padded, as the cull is
}
tier_state.resize(rows, 0);                    // attach() put every one of them at LOD0
params = view::scaled_tier_params(animation::tier_params(), lod_scale);

// per frame, before the tick
view::build_observers(renderer.update_views(camera), camera, observers);  // one per view
view::view_importance(views, positions, radii, importance);               // what the camera says
changes.clear();
tiers.assign_tiers({positions, importance, tier_state}, observers, params, changes);
for (const sim::TierChange& c : changes) animation.set_tier(entity_id(row_instance[c.index]), c.to);
sim.step();
```

**Since A44 the importance is the pixels of travel** ("The LOD policy: what the eye can see", above): `view_importance` takes each row's travel and bias beside its position and radius, and a view that contains the row contributes its weight times its lens; the scale (`--anim-lod-scale`) still multiplies the bands. The budget runs between the importance and the assignment (`update_animation_lod`: a score per row, `cap_tiers`, then `assign_tiers`), on scratch sized at attach. The paragraphs below are the frustum gate's, which did not change but for the off-screen constant.

**One observer per view, and the frustum gate is importance.** `sim::ObserverSet` gets one observer per view of the `ViewSet`, at that view's eye and with that view's weight — the centre monitor 1, the side monitors `1 / ViewQuality::lod_scale`, which is the same knob `--peripheral-lod` already uses for geometry, because a player who has said the sides are worth a quarter of the detail has said it about the animation too. Today every view of a `ViewSet` shares one eye, so that set is degenerate and the minimum over it is the distance over the largest weight; that is not worked around, because it is the shape a split-screen or co-op layout fills with two genuinely different eyes and everything above keeps working. What a *view* is worth therefore reaches the entity through its **importance**: the best weight among the views whose frustum contains its padded bounds, over the best weight in the set. Importance divides the distance, so a character only a side monitor can see scores four times as far away and coarsens sooner, which is exactly the owner's "the side monitors are peripheral vision".

**Off screen is `k_offscreen_importance` = 1/400 (1/16 before A44's bands), not infinity.** The cull pass already knows exactly what was drawn — one frame late and on the device ([renderer](renderer.md), "The renderer never reads a buffer back inside a frame") — and a tier that lags the camera by a frame pops on every cut. So the glue runs its own conservative frustum test on the CPU, six planes against one sphere per instance, against `SceneRenderer::update_views(camera)` so the frusta are **this** frame's. The sphere carries the instance's `bounds_padding`, so a limb that swings out of the rest-pose sphere still counts as on screen, which is the same direction the cull pass errs in. A factor rather than infinity because infinity would pin a character standing two metres behind the camera — about to be turned back towards — at the coarsest tier, where 1/16 lets it sit at LOD2 and keep the pose a foot-plant query may ask for.

**The changes go through `set_tier(Id128, u8)` and not through the hooks table.** `sim::MaterializationHooks` speaks `sim::EntityHandle`, only `domain/ecs` may make one, and `<flecs.h>` does not belong in `apps/` ([ADR-0028](../adr/0028-ecs-and-persistent-store.md) seam 5). Both paths go to one function here — see "How tiers reach the capability" — so the demotion still releases the pool slot and the promotion still advances the playhead analytically; the `Id128` overload exists for exactly this caller.

**What it is worth, measured.** 1,024 Khronos Foxes, 3840×2160, `--orbit 22 --no-vsync`, 300 frames, `msvc-release` on the RTX 5090, every row taken twice. `tick` is the world's fixed step — the sampler, the skinning matrices and the per-instance `joint_run` — and `lod` is the tier assignment in front of it.

FLIP calls about **0.1** the threshold at which a person starts to notice a difference, so the worst of the three is a tenth of that and the first is a hundredth. The LOD1/LOD2 step is the whole of the visible cost, which is the honest reading: that boundary is where a character stops moving, and `animation.lod.mid` (40 m of observer score) is what decides where it happens. The LOD2/LOD3 step is free *by construction* — both draw the rest pose, see "What a coarsened instance draws" — and that is the point of the decision rather than a coincidence.

**Why there are `Id128` overloads of `attach`, `play`, `set_playhead`, `joint_run` and (read-only, since S87) `player` at all.** `<flecs.h>` belongs to `domain/ecs`, `systems/` and `game/` (AGENTS.md, [ADR-0028](../adr/0028-ecs-and-persistent-store.md) seam 5) and `apps/` is deliberately not on that list — so a host outside `systems/` would have had to break the seam to attach a single character. The four overloads resolve the id through `ecs::IdentityMap` exactly as `set_tier(const Id128&, u8)` already did, and between them they are the whole of what such a host needs. They are also the vocabulary seam 3 asks for: an id that survives a tick, a save, and the wire.

**The bound a renderer needs, and why this module computes it.** A skinned instance is culled by its mesh's **rest-pose** cluster spheres, and a skinned vertex is not in them, so the renderer wants one number per instance saying how far skinning can move a vertex ([renderer](renderer.md#bounds-the-cluster-spheres-are-the-rest-poses-and-a-skinned-vertex-is-not-in-them)). That number is a property of a clip and a mesh, and the renderer has neither a clip nor a skeleton, so it lives here: `joint_influence_bounds` takes a mesh's positions and its binding stream and gives each palette slot the bounding sphere of the vertices it actually influences, and `clip_displacement_bound` maximizes `|(A - I) c + t| + ||A - I|| r` over every joint and every sampled phase of the clip. It is conservative for every vertex and any weights.

Both halves of that shape were measured rather than reasoned about. Bounding each joint by the *mesh's* own sphere instead — the obvious simplification — asks how far the tail joint would move a vertex at the nose, and gives the Khronos Fox a padding of 249 units on a mesh of radius 82. Splitting the inequality into `||A - I|| |p| + |t|`, which has the appeal of not needing the mesh at all, is looser again: a rotation about a joint a hundred units up the rig carries a hundred-unit translation that the centre term exists to cancel. The per-joint form gives the Fox 49.3 and RiggedFigure 0.48 on 0.83.

The sampling is every keyframe time of every track plus a uniform grid. That is exact for STEP and LINEAR tracks — slerp runs along the geodesic between two keys, so the displacement a joint induces is largest at an end of the interval — and dense-but-not-proven for CUBICSPLINE, the one glTF interpolation that can overshoot its keys. The test measures the truth by brute force at 997 phases and checks the bound against it: conservative, and 1.38× the measured worst on the fixture rig.

## The clip library

`Library::load_gltf(path, prefix)` reads every skin and animation of a glTF or GLB file through [assets](assets.md) and turns them into `anim::Skeleton`s and `anim::Clip`s. Skins become skeletons **in palette order**, because a vertex's `geometry::SkinBinding` names a palette slot and those bindings live in mesh streams this capability does not own; a palette that is not parent-before-child is therefore refused with a sentence rather than sorted ([ADR-0017](../adr/0017-no-hidden-limits.md): stated, not hidden). `assets::load_gltf` sorts the node array that way and every exporter writes the palette in node order, so this has not been seen in practice. Authored `inverseBindMatrices` win over recomputed ones, as [anim](anim.md) says they should. An animation is matched to the skin most of its channels land in; a channel that lands in none is counted in `LoadStats::skipped_channels` rather than dropped silently.

A **`weights` channel** is the one channel that is not matched against a skeleton at all: it drives a run of the mesh's morph channels rather than a joint, so it becomes an `anim::WeightTrack` on the clip ([anim](anim.md), "Morph weight tracks") and `assets::AnimationChannel::morph_channel` says where in the mesh's channel array it starts. One consequence is worth knowing: a clip may consist of **nothing but** weight tracks — a facial performance over a body pose another clip owns — so the "an animation with no tracks is not a clip" test looks at both arrays. The weights reach a renderer the way the joint matrices do, as a plain span the caller owns; `Clip::sample(time, pose, weights)` fills both in one walk. **And a clip needs no skeleton at all when it drives only weights.** A file with no skin but with weight curves — every Khronos morph sample is one — loads, and an animation none of whose channels lands in a skin's palette becomes a **skeleton-less clip**: `ClipAsset::skeleton` is `Library::k_not_found`, `joint_count` is zero, and its joint channels (a node that is no joint) are counted as skipped as they would be beside a skin. Before the samples went through it the library refused a skinless file outright and skipped such an animation whole, weight tracks included, so `engine-view --morph-animate` had nothing to play on any of them ([apps](apps.md), "The morph samples, end to end"). A file with neither a skin nor a weight curve is still refused, with the same sentence; `animation library: morph-weight curves load with no skin, as a skeleton-less clip` pins both.

### Non-joint ancestors

**A joint's rest is its node's transform composed with every non-joint node between it and its nearest joint ancestor — or, for a root joint, the scene root** (S92). That is what glTF means by a joint's world transform, and Blender writes it routinely: the joints sit under an `Armature` node that is not itself a joint, and that node carries a transform. The library used to parent a root joint to nothing and copy its node's local transform alone, so the Armature was lost; the game's cat, whose Armature is translated +0.375 m on y, stood buried by exactly that much, and its walk's root-translation track — authored relative to the Armature — was wrong by the same amount. A non-joint node *between* two joints was lost the same way, and the child became a root.

**Where the ancestors go.** The skeleton keeps the skin's joints and nothing else, because the palette is the vertex bindings' and cannot grow, so the chain is **folded into the joint's own local transform** — at bind (`Skeleton::local_bind`) and in every clip's tracks for that joint, at load. The alternative, a per-skeleton root-transform chain evaluated after every sample, was rejected because `anim::Clip` addresses joints only and every consumer of a pose (the sampler, the blends, the displacement bound, `muscle_sim`, a host's own `local_to_model`) would have had to learn to apply it; folded at load, everything downstream sees ordinary joint data and nothing changed past the library. A joint's parent is its nearest **joint** ancestor, through any non-joint node.

**An animated ancestor moves the skeleton.** A channel on an ancestor node is read into the joints it moves rather than counted in `skipped_channels` (and it counts toward the skin a clip is matched to, so a clip that only slides the Armature is still a clip). Per joint and per channel — everything moves a translation, since an ancestor's rotation and scale carry the child's offset; only a rotation moves a rotation, only a scale a scale:

- **nothing on the chain animates** (a still Armature under a walk's root track — the cat): the joint's own keys are mapped one by one through the chain's rest, `fold_keys`. A translation is offset and rotated, a rotation multiplied, a scale scaled; a cubic's tangents go through the linear part alone. Exact, interpolation kept.
- **one track moves the channel and it is of the channel's own kind** (the Armature's translation track, the joint's translation fixed): the same key-by-key mapping of that track, because the composed channel is an affine function of it. Exact.
- **anything else** (two animated inputs, an ancestor's rotation carrying an offset): `resample_keys` samples the chain through `anim`'s own interpolation at every key time of every input and at `k_resample_steps` (4) points inside each interval — none for STEP — composes it, and writes a LINEAR (or STEP) track. Exact at its keys; between them a chord of the true path: the test's intervening node turning a 0.5 m offset a quarter turn in one second is off by 9.6 mm between keys and 0.13 µm at them. Real clips have keys 1/24 to 1/30 s apart, where the chord is far shorter.

**The fold does no arithmetic it does not need**, which is how every existing rig loads unchanged: an identity ancestor (the existing fixture's `rig` node) returns the child exactly, and a pure translation adds and does nothing else — `core/math`'s `compose` would renormalize a product with the identity and rotate a zero vector, and either can move a last bit. TRS composition is exact for an ancestor of uniform scale; a non-uniformly scaled ancestor over a rotated child is a shear no TRS holds and is approximated by multiplying the scales, as `compose` always did.

**The mesh node's own transform is not applied**, deliberately and consistently with the importer: a skinned primitive stays in bind space and glTF places it through its joints alone ([assets](assets.md#skins-and-animations)). The inverse binds are the file's, as before. Where they include the ancestor (Blender's usually do), the rest skinning matrix is the identity and the mesh stands where its author put it; where they leave it out, the rest pose lifts the mesh by the ancestor — and the bounds padding covers that: `skeleton_displacement_bound` now starts from the rest pose's own displacement instead of zero, and `clip_displacement_bound` samples clamped rather than looped, so the clip's **last key** — a clip held at its end stands on it, and a loop wraps it to the first — is evaluated too (it used to be missed; the "slide" fixture's end is 8 mm past its 63/64 sample).

**Tested** in `tests/ancestor_tests.cpp`, over `tests/ancestor_glb.h`: the two-bone bar under an `Armature` translated +0.375 m, written at test time in the original and the **normalised** form the game rewrote its files into (an identity Armature, the translation moved into the root joint and its keys). The rest pose's lowest vertex is at exactly +0.375 (it was 0); "rise" (the Armature 0.375 → 0.875) and "slide" (the root 0 → 0.5 over a still Armature) lift it along the track; the two forms' skeletons are equal and their pose hashes (`tests/pose_hash.h`: the three channels and the skinning matrices, at eight times including the tip's slerp interval and a loop) **equal to the bit** for both clips; "both" (the two tracks at once, resampled) within 1e-6 m (measured 0); a non-joint node between the joints is folded into the child and its animated rotation turns the tip; the padding covers the posed bar at 997 phases of each clip, including the 0.375 at rest; and the two forms walked through the same LOD tiers (0 → 1 → 2 → 3 → 0) give bit-identical bone matrices at every tick. The existing fixture's hashes are pinned (`a rig with an identity ancestor poses exactly as before the fold`), taken before the fold existed, at times that keep out of a slerp interval so they pin this module and not a C library's `acos`. Run against the library without the fold, the new cases fail where they should: the rest at y = 0, the clips not lifting it, the two forms' hashes apart, the ancestor's channels counted as skipped.

**Ids are a pure function of the asset's name**, `"<prefix>/<name>"` hashed, so the same content gives the same ids in every process and on every machine and a save written by one build resolves in the next. **The prefix defaults to the file's *stem*, never its path** — a path would put "D:/work/tree/rig.glb" in the id and make every save unloadable on another machine. Two files with the same stem and a skin of the same name collide, and the answer is to pass a prefix, which is why the parameter exists.

**The standard-skeleton mapping is computed once per skeleton, at load.** `anim::map_joints` is three passes of normalized string matching over every joint; per instance or per retarget it would be a load cost paid every tick. `Library::build_retarget(from, to)` pairs two of the library's skeletons through those mappings.

## The procedural gait

**A walk and a run generated for any skeleton in the standard skeleton's roles** (`gait.h`, `src/gait.cpp`; roadmap C60, 2026-11-04). The owner's authored bodies have no walk clip (C57's is a content job), and a retarget of RiggedFigure's would slide, because the retarget does no foot locking ([anim](anim.md), `standard_skeleton.h` "What this does not do yet"). A gait built from the literature gives every rig a walk and a run at load, and is the fallback an authored clip replaces. The numbers and their sources are on [the grounding page](../experiments/gait-grounding-2026-11-04.md); what follows is the rules.

- **The curves.** Each driven joint's angle over the cycle (0 to 1 from the right heel strike) is a five-harmonic Fourier series (`gait_curve`), least-squares fitted to a periodic shape-preserving cubic through the published peaks at their phases — sagittal hip, knee and ankle from Winter and Perry & Burnfield for the walk and Novacheck for the run, the arms from Murray et al. 1967 — and the pelvis's rotation, obliquity, tilt, rise and sway and the trunk's counter-rotation as one sinusoid each (Kadaba et al. 1990, Perry, Saunders et al. 1953). The coefficients are a table in `gait.cpp`, a source per row. **The band rule**: the amplitudes are fixed per band at the band's reference speed (walk 1.37 m/s, run 3.2 m/s); the speed sets the stride and the clip's duration and nothing else.
- **The rotations are built about the body's axes and carried into each joint's rest frame.** The axes come from the rig: up from the feet to the hips, right from the left hip to the right one, forward their cross product — so a rig that stands up only through a transformed ancestor (RiggedFigure's `Z_UP`) still swings about its own axes. A body-frame turn `q_b` becomes the joint's local rotation `rest_local * (W⁻¹ q_b W)`, `W` the joint's rest rotation in model space; composed down the chain, that turns each joint about the body's axes as its parent has carried them, so the knee bends about the swung thigh's lateral axis. **The clip is a deviation from the rest pose**: an A-pose rig swings its arms from the A. Flexion is positive about the right axis for the hip, the ankle (dorsiflexion), the shoulder and the elbow, and negative for the knee, which bends backward; `gait_tests.cpp` holds both on RiggedFigure's posed joints against its own rest. The left side is the right half a cycle later; the arms swing against the legs of their side.
- **In place**: no forward root translation. The hips carry the pelvis's rise and sway in their parent's frame, converted to the rig's units by `GaitParams::metres_per_unit`. A caller drives the playhead by distance — phase = distance over `GaitCycle::stride_m` — which is what keeps the feet from sliding (engine-view's player does: [apps](apps.md#the-procedural-gait)).
- **The stride** (`gait_stride_m`): the walk's is Grieve's power law (stride ∝ speed^0.42) in the Froude form `stride/L = A (v/√(gL))^0.42`, calibrated at Perry's free walk (1.41 m at 1.37 m/s, L = 0.93 m), so a longer leg strides further and steps more slowly at one speed; the run's is speed over a stride frequency of 1.40 Hz on the reference leg (Cavanagh & Kram 1989), scaled by √(0.93/L). The leg length is measured from the joints (`gait_leg_length_m`: the hips' height above the feet over Winter's 0.491/0.530).
- **The roles** (`gait_mapping`): `anim::map_joints`' names where they hold the hips and both legs, else completed from the rest pose — the first joint with two parallel child chains of three or more running away from a third (or downward), the leg on the model's −x side the right (glTF's front faces +z), the third child's chain the spine and chest and its branch's side chains the arms. RiggedFigure maps one role by name and 18 by shape. A rig that still lacks the hips or a leg is refused with the roles named.
- **One cycle at 60 keys a second**, LINEAR, the last key the first again (the loop closes exactly), one track per driven joint (rotation) plus the hips' translation. Deterministic — fixed-step sampling, one operation order, two runs the same bytes — but **not bit-portable**: the curves go through the C library's `std::sin` and `std::cos` in double, which are not correctly rounded, so a different C library may move a key by an ulp. No test pins a literal hash of a generated clip; the keys are held to `gait_curve` in double within 0.05° (measured 1.5e-5° on RiggedFigure).
- **Not done** (each a stated simplification): no foot IK — plan 05 §5.15's "Procedural animation and IK" row, and what a speed outside the stride relation, a slope or a turn needs; no turning or slope adjustment; no stochastic variation; no jump or crouch. `Library::add_clip` is public for it: a clip made elsewhere is added as a loaded one is, its id `clip_id(name)`.

## Graphs (S35 stage 1)

**State machines as data, driving the player that already exists** (`graph.h`, `src/graph.cpp`, `schemas/animation_graph.schema`; roadmap S35, 2026-11-18; the design and its grounding: [animation graphs](../experiments/animation-graphs.md)). Stage 1 of six: machines whose states are single `Clip` nodes. No pose is computed by the graph yet; it decides which state each machine is in, and the state is played into the entity's `AnimationPlayer`, so `sample_poses` runs unchanged and a stage-1 graph's pose is, to the bit, the pose of the `play()` calls it stands for.

- **The records** (`animation_graph.schema`, a file of the capability's own): `engine.animation.Graph`, and as its children `GraphParam`, `GraphMachine` (its `GraphState`s and `GraphTransition`s as its children) and a state's pose as its one child `GraphNode`. A transition's conditions are `GraphCondition` values (`param op value`, all must hold). No `materialize` declaration: a graph is an asset entities refer to. `read_graph(document, id, desc, why)` reads one from a `doc::Document` by each record's `$type`; `GraphDesc` is the same records as plain data, which is also how a host builds one in code (`locomotion_graph`, the walker's).
- **The compile** (`compile_graph(desc, library, out, why)`), once per graph: parameters in id order (a parameter's index is its slot in `AnimationGraphInput.values`); per machine its states in id order, each state's outgoing transitions a contiguous run sorted by `(priority, id)`, and the machine's `any` transitions a run of their own evaluated first; every condition a `ControlCondition` (8 bytes), every transition a `ControlTransition` (16), a machine a `ControlMachine` (16). With a library every clip a state names must be in it, refused by the graph's, the state's and the clip's names. **Refused by name**, each with the stage that takes it (the list as of stage 2; stage 3 took the layers, and its list is in "Graphs: layers and masks" below): `Override` and `Additive` nodes, a node outside a state's pose or a `Blend1D`'s inputs, and a node weight other than 1 (stage 3's layers); `Inertialize` (stage 4); and, in no stage of the design yet, the `Machine` kind, `exit_phase`, an offset other than `Zero` (`MatchPhase` waits for clips with foot contacts), `skeleton_roles` and `root_motion`; and the stated limits (ADR-0017) with the count: 8 parameters, 2 machines, 2 sync groups, 16 inputs a `Blend1D`, and 65,535 pose clips a graph — a `Clip` state's one clip counted as a `Blend1D`'s are (b70, finding 6 of the review of batch 69: two machines of `Clip` states could pass it and truncate `PoseState::first_clip`). **The compile is n log n in the records** (b70, the same finding): a state's pose nodes, a node's children and a state's transitions are found by binary search over tables built once (`ByParent`, `ById`), where they were a scan of every node a state and of every transition a state, quadratic in the states times the nodes, and a node's placement a scan of every node a node; the case at the pose-clip limit (two compiles of 65,535 and 65,536 `Clip` states in two machines) runs inside the module's whole suite of 9 s in msvc-debug.
- **The control pass** (`graph_control`, one instance or a span of them): the first tick enters at the entry and takes at once any transition that holds from it, **a cut**; after that the clocks advance (a transition in flight finishes into its state at its duration), and the transitions are evaluated **from the state the machine is heading to** (Unity's "next state" interruption source), an `any` transition never into that state — so a change of mind mid-fade starts a new fade, which the player collapses first, as `play()` does. A taken trigger's bit is cleared. A machine with a `phase_param` copies it, wrapped into [0, 1), as its sync group's phase. Each machine that entered a state returns a `GraphStep` (12 bytes): the state, the blend, the fade, whether it was the first tick.
- **The two components** (persisted, per graph-driven entity): `AnimationGraphInput` (56 bytes: the graph's id, eight values, the trigger bits) and `AnimationGraphState` (72 since version 2: per machine its state and the destination in flight as index plus one, the transition's elapsed and duration, the two clocks; per sync group the phase; and the compiled graph's `revision`). In stage 1 the entity also carries its `AnimationPlayer`, which the steps write.
- **A graph replaced in place restarts its instances** (b70, the review of batch 69's finding 2). `GraphLibrary::add` replaces a graph with the same id in place, and its instances' state indices meant the old compile's states: a smaller replacement was read out of range by the control pass (`find_transition`) and the evaluator (`mark`, which then wrote past the program's codes). Every compile now carries `CompiledGraph::revision`, a hash of its compiled tables (never 0), which `init_graph_instance` and every reset write into the state; `graph_control` resets a state of another graph **or another revision** to "not yet entered" before it reads any index, the evaluator reads such a state as the entry's pose, and `graph_catch_up` leaves it for the next control tick. A hash, not a counter, so a save loaded by a process that compiles the same graph keeps its states; a state of version 1 (revision 0) starts at the entries once. `AnimationGraphState` version 2 only adds the field, so it is declared `@additive(2)` and needs no migration step. Case: `graph_pose_tests.cpp`, "a graph replaced by a smaller one restarts its instances" (the old fault aborts it in a debug build on `Vector`'s index assert; the write past `code_` is a raw pointer that only AddressSanitizer would see in a release build).
- **The host surface** (`AnimationSystem`, by `Id128`): `add_graph` (compile against the capability's library into `graphs()`), `attach_graph`, `has_graph`, `control_graph` (write the inputs, run the pass, return a `GraphEnter` per machine that entered: the state's clip, rate, looping, whether it is phase-locked, the fade) and `apply_graph_step` (play it into the player: `play(clip, fade, looping)` and the state's rate unless it is phase-locked; no clip is the rest pose, at once). **For the walker the control pass is still the host's call**: its one consumer runs where its machine ran, in engine-view's tick observer before a game module's tick, so a module's `actor_play` on the body still overrides it as the hotload ABI promises. The scheduled `animation.graph_control` (stage 2) is for entities that carry no player, and its query excludes the walker's.
- **The walker is the first consumer** (`apps/engine_view/player.cpp`, `PlayerBody::tick_gait`; [apps](apps.md#the-procedural-gait)): `locomotion_graph` — parameters `moving`, `fast`, `phase`; states `stand` (the idle at its own rate 1, or the rest pose), `walk` and `run` (phase-locked to sync group 1); three `any` transitions with the 0.2 s fade — compiled on the body's first walking tick and attached to its entity. What each step plays still goes through engine-view's actors, which keep their own books (the clip's travel for the tier rule, the weight fade from rest, the counts in the summary), and the distance-driven phase still sets both clips' playheads after it. **Every walker hash is unchanged by construction**: `graph_tests.cpp` writes out the machine `tick_gait` had before and drives it and the graph with the same 20,000 random ticks, with and without an idle clip, and the two make the same calls in the same order with the same arguments.

**Memory** (the owner, 2026-11-18: memory at launch is a budget). A graph instance is **128 bytes** (the two components; 120 before the revision, b70). The walker's compiled graph is **1,544 bytes** since stage 3 (1,416 in stage 2, 1,112 in stage 1; stage 3 added 128 bytes of empty layer tables, "Graphs: layers and masks"; `CompiledGraph::bytes()`: the object, its tables at their capacities — stage 2 added the pose states, clips and program, 304 bytes with the object's own growth — and any string too long for its own object; MSVC, msvc-debug, printed by the records case and held under 2 KB), of which the three states' `StateInfo` (a name, a clip name and two ids each) are about a quarter; the library holding it 1,448. A world with no graph holds **nothing**: `GraphLibrary` is an empty vector with no allocation (`bytes()` 0, asserted), no entity carries a graph component, and the only trace is the two component types' rows in flecs' metadata, registered at `install`.

**Cost.** `animation.graph.control/<n>` — the pass over 10³, 10⁴ and 10⁵ instances of the walker's graph whose inputs change every 37 to 194 ticks: at most 41 ns an instance at 10⁴, taken on a loaded machine ("Performance notes").

**Determinism.** `hashed`: compares, adds of `dt` and a floor over each instance's own two components, in instance order, no shared accumulator; one worker and eight over 4,096 instances for 64 ticks give the same bytes (a case).

## Graphs: the pose program (S35 stage 2)

**A state's pose computed by the graph, for entities that carry no player** (`graph.h`'s fourth part, `src/graph.cpp`, `src/animation.cpp`; roadmap S35, 2026-11-18; the design's sections 2, 3 and 5: [animation graphs](../experiments/animation-graphs.md#2-compiled-at-load-into-a-flat-program)). Stage 2 of six. A state is a `Clip` or a **`Blend1D`** of clips by one parameter; a cross-fade is the two states' poses summed by weight; both are evaluated by a compiled flat program, op-major over a batch of instances, as two scheduled systems. **The walker does not move**: its graph has no blend state and still drives its player through stage 1's steps, so every walker hash and pin stands as it was (the brief's rule for this stage: a walk-to-run blend by speed is a test graph's, not the walker's, until the owner sees it).

- **The `Blend1D`** (a `GraphNode` of kind `Blend1D` as a state's pose; its inputs its child `Clip` nodes in the order `inputs` names them, each at its `thresholds` entry, strictly increasing): the parameter (a float) between two thresholds weights the two neighbours linearly and every other input 0; at or beyond an end, that end's clip alone. This is Unity's 1D blend tree, whose manual draws each motion as a pyramid peaking at its threshold, "its animation weight is 1 and the other animations have a weight of 0" (*Blend Trees: 1D Blending*, read 2026-11-18). `(p − t) / (t′ − t)` is exactly 0 or 1 at a threshold, so a blend at a threshold **is** that clip. Its inputs take their looping and sync group from it (a mismatch is refused); 16 inputs at most (a stated limit, refused with the count); a blend of blends is refused (no stage builds it yet).
- **Sync groups.** A `Blend1D` (or a `Clip`) with `sync_group` 1 or 2 is **phase-locked**: every clip samples at the group's phase × its own duration — normalized time, which Unity's manual gives as the reason clips of different lengths blend when their foot contacts sit at the same normalized times ("the left foot hits at 0.0 and the right foot at 0.5", *Blend Trees*, read 2026-11-18). The phase is the machine's `phase_param` (stage 1's distance drive), or, **new in stage 2, led**: each control tick it advances by `dt × rate / duration` of the group's clip of highest weight over the state the machine is in and the one it is heading to (Unreal's rule: "the animation with the highest blend influence is considered the leader", *Sync Groups*, read 2026-11-18; a tie goes to the first in the program's order). The same page warns of play-rate "pops" when the leader changes between clips of very different lengths; that is the rule's and is kept, since normalized time keeps the contacts aligned through the switch. A group none of whose clips plays keeps its phase.
- **The blend is the normalized weighted sum**, never a slerp chain: each quaternion is multiplied by the sign of its dot with the sum so far and added with its weight, translations and scales added with theirs, and the sum normalized once — rotations to unit length, translation and scale over the weights' sum. That is ozz-animation's blending job (`blending_job.cc`, read 2026-11-18: the sign of `Dot(out, in)`, `out + rotation * weight`, one `NormalizeEst` at the end, translation and scale times `1 / accumulated_weight`), with an exact `sqrt` and divide where ozz estimates. Why not slerp: slerp is not commutative, so a chain of them depends on the order the inputs are mixed in, while the normalized sum (nlerp) is commutative and torque-minimal and costs no transcendental function; Blow's *Understanding Slerp, Then Not Using It* (read 2026-11-18, its Table 1) recommends it for systems that blend more than two animations, and pays for it with a speed along the arc that is not constant — inside a two-clip blend a rotation's angle follows the weight a little off linearly, symmetric about the midpoint, where the two agree (both bisect the arc; a case holds the midpoint of the identity and a quarter turn to its closed form within 1e-6). The sum's order is the compiled program's, so the bits do not depend on anything else.
- **The program** (`GraphOp`, 16 bytes): per state of machine 0, in index order, a `Sample` (the rest pose, then the clip at the state's clock × its rate, or the group's phase × its duration) and an `Accumulate` into the output — or for a `Blend1D` a `Sample` and an `Accumulate` per input into a sum register, a `Normalize` of it and an `Accumulate` into the output — then the output's `Normalize`. Three registers: 0 is the instance's own pool slot (so nothing is copied out), 1 a clip's sample, 2 a blend's sum. **The first contributor to a register is a set (`dst = w × a`), the rest are adds, and a normalize runs only over two or more**: so a state with no transition in flight, or a blend at a threshold, writes its one clip with a multiply by exactly 1 and no normalize, and is that clip's pose to the bit (a case at four times, both ends, beyond an end and at an inner threshold). A graph of two machines compiles its control tables and no program unless one of them is a layer (stage 3, below; `CompiledGraph::program_why` says so and `attach_graph` refuses it); so does a state cross-faded into itself (two copies of one state on one clock).
- **Evaluation** (`PoseEvaluator`, one per worker): per batch of `animation.graph.batch` instances (64), each instance's ops are marked from its state alone — which apply, as a set or an add, with what weight or time; the two states visited in index order so a sum's first contributor is the program's — and then, **op by op, the compacted list of the instances the op applies to and the op's kernel over it**, chosen once per op per batch from a table indexed by its kind (plan 11 §11.4). An op that applies to nobody costs a scan of the batch's codes. The pose pass keeps no state between ticks: the pose is a function of the two components, which is what a save holds.
- **The clocks.** The control pass's clocks are the tick's start (it advances them before taking a transition, so a state entered this tick reads 0); the program shows the tick's end, `clock + dt × divisor`, as a player advanced before it is sampled does, and a cross-fade's fraction is `(elapsed + lead) / duration`. That lead is what makes **a stage-1 graph run through the program the pose its player gets**, at every tick with no cross-fade in flight (a case over 600 random ticks, 414 of them compared to the bit); during a fade the program's sum and the player's slerp differ by the arc's speed above.
- **The scheduled systems.** `animation.graph_control` runs the control pass for each graph-driven entity its tier updates this tick, over `dt × divisor`, on the inputs gameplay last wrote into its `AnimationGraphInput`; `animation.graph_sample` gathers the same entities into batches of one graph and one skeleton and runs the program into their slots, before `build_skinning_matrices`. The scheduler owns the tick: nothing about a graph-driven entity is called by a host on the world's behalf. **Host surface**: `attach_graph(entity, graph, skeleton)` (the instance, its slot at the rest pose, LOD0, the graph's components; refused for an entity with a player, a graph with no program, an unknown skeleton), `set_graph_inputs(entity, values, triggers)`, `graph_state(entity, out)`. `apply_graph_step` refuses a `Blend1D` state: a player plays one clip.
- **LOD** (design section 5, the stage-2 part; the per-tier programs and the shared pose are stage 5's): the tiers are A44's and the plans `lod_plan`'s. LOD0 evaluates every tick, cross-fades interpolated; LOD1 every second tick with a cross-fade **cut at its midpoint** (`LodPlan::interpolate`, as a player's is) and the blend kept (a blend is the state's motion, not a transition); LOD2 every fourth tick, sampled and not skinned; **LOD3 evaluates nothing** — no control, no program, no matrices: the slot is released, and what is held is the two components (120 bytes), `SkeletonInstance` (40) and `AnimationLod` (16), **176 bytes**. The promotion advances its machines' clocks, a transition in flight and a led phase over the gap in closed form (`graph_catch_up`; no transition is taken in the gap), and lands where ticking would have, to the bit (a case over 97 frozen ticks).

**Memory** (the owner's budget at launch). Per graph-driven instance at LOD0–2: the components 120 B, `SkeletonInstance` 40, `AnimationLod` 16, and the pool slot a player's instance has too — 88 B a joint (40 of pose, 48 of matrix), **2,024 B** for a 23-joint rig, plus its 16-byte slot record: **2,216 bytes**, 56 more than a player's (whose `AnimationPlayer` is 64). Nothing per instance is kept between ticks for the program. Per graph: the walker-shaped two-state blend graph of the cases compiles to **1,432 bytes** with its 9-op program (1,560 since stage 3's empty layer tables) (the program 144 of them; MSVC, msvc-debug). Per worker: the evaluator's scratch, `(registers − 1) × batch × joints × 40` bytes of registers plus 9 bytes an op an instance of marks — **about 121 KB** at a batch of 64, three registers and 23 joints, grown once and never shrunk, so a steady tick allocates nothing. A world with no graph-driven entity holds none of it (the scratch is created on a worker's first graph batch).

**Cost.** `engine_animation_bench.exe --filter=animation.graph.* --wait-quiet=1200`, msvc-release, 2026-11-18 17:29: the harness waited its 20 minutes and never found the machine quiet (others at 100% of the CPU, the GPU lock held by another row, session unlocked), so every number is an **upper bound**. The program's rows run the two-state graph of `bench/animation_bench.cpp` over the 23-joint crowd rig, states made by 40 control ticks and frozen, most instances in a two-clip `Blend1D` (Bollo prices a 1D blend space at two sequences and a blend), a few percent mid-fade (both states):

An instance's program is about two clip samples — 2.4 times the 1.6 µs one sample cost on a quiet machine ("Performance notes"), the blend's add and normalize included — and the control pass beside it about 1.5% of that. The batch makes no difference at 23 joints on this machine under this load (within the runs' 1–6% spread), so the default stays the design's 64 (177 KB of registers in L2 at three registers; 118 KB here, register 0 being the slot); a quiet run, and a 74-joint rig, are what would move it. 10⁴ graph-driven instances at LOD0 do not fit a 60 Hz tick single-threaded any more than 10⁴ players do; the tiers are what make a crowd affordable, as for players.

**Determinism.** `hashed`, the design's section 3. Every op is per-instance arithmetic in the compiled order — `+ − × ÷ √` and the sign of a dot product, contraction off tree-wide ([ADR-0035](../adr/0035-no-floating-point-contraction.md)), no C library call (the sampler's `slerp` inside a key interval is `anim`'s, named by the design and unchanged) — over the instance's own input, state and slot, so the pose depends neither on the batch, the worker count nor the order instances are visited in. **Cases**: one worker against eight, two runs, and a batch of 7 against 64 give the same matrices and graph states over 96 instances for 48 ticks (with LOD1 instances and fades among them); and **the pin** — a `Blend1D` of the fixture's two clips at weights 0.25, 0.5 and 0.75, not looping, at one second, where both clips sit on their last key and the sampler takes no slerp — hashes to `2432560345335567898` (pose and skinning matrices; **taken on MSVC alone**, msvc-debug at x86-64-v3, 2026-11-18; GCC and Clang are the stack's containers to confirm).

## Graphs: layers and masks (S35 stage 3)

**A graph's second machine applied over its first** (`graph.h`'s fifth part, `src/graph.cpp`; roadmap S35, 2026-11-18; the design's sections 1, 2 and 5: [animation graphs](../experiments/animation-graphs.md#stages-in-build-order)). Stage 3 of six. **The walker does not move**: its graph has one machine and its crouch and head-look stay engine-view's model-space layers; what a host would call to move them is written as a hunk for a later row in [the design page](../experiments/animation-graphs.md#the-use-it-is-for-the-walkers-crouch-and-head-look).

- **The records.** A machine is a **layer** when it has a child `GraphNode` of kind `Override` or `Additive` (its *layer node*); the graph's other machine is the base. The node carries `weight` (in [0, 1]), `param` (a float parameter the weight is multiplied by each tick, the result clamped to [0, 1]: Unity's layer weight a script sets, here a parameter gameplay writes), `mask` (a `GraphMask` by name; empty: every joint at 1) and, for an additive, `reference` (below). `GraphNode` is version 2 (`mask` and `reference` added, declared `@additive`, so a version-1 record reads them empty). `GraphMask` is a new child record of the graph: `name` and `joints`, each a `GraphMaskJoint` — `joint` (a standard-skeleton role name, `Neck`, `Head`, ..., resolved through `anim::map_joints`, else a joint's own name), `subtree` (its descendants too), `weight`, and `depth`.
- **A mask is compiled once per skeleton** into two runs of joint indices: the joints at weight 1, then those strictly between 0 and 1 with their weights (`GraphLayer`, 24 bytes, its runs in `CompiledGraph::layer_joints`/`layer_weights`). A joint in neither is **never read or written** by the layer op, which is what makes "outside the mask, the base to the bit" true by construction rather than by arithmetic. A joint two entries reach takes the larger weight. **The edge** is Unreal's *Blend Depth* (*Animation Blueprint Blend Nodes*, "Layered blend per bone", read 2026-11-18: "A Blend Depth of 0 will apply a blend weight of 1 to the Bone Name and all connected child bones", a positive depth tapers it through the chain, a depth of 2 giving the bone 0.5 and the next child 1): the joint `k` generations below the named one gets `min(1, (k + 1) / depth)` of the entry's weight. Unity's *Animation Layers* (read 2026-11-18) says only that a mask "specifies the body parts on which to apply the animation"; Unreal's *Blend Masks* give a bone 0 to 1, "a value of 0 will cause no animation to play on that bone, and a value of 1 will cause animation to play at 100% value", and say nothing of what is between — the rule below is ozz's.
- **The program** gains two ops and stays flat: the base machine's states into register 0 and its normalize; the layer machine's states, by the same Sample/Accumulate/Normalize, into the **layer register** (2 with no `Blend1D` in the graph, 3 with one, so a layered graph has three or four registers, as the design allows) and its normalize; then **one layer op**, `Override` or `Additive`, reading the layer register and writing register 0 over the mask's joints. The op's per-instance code is 0 at a weight of 0 (or NaN), 1 at exactly 1, 2 between; **a layer at weight 0 is not evaluated at all**, its machine's samples included, so a layer that is off costs the marks and nothing else.
- **Override** at `t` = the weight × the joint's mask weight: the normalized weighted sum of the base at `1 − t` and the layer at `t` — ozz-animation's blending job with per-joint weights (`blending_job.cc`, re-read 2026-11-18: a layer's joint weight is `layer_weight * Max0(joint_weights[i])`, the sum divided per joint by the accumulated weight), with the base's weight the complement so the two sum to 1. That is **how a weight below 1 normalizes against the base**: the base keeps what the layer does not take, and nothing goes to the rest pose (ozz's rest pose fills only when the accumulated weight is under its threshold, which a complement never is). At code 1 the mask's full joints are a **copy** of the layer's, so an override at weight 1 with a full mask is the layer to the bit.
- **Additive.** The layer's pose is a difference from a **reference pose**, formed per joint as ozz's additive builder forms it (`additive_animation_builder.cc`, read 2026-11-18): translation `l − r`, rotation `conjugate(r) · l`, scale `l / r`; the reference is the skeleton's rest pose with the clip `reference` names sampled at its first key over it — ozz's default reference is the first key, and Unreal's aim offsets take "Selected animation frame" at "Ref Frame Index 0" (*Aim Offset*, read 2026-11-18) — or the rest pose alone when `reference` is empty (a zero or non-finite reference scale is refused, the scale being a quotient). It is applied as ozz's blending job's additive pass applies it: translation `+ d · t`; **rotation composed on the right**, `base · normalize(lerp(identity, ±d, t))`, the difference's sign taken from its `w` so the lerp goes the short way; scale **multiplied**, `× (d · t + (1 − t))`. On the right means the difference turns the joint in its own frame whatever the base did to its parent, which is `anim::blend_additive`'s order too; Unreal's *mesh-space* additive (what its aim offsets use, because a local-space one "can cause the upward-aiming pose to be skewed") is **not built** — local space only. A joint whose layer pose **is** its reference pose exactly is left as the base: that is what an additive of nothing is, and it keeps the bits (the composition would turn a −0 component of the base into +0).
- **What a host calls.** `compile_graph(desc, library, out, why, &skeleton)` — a layered graph compiled without a skeleton compiles its control tables and no program, and `program_why` says so; `AnimationSystem::add_graph(desc, skeleton, why)` compiles it for one skeleton of the library, and `attach_graph(entity, graph, skeleton)` refuses another skeleton (the library keys a compiled graph by its id, so a layered graph serves one skeleton; per-skeleton programs are stage 5's). The control pass already runs every machine; the layer machine's state is the second machine's slot of `AnimationGraphState`, so **a layer adds nothing to an instance**.
- **Refused by name** (the list as of stage 3): an `Override` or `Additive` node anywhere but as a machine's layer node, a mask or a reference on any other node, a reference on an override, a weight outside [0, 1], a weight that reads a parameter that is not a float, a mask the graph does not have or two of one name, a mask entry naming neither a role the skeleton maps nor a joint, a mask that touches no joint, a reference clip the library lacks, a weight other than 1 on any node but a layer node, a layer over no base (one machine), two layer nodes on one machine, both machines layers (a layer of a layer: no stage of the design yet); and from before, `Inertialize` (stage 4), the `Machine` kind, `exit_phase`, the `KeepPhase`/`MatchPhase` offsets, `skeleton_roles`, `root_motion` and a blend of blends (no stage yet). **More than one layer** is the components' stated limit of two machines (ADR-0017), refused with the count: a third machine takes `AnimationGraphState` version 2.

**Memory** (the owner's budget at launch). **Per instance: nothing new** — a layered instance is the stage-2 instance, 2,216 bytes at LOD0–2 for a 23-joint rig and 176 at LOD3 (the layer machine's state is in the 64-byte component already). **Per graph** (`CompiledGraph::bytes()`, MSVC, msvc-debug, printed by the compile case): the head-look override over a one-state base (7 ops, a two-joint mask) **1,552 bytes**; with a three-input `Blend1D` in the layer (13 ops) **1,648**; an additive adds its reference pose, **40 bytes a joint** (920 for 23), and a mask 6 bytes a joint it touches. Every compiled graph grew by **128 bytes** for the layer's tables while empty (the walker's 1,416 → 1,544, stage 2's blend graph 1,432 → 1,560): five empty vectors and the per-machine output arrays, kept inline rather than behind a pointer because a graph is a few per world. **Per worker**: the evaluator's scratch grows with the registers, `(registers − 1) × batch × joints × 40` — at four registers, a batch of 64 and 23 joints **173 KB** (118 KB at stage 2's three), plus 5 bytes an op an instance of marks; grown once, never shrunk. **Beyond its LOD**: at LOD3 an instance holds what it held in stage 2, 176 bytes, and its layer machine's clock is advanced at the promotion by `graph_catch_up` with the base's; at LOD1 and LOD2 the layer is evaluated whenever the program is (dropping a layer marked `detail` at LOD1 is stage 5's).

**Cost.** `engine_animation_bench.exe --filter=animation.graph.* --wait-quiet=1200`, msvc-release, 2026-11-18 20:17: the harness waited its 20 minutes and never found the machine quiet (others at 100% of the CPU, the GPU lock held by another row's tests, session unlocked), so every number is an **upper bound**, stage 2's rows taken in the same run beside them. ## Graphs: inertialization (S35 stage 4)

**A transition that cuts to its target and hides the cut under a decaying offset** (`inertialize.h`, `src/inertialize.cpp`; roadmap S35, 2026-11-19; the sources as read and the curve's derivation: [animation graphs](../experiments/animation-graphs.md#stage-4s-curve-read-and-derived)). Bollo's reason for it: a cross-fade evaluates the source and the target for as long as it lasts, and an inertialization evaluates the source once, at the transition's tick, and from then on only the target. **Built**: the curve, the per-joint offsets, their capture and application, the slots, and `Inertialize` as a transition's blend through the compile, the control pass and the scheduled `animation.graph_sample`. **Not yet: the walker.** Its body is player-driven (stage 1: each step is played into its `AnimationPlayer` through engine-view's actors), and a player has one cross-fade and no offsets, so an `Inertialize` step played that way (`apply_graph_step`) is a cross-fade of its duration; the walker's 0.2 s changes become inertialized only once it is graph-sampled (the design's "What a later row would do", engine-view's ground), and then `animation.graph.inertialize_walker` (off) selects the blend in `locomotion_graph`. No walker or pose hash moved.

- **In the graph** (`graph_control`, `state_weights`): an `Inertialize` transition is held on the machine as a cross-fade whose duration is **negated** — `AnimationGraphState` needs no field for it, and a save keeps it — and the program weighs it as **the target alone** from its first tick (the saving: one state evaluated, not two). It finishes, and is interrupted, as a cross-fade is (`elapsed` against `|duration|`). The compile takes it on a graph's base machine and refuses it by name on a layer machine (the offsets are the base pose's; a layer blends inside the program).
- **In the sample pass** (`AnimationSystem::sample_graphs`): at the transition's first tick (`elapsed` 0) the worker evaluates two more instances through the same program — the source state alone at the tick's lead, and the target one tick back — copies what the pool slot showed one tick back before the program overwrites it, and captures the offsets; the pose shown that tick is the source's. On the ticks after, the target plus the offsets. An interrupting transition's source is the old source state with the old offsets on it, and what was shown carries them too. A slot held with nothing in flight (finished, replaced by a cross-fade — whose offset is then dropped — or at a tier that does not interpolate) goes back. **LOD1's cut**: a tier with `interpolate` off opens no slot and shows the target at once (a case: the same bits as the `Cut` graph at every tick).
- **Its state**: per pose slot an `Inertial` (16 bytes: the arena slot, the skeleton, the seconds since capture, the duration), sized when a graph-driven instance whose graph inertializes is attached or promoted, outside the parallel phase; one `InertialArena` a skeleton. The systems are `multi_threaded`: a row's entry is written only by the worker sampling it, and the arenas' `acquire` and `release` go through one mutex — taken only when a transition starts or ends. A world whose graphs inertialize nothing holds none of it (`inertial_bytes()` 0, a case). **Limitation**: a phase-locked state is sampled at its group's phase, which is not kept one tick back, so its velocity at the capture reads as zero.
- **Cases** (`tests/graph_inertial_tests.cpp`): two graphs, `stand` (idle) and `move` (walk), one with `Inertialize` and one with `Cut` 0.25 s transitions — at the switch the cut's matrices jump by 0.75 where the inertialization's move by 0.0625, as much as the idle's own tick did (it shows the source); a slot is held while it lasts and given back; past the duration the two are the same bits; an interruption four ticks into the way back moves 0.067 where the ticks before it moved 0.066; and at LOD1 the inertialized instance is the cut one to the bit at every tick and holds no slot.
- **Cost**: `animation.graph.transition/{0,1}` — 10⁴ instances of the crowd's graph, a quarter in a 0.25 s transition 0.1 s in, as a cross-fade (both states evaluated) and inertialized (the target and `inertial_apply` over 23 joints) — are built and smoke-run under CTest; **their numbers are owed** (`tools/dev.ps1 bench -Preset msvc-release -Filter 'animation.graph.*'` with `--wait-quiet=600`, the `machine_state` quoted): the row that built them had no quiet hour before the gate.

- **The curve** (`inertial_curve(x0, v0, t, t1)`), per channel along its own fixed direction: the quintic `A t⁵ + B t⁴ + C t³ + a0/2 t² + v0 t + x0` that starts at the offset with its velocity and reaches 0 with zero velocity and acceleration at `t1`, under three rules that are its guard against overshoot — a velocity away from zero is dropped; `t1` is shortened to `−5 x0 / v0` when that is sooner; `a0 = (−8 v0 t1 − 20 x0) / t1²`, the zero jerk at the end, taken as 0 when negative. Under them the offset never crosses zero and never grows past `|x0|` (a sweep of 20,000 random curves); it is exactly 0 at and past `t1`. Computed in f64 in `s = t / t1`.
- **The offsets** (`InertialJoint`, 48 bytes, size-tabled: `dx`, `dv`, `dr`, `dw`): per joint the translation's offset and its velocity, and the rotation's offset `source × conj(target)` on the shorter arc as an axis times an angle, and its angular velocity — all source minus target, the velocities by a backward difference over one tick, so a target that moves is accounted for (Holden's `off_v = src_v − dst_v`). `inertial_capture(source, source_prev, target, target_prev, dt, out)` writes them at the transition's tick; **an interrupting transition passes what was shown as its source**, the old offset included, so the picture carries on without a jump (Holden's `off_x = (src_x + off_x) − dst_x`).
- **The application** (`inertial_apply(offsets, t, duration, pose)`): the translation moved along its direction by the curve of its length and its speed along it; the rotation turned **on the left** (`turn × target`, Unreal's order as read) about its axis by the curve of its angle. Scale is not inertialized (the target's at once). At and past the duration nothing is written, **so the pose is the target's to the bit**.
- **The slots** (`InertialArena`): `joints` entries a slot, handed out last-in first-out like the pose pool's, held only while a transition is in flight; in blocks of 16 slots that **never move**, so a worker's slot stays where it is while another worker acquires one; the block table (4,096 pointers, 32 KB, for the stated limit of 65,536 slots a skeleton, ADR-0017: past it a transition is a cut) is allocated at the first acquire, a block when the arena grows past its most, and its free list is sized for every slot, so a steady stream of transitions **allocates nothing** (a case counts `mem::allocations_on_thread` over 100 rounds of 64). A 23-joint transition holds 1,104 bytes; an arena that never held one holds none.
- **Determinism: portable to the bit.** `+ − × ÷` and `sqrt`, a rotation's angle from `portable_atan2` and back through `portable_sin_cos` (`core/math/portable_trig.h`, moved there for this), never the C library's. The case "the curve and the offsets are pinned" hashes 4,096 curves and a transition's offsets and 16 ticks of its poses; the value was taken on MSVC alone, and GCC and Clang must reproduce it.
- **Cases** (`tests/inertialize_tests.cpp`): the curve starts at the offset exactly with its velocity (a forward difference, held to its own truncation error: the sources state no tolerance) and is exactly 0 at the end and at rest to third order just before it; the sweep above; two moving poses — sliding and turning toward each other — shown at the transition's tick as the source (to a micrometre and a microradian, the poses' f32 rounding), leaving it at the source's velocity (to 2 mm/s over a 1 ms difference) and landing on the target to the bit; a transition interrupted halfway by a second toward a third pose, continuous in value and, to a tenth, in velocity, and landing exactly; the arena's steady state.

## What the contract could not express

This capability was built to find out what ADR-0027's contract is like from the inside. Three things it could not say, recorded here because the next capability will meet them:

1. **A system could not declare that it writes data outside the ECS.** ~~`sim::ComponentMask` addresses components, and "the pose pool" is not one.~~ **Closed, 2026-09-18**: `sim::SystemDesc` carries named resources, the scheduler's wave layering treats a resource conflict exactly like a component conflict, and this capability's third system moved back into `Systems` where it belongs, ordered after `sample_poses` by `animation.pose_pool`. See [sim](sim.md), "Named resources", and "The systems" above.
2. **The materialization hooks and the ECS did not share an identity vocabulary.** ~~`sim::MaterializationHooks` speaks `u64`~~ **Closed, 2026-09-18**: `EntityRecord::entity` is the `Id128` it came off the store with, and `promote`/`demote`/`dematerialize` take a `sim::EntityHandle` — a distinct type, valid only inside the call, which only `domain/ecs` may look inside. This capability's `materialize` hook resolves the record through the identity map and answers with the handle, which is what `reconcile_tile`'s promotions then act on; the other three go through `ecs::entity_of`. See [sim](sim.md), "Which name each hook carries".
3. **A tier is a field, not an index.** [ADR-0028](../adr/0028-ecs-and-persistent-store.md)'s own guard rail says a component the query reads and rejects on is not an index, and `AnimationLod::divisor` is exactly that: every tick, `sample_poses` visits every animated instance and skips three quarters of the LOD2 ones. A tier *relationship* would make each tier its own archetype and the query would iterate only what it should — at the cost of an archetype cross product, and of an archetype move per tier change. That trade is worth measuring once there is a scene with a real tier distribution; it is named here rather than discovered later.

## Invariants (each one tested)

Benchmarks: `tools/dev.ps1 bench -Preset msvc-release -Filter 'animation.*'`; `animation.travel.*` is one clip's travel by rig and by length ("What a clip's first play costs", above).

## Performance notes

`build/msvc-release/systems/animation/engine_animation_bench.exe --filter=animation.* --wait-quiet=1800`. **10,000 instances of a 23-joint skeleton** playing a one-second clip with a rotation track on every joint — the worst case for the sampler and the honest one for a character — through the real `SimWorld` and the real three systems, **single-threaded**.

**Machine state.** i9-10980XE, 36 logical CPUs, release build, 2026-09-18. The harness waited for a quiet machine and the run was quiet at both ends: other processes at 8.3% of the CPU at the start and 8.7% at the end, GPU 1% and 6% ([bench](bench.md#measuring-on-a-shared-machine)). A second run of the tick rows agreed within 1.4% on every row, and is not quoted because it *ended* under load (others at 17.7%) — which is exactly the case that makes a number an upper bound rather than a cost.

| Benchmark | Per tick | Per instance | What it covers |
|---|---|---|---|
| `animation.tick.lod0` | **25.28 ms** | 2.53 µs | 10^4 instances, every one every tick, sampled and skinned |
| `animation.tick.lod1` | **13.08 ms** | 1.31 µs | every second tick, no cross-fade interpolation |
| `animation.tick.lod2` | **4.08 ms** | 0.41 µs | every fourth tick, sampled but not skinned |
| `animation.tick.lod3` | **87.6 µs** | 8.8 ns | nothing animated: the query match and the divisor test |
| `animation.tick.mixed` | **4.48 ms** | 0.45 µs | 5% / 15% / 30% / 50% across the four tiers |
| `animation.pool.churn` | 7.3–7.5 ns | per slot | acquire + release, at 256, 4,096 and 65,536 slots |

> **These are the x86-64-v2 numbers, and the default build is now v3.** The table above was taken
> when the whole tree compiled without an arch flag; since [ADR-0031](../adr/0031-minimum-cpu-x86-64-v3.md)
> (2026-09-19) every preset but the `*-v2` ones is `/arch:AVX2`, and **this module is the one that
> got slower**: `lod0` **25.49 → 29.36 ms (+15.2%)**, `lod1` **13.13 → 15.11 ms (+15.1%)**,
> `mixed` **4.55 → 5.17 ms (+13.6%)**, measured in three sessions that reproduce to under 1% a
> side. `lod2` (−0.5%), `lod3` (+1.3%) and the pool (−0.3%) do not move.
>
> **It is not the sampler.** Dividing the tick rows by their update counts splits an instance in
> two, and only one half moved: the sampler (LOD2, sample and no skin) is **1.658 → 1.651 µs an
> update, unchanged**, while skinning (LOD1 minus LOD2 — `local_to_model` plus
> `skinning_matrices`) is **0.967 → 1.372 µs, +42%**. So the 23 `slerp`s that point 3 below calls
> the expensive half are exactly as fast as they were, and the 46 `Mat4` products that build a
> 23-joint skeleton's skinning matrices are what `/arch:AVX2` made worse.
>
> **Resolved, 2026-09-20 — and the diagnosis in the paragraph above was wrong about the cause.**
> Neither build vectorized the product at all; `/arch:AVX2` made MSVC copy the 4×4 result through
> **32-byte** moves instead of 16-byte ones, which cannot forward to the narrower loads the next
> joint makes of it, and `local_to_model` is a forward pass whose critical path runs through
> exactly those loads. The kernels are now hand-vectorized in 128-bit registers
> ([anim](anim.md#the-matrix-kernels-and-the-avx2-regression-they-used-to-be) has the listings, the
> method and the table), bit-identically to `Mat4 operator*`. Measured directly on the pair, one
> 23-joint instance: **0.985 → 0.587 µs at v2 and 1.322 → 0.744 µs at v3**, so the v3 build now
> costs **23% less than the v2 build did before ADR-0031**. `skinning_matrices` alone went from 20%
> slower at v3 to 1.3% *faster*.
>
> **What is left is `core/math`, not this capability.** `local_to_model` is still 28% slower at v3,
> and 89% of that remainder is `core/math::mat4_from_transform`, which is **+77% at x86-64-v3** and
> which this change does not touch — a second, larger AVX2 regression that was hidden inside the
> +42% above. It is named in anim.md with a bench row to move and is deliberately left to be scoped
> against `core/math`'s whole blast radius.
>
> **The tick rows above have not been re-measured.** They are the 10⁴-instance world, they take a
> quiet machine and half an hour, and the kernel numbers say what to expect rather than what was
> seen: skinning was about 1.0 µs of a LOD1 instance's 2.6 µs, so `lod0` and `lod1` should come
> back near or below their v2 figures and `lod2`, `lod3` and the pool should not move at all.
> Whoever next has a quiet box should take them and replace this paragraph with the numbers.

Five things these say:

1. **The tier mix is the cost, which is the LOD policy's whole claim.** The same population and the same clip cost **25.28 ms** with nothing coarsened and **4.48 ms** at a plausible distribution: **5.6×**, and it is the only reason a crowd of this size is affordable at all. A build where those two rows are close is a policy that is not working.
2. **10,000 characters all at LOD0 does not fit a frame, and was never going to.** 25 ms against a 16.6 ms budget is the honest number to put beside [ADR-0028](../adr/0028-ecs-and-persistent-store.md)'s "simulation LOD stops being an optimization and becomes load-bearing". The mixed row, at 4.5 ms, is 27% of a 60 Hz frame single-threaded — a budget item ([ADR-0018](../adr/0018-frame-budgets-as-merge-gates.md)), not a rounding error, and the thing the rate limits in `sim::TierParams` exist to keep from arriving all at once.
3. **Where the time goes, read off the rows themselves.** LOD2 samples a quarter of the population per tick for 4.08 ms, so a sampled instance is ~1.6 µs; LOD1 samples *and skins* half of it for 13.08 ms, so an instance is ~2.6 µs. The difference — about **1.0 µs** — is `local_to_model` plus `skinning_matrices`, 46 `Mat4` products for 23 joints, which is close to what that arithmetic costs and leaves little to win. The other **1.6 µs** is the sampler, and it is dominated by 23 `slerp`s with their `acos` and two `sin`s: that is `domain/anim`'s code and the first place to look, along with the per-track cursor this module still owes (see "Not yet").
4. **LOD3 is the floor, and it is what "absent capabilities are free" means per tick** ([11 §11.10](../plan/11-performance-principles.md#1110-absent-capabilities-are-free)): the instances exist, the components exist, all three systems are registered and running, and 10^4 of them cost **8.8 ns each** — a query match and a divisor test.
5. **The pool's free list is O(1) and stays that way.** 7.3 ns per acquire-and-release at 256 slots and 7.5 ns at 65,536: flat over 256× the population, which is the property a per-skeleton LIFO list is there for. It is also the number a camera cut across a tier boundary pays per instance, and it is small enough that the rate limits are about the *materialization*, not about this.

**The graph's control pass (S35 stage 1)**, `engine_animation_bench.exe --filter=animation.graph.* --wait-quiet=1200`, msvc-release, 2026-11-18 15:30: the harness waited its 20 minutes and never found the machine quiet (others at 96.4% of the CPU, sixteen agents building, the GPU lock held by another row, session unlocked), so these are **upper bounds**: the walker's graph over 10³ instances **49.2 µs** a tick (median; min 45.9), 10⁴ **409.8 µs** (min 400.8; **41 ns an instance**), 10⁵ **5.02 ms** (min 4.61). Against the 2.53 µs an LOD0 instance's sample and skin cost (above), deciding its state is under 2% of its tick; the pass is per-instance compares over 120 bytes, so it scales with the population and a quiet run should only lower it.

**The number to plan against is the single-threaded one.** [ADR-0028](../adr/0028-ecs-and-persistent-store.md) records that hosting flecs' workers on `core/jobs` currently costs a flat 1.6–2.2 ms a tick, so every worker count is slower than one worker; until that is fixed, a world does not get parallelism from `ecs::set_workers` and this capability's tick is measured without it. Nothing in these systems would stand in the way of it: they are per-instance work over disjoint writes, which is the shape that scales, and the bit-identical worker test says the answer does not change when it does.

**Zero cost when unused ([11 §11.10](../plan/11-performance-principles.md#1110-absent-capabilities-are-free)): no linked code, and no instances.** `ENGINE_WITH_ANIMATION=OFF` (and the minimal presets) drop the module, its schema library, its tests and its bench; the module disappears from `modules.json` and is listed under `disabled_capabilities`. With the capability *in* the build, a world with no `AnimationPlayer` matches no query, allocates no pool and costs three empty query matches a tick.

## Capability contract (ADR-0027)

This is a capability: it was added without editing `core/`, `foundation/`, the render graph, the scheduler, or another capability, and it can be removed from the build the same way. Two things outside its directory did change, both deliberately and both with their own commit: `cmake/EngineModule.cmake` gained the capability graph (`engine_capability_requires`), because anything that ticks depends on `domain/ecs` and that combination did not configure; and `domain/anim` gained non-owning pose views, because a pool could not be the storage its sampler writes into. Both are argued in [plan 02 §2.8.1](../plan/02-architecture.md#281-the-first-capability-built-through-the-contract).

| Registration point | This capability | Status |
|---|---|---|
| Capabilities it requires | `engine_capability_requires(animation ecs)` | declared; off when `ecs` is off |
| Component and event types | `systems/animation/schemas/animation.schema`, `animation_graph.schema` | five components (two a graph's), seven record types (`GraphMask` since S35 stage 3), no events yet |
| Tick scheduler entry | five `sim::SystemDesc` through `ecs::register_system` (two of them a graph's, S35 stage 2) | done |
| Render-graph passes | none | this capability produces a buffer; it does not draw |
| Content-build derived step | none | clips are imported at load, not precomputed |
| Protocol methods | none | the components are already reachable through `world.apply`; a `animation.play` method is a follow-up |
| Tunables | `animation.lod.near/mid/far/hysteresis/max_promotions/max_demotions/full_max/skinned_max`, `animation.graph.batch` | read once per call, never per entity |
| LOD policy | `lod_plan()`, `lod_tier()`, `AnimationSystem::hooks()` | done, over `sim::TierParams` |
| Determinism | `hashed` (the playhead and the pose); the matrices are `derived` | done |
| Zero cost when unused | no linked code, and no instances | done |
| Tests and size table | `tests/animation_tests.cpp`, `tests/lod_tests.cpp`, `tests/size_table.cpp` | 18 cases |
| Bench | `bench/animation_bench.cpp` | 10^4 instances by tier mix |
| Removal proof | `ENGINE_WITH_ANIMATION`, off in the minimal build | works |

**Removing it.** `cmake --preset msvc-minimal` (or `-DENGINE_WITH_ANIMATION=OFF`, or `-DENGINE_WITH_ECS=OFF`, which takes this capability with it) drops the module, its schema library, its tests and its bench; the module disappears from `build/<preset>/modules.json` and is listed there under `disabled_capabilities`. Everything else still builds and passes.

## Not yet

- **Layers and masks as data** ([05 §5.11](../plan/05-simulation.md#511-integration-notes); designed: [animation graphs](../experiments/animation-graphs.md), roadmap S35; state machines, 1D blends and one layer over a base with a mask are built, "Graphs", "Graphs: the pose program" and "Graphs: layers and masks" above, stages 4 to 6 are not, and the walker's crouch and head-look are still engine-view's model-space layers). A player-driven entity still samples one player; `AnimationPlayer::weight` is already the number a layer would carry, which is why it is persisted now rather than added later with a migration.
- ~~**A track cursor.**~~ **Answered another way, 2026-11-16 (A48)**: `anim::Clip::sample` searches a track of more than eight keys instead of walking it from the front, which takes the clip's length off a sample's cost (16.6 to 5.6 us for a 37-joint rig's eight-second baked clip; [anim](anim.md#sampling)) with no state per player. A cursor would still save the search's few compares; nothing measured asks for it.
- **Additive layers.** `anim::blend_additive` and `make_additive` exist and nothing here calls them.
- **IK, foot locking, a contact channel, retarget-driven playback.** `Library::build_retarget` exposes the retarget; no system applies one.
- **Protocol methods.** `animation.play`, `animation.attach` and a query over the library would be a small `register_methods()` — and would now have the `Id128` overloads to call, which is what the host-facing surface above was shaped for.
- ~~**Tiers driven by the camera.**~~ **Closed, 2026-09-18**: `engine-view --anim-lod` (on by default) builds a `sim::ObserverSet` from the renderer's views and runs `sim::TierAssignment` over the animated instances every frame. See "The app-side LOD glue" above for the pattern and the numbers. What is still open there: the crowd's positions are rebuilt once because engine-view's instances do not move, so nothing yet measures the cost of refilling them per tick; the scoring visits every instance every tick, which is 0.04 ms at 1,024 and would want a spatial structure at 10^5; and the tier is still a field rather than a relationship, so `sample_poses` visits the frozen instances too (see "What the contract could not express").
- **A tier relationship instead of a tier field**, once there is a scene whose tier distribution is worth measuring. See "What the contract could not express".
