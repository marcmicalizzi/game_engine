# doc (domain)

**Purpose.** The authoring document model (docs/plan/03-data-model.md §3.2–3.3, ADR-0002): the text-serialized, layered, stable-ID source of truth that humans and agents edit through commands. Everything the engine protocol, the editor, and the MCP bridge will do to a world goes through this module.

**Model.**
- A `Document` is an ordered `Vector<Layer>`, weakest first. `Layer` holds sparse `ObjectRecord`s keyed by `ObjectId` (`Id128`), sorted. `add_layer` appends (strongest) and leaves the edit layer where it was; a fresh document edits its first layer until `set_edit_layer` says otherwise. `remove_layer` takes one off with everything it holds, bringing the edit layer down with it when it was above, and never removes the last one.
- A record with a non-empty `type` (a registered schema struct's qualified name) *defines* the object; a record without a type overrides `properties`, `parent`, or `deleted` for an object defined in a weaker layer.
- Composition: the strongest layer wins per (object, property); the strongest layer that sets a parent wins; an object is deleted if any layer at or above its defining layer tombstones it. There are no other composition operators (no inherits, variants, or references-with-overrides).
- Property values are `JsonValue`s validated against the object's schema type on demand (`validate()`), not on every edit, so partial and in-progress states are representable.

**Composed index.** A `Document` keeps every id's resolved position in the stack and answers `resolve`, `exists`, `is_defined`, `property`, `objects`, and `children` from it. Nothing scans the layers for an id. An entry is the composed parent, the defining layer, the deletion flag, how many layers hold a record, and a 64-bit mask of *which* layers do, so a query visits only those (bit 63 stands for "layer 63 and everything above it", so a deeper stack costs a scan of the tail and nothing else). Beside it are the live object ids, sorted, and a multimap from parent to its live children, each child list sorted, so `children(parent)` is a hash lookup and a copy of *k* ids.

The index is maintained incrementally, not rebuilt: `apply` touches exactly the id its command named, because a command edits one record and a record only ever changes the composition of its own object; `undo`, `redo`, and a transaction's rollback go through `apply`, so they maintain it too; `add_layer` touches the ids of a layer that arrives with records and nothing when it arrives empty; `remove_layer` rebuilds, because every layer index above the removed one shifts. The live list absorbs changes into a pending buffer and folds them in with one merge pass when someone asks for `objects()`, so creating *m* objects in a document of *n* costs `O(n + m log m)` rather than `O(m·n)`. The one way to go behind the index's back is the mutable `layer(u32)` accessor, which marks it for a rebuild on the next query. `validate_index()` compares the maintained index against a linear recomputation and reports every disagreement; it is what the randomized command test checks after every step.

**Reading a few fields of many records.** `type_of(id)` and `parent_of(id)` answer the record's type and composed parent from the index without composing its properties, and `visit_records(id, fn)` hands `fn(layer, record)` every layer's record for the id, weakest first, so a reader that wants three properties of a hundred thousand records composes those three and not a property map per record — what the materialization driver does ([sim](sim.md#the-driver-a-document-through-the-hooks)).

**Tile index.** Beside the composed index, and maintained with it, the document keeps which live objects are in each tile of the partitioned layers' grids: `ids_in_tile(tile)` (sorted, like `children`), `untiled()` (the live objects in no tile, sorted), `object_tile(id)` and `occupied_tiles()`. An object's tile is its **defining** record's — the strongest record carrying a type — under that record's own layer's partition, by `tile_of` (below, "Partitioned layers"): exactly the rule the defining layer's `tiles/<x>_<y>.json` files it by, so "the objects of tile (x, y)" means one thing to the file layout, the index and every reader. An override in another layer does not move an object between tiles even when it sets the position, because the override's record is filed in *its* layer's files by *its* layer's rule; an object whose defining layer has no partition, or whose defining record has no usable position, is untiled. Tiles of layers on different grids share one coordinate space, as they did when readers classified records themselves (the world refuses a document on another grid than its ring, [world](world.md#the-consumers)).

*Why it is here.* A tile's records used to be found by classifying every live record of the document — the materialization driver visited each record's layers and read its position, on every tile pass — so activating one tile of 150 records in a document of 130,500 cost 37–60 ms, the cost that kept a streamed world of 10^5 residents from its budget ([E38](../experiments/e38-scheduled-npcs.md)). The index already knew, for each id, which record defines it and whether it is live; the tile is one more function of the same record, so it is kept where the rest of the composition is, and a tile pass costs its tile ([sim](sim.md#the-contract-as-implemented)).

*How it is kept.* Every path that maintains the parent-to-children multimap maintains it, in the same `touch`: `apply` recomputes the one id its command names (a position change moves it between tiles, a record that loses or gains a position moves it between a tile and the untiled set, a tombstone or a definition in another layer takes it out or files it by the new defining record), so `undo`, `redo` and a transaction's rollback do too; `add_layer` touches the ids of an arriving layer; `remove_layer` and the mutable `layer()` accessor rebuild. `set_layer_partition` changes no record and stamps nothing in the change feed, but re-files the objects the layer defines under the new grid. A tile's list is a sorted vector with a binary-search insert, as a parent's children are; the untiled set is kept the way the live list is — sorted, with a pending buffer folded in one merge pass on the next query — because in a document with no partitioned layer it is every object, and an insertion into its middle per command would make building such a document quadratic. `validate_index()` checks every entry's tile and every tile's list against a recomputation from the layers, and the randomized command test also checks the answers against a `linear_tile` that walks the layers itself. Memory: 8 bytes more per index entry (56 instead of 48) and about 16 bytes per live object in its tile's list or the untiled one.

**Mutation.** Every change is a schema-typed `Command` applied to the document's edit layer: `CreateObject` (type, parent, optional initial properties), `DeleteObject` (drops the definition when the edit layer defines it, tombstones otherwise), `SetProperty`, `ClearProperty`, `SetParent`, `RemoveRecord`, `RestoreRecord`. Strict application checks preconditions (existence, parent existence, cycles) and reports pathed diagnostics; non-strict application is for applying diffs to layers whose base is not loaded, and a `Transaction` takes the same flag, which is how undo, redo, and a merge are written. Every application yields an inverse (`RestoreRecord` of the previous edit-layer record).

**Transactions and journal.** `Transaction` groups commands with an `Attribution` (actor, role, task, rationale, timestamp), records forward and inverse commands, commits as a `Patch` into the document's journal, or rolls back (automatically on scope exit). `undo(patch)` and `redo(patch)` replay inverses in reverse or forwards in order. Patches are schema types and serialize like everything else.

**Write-back commands.** The runtime world writes back to the document through exactly this path and no other: at `TickPhase::Persist`, what systems changed in the fields a type's `materialize` declaration marks `@writeback` becomes one transaction of `SetProperty` commands on the edit layer, in (record id, row) order, attributed to actor and role **`system`**, task `sim.write_back`, with a rationale naming the tick and the counts ([sim](sim.md#write-back)). A session commits it like any other — journaled, saved, undoable — non-atomically, so a record deleted since it was materialized refuses its own command and nothing else. The journal, `doc.journal` and `session.events` then say "the simulation wrote this", which is the whole difference between a write-back and an agent's edit of the same property.

**Diff.** `diff_records(from, to)` is the machine-readable structural diff: one `RecordDiff` per object whose record differs, in id order, saying whether the record was added or removed and otherwise which of `type`, `parent`, and `deleted` changed and which properties were set or cleared (`PropertyChange`, in name order). `diff_layers(from, to)` is that rendered as commands in the same order: whole-record restore/remove where no command expresses the change (an added or removed record, a changed type or deletion flag, a parent override `to` drops), fine-grained `SetParent`, `ClearProperty`, `SetProperty` otherwise. Applying the diff to `from` yields `to` exactly (tested both directions).

**Structural merge.** `merge_layers(base, ours, theirs, [options,] out, error)` (`merge.h`) merges two layers that diverged from a common ancestor, per object and per property — never by text. Objects are identified by `Id128`, so a rename is a property change and a move is a change to one field; neither is a conflict. The two sides' `diff_records` against base drive it, so the diff machinery is not duplicated.

| What the two sides did | Merged layer | Conflict |
|---|---|---|
| changed a property on one side only | that side's value | — |
| changed it on both to the same value | that value | — |
| changed it on both to different values | ours | `PropertyBothChanged` |
| deleted an object, untouched on the other side | deleted | — |
| deleted it on one side, modified it on the other | kept, with the modifications | `DeletedAndModified` |
| deleted it on both sides | deleted (the record is removed if either side removed it) | — |
| created the same id with identical records | that record | — |
| created the same id with different records | ours | `CreatedBothDifferent` |
| reparented so that the merged layer would have a cycle | base's parent | `ParentCycle` |

A side *deletes* an object when its record is gone from the layer or its `deleted` flag went from false to true. Conflicts name the object and the property; `$type` and `$parent` stand for the record's own fields (a schema field name never contains `$`), and the property is empty for a conflict about the whole record. Each conflict carries the three values as JSON, with null for absent. `MergeOptions::prefer_on_conflict` moves the resolution from `Ours` (the default) to `Theirs`, or to `Neither`, which keeps base's value — except for a deletion against a modification, where the modifications win under both `Ours` and `Theirs`, because a deletion never silently destroys the other side's edits, and `Neither` keeps base's record untouched. `applied_ours` and `applied_theirs` count the changes each side got: one per property set or cleared, one each for a changed type, parent, or deletion flag, one for a record added or removed whole, counting for both sides when both made the same change and for neither when a conflict dropped it.

The merged layer takes base's name, role, and storage form, never keeps an empty override-only record (the normalization `ClearProperty` does), and is canonical: with no conflicts, `merge(base, a, b)` and `merge(base, b, a)` write the same `LayerFile` JSON. Cycles are judged against the finished layer, so two reparents that are each fine but together close a cycle are caught, and only a layer merge's own links are visible — the composed document's parents are `validate()`'s question. The merge fails, rather than conflicting, only when `base` itself already has a parent cycle: nothing could be kept from it.

**Not merged.** Spatial collisions (two agents placing overlapping objects) are not merge conflicts; validators catch them after the merge (plan 03 §3.3). A merge never refuses to produce a layer over a conflict, because that would lose the work on both sides.

**Files.** A layer serializes through the generated `LayerFile` schema to canonical JSON with records in id order, so two equal layers produce byte-identical files and git diffs are meaningful. Format pinned by test.

**Store.** `DocumentStore` (`document_store.h`) keeps a document as a directory: `manifest.json` (`DocumentManifest`: name, layer stack, edit layer, `undo_position`), one file or one directory per layer under `layers/`, and `journal.jsonl` (one `Patch` per line). Layer files always hold the current state, so a checkout is readable without replaying the journal, and the journal plus the manifest position make undo and redo survive across processes. Paths go through `io::Vfs`, so documents live under mounts or at native paths. `save` writes only what changed ([Saving](#saving)), also removes the files of layers the document no longer has, and reports what it wrote and removed in a `SaveReport`. **The journal is only ever appended to**: `append_journal(vfs, dir, doc)` — what a session calls after a commit — makes the file hold exactly the document's journal by cutting it in place after the patches it keeps (a redo tail the commit dropped, or a line a process died appending) and appending the new line, where the redo tail used to cost a rewrite of the whole file; it knows where each line ends from the load or its own writes, and writes the file whole only when it knows nothing of it. A last line without its newline is an append that died in the middle — the store writes a line and its newline in one write — and `load_journal` leaves it out: its commit's save never ran. `write_side_file` and `append_side_file` are the same care for the files the protocol keeps beside a document ([protocol](protocol.md#roles-leases-and-proposals)): a whole file replaced atomically and only when its bytes change, an append appended, and a directory made only when a write finds it missing.

**Partitioned layers.** One fixed tile grid is the unit of layer files, streaming, nav tiles, and agent edit leases (plan 03 §3.7). A layer carries its own storage form in a `LayerPartition` — a position property and a tile size — persisted in the manifest and mirrored in the layer's own index, and the two forms sit side by side in one document:

```
layers/<layer>.json              a layer with no partition: one canonical LayerFile
layers/<layer>/index.json        with one: which tile holds each record, and the grid
layers/<layer>/tiles/<x>_<y>.json   a LayerFile restricted to that tile's records
layers/<layer>/untiled.json      the records with no position (factions, quests, canon facts)
```

A record's tile is a function of the record alone: its position property, floored by the tile size, on the horizontal plane — x and z of a three-component position, y being up as `core/math` has it. It never depends on the other layers, on load order, or on what was on disk before, which is what makes the form canonical: the same document content always writes the same set of files, with the same bytes.

**Far from the origin** ([ADR-0053](../adr/0053-world-positions-are-f64-and-the-gpu-sees-none.md)). A property value is JSON, so a position in the document has always been f64; what is new is that the types that hold one say so (`worldpos`, [schemas/README.md](../../schemas/README.md#worldpos-dvec3-and-vec3-which-one-a-position-is)), so validation reads it as three f64 inside the cells' range and nothing on the way to the runtime world narrows it. The tile is `floor(x / tile_size)` in f64 (`tile_floor` in `partition.cpp`). **For a power-of-two size — 32 m and 64 m, every size in use — that is exact**: dividing by a power of two moves the exponent and nothing else, so a record 1/1024 m either side of an edge 420 km, 10,000 km or 1e8 m out is in the tile it is in, which float32 could not even represent (both sides are one float there). **For any other size** the quotient is rounded once by IEEE division and then floored: a function of the two doubles alone, the same on every toolchain, so the files stay canonical — but a position within one rounding of an edge can fall on the other side of the real edge (1.0 on a 0.1 grid is tile 10, where 1 / 0.1000000000000000055… is 9.99…). An exactly-corrected floor was considered and not taken: it would put that record in tile 9, which is the double's arithmetic and not what the author of "0.1" meant. A position past i32 tiles (2³¹ × the size) is untiled, never wrapped. Saving writes each number as the shortest decimal that reads back to its double (core/json's writer, `std::to_chars`), so **a tiled layer far out is the same files with the same bytes on every toolchain**. `partition.h` reads a position from `[x, y]`, `[x, y, z]`, an object with numeric `x`/`y`(/`z`), or a transform with a `position` or `translation` member. Which property carries it is either named in the partition — the reproducible form, since it depends on nothing outside the document — or, when the name is empty, taken from the record type's first `position` or `transform` field as the schema registry reports it, which is how a type opts in; a record with no type, or one whose type declares neither, goes to `untiled.json`.

Saving after a transaction rewrites only the tiles that changed — the tiles its records were and are in, and `index.json` when one of them changed tiles; a tile with no records left has its file removed ([Saving](#saving)). `repartition` converts a layer between the two forms and removes the files of the old one. None of this reaches above the file layer: the journal is per document, undo and redo replay commands, and a partitioned layer is an ordinary layer in memory that diffs and merges like any other (a merge takes base's storage form along with its name and role).

Loading checks the layout rather than trusting it, and names the file in the message: a tile listed under the wrong name, a record the index files elsewhere, records out of id order, tiles out of (x, y) order, a tile file the index does not list, an `untiled.json` the index does not expect, a partition the manifest disagrees with, and — the check that makes the layout a fact about the records rather than a convention — a record whose position does not fall in the tile it is filed under.

**What a load refuses from a directory someone else made** (T187, from [T13's reading](../experiments/fuzzing-design.md#what-the-reading-found); `session.open` loads any directory a client names). A single-file layer's `file` is held to the rule `doc.place_asset` and `doc.put_blob` hold a client's path to (`stays_under_document`: relative, no drive or stream, no `..`, no empty name, no control character, `\` a separator everywhere), and one it refuses is never handed to the file system: the message names the layer, so a manifest naming `../../x.json` learns nothing of the disk, where it used to read the file outside the document, or answer "not found" against a parse error with the native path. Links inside the directory are not followed to check (`resolves_under` is the blob store's; a proposed row). And a **`$parent` cycle is refused at load**, naming an object on it: the index, `children`, the materializer's parents-first walk and flecs' `ChildOf` all assume a forest, which only `validate` checked before. Each live object is settled once (a hash map of the ids, O(n)). Cases: `hostile_store_tests.cpp`.

**Validation.** Unknown types; overrides for objects no layer defines; objects defined in more than one layer; missing parents; parent cycles; unknown, transient, or ill-typed properties (checked by deserializing each value into a scratch instance of the type). Diagnostics are `<layer>/<id hex>/<property>`.

**Leases and proposal layers are the protocol's.** Plan 06 §6.5's leases, roles and proposal promotion live in `domain/protocol` ([protocol](protocol.md#roles-leases-and-proposals), [ADR-0039](../adr/0039-leases-and-proposals-beside-the-document.md)), because what they guard is the protocol's writes: this module still knows nothing of owners, leases or promotion, and a proposal is an ordinary layer of role `Proposal` here. What they take from it: the tile grid, through `position_property(type, partition)` and `tile_of_position` (`partition.h`) — the same rule as a record's own tile, applied to an object's **composed** position, because a lease on a tile means the objects standing in it and an override that sets only a colour still changes one of them — and `merge_layers`, which promotion runs with a base of the target's records as the proposal first touched them.

**Blobs and checkpoints** are below ([Blobs](#blobs), [Checkpoints](#checkpoints)): bytes a property names by their SHA-256 instead of holding (plan 03 §3.2), and the document's history as commits of its own git repository (plan 03 §3.3, 06 §6.4).

**Not yet (v0).** The tile grid is the document's file layout, the unit of leases, and — through the tile index — the unit the runtime world streams the document by; nothing pages a tile's records in or out of memory yet. A single-file layer that changed is serialized and written whole, whatever part of it changed: the format is one JSON document, so a layer that many edits touch belongs in tiles. A merge is between layers, not between document states, and it does not rebase a journal. A partitioned layer is loaded whole — there is no "open these tiles and not those" yet, which is what leases and streaming will need. Loading one gathers every tile's records (and the untiled file's), sorts them by id once and sets them in order, so each is an append; set one at a time in tile order, each landed in the middle of the layer's sorted map, which was quadratic and took 45 s for the 130,500 records of the npc capability's 10^5-resident world, against 3.8 s now ([E38](../experiments/e38-scheduled-npcs.md#save-size-and-load-time-at-105)). A record in two tile files is found as two equal ids side by side and refused at the later file. At that size the document in memory is the larger problem: about 1.5 KB a record, composed JSON. A save is all or nothing against a process that dies ([below](#a-save-is-all-or-nothing)), not against the power going: nothing is flushed to the device (no `fsync`, no `FlushFileBuffers`), as nothing was before, because a flush costs milliseconds a file here and an editor that loses its last second of work to a power cut has lost what a journal would have lost too.

**Performance notes.** This is the editing path, not the frame loop. The runtime world is a materialization of the document plus persistent state (plan 03 §3.4); the document itself is optimized for diffability and correctness. `bench/doc_bench.cpp` measures the composed index against the linear composition it replaced, over 1k and 100k records in a two-layer stack, plus what maintaining it costs an `apply` and what building a tile index costs. Measured on one Windows development machine (msvc-release), 100k records:

| | linear | indexed |
|---|---|---|
| `objects()` | 58.3 ms | 1.89 ms |
| `children(parent)`, per parent | 111.1 ms | 102 ns |
| `resolve(id)`, per object | 565 ns | 600 ns |
| `property(id, name)` | 295 ns | 322 ns |

The two big wins are the two that were quadratic: `objects()` resolved every id to test liveness, and `children()` walked the whole document for one parent. `resolve` and `property` are a wash, and honestly so — over a two-layer stack the index replaces two `FlatMap` binary searches with a hash lookup into a 100k-entry map and one or two of the same searches, and `resolve`'s cost is dominated by composing and allocating its property map either way. The index earns its place there by being O(1) in the depth of the stack rather than O(layers), and by making `exists()` and `is_defined()` — which every strict command calls — a single hash lookup instead of a full compose with an allocation. Maintaining it costs a `SetProperty` 722 ns at 100k records (294 ns at 1k). The tile index adds nothing measurable to a command that moves no record between tiles (`doc.apply.set_property`, 0.695 → 0.706 µs at 100k), and 0.09–0.13 µs to one that does (`doc.apply.move`, a record of a partitioned layer to another of sixteen tiles: 1.26 → 1.39 µs at 100k, 0.69 → 0.78 µs at 1k), the defining record's tile read again and a sorted insert into the new tile's list (2026-09-25, msvc-release on the i9; [E38](../experiments/e38-scheduled-npcs.md#what-the-index-costs-the-document)). `build_layer_index` over 100k records is 17.7 ms, which is a save's cost, not a query's.

## Saving

**A save writes the files whose bytes change and nothing else, and what it leaves on disk is byte for byte what writing every file would have left.** Two things decide what it writes, and neither is the disk:

- **What changed**, which the document keeps: `Document::changes(layer)` is a `LayerChanges` per layer — the ids a command edited in that layer since the last save (`apply`, and so undo, redo and a rollback, note the id in the edit layer), or `whole` when the store must look at every record: the layer arrived (`add_layer`), changed form (`set_layer_partition`), or was handed out through the mutable `layer()` accessor, after which nothing can say what changed. A successful save clears them (`clear_dirty`); `dirty()` says whether any layer changed.
- **What is there**, which the store keeps (`StoredState`, private to the module and held by the document): the native directory it describes, every document file it wrote or read with its length and a 64-bit hash of its bytes, and each partitioned layer's index as filed with where it files each id. The journal is not in it; it is only appended to.

The rules follow from those two. A layer with no changes is not visited at all — not serialized, its index not read, the file system not asked. A single-file layer that changed is serialized and written if its bytes differ. In a partitioned layer, each changed id is looked up where the kept index files it and where its record belongs now (`tile_of`: a function of the record alone), and those tiles — and `untiled.json` — are serialized and compared; the kept index is updated in place, not rebuilt from the whole layer (a debug build checks it against `build_layer_index` after every save), and `index.json` is written when a record changed tiles; a tile left without records is removed. A layer marked whole is serialized in full and each of its files compared, so an edit through the mutable accessor rewrites the files it changed and not the others; its old form's files and the tiles it no longer has are removed. The manifest is compared like any file: it changes when the undo position, the edit layer or the stack does. Because a file is written only when its canonical bytes differ from the ones there, a transaction that sets a value to itself, a rolled-back one, or an undo and its redo writes the manifest at most, and a save with nothing changed writes nothing.

**The knowledge comes from the store's own writes and from `load`**, which hashes every file it reads and compares it with the canonical bytes of what it parsed: a layer whose files are not canonical — a hand edit — is marked whole, so the next save puts it back exactly as a store that rewrote everything would have. It describes the disk only while nothing else writes the directory, which is the assumption ADR-0039 already makes (one writer per document). **When the store knows nothing** — a new document, one saved to a directory other than the one it was loaded from or last saved to, or after `mark_all_dirty()`, which is how a caller says files changed behind the store's back — every file is written, and the disk is asked what to remove: the old form's files, stray tiles in a partitioned layer's `tiles/`, and the files of layers the manifest named that the document no longer has. That is what every save used to do.

A collision of the length and the 64-bit hash would leave a changed file unwritten; for two different canonical files to collide on both is not a risk worth a byte-for-byte comparison, which would mean reading the file back.

### Writing a file

**This machine's file system charges by the operation, and by its kind, not by the byte** (`doc.fs.*`, `msvc-release`, with other processes using 10–40% of the CPU): reading a file costs about 0.3 ms from 64 B to 64 KiB and 0.5 ms at 1 MiB; asking whether one exists 0.08 ms; listing a directory of 64 files 0.26 ms; appending a line 0.5 ms. Writing is where the kinds differ:

| write, per file | 64 B | 4 KiB | 16 KiB | 64 KiB | 1 MiB |
|---|---|---|---|---|---|
| in place, write-only, not truncated, at the length it had (`doc.fs.overwrite`) | 0.50 ms | 0.50 ms | | 0.50 ms | 0.61 ms |
| the same, a byte longer or shorter than it was (`overwrite_resize`) | | 0.70 ms | 4.9 ms | 4.8 ms | |
| removed, then made again write-only (`recreate`) | | 1.2 ms | 1.2 ms | 1.2 ms | |
| in place through stdio's `"r+b"`, opened to read as well (`overwrite_rw`) | 1.1 ms | 1.3 ms | | 9.6 ms | 10.8 ms |
| truncated and rewritten, stdio's `"wb"` (`write_direct`) | 0.74 ms | 1.0 ms | | 5.8 ms | 9.6 ms |
| a new file renamed over it, `io::write_file_atomic` (`write_atomic`, what a save did) | 2.9 ms | 3.1 ms | | 3.1 ms | 3.4 ms |
| `io::make_directories` on a directory that exists, which `Vfs::write` and `Vfs::append` do before every write — until it looked first ([io](io.md#writing-a-file); now 0.07 ms) | 4.3 ms | | | | |

The rename alone is 2.1 ms (`doc.fs.rename`), and MSVC's `create_directories` creates every prefix of the path in turn, each failing because it exists. Appending to a file that grows costs nothing extra (`doc.fs.append` grows its file to 16 MB). **The cheap way to put bytes in a file is to open it for writing alone, without truncating it, and write from the start** — 0.5 ms at any size while the length stays the same, and when it changes, cutting or growing the file in place is cheap only while it is small, so from 8 KiB (between the 4 KiB and 16 KiB points measured) a file whose length changes is removed and made again instead. That is `io::overwrite_file` ([io](io.md#writing-a-file)), and a save writes each file once with it, passing the file's old length, which it knows from what it last wrote or read. None of that is atomic by itself, so the save log below is what makes a save safe, where each file used to be made safe by a rename of its own. A save makes a directory only when a write finds it missing and goes to native paths once the document directory is resolved through the `Vfs`. In the Linux container every one of these is 1–150 µs, which is why E12's tests ran 25 times faster there.

### A save is all or nothing

([ADR-0041](../adr/0041-a-save-is-a-log-then-files-written-in-place.md), proposed.) **Before it touches a file of the document, a save writes one log**, `save.pending` in the document directory: a header line, every file it is about to write — its path under the directory, its length, its bytes — every file it is about to remove, and a last line holding a hash of everything above it. Then it writes the files in place, removes the others, writes the manifest last, and removes the log. What a process that dies leaves:

- **before the log is whole** — while writing it, or before — a log whose last line is missing or does not match, and not one file of the document touched: the previous state stands. The next save removes the torn log.
- **after** — anywhere among the writes and removals, a file half written included — a whole log, which says exactly what the directory is to hold. **`load` reads the document through it** (a file the log writes is read from the log, a file it removes is not there, a directory listing is adjusted to match), so what is loaded is the new state, and **the first save of the loaded document carries the log out** — every write and removal again, which is harmless where they were done — and removes it before doing anything of its own.

**`load` never writes.** A process that only reads a document — engine-cli, a second host — must not change a directory another process may be saving into, so a pending log is read through, not acted on, and a read-only mount reads the same document a writable one does. The first save is the writer's.

**The journal agrees whichever way it went.** `Session::commit_commands` appends the commit's patch to the journal before the save, and the manifest's `undo_position` — written by that save, last — says how many patches the layer files hold. A save that died before its log was whole leaves the layer files and the manifest as they were and the new patch as the first of the redo tail: the previous state, with the commit one `doc.redo` away. One that died after leaves the new state and the new undo position once the log is read. Never a manifest of one state over layer files of the other, and never an index disagreeing with its tiles, which is what an interrupted save could leave before. A host that died in the append itself leaves half a line with no newline, which `load` leaves out (its commit never reached the save) and the next append cuts off before it adds its own; before, that half line failed every load after it.

`tests/save_tests.cpp` stops a save at every one of its file operations in turn (`SaveOptions::stop_after`, and `tear` to leave that operation half done — half a log, half a tile) for a commit that removes a tile, adds two, moves records on and off the grid and changes the index, and for structural changes (a layer added, one repartitioned, one removed), and checks each time that a load reads the old state when the save stopped before its log was whole and the new one after, that the load changed nothing on disk, that the next save leaves the directory byte for byte that state's with no log behind, and that the old state's redo tail redoes into the new one.

### A layer says which versions it holds

**A document records no version per record, so until 2026-10-06 a build read a newer record type's fields as its own**: a `worldpos` position ([ADR-0053](../adr/0053-world-positions-are-f64-and-the-gpu-sees-none.md)) read by a build whose type still said `vec3` became three float32s, silently, where a save (which names every record type's version in its manifest, [world](world.md#save-and-load)) refused with a sentence. **`LayerFile` version 2 carries a type-version table**, `types`: every record type the file's *defining* records are of that the writing build's schema registry has, at that build's version, in name order, once each (`stamp_record_types`, which `Layer::to_file` calls — so a single-file layer, a tile file and `untiled.json` all carry one). A reader checks it (`check_record_types`, in `Layer::from_json_text` and on every tile and untiled file the store loads) and **refuses a file naming a type it has at an older version**, naming the file, the layer, the type and both versions — "layer 'places' holds engine.doc.test.Placement records at version 2, newer than this build's 1: it was written by a newer engine…". A file with no table (written before version 2), one naming an older version (whose missing fields take their defaults, as in a save), and one naming a type the build does not have (the document keeps such records as data, as it always has) all load as before. A build that predates the table refuses the field itself — `types: unknown field` — which is a refusal and not a misreading, and the most a build that cannot know the rule can do.

**Why a table per file and not one number per document.** A document version would refuse every document for any type's change, could not say which type, and would be one more thing to remember to bump; the table is written from the records themselves, so it cannot be forgotten. **Why per file and not in the manifest**: a save after a transaction rewrites only the tiles whose records changed, and the table of a tile is a function of that tile's records and the build, so writing it costs what writing the tile costs and a tile's bytes stay a function of the records it holds (and the build's versions). A manifest-wide table would be a pass over every record on every save.

**Why only defining records.** An override names no type, and stamping the type the document composes for it would make an override layer's bytes depend on another layer — a defining record created or deleted elsewhere would leave the override's tile stale, and an incremental save would no longer write what a whole one does. It is not needed for a document: the layer that defines the object names its type, and a document loads whole or not at all. What it leaves open is an override layer handled **alone** — a proposal exported and merged into an older build's document — whose values reach that build unchecked; a merge that wants the check reads the type from the document it merges into.

**What it costs a document saved before.** Its files are not the canonical bytes any more (they lack the table), so the first save after a load rewrites each layer once, as it does any file not in the canonical form; nothing is migrated and the values are untouched. The test (`tests/save_tests.cpp`, "a layer names its record types' versions") writes a tiled layer 419 km out and a single-file one, finds the table in both, loads a tile without a table and with an older version, refuses a newer one in a tile and in a single-file layer by name, and keeps a type the build does not have.

### A renamed type or field

**A rename is an alias** ([plan 03 §3.8](../plan/03-data-model.md#38-schema-evolution), roadmap D28; the language's side is [schemas/README.md](../../schemas/README.md#renaming-a-field-or-a-type)): a type keeps its former name as `@alias("Old")` and a field as `@alias("old")`, and **a document written before the rename opens in the new names and its next save writes them**. A document's properties are JSON the document holds as it was written until something validates them, so the schema reader's acceptance of a former name is not enough here: left alone, the old names would be saved back forever. So the load renames the records themselves.

- **Definitions are renamed as their files are read** (`rename_defining_records`, called by `Layer::from_json_text` and on every tile and untiled file `DocumentStore::load` reads): a `type` that is a former name of a registered type becomes the type's name, and every property — and every struct value inside one, through optionals, arrays and maps — that bears a former name of a field takes the field's name (`schema::rename_former_fields`). A definition carries its type, so it needs nothing from another layer; and it has to be renamed before the load checks that each record stands in the tile it is filed under, because with no property named by the partition a record's tile is read from its type's `position` field, which a type known only by a former name does not have.
- **Overrides are renamed once the stack is whole** (`Document::rename_override_records`, which `DocumentStore::load` calls): an override names no type, so its type is the one **the composed index** gives its id (`type_of`) — never a search of the other layers — and its properties are renamed by that type's aliases.
- **An override no layer defines keeps its names, and is reported.** Nothing says which type it is a property of, so nothing says what its former names mean; each of its properties bearing a name that is a former field name of some registered type is listed in `Document::kept_names()` (layer, id, property). Such an override was already an error to `validate()` ("override record for an object no layer defines").
- **One field under two names is refused, by name.** A record — definition or override — holding a field under its current name and a former one, or two former ones, fails the load with the layer, the record and both names ("places/…/title: carries both 'title' and 'label'…"): nothing says which value the author meant.
- **A layer's type table** may name a type by a former name (a file written before the rename names the type it had): `check_record_types` resolves it (`Registry::resolve`), so a file newer than the renamed type's version is refused as it would be under the current name, and the next save's table names the current one.
- **What it costs.** A build whose registry holds no former name skips all of it: one check per file and none per record. With aliases registered, a definition costs a registry lookup and a walk of its properties, and an override a composed-index lookup and the same walk; a layer that changed fails the load's canonical check, so the next save rewrites it as it rewrites any file not in the canonical form. Nothing else is migrated.

The migration corpus holds a document written before such a rename and the bytes it saves to ([corpus](../../content/migration-corpus/README.md#the-documents)); `tests/rename_tests.cpp` opens it and saves it, and also takes a definition through the rename and its tile, a type table naming the former type, an override renamed through the index, an override no layer defines kept and reported, and one field under two names refused in a definition and in an override.

### Reading a file without a tree

(Roadmap D40.) **Opening a large document was mostly JSON, twice.** T183 sampled `engine_cli`'s 10⁵-resident case: about half of each host's time was opening its 76 MB document, 22–30 % of it parsing every file into a `JsonValue` tree before reflecting it into `LayerFile`, and 22–24 % `canonical_on_disk`, which serialized every layer again after the load to learn whether the next save must rewrite it. `bench/doc_bench.cpp` measures both on a document of that size and shape (`doc.store.load.residents`, and `doc.layer.parse`, `.from_json`, `.serialize` for one layer file of its records; `ENGINE_BENCH_DOC` keeps the document between runs so the load row run alone reports its own peaks).

**Every file of a document is read with no tree of it**: the manifest, an index, a tile, `untiled.json` and a single-file layer go through `schema::read_json_text` ([schema](schema.md#json-text-with-no-tree)) — `parse_schema_text` and `Layer::from_json_text` — which reflects the text straight into the file's struct with the tree path's verdicts word for word; a record's properties are still `JsonValue`s, built straight into the record. `tests/json_text_property_tests.cpp` holds the two paths together over the engine's own schemas (358 types). The journal's lines are read as they were.

## What a save costs

[E12](../experiments/e12-proposal-layers-and-leases.md#what-surprised-me) found an edit costing 87–158 ms and a promotion about 400 ms on Windows, almost all of it the store, so the store has benchmarks of its own. `doc.store.*` in `bench/doc_bench.cpp` times what `Session::commit_commands` does for one `doc.apply` — a one-command transaction, its journal line, the manifest's undo position, the save — on two declared shapes, with the files and bytes each commit wrote in the items and bytes columns: **store**, eight layers and 10⁴ records (`world` partitioned into 8 × 8 tiles of 64 m with 8,000 placements, seven single-file feature layers of 286 overrides), committing to a tile (`commit.tile`) or to a single-file layer (`commit.plain`), and saving with nothing changed (`save.unchanged`); and **e12**, E12's document with 4 or 16 proposal layers of ten overrides each, one agent committing to its own (`commit.e12/<agents>`). `doc.fs.*` times the file operations a save is made of, one at a time and at four sizes.

Before and after the store wrote only what changed through a log (`msvc-release` on the Windows development machine, an i9-10980XE with an NVMe drive, the two binaries run back to back; the files column counts the journal line as one; machine state: other processes used 4–24% of the CPU during the first run and 8% during the second, the GPU lock free — the first is an upper bound):

**What is left of a commit on Windows** is its file operations — the journal line (0.5 ms), the log made and removed (about 1.2 ms), each file (0.5 ms, or 1.2 ms when a file of 8 KiB or more changes length), the manifest (0.5 ms) — and a millisecond or less of serialization and hashing; the 10⁴-record single-file layer costs `commit.plain` its serialization and 53 KB. Before, a commit wrote five files and spent 67–133 ms doing it: the cost was never the bytes but the questions (`index.json` read and parsed, directories made, tiles listed, forms probed) about layers the commit had not touched, `create_directories` on every write, and a rename per file. ## Change feed

A reader that mirrors the document — the runtime world's materializer — must not rescan it to learn what changed. So every mutation stamps the ids whose composition it changed with the document's next **revision** (`IndexEntry::revision`, `revision_of(id)`, `revision()`) and appends them to a **feed**; `changed_since(since, out)` returns each id changed after revision `since` once, in id order — live, deleted and gone alike, because the reader has to hear about all three. A record nothing touched costs such a reader nothing at all.

The feed is **bounded**: past twice the index's size (and at least 4,096 entries — 24 bytes each) it drops its older half and its floor moves up, and a reader whose revision fell below the floor gets `false` and resynchronizes by comparing `revision_of` over the live set — correct, and no dearer than the full pass it replaces. **A rebuild of the index restamps every id** with one new revision and empties the feed, because after the mutable `layer()` accessor or a `remove_layer` the document cannot say what changed; a reader behind it resynchronizes the same way.

Which is why **`Transaction`'s constructor now reads the edit layer's name through the const accessor.** It used the mutable one, which marked the composed index dirty on every transaction: the first query after `begin` recomposed the whole document — an O(n) cost on every edit that the index bench never saw because it applies commands directly — and, with the feed, would have sent every reader back to a full resynchronization after every edit. `Session::merge` read its three layers the same way and now does not either.

## Blobs

**Bytes a property names instead of holding** (plan 03 §3.2: "large blobs … are separate content-addressed binary files referenced by hash from the JSON"; roadmap D13; `blob_store.h`). A heightfield's grid, a painted mask, a generated image's bytes: a property holds an `engine.doc.BlobRef` — `{"blob": <SHA-256, 64 lowercase hex>, "size": n, "media": "…"}` — and the bytes live once in the document's store:

```
blobs/<first two hex digits>/<the other 62>     the bytes and nothing else
```

- **The same content is always the same name and the same file.** The file is the bytes, so `name = SHA-256(file)`; `BlobStore::put` of bytes already stored writes nothing (`created: false`), whatever `media` it is given — media is for a reader and not part of the name — but it does set the file's time to now: a put promises a commit naming the blob, and the collection's grace period counts from the file's time, so a blob left unnamed past the period and put again is young again (batch 68's review, B3; `blob_tests.cpp`).
- **One store per document, found by the hash alone.** Not per layer and not per tile: a tile file of a partitioned layer names a blob, and `path_of(dir, name)` finds it wherever the record is filed, so moving a record between tiles rewrites its tiles and moves only the reference (`blob_tests.cpp`).
- **A read checks the bytes against the name** — and the length against the reference's `size` — and refuses a mismatch, naming the blob and the file ("does not hash to its name: the file is damaged"). A put of the same bytes over a damaged file writes them again.
- **A merge treats a reference as a value.** It is a JSON value like any other, so `merge_layers` takes one side's reference, agrees when both chose the same blob, and reports `PropertyBothChanged` with the three references when they chose different ones; two equal blobs compare by name.

**What a save writes: no blob.** A blob is written when it is put — atomically, a sibling file renamed into place, so it is whole or absent — and never changed after; the save log names layer files and the manifest only. A blob nothing references is harmless (it is collected later); a reference to a blob that is not there is not, which is why a session refuses a client's command naming a blob its store does not hold ([protocol](protocol.md#blobs-and-checkpoints)) — a commit could otherwise make a document that is damaged from its first save. A client's bytes come inline or from a file under the document's directory and nowhere else on the host's disk (`doc.put_blob`'s path rule, [protocol](protocol.md#blobs-and-checkpoints)).

**When a blob is collected: only when nothing can bring its reference back** (`BlobStore::collect`). A blob is kept while any record of any layer names it, while any command of any journal patch names it — forward and inverse, the undo history *and* the redo tail, each of which `doc.undo` and `doc.redo` can put back — while any root the caller adds names it (the protocol adds every open proposal's merge-base entries, which a promotion with `prefer: Base` can write back), and while it is younger than a grace period (an hour by default: the time between a client's put and the commit that names it). So a blob goes when its last reference is in a redo tail a new commit dropped, or was never committed at all; one the journal can still reach stays however long ago it was replaced. Collection is explicit — `doc.collect_blobs`, never a side effect of a save — because it reads every record and every patch. A blob a checkpoint held and a collection took is not lost: `doc.rollback_to` writes it back from the checkpoint ([Checkpoints](#checkpoints)).

*Why SHA-256.* The name is the blob's whole identity, so two contents must never share one: the engine's 64-bit `hash_bytes` is a table hash, and a heightfield that collided with another would be read as the other without a word. SHA-256 (`core/hash/sha256.h`, checked against FIPS 180's vectors) has no known collision and is what git's newer object format uses. Hashing costs about what reading the bytes does.

*What uses it.* **The authored heightfield** (W66, [tileset](tileset.md#the-record)) is the consumer it was built for: today its `source` names a header file beside the document and a raw float32 grid beside that, so the grid is outside the document's history — a checkpoint does not hold it and an undo cannot restore it — and W66's brush needs "a blob the journal keeps" for each stroke's before and after. With blobs the record holds the grid's `BlobRef` (and the header's fields), a stroke is a `SetProperty` of the new grid's reference, undo puts the old reference back, and the old grid stays in the store for as long as the journal can reach it. **A terrain mask tile** is the same: a painted layer per tile named by hash, so repainting one tile writes one blob and one property. Neither is moved in this change — the heightfield's reader takes a path to a header that names its grid by a relative path, so moving it means a header that names a blob, a reader that resolves one, and the tile-set build keyed by the grid's name instead of its file; that is W66's brush's first step and a row of its own.

## Checkpoints

**A checkpoint is a commit of the document directory's own git repository** (plan 03 §3.3, 06 §6.4; roadmap D14; `checkpoint.h`): `<dir>/.git`, made on the first checkpoint, holding `manifest.json`, `layers/` and `blobs/` exactly as the last save left them — and nothing else: not the journal (it grows, and a copy per checkpoint would grow the repository quadratically), not the save log, and not the protocol's `leases.json` and `proposals*` (time-bound claims and work in progress, not the world). The repository's `info/exclude` keeps the rest out, so `git status` in the directory is quiet. The commit's subject is the checkpoint's label; its body is the rationale, then the journal's patches since the previous checkpoint (one `Patch` JSON per line, from that checkpoint's undo position to this one's when the journal still holds them in order, the whole applied journal after an undo below it), then git trailers — `Engine-Actor`, `-Role`, `-Task`, `-Rationale`, `-Time`, `-Journal-Length`, `-Undo-Position`, `-Journal-From` — which `list` reads back with `%(trailers)` into `CheckpointInfo` without reading the bodies. **A label is a client's text, refused rather than altered** when it holds any control character or runs past `k_max_label_bytes` (200), and a trailer's value has every control character turned into a space: `list` asks git for each commit as its id, parents, trailers and subject, separated by U+001F and ended by a NUL — a byte git refuses in a commit message — so nothing written into a subject can end a record or start another, and a record whose id or parent is not a commit name is skipped. Batch 68's review (B9) found a label holding the old separators listing a checkpoint that never existed; `checkpoint_tests.cpp` makes that commit by hand, past the engine, and holds the listing to the real ones. The journal gives fine-grained history; git gives coarse, branchable history that a person can read with git's own tools.

**The engine runs the `git` on PATH and links no git library.** The tree has none, a download is not an option, and ADR-0014 forbids a copyleft library: git is a separate program the engine runs, not a library it links or ships, so its licence does not reach the engine's binary. Writing the few object kinds a checkpoint needs (blob, tree, commit, a ref) was weighed and not taken: that is SHA-1, zlib's format and the object grammar to write, and — the part that decides it — reading back every object git itself may write into the same repository once a person runs `git gc` or commits there by hand (packfiles, deltas, deflate), or refusing to; shelling out costs a handful of processes per checkpoint (about 20–60 ms each on Windows) and a dependency on git being installed, and gets git's own packing, verification and tools. Without git, `doc.checkpoint` and `doc.rollback_to` answer 1006 Unavailable with the reason and `doc.checkpoints` says `available: false`; `ENGINE_GIT` names another executable. A reversal is small: `Checkpoints` is the one place that runs git, behind five functions.

**The repository is the engine's, run apart from the user's git configuration**: every call names the repository and the work tree outright (so a `GIT_DIR` in the environment cannot redirect it), with no line-ending conversion (`core.autocrlf=false`: the bytes committed are the bytes saved), no hooks (`core.hooksPath` at a directory that does not exist, and `init --template=` so none are copied), no signing, no automatic gc or maintenance, a fixed committer and the checkpoint's actor as author; the child gets no console window (`platform::Process::spawn`'s `no_window`), so a checkpoint from the editor flashes nothing.

**Reading one back** (`Checkpoints::read`) is `git archive` of the commit's manifest and layers into memory — a tar stream, parsed here — checked as a load checks them: each file its schema type, each tile's records standing in that tile. A blob is read only when asked for (`read_blobs`), so a rollback of a world with a gigabyte of blobs reads the ones it lacks. Nothing is checked out over the document: rolling back is the protocol's transaction against the document as it stands ([protocol](protocol.md#blobs-and-checkpoints)), journaled and undoable, because a rollback that replaced the files would leave the runtime world, the journal, the change feed and every open session behind it.

*A choice that is the owner's:* the repository is the document directory's own `.git`, not an enclosing repository's and not a separate directory. A document kept inside another repository (a game's) therefore becomes an embedded repository there; the alternative — committing into the enclosing repository — would write commits into a game's history behind its author's back. `Checkpoints::k_git_dir` is the one name to change.

`tests/blob_tests.cpp` and `tests/checkpoint_tests.cpp` hold both: a blob's name, file and checked read, a damaged file refused and repaired, references found anywhere in a value, a save that writes no blob, a tile's reference across a move, the merge's three cases, and a seeded run of 400 steps — puts, references, clears, undos, redos, dropped redo tails, saves and collections with no grace period — after which every name the document or its journal reaches is stored and reads back, and nothing else is, with every undo to the start still finding its blobs; then the grace period, a root and a dry run. Checkpoints taken, listed newest first with their attribution and journal positions, found by an abbreviation and refused for a name that is not this document's, read back record for record (a single-file layer and a tiled one), a collected blob read back from a checkpoint, the protocol's side file left out, and a document with unsaved changes refused. A machine with no git skips the checkpoint cases and says so.
