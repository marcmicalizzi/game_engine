# doc (domain)

**Purpose.** The authoring document model (docs/plan/03-data-model.md §3.2–3.3, ADR-0002): the text-serialized, layered, stable-ID source of truth that humans and agents edit through commands. Everything the engine protocol, the editor, and the MCP bridge will do to a world goes through this module.

**Model.**
- A `Document` is an ordered `Vector<Layer>`, weakest first. `Layer` holds sparse `ObjectRecord`s keyed by `ObjectId` (`Id128`), sorted. `add_layer` appends (strongest) and leaves the edit layer where it was; a fresh document edits its first layer until `set_edit_layer` says otherwise. `remove_layer` takes one off with everything it holds, bringing the edit layer down with it when it was above, and never removes the last one.
- A record with a non-empty `type` (a registered schema struct's qualified name) *defines* the object; a record without a type overrides `properties`, `parent`, or `deleted` for an object defined in a weaker layer.
- Composition: the strongest layer wins per (object, property); the strongest layer that sets a parent wins; an object is deleted if any layer at or above its defining layer tombstones it. There are no other composition operators (no inherits, variants, or references-with-overrides).
- Property values are `JsonValue`s validated against the object's schema type on demand (`validate()`), not on every edit, so partial and in-progress states are representable.

**Composed index.** A `Document` keeps every id's resolved position in the stack and answers `resolve`, `exists`, `is_defined`, `property`, `objects`, and `children` from it. Nothing scans the layers for an id. An entry is the composed parent, the defining layer, the deletion flag, how many layers hold a record, and a 64-bit mask of *which* layers do, so a query visits only those (bit 63 stands for "layer 63 and everything above it", so a deeper stack costs a scan of the tail and nothing else). Beside it are the live object ids, sorted, and a multimap from parent to its live children, each child list sorted, so `children(parent)` is a hash lookup and a copy of *k* ids.

The index is maintained incrementally, not rebuilt: `apply` touches exactly the id its command named, because a command edits one record and a record only ever changes the composition of its own object; `undo`, `redo`, and a transaction's rollback go through `apply`, so they maintain it too; `add_layer` touches the ids of a layer that arrives with records and nothing when it arrives empty; `remove_layer` rebuilds, because every layer index above the removed one shifts. The live list absorbs changes into a pending buffer and folds them in with one merge pass when someone asks for `objects()`, so creating *m* objects in a document of *n* costs `O(n + m log m)` rather than `O(m·n)`. The one way to go behind the index's back is the mutable `layer(u32)` accessor, which marks it for a rebuild on the next query. `validate_index()` compares the maintained index against a linear recomputation and reports every disagreement; it is what the randomized command test checks after every step.

**Reading a few fields of many records.** `type_of(id)` and `parent_of(id)` answer the record's type and composed parent from the index without composing its properties, and `visit_records(id, fn)` hands `fn(layer, record)` every layer's record for the id, weakest first, so a reader that wants three properties of a hundred thousand records composes those three and not a property map per record — what the materialization driver does ([sim](sim.md#the-driver-a-document-through-the-hooks)).

**Mutation.** Every change is a schema-typed `Command` applied to the document's edit layer: `CreateObject` (type, parent, optional initial properties), `DeleteObject` (drops the definition when the edit layer defines it, tombstones otherwise), `SetProperty`, `ClearProperty`, `SetParent`, `RemoveRecord`, `RestoreRecord`. Strict application checks preconditions (existence, parent existence, cycles) and reports pathed diagnostics; non-strict application is for applying diffs to layers whose base is not loaded, and a `Transaction` takes the same flag, which is how undo, redo, and a merge are written. Every application yields an inverse (`RestoreRecord` of the previous edit-layer record).

**Transactions and journal.** `Transaction` groups commands with an `Attribution` (actor, role, task, rationale, timestamp), records forward and inverse commands, commits as a `Patch` into the document's journal, or rolls back (automatically on scope exit). `undo(patch)` and `redo(patch)` replay inverses in reverse or forwards in order. Patches are schema types and serialize like everything else.

**Write-back commands.** The runtime world writes back to the document through exactly this path and no other: at `TickPhase::Persist`, what systems changed in the fields a type's `materialize` declaration marks `@writeback` becomes one transaction of `SetProperty` commands on the edit layer, in (record id, row) order, attributed to actor and role **`system`**, task `sim.write_back`, with a rationale naming the tick and the counts ([sim](sim.md#write-back)). A session commits it like any other — journaled, saved, undoable — non-atomically, so a record deleted since it was materialized refuses its own command and nothing else. The journal, `doc.journal` and `session.events` then say "the simulation wrote this", which is the whole difference between a write-back and an agent's edit of the same property.

**Diff.** `diff_records(from, to)` is the machine-readable structural diff: one `RecordDiff` per object whose record differs, in id order, saying whether the record was added or removed and otherwise which of `type`, `parent`, and `deleted` changed and which properties were set or cleared (`PropertyChange`, in name order). `diff_layers(from, to)` is that rendered as commands in the same order: whole-record restore/remove where no command expresses the change (an added or removed record, a changed type or deletion flag, a parent override `to` drops), fine-grained `SetParent`, `ClearProperty`, `SetProperty` otherwise. Applying the diff to `from` yields `to` exactly (tested both directions).

**Structural merge.** `merge_layers(base, ours, theirs, [options,] out, error)` (`merge.h`) merges two layers that diverged from a common ancestor, per object and per property — never by text. Objects are identified by `Id128`, so a rename is a property change and a move is a change to one field; neither is a conflict. The two sides' `diff_records` against base drive it, so the diff machinery is not duplicated.

| What the two sides did | Merged layer | Conflict |
|---|---|---|
| changed a property on one side only | that side's value | — |
| changed it on both to the same value | that value | — |
| changed it on both to different values | ours | `PropertyBothChanged` |
| deleted an object, untouched on the other side | deleted | — |
| deleted it on one side, modified it on the other | kept, with the modifications | `DeletedAndModified` |
| deleted it on both sides | deleted (the record is removed if either side removed it) | — |
| created the same id with identical records | that record | — |
| created the same id with different records | ours | `CreatedBothDifferent` |
| reparented so that the merged layer would have a cycle | base's parent | `ParentCycle` |

A side *deletes* an object when its record is gone from the layer or its `deleted` flag went from false to true. Conflicts name the object and the property; `$type` and `$parent` stand for the record's own fields (a schema field name never contains `$`), and the property is empty for a conflict about the whole record. Each conflict carries the three values as JSON, with null for absent. `MergeOptions::prefer_on_conflict` moves the resolution from `Ours` (the default) to `Theirs`, or to `Neither`, which keeps base's value — except for a deletion against a modification, where the modifications win under both `Ours` and `Theirs`, because a deletion never silently destroys the other side's edits, and `Neither` keeps base's record untouched. `applied_ours` and `applied_theirs` count the changes each side got: one per property set or cleared, one each for a changed type, parent, or deletion flag, one for a record added or removed whole, counting for both sides when both made the same change and for neither when a conflict dropped it.

The merged layer takes base's name, role, and storage form, never keeps an empty override-only record (the normalization `ClearProperty` does), and is canonical: with no conflicts, `merge(base, a, b)` and `merge(base, b, a)` write the same `LayerFile` JSON. Cycles are judged against the finished layer, so two reparents that are each fine but together close a cycle are caught, and only a layer merge's own links are visible — the composed document's parents are `validate()`'s question. The merge fails, rather than conflicting, only when `base` itself already has a parent cycle: nothing could be kept from it.

**Not merged.** Spatial collisions (two agents placing overlapping objects) are not merge conflicts; validators catch them after the merge (plan 03 §3.3). A merge never refuses to produce a layer over a conflict, because that would lose the work on both sides.

**Files.** A layer serializes through the generated `LayerFile` schema to canonical JSON with records in id order, so two equal layers produce byte-identical files and git diffs are meaningful. Format pinned by test.

**Store.** `DocumentStore` (`document_store.h`) keeps a document as a directory: `manifest.json` (`DocumentManifest`: name, layer stack, edit layer, `undo_position`), one file or one directory per layer under `layers/`, and `journal.jsonl` (one `Patch` per line). Layer files always hold the current state, so a checkout is readable without replaying the journal, and the journal plus the manifest position make undo and redo survive across processes. Paths go through `io::Vfs`, so documents live under mounts or at native paths. `save` writes only what changed ([Saving](#saving)), also removes the files of layers the document no longer has, and reports what it wrote and removed in a `SaveReport`. **The journal is only ever appended to**: `append_journal(vfs, dir, doc)` — what a session calls after a commit — makes the file hold exactly the document's journal by cutting it in place after the patches it keeps (a redo tail the commit dropped, or a line a process died appending) and appending the new line, where the redo tail used to cost a rewrite of the whole file; it knows where each line ends from the load or its own writes, and writes the file whole only when it knows nothing of it. A last line without its newline is an append that died in the middle — the store writes a line and its newline in one write — and `load_journal` leaves it out: its commit's save never ran. `write_side_file` and `append_side_file` are the same care for the files the protocol keeps beside a document ([protocol](protocol.md#roles-leases-and-proposals)): a whole file replaced atomically and only when its bytes change, an append appended, and a directory made only when a write finds it missing.

**Partitioned layers.** One fixed tile grid is the unit of layer files, streaming, nav tiles, and agent edit leases (plan 03 §3.7). A layer carries its own storage form in a `LayerPartition` — a position property and a tile size — persisted in the manifest and mirrored in the layer's own index, and the two forms sit side by side in one document:

```
layers/<layer>.json              a layer with no partition: one canonical LayerFile
layers/<layer>/index.json        with one: which tile holds each record, and the grid
layers/<layer>/tiles/<x>_<y>.json   a LayerFile restricted to that tile's records
layers/<layer>/untiled.json      the records with no position (factions, quests, canon facts)
```

A record's tile is a function of the record alone: its position property, floored by the tile size, on the horizontal plane — x and z of a three-component position, y being up as `core/math` has it. It never depends on the other layers, on load order, or on what was on disk before, which is what makes the form canonical: the same document content always writes the same set of files, with the same bytes. `partition.h` reads a position from `[x, y]`, `[x, y, z]`, an object with numeric `x`/`y`(/`z`), or a transform with a `position` or `translation` member. Which property carries it is either named in the partition — the reproducible form, since it depends on nothing outside the document — or, when the name is empty, taken from the record type's first `position` or `transform` field as the schema registry reports it, which is how a type opts in; a record with no type, or one whose type declares neither, goes to `untiled.json`.

Saving after a transaction rewrites only the tiles that changed — the tiles its records were and are in, and `index.json` when one of them changed tiles; a tile with no records left has its file removed ([Saving](#saving)). `repartition` converts a layer between the two forms and removes the files of the old one. None of this reaches above the file layer: the journal is per document, undo and redo replay commands, and a partitioned layer is an ordinary layer in memory that diffs and merges like any other (a merge takes base's storage form along with its name and role).

Loading checks the layout rather than trusting it, and names the file in the message: a tile listed under the wrong name, a record the index files elsewhere, records out of id order, tiles out of (x, y) order, a tile file the index does not list, an `untiled.json` the index does not expect, a partition the manifest disagrees with, and — the check that makes the layout a fact about the records rather than a convention — a record whose position does not fall in the tile it is filed under.

**Validation.** Unknown types; overrides for objects no layer defines; objects defined in more than one layer; missing parents; parent cycles; unknown, transient, or ill-typed properties (checked by deserializing each value into a scratch instance of the type). Diagnostics are `<layer>/<id hex>/<property>`.

**Leases and proposal layers are the protocol's.** Plan 06 §6.5's leases, roles and proposal promotion live in `domain/protocol` ([protocol](protocol.md#roles-leases-and-proposals), [ADR-0039](../adr/0039-leases-and-proposals-beside-the-document.md)), because what they guard is the protocol's writes: this module still knows nothing of owners, leases or promotion, and a proposal is an ordinary layer of role `Proposal` here. What they take from it: the tile grid, through `position_property(type, partition)` and `tile_of_position` (`partition.h`) — the same rule as a record's own tile, applied to an object's **composed** position, because a lease on a tile means the objects standing in it and an override that sets only a colour still changes one of them — and `merge_layers`, which promotion runs with a base of the target's records as the proposal first touched them.

**Not yet (v0).** Git checkpointing. The tile grid is the document's file layout and the unit of leases; nothing yet streams or indexes space by it. A single-file layer that changed is serialized and written whole, whatever part of it changed: the format is one JSON document, so a layer that many edits touch belongs in tiles. A merge is between layers, not between document states, and it does not rebase a journal. A partitioned layer is loaded whole — there is no "open these tiles and not those" yet, which is what leases and streaming will need. A save is all or nothing against a process that dies ([below](#a-save-is-all-or-nothing)), not against the power going: nothing is flushed to the device (no `fsync`, no `FlushFileBuffers`), as nothing was before, because a flush costs milliseconds a file here and an editor that loses its last second of work to a power cut has lost what a journal would have lost too.

**Performance notes.** This is the editing path, not the frame loop. The runtime world is a materialization of the document plus persistent state (plan 03 §3.4); the document itself is optimized for diffability and correctness. `bench/doc_bench.cpp` measures the composed index against the linear composition it replaced, over 1k and 100k records in a two-layer stack, plus what maintaining it costs an `apply` and what building a tile index costs. Measured on one Windows development machine (msvc-release), 100k records:

| | linear | indexed |
|---|---|---|
| `objects()` | 58.3 ms | 1.89 ms |
| `children(parent)`, per parent | 111.1 ms | 102 ns |
| `resolve(id)`, per object | 565 ns | 600 ns |
| `property(id, name)` | 295 ns | 322 ns |

The two big wins are the two that were quadratic: `objects()` resolved every id to test liveness, and `children()` walked the whole document for one parent. `resolve` and `property` are a wash, and honestly so — over a two-layer stack the index replaces two `FlatMap` binary searches with a hash lookup into a 100k-entry map and one or two of the same searches, and `resolve`'s cost is dominated by composing and allocating its property map either way. The index earns its place there by being O(1) in the depth of the stack rather than O(layers), and by making `exists()` and `is_defined()` — which every strict command calls — a single hash lookup instead of a full compose with an allocation. Maintaining it costs a `SetProperty` 722 ns at 100k records (294 ns at 1k). `build_layer_index` over 100k records is 17.7 ms, which is a save's cost, not a query's.

## Saving

**A save writes the files whose bytes change and nothing else, and what it leaves on disk is byte for byte what writing every file would have left.** Two things decide what it writes, and neither is the disk:

- **What changed**, which the document keeps: `Document::changes(layer)` is a `LayerChanges` per layer — the ids a command edited in that layer since the last save (`apply`, and so undo, redo and a rollback, note the id in the edit layer), or `whole` when the store must look at every record: the layer arrived (`add_layer`), changed form (`set_layer_partition`), or was handed out through the mutable `layer()` accessor, after which nothing can say what changed. A successful save clears them (`clear_dirty`); `dirty()` says whether any layer changed.
- **What is there**, which the store keeps (`StoredState`, private to the module and held by the document): the native directory it describes, every document file it wrote or read with its length and a 64-bit hash of its bytes, and each partitioned layer's index as filed with where it files each id. The journal is not in it; it is only appended to.

The rules follow from those two. A layer with no changes is not visited at all — not serialized, its index not read, the file system not asked. A single-file layer that changed is serialized and written if its bytes differ. In a partitioned layer, each changed id is looked up where the kept index files it and where its record belongs now (`tile_of`: a function of the record alone), and those tiles — and `untiled.json` — are serialized and compared; the kept index is updated in place, not rebuilt from the whole layer (a debug build checks it against `build_layer_index` after every save), and `index.json` is written when a record changed tiles; a tile left without records is removed. A layer marked whole is serialized in full and each of its files compared, so an edit through the mutable accessor rewrites the files it changed and not the others; its old form's files and the tiles it no longer has are removed. The manifest is compared like any file: it changes when the undo position, the edit layer or the stack does. Because a file is written only when its canonical bytes differ from the ones there, a transaction that sets a value to itself, a rolled-back one, or an undo and its redo writes the manifest at most, and a save with nothing changed writes nothing.

**The knowledge comes from the store's own writes and from `load`**, which hashes every file it reads and compares it with the canonical bytes of what it parsed: a layer whose files are not canonical — a hand edit — is marked whole, so the next save puts it back exactly as a store that rewrote everything would have. It describes the disk only while nothing else writes the directory, which is the assumption ADR-0039 already makes (one writer per document). **When the store knows nothing** — a new document, one saved to a directory other than the one it was loaded from or last saved to, or after `mark_all_dirty()`, which is how a caller says files changed behind the store's back — every file is written, and the disk is asked what to remove: the old form's files, stray tiles in a partitioned layer's `tiles/`, and the files of layers the manifest named that the document no longer has. That is what every save used to do.

A collision of the length and the 64-bit hash would leave a changed file unwritten; for two different canonical files to collide on both is not a risk worth a byte-for-byte comparison, which would mean reading the file back.

### Writing a file

**This machine's file system charges by the operation, and by its kind, not by the byte** (`doc.fs.*`, `msvc-release`, with other processes using 10–40% of the CPU): reading a file costs about 0.3 ms from 64 B to 64 KiB and 0.5 ms at 1 MiB; asking whether one exists 0.08 ms; listing a directory of 64 files 0.26 ms; appending a line 0.5 ms. Writing is where the kinds differ:

| write, per file | 64 B | 4 KiB | 16 KiB | 64 KiB | 1 MiB |
|---|---|---|---|---|---|
| in place, write-only, not truncated, at the length it had (`doc.fs.overwrite`) | 0.50 ms | 0.50 ms | | 0.50 ms | 0.61 ms |
| the same, a byte longer or shorter than it was (`overwrite_resize`) | | 0.70 ms | 4.9 ms | 4.8 ms | |
| removed, then made again write-only (`recreate`) | | 1.2 ms | 1.2 ms | 1.2 ms | |
| in place through stdio's `"r+b"`, opened to read as well (`overwrite_rw`) | 1.1 ms | 1.3 ms | | 9.6 ms | 10.8 ms |
| truncated and rewritten, stdio's `"wb"` (`write_direct`) | 0.74 ms | 1.0 ms | | 5.8 ms | 9.6 ms |
| a new file renamed over it, `io::write_file_atomic` (`write_atomic`, what a save did) | 2.9 ms | 3.1 ms | | 3.1 ms | 3.4 ms |
| `io::make_directories` on a directory that exists, which `Vfs::write` and `Vfs::append` do before every write — until it looked first ([io](io.md#writing-a-file); now 0.07 ms) | 4.3 ms | | | | |

The rename alone is 2.1 ms (`doc.fs.rename`), and MSVC's `create_directories` creates every prefix of the path in turn, each failing because it exists. Appending to a file that grows costs nothing extra (`doc.fs.append` grows its file to 16 MB). **The cheap way to put bytes in a file is to open it for writing alone, without truncating it, and write from the start** — 0.5 ms at any size while the length stays the same, and when it changes, cutting or growing the file in place is cheap only while it is small, so from 8 KiB (between the 4 KiB and 16 KiB points measured) a file whose length changes is removed and made again instead. That is `io::overwrite_file` ([io](io.md#writing-a-file)), and a save writes each file once with it, passing the file's old length, which it knows from what it last wrote or read. None of that is atomic by itself, so the save log below is what makes a save safe, where each file used to be made safe by a rename of its own. A save makes a directory only when a write finds it missing and goes to native paths once the document directory is resolved through the `Vfs`. In the Linux container every one of these is 1–150 µs, which is why E12's tests ran 25 times faster there.

### A save is all or nothing

([ADR-0041](../adr/0041-a-save-is-a-log-then-files-written-in-place.md), proposed.) **Before it touches a file of the document, a save writes one log**, `save.pending` in the document directory: a header line, every file it is about to write — its path under the directory, its length, its bytes — every file it is about to remove, and a last line holding a hash of everything above it. Then it writes the files in place, removes the others, writes the manifest last, and removes the log. What a process that dies leaves:

- **before the log is whole** — while writing it, or before — a log whose last line is missing or does not match, and not one file of the document touched: the previous state stands. The next save removes the torn log.
- **after** — anywhere among the writes and removals, a file half written included — a whole log, which says exactly what the directory is to hold. **`load` reads the document through it** (a file the log writes is read from the log, a file it removes is not there, a directory listing is adjusted to match), so what is loaded is the new state, and **the first save of the loaded document carries the log out** — every write and removal again, which is harmless where they were done — and removes it before doing anything of its own.

**`load` never writes.** A process that only reads a document — engine-cli, a second host — must not change a directory another process may be saving into, so a pending log is read through, not acted on, and a read-only mount reads the same document a writable one does. The first save is the writer's.

**The journal agrees whichever way it went.** `Session::commit_commands` appends the commit's patch to the journal before the save, and the manifest's `undo_position` — written by that save, last — says how many patches the layer files hold. A save that died before its log was whole leaves the layer files and the manifest as they were and the new patch as the first of the redo tail: the previous state, with the commit one `doc.redo` away. One that died after leaves the new state and the new undo position once the log is read. Never a manifest of one state over layer files of the other, and never an index disagreeing with its tiles, which is what an interrupted save could leave before. A host that died in the append itself leaves half a line with no newline, which `load` leaves out (its commit never reached the save) and the next append cuts off before it adds its own; before, that half line failed every load after it.

`tests/save_tests.cpp` stops a save at every one of its file operations in turn (`SaveOptions::stop_after`, and `tear` to leave that operation half done — half a log, half a tile) for a commit that removes a tile, adds two, moves records on and off the grid and changes the index, and for structural changes (a layer added, one repartitioned, one removed), and checks each time that a load reads the old state when the save stopped before its log was whole and the new one after, that the load changed nothing on disk, that the next save leaves the directory byte for byte that state's with no log behind, and that the old state's redo tail redoes into the new one.

## What a save costs

[E12](../experiments/e12-proposal-layers-and-leases.md#what-surprised-me) found an edit costing 87–158 ms and a promotion about 400 ms on Windows, almost all of it the store, so the store has benchmarks of its own. `doc.store.*` in `bench/doc_bench.cpp` times what `Session::commit_commands` does for one `doc.apply` — a one-command transaction, its journal line, the manifest's undo position, the save — on two declared shapes, with the files and bytes each commit wrote in the items and bytes columns: **store**, eight layers and 10⁴ records (`world` partitioned into 8 × 8 tiles of 64 m with 8,000 placements, seven single-file feature layers of 286 overrides), committing to a tile (`commit.tile`) or to a single-file layer (`commit.plain`), and saving with nothing changed (`save.unchanged`); and **e12**, E12's document with 4 or 16 proposal layers of ten overrides each, one agent committing to its own (`commit.e12/<agents>`). `doc.fs.*` times the file operations a save is made of, one at a time and at four sizes.

The same rows in the Linux container (`linux-clang-debug`, other processes under 1% of the CPU): `commit.e12/4` 5.55 → 0.63 ms, `commit.e12/16` 7.90 → 0.70 ms, `commit.plain` 91.8 → 4.73 ms, `commit.tile` 91.0 → 8.82 ms, `save.unchanged` 88.8 → 0.13 ms. A debug build checks the kept index against `build_layer_index` on every save of a partitioned layer, which is `commit.tile`'s 8,000-record rebuild; release builds do not.

**What is left of a commit on Windows** is its file operations — the journal line (0.5 ms), the log made and removed (about 1.2 ms), each file (0.5 ms, or 1.2 ms when a file of 8 KiB or more changes length), the manifest (0.5 ms) — and a millisecond or less of serialization and hashing; the 10⁴-record single-file layer costs `commit.plain` its serialization and 53 KB. Before, a commit wrote five files and spent 67–133 ms doing it: the cost was never the bytes but the questions (`index.json` read and parsed, directories made, tiles listed, forms probed) about layers the commit had not touched, `create_directories` on every write, and a rename per file. [E12](../experiments/e12-proposal-layers-and-leases.md#results)'s own matrix, rerun: an edit 4.3 ms and a promotion 19–24 ms, where they were 87–158 ms and about 400 ms; the whole matrix in 4.3 minutes, where it took 1 h 24 min; and every count the same.

## Change feed

A reader that mirrors the document — the runtime world's materializer — must not rescan it to learn what changed. So every mutation stamps the ids whose composition it changed with the document's next **revision** (`IndexEntry::revision`, `revision_of(id)`, `revision()`) and appends them to a **feed**; `changed_since(since, out)` returns each id changed after revision `since` once, in id order — live, deleted and gone alike, because the reader has to hear about all three. A record nothing touched costs such a reader nothing at all.

The feed is **bounded**: past twice the index's size (and at least 4,096 entries — 24 bytes each) it drops its older half and its floor moves up, and a reader whose revision fell below the floor gets `false` and resynchronizes by comparing `revision_of` over the live set — correct, and no dearer than the full pass it replaces. **A rebuild of the index restamps every id** with one new revision and empties the feed, because after the mutable `layer()` accessor or a `remove_layer` the document cannot say what changed; a reader behind it resynchronizes the same way.

Which is why **`Transaction`'s constructor now reads the edit layer's name through the const accessor.** It used the mutable one, which marked the composed index dirty on every transaction: the first query after `begin` recomposed the whole document — an O(n) cost on every edit that the index bench never saw because it applies commands directly — and, with the feed, would have sent every reader back to a full resynchronization after every edit. `Session::merge` read its three layers the same way and now does not either.
