# protocol (domain)

**Purpose.** The engine protocol (docs/plan/06-agent-tooling.md §6.2, ADR-0001): JSON-RPC 2.0 dispatch over JSON values, sessions over stored documents, and the day-one method set. Transport-agnostic: `engine-host` feeds it lines from stdin (which is how engine-cli and the MCP bridge, engine-mcp, reach it), `engine-host --listen` also feeds it from a loopback WebSocket ([Transport](#transport)), tests call it in process. Every method's params and result are schema structs (`schemas/protocol.schema`), so the catalogue agents read (`engine.methods`), the JSON Schema schemac emits, and the C++ handlers agree by construction.

**Model.**
- `Dispatcher` holds `MethodDesc`s (name, doc, params type, result type, handler) sorted by name and turns a request object or batch array into a response value; `dispatch_text` adds parse-error handling and single-line framing. Notifications (no `id`) get no response. Responses carry exactly one of `result` and `error`.
- Handlers are plain functions `bool fn(Context&, const P&, R&, RpcError&)` wrapped by `method<P, R, fn>()`; `method_no_params<R, fn>()` for methods without params. `detail::read_params` turns deserialization problems into InvalidParams with `{path, message}` diagnostics in `error.data`. Command failures inside a transaction are results (`ApplyResult.diagnostics`), not RPC errors.
- `Session` owns one `doc::Document` plus its `DocumentManifest`, and every mutation goes to disk before the response: `apply` commits, drops any redo tail, journals, and saves; `undo`/`redo` move `undo_position` and save. The journal goes first (`DocumentStore::append_journal` with the document, which cuts a dropped redo tail off the file in place and appends, never rewriting it) and the save second, so a host that dies between them leaves the commit as the first patch of the redo tail; the save writes only the files the commit changed and is all or nothing ([doc](doc.md#saving), [ADR-0041](../adr/0041-a-save-is-a-log-then-files-written-in-place.md)). The side files — `leases.json`, `proposals.json`, `proposals/<layer>.base.jsonl` — go through `DocumentStore::write_side_file` and `append_side_file`: replaced atomically and only when their bytes change, and appended to. Both go through one private `commit_commands`, which also lets `merge` commit against a layer that is not the session's edit layer without moving it (the patch names the layer it edited, so undo finds it again). `doc.add_layer` appends and makes the new layer the edit layer by default; with `edit: false` the edit layer stays where it was, in memory and in the saved manifest.
- A layer's storage form is part of the protocol because it is part of the manifest. `doc.add_layer` takes an optional `partition` (`property`, `tile_size`) that stores the layer as tile files instead of one file (`domain/doc/partition.h`, plan 03 §3.7); `doc.set_partition` converts an existing layer between the two forms and rewrites its files, changing no record, so the journal, undo, and redo are untouched. An absent `partition` means one file; a `tile_size` of zero is refused rather than quietly meaning the same thing, so a caller's mistake is not silently accepted. `doc.layers`, `doc.add_layer`, and `doc.set_partition` all return the stack, and each `LayerInfo` reports the form (`partition`, absent for a single file) and the occupied `tiles`.
- `doc.merge` (`MergeParams` → `MergeResult`) is `doc::merge_layers` over three named layers, written into `output_layer` as the diff between what that layer holds and the merged records, applied non-strictly as one transaction: the result reports `applied_ours`, `applied_theirs`, the conflicts with their kind as a string, and the journal index, and the merge undoes like any other patch. A missing `output_layer` is appended to the stack outside the transaction, so undo empties it rather than removing it. Conflicts are a result, not an error; `MergePrefer` (`Ours`, `Theirs`, `Neither`) chooses how they resolve. `SessionManager` opens (or creates) a document directory, returns the existing session for an already-open path, and closes.
- Error codes: standard JSON-RPC negatives; engine codes 1000 SessionNotFound, 1001 DocumentError, 1002 ValidationFailed, 1003 NotFound, 1004 InvalidArgument, 1005 IoError, 1006 Unavailable, 1007 RenderUnavailable ([below](#methods-an-app-registers-and-render)), and plan 06 §6.5's three ([below](#roles-leases-and-proposals)): 1008 Forbidden, 1009 LeaseConflict, 1010 LeaseRequired.

**Methods (day one).** `engine.info`, `engine.methods`; `session.open` (`path`, `create`, `name`), `session.close` (the caller's hold; [several clients](#several-clients-one-host)), `session.list`, `session.info`; `client.hello`, `client.list` ([several clients](#several-clients-one-host)); `doc.layers`, `doc.add_layer` (optionally `partition`ed), `doc.set_partition`, `doc.set_edit_layer`, `doc.objects` (filter by `type` or `parent`, `offset`/`limit`), `doc.get`, `doc.apply` (commands + attribution, `atomic`, and `transaction` to stage into one), plan 06 §6.4's `doc.begin`, `doc.commit`, `doc.rollback` and `doc.transactions` ([below](#transactions-a-client-opens)), `doc.undo`, `doc.redo`, `doc.diff`, `doc.merge`, `doc.validate`, `doc.journal`, `doc.save`; `tunables.list`, `tunables.set`; `log.tail`; `schema.types`, `schema.describe`; and plan 06 §6.5's `lease.acquire`, `lease.renew`, `lease.release`, `lease.list`, `lease.require`, `doc.propose_layer`, `doc.promote`, `doc.reject` and `engine.roles` ([below](#roles-leases-and-proposals)); and `doc.put_blob`, `doc.blob`, `doc.collect_blobs`, `doc.checkpoint`, `doc.checkpoints` and `doc.rollback_to` ([below](#blobs-and-checkpoints)). Parameters and results are documented by their schema types in `schemas/protocol.schema` and by `engine.methods` at run time. engine-host adds `render.*`, `engine.ping` ([below](#engineping-liveness)) and the rest of plan 06 §6.9's day-one list — `content.build`, `session.events`, `engine.budgets`, `session.run_headless`, `engine.run_tests` — and `session.materialize` beside them, and the world capability's `session.state_hash`, `session.save_game` and `session.load_game`, below ([The day-one operations](#the-day-one-operations)).

**Invariants (tested).**
- Parse errors, invalid requests, unknown methods, and invalid params produce the standard codes with the request id echoed (null for parse errors); batches return only the responses of requests with ids and nothing for a batch of notifications.
- A rejected atomic transaction changes nothing and reports every command's diagnostic; a non-atomic one commits what succeeded.
- After `session.close`, a new `SessionManager` on the same path sees the same objects, journal, and undo position; undo and redo continue from where the previous process stopped; a new commit after undo drops the redo tail on disk as well as in memory.
- `doc.add_layer` with `edit: false` leaves the edit layer where the caller had it: the next `doc.apply` and a fresh process on the same path both edit that layer, not the new one.
- A layer added with a `partition` is stored as tile files from the first save: objects placed in different tiles land in different files, a later transaction rewrites only the tile it touched, and `doc.set_partition` without one puts the layer back in a single file. What the next process reads through `doc.objects` and `doc.get` is the same either way (`apps/engine_cli/tests`).

**Public API.** `domain/protocol/rpc.h` (`codes`, `make_error`, `Context`, `MethodDesc`, `read_only`, `Dispatcher`, `add_builtin_methods`, `method`, `method_no_params`), `domain/protocol/listener.h` (`Listener`, `CaptureSource`: the loopback WebSocket, [Transport](#transport)), `domain/protocol/clients.h` (`Clients`, `Client`: [several clients](#several-clients-one-host)), `domain/protocol/session.h` (`Session`, `SessionManager`), `domain/protocol/policy.h` (`Policy`, `Caller`, `resolve_caller`, `forbidden`, `Place`, `place_of`, `glob_match`, the tile-range helpers), `domain/protocol/leases.h` (`LeaseTable`, `lease_covers`), `domain/protocol/proposals.h` (`ProposalTable`, `compose_onto`). Types from `schemas/protocol.schema`.

**Depends on.** `base`, `containers`, `ids`, `json`, `schema`, `log`, `time`, `platform`, `tunables`, `io`, `schemas`, `doc`, and `hash` and `net` for the listener.

**Testing.** `tools/dev.ps1 test -Filter protocol`. Framing and error paths; the method catalogue; the Phase 0 exit criterion end to end over the dispatcher (open, create, apply, objects, get, atomic rejection, undo, redo, redo-tail drop, layers, diff, validate, close, reopen in a fresh manager); a layer added with `edit: false` that leaves the edit layer alone in the session and after reopening; a three-way merge of three override layers with both kinds of conflict, undone and redone, resolved toward theirs into a second layer, and refused for a missing layer, an empty output layer, and an unknown `prefer`; tunables, log tail, and schema discovery, including the default every described field states (a declared default, a value-initialized one, `null` for an optional, an enumerator by name, `[]` for a list); and the day-one operations' types — their declared defaults, the optional fields a result leaves null rather than 0, round trips of a budget, an events page and a run's params through the dispatcher's reader, and an unknown field refused. `tests/policy_tests.cpp` takes plan 06 §6.5 through the dispatcher ([below](#testing-roles-leases-and-proposals)), and `tests/e12_tests.cpp` is experiment E12's driver, a small run of which holds its invariants on every build.

**`gpu.adapters` grew the same additive way.** `engine.gfx.AdapterInfo` is at version 2 with `requirements: DeviceRequirement[]` and `verdict: DeviceVerdict` `@since(2)`, so a client that predates them reads the result it always read, and `DeviceRequirement`, `DeviceClamp`, `DeviceVerdict` and the `RequirementLevel` enum are new types of their own. The answer is the one `Device::create()` would give — the check and the report walk one table in `domain/gfx/requirements.h` ([gfx](gfx.md#what-a-device-has-to-have)) — which is what makes it worth sending back from a machine nobody here can log in to.

**`gpu.displays`: what the displays are and what a window on each is offered** (2026-10-09; E39's first measurement, [the proposal](../experiments/hdr-output-proposal.md); `gfx/display_probe.h`, [gfx](gfx.md#the-hdr-branches-and-the-surfaces-offers)). A `read_only` method with no params whose result is `engine.protocol.DisplaysResult`: `available` and `error`, `swapchain_colorspace` (the loader has the extension without which a surface lists sRGB alone), and `outputs: engine.gfx.DisplayOutput[]` — per output its name, adapter, desktop rectangle, bits per colour, DXGI colour space and `hdr` (Windows' "Use HDR" is on), the panel's primaries and its minimum, peak and full-frame luminance, Windows' SDR white level in nits, and `surfaces: SurfaceOffers[]`, per Vulkan device whether it can present to a hidden window on that output and every format, colour space and present mode it is offered. Windows only (elsewhere `available` is false with the sentence); it shows no window, opens no device and changes no display setting. `engine-cli gpu.displays --report displays.json` writes it as one JSON document.

**`schema.describe` states every field's default.** Each field of a struct's description carries `default` — the value the field holds in a default-constructed object, written through the type's own JSON writer, so it is exactly what an absent field becomes when the protocol reads params and it is in the form a caller would send (an enumerator by name, `null` for an empty optional, `[]` for an empty list); a transient field has none. schemac writes the IDL's declared defaults into the C++ initializers and nowhere else, which is why the method constructs an object to read them rather than keeping a second table. It exists for clients that generate forms or JSON Schema from the catalogue: the MCP bridge builds every tool's input schema this way ([apps](apps.md#engine-mcp-the-mcp-bridge)) and so copies no default by hand. The field is additive — a reader that did not know it reads the description it always read. A field's `type` is the IDL's spelling (`schema::kind_name` for a primitive), so the two f64 vectors of ADR-0053 read `worldpos` and `dvec3` and their defaults `[0.0, 0.0, 0.0]` or the declared one; a client that predates them sees a type name it does not know rather than a float vector, and the MCP bridge maps both ([apps](apps.md#engine-mcp-the-mcp-bridge)).

**Not yet.** Long-running operations (06 §6.8), a listener reachable from another machine, authentication — which is also why a role is what a call says it is ([below](#roles-leases-and-proposals)) — and streaming of large results. The MCP bridge exists and is a client of this protocol rather than a transport for it: engine-mcp spawns engine-host and speaks these methods over its stdio ([apps](apps.md#engine-mcp-the-mcp-bridge)). Method versioning follows schema versioning: adding a field to a params struct is additive; anything else is a new method name.

## Transport

A request reaches the dispatcher one of two ways, and **the dispatcher cannot tell which**: engine-host hands every line of stdin and every text message of a WebSocket to the same `Dispatcher::dispatch_text`, under one lock, so attribution, roles, the read-only rule, leases and the journal see the same request the same way. `transport_tests.cpp` holds that to the byte: one transaction applied over the socket and once on stdin, with the same explicit timestamp, journals identical patches, and a role refused over one is refused over the other with the same error.

- **stdio** — one request per line on stdin, one response per line on stdout. What engine-cli, engine-mcp, the console and CI use; unchanged.
- **WebSocket** — `engine-host --listen 127.0.0.1:<port>` ([apps](apps.md#engine-host---listen-the-protocol-over-a-loopback-websocket), [net](net.md)), and engine-editor's own window ([apps](apps.md#engine-editor-the-engines-window-on-a-document)): RFC 6455 over HTTP/1.1, one JSON-RPC request (or batch) per text message and one response per message, no extensions, no subprotocol. Port 0 picks a free port; the host prints `{"listen":"ws://127.0.0.1:<port>/","token":"...","session":"...","shell":"http://..."}` as its first line of stdout before it serves. engine-host still serves stdin beside it and still ends when stdin closes.

**The listener is the protocol's** (`domain/protocol/listener.h`, `protocol::Listener`; 2026-10-11, roadmap A37). It began in engine-host (`apps/engine_host/listen.cpp`) and moved here when a second host needed it: everything that makes a socket's request a protocol request — the upgrade over foundation/net, the token, the Host and Origin checks, the shell's static files, the dispatch under the host's lock — is the same in every host, so it lives where the dispatcher lives, and `net` is a foundation module, so the layering holds. A listener is made over a `Dispatcher`, the **host's own lock** (a request runs under it; engine-host's stdio loop takes it, and so does engine-editor's frame for everything that reads the document or the selection), and an optional `CaptureSource`: what `GET /capture/<id>[/<part>]` serves is the host's, because only a host keeps captures — engine-host's (`apps/engine_host/listen.cpp`, `HostCaptures`) serves the last eight `render.capture {keep}` made, and a host without one answers 404. `listener_tests.cpp` drives one in process through foundation/net's own client: the token refused and accepted both ways, a page from another origin and a request naming another `Host` refused, the shell's files served with no path escaping the directory, a capture source asked under the lock, and a `doc.apply` round trip; engine-host's `transport_tests.cpp` and the independent .NET client (`tools/host-ws.Tests.ps1`) prove engine-host unchanged in behaviour on top of it.

**Loopback, and a token — not authentication.** The listener binds 127.0.0.1 and refuses any other address with the reason (AGENTS.md's listener rule: a reachable listener is a firewall prompt per executable path, and those prompts have taken the GPU driver down). Loopback stops the network; it does not stop another process on the machine, nor a web page in the user's browser, which may open a WebSocket to 127.0.0.1. So the host makes a 128-bit token from the system's secure random source at start (base64url, 22 characters), prints it once, and closes every connection that does not carry it — `?token=` on the upgrade URL or an `X-Engine-Token` header — with close code 1008 and a reason. A browser's upgrade must also come from the listener's own origin, and every request must name the listener's own address in `Host`, which stops DNS rebinding. **That is all it is.** Whoever holds the token is whoever its requests say they are, exactly as on stdin: the roles file restricts what a *role* may change, and a role is still what a call says it is ([below](#roles-leases-and-proposals)). The token keeps the director session away from processes that were not given the line the host printed; it does not identify a person. Authentication (A4) comes before any listener another machine can reach.

**Not built yet** (roadmap A2's remaining half): the **bulk channel** of 06 §6.2 — a capture the host kept travels as an HTTP GET of its bytes on the same listener (`render.capture` with `keep`, `GET /capture/<id>`), which is a stand-in for it on loopback, and nothing yet streams a large result as binary frames beside the JSON; it waits for a client that needs more than a capture on loopback (a remote one, or a live viewport over the socket), since on loopback the GET costs one more round trip and nothing else. **TLS** and **a remote listener** wait for authentication (A4). One host is shared by several clients — each its own caller, holding its own sessions and leases and giving them back when it goes ([several clients](#several-clients-one-host), A3).

### Events

A client on a socket may ask to be **pushed** what changes instead of asking for it (2026-10-11, roadmap A2): `session.subscribe {session, kinds}` and `session.unsubscribe`, both registered `read_only` — they change no document, lease or host setting, only what this connection is sent, like the poll of `session.info` they replace. Each event is a **JSON-RPC notification** from the host, `{"jsonrpc":"2.0","method":"event.<kind>","params":{...}}` with no id, sent **on the subscriber's own connection, in order, after the change it reports is committed** — the session publishes after the commit is journaled and saved, an undo or redo after the step is saved — never before.

| kind | params type | published by | when |
|---|---|---|---|
| `journal` | `JournalEvent` | the session (`session.cpp`) | a transaction committed, undone or redone: `action`, the patch's `index`, its `layer` and `attribution`, the record ids it touches (at most 1024, `ids_total` says how many), the document `revision` after it, `journal_length`, `undo_position` |
| `selection` | `SelectionEvent` | engine-editor (`EditorDocument::select`) | the editor's selection changed: a click in its viewport, `editor.select`, a delete that cleared it. engine-host has no selection and never sends one |
| `scene` | `SceneEvent` | engine-host's `render.load {session}` | a session's scene followed its document after a transaction: `change` "moved" (with `moved`) or "rebuilt", `instances`, the `revision` it now shows. A load that found nothing to do sends nothing |
| `session` | `SessionChangeEvent` | the session manager and the session | opened, closed, a lease taken or released (with its id, holder and layer) |

`session` empty subscribes to every session the host has, including ones opened later; `kinds` empty is all four. Subscribing adds kinds to what the connection already has for that session; the result names what it holds now, the queue's bound and the connection's number. `session.subscriptions` (read-only, any transport) lists every connection's subscriptions and how many events each has had dropped since it was last sent one — an operator's view of who is behind.

**Events carry no content.** Ids, indices, revisions and attribution, never a property value: a subscriber that wants the record reads it through `doc.get` or `doc.objects`, under its role, exactly as it would have after a poll. So subscribing grants nothing a read did not, and an event can never carry a value the reader's role should not see.

**What stdio refuses.** A dispatch that did not come from a connection has `Context::connection` 0, and `session.subscribe` there is refused with 1006 Unavailable naming why: stdio is a request-and-answer pipe with no channel to push on, and the answer tells the caller to poll `session.info`'s `journal_length`. An in-process dispatcher (the editor's own calls, the console) is the same.

**The queue, and why a slow subscriber stalls nobody.** The registry (`domain/protocol/events.h`, `Subscriptions`; owned by the listener, which wires it into the dispatcher's context and the session manager when it is made) is written under the host's lock, by the code that made the change, which is what orders the events. It formats each notification once and posts it to each subscriber's connection through the listener, and the server queues it there (`net::Server::post`, [net](net.md#pushing-to-a-connection)); a writer thread of that connection's own sends it, **outside every lock**. A subscriber that stops reading fills its socket's buffers, then its queue — **256 events by default, the tunable `protocol.events.queue`** — and past the bound an event is not queued: it is dropped and counted, and the next event that connection is sent carries `dropped`, the count, so it knows to read the state again (the shell refreshes everything). Nothing waits: not the host's lock, not the writer's connection, not the other subscribers. A dropped count is told with the next event, so a subscriber that resumes after the last change of a burst learns of the gap only at the next change; one that cares sooner compares `journal_length` with `session.info`. At a few hundred bytes an event (a thousand ids at most), the bound costs a stalled subscriber at most a few megabytes. Measured on Windows loopback with the bound at 4: the socket's buffers took about 80 journal events of 64 ids each before the queue filled (`transport_tests.cpp`, "a subscriber that never reads").

**Testing.** `apps/engine_host/tests/transport_tests.cpp`: a second connection is pushed the first's commit, commit, undo and redo in order with the right indices, journal lengths, undo positions and rising revisions, and a lease's `session` events; stdio's refusal, and nothing but answers on stdout; unsubscribing stops them; a connection that never reads, with the bound set to 4 through `tunables.set`, drops events while the host goes on answering the writer, and once it reads, every gap in the indices it was sent is exactly the `dropped` the event after it carries; and on a GPU, `scene` events after a move and a rebuild. `apps/engine_editor/tests/editor_tests.cpp`: `selection` events for `editor.select`, for the viewport's own path and for the scripted pick's (`EditorInput::pick`, on a GPU). `tools/host-ws.Tests.ps1`: .NET's client receives one `event.journal`. `tools/mcp-check.ps1 -Connect`: a plain client on the host is pushed each of an attached engine-mcp's commits ([apps](apps.md#attached-to-a-running-host---connect)).

### Several clients, one host

One host serves several clients of one document at once (2026-11-17, roadmap A3): the owner's shell in a browser or in engine-editor's window, an agent's bridge attached with `engine-mcp --connect`, and a command line on the host's stdin. What makes them several clients rather than several pipes into one caller is six rules, all in this module (`clients.h`, `session.h`, the listener), so engine-host and engine-editor behave alike:

- **Each is its own caller.** `client.hello {name, attribution}` (`ClientHelloParams` → `ClientInfo`, read-only, socket connections only — stdio is answered 1006, since its caller is the host's own `--actor`) says who the connection is: a label for an operator (`name`, "shell", "engine-mcp") and the actor, role and task its calls run as. Every blank `actor`, `role` and `task` of a later call on that connection is filled from it **before** the host's identity (`resolve_caller` in `policy.h`, and the dispatcher's role gate reads the role the same way), so an agent's edit names the agent without repeating it, and a connection that said it is QA is refused a write as QA. That is every write that names a caller: `doc.apply` (and its staging into a transaction), `doc.undo`, `doc.redo`, `doc.merge`, `doc.begin`, `doc.commit`, `doc.rollback`, `doc.place_asset`, `doc.instantiate_template`, D13's `doc.put_blob`, `doc.collect_blobs`, `doc.checkpoint` and `doc.rollback_to`, the leases and the proposals; `doc.transactions`, `doc.describe` and `doc.query` are reads that name nobody (the first filters by an `actor` the call gives, empty for all). A role the roles file does not have is refused at the hello (1008). It is a declaration, as a call's attribution is (roles are guardrails, [below](#identity-and-what-a-role-restricts)); a credential that carries identity is A4's. engine-mcp says hello on every connection with its `--actor`, `--role` and `--task`; the shell with a name alone, since it edits as the host's identity.
- **One document, writes in order.** Every request from every client runs under the host's one lock ([Transport](#transport)), so transactions land one at a time in the order the host received them, and every commit, undo and redo is pushed to each subscriber in that order with a rising `revision`. `JournalEvent` and `SessionChangeEvent` (version 2) carry `connection`: the connection whose call made the change, 0 for stdio, the host itself and the engine's own write-back — so a client tells its own changes from the others' without matching attributions.
- **A session is held per client.** `session.open` of a document already open returns its session and adds the caller to its holders (`SessionInfo.holders`, version 2: connection numbers, 0 for the host's stdio and its `--doc`); `session.close` lets go of the caller's hold alone (`SessionCloseResult`: `closed` false and the holders left while anyone else holds it), and a session closes with its last holder. Closing a session the caller never opened is refused (1004, naming the holders): one client cannot close the owner's document under everyone else. The host's own clean-up of a session it just opened (`SessionManager::close`) closes it whoever holds it.
- **A lease stands against the other clients.** A lease is its actor's, as before, and it now also records the connection that took it (`LeaseInfo.connection` and `host`, version 2): the agent's lease refuses the shell's edit and the command line's alike (1009, whose `data.lease` names the connection).
- **A client that vanishes gives back what it held.** When a connection ends — closed, or dropped without a close frame — the listener, under the dispatch lock, releases every lease it took (each saved to `leases.json` and pushed as `event.session` "lease_released" with `reason` "connection closed"), then its holds, closing each session nobody else holds ("closed"), then its subscriptions and its entry. A lease a connection took therefore lives no longer than the connection — an agent that dies cannot hold tiles for the rest of a ttl nobody will renew — and one a host that has gone left in `leases.json` is dropped when the document is next opened, since `host` names another process (two hosts on one document at once is unsupported). **A lease is on a document's records, not on the session**, which is only how the connection reached them: `session.close`, even by the last holder, leaves the closer's leases as they are, so a client that closes and reopens a document while it is connected still holds them, and so does any other connection's lease in that session. A connection that drops while a session holding its lease is closed is still let go of it: the session manager remembers each connection that held a lease in a session closed under it (`SessionManager::detached_`), moves it to the ended ones when it drops (`ended_`, only those, so the list is bounded by the leases taken, not by the connections served), and the document's next open in this process drops this host's leases of ended connections before anyone can be refused by them (`Session::drop_ended_connection_leases`), as it drops another process's. Nothing is refused in between, since a closed document's leases are asked by nobody in this process. Leases taken on stdio carry connection 0 and keep their ttl, which is what engine-cli's host per call needs.
- **A transaction is its connection's while the connection lasts.** A transaction is its opener actor's ([below](#transactions-a-client-opens)), and two clients may say in their hellos that they are the same actor, so the actor alone would let the second commit, stage into or roll back the first's work. A transaction begun on a socket connection is therefore also held by that connection in the session, in memory (`Session::transaction_holds_`, never in `transactions.json`, since connections are this process's and a transaction outlives the host a call started): while it lasts, a call from any other connection or from stdio is refused 1008 with reason `transaction owner`, even under the opener's actor. When the connection ends the hold is let go with its leases and the transaction is the actor's again, **still staged**, not rolled back — the agent that reconnects (engine-mcp after a deadline, a new connection number) commits what it staged, as engine-cli's host per call does. One begun on stdio (connection 0) is held by no connection, as before. A session closed by its last holder keeps its transactions in `transactions.json` and the session manager keeps their holds (`SessionManager::parked_`), giving them back when the document is next opened, so a twin cannot take a transaction over by closing and reopening the document while its opener is connected; a dropped connection's parked holds go when it drops. A transaction nobody comes back to lapses at its `ttl_seconds`: nothing staged ever landed, and the next call that reads the table on that document rolls it back.

`client.list` (read-only, any transport; `ClientsResult`) is the operator's view: every connected client in connection order with its name, identity, requests made, the sessions it holds and its leases as `<session>:<id>`, and `you`, the asking connection.

**What it costs.** Nothing on a path that has one client: a connection's entry is one walk of a table of tens on each request, the identity a few string copies when a call leaves a field blank, and a session's holders a short sorted list. Release on a drop is one walk of each session's lease table.

**Testing.** `transport_tests.cpp`, "three clients of one host, one document, and a client that drops": a shell and an agent on two connections and the command line on stdin, with leases required; the hellos, a role nobody configured and an overlong name refused, stdio's refusal; the agent opening the host's document (one session, holders the host and the agent) and one of its own; its lease and its edit attributed by its hello and pushed to the shell with its connection; the lease refusing the shell and the command line; a third connection that said it is QA refused a write by the role gate; `client.list` from stdio; a close that lets go of the agent's hold alone, and the shell refused closing what it never opened; the agent dropped without a close frame, the shell pushed the lease's release with its reason and the closing of the agent's own session, in that order; and the shell then leasing the freed type and committing in order behind a refused command line, each event with a later revision. "a client's transactions and placements are its hello's, its connection's": a transaction begun, staged and committed and a `doc.place_asset`, every call naming nobody, attributed to the hello's actor, role and task (not the host's `--actor`) at the begin and in the journal's entry; a second connection whose hello names the same actor refused staging into, committing and rolling back the first's transaction while the first is connected, and committing a second one after the first drops, with the opener's attribution. "a lease and a transaction outlive their session's close, not their connection": a connection leases a type for a day, begins and stages a transaction and closes the document it alone held; reopened by a twin of the same actor, the transaction is refused to the twin and the lease refuses another client; the connection drops with no session naming either, and at the next open the other client leases the type, the twin commits the transaction, and the only lease left is the new one.

### The editor's methods

engine-editor runs a listener in process over a dispatcher round the session it holds (`apps/engine_editor/editor_methods.h`), with the built-in methods every host has and three of its own (and a fourth for its tests), which are what the web shell embedded beside its native viewport and the viewport share beyond the document ([apps](apps.md#engine-editor-the-engines-window-on-a-document), [engine_shell](engine_shell.md#embedded-in-the-editor)):

- **`editor.layout`** (`EditorLayoutParams` → `EditorLayoutResult`), sent by the page as a **notification**: the viewport cell's rectangle in CSS pixels from the page's corner, the page's device pixel ratio, and (version 2) whether the page is in its narrow layout, on load, on a split drag, on a resize, when the ratio changes and when the editor asks (`editor.relayout`, below). The editor moves its viewport's child window there: CSS pixels times the ratio are the window's pixels, divided by the window's pixels per coordinate unit, rounded outward so the cell is covered. Sent as a request, it answers with that rectangle and the count of layouts received. A rectangle of non-finite numbers, a negative size or a ratio of zero is refused (external input is validated, never asserted on).
- **`editor.select`** (`EditorSelectParams` → `EditorStateResult`): the outliner's choice — a live record of the editor's session, or null to clear — so the viewport outlines it and the gizmo attaches. A record that does not exist is 1003 and the selection stays.
- **`editor.state`** (no params → `EditorStateResult`): the session, the selected record, the viewport's camera as of its last frame in `render.capture`'s shape (`RenderFramedCamera`, A32), the last layout and the picture's size. The page reads it once it connects; a click in the native viewport reaches the outliner as an `event.selection` ([events](#events)), which replaced the half-second poll of this method.

- **`editor.tool`** (`EditorToolParams` → `EditorStateResult`, read-only; 2026-10-12, A39): the viewport gizmo's tool, `"translate"` or `"rotate"`, which the editor's T and R keys set too; anything else is refused. `EditorStateResult` version 2 carries it as `tool`. When the tool changes — by the method or by a key — the editor sends every connection an **`editor.tool` notification** with params `{tool}`, so the page's toggle follows a key pressed in the viewport.
- **`editor.pick_file`** (`EditorPickFileParams {filter}` → `EditorPickFileResult {path?}`, read-only): the platform's open-file dialog on the editor's window, offering the extensions in `filter` (empty: the three mesh formats), answering the chosen path or null. The dialog runs on the editor's own thread — the method hands the request over and waits with the dispatch lock released, so the viewport keeps drawing — and only in a window run with no test flag: anywhere else (a test, `--offscreen`, a dispatcher with no window behind it) it answers null at once, so no test ever opens a dialog.
- **`editor.import_mesh`** (`EditorImportMeshParams {path, name?, at?}` → `EditorImportMeshResult {id, name, mesh, translation, copied, reused}`) is a **write**, registered unmarked so roles govern it: it copies a `.gltf` (with the buffers and images it names), `.glb` or `.clusters` file into the document's `assets/<stem>/`, then applies **one transaction** creating an `engine.scene.MeshPlacement` named after the file (or `name`), its `mesh` the copy's path relative to the document, at `at` or — absent — where the viewport's line of sight meets the ground within 50 m, else 10 m in front of the camera, with the rationale `import <file>`; the new record is selected and the viewport rebuilds with it. Every check comes before a byte is written — a missing file, another extension, the loader's own refusal (`assets::load_gltf`, `geometry::read_cluster_file`), a file the `.gltf` names that is missing or outside its directory, a destination holding other bytes — and is refused with the reason (1004), the document untouched; the same bytes already there are reused, so importing a file twice copies it once. A transaction the session refuses removes what was copied (1001).
- **`editor.relayout`** goes the other way: a **notification the editor sends** to every connection of its listener (`Listener::notify_all`) when the display's scale under its window changes, asking the page to lay itself out and send `editor.layout` again whether or not its rectangle moved; params `{reason}`. The page answers with a layout; nothing answers the editor. It is the one message the editor speaks first, and it is not a subscription (roadmap A2's are): every page connected to the editor hears it.
- **`editor.test_report`** (`EditorTestReportParams` → `EditorTestReportResult`), registered only by `engine-editor --test-page`: the embedded page's test hook reports one of its own checks (`name`, `ok`, `detail`) as a notification, and the editor puts it in its summary ([engine_shell](engine_shell.md#the-test-hook)). An editor started without the flag answers -32601 for it, as engine-host does.

All of them change the editor's UI state and **never a document**, so all are registered `read_only`: a role that may write nothing still lays out, selects and reads, as the editor's test shows with a roles file whose only role names no method. They are **the editor's only**: engine-host does not register them and answers -32601, and a client that wants to know which host it has asks `engine.methods`.
## Methods an app registers, and `render.*`

`add_builtin_methods` is not the whole table. An app may add methods of its own, and engine-host does: `render.load`, `render.capture`, `render.benchmark`, `render.compare`, `render.evaluate`, `render.unload`, `render.scenes` and `render.progress` ([apps](apps.md), [renderer](renderer.md)) live in `apps/engine_host/render_methods.cpp`, not here, because the renderer is layer `systems` and the protocol is layer `domain` — a method over it cannot be registered from below it.

The registration point is **`Context::app`**, a `void*` the app fills and the methods it registered cast back. It is deliberately untyped and deliberately the only one: a handler is a plain function pointer and cannot capture, a file-scope global would make two hosts in one process impossible, and giving the protocol a typed field for every consumer above it would invert the layering. Nothing in `domain/` reads `app`, and a method that does not know what it points at must not touch it. This is the same shape ADR-0027 asks of a capability: attachment through a registration point, and no edit to the thing being attached to.

**Error code 1007, `RenderUnavailable`**, joins the list: a `render.*` method on a process with no usable GPU — no Vulkan loader or driver, no 64-bit buffer atomics, or no cluster acceleration structures and ray queries when `"raster":"rt"`, an explicit `"shadows":"rt"` or the reference integrator was asked for, in which case the message is the adapter's own verdict sentence naming the missing extension ([renderer](renderer.md#the-offscreen-contract)). It is a code of its own rather than 1006 `Unavailable` so that a client can tell "this machine cannot render" from "this host has no log ring" and from 1004 "you asked for something wrong". That distinction is what lets one end-to-end suite run on the hosted CI runners and on the GPU machines: `apps/engine_cli/tests/render_tests.cpp` skips on 1007 exactly as engine-view's suite skips on exit 3, and asserts on everything else.

The eight methods are schema-typed like the rest (`RenderLoadParams` → `RenderSceneInfo`, `RenderCaptureParams` → `RenderCaptureResult`, `RenderBenchmarkParams` → `RenderBenchmarkResult`, `RenderCompareParams` → `RenderCompareResult`, `RenderEvaluateParams` → `RenderEvaluateResult`, `RenderUnloadParams` → `RenderUnloadResult`, `render.scenes`, which takes no params, → `RenderScenesResult` of `RenderLoadedScene`s, and `render.progress`, which takes none either, → `RenderProgressResult`, with `RenderSettings`, `RenderCamera`, `RenderOrbit`, `RenderReference`, `RenderMetrics`, `RenderStats`, `RenderGpuMs`, and `RenderStreamStats` shared between them), so `engine.methods` lists them and `schema.describe` explains them with no special case anywhere. Their string fields — `raster`, `shadows`, `view`, `deform`, `weights`, `integrator` — are parsed by the same functions engine-view's flags are, so a spelling can never mean one thing on the command line and another over the protocol.

**`render.evaluate` is [04 §4.8](../plan/04-renderer.md#48-reference-renderer-and-objective-optimization)'s loop as one call**, which is what [06 §6.9](../plan/06-agent-tooling.md#69-day-one-operations) means by exposing it to agents as a single tool. Everything it does can be done with `render.capture` twice and `render.compare` once; the point is that a proposal is accepted or rejected on **one** answer taken under one camera, one frame number and one set of lights, rather than on three calls a script has to keep in step. It renders the real-time picture, renders the reference of the same frame, optionally renders the reference again at a single bounce, compares, writes `<name>.realtime.png`, `<name>.reference.png`, `<name>.flip.png` and (with `direct_only`) `<name>.reference_direct.png` and `<name>.flip_direct.png`, and returns both sets of metrics, the real-time statistics, the times and the machine state. The `direct` metrics are there because the difference between them and `full` is **the indirect light the real-time path does not have**, which is what makes a per-scene FLIP threshold explicable rather than arbitrary.

Two schema fields are additive, as the versioning rule requires: `RenderCaptureParams` gained `integrator` (`"realtime"`, the default and what every earlier caller got, or `"reference"`) and a `reference` block at version 2, and `RenderCaptureResult` gained `integrator`, `samples`, `trace_ms` and `seconds`. A reference capture has **only a color channel** — a path tracer writes no visibility buffer, so asking it for `ids`, `depth` or `normals` is 1004 with a message rather than a buffer of nothing, the same rule `"raster":"direct"` follows. Both the reference integrator and `render.evaluate` answer 1007 on a device without cluster acceleration structures, or with settings that build none (`"shadows":"rt"` or `"raster":"rt"` is what turns the chain on), so the end-to-end suite skips on them exactly as it skips on a machine with no GPU at all.

**Geometry streaming went the same way** ([04 §4.9](../plan/04-renderer.md#49-streaming-and-residency), [apps](apps.md#streaming-pages-at-run-time---stream)): `RenderSettings` is at version 3 with `stream`, `page_budget_mib` and `upload_budget_kib` `@since(3)`; `RenderLoadParams` is at version 3, with `page_bytes` `@since(2)` and `procedural` `@since(3)` (which procedural scene an empty `mesh` and `scene` build — `""`/`"heightfield"`, or `"shredded-atlas"`, the UV-atlas LOD fixture the scene corpus draws; an unknown name is an invalid-argument error rather than a silent fall back to the terrain, because a corpus scene that quietly got the wrong mesh would guard nothing); `RenderStats` is at version 4 with a `stream: RenderStreamStats` block `@since(4)`; and `RenderStreamStats` is the whole of `renderer::StreamStats`, field for field, under the key names engine-view's `streaming` summary object already uses, so one reader serves both hosts. Every one of them defaults to what a caller before them got — no streaming, no page table, and a `stream` block whose `pages_total` is 0.

Three things about that set are worth the sentence they cost, because each one is a question a reader will otherwise have to answer by reading code.

**The units differ on purpose.** The protocol says `page_budget_mib` and `upload_budget_kib`; `renderer::RenderSettings` says `page_budget_bytes` and `upload_budget_bytes`. The wire is where a *person or an agent chooses a number*, and the two numbers are chosen at different scales — a residency budget is a fraction of a scene and an upload budget is a fraction of a frame — which is why `engine-view --page-budget` takes MiB and `--upload-budget` takes KiB and why the protocol spells them the same way rather than inventing a third spelling. The renderer sizes buffers, so it counts bytes. The conversion is four lines in `read_settings` (`apps/engine_host/render_methods.cpp`), which is the one place the wire meets the module, and `systems/renderer/settings.h` is therefore never in the position of having to say what unit its caller was thinking in. The end-to-end case pins it by asking for 1 MiB against a scene of 3.8 MB of pages and checking that `budget_bytes` comes back as 1048576 rather than clamped.

**`page_bytes` is a load parameter, not a render setting.** It is `SceneDesc::page_bytes`, and it sits on `RenderLoadParams` because laying a mesh out in pages **renumbers its clusters** — it changes what loading *produces*, not how a frame is drawn. A host that keeps a `SceneData` across calls (this one does; that is what a scene id is for) cannot have it as a setting, because a settings change rebuilds only the GPU buffers and the pipelines from the `SceneData` that is already there. It applies to the procedural heightfield alone, for the reason `scene.h` gives: a glTF's and a container's layout is fixed at the default target because that target is part of `geometry::cluster_cache_key`, and two targets would be two different containers. `settings.stream` on `render.load` is the separate question of whether the page table is kept at all; asking a later call to stream a scene that was loaded without one turns streaming off with a log line rather than failing, which is `resolve_settings`' rule and not a protocol special case.

**Shadow casters went the same way** (2026-09-24, [renderer](renderer.md#shadows)). `RenderSettings` is at version 4 with `shadow_casters` `@since(4)`. It defaults to `true`, the renderer's own default, and `false` is `engine-view --no-shadow-casters`. `RenderStats` is at version 5 and `RenderViewStats` at version 2, each with a `shadow_casters` count, which is not part of `visible_pairs` because nothing draws a caster. `view` also accepts `"shadow"`, the resolve's shadow view, through the same `parse_view_mode` engine-view's flag uses. (And `"albedo"`, the textured base colour unlit, since 2026-09-24: the same parser, so no schema change; [renderer](renderer.md#built-textures).) Every one of them reads as before for a caller that does not send it. The one behaviour change is the default: a scene loaded with traced shadows now builds its casters, and a client that wants the old frames asks for `"shadow_casters": false`.

**The ray tracing chain's memory went the same way** (2026-09-24, [renderer](renderer.md#the-ray-tracing-chains-memory)). `RenderSettings` is at version 5 with `rt_budget_mib` `@since(5)`, the most device memory the per-frame cluster acceleration structures may take (0 is the `renderer.rt.budget_mib` tunable, and that tunable's 0, its default since 2026-10-27, a sixteenth of the device's memory from 512 to 4,096 MiB: [renderer](renderer.md#the-budget-follows-the-device)); it is `engine-view --rt-budget-mib`. `RenderStats` is at version 7 with an `rt: RenderRtStats` block `@since(7)` — the capacity now and at its peak, the budget as a capacity, the scene's union, the bytes now and at their peak, the last frame's built and wanted counts, the resizes, and the frames that dropped instances' structures — under the key names engine-view's `rt` summary object uses. The flythrough summary (`engine.scene.FlythroughSummary`, version 2) carries the same totals in its own `rt` block with per-frame percentiles of what was built and wanted, `FrameRecord` (version 2) carries `rt_built`, `rt_wanted` and `rt_capacity` and streaming's per-frame state, and `PassMs`/`PassPercentiles` (version 2) add the bottom-level build `blas` beside `clas`. A caller that sends none of it gets the renderer's defaults and reads the old fields unchanged. `RenderStreamStats` is at version 2 with `pool_pages` and `steals` `@since(2)` ([renderer](renderer.md#admission-never-waits-on-a-read-it-cannot-start)).
**The cascaded shadow maps added a spelling, three settings and four numbers** (2026-09-24, [renderer](renderer.md#cascaded-shadow-maps); it landed after the chain's sizing above, so a struct both changed is one version past that one's). `RenderSettings` is at version 6: `shadows` also accepts `"csm"` (parsed by the same `parse_shadow_mode` engine-view's flag uses), and `shadow_cascades` (1..4, default 4), `shadow_map` (64..4096 texels, default 2048) and `shadow_distance` (0: the far side of the scene's bounds) are `@since(6)`, validated in `read_settings` like the view fields. `RenderGpuMs` is at version 2 with `shadow` and `shadow_cull` `@since(2)`, and `RenderStats` at version 8 with `shadow_pairs` and `shadow_fallback` `@since(8)`; the results' `shadows` string says `"csm"` when that is what ran. On the scene side (`schemas/scene.schema`), `PassMs`, `FrameRecord`, `PassPercentiles` and `FlythroughSummary` are at version 3 with the same numbers per flythrough frame and over the path. Every one of them reads as before for a caller that does not send or read it. **The one behaviour change is the default on a device that cannot trace**: `"auto"` there used to draw no shadows and now draws the maps, so a client on the TITAN Xp that wants the old frames asks for `"shadows":"off"`.

**Texture sharing added a setting and two counts** (2026-09-25, [renderer](renderer.md#one-upload-per-distinct-image)). `RenderSettings` is at version 7 with `share_textures` `@since(7)`: `true`, the renderer's default, uploads one texture per distinct image content and lets every mesh that samples it share it; `false` is `engine-view --no-texture-sharing`, every mesh its own copy, as before, to measure against. `RenderLoadedScene` and `RenderUnloadResult` are at version 2 with `textures_shared` and `texture_bytes_saved` `@since(2)` — the sampled images that took another mesh's texture, and the bytes their own copies would have taken — and `textures` beside them now counts distinct textures. On the scene side `FlythroughSummary` is at version 6 with a `textures: FlythroughTextures` block `@since(6)`, the same numbers engine-view's summary line prints. A caller that sends none of it reads what it always read, and draws the same picture with less device memory. `FlythroughTextures` is at version 2 since 2026-10-27 with `normal_variance` and `normal_variance_bytes` `@since(2)` (R97, [renderer](renderer.md#normal-filtering-r97)): counts, and nothing a caller sends.

**The vertex path's indexed draw added two counts** (2026-09-24, [renderer](renderer.md#statistics)). `RenderStats` is at version 6 with `triangles_hw` and `vertex_fallback` `@since(6)`: the triangles the baseline tier's indexed draw drew in the last frame, and the clusters its index budget sent to the capacity draw instead. Both are 0 on every other path and for a caller that predates them, and nothing about a request changed — the draw is chosen by the device's `geometryShader` and `fullDrawIndexUint32` features, not by a setting. `RenderViewStats` did not grow: the counts are summed over the views, because the question a caller asks of them is whether the frame fell back at all, and `renderer::ViewStats` keeps the split for a caller in-process.

**`render.capture` needed no field** (2026-09-24; it has had a `settings` override since 2026-10-03, below). It had no `settings` block at all — it renders with the settings the scene was loaded with (`scene->requested`) — so it inherits streaming from `render.load` and adding a `stream` field there would have been a second way to say something the scene already says, and a way that could contradict it. `RenderBenchmarkParams` has had an optional `settings: RenderSettings?` since version 1, so it gets the three new fields with no change of its own, and a per-call block that turns streaming off rebuilds the GPU scene whole exactly as any other settings change does. That is what the end-to-end case asserts second, because a `pages_total` of 0 from a scene that has a page table is the only evidence that the additive field travelled all the way into the renderer rather than being decoded into a struct nobody reads.

**Not yet: the container-backed page source.** Over the protocol a streamed page's payload always comes out of host memory — `stats.stream.source` is `"host"` — where engine-view's `--page-source file` can read it back out of the meshes' `.clusters` containers instead. The blocker is not plumbing. `renderer::attach_page_source` **releases the merged host streams** as the other half of what it does, which is the whole point of it, and those streams are exactly what `RenderHost::ensure_renderer` rebuilds a `GpuScene` from when a later call changes the settings. engine-view may release them because it builds its scene once and never again; a host whose `render.benchmark` may be handed `{"stream":false}` for a scene loaded with `{"stream":true}` may not. Attaching one means either refusing that rebuild or re-opening the source against each new `GpuScene`, and neither is worth building untested — every scene this host can construct without a content fixture is the procedural heightfield, which has no container behind it and would be refused a file source anyway. When it is done, `source`, `file_reads`, `file_bytes` and `host_bytes_freed` are already in the result waiting for it.

**`render.benchmark` flies a camera path** (`RenderBenchmarkParams` version 2, `RenderBenchmarkResult` version 3). A `camera_path` names an `engine.scene.CameraPath` file, read against the loaded scene's terrain, and the run becomes a flythrough: `repeats` flights of the path at its own frame count (or `path_frames`), each after `warmup` frames and `warmup_seconds` at its first camera, and the result gains `flythrough`, the `engine.scene.FlythroughSummary` `engine-view --benchmark` ends its `.jsonl` with — per-pass percentiles over the path, the hashes that name what was measured, and the machine state. Both hosts fly it through `renderer::fly_camera_path`, so the numbers are the same numbers; `frames` is ignored when a path is given, because a path says how long it is. `RenderLoadParams` version 4 adds `overlay`, the local manifest that replaces a scene file's meshes by content hash ([renderer](renderer.md#scenes-camera-paths-and-flythroughs), [apps](apps.md#flythroughs)). The schema types come from `schemas/scene.schema`, which `protocol.schema` imports, so `schema.describe` explains the summary as it explains any result. `FlythroughSummary` went to version 4 on 2026-09-24 with `cpu_ms` and `frame_ms` percentiles (the CPU's milliseconds per frame and the wall time between frames, which `fly_camera_path` now measures), `ticks` and `interactive` (engine-view's interactive sessions; zero and null here), all `@since(4)` with defaults, so a client that read version 3 reads the same fields ([renderer](renderer.md#scenes-camera-paths-and-flythroughs)). Version 9 (2026-09-27) adds `sun`, the stand-in sun's day engine-view can run ([renderer](renderer.md#the-suns-day)); `render.benchmark` carried it as null until 2026-10-03, when the host began to run the clock and the time-lapse (below).

**One request, two hosts** (2026-10-03; [renderer](renderer.md#one-request-two-hosts)). The sky's hour and exposure ([ADR-0048](../adr/0048-the-sky-is-a-providers-model-drawn-by-the-renderer.md)), the ground's time, and the ground on rings or on the world's tiles ([ADR-0050](../adr/0050-the-ground-is-drawn-from-the-worlds-tiles.md)) had landed behind engine-view flags with nothing in `render.*`, because each host turned its own spelling into `RenderSettings` and `FrameDesc` by hand. The translation is now the renderer's (`systems/renderer/request.h`): `renderer::read_protocol_settings` and `read_protocol_clock` read the wire's types into a `renderer::RenderRequest`, engine-view's flags fill the same struct, and both hosts hand it to the same `settings_for`, `frame_clock`/`frame_at`, `flight_clock`, `view_set_desc` and `MovingGround`. `request_tests.cpp` names every field of `RenderSettings` and `FrameDesc` with the wire field that reaches it or the reason none does, by structured bindings that stop compiling when either struct grows, and holds every wire field to reaching what it names. What was added, every field optional with a default that is today's behaviour:

- **`RenderSettings` version 10**: `exposure_ev` (stops on the sky's rule) and `exposure_ev100` (a fixed EV100), `terrain_rings`, `terrain_tiles`, `deform_pool_mib`, `static_shape_kib`, `morph` (`<name|index>=<weight>` entries over the static shape stage) and `page_budget_pct` — engine-view's `--exposure`, `--exposure-ev100`, `--terrain-rings`, `--terrain-tiles`, `--deform-pool-mib`, `--static-shape-kib`, `--morph` and `--page-budget-pct`. `time_rate` (version 8) is now run: a call whose settings move the ground draws its frames through the motion, a sixtieth of a second each, waiting for its fields as an offscreen engine-view does. **One behaviour changed without a field**: a mesh whose morph channels carry authored default weights now draws them through `render.*`, as it always did in engine-view; the host drew such a mesh unmorphed, which was the hand translation's drift.
- **`RenderClock`** (`clock` on `render.capture` version 3, `render.benchmark` version 3, `render.evaluate` version 2): `time_of_day` (a sky's hour, 0..24) and `sun_rate` (the sun's day, game seconds per real second) — `--time-of-day` and `--sun-rate`. **A call's parameter, not host state**: a capture at 18:12 is a function of its request, and two calls at two hours need no write between them. `render.capture` also takes `settings` now, as the other two did, so every `RenderSettings` field is a per-call parameter of every method that draws.
- **`RenderLoadParams.ground_time_s`** (version 5): the game time a scene file's ground stands at, in place of its terrain's `time` — `--ground-time`, new in engine-view the same day. **A load parameter**, like `page_bytes`, because it changes what loading produces (the terrain mesh, its LOD graph, its cache entry, whatever stands on the ground); a file with no terrain, or no file, is refused. `RenderSceneInfo` version 2 reports `sky`, `ground_time_s` and `ground` (`none`, `mesh`, `levels`, `rings` or `tiles`).
- **`RenderSceneInfo.materials`** (version 7, T103): the material pack directory the load drew generated meshes with — the repository's default whatever `ddc` names, or `""` for none, which is what every test's host answers because the test main switches the default off ([materials](materials.md), "Where the hosts find it").
- **Results**: `RenderStats` version 9 gains `sky` (`RenderSkyStats`: the game time, the day, the hour, the sun's and the moon's azimuth and elevation, the moon's lit fraction and key, EV100, lux, the sky's lux and the exposure, under engine-view's `sun.sky` keys) and `ground` (`RenderGroundStats`: the layout, the rate, the game time, the ground's time, the levels, the chunks, rebuilds, swaps and failures, the upload bytes, the slots' device bytes, and the most the drawn layout fell behind the camera, `max_lag_m` and `max_lag_frames`, as engine-view's `time_lapse.rings` has them); `RenderGpuMs` version 3 gains `sky` and `terrain_upload`. A flythrough's `FlythroughSummary` carries the `time_lapse` and `sun` blocks engine-view writes, from the same functions (`renderer::time_lapse_summary`, `sun_summary`).

- **The far ground** (2026-10-03, [ADR-0051](../adr/0051-the-far-ground-is-the-renderers.md), [renderer](renderer.md#ground-to-the-horizon)): `RenderSettings` version 11 adds `terrain_far_levels`, how many far levels of coarser ground the tiles draw past their outermost ring (0..8; null, the default, is the `renderer.terrain.far_levels` tunable's count, which is what engine-view draws without `--terrain-far`, so a call naming none draws what engine-view draws). `RenderGroundStats` version 2 reports the count drawn as `far_levels`. It came with the far levels themselves, which reached engine-view's flag and the renderer's settings first and `request_tests.cpp` refused until the wire had a field for it.
- **The dither** (2026-10-04, [ADR-0052](../adr/0052-the-picture-is-quantized-once-with-dither.md), [renderer](renderer.md#the-output-encode)): `RenderSettings` version 12 adds `dither`, `true` by default — the output encode's triangular noise of one code step of the target, a function of the pixel alone, engine-view's `--dither on|off`. A call naming none gets what engine-view draws, which is dithered; `false` draws the picture rounded, as every call before it did. `render.*` draws into the renderer's own 8-bit target, so its captures are dithered at 8 bits; the 10-bit window is engine-view's alone. `request_tests.cpp` refused the setting until it had this field.
- **The water's tier** (2026-10-18, [water](water.md#translucent-by-volume)): `RenderSettings` version 13 adds `water_quality`, `"high"` by default — water translucent by volume, the ground under a body seen through its surface — or `"low"`, the surface alone, the picture every call drew before; anything else is refused with a sentence. engine-view's `--water-quality`. It changes what the GPU scene's material table holds, so a call that changes it rebuilds the scene, as any setting does.
- **World positions** (2026-10-06, [ADR-0053](../adr/0053-world-positions-are-f64-and-the-gpu-sees-none.md), [renderer](renderer.md#positions-in-the-files-and-on-the-wire)): `RenderCamera` version 2 has `position` and `target` as `worldpos` and `RenderSceneInfo` version 3 its `center`: three f64, the same JSON numbers, so a request written before names the same camera without its numbers being rounded to a float, a camera 10,000 km out is the one asked for to a nanometre (a float steps by a metre there), and a value outside the cells' reach is refused with its field's path. `read_protocol_camera` takes the camera as it is; engine-mcp's tools describe the fields as `worldpos` by rebuilding.

**Read-only stays read-only.** All of it rides on methods that were `read_only` and stay so: a clock, an exposure or a ground layout changes what one call draws and no document, lease or host setting. A scene whose ground is drawn as terrain levels is rebuilt for every call that draws it — the motion and the tiles carry the calls before — so no call's picture depends on another's.

**What a person at engine-view can ask that a call cannot, and why** ([renderer](renderer.md#one-request-two-hosts) has the whole list): the window, its present mode, pacing, vsync and swapchain (a presenting host's); input, an interactive session, a recording and its replay (a window's); the animation capability's `--animate` and `--morph-animate` (a capability above the renderer, which a host drives through `FrameDesc::joints`; engine-host has no world of animated instances behind `render.*`); a streamed world's ruins (`--world`, the world capability's ring of instances, which engine-view's `ViewWorld` drives — the ground on tiles follows the camera here by the ring's first-fill rule instead); the census, the occlusion check and marker captures (analyses a client composes from captures, or a follow-up); `--uv-seams` and its three companions (a content-build question: `content.build` takes them and `render.load` reads the container); `--page-source file` (the "Not yet" above); and `--tunable` (process state, which engine-host takes at start with `--tunables`).

**A scene id is the host process's, not a document session's.** `render.load` returns `"scene1"`, `"scene2"`, … and the host holds the loaded mesh, the GPU buffers, and the pipelines behind it until **`render.unload`** releases it or the host exits. It is not part of `session.*`, because a rendered scene has no document behind it yet; when it does (a document *is* the scene), the id becomes a property of the session and this pairing goes away.

**What belongs to a scene, and what to a session.** A scene is everything `apps/engine_host`'s `RenderHost::Scene` holds: the loaded `SceneData` (clusters, the LOD graph, instances, materials — the host arrays), and once a capture, benchmark or evaluate has drawn it, the `GpuScene` (geometry buffers, textures, acceleration structures), the `SceneRenderer` (pipelines, screen-sized targets) and, after a reference render, the `ReferenceRenderer`. A session is a document: its layers, journal and undo position, all on disk after every commit. The two never own each other, so **closing a session unloads nothing, and unloading a scene closes nothing**: `render.load` names no session, the same loaded scene serves whichever documents a client is working on, and a scene built from a document does not exist yet. Tying them now would mean inventing an owner — and a `session.close` that quietly freed GPU state another client was measuring. What the host *does* own is the device, which stays open when the last scene goes, because it belongs to no scene and the next load would only open it again.

**`render.unload`** (`RenderUnloadParams {scene}` → `RenderUnloadResult`) takes the scene out of the host's list and lets it go through the renderer's own teardown — the reference path tracer first (it holds the renderer and the GPU scene), then the renderer (whose destructor waits for the device to finish the frames it submitted), then the GPU scene, then the host arrays — which is the same order the host's destructor always used, now one function (`RenderHost::release`). There is no other cache to clear: `engine.budgets` reads the same list, and the derived-data cache is content-addressed files that belong to no scene. The result says what went: the counts, whether there was GPU state and a reference renderer to release, the textures and their bytes, the engine allocator's heap before and after (the host arrays), and the device memory this process used before and after as the driver reports it (VK_EXT_memory_budget, null without it). **The driver's figure counts the allocator's blocks, not its allocations**, so it moves only when whole blocks come or go: a scene small enough to fit in blocks an earlier scene opened leaves it where it was on load and on unload, and a large one — the end-to-end case draws a heightfield at 7680×4320, whose screen-sized targets are allocations of their own — takes it from 137.7 MB to 849.4 MB and unload brings it back to 139.5 MB, the same figure after every further cycle, on the RTX 5090. **Ids are never reused**, so an unloaded id stays dead: every render method given it answers 1003 NotFound — the code a missing scene has always had, so no client needs a new one — with a message that says it was unloaded (`no scene scene3: it was unloaded; render.load it again`), where an id that never existed gets only `no scene scene9`.

**`render.progress`** (no params → `RenderProgressResult`, read-only; roadmap W79) is the process's live load progress ([profiling](profiling.md#the-trace-is-live)): `render.load` follows a plan of its two stages (`scene file`, `load scene`, the same weight each) and its two milestones (`scene_read`, `scene_loaded`), finishes it when the call succeeds, and stops following it however the call ends — so an answer is either the load running now or the last one's record: `active`, `done`, `stage` and `detail` (what runs inside it), `stages_done` over `stages_expected`, a `fraction` that never falls during one load, the `milestones` reached by name, `bytes_read`, `items`, `elapsed_ms`, and a `sequence` that grows with every change. **A method and not a notification**, because what wants it — the editor's shell, an agent's client, a tester's script — polls at its own pace and a notification would need an event kind and a subscription for a value that is only ever read. The limit to know: every dispatch takes the host's one lock, so **a poll waits behind the `render.load` it asks about** on the same host and answers when that returns; the record is readable from any thread without the lock, and answering it outside the lock (a read-only fast path in the listener) is the follow-up that makes it live across connections. engine-view's window reads the same record every loading frame ([apps](apps.md#the-loading-presentation)).

**`render.scenes`** (no params → `RenderScenesResult`) lists what the host holds, in load order: each scene's id, what it was loaded from (`kind` `mesh`, `scene` or `procedural`, and the path or the procedural scene with its grid), its counts, whether its GPU state is built with the frame size and resolved raster and shadow modes it was last built for, whether a reference renderer is kept, and its texture and ray tracing bytes with the images that shared another mesh's texture and what that saved; then the adapter and the process's device memory used and available, and the engine allocator's heap. It **opens nothing**: before any render call the adapter is empty and the memory figures are null, not zero. A client that can unload has to be able to see what is loaded, and before this the only way to learn which scenes a long-lived host held was to remember every `render.load` it had ever sent.

### `engine.ping`: liveness

`engine.ping` (no params → `PingResult {pid, uptime_seconds}`) answers that the host is alive and reading requests. It reads a clock and nothing else — no session, no device, no lock — so asking costs nothing and can never itself be the call that hangs. It is registered by engine-host's `main.cpp`, not here and not beside `render.*`: liveness is a question about the process, and every method list the host serves goes through its one dispatch loop. **There is no generation** in the answer, because a host cannot know how many hosts came before it; the client that starts hosts counts them (engine-mcp's `host_info` reports its count) and compares `pid` to know whether it is still talking to the same process. What a client does with a host that does *not* answer is the client's: engine-mcp gives every call a deadline and replaces the host when one runs out ([apps](apps.md#engine-mcp-the-mcp-bridge), "Deadlines"). engine-host's `--debug-hang <method>` is the test hook that makes such a host on purpose ([apps](apps.md)).

**`Context::app` is now the host's whole state.** It is one pointer, deliberately ([above](#methods-an-app-registers-and-render)), so engine-host points it at a `host::HostState` (`apps/engine_host/host_state.h`) holding the `RenderHost` and an `OpsHost` — the sessions' runtime worlds — and `render.*`'s handlers take `.render` out of it. An app with several families of methods gathers their state behind the one pointer rather than asking the protocol for a second.

**A capability this build left out is 1006 `Unavailable`, with a message naming the switch** — `session.events` with `source: "store"` or an explicit `store` on a host without the store capability, `engine.run_tests` with a `tissue` file on a host without the tissue capability. It is not a code of its own, unlike 1007: to a client it means exactly what 1006 already says, "this host does not offer that service", and the bridge's hint for 1006 already reads that way. A method that merely reports less without a capability says so in its result instead: `session.events`' `store_status` is `"not built"`, `engine.budgets` lists no `audio.*` budgets without audio, and `session.run_headless` runs the scheduler alone and its report says why nothing materialized (below). None of the five asserts on input; every refusal is 1004 with a sentence, and a missing session is 1000.

**`content.build`** is `engine-content build` and `build-all` in the host's process, through `domain/content_build` ([content_build](content_build.md)) — the same code, so the same bytes, cache keys and skip. Give `source` (with `output`, or `cache: true` for the derived-data cache entry the source and the options address; both at once is refused, as engine-content refuses `--cache` with an output file) or `manifest`, not both. `options` are `engine-content build`'s flags as a `ContentBuildOptions`, whose declared defaults are the build's own (the module's test holds them together), and they are the defaults of a manifest's entries, which override `max_triangles`, `max_vertices`, `page_bytes`, `weld` and `atlas` as `build-all` lets them. `ddc` empty is `<repo>/ddc` found above the host executable; `jobs` sizes a job system made for the call — one mesh's primitives are its parallelism, as in `build`, and a manifest's meshes are, as in `build-all`. **An output that already records this source's hash and this build key is skipped**, for a single source as for a manifest — `build-all`'s rule, where `engine-content build` always rebuilds — and `force` rebuilds it. Each `ContentBuildOutput` is a `build-all` line: `status` (`built`, `skipped`, `failed` with `rule` and `error`), path, the identity, bytes, milliseconds, the counts, the validation warnings (`path` is the rule id), `repairs` and `atlas` exactly as engine-content's JSON line has them, `textures`, its share of the texture step, and — with `stats` (the default) — `stats`, the object `engine-content stats` prints for the container. **The texture step runs as engine-content runs it**: when the call has a derived-data root — `cache`, or a named `ddc` — every image the meshes sample is built into `<ddc>/textures/<key>.tex` ([texture](texture.md)) after the containers settle, in manifest and then image order, a texture two meshes share built once, a skipped mesh's textures checked from its container; `textures: false` is `--no-textures`, and the result's `textures` has the totals. A texture that fails is counted there and logged, and does not fail the call, where it makes engine-content exit 1: a protocol result says what happened and leaves the verdict to the caller. A failed entry is a result, not an error, and does not stop the others; an unreadable or malformed manifest is 1005 or 1004 before anything is built. **A generated mesh** (a `.flora.json` palm, a `.rock.json` rock) is given the repository's material pack, `<repo>/content/materials` above the host executable, through the function engine-content calls (`content_build::attach_repository_pack`), so one manifest through either host is the same key and the same bytes (T78, 2026-11-09: until then this host gave a generated mesh no pack; `apps/engine_cli/tests/content_build_parity_tests.cpp`). **Not yet:** a manifest's derived steps (`"clips"`, the audio capability's `.clip`) are `build-all`'s and are not read here ([content_build](content_build.md#derived-steps)).

**`session.events`** reads what has happened to a document, a page at a time. `source` is `"journal"` — the document's committed patches, each an event of kind `"commit"` with its `sequence` (the patch index), `actor`, the whole `attribution`, the `layer`, the command count and `applied` (false in the redo tail) — `"store"`, or empty for both, the journal's first. **The store half is the persistent world's event log** ([store](store.md), [03 §3.5](../plan/03-data-model.md#35-persistent-world-state)) **when the host has the store capability and the document has one**: a document "has one" when its directory holds `world.db`, or `store` names another file. That convention is this method's, because nothing else yet ties a save to a document; it is the smallest one that keeps the two side by side on disk, and the parameter is there so a save kept elsewhere can be read. The log is opened read-only (`read_only`, no journal-mode pragma), and its events come in `(tick, tile, sequence)` order through `store::EventLog::scan` — tick first, because a log is appended in tick order, so a cursor that stopped at an event finds everything appended since after it; the per-tile sequence alone cannot say "after this" for the whole log. A store event carries its `tick`, `game_time_us`, `tile`, `sequence`, `kind` (the schema type id in decimal), `actor` (the origin: deterministic, player, agent, llm or debug), `subject`, `cause`, `depth` and `payload_bytes`; the payload itself is schema-typed bytes the store does not interpret yet, so it is not returned. `since` is where a read with no cursor starts (the journal's first patch index; the log's first tick), `kind` and `actor` filter, `limit` is 1..10000, and `next` is an opaque cursor (`j=<index>;s=<tick>:<tile>:<sequence>`) that moves only past what was returned or filtered out — so it is also what to poll with, and `more` says a matching event was left for the next page. One caveat is the journal's own: a commit after an undo replaces the redo tail at the same indices, so after an undo a poller reads again from `since`.

**`engine.budgets`** names every budget the engine knows today and what uses it, so a client learns what a budget is called before it is exceeded ([ADR-0017](../adr/0017-no-hidden-limits.md)). Each `Budget` is `name`, `doc`, `limit`, `used`, `peak`, `unit`, `source` and `key`, and a `scope`:

| Name | Scope | Limit comes from | Used |
|---|---|---|---|
| `renderer.deform_pool` | process; each loaded scene | `k_default_deform_pool_kib` (8 MiB), a scene's `GpuScene::deform_pool_bytes()` | the last frame's deformed vertices × 12 bytes, and the peak |
| `renderer.page_budget` | process; each streamed scene | `settings.page_budget_mib` (no limit by default: every page) | the resident page bytes |
| `renderer.upload_budget` | process; each streamed scene | `k_default_upload_budget` (256 KiB a frame), or the setting | not tracked per frame |
| `renderer.rt` | process; each scene | `settings.rt_budget_mib`, else the `renderer.rt.budget_mib` tunable, else (its default, 0) a sixteenth of the device's memory, 512 to 4,096 MiB; the process reports `source: "device"` and no limit, each scene its own and where it came from | the per-frame structures' bytes, and their peak |
| `audio.clips`, `audio.voices` | process (with audio); each session's runtime world | the `audio.clip_budget_mb` and `audio.voices` tunables, a world's clip store and mixer | resident clip bytes, live voices |
| `memory.allocations` | process | none: a counter | `mem::allocation_counter()` |
| `memory.heap` | process | none | `mem::total_stats()`, with the peak |
| `gpu.memory` | each adapter | the device-local heaps, or VK_EXT_memory_budget's budget on the device a render call opened | that device's `used_bytes`; unknown otherwise |

**Null is not zero**: a `limit` of null is a quantity counted but not bounded (the allocation counter, whose rule — no allocations in a steady-state frame — is measured where a frame loop runs, not in a host between requests), and a `used` of null is a budget nothing in this host is using yet. The process rows are the defaults a scene starts from; a scene's rows are the buffers it was built with and what its last frames used. **Asking opens nothing**: the adapters are enumerated without a device, and only a device a `render.*` call already opened answers the memory-budget question. `scope` filters by prefix (`"process"`, `"scene"`, `"session"`, `"adapter"`). The names are stable; the end-to-end case pins them and their order.


### `session.run_headless`: the materialized world

`session.run_headless` materializes **the session's document** into **the session's runtime world** and steps it at the fixed step, 60 Hz and 16,667 µs a tick, with no rendering ([06 §6.11](../plan/06-agent-tooling.md#611-automated-playtesting)'s headless `sim` mode): `seconds` of game time rounded to whole ticks (0.5 s is 30), at most 3,600, or until `until` holds, with `seconds` as the most it may run. The world is made by the first call on a session, kept by the host while it runs — so a second call continues from the tick the first stopped at, and a fresh engine-cli call starts a fresh one — and dropped once its session is closed.

**Until 2026-09-24 this stepped a world the document did not populate**, and the page said so in four parts: no mapping from a record's type to the components it becomes, no driver walking a document's records through the materialization hooks, the executor decision open, and no write-back. Each now exists, and each is written up where it lives:

1. **The mapping is data**: a `materialize` declaration in the IDL beside the record type — which components, which property fills which field, unit conversions where both sides declare `@unit`, what the parent becomes, which fields the world may write back — compiled by schemac into a table (`schema::MaterializeRegistry`) the runtime reads with no per-type code ([schema](schema.md#materialization-type-mapping-as-data), [schemas/README.md](../../schemas/README.md#materialize-what-a-record-becomes)). A record type with no declaration stays document-only, by design, and is counted.
2. **The driver** walks the document's live records through its composed index into the scheduler's hooks table, parents before children and then by id, the first call in full and later ones through the document's change feed so an unchanged record costs nothing ([sim](sim.md#the-driver-a-document-through-the-hooks)); the entity store's hook creates each entity keyed by its record's `Id128`, writes its fields and makes the document's parent its `ChildOf` ([ecs](ecs.md#materialization-the-entity-stores-hook)).
3. **One executor**: the engine's scheduler owns the tick and runs flecs' systems inside its phases ([ADR-0038](../adr/0038-the-scheduler-owns-the-tick.md), proposed; `executor` in the result says `"scheduler"`).
4. **Write-back**: at `Persist`, every `write_back_every` ticks (default 60, one game second) and once more when the call returns, what systems changed in the writable fields is committed to the session as one transaction attributed to `system` — so `session.events` shows it as a commit whose actor is `system` — and, when the document keeps a `world.db`, logged as one `engine.world.WriteBack` event per record, origin `deterministic` ([sim](sim.md#write-back), [store](store.md#write-back-events), [doc](doc.md)). Nothing else writes the document from the world.

**Every call materializes first**: the whole document on the first call, and what changed since on every later one — so an agent's `doc.apply` between two calls reaches the world on the next. The result carries that pass as `materialize` (a `MaterializeResult`, below).

**What world the host builds.** With the ECS capability: `sim::SimScheduler`, a flecs world (`ecs::SimWorld`) whose systems the scheduler runs, the entity store's hook first in the hooks table, the engine's world components (`engine.world.Transform`) and every ticking capability the host links — `systems/kinematics` (so `engine.kinematics.Mover` records move), `systems/animation` (over an empty clip library, its hooks after the entity store's) and `systems/audio_system` (over a mixer on the null backend; the host pulls zero frames after each tick so the commands it queues are applied and the ring never fills). Records materialize at **LOD0**: a headless run has no observer to promote from. Without the ECS capability it is the scheduler alone — the fixed step, the tick and the game clock — and a driver with no target, which materializes nothing and says why in its report (`no entity store`); `world` says which.

**The result.** The ticks this call ran, the game seconds they advanced, the wall milliseconds, the predicate's value when the call returned (null without `until`; read after the final write-back, so a document term can turn true on it with the time already out — `stopped` says which ended the loop), the world's own tick and game time, its kind (`"ecs"` or `"scheduler"`), `executor`, the systems it ticks (the flecs systems in registration order, then the scheduler's own table: `sim.write_back`), `entities` (entities with a persistent identity), `materialized` (the entities the driver holds from the document), `materialize` (this call's pass), and `write_backs`/`written_fields` (the commits this call made and the fields they wrote). `RunHeadlessParams` and `RunHeadlessResult` are at version 2; `write_back_every`, `executor`, `materialize`, `write_backs` and `written_fields` are `@since(2)` with defaults, so a client that read version 1 reads what it always read — except that `materialized` is no longer 0 by construction.

**The predicate** reads the document and the live world. `{"object": <id>, "property": <name>, <test>}` is a live document object's composed property; `{"object": <id>, "component": <type>, "field": <name>, <test>}` is a field of the live entity that object materialized into, by the component's qualified name (read through `ecs::component_json`, so the host names no flecs type); `<test>` is `"equals": <value>` (compared as JSON, numbers by value), `"at_least": <number>` or `"at_most": <number>`, and a name may end in `[i]` to take one element of an array — `"position[0]"`. With them `{"object": <id>, "exists": true|false}`, the run's own clock `{"ticks_at_least": n}` and `{"seconds_at_least": s}` (counted in this call's fixed steps), and `all`/`any`/`not` over them. A document term now changes during a run, because write-back writes the document: at the default cadence once a game second, and every tick with `"write_back_every": 1`. A malformed predicate — an unknown term, a key a term does not take, an id that is not 32 hex digits, a term with no test or two, a bound that is not a number, nesting past 32 or more than 1,024 terms — is 1004 naming the path (`until.all[1].object`).

**Streamed tile by tile (`stream`, version 3).** With `stream` — a `HeadlessWorld` — the call does not materialize the whole document: it keeps a **tile ring** round the observers it declares ([world](world.md)) — each a `HeadlessObserver`, whose `position` is a `worldpos` since version 2 (2026-10-06, [ADR-0053](../adr/0053-world-positions-are-f64-and-the-gpu-sees-none.md): f64, refused outside the cells' extent, and the same JSON as before) — and materializes the document's partitioned layers a tile at a time as the ring takes tiles in, through the same driver (`sim::Materializer`'s tile passes, [sim](sim.md#the-driver-a-document-through-the-hooks)). Each observer is a position, a velocity in metres per game second applied every tick, and a weight; the ring's `tile_size` must be the partitioned layers' own (on another grid the document consumer refuses every tile, counted in `refused` with one warning in the log, since one ring tile would then name parts of up to four of the layer's), `rings` are the radii in tiles innermost first (empty: the capability's 1.5, 8 and 24), `hysteresis` is the ring's, and `simulated` says how many rings, innermost first, are materialized and reconciled. What no layer tiles — an untiled layer's records — is materialized whole first, as a streamed game's global records would be, and with it what changed since the last call in the tiles still live, so an edit between calls reaches the world at the next one ([world](world.md#the-hosts), "Edits between calls"). The ring updates once before the first tick with no budget, so the call starts from the whole ring, and then once between every two ticks at the ring's budget (8 activations and 16 deactivations an update by default, the `world.ring.*` tunables), so an observer that outruns the budget fills in over the next ticks rather than stalling one. **With the store capability and `store` (the default)**, each tile is reconciled from the document's `world.db` (created beside it when absent) when it comes in — `SimScheduler::reconcile_tile`, step 1 of [05 §5.5](../plan/05-simulation.md#55-reconciliation-when-a-tile-activates) — and its projections and snapshot are written when it goes, so a tile that comes back reads what it left ([store](store.md)). The ring and its store outlive the call, as the runtime world does, and take the first call's parameters; a later call's observers move it. The result's `streamed` (a `HeadlessWorldResult`) is the call's share: updates and the events by kind, the active tiles after the call in tile order with their rings, the tiles the document consumer materialized and let go with the entities it created and dematerialized (and, since `HeadlessWorldResult` version 2, `arrived`: how many of those created were brought in between passes because a capability's own rule put them in a live tile — the npc capability's schedule index, [npc](npc.md#the-schedule-index); a field `@since(2)`, so a client that read version 1 reads what it always read), the store consumer's reconciled, known, summarized, read-back and written tiles, the ring update's median and worst microseconds and each consumer's milliseconds, and whether the store was kept. A host without the world capability answers a call with `stream` 1006 `Unavailable`, naming `ENGINE_WITH_WORLD`. Both types are new and `@since(3)`, so a client that read version 2 reads what it always read. **The method is still a write**: it was one before (it commits write-back to the document) and it is not registered `read_only`, so a role that lists it gets the stream with it and one that does not is refused, as before ([Roles, leases and proposals](#roles-leases-and-proposals)). The edit that added it is confined to `apps/engine_host/ops_methods.cpp` and the schema; `apps/engine_cli/tests/ops_tests.cpp`'s case "run_headless streams a partitioned document tile by tile round its observers" drives it end to end — a partitioned document of three places (one in the origin's tile, one in the tile east of it, one two kilometres away) under rings of 1.5 and 3 tiles: the four inner tiles materialized and reconciled on the first call with one entity made, the observer moved two kilometres by the next call so the origin's tiles are let go and written and the far place's come in, then walking back at 600 m/s with the budget spreading the tiles over the ticks and the origin's tiles reconciled from what the store kept of them; and rings that do not grow outward refused with a sentence.

**Continuing, and the player (`HeadlessWorld` version 2).** A call that **declares observers** puts them where it says and fills the ring round them with no budget, as before — the first call, or a jump. A call that **declares none** — or names no `stream` at all, on a world that is already streamed — **continues**: the observers go on from where they are and nothing is filled, so the call's `updates` is its ticks, and a run split over calls, or over a save and a load, is the run that never stopped ([world](world.md#save-and-load)). Before version 2 a call on a streamed world with no `stream` materialized the whole document beside the ring, and one with an empty `observers` list emptied the ring; neither was relied on. `player` (a `HeadlessPlayer`, `@since(2)`) makes one of the observers the player: `log` is an input log as `input::InputLog` writes it, its ticks the world's, `map` the action map it was recorded against as JSON (a map whose hash is not the log's is 1004 naming both), `action` an `Axis2` of the map (default `move`), `speed` metres per game second at full deflection, `observer` which one it steers. Each tick the observer moves at the action's value times the speed — x along world x, y forward along −z — instead of at its velocity ([world](world.md#the-player)). The input state is the fold of the log up to the world's tick, so a log handed to a world at tick K catches up first; named again on a later call, a log replaces the one the world has, and not named, the world keeps its own.

### `session.save_game`, `session.load_game`, `session.state_hash`

[03 §3.5](../plan/03-data-model.md#35-persistent-world-state)'s save game and [05 §5.10](../plan/05-simulation.md#510-determinism-and-replay)'s replay assertion, as three methods of the world capability ([world](world.md#save-and-load), [ADR-0042](../adr/0042-a-save-is-the-store-the-document-and-the-drivers.md)); a host without it answers each 1006 naming `ENGINE_WITH_WORLD`.

**`session.state_hash`** (`StateHashParams` → `StateHashResult`) is the persistent-state hash of the session's world ([world](world.md#the-persistent-state-hash)): the clock, the document's live records composed across its layers, and the store's events, projections and snapshots in key order, as 16 hex digits, with each part and its count beside it so a mismatch says where it is; `store` is `"read"` or `"absent"`. A session whose world has not run hashes at tick 0.

**`session.save_game`** (`SaveGameParams` → `SaveGameResult`) writes the session's running world into `path` — a new or empty directory, outside the document's — as a save: the document's directory copied, the store backed up (`VACUUM INTO`, [store](store.md)), the player's input log up to the tick and its map, and a `save.json` manifest naming and hashing every file. The result is the path, the tick and game time, the state hash, whether the world was streamed with its tile and observer counts and whether it has a player, and every file with its size and hash. Between two calls nothing is pending — every `session.run_headless` ends with its write-back flushed — so a save changes nothing in the session.

**`session.load_game`** (`LoadGameParams` → `LoadGameResult`) opens a new session on a save: `path` is the save's directory, `dir` a new or empty one the document and the store are copied into, so the save itself is never written. It refuses, before it copies anything, a save that is not one, one written at a version newer than this build's or in a format this build lacks, and one whose files are not the sizes and hashes its manifest gives, naming the file — 1002. A save written at an older version migrates, and `migrations` lists each step. Then it makes the world at the save's tick and game time, restores its tiles, observers and player, and hashes it: `saved_state_hash` is what the save recorded and `state_hash` the loaded world's, and a load that migrated nothing and does not reproduce it is refused and its session closed. The next `session.run_headless` on the new session continues the run: declare no observers, and hand the player's log over again.

**All three are read-only** in the sense of [Identity, and what a role restricts](#identity-and-what-a-role-restricts): none changes a document, a lease or a host setting. A save writes a new directory from what the session holds, as `doc.save` and `render.capture` write theirs; a load opens a new session on a new directory, as `session.open` with `create` does, and refuses a directory with anything in it; the hash reads. The E2E cases are `apps/engine_cli/tests/save_tests.cpp`: a streamed world with a scripted observer, a player and carts driving across tile edges run 300 ticks, saved, run on to 600; the save loaded in a fresh host, saved again to the same bytes, and run on to 600 with the log handed over; and the starting document run to 600 in one call — one state hash, `c2168e9307bca23b`, on MSVC, Clang and GCC; then a whole-document world saved and loaded into a second session in the same host and the two run on alike, and the refusals — a save inside the document, into a directory that is not empty, a file changed since, a load into a document, an unknown session.

### `session.materialize`

`session.materialize` (`MaterializeParams` → `MaterializeResult`) is the same pass on its own, with the report in full: materialize the session's document — `scope` `"whole"` (the default), `"tile"` with `tile_x`/`tile_y` (the records of that tile of the partitioned layers that define them), or `"untiled"` — into the session's runtime world now, and return what happened. The world is the one `run_headless` steps, so a report after a run is an incremental pass.

`MaterializeResult` says whether the pass was full or followed the change feed, the document revision the world now reflects, and the counts — `visited`, `created`, `updated`, `unchanged` (looked at and already in sync), `dematerialized`, `relinked` (held records materialized again because their parent now has an entity), `skipped`, `live`, `orphans` (held records whose parent has none) — and the wall time and tier. Then **which types mapped and which records were skipped and why**: `types`, one `MaterializeTypeReport` per record type the pass met, with `mapped`, `records`, `materialized`, `skipped` and, when it skipped any, the first `reason` — `no mapping` (document-only by design), `unknown type` (not in this build's registry), `tier`, `missing component` (with the component in `detail`), `no entity store`, `no hook` — and `skips`, the first 64 skipped records by id. And `mappings`: every mapping this build compiled, whether or not the document uses it — the record type, its components, each field row with its conversion and write-back flag, the parent rule and the tiers — so a client learns what a record type becomes before it authors one. A `scope` that is not one of the three is 1004.

### `engine.run_tests`

### `profile.*`: the frame capture over the protocol

[06 §6.6](../plan/06-agent-tooling.md#66-introspection)'s `profile` (roadmap A10): engine-host registers `profile.start`, `profile.report` and `profile.stop` (`apps/engine_host/profile_methods.cpp`), over [core/profiling](profiling.md#the-frame-capture)'s frame capture and [profiler](profiler.md)'s frame report. A client starts the capture, has the host draw — `render.capture`, `render.benchmark`, a camera path — and stops it; the frames mark themselves and record their GPU timer zones and CPU spans (`systems/renderer`, [renderer](renderer.md#the-frame-capture)), and every zone of every thread of the host records itself (the dispatch of each request is `rpc.dispatch`).

| Method | Params → result (each at version 1) |
|---|---|
| `profile.start` | `ProfileStartParams` (`capacity`, events; 0 the default 262,144, at most 4,194,304) → `ProfileStartResult` (`capacity`, and `capture`, the capture's number) |
| `profile.report` | `ProfileReportParams` (`window_frames`, `max_series` 1 to 64, default 16, `out_dir`, `name`, `capture`) → `ProfileReport` (`capture`, `ProfileSeries` for the frame, and lists `gpu`, `cpu`, `zones`) |
| `profile.stop` | the same → the same, after the stop |

- **The capture is the process's**: one at a time (a second `profile.start` is refused with 1004), the same for every client and scene of the host. `profile.report` reads the running capture (`running` true; what is still being written is left out) or the last one stopped, as often as asked and over any window; `profile.stop` with nothing running is refused, and a `profile.stop` whose parameters are refused leaves the capture running.
- **Two clients and one capture.** The buffer holds one capture — up to 4,194,304 events of 48 bytes, about 200 MiB, which is why a second is refused rather than allocated beside it — and `profile.start` clears it. So a second client cannot start while the first's runs, but it can `profile.stop` the first's and start its own, and then the first's events are gone. Each start is numbered (`capture`, from 1 in each host process) and every report says which it read; a `profile.report` or `profile.stop` that passes the number its start returned and finds another capture there is refused with 1003, "capture 1 was replaced by capture 2 (another profile.start): its events are gone", and changes nothing — the second client's capture keeps running. A call with `capture` 0 reads whichever is there, which is the one way to be handed another client's report, and the report's `capture` says when it happened. A capture stopped by someone else is still readable by its number (`running` false); only its `profile.stop` is refused, as nothing is running. Zones are kept by the same rule below the protocol ([profiling](profiling.md#the-frame-capture)): a zone that began under one capture and ends under another is dropped, never counted in the second. engine-cli starts a host per call, so a capture across engine-cli calls is not possible; this is for `engine-host --listen` and `engine-mcp`'s clients.
- **The trace is written as `render.capture` writes its files**: the directory made and the path joined through `foundation/io`, and a failure the protocol's 1005 naming the path and the status.
- **Bounded**: each list is cut to `max_series`, largest total first, and `series_dropped` counts the rest, so a result is at most three lists of 64 series — under 40 KB — however long the capture ran. `dropped_events` says how many events a full buffer refused.
- **A capture that filled says so.** `truncated` is true when the buffer filled, and `truncated_ms` says when, from the capture's start. The report then ends there: the frame in progress is left out with its zones and values (`truncated_in_frame`, its index `truncated_frame`), and so is each value track's last measured frame, so every median and tail is over whole frames ([profiler](profiler.md#the-frame-report), "A capture that filled"). Before 2026-11-18 such a frame was stretched to the stop. engine-mcp's summary says it in a sentence: when the buffer filled, during which frame, that the numbers cover the frames before it, and to start again with a larger capacity. `invalid_values` counts values left out because they were not a time.
- **The capacity a start reports is the capacity it asked for**, not the buffer it got. The host keeps the largest buffer any capture asked for, up to the 4,194,304-event bound (about 200 MiB, and every role may ask), for the rest of the process. A later, smaller capture therefore drops later than its `capacity` says. Returning the buffer's own size, and freeing a larger-than-default buffer at the stop, are not built.
- **The trace**: with `out_dir`, `<out_dir>/<name>.trace.json` (Chrome's JSON Object Format, which Perfetto opens; [profiler](profiler.md#the-trace)) and its path as `trace`. `name` must be a plain file name.
- **Read-only.** A capture changes no document, lease or host setting — it records what the host does while it is on, as `render.capture` records a frame — so every role may profile.
- **Which frames.** A frame is the renderer's, from the start of `begin_frame` (its wait for the slot) to the end of its submission; each carries a number no other renderer of the process uses, so two scenes' frames in one capture stay apart. A host's turn between frames (engine-view's update, engine-host's request handling) is not inside a frame. GPU times come back `frames_in_flight` frames later and are counted against the frame that drew them; `gpu_frames` says for how many frames of the window they did.
- **What is not there yet**: GPU counters, memory by tag and a Tracy capture beside the trace (§6.6 lists all three; roadmap T45), and engine-editor's and engine-view's own loops, which do not register these methods.

**Testing.** `apps/engine_cli/tests/profile_tests.cpp` (no device): the refusals before a capture, a capacity past the bound, a second start; a running report holding `rpc.dispatch` outside every frame, bounded by `max_series`; three refused stops that leave it running; a stop that writes the trace into the test's scratch directory, read back through `core/json`; the stopped capture read again, and a second stop refused; then a second capture replacing the first, a report and a stop naming the first refused with 1003 and the replacement's number, a number never started refused, and the second stopped by its own. `render_tests.cpp`'s "render: profile.* reports a benchmark's frames, GPU passes and CPU spans" draws a 12-frame benchmark under a capture and checks the frames, the GPU frames, a positive GPU median and `renderer.record` among the CPU spans; on a device with no GPU timer it says so and stops (one with no timestamps cannot make a renderer, so the benchmark is refused), and on one whose frames come back untimed it checks the frames and CPU spans and that there is no GPU series.
## Transactions a client opens

[Plan 06 §6.4](../plan/06-agent-tooling.md#64-transactions-checkpoints-rollback)'s `begin_transaction → commands → validate → commit | rollback`, for work an agent cannot say in one `doc.apply`: it reads, decides, edits, reads what it edited and edits again, and wants the whole of it to land as one change or not at all (2026-11-17, roadmap A11).

| Method | Params → result | What |
|---|---|---|
| `doc.begin` | `BeginParams` → `TransactionInfo` | open one on a layer (empty: the session's edit layer), with the opener's attribution and an idle `ttl_seconds` (default 3600, 1 s to 24 h) |
| `doc.apply` with `transaction` | `ApplyParams` (version 3) → `ApplyResult` (version 2: `transaction`, `staged`) | check the commands and stage them; nothing is committed |
| `doc.commit` | `TransactionParams` → `ApplyResult` | apply every staged command as one checked transaction: one journal patch, or nothing |
| `doc.rollback` | `TransactionParams` → `TransactionInfo` | drop it and what it staged |
| `doc.transactions` | `TransactionsParams` → `TransactionsResult` | the open ones, by actor or all; read-only |

**A transaction is staged commands kept beside the document, not a document transaction held open across calls.** `transactions.json` (schema `TransactionsFile`) holds each open one with its commands, written before the answer like `leases.json`, for the same reason: engine-cli starts a host per call and engine-mcp replaces one that misses a deadline, so a transaction living in a host's memory would vanish between the calls it exists to join. Holding a `doc::Transaction` open instead would also put a client's uncommitted records in the document every other client reads; staged, they are invisible to everyone, the caller included, until the commit (`doc.get` of a staged creation is 1003). That is read-committed isolation and no more: a client sees others' commits as they land.

**Every staging call is checked as a write is, then taken back.** The transaction's earlier commands are applied again, then the call's, in one `doc::Transaction` through the session's `commit_commands` with the caller, so the call's commands are judged against the document as the transaction would leave it (a `SetProperty` on an object the transaction created applies), and the role, a proposal's owner and state, and the leases are asked exactly as for a `doc.apply` — a refusal is the same RPC error (1008, 1009, 1010) at the call that caused it, not at the commit. Then it is rolled back and only the command list grows. `atomic` (the default) stages all of a call's commands or none; with `atomic: false` it stages the ones that applied; a call that stages nothing reports its diagnostics with `applied: 0`. **The commit asks everything again**, because the document and the leases may have moved since: it is one `doc.apply` of the staged commands with the opener's attribution (a `rationale` given at commit replaces the one given at begin; an explicit timestamp is the patch's), so its patch is byte for byte the patch one `doc.apply` of the same commands journals, and one undo takes it all back. A commit that cannot land — a staged command no longer applies because another client committed under it (`committed: false` with the diagnostics), or a role or lease now refuses it (the RPC error) — lands nothing and **leaves the transaction open**, so the agent can renew a lease and commit again, or roll back; a database would abort it, and a model that lost twenty staged edits to an expired lease would have to rebuild them from memory, which is the opposite of plan 06 §6.8's "agents resume from the ledger and the document". A commit with nothing staged closes it and journals nothing.

**A transaction is its opener's and one layer's.** Only the actor that opened it stages, commits or rolls it back (1008, reason `transaction owner`), and while the socket connection it was begun on lasts, only that connection ([several clients](#several-clients-one-host)); a staging call naming another `layer` is 1004, since a transaction is one patch and a patch is one layer's; `doc.begin` makes the layer checks at once (a proposal of someone else's, a closed one, a role that needs review on a feature layer), so an agent is refused before it does the work. **An idle transaction lapses**: each call that stages moves its expiry to then plus `ttl_seconds`, by the host's wall clock as leases are, and a lapsed one is rolled back — dropped by the next call that reads the table, and a call naming it is 1003 saying it lapsed and nothing landed. Ids only grow, per document. Leases are not tied to a transaction, as they are not tied to a proposal: an agent that needs its tiles to stay its own until the commit holds the lease until then.

`doc.begin`, `doc.commit` and `doc.rollback` are writes for the dispatcher's gate (a role must name them; `content/roles/roles.json` gives them to the designer and environment roles beside `doc.apply`); `doc.transactions` is a read. What it costs: a staging call applies and rolls back everything staged so far, and rewrites `transactions.json`, so a transaction of *n* calls costs O(*n*²) command applications in all — nothing at an agent's tens of edits, and the reason to commit a large batch as one `doc.apply` rather than as a thousand staged calls. This is a transaction's rollback, not plan 06 §6.4's `rollback_to(checkpoint)`, which restores the document to a checkpoint (roadmap D13).

**Tested** in `tests/policy_tests.cpp` (three cases: several calls land as one patch identical to one `doc.apply`'s and one undo takes it back; rollback, a lapse judged a day ahead of the host's clock, a commit under which another client deleted a staged command's object, the opener-only rule, the one-layer rule, and a transaction committed by a second session manager; the dispatcher's gate, the fail-fast refusals at `doc.begin`, a transaction in a proposal promoted afterwards, and a lease released between staging and commit refusing the commit and leaving it open), in `apps/engine_cli/tests/policy_tests.cpp` through the executables (staged by three engine-cli processes and committed by a fourth; the refusals over one `engine-host --stdio`), and in `apps/mcp_bridge/tests/mcp_tests.cpp` (the four tools and a staged `create_object`).

## Placing an asset, instantiating a template

[Plan 06 §6.9](../plan/06-agent-tooling.md#69-day-one-operations)'s `place_asset` and `instantiate_template` (2026-11-17, roadmap A12): two compound edits an agent would otherwise spell as a batch of `CreateObject` commands with ids, paths and transforms worked out by hand (`domain/protocol/src/placement.cpp`). **Each compiles to commands and goes through the session's checked write** — one `doc.apply`, or with `transaction` one staging call into an open transaction ([above](#transactions-a-client-opens)) — so roles, proposals, leases, the journal, undo and the dispatcher's gate treat it exactly as the commands it is: one undo takes a placement or a copy back whole. Both are writes. Both answer `PlaceResult`: the `ids` made, in the order asked, and the `apply` result (an `ApplyResult`); `place_asset` adds the asset's `kind` and `bytes`.

**`doc.place_asset`** (`PlaceAssetParams`: `asset`, `placements: AssetPlacement[]`, `seed`, `layer`, `transaction`, `attribution`) makes one `engine.scene.MeshPlacement` per placement — the record type [doc_scene](doc_scene.md#the-record-type) draws and engine-editor's viewport shows — with `mesh` the asset exactly as given and the placement's name, parent, translation, rotation, yaw and scale. **The asset is checked before anything is written**: it must be a `.gltf`, `.glb` or `.clusters` (1004 otherwise), exist under the document's directory (1003), and read as its kind — a GLB's and a cluster container's four magic bytes, read with `io::read_file_range` so a 300 MB container costs four bytes, and a `.gltf` parsed as JSON naming `asset.version` (1004 when it does not). That is the check a record is worth refusing over; whether the mesh imports (its buffers, its triangles) is the importer's and the content build's question. **Where it may read** (2026-11-18): only under the document's directory, the one root a scene's mesh paths resolve against ([doc_scene](doc_scene.md), its `resolve_path`), so the path must be relative — no leading `/` or `\`, no drive (`C:`), no `:` anywhere (an NTFS stream), no `..` component, no empty name, no control character — and is joined to the session's directory as the scene joins it. A host serves clients of several roles, and an absolute path or one that climbs out would let any of them learn whether a file exists anywhere on the host's machine and, through the kind check, its first bytes. So a refused path and a path with no readable file under the document are one answer: 1003 with one sentence that names neither the path nor the directory. A symbolic link or junction inside the document's directory is followed, as the scene follows it: whoever can make one there already has the disk. A scene record written by other means may still name an absolute mesh, which the viewport draws; only this method's reading is confined. An id left null is generated from the seed, a hash of the asset path and the placement's index, so the same call places the same ids in any document and the same seed with another asset places others; a generated id that exists already is the transaction's diagnostic, and another seed is the answer. A placement is untiled unless its layer is partitioned on `translation` (the type has no `position`): a role restricted to tiles needs `untiled`, and a lease needs the type.

**`doc.instantiate_template`** (`InstantiateTemplateParams`: `root`, `parent`, `id`, `seed`, `offset`, `max_records`, `record_origin`, `layer`, `transaction`, `attribution`) is plan 03 §3.2's *instantiate-and-record-origin*, chosen over live composition there because a live template makes "what does this edit change" non-local. **Any live object is a template**: the copy is it and every live descendant, composed across the layers, depth first with children by id — an order that is the document's alone — and refused (1004) past `max_records` (default 10,000), naming the count. Each copy is a `CreateObject` of the source's type and composed properties, its parent the copy of the source's parent (the root's is `parent`), its id `id` for the root (or generated from the root and the seed) and for the rest a hash of the copy's root and the source, so a copy's ids are a function of what the call names. **`offset` (`dvec3`) is added to every property whose field is a `worldpos`** in the source's registered type — the engine's word for "where something is" (ADR-0053) — and nothing else moves: a `vec3` that happens to be called position is not a world position, and turning a copy is not built. With `record_origin` (the default) the copy's root gets a child **`engine.protocol.TemplateOrigin`** record: the template's root, each source in copy order beside its copy, and the root's `position` when it has one, so the origin stands in the copy's tile and a tile lease or role covering the copy covers its record too. A `TemplateOrigin` under a template is not copied: it is the template's history, not its content. The copy is not live — editing the template later changes no copy — and the origin is what a tool that wants to carry a template's change to its copies reads.

**General purpose**: neither knows any type but the two it writes. An imported glTF placed by `place_asset` is drawn as every placement is; a hand-authored subtree of any record types instantiates the same way, and a type with no `worldpos` field is copied where it was. **Tested** in `tests/policy_tests.cpp` (a GLB placed twice as one patch that validates, the same ids from the same call in another document and others from another seed, a `.gltf` staged into a transaction and landing at its commit, and the refusals — a kind that is not a mesh, a missing file, a file that does not read as its kind, nothing to place, QA at the gate; a real GLB beside the document refused under nine names — absolute, `..` in three spellings, a leading slash, a UNC share, a drive, a stream, an empty name — each with the missing file's code and sentence, while a subdirectory's file reads under either separator; a four-node yard copied with its offset, parents and order, the template untouched, the origin's fields and place, a copy of the copy leaving the first origin behind, one undo, an unknown root, `max_records`, and a copy staged and committed) and in `apps/engine_cli/tests/policy_tests.cpp` over one `engine-host --stdio` (a placement, its copy, and the refusals).

## Describing an object, a tile or a region

[Plan 06 §6.6](../plan/06-agent-tooling.md#66-introspection)'s `describe(object | tile | region, detail)` (2026-11-18, roadmap A13; `domain/protocol/src/describe.cpp`): what an agent needs to see of a part of the document before it edits it, in a size it can read. **`doc.describe`** (`DescribeParams` → `DescribeResult`) takes exactly one of `id`, `tile` (a `DescribeTile`) and `region` (a `TileRange`, inclusive, at most 65,536 tiles), a `detail` (`DescribeDetail`: `Summary`, `Standard` — the default — or `Full`), `max_records` (1 to 10,000, default 256) and `max_bytes` (1 KiB to 4 MiB, default 64 KiB); anything else is 1004, an object that is not live 1003. It is **read-only**: it changes nothing, so no role restricts it.

**What is in scope.** An object's scope is it and its live children at `Summary` and `Standard`, and its whole live subtree at `Full`, depth first with children by id (the order `instantiate_template` copies in). A tile's is the live records whose defining record is in that tile of its layer's grid, by id; a region's is its tiles' row by row (y, then x), by id within a tile. Everything is asked of the document — `exists`, `children`, `type_of`, `parent_of`, `property`, `object_tile`, `ids_in_tile` — never a walk of the layers. A region with more tiles than the document has occupied tiles is answered from the live set and sorted into the same order instead, so a large empty region costs the document's size and not its area; the two paths list the same records in the same order, and the test holds them to it.

**What it says.** `total` and `types` (counts by type, the most numerous first) cover the whole scope. `records` lists `DescribedRecord`s: id, type, parent, `name` (the record's `name` property when it is a string), `position` (the first `worldpos` field of the record's registered type that the record sets — the engine's word for where a thing is, ADR-0053, whatever the field is called; a `vec3` is not one), the tile it is filed in, its live child count, its depth below the object, and at `Full` its composed properties. `Summary` lists the object alone, or for a tile or region nothing. **`summary`** is one or two sentences built from templates over those counts — `engine.world.Node 'n' <id> at (5.00, 0.00, 5.00) in tile (0, 0), a root, with 2 live records as children: 2 engine.world.Node.`, `Tile (0, 0) holds 5 live records: 4 engine.world.Node and 1 engine.protocol.test.Prop.` — eight types at most and "and N more types" after, positions to the centimetre; no model writes it, so the same document gives the same words.

**The bounds.** Records are listed in scope order until the next would pass `max_records` or take the listed records' JSON past `max_bytes`; from then on every record is counted in `omitted`, `bound` names the bound, and the sentence ends `Listed L of N; M left out by <bound>.` The object asked about is always listed, whatever the bounds, since it is what was asked for. A `Full` subtree is walked to count it; a walk past 1,048,576 records stops there with `bound` `"walk"`, its counts a floor. What a call costs: the scope's records once each for the counts (a hash lookup for the type), and the listed ones again to build them — at most `max_records` resolutions and `max_bytes` of JSON, plus one serialization each to measure it.

**General purpose**: it knows no record type. An imported asset's placements, a hand-authored node tree or a type a game adds are described alike; a type with no `worldpos` field has no `position` and is still placed by its tile. **Not yet**: plan 06 §6.7's world mips (semantic, visual, design-density) and the edit cell's overlap ring; a description is of the document as it stands, at the three detail levels, and the context package that budgets tokens across mip levels is still to be built on it. A session's view policy (ADR-0033, roadmap A26) is not applied to what it lists, as it is not yet applied to `doc.get`. **Tested** in `tests/policy_tests.cpp` ("describe: an object at three details, its sentence, and the bounds"; "describe: a tile and a region from the tile index, in one order, under any role"), in `apps/engine_cli/tests/policy_tests.cpp` over one `engine-host --stdio` under the QA role ("host: doc.describe over --stdio"), and in `apps/mcp_bridge/tests/mcp_tests.cpp` (`describe_document`).

## Querying the document

[Plan 06 §6.6](../plan/06-agent-tooling.md#66-introspection)'s `query(sql | structured)` (2026-11-18, roadmap A14; `domain/protocol/src/query.cpp`). The structured half over the document is built; the SQL half over the store is designed below and **proposed, not built**.

**`doc.query`** (`QueryParams` → `QueryResult`, read-only) returns the live records that pass a `filter`, in id order, a page at a time. **Where it looks** is narrowed through the document's indices before the filter runs — the children of `parent` (`children`), the records filed in the tiles of `region` (`ids_in_tile`, or the live set filtered by `object_tile` when the region has more tiles than the document has occupied ones, as `doc.describe` does; at most 65,536 tiles), or every live record (`objects`) — and never by a walk of the layers. **The filter** is `session.run_headless`'s `until` vocabulary over one record: `{"type": "<pattern>"}` (`*` any run of characters, the roles file's `glob_match`), `{"property": "<name>", <test>}` with `equals` (JSON, numbers by value), `at_least`, `at_most`, `prefix` or `exists`, a name ending in `[i]` taking one element of an array (`"position[0]"`), `{"parent": "<id>"}`, and `all`, `any`, `not`; a term with an unknown key, two tests, a test of the wrong kind, nesting past 32 or more than 1,024 terms is 1004 naming the path (`filter.all[0]: ...`). Each row is the id, type and parent and the composed `fields` asked for.

**A filter is input from outside, so it is data and never text**: it is compiled once into a tree of terms and walked per record; nothing a client writes is joined into a statement or evaluated as code. **What it can reach** is what `doc.get` and `doc.objects` return to the same caller — the composed live records of the session's document — and nothing else: no layer's own records, no journal, no file. **What it can cost** is bounded per page and the bound that ended it is in the result: `max_rows` (1 to 10,000, default 100) rows, `max_examined` (1 to 1,000,000, default 100,000) candidates the filter runs over, `max_ms` (1 to 10,000 ms, default 2,000; the clock read every 256 candidates) of examining, and `max_bytes` (1 KiB to 4 MiB, default 256 KiB) of rows as JSON. Memory is the candidate list (16 bytes a record in scope) plus the compiled filter (at most 1,024 terms) plus the rows. A page that stops at a bound has `complete: false`, `bound` naming it, and `next`, the last id it examined, which as the next call's `after` resumes exactly there: pages of three read the same rows as one call and none twice, and the test holds them to it. The narrowing is paid in full on every page (a `region` call sorts its candidates), which is why `max_examined` bounds the filter's work and not the narrowing's.

**Content classes ([ADR-0033](../adr/0033-content-classes-and-view-policies.md))**: a query is a read and is held to exactly what a read may see, not to more. Until a session carries a view policy (roadmap A26) no record is classified and nothing is withheld from `doc.get`, so nothing is withheld here. **When it does** (proposed): the policy filters the candidate list before the filter runs, and a property the policy withholds is absent to the terms, so a record a role may not read never matches and a filter on a withheld property cannot learn its value by matching on it (`{"property": "nudity", "equals": "full"}` matches nothing rather than telling an agent which records carry it); the counts in the result (`candidates`, `examined`) are of what the policy left, for the same reason.

**SQL over the store (proposed, not built).** The store's `world.db` (`events`, `projections`, `snapshots`; [store](store.md)) is where 03 §3.5 wants SQL, and its half of `query` is a method of the store capability in engine-host, beside `session.events`, since this module may not link a capability. The design, so that what a client writes stays its own statement and cannot reach past it: a connection of its own opened `read_only` (SQLite's `SQLITE_OPEN_READONLY`), never the world's; the client's text prepared once with `sqlite3_prepare_v3` and refused unless it is one statement (an empty tail) that `sqlite3_stmt_readonly` says writes nothing; **an authorizer** (`sqlite3_set_authorizer`) that admits `SELECT`, reads of the three tables' columns and a list of pure functions, and denies everything else — `ATTACH`, `PRAGMA`, `sqlite_master`, a temp table, `load_extension`, any write; the client's values given as `params` and bound with `sqlite3_bind_*`, never spliced into the text; `sqlite3_limit` on the statement's length (64 KiB), a value's length (1 MiB), columns (64), expression depth (100), compound selects (8) and attached databases (0); `max_ms` through a progress handler that interrupts the statement; `max_rows` and `max_bytes` by stepping; the connection's page cache and temp store bounded by `OpenOptions`. Payloads and projection blobs are opaque bytes the store does not type ([store](store.md), "Not yet"), so a classified one cannot be told from an unclassified one in SQL: under a policy below full the authorizer denies the blob columns outright rather than return bytes it cannot judge. What it would cost a client is the same four bounds and the result names the one hit.

**General purpose**: the filter knows no record type, and a game's types are queried as the engine's are. **Tested** in `tests/policy_tests.cpp` ("query: a structured filter over the document, in id order, a page at a time": every record, a type pattern, an array element's bound with fields, a nested any/all/not with a number compared by value, prefix and exists; a parent's children and two regions, one through the tile index and one through the live set; pages of three against one call; the examination and byte bounds with `next`; nine refusals; QA querying), in `apps/engine_cli/tests/policy_tests.cpp` over one `engine-host --stdio` under QA ("host: doc.query over --stdio") and in `apps/mcp_bridge/tests/mcp_tests.cpp` (`query`).

## Roles, leases and proposals

[Plan 06 §6.5](../plan/06-agent-tooling.md#65-permissions-concurrency-and-leases) in four bullets: roles are configuration; an agent leases (layer, tile set) or (layer, object-type set) before editing, and conflicts fail at acquisition; agents write to their own proposal layers, promoted into a target by structural merge after validation; read access is unrestricted. All of it is **this module's**, not engine-host's — `policy.h`, `leases.h`, `proposals.h`, `src/policy_methods.cpp` — because the writes it guards are this module's `doc.*` methods, and every dispatcher that serves them (engine-host, a future editor host, the tests) has to guard them alike. A host loads a roles file and says who it is; nothing else. [ADR-0039](../adr/0039-leases-and-proposals-beside-the-document.md) (proposed) records the four decisions below that would surprise someone; [E12](../experiments/e12-proposal-layers-and-leases.md) measured what leases buy.

| Method | Params → result | What |
|---|---|---|
| `lease.acquire` | `LeaseAcquireParams` → `LeaseInfo` | tiles (`TileRange[]`) or `object_types` of a layer, for `ttl_seconds` (1 s to 24 h); 1009 naming the holder when another actor's live lease overlaps |
| `lease.renew`, `lease.release` | `LeaseRenewParams`, `LeaseReleaseParams` → `LeaseInfo` | the holder's alone (1008 otherwise) |
| `lease.list` | `LeaseListParams` → `LeasesResult` | every live lease, by layer or holder; read-only |
| `lease.require` | `LeaseRequireParams` → `LeasesResult` | whether every writing `doc.*` call needs a covering lease |
| `doc.propose_layer` | `ProposeLayerParams` → `LayersResult` | a proposal layer over a target, owned by the caller; reopens a closed one of the caller's |
| `doc.promote` | `PromoteParams` → `PromoteResult` | merge, validate, commit; or refuse with the conflicts and the new validation problems |
| `doc.reject` | `RejectParams` → `LayersResult` | empty an open proposal without merging it |
| `engine.roles` | — → `RolesResult` | the loaded roles, each with the methods it may call, and the host's identity; read-only |

### Identity, and what a role restricts

**A call's identity is its attribution**: the `actor`, `role` and `task` of `attribution` in its params, with blank fields taken from the host's identity (`engine-host --actor`, `--role`, `--task`, `Policy::identity`). The methods that write records carry one — `doc.apply`, the new methods, and, since this change, `doc.undo`, `doc.redo` and `doc.merge` (`StepParams` and `MergeParams` version 2, `attribution: Attribution?` `@since(2)`; a merge given one journals it instead of the host's own). A method that carries none — `doc.add_layer`, `tunables.set`, `content.build`, `session.run_headless` — runs as the host's identity. **Roles are guardrails for cooperating agents, not security**: the protocol has no authentication, so a role is whatever a call says it is. What a role buys is that an agent told to be QA cannot change the terrain by mistake, and that the refusal says so in a structured error a model can act on. Where one agent owns one host — engine-mcp starts a host per agent ([apps](apps.md#roles-leases-and-proposals)) — the host is given that agent's identity, and the bridge refuses a call that names another role.

**The role a call runs in** is its attribution's role, else the host's `--role`, else the roles file's `default_role`; none at all means unrestricted, and so does a host with no roles file, which is every host before this change. A named role the file does not have is 1008 rather than no restriction, since a call that claims a role nobody configured must not fall through to none.

**Read access is never restricted, and a method is a write unless registered `read_only`** (`MethodDesc::read_only`, `read_only(method<...>(...))`, reported as `MethodInfo.read_only`, `@since(2)`). The default is a write on purpose: a method nobody classified is refused to a role that did not name it — loud — rather than open to every role — silent. Read-only means changing no document, no lease and no host setting: the `doc.*` readers, `doc.save` (it writes what the document already holds), `session.open` and `session.close` and `render.unload` (housekeeping of a caller's own handles: a role that may only look must still open what it looks at and let it go), every `render.*` and `engine.*`, `session.events` and `session.materialize` (the runtime world is a cache of the document), `session.state_hash`, `session.save_game` (it writes a new directory from what the session holds) and `session.load_game` (it opens a new session on a new directory, as `session.open` with `create` does), `lease.list`. The writes are the `doc.*` editors, `lease.*` but `list`, `tunables.set`, `content.build` and `session.run_headless` (its write-back changes the document); `engine.methods` says which is which. The dispatcher is the gate: it reads `params.attribution.role` from the raw JSON once, so no handler has to learn to, and refuses a write the role's `methods` patterns (`*` a wildcard) do not name — 1008 with `data.reason` `"method"`. **That holds for every client, the console included**: a call from an `engine-host --console` script ([apps](apps.md#the-console-luau-scripts-over-the-protocol)) is a request object handed to this same dispatcher, so `--roles`, the host's `--actor`/`--role`/`--task` and this rule apply to it as to a line on stdin — a `qa` script's `doc.apply` is refused with 1008 and reaches the script's `pcall` as `{code, message, data}`, and its reads are not restricted (`apps/engine_cli/tests/console_tests.cpp`).

**What a role restricts in a write** is checked by the session, per transaction, and a refusal rolls the whole transaction back — a write is the caller's to make or not, never half of one — and is an RPC error, not a diagnostic:

- `layers`: the layer whose content changes. For a proposal layer that is its **target**, so `"layers": ["world"]` means "may change world, directly or through a proposal".
- `tiles` (ranges; none is the whole partition) and `untiled`: where each touched object stands before and after the change.
- `object_types` (patterns): each touched object's type.
- `review_required`: it writes only to proposal layers it owns and may not promote (`doc.promote` answers 1008 with reason `"review required"`); plan 06 §6.10's director is a role without it.

`data.reason` is `method`, `layer`, `tile`, `untiled`, `type`, `review required`, `proposal owner`, `proposal closed`, `lease holder` or `unknown role`, with the role and what was refused (`layer`, `object`, `tile`, `type`, `method`). `content/roles/roles.json` is the five named roles, and `content/roles/README.md` says what each allows and why the default is read-only.

### Where an object stands

Tiles and types are judged by the object's **composed** position and type (`place_of`): the strongest layer's `position` (or the partition's named property, or the type's `transform`), tiled by the **lease layer's** partition — a proposal's target, or the edited layer itself. Not by the edited record alone, which is what files are laid out by ([doc](doc.md)): an override that sets a colour and not a position still changes an object standing somewhere, and "a lease on tile (3, 7)" means the objects standing in it. Every object a write's commands name is placed **before its first change and after the transaction**, and both places are checked, so a move out of a lease or a role's tiles is caught by where it lands and a create-then-position in one transaction is judged by where it ends up. A record that is gone after the change (a delete in its defining layer) has no after; one that did not exist before has no before. An object with no position, or on a layer with no partition, has no tile: only an object-type lease covers it, and a role covers it only with `untiled`.

**The check allocates nothing per record**: a place is a hash lookup in the composed index, a visit to the layers holding the id, and a registry lookup for the type (whose name the registry owns), and a lease table is tens of entries walked in place. A write that no role restricts, into a document that does not require leases, records nothing at all — one branch per command.

### Leases

One table per document, **kept beside it as `leases.json`** (schema `LeaseFile`) and written before the answer, as the document's own files are: engine-cli starts a host per call, and engine-mcp replaces a host that misses a deadline, so a host's memory is exactly where a lease granted a moment ago would not be. Expiry is by the host's wall clock (`time::wall_unix_ms`), so it means the same to every process on the machine; an expired lease covers nothing and is dropped by the next acquisition, list or require. Ids only grow. Two hosts writing one document at once is as unsupported as it always was. A lease taken over a socket connection also ends with the connection, and one a gone host's connection left in the file is dropped at the next open ([several clients](#several-clients-one-host)).

- **Acquisition** (`lease.acquire`) names tiles or object types, not both, on a layer that is not a proposal (1004 names the target to lease instead). It is refused with **1009 LeaseConflict** when another actor's live lease on the same layer has an intersecting tile range or a type in common, and `data.lease` is that lease: who holds it, for which task, until when. Overlapping one's own leases is allowed. A role may lease only a layer it may change, ranges inside one of its own, and types its patterns name. Type names are exact, because overlap has to be decidable from the names.
- **A tile lease and a type lease on one layer** can both cover a record (a light standing in a leased tile, under a lease on lights), and whether one does is not decidable from the two scopes. That overlap is refused **at the edit**: 1009 names the other holder.
- **Edits need leases only when the document says so** (`lease.require`, `LeaseFile.required`), off by default: every document and test written before leases edits as it did, and a single-agent document pays nothing. When it is on, every object a writing `doc.*` call touches — `apply`, `undo`, `redo`, `merge`'s output layer — must be covered, where it stood and where it stands, by a live lease of the caller's and by nobody else's: **1010 LeaseRequired** when none of the caller's covers it, 1009 when someone else's does.
- **A lease must be held until the proposal that carries its edits is promoted.** A lease released right after the edit protects nothing: the edit sits unmerged in the proposal, the next holder of the tile changes the record, and the promotion finds a conflict the lease existed to prevent. [E12](../experiments/e12-proposal-layers-and-leases.md)'s first run did exactly that and found a DeletedAndModified conflict with leases on. The protocol does not tie a lease to a proposal; the agent's protocol is acquire, read, edit, promote, release, and the MCP tools say so.
- **A promotion is not lease-checked.** It is the merge the leases existed to keep clean, and each record the proposal holds was checked when it was written. Nor is the runtime world's write-back (`Session::apply` without a caller, attributed to `system`): the simulation writing what it computed is not an agent editing.

### Proposal layers and promotion

`doc.propose_layer {name, target}` appends a layer of role `Proposal` over `target`, stored in the target's form (its partition), and records the caller as its owner: a **layer property** kept in `proposals.json` (schema `ProposalsFile`) and reported by `doc.layers` as `LayerInfo.proposal` (`@since(3)`) — target, owner, owner role, task, the rationale the proposal was opened with, state, when, and how many target records it has touched. It is the protocol's and not `domain/doc`'s: in memory, on disk and in the journal a proposal is an ordinary layer. **Only its owner writes it, and only while it is open** (1008 otherwise). Read access is unrestricted, so everyone reads it: proposals compose into the document like any layer, which is the "read-only context from neighbours" the plan asks for — and which also means a neighbour's in-progress deletion hides the object from everyone's strict `doc.apply` at once, so that collision surfaces at the edit rather than the merge.

**The merge base is per record, from the proposal's first touch.** The first commit that changes a record in a proposal appends the target's record as it stood then (or its absence) to `proposals/<layer>.base.jsonl` (one `ProposalBaseEntry` a line). `doc.promote` then merges three layers with `doc::merge_layers`: `base`, the target with each record the proposal holds put back as the proposal first found it; `theirs`, that base with the proposal's opinions composed on (`compose_onto`: properties and a parent overlay, a type defines, a tombstone drops a record the target defines and tombstones one it does not); and `ours`, the target now. This costs what the proposal touched rather than what the target holds, and a change promoted into the target *before* the proposal first touched a record is what the agent built on, so it is never reported against it — where a whole-target copy taken at `propose_layer` would call it a conflict. A record held with no recorded base (the proposal was written behind the protocol's back, or an undo refilled a closed one) merges against the target as it stands and can take the proposal's side but never conflict. ADR-0039 has the comparison.

**Validation runs on the merged world before anything is committed.** The accepted world is every layer that is not a proposal; `doc.promote` validates it as it is and with the target replaced by the merged layer, and what the second finds that the first did not is the promotion's to fix (`PromoteResult.validation`). Problems already there, or in other agents' proposals, do not block it — otherwise one agent's broken record would block every promotion. A promotion that leaves a child without its parent, overrides an object no accepted layer defines (an edit to a neighbour's unpromoted creation), or writes a property its type lacks is refused.

**It is refused, not an error, when anything stands in the way**: `promoted: false`, `ok: false`, `refused` a sentence, and every conflict and new validation problem. `prefer` (`PromotePrefer`) settles conflicts — `Refuse` (the default: a person or a director decides), `Target` (keep what the target has), `Proposal`, `Base` — and never validation. `dry_run` does everything but commit. **Committed, it is two journal patches**: the target's, attributed to the promoter with the proposal's owner, task and opening rationale in the rationale (plan 06 §6.8: an accepted proposal records why next to the change), and the proposal's emptying patch. The proposal layer **stays in the stack, empty and `Promoted`**, and its owner reopens it by name for the next piece of work — removing it would break undo for everyone, since every earlier patch names its layer and the journal is one line per document. `doc.undo {steps: 2}` takes a promotion back and leaves the proposal holding its records again; its state is not journaled, so it stays closed until its owner reopens it. `doc.reject` empties an open proposal without merging it (its owner may always; anyone else needs a role that may change the target). `PromoteResult` reports `merge_ms`, `validate_ms` and `commit_ms`, which E12 reads.

## Blobs and checkpoints

Roadmap D13 and D14: the document's store of content-addressed blobs and its checkpoints, over the store and repository `domain/doc` keeps ([doc](doc.md#blobs), [doc](doc.md#checkpoints)). `src/session_history.cpp` is the session's half, `src/history_methods.cpp` the wire; every params and result type is in `schemas/protocol.schema`, so engine-cli reaches them by name (`engine-cli --doc ./world doc.checkpoint '{"label":"before the river"}'`).

| Method | Params → result | What |
|---|---|---|
| `doc.put_blob` | `PutBlobParams` → `BlobResult` | bytes into the store from a file under the document's directory (`path`, relative to it) or inline (`data_base64`), never both; answers the `BlobRef` to set and whether it was new. A write: it changes no document, but a role must name it |
| `doc.blob` | `BlobParams` → `BlobResult` | read-only: the blob's path, its bytes checked against its name, and with `data` the bytes as base64; 1003 for a name the store lacks, 1004 for one that is not a name |
| `doc.collect_blobs` | `CollectBlobsParams` → `CollectBlobsResult` | removes what nothing can bring back: no layer, no journal patch (undo history and redo tail), no open proposal's merge base and no command staged in an open transaction names it (a lapsed transaction rolled back first), and it is older than `min_age_s` (an hour); `dry_run` |
| `doc.checkpoint` | `CheckpointParams` → `engine.doc.CheckpointInfo` | saves, then commits the document to `<dir>/.git`; 1006 with the reason when there is no git; 1004 for a `label` holding a control character or past 200 bytes ([doc](doc.md#checkpoints)) |
| `doc.checkpoints` | `CheckpointsParams` → `CheckpointsResult` | read-only: newest first, with who took each, why and the journal's positions; `available` and the git that answered |
| `doc.rollback_to` | `RollbackParams` → `RollbackResult` | the accepted layers made what the checkpoint held, as journaled patches; `dry_run` |

**A command naming a blob the store does not hold is refused** — a diagnostic naming the blob ("doc.put_blob it first"), and with `atomic` the whole transaction — in every client's `doc.apply` (`Session::commit_commands`, strict commands). Replays are not checked: an undo, a redo or a merge replays references the journal accepted, and nothing the journal can reach is ever collected. So the order is put, then apply; the grace period of a collection is what keeps a blob between the two, and a put of bytes the store already holds starts it again (`created: false` is still a put).

**A `path` is read only under the document's directory** (`read_under_document`, `src/document_path.h`). A host serves clients of several roles, and `doc.blob` with `data` is read-only and open to every role, so a `path` the host would read anywhere is a copy of any file the host can read, handed to any client (batch 68's review, B1). The rule is `doc.place_asset`'s (`stays_under_document`, one function with the same behaviour): relative, no drive, no stream (`:`), no `..` component, no empty name, no control character; and then, links followed, the file must still be under the directory, so a link inside it that points out is refused too. **A refused path and an unreadable one answer the same code (1003) and the same sentence**, naming neither the path nor the directory, so a client learns nothing of the disk outside. *Why keep `path` at all*, when `data_base64` carries the same bytes: a large file a host-side tool wrote into the document's directory (a baked grid, a generated image of hundreds of megabytes) goes in without a base64 round trip through the client and the JSON line; the inline form is for what a client holds itself.

**What a rollback does** (`Session::rollback_to`). It reads the checkpoint's manifest and layers back from the repository and, for every layer of the stack, writes the difference between what the layer holds and what the checkpoint held as **one patch per layer it changes** — `doc::diff_layers`, applied as a merge's commands are, without the composed document's preconditions — through the same commit path as every write: journaled, saved, published as `journal` events, stamped in the change feed, and undone by `doc.undo` with `patches` steps. That is the decision under everything else: a rollback is a forward edit, never files put back, so the runtime world follows it through the change feed as it follows any edit (`changed_since` names exactly the records the rollback changed), the journal says who rolled back to what and why (the rationale begins "rollback to checkpoint <id> "<label>""), every open session sees it, and nothing in the history is lost — a rollback can itself be undone, and checkpoints after it stay reachable.

- **Layers.** A layer the checkpoint had is restored, its storage form put back too (`doc.set_partition`, outside the journal as that method always is); one it did not have is *emptied* and kept in the stack, as a promoted proposal is, because every earlier patch names its layer; one it had that the stack lost is appended on top, empty, outside the transactions (as a merge's new output layer is), then restored — the stack's order is not restored. The checkpoint's edit layer becomes the session's when the stack has it.
- **Open proposals are left as they are** (`action: "kept"`) — they are their owners' work in progress, not the accepted world, and the checkpoint's own proposal layers are not restored. Their merge bases are untouched, so a promotion afterwards sees the rollback as the target's change: where the proposal touched a record the rollback changed, the promotion reports the conflict and a person decides; nothing is overwritten silently.
- **Who may call it.** It is a write a role must name (only the director in `content/roles/roles.json`), and each layer's patch is checked exactly as a `doc.apply` into that layer is — the role's layers, tiles and types where every touched record stood and stands, `review_required` (such a role is refused: a rollback cannot go through a proposal), and, when the document requires leases, every touched record covered by the caller's lease and nobody else's. **The checks run for every layer before any layer changes** (`Session::check_commands`, a transaction rolled back), so a refusal — 1008, 1009 naming the other lease's holder, 1010 — leaves the document as it was. Leases are not released or changed by a rollback: they are time-bound claims, and a rollback over a tile someone else holds is refused like any edit there.
- **Blobs.** A blob the checkpoint's layers name that the store has collected since is written back from the checkpoint first (`blobs_restored`).
- **Whole or not at all.** After the checks pass, what can still refuse a layer is a save that fails (or the store refusing a blob back). Then everything the rollback changed is taken back before the refusal is answered: the layers that had landed are undone newest first, as `doc.undo` would undo them — so they stand in the redo tail, which the next commit drops, as a commit whose save died does — the storage forms are put back and the layers it appended are taken off again; the message ends "nothing of the rollback stands". Blobs written back stay (a collection decides). Only when that taking back fails too does part of the rollback stand, and then the error's `data` is the `RollbackResult` of exactly what stands — its `layers` with their `patch_index`, `patches` their count — and `doc.undo` with `patches` steps takes it back (a storage form changed stays changed; `doc.set_partition` puts it back). Batch 68's review (B10) found it stopping part-way and saying nothing; `history_tests.cpp` refuses the second layer through `Session::fail_rollback_for_test`, once with the taking back allowed and once with it refused.

**What a checkpoint does to leases and proposals: nothing.** It holds the document's own files and not `leases.json` or `proposals*`; it is a write a role must name because it is the history others roll back to.
