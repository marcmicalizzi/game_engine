# protocol (domain)

**Purpose.** The engine protocol (docs/plan/06-agent-tooling.md §6.2, ADR-0001): JSON-RPC 2.0 dispatch over JSON values, sessions over stored documents, and the day-one method set. Transport-agnostic: `engine-host` feeds it lines from stdin, the editor and the MCP bridge will feed it from sockets, tests call it in process. Every method's params and result are schema structs (`schemas/protocol.schema`), so the catalogue agents read (`engine.methods`), the JSON Schema schemac emits, and the C++ handlers agree by construction.

**Model.**
- `Dispatcher` holds `MethodDesc`s (name, doc, params type, result type, handler) sorted by name and turns a request object or batch array into a response value; `dispatch_text` adds parse-error handling and single-line framing. Notifications (no `id`) get no response. Responses carry exactly one of `result` and `error`.
- Handlers are plain functions `bool fn(Context&, const P&, R&, RpcError&)` wrapped by `method<P, R, fn>()`; `method_no_params<R, fn>()` for methods without params. `detail::read_params` turns deserialization problems into InvalidParams with `{path, message}` diagnostics in `error.data`. Command failures inside a transaction are results (`ApplyResult.diagnostics`), not RPC errors.
- `Session` owns one `doc::Document` plus its `DocumentManifest`, and every mutation goes to disk before the response: `apply` commits, drops any redo tail, journals, and saves; `undo`/`redo` move `undo_position` and save. Both go through one private `commit_commands`, which also lets `merge` commit against a layer that is not the session's edit layer without moving it (the patch names the layer it edited, so undo finds it again). `doc.add_layer` appends and makes the new layer the edit layer by default; with `edit: false` the edit layer stays where it was, in memory and in the saved manifest.
- A layer's storage form is part of the protocol because it is part of the manifest. `doc.add_layer` takes an optional `partition` (`property`, `tile_size`) that stores the layer as tile files instead of one file (`domain/doc/partition.h`, plan 03 §3.7); `doc.set_partition` converts an existing layer between the two forms and rewrites its files, changing no record, so the journal, undo, and redo are untouched. An absent `partition` means one file; a `tile_size` of zero is refused rather than quietly meaning the same thing, so a caller's mistake is not silently accepted. `doc.layers`, `doc.add_layer`, and `doc.set_partition` all return the stack, and each `LayerInfo` reports the form (`partition`, absent for a single file) and the occupied `tiles`.
- `doc.merge` (`MergeParams` → `MergeResult`) is `doc::merge_layers` over three named layers, written into `output_layer` as the diff between what that layer holds and the merged records, applied non-strictly as one transaction: the result reports `applied_ours`, `applied_theirs`, the conflicts with their kind as a string, and the journal index, and the merge undoes like any other patch. A missing `output_layer` is appended to the stack outside the transaction, so undo empties it rather than removing it. Conflicts are a result, not an error; `MergePrefer` (`Ours`, `Theirs`, `Neither`) chooses how they resolve. `SessionManager` opens (or creates) a document directory, returns the existing session for an already-open path, and closes.
- Error codes: standard JSON-RPC negatives; engine codes 1000 SessionNotFound, 1001 DocumentError, 1002 ValidationFailed, 1003 NotFound, 1004 InvalidArgument, 1005 IoError, 1006 Unavailable.

**Methods (day one).** `engine.info`, `engine.methods`; `session.open` (`path`, `create`, `name`), `session.close`, `session.list`, `session.info`; `doc.layers`, `doc.add_layer` (optionally `partition`ed), `doc.set_partition`, `doc.set_edit_layer`, `doc.objects` (filter by `type` or `parent`, `offset`/`limit`), `doc.get`, `doc.apply` (commands + attribution, `atomic`), `doc.undo`, `doc.redo`, `doc.diff`, `doc.merge`, `doc.validate`, `doc.journal`, `doc.save`; `tunables.list`, `tunables.set`; `log.tail`; `schema.types`, `schema.describe`. Parameters and results are documented by their schema types in `schemas/protocol.schema` and by `engine.methods` at run time.

**Invariants (tested).**
- Parse errors, invalid requests, unknown methods, and invalid params produce the standard codes with the request id echoed (null for parse errors); batches return only the responses of requests with ids and nothing for a batch of notifications.
- A rejected atomic transaction changes nothing and reports every command's diagnostic; a non-atomic one commits what succeeded.
- After `session.close`, a new `SessionManager` on the same path sees the same objects, journal, and undo position; undo and redo continue from where the previous process stopped; a new commit after undo drops the redo tail on disk as well as in memory.
- `doc.add_layer` with `edit: false` leaves the edit layer where the caller had it: the next `doc.apply` and a fresh process on the same path both edit that layer, not the new one.
- A layer added with a `partition` is stored as tile files from the first save: objects placed in different tiles land in different files, a later transaction rewrites only the tile it touched, and `doc.set_partition` without one puts the layer back in a single file. What the next process reads through `doc.objects` and `doc.get` is the same either way (`apps/engine_cli/tests`).

**Public API.** `domain/protocol/rpc.h` (`codes`, `make_error`, `Context`, `MethodDesc`, `Dispatcher`, `add_builtin_methods`, `method`, `method_no_params`), `domain/protocol/session.h` (`Session`, `SessionManager`). Types from `schemas/protocol.schema`.

**Depends on.** `base`, `containers`, `ids`, `json`, `schema`, `log`, `time`, `platform`, `tunables`, `io`, `schemas`, `doc`.

**Testing.** `tools/dev.ps1 test -Filter protocol`. Framing and error paths; the method catalogue; the Phase 0 exit criterion end to end over the dispatcher (open, create, apply, objects, get, atomic rejection, undo, redo, redo-tail drop, layers, diff, validate, close, reopen in a fresh manager); a layer added with `edit: false` that leaves the edit layer alone in the session and after reopening; a three-way merge of three override layers with both kinds of conflict, undone and redone, resolved toward theirs into a second layer, and refused for a missing layer, an empty output layer, and an unknown `prefer`; tunables, log tail, and schema discovery.

**Not yet.** Leases and proposal promotion (06 §6.5), long-running operations (06 §6.8), the MCP bridge, sockets, authentication, streaming of large results. Method versioning follows schema versioning: adding a field to a params struct is additive; anything else is a new method name.

## Methods an app registers, and `render.*`

`add_builtin_methods` is not the whole table. An app may add methods of its own, and engine-host does: `render.load`, `render.capture`, `render.benchmark`, and `render.compare` ([apps](apps.md), [renderer](renderer.md)) live in `apps/engine_host/render_methods.cpp`, not here, because the renderer is layer `systems` and the protocol is layer `domain` — a method over it cannot be registered from below it.

The registration point is **`Context::app`**, a `void*` the app fills and the methods it registered cast back. It is deliberately untyped and deliberately the only one: a handler is a plain function pointer and cannot capture, a file-scope global would make two hosts in one process impossible, and giving the protocol a typed field for every consumer above it would invert the layering. Nothing in `domain/` reads `app`, and a method that does not know what it points at must not touch it. This is the same shape ADR-0027 asks of a capability: attachment through a registration point, and no edit to the thing being attached to.

**Error code 1007, `RenderUnavailable`**, joins the list: a `render.*` method on a process with no usable GPU — no Vulkan loader or driver, no 64-bit buffer atomics, or no cluster acceleration structures when `"raster":"rt"` was asked for. It is a code of its own rather than 1006 `Unavailable` so that a client can tell "this machine cannot render" from "this host has no log ring" and from 1004 "you asked for something wrong". That distinction is what lets one end-to-end suite run on the hosted CI runners and on the GPU machines: `apps/engine_cli/tests/render_tests.cpp` skips on 1007 exactly as engine-view's suite skips on exit 3, and asserts on everything else.

The four methods are schema-typed like the rest (`RenderLoadParams` → `RenderSceneInfo`, `RenderCaptureParams` → `RenderCaptureResult`, `RenderBenchmarkParams` → `RenderBenchmarkResult`, `RenderCompareParams` → `RenderCompareResult`, with `RenderSettings`, `RenderCamera`, `RenderOrbit`, `RenderStats`, and `RenderGpuMs` shared between them), so `engine.methods` lists them and `schema.describe` explains them with no special case anywhere. Their string fields — `raster`, `shadows`, `view`, `deform`, `weights` — are parsed by the same functions engine-view's flags are, so a spelling can never mean one thing on the command line and another over the protocol.

**A scene id is the host process's, not a document session's.** `render.load` returns `"scene1"`, `"scene2"`, … and the host holds the loaded mesh, the GPU buffers, and the pipelines behind it until it exits. It is not part of `session.*`, because a rendered scene has no document behind it yet; when it does (a document *is* the scene), the id becomes a property of the session and this pairing goes away.
