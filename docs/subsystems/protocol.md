# protocol (domain)

**Purpose.** The engine protocol (docs/plan/06-agent-tooling.md §6.2, ADR-0001): JSON-RPC 2.0 dispatch over JSON values, sessions over stored documents, and the day-one method set. Transport-agnostic: `engine-host` feeds it lines from stdin (which is how engine-cli and the MCP bridge, engine-mcp, reach it), `engine-host --listen` also feeds it from a loopback WebSocket ([Transport](#transport)), tests call it in process. Every method's params and result are schema structs (`schemas/protocol.schema`), so the catalogue agents read (`engine.methods`), the JSON Schema schemac emits, and the C++ handlers agree by construction.

**Model.**
- `Dispatcher` holds `MethodDesc`s (name, doc, params type, result type, handler) sorted by name and turns a request object or batch array into a response value; `dispatch_text` adds parse-error handling and single-line framing. Notifications (no `id`) get no response. Responses carry exactly one of `result` and `error`.
- Handlers are plain functions `bool fn(Context&, const P&, R&, RpcError&)` wrapped by `method<P, R, fn>()`; `method_no_params<R, fn>()` for methods without params. `detail::read_params` turns deserialization problems into InvalidParams with `{path, message}` diagnostics in `error.data`. Command failures inside a transaction are results (`ApplyResult.diagnostics`), not RPC errors.
- `Session` owns one `doc::Document` plus its `DocumentManifest`, and every mutation goes to disk before the response: `apply` commits, drops any redo tail, journals, and saves; `undo`/`redo` move `undo_position` and save. The journal goes first (`DocumentStore::append_journal` with the document, which cuts a dropped redo tail off the file in place and appends, never rewriting it) and the save second, so a host that dies between them leaves the commit as the first patch of the redo tail; the save writes only the files the commit changed and is all or nothing ([doc](doc.md#saving), [ADR-0041](../adr/0041-a-save-is-a-log-then-files-written-in-place.md)). The side files — `leases.json`, `proposals.json`, `proposals/<layer>.base.jsonl` — go through `DocumentStore::write_side_file` and `append_side_file`: replaced atomically and only when their bytes change, and appended to. Both go through one private `commit_commands`, which also lets `merge` commit against a layer that is not the session's edit layer without moving it (the patch names the layer it edited, so undo finds it again). `doc.add_layer` appends and makes the new layer the edit layer by default; with `edit: false` the edit layer stays where it was, in memory and in the saved manifest.
- A layer's storage form is part of the protocol because it is part of the manifest. `doc.add_layer` takes an optional `partition` (`property`, `tile_size`) that stores the layer as tile files instead of one file (`domain/doc/partition.h`, plan 03 §3.7); `doc.set_partition` converts an existing layer between the two forms and rewrites its files, changing no record, so the journal, undo, and redo are untouched. An absent `partition` means one file; a `tile_size` of zero is refused rather than quietly meaning the same thing, so a caller's mistake is not silently accepted. `doc.layers`, `doc.add_layer`, and `doc.set_partition` all return the stack, and each `LayerInfo` reports the form (`partition`, absent for a single file) and the occupied `tiles`.
- `doc.merge` (`MergeParams` → `MergeResult`) is `doc::merge_layers` over three named layers, written into `output_layer` as the diff between what that layer holds and the merged records, applied non-strictly as one transaction: the result reports `applied_ours`, `applied_theirs`, the conflicts with their kind as a string, and the journal index, and the merge undoes like any other patch. A missing `output_layer` is appended to the stack outside the transaction, so undo empties it rather than removing it. Conflicts are a result, not an error; `MergePrefer` (`Ours`, `Theirs`, `Neither`) chooses how they resolve. `SessionManager` opens (or creates) a document directory, returns the existing session for an already-open path, and closes.
- Error codes: standard JSON-RPC negatives; engine codes 1000 SessionNotFound, 1001 DocumentError, 1002 ValidationFailed, 1003 NotFound, 1004 InvalidArgument, 1005 IoError, 1006 Unavailable, 1007 RenderUnavailable ([below](#methods-an-app-registers-and-render)), and plan 06 §6.5's three ([below](#roles-leases-and-proposals)): 1008 Forbidden, 1009 LeaseConflict, 1010 LeaseRequired.

**Methods (day one).** `engine.info`, `engine.methods`; `session.open` (`path`, `create`, `name`), `session.close` (the caller's hold; [several clients](#several-clients-one-host)), `session.list`, `session.info`; `client.hello`, `client.list` ([several clients](#several-clients-one-host)); `doc.layers`, `doc.add_layer` (optionally `partition`ed), `doc.set_partition`, `doc.set_edit_layer`, `doc.objects` (filter by `type` or `parent`, `offset`/`limit`), `doc.get`, `doc.apply` (commands + attribution, `atomic`, and `transaction` to stage into one), plan 06 §6.4's `doc.begin`, `doc.commit`, `doc.rollback` and `doc.transactions` ([below](#transactions-a-client-opens)), `doc.undo`, `doc.redo`, `doc.diff`, `doc.merge`, `doc.validate`, `doc.journal`, `doc.save`; `tunables.list`, `tunables.set`; `log.tail`; `schema.types`, `schema.describe`; and plan 06 §6.5's `lease.acquire`, `lease.renew`, `lease.release`, `lease.list`, `lease.require`, `doc.propose_layer`, `doc.promote`, `doc.reject` and `engine.roles` ([below](#roles-leases-and-proposals)); and `doc.put_blob`, `doc.blob`, `doc.collect_blobs`, `doc.checkpoint`, `doc.checkpoints` and `doc.rollback_to` ([below](#blobs-and-checkpoints)). Parameters and results are documented by their schema types in `schemas/protocol.schema` and by `engine.methods` at run time. engine-host adds `render.*`, `engine.ping` ([below](#engineping-liveness)) and the rest of plan 06 §6.9's day-one list — `content.build`, `session.events`, `engine.budgets`, `session.run_headless`, `engine.run_tests` — and `session.materialize` beside them, and the world capability's `session.state_hash`, `session.save_game` and `session.load_game`, below ([The day-one operations](#the-day-one-operations)).

**Invariants (tested).**
- Parse errors, invalid requests, unknown methods, and invalid params produce the standard codes with the request id echoed (null for parse errors); batches return only the responses of requests with ids and nothing for a batch of notifications.
- A rejected atomic transaction changes nothing and reports every command's diagnostic; a non-atomic one commits what succeeded.
- After `session.close`, a new `SessionManager` on the same path sees the same objects, journal, and undo position; undo and redo continue from where the previous process stopped; a new commit after undo drops the redo tail on disk as well as in memory.
- `doc.add_layer` with `edit: false` leaves the edit layer where the caller had it: the next `doc.apply` and a fresh process on the same path both edit that layer, not the new one.
- A layer added with a `partition` is stored as tile files from the first save: objects placed in different tiles land in different files, a later transaction rewrites only the tile it touched, and `doc.set_partition` without one puts the layer back in a single file. What the next process reads through `doc.objects` and `doc.get` is the same either way (`apps/engine_cli/tests`).

**Public API.** `domain/protocol/rpc.h` (`codes`, `make_error`, `Context`, `MethodDesc`, `read_only`, `Dispatcher`, `add_builtin_methods`, `method`, `method_no_params`), `domain/protocol/listener.h` (`Listener`, `CaptureSource`: the loopback WebSocket, [Transport](#transport)), `domain/protocol/clients.h` (`Clients`, `Client`: [several clients](#several-clients-one-host)), `domain/protocol/session.h` (`Session`, `SessionManager`), `domain/protocol/policy.h` (`Policy`, `Caller`, `resolve_caller`, `forbidden`, `Place`, `place_of`, `glob_match`, the tile-range helpers), `domain/protocol/leases.h` (`LeaseTable`, `lease_covers`), `domain/protocol/proposals.h` (`ProposalTable`, `compose_onto`). Types from `schemas/protocol.schema`.

**Depends on.** `base`, `containers`, `ids`, `json`, `schema`, `log`, `time`, `platform`, `tunables`, `io`, `schemas`, `doc`, and `hash` and `net` for the listener.

**Testing.** `tools/dev.ps1 test -Filter protocol`. Framing and error paths; the method catalogue; the Phase 0 exit criterion end to end over the dispatcher (open, create, apply, objects, get, atomic rejection, undo, redo, redo-tail drop, layers, diff, validate, close, reopen in a fresh manager); a layer added with `edit: false` that leaves the edit layer alone in the session and after reopening; a three-way merge of three override layers with both kinds of conflict, undone and redone, resolved toward theirs into a second layer, and refused for a missing layer, an empty output layer, and an unknown `prefer`; tunables, log tail, and schema discovery, including the default every described field states (a declared default, a value-initialized one, `null` for an optional, an enumerator by name, `[]` for a list); and the day-one operations' types — their declared defaults, the optional fields a result leaves null rather than 0, round trips of a budget, an events page and a run's params through the dispatcher's reader, and an unknown field refused. `tests/policy_tests.cpp` takes plan 06 §6.5 through the dispatcher ([below](#testing-roles-leases-and-proposals)), and `tests/e12_tests.cpp` is experiment E12's driver, a small run of which holds its invariants on every build.

**`gpu.adapters` grew the same additive way.** `engine.gfx.AdapterInfo` is at version 2 with `requirements: DeviceRequirement[]` and `verdict: DeviceVerdict` `@since(2)`, so a client that predates them reads the result it always read, and `DeviceRequirement`, `DeviceClamp`, `DeviceVerdict` and the `RequirementLevel` enum are new types of their own. The answer is the one `Device::create()` would give — the check and the report walk one table in `domain/gfx/requirements.h` ([gfx](gfx.md#what-a-device-has-to-have)) — which is what makes it worth sending back from a machine nobody here can log in to.

**`gpu.displays`: what the displays are and what a window on each is offered** (2026-10-09; E39's first measurement, [the proposal](../experiments/hdr-output-proposal.md); `gfx/display_probe.h`, [gfx](gfx.md#the-hdr-branches-and-the-surfaces-offers)). A `read_only` method with no params whose result is `engine.protocol.DisplaysResult`: `available` and `error`, `swapchain_colorspace` (the loader has the extension without which a surface lists sRGB alone), and `outputs: engine.gfx.DisplayOutput[]` — per output its name, adapter, desktop rectangle, bits per colour, DXGI colour space and `hdr` (Windows' "Use HDR" is on), the panel's primaries and its minimum, peak and full-frame luminance, Windows' SDR white level in nits, and `surfaces: SurfaceOffers[]`, per Vulkan device whether it can present to a hidden window on that output and every format, colour space and present mode it is offered. Windows only (elsewhere `available` is false with the sentence); it shows no window, opens no device and changes no display setting. `engine-cli gpu.displays --report displays.json` writes it as one JSON document.

**`schema.describe` states every field's default.** Each field of a struct's description carries `default` — the value the field holds in a default-constructed object, written through the type's own JSON writer, so it is exactly what an absent field becomes when the protocol reads params and it is in the form a caller would send (an enumerator by name, `null` for an empty optional, `[]` for an empty list); a transient field has none. schemac writes the IDL's declared defaults into the C++ initializers and nowhere else, which is why the method constructs an object to read them rather than keeping a second table. It exists for clients that generate forms or JSON Schema from the catalogue: the MCP bridge builds every tool's input schema this way ([apps](apps.md#engine-mcp-the-mcp-bridge)) and so copies no default by hand. The field is additive — a reader that did not know it reads the description it always read. A field's `type` is the IDL's spelling (`schema::kind_name` for a primitive), so the two f64 vectors of ADR-0053 read `worldpos` and `dvec3` and their defaults `[0.0, 0.0, 0.0]` or the declared one; a client that predates them sees a type name it does not know rather than a float vector, and the MCP bridge maps both ([apps](apps.md#engine-mcp-the-mcp-bridge)).

**Not yet.** Long-running operations (06 §6.8), a listener reachable from another machine (TLS; authentication itself is [below](#who-a-connection-is)), and streaming of large results. The MCP bridge exists and is a client of this protocol rather than a transport for it: engine-mcp spawns engine-host and speaks these methods over its stdio ([apps](apps.md#engine-mcp-the-mcp-bridge)). Method versioning follows schema versioning: adding a field to a params struct is additive; anything else is a new method name.

## Transport

A request reaches the dispatcher one of two ways, and **the dispatcher cannot tell which**: engine-host hands every line of stdin and every text message of a WebSocket to the same `Dispatcher::dispatch_text`, under one lock, so attribution, roles, the read-only rule, leases and the journal see the same request the same way. `transport_tests.cpp` holds that to the byte: one transaction applied over the socket and once on stdin, with the same explicit timestamp, journals identical patches, and a role refused over one is refused over the other with the same error.

- **stdio** — one request per line on stdin, one response per line on stdout. What engine-cli, engine-mcp, the console and CI use; unchanged.
- **WebSocket** — `engine-host --listen 127.0.0.1:<port>` ([apps](apps.md#engine-host---listen-the-protocol-over-a-loopback-websocket), [net](net.md)), and engine-editor's own window ([apps](apps.md#engine-editor-the-engines-window-on-a-document)): RFC 6455 over HTTP/1.1, one JSON-RPC request (or batch) per text message and one response per message, no extensions, no subprotocol. Port 0 picks a free port; the host prints `{"listen":"ws://127.0.0.1:<port>/","token":"...","session":"...","shell":"http://..."}` as its first line of stdout before it serves. engine-host still serves stdin beside it and still ends when stdin closes.

**The listener is the protocol's** (`domain/protocol/listener.h`, `protocol::Listener`; 2026-10-11, roadmap A37). It began in engine-host (`apps/engine_host/listen.cpp`) and moved here when a second host needed it: everything that makes a socket's request a protocol request — the upgrade over foundation/net, the token, the Host and Origin checks, the shell's static files, the dispatch under the host's lock — is the same in every host, so it lives where the dispatcher lives, and `net` is a foundation module, so the layering holds. A listener is made over a `Dispatcher`, the **host's own lock** (a request runs under it; engine-host's stdio loop takes it, and so does engine-editor's frame for everything that reads the document or the selection), and an optional `CaptureSource`: what `GET /capture/<id>[/<part>]` serves is the host's, because only a host keeps captures — engine-host's (`apps/engine_host/listen.cpp`, `HostCaptures`) serves the last eight `render.capture {keep}` made, and a host without one answers 404. `listener_tests.cpp` drives one in process through foundation/net's own client: the token refused and accepted both ways, a page from another origin and a request naming another `Host` refused, the shell's files served with no path escaping the directory, a capture source asked under the lock, and a `doc.apply` round trip; engine-host's `transport_tests.cpp` and the independent .NET client (`tools/host-ws.Tests.ps1`) prove engine-host unchanged in behaviour on top of it.

**Loopback, and a token — not authentication.** The listener binds 127.0.0.1 and refuses any other address with the reason (AGENTS.md's listener rule: a reachable listener is a firewall prompt per executable path, and those prompts have taken the GPU driver down). Loopback stops the network; it does not stop another process on the machine, nor a web page in the user's browser, which may open a WebSocket to 127.0.0.1. So the host makes a 128-bit token from the system's secure random source at start (base64url, 22 characters), prints it once, and closes every connection that does not carry it — in an `X-Engine-Token` header, never in a URL — or a credential the operator issued, with close code 1008 and a reason ([who a connection is](#who-a-connection-is), A4). A browser's upgrade must also come from the listener's own origin, and every request must name the listener's own address in `Host`, which stops DNS rebinding. Whoever holds the operator's token is whoever its requests say they are, exactly as on stdin; a connection holding a credential is that credential's actor and role and nobody else.

**Not built yet** (roadmap A2's remaining half): the **bulk channel** of 06 §6.2 — a capture the host kept travels as an HTTP GET of its bytes on the same listener (`render.capture` with `keep`, `GET /capture/<id>`), which is a stand-in for it on loopback, and nothing yet streams a large result as binary frames beside the JSON; it waits for a client that needs more than a capture on loopback (a remote one, or a live viewport over the socket), since on loopback the GET costs one more round trip and nothing else. **TLS** and **a remote listener** wait for authentication (A4). One host is shared by several clients — each its own caller, holding its own sessions and leases and giving them back when it goes ([several clients](#several-clients-one-host), A3).

### Events

A client on a socket may ask to be **pushed** what changes instead of asking for it (2026-10-11, roadmap A2): `session.subscribe {session, kinds}` and `session.unsubscribe`, both registered `read_only` — they change no document, lease or host setting, only what this connection is sent, like the poll of `session.info` they replace. Each event is a **JSON-RPC notification** from the host, `{"jsonrpc":"2.0","method":"event.<kind>","params":{...}}` with no id, sent **on the subscriber's own connection, in order, after the change it reports is committed** — the session publishes after the commit is journaled and saved, an undo or redo after the step is saved — never before.

| kind | params type | published by | when |
|---|---|---|---|
| `journal` | `JournalEvent` | the session (`session.cpp`) | a transaction committed, undone or redone: `action`, the patch's `index`, its `layer` and `attribution`, the record ids it touches (at most 1024, `ids_total` says how many), the document `revision` after it, `journal_length`, `undo_position` |
| `selection` | `SelectionEvent` | engine-editor (`EditorDocument::select`) | the editor's selection changed: a click in its viewport, `editor.select`, a delete that cleared it. engine-host has no selection and never sends one |
| `scene` | `SceneEvent` | engine-host's `render.load {session}` | a session's scene followed its document after a transaction: `change` "moved" (with `moved`) or "rebuilt", `instances`, the `revision` it now shows. A load that found nothing to do sends nothing |
| `session` | `SessionChangeEvent` | the session manager and the session | opened, closed, a lease taken or released (with its id, holder and layer), a change to the task ledger (with the task or review item and who changed it, and `ledger_changed` with the ids another process changed, [below](#the-task-ledger-and-review-items)) |

`session` empty subscribes to every session the host has, including ones opened later; `kinds` empty is all four. Subscribing adds kinds to what the connection already has for that session; the result names what it holds now, the queue's bound and the connection's number. `session.subscriptions` (read-only, any transport) lists every connection's subscriptions and how many events each has had dropped since it was last sent one — an operator's view of who is behind.

**Events carry no content.** Ids, indices, revisions and attribution, never a property value: a subscriber that wants the record reads it through `doc.get` or `doc.objects`, under its role, exactly as it would have after a poll. So subscribing grants nothing a read did not, and an event can never carry a value the reader's role should not see.

**What stdio refuses.** A dispatch that did not come from a connection has `Context::connection` 0, and `session.subscribe` there is refused with 1006 Unavailable naming why: stdio is a request-and-answer pipe with no channel to push on, and the answer tells the caller to poll `session.info`'s `journal_length`. An in-process dispatcher (the editor's own calls, the console) is the same.

**The queue, and why a slow subscriber stalls nobody.** The registry (`domain/protocol/events.h`, `Subscriptions`; owned by the listener, which wires it into the dispatcher's context and the session manager when it is made) is written under the host's lock, by the code that made the change, which is what orders the events. It formats each notification once and posts it to each subscriber's connection through the listener, and the server queues it there (`net::Server::post`, [net](net.md#pushing-to-a-connection)); a writer thread of that connection's own sends it, **outside every lock**. A subscriber that stops reading fills its socket's buffers, then its queue — **256 events by default, the tunable `protocol.events.queue`** — and past the bound an event is not queued: it is dropped and counted, and the next event that connection is sent carries `dropped`, the count, so it knows to read the state again (the shell refreshes everything). Nothing waits: not the host's lock, not the writer's connection, not the other subscribers. A dropped count is told with the next event, so a subscriber that resumes after the last change of a burst learns of the gap only at the next change; one that cares sooner compares `journal_length` with `session.info`. At a few hundred bytes an event (a thousand ids at most), the bound costs a stalled subscriber at most a few megabytes. Measured on Windows loopback with the bound at 4: the socket's buffers took about 80 journal events of 64 ids each before the queue filled (`transport_tests.cpp`, "a subscriber that never reads").

**Testing.** `apps/engine_host/tests/transport_tests.cpp`: a second connection is pushed the first's commit, commit, undo and redo in order with the right indices, journal lengths, undo positions and rising revisions, and a lease's `session` events; stdio's refusal, and nothing but answers on stdout; unsubscribing stops them; a connection that never reads, with the bound set to 4 through `tunables.set`, drops events while the host goes on answering the writer, and once it reads, every gap in the indices it was sent is exactly the `dropped` the event after it carries; and on a GPU, `scene` events after a move and a rebuild. `apps/engine_editor/tests/editor_tests.cpp`: `selection` events for `editor.select`, for the viewport's own path and for the scripted pick's (`EditorInput::pick`, on a GPU). `tools/host-ws.Tests.ps1`: .NET's client receives one `event.journal`. `tools/mcp-check.ps1 -Connect`: a plain client on the host is pushed each of an attached engine-mcp's commits ([apps](apps.md#attached-to-a-running-host---connect)).

### Several clients, one host

One host serves several clients of one document at once (2026-11-17, roadmap A3): the owner's shell in a browser or in engine-editor's window, an agent's bridge attached with `engine-mcp --connect`, and a command line on the host's stdin. What makes them several clients rather than several pipes into one caller is six rules, all in this module (`clients.h`, `session.h`, the listener), so engine-host and engine-editor behave alike:

- **Each is its own caller.** `client.hello {name, attribution}` (`ClientHelloParams` → `ClientInfo`, read-only, socket connections only — stdio is answered 1006, since its caller is the host's own `--actor`) says who the connection is: a label for an operator (`name`, "shell", "engine-mcp") and the actor, role and task its calls run as. Every blank `actor`, `role` and `task` of a later call on that connection is filled from it **before** the host's identity (`resolve_caller` in `policy.h`, and the dispatcher's role gate reads the role the same way), so an agent's edit names the agent without repeating it, and a connection that said it is QA is refused a write as QA. That is every write that names a caller: `doc.apply` (and its staging into a transaction), `doc.undo`, `doc.redo`, `doc.merge`, `doc.begin`, `doc.commit`, `doc.rollback`, `doc.place_asset`, `doc.instantiate_template`, D13's `doc.put_blob`, `doc.collect_blobs`, `doc.checkpoint` and `doc.rollback_to`, the leases and the proposals; `doc.transactions`, `doc.describe` and `doc.query` are reads that name nobody (the first filters by an `actor` the call gives, empty for all). A role the roles file does not have is refused at the hello (1008). It is a declaration, as a call's attribution is (roles are guardrails, [below](#identity-and-what-a-role-restricts)); a credential that carries identity is A4's. engine-mcp says hello on every connection with its `--actor`, `--role` and `--task`; the shell with a name alone, since it edits as the host's identity.
- **One document, writes in order.** Every request from every client runs under the host's one lock ([Transport](#transport); a read whose work touches nothing of the host's lets it go for that work, [below](#work-outside-the-dispatch-lock)), so transactions land one at a time in the order the host received them, and every commit, undo and redo is pushed to each subscriber in that order with a rising `revision`. `JournalEvent` and `SessionChangeEvent` (version 2) carry `connection`: the connection whose call made the change, 0 for stdio, the host itself and the engine's own write-back — so a client tells its own changes from the others' without matching attributions.
- **A session is held per client.** `session.open` of a document already open returns its session and adds the caller to its holders (`SessionInfo.holders`, version 2: connection numbers, 0 for the host's stdio and its `--doc`); `session.close` lets go of the caller's hold alone (`SessionCloseResult`: `closed` false and the holders left while anyone else holds it), and a session closes with its last holder. Closing a session the caller never opened is refused (1004, naming the holders): one client cannot close the owner's document under everyone else. The host's own clean-up of a session it just opened (`SessionManager::close`) closes it whoever holds it.
- **A lease stands against the other clients.** A lease is its actor's, as before, and it now also records the connection that took it (`LeaseInfo.connection` and `host`, version 2): the agent's lease refuses the shell's edit and the command line's alike (1009, whose `data.lease` names the connection).
- **A client that vanishes gives back what it held.** When a connection ends — closed, or dropped without a close frame — the listener, under the dispatch lock, releases every lease it took (each saved to `leases.json` and pushed as `event.session` "lease_released" with `reason` "connection closed"), then its holds, closing each session nobody else holds ("closed", which also frees the document's directory from the roots' protection, so the next client's open may write it, [below](#the-hosts-file-roots)), then its subscriptions and its entry. A lease a connection took therefore lives no longer than the connection — an agent that dies cannot hold tiles for the rest of a ttl nobody will renew — and one a host that has gone left in `leases.json` is dropped when the document is next opened, since `host` names another process (two hosts on one document at once is unsupported). **A lease is on a document's records, not on the session**, which is only how the connection reached them: `session.close`, even by the last holder, leaves the closer's leases as they are, so a client that closes and reopens a document while it is connected still holds them, and so does any other connection's lease in that session. A connection that drops while a session holding its lease is closed is still let go of it: the session manager remembers each connection that held a lease in a session closed under it (`SessionManager::detached_`), moves it to the ended ones when it drops (`ended_`, only those, so the list is bounded by the leases taken, not by the connections served), and the document's next open in this process drops this host's leases of ended connections before anyone can be refused by them (`Session::drop_ended_connection_leases`), as it drops another process's. Nothing is refused in between, since a closed document's leases are asked by nobody in this process. Leases taken on stdio carry connection 0 and keep their ttl, which is what engine-cli's host per call needs.
- **A transaction is its connection's while the connection lasts.** A transaction is its opener actor's ([below](#transactions-a-client-opens)), and two clients may say in their hellos that they are the same actor, so the actor alone would let the second commit, stage into or roll back the first's work. A transaction begun on a socket connection is therefore also held by that connection in the session, in memory (`Session::transaction_holds_`, never in `transactions.json`, since connections are this process's and a transaction outlives the host a call started): while it lasts, a call from any other connection or from stdio is refused 1008 with reason `transaction owner`, even under the opener's actor. When the connection ends the hold is let go with its leases and the transaction is the actor's again, **still staged**, not rolled back — the agent that reconnects (engine-mcp after a deadline, a new connection number) commits what it staged, as engine-cli's host per call does. One begun on stdio (connection 0) is held by no connection, as before. A session closed by its last holder keeps its transactions in `transactions.json` and the session manager keeps their holds (`SessionManager::parked_`), giving them back when the document is next opened, so a twin cannot take a transaction over by closing and reopening the document while its opener is connected; a dropped connection's parked holds go when it drops. A transaction nobody comes back to lapses at its `ttl_seconds`: nothing staged ever landed, and the next call that reads the table on that document rolls it back.

`client.list` (read-only, any transport; `ClientsResult`) is the operator's view: every connected client in connection order with its name, identity, requests made, the sessions it holds and its leases as `<session>:<id>`, and `you`, the asking connection.

**What it costs.** Nothing on a path that has one client: a connection's entry is one walk of a table of tens on each request, the identity a few string copies when a call leaves a field blank, and a session's holders a short sorted list. Release on a drop is one walk of each session's lease table.

**Testing.** `transport_tests.cpp`, "three clients of one host, one document, and a client that drops": a shell and an agent on two connections and the command line on stdin, with leases required; the hellos, a role nobody configured and an overlong name refused, stdio's refusal; the agent opening the host's document (one session, holders the host and the agent) and one of its own; its lease and its edit attributed by its hello and pushed to the shell with its connection; the lease refusing the shell and the command line; a third connection that said it is QA refused a write by the role gate; `client.list` from stdio; a close that lets go of the agent's hold alone, and the shell refused closing what it never opened; the agent dropped without a close frame, the shell pushed the lease's release with its reason and the closing of the agent's own session, in that order; and the shell then leasing the freed type and committing in order behind a refused command line, each event with a later revision. "a client's transactions and placements are its hello's, its connection's": a transaction begun, staged and committed and a `doc.place_asset`, every call naming nobody, attributed to the hello's actor, role and task (not the host's `--actor`) at the begin and in the journal's entry; a second connection whose hello names the same actor refused staging into, committing and rolling back the first's transaction while the first is connected, and committing a second one after the first drops, with the opener's attribution. "a lease and a transaction outlive their session's close, not their connection": a connection leases a type for a day, begins and stages a transaction and closes the document it alone held; reopened by a twin of the same actor, the transaction is refused to the twin and the lease refuses another client; the connection drops with no session naming either, and at the next open the other client leases the type, the twin commits the transaction, and the only lease left is the new one.

### Who a connection is

A connection authenticates once, at its upgrade, and is refused (close 1008, with a reason naming which kind of credential was missing or wrong and never what was sent) before its first message is read when it presents nothing the host knows (2026-11-18, roadmap A4, [ADR-0069](../adr/0069-a-connection-is-who-its-credential-says.md)). What it may present:

- **The operator's token**, the one the host prints at start, in the `X-Engine-Token` header. The operator is not bound: `client.hello` declares an identity and calls may name any role the roles file has, as on stdin.
- **A credential the operator issued**, in the same header. `engine-host --issue-credential <file> --name <n> --actor <a> [--role <r>] [--task <t>]` makes a token of 128 bits from the operating system's secure random source (`platform::secure_random`), 22 characters of unpadded base64url, appends `{name, actor, role, task, token_sha256, issued_unix_ms}` to the file (`CredentialsFile`) and prints the token once; `engine-host --listen ... --credentials <file>` and `engine-editor --credentials <file>` accept every credential in it. The file keeps only each token's SHA-256 (`core/hash/sha256.h`, the blobs' hash, D13), a lookup key over 128 random bits that nobody can turn back into the token: a fast hash is the right kind when the secret is random rather than chosen, and SHA-256 rather than the SHA-1 beside it because SHA-1 has had practical collisions and decides nothing about trust in this tree. A presented token's digest is compared with every entry's in constant time. Issuing is a flag of the host's command line, never a method, so no agent can issue itself one. A connection that presented a credential is **bound**: its actor, role and task are the credential's, and a call whose `attribution` names another actor or role, or a `client.hello` that does, is refused by the dispatcher with 1008 and `data.reason` `"identity"` before its handler runs — whatever the method. That turns a role from a guardrail into a boundary for that connection. **A role a host cannot enforce is never a label** (ADR-0069 decision 3a; found by a security review of this work, 2026-11-18): a bound connection runs in its credential's role as the host's roles file defines it and in nothing else — never the host's `--role` or `--task`, never the file's `default_role` — and the dispatcher gates it whether or not a file is loaded (`policy.h`, `bound_role`, `bound_allows_method`). The role every handler checks layers, tiles and types against is the credential's whatever the call said: `resolve_caller` refuses a named actor or role that is not the credential's itself (1008, `identity`, the gate's words), so it does not lean on the dispatcher's look at a top-level `attribution`. Nothing carries an attribution past that look today (params are objects, `read_params` refuses an array, and every params type holds it at the top level as `attribution`); the second check is there so a type that ever does cannot turn it into another role. A credential that names no role, or whose role the host cannot enforce (no roles file, which is every engine-editor), runs in a role naming no method, layer or type: its reads pass and every write is refused with 1008, `data.reason` `"no role"` or `"unenforced role"`. Fail closed, because the other way a credential issued `--role qa` to an editor was an unrestricted writer that `client.list` showed as `qa`. The host says at start, on stderr, how many credentials may only read there. **So on engine-editor every credential reads and does not write**: an agent that writes beside the owner attaches to `engine-host --listen --roles <file> --credentials <file>` on the document instead.
- **A browser page's cookie.** A browser cannot set a header on a WebSocket, so the `shell` address the host prints (and each one engine-editor loads) carries a **one-time ticket**, not the token — 128 random bits, good for one spend within ten minutes (`Listener::k_ticket_lifetime_ms`) and only on a request naming the listener's own address: `GET /?ticket=` spends it, answers 303 to the same address without the ticket with `Set-Cookie: engine_session_<port>=<a fresh secret>; HttpOnly; SameSite=Strict; Path=/`, and the page's socket and its `<img>` captures carry the cookie. The port is in the name because a browser keeps one cookie per name, host and path and none per port: under one name, a second host's shell overwrote the first's cookie and broke its captures and reconnects. The name does not keep the cookie from other servers on 127.0.0.1 — the browser sends it to every port — which ADR-0069 records under "What this is not". A spent, expired or unknown ticket is 403, except to a browser that already holds this host's cookie (a second tab opened from the same printed address), which is sent on without a new one; a reload is a GET of the ticketless address and needs nothing. The cookie is the operator's and lives for the browser session and the host's life. A running engine-host cannot yet print a fresh address, so a page opened later than ten minutes after start needs a restart.

**Never in a URL, never logged.** `?token=` is not read anywhere — not on the upgrade, not on `GET /capture/<id>` (header or cookie) — and no log line or error names a token, a ticket or a cookie's value. `client.list` reports how each connection authenticated (`ClientInfo.credential`: `"operator"` or the credential's name, and `bound`), never the secret. stdio is unchanged: whoever writes to the host's stdin started it. A write a client makes through an app's own document object is attributed to that client as every protocol write is (`editor.import_mesh` resolves its caller from the connection), and an agent is given a credential, never the announcement's operator token, in a file `engine-mcp --token-file` reads ([apps](apps.md)). Unauthenticated sockets hold no place an authenticated client needs ([net](net.md)).

**Testing.** `listener_tests.cpp`, "a credential's role binds with or without a roles file": with no roles file a credential naming `qa` and one naming no role both read and are refused a `doc.apply` (`unenforced role`, `no role`); with a roles file on a `--role director` host the role-less one is still refused (`no role`) and `qa` is held to its methods (`method`); `read_only_count` agrees. "resolve_caller holds a bound connection to its credential's role": a `given` naming another role or actor is refused with `identity`, and blank or its own resolves to the credential's role. `editor_tests.cpp`'s import case journals a client's import as the client. The cookie's name carries the port, and another port's name is refused. `listener_tests.cpp`, "a credential binds who a connection is": malformed credentials files refused without quoting a digest; a credential's connection listed as bound with its actor and role, a `doc.apply` naming another actor or role and a hello naming another actor refused with reason `identity`, its own and blank attributions committed and journaled as the credential's; the operator unbound; a shell address's ticket spent once for a cookie (the redirect keeps the session and `embedded=1` and drops the ticket), the spent address sent on again for a browser holding the cookie and refused without it, an unknown ticket and one past its lifetime refused, SHA-256's FIPS vector as the digest, a capture and a socket accepted with the cookie and refused with another; and in the first listener case, a token in the URL refused on the upgrade and on a capture. `transport_tests.cpp` and `tools/host-ws.Tests.ps1` present the header.

### Two hosts, one side file

One host serializes its clients; two host *processes* on one document serialize nothing, and that is the ordinary case for the tables kept beside a document: engine-cli starts a host per call, and an agent makes two calls at once as a matter of course. Each host read `transactions.json` or `leases.json` at its open, changed it in memory and wrote it whole, so the second writer dropped the first's staged command, its whole new transaction or its lease, both answered success, and both could hand out the same id from the counter they had each read (batch 68's review, 2026-11-18). **Every change to those two tables is now a read-modify-write under the file's lock** (`side_file.h`): `update_side_file` takes `<file>.lock` exclusively, reads the table afresh, lets the call change it, writes it back (atomically, and not at all when the bytes are the ones there) and lets go. The lock is the operating system's own (`LockFileEx` on Windows, `flock` elsewhere) on a file made once and never removed, which is why it was chosen over an exclusive-create lock file such as the GPU lock's: a host that dies or is killed by engine-mcp's deadline lets go with its handles, so nothing is ever stale and nothing has to judge a holder dead and break it, and the second holder in one process waits as one in another process does (`flock` belongs to the open file, where a POSIX record lock would be the process's and let it in). A holder keeps it for one call — a commit's includes the document's save — and a caller that waits 10 s (`k_side_file_lock_timeout_ms`) is refused 1005 naming the file, since a holder that long has stopped. The tables are not held for a host's life, as the review's smallest mend would have done: that would make every engine-cli call wait for an open editor. **Ids are drawn, not counted**: 53 random bits (exact in every JSON client), drawn again while the table holds the id — and for a transaction while the journal names it — so two hosts never need a number they both read; `LeaseFile` and `TransactionsFile` went to version 2 without `next_id`, and a side file, which names no version, is read at the build's version and then at each older one through the registered step that drops the counter. **A reader takes the lock too** (`read_side_file_locked`: a host's open, and the lease check below), although a writer replaces the file whole and a reader would see the old table or the new: on Windows a reader holding the file open makes the writer's rename over it fail, and the first run of the eight-process test below lost two of its eight staging calls to "permission denied" past `write_file_atomic`'s retries. A lease is checked against the table the file holds when the write is checked (read afresh), so a lease another host granted, or its `lease.require`, holds at once; that is one more small read per checked write. **`proposals.json` goes through the same helper** (2026-11-18): opening, reopening, promoting and rejecting a proposal read the table afresh under its lock and replace that proposal's entry alone (`Session::save_proposals(layer)`), and a host's open reads it under the lock; written whole from a host's table, as it was, the second host to open a proposal wrote a table without the first host's. The proposal's layer is the document's, so this keeps the table's entries and not two hosts' layers. **What this does not make safe:** the document's own files, which two hosts writing at once still overwrite (as before, unsupported: one host per document, with any number of clients). **A live host's clients' leases stay when another host opens the document** (2026-11-18): a host's open drops a socket connection's lease that another host granted as a gone host's, and from `host` alone it could not tell a gone host from a live one, so a second host's open — `session.open`, a read any credential may make — ended a live host's clients' leases (the first review of the joined protocol work). Now a host holds a **mark** while its socket connections may hold leases on the document: the operating system's lock on `leases.<host>.lock` (`side_file.h`'s lock, so a host that dies lets go with its handles), taken with its first connection lease and let go with the session. The open drops a foreign connection lease only when that host's mark is missing or free, and removes a free mark, since a host's name is drawn once per process and never comes back; a mark it cannot open counts as alive, and the lease then lasts no longer than its own expiry. It costs one 0-byte file per host process that granted a socket lease on the document while that host lives, and one lock probe per foreign lease at an open. The task ledger (roadmap A23) writes its file through the same helper ([below](#the-task-ledger-and-review-items)). Tested in `tests/policy_tests.cpp`: two session managers on one directory interleaved as two calls are (no staged command lost, three transactions with three ids), eight threads each with its own session manager staging four calls at once into one transaction (32 staged), two session managers granting leases from one file (three leases, three ids), the lock refusing a second holder for the wait and admitting it after, a version-1 `leases.json` read, two session managers that each open a proposal both kept in `proposals.json`, and a second host's open keeping the lease of a host whose mark is held, dropping one whose host left none, and, once the mark is let go, the third host's open dropping that lease and the mark; and through the executables in `apps/engine_cli/tests/policy_tests.cpp` (eight engine-cli processes staging into one transaction at once).

### Work outside the dispatch lock

Every request runs under the host's one dispatch lock, which is what keeps a host's state single-threaded with a socket in the process — and in engine-host the world advances only through requests (`session.run_headless`, `session.materialize`), so a handler that runs for a second holds every other client and the world for that second. **A handler whose work reads nothing of the host's while it runs lets the lock go for that work** through `protocol::without_dispatch_lock(ctx, work)` (`rpc.h`, 2026-11-18, roadmap A14): it looks up what it needs under the lock and copies it out, runs `work` with the lock let go, and takes it back before it answers. A review item's subject digest reads its files this way too (A56, [What a close is tied to](#what-a-close-is-tied-to), "What it costs"), comparing the document with what it composed once it has the lock back. `store.query`'s statement was the first such work: it runs on a connection of its own to a file whose path it resolved under the lock, against the text and the bound values the request brought, for up to its `max_ms`, while other connections are answered and the world ticks beside it. The alternative, a lower clamp on `max_ms` with the statement still under the lock, would still have stopped the host for that long on every call, and any role may call it.

**What makes letting it go safe**, and what a new user of it must keep:

- **The lock is the caller's to name.** `Context::dispatch_lock` is set, under the lock, by whoever holds it for the request — the listener (`Listener::message`) and engine-host's stdio loop — and put back to null after, as `connection` is; a caller that holds no lock (an in-process dispatcher, a test, `--console`) leaves it null and `work` simply runs where it is, so no handler unlocks a mutex its thread does not hold. engine-editor's own frame dispatch leaves it null: the editor registers no method that uses it (its `editor.pick_file` waits on a condition variable of its own with the lock released, `editor_methods.h`).
- **The request's fields of the context are cleared while the lock is let go, and put back after.** The stdio loop does not set `connection` and reads the 0 a request leaves behind, so a stdio call answered beside a socket's query ran as that socket's connection until the helper cleared both fields before letting go (the case's close from stdin was refused as "not held by connection 1"); another connection's request sets and clears them meanwhile, and the helper restores both before it returns, so a later call of the same batch still runs as its connection's caller (its hello's attribution, its role at the gate).
- **Nothing found under the lock is touched after it.** A session, a document or a world the handler looked up may be closed, reopened or gone when the lock comes back; `store.query` answers from its own result alone. A session closed meanwhile, or its document opened again, leaves the statement its connection to the file and its rows, and a later call on a closed session's id is 1000. In WAL mode (every `world.db` the engine writes) the world's appends go on beside the reader, which pins the WAL against a checkpoint for at most the statement's `max_ms` ([store](store.md#sql-a-client-wrote), "Beside a world"); a file in rollback-journal mode would make a writer's commit wait on the reader's shared lock, up to the writer's busy timeout of 5 s.
- **The host waits for it to end.** At exit the listener's `stop` shuts every socket and joins every connection's thread, so a statement running then finishes within its `max_ms` (one opcode more; [store](store.md#sql-a-client-wrote), "The bounds"), takes the lock back, answers into a closed socket, and only then does the host tear down its sessions.
- **One at a time per connection, several at once across them.** A connection's requests are read one after another on its own thread, so one connection runs at most one statement; several connections each run their own, each with its own 8 MiB page cache and temporary files, bounded by the number of connections a loopback listener serves. Nothing in a JSON-RPC batch is atomic, and a batch holding a query lets other clients' requests in between its calls.

**Which host writes the store beside a query.** engine-host only, and only from requests: a runtime world's write-back (`RuntimeWorld::log_writeback`) and a streamed world's tile store open `world.db` for writing under the dispatch lock, on whichever thread dispatched the request; no thread of engine-host writes it otherwise. engine-editor links no store and registers no `store.query`, and its frame loop dispatches under its own lock, so nothing writes a `world.db` beside a query there.

**Tested** in `apps/engine_host/tests/transport_tests.cpp`, "a long store.query holds up no other client, no tick, no close and no exit": one connection's batch of a never-ending statement (stopped at 4 s) and an edit naming nobody; a second connection answered `engine.ping` and a quarter-second `session.run_headless` whose tick moved, in under half the statement's time; the edit attributed to the first connection's hello though the second connection's requests ran in between; a second statement beside the session's close and its document's reopening from stdin, which answer at once, the statement still answering with its bound; and the host told to exit with a third running, which exits cleanly once it ends. A build without the store runs the same case to its 1006 answer over the socket.

### The editor's methods

engine-editor runs a listener in process over a dispatcher round the session it holds (`apps/engine_editor/editor_methods.h`), with the built-in methods every host has and three of its own (and a fourth for its tests), which are what the web shell embedded beside its native viewport and the viewport share beyond the document ([apps](apps.md#engine-editor-the-engines-window-on-a-document), [engine_shell](engine_shell.md#embedded-in-the-editor)):

- **`editor.layout`** (`EditorLayoutParams` → `EditorLayoutResult`), sent by the page as a **notification**: the viewport cell's rectangle in CSS pixels from the page's corner, the page's device pixel ratio, and (version 2) whether the page is in its narrow layout, on load, on a split drag, on a resize, when the ratio changes and when the editor asks (`editor.relayout`, below). The editor moves its viewport's child window there: CSS pixels times the ratio are the window's pixels, divided by the window's pixels per coordinate unit, rounded outward so the cell is covered. Sent as a request, it answers with that rectangle and the count of layouts received. A rectangle of non-finite numbers, a negative size or a ratio of zero is refused (external input is validated, never asserted on).
- **`editor.select`** (`EditorSelectParams` → `EditorStateResult`): the outliner's choice — a live record of the editor's session, or null to clear — so the viewport outlines it and the gizmo attaches. A record that does not exist is 1003 and the selection stays.
- **`editor.state`** (no params → `EditorStateResult`): the session, the selected record, the viewport's camera as of its last frame in `render.capture`'s shape (`RenderFramedCamera`, A32), the last layout and the picture's size. The page reads it once it connects; a click in the native viewport reaches the outliner as an `event.selection` ([events](#events)), which replaced the half-second poll of this method.

- **`editor.tool`** (`EditorToolParams` → `EditorStateResult`, read-only; 2026-10-12, A39): the viewport gizmo's tool, `"translate"` or `"rotate"`, which the editor's T and R keys set too; anything else is refused. `EditorStateResult` version 2 carries it as `tool`. When the tool changes — by the method or by a key — the editor sends every connection an **`editor.tool` notification** with params `{tool}`, so the page's toggle follows a key pressed in the viewport.
- **`editor.pick_file`** (`EditorPickFileParams {filter}` → `EditorPickFileResult {path?, grant?}`, read-only): the platform's open-file dialog on the editor's window, offering the extensions in `filter` (empty: the three mesh formats), answering the chosen file's name in `path` and a `grant` that `editor.import_mesh` takes in place of a path (never the file's directory), or null. The dialog runs on the editor's own thread — the method hands the request over and waits with the dispatch lock released, so the viewport keeps drawing — and only in a window run with no test flag: anywhere else (a test, `--offscreen`, a dispatcher with no window behind it) it answers null at once, so no test ever opens a dialog.
- **`editor.import_mesh`** (`EditorImportMeshParams {path | grant, name?, at?}` → `EditorImportMeshResult {id, name, mesh, translation, copied, reused}`) is a **write**, registered unmarked so roles govern it: given exactly one of a client's `path` (admitted by the editor's roots) and a `grant` (`editor.pick_file`'s or a drop's), it copies a `.gltf` (with the buffers and images it names), `.glb` or `.clusters` file into the document's `assets/<stem>/`, then applies **one transaction** creating an `engine.scene.MeshPlacement` named after the file (or `name`), its `mesh` the copy's path relative to the document, at `at` or — absent — where the viewport's line of sight meets the ground within 50 m, else 10 m in front of the camera, with the rationale `import <file>`; the new record is selected and the viewport rebuilds with it. Every check comes before a byte is written — a missing file, another extension, the loader's own refusal (`assets::load_gltf`, `geometry::read_cluster_file`), a file the `.gltf` names that is missing or outside its directory, a destination holding other bytes — and is refused with the reason (1004), the document untouched; the same bytes already there are reused, so importing a file twice copies it once. A transaction the session refuses removes what was copied (1001).
- **`editor.relayout`** goes the other way: a **notification the editor sends** to every connection of its listener (`Listener::notify_all`) when the display's scale under its window changes, asking the page to lay itself out and send `editor.layout` again whether or not its rectangle moved; params `{reason}`. The page answers with a layout; nothing answers the editor. It is the one message the editor speaks first, and it is not a subscription (roadmap A2's are): every page connected to the editor hears it.
- **`editor.test_report`** (`EditorTestReportParams` → `EditorTestReportResult`), registered only by `engine-editor --test-page`: the embedded page's test hook reports one of its own checks (`name`, `ok`, `detail`) as a notification, and the editor puts it in its summary ([engine_shell](engine_shell.md#the-test-hook)). An editor started without the flag answers -32601 for it, as engine-host does.

All of them change the editor's UI state and **never a document**, so all are registered `read_only`: a role that may write nothing still lays out, selects and reads, as the editor's test shows with a roles file whose only role names no method. They are **the editor's only**: engine-host does not register them and answers -32601, and a client that wants to know which host it has asks `engine.methods`.
## Methods an app registers, and `render.*`

`add_builtin_methods` is not the whole table. An app may add methods of its own, and engine-host does: `render.load`, `render.capture`, `render.benchmark`, `render.compare`, `render.evaluate`, `render.unload`, `render.scenes` and `render.progress` ([apps](apps.md), [renderer](renderer.md)) live in `apps/engine_host/render_methods.cpp`, not here, because the renderer is layer `systems` and the protocol is layer `domain` — a method over it cannot be registered from below it.

The registration point is **`Context::app`**, a `void*` the app fills and the methods it registered cast back. It is deliberately untyped and deliberately the only one: a handler is a plain function pointer and cannot capture, a file-scope global would make two hosts in one process impossible, and giving the protocol a typed field for every consumer above it would invert the layering. Nothing in `domain/` reads `app`, and a method that does not know what it points at must not touch it. This is the same shape ADR-0027 asks of a capability: attachment through a registration point, and no edit to the thing being attached to.

**Error code 1007, `RenderUnavailable`**, joins the list: a `render.*` method on a process with no usable GPU — no Vulkan loader or driver, no 64-bit buffer atomics, or no cluster acceleration structures and ray queries when `"raster":"rt"`, an explicit `"shadows":"rt"` or the reference integrator was asked for, in which case the message is the adapter's own verdict sentence naming the missing extension ([renderer](renderer.md#the-offscreen-contract)). It is a code of its own rather than 1006 `Unavailable` so that a client can tell "this machine cannot render" from "this host has no log ring" and from 1004 "you asked for something wrong". That distinction is what lets one end-to-end suite run on the hosted CI runners and on the GPU machines: `apps/engine_cli/tests/render_tests.cpp` skips on 1007 exactly as engine-view's suite skips on exit 3, and asserts on everything else.

The eight methods are schema-typed like the rest (`RenderLoadParams` → `RenderSceneInfo`, `RenderCaptureParams` → `RenderCaptureResult`, `RenderBenchmarkParams` → `RenderBenchmarkResult`, `RenderCompareParams` → `RenderCompareResult`, `RenderEvaluateParams` → `RenderEvaluateResult`, `RenderUnloadParams` → `RenderUnloadResult`, `render.scenes`, which takes no params, → `RenderScenesResult` of `RenderLoadedScene`s, and `render.progress`, which takes none either, → `RenderProgressResult`, with `RenderSettings`, `RenderCamera`, `RenderOrbit`, `RenderReference`, `RenderMetrics`, `RenderStats`, `RenderGpuMs`, and `RenderStreamStats` shared between them), so `engine.methods` lists them and `schema.describe` explains them with no special case anywhere. Their string fields — `raster`, `shadows`, `view`, `deform`, `weights`, `integrator` — are parsed by the same functions engine-view's flags are, so a spelling can never mean one thing on the command line and another over the protocol.

**`render.evaluate` is [04 §4.8](../plan/04-renderer.md#48-reference-renderer-and-objective-optimization)'s loop as one call**, which is what [06 §6.9](../plan/06-agent-tooling.md#69-day-one-operations) means by exposing it to agents as a single tool. Everything it does can be done with `render.capture` twice and `render.compare` once; the point is that a proposal is accepted or rejected on **one** answer taken under one camera, one frame number and one set of lights, rather than on three calls a script has to keep in step. It renders the real-time picture, renders the reference of the same frame, optionally renders the reference again at a single bounce, compares, writes `<name>.realtime.png`, `<name>.reference.png`, `<name>.flip.png` and (with `direct_only`) `<name>.reference_direct.png` and `<name>.flip_direct.png`, and returns both sets of metrics, the real-time statistics, the times and the machine state. The `direct` metrics are there because the difference between them and `full` is **the indirect light the real-time path does not have**, which is what makes a per-scene FLIP threshold explicable rather than arbitrary.

Two schema fields are additive, as the versioning rule requires: `RenderCaptureParams` gained `integrator` (`"realtime"`, the default and what every earlier caller got, or `"reference"`) and a `reference` block at version 2, and `RenderCaptureResult` gained `integrator`, `samples`, `trace_ms` and `seconds`. A reference capture has **only a color channel** — a path tracer writes no visibility buffer, so asking it for `ids`, `depth` or `normals` is 1004 with a message rather than a buffer of nothing, the same rule `"raster":"direct"` follows. Both the reference integrator and `render.evaluate` answer 1007 on a device without cluster acceleration structures, or with settings that build none (`"shadows":"rt"` or `"raster":"rt"` is what turns the chain on), so the end-to-end suite skips on them exactly as it skips on a machine with no GPU at all.

**Geometry streaming went the same way** ([04 §4.9](../plan/04-renderer.md#49-streaming-and-residency), [apps](apps.md#streaming-pages-at-run-time---stream)): `RenderSettings` is at version 3 with `stream`, `page_budget_mib` and `upload_budget_kib` `@since(3)`; `RenderLoadParams` is at version 3, with `page_bytes` `@since(2)` and `procedural` `@since(3)` (which procedural scene an empty `mesh` and `scene` build — `""`/`"heightfield"`, or `"shredded-atlas"`, the UV-atlas LOD fixture the scene corpus draws; an unknown name is an invalid-argument error rather than a silent fall back to the terrain, because a corpus scene that quietly got the wrong mesh would guard nothing); `RenderStats` is at version 4 with a `stream: RenderStreamStats` block `@since(4)`; and `RenderStreamStats` is the whole of `renderer::StreamStats`, field for field, under the key names engine-view's `streaming` summary object already uses, so one reader serves both hosts. Every one of them defaults to what a caller before them got — no streaming, no page table, and a `stream` block whose `pages_total` is 0.

Three things about that set are worth the sentence they cost, because each one is a question a reader will otherwise have to answer by reading code.

**The units differ on purpose.** The protocol says `page_budget_mib` and `upload_budget_kib`; `renderer::RenderSettings` says `page_budget_bytes` and `upload_budget_bytes`. The wire is where a *person or an agent chooses a number*, and the two numbers are chosen at different scales — a residency budget is a fraction of a scene and an upload budget is a fraction of a frame — which is why `engine-view --page-budget` takes MiB and `--upload-budget` takes KiB and why the protocol spells them the same way rather than inventing a third spelling. The renderer sizes buffers, so it counts bytes. The conversion is four lines in `read_settings` (`apps/engine_host/render_methods.cpp`), which is the one place the wire meets the module, and `systems/renderer/settings.h` is therefore never in the position of having to say what unit its caller was thinking in. The end-to-end case pins it by asking for 1 MiB against a scene of 3.8 MB of pages and checking that `budget_bytes` comes back as 1048576 rather than clamped.

**`page_bytes` is a load parameter, not a render setting.** It is `SceneDesc::page_bytes`, and it sits on `RenderLoadParams` because laying a mesh out in pages **renumbers its clusters** — it changes what loading *produces*, not how a frame is drawn. A host that keeps a `SceneData` across calls (this one does; that is what a scene id is for) cannot have it as a setting, because a settings change rebuilds only the GPU buffers and the pipelines from the `SceneData` that is already there. It applies to the procedural heightfield alone, for the reason `scene.h` gives: a glTF's and a container's layout is fixed at the default target because that target is part of `geometry::cluster_cache_key`, and two targets would be two different containers. `settings.stream` on `render.load` is the separate question of whether the page table is kept at all; asking a later call to stream a scene that was loaded without one turns streaming off with a log line rather than failing, which is `resolve_settings`' rule and not a protocol special case.

**Shadow casters went the same way** (2026-09-24, [renderer](renderer.md#shadows)). `RenderSettings` is at version 4 with `shadow_casters` `@since(4)`. It defaults to `true`, the renderer's own default, and `false` is `engine-view --no-shadow-casters`. `RenderStats` is at version 5 and `RenderViewStats` at version 2, each with a `shadow_casters` count, which is not part of `visible_pairs` because nothing draws a caster. `view` also accepts `"shadow"`, the resolve's shadow view, through the same `parse_view_mode` engine-view's flag uses. (And `"albedo"`, the textured base colour unlit, since 2026-09-24: the same parser, so no schema change; [renderer](renderer.md#built-textures).) Every one of them reads as before for a caller that does not send it. The one behaviour change is the default: a scene loaded with traced shadows now builds its casters, and a client that wants the old frames asks for `"shadow_casters": false`.

**The ray tracing chain's memory went the same way** (2026-09-24, [renderer](renderer.md#the-ray-tracing-chains-memory)). `RenderSettings` is at version 5 with `rt_budget_mib` `@since(5)`, the most device memory the per-frame cluster acceleration structures may take (0 is the `renderer.rt.budget_mib` tunable, and that tunable's 0, its default since 2026-10-27, a sixteenth of the device's memory from 512 to 4,096 MiB: [renderer](renderer.md#the-budget-follows-the-device)); it is `engine-view --rt-budget-mib`. `RenderStats` is at version 7 with an `rt: RenderRtStats` block `@since(7)` — the capacity now and at its peak, the budget as a capacity, the scene's union, the bytes now and at their peak, the last frame's built and wanted counts, the resizes, and the frames that dropped instances' structures — under the key names engine-view's `rt` summary object uses. The flythrough summary (`engine.scene.FlythroughSummary`, version 2) carries the same totals in its own `rt` block with per-frame percentiles of what was built and wanted, `FrameRecord` (version 2) carries `rt_built`, `rt_wanted` and `rt_capacity` and streaming's per-frame state, and `PassMs`/`PassPercentiles` (version 2) add the bottom-level build `blas` beside `clas`. **The cascaded shadow maps added a spelling, three settings and four numbers** (2026-09-24, [renderer](renderer.md#cascaded-shadow-maps); it landed after the chain's sizing above, so a struct both changed is one version past that one's). `RenderSettings` is at version 6: `shadows` also accepts `"csm"` (parsed by the same `parse_shadow_mode` engine-view's flag uses), and `shadow_cascades` (1..4, default 4), `shadow_map` (64..4096 texels, default 2048) and `shadow_distance` (0: the far side of the scene's bounds) are `@since(6)`, validated in `read_settings` like the view fields. `RenderGpuMs` is at version 2 with `shadow` and `shadow_cull` `@since(2)`, and `RenderStats` at version 8 with `shadow_pairs` and `shadow_fallback` `@since(8)`; the results' `shadows` string says `"csm"` when that is what ran. Every one of them reads as before for a caller that does not send or read it. **The one behaviour change is the default on a device that cannot trace**: `"auto"` there used to draw no shadows and now draws the maps, so a client on the TITAN Xp that wants the old frames asks for `"shadows":"off"`.

**The vertex path's indexed draw added two counts** (2026-09-24, [renderer](renderer.md#statistics)). `RenderStats` is at version 6 with `triangles_hw` and `vertex_fallback` `@since(6)`: the triangles the baseline tier's indexed draw drew in the last frame, and the clusters its index budget sent to the capacity draw instead. **`render.capture` needed no field** (2026-09-24; it has had a `settings` override since 2026-10-03, below). It had no `settings` block at all — it renders with the settings the scene was loaded with (`scene->requested`) — so it inherits streaming from `render.load` and adding a `stream` field there would have been a second way to say something the scene already says, and a way that could contradict it. `RenderBenchmarkParams` has had an optional `settings: RenderSettings?` since version 1, so it gets the three new fields with no change of its own, and a per-call block that turns streaming off rebuilds the GPU scene whole exactly as any other settings change does. That is what the end-to-end case asserts second, because a `pages_total` of 0 from a scene that has a page table is the only evidence that the additive field travelled all the way into the renderer rather than being decoded into a struct nobody reads.

**Not yet: the container-backed page source.** Over the protocol a streamed page's payload always comes out of host memory — `stats.stream.source` is `"host"` — where engine-view's `--page-source file` can read it back out of the meshes' `.clusters` containers instead. The blocker is not plumbing. `renderer::attach_page_source` **releases the merged host streams** as the other half of what it does, which is the whole point of it, and those streams are exactly what `RenderHost::ensure_renderer` rebuilds a `GpuScene` from when a later call changes the settings. engine-view may release them because it builds its scene once and never again; a host whose `render.benchmark` may be handed `{"stream":false}` for a scene loaded with `{"stream":true}` may not. Attaching one means either refusing that rebuild or re-opening the source against each new `GpuScene`, and neither is worth building untested — every scene this host can construct without a content fixture is the procedural heightfield, which has no container behind it and would be refused a file source anyway. When it is done, `source`, `file_reads`, `file_bytes` and `host_bytes_freed` are already in the result waiting for it.

**`render.benchmark` flies a camera path** (`RenderBenchmarkParams` version 2, `RenderBenchmarkResult` version 3). A `camera_path` names an `engine.scene.CameraPath` file, read against the loaded scene's terrain, and the run becomes a flythrough: `repeats` flights of the path at its own frame count (or `path_frames`), each after `warmup` frames and `warmup_seconds` at its first camera, and the result gains `flythrough`, the `engine.scene.FlythroughSummary` `engine-view --benchmark` ends its `.jsonl` with — per-pass percentiles over the path, the hashes that name what was measured, and the machine state. Both hosts fly it through `renderer::fly_camera_path`, so the numbers are the same numbers; `frames` is ignored when a path is given, because a path says how long it is. `RenderLoadParams` version 4 adds `overlay`, the local manifest that replaces a scene file's meshes by content hash ([renderer](renderer.md#scenes-camera-paths-and-flythroughs), [apps](apps.md#flythroughs)). The schema types come from `schemas/scene.schema`, which `protocol.schema` imports, so `schema.describe` explains the summary as it explains any result. `FlythroughSummary` went to version 4 on 2026-09-24 with `cpu_ms` and `frame_ms` percentiles (the CPU's milliseconds per frame and the wall time between frames, which `fly_camera_path` now measures), `ticks` and `interactive` (engine-view's interactive sessions; zero and null here), all `@since(4)` with defaults, so a client that read version 3 reads the same fields ([renderer](renderer.md#scenes-camera-paths-and-flythroughs)). Version 9 (2026-09-27) adds `sun`, the stand-in sun's day engine-view can run ([renderer](renderer.md#the-suns-day)); `render.benchmark` carried it as null until 2026-10-03, when the host began to run the clock and the time-lapse (below).

**One request, two hosts** (2026-10-03; [renderer](renderer.md#one-request-two-hosts)). The sky's hour and exposure ([ADR-0048](../adr/0048-the-sky-is-a-providers-model-drawn-by-the-renderer.md)), the ground's time, and the ground on rings or on the world's tiles ([ADR-0050](../adr/0050-the-ground-is-drawn-from-the-worlds-tiles.md)) had landed behind engine-view flags with nothing in `render.*`, because each host turned its own spelling into `RenderSettings` and `FrameDesc` by hand. What was added, every field optional with a default that is today's behaviour:

**Read-only stays read-only.** All of it rides on methods that were `read_only` and stay so: a clock, an exposure or a ground layout changes what one call draws and no document, lease or host setting. A scene whose ground is drawn as terrain levels is rebuilt for every call that draws it — the motion and the tiles carry the calls before — so no call's picture depends on another's.

**What a person at engine-view can ask that a call cannot, and why** ([renderer](renderer.md#one-request-two-hosts) has the whole list): the window, its present mode, pacing, vsync and swapchain (a presenting host's); input, an interactive session, a recording and its replay (a window's); the animation capability's `--animate` and `--morph-animate` (a capability above the renderer, which a host drives through `FrameDesc::joints`; engine-host has no world of animated instances behind `render.*`); a streamed world's ruins (`--world`, the world capability's ring of instances, which engine-view's `ViewWorld` drives — the ground on tiles follows the camera here by the ring's first-fill rule instead); the census, the occlusion check and marker captures (analyses a client composes from captures, or a follow-up); `--uv-seams` and its three companions (a content-build question: `content.build` takes them and `render.load` reads the container); `--page-source file` (the "Not yet" above); and `--tunable` (process state, which engine-host takes at start with `--tunables`).

**A scene id is the host process's, not a document session's.** `render.load` returns `"scene1"`, `"scene2"`, … and the host holds the loaded mesh, the GPU buffers, and the pipelines behind it until **`render.unload`** releases it or the host exits. It is not part of `session.*`, because a rendered scene has no document behind it yet; when it does (a document *is* the scene), the id becomes a property of the session and this pairing goes away.

**What belongs to a scene, and what to a session.** A scene is everything `apps/engine_host`'s `RenderHost::Scene` holds: the loaded `SceneData` (clusters, the LOD graph, instances, materials — the host arrays), and once a capture, benchmark or evaluate has drawn it, the `GpuScene` (geometry buffers, textures, acceleration structures), the `SceneRenderer` (pipelines, screen-sized targets) and, after a reference render, the `ReferenceRenderer`. A session is a document: its layers, journal and undo position, all on disk after every commit. The two never own each other, so **closing a session unloads nothing, and unloading a scene closes nothing**: `render.load` names no session, the same loaded scene serves whichever documents a client is working on, and a scene built from a document does not exist yet. Tying them now would mean inventing an owner — and a `session.close` that quietly freed GPU state another client was measuring. What the host *does* own is the device, which stays open when the last scene goes, because it belongs to no scene and the next load would only open it again.

**`render.unload`** (`RenderUnloadParams {scene}` → `RenderUnloadResult`) takes the scene out of the host's list and lets it go through the renderer's own teardown — the reference path tracer first (it holds the renderer and the GPU scene), then the renderer (whose destructor waits for the device to finish the frames it submitted), then the GPU scene, then the host arrays — which is the same order the host's destructor always used, now one function (`RenderHost::release`). There is no other cache to clear: `engine.budgets` reads the same list, and the derived-data cache is content-addressed files that belong to no scene. The result says what went: the counts, whether there was GPU state and a reference renderer to release, the textures and their bytes, the engine allocator's heap before and after (the host arrays), and the device memory this process used before and after as the driver reports it (VK_EXT_memory_budget, null without it). **The driver's figure counts the allocator's blocks, not its allocations**, so it moves only when whole blocks come or go: a scene small enough to fit in blocks an earlier scene opened leaves it where it was on load and on unload, and a large one — the end-to-end case draws a heightfield at 7680×4320, whose screen-sized targets are allocations of their own — takes it from 137.7 MB to 849.4 MB and unload brings it back to 139.5 MB, the same figure after every further cycle, on the RTX 5090. **Ids are never reused**, so an unloaded id stays dead: every render method given it answers 1003 NotFound — the code a missing scene has always had, so no client needs a new one — with a message that says it was unloaded (`no scene scene3: it was unloaded; render.load it again`), where an id that never existed gets only `no scene scene9`.

**`render.progress`** (no params → `RenderProgressResult`, read-only; roadmap W79) is the process's live load progress ([profiling](profiling.md#the-trace-is-live)): `render.load` follows a plan of its two stages (`scene file`, `load scene`, the same weight each) and its two milestones (`scene_read`, `scene_loaded`), finishes it when the call succeeds, and stops following it however the call ends — so an answer is either the load running now or the last one's record: `active`, `done`, `stage` and `detail` (what runs inside it), `stages_done` over `stages_expected`, a `fraction` that never falls during one load, the `milestones` reached by name, `bytes_read`, `items`, `elapsed_ms`, and a `sequence` that grows with every change. **A method and not a notification**, because what wants it — the editor's shell, an agent's client, a tester's script — polls at its own pace and a notification would need an event kind and a subscription for a value that is only ever read. The limit to know: every dispatch takes the host's one lock, so **a poll waits behind the `render.load` it asks about** on the same host and answers when that returns; the record is readable from any thread without the lock, and answering it outside the lock (a read-only fast path in the listener) is the follow-up that makes it live across connections. engine-view's window reads the same record every loading frame ([apps](apps.md#the-loading-presentation)).

**`render.scenes`** (no params → `RenderScenesResult`) lists what the host holds, in load order: each scene's id, what it was loaded from (`kind` `mesh`, `scene` or `procedural`, and the path or the procedural scene with its grid), its counts, whether its GPU state is built with the frame size and resolved raster and shadow modes it was last built for, whether a reference renderer is kept, and its texture and ray tracing bytes with the images that shared another mesh's texture and what that saved; then the adapter and the process's device memory used and available, and the engine allocator's heap. It **opens nothing**: before any render call the adapter is empty and the memory figures are null, not zero. A client that can unload has to be able to see what is loaded, and before this the only way to learn which scenes a long-lived host held was to remember every `render.load` it had ever sent.

### `engine.ping`: liveness

`engine.ping` (no params → `PingResult {pid, uptime_seconds}`) answers that the host is alive and reading requests. It reads a clock and nothing else — no session, no device, no lock — so asking costs nothing and can never itself be the call that hangs. It is registered by engine-host's `main.cpp`, not here and not beside `render.*`: liveness is a question about the process, and every method list the host serves goes through its one dispatch loop. **There is no generation** in the answer, because a host cannot know how many hosts came before it; the client that starts hosts counts them (engine-mcp's `host_info` reports its count) and compares `pid` to know whether it is still talking to the same process. What a client does with a host that does *not* answer is the client's: engine-mcp gives every call a deadline and replaces the host when one runs out ([apps](apps.md#engine-mcp-the-mcp-bridge), "Deadlines"). engine-host's `--debug-hang <method>` is the test hook that makes such a host on purpose ([apps](apps.md)).

All fifteen types were new, so nothing existing moved a version; they are schema types in `schemas/protocol.schema` like every other method's, `engine.methods` lists them, `schema.describe` explains them, and the MCP bridge's `list_schema` shows them with no change anywhere. The bridge's curated tools are a table, though, so reaching them as MCP tools took five rows in `apps/mcp_bridge/tools.cpp` ([apps](apps.md#the-tools)), and `session.materialize` a sixth (`materialize`).

**`Context::app` is now the host's whole state.** It is one pointer, deliberately ([above](#methods-an-app-registers-and-render)), so engine-host points it at a `host::HostState` (`apps/engine_host/host_state.h`) holding the `RenderHost` and an `OpsHost` — the sessions' runtime worlds — and `render.*`'s handlers take `.render` out of it. An app with several families of methods gathers their state behind the one pointer rather than asking the protocol for a second.

**A capability this build left out is 1006 `Unavailable`, with a message naming the switch** — `session.events` with `source: "store"` or an explicit `store` on a host without the store capability, `engine.run_tests` with a `tissue` file on a host without the tissue capability. It is not a code of its own, unlike 1007: to a client it means exactly what 1006 already says, "this host does not offer that service", and the bridge's hint for 1006 already reads that way. A method that merely reports less without a capability says so in its result instead: `session.events`' `store_status` is `"not built"`, `engine.budgets` lists no `audio.*` budgets without audio, and `session.run_headless` runs the scheduler alone and its report says why nothing materialized (below). None of the five asserts on input; every refusal is 1004 with a sentence, and a missing session is 1000.

**`content.build`** is `engine-content build` and `build-all` in the host's process, through `domain/content_build` ([content_build](content_build.md)) — the same code, so the same bytes, cache keys and skip. Give `source` (with `output`, or `cache: true` for the derived-data cache entry the source and the options address; both at once is refused, as engine-content refuses `--cache` with an output file) or `manifest`, not both. `options` are `engine-content build`'s flags as a `ContentBuildOptions`, whose declared defaults are the build's own (the module's test holds them together), and they are the defaults of a manifest's entries, which override `max_triangles`, `max_vertices`, `page_bytes`, `weld` and `atlas` as `build-all` lets them. `ddc` empty is `<repo>/ddc` found above the host executable; `jobs` sizes a job system made for the call — one mesh's primitives are its parallelism, as in `build`, and a manifest's meshes are, as in `build-all`. **An output that already records this source's hash and this build key is skipped**, for a single source as for a manifest — `build-all`'s rule, where `engine-content build` always rebuilds — and `force` rebuilds it. Each `ContentBuildOutput` is a `build-all` line: `status` (`built`, `skipped`, `failed` with `rule` and `error`), path, the identity, bytes, milliseconds, the counts, the validation warnings (`path` is the rule id), `repairs` and `atlas` exactly as engine-content's JSON line has them, `textures`, its share of the texture step, and — with `stats` (the default) — `stats`, the object `engine-content stats` prints for the container. **The texture step runs as engine-content runs it**: when the call has a derived-data root — `cache`, or a named `ddc` — every image the meshes sample is built into `<ddc>/textures/<key>.tex` ([texture](texture.md)) after the containers settle, in manifest and then image order, a texture two meshes share built once, a skipped mesh's textures checked from its container; `textures: false` is `--no-textures`, and the result's `textures` has the totals. A texture that fails is counted there and logged, and does not fail the call, where it makes engine-content exit 1: a protocol result says what happened and leaves the verdict to the caller. A failed entry is a result, not an error, and does not stop the others; an unreadable or malformed manifest is 1005 or 1004 before anything is built. **A generated mesh** (a `.flora.json` palm, a `.rock.json` rock) is given the repository's material pack, `<repo>/content/materials` above the host executable, through the function engine-content calls (`content_build::attach_repository_pack`), so one manifest through either host is the same key and the same bytes (T78, 2026-11-09: until then this host gave a generated mesh no pack; `apps/engine_cli/tests/content_build_parity_tests.cpp`). **Not yet:** a manifest's derived steps (`"clips"`, the audio capability's `.clip`) are `build-all`'s and are not read here ([content_build](content_build.md#derived-steps)). **Content classes** (C62, `ContentBuildOutput` version 2): an output whose source's sidecar declares a class carries `content_classes` (its categories with their ladders, its levels and its materials', by name), null for every other; a sidecar that cannot be read fails that output with rule `content.class`; and a manifest naming a categories file is refused here, because that path would be read without the roots' admission every other path of the call takes ([content_build](content_build.md#content-classes)).

**`session.events`** reads what has happened to a document, a page at a time. `source` is `"journal"` — the document's committed patches, each an event of kind `"commit"` with its `sequence` (the patch index), `actor`, the whole `attribution`, the `layer`, the command count and `applied` (false in the redo tail) — `"store"`, or empty for both, the journal's first. **The store half is the persistent world's event log** ([store](store.md), [03 §3.5](../plan/03-data-model.md#35-persistent-world-state)) **when the host has the store capability and the document has one**: a document "has one" when its directory holds `world.db`, or `store` names another file. That convention is this method's, because nothing else yet ties a save to a document; it is the smallest one that keeps the two side by side on disk, and the parameter is there so a save kept elsewhere can be read. The log is opened read-only (`read_only`, no journal-mode pragma), and its events come in `(tick, tile, sequence)` order through `store::EventLog::scan` — tick first, because a log is appended in tick order, so a cursor that stopped at an event finds everything appended since after it; the per-tile sequence alone cannot say "after this" for the whole log. A store event carries its `tick`, `game_time_us`, `tile`, `sequence`, `kind` (the schema type id in decimal), `actor` (the origin: deterministic, player, agent, llm or debug), `subject`, `cause`, `depth` and `payload_bytes`; the payload itself is schema-typed bytes the store does not interpret yet, so it is not returned. `since` is where a read with no cursor starts (the journal's first patch index; the log's first tick), `kind` and `actor` filter, `limit` is 1..10000, and `next` is an opaque cursor (`j=<index>;s=<tick>:<tile>:<sequence>`) that moves only past what was returned or filtered out — so it is also what to poll with, and `more` says a matching event was left for the next page. One caveat is the journal's own: a commit after an undo replaces the redo tail at the same indices, so after an undo a poller reads again from `since`.

**`engine.budgets`** names every budget the engine knows today and what uses it, so a client learns what a budget is called before it is exceeded ([ADR-0017](../adr/0017-no-hidden-limits.md)). Each `Budget` is `name`, `doc`, `limit`, `used`, `peak`, `unit`, `source` and `key`, and a `scope`:

| Name | Scope | Limit comes from | Used |
|---|---|---|---|
| `renderer.deform_pool` | process; each loaded scene | `k_default_deform_pool_kib` (8 MiB), a scene's `GpuScene::deform_pool_bytes()` | the last frame's deformed vertices × 12 bytes, and the peak |
| `renderer.page_budget` | process; each streamed scene | `settings.page_budget_mib` (no limit by default: every page) | the resident page bytes |
| `renderer.upload_budget` | process; each streamed scene | `k_default_upload_budget` (256 KiB a frame), or the setting | not tracked per frame |
| `renderer.rt` | process; each scene | `settings.rt_budget_mib`, else the `renderer.rt.budget_mib` tunable, else (its default, 0) a sixteenth of the device's memory, 512 to 4,096 MiB; the process reports `source: "device"` and no limit, each scene its own and where it came from | the per-frame structures' bytes, and their peak |
| `audio.clips`, `audio.voices` | process (with audio); each session's runtime world | the `audio.clip_budget_mb` and `audio.voices` tunables, a world's clip store and mixer | resident clip bytes, live voices |
| `memory.allocations` | process | none: a counter | `mem::allocation_counter()` |
| `memory.heap` | process | none | `mem::total_stats()`, with the peak |
| `gpu.memory` | each adapter | the device-local heaps, or VK_EXT_memory_budget's budget on the device a render call opened | that device's `used_bytes`; unknown otherwise |

**Null is not zero**: a `limit` of null is a quantity counted but not bounded (the allocation counter, whose rule — no allocations in a steady-state frame — is measured where a frame loop runs, not in a host between requests), and a `used` of null is a budget nothing in this host is using yet. The process rows are the defaults a scene starts from; a scene's rows are the buffers it was built with and what its last frames used. **Asking opens nothing**: the adapters are enumerated without a device, and only a device a `render.*` call already opened answers the memory-budget question. `scope` filters by prefix (`"process"`, `"scene"`, `"session"`, `"adapter"`). The names are stable; the end-to-end case pins them and their order.


### `session.run_headless`: the materialized world

`session.run_headless` materializes **the session's document** into **the session's runtime world** and steps it at the fixed step, 60 Hz and 16,667 µs a tick, with no rendering ([06 §6.11](../plan/06-agent-tooling.md#611-automated-playtesting)'s headless `sim` mode): `seconds` of game time rounded to whole ticks (0.5 s is 30), at most 3,600, or until `until` holds, with `seconds` as the most it may run. The world is made by the first call on a session, kept by the host while it runs — so a second call continues from the tick the first stopped at, and a fresh engine-cli call starts a fresh one — and dropped once its session is closed.

**Until 2026-09-24 this stepped a world the document did not populate**, and the page said so in four parts: no mapping from a record's type to the components it becomes, no driver walking a document's records through the materialization hooks, the executor decision open, and no write-back. Each now exists, and each is written up where it lives:

1. **The mapping is data**: a `materialize` declaration in the IDL beside the record type — which components, which property fills which field, unit conversions where both sides declare `@unit`, what the parent becomes, which fields the world may write back — compiled by schemac into a table (`schema::MaterializeRegistry`) the runtime reads with no per-type code ([schema](schema.md#materialization-type-mapping-as-data), [schemas/README.md](../../schemas/README.md#materialize-what-a-record-becomes)). A record type with no declaration stays document-only, by design, and is counted.
2. **The driver** walks the document's live records through its composed index into the scheduler's hooks table, parents before children and then by id, the first call in full and later ones through the document's change feed so an unchanged record costs nothing ([sim](sim.md#the-driver-a-document-through-the-hooks)); the entity store's hook creates each entity keyed by its record's `Id128`, writes its fields and makes the document's parent its `ChildOf` ([ecs](ecs.md#materialization-the-entity-stores-hook)).
3. **One executor**: the engine's scheduler owns the tick and runs flecs' systems inside its phases ([ADR-0038](../adr/0038-the-scheduler-owns-the-tick.md), proposed; `executor` in the result says `"scheduler"`).
4. **Write-back**: at `Persist`, every `write_back_every` ticks (default 60, one game second) and once more when the call returns, what systems changed in the writable fields is committed to the session as one transaction attributed to `system` — so `session.events` shows it as a commit whose actor is `system` — and, when the document keeps a `world.db`, logged as one `engine.world.WriteBack` event per record, origin `deterministic` ([sim](sim.md#write-back), [store](store.md#write-back-events), [doc](doc.md)). Nothing else writes the document from the world.

**Every call materializes first**: the whole document on the first call, and what changed since on every later one — so an agent's `doc.apply` between two calls reaches the world on the next. The result carries that pass as `materialize` (a `MaterializeResult`, below).

**What world the host builds.** With the ECS capability: `sim::SimScheduler`, a flecs world (`ecs::SimWorld`) whose systems the scheduler runs, the entity store's hook first in the hooks table, the engine's world components (`engine.world.Transform`) and every ticking capability the host links — `systems/kinematics` (so `engine.kinematics.Mover` records move), `systems/animation` (over an empty clip library, its hooks after the entity store's) and `systems/audio_system` (over a mixer on the null backend; the host pulls zero frames after each tick so the commands it queues are applied and the ring never fills). Records materialize at **LOD0**: a headless run has no observer to promote from. Without the ECS capability it is the scheduler alone — the fixed step, the tick and the game clock — and a driver with no target, which materializes nothing and says why in its report (`no entity store`); `world` says which.

**The result.** The ticks this call ran, the game seconds they advanced, the wall milliseconds, the predicate's value when the call returned (null without `until`; read after the final write-back, so a document term can turn true on it with the time already out — `stopped` says which ended the loop), the world's own tick and game time, its kind (`"ecs"` or `"scheduler"`), `executor`, the systems it ticks (the flecs systems in registration order, then the scheduler's own table: `sim.write_back`), `entities` (entities with a persistent identity), `materialized` (the entities the driver holds from the document), `materialize` (this call's pass), and `write_backs`/`written_fields` (the commits this call made and the fields they wrote). `RunHeadlessParams` and `RunHeadlessResult` are at version 2; `write_back_every`, `executor`, `materialize`, `write_backs` and `written_fields` are `@since(2)` with defaults, so a client that read version 1 reads what it always read — except that `materialized` is no longer 0 by construction.

**The predicate** reads the document and the live world. `{"object": <id>, "property": <name>, <test>}` is a live document object's composed property; `{"object": <id>, "component": <type>, "field": <name>, <test>}` is a field of the live entity that object materialized into, by the component's qualified name (read through `ecs::component_json`, so the host names no flecs type); `<test>` is `"equals": <value>` (compared as JSON, numbers by value), `"at_least": <number>` or `"at_most": <number>`, and a name may end in `[i]` to take one element of an array — `"position[0]"`. With them `{"object": <id>, "exists": true|false}`, the run's own clock `{"ticks_at_least": n}` and `{"seconds_at_least": s}` (counted in this call's fixed steps), and `all`/`any`/`not` over them. A document term now changes during a run, because write-back writes the document: at the default cadence once a game second, and every tick with `"write_back_every": 1`. A malformed predicate — an unknown term, a key a term does not take, an id that is not 32 hex digits, a term with no test or two, a bound that is not a number, nesting past 32 or more than 1,024 terms — is 1004 naming the path (`until.all[1].object`).

**Streamed tile by tile (`stream`, version 3).** With `stream` — a `HeadlessWorld` — the call does not materialize the whole document: it keeps a **tile ring** round the observers it declares ([world](world.md)) — each a `HeadlessObserver`, whose `position` is a `worldpos` since version 2 (2026-10-06, [ADR-0053](../adr/0053-world-positions-are-f64-and-the-gpu-sees-none.md): f64, refused outside the cells' extent, and the same JSON as before) — and materializes the document's partitioned layers a tile at a time as the ring takes tiles in, through the same driver (`sim::Materializer`'s tile passes, [sim](sim.md#the-driver-a-document-through-the-hooks)). Each observer is a position, a velocity in metres per game second applied every tick, and a weight; the ring's `tile_size` must be the partitioned layers' own (on another grid the document consumer refuses every tile, counted in `refused` with one warning in the log, since one ring tile would then name parts of up to four of the layer's), `rings` are the radii in tiles innermost first (empty: the capability's 1.5, 8 and 24), `hysteresis` is the ring's, and `simulated` says how many rings, innermost first, are materialized and reconciled. What no layer tiles — an untiled layer's records — is materialized whole first, as a streamed game's global records would be, and with it what changed since the last call in the tiles still live, so an edit between calls reaches the world at the next one ([world](world.md#the-hosts), "Edits between calls"). The ring updates once before the first tick with no budget, so the call starts from the whole ring, and then once between every two ticks at the ring's budget (8 activations and 16 deactivations an update by default, the `world.ring.*` tunables), so an observer that outruns the budget fills in over the next ticks rather than stalling one. **With the store capability and `store` (the default)**, each tile is reconciled from the document's `world.db` (created beside it when absent) when it comes in — `SimScheduler::reconcile_tile`, step 1 of [05 §5.5](../plan/05-simulation.md#55-reconciliation-when-a-tile-activates) — and its projections and snapshot are written when it goes, so a tile that comes back reads what it left ([store](store.md)). The ring and its store outlive the call, as the runtime world does, and take the first call's parameters; a later call's observers move it. The result's `streamed` (a `HeadlessWorldResult`) is the call's share: updates and the events by kind, the active tiles after the call in tile order with their rings, the tiles the document consumer materialized and let go with the entities it created and dematerialized (and, since `HeadlessWorldResult` version 2, `arrived`: how many of those created were brought in between passes because a capability's own rule put them in a live tile — the npc capability's schedule index, [npc](npc.md#the-schedule-index); a field `@since(2)`, so a client that read version 1 reads what it always read), the store consumer's reconciled, known, summarized, read-back and written tiles, the ring update's median and worst microseconds and each consumer's milliseconds, and whether the store was kept. A host without the world capability answers a call with `stream` 1006 `Unavailable`, naming `ENGINE_WITH_WORLD`. Both types are new and `@since(3)`, so a client that read version 2 reads what it always read. **The method is still a write**: it was one before (it commits write-back to the document) and it is not registered `read_only`, so a role that lists it gets the stream with it and one that does not is refused, as before ([Roles, leases and proposals](#roles-leases-and-proposals)). The edit that added it is confined to `apps/engine_host/ops_methods.cpp` and the schema; `apps/engine_cli/tests/ops_tests.cpp`'s case "run_headless streams a partitioned document tile by tile round its observers" drives it end to end — a partitioned document of three places (one in the origin's tile, one in the tile east of it, one two kilometres away) under rings of 1.5 and 3 tiles: the four inner tiles materialized and reconciled on the first call with one entity made, the observer moved two kilometres by the next call so the origin's tiles are let go and written and the far place's come in, then walking back at 600 m/s with the budget spreading the tiles over the ticks and the origin's tiles reconciled from what the store kept of them; and rings that do not grow outward refused with a sentence.

**Continuing, and the player (`HeadlessWorld` version 2).** A call that **declares observers** puts them where it says and fills the ring round them with no budget, as before — the first call, or a jump. A call that **declares none** — or names no `stream` at all, on a world that is already streamed — **continues**: the observers go on from where they are and nothing is filled, so the call's `updates` is its ticks, and a run split over calls, or over a save and a load, is the run that never stopped ([world](world.md#save-and-load)). Before version 2 a call on a streamed world with no `stream` materialized the whole document beside the ring, and one with an empty `observers` list emptied the ring; neither was relied on. `player` (a `HeadlessPlayer`, `@since(2)`) makes one of the observers the player: `log` is an input log as `input::InputLog` writes it, its ticks the world's, `map` the action map it was recorded against as JSON (a map whose hash is not the log's is 1004 naming both), `action` an `Axis2` of the map (default `move`), `speed` metres per game second at full deflection, `observer` which one it steers. Each tick the observer moves at the action's value times the speed — x along world x, y forward along −z — instead of at its velocity ([world](world.md#the-player)). The input state is the fold of the log up to the world's tick, so a log handed to a world at tick K catches up first; named again on a later call, a log replaces the one the world has, and not named, the world keeps its own.

### `session.save_game`, `session.load_game`, `session.state_hash`

[03 §3.5](../plan/03-data-model.md#35-persistent-world-state)'s save game and [05 §5.10](../plan/05-simulation.md#510-determinism-and-replay)'s replay assertion, as three methods of the world capability ([world](world.md#save-and-load), [ADR-0042](../adr/0042-a-save-is-the-store-the-document-and-the-drivers.md)); a host without it answers each 1006 naming `ENGINE_WITH_WORLD`.

**`session.state_hash`** (`StateHashParams` → `StateHashResult`) is the persistent-state hash of the session's world ([world](world.md#the-persistent-state-hash)): the clock, the document's live records composed across its layers, and the store's events, projections and snapshots in key order, as 16 hex digits, with each part and its count beside it so a mismatch says where it is; `store` is `"read"` or `"absent"`. A session whose world has not run hashes at tick 0.

**`session.save_game`** (`SaveGameParams` → `SaveGameResult`) writes the session's running world into `path` — a new or empty directory, outside the document's — as a save: the document's directory copied, the store backed up (`VACUUM INTO`, [store](store.md)), the player's input log up to the tick and its map, and a `save.json` manifest naming and hashing every file. The result is the path, the tick and game time, the state hash, whether the world was streamed with its tile and observer counts and whether it has a player, and every file with its size and hash. Between two calls nothing is pending — every `session.run_headless` ends with its write-back flushed — so a save changes nothing in the session.

**`session.load_game`** (`LoadGameParams` → `LoadGameResult`) opens a new session on a save: `path` is the save's directory, `dir` a new or empty one the document and the store are copied into, so the save itself is never written. It refuses, before it copies anything, a save that is not one, one written at a version newer than this build's or in a format this build lacks, and one whose files are not the sizes and hashes its manifest gives, naming the file — 1002. A save written at an older version migrates, and `migrations` lists each step. Then it makes the world at the save's tick and game time, restores its tiles, observers and player, and hashes it: `saved_state_hash` is what the save recorded and `state_hash` the loaded world's, and a load that migrated nothing and does not reproduce it is refused and its session closed. The next `session.run_headless` on the new session continues the run: declare no observers, and hand the player's log over again.

**The three are one of each class** of [what a read may do](#what-a-read-may-do): the hash reads; a save is a read that leaves a file, a new directory from what the session holds, refused to a credential that may only read; a load is a write, since it makes a running world in a new directory (and refuses a directory with anything in it), so a role names it. The E2E cases are `apps/engine_cli/tests/save_tests.cpp`: a streamed world with a scripted observer, a player and carts driving across tile edges run 300 ticks, saved, run on to 600; the save loaded in a fresh host, saved again to the same bytes, and run on to 600 with the log handed over; and the starting document run to 600 in one call — one state hash, `c2168e9307bca23b`, on MSVC, Clang and GCC; then a whole-document world saved and loaded into a second session in the same host and the two run on alike, and the refusals — a save inside the document, into a directory that is not empty, a file changed since, a load into a document, an unknown session.

### `session.materialize`

`session.materialize` (`MaterializeParams` → `MaterializeResult`) is the same pass on its own, with the report in full: materialize the session's document — `scope` `"whole"` (the default), `"tile"` with `tile_x`/`tile_y` (the records of that tile of the partitioned layers that define them), or `"untiled"` — into the session's runtime world now, and return what happened. The world is the one `run_headless` steps, so a report after a run is an incremental pass.

`MaterializeResult` says whether the pass was full or followed the change feed, the document revision the world now reflects, and the counts — `visited`, `created`, `updated`, `unchanged` (looked at and already in sync), `dematerialized`, `relinked` (held records materialized again because their parent now has an entity), `skipped`, `live`, `orphans` (held records whose parent has none) — and the wall time and tier. Then **which types mapped and which records were skipped and why**: `types`, one `MaterializeTypeReport` per record type the pass met, with `mapped`, `records`, `materialized`, `skipped` and, when it skipped any, the first `reason` — `no mapping` (document-only by design), `unknown type` (not in this build's registry), `tier`, `missing component` (with the component in `detail`), `no entity store`, `no hook` — and `skips`, the first 64 skipped records by id. And `mappings`: every mapping this build compiled, whether or not the document uses it — the record type, its components, each field row with its conversion and write-back flag, the parent rule and the tiers — so a client learns what a record type becomes before it authors one. A `scope` that is not one of the three is 1004.

### `engine.run_tests`

`engine.run_tests` runs the engine's own checks that are safe inside a host and returns one report: each `TestCheck` has a `suite`, a stable `id`, a `subject`, a `severity` (error, warning, info), a `verdict` (pass, fail, skipped, info), a `message`, pathed `diagnostics` and a `value`, and the result counts them, with `ok` true when no error-severity check failed. **It never spawns a process** — ctest, the test executables and the benches are a CI job, which is where their machine state and their GPU lock are handled — **and never opens a socket.** Each input is optional:

- `session`: `doc.schema` is `doc.validate` itself, called through the dispatcher so the check follows the method, with its `<layer>/<id>/<property>` diagnostics; `doc.index` is `Document::validate_index()`, the composed index against a linear recomputation of the layers.
- `tissue`: a `.tissue` container or an interchange `.json`, read (`tissue.read`), then every row of the tissue validators ([tissue](tissue.md)) as a check under the row's own id, subject, severity and verdict, the threshold and witness in the message and the measured value in `value`; `tissue_modes` is `--no-modes` inverted. 1006 without the tissue capability.

### `profile.*`: the frame capture over the protocol

[06 §6.6](../plan/06-agent-tooling.md#66-introspection)'s `profile` (roadmap A10): engine-host registers `profile.start`, `profile.report` and `profile.stop` (`apps/engine_host/profile_methods.cpp`), over [core/profiling](profiling.md#the-frame-capture)'s frame capture and [profiler](profiler.md)'s frame report. A client starts the capture, has the host draw — `render.capture`, `render.benchmark`, a camera path — and stops it; the frames mark themselves and record their GPU timer zones and CPU spans (`systems/renderer`, [renderer](renderer.md#the-frame-capture)), and every zone of every thread of the host records itself (the dispatch of each request is `rpc.dispatch`).

| Method | Params → result (each at version 1) |
|---|---|
| `profile.start` | `ProfileStartParams` (`capacity`, events; 0 the default 262,144, at most 4,194,304) → `ProfileStartResult` (`capacity`, and `capture`, the capture's number) |
| `profile.report` | `ProfileReportParams` (`window_frames`, `max_series` 1 to 64, default 16, `out_dir`, `name`, `capture`) → `ProfileReport` (`capture`, `ProfileSeries` for the frame, and lists `gpu`, `cpu`, `zones`) |
| `profile.stop` | the same → the same, after the stop |

- **The capture is the process's**: one at a time (a second `profile.start` is refused with 1004), the same for every client and scene of the host. `profile.report` reads the running capture (`running` true; what is still being written is left out) or the last one stopped, as often as asked and over any window; `profile.stop` with nothing running is refused, and a `profile.stop` whose parameters are refused leaves the capture running.
- **Two clients and one capture.** The buffer holds one capture — up to 4,194,304 events of 48 bytes, about 200 MiB, which is why a second is refused rather than allocated beside it — and `profile.start` clears it. So a second client cannot start while the first's runs, but it can `profile.stop` the first's and start its own, and then the first's events are gone. Each start is numbered (`capture`, from 1 in each host process) and every report says which it read; a `profile.report` or `profile.stop` that passes the number its start returned and finds another capture there is refused with 1003, "capture 1 was replaced by capture 2 (another profile.start): its events are gone", and changes nothing — the second client's capture keeps running. A call with `capture` 0 reads whichever is there, which is the one way to be handed another client's report, and the report's `capture` says when it happened. A capture stopped by someone else is still readable by its number (`running` false); only its `profile.stop` is refused, as nothing is running. Zones are kept by the same rule below the protocol ([profiling](profiling.md#the-frame-capture)): a zone that began under one capture and ends under another is dropped, never counted in the second. engine-cli starts a host per call, so a capture across engine-cli calls is not possible; this is for `engine-host --listen` and `engine-mcp`'s clients.
- **The trace is written as `render.capture` writes its files**: the directory made and the path joined through `foundation/io`, and a failure the protocol's 1005 naming the path and the status.
- **Bounded**: each list is cut to `max_series`, largest total first, and `series_dropped` counts the rest, so a result is at most three lists of 64 series — under 40 KB — however long the capture ran. `dropped_events` says how many events a full buffer refused.
- **A capture that filled says so.** `truncated` is true when the buffer filled, and `truncated_ms` says when, from the capture's start. The report then ends there: the frame in progress is left out with its zones and values (`truncated_in_frame`, its index `truncated_frame`), and so is each value track's last measured frame, so every median and tail is over whole frames ([profiler](profiler.md#the-frame-report), "A capture that filled"). Before 2026-11-18 such a frame was stretched to the stop. engine-mcp's summary says it in a sentence: when the buffer filled, during which frame, that the numbers cover the frames before it, and to start again with a larger capacity. `invalid_values` counts values left out because they were not a time.
- **The capacity a start reports is the buffer's own** (`profiling::capture_capacity()`), and the buffer is exactly what the start asked for: a smaller capture after a larger one gets a smaller buffer, gives the larger back, and drops where its `capacity` says (found by batch 68's review of the capture, mended in batch 69; [profiling](profiling.md#the-frame-capture)). A stopped capture keeps its buffer until the next `profile.start`, since `profile.report` still reads it; a client done with a 4,194,304-event capture (about 200 MiB, which every role may ask for) gives the memory back by starting and stopping a small one.
- **The trace**: with `out_dir`, `<out_dir>/<name>.trace.json` (Chrome's JSON Object Format, which Perfetto opens; [profiler](profiler.md#the-trace)) and its path as `trace`, `<root>://<relative>`. `out_dir` is a client path, made only under a writable root, and `name` one plain file name ([the host's file roots](#the-hosts-file-roots)).
- **Read-only.** A capture changes no document, lease or host setting — it records what the host does while it is on, as `render.capture` records a frame — so every role may profile.
- **Which frames.** A frame is the renderer's, from the start of `begin_frame` (its wait for the slot) to the end of its submission; each carries a number no other renderer of the process uses, so two scenes' frames in one capture stay apart. A host's turn between frames (engine-view's update, engine-host's request handling) is not inside a frame. GPU times come back `frames_in_flight` frames later and are counted against the frame that drew them; `gpu_frames` says for how many frames of the window they did.
- **What is not there yet**: GPU counters, memory by tag and a Tracy capture beside the trace (§6.6 lists all three; roadmap T45), and engine-editor's and engine-view's own loops, which do not register these methods.

**Testing.** `apps/engine_cli/tests/profile_tests.cpp` (no device): the refusals before a capture, a capacity past the bound, a second start; a running report holding `rpc.dispatch` outside every frame, bounded by `max_series`; three refused stops that leave it running; a stop that writes the trace into the test's scratch directory, read back through `core/json`; the stopped capture read again, and a second stop refused; then a second capture replacing the first, a report and a stop naming the first refused with 1003 and the replacement's number, a number never started refused, and the second stopped by its own. `render_tests.cpp`'s "render: profile.* reports a benchmark's frames, GPU passes and CPU spans" draws a 12-frame benchmark under a capture and checks the frames, the GPU frames, a positive GPU median and `renderer.record` among the CPU spans; on a device with no GPU timer it says so and stops (one with no timestamps cannot make a renderer, so the benchmark is refused), and on one whose frames come back untimed it checks the frames and CPU spans and that there is no GPU series.
## Transactions a client opens

[Plan 06 §6.4](../plan/06-agent-tooling.md#64-transactions-checkpoints-rollback)'s `begin_transaction → commands → validate → commit | rollback`, for work an agent cannot say in one `doc.apply`: it reads, decides, edits, reads what it edited and edits again, and wants the whole of it to land as one change or not at all (2026-11-17, roadmap A11).

| Method | Params → result | What |
|---|---|---|
| `doc.begin` | `BeginParams` → `TransactionInfo` | open one on a layer (empty: the session's edit layer), with the opener's attribution and an idle `ttl_seconds` (default 3600, 1 s to 24 h) |
| `doc.apply` with `transaction` | `ApplyParams` (version 3) → `ApplyResult` (version 2: `transaction`, `staged`) | check the commands and stage them; nothing is committed |
| `doc.commit` | `TransactionParams` → `ApplyResult` | apply every staged command as one checked transaction: one journal patch, or nothing |
| `doc.rollback` | `TransactionParams` → `TransactionInfo` | drop it and what it staged |
| `doc.transactions` | `TransactionsParams` → `TransactionsResult` | the open ones, by actor or all; read-only |

**A transaction is staged commands kept beside the document, not a document transaction held open across calls.** `transactions.json` (schema `TransactionsFile`) holds each open one with its commands, written before the answer like `leases.json`, for the same reason: engine-cli starts a host per call and engine-mcp replaces one that misses a deadline, so a transaction living in a host's memory would vanish between the calls it exists to join. Holding a `doc::Transaction` open instead would also put a client's uncommitted records in the document every other client reads; staged, they are invisible to everyone, the caller included, until the commit (`doc.get` of a staged creation is 1003). That is read-committed isolation and no more: a client sees others' commits as they land.

**Every staging call is checked as a write is, then taken back.** The transaction's earlier commands are applied again, then the call's, in one `doc::Transaction` through the session's `commit_commands` with the caller, so the call's commands are judged against the document as the transaction would leave it (a `SetProperty` on an object the transaction created applies), and the role, a proposal's owner and state, and the leases are asked exactly as for a `doc.apply` — a refusal is the same RPC error (1008, 1009, 1010) at the call that caused it, not at the commit. Then it is rolled back and no record changes — but the pass is not invisible to the document's bookkeeping: the rollback applies each inverse through `Document::apply`, so every record a staging call touches is stamped in the change feed twice (a feed reader such as `sim::Materializer` sees it as changed and finds it as it was) and marked for the next save (which writes the same bytes), and a staging call into a transaction of more than about two thousand commands trims the feed past its bound and sends its readers to a full resynchronisation. It stays so because the alternative is a second way to apply commands — against a copy of the touched records, or with the feed and the change sets saved and put back around the pass — beside the one every write is checked by, and the cost is bounded by the transaction's own bound below; `doc.rollback_to`'s check-only pass behaves the same. `atomic` (the default) stages all of a call's commands or none; with `atomic: false` it stages the ones that applied; a call that stages nothing reports its diagnostics with `applied: 0`. **The commit asks everything again**, because the document and the leases may have moved since: it is one `doc.apply` of the staged commands with the opener's attribution (a `rationale` given at commit replaces the one given at begin; an explicit timestamp is the patch's), so its patch is byte for byte the patch one `doc.apply` of the same commands journals but for `transaction` (`Patch` version 2), which names the transaction it is the commit of and is 0 on every other write, and one undo takes it all back. **A commit lands once**: the patch is journaled and the document saved before the entry leaves `transactions.json`, so a failure after the journal — the table's write refused because a scanner holds the file past the rename's retries, a host killed there, or the document's save itself — used to answer an error for a commit that had landed and leave it open, and a retry applied its commands again (batch 68's review). **Landed means in the document as saved**: the patch naming the transaction stands before the undo position, and no save has failed since the host last wrote the document whole. A `doc.commit` naming a landed transaction is answered with that patch (`committed: true`, its `patch_index`, a diagnostic saying nothing was applied again), after the files are saved when this host's own save of it was what failed; every read of the table drops the entries that landed; and `doc.rollback` of one is 1003 naming the patch. **A patch in the redo tail has not landed**, whatever the journal says: a save that fails after the journal's write leaves the files at the undo position they were saved at, so the next host reads the commit as the tail's first patch and the document without its work. Its entry stays listed, and the retry commits the staged commands afresh — the commit cuts the tail, so the old patch goes with it and nothing is applied twice — where the first form of this rule dropped the entry on the next host's first read of the table, answered the retry `committed: true` for work the document did not hold, and let the next commit by anyone cut it off for good (the first review of the joined protocol work). A transaction that landed and was then undone is answered 1003 saying so, with `doc.redo` the way back, never `committed: true`; the journal does not record who undid it. The answer is the opener actor's (another is 1008). In the host whose save failed, the entry stays too, and staging into it or rolling it back is 1004 until a `doc.commit` saves it. A commit that cannot land — a staged command no longer applies because another client committed under it (`committed: false` with the diagnostics), or a role or lease now refuses it (the RPC error) — lands nothing and **leaves the transaction open**, so the agent can renew a lease and commit again, or roll back; a database would abort it, and a model that lost twenty staged edits to an expired lease would have to rebuild them from memory, which is the opposite of plan 06 §6.8's "agents resume from the ledger and the document". A commit with nothing staged closes it and journals nothing.

**A transaction is its opener's and one layer's.** Only the actor that opened it stages, commits or rolls it back (1008, reason `transaction owner`), and while the socket connection it was begun on lasts, only that connection ([several clients](#several-clients-one-host)); a staging call naming another `layer` is 1004, since a transaction is one patch and a patch is one layer's; `doc.begin` makes the layer checks at once (a proposal of someone else's, a closed one, a role that needs review on a feature layer), so an agent is refused before it does the work. **An idle transaction lapses**: each call that stages moves its expiry to then plus `ttl_seconds`, by the host's wall clock as leases are, and a lapsed one is rolled back — dropped by the next call that reads the table, and a call naming it is 1003 saying it lapsed and nothing landed. Ids are drawn at random, never one an open transaction or a journal patch names ([two hosts](#two-hosts-one-side-file)). The connection's hold is the host's and lives in its memory (`SessionManager::parked_` above keeps it across a close): another host process sees only the opener actor, as it sees only the actor of a lease taken on stdio. Leases are not tied to a transaction, as they are not tied to a proposal: an agent that needs its tiles to stay its own until the commit holds the lease until then.

`doc.begin`, `doc.commit` and `doc.rollback` are writes for the dispatcher's gate (a role must name them; `content/roles/roles.json` gives them to the designer and environment roles beside `doc.apply`); `doc.transactions` is a read. What it costs: a staging call applies and rolls back everything staged so far, and rewrites `transactions.json`, so a transaction of *n* calls costs O(*n*²) command applications in all — nothing at an agent's tens of edits, and the reason to commit a large batch as one `doc.apply` rather than as a thousand staged calls. **It is bounded**: a transaction holds at most 10,000 commands (`Session::k_max_staged_commands`) and an actor has at most 64 open at once (`k_max_open_transactions`), and a call past either is 1004 and changes nothing, so one role allowed `doc.begin` cannot make every later call on the document parse an unbounded table under the host's lock. This is a transaction's rollback, not plan 06 §6.4's `rollback_to(checkpoint)`, which restores the document to a checkpoint (roadmap D13).

**Tested** in `tests/policy_tests.cpp` (several calls land as one patch identical to one `doc.apply`'s but for its `transaction`, a commit again is answered with that patch and applies nothing, and one undo takes it back; a commit whose table write failed retried in the same host and, for a second one, in the next, each landing once; the two bounds; two hosts and eight writers at once ([two hosts](#two-hosts-one-side-file)); rollback, a lapse judged a day ahead of the host's clock, a commit under which another client deleted a staged command's object, the opener-only rule, the one-layer rule, and a transaction committed by a second session manager; the dispatcher's gate, the fail-fast refusals at `doc.begin`, a transaction in a proposal promoted afterwards, and a lease released between staging and commit refusing the commit and leaving it open), in `apps/engine_cli/tests/policy_tests.cpp` through the executables (staged by three engine-cli processes and committed by a fourth, whose second commit is answered with the patch that landed; staged into by eight at once; the refusals over one `engine-host --stdio`), and in `apps/mcp_bridge/tests/mcp_tests.cpp` (the four tools and a staged `create_object`).

## Placing an asset, instantiating a template

[Plan 06 §6.9](../plan/06-agent-tooling.md#69-day-one-operations)'s `place_asset` and `instantiate_template` (2026-11-17, roadmap A12): two compound edits an agent would otherwise spell as a batch of `CreateObject` commands with ids, paths and transforms worked out by hand (`domain/protocol/src/placement.cpp`). **Each compiles to commands and goes through the session's checked write** — one `doc.apply`, or with `transaction` one staging call into an open transaction ([above](#transactions-a-client-opens)) — so roles, proposals, leases, the journal, undo and the dispatcher's gate treat it exactly as the commands it is: one undo takes a placement or a copy back whole. Both are writes. Both answer `PlaceResult`: the `ids` made, in the order asked, and the `apply` result (an `ApplyResult`); `place_asset` adds the asset's `kind` and `bytes`.

**`doc.place_asset`** (`PlaceAssetParams`: `asset`, `placements: AssetPlacement[]`, `seed`, `layer`, `transaction`, `attribution`) makes one `engine.scene.MeshPlacement` per placement — the record type [doc_scene](doc_scene.md#the-record-type) draws and engine-editor's viewport shows — with `mesh` the asset exactly as given and the placement's name, parent, translation, rotation, yaw and scale. **The asset is checked before anything is written**: it must be a `.gltf`, `.glb` or `.clusters` (1004 otherwise), exist under the document's directory (1003), and read as its kind — a GLB's and a cluster container's four magic bytes, read with `io::read_file_range` so a 300 MB container costs four bytes, and a `.gltf` parsed as JSON naming `asset.version` (1004 when it does not). That is the check a record is worth refusing over; whether the mesh imports (its buffers, its triangles) is the importer's and the content build's question. **Where it may read** (2026-11-18): only under the document's directory, the one root a scene's mesh paths resolve against ([doc_scene](doc_scene.md), its `resolve_path`), so the path must be relative — no leading `/` or `\`, no drive (`C:`), no `:` anywhere (an NTFS stream), no `..` component, no empty name, no control character — and is joined to the session's directory as the scene joins it. A host serves clients of several roles, and an absolute path or one that climbs out would let any of them learn whether a file exists anywhere on the host's machine and, through the kind check, its first bytes. So a refused path and a path with no readable file under the document are one answer: 1003 with one sentence that names neither the path nor the directory. A symbolic link or junction inside the document's directory is followed, as the scene follows it: whoever can make one there already has the disk. A scene record written by other means may still name an absolute mesh, which the viewport draws; only this method's reading is confined. An id left null is generated from the seed, a hash of the asset path and the placement's index, so the same call places the same ids in any document and the same seed with another asset places others; a generated id that exists already is the transaction's diagnostic, and another seed is the answer. A placement is untiled unless its layer is partitioned on `translation` (the type has no `position`): a role restricted to tiles needs `untiled`, and a lease needs the type.

**`doc.instantiate_template`** (`InstantiateTemplateParams`: `root`, `parent`, `id`, `seed`, `offset`, `max_records`, `record_origin`, `layer`, `transaction`, `attribution`) is plan 03 §3.2's *instantiate-and-record-origin*, chosen over live composition there because a live template makes "what does this edit change" non-local. **Any live object is a template**: the copy is it and every live descendant, composed across the layers, depth first with children by id — an order that is the document's alone — and refused (1004) past `max_records` (default 10,000), naming the count. Each copy is a `CreateObject` of the source's type and composed properties, its parent the copy of the source's parent (the root's is `parent`), its id `id` for the root (or generated from the root and the seed) and for the rest a hash of the copy's root and the source, so a copy's ids are a function of what the call names. **`offset` (`dvec3`) is added to every property whose field is a `worldpos`** in the source's registered type — the engine's word for "where something is" (ADR-0053) — and nothing else moves: a `vec3` that happens to be called position is not a world position, and turning a copy is not built. With `record_origin` (the default) the copy's root gets a child **`engine.protocol.TemplateOrigin`** record: the template's root, each source in copy order beside its copy, and the root's `position` when it has one, so the origin stands in the copy's tile and a tile lease or role covering the copy covers its record too. A `TemplateOrigin` under a template is not copied: it is the template's history, not its content. The copy is not live — editing the template later changes no copy — and the origin is what a tool that wants to carry a template's change to its copies reads.

**General purpose**: neither knows any type but the two it writes. An imported glTF placed by `place_asset` is drawn as every placement is; a hand-authored subtree of any record types instantiates the same way, and a type with no `worldpos` field is copied where it was. **Tested** in `tests/policy_tests.cpp` (a GLB placed twice as one patch that validates, the same ids from the same call in another document and others from another seed, a `.gltf` staged into a transaction and landing at its commit, and the refusals — a kind that is not a mesh, a missing file, a file that does not read as its kind, nothing to place, QA at the gate; a real GLB beside the document refused under nine names — absolute, `..` in three spellings, a leading slash, a UNC share, a drive, a stream, an empty name — each with the missing file's code and sentence, while a subdirectory's file reads under either separator; a four-node yard copied with its offset, parents and order, the template untouched, the origin's fields and place, a copy of the copy leaving the first origin behind, one undo, an unknown root, `max_records`, and a copy staged and committed) and in `apps/engine_cli/tests/policy_tests.cpp` over one `engine-host --stdio` (a placement, its copy, and the refusals).

## Describing an object, a tile or a region

[Plan 06 §6.6](../plan/06-agent-tooling.md#66-introspection)'s `describe(object | tile | region, detail)` (2026-11-18, roadmap A13; `domain/protocol/src/describe.cpp`): what an agent needs to see of a part of the document before it edits it, in a size it can read. **`doc.describe`** (`DescribeParams` → `DescribeResult`) takes exactly one of `id`, `tile` (a `DescribeTile`) and `region` (a `TileRange`, inclusive, at most 65,536 tiles), a `detail` (`DescribeDetail`: `Summary`, `Standard` — the default — or `Full`), `max_records` (1 to 10,000, default 256) and `max_bytes` (1 KiB to 4 MiB, default 64 KiB); anything else is 1004, an object that is not live 1003. It is **read-only**: it changes nothing, so no role restricts it.

**What is in scope.** An object's scope is it and its live children at `Summary` and `Standard`, and its whole live subtree at `Full`, depth first with children by id (the order `instantiate_template` copies in). A tile's is the live records whose defining record is in that tile of its layer's grid, by id; a region's is its tiles' row by row (y, then x), by id within a tile. Everything is asked of the document — `exists`, `children`, `type_of`, `parent_of`, `property`, `object_tile`, `ids_in_tile` — never a walk of the layers. A region with more tiles than the document has occupied tiles is answered from the live set and sorted into the same order instead, so a large empty region costs the document's size and not its area; the two paths list the same records in the same order, and the test holds them to it.

**What it says.** `total` and `types` (counts by type, the most numerous first) cover the whole scope. `records` lists `DescribedRecord`s: id, type, parent, `name` (the record's `name` property when it is a string), `position` (the first `worldpos` field of the record's registered type that the record sets — the engine's word for where a thing is, ADR-0053, whatever the field is called; a `vec3` is not one), the tile it is filed in, its live child count, its depth below the object, and at `Full` its composed properties. `Summary` lists the object alone, or for a tile or region nothing. **`summary`** is one or two sentences built from templates over those counts — `engine.world.Node 'n' <id> at (5.00, 0.00, 5.00) in tile (0, 0), a root, with 2 live records as children: 2 engine.world.Node.`, `Tile (0, 0) holds 5 live records: 4 engine.world.Node and 1 engine.protocol.test.Prop.` — eight types at most and "and N more types" after, positions to the centimetre; no model writes it, so the same document gives the same words.

**The bounds.** Records are listed in scope order until the next would pass `max_records` or take the listed records' JSON past `max_bytes`; from then on every record is counted in `omitted`, `bound` names the bound, and the sentence ends `Listed L of N; M left out by <bound>.` The object asked about is always listed, whatever the bounds, since it is what was asked for. A `Full` subtree is walked to count it; a walk past 1,048,576 records stops there with `bound` `"walk"`, its counts a floor. What a call costs: the scope's records once each for the counts (a hash lookup for the type), and the listed ones again to build them — at most `max_records` resolutions and `max_bytes` of JSON, plus one serialization each to measure it.

**General purpose**: it knows no record type. An imported asset's placements, a hand-authored node tree or a type a game adds are described alike; a type with no `worldpos` field has no `position` and is still placed by its tile. **Not yet**: plan 06 §6.7's world mips (semantic, visual, design-density) and the edit cell's overlap ring; a description is of the document as it stands, at the three detail levels, and the context package that budgets tokens across mip levels is still to be built on it. A session's view policy (ADR-0033, roadmap A26) is not applied to what it lists, as it is not yet applied to `doc.get`. **Tested** in `tests/policy_tests.cpp` ("describe: an object at three details, its sentence, and the bounds"; "describe: a tile and a region from the tile index, in one order, under any role"), in `apps/engine_cli/tests/policy_tests.cpp` over one `engine-host --stdio` under the QA role ("host: doc.describe over --stdio"), and in `apps/mcp_bridge/tests/mcp_tests.cpp` (`describe_document`).

## Querying the document

[Plan 06 §6.6](../plan/06-agent-tooling.md#66-introspection)'s `query(sql | structured)` (2026-11-18, roadmap A14): the structured half over the document is `doc.query` (`domain/protocol/src/query.cpp`), the SQL half over the store `store.query` (below).

**`doc.query`** (`QueryParams` → `QueryResult`, read-only) returns the live records that pass a `filter`, in id order, a page at a time. **Where it looks** is narrowed through the document's indices before the filter runs — the children of `parent` (`children`), the records filed in the tiles of `region` (`ids_in_tile`, or the live set filtered by `object_tile` when the region has more tiles than the document has occupied ones, as `doc.describe` does; at most 65,536 tiles), or every live record (`objects`) — and never by a walk of the layers. **The filter** is `session.run_headless`'s `until` vocabulary over one record: `{"type": "<pattern>"}` (`*` any run of characters, the roles file's `glob_match`), `{"property": "<name>", <test>}` with `equals` (JSON, numbers by value), `at_least`, `at_most`, `prefix` or `exists`, a name ending in `[i]` taking one element of an array (`"position[0]"`), `{"parent": "<id>"}`, and `all`, `any`, `not`; a term with an unknown key, two tests, a test of the wrong kind, nesting past 32 or more than 1,024 terms is 1004 naming the path (`filter.all[0]: ...`). Each row is the id, type and parent and the composed `fields` asked for.

**A filter is input from outside, so it is data and never text**: it is compiled once into a tree of terms and walked per record; nothing a client writes is joined into a statement or evaluated as code. **What it can reach** is what `doc.get` and `doc.objects` return to the same caller — the composed live records of the session's document — and nothing else: no layer's own records, no journal, no file. **What it can cost** is bounded per page and the bound that ended it is in the result: `max_rows` (1 to 10,000, default 100) rows, `max_examined` (1 to 1,000,000, default 100,000) candidates the filter runs over, `max_ms` (1 to 10,000 ms, default 2,000; the clock read every 256 candidates) of examining, and `max_bytes` (1 KiB to 4 MiB, default 256 KiB) of rows as JSON. Memory is the candidate list (16 bytes a record in scope) plus the compiled filter (at most 1,024 terms) plus the rows. A page that stops at a bound has `complete: false`, `bound` naming it, and `next`, the last id it examined, which as the next call's `after` resumes exactly there: pages of three read the same rows as one call and none twice, and the test holds them to it. The narrowing is paid in full on every page (a `region` call sorts its candidates), which is why `max_examined` bounds the filter's work and not the narrowing's.

**Content classes ([ADR-0033](../adr/0033-content-classes-and-view-policies.md))**: a query is a read and is held to exactly what a read may see, not to more. Until a session carries a view policy (roadmap A26) no record is classified and nothing is withheld from `doc.get`, so nothing is withheld here. **When it does** (proposed): the policy filters the candidate list before the filter runs, and a property the policy withholds is absent to the terms, so a record a role may not read never matches and a filter on a withheld property cannot learn its value by matching on it (`{"property": "nudity", "equals": "full"}` matches nothing rather than telling an agent which records carry it); the counts in the result (`candidates`, `examined`) are of what the policy left, for the same reason.

**SQL over the store: `store.query`.** The store's `world.db` (`events`, `projections`, `snapshots`; [store](store.md)) is where 03 §3.5 wants SQL, and its half of `query` is `store.query` (`StoreQueryParams` → `StoreQueryResult`, registered `read_only`: it changes no document, lease or host setting), a method of the store capability in engine-host beside `session.events` (`apps/engine_host/store_query.cpp`), since this module may not link a capability; a host built without the store answers 1006 naming `ENGINE_WITH_STORE`. **It takes no path**: the store is the session's own `world.db`, and a document with none is 1003. What keeps a client's text its own statement is the store's (`store::run_sql_query`, [store](store.md#sql-a-client-wrote)), built as this page designed it with three changes the store page gives the reasons for: the prepare also refuses every virtual table (`SQLITE_PREPARE_NO_VTAB`), the connection carries SQLite's own hardening for untrusted SQL (defensive mode, the schema untrusted, triggers and views off, `query_only`, memory-mapped I/O off), and the temporary store is bounded by `max_ms` rather than by `OpenOptions`, because SQLite has no per-connection cap on it. The method parses `params` into bound values (null, a boolean as 1 or 0, an integer, a real, text, `{"blob": "<base64>"}`), checks the bounds (`max_rows` 1 to 10,000, default 1,000; `max_ms` 1 to 10,000, default 2,000; `max_bytes` 1 KiB to 4 MiB of values, default 256 KiB), and returns `columns`, `rows` as arrays of values (a blob as `{"blob": "<base64>"}`; text that is not well-formed UTF-8, which a statement can make with a bare `CAST(x'ff' AS TEXT)`, in the same blob form, since written as text it would be invalid JSON and, over the listener, an invalid text frame that ends the connection; an infinite real as `{"real": "inf"}` or `"-inf"`, and no NaN, which SQLite stores as NULL — `9e999 - 9e999` is null), `complete`, the `bound` that ended it, `bytes`, `elapsed_ms` and `instructions`; a refused or failing statement is 1004 with SQLite's reason. Nothing of a query outlives its call: the statement is finalized and the connection closed before it answers, so it keeps no cursor and a next page is the client's own `LIMIT`/`OFFSET` or keyset. **It never holds the world up**: the statement runs with the dispatch lock let go ([work outside the dispatch lock](#work-outside-the-dispatch-lock)), so for its `max_ms` the other clients are answered and the world ticks; under the lock, as first built, one client's query stopped both for as long, again and again. **What the view policy (roadmap A26) will have to cap**: payloads and projection blobs are opaque bytes the store does not type ([store](store.md), "Not yet"), so a classified one cannot be told from an unclassified one in SQL; under a policy below full the authorizer must deny the blob columns (`events.payload`, `projections.blob`, `snapshots.blob`) and every function that could read them, rather than return bytes it cannot judge, and the counts a query can compute over the rows are then of rows a policy may not let a role see, so a policy below full that withholds whole records refuses `store.query` until the store can tell them apart. **Tested** in `foundation/store/tests/sql_query_tests.cpp` (the refusals, the bounds, the settings and a world appending beside a query; [store](store.md#sql-a-client-wrote)) and over one `engine-host --stdio` in `apps/engine_cli/tests/ops_tests.cpp` ("store.query runs one SELECT over the document's world.db and refuses the rest"), and over the listener in `apps/engine_host/tests/transport_tests.cpp` ("store.query's text that is not UTF-8 comes back as bytes, the connection up": a lone `0xFF` and an overlong form in the blob form, well-formed text as text, and the next call on the connection answered).

**General purpose**: the filter knows no record type, and a game's types are queried as the engine's are. **Tested** in `tests/policy_tests.cpp` ("query: a structured filter over the document, in id order, a page at a time": every record, a type pattern, an array element's bound with fields, a nested any/all/not with a number compared by value, prefix and exists; a parent's children and two regions, one through the tile index and one through the live set; pages of three against one call; the examination and byte bounds with `next`; nine refusals; QA querying), in `apps/engine_cli/tests/policy_tests.cpp` over one `engine-host --stdio` under QA ("host: doc.query over --stdio") and in `apps/mcp_bridge/tests/mcp_tests.cpp` (`query`).

## Roles, leases and proposals

[Plan 06 §6.5](../plan/06-agent-tooling.md#65-permissions-concurrency-and-leases) in four bullets: roles are configuration; an agent leases (layer, tile set) or (layer, object-type set) before editing, and conflicts fail at acquisition; agents write to their own proposal layers, promoted into a target by structural merge after validation; read access is unrestricted. All of it is **this module's**, not engine-host's — `policy.h`, `leases.h`, `proposals.h`, `src/policy_methods.cpp` — because the writes it guards are this module's `doc.*` methods, and every dispatcher that serves them (engine-host, a future editor host, the tests) has to guard them alike. A host loads a roles file and says who it is; nothing else. [ADR-0039](../adr/0039-leases-and-proposals-beside-the-document.md) (proposed) records the four decisions below that would surprise someone; [E12](../experiments/e12-proposal-layers-and-leases.md) measured what leases buy.

### Identity, and what a role restricts

**A call's identity is its attribution**, except on a connection bound to a credential, which is the credential's ([who a connection is](#who-a-connection-is)): the `actor`, `role` and `task` of `attribution` in its params, with blank fields taken from the connection's `client.hello` and then the host's identity (`engine-host --actor`, `--role`, `--task`, `Policy::identity`). The methods that write records carry one — `doc.apply`, the new methods, and, since this change, `doc.undo`, `doc.redo` and `doc.merge` (`StepParams` and `MergeParams` version 2, `attribution: Attribution?` `@since(2)`; a merge given one journals it instead of the host's own). A method that carries none — `doc.add_layer`, `tunables.set`, `content.build`, `session.run_headless` — runs as the host's identity. **Roles are guardrails for cooperating agents, not security**: the protocol has no authentication, so a role is whatever a call says it is. What a role buys is that an agent told to be QA cannot change the terrain by mistake, and that the refusal says so in a structured error a model can act on. Where one agent owns one host — engine-mcp starts a host per agent ([apps](apps.md#roles-leases-and-proposals)) — the host is given that agent's identity, and the bridge refuses a call that names another role.

**The role a call runs in** is its attribution's role, else the host's `--role`, else the roles file's `default_role`; none at all means unrestricted, and so does a host with no roles file, which is every host before this change. A named role the file does not have is 1008 rather than no restriction, since a call that claims a role nobody configured must not fall through to none.

**Read access is never restricted, and a method is a write unless registered `read_only`** (`MethodDesc::read_only`, `read_only(method<...>(...))`, reported as `MethodInfo.read_only`, `@since(2)`). The default is a write on purpose: a method nobody classified is refused to a role that did not name it — loud — rather than open to every role — silent. Read-only means changing no document, no lease, no host setting, not the running world and not what is on a person's screen; a read that leaves a file the caller asked for is a read of its own kind, and [what a read may do](#what-a-read-may-do) sorts every registration into the three with its reason. `engine.methods` says which is which (`read_only`, and `leaves_files`, `@since(3)`). The dispatcher is the gate: it reads `params.attribution.role` from the raw JSON once, so no handler has to learn to, and refuses a write the role's `methods` patterns (`*` a wildcard) do not name — 1008 with `data.reason` `"method"`. **That holds for every client, the console included**: a call from an `engine-host --console` script ([apps](apps.md#the-console-luau-scripts-over-the-protocol)) is a request object handed to this same dispatcher, so `--roles`, the host's `--actor`/`--role`/`--task` and this rule apply to it as to a line on stdin — a `qa` script's `doc.apply` is refused with 1008 and reaches the script's `pcall` as `{code, message, data}`, and its reads are not restricted (`apps/engine_cli/tests/console_tests.cpp`).

**What a role restricts in a write** is checked by the session, per transaction, and a refusal rolls the whole transaction back — a write is the caller's to make or not, never half of one — and is an RPC error, not a diagnostic:

- `layers`: the layer whose content changes. For a proposal layer that is its **target**, so `"layers": ["world"]` means "may change world, directly or through a proposal".
- `tiles` (ranges; none is the whole partition) and `untiled`: where each touched object stands before and after the change.
- `object_types` (patterns): each touched object's type.
- `review_required`: it writes only to proposal layers it owns and may not promote (`doc.promote` answers 1008 with reason `"review required"`); plan 06 §6.10's director is a role without it.

`data.reason` is `method`, `layer`, `tile`, `untiled`, `type`, `review required`, `proposal owner`, `proposal closed`, `lease holder` or `unknown role`, with the role and what was refused (`layer`, `object`, `tile`, `type`, `method`). `content/roles/roles.json` is the five named roles, and `content/roles/README.md` says what each allows and why the default is read-only.

### What a read may do

A credential that may only read — one that names no role, or a role the host cannot enforce ([who a connection is](#who-a-connection-is), ADR-0069) — was still writing files through methods registered read-only: a capture's pictures, a profile's trace, a created document, a save, derived data, a document rewritten from a stale host's memory, a dialog on the person's screen. So every `read_only(` registration is sorted into one of three, and the sort is the rule a new method follows:

- **A read**: it changes nothing but this connection's own state. Open to every caller.
- **A read that leaves a file** the caller asked for: `read_leaving_files(method, when)` (`domain/protocol/rpc.h`), where `when` says from the call's params whether this call does (null: every call). The dispatcher refuses such a call to a connection that may only read — 1008, `data.reason` `"no role"` or `"unenforced role"`, before its handler runs, so nothing is made — because that state means nothing is written on its behalf; an enforced role keeps it as a read, confined by [the host's file roots](#the-hosts-file-roots). Unbound callers (stdio, the operator's token, the console) are the operator and are not touched.
- **A write** by AGENTS.md's rule: it changes a document, a lease, a host setting, the running world, or what is on a person's screen. Re-registered unmarked, so a role must name it; the shipped roles file's rows gained the ones an agent's role needs (`content/roles/README.md`).

**Housekeeping a call did not choose does not make a read leave a file**: dropping a lapsed lease, claim or transaction, a dead host's leases, or making a lock file beside a side file writes the bytes any caller's next call would write, and refusing it would buy nothing but a reader that cannot list. A read whose housekeeping does more than that is a fault in the housekeeping, not in the sort: the open's drop of every other host's socket leases (which a read-only `session.open` reaches) is mended where the leases are, not here.

### Where an object stands

Tiles and types are judged by the object's **composed** position and type (`place_of`): the strongest layer's `position` (or the partition's named property, or the type's `transform`), tiled by the **lease layer's** partition — a proposal's target, or the edited layer itself. Not by the edited record alone, which is what files are laid out by ([doc](doc.md)): an override that sets a colour and not a position still changes an object standing somewhere, and "a lease on tile (3, 7)" means the objects standing in it. Every object a write's commands name is placed **before its first change and after the transaction**, and both places are checked, so a move out of a lease or a role's tiles is caught by where it lands and a create-then-position in one transaction is judged by where it ends up. A record that is gone after the change (a delete in its defining layer) has no after; one that did not exist before has no before. An object with no position, or on a layer with no partition, has no tile: only an object-type lease covers it, and a role covers it only with `untiled`.

**The check allocates nothing per record**: a place is a hash lookup in the composed index, a visit to the layers holding the id, and a registry lookup for the type (whose name the registry owns), and a lease table is tens of entries walked in place. A write that no role restricts, into a document that does not require leases, records nothing at all — one branch per command.

### Leases

One table per document, **kept beside it as `leases.json`** (schema `LeaseFile`) and written before the answer, as the document's own files are: engine-cli starts a host per call, and engine-mcp replaces a host that misses a deadline, so a host's memory is exactly where a lease granted a moment ago would not be. Expiry is by the host's wall clock (`time::wall_unix_ms`), so it means the same to every process on the machine; an expired lease covers nothing and is dropped by the next acquisition, list or require. Every change is a read-modify-write under the file's lock and an id is drawn at random, so two hosts granting leases on one document lose none and give no two the same id; the document's own files written by two hosts at once are as unsupported as they always were ([two hosts](#two-hosts-one-side-file)). A lease taken over a socket connection also ends with the connection, and one a gone host's connection left in the file is dropped at the next open ([several clients](#several-clients-one-host)).

- **Acquisition** (`lease.acquire`) names tiles or object types, not both, on a layer that is not a proposal (1004 names the target to lease instead). It is refused with **1009 LeaseConflict** when another actor's live lease on the same layer has an intersecting tile range or a type in common, and `data.lease` is that lease: who holds it, for which task, until when. Overlapping one's own leases is allowed. A role may lease only a layer it may change, ranges inside one of its own, and types its patterns name. Type names are exact, because overlap has to be decidable from the names.
- **A tile lease and a type lease on one layer** can both cover a record (a light standing in a leased tile, under a lease on lights), and whether one does is not decidable from the two scopes. That overlap is refused **at the edit**: 1009 names the other holder.
- **Edits need leases only when the document says so** (`lease.require`, `LeaseFile.required`), off by default: every document and test written before leases edits as it did, and a single-agent document pays nothing. When it is on, every object a writing `doc.*` call touches — `apply`, `undo`, `redo`, `merge`'s output layer — must be covered, where it stood and where it stands, by a live lease of the caller's and by nobody else's: **1010 LeaseRequired** when none of the caller's covers it, 1009 when someone else's does.
- **A lease must be held until the proposal that carries its edits is promoted.** A lease released right after the edit protects nothing: the edit sits unmerged in the proposal, the next holder of the tile changes the record, and the promotion finds a conflict the lease existed to prevent. [E12](../experiments/e12-proposal-layers-and-leases.md)'s first run did exactly that and found a DeletedAndModified conflict with leases on. The protocol does not tie a lease to a proposal; the agent's protocol is acquire, read, edit, promote, release, and the MCP tools say so.
- **A promotion is not lease-checked.** It is the merge the leases existed to keep clean, and each record the proposal holds was checked when it was written. Nor is the runtime world's write-back (`Session::apply` without a caller, attributed to `system`): the simulation writing what it computed is not an agent editing.

### Proposal layers and promotion

`doc.propose_layer {name, target}` appends a layer of role `Proposal` over `target`, stored in the target's form (its partition), and records the caller as its owner: a **layer property** kept in `proposals.json` (schema `ProposalsFile`) and reported by `doc.layers` as `LayerInfo.proposal` (`@since(3)`) — target, owner, owner role, task, the rationale the proposal was opened with, state, when, and how many target records it has touched. It is the protocol's and not `domain/doc`'s: in memory, on disk and in the journal a proposal is an ordinary layer. **Only its owner writes it, and only while it is open** (1008 otherwise). Read access is unrestricted, so everyone reads it: proposals compose into the document like any layer, which is the "read-only context from neighbours" the plan asks for — and which also means a neighbour's in-progress deletion hides the object from everyone's strict `doc.apply` at once, so that collision surfaces at the edit rather than the merge.

**The merge base is per record, from the proposal's first touch.** The first commit that changes a record in a proposal appends the target's record as it stood then (or its absence) to `proposals/<layer>.base.jsonl` (one `ProposalBaseEntry` a line). `doc.promote` then merges three layers with `doc::merge_layers`: `base`, the target with each record the proposal holds put back as the proposal first found it; `theirs`, that base with the proposal's opinions composed on (`compose_onto`: properties and a parent overlay, a type defines, a tombstone drops a record the target defines and tombstones one it does not); and `ours`, the target now. This costs what the proposal touched rather than what the target holds, and a change promoted into the target *before* the proposal first touched a record is what the agent built on, so it is never reported against it — where a whole-target copy taken at `propose_layer` would call it a conflict. A record held with no recorded base (the proposal was written behind the protocol's back, or an undo refilled a closed one) merges against the target as it stands and can take the proposal's side but never conflict. ADR-0039 has the comparison.

**Validation runs on the merged world before anything is committed.** The accepted world is every layer that is not a proposal; `doc.promote` validates it as it is and with the target replaced by the merged layer, and what the second finds that the first did not is the promotion's to fix (`PromoteResult.validation`). Problems already there, or in other agents' proposals, do not block it — otherwise one agent's broken record would block every promotion. A promotion that leaves a child without its parent, overrides an object no accepted layer defines (an edit to a neighbour's unpromoted creation), or writes a property its type lacks is refused.

**It is refused, not an error, when anything stands in the way**: `promoted: false`, `ok: false`, `refused` a sentence, and every conflict and new validation problem. `prefer` (`PromotePrefer`) settles conflicts — `Refuse` (the default: a person or a director decides), `Target` (keep what the target has), `Proposal`, `Base` — and never validation. `dry_run` does everything but commit. **Committed, it is two journal patches**: the target's, attributed to the promoter with the proposal's owner, task and opening rationale in the rationale (plan 06 §6.8: an accepted proposal records why next to the change), and the proposal's emptying patch. The proposal layer **stays in the stack, empty and `Promoted`**, and its owner reopens it by name for the next piece of work — removing it would break undo for everyone, since every earlier patch names its layer and the journal is one line per document. `doc.undo {steps: 2}` takes a promotion back and leaves the proposal holding its records again; its state is not journaled, so it stays closed until its owner reopens it. `doc.reject` empties an open proposal without merging it (its owner may always; anyone else needs a role that may change the target). `PromoteResult` reports `merge_ms`, `validate_ms` and `commit_ms`, which E12 reads.

**A proposal's changes are pushed** (2026-11-18, roadmap A55): opening, reopening, promoting and rejecting one publish `event.session` (`SessionChangeEvent` version 4's changes `proposal_opened`, `proposal_reopened`, `proposal_promoted`, `proposal_rejected`, with the proposal's `layer`, the `actor` who did it and its `connection`) after `proposals.json` is written, so a queue of proposals waiting re-reads `doc.layers` on an event rather than on a timer. A dry run, and a promotion refused for its conflicts or its validation, change no proposal and publish nothing; the promotion's two patches are pushed as `journal` events as every commit's are. Its state is a field of the host's proposal table and not journaled, so another host's change to it is not pushed (a proposal is written by one host's clients at a time; two hosts on one document are unsupported for the document's own files). Tested in `tests/policy_tests.cpp` ("opening, promoting, reopening and rejecting are pushed as session events": the four in order with their layer and actor, a dry run between them publishing nothing).

### What a promotion is tied to

**"Take the proposal's" applies to the values the person saw** (roadmap A56, beside [What a close is tied to](#what-a-close-is-tied-to)). Between a dry run a person reads and the promotion they send with `prefer`, the proposal's owner — who alone writes it, and whose writes nothing else holds back — can add, change or remove an opinion, and another client can change the target's value at a conflict; either way the `prefer` would settle conflicts the person never saw. So every `doc.promote` answers `PromoteResult.digest` (version 2): a SHA-256 over the proposal and its target by name, every record the proposal layer holds as it holds it, in id order, and each conflict's object, property, kind and the target's value there. A promotion that carries its dry run's digest (`PromoteParams.digest`, version 2) is refused with 1004 (`proposal moved`, the digest now in `data.digest`) when the same merge now gives another, checked after the merge and before validation and commit, so a refused promotion changes nothing and publishes nothing; the page dry-runs again and draws what it shows. **What it leaves out**: the target's values where nothing conflicts, which the merge takes whatever they are and the person's choice does not touch, and the merge base, which only the proposal's own first touches write. An agent's promotion that sends no digest is checked as before: the guarantee is for a promoter who looked. **A promotion with `prefer: Base` takes no base value the digest does not cover**: the merge reads the base only for ids the proposal holds (`Session::promote` overlays `ProposalTable::base_of` on the target for those alone), whose records the digest covers, and an id's base is recorded once, at the proposal's first touch of it, and never rewritten while the proposal is open (`ProposalTable::note_base` keeps the first; only a reopen, a promotion or a rejection clears the bases, and each of those changes the proposal's state and empties or refills its layer, which moves the digest). A record dropped from the proposal and touched again keeps the base it had.

`tests/policy_tests.cpp` ("a promotion is refused when what its dry run showed has moved"): two dry runs of nothing moved give one digest; the owner's command added after the dry run refuses the promotion, and so does the owner's command undone after one (an opinion taken back); a fresh dry run, then the target's value at the conflict changed, refuses it with the target as it was and nothing journaled; the target brought to the proposal's value, so the conflict goes, refuses the dry run that showed it; and a dry run of what stands is taken with `prefer: Proposal`.

## Blobs and checkpoints

Roadmap D13 and D14: the document's store of content-addressed blobs and its checkpoints, over the store and repository `domain/doc` keeps ([doc](doc.md#blobs), [doc](doc.md#checkpoints)). `src/session_history.cpp` is the session's half, `src/history_methods.cpp` the wire; every params and result type is in `schemas/protocol.schema`, so engine-cli reaches them by name (`engine-cli --doc ./world doc.checkpoint '{"label":"before the river"}'`), and engine-mcp has a tool for each — `put_blob`, `read_blob` (the bytes as a file in the workspace, never inline), `collect_blobs`, `checkpoint`, `checkpoints`, `rollback_to` ([apps](apps.md#blobs-reach-an-agent-as-a-file); roadmap A49).

| Method | Params → result | What |
|---|---|---|
| `doc.put_blob` | `PutBlobParams` → `BlobResult` | bytes into the store from a file under the document's directory (`path`, relative to it) or inline (`data_base64`), never both; answers the `BlobRef` to set and whether it was new. A write: it changes no document, but a role must name it |
| `doc.blob` | `BlobParams` → `BlobResult` | read-only: the blob's path, its bytes checked against its name, and with `data` the bytes as base64; 1003 for a name the store lacks, 1004 for one that is not a name |
| `doc.collect_blobs` | `CollectBlobsParams` → `CollectBlobsResult` | removes what nothing can bring back: no layer, no journal patch (undo history and redo tail), no open proposal's merge base and no command staged in an open transaction names it (a lapsed transaction rolled back first), and it is older than `min_age_s` (an hour); `dry_run` |
| `doc.checkpoint` | `CheckpointParams` → `engine.doc.CheckpointInfo` | saves, then commits the document to `<dir>/.git`; 1006 with the reason when there is no git; 1004 for a `label` holding a control character or past 200 bytes ([doc](doc.md#checkpoints)) |
| `doc.checkpoints` | `CheckpointsParams` → `CheckpointsResult` | read-only: newest first, with who took each, why and the journal's positions; `available` and the git that answered |
| `doc.rollback_to` | `RollbackParams` → `RollbackResult` | the accepted layers made what the checkpoint held, as journaled patches; `dry_run` |

**A command naming a blob the store does not hold is refused** — a diagnostic naming the blob ("doc.put_blob it first"), and with `atomic` the whole transaction — in every client's `doc.apply` (`Session::commit_commands`, strict commands). Replays are not checked: an undo, a redo or a merge replays references the journal accepted, and nothing the journal can reach is ever collected. So the order is put, then apply; the grace period of a collection is what keeps a blob between the two, and a put of bytes the store already holds starts it again (`created: false` is still a put).

**A `path` is read only under the document's directory** (`read_under_document`, `src/document_path.h`). A host serves clients of several roles, and `doc.blob` with `data` is read-only and open to every role, so a `path` the host would read anywhere is a copy of any file the host can read, handed to any client (batch 68's review, B1). The rule is `doc.place_asset`'s (`stays_under_document`, one function with the same behaviour): relative, no drive, no stream (`:`), no `..` component, no empty name, no control character; and then, links followed, the file must still be under the directory, so a link inside it that points out is refused too. **A `\` is a separator on every platform**, in the rule and in the read (`document_relative_path` hands the file system the path with every `\` made `/`), because a client on any machine may send either and a document written on one platform is served on another: `props\crate.glb` reads the same file on Linux as on Windows, and `..\..\x` is refused on both rather than becoming one file name on Linux. **A refused path and an unreadable one answer the same code (1003) and the same sentence**, naming neither the path nor the directory, so a client learns nothing of the disk outside. *Why keep `path` at all*, when `data_base64` carries the same bytes: a large file a host-side tool wrote into the document's directory (a baked grid, a generated image of hundreds of megabytes) goes in without a base64 round trip through the client and the JSON line; the inline form is for what a client holds itself.

**What a rollback does** (`Session::rollback_to`). It reads the checkpoint's manifest and layers back from the repository and, for every layer of the stack, writes the difference between what the layer holds and what the checkpoint held as **one patch per layer it changes** — `doc::diff_layers`, applied as a merge's commands are, without the composed document's preconditions — through the same commit path as every write: journaled, saved, published as `journal` events, stamped in the change feed, and undone by `doc.undo` with `patches` steps. That is the decision under everything else: a rollback is a forward edit, never files put back, so the runtime world follows it through the change feed as it follows any edit (`changed_since` names exactly the records the rollback changed), the journal says who rolled back to what and why (the rationale begins "rollback to checkpoint <id> "<label>""), every open session sees it, and nothing in the history is lost — a rollback can itself be undone, and checkpoints after it stay reachable.

- **Layers.** A layer the checkpoint had is restored, its storage form put back too (`doc.set_partition`, outside the journal as that method always is); one it did not have is *emptied* and kept in the stack, as a promoted proposal is, because every earlier patch names its layer; one it had that the stack lost is appended on top, empty, outside the transactions (as a merge's new output layer is), then restored — the stack's order is not restored. The checkpoint's edit layer becomes the session's when the stack has it.
- **Open proposals are left as they are** (`action: "kept"`) — they are their owners' work in progress, not the accepted world, and the checkpoint's own proposal layers are not restored. Their merge bases are untouched, so a promotion afterwards sees the rollback as the target's change: where the proposal touched a record the rollback changed, the promotion reports the conflict and a person decides; nothing is overwritten silently.
- **Who may call it.** It is a write a role must name (only the director in `content/roles/roles.json`), and each layer's patch is checked exactly as a `doc.apply` into that layer is — the role's layers, tiles and types where every touched record stood and stands, `review_required` (such a role is refused: a rollback cannot go through a proposal), and, when the document requires leases, every touched record covered by the caller's lease and nobody else's. **The checks run for every layer before any layer changes** (`Session::check_commands`, a transaction rolled back), so a refusal — 1008, 1009 naming the other lease's holder, 1010 — leaves the document as it was. Leases are not released or changed by a rollback: they are time-bound claims, and a rollback over a tile someone else holds is refused like any edit there.
- **Blobs.** A blob the checkpoint's layers name that the store has collected since is written back from the checkpoint first (`blobs_restored`).
- **Whole or not at all.** After the checks pass, what can still refuse a layer is a save that fails (or the store refusing a blob back). Then everything the rollback changed is taken back before the refusal is answered: the layers that had landed are undone newest first, as `doc.undo` would undo them — so they stand in the redo tail, which the next commit drops, as a commit whose save died does — the storage forms are put back and the layers it appended are taken off again; the message ends "nothing of the rollback stands". Blobs written back stay (a collection decides). Only when that taking back fails too does part of the rollback stand, and then the error's `data` is the `RollbackResult` of exactly what stands — its `layers` with their `patch_index`, `patches` their count — and `doc.undo` with `patches` steps takes it back (a storage form changed stays changed; `doc.set_partition` puts it back). Batch 68's review (B10) found it stopping part-way and saying nothing; `history_tests.cpp` refuses the second layer through `Session::fail_rollback_for_test`, once with the taking back allowed and once with it refused.

**What a checkpoint does to leases and proposals: nothing.** It holds the document's own files and not `leases.json` or `proposals*`; it is a write a role must name because it is the history others roll back to.

`tests/history_tests.cpp` takes it through the dispatcher: a blob put inline and from a file, read back with its bytes, refused for a bad or unknown name, referenced from a property, and a two-command transaction refused whole for naming one the store lacks; the catalogue's read-only marks; a collection taking the unnamed blob, keeping one an undo's redo tail can bring back, and taking it once a new commit drops that tail; a checkpoint, a dry run that changes nothing, and a rollback over a moved, a deleted and a repainted record and a new layer with a record — the tiled layer's files byte for byte the checkpoint's, the new layer emptied and kept, the change feed naming the rolled-back records and not an untouched one, the journal's attribution, undone and redone; an unknown checkpoint; a collected blob restored by a rollback; QA refused both writes, a review-required role refused a rollback, another actor's lease refusing one with 1009 and nothing changed, a proposal kept; 1006 and `available: false` with `ENGINE_GIT` naming nothing; and a seeded run of 70 edits, undos, redos, checkpoints and rollbacks over a tiled and a plain layer in which every rollback leaves each layer equal to what that checkpoint held and the composed index valid.

## The task ledger and review items

[Plan 06 §6.8](../plan/06-agent-tooling.md#68-long-running-work)'s long-running work (2026-11-18, roadmap A23, [ADR-0072](../adr/0072-the-task-ledger-beside-the-document.md), proposed): **agents resume from the ledger and the document, never from conversation memory.** A **task** is a piece of work with a goal and acceptance criteria that a role claims, works and finishes; a **review item** is where a check goes that the one who found it may not or cannot make — the designed place for AGENTS.md's rule that a check needing a higher view policy becomes a human review item, never a configuration edit ([ADR-0033](../adr/0033-content-classes-and-view-policies.md)). `src/ledger.cpp` is the whole of it; every params and result type is in `schemas/protocol.schema`, so engine-cli reaches the methods by name as it reaches every other (`engine-cli --doc ./world task.list '{"statuses":["Open"]}'`). No MCP tool yet.

| Method | Params → result | What |
|---|---|---|
| `task.create` | `TaskCreateParams` → `TasksResult` | a title (1 to 200 bytes), a goal (4 KiB), up to 32 acceptance criteria, the `owner_role` that should do it (a role of the roles file, or empty for any) and its `links` |
| `task.claim` | `TaskClaimParams` → `TasksResult` | take an open task for `ttl_seconds` (1 s to 7 days, default an hour), or renew one's own claim; 1009 naming the claimant while another actor's claim stands, 1008 (`task role`) when the call's role is not the task's |
| `task.update` | `TaskUpdateParams` → `TasksResult` | the claimant's note, links and status (Blocked, Claimed again, Done, Dropped, or Open to let go), or the creator's Dropped, or Open on a Done or Dropped task (reopen); anyone else 1008 (`task owner`) |
| `task.list` | `TaskListParams` → `TasksResult` | read-only: one task, or every task by status, role, claimant and a list of ids, in a stated order and to a `limit`, with how many more matched ([the lists](#the-task-ledger-and-review-items), below); `brief` leaves the histories out |
| `review.raise` | `ReviewRaiseParams` → `ReviewsResult` | a `kind`, an `audience` (`Agent` or `Human`), a summary, the `subject` (a layer, live records, a checkpoint, blobs), the `report` (JSON numbers, at most 64 KiB), and the task it is for |
| `review.close` | `ReviewCloseParams` → `ReviewsResult` | Accepted, Rejected, or Withdrawn by its raiser; a `Human` item only under a role marked `human`, and never withdrawn (1008, `human review`); with the `revision` its closer saw, refused 1004 (`revision moved`) when the item has changed since, and with the subject `digest` it saw (version 3), refused 1004 (`subject moved`) when what the item is about has; a `Human` item's close carries both (1004, `seen required`); a refused close writes nothing and pushes nothing ([What a close is tied to](#what-a-close-is-tied-to)) |
| `review.list` | `ReviewListParams` → `ReviewsResult` | read-only: one item, or every item by state, audience, kind, task and a list of ids, ordered and limited as `task.list` is; with `digest` (version 3), one item's subject digest now and whether it is the stamp, with no ids, order or limit beside it ([What a close is tied to](#what-a-close-is-tied-to)) |

Each write answers the task or item it changed, as `tasks[0]` or `reviews[0]`, and pushes `event.session` (`SessionChangeEvent` version 3: `task_created`, `task_claimed`, `task_updated`, `review_raised`, `review_closed`, with `task` or `review` and the `actor`) to a subscriber, after the ledger is written ([Events](#events)). Like every event it carries ids, not content.

**The ledger's events** (2026-11-18, roadmap A55). Those five come from the host that made the change, and the ledger is a file other processes write too — engine-cli's host per call, a second host on the document — so a queue that waited for events alone would miss every item an engine-cli raised. **A change another process made is pushed as `ledger_changed`** (`SessionChangeEvent` version 4: `tasks` and `reviews`, the ids whose entries were made, changed or are gone, at most 1,024 of each with `tasks_total` and `reviews_total`, and `ledger_revision`), never the ledger itself; a reader reads the ids with `task.list {tasks}` and `review.list {reviews}`.

- **The hint is the system's directory-change notice, and only a hint.** Every session of a host that has someone to tell watches its document's directory for `ledger.json` with the platform's own notice (`DirWatch`, `dir_watch.h`: `ReadDirectoryChangesW` on Windows, inotify on Linux) on a thread that sleeps until the system speaks — no polling loop, and no timer that wakes when nothing happened. **A watch exists only while someone can be told**: a host that listens (engine-host `--listen`, the editor's in-process listener) and has started its looker. The watches start with the looker (`Listener::start`) and stop with it (`Listener::stop`), and `SessionManager::watches_ledgers` is the one place that says whether they run. So engine-cli's host per call, `engine-host --stdio` with no `--listen` and a console start no watch thread, make no read of the ledger at open and pay nothing more per write, although engine-host builds its listener in every mode (`ledger_tests.cpp`, "a host that tells nobody watches nothing": a listener never started, then started, then stopped). Where the system gives no notice, the watch looks once a second instead and logs that it does (`protocol.watch`).
- **The decision is the file's.** A look reads `ledger.json` under its lock between processes (for the read alone), and when its bytes are the ones the session last saw it is done: a read and a hash, no parse. Otherwise it parses and compares the ledger's **revision, size and content hash** (of the bytes this tree writes, so the same content in other spacing is no change) with what the session last saw, and **any of the three differing is a change — inequality, never "greater"**, because a ledger restored from an older copy has a revision that went back and is still a change. The ids are those whose entries' hashes differ. A notice for a write that changed nothing therefore publishes nothing (the side-file helper writes nothing when the bytes are unchanged, and a rewrite with the same bytes or the same content is a look that finds nothing); a notice the system says it dropped (an overflowed buffer, `IN_Q_OVERFLOW`) is a look like any other; and notices that were lost lose nothing, since the next look, or the next write this host makes, compares the whole file with what was seen.
- **This host's own writes are not told twice, and swallow nobody's.** A write reads the ledger afresh under its lock, so what it writes carries every other process's write since the session last saw the ledger. Before the call's own event goes out, what the written ledger differs by from what the session last saw — but **every entry the call itself changed**, which its one event stands for: the task of a create, a claim and an update, the item of a close, and both the item and its task of a raise for a task — is published as `ledger_changed`, which is exactly **another process's write, or a claim this host's clock let lapse** (nothing else tells a lapse); then the written ledger is what the session has seen, so the write's own notice publishes nothing more. A list that let claims lapse does the same with no task of its own. `ledger_tests.cpp`, "a write's own event is the one event it pushes, its task included" (a raise for a task and its close, each one event, and the other host's note on the task `ledger_changed`) and "a claim the host's clock let lapse is told as ledger_changed" (by a list, and beside an update's own `task_updated`). A read that writes nothing does none of this and costs what it always did.
- **A storm is one look.** The watch only wakes the listener's looker, which waits a quarter second (`Listener::k_ledger_look_ms`) for the rest of a burst and then looks once at every ledger a notice named, so another process's burst of writes costs this host at most four looks a second, however many writes it makes. **A look holds the host's lock only to decide and publish**: the session's last sight is copied out under it, the file is read, hashed and parsed with it let go, and it is taken back to compare and publish (a look that raced one of this host's own writes is put back for the next rather than taken over it). So a burst of another client's writes never makes this host's own readers wait for a parse of the ledger. What a look costs under the host's lock is a pass over the entries' hashes; outside it, a read and a hash of the file, and when the file changed a parse and a serialization of each entry — about what a call over the ledger costs, roughly a second at the 8 MiB bound in `msvc-debug` (estimated from the bounds' measurement above, not measured), four times a second at most. A write of this host's own on a watched session pays for one more serialization of the ledger and one of each entry (what it wrote, so the comparison has something to compare), roughly that write's cost again, only on a host with a listener; a read pays nothing.
- **A write that failed is not a write.** What a call wrote is recorded only once the file holds it (`update_side_file`'s `written`, set after the write succeeded), so a write refused at the rename past its retries or by a full disk pushes no event, then or at a later look, for an entry that exists nowhere (`ledger_tests.cpp`, "a write that failed is not a write": a write made to fail by `detail::fail_next_side_writes_for_test`, then the other host's next write named alone).
- **No write falls between a watch's start and what it has seen.** The order is fixed: the waker is set, then the system's watch is **registered** (`DirWatch::start` returns only once the first `ReadDirectoryChangesW` is in flight or `inotify_add_watch` has answered, or once it fell back to looking), and only then is the file read for what the session has seen. A write after that read raises a notice someone is told of, and one before it is in what was read. A notice that comes before the looker's first wait is kept (the looker's flag, then the session's), not lost. `ledger_tests.cpp`, "a write the moment a watch starts is announced" and "a listener's looker announces a write made as it starts", make the watch's thread 300 ms slow to register (`DirWatch::delay_registration_for_test`) and write the moment the start returns.
- **Tested** in `tests/ledger_tests.cpp`: two hosts on one directory, the looks made by hand so the case holds the decision to the bytes whatever the platform's notices do — a burst of three of the other host's tasks and one look, one event naming the three and the revision; a second look, a rewrite with the same bytes and one with the same content in other spacing, each publishing nothing; a fourth task, then the ledger restored to the copy before it, a change naming the task that is gone with the revision gone back; and the other host's write followed by this host's own before any look, the other's told first and this host's notice publishing nothing more. And over the platform's own notice: twenty tasks written by the other host wake the session's watch within ten seconds, by the system's notice and not the fallback on Windows and Linux, and the look after is one event naming the twenty. `apps/engine_host/tests/transport_tests.cpp`, "a review item another process raises is pushed as ledger_changed": two engine-host processes on one document, the second raising an item on its stdin, and a socket subscriber of the first pushed `ledger_changed` naming that item and revision 1, which it then reads by id. The listener's quarter-second looker is exercised there and nowhere in-process.

**How a caller was known is written beside everything it wrote.** A task's creator and claimant (`created_via`, `claimant_via`), an item's raiser and closer (`raised_via`, `closed_via`, and `closed_human_via`, the credential that made the closer a person) and every history line (`WorkNote.via`, `human_via`) carry `Caller::via`, set by `resolve_caller` alone: `credential:<name>` for a connection bound to a credential the operator issued, `operator` for a connection on the printed token or the shell's cookie, `stdio` for stdin, engine-cli and a console script, and `host` for the host's own change, a claim its clock let lapse. Everything but a credential's is the caller's own claim of its actor name, so a queue that draws the ledger (the editor's, A24) shows the two apart rather than trusting a name. `TaskInfo`, `ReviewInfo` and `WorkNote` are version 2 for it, additive.

**What a task is.** `TaskInfo`: an id drawn at random against the ledger's other tasks (53 bits, `fresh_side_file_id`, as a lease's and a transaction's are; a counter's next id, after a ledger is restored from a copy, would name a task someone already knew by that number as a different one) and its `key`, `task/<id>` — what a call's `attribution.task` names while it does this work, so that the journal's entries, the leases and the transactions made for a task are found from it and it from them; the title, goal and acceptance criteria; `owner_role`; `status` (`Open`, `Claimed`, `Blocked`, `Done`, `Dropped`); who made it, who holds it, in which role, since when and until when; `links` (`WorkLinks`: proposal layers, leases, transactions, checkpoints, records — names and ids, never a file path, since a ledger outlives the machine that wrote it); the review items raised for it; and a history (`WorkNote`: when, who, in which role, what changed, the note), the newest 256 lines kept and `history_dropped` counting the rest. **What an agent reads to pick up work another left** is `task.list` for its role and the open or lapsed tasks, then the task's history and links: the proposal holding the work so far, the checkpoint it last took, the transaction it was staging (a transaction outlives its host, [above](#transactions-a-client-opens)), and the notes, Blocked's among them, that say what stood in the way.

**Who may do what.** Making a task, claiming one and changing one are writes a role must name (`task.*` in the designer's and the environment's rows of `content/roles/roles.json`, everything for the director; QA, the default role, writes nothing); `task.list` is a read. A claim is the claimant actor's — not its connection's, unlike a lease: a task is long work across many hosts and reconnections, and a connection that drops says nothing about whether its agent is coming back. So **a claim lapses** instead: at `claim_expires_unix_ms`, by the host's wall clock as leases are, a Claimed or Blocked task is Open again, its history saying whose claim lapsed, and the next call to read or write the ledger records it (`lapsed` in the result). Every `task.update` by the claimant renews the claim by the time to live it was taken with, so an agent that is working keeps it without asking. Done keeps the claimant as who did it. Only the claimant finishes; the creator may drop a task anyone holds (it was the creator's to ask for) and reopen one that is Done or Dropped, which is how a person sends finished work back.

**What a review item is.** `ReviewInfo`: an id drawn as a task's is, a `revision` that is 1 when it is raised and moves on every change to it (the history's length stops moving at its cap, so it cannot stand for what a caller saw; `review.close` given the revision its closer read is refused 1004, `revision moved`, with the item's revision in `data`, when it has moved), a `kind` — data, not code: `classified content review` is plan 06 §6.10's, `validation` or `promotion` or a game's own are as good — the `audience`, a summary of what is to be decided, and **exactly what is to be reviewed, never a picture**: `subject` names a layer, up to 1,024 records that must be live when it is raised, a checkpoint and blobs, and the host stamps it with the document's version then (`journal_length`, `undo_position`; a value the raiser sends is ignored), and `report` holds the check's numbers. A classified item carries the numeric validator report and the identity and version of what failed the policy, and nothing that would show it.

**How one is raised and by whom it is closed.** Anyone whose role names `review.raise` raises one: a reviewing agent, a validator's host, a promotion that wants a person's eye, and (when it exists) the invalidation substrate §6.8 names. An `Agent` item is closed — Accepted or Rejected — by any call whose role names `review.close`, and withdrawn by its raiser alone (1008, `review raiser`, for anyone else). **A `Human` item is closed only on a connection that presented a credential the operator issued for a role the roles file marks `human`** (`Role.human`, version 2; ADR-0069), and is never withdrawn, not even by the one who raised it: an agent that could take back the item it raised for a person could make the person's check disappear. The shipped file marks one role, `reviewer`, and no role an agent runs in; the director, which agents may run as, is refused. **A host with no human role has nobody who can close one** — a host with no roles file included, where nothing else is restricted — and the refusal says so: the item waits for an operator to load a roles file with a person's role and issue a credential for it, which is configuration the operator writes and an agent never does. **Naming a human role makes no call a person's**: a call's attribution, a connection's `client.hello` and a host's start line are claims any process types, and the first form of this rule believed them, so `engine-cli --roles … --role reviewer review.close` — the cheapest command an agent has, since engine-cli forwards `--role` to the host it starts — closed a person's item (the first review of the joined protocol work). Now a call with no credential that names a human role is refused at the role it resolves to (1008, `human review`, `Policy::resolve_role`), on stdio, engine-cli and an operator's connection alike; `engine-host` refuses `--role <a human role>` in every mode but `--issue-credential` (exit 2), engine-cli refuses it before any host starts, and a roles file whose `default_role` is human does not load. **How a caller is known to be a person is one field, read in one place**: `Caller::human_via`, the name of the credential that conferred a human role (`human_role` beside it), set only by `resolve_caller`; `review.close` reads it, and a task whose `owner_role` is a human role is claimed only by a caller whose `human_via` confers that role, never by a working role of the same name. `Role::human` is read in `policy.cpp` alone, and the lint's `human-flag` rule fails a read anywhere else, because the next check written by copying this one must not read the working role's flag. Until the editor's seat is built, a person's item is closed only over a listener with such a credential; against a process of the same user that can read the credential's file, that is a rule and an audit trail, not a wall. An agent is never issued a credential in a human role; engine-mcp's own host refuses its `--role` when that role is human, and refuses a call that names one.

**Where it is stored, and what survives a restart.** Everything: `ledger.json` beside the document (schema `LedgerFile` version 2: the tasks and the items; version 1 also counted the next ids, and its registered step drops the counters and gives every item revision 1, so a version-1 ledger reads and keeps its ids), written before the answer, and not in a checkpoint, which holds the world and not its work in progress ([doc](doc.md#checkpoints)). **No host keeps the ledger in memory.** Every call — the reads too, since one may let a claim lapse — takes `ledger.json.lock` exclusively between processes, reads the file, changes it and writes it back atomically, and lets go (`update_ledger` over `update_side_file`, `side_file.h`, the one helper every table beside a document goes through, as in "Two hosts, one side file"). The lock is the operating system's on an open handle (`LockFileEx` on Windows, `flock` elsewhere), so a host that dies holding it leaves nothing for anyone to break, and a call that waits for it more than 10 s is answered 1005 saying so. Two helpers were written for this on one morning, this one's and the transactions' and leases'; the side-file helper was kept, since it guarantees more: it reads a file of an older version through the registered migrations, writes nothing when the bytes are unchanged (so a read that let nothing lapse leaves the file and its time alone), and waits on a deadline with growing pauses rather than a flat poll; and a read of a document with no ledger takes no lock and leaves no lock file. Plan 06 §6.8 put the ledger in `work/tasks/*.json`, a file per task; one file is what lets one lock make a call's read, its checks and its write one step, and ids unique, without a directory scan. What it costs: a call reads and writes the whole ledger, so a long-lived document's ledger grows with every task it ever had (an archive is not built), and two writers wait for each other for the few milliseconds a write takes.

**The ledger's bounds.** Without them one loop of `task.create` and 256 `task.update` notes of 4 KiB each, from any role that names `task.*`, grows the file by about a megabyte a task; every call then parses and rewrites hundreds of megabytes under a lock the others wait 10 s for, and a person's `review.close` is one of the waits that runs out (the first review of the joined protocol work). Three bounds now, each refused 1004 with `data` `{"reason": "ledger bound", "bound", "limit"}`: **256 open tasks per actor** (`open tasks per actor`: not Done or Dropped, counted by creator), because the longest plan this project has run kept tens of rows open at once, a creator past 256 is a loop rather than a plan, and an agent resuming from `task.list` reads every one; **256 open review items per actor** (`open items per actor`, counted by raiser), because a person closes them one at a time and a 257th waiting on the same person hides the rest rather than adding to them, and a raiser's own agent items are its to withdraw; and **8 MiB of file** (`ledger bytes`), because every call, the reads included, reads and writes the whole file while others wait, and the slowest call has to stay far inside that 10 s wait — 8 MiB is 256 tasks of 32 KiB each, and one call over a ledger at the bound costs about 0.9 s in `msvc-debug` (measured 2026-11-18 from the bounds case's file-size subcase, four calls over an 8 MiB file, two of them writing it back: 3.76 s and 3.73 s in two runs, with the machine at 100 % CPU and fourteen rows building beside it, so an upper bound), which is under the second this bound was chosen against; a refused call costs as much as a taken one, since the file is read before the size is looked at. The size is looked at under the lock before a call that adds a task, an item, a note or links, so no two writers both pass it and the file stops at the bound plus one call's growth (at most about 100 KiB: a review item's 64 KiB report and its subject); a claim, a status change and a close still answer, so a full ledger is worked down rather than locked. The per-actor counts are by actor name, which a caller with no credential names freely (as the transactions' per-actor bound is), so for those callers the file's bound is the one that holds. Done and closed work past a threshold is not archived yet (roadmap A64).

**The ledger's lists** (2026-11-18, roadmap A55). A queue that shows "the newest fifty" should read fifty, and one that was told which items changed should read those, so both lists take three more things (`TaskListParams` and `ReviewListParams` version 2): **`order`** (`LedgerOrder`), **`limit`** and the ids to read (`tasks`, `reviews`). The order is stated and the same on every read of one ledger: **by an entry's last change, then by id** — a task's `updated_unix_ms` (every write to a task sets it), a review item's newest history line (every change to an item writes one, and the newest is never the one the cap lets go) — `Oldest` first by default and `Newest` its exact reverse, so the ties of a burst inside one millisecond still come back in one order. The order is the ledger's, not the file's: the file keeps entries in the order they were made, and a list of them by creation would put a task reopened today among last month's. `limit` 0 is every match, and 1 to 1,024 answers that many of the order's first; **a `limit` past 1,024, or more than 1,024 ids, is refused** (1004, `data.reason` `"list limit"`) rather than clamped, because a clamped answer is fewer entries than were asked for with only a count to say so, and a caller that wants every match asks for that with 0 (the ledger's own 8 MiB bound bounds that answer). The answer says how many matched past the limit (`more`, `TasksResult` and `ReviewsResult` version 3), so a section that holds more than it shows says how many it did not. An id the ledger no longer holds is left out of the answer, not refused: the ids come from events, and an event may name an item a restored ledger no longer has. **What a list costs under the lock**: the filters and the order are a pass and a sort of keys over the entries the file already parsed, and only the answered entries are copied, so a list's cost is the read it always made — the whole file parsed under `ledger.json.lock`, about 0.9 s at the 8 MiB bound in `msvc-debug` (above) — and the limit bounds what is sent, not what is read. A reader is never made to wait for that read by its own session: a session that may not write its directory reads plainly, without the lock (above), and a burst of another process's writes waits for the lock as a reader does, each writer for one call.

**The ledger's revision** (`LedgerFile` version 3, additive, so a version-2 file reads with revision 0 and a version-1 file through its step and then this one): a number the ledger carries that moves by one on every write it takes. A call that changes nothing writes nothing (a read that lets no claim lapse sets no write, and the side-file helper writes nothing when the bytes are the ones there), so the revision moves when the content does and only then. Every answer names the revision it read or wrote (`ledger_revision`), and the ledger's own event does too ([below](#the-task-ledger-and-review-items)), so a reader can tell whether its read is the one an event spoke of. It is compared for inequality and never for order: a ledger restored from an older copy has a revision that went back, and it is still a change. **An older build does not share a ledger with a newer one**: a reader refuses a field it does not know, so a build from before a version refuses, with 1004 on every `task.*` and `review.*` call, a ledger a newer host has written once; that is the rule and not a gap — a reader fails closed rather than drop what it cannot read, and only tests and proofs of concept consume the engine, so nothing is kept for an older build. `LedgerFile` version 4 adds no field of its own: its items carry their subject digests (`ReviewInfo` version 3, every field an addition), so its step from 3 is registered and changes nothing, and a version-2 or version-3 ledger reads with its items unstamped ([What a close is tied to](#what-a-close-is-tied-to)).

**General purpose**: neither a task nor an item knows a record type or a generator; a game's tasks and its own kinds of review are data in the same file. **Not yet**: MCP tools (roadmap A49); a review item that blocks a proposal's promotion (§6.10's "block promotion"), the editor's review queue (A24) and a classified item raised by a capture or a validator under a view policy (A26), which build on this; archiving; and a credential that makes `human` more than a declaration (A4).

**Tested** in `tests/ledger_tests.cpp` (eleven cases: a task created with its links, claimed, refused to a second actor's claim and update, blocked, unblocked, linked without duplicates, finished, its history in order and its events pushed, then read, filtered and reopened by a second session manager on the same directory; a claim that lapses at a one-second ttl and is taken by another; a task for one role refused to another, the role gate refusing QA, a classified item for a person with its report and its host-stamped version refused to three agent roles and to its raiser's withdrawal and closed by the reviewer, agent items withdrawn by their raiser alone, the lists, and what a subject may name; a host with no human role refusing to close one; and two session managers on two threads writing one ledger, 25 tasks and 25 notes each, every one kept and no id twice — run once with the lock taken out, it failed on its first collision; and a version-1 ledger written by hand, read with its ids, a new id drawn beside them, written back without the counters, its item at revision 1 and closed to 2; the life and roles cases also hold the `via` fields and the revision, a close against a revision that moved refused; and the bounds over ledgers written by hand, 256 open tasks and 256 open items of one actor refused the next, another actor and a dropped task or withdrawn item letting work go on, and an 8 MiB file refusing a create and a note but taking a claim and Done; and, over a ledger written by hand with its own times, the lists' order by last change and then id with `Newest` its reverse, a limit with `more`, the ids an event named with one the ledger lacks left out, a limit past 1,024 and 1,025 ids refused with `list limit`, and the revision moved by a write and not by a read that leaves the file's bytes alone), `tests/policy_tests.cpp` (the shipped roles file's one human role), `tests/listener_tests.cpp` ("a person's review item is closed by a credential for a human role alone": over a real listener with the shipped roles file, a credential issued for `reviewer` closes an item raised for a person and the item records `closed_via` and `closed_human_via`, one issued for `director` is refused 1008 `human review`, and on a host with no roles file the `reviewer` credential only reads, its close refused and the item still open), and `apps/engine_cli/tests/policy_tests.cpp` ("cli: eight processes at once write one ledger and lose nothing": eight engine-cli calls started together, eight ids, and an item raised by one process and listed by the next).

### What a close is tied to

Roadmap A56, the editor's review queue's design ([engine_shell](engine_shell.md)) cut into the protocol. **A person who accepts an item accepts what the window showed them**, and between the drawing and the click another connection can change the subject's records, change a record the subject hangs under, add a layer over it, rewrite an asset file (which makes no journal entry at all), or undo below the stamp and redo after the close; and journal numbers stamped by two processes are not one history. The item's `revision` covers changes to the item; the **subject digest** covers the document the item is about (`src/subject_digest.cpp`).

**What it hashes**: one SHA-256 over a canonical stream — a version line; the layer the subject is judged in, by name; then, sorted by id and each once, every record the subject names and every `ChildOf` ancestor of one, as its composed line (`doc::append_composed_record`, [doc](doc.md#the-canonical-form-of-a-composed-record): type, parent and composed properties, or a mark that it is gone or a tombstone wins) and, when the subject names a layer, the record that layer holds itself (a proposal's own opinion) or a mark that it holds none; then every blob those records and the subject name, by its SHA-256 name, which is its content, and whether the store holds it; then every file the subject lists (`ReviewSubject.assets`, version 2) and every file those records name, by its spelling, with the SHA-256 of its bytes read now through the host's roots, or a mark for which of three other things it is: admitted and not there (`missing`; a place under a regular file, `props/crate.glb/x.png`, is not there either, on Linux's `ENOTDIR` as on Windows' "path not found", as the roots' admission takes it: "a record's string under a regular file is missing, and the raise stands"); admitted and not read (`not readable` — not a regular file, a read that failed — `too large` or `over the subject's bound`); or **outside this host's roots** (an entry of `subject.assets` under a root name it does not have or in a place its roots do not admit, or a string a record holds that the raising host may have admitted under a root this one lacks: "Which strings are files", below), never opened. **A host that cannot see a file says so and never calls it a change**: a raise naming any file outside the raising host's roots is refused (1004, `subject not readable here`, `data.entries` the files by the spelling they were given) — whoever asks a person to judge runs where the thing can be seen; a detail on a host with any such file answers `SubjectState.comparable` false with `outside` naming them, `not_comparable` naming everything that keeps it from comparing, and `same` false; and a close carrying a digest there is refused `subject not readable here`, never `subject moved`. **The rule all of it follows: a raise is made, and a close accepted, only where every file the subject names was read and hashed on this host, or is honestly not there** (admitted by the roots, and no file at that place; `missing` compares). A file that is there and `not readable` — not a regular file, an open the system could not confirm was of the admitted path, a read that failed — refuses a raise (1004, `subject not readable here`, `data.entries` its spelling) and makes a detail not comparable (`SubjectState.not_comparable` names it), its close refused for it. **A file past a byte bound, and a file past the files bound, was not read either**: a raise is refused by the bound (`subject too large`, below), and at a detail it is listed in `not_comparable` (by its spelling, or `<n> more past protocol.review.subject_files` for the count), so a close is refused `subject not readable here`, with that detail's own digest too, since its bytes could change unseen between the two; a `.gltf` or `.glb` past the file bound is that entry as well, since nothing it names was followed. On Linux an open is confirmed through the link under `/proc/self/fd` ([io](io.md#roots)): **a host without `/proc`** (a chroot or a sandbox that does not mount it) can confirm none, so every file is `not readable` there — it refuses every raise that names a file and compares no detail that names one, rather than compare a subject of which it read nothing.

**A number is hashed as its JSON spells it**, so `1` and `1.0` are two lines though every typed reader sees one value; nothing the engine does on its own respells one — a layer's save and load keep each value's JSON kind, a merge, an undo and a rollback copy values as they stand, validation reads a record into a scratch object and writes nothing back, and a write-back writes only a field the world changed — so the digest moves on a respelling only when a client wrote the other spelling, which is a change of the record's bytes.

**A blob is digested by its name and whether the store holds it, and never read**: its name is the SHA-256 of its bytes, and the store holds them to it at both ends — a put over a file of that name whose bytes are not its name writes it again (`BlobStore::put`), and every read refuses bytes that do not hash to their name (`BlobStore::read`, `doc.blob`) — so a damaged blob is refused to whoever reads it and is never shown as the subject.

**Which strings are files.** Nothing in the schema marks a field as a path (`MeshPlacement.mesh` is a string), so the rule is one any record's value is measured by and never a list of types: a string property — of the composed record, and of the judged layer's own record, whose properties alone are searched and never its type (`engine.world.Node` passes the rule with the extension `Node`; "a subject judged in a layer names no file by its record's type") — at any depth of its value, whose last component ends in an extension of one to eight letters or digits (`props/crate.glb`, `content://rock.png`), resolved against the document's directory as every path a record names is ([Where a relative path starts](#where-a-relative-path-starts)). A string that passes and names nothing under a root digests as `missing`, a constant for that string. **A string the raise did not read as a file never blocks a raise or a close**: a URL (`https://…`, whose `https` passes as a root's name and is no host's), text with a colon, a root nobody had, a climb out of every root — at the raise each is one constant line, `names no file a root admits`, listed in `unreadable`, and the digest stays comparable. **What tells it from a file only some hosts can see is what the raise read**, recorded on the item as `ReviewInfo.raised_files` (version 3): the stored spellings of the files the raise's digest read as files — every one the raising host's roots admitted, there or not, listed or named by a record (a file a glTF names follows from the glTF and is not recorded) — each `<root>://<relative>` or relative to the document as the subject or the record spells it, never absolute, at most the files bound of them and each within its own length rule (1,024 bytes, for a listed entry and a record's string alike), so a raise that would record more or longer is refused by the bound it passes. At a detail or a close a spelling of that list this host's roots do not admit is `outside`, and the subject is not comparable here, **whatever names this host's roots have**: a root's name is portable and its place is not, so two hosts with roots named alike can admit different files ("two hosts with the same root names in different places compare only what both read": a record's `../../c/rock.png` the raiser read under its `content`; a second host whose `content` is elsewhere answering it `outside` and refusing a person's close `subject not readable here`; a third with no `content` at all answering the same). A string not in the list that this host does not admit is the constant line. An item with no list — one with no `raised_digest`, raised before digests — has nothing that says a string was not read as a file, so there every string this host does not admit is `outside`. An entry of `subject.assets` stays strict: not admitted is `outside`, and refuses a raise ("a string no host could admit never blocks a raise or a close": a URL, a colon, an unknown root and a climb set on the subject after a raise, and a person's close with a fresh detail standing; the same strings before a raise, and the raise standing). **What is still not held**: a file reference added to a record after the raise, in a field the guess picks up, on a host that cannot admit it, digests as the constant line there — the raise never read it, so nothing says it is a file — and a person on that host can close over a file their host never read; the schema annotation of roadmap T206, which marks a field as a path so that what a record says is a file is one whatever host reads it, closes that. An imported or hand-authored record gets this as a generated one does; a subject naming no file pays nothing for it. **What the rule misses**, until a schema annotation marks a field as a path (roadmap T206) and replaces the guess: a name with no extension (`terrain/height`), an extension of more than eight characters, and a directory named as a set of files (`textures/`). **A record's string whose admitted place holds a folder was never a file**: `renders/v1.2`, `scans/2026.11` pass the guess, and the folder digests as the string's constant line, `names no file a root admits`, the line a host that does not admit the string writes, so two hosts agree on it, it is not recorded in `raised_files`, the raise stands and a detail compares; a folder's contents are never hashed, since what a folder stands for is a reader's to say (roadmap A68). A string the raise read as a file that is a folder at a detail is that line too, which is not the file's hash, so its close is `subject moved` ("a record's string naming a folder digests as no file, and the raise stands": a folder under the document's directory and one under a root a second host lacks, the second host answering the stamp; the mesh made a folder after a raise). An entry of `subject.assets` that is a folder (`set.d`), and a file a glTF names that is one, stay `not readable`: the raiser or the glTF said it is a file, so a raise over it is refused and a detail over it does not compare; a FIFO or a device a record's string leads to is `not readable` as well. An entry of `subject.assets` is read whatever its name, so a raiser lists what the rule would miss. **An entry is a stored path** ([Paths a document's records hold](#paths-a-documents-records-hold), T174): `<root>://<relative>` or relative to the document, never absolute, held to that form at the raise by `io::check_stored_path_form` and refused with the answer a record's absolute path gets (`path_not_found`, one rule and one wording), then admitted for reading through `io::admit_stored_path`, as every file the digest reads is; so no ledger, no answer and no commit of a document carries a path of the machine ("a subject's listed file is a stored path, never an absolute one"). **An older raise's absolute entry is a decision, not an accident**: a ledger written before the form was held at the raise can hold one, and it is not mended (only tests hold such a ledger), so the entry is `outside` on every host and such a person's item is closed on none; but no answer echoes it — the detail's lists, a refusal's `entries` and the item's own `subject.assets` in every answer give it by its index, `assets[2]` ("an old item's absolute asset is answered by its index, never its spelling"). **What a glTF names is part of it**: a file the subject names that is a `.gltf` or a `.glb` has its external `buffers[].uri` and `images[].uri` read too — a `data:` URI is in the file already; a `.glb`'s JSON is its first chunk, read from its 12-byte header (`glTF`, version 2, a length within the file's size) and that chunk's own 8 (type `JSON`, a length within the header's and within the JSON bound), the chunk's trailing NUL bytes dropped before it is parsed (the format pads with spaces, which are JSON's own; some exporters padded with NUL, where the importer's tokenizer stops), and its buffer 0, the binary chunk, names nothing, while any other buffer and any image may name a file as a `.gltf`'s do ("a .glb's external files are read with it, and a broken one refuses a raise": an external buffer rewritten refusing the close; a header of eight bytes, and a chunk past the bound, each refusing the raise; "a .glb padded with NUL is followed, and each broken header refuses a raise": a NUL-padded chunk's image read, then a version other than 2, a length past the file's size, a first chunk not `JSON` and a chunk past the header's length, each refusing the raise `names not read`) — each **admitted through the host's roots exactly as a record's own file is**: its URI's own rule first (`io::uri_relative_path`: decoded once, and refused for a backslash in the decoded text — a URI has none, and none is turned into a separator — a control byte, a colon in its first segment or a leading `/`), then `io::admit_stored_path` from the glTF's admitted directory, so it gets the stored path's text rules, its links resolved, a share refused and the root check (with the host let go, against the roots copied under the lock, `io::Roots::read_copy`). **A `..` is no way out; the roots are the door**: `models/x.gltf` naming `../textures/x.png` is an ordinary layout, which the importer reads, so the URI's rule keeps a climb at the front as it is spelled and the admission decides where it leads; a `..` after a named segment (`a/../b`) is refused by the text, since an open would resolve it through whatever `a` is ([io](io.md#roots)), so it is not followed and a raise over it is refused `names not read` — under a root it is read and hashed as any file. **A name the rule, the text rules or the roots refuse is not followed**: a line `not a file under the glTF's directory` when refused for its text (the same on every host; listed in `unreadable`) or `outside this host's roots` when refused for its place (a climb above the root, a link under it to a directory outside it; listed in `outside`), either way listed in `SubjectState.not_comparable`, so a detail there is not comparable and a close carrying a digest is refused `subject not readable here`; and a raise over it is refused (1004, `names not read`, `data.entries` the name by its index), since the item would be stamped over a file its digest never read. **It is never opened or sized**: it adds nothing to `asset_bytes`, and a raise refused past a bound answers no figure for it, so a client learns nothing of a place outside the roots. Each is counted under the four bounds and answered by where the glTF names it, never by the URI's text, which may be any length and spell any place: `<glTF>#images[3]`, `<glTF>#buffers[0]`, in `SubjectState`'s lists and in the stream ("a glTF's named file passes the host's roots, and one refused is never opened": a plain `../../../outside.bin` above the root, the climb to it encoded with backslashes, an encoded `\\host\share`, and a junction or a link to a directory outside the root, each with the detail's opens and bytes the glTF's and its buffer's alone and the detail not comparable, and a raise over the first two refused `names not read`). The JSON is read with the engine's own reader (`core/json`): the protocol takes no dependency on the importer. **A glTF whose names cannot be followed says so**: one that reader refuses (nested past its depth of 256, which the importer's reader may still take), one past `protocol.review.gltf_json_bytes` ("What it costs"), a `.glb` whose headers do not hold or whose JSON chunk is past that bound, is hashed as any file is, a line says its names were not followed and why, it is listed in `unreadable`, and a raise over it is refused (1004, `names not read`, `data.entries` the glTF by its stored spelling, and for the bound `data.bound`, `data.limit` and `data.figure`), since the item would be stamped over geometry its digest never saw; and **at a detail or a close the subject is not comparable here** — the glTF is listed in `not_comparable` and a close carrying a digest, even that detail's own, is refused `subject not readable here` — since what it names was never read, and the files it names could change unseen between the detail and the close ("a glTF whose names cannot be followed says so, and no raise is made over it": a glTF 300 deep with an external buffer set on the subject after a raise, its detail not comparable and its close refused, then one past the bound lowered to 16 bytes).

**What is followed is a `.gltf` or a `.glb`, by its suffix, and nothing else**: a file that names others in another way is hashed as its own bytes only, and a rewrite of what it names is not seen. Three such readers are in the tree: the renderer imports every mesh that is not a `.clusters` file as a glTF by its content, so a glTF under another suffix (`props/crate.mesh`) is drawn with its buffers and hashed alone; a `.clusters` container names its images by path; and a heightfield record's source is a JSON header whose `data` names the grid the renderer reads. None of them is marked not comparable, since a scene's built meshes would then make every item unraisable; roadmap A68 has each reader of a file that names files register how its names are read, at a registration point the digest asks, so the digest and the renderer cannot disagree about what a subject is made of.

**What it leaves out, and why**: a record the subject names only by reference in a property (a material record by its id), unless the subject lists it — the raiser lists what the decision rests on, and following every id-valued string would make the digest of one prop the digest of half the world; a record's children (the item is about the record, not what was later hung under it); **the layer stack itself** — what a layer composes for the subject is in the subject's composed lines (a stronger layer overriding a property, a layer's opinion taken out) and the judged layer's own record, so a layer that holds nothing of the subject, another agent's proposal opened beside it above all, is nothing its reviewer saw, where hashing every layer's name refused every honest close each time one opened (A56); a layer's storage form (it changes no composition); the scene's sky and its hour; the journal's positions (`journal_length` and `undo_position` stay on the subject as colour, never as what decides); and anything after the close.

**When it is computed**: stamped at the raise into `ReviewInfo.raised_digest` (version 3) by the raising host from its own document — content, so a digest stamped by engine-cli's host compares with one the editor computes when both can read every file the subject names, and the one that cannot says so (`comparable`) rather than answering a difference; computed again when an item's detail is opened, `review.list {review, digest: true}` into `ReviewsResult.subject` (version 4, a `SubjectState`: the digest, whether it is the stamp, the records gone, the files admitted and not read, the files outside the roots and whether it compares, and what it covered and cost), for one item and never for a list (1004); the detail is one item by id alone, so a list's `reviews`, `order` other than the default, `limit`, or any of its filters — `state`, `audience`, `kind`, `task` — beside `digest` is refused (1004, `detail form`) rather than ignored, since each would change nothing or hide the item it names, a filter that did not match answering no item and no error (`ReviewListParams` version 3; "the detail form refuses a list's filters beside it"); and at the close. No computation holds the ledger's lock or the host's dispatch lock while it reads a file (below, "What it costs").

**The close carries what the page showed**: `review.close {review, resolution, note, revision, digest}` — the item's revision and the subject digest its detail was drawn with (`ReviewCloseParams` version 3; the design's `seen: {revision, digest}`, flat because `revision` was already a field of its own). The host computes the subject's digest again in full, reading the subject from the ledger first (a subject never changes after its raise) and its files with no lock held, then, under the dispatch lock and the ledger's, on the values of that same pass, refuses the close with 1004 when the item's revision moved (`revision moved`) or the digest differs (`subject moved`, the digest now in `data.digest` and whether it is still the stamp in `data.same`), so the page draws the new statement and the person decides again. **A close that compares nothing** — an agent's close that sends no digest, a raiser's withdrawal — decides without the digest's passes, on the item as the ledger holds it under its lock: it reads no file, is never refused `subject changing`, and answers no subject statement: `ReviewsResult.subject` is null (optional, as it is on a list's rows), so nothing in the answer of a close that compared nothing reads as "could not compare", which a statement's `comparable` false would ("a close that compares nothing decides without reading the subject"). A person's item is closed only with both (`seen required`): the guarantee is the person's, so a page that dropped one half could not decide past a change; an agent's item checks what its closer sends. The record of the decision holds the digest it was made at (`ReviewInfo.decided_at`) — the one its closer sent, which the host found equal, and nothing when the closer sent none (an agent's close, a withdrawal: nothing was compared; "a close that sent no digest records none it was decided at") — and the answer the subject as it was then (`ReviewsResult.subject`). A person may accept a subject that changed since its raise — the detail says so and the close records the digest they decided at — but never one that changed since they looked. Between the composition and the write the document of this host cannot change unseen: the pass that read the files with the host let go compares the document's revision, its journal and its stack with what it composed before it decides, and composes again when they moved; a file can still be rewritten by another process after its read, and that window is the call's own milliseconds, the digest recorded the one computed.

`tests/ledger_tests.cpp` ("a person's close is refused when what the item is about moved since it was seen") takes the four attacks the queue's design found, each a close the item's revision alone let through: a `SetProperty` of the subject's record; one of the `ChildOf` parent it hangs under; a stronger layer overriding a property of the subject, and a proposal that overrode one rejected, which empties its layer (no method mutes or reorders a layer) — while a layer added that holds nothing of the subject leaves the digest equal and the close stands; the mesh its record names rewritten at the same length with its time put back (`std::filesystem::last_write_time`), which no journal entry, size or time shows; and an undo below the stamp — refused — then the redo, after which the same digest closes it, because the check is the content and not the journal's position. Beside them: nothing changed, accepted with `decided_at` the digest seen; and another host's stamp of the same content equal to this host's digest, then refused once this host's document moved. The base's case for a person's item gains its `seen required` refusal.

**It hashes content and never trusts a file's time or size.** Nothing is cached: every computation reads every asset again, and composes every record again from the index. **Where a hash may be reused**, if the cost measured says it must: a record's line by its id and its `revision_of` stamp, which the document moves on every change to that record's composition and restamps on every index rebuild, so a reuse decides from the document's own record of its mutations and never from a clock (the stamps start again in a new process, so such a cache lives and dies with its session's document); and an asset's hash at a detail's opening, while the directory-change notice on its root (A55) has reported nothing for it, a dropped notice clearing them all. **Where it is always read again: at the close**, so the computation that decides trusts nothing kept.

**What it costs** is bounded by four bounds, each a tunable read once a computation and none hidden: `protocol.review.subject_files`, the files one subject names in all, listed and named by its records together (256); `protocol.review.file_bytes`, one file's bytes (256 MiB); `protocol.review.subject_bytes`, every file's bytes together (1 GiB); and `protocol.review.subject_records`, the records composed, the subject's and their ancestors, each once (4,096); beside them one of a glTF's own, `protocol.review.gltf_json_bytes` (64 MiB), the bytes of a `.gltf`, or of a `.glb`'s JSON chunk, parsed into a tree to follow its names, below the file bound because the tree is built with the host let go and once a call: past it, the glTF's bytes are still hashed and a line says its names were not followed. **The files bound limits what is collected and answered, not only what is read**: a glTF's names are taken each once (a hash set) and only up to what is left of the bound, and every file past it, whether the records or a glTF named it, is one count — a line `past the bound` and one entry of `unreadable` and of `not_comparable`, `<n> more past protocol.review.subject_files` — never a line or an entry a name ("past the files bound a digest collects and answers a handful of names": a glTF naming 100,000 images, then ten record-named strings beside it, with the bound at 4; `SessionManager::digest_names_collected` holds what was collected). The ancestors are counted as they are met — a walk up stops at the first record already met — so the work is the distinct records and never the records times their depth. **A raise past any bound is refused** (1004, `subject too large`, `data.bound` the tunable's name, `data.limit` and `data.figure` a count or a size, never a path), before a byte of a file the subject lists or its records name is read: every such file is opened and held to the byte bounds by its size first. **A glTF's names are bounded as they are read**: only the glTF says what it names, so it is read first, in full (within its JSON's own bound); then a raise whose names pass the files bound stops before it opens one of them, and one within it holds them to the byte bounds by their sizes before a byte of them is read ("the files a glTF subject names are read with it": the raise refused past the files bound read the glTF's bytes alone, and opened it twice, to size it and to read it). **A detail or a close past one says so in the stream** — a file past its bound is a line `too large`, a file past the subject's bound a line `over the subject's bound`, the files past the count one line with their number, and a line `over` names each bound passed with its figure — so a subject digested past one never equals one that was not; and what is past a bound was not read, so the detail is not comparable and a close is refused `subject not readable here`, with the stamp or with that detail's own digest, naming the bound passed as the raise's refusal does (`data.bound`, `data.limit`, `data.figure`, and the tunable in the message), since every host with the same bounds answers alike and the remedy is the bound, not another host: nothing is ever digested silently weaker, and no close is accepted over bytes this host did not read. Within them: one index lookup and one canonical line a record, the layer's own record beside each; one stat a blob; and every byte of every file read and hashed in one-megabyte reads by `core/hash`'s portable SHA-256. `SubjectState.ms`, `asset_bytes` and `passes` report each computation's. **Nothing bounds how many digests run at once**: each call reads with no lock held, so as many connections as ask — details, closes and raises together — digest at once, each within its own bounds, and what limits them together is the host's memory and its disk. **A container's tree costs many times its bytes**: the engine's reader builds one `JsonValue` a token (24 bytes, `core/json`'s size table) plus each array's and object's storage, so a `.gltf` or a `.glb`'s JSON chunk at the 64 MiB bound written as `[0,0,…]`, some 32 million values, comes to about 0.8 GB, and up to about twice that while its arrays grow, for each such call at once — arithmetic from the type's size, not a measurement; an operator who expects many callers at once lowers `protocol.review.gltf_json_bytes`.

**Only the admitted file is read**: the open is held to the path the roots admitted, since the reads come with the lock let go, possibly seconds after the admission on a later pass, and a component swapped for a link meanwhile would lead anywhere — `io::FileHandle::open_regular_unmoved` compares what the system says the opened handle is with the admitted path and, when they differ, answers what a missing file answers (`missing`: at the admitted place there is no file, and an open that succeeded tells nothing of what was at the link's end; an open the system refuses first, a denied file, a directory or a device there, answers `not readable`, which does tell, roadmap T209), and `not readable` when the system cannot say what it opened ([io](io.md#roots)). **Only a regular file is read**, through `io::FileHandle::open_regular`: a directory, a FIFO, a socket or a device is `not readable` and is never opened in a way that can wait (on Linux the open is `O_NONBLOCK` and the type `fstat`'s, so a FIFO under a root with no writer answers at once instead of holding the host until one appears; on Windows the handle's type).

**The host is let go for the reads.** A pass composes the document's part under the dispatch lock — the records' lines, the blobs', and each file admitted through the roots — then reads the files with the dispatch lock let go (`without_dispatch_lock`, [Work outside the dispatch lock](#work-outside-the-dispatch-lock)), reading nothing of the host's while it does, so every other client and the editor's frame are answered meanwhile; then, under the lock again, it looks the session up anew and compares the document's revision, journal, undo position and stack with what it composed against. **A pass is thrown away only when the subject moved**: a document that moved is composed again there, under the lock, and when that half — the stream up to the files, and the files admitted to the same places — is the one the reads were made for, the reads stand, whatever else the document's counters say (an agent editing another record, a write-back at `Persist`); and the item's own `revision` is compared, never the ledger's, so a write about another item or a task (a claim lapsing in someone's `task.list`) moves nothing (a raise, which has no item yet, makes the ledger's own refusals again in its write). Moved, it composes and reads again, three passes in all, then refuses 1004 (`subject changing`, `data.passes`) — a raise, a close and a detail alike ("an edit outside the subject during a digest's reads keeps the pass": another record edited and a task created at every pass's reads, and the close standing in one pass with the files read once); the decision of a close or a raise is made under the lock on values read in that same pass. **The refusals that read no file come first**: an item already closed or a replay, a revision that moved, a role or a raiser the close refuses, a person's close without what it saw, a session that may not write, a subject layer or record that is not there, and the ledger's own bounds, all made in a first read of the ledger before a byte of any file is read (`SessionManager::digest_bytes_read`, which a case reads, counts every byte a digest read, and `digest_files_opened` beside it every open the digest asked of the system, whatever it answered, so a case holds that a file was never opened at all, which a count of bytes cannot show). **It has not been measured yet** (roadmap A56, not done): the measurement wanted is `msvc-release` on a quiet machine, `review.list {review, digest}` over a subject of a thousand records of about a kilobyte each under a few dozen ancestors, then with assets of 20 MB and of 200 MB, reading `ms` and `asset_bytes` from each answer; its numbers, with the machine's state, belong here, and until then this page states none.

`tests/ledger_tests.cpp` ("a raise stamps the subject's digest, and another host's detail agrees"): the stamp covering the placement, its node and its mesh; the detail the same; a list refused a digest; a second session manager on the same directory computing the same digest; a missing listed file digested as such, and a listed file under a root the host lacks refused at the raise; and an edit of the subject moving it. "the detail form stands alone, and ledgers from before digests read": a version-2 and a version-3 ledger read, their item's detail not the stamp, then each written back by a close at the current version and read again with the item as the old host wrote it. "the files a glTF subject names are read with it": a placement's mesh a `.gltf` naming a buffer, a percent-encoded image, a `data:` buffer and an image above its directory — the three counted against the files bound and read, the one above among them, and the image above and the buffer each rewritten at the same length with its time put back refusing the close `subject moved`. "a host that cannot see a subject's file says so, and never calls it moved": two hosts over one document with different roots — one has a `content` root and the test tree, the other only the case's folder — and a subject naming `content://rock.png` and an existing file beside that folder; the second's detail is not comparable and names both as outside, its close is refused `subject not readable here`, it refuses to raise the same subject, and the first compares and answers the stamp. Beside it, with each bound lowered for the case rather than gigabytes written: "a subject past a digest's bound is refused at the raise, and said at a detail" (each of the four refused naming its tunable and figure with no byte read, the mesh grown past the file bound, then past the subject's, and a record naming a second file past a files bound of one, each differing from the stamp, not comparable, and refusing a close `subject not readable here` with the detail's own digest, a directory and on Linux a FIFO refusing a raise, answered at once, and a listed file made a directory after its raise leaving the detail not comparable and its close refused `subject not readable here`); "a close or a raise refused before its digest reads no asset" (each refusal above, `digest_bytes_read` unmoved); and "a digest lets the host go for its reads, and composes again past an edit" (a second client's call answered from inside the read through `SessionManager::set_digest_read_hook_for_test`, an edit there making a second pass, an edit at every pass refused after three). `foundation/io`'s "open_regular opens a regular file and refuses anything else without waiting" holds the open itself.

## The host's file roots

**Built in part, 2026-11-18** (roadmap T174, [ADR-0071](../adr/0071-a-host-reads-and-writes-only-under-its-roots.md)). [What is built](#what-is-built-and-what-is-left) lists the methods that go through the roots now and the ones that do not yet; the design below is the rule both follow, with two changes made while building it. **Roots have names**, and a path crosses the protocol and is stored as `<root>://<relative>`, never as an absolute path (the owner, 2026-11-18: an absolute path of the operator's machine should not end up in a committed document, and may name a worktree that is gone). And the owner decided the first question below: **only the operator's folders**. Many methods take a path from the client and make the host read, write or create there with its own rights: thirty-seven places on main and the branches of 2026-11-18, every one listed with what it lets a client learn or change and what confines it, in [the survey](../experiments/host-file-roots-survey-2026-11-18.md). Most are registered `read_only`, so every role reaches them, the default one included; three carry a lexical check of their own and the rest none. A role decides *whether* a method may be called; nothing decides *where* on the disk the call may reach. This section is that rule: one set of directories per host, the operator's, and one function every method calls before it touches a path a client named.

### Roots

**A root is a directory with an access, read or read-and-write**, made canonical once when the host starts. A client-named path is admitted for reading when it lands under any root, and for writing or making a directory when it lands under a read-and-write root. Nothing else on the disk exists for a client: a path outside every root and a path that names nothing get the same answer.

**With nothing configured a host has these roots, and only these:**

| Root | Access | Why |
|---|---|---|
| the **document directory**: `--doc` on engine-host and engine-editor (engine-cli forwards its own `--doc` there rather than sending `session.open`) | read | what the operator handed the host to work on; a document's assets, scenes and blobs live under it, which is where `doc.place_asset` and `doc.put_blob` already confine their reads |
| the **output directory**, `<doc>/out/`, made on the first write | read and write | below; a root only when nothing is there yet or a plain directory is, inside the document after resolving (`io::Roots::add_inside`): a link, a junction or a file at `out` (a document from a checkout or an archive) would make its author's target the host's writable root, so the host starts with no `out` root and a path naming `out://` is told the root is not present |
| the host's **derived-data root** (`--ddc`, or the document's, or the walk to the directory holding `AGENTS.md`, as today) | read | a client may name a built container in it; the host writes there only by content address, never at a path a client names |

**The output directory is the one place a client may make the host write by default**, because the host's products for its clients — captures, heat maps, evaluations, traces, saves and a loaded save's working copy, built containers — belong beside the document they were made from, inside the directory the operator already gave the host, where a test's `TempDir` already holds them. It is **not the document directory itself**, because a write there lands on the document's own files (`manifest.json`, `layers/`, `blobs/`, the journal and its side files) behind the journal, the roles and the leases at once — the survey's row 17, `content.build` `output` over `layers/base.json`. It is not the system's temporary directory, which is a place every process shares (the test-hygiene rule in `AGENTS.md`) and which the operator never named. And it is already outside a checkpoint: D13's `.git/info/exclude` keeps only `manifest.json`, `layers/` and `blobs/`. A host with no `--doc` has the derived-data root alone, and refuses every client-named path but a container in it until its operator names a root.

**The operator names more on the command line**: `--root <name>=<dir>` or `<dir>:ro` (read; `:ro` spelled out lets a directory whose own name ends in `:rw` be read-only) and `--root <name>=<dir>:rw` (read and write), repeatable, a client naming one as `<name>://<path>`, on engine-host and engine-editor, and forwarded by engine-cli and engine-mcp to the hosts they start, as `--mount` is; or `--roots <file.json>`, an `engine.protocol.RootsFile` (`@kind(document)`: `{"roots":[{"path":"D:/assets","write":false}]}`) for a host that lives long. **Every `--mount <scheme>=<dir>[:rw]` is a root too**, with its own flag, so `content://a.glb` and the native path under the mount are one file and one answer. A read root must exist at start and a read-and-write root is made then; either refused at start exits 2 naming it. A root that is itself a link or a junction is followed once, at start, and its target is the root; the start's log line names both, so a root retargeted later is not followed. **A client makes documents below a root, not at it**: `session.open` with `create` is refused, with the answer any place a client may not write gets, at a directory that is or holds a root's own directory, a served directory or an open document's directory, and at an open document's `out/` (`io::Roots::may_make_document`), since the new document would be protected while open and close that place to every client write — `create` at `out://` made the host's `out/` a document, and every capture, save and trace after it was refused (`protocol_tests`, "session.open does not make the host's out/ a document", "session.open does not make a writable root's own directory a document"). `session.load_game`'s `dir`, the other place a client-named directory becomes a document's, asks the same and answers the same (`save_tests`, "a load does not make the host's out/ or a root's own directory a document"), and engine-mcp's hint for the refusal says where a document is made rather than to pass the `create` the client passed. A document at a directory of its own is the operator's `--doc <dir> --create`. Whether a client may make one in a directory that already holds other files is a separate question, not asked yet.

**Roots are operator configuration that no protocol method changes**, as a view policy is ([ADR-0033](../adr/0033-content-classes-and-view-policies.md)). `engine.roots` (read-only, `RootsResult`) answers each root as the operator named it, its canonical form and its access, and the base relative paths resolve against, so a client — an agent above all — can learn where it may write without trying; nothing writes them. An agent that needs another directory asks its operator.

**Two kinds of directory are never written by a client, whatever the roots say**, and the start refuses a configuration that would allow it (exit 2, naming both):

- **an open document's directory outside its `out/`**: for every session the host holds (`session.open`, `session.load_game`), a client-named write that lands in `<that document>/` but not in `<that document>/out/` is refused like one outside every root, so an operator's `--root D:/work:rw` that holds a document cannot be used to go behind its journal. A document's files change through `doc.*` alone. The protection lasts exactly as long as a session has the document open (below, in [what is built](#what-is-built-and-what-is-left)).
- **a directory the host serves to a browser**: the listener's shell directory (`--shell`, else `<exe>/../shell`, a directory on disk read on every request: the survey's row 27). Its pages run in the operator's origin with the operator's cookie, so a file a client places there is stored script with the operator's session. No write root may hold it or lie under it, and the function refuses a write that lands under it even through a link. The shell directory is the listener's **own read root**, held apart from the methods' roots: `GET /shell/<path>` is admitted by the same function against that one root and no other, so no method reads the shell and the shell serves nothing else.

### Per host, not per role or per credential

**One set of roots for every client of a host.** What has to be bounded is the host *process*'s rights over the operator's disk, and the one who can bound them is the operator, once, for the process. A role already decides whether a method may be called at all, and stays the place for that: `content.build` is still refused to `qa`, and a role that may call a writer still writes only under the roots. A roles file is shipped content (`content/roles/roles.json`) and must not name a machine's directories; a credential (A4) names a role, and a second policy beside it would give the same answer for every credential on every host there is. The function takes the roots it checks against as an argument, so narrowing them for a credential later is a change of which set is passed, not of the rule; [ADR-0071](../adr/0071-a-host-reads-and-writes-only-under-its-roots.md) says when.

The capture writers stay `read_only`: they change no document, lease or host setting (the rule above), and with roots a role that may only look writes only under `out/`.

### Where a relative path starts

**A relative client path resolves against the document directory of the session the call names**, else the host's `--doc`, else it is refused (no base); so `"out/captures"` names one place for a writer and for the reader of what it wrote. An empty `out_dir` is the output directory itself (today it is the host's working directory). **A path named inside a file the host reads for a client** — a scene file's meshes, heightfields, materials and images; a glTF's buffers and images; a manifest's entries; an overlay's meshes — resolves against that file's directory, as today, and then passes the same function with the same roots and the same access. **A path a document's record names** (`engine.scene.MeshPlacement.mesh`, a heightfield's `source`, a terrain material's images) resolves against the document's directory and then passes it too: a record any writing role committed is a client's path (the survey's row 9). A refusal inside a file answers for the field the client named, with the entry that named it.

### Where derived data goes

**The host's derived-data folder is a root of its own, `ddc`**: engine-host names the repository's `ddc/` (the walk up from its executable to the directory holding `AGENTS.md`), makes it at start if it is missing, and holds it **read** for clients — a client may name a built container in it, and only the host writes there, by content address. `render.load {session}` with no `ddc` and `content.build`'s `cache` with none both write under it (`derived_data_root`). A host with no such folder puts a session's derived data in **`<that document>/out/ddc`**, and nowhere for a session whose directory may not be written, where a generator that needs a root refuses and says so. Before 2026-11-18 a session's load walked up from the document to a repository's `ddc/` or made `<doc>/ddc`: inside an open document outside its `out/`, or under no root at all, both places the roots keep every client write from (`protocol_tests`, "a session's derived data goes to the host's ddc root, else its out/ddc"). A client's own `ddc` is admitted as any output is. engine-editor gives its listener no `ddc` root yet, so its sessions take `out/ddc`; its viewport's own root is the operator's `--ddc`.

### Paths a document's records hold

**Built 2026-11-18** (`domain/protocol/record_paths.h`, `io::admit_stored_path` in [io](io.md#roots), `systems/doc_scene`'s reader). A record a writing role commits is a client's path stored for every later reader: `engine.scene.MeshPlacement.mesh`, `engine.terrain.Heightfield.source` and each of its ground material layers' `base_color`, `normal`, `roughness`, `mask` and `height` are opened by every `render.load {session}` and every editor viewport, by anyone, across restarts and on other machines — and a terrain image or a heightfield comes back as pixels in a capture. These are the only `@kind(record)` fields that name a file today (`holds_stored_paths`); a reader that opens a path from another adds it to the table and to its own admission in the same commit.

**What a record stores is the portable form**: `<root>://<relative>` or a path relative to the document's directory — the two forms that name the same file on another machine and in another checkout — and **never an absolute path** (`Refusal::absolute_stored`), whether or not a root holds it. The owner's two reasons for every path hold here first: a document is committed (its checkpoint is a git commit), so an absolute path of the machine that wrote it would land in the repository, and an absolute path may name a worktree that is gone by the time anyone reads it. A relative path may climb out of the document (`../shared/rock.glb`) when the roots admit where it lands.

**Admitted when the record lands.** Every way a record reaches a session's document goes through `Session::commit_commands` or `Session::step`, and both read the records each command named as they now stand — composed, and as the layer the commands wrote holds them, because a stronger layer's value hides a weaker one's from the composed record but not from that layer's file, its journal or its checkpoint (an absolute `mesh` written into `base` under `edit`'s override is refused as any other is; `protocol_tests`, "a path written into a layer a stronger one hides is admitted as any other is") — and pass their paths through `check_stored_paths` before anything is journaled: `doc.apply`, a transaction's stage and commit, a merge's result, a promotion and the other replays of a proposal, `doc.rollback_to` (its pre-check, `check_commands`, too), and an undo or a redo that brings a path back — which is admitted again, because the session's roots may not be the ones it was written under. A refused path refuses the whole call with the answer every refused path gets (1003, `data.reason` "path", `data.field` the record's field such as `mesh` or `materials.layers[1].normal`, the sentence repeating the record's own spelling) and `data.object` the record's id; nothing lands. Whether the file is there is not asked: a record may name a mesh not built yet. A session no host gave roots (the engine's own writers, a test of the document alone) holds the stored form alone. The session's roots are the host's (`SessionManager::set_roots`, set by engine-host and engine-editor at start; `session.open` sets them from the context when a host did not). The runtime world's write-back is one of those writers: a record it moves keeps its path, and a record whose path is refused cannot be written by anyone but to mend or delete it (`protocol_tests`, "a path a record holds is admitted as it lands, by every way a record lands").

**Admitted again when it is read**, because a document can arrive from a checkout or an archive with paths no host of this machine admitted: `doc_scene::read_document_scene` takes the host's `const io::Roots*` — engine-host's `render.load {session}` passes `Context::roots`, the editor's viewport its listener's roots — and admits every stored path from the document's directory before anything opens it; the scene names the native path admitted. A placement whose path is refused is left out, never opened and never an instance; a ground whose source or any material image is refused is left out whole; both are counted in `RenderSceneInfo.left_out` (`doc_scene_tests`, "with a host's roots, a record whose path is refused is left out and counted"). The roots are passed to the reader rather than admitted by its caller because only the reader knows which fields it opens; the protocol's table names the same fields for the write, and the two are kept together by the comment on each. With no roots (engine-view, the tools, an editor that serves no client — `--offscreen`, or a window with `--no-shell` and no `--listen` — the operator's own reading) every path is resolved as written, as before; the roots are for clients, and an editor takes its listener's for its session and its viewport together (`EditorDocument::serve_clients`) only when it serves some ([apps](apps.md#engine-editor-the-engines-window-on-a-document)).

**What a client is told about them** (T174, the owner's rule: no client is told an absolute path of this machine, and for a path outside the roots a refusal and a missing file read alike). The reader names a record's file by the record's own spelling in its own sentences; the sentences of what it calls — the tile-set provider's (the header, its grid), the mesh loaders' (a `.gltf`, a `.clusters` container, an image) — name the native files they opened, so `render.load {session}` answers the reader's and `load_scene`'s errors through **the one shown form**, `shown_message(message, named, roots)` in `paths.h`: each mesh's admitted native path by the record's spelling, the ground's by its source's, then every root's directory by `<root>://`, longest first (`protocol_tests`, "an answer names a root's file by its root, never by the host's directory"; `doc_scene`'s "under a host's roots the reader's refusals name the record's spelling"). `editor.import_mesh` answers its importer's sentences through the same function, naming the chosen file by the client's spelling (or, by a grant, by its own name) and the files beside it by that spelling's directory, never the root's directory or the person's ([apps](apps.md#engine-editor-the-engines-window-on-a-document)). The host's own log keeps the native path, in typed fields: it is the operator's.

**What this breaks.** A document holding an absolute path in a record — every one written before 2026-11-18 that took a path from a client verbatim — now has that record left out of every host's load and refused on its next write; only tests and proofs of concept consume the engine, and none in the tree stores one (the editor's import and `doc.place_asset` store `assets/<stem>/<file>` and the client's relative spelling; `doc_scene_tests`' operator-only case keeps one to show the reading without roots). Such a document is mended by setting the path to its relative or `<root>://` form. An undo of that mend is refused, as is an undo that would bring such a record back from a delete, and so every patch before it is out of undo's reach (a rollback's take-back, which undoes through the same step, can stop there too): that is the rule working, since an undo would put the absolute path back in the document. A ground layer's `height` image was read as written, against the process's directory, until this change; it is resolved from the document as its four sibling images are.

### The one function

**`io::Roots::admit`, in `foundation/io` (`include/foundation/io/roots.h`)**, beside `Vfs` and the native-path operations it builds on: it is file access, it needs the operating system's final-path calls `foundation/io` already wraps, and every module that reads on a client's behalf can reach layer 1 — `domain/protocol` and `domain/assets` (layer 2), `systems/renderer` and `systems/doc_scene` (layer 3), the hosts (layer 4). It is not in `domain/protocol`, because the renderer's scene reader and the glTF importer would then depend on the protocol to read a file.

```cpp
enum class Access : u8 { read, write, make_directory };
// Why a path was refused: logged for the operator, never told to the client.
enum class Refusal : u8 { empty, control, reserved_character, stream, namespace_prefix, unc, device,
                          trailing_dot_or_space, no_base, outside, read_only_root, document,
                          served, final_link, no_dos_name, cannot_resolve };
class Roots {
 public:
  Status add(std::string_view dir, bool writable);          // at start: canonical, logged
  void serve(std::string_view dir);                         // the listener's shell: never written
  void protect(std::string_view document_dir);              // a session made; release() when it closes
  // True with the native path to open — the one the caller opens, never the client's string.
  bool admit(std::string_view path, std::string_view base, Access access, std::string& native,
             Refusal& why) const;
};
```

`domain/protocol` adds the one wrapper every handler calls, `admit_client_path(ctx, field, path, base, access, native, error)` (`include/domain/protocol/paths.h`), which makes the refusal's error and logs it; `Context` holds the host's `io::Roots`, and a dispatcher has no way to be built without one. A reader in a lower layer that resolves paths named inside a file (`renderer::read_scene_file`, `doc_scene`, `assets::load_gltf`, `content_build::read_manifest`) takes a `const io::Roots*` in its options and calls `admit` on every path it opens, reporting a refusal as the missing file it is to the client. **engine-view, engine-content and every tool pass none**: every path they read is their operator's, typed on their own command line, so nothing in them changes. That is not a switch that turns the check off: a protocol host cannot be built without roots, and a reader handed none is never serving a client.

**The rules, in order; the first that refuses ends the call.** The same rules on Windows and Linux except where a step says so, so a test proves a rule on either.

1. **Text.** Valid UTF-8, not empty, no byte below 0x20 and no 0x7F, at most 32,767 UTF-16 units on Windows and `PATH_MAX` bytes on Linux. `\` is a separator on both systems (a Linux file whose name holds a backslash cannot be named; nothing honest does).
2. **Characters Windows reserves**: none of `< > " | ? *`, on both systems.
3. **`:`** only as the second character of an absolute path whose first is an ASCII letter and whose third is a separator (`C:/`). This refuses alternate data streams (`a.png:x`, `a::$DATA`, `dir::$INDEX_ALLOCATION`, which makes a directory) and drive-relative paths (`C:x`, which means "x in drive C's current directory").
4. **Namespaces**: no `\\?\`, `\\.\` or `\??\` prefix, in any mix of separators: they skip Win32's normalization and reach devices.
5. **No network share**: a root on one is refused at start, with a message and exit 2 (a UNC spelling, a mapped network drive, or a directory whose canonical form is UNC), until someone needs one and designs it; so a UNC path and a path on a remote drive are under no root and are refused before step 8 opens anything, since resolving one would make the host connect to the client's server with the operator's credentials ([io](io.md#roots)).
6. **Components**, after `.` components are dropped: none is a device name — compared case-insensitively after trailing dots and spaces and everything from its first dot are removed: `CON`, `PRN`, `AUX`, `NUL`, `COM0`-`COM9`, `LPT0`-`LPT9`, the superscript `COM¹²³` and `LPT¹²³`, `CONIN$`, `CONOUT$`, `CLOCK$` — and none but `..` ends in a dot or a space. Win32 strips trailing dots and spaces, so `a.png.` is `a.png` and whether `.. ` is `..` in the middle of a path depends on the order of its normalization steps; refusing them on both systems means that question never has to be answered, and costs no honest name. Device names are refused on Linux too, so a document written there opens on Windows.
7. **Absolute.** A relative path is joined to the base (above); `..` is then collapsed against the component before it. A `..` that would climb above a volume's root is refused. Collapsing it lexically is safe because of step 11: the host opens the canonical path it checked, so `root/link/../x` is `root/x` both when checked and when opened.
8. **Canonical.** The path is split into its longest prefix that exists and the rest. **Windows**: the prefix is opened with `CreateFileW(FILE_READ_ATTRIBUTES, FILE_SHARE_READ | FILE_SHARE_WRITE | FILE_SHARE_DELETE, OPEN_EXISTING, FILE_FLAG_BACKUP_SEMANTICS)`, which follows symbolic links, junctions and mount points, and named by `GetFinalPathNameByHandleW(FILE_NAME_NORMALIZED | VOLUME_NAME_DOS)`: long names for 8.3 short ones (`PROGRA~1`), the on-disk case, the drive letter; the `\\?\` prefix is removed (`\\?\UNC\` becomes `//`). A prefix whose final path has no DOS name (a volume reached only through a folder mount) is refused. **Linux**: `realpath(3)` of the prefix, which follows every symbolic link. The rest is appended as written: nothing in it exists, so it holds no link and no short name.
9. **Under a root**: the canonical path equals a root or continues it by whole components (`D:/a/b` does not hold `D:/a/bc`). Windows compares case-insensitively, ordinal (`CompareStringOrdinal(..., TRUE)`), because both sides came out of step 8 and a case-sensitive directory under a root is still under it; Linux compares bytes. For **read** any root admits; for **write** and **make_directory** only when the most specific root that holds the path is read-and-write (a read-only root inside a writable one stays read-only), and then not under a protected document's directory outside its `out/`, nor under a served directory.
10. **The last component of a write**: when it exists it must be a regular file — not a directory, a symbolic link, a junction or any other reparse point — and the write goes to a sibling temporary file renamed over it (`write_file_atomic`), so a hard link there is replaced, never written through (the forest's tile sets are hard links to a shared copy). `make_directory` makes each missing component one at a time under the canonical prefix.
11. **The answer** is the canonical path, and the caller opens that string, never the client's.

**What is left to the operator**: between the check and the open the tree can change, but no method makes a link or a junction, so only a process with the operator's own rights can race the check, and such a process could write the file anyway. A hard link the operator made inside a root to a file outside it is a file of the root: a hard link *is* the file, and there is nothing to resolve.

**What a refused call is told: one code and one sentence, the same for refused and missing.** 1003 (`NotFound`) with `data.reason` `"path"` and `data.field` the field, and for a read `"<field>: no file this host may read at '<the client's string>'"`, for a write `"<field>: no place this host may write at '<the client's string>'"`. The sentence repeats only what the client sent, never the canonical form, a link's target or the nearest root, so neither existence, nor a link, nor a device outside the roots is told by the answer. A write the function admitted that then fails on the disk (full, refused by the system) is 1005 with its status, since the place was the client's to name. Inside the roots everything is as today: a file that is there but does not parse says so.

**What is logged for the operator**: no more than the client was told, because engine-host's log ring holds every record and `log.tail` is a read every role may make. A refused path and a path admitted but not there leave one and the same warning, `"a client path was not admitted or is not there"` (category `protocol.paths`, written by `path_not_found`), with the fields `field`, `access` and `path` — the client's spelling when it is root-qualified or relative, `(absolute)` when it names a directory of the host. The refusal's reason and the canonical form are not logged: on Windows the canonical form is the on-disk name of every existing prefix, so with the reason it was an oracle for any file on the disk, its true case, its long name and the target of every link it crossed. A root the host lacks logs the root's name, as the answer does. Each root's directory is printed once at start on the host's own stderr (`describe_host_roots`, `engine-host: root <name> = <dir> (read and write)`, and the directories served), never logged; the start's log line per root names it and its access only. Nothing is rate-limited: a refusal costs the call that made it.

### Questions for the owner

- **May a role ever make the host write outside the document's `out/`?** **Decided by the owner, 2026-11-18: "Only operator folders."** A client makes the host write only inside the document's own `out/` and inside folders the operator named when starting the host (`--root <name>=<dir>:rw`), for every role alike; a role decides which writers it may call, not where they write.
- **May the browser shell name a path at all?** Still a recommendation, not answered: no path of its own. It picks an entry the host listed (a root and a path under it), uses `keep` for pictures and a grant for imports, and its console is treated as any client's. The reason beside it: a path a page sends is a path a page could have been made to send, and a listed entry is already in the portable form, so the shell never handles an absolute path of the machine at all. The other answer, letting it name paths under the roots like any client, costs nothing in the check, but makes the page that carries the operator's cookie the one client whose every path is the operator's.

### What is built, and what is left

**Built** (`io::Roots` in `foundation/io`, [io](io.md#roots); the protocol's door `admit_client_path` in `include/domain/protocol/paths.h`):

- **The roots**: `--root <name>=<dir>[:rw]` on engine-host and engine-editor, forwarded by engine-cli and engine-mcp; `doc` (the `--doc` directory, read) and `out` (its `out/`, read and write, made by the first write under it) by default; every `--mount` a root of its scheme's name; the shell's directory served and never written. `configure_host_roots` sets them and logs one line per root; a root that cannot be one exits 2 naming it. `Context::roots`; **a context with no roots refuses every client path** (fail closed). engine-mcp starts its host with `--root workspace=<workspace>:rw`. engine-cli's `--doc` and `--create` go to the host it starts, which opens the document at start, and engine-cli opens it as `doc://`; the host's own `--create` takes `--name`.

## View policies on captures, reads and review items

**Designed 2026-11-18, not built** (roadmap A26 on C3 and A23; [ADR-0073](../adr/0073-classes-travel-with-derived-data-and-policies-are-the-operators.md), proposed; the whole design and its build rows are [content classes](../content-classes.md)). What this module will own of it:

- **Which policy a call runs under.** One operator file of named policies, capping categories by name, `--view-policies` (once) with `--view-policy` (an unknown name refuses the start) on the host's command line, read once at start. `agent-default` is compiled in, and it is what a host told nothing runs. A credentialed connection runs under its credential's policy or `agent-default`, never the host's (roadmap A4). engine-cli and engine-mcp forward no policy. A call may narrow its policy for itself and never widen it.
- **Kept out of every client's reach, and what that is.** The start refuses, by canonical path, a policies file inside the document or inside any root a client may name (roadmap T174), one reached through a link and one with a second hard link, and checks again at each document opened. No method writes a policy or names its file, and no client-named write lands on a `*.provenance.json`. The roles file has no policy field, because a role says what a caller may change and a policy what it may see. `engine.view_policy`, a read, answers the caller's effective policy, its source (`compiled-in`, `start line`, `credential`) and the file's hash. This is a wall against a client and, for whoever starts a host, an agent included (the owner, 2026-11-18, ADR-0073), the starter's choice on the record: every result names the policy, its source and the file's hash, and a host started wider than `agent-default` says so on stderr and in its start line.
- **Refusals.** 1011 `ContentAboveViewPolicy` names the policy, the category, the level and the cap, never the content. It answers `render.load` of one mesh above the cap; `render.capture` and `render.evaluate` of a scene unless the caller's policy makes the same decision as the scene's for every class it decided, checked before the first frame and again after the last is recorded; `render.compare` of such an image; and `doc.blob` of such a blob. `GET /capture/<id>` answers such a connection 404 and no body, as it answers an id that does not exist.
- **The review item.** Each refusal makes the host raise a `classified content review` for a person through the ledger, attributed to the caller and deduplicated by the subject's identity, the build key and the category, naming the latest version. The item carries numbers and identity: `ReviewSubject` version 2 adds `assets` by portable path. A role marked `human` closes it, as every person's item is closed today.
- **Records.** A placement's class may be raised by any role that may write it. A transaction is refused (1008, `"content class"`) when the composed class of any placement it touches falls, before against after, unless the role is marked `human`: whatever produced it (an apply, an undo, a redo, a merge's result, a rollback, a promotion, a change to the layer stack), a deleted placement counting as all `none`. Reads report each record's effective class and `above_policy`.
