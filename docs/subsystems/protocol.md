# protocol (domain)

**Purpose.** The engine protocol (docs/plan/06-agent-tooling.md §6.2, ADR-0001): JSON-RPC 2.0 dispatch over JSON values, sessions over stored documents, and the day-one method set. Transport-agnostic: `engine-host` feeds it lines from stdin (which is how engine-cli and the MCP bridge, engine-mcp, reach it), the editor will feed it from a socket, tests call it in process. Every method's params and result are schema structs (`schemas/protocol.schema`), so the catalogue agents read (`engine.methods`), the JSON Schema schemac emits, and the C++ handlers agree by construction.

**Model.**
- `Dispatcher` holds `MethodDesc`s (name, doc, params type, result type, handler) sorted by name and turns a request object or batch array into a response value; `dispatch_text` adds parse-error handling and single-line framing. Notifications (no `id`) get no response. Responses carry exactly one of `result` and `error`.
- Handlers are plain functions `bool fn(Context&, const P&, R&, RpcError&)` wrapped by `method<P, R, fn>()`; `method_no_params<R, fn>()` for methods without params. `detail::read_params` turns deserialization problems into InvalidParams with `{path, message}` diagnostics in `error.data`. Command failures inside a transaction are results (`ApplyResult.diagnostics`), not RPC errors.
- `Session` owns one `doc::Document` plus its `DocumentManifest`, and every mutation goes to disk before the response: `apply` commits, drops any redo tail, journals, and saves; `undo`/`redo` move `undo_position` and save. The journal goes first (`DocumentStore::append_journal` with the document, which cuts a dropped redo tail off the file in place and appends, never rewriting it) and the save second, so a host that dies between them leaves the commit as the first patch of the redo tail; the save writes only the files the commit changed and is all or nothing ([doc](doc.md#saving), [ADR-0041](../adr/0041-a-save-is-a-log-then-files-written-in-place.md)). The side files — `leases.json`, `proposals.json`, `proposals/<layer>.base.jsonl` — go through `DocumentStore::write_side_file` and `append_side_file`: replaced atomically and only when their bytes change, and appended to. Both go through one private `commit_commands`, which also lets `merge` commit against a layer that is not the session's edit layer without moving it (the patch names the layer it edited, so undo finds it again). `doc.add_layer` appends and makes the new layer the edit layer by default; with `edit: false` the edit layer stays where it was, in memory and in the saved manifest.
- A layer's storage form is part of the protocol because it is part of the manifest. `doc.add_layer` takes an optional `partition` (`property`, `tile_size`) that stores the layer as tile files instead of one file (`domain/doc/partition.h`, plan 03 §3.7); `doc.set_partition` converts an existing layer between the two forms and rewrites its files, changing no record, so the journal, undo, and redo are untouched. An absent `partition` means one file; a `tile_size` of zero is refused rather than quietly meaning the same thing, so a caller's mistake is not silently accepted. `doc.layers`, `doc.add_layer`, and `doc.set_partition` all return the stack, and each `LayerInfo` reports the form (`partition`, absent for a single file) and the occupied `tiles`.
- `doc.merge` (`MergeParams` → `MergeResult`) is `doc::merge_layers` over three named layers, written into `output_layer` as the diff between what that layer holds and the merged records, applied non-strictly as one transaction: the result reports `applied_ours`, `applied_theirs`, the conflicts with their kind as a string, and the journal index, and the merge undoes like any other patch. A missing `output_layer` is appended to the stack outside the transaction, so undo empties it rather than removing it. Conflicts are a result, not an error; `MergePrefer` (`Ours`, `Theirs`, `Neither`) chooses how they resolve. `SessionManager` opens (or creates) a document directory, returns the existing session for an already-open path, and closes.
- Error codes: standard JSON-RPC negatives; engine codes 1000 SessionNotFound, 1001 DocumentError, 1002 ValidationFailed, 1003 NotFound, 1004 InvalidArgument, 1005 IoError, 1006 Unavailable, 1007 RenderUnavailable ([below](#methods-an-app-registers-and-render)), and plan 06 §6.5's three ([below](#roles-leases-and-proposals)): 1008 Forbidden, 1009 LeaseConflict, 1010 LeaseRequired.

**Methods (day one).** `engine.info`, `engine.methods`; `session.open` (`path`, `create`, `name`), `session.close`, `session.list`, `session.info`; `doc.layers`, `doc.add_layer` (optionally `partition`ed), `doc.set_partition`, `doc.set_edit_layer`, `doc.objects` (filter by `type` or `parent`, `offset`/`limit`), `doc.get`, `doc.apply` (commands + attribution, `atomic`), `doc.undo`, `doc.redo`, `doc.diff`, `doc.merge`, `doc.validate`, `doc.journal`, `doc.save`; `tunables.list`, `tunables.set`; `log.tail`; `schema.types`, `schema.describe`; and plan 06 §6.5's `lease.acquire`, `lease.renew`, `lease.release`, `lease.list`, `lease.require`, `doc.propose_layer`, `doc.promote`, `doc.reject` and `engine.roles` ([below](#roles-leases-and-proposals)). Parameters and results are documented by their schema types in `schemas/protocol.schema` and by `engine.methods` at run time. engine-host adds `render.*`, `engine.ping` ([below](#engineping-liveness)) and the rest of plan 06 §6.9's day-one list — `content.build`, `session.events`, `engine.budgets`, `session.run_headless`, `engine.run_tests` — and `session.materialize` beside them, and the world capability's `session.state_hash`, `session.save_game` and `session.load_game`, below ([The day-one operations](#the-day-one-operations)).

**Invariants (tested).**
- Parse errors, invalid requests, unknown methods, and invalid params produce the standard codes with the request id echoed (null for parse errors); batches return only the responses of requests with ids and nothing for a batch of notifications.
- A rejected atomic transaction changes nothing and reports every command's diagnostic; a non-atomic one commits what succeeded.
- After `session.close`, a new `SessionManager` on the same path sees the same objects, journal, and undo position; undo and redo continue from where the previous process stopped; a new commit after undo drops the redo tail on disk as well as in memory.
- `doc.add_layer` with `edit: false` leaves the edit layer where the caller had it: the next `doc.apply` and a fresh process on the same path both edit that layer, not the new one.
- A layer added with a `partition` is stored as tile files from the first save: objects placed in different tiles land in different files, a later transaction rewrites only the tile it touched, and `doc.set_partition` without one puts the layer back in a single file. What the next process reads through `doc.objects` and `doc.get` is the same either way (`apps/engine_cli/tests`).

**Public API.** `domain/protocol/rpc.h` (`codes`, `make_error`, `Context`, `MethodDesc`, `read_only`, `Dispatcher`, `add_builtin_methods`, `method`, `method_no_params`), `domain/protocol/session.h` (`Session`, `SessionManager`), `domain/protocol/policy.h` (`Policy`, `Caller`, `resolve_caller`, `forbidden`, `Place`, `place_of`, `glob_match`, the tile-range helpers), `domain/protocol/leases.h` (`LeaseTable`, `lease_covers`), `domain/protocol/proposals.h` (`ProposalTable`, `compose_onto`). Types from `schemas/protocol.schema`.

**Depends on.** `base`, `containers`, `ids`, `json`, `schema`, `log`, `time`, `platform`, `tunables`, `io`, `schemas`, `doc`.

**Testing.** `tools/dev.ps1 test -Filter protocol`. Framing and error paths; the method catalogue; the Phase 0 exit criterion end to end over the dispatcher (open, create, apply, objects, get, atomic rejection, undo, redo, redo-tail drop, layers, diff, validate, close, reopen in a fresh manager); a layer added with `edit: false` that leaves the edit layer alone in the session and after reopening; a three-way merge of three override layers with both kinds of conflict, undone and redone, resolved toward theirs into a second layer, and refused for a missing layer, an empty output layer, and an unknown `prefer`; tunables, log tail, and schema discovery, including the default every described field states (a declared default, a value-initialized one, `null` for an optional, an enumerator by name, `[]` for a list); and the day-one operations' types — their declared defaults, the optional fields a result leaves null rather than 0, round trips of a budget, an events page and a run's params through the dispatcher's reader, and an unknown field refused. `tests/policy_tests.cpp` takes plan 06 §6.5 through the dispatcher ([below](#testing-roles-leases-and-proposals)), and `tests/e12_tests.cpp` is experiment E12's driver, a small run of which holds its invariants on every build.

**`gpu.adapters` grew the same additive way.** `engine.gfx.AdapterInfo` is at version 2 with `requirements: DeviceRequirement[]` and `verdict: DeviceVerdict` `@since(2)`, so a client that predates them reads the result it always read, and `DeviceRequirement`, `DeviceClamp`, `DeviceVerdict` and the `RequirementLevel` enum are new types of their own. The answer is the one `Device::create()` would give — the check and the report walk one table in `domain/gfx/requirements.h` ([gfx](gfx.md#what-a-device-has-to-have)) — which is what makes it worth sending back from a machine nobody here can log in to.

**`schema.describe` states every field's default.** Each field of a struct's description carries `default` — the value the field holds in a default-constructed object, written through the type's own JSON writer, so it is exactly what an absent field becomes when the protocol reads params and it is in the form a caller would send (an enumerator by name, `null` for an empty optional, `[]` for an empty list); a transient field has none. schemac writes the IDL's declared defaults into the C++ initializers and nowhere else, which is why the method constructs an object to read them rather than keeping a second table. It exists for clients that generate forms or JSON Schema from the catalogue: the MCP bridge builds every tool's input schema this way ([apps](apps.md#engine-mcp-the-mcp-bridge)) and so copies no default by hand. The field is additive — a reader that did not know it reads the description it always read.

**Not yet.** Long-running operations (06 §6.8), sockets, authentication — which is also why a role is what a call says it is ([below](#roles-leases-and-proposals)) — and streaming of large results. The MCP bridge exists and is a client of this protocol rather than a transport for it: engine-mcp spawns engine-host and speaks these methods over its stdio ([apps](apps.md#engine-mcp-the-mcp-bridge)). Method versioning follows schema versioning: adding a field to a params struct is additive; anything else is a new method name.

## Methods an app registers, and `render.*`

`add_builtin_methods` is not the whole table. An app may add methods of its own, and engine-host does: `render.load`, `render.capture`, `render.benchmark`, `render.compare`, `render.evaluate`, `render.unload` and `render.scenes` ([apps](apps.md), [renderer](renderer.md)) live in `apps/engine_host/render_methods.cpp`, not here, because the renderer is layer `systems` and the protocol is layer `domain` — a method over it cannot be registered from below it.

The registration point is **`Context::app`**, a `void*` the app fills and the methods it registered cast back. It is deliberately untyped and deliberately the only one: a handler is a plain function pointer and cannot capture, a file-scope global would make two hosts in one process impossible, and giving the protocol a typed field for every consumer above it would invert the layering. Nothing in `domain/` reads `app`, and a method that does not know what it points at must not touch it. This is the same shape ADR-0027 asks of a capability: attachment through a registration point, and no edit to the thing being attached to.

**Error code 1007, `RenderUnavailable`**, joins the list: a `render.*` method on a process with no usable GPU — no Vulkan loader or driver, no 64-bit buffer atomics, or no cluster acceleration structures and ray queries when `"raster":"rt"`, an explicit `"shadows":"rt"` or the reference integrator was asked for, in which case the message is the adapter's own verdict sentence naming the missing extension ([renderer](renderer.md#the-offscreen-contract)). It is a code of its own rather than 1006 `Unavailable` so that a client can tell "this machine cannot render" from "this host has no log ring" and from 1004 "you asked for something wrong". That distinction is what lets one end-to-end suite run on the hosted CI runners and on the GPU machines: `apps/engine_cli/tests/render_tests.cpp` skips on 1007 exactly as engine-view's suite skips on exit 3, and asserts on everything else.

The seven methods are schema-typed like the rest (`RenderLoadParams` → `RenderSceneInfo`, `RenderCaptureParams` → `RenderCaptureResult`, `RenderBenchmarkParams` → `RenderBenchmarkResult`, `RenderCompareParams` → `RenderCompareResult`, `RenderEvaluateParams` → `RenderEvaluateResult`, `RenderUnloadParams` → `RenderUnloadResult`, and `render.scenes`, which takes no params, → `RenderScenesResult` of `RenderLoadedScene`s, with `RenderSettings`, `RenderCamera`, `RenderOrbit`, `RenderReference`, `RenderMetrics`, `RenderStats`, `RenderGpuMs`, and `RenderStreamStats` shared between them), so `engine.methods` lists them and `schema.describe` explains them with no special case anywhere. Their string fields — `raster`, `shadows`, `view`, `deform`, `weights`, `integrator` — are parsed by the same functions engine-view's flags are, so a spelling can never mean one thing on the command line and another over the protocol.

**`render.evaluate` is [04 §4.8](../plan/04-renderer.md#48-reference-renderer-and-objective-optimization)'s loop as one call**, which is what [06 §6.9](../plan/06-agent-tooling.md#69-day-one-operations) means by exposing it to agents as a single tool. Everything it does can be done with `render.capture` twice and `render.compare` once; the point is that a proposal is accepted or rejected on **one** answer taken under one camera, one frame number and one set of lights, rather than on three calls a script has to keep in step. It renders the real-time picture, renders the reference of the same frame, optionally renders the reference again at a single bounce, compares, writes `<name>.realtime.png`, `<name>.reference.png`, `<name>.flip.png` and (with `direct_only`) `<name>.reference_direct.png` and `<name>.flip_direct.png`, and returns both sets of metrics, the real-time statistics, the times and the machine state. The `direct` metrics are there because the difference between them and `full` is **the indirect light the real-time path does not have**, which is what makes a per-scene FLIP threshold explicable rather than arbitrary.

Two schema fields are additive, as the versioning rule requires: `RenderCaptureParams` gained `integrator` (`"realtime"`, the default and what every earlier caller got, or `"reference"`) and a `reference` block at version 2, and `RenderCaptureResult` gained `integrator`, `samples`, `trace_ms` and `seconds`. A reference capture has **only a color channel** — a path tracer writes no visibility buffer, so asking it for `ids`, `depth` or `normals` is 1004 with a message rather than a buffer of nothing, the same rule `"raster":"direct"` follows. Both the reference integrator and `render.evaluate` answer 1007 on a device without cluster acceleration structures, or with settings that build none (`"shadows":"rt"` or `"raster":"rt"` is what turns the chain on), so the end-to-end suite skips on them exactly as it skips on a machine with no GPU at all.

**Geometry streaming went the same way** ([04 §4.9](../plan/04-renderer.md#49-streaming-and-residency), [apps](apps.md#streaming-pages-at-run-time---stream)): `RenderSettings` is at version 3 with `stream`, `page_budget_mib` and `upload_budget_kib` `@since(3)`; `RenderLoadParams` is at version 3, with `page_bytes` `@since(2)` and `procedural` `@since(3)` (which procedural scene an empty `mesh` and `scene` build — `""`/`"heightfield"`, or `"shredded-atlas"`, the UV-atlas LOD fixture the scene corpus draws; an unknown name is an invalid-argument error rather than a silent fall back to the terrain, because a corpus scene that quietly got the wrong mesh would guard nothing); `RenderStats` is at version 4 with a `stream: RenderStreamStats` block `@since(4)`; and `RenderStreamStats` is the whole of `renderer::StreamStats`, field for field, under the key names engine-view's `streaming` summary object already uses, so one reader serves both hosts. Every one of them defaults to what a caller before them got — no streaming, no page table, and a `stream` block whose `pages_total` is 0.

Three things about that set are worth the sentence they cost, because each one is a question a reader will otherwise have to answer by reading code.

**The units differ on purpose.** The protocol says `page_budget_mib` and `upload_budget_kib`; `renderer::RenderSettings` says `page_budget_bytes` and `upload_budget_bytes`. The wire is where a *person or an agent chooses a number*, and the two numbers are chosen at different scales — a residency budget is a fraction of a scene and an upload budget is a fraction of a frame — which is why `engine-view --page-budget` takes MiB and `--upload-budget` takes KiB and why the protocol spells them the same way rather than inventing a third spelling. The renderer sizes buffers, so it counts bytes. The conversion is four lines in `read_settings` (`apps/engine_host/render_methods.cpp`), which is the one place the wire meets the module, and `systems/renderer/settings.h` is therefore never in the position of having to say what unit its caller was thinking in. The end-to-end case pins it by asking for 1 MiB against a scene of 3.8 MB of pages and checking that `budget_bytes` comes back as 1048576 rather than clamped.

**`page_bytes` is a load parameter, not a render setting.** It is `SceneDesc::page_bytes`, and it sits on `RenderLoadParams` because laying a mesh out in pages **renumbers its clusters** — it changes what loading *produces*, not how a frame is drawn. A host that keeps a `SceneData` across calls (this one does; that is what a scene id is for) cannot have it as a setting, because a settings change rebuilds only the GPU buffers and the pipelines from the `SceneData` that is already there. It applies to the procedural heightfield alone, for the reason `scene.h` gives: a glTF's and a container's layout is fixed at the default target because that target is part of `geometry::cluster_cache_key`, and two targets would be two different containers. `settings.stream` on `render.load` is the separate question of whether the page table is kept at all; asking a later call to stream a scene that was loaded without one turns streaming off with a log line rather than failing, which is `resolve_settings`' rule and not a protocol special case.

**Shadow casters went the same way** (2026-09-24, [renderer](renderer.md#shadows)). `RenderSettings` is at version 4 with `shadow_casters` `@since(4)`. It defaults to `true`, the renderer's own default, and `false` is `engine-view --no-shadow-casters`. `RenderStats` is at version 5 and `RenderViewStats` at version 2, each with a `shadow_casters` count, which is not part of `visible_pairs` because nothing draws a caster. `view` also accepts `"shadow"`, the resolve's shadow view, through the same `parse_view_mode` engine-view's flag uses. (And `"albedo"`, the textured base colour unlit, since 2026-09-24: the same parser, so no schema change; [renderer](renderer.md#built-textures).) Every one of them reads as before for a caller that does not send it. The one behaviour change is the default: a scene loaded with traced shadows now builds its casters, and a client that wants the old frames asks for `"shadow_casters": false`.

**The ray tracing chain's memory went the same way** (2026-09-24, [renderer](renderer.md#the-ray-tracing-chains-memory)). `RenderSettings` is at version 5 with `rt_budget_mib` `@since(5)`, the most device memory the per-frame cluster acceleration structures may take (0 is the `renderer.rt.budget_mib` tunable, 1024); it is `engine-view --rt-budget-mib`. `RenderStats` is at version 7 with an `rt: RenderRtStats` block `@since(7)` — the capacity now and at its peak, the budget as a capacity, the scene's union, the bytes now and at their peak, the last frame's built and wanted counts, the resizes, and the frames that dropped instances' structures — under the key names engine-view's `rt` summary object uses. The flythrough summary (`engine.scene.FlythroughSummary`, version 2) carries the same totals in its own `rt` block with per-frame percentiles of what was built and wanted, `FrameRecord` (version 2) carries `rt_built`, `rt_wanted` and `rt_capacity` and streaming's per-frame state, and `PassMs`/`PassPercentiles` (version 2) add the bottom-level build `blas` beside `clas`. A caller that sends none of it gets the renderer's defaults and reads the old fields unchanged. `RenderStreamStats` is at version 2 with `pool_pages` and `steals` `@since(2)` ([renderer](renderer.md#admission-never-waits-on-a-read-it-cannot-start)).
**The cascaded shadow maps added a spelling, three settings and four numbers** (2026-09-24, [renderer](renderer.md#cascaded-shadow-maps); it landed after the chain's sizing above, so a struct both changed is one version past that one's). `RenderSettings` is at version 6: `shadows` also accepts `"csm"` (parsed by the same `parse_shadow_mode` engine-view's flag uses), and `shadow_cascades` (1..4, default 4), `shadow_map` (64..4096 texels, default 2048) and `shadow_distance` (0: the far side of the scene's bounds) are `@since(6)`, validated in `read_settings` like the view fields. `RenderGpuMs` is at version 2 with `shadow` and `shadow_cull` `@since(2)`, and `RenderStats` at version 8 with `shadow_pairs` and `shadow_fallback` `@since(8)`; the results' `shadows` string says `"csm"` when that is what ran. On the scene side (`schemas/scene.schema`), `PassMs`, `FrameRecord`, `PassPercentiles` and `FlythroughSummary` are at version 3 with the same numbers per flythrough frame and over the path. Every one of them reads as before for a caller that does not send or read it. **The one behaviour change is the default on a device that cannot trace**: `"auto"` there used to draw no shadows and now draws the maps, so a client on the TITAN Xp that wants the old frames asks for `"shadows":"off"`.

**Texture sharing added a setting and two counts** (2026-09-25, [renderer](renderer.md#one-upload-per-distinct-image)). `RenderSettings` is at version 7 with `share_textures` `@since(7)`: `true`, the renderer's default, uploads one texture per distinct image content and lets every mesh that samples it share it; `false` is `engine-view --no-texture-sharing`, every mesh its own copy, as before, to measure against. `RenderLoadedScene` and `RenderUnloadResult` are at version 2 with `textures_shared` and `texture_bytes_saved` `@since(2)` — the sampled images that took another mesh's texture, and the bytes their own copies would have taken — and `textures` beside them now counts distinct textures. On the scene side `FlythroughSummary` is at version 6 with a `textures: FlythroughTextures` block `@since(6)`, the same numbers engine-view's summary line prints. A caller that sends none of it reads what it always read, and draws the same picture with less device memory.

**The vertex path's indexed draw added two counts** (2026-09-24, [renderer](renderer.md#statistics)). `RenderStats` is at version 6 with `triangles_hw` and `vertex_fallback` `@since(6)`: the triangles the baseline tier's indexed draw drew in the last frame, and the clusters its index budget sent to the capacity draw instead. Both are 0 on every other path and for a caller that predates them, and nothing about a request changed — the draw is chosen by the device's `geometryShader` and `fullDrawIndexUint32` features, not by a setting. `RenderViewStats` did not grow: the counts are summed over the views, because the question a caller asks of them is whether the frame fell back at all, and `renderer::ViewStats` keeps the split for a caller in-process.

**`render.capture` needed no field.** It has no `settings` block at all — it renders with the settings the scene was loaded with (`scene->requested`) — so it inherits streaming from `render.load` and adding a `stream` field there would have been a second way to say something the scene already says, and a way that could contradict it. `RenderBenchmarkParams` has had an optional `settings: RenderSettings?` since version 1, so it gets the three new fields with no change of its own, and a per-call block that turns streaming off rebuilds the GPU scene whole exactly as any other settings change does. That is what the end-to-end case asserts second, because a `pages_total` of 0 from a scene that has a page table is the only evidence that the additive field travelled all the way into the renderer rather than being decoded into a struct nobody reads.

**Not yet: the container-backed page source.** Over the protocol a streamed page's payload always comes out of host memory — `stats.stream.source` is `"host"` — where engine-view's `--page-source file` can read it back out of the meshes' `.clusters` containers instead. The blocker is not plumbing. `renderer::attach_page_source` **releases the merged host streams** as the other half of what it does, which is the whole point of it, and those streams are exactly what `RenderHost::ensure_renderer` rebuilds a `GpuScene` from when a later call changes the settings. engine-view may release them because it builds its scene once and never again; a host whose `render.benchmark` may be handed `{"stream":false}` for a scene loaded with `{"stream":true}` may not. Attaching one means either refusing that rebuild or re-opening the source against each new `GpuScene`, and neither is worth building untested — every scene this host can construct without a content fixture is the procedural heightfield, which has no container behind it and would be refused a file source anyway. When it is done, `source`, `file_reads`, `file_bytes` and `host_bytes_freed` are already in the result waiting for it.

**`render.benchmark` flies a camera path** (`RenderBenchmarkParams` version 2, `RenderBenchmarkResult` version 3). A `camera_path` names an `engine.scene.CameraPath` file, read against the loaded scene's terrain, and the run becomes a flythrough: `repeats` flights of the path at its own frame count (or `path_frames`), each after `warmup` frames and `warmup_seconds` at its first camera, and the result gains `flythrough`, the `engine.scene.FlythroughSummary` `engine-view --benchmark` ends its `.jsonl` with — per-pass percentiles over the path, the hashes that name what was measured, and the machine state. Both hosts fly it through `renderer::fly_camera_path`, so the numbers are the same numbers; `frames` is ignored when a path is given, because a path says how long it is. `RenderLoadParams` version 4 adds `overlay`, the local manifest that replaces a scene file's meshes by content hash ([renderer](renderer.md#scenes-camera-paths-and-flythroughs), [apps](apps.md#flythroughs)). The schema types come from `schemas/scene.schema`, which `protocol.schema` imports, so `schema.describe` explains the summary as it explains any result. `FlythroughSummary` went to version 4 on 2026-09-24 with `cpu_ms` and `frame_ms` percentiles (the CPU's milliseconds per frame and the wall time between frames, which `fly_camera_path` now measures), `ticks` and `interactive` (engine-view's interactive sessions; zero and null here), all `@since(4)` with defaults, so a client that read version 3 reads the same fields ([renderer](renderer.md#scenes-camera-paths-and-flythroughs)).

**A scene id is the host process's, not a document session's.** `render.load` returns `"scene1"`, `"scene2"`, … and the host holds the loaded mesh, the GPU buffers, and the pipelines behind it until **`render.unload`** releases it or the host exits. It is not part of `session.*`, because a rendered scene has no document behind it yet; when it does (a document *is* the scene), the id becomes a property of the session and this pairing goes away.

**What belongs to a scene, and what to a session.** A scene is everything `apps/engine_host`'s `RenderHost::Scene` holds: the loaded `SceneData` (clusters, the LOD graph, instances, materials — the host arrays), and once a capture, benchmark or evaluate has drawn it, the `GpuScene` (geometry buffers, textures, acceleration structures), the `SceneRenderer` (pipelines, screen-sized targets) and, after a reference render, the `ReferenceRenderer`. A session is a document: its layers, journal and undo position, all on disk after every commit. The two never own each other, so **closing a session unloads nothing, and unloading a scene closes nothing**: `render.load` names no session, the same loaded scene serves whichever documents a client is working on, and a scene built from a document does not exist yet. Tying them now would mean inventing an owner — and a `session.close` that quietly freed GPU state another client was measuring. What the host *does* own is the device, which stays open when the last scene goes, because it belongs to no scene and the next load would only open it again.

**`render.unload`** (`RenderUnloadParams {scene}` → `RenderUnloadResult`) takes the scene out of the host's list and lets it go through the renderer's own teardown — the reference path tracer first (it holds the renderer and the GPU scene), then the renderer (whose destructor waits for the device to finish the frames it submitted), then the GPU scene, then the host arrays — which is the same order the host's destructor always used, now one function (`RenderHost::release`). There is no other cache to clear: `engine.budgets` reads the same list, and the derived-data cache is content-addressed files that belong to no scene. The result says what went: the counts, whether there was GPU state and a reference renderer to release, the textures and their bytes, the engine allocator's heap before and after (the host arrays), and the device memory this process used before and after as the driver reports it (VK_EXT_memory_budget, null without it). **The driver's figure counts the allocator's blocks, not its allocations**, so it moves only when whole blocks come or go: a scene small enough to fit in blocks an earlier scene opened leaves it where it was on load and on unload, and a large one — the end-to-end case draws a heightfield at 7680×4320, whose screen-sized targets are allocations of their own — takes it from 137.7 MB to 849.4 MB and unload brings it back to 139.5 MB, the same figure after every further cycle, on the RTX 5090. **Ids are never reused**, so an unloaded id stays dead: every render method given it answers 1003 NotFound — the code a missing scene has always had, so no client needs a new one — with a message that says it was unloaded (`no scene scene3: it was unloaded; render.load it again`), where an id that never existed gets only `no scene scene9`.

**`render.scenes`** (no params → `RenderScenesResult`) lists what the host holds, in load order: each scene's id, what it was loaded from (`kind` `mesh`, `scene` or `procedural`, and the path or the procedural scene with its grid), its counts, whether its GPU state is built with the frame size and resolved raster and shadow modes it was last built for, whether a reference renderer is kept, and its texture and ray tracing bytes with the images that shared another mesh's texture and what that saved; then the adapter and the process's device memory used and available, and the engine allocator's heap. It **opens nothing**: before any render call the adapter is empty and the memory figures are null, not zero. A client that can unload has to be able to see what is loaded, and before this the only way to learn which scenes a long-lived host held was to remember every `render.load` it had ever sent.

### `engine.ping`: liveness

`engine.ping` (no params → `PingResult {pid, uptime_seconds}`) answers that the host is alive and reading requests. It reads a clock and nothing else — no session, no device, no lock — so asking costs nothing and can never itself be the call that hangs. It is registered by engine-host's `main.cpp`, not here and not beside `render.*`: liveness is a question about the process, and every method list the host serves goes through its one dispatch loop. **There is no generation** in the answer, because a host cannot know how many hosts came before it; the client that starts hosts counts them (engine-mcp's `host_info` reports its count) and compares `pid` to know whether it is still talking to the same process. What a client does with a host that does *not* answer is the client's: engine-mcp gives every call a deadline and replaces the host when one runs out ([apps](apps.md#engine-mcp-the-mcp-bridge), "Deadlines"). engine-host's `--debug-hang <method>` is the test hook that makes such a host on purpose ([apps](apps.md)).

All fifteen types were new, so nothing existing moved a version; they are schema types in `schemas/protocol.schema` like every other method's, `engine.methods` lists them, `schema.describe` explains them, and the MCP bridge's `list_schema` shows them with no change anywhere. The bridge's curated tools are a table, though, so reaching them as MCP tools took five rows in `apps/mcp_bridge/tools.cpp` ([apps](apps.md#the-tools)), and `session.materialize` a sixth (`materialize`).

**`Context::app` is now the host's whole state.** It is one pointer, deliberately ([above](#methods-an-app-registers-and-render)), so engine-host points it at a `host::HostState` (`apps/engine_host/host_state.h`) holding the `RenderHost` and an `OpsHost` — the sessions' runtime worlds — and `render.*`'s handlers take `.render` out of it. An app with several families of methods gathers their state behind the one pointer rather than asking the protocol for a second.

**A capability this build left out is 1006 `Unavailable`, with a message naming the switch** — `session.events` with `source: "store"` or an explicit `store` on a host without the store capability, `engine.run_tests` with a `tissue` file on a host without the tissue capability. It is not a code of its own, unlike 1007: to a client it means exactly what 1006 already says, "this host does not offer that service", and the bridge's hint for 1006 already reads that way. A method that merely reports less without a capability says so in its result instead: `session.events`' `store_status` is `"not built"`, `engine.budgets` lists no `audio.*` budgets without audio, and `session.run_headless` runs the scheduler alone and its report says why nothing materialized (below). None of the five asserts on input; every refusal is 1004 with a sentence, and a missing session is 1000.

**`content.build`** is `engine-content build` and `build-all` in the host's process, through `domain/content_build` ([content_build](content_build.md)) — the same code, so the same bytes, cache keys and skip. Give `source` (with `output`, or `cache: true` for the derived-data cache entry the source and the options address; both at once is refused, as engine-content refuses `--cache` with an output file) or `manifest`, not both. `options` are `engine-content build`'s flags as a `ContentBuildOptions`, whose declared defaults are the build's own (the module's test holds them together), and they are the defaults of a manifest's entries, which override `max_triangles`, `max_vertices`, `page_bytes`, `weld` and `atlas` as `build-all` lets them. `ddc` empty is `<repo>/ddc` found above the host executable; `jobs` sizes a job system made for the call — one mesh's primitives are its parallelism, as in `build`, and a manifest's meshes are, as in `build-all`. **An output that already records this source's hash and this build key is skipped**, for a single source as for a manifest — `build-all`'s rule, where `engine-content build` always rebuilds — and `force` rebuilds it. Each `ContentBuildOutput` is a `build-all` line: `status` (`built`, `skipped`, `failed` with `rule` and `error`), path, the identity, bytes, milliseconds, the counts, the validation warnings (`path` is the rule id), `repairs` and `atlas` exactly as engine-content's JSON line has them, `textures`, its share of the texture step, and — with `stats` (the default) — `stats`, the object `engine-content stats` prints for the container. **The texture step runs as engine-content runs it**: when the call has a derived-data root — `cache`, or a named `ddc` — every image the meshes sample is built into `<ddc>/textures/<key>.tex` ([texture](texture.md)) after the containers settle, in manifest and then image order, a texture two meshes share built once, a skipped mesh's textures checked from its container; `textures: false` is `--no-textures`, and the result's `textures` has the totals. A texture that fails is counted there and logged, and does not fail the call, where it makes engine-content exit 1: a protocol result says what happened and leaves the verdict to the caller. A failed entry is a result, not an error, and does not stop the others; an unreadable or malformed manifest is 1005 or 1004 before anything is built.

**`session.events`** reads what has happened to a document, a page at a time. `source` is `"journal"` — the document's committed patches, each an event of kind `"commit"` with its `sequence` (the patch index), `actor`, the whole `attribution`, the `layer`, the command count and `applied` (false in the redo tail) — `"store"`, or empty for both, the journal's first. **The store half is the persistent world's event log** ([store](store.md), [03 §3.5](../plan/03-data-model.md#35-persistent-world-state)) **when the host has the store capability and the document has one**: a document "has one" when its directory holds `world.db`, or `store` names another file. That convention is this method's, because nothing else yet ties a save to a document; it is the smallest one that keeps the two side by side on disk, and the parameter is there so a save kept elsewhere can be read. The log is opened read-only (`read_only`, no journal-mode pragma), and its events come in `(tick, tile, sequence)` order through `store::EventLog::scan` — tick first, because a log is appended in tick order, so a cursor that stopped at an event finds everything appended since after it; the per-tile sequence alone cannot say "after this" for the whole log. A store event carries its `tick`, `game_time_us`, `tile`, `sequence`, `kind` (the schema type id in decimal), `actor` (the origin: deterministic, player, agent, llm or debug), `subject`, `cause`, `depth` and `payload_bytes`; the payload itself is schema-typed bytes the store does not interpret yet, so it is not returned. `since` is where a read with no cursor starts (the journal's first patch index; the log's first tick), `kind` and `actor` filter, `limit` is 1..10000, and `next` is an opaque cursor (`j=<index>;s=<tick>:<tile>:<sequence>`) that moves only past what was returned or filtered out — so it is also what to poll with, and `more` says a matching event was left for the next page. One caveat is the journal's own: a commit after an undo replaces the redo tail at the same indices, so after an undo a poller reads again from `since`.

**`engine.budgets`** names every budget the engine knows today and what uses it, so a client learns what a budget is called before it is exceeded ([ADR-0017](../adr/0017-no-hidden-limits.md)). Each `Budget` is `name`, `doc`, `limit`, `used`, `peak`, `unit`, `source` and `key`, and a `scope`:

| Name | Scope | Limit comes from | Used |
|---|---|---|---|
| `renderer.deform_pool` | process; each loaded scene | `k_default_deform_pool_kib` (8 MiB), a scene's `GpuScene::deform_pool_bytes()` | the last frame's deformed vertices × 12 bytes, and the peak |
| `renderer.page_budget` | process; each streamed scene | `settings.page_budget_mib` (no limit by default: every page) | the resident page bytes |
| `renderer.upload_budget` | process; each streamed scene | `k_default_upload_budget` (256 KiB a frame), or the setting | not tracked per frame |
| `renderer.rt` | process; each scene | the `renderer.rt.budget_mib` tunable (1024), or `settings.rt_budget_mib` | the per-frame structures' bytes, and their peak |
| `audio.clips`, `audio.voices` | process (with audio); each session's runtime world | the `audio.clip_budget_mb` and `audio.voices` tunables, a world's clip store and mixer | resident clip bytes, live voices |
| `memory.allocations` | process | none: a counter | `mem::allocation_counter()` |
| `memory.heap` | process | none | `mem::total_stats()`, with the peak |
| `gpu.memory` | each adapter | the device-local heaps, or VK_EXT_memory_budget's budget on the device a render call opened | that device's `used_bytes`; unknown otherwise |

**Null is not zero**: a `limit` of null is a quantity counted but not bounded (the allocation counter, whose rule — no allocations in a steady-state frame — is measured where a frame loop runs, not in a host between requests), and a `used` of null is a budget nothing in this host is using yet. The process rows are the defaults a scene starts from; a scene's rows are the buffers it was built with and what its last frames used. **Asking opens nothing**: the adapters are enumerated without a device, and only a device a `render.*` call already opened answers the memory-budget question. `scope` filters by prefix (`"process"`, `"scene"`, `"session"`, `"adapter"`). The names are stable; the end-to-end case pins them and their order.


### `session.run_headless`: the materialized world

`session.run_headless` materializes **the session's document** into **the session's runtime world** and steps it at the fixed step, 60 Hz and 16,667 µs a tick, with no rendering ([06 §6.11](../plan/06-agent-tooling.md#611-automated-playtesting)'s headless `sim` mode): `seconds` of game time rounded to whole ticks (0.5 s is 30), at most 3,600, or until `until` holds, with `seconds` as the most it may run. The world is made by the first call on a session, kept by the host while it runs — so a second call continues from the tick the first stopped at, and a fresh engine-cli call starts a fresh one — and dropped once its session is closed.

**Until 2026-09-24 this stepped a world the document did not populate**, and the page said so in four parts: no mapping from a record's type to the components it becomes, no driver walking a document's records through the materialization hooks, the executor decision open, and no write-back. Each now exists, and each is written up where it lives:

1. **The mapping is data**: a `materialize` declaration in the IDL beside the record type — which components, which property fills which field, unit conversions where both sides declare `@unit`, what the parent becomes, which fields the world may write back — compiled by schemac into a table (`schema::MaterializeRegistry`) the runtime reads with no per-type code ([schema](schema.md#materialization-type-mapping-as-data), [schemas/README.md](../../schemas/README.md#materialize-what-a-record-becomes)). A record type with no declaration stays document-only, by design, and is counted.
2. **The driver** walks the document's live records through its composed index into the scheduler's hooks table, parents before children and then by id, the first call in full and later ones through the document's change feed so an unchanged record costs nothing ([sim](sim.md#the-driver-a-document-through-the-hooks)); the entity store's hook creates each entity keyed by its record's `Id128`, writes its fields and makes the document's parent its `ChildOf` ([ecs](ecs.md#materialization-the-entity-stores-hook)).
3. **One executor**: the engine's scheduler owns the tick and runs flecs' systems inside its phases ([ADR-0038](../adr/0038-the-scheduler-owns-the-tick.md), proposed; `executor` in the result says `"scheduler"`).
4. **Write-back**: at `Persist`, every `write_back_every` ticks (default 60, one game second) and once more when the call returns, what systems changed in the writable fields is committed to the session as one transaction attributed to `system` — so `session.events` shows it as a commit whose actor is `system` — and, when the document keeps a `world.db`, logged as one `engine.world.WriteBack` event per record, origin `deterministic` ([sim](sim.md#write-back), [store](store.md#write-back-events), [doc](doc.md)). Nothing else writes the document from the world.

**Every call materializes first**: the whole document on the first call, and what changed since on every later one — so an agent's `doc.apply` between two calls reaches the world on the next. The result carries that pass as `materialize` (a `MaterializeResult`, below).

**What world the host builds.** With the ECS capability: `sim::SimScheduler`, a flecs world (`ecs::SimWorld`) whose systems the scheduler runs, the entity store's hook first in the hooks table, the engine's world components (`engine.world.Transform`) and every ticking capability the host links — `systems/kinematics` (so `engine.kinematics.Mover` records move), `systems/animation` (over an empty clip library, its hooks after the entity store's) and `systems/audio_system` (over a mixer on the null backend; the host pulls zero frames after each tick so the commands it queues are applied and the ring never fills). Records materialize at **LOD0**: a headless run has no observer to promote from. Without the ECS capability it is the scheduler alone — the fixed step, the tick and the game clock — and a driver with no target, which materializes nothing and says why in its report (`no entity store`); `world` says which.

**The result.** The ticks this call ran, the game seconds they advanced, the wall milliseconds, the predicate's value when the call returned (null without `until`; read after the final write-back, so a document term can turn true on it with the time already out — `stopped` says which ended the loop), the world's own tick and game time, its kind (`"ecs"` or `"scheduler"`), `executor`, the systems it ticks (the flecs systems in registration order, then the scheduler's own table: `sim.write_back`), `entities` (entities with a persistent identity), `materialized` (the entities the driver holds from the document), `materialize` (this call's pass), and `write_backs`/`written_fields` (the commits this call made and the fields they wrote). `RunHeadlessParams` and `RunHeadlessResult` are at version 2; `write_back_every`, `executor`, `materialize`, `write_backs` and `written_fields` are `@since(2)` with defaults, so a client that read version 1 reads what it always read — except that `materialized` is no longer 0 by construction.

**The predicate** reads the document and the live world. `{"object": <id>, "property": <name>, <test>}` is a live document object's composed property; `{"object": <id>, "component": <type>, "field": <name>, <test>}` is a field of the live entity that object materialized into, by the component's qualified name (read through `ecs::component_json`, so the host names no flecs type); `<test>` is `"equals": <value>` (compared as JSON, numbers by value), `"at_least": <number>` or `"at_most": <number>`, and a name may end in `[i]` to take one element of an array — `"position[0]"`. With them `{"object": <id>, "exists": true|false}`, the run's own clock `{"ticks_at_least": n}` and `{"seconds_at_least": s}` (counted in this call's fixed steps), and `all`/`any`/`not` over them. A document term now changes during a run, because write-back writes the document: at the default cadence once a game second, and every tick with `"write_back_every": 1`. A malformed predicate — an unknown term, a key a term does not take, an id that is not 32 hex digits, a term with no test or two, a bound that is not a number, nesting past 32 or more than 1,024 terms — is 1004 naming the path (`until.all[1].object`).

**Streamed tile by tile (`stream`, version 3).** With `stream` — a `HeadlessWorld` — the call does not materialize the whole document: it keeps a **tile ring** round the observers it declares ([world](world.md)) and materializes the document's partitioned layers a tile at a time as the ring takes tiles in, through the same driver (`sim::Materializer`'s tile passes, [sim](sim.md#the-driver-a-document-through-the-hooks)). Each observer is a position, a velocity in metres per game second applied every tick, and a weight; the ring's `tile_size` must be the partitioned layers' own (on another grid the document consumer refuses every tile, counted in `refused` with one warning in the log, since one ring tile would then name parts of up to four of the layer's), `rings` are the radii in tiles innermost first (empty: the capability's 1.5, 8 and 24), `hysteresis` is the ring's, and `simulated` says how many rings, innermost first, are materialized and reconciled. What no layer tiles — an untiled layer's records — is materialized whole first, as a streamed game's global records would be. The ring updates once before the first tick with no budget, so the call starts from the whole ring, and then once between every two ticks at the ring's budget (8 activations and 16 deactivations an update by default, the `world.ring.*` tunables), so an observer that outruns the budget fills in over the next ticks rather than stalling one. **With the store capability and `store` (the default)**, each tile is reconciled from the document's `world.db` (created beside it when absent) when it comes in — `SimScheduler::reconcile_tile`, step 1 of [05 §5.5](../plan/05-simulation.md#55-reconciliation-when-a-tile-activates) — and its projections and snapshot are written when it goes, so a tile that comes back reads what it left ([store](store.md)). The ring and its store outlive the call, as the runtime world does, and take the first call's parameters; a later call's observers move it. The result's `streamed` (a `HeadlessWorldResult`) is the call's share: updates and the events by kind, the active tiles after the call in tile order with their rings, the tiles the document consumer materialized and let go with the entities it created and dematerialized (and, since `HeadlessWorldResult` version 2, `arrived`: how many of those created were brought in between passes because a capability's own rule put them in a live tile — the npc capability's schedule index, [npc](npc.md#the-schedule-index); a field `@since(2)`, so a client that read version 1 reads what it always read), the store consumer's reconciled, known, summarized, read-back and written tiles, the ring update's median and worst microseconds and each consumer's milliseconds, and whether the store was kept. A host without the world capability answers a call with `stream` 1006 `Unavailable`, naming `ENGINE_WITH_WORLD`. Both types are new and `@since(3)`, so a client that read version 2 reads what it always read. **The method is still a write**: it was one before (it commits write-back to the document) and it is not registered `read_only`, so a role that lists it gets the stream with it and one that does not is refused, as before ([Roles, leases and proposals](#roles-leases-and-proposals)). The edit that added it is confined to `apps/engine_host/ops_methods.cpp` and the schema; `apps/engine_cli/tests/ops_tests.cpp`'s case "run_headless streams a partitioned document tile by tile round its observers" drives it end to end — a partitioned document of three places (one in the origin's tile, one in the tile east of it, one two kilometres away) under rings of 1.5 and 3 tiles: the four inner tiles materialized and reconciled on the first call with one entity made, the observer moved two kilometres by the next call so the origin's tiles are let go and written and the far place's come in, then walking back at 600 m/s with the budget spreading the tiles over the ticks and the origin's tiles reconciled from what the store kept of them; and rings that do not grow outward refused with a sentence.

**Continuing, and the player (`HeadlessWorld` version 2).** A call that **declares observers** puts them where it says and fills the ring round them with no budget, as before — the first call, or a jump. A call that **declares none** — or names no `stream` at all, on a world that is already streamed — **continues**: the observers go on from where they are and nothing is filled, so the call's `updates` is its ticks, and a run split over calls, or over a save and a load, is the run that never stopped ([world](world.md#save-and-load)). Before version 2 a call on a streamed world with no `stream` materialized the whole document beside the ring, and one with an empty `observers` list emptied the ring; neither was relied on. `player` (a `HeadlessPlayer`, `@since(2)`) makes one of the observers the player: `log` is an input log as `input::InputLog` writes it, its ticks the world's, `map` the action map it was recorded against as JSON (a map whose hash is not the log's is 1004 naming both), `action` an `Axis2` of the map (default `move`), `speed` metres per game second at full deflection, `observer` which one it steers. Each tick the observer moves at the action's value times the speed — x along world x, y forward along −z — instead of at its velocity ([world](world.md#the-player)). The input state is the fold of the log up to the world's tick, so a log handed to a world at tick K catches up first; named again on a later call, a log replaces the one the world has, and not named, the world keeps its own.

### `session.save_game`, `session.load_game`, `session.state_hash`

[03 §3.5](../plan/03-data-model.md#35-persistent-world-state)'s save game and [05 §5.10](../plan/05-simulation.md#510-determinism-and-replay)'s replay assertion, as three methods of the world capability ([world](world.md#save-and-load), [ADR-0042](../adr/0042-a-save-is-the-store-the-document-and-the-drivers.md)); a host without it answers each 1006 naming `ENGINE_WITH_WORLD`.

**`session.state_hash`** (`StateHashParams` → `StateHashResult`) is the persistent-state hash of the session's world ([world](world.md#the-persistent-state-hash)): the clock, the document's live records composed across its layers, and the store's events, projections and snapshots in key order, as 16 hex digits, with each part and its count beside it so a mismatch says where it is; `store` is `"read"` or `"absent"`. A session whose world has not run hashes at tick 0.

**`session.save_game`** (`SaveGameParams` → `SaveGameResult`) writes the session's running world into `path` — a new or empty directory, outside the document's — as a save: the document's directory copied, the store backed up (`VACUUM INTO`, [store](store.md)), the player's input log up to the tick and its map, and a `save.json` manifest naming and hashing every file. The result is the path, the tick and game time, the state hash, whether the world was streamed with its tile and observer counts and whether it has a player, and every file with its size and hash. Between two calls nothing is pending — every `session.run_headless` ends with its write-back flushed — so a save changes nothing in the session.

**`session.load_game`** (`LoadGameParams` → `LoadGameResult`) opens a new session on a save: `path` is the save's directory, `dir` a new or empty one the document and the store are copied into, so the save itself is never written. It refuses, before it copies anything, a save that is not one, one written at a version newer than this build's or in a format this build lacks, and one whose files are not the sizes and hashes its manifest gives, naming the file — 1002. A save written at an older version migrates, and `migrations` lists each step. Then it makes the world at the save's tick and game time, restores its tiles, observers and player, and hashes it: `saved_state_hash` is what the save recorded and `state_hash` the loaded world's, and a load that migrated nothing and does not reproduce it is refused and its session closed. The next `session.run_headless` on the new session continues the run: declare no observers, and hand the player's log over again.

**All three are read-only** in the sense of [Identity, and what a role restricts](#identity-and-what-a-role-restricts): none changes a document, a lease or a host setting. A save writes a new directory from what the session holds, as `doc.save` and `render.capture` write theirs; a load opens a new session on a new directory, as `session.open` with `create` does, and refuses a directory with anything in it; the hash reads. The E2E cases are `apps/engine_cli/tests/save_tests.cpp`: a streamed world with a scripted observer, a player and carts driving across tile edges run 300 ticks, saved, run on to 600; the save loaded in a fresh host, saved again to the same bytes, and run on to 600 with the log handed over; and the starting document run to 600 in one call — one state hash, `c2168e9307bca23b`, on MSVC, Clang and GCC; then a whole-document world saved and loaded into a second session in the same host and the two run on alike, and the refusals — a save inside the document, into a directory that is not empty, a file changed since, a load into a document, an unknown session.

### `session.materialize`

`session.materialize` (`MaterializeParams` → `MaterializeResult`) is the same pass on its own, with the report in full: materialize the session's document — `scope` `"whole"` (the default), `"tile"` with `tile_x`/`tile_y` (the records of that tile of the partitioned layers that define them), or `"untiled"` — into the session's runtime world now, and return what happened. The world is the one `run_headless` steps, so a report after a run is an incremental pass.

`MaterializeResult` says whether the pass was full or followed the change feed, the document revision the world now reflects, and the counts — `visited`, `created`, `updated`, `unchanged` (looked at and already in sync), `dematerialized`, `relinked` (held records materialized again because their parent now has an entity), `skipped`, `live`, `orphans` (held records whose parent has none) — and the wall time and tier. Then **which types mapped and which records were skipped and why**: `types`, one `MaterializeTypeReport` per record type the pass met, with `mapped`, `records`, `materialized`, `skipped` and, when it skipped any, the first `reason` — `no mapping` (document-only by design), `unknown type` (not in this build's registry), `tier`, `missing component` (with the component in `detail`), `no entity store`, `no hook` — and `skips`, the first 64 skipped records by id. And `mappings`: every mapping this build compiled, whether or not the document uses it — the record type, its components, each field row with its conversion and write-back flag, the parent rule and the tiers — so a client learns what a record type becomes before it authors one. A `scope` that is not one of the three is 1004.

### `engine.run_tests`

`engine.run_tests` runs the engine's own checks that are safe inside a host and returns one report: each `TestCheck` has a `suite`, a stable `id`, a `subject`, a `severity` (error, warning, info), a `verdict` (pass, fail, skipped, info), a `message`, pathed `diagnostics` and a `value`, and the result counts them, with `ok` true when no error-severity check failed. **It never spawns a process** — ctest, the test executables and the benches are a CI job, which is where their machine state and their GPU lock are handled — **and never opens a socket.** Each input is optional:

- `session`: `doc.schema` is `doc.validate` itself, called through the dispatcher so the check follows the method, with its `<layer>/<id>/<property>` diagnostics; `doc.index` is `Document::validate_index()`, the composed index against a linear recomputation of the layers.
- `tissue`: a `.tissue` container or an interchange `.json`, read (`tissue.read`), then every row of the tissue validators ([tissue](tissue.md)) as a check under the row's own id, subject, severity and verdict, the threshold and witness in the message and the measured value in `value`; `tissue_modes` is `--no-modes` inverted. 1006 without the tissue capability.
- `containers`: per `.clusters` file, `content.read` (`engine-content info`'s read: header, section table, content hash, counts), then `content.cluster_budget` (at most 2^24 clusters), `content.lod` (`geometry::validate_cluster_lod`, with the source triangles taken back through `vertex_source` from level 0, since a container does not carry its source's indices — which turns "level 0 covers the source once" into a check of that mapping and leaves the rest as the builder's tests hold it), `content.pages` (`validate_cluster_pages`, skipped without a page table), `content.identity` (a warning when the container records no source hash and build key, since an incremental build then rebuilds it), and `content.images` (a warning for an image slot that neither carries its bytes nor names a file that is there). A file that does not read fails `content.read` and skips the rest.

## Roles, leases and proposals

[Plan 06 §6.5](../plan/06-agent-tooling.md#65-permissions-concurrency-and-leases) in four bullets: roles are configuration; an agent leases (layer, tile set) or (layer, object-type set) before editing, and conflicts fail at acquisition; agents write to their own proposal layers, promoted into a target by structural merge after validation; read access is unrestricted. All of it is **this module's**, not engine-host's — `policy.h`, `leases.h`, `proposals.h`, `src/policy_methods.cpp` — because the writes it guards are this module's `doc.*` methods, and every dispatcher that serves them (engine-host, a future editor host, the tests) has to guard them alike. A host loads a roles file and says who it is; nothing else. [ADR-0039](../adr/0039-leases-and-proposals-beside-the-document.md) (proposed) records the four decisions below that would surprise someone; [E12](../experiments/e12-proposal-layers-and-leases.md) measured what leases buy.

| Method | Params → result | What |
|---|---|---|
| `lease.acquire` | `LeaseAcquireParams` → `LeaseInfo` | tiles (`TileRange[]`) or `object_types` of a layer, for `ttl_seconds` (1 s to 24 h); 1009 naming the holder when another actor's live lease overlaps |
| `lease.renew`, `lease.release` | `LeaseRenewParams`, `LeaseReleaseParams` → `LeaseInfo` | the holder's alone (1008 otherwise) |
| `lease.list` | `LeaseListParams` → `LeasesResult` | every live lease, by layer or holder; read-only |
| `lease.require` | `LeaseRequireParams` → `LeasesResult` | whether every writing `doc.*` call needs a covering lease |
| `doc.propose_layer` | `ProposeLayerParams` → `LayersResult` | a proposal layer over a target, owned by the caller; reopens a closed one of the caller's |
| `doc.promote` | `PromoteParams` → `PromoteResult` | merge, validate, commit; or refuse with the conflicts and the new validation problems |
| `doc.reject` | `RejectParams` → `LayersResult` | empty an open proposal without merging it |
| `engine.roles` | — → `RolesResult` | the loaded roles, each with the methods it may call, and the host's identity; read-only |

### Identity, and what a role restricts

**A call's identity is its attribution**: the `actor`, `role` and `task` of `attribution` in its params, with blank fields taken from the host's identity (`engine-host --actor`, `--role`, `--task`, `Policy::identity`). The methods that write records carry one — `doc.apply`, the new methods, and, since this change, `doc.undo`, `doc.redo` and `doc.merge` (`StepParams` and `MergeParams` version 2, `attribution: Attribution?` `@since(2)`; a merge given one journals it instead of the host's own). A method that carries none — `doc.add_layer`, `tunables.set`, `content.build`, `session.run_headless` — runs as the host's identity. **Roles are guardrails for cooperating agents, not security**: the protocol has no authentication, so a role is whatever a call says it is. What a role buys is that an agent told to be QA cannot change the terrain by mistake, and that the refusal says so in a structured error a model can act on. Where one agent owns one host — engine-mcp starts a host per agent ([apps](apps.md#roles-leases-and-proposals)) — the host is given that agent's identity, and the bridge refuses a call that names another role.

**The role a call runs in** is its attribution's role, else the host's `--role`, else the roles file's `default_role`; none at all means unrestricted, and so does a host with no roles file, which is every host before this change. A named role the file does not have is 1008 rather than no restriction, since a call that claims a role nobody configured must not fall through to none.

**Read access is never restricted, and a method is a write unless registered `read_only`** (`MethodDesc::read_only`, `read_only(method<...>(...))`, reported as `MethodInfo.read_only`, `@since(2)`). The default is a write on purpose: a method nobody classified is refused to a role that did not name it — loud — rather than open to every role — silent. Read-only means changing no document, no lease and no host setting: the `doc.*` readers, `doc.save` (it writes what the document already holds), `session.open` and `session.close` and `render.unload` (housekeeping of a caller's own handles: a role that may only look must still open what it looks at and let it go), every `render.*` and `engine.*`, `session.events` and `session.materialize` (the runtime world is a cache of the document), `session.state_hash`, `session.save_game` (it writes a new directory from what the session holds) and `session.load_game` (it opens a new session on a new directory, as `session.open` with `create` does), `lease.list`. The writes are the `doc.*` editors, `lease.*` but `list`, `tunables.set`, `content.build` and `session.run_headless` (its write-back changes the document); `engine.methods` says which is which. The dispatcher is the gate: it reads `params.attribution.role` from the raw JSON once, so no handler has to learn to, and refuses a write the role's `methods` patterns (`*` a wildcard) do not name — 1008 with `data.reason` `"method"`.

**What a role restricts in a write** is checked by the session, per transaction, and a refusal rolls the whole transaction back — a write is the caller's to make or not, never half of one — and is an RPC error, not a diagnostic:

- `layers`: the layer whose content changes. For a proposal layer that is its **target**, so `"layers": ["world"]` means "may change world, directly or through a proposal".
- `tiles` (ranges; none is the whole partition) and `untiled`: where each touched object stands before and after the change.
- `object_types` (patterns): each touched object's type.
- `review_required`: it writes only to proposal layers it owns and may not promote (`doc.promote` answers 1008 with reason `"review required"`); plan 06 §6.10's director is a role without it.

`data.reason` is `method`, `layer`, `tile`, `untiled`, `type`, `review required`, `proposal owner`, `proposal closed`, `lease holder` or `unknown role`, with the role and what was refused (`layer`, `object`, `tile`, `type`, `method`). `content/roles/roles.json` is the five named roles, and `content/roles/README.md` says what each allows and why the default is read-only.

### Where an object stands

Tiles and types are judged by the object's **composed** position and type (`place_of`): the strongest layer's `position` (or the partition's named property, or the type's `transform`), tiled by the **lease layer's** partition — a proposal's target, or the edited layer itself. Not by the edited record alone, which is what files are laid out by ([doc](doc.md)): an override that sets a colour and not a position still changes an object standing somewhere, and "a lease on tile (3, 7)" means the objects standing in it. Every object a write's commands name is placed **before its first change and after the transaction**, and both places are checked, so a move out of a lease or a role's tiles is caught by where it lands and a create-then-position in one transaction is judged by where it ends up. A record that is gone after the change (a delete in its defining layer) has no after; one that did not exist before has no before. An object with no position, or on a layer with no partition, has no tile: only an object-type lease covers it, and a role covers it only with `untiled`.

**The check allocates nothing per record**: a place is a hash lookup in the composed index, a visit to the layers holding the id, and a registry lookup for the type (whose name the registry owns), and a lease table is tens of entries walked in place. A write that no role restricts, into a document that does not require leases, records nothing at all — one branch per command.

### Leases

One table per document, **kept beside it as `leases.json`** (schema `LeaseFile`) and written before the answer, as the document's own files are: engine-cli starts a host per call, and engine-mcp replaces a host that misses a deadline, so a host's memory is exactly where a lease granted a moment ago would not be. Expiry is by the host's wall clock (`time::wall_unix_ms`), so it means the same to every process on the machine; an expired lease covers nothing and is dropped by the next acquisition, list or require. Ids only grow. Two hosts writing one document at once is as unsupported as it always was.

- **Acquisition** (`lease.acquire`) names tiles or object types, not both, on a layer that is not a proposal (1004 names the target to lease instead). It is refused with **1009 LeaseConflict** when another actor's live lease on the same layer has an intersecting tile range or a type in common, and `data.lease` is that lease: who holds it, for which task, until when. Overlapping one's own leases is allowed. A role may lease only a layer it may change, ranges inside one of its own, and types its patterns name. Type names are exact, because overlap has to be decidable from the names.
- **A tile lease and a type lease on one layer** can both cover a record (a light standing in a leased tile, under a lease on lights), and whether one does is not decidable from the two scopes. That overlap is refused **at the edit**: 1009 names the other holder.
- **Edits need leases only when the document says so** (`lease.require`, `LeaseFile.required`), off by default: every document and test written before leases edits as it did, and a single-agent document pays nothing. When it is on, every object a writing `doc.*` call touches — `apply`, `undo`, `redo`, `merge`'s output layer — must be covered, where it stood and where it stands, by a live lease of the caller's and by nobody else's: **1010 LeaseRequired** when none of the caller's covers it, 1009 when someone else's does.
- **A lease must be held until the proposal that carries its edits is promoted.** A lease released right after the edit protects nothing: the edit sits unmerged in the proposal, the next holder of the tile changes the record, and the promotion finds a conflict the lease existed to prevent. [E12](../experiments/e12-proposal-layers-and-leases.md)'s first run did exactly that and found a DeletedAndModified conflict with leases on. The protocol does not tie a lease to a proposal; the agent's protocol is acquire, read, edit, promote, release, and the MCP tools say so.
- **A promotion is not lease-checked.** It is the merge the leases existed to keep clean, and each record the proposal holds was checked when it was written. Nor is the runtime world's write-back (`Session::apply` without a caller, attributed to `system`): the simulation writing what it computed is not an agent editing.

### Proposal layers and promotion

`doc.propose_layer {name, target}` appends a layer of role `Proposal` over `target`, stored in the target's form (its partition), and records the caller as its owner: a **layer property** kept in `proposals.json` (schema `ProposalsFile`) and reported by `doc.layers` as `LayerInfo.proposal` (`@since(3)`) — target, owner, owner role, task, the rationale the proposal was opened with, state, when, and how many target records it has touched. It is the protocol's and not `domain/doc`'s: in memory, on disk and in the journal a proposal is an ordinary layer. **Only its owner writes it, and only while it is open** (1008 otherwise). Read access is unrestricted, so everyone reads it: proposals compose into the document like any layer, which is the "read-only context from neighbours" the plan asks for — and which also means a neighbour's in-progress deletion hides the object from everyone's strict `doc.apply` at once, so that collision surfaces at the edit rather than the merge.

**The merge base is per record, from the proposal's first touch.** The first commit that changes a record in a proposal appends the target's record as it stood then (or its absence) to `proposals/<layer>.base.jsonl` (one `ProposalBaseEntry` a line). `doc.promote` then merges three layers with `doc::merge_layers`: `base`, the target with each record the proposal holds put back as the proposal first found it; `theirs`, that base with the proposal's opinions composed on (`compose_onto`: properties and a parent overlay, a type defines, a tombstone drops a record the target defines and tombstones one it does not); and `ours`, the target now. This costs what the proposal touched rather than what the target holds, and a change promoted into the target *before* the proposal first touched a record is what the agent built on, so it is never reported against it — where a whole-target copy taken at `propose_layer` would call it a conflict. A record held with no recorded base (the proposal was written behind the protocol's back, or an undo refilled a closed one) merges against the target as it stands and can take the proposal's side but never conflict. ADR-0039 has the comparison.

**Validation runs on the merged world before anything is committed.** The accepted world is every layer that is not a proposal; `doc.promote` validates it as it is and with the target replaced by the merged layer, and what the second finds that the first did not is the promotion's to fix (`PromoteResult.validation`). Problems already there, or in other agents' proposals, do not block it — otherwise one agent's broken record would block every promotion. A promotion that leaves a child without its parent, overrides an object no accepted layer defines (an edit to a neighbour's unpromoted creation), or writes a property its type lacks is refused.

**It is refused, not an error, when anything stands in the way**: `promoted: false`, `ok: false`, `refused` a sentence, and every conflict and new validation problem. `prefer` (`PromotePrefer`) settles conflicts — `Refuse` (the default: a person or a director decides), `Target` (keep what the target has), `Proposal`, `Base` — and never validation. `dry_run` does everything but commit. **Committed, it is two journal patches**: the target's, attributed to the promoter with the proposal's owner, task and opening rationale in the rationale (plan 06 §6.8: an accepted proposal records why next to the change), and the proposal's emptying patch. The proposal layer **stays in the stack, empty and `Promoted`**, and its owner reopens it by name for the next piece of work — removing it would break undo for everyone, since every earlier patch names its layer and the journal is one line per document. `doc.undo {steps: 2}` takes a promotion back and leaves the proposal holding its records again; its state is not journaled, so it stays closed until its owner reopens it. `doc.reject` empties an open proposal without merging it (its owner may always; anyone else needs a role that may change the target). `PromoteResult` reports `merge_ms`, `validate_ms` and `commit_ms`, which E12 reads.

### Wire changes, all additive

`MethodInfo` version 2 (`read_only`), `LayerInfo` version 3 (`proposal`), `ApplyParams` version 2 (`layer`: the layer a transaction edits, empty the session's edit layer — agents sharing one session name their own proposals rather than moving the session's edit layer under each other), `StepParams` and `MergeParams` version 2 (`attribution`). New types: `TileRange`, `Role`, `RolesFile`, `RoleInfo`, `RolesResult`, `LeaseInfo`, `LeaseFile`, the four lease params, `LeasesResult`, `ProposalState`, `ProposalInfo`, `ProposalsFile`, `ProposalBaseEntry`, `ProposeLayerParams`, `PromotePrefer`, `PromoteParams`, `PromoteResult`, `RejectParams`. A caller that sends none of the new fields gets what it always got.
