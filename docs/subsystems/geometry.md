# geometry (domain)

**Purpose.** The cluster geometry format and its builder (docs/plan/04-renderer.md §4.3, ADR-0005). The cluster is the universal unit of rasterization, streaming, and acceleration-structure construction, so its layout is a contract shared by the content build, the mesh-shader and software-raster paths, the residency manager, and the acceleration-structure builder. This module owns that layout and the CPU-side builder over meshoptimizer.

**Format (v1).** `ClusterDesc` (48 bytes, GPU-mirrored): vertex and triangle offsets and counts, a bounding sphere, and a normal cone for backface culling in meshoptimizer's form (an apex as three floats and one `u32` packing the axis as three snorm8 and the cutoff as a snorm8; `encode_cone`/`decode_cone`, `NormalCone`). A cluster is entirely backfacing when `dot(normalize(cone_apex - camera), axis) >= cutoff`, which `cluster_backfacing` evaluates on the packed values exactly as the GPU pass does; a cutoff of 1 (`k_cone_none`) marks a cluster that is never culled, either because its normals spread too far or because the mesh is two-sided (`normal_cones = false` in either builder's options). Winding is the convention: counter-clockwise seen from outside is the front, the same rule the rasterizer uses. `ClusterMesh` holds the descriptors, cluster-ordered vertex positions (source vertices shared between clusters are duplicated, and `vertex_source` remembers where each came from), a parallel `VertexAttributes` stream (8 bytes per vertex: an octahedral normal in two snorm16, a UV in two half floats; `encode_normal_oct`/`decode_normal_oct`, `encode_half2`/`decode_half2`), and one packed `u32` per triangle holding three 8-bit local indices.

**Quantized positions.** Positions also exist on one 16-bit grid per mesh: `quantized` (three `u16` per vertex, cluster-ordered, parallel to `vertices`) with `quant_origin` at the AABB minimum of `vertices` and `quant_scale` = the largest AABB extent / 65535, so q = round((p − origin) / step) clamped to 0..65535 per axis and a degenerate mesh keeps step 1. `quantize_positions` fills all three; every builder calls it last, so a merged mesh gets one grid over all of its parts rather than one grid per part. `dequantize_position` is the CPU reference for the shaders' `load_position`, and `validate_clusters` checks every vertex is within half a step (a 20-unit terrain quantizes to a 3.05e-4 step, a unit mesh to 1.53e-5, a thousand-unit mesh to 0.0153). **Six bytes of position per vertex instead of twelve** on the GPU: the mesh-shader, vertex, and software rasterizers and the material resolve all read this stream (`gfx::MeshDesc`), so the float `vertices` are uploaded only where the acceleration structure builders need them. The stream is padded with one zero to an even `u16` count so a shader may read the last triple as two whole 32-bit words. Welded meshes stay crack-free: every cluster's copy of a shared source vertex quantizes the same float position on the same mesh-wide grid, so the copies land on the same integer triple and a seam's two sides move by exactly the same amount. Both builders take an optional `AttributeSource` (normals and UVs indexed like the source positions); missing normals are computed area-weighted from the faces (`compute_vertex_normals`), missing UVs are zero, and `fill_cluster_attributes` maps them through `vertex_source`, which also gives every LOD level its attributes because clusterlod keeps original vertices. Limits: at most 255 vertices and 512 triangles per cluster by the format; the builder default is 64 vertices and 124 triangles, which fits one mesh-shader workgroup.

**Builder.** `weld_vertices` comes first when the source is an exported file: it merges vertices whose position, normal, and UV are bit-identical and drops unreferenced ones (meshoptimizer's multi-stream remap), because exporters write unindexed or seam-split meshes and the 64-vertex cluster limit then caps clusters at 21 triangles with no shared edges for the LOD builder to collapse (Suzanne: 11,808 vertices become 2,012 and 188 leaf clusters become 42; the SciFiHelmet: 70,074 become 14,085). Vertices that differ in any attribute stay apart, so seams keep their normals and UVs. `build_clusters` runs `meshopt_buildMeshlets`, `meshopt_optimizeMeshlet`, and `meshopt_computeMeshletBounds`, then lays the result out in the format above; the LOD builder computes the same meshlet bounds on each cluster's local indices because clusterlod's own bounds carry no cone. `validate_clusters` checks the invariants tests rely on: ranges and limits, every source triangle present exactly once (by sorted corner triple), every vertex inside its cluster's sphere, and every non-degenerate face normal inside its cluster's cone (within the half-angle whose sine is the cutoff, with slack for the snorm8 packing).

**LOD DAG.** `build_cluster_lod` (`cluster_lod.h`) runs meshoptimizer's reference cluster LOD builder (`demo/clusterlod.h`: clusterize, partition clusters into groups, simplify each group, repeat until one cluster remains) and lays every level out in the shared format, level 0 first. **What it hands that builder is the subject of its own section below** ("What the simplifier is given, and why"): the positions, the UVs as a weighted attribute, and a tag on every vertex that sits on an atlas seam — and deliberately not the normals, which cost between 28% and four times the triangles for nothing this defect cares about. Each cluster carries a `ClusterLodDesc` (48 bytes, GPU-mirrored) with two spheres and two errors: `own` is the bound of the group the cluster was simplified from (error 0 for original geometry) and `parent` the bound of its own group's simplified output (infinite when the group could not be simplified further). A view-dependent cut is one test per cluster with no hierarchy traversal: render when the projected own error is at or under the threshold and the projected parent error is over it. Errors are monotonic along every DAG path, so exactly one cluster per path passes for any threshold and the cut is crack-free by construction. `lod_selects`, `select_lod`, and `projected_error` are the CPU reference for the GPU pass in `domain/gfx/shaders/cluster_cull.slang` (error / max(distance - radius, znear) * cot(fov/2) * height / 2, in pixels). A 129×129 heightfield (32,768 triangles) becomes 727 clusters in 10 levels (341 leaves down to 1) in about 200 ms; engine-view's 257×257 terrain (131,072 triangles) takes 860 ms for 2,898 clusters in 12 levels. `merge_cluster_lod` joins DAGs built over parts of one mesh into one (streams concatenated, offsets and group indices shifted, level counts added, every level-0 cluster first) and reports which part each cluster came from; engine-view builds one DAG per glTF primitive so that every cluster has a single material, at the price of clustering and simplifying each material's triangles on their own.

**A scene's meshes: one set of buffers, a grid each.** `merge_cluster_meshes` joins DAGs built over *separate meshes* into the one set of buffers a scene draws from, and differs from `merge_cluster_lod` in the two ways a scene needs. Each mesh **keeps its own 16-bit grid**: `quantized` is concatenated untouched (three `u16` at the merged vertex index, the whole stream padded to an even count once at the end) and `ClusterMeshPart` reports the origin and step to decode that mesh's vertices with, because quantizing a scene on one grid would spend the 16 bits on the distance between meshes rather than on each mesh's own detail — a 2 cm avocado beside a 20 m terrain would quantize to the terrain's step. And every mesh's clusters stay **contiguous**, so `{first_cluster, cluster_count}` names them and an instance reaches a cluster as `first_cluster + local`; within a mesh the level-0 clusters still come first, so a direct draw of the leaves is still the first `leaf_cluster_count` of them. `out.quant_origin`/`quant_scale` are the first mesh's, so a one-mesh merge behaves as before and `dequantize_position` on the merged mesh is only correct for that mesh. `gfx::MeshDesc` mirrors a `ClusterMeshPart` on the GPU.

**Cluster file.** `cluster_file.h` is the `.clusters` container `engine-content build` writes and the renderer loads instead of importing glTF and clustering at startup (docs/plan/07-content-pipeline.md §7.3): one `ClusterLodMesh`, a material index per cluster, the materials as a 64-byte GPU-shaped record (`ClusterFileMaterial`), the image paths those slots name, as the source gave them, the encoded bytes of the images the source embedded rather than named ("Embedded images" below), and the source mesh those paths are relative to. The layout is a 32-byte header — magic `CLST`, version, flags, section count, total bytes, content hash — then a table of `{kind, element_size, element_count, offset}` records, then the payloads, each at a 16-byte aligned offset from the start of the file. Little-endian, no pointers, every section an array of one fixed-size element that the reader and the writer move with `memcpy`, so a mapped file is already the bytes the GPU wants. The kinds (1 clusters, 2 lod, 3 vertices, 4 attributes, 5 triangles, 6 vertex_source, 7 level_cluster_counts, 8 cluster_material, 9 materials, 10 image_paths, 11 strings, 12 scalars, 13 quantized positions as `u16` triples, with the grid origin and step in the scalars record, 14 source_path, one NUL-terminated string naming the mesh the container was built from as it was given to the builder, 15 source_hash, two `u64` holding that source's content hash (`assets::source_mesh_hash`) and the build key over it and the options (`cluster_cache_key`)) are fixed and append-only, and **a reader skips a section whose kind it does not know**, so a file written by a newer build still loads as long as the sections this build requires are present; removing a required kind or changing an element's layout is a version bump. Everything that can be wrong is refused with its own message and leaves the output empty: a truncated file, the wrong magic, an unsupported version, a section that runs past the end, a content hash that does not match, a missing required section, or counts that do not agree. The hash (`core/hash`'s `hash_bytes`) covers every byte after the header, so it pins the section table as well as the payloads, and `cluster_file_hash` computes the same value from a `ClusterFileData` in memory: that is the identity the derived-data cache addresses a built mesh by. Writes go through `io::write_file_atomic`, so a reader sees the old bytes or the new ones and never a mix. Suzanne is 199 KB (88 clusters in 7 levels), the FlightHelmet 5.3 MB (2,348 clusters in 10 levels). The source path is what tells a reader where an image *file* is: it resolves the relative image paths against `parent_path(source_path)`, and against the container's own directory when the file does not say (an older file, or a mesh built from bytes with no file behind them). An image the source did not put in a file of its own travels inside the container instead, which is what makes one drawable on its own ("Embedded images" below). The source *identity* is what makes an incremental build possible: `ClusterFileData::source_hash` and `build_key` are the two words of section 15, and `read_cluster_file_identity(path, ...)` reads them — the header, the section table, and the content hash checked exactly as a full read checks them, and then the sixteen bytes — without rebuilding the mesh. Both are zero in a container that recorded none, which an incremental build reads as "rebuild it" rather than as a hit: `engine-content build-all` skips an entry only when both match what it computes from the source now ([apps](apps.md)).

**The material record.** `ClusterFileMaterial` is 64 bytes and stays 64 bytes: the first 32 are the original record — base color, metallic, roughness, and the base-color and normal image slots, indices into `image_paths` or −1 — and never move. The second 32 were `u32 pad[8]` and are now named one field per word, in order: `metallic_roughness_image` (pad[0]), `occlusion_image` (pad[1]), `emissive_image` (pad[2]), the emissive factor's three floats (pad[3..5]), `normal_scale` (pad[6]), and the packed `alpha` word (pad[7]: the alpha mode in bits 0..1, double-sidedness in bit 2, and the alpha cutoff as a unorm16 in bits 16..31, which is far finer than the 8-bit alpha it is compared against and is what keeps the record at 64 bytes). Every one of those words **reads as "none" or "off" when it is zero**, which is exactly what a file written before they existed gives: that is why the three new image slots are **one-based**, 0 meaning no image and slot *n* naming image *n* − 1 (`encode_optional_image`, `decode_optional_image`, and `encode_alpha_word` with `alpha_word_mode`, `alpha_word_double_sided`, `alpha_word_cutoff` convert). Old containers therefore still load and simply carry no metallic-roughness, occlusion, or emissive texture — but they are also wrong in the sense the derived-data cache cares about, so `k_cluster_cache_version` went to 2 and an entry built before that lost the cache and was rebuilt (the constant has moved on since; "Embedded images" below has the current value).

**Derived-data cache.** The same header declares where a built mesh lives and what addresses it, because `engine-content` and `engine-view` have to agree byte for byte: what one writes, the other finds. `cluster_cache_key(source_hash, options, weld)` mixes the source's content hash (`assets::source_mesh_hash`: the glTF's own bytes plus the bytes of every external buffer its `buffers[].uri` names) with the per-cluster limits, the cone and ray-tracing switches, welding, and `k_cluster_cache_version`, which is bumped whenever a builder change would make an old entry wrong. `cluster_cache_path(ddc_root, key)` is `<ddc_root>/clusters/<key as 16 lower-case hex digits>.clusters`, and `find_ddc_root(start)` walks up from a directory — an executable's, in practice — to the first one holding an `AGENTS.md` and returns `<that>/ddc`, empty when there is none. Derived data is rebuildable and git-ignored ([07 §7.3](../plan/07-content-pipeline.md)); nothing under `ddc/` is ever committed.

**The limit nothing in this module can fix.** The seam rule stops a collapse crossing an island edge; it cannot make an island survive being smaller than a triangle. Both machine-generated characters have an island whose UV area rounds to **zero** texels of a 4,096 atlas (six triangles on one, a single triangle on the other), and once a level's triangles are larger than an island, the island's texture is unreachable however the collapse is chosen — the geometry simply has nowhere to put those UVs. That is a **texture-space** problem and its fixes are texture-space ones: repack the atlas with fewer, larger islands, or bake per-level textures in the content pipeline ([07 §7.4](../plan/07-content-pipeline.md#74-validation-rules-automatic), where the fragmentation validator belongs). `engine-content stats` reports the numbers that say how close a mesh is to that wall — `islands`, `seam_fraction`, `smallest_island_texels_4096` and its triangle count — and reporting them is as far as the geometry builder can go.

**Not yet.** Quantized positions for the acceleration structure builders (`gfx/acceleration.h`, `gfx/cluster_acceleration.h` and engine-view's `--raster rt` still read the float `vertices`, which is why both streams are kept; the builders take a vertex format, so this is a format change, not a shader change), per-cluster grids finer than the mesh-wide one, tangents, the per-level BVH clusterlod can build over groups (the flat cut is one thread per cluster, which is fine until scenes reach millions of clusters), the GPU half of streaming (pages are built and stored — see "Pages and streaming" below — but the feedback buffer and the GPU residency manager are not), and precomputed cluster-AS inputs.

**Performance notes.** The builder is a content-build step, not a frame-loop one. The GPU reads `ClusterDesc`, the packed triangle words, and the quantized positions directly through device addresses; the 16-bit grid halves position bandwidth and footprint (6 bytes a vertex instead of 12) at a cost of under two thousandths of a pixel at 320×240 on a 20-unit terrain.

## What the simplifier is given, and why

**The defect, first, because the fix only makes sense against it.** Until 2026-09-19 `build_cluster_lod` filled meshoptimizer's `clodMesh` with five fields — the indices, the vertex count, and the positions — and left the other five at zero: `vertex_attributes`, `attribute_weights`, `attribute_count`, `attribute_protect_mask`, `vertex_lock`. That is not a neutral default. `clodDefaultConfig` sets `simplify_permissive = true`, and permissive simplification is defined by `meshoptimizer.h` as *"allow collapses across attribute discontinuities, except for vertices that are tagged with `meshopt_SimplifyVertex_Protect` in `vertex_lock`"* — clusterlod's own header even says "make sure to use `attribute_protect_mask` if this is set!". So the builder was running in the one mode that needs to be told where the seams are, and telling it nothing. Two things followed from that, and they compound:

- **No attribute term in the error metric at all.** With `attribute_count == 0` the simplifier's quadrics are positions only (`rankEdgeCollapses` adds the attribute quadric only when there are attributes), so a collapse that leaves the silhouette untouched and destroys the texture coordinates scores as free.
- **No topological barrier either.** clusterlod builds its connectivity from `meshopt_generatePositionRemap`, a **position-only** remap — which is right and necessary, or nothing at a seam could ever collapse and a seam-split export would not simplify at all. Permissive mode then downgrades every `Kind_Seam` vertex to `Kind_Complex` unless it is tagged, and a `Complex` vertex's wedges merge freely. So the two sides of an atlas island edge became one vertex whenever the cost in *position* was low, which on a smooth surface is always.

The failure is therefore a function of **how fragmented the atlas is**, which is exactly why it was not found earlier: the Khronos samples have a handful of large clean islands, a collapse across one of their edges is rare and lands somewhere nearby in the atlas, and every picture test the project had compared the engine against *itself at the same LOD*. On a machine-generated character (539,596 triangles, one material, an atlas of thousands of small islands) it is the first thing a viewer sees: at the default threshold the black clothing is covered in skin-coloured fragments and the skin and hair in black ones, because a simplified triangle interpolates its UVs from one island's corner to another's.

**What it is given now.** Five floats per source vertex — the normal, then the first UV set — with weights, and a per-vertex tag array:

| `ClusterLodOptions` field | What it does |
|---|---|
| `uv_weight` (0.5) | the attribute weight `meshopt_simplifyWithAttributes` takes for the two UV floats. meshoptimizer normalizes the positions of the subset it is simplifying by that subset's own extent and multiplies each attribute by its weight, so a weight of *w* makes one unit of attribute error worth *w* times **the group's own size** of geometric error. That is scale-free, which is what makes one default right for a 2 cm prop and a 20 m terrain. |
| `normal_weight` (**0**) | the same for the three normal floats, and **off by default** — see "What the weights are worth" below, which is the one place a measurement changed the answer. |
| `uv_seams` (`protect`) | tags every vertex that shares a position with another vertex but disagrees about the UV, so permissive mode leaves it a seam vertex: a collapse may slide **along** an island edge, never **across** it. **This is the fix**; the weights are not. |
| `normal_seams` (`none`) | the same for a hard shading edge. Off by default; see below. |
| `skin_seams` (`protect`) | the same for a vertex whose skin binding differs from its position-twin's. Free on a rigid mesh, which has no such pairs. |

The tags go in `clodMesh::vertex_lock` rather than through `attribute_protect_mask`, which would do the same job: one code path then serves all three attributes and all three rules, and it does not depend on how clusterlod indexes the attribute array. `SeamRule::lock` writes `meshopt_SimplifyVertex_Lock` instead, which pins the vertex outright.

**A discontinuity is defined as the weld defines it.** `weld_vertices` keys on position, normal, UV, and skin binding together, so after welding two vertices at one position necessarily disagree about one of them; the builder asks `meshopt_generatePositionRemap` the same question and compares the three attributes to find out *which*. Exact float comparison, deliberately: a well-behaved exporter writes bit-identical values for a duplicate that is not a seam, and a tolerance here would be a second, invisible weld.

**What the weights are worth, which is not what was assumed.** The obvious design — the one meshoptimizer's own cluster-LOD sample uses and the one this change started with — is normals and UVs both weighted at 0.5. Measured, that is wrong for this engine, and the measurement is the most useful thing in this section. Holding the seam rule at `protect` and sweeping the weights, cutting at 1080p and one pixel:

| `normal_weight` | heightfield at 30 units | at 120 units | shredded torus at 6 units | worst UV error |
|---|---|---|---|---|
| 0 | 16,367 tri | 2,041 tri | 4,602 tri | 8.0 texels |
| 0.05 | 16,369 | 2,040 | 4,602 | 8.0 |
| 0.1 | 21,010 | 2,038 | 4,602 | 8.0 |
| 0.25 | **32,768** (all of it) | 4,084 | 4,602 | 8.0 |
| 0.5 | **32,768** | 8,177 | 4,602 | 8.0 |

Two things fall out of that table. **The atlas column does not move at all** — the cut and the UV error are identical at every weight, so the weights contribute *nothing* to the defect this change exists for; `uv_seams = protect` does the whole job. And **the normal weight is expensive**: at 0.5 a 129×129 heightfield draws every one of its triangles where it used to draw half, and four times as many at four times the distance, because a normal delta is an absolute number that does not shrink as the group does while the position error does. It is therefore off by default. What it buys is shading accuracy, and the LOD threshold buys that more cheaply and with a knob the viewer already has; leaving it on would silently redefine what `--lod 1` means for every scene, every corpus threshold and every measurement in these pages.

The UV weight stays at 0.5 because it is **free** on everything measured: on a sane parametrization the UV is locally affine in the position, so the term is nearly redundant with the position term and bites only where a collapse *shears* the texture — which is the one thing a position metric genuinely cannot see. `uv_weight = 0` and every seam rule at `none` reproduces the position-only build exactly, which is how the "before" column of every table here is produced.

**The error the cut uses does not need a second term, and that is worth knowing.** The obvious worry is that `ClusterLodDesc::own_error`/`parent_error` bound the surface and not the picture, so a seam-safe build would still switch LOD where the silhouette allows rather than where the texture does. It does not arise: `meshopt_simplifyEdge` computes `result_error` from the same collapse cost it ranks by, and that cost already includes the attribute quadric when attributes are supplied. clusterlod stores that number as the group's `bounds.error`, which is what becomes our two errors. **So supplying the attributes moves the LOD transition as well as the triangles** — a group whose simplification cost UV accuracy now reports a larger error and is refined sooner, in exactly the units `lod_selects` and `cluster_cull.slang` already project. Nothing in the cut, the GPU pass, or the page layout changed. (The corollary is that `normal_weight`/`uv_weight` are part of `cluster_cache_key`: two weights are two different meshes *and* two different error fields.)

**Why `protect` and not `lock`, measured.** On the shredded-atlas fixture below (9,216 triangles, 288 islands in a 17×17 atlas), holding everything else fixed:

| `uv_seams` | clusters | DAG levels | triangles at the coarsest cut |
|---|---|---|---|
| `none` | 309 | 9 | 34 |
| `protect` | 293 | 8 | 66 |
| `lock` | 263 | 3 | 2,700 |

`lock` is not a stricter version of `protect`; it is a different outcome. Pinning the island borders leaves the simplifier nothing to collapse after two rounds, so the DAG stops at three levels and the mesh never gets coarser than 2,700 triangles — 41× what `protect` reaches — while the *total* cluster count goes **down**, because the cheap levels were never built. That is the trap in reading a cluster total as a cost: a rule that gets stuck sooner produces fewer clusters and a worse mesh. `protect` costs one level and about a doubling of the coarsest cut, which is the real price of the fix and is small.

`normal_seams` is `none` for a related reason: merging the two sides of a hard edge changes the shading by a bounded amount that a viewer reads as "smoother", and on a mechanical model those edges are also where the *silhouette* is, so the position metric already resists it. A UV discontinuity is not a bounded change but a change of **address** — the two sides index unrelated parts of the atlas — and no weight can price it, because the error it causes is not proportional to the distance between the two UVs. That asymmetry is the whole reason one of these is a weight and the other is a rule, and it is why the rule is on by default and the weight is not.

**The skin binding is a third kind of discontinuity, and it is a rule and not a weight.** `weld_vertices` deliberately keeps two coincident vertices with different bone weights apart ("Skinned meshes" below), because merging them would hand one surface the other's deformation. Permissive simplification would have undone that care at the first LOD level, silently, so `skin_seams` defaults to `protect` and tags exactly those pairs. It costs nothing on a rigid mesh, which has no such pairs at all.

What the binding is deliberately **not** is an attribute in the error metric, and the reasoning is worth keeping because it is not the obvious answer. A joint *index* is categorical — the distance between joint 5 and joint 6 is not a number — so a quadric over one is meaningless. The four *weights* are continuous and could be weighted, at the price of a nine-float attribute record instead of five, but on a well-authored skin they vary smoothly with position and the term would be largely redundant with the position term that is already there. And the case that would justify the cost does not arise: clusterlod keeps **original** vertices, so a coarse cluster's vertex always carries an authored binding rather than one a simplifier invented — the same property that makes skinning crack-free. What is left is a collapse between two *different* positions whose bindings differ a lot, an elbow vertex collapsing into a forearm one; that deforms slightly wrongly at a coarse level, it is bounded by the geometric error the cut is already chosen by, and whether it is worth a metric term is a measurement nobody has taken. It is recorded as a follow-up rather than assumed either way.

**The measurement the fix is judged by.** `measure_lod_attribute_error` (`cluster_lod.h`) is the CPU metric, and it needs no GPU, so it is the gate rather than the corroboration: sample the level-0 surface, find the closest point on the triangles of a cut, interpolate both meshes' **stored** attributes there, and report how far apart they are in texels of a 4,096 atlas and in degrees. Stored rather than source, because that is what the resolve interpolates; the floor of the measurement is therefore the format's own half-float UV, about two texels of 4,096 near the top of the range, which is why the default tolerance is eight. Sampling is a fixed stride over the level-0 triangles capped at `max_samples`, so the result is a function of the mesh alone and two runs agree to the bit. The search is a uniform grid in CSR form walked in shells, and the shell walk is exact rather than approximate: after searching every cell within *r* of the sample's own cell, nothing outside can be nearer than *r* cells.

On the fixture, at a matched budget of about a fifth of the source triangles:

| build | cut | UV error mean | p99 | max | samples over 8 texels | normals, mean |
|---|---|---|---|---|---|---|
| positions only (before) | 42 clusters, 2,298 triangles | 263 texels | 2,747 | 4,449 | **30.7%** | 0.61° |
| attributes + protected seams | 40 clusters, 1,836 triangles | 2.6 texels | 8.0 | 10.1 | **1.0%** | 0.50° |

The maximum is the number that says "never crossed an island": an atlas slot is about 240 texels of 4,096 here, so a worst sample of 10 texels cannot have left the island it belongs to, while a worst sample of 4,449 has crossed most of the atlas. The residual 1.0% is samples between 8 and 10 texels — ordinary simplification, measured against a deliberately tight tolerance.

## The shredded atlas

`stress_mesh.h` builds the fixture the section above is measured on, and it is **engine code rather than a test helper** for one reason: the same generator has to be reachable from this module's unit tests, from the renderer's procedural scene, and from the versioned scene corpus CI runs, which cannot share a `tests/support` header. It also has to exist at all, because the model that exposed the defect is the project owner's and may not be committed.

`build_shredded_atlas_torus` is a torus — no poles, every quad the same size, and a parametrization periodic in both directions, so the wrap is itself a seam for free — cut into islands of `island_side × island_side` quads. Each island gets its own copy of its `(side+1)²` vertices, computed from the *global* parameter so that the two sides of an island edge land on bit-identical positions and normals and differ only in UV, which is what a well-behaved exporter writes and what the weld keys on. The islands are shuffled into the slots of a square atlas with a seeded Fisher-Yates, deliberately rather than laid out in order: neighbouring islands in neighbouring slots would make a cross-island collapse land somewhere that still looks almost right. `island_side = 1` makes every quad its own island, which no simplifier can do anything with at all; `4` leaves an island's interior weldable and only its border a seam, which is what a real fragmented atlas looks like.

`build_atlas_probe_texture` is the other half: one saturated hue per atlas slot, with a gentle gradient inside the slot so that an error small enough to stay in its island still reads as a shade. A UV a collapse dragged into another island therefore reads a completely different colour, which is what makes a picture comparison measure this defect and not the shading.

Both are deterministic functions of their options — no hashing order, no thread order, no `<random>` distribution (whose results are not specified to agree between standard libraries), so the fixture is the same mesh on every machine.

**The morph fixture lives beside it**, for the same reason and with the same rule. `build_morph_sphere` is a UV sphere with Gaussian channels along its normal, and one generator gives the two shapes the deform chain has to be right on: a **face-like rig** (several channels at a small `falloff`, each touching a few percent of the vertices, which is what the sparse layout is designed for and the case where most clusters are touched by nothing) and a **morphing sphere** (one channel wide enough to reach every vertex, which is where reconstructing a normal from the deformed positions and interpolating a delta normal disagree most, because the curvature changes everywhere). Its normal deltas are the analytic normal of the displaced surface minus the rest one, so a test comparing delta normals against the truth *has* a truth rather than comparing the code with itself. `split_seam` makes the wrap column's deltas differ from column 0's, which is the authored discontinuity the weld key and `morph_seams` exist for; the wrap column is computed at **u = 0** rather than at u = 1 so its position is bit-identical to its twin's, because `cos(2 pi)` in single precision is not `cos(0)` and two positions differing in the last bit are two positions to every weld in the tree — which would make the fixture's seam a position seam instead of the pure attribute seam it is meant to be. `morph_fixture_position`/`_normal` are the float answer at a set of weights, so the stored stream is measured against the source rather than against another copy of the same arithmetic.

## Pages and streaming

`cluster_pages.h` is [04 §4.3](../plan/04-renderer.md#43-geometry) step 3 and [§4.9](../plan/04-renderer.md#49-streaming-and-residency) on the CPU: the clusters of one mesh laid out in fixed-size **pages** so a viewer can hold part of a mesh and still draw all of it, plus the selection rule and the residency model that go with pages. The GPU half — the cull pass writing requested pages to a feedback buffer, a GPU-side residency manager, the actual I/O — is not here yet.

**The layout rule.** `build_cluster_pages(mesh, options, out, error, source_of_cluster)` **renumbers** the mesh so that a page is a contiguous range of clusters, and it orders the pages so that a viewer holding the first *n* has a complete, if coarse, picture of the whole mesh rather than a detailed picture of a sixth of it. The order is:

1. every group with **no coarser version** — the root, and every group the simplifier got stuck on (`parent_error == k_lod_terminal_error`) — coarsest level first;
2. everything else, coarsest level first;
3. by group index within a level, which is there only to make the result a function of the input.

The first block is the mesh's **minimum resident set**: nothing can stand in for it, so those are the pages the residency manager pins, and a viewer that has them can draw the mesh. Splitting it out is not an optimization but a correctness fix: a DAG has one root per part that simplified all the way down *plus one per stuck group*, those extra roots sit at middling levels, and with a plain level ordering they land in the middle of the page array — so "the first *n* pages are a picture" was false for every mesh with a patch the simplifier could not merge, and pinning one of them stranded every page above it (the FlightHelmet could not be brought under a 25% budget at all, because its pinned mid-array page held six ancestors hostage). It does not disturb the property everything else rests on — a cluster's children are always later in the array — because a group that produced parents was necessarily simplified, so a cluster's children are never a terminal group.

Within a level the clusters are packed **group by group** — a group being the siblings a LOD cut refines into together, which share one parent error and therefore enter and leave a cut as one — so a camera move touches as few pages as it can. A group is split across pages only when it does not fit in a page at all; the page grows instead and is flagged `k_page_oversized`, because splitting a group would turn one page request into two for every cut that crosses it. Bytes are counted over exactly what the GPU streams for a cluster: `ClusterDesc` + `ClusterLodDesc` (96 bytes), six bytes of quantized position and eight of attributes per vertex, and four bytes per packed triangle — about 1.5 KB for a full 64-vertex, 124-triangle cluster, so a 128 KB page holds roughly 88 of them. The float `vertices` are not in the count and not in a page: only the acceleration-structure builders read those.

**Finding a cluster's children.** The format does not store clusterlod's `refined` index, so the only way back from a cluster to the group it refines into is the bound: every member of group *g* carries *g*'s simplified bound as `parent`/`parent_error`, and every cluster produced by simplifying *g* carries the same bits as `own`/`own_error`, so a sorted table of group bounds matches them exactly. The catch, and it is worth knowing before it costs an afternoon: when a simplification step costs **no error at all** — a flat panel, a piece of glass — clusterlod carries the group's bound and error through to the next level unchanged, so the bound alone is ambiguous between a group and the one above it. The key is therefore the level *and* the bound: a cluster at level L is always produced from a group at level L − 1, because each round of the builder partitions only the clusters the round before it made. Without the level in the key the FlightHelmet matched a cluster at level 2 against a 518-cluster range spanning three levels, and `validate_cluster_pages` caught it as "children that are not after it".

Renumbering means the permutation has to reach everything that names a cluster, and it does: the cluster and LOD descriptors, the vertex, attribute, quantized-position and triangle streams (reordered so a page's ranges are contiguous there too, with the offsets rewritten), and the group indices, which are renumbered into page order as well. A caller with per-cluster arrays of its own — a material per cluster, `part_of_cluster` from `merge_cluster_lod` — asks for `source_of_cluster` and runs `permute_cluster_array` over them. The layout is a function of the input alone (counting sorts and one total order over group bounds, no hash iteration and no thread order), so two builds of one mesh give the same bytes. The builder takes **one mesh's DAG**, before `merge_cluster_meshes` joins several into a scene: the renumbering is over the whole cluster array, and running it on a merged scene would break the per-mesh contiguity `ClusterMeshPart` promises.

One consequence is worth knowing before it surprises someone: a paged mesh no longer has its **level-0 clusters first**. They are last, because they are the finest. The clusters of a level are still contiguous, so a direct draw of the leaves is still one range — it just no longer starts at zero, which is why `engine-view --no-cull` (whose direct draw is `vkCmdDrawMeshTasksEXT(leaf_count)` over clusters 0..n) turns culling back on for a paged mesh rather than drawing the wrong end of the array. Nothing else cares: the cull pass tests every cluster on its own.

**The drawing rule.** `select_lod_streaming` is `select_lod` with pages that may be missing:

> draw c ⟺ c's group is resident **and** its projected parent error is over the threshold **and** (its projected own error is at or under the threshold **or** the pages holding its children are not all resident).

The last clause is the fallback: a cluster that wanted to refine and could not is drawn instead of the finer clusters it would have been replaced by, and it appends the pages it is missing to `page_requests` (sorted and free of repeats, so coarse first, which is also priority order because a coarser page completes more of the picture). With everything resident the rule is `select_lod` exactly, cluster for cluster and in the same order; the test asserts that at four distances.

**Why it is safe, and the invariant that makes it so.** Both residency tests are over a whole **group**, not over the cluster: the parent that would be drawn instead takes the same decision over the same group as the children that would replace it, so the two can never disagree and no surface is drawn twice at a page boundary. That alone is not enough, and finding out why cost an afternoon: the per-cluster test cannot see a *grandparent* that is missing. Evict a page in the middle of the DAG and its clusters stop drawing, their parents draw in their place — and the clusters two levels down go on drawing the same surface underneath them, because from where they stand everything they can test is resident. The fix is an invariant on residency rather than another term in the rule: **a page is resident only while the pages holding its clusters' parents are.** Requests keep one end of it, since a request only ever comes from a cluster that is being drawn and therefore from a resident parent; eviction keeps the other, by only ever taking a page that no resident page names as a child. The coarse-to-fine order is what makes that check cheap — a cluster's children are always in a later page, so "nothing under it is resident" is a scan of one short list. With the invariant, `descend(group) = resident(group) and error(group) > threshold` is monotone along every path of the DAG, exactly one cluster per path is drawn, and the cut is crack-free by the same argument the resident case rests on.

**The residency model.** `PageResidencyManager` is the CPU reference of [§4.9](../plan/04-renderer.md#49-streaming-and-residency) for one mesh: a budget in bytes, a request queue (`request`/`admit`, deduplicated, served in request order, which is ancestor-before-child because of where requests come from), `touch` to mark a page used this frame, and `evict_to_budget`. Eviction is least-recently-used by frame, ties broken by page index so a run is reproducible, restricted to the pages that may go at all: not a `k_page_root` page, and not a page with a resident child. `k_page_root` marks a page holding a group with **no coarser version**, which the layout keeps at the front; those pages are resident from `reset` and never evicted, because evicting one would leave a hole no fallback can fill. **A budget below them is not honoured** — Suzanne's whole mesh is one root page, so a 25% budget holds 111 KB anyway — and that is the right answer: the alternative is a mesh that cannot be drawn. Together the two restrictions make eviction peel the DAG from the fine end inward, which is also what one wants: the fine pages are the bulk of the bytes and the first thing a camera pulling back stops needing. The scan-per-eviction is `O(pages)`; the GPU manager will keep a heap, but the model is called once a frame over hundreds of pages and the clarity is worth more here.

**What it costs on the sample meshes** (`engine-content stats`, 128 KB pages, a camera flying from 50 mesh radii to 0.5 in 32 steps at 1080p and one pixel of error, under a budget of a quarter of the page bytes). The **FlightHelmet** (2,348 clusters, 10 levels, 170 groups) fills 25 pages at 91% and 2.85 MB of page bytes; one page is pinned. The whole outer half of the fly-in — from 50 radii down to about 10 — draws out of **that one page**: 7 to 38 clusters and 319 to 2,618 triangles, nothing requested. The last six steps are where streaming happens: 2 pages at 8.5 radii, 5 at 5.3, 7 at 3.7, 11 at 2.1, and 17 at half a radius for the full 960-cluster, 80,422-triangle cut. Under the 747 KB budget the viewer holds 6 pages (687 KB), draws 281 of those 960 clusters at the closest step, and has 8 pages outstanding — the honest picture of a budget a third of the working set: it lags rather than cracks. **Suzanne** (88 clusters, 7 levels) is 113,528 bytes, one page, no children, nothing to stream: the sweep requests nothing at any distance and the cut runs from 3 clusters and 245 triangles at 50 radii to all 42 leaves and 3,936 triangles from 3.7 radii in.

**A scene of paged meshes.** `merge_paged_cluster_meshes` is what `merge_cluster_meshes` is for geometry, for page tables: it joins meshes that have each been laid out in pages into one scene's buffers **and** one scene's page table, and `parts_out[m].first_page`/`page_count` name mesh *m*'s run of it. Concatenation is all it is — cluster, vertex and triangle ranges shifted by the merged bases, child-page entries and `page_of_cluster` by the pages before this mesh, `children` by the clusters before it — but two things about it are not obvious and cost a debugging session each if they are got wrong.

The first is **order**. `merge_cluster_meshes` reorders each mesh's clusters so its level-0 clusters come first, which is the scene convention that makes a direct draw of the leaves one range. A paged mesh is ordered the other way round — coarse first, leaves last, because that is what makes a page a contiguous run of clusters — so pulling its leaves to the front would leave every one of its pages naming clusters that are no longer beside each other, and the page table would describe a mesh that no longer exists. The merge therefore takes a `ClusterOrder`, and the paged merge passes `keep`. `ClusterMeshPart` gained `first_leaf_cluster` to say where the leaves actually are: zero for a mesh merged the default way, `cluster_count - leaf_cluster_count` for a paged one, so a caller that wants the leaves has one rule for both instead of a convention that is true half the time.

The second is **what gets pinned**. The residency manager pins every page flagged `k_page_root` — a page holding a group nothing coarser can replace — and *not* page 0, which happens to be such a page in a single mesh and is the wrong rule for a scene. Each mesh contributes at least one root page, and its root pages are the front of *its* run, not of the array; a scene that pinned page 0 alone would hold mesh 0's coarsest page and be unable to draw mesh 1 at all. The flag is on the page, so the manager needs no special case, but `validate_cluster_pages` does: the two invariants that are about a *mesh* rather than about the array — the pinned pages being a prefix, and levels never rising from one page to the next — are checked per mesh by the overload that takes the `ClusterMeshPart` array, because mesh 1's coarsest page necessarily follows mesh 0's finest. Everything else (the pages tiling the clusters, the vertices and the triangles; the byte target; children finer and later; child-page runs ascending and unique) holds over the whole scene unchanged, and nothing links two meshes, so a page's children are always in the mesh the page belongs to. `select_lod_streaming` and the manager need no scene-specific code at all: groups are renumbered per mesh by the merge, so a group is still one run of clusters, and the cut of a scene is exactly the union of its meshes' cuts with the cluster and page indices shifted — which is what the test asserts, at three distances and with everything resident, with the pinned pages alone, and with one leaf page of the second mesh missing. Every mesh must have been laid out with the same `page_bytes_target`, because the merged table carries one and two targets in one scene would make every fill ratio and every oversized flag mean something different from page to page.

**Request priority.** [§4.9](../plan/04-renderer.md#49-streaming-and-residency) asks for priority = f(screen contribution, distance to observer, time since request) with a starvation guard for the current view. `PageResidencyManager::request` takes a `PageRequest` — a page, the projected diameter in pixels of the requesting cluster's bounding sphere (`screen_pixels`, which is `projected_error`'s projection applied to the sphere's own size rather than to an error, so the two are in the same units and the same view), and the distance from the observer to the near side of that sphere — and the queue is served most urgent first, in this order:

1. a request that has waited more than `starvation_frames()` frames, oldest first;
2. the largest screen contribution;
3. the smallest distance to the observer;
4. the smallest page index.

Rules 2 and 3 are what the page is worth *now*: screen size is the term that decides, and distance settles the one thing screen size cannot, which is that a small near cluster and a large far one project to the same size and the near one is the one an observer moving at all will still want next frame. Rule 4 makes the order total, so a run is reproducible — and it also means a queue of requests that carry no view (`request(u32)`, whose priority is "nothing known") is served in page order, which is coarse first, which is exactly what the manager did before priorities existed. `select_lod_streaming` has an overload that fills the priorities in from the cluster that made each request, keeping the best of them for a page several clusters ask for, because the page is worth what the cluster that would show most of it says it is.

Rule 1, the guard, is a **step rather than a slope**, and that is the decision worth recording. A smooth "time since request" term reads well in a formula and is unimplementable behind a heap: it changes every queued page's key every frame, so the ordering the heap was built under is stale the moment the frame advances, and re-keying the whole queue every frame costs more than the queue is worth. A step costs one drain of a FIFO that is already in request order. It is also the honest statement of the requirement — not "old requests count for a little more" but "nothing waits longer than N frames", which is what a viewer parked in front of a small distant detail needs. The default N is 16, about a quarter of a second at 60 Hz: long enough that the guard does not fight the screen order under any normal load, short enough that nothing a viewer is looking at stays missing for longer than a glance. The requests themselves do not age: a page's score is what the clusters that asked for it said, kept at the best of them, so a re-request may only ever move a page up the queue and never down.

The queue is an indexed binary max-heap — `heap_` of page indices, `heap_at_` giving every queued page its slot — so a re-request with a better priority and the guard's promotion are one sift of one entry instead of a rebuild, and `admit` is a pop. Every array is sized once in `reset` and the heap keeps its capacity across a drain, so requesting and admitting in a steady state allocates nothing. The eviction side is still the linear scan it was: it runs once a frame over hundreds of pages, and unlike the request queue it has no key that a caller can improve.

**The container read by range, which is what makes a page's payload come off disk.** `read_cluster_file` answers "give me this mesh" and costs the whole file in host memory — which is why a streamed scene's pages came out of a `SceneData` rather than out of the file, and why streaming saved device memory and not host memory ([renderer](renderer.md#geometry-streaming-the-gpu-half-of-pages-and-residency)). `ClusterFileReader` is the other half of the question. `open` reads the header and the section table (a few hundred bytes, two ranged reads) and, when a caller asks for it, the **resident** sections: the cluster and LOD descriptors, the level counts, the scalars and the 16-bit grid, the page table, the material map, the materials, the image paths, records and bytes, the source path and the source identity. `mesh.vertices`, `mesh.quantized`, `mesh.attributes`, `mesh.triangles`, `mesh.vertex_source` and `mesh.skin` come back **empty** however long they are in the file, and `range(kind, element_size, first, count, ...)` says where any run of any section is, for `io::FileHandle::read_at` ([io](io.md#ranged-reads-a-file-open-addressed-by-offset)).

What makes that work at all is the layout rule above: `build_cluster_pages` reordered the vertex, attribute, quantized and triangle streams so that **a page's slice of each is one contiguous run**, so a page's payload is three or four ranged reads of one file rather than a gather. The test is the statement: for every page of the fixture, the four ranges are read off disk and compared byte for byte against what a full read holds at the same indices.

Two decisions in it are worth recording. The resident decode is done by **rewriting the resident sections as a container of their own** and handing that to `read_cluster_file_memory`, rather than by copying the decode: a second reader of one format would be two sets of checks, two sets of messages, and a drift nobody would notice until a container loaded one way and not the other, and the test holds the resident result to the full read field by field for the same reason. The paged sections are listed in that rewritten container with **zero elements** rather than left out, because "present and empty" and "absent" mean different things to the decoder — an absent `Quantized` section means "requantize this mesh", which on an empty mesh would throw the 16-bit grid away, and an absent `Vertices` section is a file it refuses outright. And the one thing `open` does **not** check is the header's content hash: it covers every byte after the header, and checking it means reading the file, which is the cost the reader exists to avoid. `header_hash()` hands the stored value over instead, which is what the renderer compares against the full read its load already made.

**In the container.** Three more append-only section kinds carry the table: **16 `pages`** (`ClusterPageDesc` per page), **17 `page_children`** (the flat `u32` child-page list), and **18 `page_scalars`** (one `u32`, the byte target the layout was given). `page_of_cluster` and `children` are *not* stored: they are rebuilt on read by `rebuild_cluster_page_index`, which costs one sort over the clusters and keeps eight bytes a cluster off disk. The target is stored, because it cannot be derived — the largest page is a lower bound on it, and for a mesh that fits in one page it is that page's own size, so a fill ratio computed from it would read 1.0 whatever the target was. A container written before the sections existed, or one built with `--page-bytes 0`, reads with an empty page table rather than as a failure, exactly as the source path and the source identity do; the caller builds one with `build_cluster_pages` if it wants one. All three sections are written even when there is no table, so a container's section list does not depend on how it was built. Because a paged container's clusters are *renumbered*, the page target is part of `cluster_cache_key` and `k_cluster_cache_version` went to 3: two page sizes are two different containers, and every cache entry built before that was stale rather than merely missing a section.

**What moved to the GPU, and what stayed.** The GPU half of §4.9 is built ([renderer](renderer.md#geometry-streaming-the-gpu-half-of-pages-and-residency)), and the split it settled on is worth recording here, because it decides what this module's data is *for*. **`select_lod_streaming`'s rule moved**: `cluster_cull.slang` runs it per (instance, cluster) pair against a residency word array, and a gfx test holds the two to the same cut and the same request set on random ancestor-closed residencies. What the shader needs from this module travels with the scene and is never itself paged — `page_of_cluster`, the per-cluster `ClusterChildren`, and `ClusterPageDesc` — which is 12 bytes a cluster and 48 a page against the ~1.5 KB a cluster a page carries. **`PageResidencyManager` stayed on the CPU**, unchanged in shape: the renderer feeds it the GPU's requests and used-bits one frame slot late and drives `admit`/`evict_to_budget` from them, so the priority heap, the starvation guard and the ancestor-closed eviction are this module's code running beside a frame rather than a second implementation.

One thing the GPU cannot reproduce and does not try to: the CPU coalesces several clusters' requests for one page into the *best* of their priorities, and the shader's per-page mask lets the first lane write its own. The manager takes the best of everything it is told over successive frames, so the two converge; the shader's alternative was two more atomics per losing lane.

`drop` is the one addition the GPU half needed. A request is made by a cluster that is being drawn, so it arrives with a resident parent — but the queue is not served in the frame it was filled in, and a parent evicted while its request waits turns that request **stale**: admitting it would put fine geometry back under a hole, which is the grandparent case the ancestor-closed invariant exists to prevent. The manager cannot tell on its own (it knows a page's children, not which of a page's parents a request came through), so it offers the removal and the caller decides. It showed up as one page in sixty under a budget tight enough to evict every frame, which is the kind of defect that only a residency test with real eviction pressure finds.

**Public API.** `domain/geometry/cluster_pages.h`: `k_page_root`, `k_page_oversized`, `ClusterPageDesc` (48 bytes, GPU-mirrorable, pinned by the size table), `ClusterChildren`, `ClusterPages`, `ClusterPagesOptions`, `cluster_page_bytes`, `build_cluster_pages`, `permute_cluster_array`, `rebuild_cluster_page_index`, `validate_cluster_pages` (one mesh, or a scene with its `ClusterMeshPart` array), `merge_paged_cluster_meshes`, `PageResidency`, `select_lod_streaming` (plain page requests, or `PageRequest`s carrying their priority), `k_unknown_distance`, `PageRequest` (12 bytes, pinned by the size table), `screen_pixels`, `sphere_distance`, `PageResidencyManager` (including `drop`, which takes a stale request out of the queue without admitting it). `cluster_lod.h` gained `ClusterOrder` and `ClusterMeshPart::first_leaf_cluster`/`first_page`/`page_count` for the paged merge.

**Testing (pages).** `tools/dev.ps1 test -Filter geometry`, `cluster_pages_tests.cpp`: a 32,768-triangle terrain (727 clusters, 49 groups) lays out in 8 pages of 128 KB at 91% fill with no oversized page, the pages tiling the clusters, the vertices and the triangles with every group in one page, the pinned pages a prefix, every level no coarser than the one before it and every cluster's children after it; the permutation leaving the multiset of triangles-as-position-triples untouched, `validate_cluster_lod` still passing against the source indices, every cluster's bounds, errors and level unchanged, group membership the same partition renumbered, `select_lod` giving the same cut modulo the renumbering at three distances, and a second run giving the same pages and the same permutation byte for byte; a 2 KB target making oversized pages rather than split groups; `select_lod_streaming` equal to `select_lod` with everything resident; a missing leaf page falling back to the parents, asking for exactly that page, and still covering the surface exactly once (the coverage check walks the DAG from its roots and asserts that every live cluster is drawn or refined, which catches a hole and a double-draw alike); the same with nothing but the root pages resident; and the manager admitting in request order, evicting the least recently used page that has nothing under it, and peeling everything but the `k_page_root` pages away under a budget of zero. For a **scene**, two terrains laid out in 16 KB pages and merged: the page invariants hold over the merged table per mesh, every page descriptor is its mesh's own with every index shifted (including the child-page entries, which never leave the mesh), a paged part's leaves are its last clusters and `first_leaf_cluster` says so, the streaming cut of the scene is the union of the two meshes' cuts at three distances with everything resident, with the pinned pages alone and with one leaf page of the second mesh missing, both meshes' first pages are pinned from `reset`, a budget of zero peels both meshes down to their own root pages and no further, what is left still draws clusters of *both* meshes, and two page targets in one scene are refused. For **priority**, four requests queued in the reverse of the order they should be served in come out big-near, big-far, small-far, then the one with no view behind it; the same four in any order give the same answer and a worse repeat of a queued request does not move it while a better one does; plain `request(u32)` calls come out in page order; and a small far request that would otherwise be starved for good by a big near one every frame is served on exactly the frame its age reaches the bound, never when the bound is set beyond the run, and on the same frame when the run is repeated. `select_lod_streaming`'s two overloads give the same cut and the same pages, the priorities are the view's (pulling the camera back shrinks every one of them), and `screen_pixels` is checked against `projected_error` on twice the radius. `cluster_file_tests.cpp` writes the fixture DAG in 64 KB pages and reads it back: the descriptors and the child list array by array, the two per-cluster tables rebuilt to what the builder had, the page table and the DAG both revalidating, the coarsest level first in the container, a mesh with no page table writing both sections empty and reading back with none, and a file whose `pages` kind this build does not recognize loading as a container with no pages.


## Skinned meshes: the binding stream

Skinning is the first real consumer of the deformed-vertex pool ([04 §4.3](../plan/04-renderer.md#43-geometry), [gfx](gfx.md)), and what it needs from this module is one more per-vertex stream that survives every transformation a cluster mesh goes through. `SkinBinding` (`cluster.h`, **8 bytes**, GPU-mirrored, pinned by the size table) is four `u8` joint indices and four `u8` weights **summing to exactly 255**, cluster-ordered like `VertexAttributes`. `ClusterMesh::skin` is empty or parallel to `vertices`, and `skin_joint_count` is the width of the palette the indices name.

**Why those eight bytes.** Four influences is what every exporter writes and what a mesh-shader workgroup can afford to load beside the positions and the attributes. A `u8` joint index caps a skin at `k_max_skin_joints` = 256, which is more than a humanoid with fingers and toes; a character that wants more is split into several skinned meshes, which is how it would be streamed anyway, and the glTF importer refuses a larger skin rather than wrapping the index. The weights are quantized to a **fixed sum** rather than renormalized on the GPU for two reasons: the shader's four multiply-adds then need no divide, and — the one that matters — every copy of a surface point gets *bitwise identical* weights, which is what the crack rule asks of a deformer's inputs. `make_skin_binding` does the quantization, putting the rounding error on the largest influence, where there is always room for it (with four influences the biggest quantizes to at least 64, and the correction is at most ±2).

It is a **separate optional stream** rather than two more words in `VertexAttributes` because the overwhelming majority of a scene's vertices are rigid, and eight bytes a vertex on all of them is page budget spent on nothing. `cluster_page_bytes` counts the stream only when the mesh carries it, so a skinned cluster is about 14 bytes a vertex heavier than a rigid one and a 128 KB page holds correspondingly fewer of them — which is the honest number, since a cluster whose bindings are not resident cannot be deformed.

**Skinning cannot crack, and the pipeline is why.** The binding reaches a built cluster the same way a normal does — through `vertex_source`, in `fill_cluster_attributes` — so every copy of a source vertex, in every cluster and on every LOD level, carries the same four joints and the same four weights. Coarse levels are safe for the same reason quantization is: clusterlod keeps *original* vertices, so a simplified cluster's vertex is a source vertex with its authored binding, never a binding a simplifier interpolated. Contrast the `wave` deformer of [E25](../experiments/e25-deformed-clusters.md), which reads a *normal* — a quantity welded duplicates disagree about and a simplifier recomputes — and tears the surface open. The remaining way to crack a skinned mesh is to author two coincident vertices with different weights, and that is exactly what the weld preserves rather than papers over.

**The weld key includes the binding.** `weld_vertices` takes an optional `Vector<SkinBinding>*` and adds it as a fourth stream to meshoptimizer's multi-stream remap, so two duplicates that agree on position, normal, and UV but disagree on weights **stay two vertices**. Merging them would silently hand one surface the other's deformation, and since the weld runs before clustering there would be no later point at which the loss could be noticed. The cost is a handful of extra vertices on meshes whose exporter split weights at a seam; the alternative is a defect nobody can see until the character moves.

That was the format's half of it, and for one release it was the *only* half: the parameter existed and neither builder passed it. `engine-content build` and `engine-view --mesh` both do now, and they have to agree byte for byte because they share cache entries — so `k_cluster_cache_version` is **5**, and every container built at 4 from a skinned source was welded without the binding in the key and is rebuilt. A rigid mesh's container is unchanged; only its cache path moved. The lesson is the general one: a parameter that every caller leaves at its default is not a feature, and a version constant bumped for the format is not a version constant bumped for the builders.

**Through the merges and the page layout.** `merge_cluster_lod` and `merge_cluster_meshes` concatenate `skin` exactly as they concatenate `attributes`, and take the merged `skin_joint_count` as the widest of the parts. For the parts of one mesh that is the mesh's own palette; for the separate meshes of a scene it is only the bound `validate_clusters` needs, because each mesh's bindings index *its own* skeleton and a renderer reaches the right bone matrices through the instance's deform record, never through the merged mesh. `build_cluster_pages` permutes the stream with the vertices it belongs to, so a page's bindings are one contiguous run of the stream the way its positions are.

**Validation.** `validate_clusters` checks that the stream is present or absent as a whole, that every binding's weights sum to 255, and that a joint carrying weight is inside `skin_joint_count`; a palette declared with no stream, or a stream with no palette, fails too. The fixed sum is an invariant of whoever built the mesh, not something the GPU is asked to repair, so a stream that has lost it is a bug rather than a rounding artifact.

**In the container.** Two more append-only section kinds: **19 `skin`** (`SkinBinding` per vertex, parallel to `vertices`) and **20 `skin_scalars`** (one `u32`, the palette width). The width needs a section of its own because `ClusterFileScalars`' eight words are all spoken for — four counts and the four floats of the 16-bit grid — and growing that record would change the layout of an element every existing container already carries. Both sections are written even for an unskinned mesh, empty and zero, so a container's section list does not depend on what it holds; a file with neither reads as an unskinned mesh, and a file with bindings but no width is refused, because a palette nothing can be checked against is worse than no palette at all. A container written before the sections existed is not merely missing them — its *weld* predates the binding being part of the key — so `k_cluster_cache_version` is **4** and every earlier entry is rebuilt.

**Testing (skin).** `cluster_tests.cpp`: `make_skin_binding` normalizes an unnormalized triple to 255 with the rounding on the largest influence, gives a single influence the whole 255, and binds a vertex with no weight rigidly to its first joint; a two-joint grid's bindings follow `vertex_source` vertex for vertex and validate, while a bumped weight, an out-of-palette joint, and a short stream each fail with their own sentence; an unskinned build carries no stream at all; and the unindexed grid welds back to 81 vertices with matching bindings but to 82 when one corner's weights differ. `cluster_lod_tests.cpp` checks the bindings of every *coarse* cluster against the source vertex's, which is the crack-freedom argument as an assertion, and carries the stream through both merges. `cluster_pages_tests.cpp` measures the eight extra bytes a vertex and checks that the permutation keeps every vertex with its own binding. `cluster_file_tests.cpp` round-trips a skinned container, reads one whose `skin` kind this build does not know as an unskinned mesh, and refuses one that kept the bindings but lost the width.


## Morph channels: the second per-vertex deformation stream

A **morph channel** is a named per-vertex displacement of the rest mesh played at a weight. Two
consumers want them and they want different things from them: facial and corrective animation
drives a handful of channels per frame from an animation clip, and **parametric characters** bake a
weighted set of shape channels once into a body that is then skinned like any other mesh. Both go
through the same stream and the same deform stages ([gfx](gfx.md), "The deform chain"); this page
is the format's half.

**The format is sparse and cluster-ordered, and both halves of that are forced by the GPU pass.**

*Sparse*, because a channel touches a region — a brow, a jaw, one seam — and a character carries
dozens. Fifty channels over a 300,000-vertex character is 1.8 GB stored densely and a few megabytes
stored as "the vertices this one moves". So `MorphChannelSource` (the builders' input) and
`ClusterMesh`'s stream both hold only the affected vertices.

*Cluster-ordered*, because the question the deform pass asks is never "where are channel k's
deltas" but "which channels touch **this visible cluster**, and where are their deltas" — one
workgroup runs per cluster of the cut and must read nothing else. The directory is therefore a CSR
keyed by cluster:

| `ClusterMesh` field | What |
|---|---|
| `morph_channels` | `MorphChannel`, **16 bytes**, GPU-mirrored: the two quantization scales, the channel's largest displacement, and the source's default weight. |
| `morph_names` | one name per channel, host side only — a shader has no use for a name, and putting one in the record would make it variable-length. |
| `morph_cluster_slices` | `clusters + 1` `u32`: cluster *c*'s slices are `[slices[c], slices[c+1])`. A cluster no channel touches costs **four bytes**. |
| `morph_slices` | `MorphSlice`, 12 bytes: `{channel, first_delta, delta_count}`, ascending by channel within a cluster, with the delta runs contiguous and in slice order. |
| `morph_indices` | one `u8` cluster-**local** vertex index per delta (a cluster holds at most 255 vertices), padded to a multiple of four. |
| `morph_deltas` / `morph_normal_deltas` | three `i16` per delta each, padded to an even count like `quantized`. The normal array is either empty or exactly parallel; a channel that moves no normals writes zeros into it. |

`morph_delta_count` says how many deltas the three arrays really hold, because they are padded and
their lengths cannot.

**The quantization, and why 16 bits is not a compromise here.** A delta is `i16 * scale`, and the
scale is **the channel's own** largest absolute component over 32767 — its own extent, not the
mesh's. That is what makes it free rather than merely cheap, and the argument is one line: the
position the delta is added to is *already* on a 16-bit grid over the whole mesh's extent
(`quantize_positions`), so a channel whose displacement is a fraction *f* of the mesh is stored on
a grid *1/f* times finer than the position it modifies. Measured on the fixture below — a
two-unit sphere whose largest channel displacement is 0.0797 units:

| | mesh position grid | morph delta grid |
|---|---|---|
| step | 3.05e-5 | 2.4e-6 (largest channel) |
| worst error over 2,210 deltas | 1.53e-5 (half a step) | **1.86e-6** |
| mean error | — | 9.06e-7 |

The worst morph error is **an eighth of the position grid's own worst error**, so a morphed vertex
is no less accurate than a rest one and the whole question is settled by the mesh's grid, where it
already was. Normal deltas quantize the same way against their own scale and come back within
1e-3 of a unit vector's component, which is finer than the octahedral snorm16 the attribute stream
stores a normal in. The alternative worth naming: float deltas cost twice the bytes for an
accuracy no reader can use, and 8-bit deltas would be *coarser* than the position grid on any
channel that moves more than 1/256 of the mesh, which is most of them.

**The weld key sees a vertex's deltas, and the interning is what makes that affordable.** Two
vertices identical in position, normal, UV and skin binding but different in *any* channel are
different vertices — merging them hands one surface the other's displacement, which is the skin
rule word for word ("Skinned meshes" above). The obvious implementation, a dense per-vertex row of
every channel's delta as a weld stream, is megabytes a vertex-pass on a character and is exactly
what the sparse layout exists to avoid. Instead `morph_vertex_keys` gives every source vertex a
32-bit **id**: its quantized deltas, in channel order, interned through a hash map that compares
bytes on a collision. Equal ids mean bit-identical delta tuples, so there is no false-merge
probability to reason about; the walk is over the sparse data, so it costs the deltas and not the
vertices; and a vertex no channel touches gets id 0 without being visited at all. The id is then
one more four-byte stream of meshoptimizer's multi-stream remap, beside the position, normal, UV
and binding ones. `weld_vertices` also **remaps the channels themselves**, rewriting each one's
vertex list to the new numbering, re-sorting, dropping entries for vertices the weld removed, and
deduplicating — exact, because two vertices only merged if their tuples were identical.

**`morph_seams` is `protect`, and the argument is the skin one with a sharper consequence.**
`ClusterLodOptions::morph_seams` tags every vertex whose morph id differs from its position twin's,
so permissive simplification cannot merge the wedges the weld deliberately kept apart. Skipping it
would undo the weld at the first LOD level; and where a merged skin wedge is a wrong deformation,
a merged morph wedge is a **hole** — the two sides of the seam are told to go to different places
the moment the channel plays. It uses the same interned ids the weld keyed on, so "these two
vertices carry different deltas" means exactly the same thing in both places. It costs nothing on a
mesh with no channels (there are no such pairs) and nothing on one whose coincident vertices agree.
It is in `cluster_cache_key` with the other three seam rules.

**Through the pipeline, and the one property everything else rests on.** The stream reaches a built
cluster through `vertex_source` exactly as a normal, a UV and a skin binding do
(`fill_cluster_morph`), so every copy of a source vertex — in every cluster, on every LOD level —
carries bitwise the same deltas, which is the crack argument. A channel's **scale is computed from
the whole source channel** and not from the vertices a given part happens to hold: that is what lets
`merge_cluster_lod` concatenate the parts of one mesh with no requantization, since every part
quantized channel *k* on the same grid, and it is checked rather than assumed (two parts that
disagree about a scale are refused). `merge_cluster_meshes` concatenates *different* meshes'
channel sets and records each mesh's run on `ClusterMeshPart::first_morph_channel`/
`morph_channel_count`, the same split the skin palette gets and for the same reason: an instance
reaches its own weights through its deform record, never through the merged mesh.
`build_cluster_pages` permutes the stream with the clusters it is keyed by — `append_cluster_morph`
is the one routine all three of them call, in the output's cluster order — so a page's slices and
deltas come out as one contiguous run of each array, like its positions.

**In the page budget.** `cluster_page_bytes` counts a cluster's own share: four bytes of directory,
twelve per slice, and one plus six (plus six more with normal deltas) per delta. On the face-rig
fixture that is +85% on a cluster the channels reach, which is the honest number — a cluster whose
deltas are not resident cannot be morphed — and **exactly zero** on a mesh with no channels, which
is why every rigid page in the corpus is the size it was.

**In the container.** Seven more append-only kinds, 23 to 29: `morph_channels`, `morph_names` (the
names NUL-terminated back to back, a section of their own rather than offsets into `strings` so a
build with no images still writes them), `morph_cluster_slices`, `morph_slices`, `morph_indices`,
`morph_deltas` (the position deltas then, when there are any, the normal deltas, back to back in
one section, since they are the same element and the same length), and `morph_scalars` (the delta
count, and whether normal deltas follow). All seven are written even for a mesh with no channels,
so a container's section list says what the format is rather than what this mesh happened to have,
and a file from before they existed reads as a mesh with no channels. `k_cluster_cache_version` is
**8**: an entry built at 7 from a source with morph targets carries none of the stream *and* was
welded without the deltas in the key.

**Not streamed, and that is a decision.** The whole morph stream is in `ClusterFileReader`'s
*resident* list, deltas included, because the renderer **refuses to stream a morphed mesh** and
says so ([renderer](renderer.md)). Paging it needs the slice directory's indices patched per page
the way `ClusterDesc`'s vertex offsets are, which is the same work and belongs with it rather than
half-done.

**The bound a renderer culls by.** `morph_bounds_padding(mesh, weights)` is the sum over channels
of |weight| × `MorphChannel::max_displacement`, which goes into `gfx::InstanceDesc::bounds_padding`
beside skinning's ([renderer](renderer.md), "Skinned instances"). It is the triangle inequality and
nothing cleverer, deliberately: the channels of a face move the same region in the same direction
as often as not, so a bound that assumed cancellation would be wrong on exactly the content this
exists for. A tighter bound is possible and is a follow-up — the largest displacement *per cluster*
rather than per channel would shrink it by the ratio of the channel's region to the mesh, at the
cost of a per-(cluster, channel) float the directory would have to carry.

**A second source of displacement is coming, and this stream is only the first.** The characters
this is for are two-level: a low-resolution canonical **control mesh** (about 13k vertices) carries
the shape channels, the skin weights and the cage, and a dense detail surface (hundreds of
thousands to millions of triangles, from a sculpt, a scan or a generator) is bound to it, each
dense vertex following a few control vertices with weights — the same transfer ADR-0026 plans for
soft tissue. Under that scheme a dense character's morph data is a function of the **control
mesh's** size and not the render mesh's, which is the whole point of it. What the render mesh would
then carry is a per-vertex binding stream of a few indices and weights — the same record shape as
`SkinBinding`, and the same shape a cage binding needs — plus the control mesh's own channel
deltas, and the displacement of a render vertex is the weighted sum of its control vertices'.
Nothing above has to change for that: the per-cluster directory is specific to *this* source, and
a binding stream needs no directory at all (it is per vertex, like the skin binding, and travels
through `vertex_source` the same way), so the two are alternative sources under one stage rather
than a layout that has to be redesigned. The stage's contract in gfx.md is written as "a rest-space
displacement source evaluated per render vertex" for exactly that reason, and the bound above,
being per channel, is the same number either way.

## Embedded images: the container carries them

**A container is self-sufficient for drawing, or says precisely what else it needs.** That is the property the renderer rests on — [apps](apps.md) promises that a mesh drawn from its `.clusters` container is the picture its glTF draws — and until 2026-09-18 it was false for every GLB. A `.glb` keeps its textures inside itself as buffer views, so those images have no path; the container recorded the paths and nothing else, and the renderer's loader handed the GPU upload an `assets::ImageRef` with neither bytes nor a URI, which it skipped with `texture skipped … "image has neither bytes nor a uri"`. The mesh therefore drew **textured from the source and untextured from the cache**, so the first run of `engine-view --mesh Lantern.glb` and every run after it disagreed — PSNR 26.0, FLIP mean 0.0189 with a worst pixel of 0.97 — and the reference-compare corpus caught it as a `thin-geometry` number that alternated between runs ([renderer](renderer.md#reference-renderer)).

**Two more append-only section kinds carry them.** **21 `images`** is one `ClusterFileImage` per image, *parallel to `image_paths`*; **22 `image_bytes`** is a flat `u8` payload holding the encoded files — PNG or JPEG bytes exactly as they were found, never decoded — back to back. The record is 24 bytes: the content hash of the bytes (`core/hash`'s `hash_bytes`), their offset and length in the payload, and a **one-based** byte offset into `strings` for the media type. Zero length means "this image is the file `image_paths[i]` names", zero mime means "the source did not say", so an all-zero record is an external image and a record from a build that did not fill a field reads as none — the same rule the material record's one-based image slots follow, and for the same reason. Both sections are written even when a mesh has no images, so a container's section list says what the format is rather than what this mesh happened to have, and a container written before they existed reads with `ClusterFileData::images` empty and draws exactly what it drew.

**Identical bytes are stored once.** An exporter that packs occlusion, roughness, and metallic into one texture names it from several material slots, and a glTF may point two `images` entries at one buffer view. The writer keeps one copy: it hashes each image, looks for an earlier blob with the same hash *and* length, and confirms with a `memcmp` before sharing the range — a 64-bit collision that quietly swapped two textures would be invisible in the picture, and the comparison costs one pass over bytes that are in cache anyway. `summarize_cluster_images` runs the same rule over a `ClusterFileData`, so what a build reports and what a reader reports of the file that build wrote are the same numbers.

**Why the bytes and not a reference, and what the long-term form is.** Three shapes were on the table.

- *Carry the encoded bytes* — this one. A container is then a complete answer to "draw this mesh", the derived-data cache stays a true cache (delete it and nothing is lost; keep it and nothing else has to be present), and it is one section pair and no new concepts.
- *Record a reference into the source* — the image's index in the glTF, resolved at load against the recorded `source_path` and checked against the recorded `source_hash`. It keeps containers small, and it was rejected: it makes **drawing** depend on the source file still being there and still being unchanged, which is exactly the coupling a derived container exists to remove — a container copied to another machine, or built from a source that has since moved, would go back to drawing untextured. It is also not obviously cheaper: getting at one buffer view means reading and parsing the whole 9.5 MB GLB again.
- *Decoded or GPU-ready texture derivatives in the DDC, keyed by image content hash* — where [07 §7.3](../plan/07-content-pipeline.md#73-content-build-the-derived-data-graph) is going, and **the long-term form**. It is what the engine actually wants: BC7/BC5 blocks in a KTX2 container with mips, built once and uploaded without a decode. It needs a texture pipeline that does not exist yet (`foundation/image` decodes to 8-bit RGBA and says so under "Not yet"), and inventing a second derived format and a second cache inside a correctness fix would have been the wrong order.

The step taken does not block the step after it, deliberately: the record's identity is the **content hash of the encoded image**, not an index or a path, so when texture derivatives arrive a container already says exactly which cache entry each of its images is. At that point the bytes become a fallback for an image nothing has built a derivative of yet, or drop out of the container entirely — either way, the reader changes and the format does not have to.

**What it costs**, `engine-content build` on the samples, before and after (`msvc-debug`, the same source files):

| Model | Container before | After | Images | Embedded | Image bytes |
|---|---|---|---|---|---|
| `Lantern/Lantern.glb` | 360,964 | 9,690,467 | 4 | 4 | 9,329,347 |
| `BoomBox/BoomBox.glb` | 326,964 | 10,731,717 | 4 | 4 | 10,404,597 |
| `Corset/Corset.glb` | 990,340 | 13,818,058 | 3 | 3 | 12,827,578 |
| `Avocado/Avocado.glb` | 33,748 | 8,118,790 | 3 | 3 | 8,084,902 |
| `FlightHelmet/FlightHelmet.gltf` | 5,298,676 | 5,299,104 | 15 | 0 | 0 |

A GLB's container grows by its textures, which is the honest price of the guarantee and is what a source-sized container should cost: the Lantern's 9.3 MB of PNG *is* the Lantern. The FlightHelmet, whose fifteen images are files beside the glTF, pays 428 bytes for fifteen empty records and keeps resolving its paths against the source directory. This is also the number the texture pipeline improves rather than the geometry: BC7 with mips is smaller than the PNGs and uploads without a decode.

Because a container built at cache version 5 from a GLB is not merely missing a section but is **the wrong answer** for that mesh, `k_cluster_cache_version` went to **6** and every such entry was rebuilt. It is **7** now, for the same kind of reason on the geometry side: an entry built at 6 or earlier was simplified with no attribute metric and no seam tags ("What the simplifier is given, and why" above), so on a fragmented atlas its coarse levels interpolate the texture across unrelated islands. That is not a missing section a reader can work around — the triangles themselves are the wrong ones.

**Testing (images).** `cluster_file_tests.cpp`: the fixture now carries three image slots — one named by a path with no bytes, and two embedded with the *same* bytes — so the round trip covers both forms and the dedup. The two embedded slots come back byte for byte with their media type, the `image_bytes` payload is one copy rather than two, the two records point at the same offset, the record's hash is `hash_bytes` over those bytes, and `summarize_cluster_images` reports 3 images, 2 embedded, 1 distinct, 1 deduplicated both from what was written and from what was read back. A container whose `images` kind this build does not know reads with its paths and no bytes, which is the older container exactly; a record array shorter than the path array is refused with its own sentence rather than silently dropping a texture; and a record whose bytes run past the payload is named as such. `engine-content` builds the cube fixture and checks that the container carries the GLB's PNG — the same length the summary reports, starting with the PNG signature — while the fixture whose texture is an external file reports zero embedded bytes and keeps its path. The picture itself is pinned end to end in `engine-view`'s test ([apps](apps.md)).
