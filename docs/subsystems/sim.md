# sim (domain)

**Purpose.** The simulation core of [05 §5.2–§5.5](../plan/05-simulation.md#52-sim-scheduler): the hierarchical timing wheel over `GameTime` and its budgeted fast-forward, LOD tier assignment over the observer set, the tick scheduler that carries the phase order, the system registration table, the materialization contract of [03 §3.4](../plan/03-data-model.md#34-the-runtime-world), and tile reconciliation, and **the materialization driver** that walks an authoring document through that contract and writes the world's changes back to it. It is the registration point capabilities attach to when they tick, schedule, summarize, or materialize ([ADR-0027](../adr/0027-additive-capabilities.md)), which is why it is **not** an optional capability: a registration point that can be switched off is one nobody can register with.

**Owned data.** The timer slab and its free list, the wheel's buckets and occupancy bits, the summarizer table, the system registration table and the schedule computed from it, the materialization hooks table, the executor seam, the fixed-step and game clocks of one simulation, and — per `Materializer` — which document records have been materialized, the document revision each reflects and the tile each is filed under, the tiles it has passed and not let go of, and the tile sources registered with it. Nothing else may hold a timer's storage; a `TimerHandle` is the only outside reference to one.

**The scheduler owns the tick** ([ADR-0038](../adr/0038-the-scheduler-owns-the-tick.md), proposed). The clock, the fixed step and the phase order are this module's, and systems that live in another executor — flecs' systems, for the entity store — run inside its phases through `TickExecutor` ("The executor seam" below). engine-host's runtime world is built that way; `ecs::SimWorld::step()` is flecs' own pipeline and remains for a world nobody schedules.

## Why a wheel and not a heap

The simulation schedules 10^5–10^6 timers whose due times are spread over game *years*, and cancels most of them before they fire: an NPC's next meal is rescheduled every time it eats, and a rescheduled timer is a cancel plus an insert. A binary heap pays O(log n) on both, with a cache miss per level of the heap, and cannot cancel at all without a side index from handle to heap position that has to be maintained on every sift. The wheel pays a bucket push and a bucket unlink, both O(1). Measured at 10^6 timers: 68 ns to insert, 32 ns to cancel, and the cost of neither grows with how many timers are asleep.

What the wheel gives up is a cheap answer to "what is the next event": it has to look. This implementation buys that back with one occupancy bit per bucket, so `advance` finds the next non-empty bucket with a `countr_zero` over at most sixteen words per level, and skipping a game month with nothing scheduled costs the same as skipping a tick — which is exactly the operation [§13.5](../plan/13-reference-consumer-games.md#135-mapping-to-the-roadmap)'s "leave for a game-week and the dune has moved" needs to be cheap.

**The level ladder is ticks, seconds, minutes, hours, days — approximately, and on purpose.** Level 0's resolution is the fixed step exactly; every level above is an integer multiple of the level below (60, 60, 60, 24, then 1024 buckets of about a day), so cascading between levels is exact integer arithmetic. The multiples are chosen so the spans land near a second, a minute, an hour and a day, *near* and not *on*, because a 60 Hz step is 16,667 µs and no ladder of integers off that hits a second. The drift is 0.002% at the day level and it is invisible: a level span is an internal bucketing choice, while a timer's due time is exact microseconds and is compared exactly. A design that forced the levels onto real seconds would have to make the tick level inexact instead, which would put the error where it is visible.

**A timer beyond the top level's span (about 2.8 game years) is not dropped.** It waits in a far list that is re-homed when the top level's block turns over, and `advance` will find it by scanning that list when every level is empty. The list is linear because it is meant to be nearly empty; a game that schedules a population of timers decades out should say so, and the wheel would then want a sixth level rather than a longer list ([ADR-0017](../adr/0017-no-hidden-limits.md): the limit is stated and handled, not hidden).

**Delivery order is (due time, insertion sequence).** Both are integers the wheel assigns, so two runs with the same inputs deliver the same events in the same order on every machine, and the order does not depend on how many timers happened to share a bucket or on what order the bucket's list is threaded in. A periodic keeps the sequence it was registered with across every firing, so a periodic registered before a timer always precedes it when they fall on the same instant, however many times it has fired since.

**A sink may schedule and cancel while it is being delivered to.** A timer the sink schedules for a time still inside the current `advance` is delivered by that same `advance`; a timer the sink cancels is skipped even if it was already in the batch being delivered (the batch holds handles, not indices, and a stale one is refused). A periodic re-arms *before* its sink runs, so a sink that cancels its own timer wins and a sink that does not gets a wheel already holding the next firing. What a sink may not do is call `advance` re-entrantly.

## Fast-forward: why the budget is the summarization trigger

`advance(from, to, budget, sink)` first *counts* the events due in the gap — walking only the buckets whose time range intersects it, and counting a periodic's firings arithmetically rather than one visit at a time — and stops counting as soon as the count passes the budget. If it did not pass, the gap is an ordinary advance and nothing is coarsened. If it did, every registered summarizer is asked to `summarize_interval(from, to)` exactly once and the periodics of summarized systems are re-armed past `to` instead of firing.

The budget is the trigger rather than, say, the gap length, because **the gap length is not what costs anything**. Thirty game days with one weekly periodic in them is 4 events and should simply run; thirty game days with an hourly economy is 720 and should too, if the caller can afford 720; thirty game days for ten thousand tiles' worth of NPC routines is tens of millions and cannot. The quantity the caller actually has to bound is the number of events it is willing to execute, so that is the quantity the API takes. It also makes the trigger *testable*: the same wheel with the same content takes the executing path under a large budget and the summarizing path under a small one, and the module's test asserts that an exact summarizer ends in the same state either way.

**The budget is a trigger, not a cap.** One-shot timers and the periodics of systems that registered no summarizer are delivered whatever the budget says, because they have no coarse form — a scheduled assassination does not have an average. That is deliberate: a budget that silently dropped them would turn a performance knob into a correctness one.

### The contract every LOD2/LOD3 system must meet

A system that runs at LOD2 or LOD3 registers a `Summarizer` ([05 §5.3](../plan/05-simulation.md#53-event-scheduler-temporal-lod) makes this mandatory) and its `summarize_interval(from, to)` must hold all of:

1. **Equivalence.** Applying the summary over `(from, to]` must leave the system in the state it would have reached by executing every one of its periodic events in that interval. Exactly, if the system's per-event effect is affine in time or otherwise closed-form (an hour counter, a stockpile that accrues at a rate, a decay toward a baseline). Approximately, with the approximation *written down on the system's own docs page*, when it is not — and then the error must not accumulate without bound across repeated summaries, because a tile can be summarized many times over a save's life.
2. **Determinism from stated inputs only.** The summary is a function of `from`, `to`, the system's own persistent state, and — for the reconciliation path — the tile's stored `seed` and the global events that intersect the tile. Never of wall-clock time, of how the gap was split into calls, or of anything the renderer produced. `SummarizeInterval` carries `tile` and `seed` for exactly this reason.
3. **Idempotence over a partition.** Summarizing `(a, b]` then `(b, c]` must equal summarizing `(a, c]`. A caller is free to fast-forward in several steps, and a system whose summary is not additive over adjacent intervals will drift apart from one that is.
4. **No events out.** A summary may write the system's own state and enqueue *future* timers; it must not emit world events dated inside the gap. Those events never happened at LOD2/LOD3 and nothing was there to observe them; emitting them retroactively is how a fast-forward turns into a cascade ([05 §5.7](../plan/05-simulation.md#57-world-events-and-consequences)).
5. **Bounded cost.** O(1) in the gap length, or at worst O(events in the gap) with a constant far below executing them. A summary that loops over the skipped events one at a time is not a summary.

A system that cannot meet (1) honestly should not claim LOD2/LOD3 at all: it should keep its periodic un-summarized, and accept that a fast-forward executes it.

## Why tiers are a function over the observer set

A tier is not a property of an entity. `TierAssignment` computes, per entity, the **minimum over observers** of `distance / (observer weight × entity importance)` and maps that score through a table of band boundaries. The observer set is the generalization that keeps working: two players in co-op, a security camera, a quest marker, an audio listener, and a dedicated server with no camera at all are all observers, and nothing in the simulation has to know which one is "the player" — [05 §5.12](../plan/05-simulation.md#512-multiplayer-readiness) calls the same set interest management, and it is the same set. A radius around a singleton camera would have to be unpicked for every one of those cases, and the unpicking would reach into every capability's LOD policy.

Importance and weight divide the distance rather than shifting the boundaries, so one table of boundaries serves every entity and every observer: a named character in a quest is "nearer" to every observer at once, and a heavyweight observer pulls everything near it up a tier without a second table. Importance covers what [05 §5.4](../plan/05-simulation.md#54-lod-tier-assignment) lists — quest relevance, named-character status, being in combat, being audible — as one number the game computes however it likes.

**Hysteresis and rate limits are what make the function usable rather than merely correct.** Promotion tests the band boundary; demotion tests the boundary widened by `hysteresis`. A crowd walking along a boundary therefore crosses once instead of oscillating, and the cost of materializing is paid once per crossing rather than every tick — the module's test walks one entity across a boundary and back with and without the band, because the difference is the whole point. On top of that, at most `max_promotions` and `max_demotions` entities change tier per call, nearest-first for promotions and farthest-first for demotions, so a camera cut that puts ten thousand entities inside the LOD0 radius spreads its materialization over ticks instead of dropping a frame. Deferred candidates are not forgotten; they are simply re-evaluated next tick.

**Changes come out in entity order**, not in the order the rate limit selected them, so a consumer walks its own arrays forwards and two runs produce identical bytes.

### Positions are f64

**An observer and an entity are `WorldPos`** ([ADR-0053](../adr/0053-world-positions-are-f64-and-the-gpu-sees-none.md); 2026-10-06): `ObserverSet::add` takes one, `TierInput::positions` is a span of them, `EntityRecord::position` is one, and the scheduler's reconciliation scores the records it loads from theirs. Until then all four were float32 world positions, which step by 3.1 cm at 419 km, a metre at 10,000 km and 8 m at 1e8 m: an entity half a metre inside a 32 m band 10,000 km out was rounded onto the boundary and given the next tier, and every caller narrowed its own f64 position to hand it over (the seams `observer_position` in engine-view and `tier_position` in npc, now gone).

**The one narrowing is the distance.** `score` takes the displacement from each observer in f64, its length in f64, and only then a float32 — a length in metres, which a float holds to a part in 2^24 at any size — so the distance a score is made of is within half a float step of the true one wherever the two positions are (0.95 µm at 30 m). Narrowing the displacement first and taking its length in float32 rounds each axis and then the sum, two to three times that. Scores, boundaries and `last_scores()` stay float32: a tier is a band of metres, and the score is not a position. The tier tests hold it: an entity 30 m from its observer (and one in 1024ths in no axis's direction, and one not in 1024ths) has the same tier and a distance within a micrometre of the true one at the origin and at the three far sites, and a 64-entity population round an observer, moved with it to each site, gives the same tiers and the same change list's bytes after three passes with the rate limits on; one 31.5 m out, half a metre inside the first boundary, is tier 0 at every site, where a float32 world position put it on the boundary at 10,000 km.

**What it costs**, measured 2026-10-06 on the i9-10980XE, `msvc-release`, the same build alternated with the float32 one so both saw the same machine — **not quiet**: other processes at 15–47% of the CPU and the GPU lock held by another agent's captures, so upper bounds: `sim.tiers.assign/0` (10^5 entities, three observers, no job system) **2.41–2.44 ms → 2.67–2.79 ms**, a tenth more, 0.8 ns per entity and observer; with eight workers 0.66–0.72 ms → 0.71–0.74 ms. Taking one f64 square root per entity (the minimum of `(distance / weight)^2` over the observers) instead of one per observer saved none of it — 2.72 and 2.79 ms — so the cost is the f64 arithmetic and the 24-byte positions, not the root; the per-observer form stayed for its single rounding. `EntityRecord` grew from 56 to 72 bytes (the size table says why); it is built on the stack per record and never stored.

## The tick

`SimScheduler` runs the eight phases of [05 §5.2](../plan/05-simulation.md#52-sim-scheduler) in order — input, events in, LOD assignment, systems, physics, post-physics, events out, persistence flush — on a fixed step from `core/time`. The timing wheel is pumped at the top of `events in`, so a phase's systems see this tick's events and nothing arrives mid-phase; the persistence hook closes `persist`.

`step()` reads no clock at all, which is what lets a replay, a headless fast-forward and a live session take the same path ([05 §5.10](../plan/05-simulation.md#510-determinism-and-replay)). `advance(real_ns)` is the same machinery with a `FixedStepClock` in front of it. The scheduler keeps its own tick counter rather than the accumulator's, so `step()` called directly still counts.

**Where the clock starts.** `SimSchedulerConfig::epoch` is the game time the clock and the wheel's origin start at, and `start_tick` the tick the counter starts at. A world loaded from a save starts at the tick and game time it was saved at ([world](world.md#save-and-load)), because everything downstream keys on the tick: the write-back's cadence is `tick % writeback_every`, the store's events and snapshots record it, and a timer due after the save must fall on the instant it would have in the run that never stopped — the test runs a periodic 300 ticks straight through and 120 then 180 in a scheduler configured to start where the first stopped, and compares the firings.

**The schedule is a pure function of the registration.** Systems declare read and write component-set masks; two systems conflict when one writes something the other reads or writes (read-read is free, which is the point of declaring the sets). Within a phase, a system is placed one *wave* after the latest system it conflicts with, in declaration order — longest-path layering, which is the fewest barriers that still preserves declaration order between every conflicting pair. Systems in one wave provably do not conflict and run in parallel on `core/jobs`' performance pool; waves are separated by a wait. Nothing about this depends on the worker count, and `schedule_hash()` is a 64-bit summary a test or a tool can compare: the module's test asserts that eight workers produce the same bytes as one and as none.

A system that declares empty masks declares "I conflict with nothing", which is a promise, not an absence of information. Declaring nothing and then racing is a bug in the system, and the masks are where it is visible in review.

### Named resources: declaring data that is not in the ECS

**A component mask can only name components, and [03 §3.4](../plan/03-data-model.md#34-the-runtime-world) tells a hot system not to keep its data there.** A pose pool, a physics island set, a GPU upload buffer: those are what a capability owns, and two of its systems ordered by one of them had nothing to declare. `systems/animation` met this first and worked around it by moving its third system into a later phase, which was honest and happened to be defensible on its own merits — but it moved a system for a reason that had nothing to do with which phase it belongs in, and a capability whose two pool-ordered systems genuinely belong in one phase had only the choice of over-declaring on a proxy component, which costs parallelism the schedule cannot explain.

So a system declares **resources** beside its components. A resource is a name a capability registers once (`sim::resource_id("animation.pose_pool")`, or `sim::resource_mask(...)` for a whole declaration), and `SystemDesc::reads_resources`/`writes_resources` are the sets over them. **Wave layering treats a resource conflict exactly like a component conflict** — a writer conflicts with every other toucher, two readers do not — and `schedule_hash()` covers both, so a declaration that changes changes the hash.

Three things about the shape, each of which was a choice:

- **The registry is the process's, not a world's.** A component index belongs to a world because the type is registered into that world; "the animation pose pool" means the same thing in every world in the process, and a capability that installs into two worlds writes the same declaration in both. It also has to be reachable from a module that has no world to ask: `domain/sim` must stay free of `domain/ecs` for [ADR-0028 §7](../adr/0028-ecs-and-persistent-store.md) to stay answerable. Registration is interned by *text*, so two translation units holding two copies of one literal name one resource; it is cold (install time, one thread) and, like `ecs::ComponentRegistry`, not synchronized.
- **The scheduler never sees what is behind the id.** It is a declaration, not an ownership mechanism: nothing here allocates a pool, hands one out, or checks that a system touched what it said it would. What it buys is that the *ordering* is a stated property of the registration rather than a side effect of a phase assignment, which is the whole argument for `SystemDesc` existing at all.
- **64 resources, one word.** The conflict test is one `and` per pair of systems in a phase, once, when the schedule is built. A resource is per capability rather than per type, so 64 is a different order of magnitude from the 256 components; the cap is stated, asserted, counted when it overflows (`ResourceRegistry::overflowed()`, which logs rather than aliasing somebody else's bit) and cheap to raise ([ADR-0017](../adr/0017-no-hidden-limits.md)).

What a resource is **not** is a query term. `ecs::register_system`'s debug check compares a system's flecs query against its *component* masks and deliberately says nothing about its resources, because a query has no terms for them — which is exactly why they exist. What that check does add is that every declared resource id is one the registry handed out, so a mask built from a stale constant instead of from `sim::resource_mask()` fails at registration rather than claiming another capability's pool.

**`domain/sim` does not depend on `domain/ecs`, and `sim::TickPhase` is now the engine's one phase enum.** `ecs::TickPhase` is an alias of it ([ADR-0028](../adr/0028-ecs-and-persistent-store.md) seam 2, 2026-09-18): not a copy with the same enumerators in the same order, the same type, so a capability's `SystemDesc::phase` and the flecs phase entity its body attaches to cannot drift apart. The dependency goes `domain/ecs` → `domain/sim` and never the other way, because the scheduler has to stay free of flecs for [ADR-0028 §7](../adr/0028-ecs-and-persistent-store.md)'s open question — whether flecs' pipeline stays the executor — to stay answerable. `ecs::phase_entity_name()` is the flecs entity's name (`sim_lod`) where `sim::phase_name()` is the phase's own short name (`lod`); the phase-order tests on both sides pin the order.

**What that seam means for this module.** The registration table here and `ecs::SystemRegistry` are the same declaration seen from two sides: `ecs::register_system()` takes a `sim::SystemDesc`, records it per world, and in debug builds checks its read/write masks against the flecs query's terms. The masks' component indices come from `ecs::ComponentRegistry`, which assigns them in registration order per world — this module states the width (`k_max_components`) and the conflict rule, and the entity store decides which component is which bit.

### The executor seam

`TickExecutor` is how systems this table does not hold run inside this scheduler's phases: a context and three function pointers, called once at the start of every tick (after the clock has advanced, before `Input`), once in every phase, and once at the end of the tick (after `Persist` and the persist hook). This module never learns what is behind them, so it stays free of flecs — the reason `ecs::TickPhase` aliases this module's enum and not the reverse. `ecs::ScheduledTick` is the one implementation: it publishes the tick and game time to the flecs world, opens a flecs frame, runs each phase's flecs systems as a per-phase flecs pipeline, and closes the frame ([ecs](ecs.md#the-tick-under-the-engines-scheduler)).

**A phase, in order:** at `EventsIn` the timing wheel; the begin-tick hooks of the phase's table systems; **the executor's systems for the phase**; the table's waves; the end-tick hooks; at `Persist`, the persist hook. The executor goes before the table because the table today holds engine systems that consume what capabilities' systems wrote in the same phase — the write-back at `Persist` is the first — and none that produces for them. A table system that must run before flecs' in its phase is the day that order becomes a declaration ([ADR-0038](../adr/0038-the-scheduler-owns-the-tick.md), "Revisit when").

The executor is one per scheduler, set with `set_executor` and detached by setting a default one. The scheduler's own tick counter and game clock are the only clock; the executor is told them, and a world an executor drives refuses to step itself.

## The materialization contract

[03 §3.4](../plan/03-data-model.md#34-the-runtime-world)'s four hooks — `materialize(record, tier)`, `promote(entity, from, to)`, `demote(entity, from, to)`, `dematerialize(entity)` — are a table of function pointers with a context and a tier mask, walked in registration order. They are data and not a base class for the same reason `SystemDesc` is: a capability that implements none of them contributes no row and costs nothing, and the tier mask means a hook that only exists at LOD0/LOD1 is not called for a transition that happens entirely beyond it.

`apply_tier_changes(changes, entities)` is the driver: the tier code never sees an entity id (it works on SoA indices) and the hook code never sees a position, and the caller's `entities[change.index]` is the one place they meet.

### Which name each hook carries

**The hooks used to speak `u64` and not say which `u64`.** [ADR-0028](../adr/0028-ecs-and-persistent-store.md) seam 3 settles the engine's vocabulary — persistent identity is `Id128`, and a runtime entity id must not outlive a tick's working set — but the materialization contract is precisely where the two meet, so a capability bridging them had to choose which the `u64` was and had no way to say what it chose. Two capabilities choosing differently would not have interoperated, and nothing would have caught it. Both names are now in the types:

| Hook | Name it carries | Why that one |
|---|---|---|
| `materialize(record, tier)` | `EntityRecord::entity`, an **`Id128`** | The record came out of the store. The only name that survived the trip is the persistent one, and there is no runtime handle yet — producing one is what the call is for. |
| returns | an **`EntityHandle`** | The handle the record now has: created by a hook that brings the entity into being, or resolved by one that found the entity that already existed. Null means "I gave this record no runtime existence"; the first non-null answer in registration order wins, and every hook still runs, because a second hook attaching its own state to the entity the first created is the ordinary case. |
| `promote` / `demote` / `dematerialize` | an **`EntityHandle`** | They act on something already live *this tick*. They are driven by `TierAssignment`, whose input is an array the caller is already holding and whose output indexes into it, so the handle is already in hand. An `Id128` here would put a hash lookup per entity per tier change in front of information the caller had, for a name nothing on this path needs. |

`EntityHandle` is a struct wrapping a `u64` and not a `u64`, which is the part that makes this a fix rather than a convention: the two cannot be swapped at a call site by a cast that compiles, and **`domain/ecs` is the only module allowed to know what is inside one** (`ecs::handle_of`, `ecs::entity_of`, `ecs::handle_for`). So "nothing outside `domain/ecs` stores a flecs entity id past a tick" stops being a rule reviews enforce and becomes a thing that is awkward to write. A null handle is skipped by `apply_tier_changes` and by `dematerialize` rather than handed to a hook, because a row nothing materialized has nothing to promote.

`reconcile_tile`'s step 5 is what this was blocking: it promotes what step 4 brought in, and a promotion needs the runtime handle. It now takes each handle out of the materialization that produced it instead of reusing the record's name and hoping.

**`EntityRecord::source`** carries a document record's mapping row and property values (`RecordSource`, below) when the driver is the caller; a record from the store has none, because its projections are opaque bytes today, and a hook then resolves an entity that already exists and creates none.

**Hook order.** `materialize` walks the table in registration order, so the hook that brings the entity into being — the entity store's — registers first, and every later hook attaches to what it created. `dematerialize` walks it **backwards**, the mirror of construction: every hook that attached state lets go before the hook that created the entity destroys it. Walked forwards, the entity store would delete the entity first and every later hook would be handed a handle naming nothing, and leak what it held — the animation capability's pose-pool slot, for one.

## The driver: a document through the hooks

`Materializer` (`domain/sim/materialize.h`) is the caller of the contract that reads an authoring document, and `sim::materialize(document, world, scope)` is the same thing spelled as the plan's sentence. It is what makes the runtime world a materialization of the document ([03 §3.4](../plan/03-data-model.md#34-the-runtime-world)) rather than a world that happens to be beside one.

**What it reads.** The document's live records, through `doc::Document`'s composed index (`objects()`, `type_of`, `parent_of`, `visit_records`, `revision_of`, `changed_since`, and for a tile or the untiled records its tile index, `ids_in_tile`, `untiled` and `object_tile` — never a scan of the layers), and for each record its type's row in the mapping table schemac compiled from the IDL's `materialize` declarations (`schema::MaterializeRegistry`, [schema](schema.md#materialization-type-mapping-as-data)). A type with no row stays document-only, by design, and is counted. For a record it can materialize it builds an `EntityRecord` whose `source` carries the mapping and one composed value per mapping row — the strongest layer's value, found in one visit of the layers that hold the record, or the record type's schema default where no layer sets the property — and hands it to `SimScheduler::materialize` at the configured tier. It writes no component itself: the entity store's hook does (`ecs::RecordMaterializer`, [ecs](ecs.md#materialization-the-entity-stores-hook)), and a test's fake does in `tests/materialize_tests.cpp`.

**What it holds.** Per record it materialized: the document revision the entity reflects, the mapping, the parent, the depth, the tile, whether the parent was linked. **No runtime handle** — that would outlive the call that produced it (ADR-0028 seam 3); when a hook needs one to dematerialize, the target resolves the record's `Id128` for the call (`MaterializeTarget::resolve`). A record and its entity are one identity because the entity is keyed by the record's id, not because the driver remembers a pairing.

### The contract as implemented

1. **Parents before children, then by id.** A call collects its candidates and materializes them in (depth, id) order, depth being the number of ancestors on the composed parent chain. Nothing downstream sees hash-table order or layer order, so two runs over one document create the same entities in the same order — and, in a fresh flecs world, even the same flecs ids (the ECS test checks both, and pins a hash of the world). Dematerialization is the mirror: deepest first, then by id. `last_order()` and `last_order_hash()` expose what the last call handed the hooks, and the sim test pins that hash.
2. **The first call is a full pass; later whole-document calls follow the change feed.** `doc::Document` stamps every id a mutation touches with a revision and keeps a bounded feed of them ([doc](doc.md#change-feed)). The driver asks what changed since the revision it reflects: a changed record is materialized again (the hooks find the entity by its id and update it), a deleted one — or one whose type stopped mapping — is dematerialized, a new one created. **An unchanged record costs nothing**: it is not visited, compared or handed to a hook; `stats().hook_calls` is the counter the tests watch, and `ecs.materialize.nochange` the bench. When the feed cannot answer — the document rebuilt its index, or the driver fell behind the feed's bound — the call is a full pass that compares each record's revision with the one it holds: correct whatever happened in between, and no dearer than the first pass.
3. **Per tile when the layer is partitioned.** `MaterializeScope::of_tile(x, y)` is the records of that tile of the partitioned layers that define them — the tile is `doc::tile_of` of the defining record under its layer's partition, the same function the layer's file layout uses, so "tile (x, y)" means the records `layers/<layer>/tiles/<x>_<y>.json` holds — and `untiled()` everything in no tile. **A tile pass costs its tile.** It takes its records from the document's tile index (`doc::Document::ids_in_tile`, `untiled`, [doc](doc.md)), which keeps that set per tile as every command changes it, and it finds what the driver holds there from the driver's own filing of held records per tile — so it visits the tile's records and nothing else, and neither does a tile's let-go (`dematerialize(scope)`) or `held(scope)`. It used to classify every live record of the document to find its tile's — a visit of the record's layers and a read of its position — which at 10^5 residents was 60 ms a tile of ~150 records on the i9 (37 ms on E38's Xeon), and is now 0.58 ms; letting a tile go in a world that holds every other one was 1.06 ms, a walk of everything held, and is now 0.20 ms ([E38](../experiments/e38-scheduled-npcs.md#follow-up-2026-09-25-a-tile-pass-costs-the-tile-and-the-schedule-index)). The classification is kept only as the equivalence test's oracle, never as a fallback. A tile pass owns what it filed under that tile: a record that moved out of it is dematerialized by that tile's pass and created again by its new tile's. A child whose parent is in another tile — or has no entity for another reason — is an **orphan**: materialized without its relationship and re-materialized (a *relink*) as soon as its parent is; the report counts both. **The mirror of a tile pass** is `dematerialize(scope)`: what the driver holds filed under the scope, deepest first, and nothing else — a child held under another tile whose parent goes becomes an orphan and relinks when the parent's tile comes back, as a deletion would leave it — and `held(scope)` is the ids a scope holds, sorted. Both were added (2026-09-25) for a tile that goes inactive ([world](world.md#the-consumers)): the only way to let go of one tile before was `dematerialize_all`, and a world streamed tile by tile has to drop the tiles behind its observers while it keeps the ones round them.
4. **What is skipped, and why.** Every live record in scope a call looks at is either materialized or counted with a reason: `no mapping` (document-only by design), `unknown type` (not in this build's schema registry — usually a capability switched off), `tier` (the mapping's `@tiers` do not include the call's tier), `missing component` (a component the mapping names is not registered in this world; the whole record is skipped rather than half made, and the report names the component), `no entity store` (a world with no target — a build without the ECS), `no hook` (every hook ran and none gave it a runtime existence). The report groups them by type and lists the first 64 by id.
5. **Between ticks.** The driver is called by whoever owns the tick, outside it; the entity store's hook refuses a call while the world is deferred or readonly, because a created entity would not be in the identity map until the merge and a later hook of the same record would not find it.

### Write-back

The reverse path, for the fields a mapping marks `@writeback` — position and orientation of the world's own `Transform`, and whatever gameplay state a capability's mapping marks. **At `TickPhase::Persist`**, the declared phase ([03 §3.5](../plan/03-data-model.md#35-persistent-world-state)'s persistence flush), every `writeback_every` ticks: `install_writeback()` puts a system (`sim.write_back`) in this scheduler's table, which runs after every flecs system of the tick has written what it writes. It asks the target for the writable fields whose bytes changed since they were last materialized or collected (`MaterializeTarget::collect_writeback`), turns them into one transaction of `SetProperty` commands in (record id, row) order, attributed to **`system`** (actor and role `system`, task `sim.write_back`, a rationale naming the tick and the counts), and hands it to a sink. engine-host's sink commits it to the session — journaled, saved and undoable like any other patch — and appends one event per record to the store's log when the document keeps one ([store](store.md#write-back-events)); a test's sink applies it to a `doc::Document`. `flush_writeback()` does the same on demand, and a host calls it when a run ends so the document says where the world stopped. **Nothing else writes the document from the world.**

A converted row goes back through the inverse of its conversion, in the record's own units. "Changed" is decided on the component's bytes, never on JSON, so materializing a value and writing it back is not a change, and an f32 that round-trips through a unit conversion does not creep. **A world position is f64 both ways** ([ADR-0053](../adr/0053-world-positions-are-f64-and-the-gpu-sees-none.md)): a `worldpos` property fills a `WorldPos` field with the record's double, a row between two length units scales it in f64 and stores f64 (and refuses a result past the cells' range), and write-back hands the document the double the field holds — nothing at all while nothing moved it, and to the bit when something did, 420 km, 10,000 km or 1e8 m out (`domain/ecs` `materialize_tests.cpp`, "ecs far").

**The world is in sync with what it wrote.** A record held in sync before a write-back is still in sync after it — the commit is the world's own state going back — so its held revision moves with the document and the next pass leaves it alone (the tests check the next pass calls no hook). A record someone else edited since it was materialized stays behind, so the next pass still brings that edit into the world.

### Records that move

A tile pass files a record under the tile it is in when it is materialized, and a later pass of that tile is what used to re-file it. So when a system moved a record — a cart driving east — and the write-back told the document, the document filed it under its new tile while the driver still held it under the old one, until that tile's next pass. What the driver held was then a function of **when each record was last materialized**: a tile going inactive dropped the cart it had once held, wherever the cart now was, and a world loaded from a save — which materializes each record where the document says it is — held a different set of entities than the run that never stopped. The replay test found it: the continuous run and the loaded one agreed at the save and parted at the next deactivation ([world](world.md#records-that-move)).

The driver now **reports** it and does not decide it. Every held record a write-back wrote is remembered until `take_moved`, which returns those whose document tile is not the tile they are filed under (sorted by id, once each) — `TileMove`: the record, where it is filed, where the document puts it. Whether the new tile is live is the tile ring's knowledge, not the driver's, so the world answers: `refile(id, tile)` files it under the tile it is in now, `dematerialize(ids)` lets it go. The world capability's document consumer does exactly that between ticks ([world](world.md#records-that-move)), which keeps what is materialized a function of the document and the live tiles — [03 §3.4](../plan/03-data-model.md#34-the-runtime-world)'s "a materialization of (document + persistent state) … for a set of loaded tiles", now literally. A whole-document world ignores the report: nothing there is filed by tile in a way anything reads, and what is remembered is bounded by what is held.

**Cadence, and why it is not every tick by default.** A commit is a journal entry and a save of the document. engine-host defaults `write_back_every` to 60 (one game second) plus a flush at the end of every call, so a one-hour headless run is 3,600 commits rather than 216,000; a caller that wants the document to follow the world tick by tick asks for 1.

### Records the document has not caught up with

A record is filed under the tile its document puts it in, and the document learns where a record is at the record's next write-back. For a record a system moves, that is soon enough: it is held, its write-back tells the document, and `take_moved` does the rest. For a record whose owner moves it by a rule of its own **while nothing holds it**, it is not: a resident whose routine walked it to work in a tile nobody simulates is let go there, and its routine walks it home to a live tile hours later while its record still says work — and a pass of its home's tile, going by the document, never brings it in ([npc](npc.md#records-that-move-and-the-boundary)). What was materialized was then a function of where records were last *written*, not of where their owners' rules have them.

**A `TileSource` is how an owner says where such a record is now** — a registration point added to the driver for the npc capability's schedule index (2026-09-25), and the smallest one that could be: the driver is the only caller that brings records in by tile, so it is the only place a capability can say "this record is in that tile now" without editing the ring or the scheduler (ADR-0027). A source is four function pointers: `where(id)` (the tile the owner has a record in now, or no opinion), `tile_in(tile)` (a tile's pass begins: the records the owner has in it now), `tile_out(tile)` (the tile is let go), and `arrivals()` (the records the owner's rule brought into a live tile since it was last asked). **Live** is the driver's own word: a tile it has passed and not let go of (`tile_live`), which is exactly the document consumer's tiles in a streamed world. With sources registered:

- **Filing.** A record the driver meets — in any pass — is filed under the tile a source places it in when that tile is live, and under its document tile otherwise (`MaterializeReport::placed` counts the first). A pass of a tile takes the tile's own records *and* the ones the sources place in it; one it meets held under another tile that a source places in this one is refiled here; and a record filed under the tile that neither its document nor a source puts there any more is let go, unless a source places it in another live tile, where it is refiled instead.
- **Arrivals.** `materialize_arrivals(document)` brings in, filed under their tile, the records the sources report as arrived in a tile that is still live — parents first, then by id, each once, and none the driver already holds. It is called between ticks, as every call of the driver is; the world's document consumer calls it when it settles ([world](world.md#records-that-move)).
- **The rule this buys.** After any sequence of tile passes at one time, a record is held when its document tile or the tile a source places it in is live, and it is filed under the second when that is live and under the first otherwise — which does not depend on the order the tiles came in, because a later pass refiles what an earlier one filed by the document alone. The npc test shuffles the order five ways and compares every held record, its filing and its state; the driver's own test takes the two orders of two tiles through a fake source.

A driver with no source behaves exactly as it did before sources existed, which the equivalence test above holds it to; a world that is not streamed has no live tile, so a registered source is never asked where anything is.

## Tile reconciliation

`reconcile_tile` is [05 §5.5](../plan/05-simulation.md#55-reconciliation-when-a-tile-activates)'s five steps over those hooks: load the tile's projections from the store, compute the elapsed game time since the tile was last active, run every LOD3 summarizer over the gap from the tile's stored seed, materialize the records at LOD2, then promote by observer distance. The plan's own fifth step — applying derived visual state by selecting damage-state variants — is the renderer's and is deliberately not done here.

The store is a pair of function pointers, not an include of `foundation/store`: reconciliation needs "give me this tile's state" and "give me this tile's records", `domain/sim` must not depend on an optional capability ([ADR-0027](../adr/0027-additive-capabilities.md) decision 1), and a test can hand it a fake. Summarizers run in registration order, so two reconciliations of the same tile produce the same summary in the same order whatever the tile contains. **The first real `TileStore`** is the world capability's `WorldStore` over `foundation/store` ([world](world.md#the-consumers), 2026-09-25): the state is the tile's snapshot (last active at its game time, the seed a hash of the world's and the tile's), the records its projections, written when the tile went inactive; its store consumer runs `reconcile_tile` when a tile activates, after the document consumer has made the tile's entities, so step 4 resolves them and step 5 promotes them.

## Invariants

- Every live timer sits in the bucket its due time and the wheel's current position name, its level is the one `choose_level` would pick, and the occupancy bit of every bucket agrees with whether that bucket's list is empty. `TimingWheel::validate()` checks all of this against a linear recomputation; the cascade test calls it after every one of 2,940 advances.
- A slot's generation is odd while live and even while free, so a handle from a previous occupant of a slot is refused rather than cancelling somebody else's timer.
- `advance` never moves `now` past an undelivered due timer: the skip search jumps only to the start of a bucket that has work, and a partially covered final bucket is checked for a genuinely due entry before it is returned.
- `assign_tiers` writes back exactly the transitions it emits, and emits them in ascending entity index.
- **A `TierChange` has no indeterminate bytes.** Its `u16 pad` is a named, zero-initialized member rather than tail padding the compiler leaves to chance, because the determinism claim below is about the change list's *bytes* and the test compares them with `memcmp`. Padding carries whatever the allocator last left in the block a `Vector` grew into, which is a function of the build, not of the simulation: the Clang debug build had been handing out fresh zeroed pages and passing, and the GCC RelWithDebInfo build failed the eight-workers test on 2026-09-19 with two garbage bytes per element. Any type whose bytes are compared, hashed, or written out belongs to this rule, not just this one.
- A phase's schedule is ordered by (wave, declaration index), and two systems that conflict are never in the same wave.

**Determinism stance ([ADR-0010](../adr/0010-deterministic-sim-and-lod-contract.md)):** `hashed`. Every ordering decision in the module is made on integers the module itself assigned (due time, insertion sequence, declaration index, entity index); the only floating point is the tier score, which is computed per entity from the inputs alone and never compared across entities except through a sort whose ties break on the index.

**LOD policy.** This module *is* one of the registration points for LOD policy, and it supplies the reference implementation the rest of the engine's capabilities are expected to agree with (`TierAssignment::score`/`tier_of` are public so a capability's own policy can be checked against them).

**Zero-cost-when-unused ([11 §11.10](../plan/11-performance-principles.md#1110-absent-capabilities-are-free)):** no instances. A wheel with no timers scheduled has 1,229 empty buckets and five zero occupancy words, and `advance` over any interval is a bitmask scan that finds nothing; a scheduler with no systems registered runs eight phases of nothing; a hooks table with no rows makes `apply_tier_changes` a loop over an empty vector. The module allocates nothing per event in steady state: timers come from a slab with a free list, and the scheduler's per-wave invocation and job arrays are reserved once when the schedule is built.

**Depends on.** `base`, `containers`, `time`, `math`, `jobs`, `log`, `ids`, and — for the driver — `json`, `schema`, `memory` and `doc`: it reads an authoring document through its composed index and the mapping table in `core/schema`. None is a capability, so the scheduler stays switch-free.

## Performance notes

Measured with `tools/dev.ps1 bench -Preset msvc-release -Filter sim.*` on an i9-10980XE, release.

**Machine state:** the wheel and tier rows were re-taken on 2026-09-18 with `--require-quiet` and repeated ([bench](bench.md#measuring-on-a-shared-machine)) — two runs, both starting and ending below 10% others' CPU, agreeing within 1%. The `sim.scheduler.tick` row is the original and was measured before the harness recorded anything; "otherwise idle" is what this page used to claim for all of them, and on this box that claim was never checked.

| Benchmark | Per operation | What it covers |
|---|---|---|
| `sim.wheel.insert` | **67 ns** | 10^6 timers spread over 30 game days into an empty wheel |
| `sim.wheel.cancel` | **31 ns** | cancelling every second one of those 10^6 |
| `sim.wheel.advance` | **645 ns** | advancing 30 game days, delivering the surviving 5×10^5 |
| `sim.wheel.tick` | **105 ns** | one fixed step with 10^6 timers resident and nothing due |
| `sim.tiers.assign` | **24.8 ns** (no job system) → **6.8 ns** (8 workers) | 10^5 entities, three observers |
| `sim.scheduler.tick` | **0.97 µs** (no job system) | 16 systems × 4 batches, empty bodies |

The wheel rows moved by under 3% from the figures first recorded here (68 / 32 / 662 / 106 ns), which is what an O(1) bucket operation should look like from one day to the next. **The tier rows moved by 8% and 12% the wrong way** (23.0 → 24.8 and 6.1 → 6.8), with both quiet runs agreeing to within 1% of each other, so it is not noise in *this* measurement. The ratio between them is unchanged, which is the useful part and which is what the discussion below rests on; the absolute pair is the reminder that a number recorded without the machine's state beside it cannot be compared against a number recorded with it. Nothing in `domain/sim` changed in between.

Three things the numbers say:

1. **Insert and cancel cost what an O(1) bucket operation should**, and the dominant term is not the list surgery but the integer divisions that map a due time to a level index. Computing all six indices by successive division from level 0 — rather than dividing the due time by each level's resolution and by each level's block size separately — plus caching the wheel's own indices took insert from 176 ns to 68 ns, a 2.6× improvement with no change in behaviour. The next step, if it is ever needed, is a reciprocal-multiply table for the five divisors.
2. **`advance` is dominated by cascading, not by delivery.** With 5×10^5 timers spread over 30 days, every timer falls from level 4 to level 0 through four cascades, so 5×10^5 deliveries do about 2×10^6 re-links, each one a random access into 56 MB of slab. 662 ns per delivered event is therefore a worst case for a wheel that is being drained from empty; the operating point [05 §5.6](../plan/05-simulation.md#56-what-npc-scale-is-realistic) actually projects — 10^6 LOD3 NPCs at about 3.5k events a second — is 2.3 ms of CPU per wall-clock second, and `sim.wheel.tick` shows that holding those 10^6 timers costs 106 ns of a 16.7 ms tick when none of them is due. If the cascade ever shows up in a profile, the fix is to make a bucket a contiguous array of slot indices with the slot carrying its position, which trades the intrusive list's second random write for one.
3. **Tier assignment scales 3.6× from no job system to eight workers**, not 8×, because scoring is only part of it: the candidate selection, the two sorts and the write-back are serial. Keeping the serial part to a compare-and-append is what makes even 3.6× possible — both hysteresis bands come out of one walk of the boundary table inside the scoring pass, and moving that work the other way (two separate band lookups in the serial pass) measured 2.6× *slower* overall, which is the sharpest evidence available that the serial tail is what governs here. 0.68 ms for 10^5 entities is comfortably under the 1.6 ms [ADR-0028](../adr/0028-ecs-and-persistent-store.md) records for E6's single-threaded LOD pass, but the ADR's point stands: at that population LOD assignment is a budget item, not a rounding error, and the rate limits exist partly so it does not have to act on everything every tick.

`sim.scheduler.tick` with a job system costs 10–12 µs against 0.97 µs without one, for 64 empty invocations: that is the job submission and counter wait, about 160 ns an invocation, and it is the floor a system's body has to be worth crossing. Systems with real work are the only ones that should declare more than one batch, and a phase of cheap systems is better left to the no-job path.

### The materialization driver

The driver's rows live in `domain/ecs`'s bench (`ecs.materialize.*`, `bench/materialize_bench.cpp`), because a driver with nothing to write into measures a hash map: they run it over the entity store's hook into a fresh flecs world. The document is E6's shape at scale — a `Market` and its sixteen `Stall`s, repeated — so it is also a hierarchy, and every stall maps four fields into three components and has two `@writeback` fields watched. `tools/dev.ps1 bench -Preset msvc-release -Filter ecs.materialize` on the i9-10980XE, release, 2026-09-24.

**Machine state:** not quiet, and quoted rather than claimed. Two runs, each after `--wait-quiet` gave up or found a lull: the first started at 9.3% and ended at 10.5% others' CPU, the second started at 9.0% and ended at 10.4%, the GPU idle both times. The two agree within 4% on every row but one (below), so these are upper bounds that are probably close to the cost.

| Benchmark | 10^4 records | 10^5 records | What it covers |
|---|---|---|---|
| `ecs.materialize.full` | **31.6–33.0 ms** (3.2 µs a record) | **353–366 ms** (3.6 µs a record) | the first pass into an empty world: every entity created, every field written, every shadow taken |
| `ecs.materialize.nochange` | **91 ns** | **95 ns** | the next pass, nothing changed |
| `ecs.materialize.incremental_1pct` | **207 µs** (2.1 µs a change) | **3.4–4.1 ms** (3.4–4.1 µs a change) | 1% of the stalls repainted between passes |

What the rows say:

1. **An unchanged record costs nothing, and the row proves it by not growing.** 91 ns at 10^4 and 95 ns at 10^5 is the report and the feed's "nothing since revision r", independent of the document's size. The first measurement of this row was 2.9 µs and 32.4 µs — linear, a third of a nanosecond a record — and the whole of it was `HashMap::clear()` on the per-call depth cache, which zeroes its bucket array whether or not anything is in it: a megabyte at 10^5, every call. The cache is now cleared only when a pass put something in it.
2. **The first pass is dominated by flecs, and by flecs' tables in particular.** The first version created each entity with `ecs_entity_init` and `add`: 52.0 ms and 585 ms, and **23,787 tables** for 5,883 parents, because flecs walks the table graph from the parent's `ChildOf` table one id at a time and keeps every table the walk made. Finding the destination table by type (`ecs_table_find`) and committing the entity to it (`ecs_commit`) makes one table per parent — **6,137** at 10^5, **843** at 10^4 — and took the pass to the figures above, 37–40% less ([ecs](ecs.md#materialization-the-entity-stores-hook)). What remains is per entity: the table lookup by type, the move, one `ensure` and `modified` per component (so observers and change detection see one write each), the identity map's `OnSet`, and the write-back shadow.
3. **An update costs about what a creation does, minus the creation.** The incremental row is the change feed's ids, one composed-value visit each, the depth walk (cached per call), and the hook's field writes. At 10^5 it runs 3.4–4.1 µs a change against 2.1 µs at 10^4 — the one row whose two runs disagree, the first with a 20% spread — which is cache, not work: the document's index, the held map and flecs' entity index are all past L2 at 10^5, and every change is a handful of dependent misses among them.

The hierarchy is the part of this to watch. A document whose parents each have one child costs a table per child; the table watchdog is what says so ([ecs](ecs.md#two-traps-e6-measured-as-guard-rails)).

## What is stubbed

- **The registration table is not yet static.** [ADR-0027](../adr/0027-additive-capabilities.md) describes `SystemDesc` as constant-initialized descriptors in a link-time table; here they are added at runtime with `add_system`. The shape matches field for field (plus `context` and `batches`, because the ADR's sketch assumes a system reaches its module's globals and a testable one has to be handed its state), so the static form is a mechanical change.
- **`SystemDesc::tiers` and `Determinism` are recorded, not enforced.** Nothing filters a system's invocation by tier yet, because nothing here owns the entity-to-tier mapping; the scheduler carries the declarations so that the tick which does can read them.
- **`Batch` is an index range the scheduler does not interpret.** It has no entity store to split, so a system that declares four batches gets four invocations numbered 0–3 and decides itself what they mean. When the scheduler drives an entity store, the batch becomes a row range.
- **No event bus.** [05 §5.7](../plan/05-simulation.md#57-world-events-and-consequences)'s subscribe-by-type-and-tile, causal depth cap, and per-system event budget are not here; the wheel delivers to one sink and the game routes. The first capability to schedule timers, npc, installs itself as that sink and forwards every event that is not its own to one its host names ([npc](npc.md#the-transitions-on-the-wheel)); a second would make the sink want to become a table.
- **The persistent-state hash is the world capability's** (`world::state_hash`, [world](world.md#the-persistent-state-hash)), because it reads the store's tables and this module does not depend on the store; `schedule_hash()` covers only the schedule.
- **`reconcile_tile` does no writing back.** It reads the tile and materializes; persisting the summarized state is the caller's, through the `persist` phase.
- **Materialization from the store.** The driver reads a *document*. There is now a `TileStore` over `foundation/store` — the world capability's `WorldStore`, whose projections a tile writes when it goes ([world](world.md#the-consumers)) — but a store record still carries no source a hook could build components from (a projection is where a record was, not what it is), so reconciliation resolves the entities the document made and creates none, and the write-back writes the document and the event log, not projections.
- **Promotion of materialized records, for types other than residents.** The driver materializes at one tier. For `engine.npc.Resident` records the npc capability drives `promote`/`demote` itself — a table system at `Lod` running `TierAssignment` over the residents it holds against the host's observers and applying the result through `apply_tier_changes` ([npc](npc.md#the-capability-at-each-tier-the-lod-policy)), with nothing here edited. Every other record type stays at the tier it was materialized at, apart from reconciliation's promotion when its tile activates.
- **Write-back scans every watched entity once per flush.** Cheap at the default cadence; a world of 10^5 writable entities flushing every tick would want flecs' change detection to skip the tables no system wrote ([ecs](ecs.md#not-yet)). 6.3 ms a flush at 10^5 residents ([E38](../experiments/e38-scheduled-npcs.md#the-write-back-scan)).
- **The far list is linear** and the top level's span is about 2.8 game years; see above for when that stops being the right shape.
