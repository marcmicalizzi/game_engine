# platform (core)

**Purpose.** Facts about the machine and the OS that everything else builds on: processor topology (logical CPUs, cores and SMT siblings, packages, NUMA nodes, cache hierarchy, cache domains, efficiency classes), CPUID instruction-set features with OS support taken into account, the startup check that refuses a machine older than the build ([ADR-0031](../adr/0031-minimum-cpu-x86-64-v3.md)), no dialog and one line on stderr for every fatal fault (below), and thread pinning, priority, naming, and identification. This is Stage 1 of hardware characterization (ADR-0011): detection, no benchmarking.

**Owned data.** The cached `Topology` and `CpuFeatures`, detected once per process.

**Invariants.**
- Engine CPU ids are dense `0..n-1`; `LogicalCpu` keeps OS coordinates (`os_group`, `os_index`) for pinning, and `Topology::find` maps back.
- Every CPU belongs to exactly one cache domain; domains are disjoint and cover all CPUs.
- `performance_cpus` and `efficiency_cpus` partition the CPU set; `performance_cpus` is never empty. On homogeneous parts `efficiency_cpus` is empty.
- `CpuFeatures::avx2 == true` means the instructions can execute (CPUID bit and XCR0 state both checked), likewise for AVX-512.
- No translation unit of this module is compiled with the build's arch flag, whatever `ENGINE_CPU_BASELINE` says (below).
- `missing_baseline_features` never writes past the buffer it is given and always terminates it; the count it returns is the full count, even when the list was truncated.

**Public API.**
- `core/platform/topology.h`: `CpuSet`, `CacheInfo`, `LogicalCpu`, `CacheDomain`, `Topology`, `topology()`, `detect_topology()`, `describe_topology()`.
- `core/platform/cpu_features.h`: `CpuFeatures`, `cpu_features()`, `detect_cpu_features()`.
- `core/platform/cpu_baseline.h`: `CpuBaseline`, `k_build_cpu_baseline`, `k_exit_cpu_too_old`, `cpu_baseline_name`, `missing_baseline_features`, `report_cpu_baseline`, `require_cpu_baseline`.
- `core/platform/thread.h`: `pin_current_thread`, `set_current_thread_priority`, `set_current_thread_name`, `current_cpu`, `current_thread_index`, `yield_thread`, `pause_cpu`, `sleep_ms`.
- `core/platform/spin_lock.h`: `SpinLock`, a constant-initializable test-and-test-and-set lock for registries touched during static initialization and for very short critical sections.
- `core/platform/process.h`: `Process` (spawn with piped stdin/stdout, `write`, `read_line`, `read_all`, `wait`, `kill`) and `executable_directory()`. `k_exit_gpu_lock_gave_up` (75) is the exit code of a process that gave up waiting for the machine-wide GPU lock before it used the GPU ([gpu_lock](gpu_lock.md)); **`Process::wait()` ends its caller with the same code** when a child exits with it and the caller takes part in the lock (`ENGINE_GPU_LOCK_ON_DEVICE=1`, which a test's processes inherit), so that an engine-host that gave up under engine-cli under an end-to-end test reaches CTest as that test's skip and not as a failure of whatever engine-cli was asked. Outside a test's tree the code is returned like any other. This module sits below `gpu_lock` and so spells the switch's name out.

**Detection sources.**
- Windows: `GetLogicalProcessorInformationEx(RelationAll)`. Processor groups define the numbering; core records supply SMT and `EfficiencyClass`; cache records supply levels, sizes, line size, and sharing; NUMA and package records supply the rest. Cache domain = the set of CPUs sharing the highest-level non-instruction cache.
- Linux: sysfs (`topology/`, `cache/index*/`, `node*/cpulist`). Efficiency class is a heuristic (max frequency at least 15% below the fastest CPU). Compiled and reviewed but not yet exercised on hardware in this repository; verify on the first Linux build.
- CPUID leaves 0, 1, 7 (subleaves 0 and 1), 0x80000001, and 0x80000002–4; XCR0 via `xgetbv`. LZCNT is read from 0x80000001's ABM bit on both vendors — leaf 7's TZCNT bit is BMI1's and says nothing about LZCNT — and MOVBE from leaf 1. Those two are in `CpuFeatures` because x86-64-v3 contains them and a virtual machine is more likely to mask them off than to mask AVX2.

## The startup check, and why this module gives up the arch flag

[ADR-0031](../adr/0031-minimum-cpu-x86-64-v3.md) made x86-64-v3 the promised minimum CPU. A binary built for it that starts on an older machine dies on an illegal instruction, in a stack frame that says nothing about what happened; `core/platform/cpu_baseline.h` turns that into one line on stderr and exit code `k_exit_cpu_too_old` (78):

```
engine: this build needs x86-64-v3 and this CPU has no AVX, AVX2, FMA, BMI1, BMI2, F16C, LZCNT,
MOVBE (Intel(R) Core(TM) i7 CPU X 980 @ 3.33GHz); rebuild with -DENGINE_CPU_BASELINE=v2 ...
```

Two things make that check safe, and both are properties of the build rather than promises made in a comment:

- **Nothing in this module can be an AVX2 instruction.** `cmake/EngineCpuBaseline.cmake`'s `engine_strip_cpu_baseline(engine_platform)` takes the arch flag back off this one target, so `cpu_baseline.cpp` and the `cpu_features.cpp` it calls are compiled at the floor whatever the rest of the tree is built for. `build/<preset>/compile_commands.json` is where that is checked, and it is the artefact the claim rests on rather than this sentence — on 2026-09-19, 846 of `msvc-release`'s 851 translation units carried `/arch:AVX2` and the five that did not were exactly this module's. Since [ADR-0034](../adr/0034-host-tools-build-for-the-build-machine.md) that reading is a test, `build.cpu_baseline`, run after every build: this module's translation units and the host tools' (`tools/schemac`, which the build runs and never ships) carry no instruction-set flag, and every other one carries all of the baseline's — on 2026-09-22, 849 of 861 at v3, the other twelve being these five and schemac's seven. `dumpbin /SYMBOLS engine_platform.lib` is the second artefact: it shows the `.CRT$XCT` section and `engine_cpu_baseline_init` in it. The module gives up nothing real: CPUID, the topology walk and thread pinning all happen once at start-up, and the rule is one sentence — *the module that decides whether the binary may run is compiled for every machine* — instead of a list of files somebody has to maintain.
- **It runs before anything else can.** Every app's `main()`, the shared test main, and the shared bench main call `require_cpu_baseline()` as their first statement, and `engine_app()`, `engine_test_main` and `engine_bench_main` link `engine::platform` unconditionally so no CMakeLists has to remember. The explicit call is also what pulls this object file out of the static library. On top of it, an initializer in the same translation unit runs the check ahead of every *dynamic initializer* in the binary — `.CRT$XCT` sorts before the `.CRT$XCU` MSVC emits C++ initializers into, and a GCC/Clang `constructor(101)` sorts before the default priority — which is what covers a `static Foo g = expensive();` in a translation unit that *was* compiled with AVX2. Without that half, "the first statement of `main`" would still be after every such initializer — and after `main`'s own prologue, which is generated by a compiler that has been told it may use AVX2. The only code that runs ahead of `.CRT$XCT` is the C runtime's own start-up, which is not compiled with this tree's flags.

The check takes the feature set it judges rather than reading CPUID itself, which is why the interesting case is a unit test (`tests/cpu_baseline_tests.cpp`) and not a machine nobody has: the test hands it a Westmere, a **Sandy Bridge**, a Core 2, a Haswell, and a Haswell with LZCNT and MOVBE masked off the way a hypervisor does, and checks the list of names each produces. The Sandy Bridge case is the project's Linux GPU runner (Xeon E5-2670) and is the one that pins a property the others cannot: it **has** AVX, so the line it prints must not say "no AVX" — the features are checked one at a time rather than in tiers precisely so that a machine which is short of only part of a level is told which part. `require_cpu_baseline()` is four lines on top of that and uses `detect_cpu_features()` rather than the cached `cpu_features()`, because a function-local static reaches for the compiler's thread-safe-statics machinery at a point in start-up where it has no business being asked.

**Untested on GCC and Clang.** The constructor attribute and `-march=x86-64-v2/v3` were written from documented behaviour; hosted CI was unavailable when this landed and no Linux machine here has run them.

**Verified on.** Intel i9-10980XE (36 logical CPUs, 18 cores with SMT, one cache domain, one class). The i9-13980HX laptop (8 P + 16 E cores, hybrid) is the next target and will exercise `efficiency_cpus`.

**Depends on.** `base`, `memory`, `containers`.

**Testing.** `tools/dev.ps1 test -Filter platform`. Tests check the invariants above on whatever machine runs them, that repeated detection is stable, that pinning moves a thread onto the requested CPU, and that CPUID implications hold. `tests/cpu_baseline_tests.cpp` drives the baseline check with forced feature masks: a Westmere against a v3 build names all eight missing features in order and against a v2 build names none; a Core 2 fails even v2; a Haswell passes both; one missing feature is named on its own; a truncated buffer is truncated rather than overrun and still counts in full; and this binary's own `k_build_cpu_baseline` is the one the preset configured. `tests/fault_report_tests.cpp` starts `engine_platform_fault_probe` as a child once for each kind of fatal fault and reads the line its death prints ([below](#every-fatal-fault-prints-one-line)).

**Performance notes.** Cold data. `describe_topology` prints a summary for logs; the job system consumes the structure directly.

## No engine binary opens a dialog when it fails

[error_dialogs.h](../../core/platform/include/core/platform/error_dialogs.h). On Windows a failure is answered with a window by default: the debug runtime's "Debug Error! abort() has been called" with its Abort, Retry and Ignore, the assertion box, and the system's "has stopped working". A window waits for somebody to click it, and a test or a bench run by an agent, by CTest or by CI has nobody: the process stands until the run's timeout and whatever started it stands with it. It happened on 2026-09-28, when a bench of a module still under construction called `abort()` in a debug build and its box sat on the owner's screen while the agent that ran it waited.

`platform::quiet_error_dialogs()` turns each of them into a line on stderr and an exit code. The system's boxes are switched off for the process (`SetErrorMode` with the critical-error, fault and open-file flags); `abort()` keeps its message, which goes to stderr, and skips the hand-off to fault reporting (`_set_abort_behavior`, `_set_error_mode`); and in a debug build the runtime's three report types — warnings, errors, assertions — are sent to stderr as a file (`_CrtSetReportMode`, `_CrtSetReportFile`). **Nothing about what fails or what it exits with changes**; only where the message goes. Switching the fault box off left a fault with no message at all; the handlers that give it one are the next section's, installed beside this function.

It is called from `require_cpu_baseline()`, and so runs where that check runs: before every other dynamic initializer, in every executable that links this module, and again at the top of every `main()`, the test main and the bench main. That reach is why it lives here and not in the test support directory: an end-to-end test starts `engine-view` or `engine-content` as a child, and a box from the child holds the test as surely as one from the test. It is idempotent.

**A developer who wants the box**, to press Retry and land in a debugger, sets `ENGINE_ERROR_DIALOGS=1` in the environment and the process is left as the system made it. The variable is read with `GetEnvironmentVariableA`, since this runs before `main` and the runtime's own table may not be built. On other platforms there is nothing to switch off and the function does nothing. The test (`error_dialogs_tests.cpp`) asks the process what it is set to after the initializer has run, and asserts that no report type opens a window rather than that the mode is exactly this function's: doctest sets the assertion reports to a file and the debugger output for the length of a test case, which is why a test never showed a box and a bench, which has no doctest round it, did.

## Every fatal fault prints one line

`src/fault_report.cpp` (internal; the promise is this section's). **Why it exists**: switching the fault box off left nothing in its place. On 2026-10-03 a debug `engine-view` read past the end of a terrain field (the bound fixed in `2efc7749`) and ended with 0xC0000005 having printed nothing; `tools/gpu-lock.ps1 run`, which it was started under, reported the code as 1, and an agent spent an hour bisecting what one line would have said. Now every fatal fault prints **one line** on stderr and the process ends with the status in the table — measured on 2026-10-04, `msvc-release`:

```
engine: fatal: access violation writing 0x10 at engine_platform_fault_probe.exe+0x25b7 in thread 127788 "fault-worker"; exit code 0xc0000005; stack: engine_platform_fault_probe.exe+0x21fa ucrtbase.dll+0x2cd30 KERNEL32.DLL+0x2cd87 ntdll.dll+0xacaec
engine: fatal: abort() in thread 126752 (main); exit code 3; stack: ucrtbase.dll+0xc2139 ucrtbase.dll+0xa5261 engine_platform_fault_probe.exe+0x291b engine_platform_fault_probe.exe+0xce5f KERNEL32.DLL+0x2cd87 ntdll.dll+0xacaec
```

and in the Linux container, `linux-gcc-release`:

```
engine: fatal: SIGSEGV, address not mapped reading 0x10 at engine_platform_fault_probe+0x2b67 in thread 9674 "engine_platform" (main); signal 11, re-raised; stack: engine_platform_fault_probe+0x29aa libc.so.6+0x2a1ca libc.so.6+0x2a28b engine_platform_fault_probe+0x2a95
```

It says what happened — for a memory fault the address and whether it was read, written or executed — **the faulting instruction as module plus offset**, the thread (its id; the name it gave `set_current_thread_name`, or on Linux the kernel's name for it; `(main)` for the main thread), the exit status, and up to sixteen return addresses above the fault, each as module plus offset too.

| What | Windows: the line says | exit code | Linux: the line says | the parent sees |
|---|---|---|---|---|
| a bad read, write or jump | `access violation reading`, `writing` or `executing <address>` | 0xC0000005 | `SIGSEGV, address not mapped` or `access denied`, then `reading`, `writing` or `executing <address>` | SIGSEGV |
| a mapped file read past its end | `in-page error reading <address>` | 0xC0000006 | `SIGBUS, no such physical address reading <address>` | SIGBUS |
| stack overflow | `stack overflow` | 0xC00000FD | `SIGSEGV, stack overflow` (a fault within 64 KiB of the stack pointer) | SIGSEGV |
| illegal instruction (`ud2`, an instruction the CPU lacks) | `illegal instruction` | 0xC000001D | `SIGILL, illegal instruction` | SIGILL |
| integer divide by zero | `integer divide by zero` | 0xC0000094 | `SIGFPE, integer divide by zero` | SIGFPE |
| `abort()` — and so a failed `ENGINE_ASSERT` or `std::terminate` | `abort()` | 3 | `SIGABRT, abort()` | SIGABRT |
| pure virtual call | `pure virtual function call` | 3 | libstdc++'s own line, then `SIGABRT, abort()` | SIGABRT |
| invalid argument to the C runtime | `invalid parameter passed to the C runtime` (a debug build adds `in <function>`) | 0xC0000409 | — | — |
| any other unhandled exception | its name, or `exception 0x<code>` | its code | — | — |

**The exit statuses are the ones the process had before**: the system ends an unhandled exception with its code, the runtime's `abort()` exits 3 and a pure virtual call ends in it, and the runtime's own invalid-parameter handler fails fast, which exits 0xC0000409 — so nothing that read an exit code reads a different one. On Linux the handler resets the signal to its default action and raises it again, so the parent's `waitpid` says the child died of SIGSEGV, not that it exited (and a core file is written wherever the system writes one).

**What a handler may do, and why so little.** It runs where the process is already broken — a corrupt heap, no stack left, a lock held by the thread that faulted — so it allocates nothing, takes no lock of ours and uses no stdio: the line is built in a static buffer that one thread at a time owns and goes out by `WriteFile` or `write(2)`. A second thread that faults meanwhile waits for the first to end the process; a fault inside the handler ends it at once. The module of an address is the loader's own lookup on Windows (`RtlPcToFileHeader`, which exception dispatch itself uses, and `GetModuleFileNameW` for the name) and `/proc/self/maps` read with `open` and `read` on Linux. The stack is the system's unwinder over the faulting context on Windows (`RtlLookupFunctionEntry` and `RtlVirtualUnwind`), stopping at the first frame outside the thread's stack; on Linux glibc's `backtrace`, which loads libgcc's unwinder on its first call — that call is made at installation, so no handler loads a library. **No symbol library is loaded anywhere**: resolving is afterwards, against the build's symbols. The description is written before the stack is walked, so a walk that faults on a broken stack still leaves the first half of the line.

**Resolving a line.** On Windows the offset is from the image's base (its RVA): `ln engine-view.exe+0x25b7` in WinDbg or cdb with the PDB on the symbol path, or `llvm-symbolizer --obj=engine-view.exe --relative-address 0x25b7`. On Linux it is from the module's mapping at offset 0, which for a position-independent executable or a shared object is the address `addr2line -f -C -e <module> 0x<offset>` takes. Every stack entry after the faulting instruction is a return address, one instruction past its call.

**Windows, in detail.** A top-level exception filter (`SetUnhandledExceptionFilter`), which runs for an exception no frame handled on any thread, and never while a debugger is attached — the debugger is given it first. A C++ exception nobody caught goes on to the runtime's own filter, which calls `std::terminate` and so `abort()`. The runtime's `SIGABRT` handler, `_set_purecall_handler` and `_set_invalid_parameter_handler` cover the three failures that are calls rather than exceptions; their line has no faulting instruction, and the stack starts in the runtime's call. In a debug build the runtime reports `abort()` and an invalid parameter through its own report first (stderr, `quiet_error_dialogs()`), so its text precedes the line there. The main thread gets a 32 KiB stack guarantee (`SetThreadStackGuarantee`) so that a stack overflow there leaves the filter room to walk; on another thread it walks only when 16 KiB remain, and says so when they do not.

**Linux, in detail.** `sigaction` handlers for SIGSEGV, SIGBUS, SIGFPE, SIGILL and SIGABRT, on a 64 KiB alternate stack (`sigaltstack`) for the main thread. A handler somebody installed first — a sanitizer's runtime, a host that embeds the engine — is left alone. Read, write or execute comes from the page fault's error code in the signal's context. A jump into memory that is not code leaves the unwinder nothing to read, so the return address the call left at the stack pointer is the stack's first entry.

**What it cannot catch.** A *fail-fast* ends the process in the kernel without running a handler: on Windows a `/GS` stack-cookie failure, `__fastfail`, and the heap's termination on corruption exit 0xC0000409 or 0xC0000374 with no line, and only a debugger or another process can see them. A stack overflow on a Linux thread other than the main one dies of SIGSEGV with no line, since only the main thread has an alternate stack. **Under a sanitizer** (`msvc-asan`, any `-fsanitize=address`, `thread` or `memory` build) nothing is installed: its report says more. **Release builds carry Tracy**, whose client installs crash handlers of its own over these — on Windows a filter that reports to a connected profiler and otherwise lets the process die silently, on Linux handlers that end every fault in `abort()` — so the build defines `TRACY_NO_CRASH_HANDLER` ([profiling](profiling.md)).

It is installed by `require_cpu_baseline()` once the CPU check has passed, and so has the same reach as `quiet_error_dialogs()`: every executable that links this module, before anything of its own has run. After the check rather than before it, because the handlers use `std::atomic`, and the linker may keep an out-of-line copy of one of its functions from a translation unit compiled for the baseline — which a CPU that fails the check must never run; that CPU gets the check's own line and exit 78. **`ENGINE_ERROR_DIALOGS=1` leaves it out too**, so a developer who asked for the boxes gets the system's answer to a fault — a debugger, Windows Error Reporting, or on Linux the signal's default — as before.

**What holds it.** `tests/fault_report_tests.cpp` starts `engine_platform_fault_probe` (`tests/fault_probe_main.cpp`, one argument per kind) as a child for every row of the table on its platform but the in-page error, and a write through a bad pointer on a worker thread named `fault-worker`, and asserts **exactly one** `engine: fatal:` line, ending in a newline; what it says; that the faulting instruction is the probe's module plus an offset where the instruction is the probe's; the thread (`(main)`, or the worker's name); a stack with the probe in it; and the exit code on Windows, or on Linux the signal the parent's `waitpid` reports — the test starts the probe with `posix_spawn` and waits for it itself there, because `Process::wait()` reports a child that died of a signal as -1. A probe that does not fault prints no such line and exits 0. Before the handlers, every case failed on "one line": in `msvc-release` the probe's read, its worker's write and its `abort()` exited 0xC0000005, 0xC0000005 and 3 having printed nothing. **The probe has to fault in every build**, which an optimizer resists: GCC at `-O2` dropped a division by zero whose quotient went to an unused return value (division has no side effects to it), and turned the worker's last call into a tail call that took the probe's frame off the stack, so the quotient goes to a volatile and the worker does something after the call.
